# Part 38: Channels (mpsc, message passing concurrency)

> โมดูล: ระดับกลาง (Intermediate) | ระดับ: กลาง | เวลาโดยประมาณ: 180 นาที

## เป้าหมายของบทเรียน

หลังจากจบบทนี้ คุณจะสามารถ:

- อธิบายปรัชญา **"don't share state, send messages instead"** ได้อย่างลึกซึ้ง และเชื่อมโยงได้ว่าทำไมการส่ง
  ownership ของค่าผ่าน channel (ซึ่งก็คือการ **move** ตามที่เรียนใน Part 6) ถึงตัดปัญหา data race ออกไปได้
  ตั้งแต่ต้นทาง โดยไม่ต้องพึ่งเครื่องมือ synchronization เพิ่มเติมเลย
- สร้างและใช้ `std::sync::mpsc::channel()` ได้อย่างถูกต้อง: `tx.send(value)`, `rx.recv()`, เข้าใจว่า `.recv()`
  คืน `Result<T, RecvError>` (ตามที่เรียนใน Part 12) และรู้ว่า `Err` หมายถึง "sender ทุกตัวถูก drop แล้ว"
- วนรับข้อความจาก `Receiver<T>` ได้สองแบบ: แบบ manual loop ด้วย `match` บน `.recv()` และแบบ `for` loop ตรง ๆ
  บน `Receiver` เอง (เพราะมัน implement `Iterator` ตามที่เรียนใน Part 25) พร้อมรู้ว่า loop แบบหลังจบเองอัตโนมัติ
  เมื่อ channel ปิด
- สร้าง **multiple producers** ได้ด้วยการ `.clone()` ตัว `Sender<T>` ให้ thread หลายตัวส่งเข้า channel เดียวกัน
  พร้อมเข้าใจ (และพิสูจน์ด้วยการรันจริงหลายรอบ) ว่าลำดับการมาถึงของข้อความจากผู้ส่งต่างคนกันนั้น**ไม่แน่นอน**
- เลือกใช้ `.try_recv()` และ `.recv_timeout()` ได้ถูกสถานการณ์ แทนการ `.recv()` แบบบล็อกตลอดไป
- อธิบายความแตกต่างระหว่าง unbounded channel (`mpsc::channel()`) กับ bounded/synchronous channel
  (`mpsc::sync_channel(bound)`) ได้ พร้อมเหตุผลเชิง memory ว่าทำไม backpressure ถึงสำคัญในระบบจริง
- สร้าง **worker pool pattern** เบื้องต้นด้วย `Arc<Mutex<Receiver<T>>>` เพื่อให้ worker หลายตัวแบ่งงานจาก
  `Receiver` ตัวเดียวกันได้ (พร้อมรู้ตัวว่านี่เป็นการ "ใช้ไปก่อน เข้าใจเหตุผลเต็ม ๆ ทีหลัง" ซึ่งจะอธิบายเต็มรูปแบบ
  ใน Part 39)
- ตัดสินใจได้ว่าเมื่อไหร่ควรเลือก message passing (channels) กับเมื่อไหร่ shared state (Part 39) เหมาะสมกว่า

## ความรู้ที่ต้องมีมาก่อน

- **Part 37 (Threads พื้นฐาน)**: บทนี้ต่อยอดโดยตรงจาก `std::thread::spawn`, `move` closure ที่บังคับใช้กับ
  thread (เพราะ closure ต้อง `'static`), และ `.join()` เพื่อรอ thread ทำงานจบ — ถ้ายังไม่คุ้นกับสามสิ่งนี้
  ให้กลับไปทวน Part 37 ก่อน เพราะบทนี้จะไม่สอนพื้นฐานพวกนั้นซ้ำอีก Part 37 ปิดท้ายด้วยการเกริ่นว่าการแก้ปัญหา
  "หลาย thread ต้องแบ่งปันข้อมูลกัน" มีสองทางหลัก คือ **ส่งข้อความ (message passing — บทนี้)** และ **แบ่งปัน
  memory ร่วมกันอย่างปลอดภัย (shared state ด้วย `Mutex`/`Arc` — Part 39)** บทนี้คือทางเลือกแรก
- **Part 6 (Ownership)**: หัวใจของ channel ทั้งบทคือการ "ส่งค่าไปให้ thread อื่น" ซึ่งในทาง Rust ก็คือการ **move**
  ownership ธรรมดา ๆ ที่เรียนมาแล้ว — บทนี้แค่เปลี่ยนบริบทจาก "move ระหว่างตัวแปรในฟังก์ชันเดียว" เป็น "move ข้าม
  thread ผ่านช่องสัญญาณ" เท่านั้นเอง กลไกและกฎเบื้องหลังเหมือนกันทุกอย่าง
- **Part 12 (Result และ Error Handling)**: `.recv()` คืน `Result<T, RecvError>` และ `.try_recv()`/
  `.recv_timeout()` คืน `Result<T, TryRecvError>`/`Result<T, RecvTimeoutError>` — ต้องคุ้นกับการ `match` บน
  `Result` และความหมายของ `Ok`/`Err` มาก่อน
- **Part 25 (Iterators เบื้องต้น)**: หัวข้อ 38.4 จะใช้ข้อเท็จจริงที่ว่า `Receiver<T>` implement `Iterator` (และ
  `IntoIterator`) ทำให้เขียน `for received in rx { ... }` ได้ตรง ๆ — ต้องเข้าใจว่า `for` loop desugar เป็นการเรียก
  `.next()` วนซ้ำเรื่อย ๆ จนกว่าจะได้ `None` มาก่อน (ตามที่เรียนใน Part 25) จึงจะเข้าใจว่าทำไม loop แบบนี้ถึง "จบ
  เองอัตโนมัติ" เมื่อ channel ปิด
- **Part 21/24 (Trait Objects, Closures)**: หัวข้อ worker pool (38.8) และ pipeline ตัวอย่างจริง (38.10) ใช้
  `Box<dyn FnOnce() + Send + 'static>` เป็น "งาน" ที่ส่งผ่าน channel — ต้องเข้าใจว่า `dyn FnOnce()` คือ trait object
  ของ closure ที่เรียกได้ครั้งเดียว และทำไมต้องห่อด้วย `Box` เพื่อให้มีขนาดคงที่ ณ compile time (ตามที่เรียนใน
  Part 21 และ Part 27 เรื่อง `Box<T>`)

## เนื้อหา

### 38.1 ปรัชญา Message Passing: "Don't Share State, Send Messages Instead"

Part 37 ปิดท้ายด้วยคำถามที่ยังไม่มีคำตอบ: เมื่อ thread หลายตัวต้อง**ทำงานร่วมกัน** (ไม่ใช่แค่ทำงานแยกกันอย่าง
อิสระ) จะให้มันสื่อสารกันได้อย่างไรโดยไม่เกิด **data race** — สถานการณ์ที่ thread สองตัวหรือมากกว่าเข้าถึง memory
ตำแหน่งเดียวกัน**ในเวลาเดียวกัน** โดยที่อย่างน้อยหนึ่งใน operation นั้นเป็นการเขียน ซึ่งในภาษาที่ไม่มีการป้องกัน
(เช่น C/C++) จะทำให้ผลลัพธ์**ไม่แน่นอน** (undefined behavior) ขึ้นอยู่กับว่า thread ไหนได้ CPU ก่อน — บั๊กประเภทนี้
ขึ้นชื่อว่า debug ยากที่สุดในโปรแกรมมิ่งทั้งหมด เพราะมันไม่ reproduce ซ้ำแบบเดิมทุกครั้ง (บางครั้งรันแล้วผ่าน
บางครั้งรันแล้ว crash โดยไม่มีอะไรเปลี่ยนในโค้ดเลย)

มีสองวิธีหลักในการแก้ปัญหานี้ในทางวิศวกรรมซอฟต์แวร์ทั่วโลก:

1. **Shared-state concurrency**: ยอมให้ thread หลายตัวเข้าถึง memory ก้อนเดียวกันได้ แต่ใส่ "กลไกป้องกัน"
   (เช่น lock/mutex) ที่บังคับว่า **ในเวลาหนึ่ง ๆ มีแค่ thread เดียวเท่านั้นที่แก้ไขข้อมูลนั้นได้** — นี่คือแนวทาง
   ที่ภาษาส่วนใหญ่ (C++, Java, Go เมื่อใช้ shared memory) และ Rust เองก็รองรับผ่าน `Mutex<T>`/`Arc<T>` ซึ่งเป็น
   เนื้อหาของ **Part 39**
2. **Message-passing concurrency**: **ไม่ให้ thread ไหนเข้าถึง memory ก้อนเดียวกันพร้อมกันเลย** แต่ให้ thread
   สื่อสารกันด้วยการ **ส่งค่าที่เป็นเจ้าของทั้งหมด (owned value) ไปให้กันตรง ๆ ผ่านช่องสัญญาณ (channel)** — เมื่อ
   thread A ส่งค่าไปให้ thread B, **ownership ของค่านั้นย้ายจาก A ไป B ทันที** (มันคือการ **move** แบบเดียวกับที่
   เรียนใน Part 6 เป๊ะ ๆ ไม่มีอะไรพิเศษเพิ่ม) พอค่านั้นอยู่ในมือ B แล้ว A ก็ **ไม่มีทางแตะมันได้อีก** เพราะ compiler
   บังคับกฎ ownership เดิมทุกอย่าง — ผลคือ **ไม่มีช่วงเวลาไหนเลยที่ A และ B จะเข้าถึงค่าเดียวกันพร้อมกัน** เพราะ
   ownership เป็นของฝ่ายใดฝ่ายหนึ่งเสมอ ไม่ใช่ทั้งสองฝ่ายพร้อมกัน

แนวคิดที่สองนี้ Rust ไม่ได้คิดขึ้นเอง แต่**สืบทอดมาจากภาษาอย่าง Erlang** (ที่ใช้ message passing เป็นกลไกหลักของ
concurrency ทั้งภาษามาตั้งแต่ปี 1986 เพื่อสร้างระบบโทรคมนาคมที่ต้อง reliable สูงมาก) และ **Go** (ที่ทำให้แนวคิดนี้
เป็นที่นิยมกว้างขวางขึ้นผ่าน channel และ goroutine พร้อม motto ที่โด่งดัง **"Do not communicate by sharing memory;
instead, share memory by communicating"**) — Rust หยิบแนวคิดเดียวกันนี้มาใส่ไว้ใน standard library ภายใต้โมดูล
`std::sync::mpsc` (mpsc ย่อมาจาก **m**ultiple **p**roducer, **s**ingle **c**onsumer ซึ่งจะอธิบายความหมายในหัวข้อ
ต่อไป) และเพราะ Rust มี ownership system ที่บังคับโดย compiler อยู่แล้ว **message passing ใน Rust จึงปลอดภัยกว่า
ใน Go หรือ Erlang อีกขั้นหนึ่ง**: ใน Go คุณยังสามารถส่ง pointer ผ่าน channel แล้วยังเก็บ pointer ตัวเดิมไว้ใช้ต่อ
ที่ฝั่งผู้ส่งได้ (ทำให้เกิด data race แอบแฝงได้ถ้าไม่ระวัง) แต่ใน Rust **การส่งค่าผ่าน channel คือการ move ที่
compiler ตรวจสอบ** — ถ้าคุณพยายามใช้ค่าที่ส่งไปแล้วต่อที่ฝั่งผู้ส่ง compiler จะปฏิเสธการ compile ตั้งแต่ต้น (จะ
เห็นตัวอย่าง error จริงนี้ในหัวข้อ "กับดักที่พบบ่อย")

นี่คือเหตุผลเชิงลึกว่าทำไม message passing มักถูกมองว่า **"คิดง่ายกว่า" (easier to reason about)** เมื่อเทียบกับ
shared-state: คุณไม่ต้องถามตัวเองตลอดเวลาว่า **"ตอนนี้มี thread อื่นกำลังแก้ไขข้อมูลนี้อยู่หรือไม่"** เพราะคำตอบ
คือ **"เป็นไปไม่ได้อยู่แล้ว — ข้อมูลนี้มีเจ้าของแค่คนเดียว ณ เวลาใดเวลาหนึ่งเสมอ"** ความซับซ้อนทั้งหมดเรื่อง
synchronization (lock, race condition, deadlock จาก lock หลายตัว) ที่ยังต้องเจอใน shared-state concurrency
ถูกแทนที่ด้วยคำถามที่ตรงไปตรงมากว่า: **"ใครควรเป็นเจ้าของข้อมูลนี้ ณ จุดนี้ในโปรแกรม"** ซึ่งเป็นคำถามแบบเดียวกับ
ที่คุณตอบมาตลอดตั้งแต่ Part 6 อยู่แล้ว เพียงแค่ตอนนี้ "การส่งต่อ ownership" เกิดขึ้นข้าม thread เท่านั้นเอง

แต่ก็ต้องพูดตรง ๆ ว่า message passing **ไม่ใช่คำตอบสำหรับทุกสถานการณ์** — บางครั้ง thread หลายตัวจำเป็นต้อง
**อ่าน/เขียนโครงสร้างข้อมูลเดียวกันที่มีอายุยาว** (เช่น cache ที่ทุก thread ต้องเห็นค่าล่าสุดตรงกัน หรือ counter
ที่นับรวมจากทุก thread) ซึ่งถ้าจะทำผ่าน message passing อย่างเดียวจะต้องส่งข้อความไปมาจำนวนมากเพื่อ "ถาม-ตอบ"
สถานะของข้อมูลนั้นตลอดเวลา ซึ่งช้าและซับซ้อนกว่าการแบ่งปัน memory ตรง ๆ ผ่าน `Mutex` — เราจะเจาะลึกการตัดสินใจ
เลือกระหว่างสองแนวทางนี้อย่างเป็นระบบในหัวข้อ 38.9 หลังจากเรียนเครื่องมือของทั้งสองแนวทางครบแล้ว (Part 39 สำหรับ
shared-state)

### 38.2 `std::sync::mpsc::channel()`: หัวใจของ Message Passing ใน Rust

`mpsc` ในชื่อโมดูลย่อมาจาก **multiple producer, single consumer** — บอกโครงสร้างของ channel ไว้ตรง ๆ ในชื่อเลย:
**ส่งเข้าได้จากหลาย thread (multiple producer/sender)** แต่ **รับออกได้จาก thread เดียวเท่านั้น (single
consumer/receiver)** เราจะเห็นว่าทำไมข้อจำกัดนี้สมเหตุสมผลในหัวข้อ 38.5 และจะเห็นวิธี "โกง" ข้อจำกัดฝั่ง consumer
ด้วย `Arc<Mutex<Receiver<T>>>` ในหัวข้อ 38.8

ฟังก์ชัน `mpsc::channel::<T>()` สร้าง**คู่ของสองสิ่ง** กลับมาเป็น tuple: `(Sender<T>, Receiver<T>)`

```rust
use std::sync::mpsc;

fn main() {
    let (tx, rx): (mpsc::Sender<String>, mpsc::Receiver<String>) = mpsc::channel();
    println!("สร้าง channel สำเร็จ: มี Sender และ Receiver คนละตัว");
    // (ตัวแปรทั้งสองยังไม่ได้ใช้งานจริงในตัวอย่างนี้ — แค่โชว์ type)
    let _ = tx;
    let _ = rx;
}
```

สังเกตชื่อตัวแปรที่ใช้กันเป็นธรรมเนียมในโค้ด Rust แทบทุกที่: **`tx`** (ย่อจาก **transmit**, ฝั่งส่ง) และ **`rx`**
(ย่อจาก **receive**, ฝั่งรับ) — ชื่อนี้มาจากศัพท์วิศวกรรมโทรคมนาคม (เหมือนขา TX/RX บนสาย serial port) และกลายเป็น
convention ที่ใช้กันแพร่หลายมากในโค้ด Rust ที่เกี่ยวกับ channel จนควรทำตามเพื่อให้คนอ่านโค้ดคุ้นตาทันที

ปกติเราไม่ต้องระบุ type ให้ตรง ๆ แบบตัวอย่างข้างบน (นั่นแค่โชว์ให้เห็น type จริง) — Rust จะ **infer type ของ `T`**
จากการใช้งานครั้งแรกที่เรียก `.send()` หรือจาก type annotation ตรงจุดอื่นในโค้ด:

```rust
use std::sync::mpsc;

fn main() {
    let (tx, rx) = mpsc::channel(); // ยังไม่รู้ T ตอนนี้

    tx.send(42).unwrap(); // compiler เห็น 42 (i32) ตรงนี้ จึง infer ว่า T = i32
    tx.send(100).unwrap();

    println!("{:?}", rx.recv());
    println!("{:?}", rx.recv());
}
```

สอง method ที่สำคัญที่สุดของบทนี้คือ:

- **`tx.send(value)`** — ส่งค่า `value` เข้า channel คืนค่าเป็น `Result<(), SendError<T>>` (จะ `Err` ก็ต่อเมื่อ
  `Receiver` ทุกตัวถูก drop ไปแล้ว ไม่มีใครรอรับข้อความนี้อีกต่อไป) จุดที่สำคัญที่สุดต้องเน้นย้ำคือ: **`.send()`
  รับ `value` โดย value (ไม่ใช่ reference) จึงเป็นการ move ค่านั้นเข้าไปในกลไกภายในของ channel ทันที** —
  หลังจากเรียก `.send(value)` แล้ว **ตัวแปร `value` เดิมจะใช้ต่อไม่ได้อีก** เพราะ ownership ของมันย้ายไปแล้ว
  (เดี๋ยวเราจะเห็น error จริงของกรณีที่ลืมกฎนี้ในหัวข้อ "กับดักที่พบบ่อย")
- **`rx.recv()`** — **บล็อกการทำงานของ thread ปัจจุบันไว้จนกว่าจะมีข้อความมาถึง** (ถ้า channel ว่างอยู่ ณ ขณะนั้น
  thread ที่เรียก `.recv()` จะหยุดรอ ไม่ทำงานอะไรต่อ ไม่กิน CPU แบบ busy-loop) คืนค่าเป็น **`Result<T, RecvError>`**
  ตามที่เรียนมาใน Part 12 — `Ok(value)` เมื่อมีข้อความมาถึงจริง และ **`Err(RecvError)` มีความหมายเจาะจงมาก: "sender
  ทุกตัวที่เชื่อมกับ channel นี้ถูก drop ไปหมดแล้ว ไม่มีทางที่จะมีข้อความใหม่เข้ามาอีกต่อไปเลย"** — นี่ไม่ใช่ error
  ทั่วไปที่แปลว่า "มีอะไรผิดพลาด" แต่เป็นสัญญาณบอกสถานะที่ชัดเจนว่า "จบการสื่อสารแล้วอย่างสมบูรณ์"

มาดูตัวอย่างที่พิสูจน์ความหมายของ `Err(RecvError)` ให้เห็นชัด ๆ (โค้ดนี้รันจริงและได้ผลตามที่อธิบาย):

```rust
use std::sync::mpsc;

fn main() {
    let (tx, rx): (mpsc::Sender<i32>, mpsc::Receiver<i32>) = mpsc::channel();
    drop(tx); // drop sender ทันที ไม่ส่งอะไรเลย — บอก channel ว่า "ไม่มีใครจะส่งอะไรมาอีกแล้ว"

    match rx.recv() {
        Ok(v) => println!("ได้รับ: {v}"),
        Err(e) => println!("เกิด error: {e}"),
    }

    println!("Debug: {:?}", rx.recv());
}
```

ผลลัพธ์จริงจากการรัน:

```
เกิด error: receiving on a closed channel
Debug: Err(RecvError)
```

สังเกตว่า `RecvError` implement `Display` ให้ข้อความที่อ่านง่าย (`"receiving on a closed channel"`) และ
`Debug` ให้ชื่อ type ตรง ๆ (`RecvError` เป็น unit struct ไม่มีข้อมูลข้างในเลย เพราะมันมีความหมายแค่แบบเดียวเท่านั้น
คือ "ไม่มี sender เหลือแล้ว" ไม่มีเหตุผลอื่นที่ทำให้ `.recv()` fail ได้อีก) — และสังเกตว่าเราเรียก `rx.recv()` ได้
**สองครั้ง** โดยครั้งที่สองก็ยังได้ `Err` เหมือนกัน (ไม่ panic ไม่ crash) เพราะสถานะ "channel ปิดแล้ว" เป็นสถานะ
ที่ถาวร ไม่มีทางกลับมาเป็น "เปิด" อีก

จุดที่ควรสังเกตให้ดีคือ **drop(tx) ในตัวอย่างนี้ทำให้ `rx.recv()` คืนค่า `Err` แทบจะทันที ไม่บล็อกรอเลย** เพราะ
compiler รู้ทันทีว่าไม่มีทางมีข้อความใหม่เข้ามาแล้ว — นี่ต่างจากสถานการณ์ที่ยังมี `Sender` เหลืออยู่แต่ยังไม่ได้ส่ง
อะไรเลย ซึ่ง `.recv()` จะ **บล็อกรอตลอดไป** (ไม่มี timeout) จนกว่าจะมีคนส่งข้อความมา หรือ sender ตัวสุดท้ายถูก drop
— นี่คือต้นเหตุของ pitfall ที่พบบ่อยที่สุดในบทนี้ (deadlock จากการรอข้อความที่ไม่มีวันมาถึง) ซึ่งจะสาธิตให้เห็นจริง
ในหัวข้อ "กับดักที่พบบ่อย"

#### `tx.send()` ก็คืน `Result` เหมือนกัน — และค่าที่ส่งไม่สำเร็จก็ไม่ได้หายไปไหน

เรามักโฟกัสที่ `.recv()` ว่าคืน `Result` เพราะมันมี pattern การใช้งานที่เห็นชัดกว่า แต่อย่าลืมว่า **`tx.send(value)`
ก็คืน `Result<(), SendError<T>>` เช่นกัน** ไม่ใช่ `()` เปล่า ๆ — มันจะ `Err` ก็ต่อเมื่อ **`Receiver` ถูก drop ไป
แล้ว** (สถานการณ์กลับกันกับ `RecvError` ที่เกิดจาก `Sender` ถูก drop ทั้งหมด) เช่นสถานการณ์ที่ main thread หมด
ความสนใจในผลลัพธ์แล้ว เลิกรอและปล่อยให้ `rx` หลุด scope ไป ในขณะที่ thread ลูกยังพยายามส่งข้อความต่อไปอยู่:

```rust
use std::sync::mpsc;

fn main() {
    let (tx, rx) = mpsc::channel::<String>();
    drop(rx); // drop receiver ก่อน - ไม่มีใครจะรับข้อความนี้ได้อีกแล้ว

    match tx.send("ข้อมูลสำคัญ".to_string()) {
        Ok(()) => println!("ส่งสำเร็จ"),
        Err(e) => println!("ส่งไม่สำเร็จ แต่ค่ายังไม่หายไปไหน กู้กลับมาได้: {}", e.0),
    }
}
```

ผลลัพธ์จริงจากการรัน:

```
ส่งไม่สำเร็จ แต่ค่ายังไม่หายไปไหน กู้กลับมาได้: ข้อมูลสำคัญ
```

จุดที่น่าสนใจมากคือ **`SendError<T>` เป็น tuple struct ที่เก็บค่า `T` ที่ส่งไม่สำเร็จเอาไว้ข้างใน (`e.0`)** —
ต่างจาก error ทั่วไปที่มักบอกแค่ "เกิดอะไรขึ้น" แล้วปล่อยให้ค่าตั้งต้นสูญหายไปเฉย ๆ (เพราะมันถูก move เข้า
`.send()` ไปแล้ว) การออกแบบ `SendError<T>` ให้ **คืนค่าที่ส่งไม่สำเร็จกลับมาด้วย** สอดคล้องกับหลักการที่ Rust
ยึดมาตลอดทั้งหลักสูตร: **การ move ไม่ควรทำให้ข้อมูลสูญหายไปอย่างไม่มีทางกู้กลับ ถ้ามันล้มเหลว** ในโค้ด production
ที่ต้องมั่นใจว่าไม่มีข้อมูลตกหล่นหาย (เช่น queue งานที่ต้อง retry หรือเก็บ log เมื่อส่งไม่สำเร็จ) ความสามารถนี้
สำคัญมาก — เทียบกับถ้า `.send()` แค่คืน `Result<(), ()>` เฉย ๆ (ไม่เก็บค่ากลับมา) ผู้เรียกจะไม่มีทางรู้เลยว่าค่า
อะไรที่ส่งไม่สำเร็จ ต้องจดจำเองจากภายนอก ซึ่งเสี่ยงพลาดกว่ามาก

ในโค้ดตัวอย่างส่วนใหญ่ของบทนี้ที่เขียน `tx.send(value).unwrap()` ตรง ๆ นั้นยอมรับได้ในบริบทตัวอย่าง/prototype
(ตามเกณฑ์ที่เรียนมาใน Part 11 เรื่องเมื่อไหร่ `.unwrap()` ยอมรับได้) เพราะเรารู้แน่ชัดว่า `Receiver` ยังมีชีวิตอยู่
ตลอดช่วงที่ thread ทำงาน แต่ **ในโค้ด production ที่ปลายทางของ `Receiver` อาจเลิกรอไปก่อนเวลา (เช่น ผู้ใช้ยกเลิก
คำขอกลางทาง)** การ `.unwrap()` ตรงนี้จะทำให้ thread ที่กำลังส่งข้อความ panic ไปด้วย — ควร `match`/`if let Err`
จัดการอย่างเหมาะสมแทน (เช่น หยุดส่งข้อความที่เหลือแล้วจบ thread ไปอย่างสงบ) ซึ่งจะเห็นสถานการณ์นี้เกิดขึ้นจริงใน
หัวข้อ "กับดักที่พบบ่อย"

### 38.3 ตัวอย่างพื้นฐาน: ส่งข้อความข้าม Thread ด้วย `move` Closure

มาดูตัวอย่างที่ใช้ channel ร่วมกับ `thread::spawn` จริง ๆ ตามที่เรียนมาใน Part 37 — spawn thread หนึ่งตัวให้ส่ง
ข้อความหลายชิ้น ส่วน main thread รับและพิมพ์ออกมา:

```rust
use std::sync::mpsc;
use std::thread;

fn main() {
    let (tx, rx) = mpsc::channel();

    let sender_handle = thread::spawn(move || {
        let messages = vec!["สวัสดี", "จาก", "thread", "ลูก"];
        for msg in messages {
            println!("[thread ลูก] กำลังส่ง: {msg}");
            tx.send(msg.to_string()).unwrap();
        }
        println!("[thread ลูก] ส่งครบแล้ว จบการทำงาน");
    });

    for received in rx {
        println!("[main] ได้รับ: {received}");
    }

    sender_handle.join().unwrap();
}
```

ผลลัพธ์จริงจากการรัน (ลำดับนี้คงที่ในตัวอย่างนี้ เพราะมี producer เพียงตัวเดียว — ต่างจากหัวข้อ 38.5 ที่จะมีหลาย
producer และลำดับจะไม่คงที่):

```
[thread ลูก] กำลังส่ง: สวัสดี
[thread ลูก] กำลังส่ง: จาก
[thread ลูก] กำลังส่ง: thread
[thread ลูก] กำลังส่ง: ลูก
[thread ลูก] ส่งครบแล้ว จบการทำงาน
[main] ได้รับ: สวัสดี
[main] ได้รับ: จาก
[main] ได้รับ: thread
[main] ได้รับ: ลูก
```

**อธิบายทีละส่วน:**

- `thread::spawn(move || { ... })` — สังเกตคำว่า **`move`** อยู่หน้า closure ตรงกับที่เรียนใน Part 37 ว่า
  closure ที่ส่งเข้า `thread::spawn` ต้องมี bound เป็น `'static` (ไม่ borrow อะไรจาก scope ภายนอกเลย) เพราะ Rust
  ไม่รู้ว่า thread ใหม่จะทำงานอยู่นานกว่า thread ที่ spawn มันหรือไม่ — `move` บังคับให้ closure **ยึด ownership**
  ของทุกตัวแปรที่มันใช้จากภายนอก (ในที่นี้คือ `tx`) เข้าไปข้างในตัวมันเองทั้งหมด **`tx` ที่ประกาศไว้ใน main จึงถูก
  ย้าย (move) เข้าไปอยู่ใน closure ของ thread ลูกอย่างสมบูรณ์** — หลังจากบรรทัดนี้ main thread **ไม่มี `tx` เหลือ
  ให้ใช้อีกแล้ว** (สังเกตว่าโค้ดข้างบนไม่มีการเรียก `tx.send()` ที่ main thread เลย เพราะทำไม่ได้อีกต่อไป)
- ข้างใน closure วนส่งข้อความ 4 ชิ้นด้วย `tx.send(msg.to_string())` — แต่ละครั้งที่เรียก `.send()` คือการ **move**
  `String` ตัวใหม่ (จาก `.to_string()`) เข้าไปในกลไกภายในของ channel — เมื่อ main thread เรียก `rx.recv()`
  (ผ่าน `for` loop ที่จะอธิบายในหัวข้อถัดไป) ownership ของ `String` นั้นก็ย้ายมาเป็นของ main thread ต่อ ทั้ง
  กระบวนการนี้**ไม่มี clone หรือ copy ข้อมูลจริงเกิดขึ้นเลย** (ยกเว้น pointer/length/capacity ภายในของ `String`
  เอง ซึ่งเป็นต้นทุนคงที่เล็กมาก ไม่ขึ้นกับความยาวของสตริง) — นี่คือประโยชน์เชิง performance ที่มาพร้อมกับความ
  ปลอดภัยแบบ "ฟรี" ของ move semantics ที่เรียนมาตั้งแต่ Part 6
- `for received in rx { ... }` — นี่คือการวนรับข้อความแบบสั้นที่สุด จะอธิบายเจาะลึกในหัวข้อ 38.4
- `sender_handle.join().unwrap()` — รอให้ thread ลูกทำงานจบสมบูรณ์ก่อนที่ main จะจบ ตามหลักที่เรียนมาใน Part 37
  (ถ้าไม่ `.join()` โปรแกรมอาจจบไปก่อนที่ thread ลูกจะพิมพ์บรรทัดสุดท้ายเสร็จ แม้ในตัวอย่างนี้ `for received in rx`
  จะบล็อกรอจนกว่า channel ปิดอยู่แล้ว ทำให้ `.join()` แทบจะคืนทันทีเมื่อถึงจุดนั้น แต่การเขียน `.join()` เสมอเป็น
  นิสัยที่ดี — เพื่อความชัดเจนว่าเราตั้งใจรอ thread ให้จบจริง ๆ ไม่ใช่บังเอิญรอเพราะกลไกอื่น)

### 38.4 วนรับข้อความด้วย `for` Loop บน `Receiver`: เพราะมันคือ Iterator

Part 25 สอนไปแล้วว่า `for` loop ใน Rust ไม่ได้เป็น syntax พิเศษที่ผูกติดกับ `Vec`/array เท่านั้น แต่ทำงานกับอะไรก็ตาม
ที่ implement trait `IntoIterator` — และ **`Receiver<T>` ก็ implement `Iterator` (ผ่าน `IntoIterator`) ให้มา
โดยตรงจาก standard library** โดยมีพฤติกรรมที่ตรงไปตรงมามาก: **`.next()` ของมันก็คือการเรียก `.recv()` แล้ว
แปลง `Result<T, RecvError>` เป็น `Option<T>`** — `Ok(value)` กลายเป็น `Some(value)`, และ `Err(RecvError)`
กลายเป็น `None` (นึกถึง Part 12 ที่สอน `.ok()` แปลง `Result<T, E>` เป็น `Option<T>` — ภายในกลไกของ `Receiver`
ก็ทำสิ่งที่คล้ายกันนี้เอง)

นี่คือเหตุผลที่ `for received in rx { ... }` **จบ loop เองโดยอัตโนมัติเมื่อ channel ปิด** (เมื่อ sender ทุกตัว
ถูก drop) — ไม่ต้องเขียนเงื่อนไข break เองเลย เพราะกลไกของ `for` loop ที่ desugar เป็นการเรียก `.next()` ซ้ำ ๆ
จนกว่าจะได้ `None` (ตามที่เรียนใน Part 25) นั้น**ตรงกับพฤติกรรมที่เราต้องการเป๊ะ ๆ อยู่แล้ว**: "รับข้อความไปเรื่อย ๆ
จนกว่าจะไม่มีข้อความให้รับอีกแล้วอย่างถาวร"

มาเทียบสองรูปแบบเคียงกันเพื่อเห็นความต่างชัด ๆ — แบบแรกคือ **manual loop** ด้วย `match` บน `.recv()` ตรง ๆ:

```rust
use std::sync::mpsc;
use std::thread;

fn main() {
    let (tx, rx) = mpsc::channel();
    thread::spawn(move || {
        for i in 1..=3 {
            tx.send(i).unwrap();
        }
        println!("[thread ลูก] ส่งครบ 3 ข้อความแล้ว - closure จบ, tx ถูก drop อัตโนมัติ");
    });

    loop {
        match rx.recv() {
            Ok(value) => println!("ได้รับ: {value}"),
            Err(_) => {
                println!("ช่องสัญญาณถูกปิดแล้ว (sender ทั้งหมดถูก drop แล้ว) - เลิกวนลูป");
                break;
            }
        }
    }
}
```

ผลลัพธ์จริง:

```
[thread ลูก] ส่งครบ 3 ข้อความแล้ว - closure จบ, tx ถูก drop อัตโนมัติ
ได้รับ: 1
ได้รับ: 2
ได้รับ: 3
ช่องสัญญาณถูกปิดแล้ว (sender ทั้งหมดถูก drop แล้ว) - เลิกวนลูป
```

(หมายเหตุ: ในการรันจริง บรรทัด `"[thread ลูก] ส่งครบ 3 ข้อความแล้ว..."` อาจปรากฏก่อนหรือหลังบรรทัด `"ได้รับ: 1"`
สลับกันได้เล็กน้อย ขึ้นกับ OS scheduler ว่าให้ thread ไหนได้ CPU ก่อน — แต่ลำดับของ `"ได้รับ: 1"`, `"ได้รับ: 2"`,
`"ได้รับ: 3"` จะเรียงตามลำดับที่ส่งเสมอ เพราะ mpsc channel การันตี **FIFO (First-In-First-Out) สำหรับข้อความจาก
sender ตัวเดียวกัน** — นี่คือการันตีสำคัญที่ต่างจากกรณีหลาย sender ในหัวข้อถัดไป)

สังเกตว่า `.recv()` คืน `Result<i32, RecvError>` เราจึง `match` ได้ตรง ๆ ทั้งสองกรณี — `Ok(value)` เอาค่ามาใช้
พิมพ์ ส่วน `Err(_)` (ไม่สนใจรายละเอียด error เพราะมีความหมายเดียวเท่านั้น) ให้ `break` ออกจาก `loop`

ทีนี้มาดูรูปแบบที่สอง คือใช้ `for received in rx` ตรง ๆ (แบบเดียวกับหัวข้อ 38.3):

```rust
use std::sync::mpsc;
use std::thread;

fn main() {
    let (tx, rx) = mpsc::channel();
    thread::spawn(move || {
        for i in 1..=3 {
            tx.send(i).unwrap();
        }
    });

    for received in rx {
        println!("ได้รับ: {received}");
    }
    println!("loop จบเองแล้ว เพราะ channel ปิด (ไม่ต้องเขียน break เอง)");
}
```

โค้ดสองแบบนี้ **ให้ผลลัพธ์ที่เทียบเท่ากันทุกประการ** แต่แบบที่สองกระชับกว่ามาก — นี่คือเหตุผลที่ในโค้ด Rust จริง
เราเห็น `for received in rx` บ่อยกว่า manual loop มาก **ยกเว้นกรณีที่ต้องการควบคุมพฤติกรรมเพิ่มเติมระหว่างรอ**
เช่น ต้องการ timeout (หัวข้อ 38.6), ต้องการทำอย่างอื่นสลับไปด้วยระหว่างรอ, หรือต้องการแยกแยะ error หลายแบบ (เช่น
`try_recv()` ที่มี `Err` สองความหมายต่างกัน) — กรณีเหล่านี้ manual `match` ยังจำเป็นอยู่ เพราะ `for` loop บน
iterator ไม่มีทางสื่อสารเรื่อง "ทำไมถึงหยุด" กลับมาได้ (มันรู้แค่ `Some`/`None` เท่านั้น ไม่รู้จัก `RecvError` เลย
เพราะมันถูกแปลงทิ้งไปแล้วตอน `.next()`)

### 38.5 Multiple Producers: `Sender<T>` implement `Clone`

ตัวอักษร "mp" ใน `mpsc` (multiple producer) หมายความว่า **`Sender<T>` implement trait `Clone`** — เรา clone
`Sender` ตัวเดิมให้กลายเป็น handle หลายตัวที่ **ทุกตัวชี้ไปที่ channel เดียวกัน** ทำให้ thread หลายตัวส่งข้อความ
เข้า channel เดียวกันได้พร้อม ๆ กัน โดยที่ทุกข้อความยังไปรวมกันที่ `Receiver` ตัวเดียวเหมือนเดิม (ต่างจาก
`Receiver<T>` ที่**ไม่** implement `Clone` — จะเห็น error จริงของการพยายาม clone `Receiver` ในหัวข้อ "กับดักที่
พบบ่อย")

```rust
use std::sync::mpsc;
use std::thread;
use std::time::Duration;

fn main() {
    let (tx, rx) = mpsc::channel();

    let mut handles = vec![];
    for worker_id in 1..=3 {
        let tx_clone = tx.clone(); // clone Sender ให้ thread นี้เป็นเจ้าของ handle ของตัวเอง
        let handle = thread::spawn(move || {
            for msg_num in 1..=3 {
                let message = format!("worker-{worker_id}-msg-{msg_num}");
                tx_clone.send(message).unwrap();
                thread::sleep(Duration::from_millis(3));
            }
        });
        handles.push(handle);
    }
    drop(tx); // สำคัญมาก: drop ตัวต้นฉบับด้วย ไม่งั้น channel จะไม่ปิดแม้ clone ทุกตัวจะถูก drop ไปแล้ว

    for received in rx {
        println!("{received}");
    }

    for handle in handles {
        handle.join().unwrap();
    }
}
```

ผลลัพธ์จากการรันจริง **3 รอบติดกัน** (ตั้งใจรันซ้ำหลายครั้งเพื่อพิสูจน์ข้อเท็จจริงเรื่องลำดับที่ไม่แน่นอน ไม่ใช่แค่
สมมติเอาเอง):

รอบที่ 1:
```
worker-2-msg-1
worker-1-msg-1
worker-3-msg-1
worker-2-msg-2
worker-3-msg-2
worker-1-msg-2
worker-3-msg-3
worker-1-msg-3
worker-2-msg-3
```

รอบที่ 2:
```
worker-1-msg-1
worker-2-msg-1
worker-3-msg-1
worker-2-msg-2
worker-1-msg-2
worker-3-msg-2
worker-2-msg-3
worker-1-msg-3
worker-3-msg-3
```

รอบที่ 3:
```
worker-3-msg-1
worker-1-msg-1
worker-2-msg-1
worker-1-msg-2
worker-2-msg-2
worker-3-msg-2
worker-1-msg-3
worker-2-msg-3
worker-3-msg-3
```

สังเกตให้ดี: **ทั้งสามรอบให้ลำดับที่ต่างกันโดยสิ้นเชิง** ไม่มีรอบไหนซ้ำกันเลย นี่คือการพิสูจน์ด้วยการรันจริง (ไม่ใช่
การอนุมานเอาเอง) ว่า **ลำดับการมาถึงของข้อความจาก sender ต่างตัวกันไม่มีการันตีใด ๆ ทั้งสิ้น** ขึ้นอยู่กับว่า OS
scheduler ตัดสินใจให้ thread ไหนได้ CPU ก่อนในแต่ละช่วงเวลา ซึ่งเป็นสิ่งที่เราไม่สามารถควบคุมหรือคาดเดาได้จาก
ระดับโค้ด Rust เลย — แต่ในทางกลับกัน **ข้อความจาก worker เดียวกันจะยังเรียงตามลำดับที่ส่งเสมอ** (สังเกตว่าทุกรอบ
`worker-1-msg-1` มาก่อน `worker-1-msg-2` มาก่อน `worker-1-msg-3` เสมอ ไม่มีรอบไหนที่สลับกัน) เพราะข้อความจาก
sender ตัวเดียวกันยังคงเดินทางผ่าน "ท่อ" เดียวกันตามลำดับ FIFO ที่การันตีไว้ตามหัวข้อ 38.4 — **การันตี FIFO เป็น
per-sender ไม่ใช่ global ข้าม sender ทุกตัว**

จุดสำคัญที่พลาดง่ายมากคือบรรทัด `drop(tx);` **ก่อน** เข้า `for received in rx` — ทำไมต้อง drop ตัวต้นฉบับด้วย
ทั้งที่ clone ไปให้ thread อื่นหมดแล้ว? เพราะ **channel จะปิด (ทำให้ `.recv()`/`for` loop จบ) ก็ต่อเมื่อ `Sender`
ทุกตัว — รวมทั้งตัวต้นฉบับกับทุก clone — ถูก drop จนหมดสิ้น** ถ้าเราลืม drop ตัวต้นฉบับ (`tx` ที่ยังอยู่ใน main
scope) แม้ thread ลูกทั้ง 3 ตัวจะส่งครบและ `tx_clone` ของแต่ละ thread จะถูก drop อัตโนมัติเมื่อ closure จบไปแล้ว
ก็ตาม **`tx` ตัวเดิมใน main ก็ยังมีชีวิตอยู่** (ยังไม่ถูกใช้ต่อ แต่ยังไม่ตาย) ทำให้ channel ยังไม่ปิด และ
`for received in rx` จะบล็อกรอตลอดไปโดยไม่มีวันจบ — นี่คือรูปแบบ deadlock ที่พบบ่อยมากในโค้ดจริงที่ใช้ multiple
producers ซึ่งจะสาธิตอาการนี้ให้เห็นจริงในหัวข้อ "กับดักที่พบบ่อย"

### 38.6 ทางเลือกแบบไม่บล็อก: `.try_recv()` และ `.recv_timeout()`

`.recv()` ที่เรียนมาบล็อกรอ**ตลอดไป**จนกว่าจะมีข้อความหรือ channel ปิด — ซึ่งเหมาะกับกรณีที่ thread นั้นไม่มีอะไร
อย่างอื่นให้ทำนอกจากรอรับข้อความ แต่ในโปรแกรมจริงหลายสถานการณ์ thread จำเป็นต้อง **"แวบไปเช็คก่อน" ว่ามีข้อความ
มาหรือยัง แล้วไปทำงานอย่างอื่นต่อถ้ายังไม่มี** (เช่น game loop ที่ต้อง render frame ต่อไปแม้ยังไม่มี input ใหม่)
หรือ **"รอได้ แต่ไม่เกินเวลาที่กำหนด"** (เช่น รอผลลัพธ์จาก worker แต่ถ้าช้าเกินไปต้องยกเลิกแล้วรายงาน timeout)
สองสถานการณ์นี้มี method รองรับโดยเฉพาะ:

```rust
use std::sync::mpsc;
use std::thread;
use std::time::Duration;

fn main() {
    let (tx, rx) = mpsc::channel::<i32>();

    // try_recv: ไม่มีข้อความเลยตอนนี้ -> คืน Err ทันที ไม่บล็อกแม้แต่เสี้ยววินาที
    match rx.try_recv() {
        Ok(v) => println!("ได้รับ: {v}"),
        Err(e) => println!("try_recv ตอนยังไม่มีข้อความ: {e}"),
    }

    thread::spawn(move || {
        thread::sleep(Duration::from_millis(200));
        tx.send(42).unwrap();
    });

    // recv_timeout: รอไม่เกิน 50ms - คาดว่าจะ timeout เพราะ thread ส่งช้ากว่านั้น (200ms)
    match rx.recv_timeout(Duration::from_millis(50)) {
        Ok(v) => println!("ได้รับ (ภายใน 50ms): {v}"),
        Err(e) => println!("recv_timeout หลังจาก 50ms: {e}"),
    }

    // recv_timeout รอบสอง: รอนานพอ (500ms) ควรได้รับค่าจริง
    match rx.recv_timeout(Duration::from_millis(500)) {
        Ok(v) => println!("ได้รับ (ภายใน 500ms รอบสอง): {v}"),
        Err(e) => println!("recv_timeout รอบสอง: {e}"),
    }
}
```

ผลลัพธ์จริงจากการรัน:

```
try_recv ตอนยังไม่มีข้อความ: receiving on an empty channel
recv_timeout หลังจาก 50ms: timed out waiting on channel
ได้รับ (ภายใน 500ms รอบสอง): 42
```

ผลลัพธ์นี้ตรงกับที่คาดไว้เป๊ะ: `try_recv()` ครั้งแรกคืน error ทันที (ข้อความ `"receiving on an empty channel"`)
เพราะ thread ที่จะส่งค่ายังไม่ทันเริ่ม sleep เสร็จเลย, `recv_timeout(50ms)` timeout จริง (ข้อความ `"timed out
waiting on channel"`) เพราะ thread sleep ไว้ 200ms ซึ่งนานกว่า 50ms ที่เรารอ, และ `recv_timeout(500ms)` รอบสอง
ได้ค่า `42` จริงเพราะรอนานพอ (500ms > 200ms ที่ thread ใช้ก่อนส่ง)

**อธิบายความต่างของทั้งสอง method:**

- **`.try_recv()`** — ไม่บล็อกเลยแม้แต่นิดเดียว เช็คแล้วตอบทันที คืน `Result<T, TryRecvError>` ซึ่ง `TryRecvError`
  มีสอง variant ที่ **ความหมายต่างกันโดยสิ้นเชิง**: `Empty` (ยังไม่มีข้อความ ณ ขณะนี้ แต่ sender ยังมีชีวิตอยู่
  อาจมีข้อความมาทีหลังได้) กับ `Disconnected` (sender ทุกตัวถูก drop แล้ว ไม่มีทางมีข้อความอีกต่อไปเลย — ความหมาย
  เดียวกับ `RecvError` ของ `.recv()`) เหมาะมากกับ loop ที่ต้องทำงานอย่างอื่นควบคู่ไปด้วย เช่น game loop, event
  loop, หรือ polling ทรัพยากรอื่นสลับกันไป — เขียนแบบนี้ได้: `loop { if let Ok(msg) = rx.try_recv() { handle(msg);
  } do_other_work(); }`
- **`.recv_timeout(duration)`** — บล็อกรอ **จนถึงเวลาที่กำหนดเป็นอย่างมาก** ถ้ามีข้อความมาก่อนเวลาหมดก็คืน `Ok`
  ทันที ไม่ต้องรอครบเวลา แต่ถ้าครบเวลาแล้วยังไม่มีข้อความก็คืน `Err(RecvTimeoutError::Timeout)` คืน `Result<T,
  RecvTimeoutError>` ที่มีสอง variant คล้ายกัน: `Timeout` (ครบเวลาแล้ว sender ยังมีชีวิตอยู่) กับ `Disconnected`
  (channel ปิดไปก่อนครบเวลาด้วยซ้ำ) เหมาะมากกับสถานการณ์ที่ **"ยอมรอได้ในระดับหนึ่ง แต่ต้องมี upper bound ที่
  ชัดเจน"** เช่น การรอผลลัพธ์จาก worker thread ที่ปกติเสร็จเร็ว แต่ถ้าช้าผิดปกติเกินค่าที่กำหนดไว้ (เช่น request
  timeout ในระบบเครือข่าย) ก็ต้องยกเลิกการรอแล้วรายงานปัญหาแทนที่จะรอค้างไปตลอดกาล

มาดูข้อความ error ตอน channel ถูกปิดไปแล้ว (sender ถูก drop) เทียบกับตอนที่แค่ "ยังไม่มีข้อความ" ให้เห็นความต่าง
ชัด ๆ อีกครั้ง (โค้ดนี้ก็รันจริงและยืนยันข้อความตรงตามนี้):

```rust
use std::sync::mpsc;
use std::time::Duration;

fn main() {
    let (tx, rx) = mpsc::channel::<i32>();
    drop(tx); // sender ทุกตัวถูก drop แล้วตั้งแต่แรก

    match rx.try_recv() {
        Ok(v) => println!("ok: {v}"),
        Err(e) => println!("try_recv หลัง sender ถูก drop: {e} (debug: {e:?})"),
    }
    match rx.recv_timeout(Duration::from_millis(10)) {
        Ok(v) => println!("ok: {v}"),
        Err(e) => println!("recv_timeout หลัง sender ถูก drop: {e} (debug: {e:?})"),
    }
}
```

ผลลัพธ์จริง:

```
try_recv หลัง sender ถูก drop: receiving on a closed channel (debug: Disconnected)
recv_timeout หลัง sender ถูก drop: channel is empty and sending half is closed (debug: Disconnected)
```

สังเกตว่า `Debug` ของทั้งคู่บอกตรง ๆ ว่าเป็น `Disconnected` (ไม่ใช่ `Empty`/`Timeout`) — นี่คือเหตุผลที่ในโค้ด
production ที่ใส่ใจแยกแยะเหตุผลของความล้มเหลว ควร `match` แยก variant ให้ครบทั้งสองกรณีเสมอ ไม่ใช่แค่ `Err(_)`
เฉย ๆ เพราะ "ยังไม่มีข้อความตอนนี้" กับ "ไม่มีวันมีข้อความอีกแล้ว" ต้องมีวิธีจัดการที่ต่างกันโดยสิ้นเชิงในโค้ดจริง
(กรณีแรกอาจ retry ต่อได้ ส่วนกรณีที่สอง retry ไปก็ไม่มีประโยชน์ ควรเลิก loop ไปเลย)

### 38.7 Bounded Channel: `mpsc::sync_channel(bound)` และ Backpressure

`mpsc::channel()` ที่เรียนมาทั้งหมดจนถึงตอนนี้เป็น **unbounded channel** — ไม่มีขีดจำกัดว่าข้อความที่ยังไม่ถูกรับ
สามารถสะสมอยู่ใน channel ได้มากแค่ไหน ถ้า producer ส่งเร็วกว่า consumer รับมาก ๆ (เช่น producer ส่ง 1 ล้าน
ข้อความต่อวินาที แต่ consumer รับได้แค่ 1 พันข้อความต่อวินาที) **ข้อความที่ยังไม่ถูกรับจะสะสมอยู่ใน memory ของ
channel ไปเรื่อย ๆ ไม่มีเพดาน** — ถ้าปล่อยไว้นานพอ โปรแกรมจะกิน memory จนระบบล่มได้จริง ๆ นี่ไม่ใช่ปัญหาทาง
ทฤษฎีเท่านั้น แต่เป็นสาเหตุ **out-of-memory (OOM) ในระบบ production จริง** ที่เกิดขึ้นบ่อยเมื่อ pipeline มี
คอขวด (bottleneck) อยู่ที่จุดใดจุดหนึ่งโดยไม่รู้ตัว

`mpsc::sync_channel(bound)` แก้ปัญหานี้ด้วยการกำหนด **ขนาดบัฟเฟอร์สูงสุด (`bound`)** — ถ้าจำนวนข้อความที่รอรับ
อยู่ถึงขีดจำกัดแล้ว **`.send()` จะบล็อกรอ** (ไม่ใช่ error ทันที) จนกว่า consumer จะรับข้อความบางส่วนไปก่อนเพื่อ
เปิดที่ว่างในบัฟเฟอร์ — พฤติกรรมนี้เรียกว่า **backpressure**: producer ที่เร็วเกินไปจะถูก "หน่วง" ให้ช้าลงโดย
อัตโนมัติให้สอดคล้องกับความเร็วของ consumer แทนที่จะให้ข้อความสะสมไม่มีที่สิ้นสุด

```rust
use std::sync::mpsc;
use std::thread;
use std::time::{Duration, Instant};

fn main() {
    let (tx, rx) = mpsc::sync_channel::<i32>(2); // bound = 2 (บัฟเฟอร์เก็บได้สูงสุด 2 ข้อความก่อนต้องรอ)

    let consumer = thread::spawn(move || {
        thread::sleep(Duration::from_millis(300)); // consumer ทำงานช้า จงใจ เพื่อให้เห็น backpressure ชัด ๆ
        for _ in 0..5 {
            let v = rx.recv().unwrap();
            println!("[consumer] ได้รับ: {v}");
        }
    });

    let start = Instant::now();
    for i in 1..=5 {
        tx.send(i).unwrap();
        println!("[producer] ส่ง {i} แล้ว ณ เวลา {:?}", start.elapsed());
    }
    consumer.join().unwrap();
}
```

ผลลัพธ์จริงจากการรัน (ตัวเลขเวลาที่แน่นอนแปรผันได้เล็กน้อยในแต่ละครั้งที่รัน แต่**รูปแบบ**เหมือนกันทุกครั้ง):

```
[producer] ส่ง 1 แล้ว ณ เวลา 1.08µs
[producer] ส่ง 2 แล้ว ณ เวลา 9.317µs
[consumer] ได้รับ: 1
[consumer] ได้รับ: 2
[producer] ส่ง 3 แล้ว ณ เวลา 300.321996ms
[producer] ส่ง 4 แล้ว ณ เวลา 300.34994ms
[consumer] ได้รับ: 3
[consumer] ได้รับ: 4
[consumer] ได้รับ: 5
[producer] ส่ง 5 แล้ว ณ เวลา 300.352272ms
```

**อ่านผลลัพธ์นี้อย่างละเอียด เพราะมันพิสูจน์ backpressure ให้เห็นจริงด้วยตัวเลขเวลา:**

- **ข้อความที่ 1 และ 2 ถูกส่งแทบจะทันที** (1.08 ไมโครวินาที และ 9.3 ไมโครวินาที) เพราะ `bound = 2` — บัฟเฟอร์ยัง
  มีที่ว่างพอสำหรับ 2 ข้อความแรกโดยไม่ต้องรอ consumer เลย (consumer ตอนนี้ยัง sleep อยู่)
- **ข้อความที่ 3 ถูกส่งช้าไปถึง ~300 มิลลิวินาที** — ตรงกับเวลาที่ consumer sleep ไว้เป๊ะ ๆ! นี่คือ backpressure
  ที่เห็นชัดที่สุด: **`tx.send(3)` บล็อกรออยู่จนกว่า consumer จะตื่นและ `.recv()` เอาข้อความที่ 1 ออกไปก่อน เพื่อ
  เปิดที่ว่างในบัฟเฟอร์ให้ข้อความที่ 3 เข้ามาได้** ถ้าไม่มี bound (ใช้ `mpsc::channel()` ธรรมดา) ข้อความที่ 3, 4, 5
  จะถูกส่งแทบจะทันทีเหมือนข้อความที่ 1, 2 โดยไม่ต้องรอ consumer เลย — ต่างกันโดยสิ้นเชิง
- **ข้อความที่ 4 และ 5 ส่งตามมาเร็ว ๆ** หลังจากข้อความที่ 3 ผ่านไปได้ เพราะ consumer เริ่มรับข้อความไปเรื่อย ๆ
  อย่างต่อเนื่องแล้ว (เห็นจาก `[consumer] ได้รับ: 3`, `4`, `5` ที่ตามมาติด ๆ กัน) ทำให้มีที่ว่างในบัฟเฟอร์เปิดขึ้น
  ให้ producer ส่งต่อได้เรื่อย ๆ โดยไม่ต้องรอนานเท่าตอนแรก

**กรณีพิเศษที่ควรรู้จัก**: `mpsc::sync_channel(0)` (bound เป็น 0) สร้างสิ่งที่เรียกว่า **rendezvous channel** —
`.send()` จะบล็อกรอจนกว่าจะมี**ฝั่ง consumer มาเรียก `.recv()` พร้อมรับข้อความนั้นตรงเวลาเป๊ะ ๆ**เท่านั้น (ไม่มี
บัฟเฟอร์เลยแม้แต่ 1 ที่) — เหมือนกับการ "ส่งมือต่อมือ" ที่ทั้งสองฝ่ายต้องพร้อมพร้อมกันจริง ๆ ถึงจะสำเร็จ ใช้ในกรณี
ที่ต้องการซิงค์ (synchronize) การทำงานของสอง thread ให้แน่ใจว่า **ข้อความที่ส่งไปถูกรับไปประมวลผลแล้วจริง ๆ** ไม่ใช่
แค่ "ถูกวางไว้ในบัฟเฟอร์รอ" เท่านั้น

**เมื่อไหร่ควรใช้ bounded channel แทน unbounded**: ใช้ `sync_channel` เมื่อ producer และ consumer มีความเร็ว
**ไม่แน่นอนหรือแตกต่างกันมากได้** และคุณต้องการการันตีว่า memory ที่ใช้โดย channel **จะไม่โตแบบไม่มีขีดจำกัด**
เช่น ระบบ log processing ที่รับ log จาก network เข้ามาเร็วมากแต่เขียนลงดิสก์ได้ช้ากว่า, หรือ image processing
pipeline ที่อ่านไฟล์เร็วกว่าที่จะประมวลผลแต่ละภาพได้ — ในทางกลับกัน ใช้ `channel()` ธรรมดา (unbounded) เมื่อคุณ
**มั่นใจแล้วว่าจำนวนข้อความมีขอบเขตจำกัดอยู่แล้วโดยธรรมชาติ** (เช่น ส่งงานแค่ N ชิ้นที่รู้จำนวนแน่นอนตั้งแต่ต้น
ไม่ใช่ stream ที่ไม่รู้จบ) หรือความแตกต่างของความเร็ว producer/consumer ไม่มากพอที่จะเป็นปัญหาจริง

### 38.8 Worker Pool Pattern: แบ่งงานให้ Worker หลายตัวจาก `Receiver` เดียว

ทุกตัวอย่างที่ผ่านมามี **หนึ่ง `Receiver`** อยู่ที่ **หนึ่ง thread** เสมอ (ตรงกับความหมายของ "single consumer"
ใน mpsc) แต่ในโปรแกรมจริงจำนวนมาก เราต้องการ **หลาย worker thread ที่แบ่งงานกันดึงจาก queue เดียวกัน** (เช่น
web server ที่มี worker pool คอยรับ request มาประมวลผล, หรือระบบประมวลผลไฟล์ที่มี worker หลายตัวคอยหยิบไฟล์ไป
แปลงทีละไฟล์) — นี่คือจุดที่ข้อจำกัด "single consumer" ของ `Receiver<T>` กลายเป็นปัญหา เพราะ **`Receiver<T>`
ไม่ implement `Clone`** (ถูกต้องแล้วตามหลักการออกแบบ mpsc — ถ้า clone ได้ ก็จะกลายเป็น "multiple consumer" ที่
ขัดกับชื่อและสัญญาของ type นี้ทันที)

วิธีแก้ที่ใช้กันเป็นมาตรฐานคือห่อ `Receiver<T>` ด้วย **`Arc<Mutex<Receiver<T>>>`**:

- **`Mutex<Receiver<T>>`** ทำให้ worker thread ต้อง "ขอ lock" ก่อนจะเข้าถึง `Receiver` ได้ — การันตีว่า ณ เวลา
  หนึ่ง ๆ มีแค่ worker เดียวที่กำลังเรียก `.recv()` อยู่ (ป้องกัน data race บน `Receiver` เอง ซึ่งไม่ใช่ type ที่
  ปลอดภัยให้หลาย thread เรียก method พร้อมกันโดยไม่มีการป้องกัน)
- **`Arc<...>`** (Atomically Reference Counted) ทำให้ worker หลาย thread **ใช้ `Mutex<Receiver<T>>` ตัวเดียวกัน
  ร่วมกันได้** โดยแต่ละ thread ถือ "handle" ของตัวเองที่ชี้ไปยังข้อมูลตัวเดียวกันบน heap (คล้ายกับ `Rc<T>` ที่
  เรียนมาใน Part 28 แต่ปลอดภัยสำหรับข้าม thread — ปุ่มกดสำคัญคือ **การนับ reference ของ `Arc` ทำแบบ atomic
  operation ที่ปลอดภัยเมื่อหลาย thread เพิ่ม/ลด count พร้อมกัน** ต่างจาก `Rc<T>` ที่ไม่ปลอดภัยข้าม thread เลย)

ตอนนี้ **เราจะยังไม่เจาะลึกว่า `Mutex`/`Arc` ทำงานอย่างไรข้างในหรือทำไม compiler ยอมให้ใช้แบบนี้** — เพียงแค่ใช้
มันแบบ pragmatic ในฐานะ "เครื่องมือสำเร็จรูปที่แก้ปัญหานี้ได้" ก่อน **เราจะเข้าใจเหตุผลเบื้องหลังอย่างละเอียดครบ
ถ้วนใน Part 39** (ทำไม `Mutex<T>` ถึงป้องกัน data race ได้จริง, ทำไม `Arc<T>` ถึงจำเป็นเมื่อใช้ข้าม thread, และ
ทำไม `.lock()` คืนค่าเป็น `LockResult<MutexGuard<T>>` ที่ต้อง `.unwrap()`) — ตอนนี้จำแค่รูปแบบการใช้งานนี้ไว้ก่อน
เพราะมันเป็น pattern ที่พบบ่อยมากจนควรรู้จักหน้าตาไว้ตั้งแต่ตอนนี้:

```rust
use std::sync::{mpsc, Arc, Mutex};
use std::thread;

type Job = Box<dyn FnOnce() + Send + 'static>;

fn main() {
    let (tx, rx) = mpsc::channel::<Job>();
    let rx = Arc::new(Mutex::new(rx)); // ห่อ Receiver ด้วย Arc<Mutex<...>> เพื่อแบ่งให้หลาย worker ใช้ร่วมกัน

    let mut workers = vec![];
    for worker_id in 1..=3 {
        let rx_clone = Arc::clone(&rx); // clone แค่ตัว Arc (เพิ่ม reference count) ไม่ใช่ clone Receiver จริง
        let handle = thread::spawn(move || loop {
            let job = {
                let receiver = rx_clone.lock().unwrap(); // ขอ lock ก่อนแตะ Receiver
                receiver.recv()
            }; // lock ถูกปล่อยตรงนี้ (จบ scope ของ receiver) ก่อนจะเรียก job() ด้านล่าง
            match job {
                Ok(job) => {
                    println!("[worker {worker_id}] กำลังทำงาน");
                    job();
                }
                Err(_) => {
                    println!("[worker {worker_id}] ไม่มีงานเหลือแล้ว ปิดตัว");
                    break;
                }
            }
        });
        workers.push(handle);
    }

    for i in 1..=6 {
        let job: Job = Box::new(move || {
            println!("  -> กำลังประมวลผลงานที่ {i}");
        });
        tx.send(job).unwrap();
    }
    drop(tx); // ปิด channel เพื่อให้ worker ทุกตัวออกจาก loop ได้เมื่อไม่มีงานเหลือ

    for w in workers {
        w.join().unwrap();
    }
}
```

ผลลัพธ์จริงจากการรัน (รันซ้ำ 3 ครั้งเพื่อตรวจสอบความคงเส้นคงวา):

```
[worker 1] กำลังทำงาน
  -> กำลังประมวลผลงานที่ 1
[worker 1] กำลังทำงาน
  -> กำลังประมวลผลงานที่ 2
[worker 1] กำลังทำงาน
  -> กำลังประมวลผลงานที่ 3
[worker 1] กำลังทำงาน
  -> กำลังประมวลผลงานที่ 4
[worker 1] กำลังทำงาน
  -> กำลังประมวลผลงานที่ 5
[worker 1] กำลังทำงาน
  -> กำลังประมวลผลงานที่ 6
[worker 1] ไม่มีงานเหลือแล้ว ปิดตัว
[worker 2] ไม่มีงานเหลือแล้ว ปิดตัว
[worker 3] ไม่มีงานเหลือแล้ว ปิดตัว
```

**ข้อสังเกตสำคัญที่ไม่ควรมองข้าม** (และเป็นเหตุผลที่ต้องรันโค้ดจริงเพื่อเห็น แทนจะเดาเอาจากทฤษฎีอย่างเดียว):
ในการรันซ้ำหลายครั้งของตัวอย่างนี้ **worker 1 คว้างานไปทำทั้งหมด 6 ชิ้นเสมอ** ไม่มีการแบ่งงานให้ worker 2 หรือ 3
เลยแม้แต่ชิ้นเดียว! เหตุผลคือ **แต่ละ "งาน" ในตัวอย่างนี้เบามาก** (แค่ `println!` บรรทัดเดียว ทำเสร็จในเสี้ยว
ไมโครวินาที) ทำให้ worker 1 (ซึ่ง spawn ก่อนและมักได้ CPU ก่อน) วนกลับไปขอ lock และ `.recv()` งานชิ้นต่อไปได้เร็ว
กว่าที่ OS scheduler จะสลับไปให้ worker 2/3 ได้ทำงานเลย — นี่คือข้อจำกัดที่แท้จริงของ pattern "lock ทั้งการเรียก
`.recv()`" แบบง่าย ๆ นี้: **มันไม่การันตีการแบ่งงานอย่างเป็นธรรม (fairness) เมื่องานเบามาก** ถ้าต้องการดูการ
กระจายงานที่สมจริงกว่า งานแต่ละชิ้นต้องใช้เวลาทำงานที่พอสมควร (จำลองด้วย `thread::sleep` หรือเป็นงานที่ใช้ CPU
จริง) ให้ OS มีโอกาสสลับไปรัน worker อื่นระหว่างที่ worker 1 กำลังทำงานอยู่ — จะเห็นการกระจายงานที่ทั่วถึงกว่านี้
ในตัวอย่างปลายบท (หัวข้อ 38.10) ที่จำลองงาน "download" ที่ใช้เวลาจริงด้วย `thread::sleep`

**ข้อสังเกตเชิงออกแบบที่แอบซ่อนอยู่ (ทวนความเข้าใจล่วงหน้าก่อน Part 39)**: สังเกตบรรทัดที่เขียนว่า `let job = {
let receiver = rx_clone.lock().unwrap(); receiver.recv() };` ให้ดี — เราตั้งใจใส่ **วงเล็บปีกกา `{ ... }` ครอบ
เฉพาะส่วนที่ต้องใช้ lock** เพื่อให้ `receiver` (ตัวแปรที่ถือ lock ไว้) **หลุด scope และปล่อย lock ทันทีที่ได้ค่า
`job` ออกมา ก่อนที่จะเรียก `job()` ด้านนอกวงเล็บ** นี่ไม่ใช่รายละเอียดเล็กน้อยที่มองข้ามได้ — ถ้าเขียนแบบไม่ระวัง
โดยถือ lock ไว้ตลอดช่วงที่เรียก `job()` ด้วย (เช่น ย้าย `job()` เข้าไปอยู่ในวงเล็บเดียวกัน) จะเกิดผลเสียสองอย่าง:
(1) **worker อื่นทั้งหมดต้องรอ lock จนกว่างานปัจจุบันจะทำเสร็จ** ทำให้กลายเป็นทำงานทีละตัวเรียงกันเหมือนไม่มี
worker pool เลย (สูญเสียประโยชน์ของการมีหลาย worker ไปโดยสิ้นเชิง) และ (2) **ถ้างานนั้น panic ขึ้นมาขณะที่ถือ
lock อยู่ `Mutex` จะเข้าสู่สถานะ "poisoned"** (เราจะเรียนเรื่องนี้เต็มรูปแบบใน Part 39) ทำให้ worker ตัวอื่นที่มา
ขอ lock ทีหลังได้รับ error ไปด้วย ทั้งที่งานของพวกมันไม่ได้เกี่ยวข้องกับ panic นั้นเลย — การจำกัดขอบเขตของ lock
ให้สั้นที่สุดเท่าที่จำเป็น (เอาแค่สิ่งที่ต้องป้องกันจริง ๆ คือการเข้าถึง `Receiver` เท่านั้น ไม่รวมการทำงานของ
`job()` ที่ไม่ได้แตะ `Receiver` เลย) คือหลักการออกแบบที่สำคัญมากเมื่อทำงานกับ `Mutex` ซึ่ง Part 39 จะเจาะลึกเหตุผล
เต็มรูปแบบอีกครั้ง

### 38.9 Channels vs Shared State: กรอบการตัดสินใจ

หลังจากเห็นเครื่องมือของ message passing ครบแล้ว (และแอบเห็นเงาของ shared-state ผ่าน `Arc<Mutex<...>>` ไปแล้ว
ในหัวข้อก่อน) นี่คือเวลาที่เหมาะจะสรุปกรอบการตัดสินใจว่า **เมื่อไหร่ควรเลือกทางไหน** — คำตอบไม่ใช่ "อันหนึ่งดีกว่า
อีกอันเสมอ" แต่ขึ้นกับ**รูปร่างของปัญหา**:

**เลือก Message Passing (channels) เมื่อ:**

1. **งานมีลักษณะเป็น pipeline หรือ producer-consumer ชัดเจน** — ข้อมูลไหลจากจุด A ไปจุด B เป็นขั้นเป็นตอน แต่ละ
   ขั้นรับข้อมูล ประมวลผล แล้วส่งต่อ ไม่มีความจำเป็นต้อง "แชร์" ข้อมูลเดียวกันระหว่างสองขั้นตอนพร้อมกัน (แค่ส่งต่อ
   แล้วจบความเกี่ยวข้อง) เช่น ตัวอย่าง download pipeline ที่จะเห็นในหัวข้อ 38.10
2. **ต้องการความชัดเจนเรื่อง ownership transfer** — เมื่อคุณต้องการสื่อสารกับคนอ่านโค้ด (และกับ compiler) อย่าง
   ชัดเจนว่า "ข้อมูลนี้ส่งไปแล้ว ฉันจะไม่แตะมันอีกต่อไป" การส่งผ่าน channel บังคับความชัดเจนนี้โดยอัตโนมัติ
   (compiler เช็คให้ผ่าน move semantics) ในขณะที่ shared-state ทำให้ "ใครเป็นเจ้าของข้อมูลกันแน่" คลุมเครือกว่า
3. **ต้องการหลีกเลี่ยงความซับซ้อนของ lock โดยสิ้นเชิง** — ไม่มี deadlock จาก lock หลายตัวที่ล็อกไขว้กัน (lock
   ordering issues), ไม่มีความเสี่ยงเรื่อง lock contention ที่ทำให้ thread หลายตัวรอ lock เดียวกันจนช้าลง (แม้
   channel เองก็มี internal locking แต่ถูกซ่อนไว้และออกแบบมาให้มีประสิทธิภาพสำหรับ use case นี้โดยเฉพาะ)

**เลือก Shared State (`Mutex`/`Arc` — Part 39) เมื่อ:**

1. **หลาย thread ต้องอ่าน/เขียนโครงสร้างข้อมูล "เดียวกัน" ที่มีอายุยาวและถูกเข้าถึงบ่อยมาก** — เช่น cache ที่ทุก
   thread ต้องเห็นค่าล่าสุดตรงกันเสมอ, counter/statistics ที่ต้องนับรวมจากหลาย thread อย่างต่อเนื่อง, หรือ
   configuration ที่โหลดครั้งเดียวแต่ทุก thread ต้องอ่านได้ตลอดอายุโปรแกรม — ถ้าทำผ่าน message passing อย่าง
   เดียว จะต้องส่ง "คำถาม" ไปหา thread ที่เป็นเจ้าของข้อมูลทุกครั้งที่ต้องการอ่าน/เขียน ซึ่งทั้งช้ากว่า (มี
   overhead ของการส่ง/รับข้อความทุกครั้ง) และซับซ้อนกว่า (ต้องออกแบบ protocol ถาม-ตอบเอง)
2. **ต้องการประสิทธิภาพสูงสุดสำหรับการเข้าถึงข้อมูลที่ใช้ร่วมกันบ่อยมาก** — การ lock/unlock `Mutex` สั้น ๆ เพื่อ
   อ่าน/เขียนค่าตรง ๆ มักเร็วกว่าการสร้าง/ส่ง/รับ message ทั้งชุดสำหรับการเปลี่ยนแปลงเล็ก ๆ น้อย ๆ ที่เกิดขึ้นถี่มาก
3. **ธรรมชาติของข้อมูลเป็น "สถานะที่ใช้ร่วมกัน" มากกว่า "เหตุการณ์ที่ส่งต่อกัน"** — ถ้าคำอธิบายปัญหาของคุณใช้คำว่า
   "สถานะ", "การนับ", "cache", "การตั้งค่าที่ใช้ร่วมกัน" มักชี้ไปทาง shared-state แต่ถ้าใช้คำว่า "งาน", "คำสั่ง",
   "เหตุการณ์", "ผลลัพธ์ที่ส่งกลับ" มักชี้ไปทาง message passing

ในทางปฏิบัติ **ระบบจริงจำนวนมากใช้ทั้งสองแนวทางผสมกัน** ตามที่ตัวอย่างในหัวขัด 38.8 ก็แอบใช้ทั้งคู่ไปแล้ว (channel
สำหรับส่งงาน + `Mutex` สำหรับแบ่งปัน `Receiver`) — นี่ไม่ใช่ความขัดแย้งของแนวคิด แต่เป็นการใช้เครื่องมือที่เหมาะสม
กับแต่ละส่วนของปัญหา: **"การส่งงานจาก dispatcher ไปยัง worker"** เป็นธรรมชาติของ message passing (เหตุการณ์ที่
ส่งต่อ) ในขณะที่ **"การแบ่งปัน `Receiver` ตัวเดียวให้ worker หลายตัวเข้าถึง"** เป็นธรรมชาติของ shared-state
(โครงสร้างข้อมูลเดียวที่ต้องเข้าถึงพร้อมกันอย่างปลอดภัย) — Part 39 จะเจาะลึกเครื่องมือฝั่ง shared-state เต็ม
รูปแบบ และ Part 40 จะปิดท้ายด้วย `Send`/`Sync` trait ที่อธิบายว่าทำไม compiler ถึงรู้ได้ว่า type ไหน "ปลอดภัยที่
จะส่งข้าม thread" หรือ "ปลอดภัยที่จะแบ่งปันข้าม thread" ได้บ้าง — ซึ่งเป็นกลไกที่ทำให้ทั้งบทนี้และ Part 39 compile
ผ่านได้อย่างปลอดภัยตั้งแต่แรก

### 38.10 ตัวอย่างจริง: Task Processing Pipeline แบบ Request/Response

มาปิดเนื้อหาด้วยตัวอย่างที่รวมทุกอย่างที่เรียนมาในบทนี้เข้าด้วยกัน: ระบบจำลองการ **ดาวน์โหลดไฟล์หลายไฟล์พร้อมกัน**
ด้วย worker pool — dispatcher (main thread) ส่ง "งานดาวน์โหลด" ผ่าน job channel ไปให้ worker หลายตัวที่แบ่งงาน
กันผ่าน `Arc<Mutex<Receiver<Job>>>` (ตามหัวข้อ 38.8) แต่ครั้งนี้ **worker แต่ละตัวจะส่งผลลัพธ์กลับผ่าน channel
ที่สอง (result channel)** ให้ main thread เก็บรวบรวมทั้งหมด — นี่คือรูปแบบ **request/response แบบ message
passing เต็มรูปแบบ**: ส่งคำขอไปทางหนึ่ง รับคำตอบกลับมาอีกทาง โดยไม่มีการแบ่งปัน memory โดยตรงระหว่าง dispatcher
กับ worker เลย (นอกจาก `Receiver` ของ job channel ที่ต้องแบ่งปันเพราะข้อจำกัดของ mpsc ตามที่อธิบายไปแล้ว)

```rust
use std::sync::{mpsc, Arc, Mutex};
use std::thread;
use std::time::Duration;

#[derive(Debug)]
struct DownloadTask {
    id: u32,
    url: String,
}

#[derive(Debug)]
struct DownloadResult {
    task_id: u32,
    url: String,
    size_bytes: u64,
}

fn simulate_download(url: &str) -> u64 {
    // จำลองงานที่ใช้เวลา (เช่น การดาวน์โหลดจริงผ่านเครือข่าย) ด้วย sleep สั้น ๆ
    thread::sleep(Duration::from_millis(15));
    (url.len() as u64) * 137 // ตัวเลขจำลอง "ขนาดไฟล์" แบบง่าย ไม่ใช่ของจริง
}

fn main() {
    const WORKER_COUNT: usize = 4;

    let (job_tx, job_rx) = mpsc::channel::<DownloadTask>();
    let job_rx = Arc::new(Mutex::new(job_rx));
    let (result_tx, result_rx) = mpsc::channel::<DownloadResult>();

    let mut workers = vec![];
    for worker_id in 1..=WORKER_COUNT {
        let job_rx = Arc::clone(&job_rx);
        let result_tx = result_tx.clone(); // แต่ละ worker มี Sender ของ result channel เป็นของตัวเอง
        let handle = thread::spawn(move || loop {
            let task = {
                let receiver = job_rx.lock().unwrap();
                receiver.recv()
            };
            let task = match task {
                Ok(task) => task,
                Err(_) => break, // dispatcher ปิด job channel แล้ว ไม่มีงานเหลือให้ทำอีก
            };
            println!(
                "[worker {worker_id}] เริ่ม download task #{} ({})",
                task.id, task.url
            );
            let size = simulate_download(&task.url);
            let result = DownloadResult {
                task_id: task.id,
                url: task.url,
                size_bytes: size,
            };
            result_tx
                .send(result)
                .expect("ส่งผลลัพธ์กลับไม่สำเร็จ - main thread หายไปแล้ว?");
        });
        workers.push(handle);
    }
    drop(result_tx); // สำคัญ: drop ตัวต้นฉบับ ไม่งั้น result channel จะไม่ปิดแม้ worker ทุกตัวจบแล้ว

    let urls = vec![
        "https://example.com/a.zip",
        "https://example.com/b.iso",
        "https://example.com/c.tar.gz",
        "https://example.com/d.mp4",
        "https://example.com/e.png",
        "https://example.com/f.pdf",
        "https://example.com/g.docx",
        "https://example.com/h.csv",
    ];

    for (i, url) in urls.into_iter().enumerate() {
        let task = DownloadTask {
            id: (i + 1) as u32,
            url: url.to_string(),
        };
        job_tx.send(task).unwrap();
    }
    drop(job_tx); // ปิด job channel เพื่อให้ worker แต่ละตัวออกจาก loop ได้เมื่องานหมด

    // result_rx.into_iter() บล็อกรวบรวมผลลัพธ์จนกว่า result channel จะปิด (worker ทุกตัวจบงานแล้ว)
    let mut results: Vec<DownloadResult> = result_rx.into_iter().collect();
    results.sort_by_key(|r| r.task_id); // เรียงตาม task_id เพราะลำดับที่ worker ทำเสร็จไม่แน่นอน

    for w in workers {
        w.join().unwrap();
    }

    println!("\n=== สรุปผลลัพธ์ทั้งหมด ({} tasks) ===", results.len());
    for r in &results {
        println!("task #{}: {} -> {} bytes (จำลอง)", r.task_id, r.url, r.size_bytes);
    }
}
```

ผลลัพธ์จริงจากการรัน:

```

[worker 1] เริ่ม download task #1 (https://example.com/a.zip)
[worker 2] เริ่ม download task #4 (https://example.com/d.mp4)
[worker 3] เริ่ม download task #3 (https://example.com/c.tar.gz)
[worker 1] เริ่ม download task #5 (https://example.com/e.png)
[worker 2] เริ่ม download task #6 (https://example.com/f.pdf)
[worker 4] เริ่ม download task #7 (https://example.com/g.docx)
[worker 3] เริ่ม download task #8 (https://example.com/h.csv)

task #3: https://example.com/c.tar.gz -> 3836 bytes (จำลอง)
task #4: https://example.com/d.mp4 -> 3425 bytes (จำลอง)
task #5: https://example.com/e.png -> 3425 bytes (จำลอง)
task #6: https://example.com/f.pdf -> 3425 bytes (จำลอง)
```

**สังเกตสองเรื่องสำคัญที่ยืนยันแนวคิดของบททั้งหมด:**

1. **งานกระจายไปทั้ง 4 worker อย่างทั่วถึง** (worker 1, 2, 3, 4 ทำงานคนละ 2 task) ต่างจากตัวอย่าง worker pool
   ในหัวข้อ 38.8 ที่ worker 1 คว้างานไปหมด — เพราะครั้งนี้แต่ละงานใช้เวลาจริง (`thread::sleep(15ms)` จำลองการ
   ดาวน์โหลด) ทำให้ OS scheduler มีโอกาสสลับไปให้ worker อื่นได้ระหว่างที่ worker หนึ่งกำลัง "ดาวน์โหลด" อยู่ —
   นี่คือหลักฐานที่ยืนยันคำอธิบายในหัวข้อ 38.8 ว่าความเป็นธรรมของการกระจายงานขึ้นอยู่กับว่างานแต่ละชิ้นใช้เวลา
   นานพอที่จะให้ scheduler สลับ thread หรือไม่
2. **ลำดับที่ worker เริ่มงาน (`เริ่ม download task #...`) ไม่ตรงกับลำดับ task id เลย** (worker 4 เริ่ม task #2
   ก่อน worker 1 เริ่ม task #1 ด้วยซ้ำ) — ยืนยันอีกครั้งว่าลำดับการประมวลผลข้าม thread ไม่มีการันตี แต่ **ผลลัพธ์
   สุดท้ายที่พิมพ์ออกมาเรียงตาม `task_id` ครบถ้วนถูกต้องทุก task** เพราะเราตั้งใจ `.sort_by_key(|r| r.task_id)`
   ก่อนแสดงผล — นี่คือ pattern สำคัญที่ควรจำ: **ถ้าลำดับผลลัพธ์สุดท้ายสำคัญกับ business logic ห้ามพึ่งลำดับที่
   มาถึงจาก channel เด็ดขาด ต้องแนบข้อมูลระบุตัวตน (เช่น `task_id`) ไปกับผลลัพธ์เสมอ แล้วค่อยจัดเรียงเอาเองที่
   ปลายทาง**

โครงสร้างของตัวอย่างนี้ (job channel + shared receiver ผ่าน `Arc<Mutex<...>>` + result channel ที่แต่ละ worker
มี sender ของตัวเอง) คือรูปแบบที่พบได้จริงในระบบ production จำนวนมาก เช่น thread pool ของ web server, ระบบ
ประมวลผลรูปภาพ/วิดีโอแบบ batch, หรือระบบ scraping ที่ต้องดาวน์โหลดหลาย URL พร้อมกันโดยจำกัดจำนวน worker ไม่ให้
เปิด connection มากเกินไปพร้อมกัน

## กับดักที่พบบ่อย (Common Pitfalls)

**1. Deadlock: รอ `.recv()` ตลอดไปเพราะยังมี `Sender` ที่ไม่ตายและไม่ส่งอะไรเลย**

```rust
use std::sync::mpsc;

fn main() {
    let (tx, rx) = mpsc::channel::<i32>();

    // ไม่ได้ spawn thread ไหนมาส่งอะไรเข้า tx เลย
    // แต่ tx ตัวนี้ยังไม่ถูก drop (ยังอยู่ในสโคปของ main จนจบฟังก์ชัน)
    println!("กำลังรอรับข้อความ...");
    let value = rx.recv(); // <- ค้างตรงนี้ตลอดไป เพราะ tx ยังไม่ตาย และไม่มีใครส่งอะไรมาเลย
    println!("ได้รับ: {value:?}");
}
```

โค้ดนี้ **compile ผ่านสมบูรณ์** ไม่มี error ใด ๆ เลย — แต่พอรันจริงจะพิมพ์แค่บรรทัดแรก (`"กำลังรอรับข้อความ..."`)
แล้ว**ค้างตลอดไป ไม่มีวันจบเอง** (ทดสอบจริงด้วยการรันภายใต้ timeout 2 วินาที: โปรแกรมพิมพ์บรรทัดแรกแล้วถูก
บังคับปิดเมื่อครบเวลา ยืนยันว่ามันค้างจริง ไม่ได้แค่ทำงานช้า) เหตุผลตรงกับที่อธิบายไว้ในหัวข้อ 38.2: **`.recv()`
บล็อกรอ "ตลอดไป" จนกว่าจะมีข้อความ หรือ `Sender` ทุกตัวถูก drop เท่านั้น** ในโค้ดนี้ `tx` ยังมีชีวิตอยู่จนจบ
ฟังก์ชัน `main` (ยังไม่ถูก drop เพราะยังไม่ได้ใช้ให้หมดหน้าที่) แต่ก็ไม่มีใครเรียก `tx.send()` เลยสักครั้ง — ผลคือ
channel ไม่มีทาง "ปิด" และไม่มีทางมีข้อความมาถึง `.recv()` จึงรอตลอดไปอย่างแท้จริง

**วิธีแก้**: ตรวจสอบให้แน่ใจว่าทุกครั้งที่มีการเรียก `.recv()` (หรือใช้ `for` loop บน `Receiver`) จะต้องมี
**อย่างน้อยหนึ่งใน** สองเงื่อนไขนี้เกิดขึ้นแน่นอนในอนาคต: (1) มี `Sender` ตัวใดตัวหนึ่งเรียก `.send()` จริง หรือ
(2) `Sender` ทุกตัวถูก drop (ตรง ๆ ด้วย `drop(tx)` หรือโดยธรรมชาติเมื่อ scope ที่เก็บมันจบลง) — ถ้าตั้งใจจะรอ
ข้อความจริง ให้ spawn thread ที่จะส่งข้อความมาก่อนเรียก `.recv()`; ถ้าไม่แน่ใจว่าจะมีข้อความมาหรือไม่ ให้ใช้
`.recv_timeout()` แทน `.recv()` เพื่อป้องกันการค้างตลอดไป (ตามที่เรียนในหัวข้อ 38.6)

**2. ลืม `drop()` ตัวต้นฉบับของ `Sender` หลังจาก `.clone()` ไปให้ thread อื่นหมดแล้ว**

นี่คือ variant ของ deadlock ข้างบนที่พบบ่อยมากเมื่อใช้ multiple producers (หัวข้อ 38.5) — ถ้าเขียนโค้ดแบบ
ตัวอย่างในหัวข้อ 38.5 แต่ **ลืมบรรทัด `drop(tx);`** ก่อนเข้า `for received in rx`:

```rust
use std::sync::mpsc;
use std::thread;

fn main() {
    let (tx, rx) = mpsc::channel();

    for worker_id in 1..=3 {
        let tx_clone = tx.clone();
        thread::spawn(move || {
            tx_clone.send(format!("จาก worker {worker_id}")).unwrap();
        });
    }
    // ไม่ได้ drop(tx) ตรงนี้ — tx ตัวต้นฉบับยังมีชีวิตอยู่จนจบฟังก์ชัน

    for received in rx { // ค้างตลอดไป แม้ทุก thread จะส่งข้อความครบและจบไปแล้ว
        println!("{received}");
    }
}
```

โค้ดนี้จะพิมพ์ข้อความจากทั้ง 3 worker ครบถ้วน (thread ทั้งหมดทำงานจบและ `tx_clone` ของแต่ละตัวถูก drop อัตโนมัติ
เมื่อ closure จบ) **แต่ `for received in rx` จะไม่จบ loop เอง** เพราะ `tx` ตัวต้นฉบับใน `main` ยังไม่ถูก drop —
โปรแกรมจะค้างอยู่ที่การรอข้อความถัดไปตลอดไปหลังพิมพ์ข้อความสุดท้ายจากทั้ง 3 worker ไปแล้ว **วิธีแก้**: เรียก
`drop(tx)` (หรือให้ `tx` หลุดจาก scope ไปตามธรรมชาติ) ทันทีหลังจาก spawn thread ที่ต้องใช้ clone ของมันครบทุกตัว
แล้ว ก่อนจะเข้าสู่ loop รับข้อความ — กฎง่าย ๆ ที่จำได้เสมอ: **"ทุก `Sender` ตัวต้นฉบับที่ clone ไปแล้วและไม่ได้
ใช้ต่อ ต้องถูก drop อย่างชัดเจน (หรือให้หลุด scope) ก่อนที่ฝั่ง receiver จะรอ channel ปิด"**

**3. พยายาม `.clone()` `Receiver<T>` (E0599)**

```rust
use std::sync::mpsc;

fn main() {
    let (tx, rx) = mpsc::channel::<i32>();
    let rx2 = rx.clone();
    tx.send(1).unwrap();
    println!("{:?}", rx.recv());
    println!("{:?}", rx2.recv());
}
```

Error จริงจาก compiler:

```
error[E0599]: no method named `clone` found for struct `std::sync::mpsc::Receiver<T>` in the current scope
 --> src/main.rs:5:18
  |
5 |     let rx2 = rx.clone();
  |                  ^^^^^ method not found in `std::sync::mpsc::Receiver<i32>`
```

ตามที่อธิบายไว้ในหัวข้อ 38.8 — **`Receiver<T>` ไม่ implement `Clone`** ตามการออกแบบของ mpsc (multiple
**producer**, single **consumer**) โดยตั้งใจ ถ้า `Receiver` clone ได้ ความหมายของชื่อ mpsc เองก็จะพังทันที
(กลายเป็น multiple consumer โดยไม่มีกลไกป้องกัน race condition ระหว่างสอง `Receiver` ที่แย่งกันรับข้อความ
เดียวกัน) **วิธีแก้**: ถ้าต้องการให้หลาย thread รับข้อความจาก channel เดียวกันได้จริง ๆ ต้องห่อ `Receiver` ด้วย
`Arc<Mutex<Receiver<T>>>` ตามรูปแบบที่เรียนในหัวข้อ 38.8 (ซึ่งจะบังคับให้แต่ละ thread ต้องขอ lock ก่อนแตะ
`Receiver` ทำให้ปลอดภัยจาก race condition) ไม่ใช่พยายาม clone `Receiver` ตรง ๆ

**4. ลืม `move` ใน closure ที่ต้องใช้ `Sender`/`Receiver` ข้าม thread (E0373)**

```rust
use std::sync::mpsc;
use std::thread;

fn main() {
    let (tx, rx) = mpsc::channel();
    let handle = thread::spawn(|| { // ลืม move
        tx.send("hello".to_string()).unwrap();
    });
    handle.join().unwrap();
    println!("{:?}", rx.recv());
}
```

Error จริงจาก compiler (ตรงกับสิ่งที่ Part 37 เตือนไว้เรื่อง `'static` bound ของ closure ที่ส่งเข้า
`thread::spawn`):

```
error[E0373]: closure may outlive the current function, but it borrows `tx`, which is owned by the current function
 --> src/main.rs:6:32
  |
6 |     let handle = thread::spawn(|| {
  |                                ^^ may outlive borrowed value `tx`
7 |         tx.send("hello".to_string()).unwrap();
  |         -- `tx` is borrowed here
  |
note: function requires argument type to outlive `'static`
help: to force the closure to take ownership of `tx` (and any other referenced variables), use the `move` keyword
  |
6 |     let handle = thread::spawn(move || {
  |                                ++++
```

**วิธีแก้**: ตรงตาม suggestion ของ compiler เป๊ะ ๆ — เพิ่ม `move` หน้า closure (`thread::spawn(move || { ... })`)
เพื่อให้ closure ยึด ownership ของ `tx` เข้าไปเต็มตัว แทนที่จะแค่ borrow มันชั่วคราว (ซึ่งเป็นสิ่งที่ Rust ไม่ยอม
ให้เกิดขึ้น เพราะ compiler ไม่สามารถการันตีได้ว่า `tx` ที่อยู่ใน `main` จะมีชีวิตอยู่นานพอสำหรับ thread ใหม่ที่
อาจทำงานนานกว่า `main` — ตรงตามหลักที่เรียนมาในหัวข้อ 38.3 และ Part 37)

**5. ใช้ `Sender` ต่อหลังจากที่ `move` เข้า closure ไปแล้ว (E0382)**

```rust
use std::sync::mpsc;
use std::thread;

fn main() {
    let (tx, rx) = mpsc::channel();
    thread::spawn(move || {
        tx.send(1).unwrap();
    });
    // ลืมว่า tx ถูก move เข้า closure ไปแล้ว พยายามใช้ต่อ
    tx.send(2).unwrap();
    println!("{:?}", rx.recv());
    println!("{:?}", rx.recv());
}
```

Error จริงจาก compiler:

```
error[E0382]: borrow of moved value: `tx`
  --> src/main.rs:10:5
   |
 5 |     let (tx, rx) = mpsc::channel();
   |          -- move occurs because `tx` has type `std::sync::mpsc::Sender<i32>`, which does not implement the `Copy` trait
 6 |     thread::spawn(move || {
   |                   ------- value moved into closure here
 7 |         tx.send(1).unwrap();
   |         -- variable moved due to use in closure
...
10 |     tx.send(2).unwrap();
   |     ^^ value borrowed here after move
   |
help: consider cloning the value before moving it into the closure
   |
 6 ~     let value = tx.clone();
 7 ~     thread::spawn(move || {
 8 ~         value.send(1).unwrap();
```

นี่คือ error แบบเดียวกับที่เรียนมาแล้วตั้งแต่ Part 6 (use of moved value) เพียงแค่เกิดในบริบทของ thread/channel —
`tx` ถูก move เข้า closure ของ `thread::spawn` ไปแล้วในบรรทัดที่ 6-8 ทำให้ `main` **ไม่มี `tx` เหลือให้ใช้อีก**
พอพยายามเรียก `tx.send(2)` ต่อในบรรทัดที่ 10 จึงเจอ error ทันที **วิธีแก้**: ตรงตาม suggestion ของ compiler เอง
— ถ้าต้องการส่งข้อความทั้งจาก thread ใหม่และจาก `main` เอง (ทั้งสองฝั่งเป็น "ผู้ส่ง") ต้อง **`.clone()` ก่อน
move** เพื่อให้ทั้งสองฝั่งมี handle ของตัวเอง คนละตัวกัน (ตรงกับหลัก multiple producer ในหัวข้อ 38.5):

```rust
use std::sync::mpsc;
use std::thread;

fn main() {
    let (tx, rx) = mpsc::channel();
    let tx_for_thread = tx.clone(); // clone ก่อน move เพื่อให้ main ยังมี tx ตัวเดิมใช้ต่อได้
    thread::spawn(move || {
        tx_for_thread.send(1).unwrap();
    });
    tx.send(2).unwrap(); // ใช้ tx ตัวเดิมของ main ได้ตามปกติ เพราะไม่ได้ move มันไปไหน
    println!("{:?}", rx.recv());
    println!("{:?}", rx.recv());
}
```

**6. คิดว่า `sync_channel` เหมือน `channel` ธรรมดา แล้วแปลกใจที่ `.send()` "ค้าง"**

เมื่อสลับจาก `mpsc::channel()` (unbounded) ไปใช้ `mpsc::sync_channel(bound)` (bounded) โดยไม่ระวังเรื่อง
ลำดับการทำงาน อาจทำให้โปรแกรมที่เดิม compile และรันได้ปกติ **กลายเป็นค้าง (บล็อกตลอดไป)** โดยไม่มี error ให้เห็น
เลย เช่น การเรียก `.send()` หลายครั้งเกิน `bound` **จาก thread เดียวกัน** ที่เป็นทั้ง producer และ consumer เอง
โดยไม่มี thread อื่นมาช่วยรับ:

```rust
use std::sync::mpsc;

fn main() {
    let (tx, rx) = mpsc::sync_channel::<i32>(1); // bound = 1

    tx.send(1).unwrap(); // ส่งได้ - บัฟเฟอร์ยังมีที่ว่าง (0/1 -> 1/1)
    tx.send(2).unwrap(); // ค้างตลอดไป! บัฟเฟอร์เต็มแล้ว (1/1) และไม่มี thread อื่นมาเรียก rx.recv() เพื่อเปิดที่ว่าง
    println!("{:?}", rx.recv());
    println!("{:?}", rx.recv());
}
```

โค้ดนี้ compile ผ่าน แต่จะค้างที่บรรทัด `tx.send(2)` ตลอดไป เพราะ **thread เดียวกันเป็นทั้งคนส่งและคนรับ** — มัน
เรียก `.send(2)` (ซึ่งต้องรอให้มีคนมา `.recv()` ก่อนเพื่อเปิดที่ว่าง) แต่โค้ดที่จะเรียก `rx.recv()` อยู่ **บรรทัด
ถัดไป ซึ่งไม่มีวันถูกรันเลยเพราะ thread เดียวกันติดอยู่ที่ `.send(2)` ไปก่อนแล้ว** — นี่คือ deadlock แบบง่ายที่สุด
ที่เกิดจาก bounded channel โดยเฉพาะ (ไม่เกิดกับ unbounded channel เพราะ `.send()` ของ unbounded ไม่มีวันบล็อก)
**วิธีแก้**: ต้องมี**อีก thread หนึ่ง**ที่คอยเรียก `.recv()` เพื่อรับข้อความออกจากบัฟเฟอร์ก่อนที่ thread ฝั่ง
ส่งจะพยายามส่งเกิน `bound` (ตามรูปแบบที่ถูกต้องในหัวข้อ 38.7 ที่แยก producer/consumer เป็นสอง thread ชัดเจน)
หรือถ้าตั้งใจให้ thread เดียวทำทั้งสองหน้าที่จริง ๆ ต้องสลับลำดับการเรียก `.send()`/`.recv()` ให้ไม่มีจังหวะไหน
ที่บัฟเฟอร์เต็มเกิน `bound` ก่อนจะมีการ `.recv()` มาคั่น

## แบบฝึกหัด (Exercises)

1. **[ง่าย]** เขียนโปรแกรมที่ spawn thread หนึ่งตัวส่งเลข `1` ถึง `10` เข้า channel ทีละตัว (ใช้ `mpsc::channel()`
   ธรรมดา) ส่วน main thread รับค่าทั้งหมดด้วย `for received in rx` แล้วรวมผลรวม (sum) ของเลขทั้งหมดเก็บไว้ใน
   ตัวแปร พิมพ์ผลรวมสุดท้ายออกมา (คำตอบที่ถูกต้องคือ 55) — hint: ผลรวมต้องสะสมอยู่นอก loop ก่อนแล้วบวกทีละตัว
   ข้างใน `for` loop

2. **[กลาง]** ปรับตัวอย่างในหัวข้อ 38.5 ให้เป็นระบบ "นับคะแนนโหวต" จำลอง — spawn 3 thread แทน "หน่วยลงคะแนน"
   (แต่ละ thread คือ `tx.clone()` ของตัวเอง) แต่ละ thread ส่งชื่อผู้สมัคร (`String`) ที่สุ่มมาจาก
   `["A", "B", "C"]` จำนวน 10 ครั้งเข้า channel เดียวกัน (ใช้ index `i % 3` ง่าย ๆ แทนการสุ่มจริงก็ได้ เพื่อให้
   ผลลัพธ์ตรวจสอบได้) main thread รับคะแนนโหวตทั้งหมดด้วย `for` loop แล้วนับจำนวนโหวตของผู้สมัครแต่ละคนด้วย
   `HashMap<String, u32>` (ทวนจาก Part 15) พิมพ์สรุปคะแนนของแต่ละผู้สมัครท้ายโปรแกรม — ลองรันโปรแกรมซ้ำหลายครั้ง
   แล้วสังเกตว่า **ลำดับ**ที่คะแนนโหวตมาถึงเปลี่ยนไปทุกครั้งหรือไม่ แต่ **ผลรวมคะแนน**ของแต่ละผู้สมัครควรจะ
   เหมือนกันทุกครั้ง เพราะเหตุใด (hint: อย่าลืม `drop(tx)` ตัวต้นฉบับก่อนเข้า loop รับข้อความ)

3. **[ยาก]** เขียนโปรแกรมที่ใช้ `mpsc::sync_channel(3)` (bound = 3) จำลองสถานการณ์ "สายพานการผลิต" — thread
   หนึ่งตัวเป็น producer ที่ผลิตชิ้นงาน (เลข 1 ถึง 10) ส่งเข้า channel ให้เร็วที่สุด (ไม่ sleep) ส่วน thread อีก
   ตัวเป็น consumer ที่ประมวลผลช้ากว่า (จำลองด้วย `thread::sleep(Duration::from_millis(50))` ก่อนรับแต่ละชิ้น)
   ใช้ `std::time::Instant` วัดเวลาที่ producer ใช้ในการส่งแต่ละชิ้นงาน (แบบเดียวกับตัวอย่างในหัวข้อ 38.7) แล้ว
   พิมพ์ผลลัพธ์ให้เห็นว่าชิ้นงานลำดับที่ 1-3 ส่งได้เร็วแค่ไหน เทียบกับชิ้นงานลำดับที่ 4 เป็นต้นไปที่ต้องรอ
   backpressure — อธิบายด้วยคำพูดของตัวเองว่าทำไมชิ้นงานที่ 4 ถึงส่งช้ากว่าชิ้นงานที่ 1-3 อย่างมีนัยสำคัญ

4. **[ยาก/ประยุกต์ใช้งานจริง]** ขยายตัวอย่าง pipeline ในหัวข้อ 38.10: เปลี่ยนจากการจำลอง "download" เป็นการ
   จำลองระบบ **"ประมวลผลคำสั่งซื้อ" (order processing)** — สร้าง struct `Order { id: u32, item_name: String,
   quantity: u32, price_per_unit: f64 }` สร้างรายการคำสั่งซื้อ 10-15 รายการ ส่งผ่าน job channel ไปยัง worker
   pool (4 worker ตามเดิม แบ่งกันผ่าน `Arc<Mutex<Receiver<Order>>>`) แต่ละ worker คำนวณ **ยอดรวมของคำสั่งซื้อนั้น**
   (`quantity * price_per_unit`) และจำลองเวลาประมวลผลด้วย `thread::sleep` สั้น ๆ ก่อนส่งผลลัพธ์ (struct
   `OrderResult { order_id: u32, total: f64 }`) กลับผ่าน result channel ที่สอง — main thread เก็บผลลัพธ์ทั้งหมด
   เรียงตาม `order_id` แล้วพิมพ์สรุปยอดขายรวมทั้งหมด (ผลรวมของทุก `total`) ท้ายโปรแกรม (hint: ต้อง `drop()`
   ทั้ง `job_tx` ตัวต้นฉบับหลังส่งงานครบ และ `result_tx` ตัวต้นฉบับก่อนเก็บผลลัพธ์ ตามรูปแบบในหัวข้อ 38.10
   เป๊ะ ๆ — ลองคิดดูว่าถ้าลืม `drop()` ตัวไหนตัวหนึ่งจะเกิดอะไรขึ้น แล้วทดลองลบทิ้งดูจริง ๆ เพื่อยืนยันคำตอบ)

## สรุป

บทนี้เจาะลึก **message-passing concurrency** ผ่าน `std::sync::mpsc` ในฐานะทางเลือกแรกจากสองทางที่ Part 37 เกริ่น
ไว้สำหรับแก้ปัญหา "หลาย thread ต้องสื่อสาร/แบ่งปันข้อมูลกัน" — เริ่มจากปรัชญา "don't share state, send messages
instead" ที่ Rust สืบทอดมาจาก Erlang/Go และทำให้ปลอดภัยยิ่งขึ้นด้วยการผูกมันเข้ากับ move semantics ที่มีอยู่แล้ว
ตั้งแต่ Part 6 (การส่งค่าผ่าน channel **คือ** การ move ธรรมดา ๆ ไม่ใช่กลไกพิเศษแยกต่างหาก) จากนั้นไล่เรียงเครื่องมือ
ทั้งหมดของ `mpsc`: `channel()` สำหรับสร้าง `Sender<T>`/`Receiver<T>`, `.send()`/`.recv()` พื้นฐานพร้อมความหมายของ
`RecvError`, การวนรับข้อความทั้งสองแบบ (`match` บน `.recv()` และ `for` loop บน `Receiver` ที่ implement `Iterator`
ตามความรู้จาก Part 25), multiple producers ผ่าน `.clone()` (พร้อมพิสูจน์ความไม่แน่นอนของลำดับข้ามผู้ส่งด้วยการ
รันจริงหลายรอบ), ทางเลือกไม่บล็อกอย่าง `.try_recv()`/`.recv_timeout()`, bounded channel (`sync_channel`) กับ
แนวคิด backpressure ที่ป้องกัน memory โตไม่มีขีดจำกัดในระบบจริง, และปิดท้ายด้วย worker pool pattern ที่ต้องใช้
`Arc<Mutex<Receiver<T>>>` เป็นทางออกเชิงปฏิบัติ (พร้อมสัญญาว่าจะอธิบายเหตุผลเบื้องหลังให้ครบใน Part 39) ตัวอย่าง
task processing pipeline ท้ายบทรวมทุกเครื่องมือเข้าด้วยกันเป็นระบบ request/response ที่สมบูรณ์ พร้อมข้อสังเกต
จริงจากการรันซ้ำหลายครั้งที่ยืนยันทั้งความไม่แน่นอนของลำดับและความสำคัญของการแนบ ID กับผลลัพธ์เพื่อจัดเรียงเอง
ทีหลัง

ใน **Part 39 (Mutex, Arc และ Shared-State Concurrency)** เราจะเจาะลึกทางเลือกที่สองที่บทนี้แอบใช้แบบ pragmatic
ไปแล้วใน worker pool pattern — `Mutex<T>` ทำงานอย่างไรข้างในถึงป้องกัน data race ได้จริง, `MutexGuard` และ RAII
pattern ที่ทำให้ lock ถูกปล่อยอัตโนมัติ, `Arc<T>` ต่างจาก `Rc<T>` (Part 28) อย่างไรและทำไมถึงจำเป็นข้าม thread,
และกรอบการตัดสินใจแบบเจาะลึกกว่าหัวข้อ 38.9 ว่าเมื่อไหร่ shared-state ให้ประสิทธิภาพและความชัดเจนที่ดีกว่า
message-passing จริง ๆ ในสถานการณ์ที่ซับซ้อนขึ้น
