# Part 15: Collections: HashMap, HashSet, BTreeMap/BTreeSet

> โมดูล: พื้นฐานภาษา Rust (Core Language Fundamentals) | ระดับ: กลาง | เวลาโดยประมาณ: 180 นาที

## เป้าหมายของบทเรียน

หลังจากจบบทนี้ คุณจะสามารถ:

- อธิบายได้ว่าทำไมการค้นหาข้อมูลด้วย "คีย์" (key) ใน `Vec` ต้องใช้เวลา O(n) และ **hash-based collection**
  แก้ปัญหานี้ให้กลายเป็น O(1) โดยเฉลี่ยได้อย่างไร
- สร้างและใช้งาน `HashMap<K, V>` ได้อย่างครบวงจร: สร้าง, insert, ดึงค่า, อัปเดตค่า, ลบค่า, และวน iterate
- อธิบายความสัมพันธ์ระหว่าง ownership กับการ insert ค่าลง `HashMap` (ทำไม insert ค่าที่ไม่ implement `Copy` แล้ว
  ตัวแปรเดิมถึงใช้ต่อไม่ได้) และรู้วิธีแก้ด้วย `.clone()` อย่างเหมาะสม
- ใช้ `.get()` ที่คืนค่าเป็น `Option<&V>` ร่วมกับเทคนิคจาก Part 11 (`.unwrap_or()`, `.map()`, `.and_then()`,
  `.unwrap_or_else()`) ได้อย่างคล่องแคล่ว และรู้ว่าทำไมการ index ด้วย `map[&key]` ตรง ๆ เสี่ยง panic
- ใช้ `.entry()` API (`.or_insert()`, `.or_insert_with()`, `.or_default()`) แก้ปัญหา "เช็คก่อนว่ามีคีย์นี้ไหม
  แล้วค่อยเพิ่ม/อัปเดต" ได้อย่างมีประสิทธิภาพกว่าการเขียน `if/else` เอง และอธิบายเหตุผลด้าน performance ได้
- แยกแยะได้ว่าเมื่อไหร่ควรใช้ `HashMap`/`HashSet` (เร็วที่สุด ไม่สนลำดับ) เทียบกับ `BTreeMap`/`BTreeSet`
  (เรียงลำดับตามคีย์เสมอ ทำ range query ได้) และอธิบายได้ว่าทำไม `HashMap` ไม่การันตีลำดับการ iterate เลย
- ใช้ set operation (`.union()`, `.intersection()`, `.difference()`, `.symmetric_difference()`) ของ `HashSet`
  แก้ปัญหาจริง เช่นหา tag ที่สินค้าสองชิ้นมีร่วมกัน หรือหานักเรียนที่ลงทั้งสองวิชา

## ความรู้ที่ต้องมีมาก่อน

- **Part 6 (Ownership)**: ต้องเข้าใจเรื่อง move และ `Copy` trait ให้แน่น เพราะการ insert ค่าที่ไม่ implement `Copy`
  (เช่น `String`) ลง `HashMap` คือการ **move ค่านั้นเข้าไปเป็นของ map** โดยตรง — พฤติกรรมเดียวกับที่คุณเคยเห็นตอน
  ส่งค่าเข้าฟังก์ชันหรือ assign ให้ตัวแปรอื่น
- **Part 7 (Borrowing)**: ต้องเข้าใจ `&T`/`&mut T` เพราะ `.get()` คืนค่าเป็น reference (`Option<&V>`) ไม่ใช่ค่าตรง ๆ
  และการถือ reference จาก map ค้างไว้พร้อมกับพยายามแก้ไข map เดิมจะโดน borrow checker เตือน
- **Part 9 (Structs)**: ใช้ประกอบตัวอย่างจริงในบทนี้ (ระบบสต็อกสินค้า, ระบบตะกร้าสินค้า) ที่อาจมี struct เป็น value
  ใน map
- **Part 11 (Option<T> และ Null Safety)**: **สำคัญที่สุดสำหรับบทนี้** เพราะ `.get()` ของ `HashMap` คืนค่าเป็น
  `Option<&V>` เสมอ (ไม่มี `None` แบบภาษาอื่น ไม่มี null pointer exception) ทุกเทคนิคที่คุณเรียนมาใน Part 11 —
  `.unwrap()`, `.expect()`, `.unwrap_or()`, `.unwrap_or_else()`, `.unwrap_or_default()`, `.map()`, `.and_then()`,
  `if let Some(x) = ...`, `match` — จะถูกใช้งานจริงกับ `HashMap` ตลอดทั้งบทนี้ ถ้ายังไม่คล่องกับ `Option<T>`
  แนะนำให้กลับไปทวน Part 11 ก่อน เพราะบทนี้จะไม่อธิบาย mechanics ของ `Option<T>` ซ้ำอีก แต่จะใช้งานมันตรง ๆ เลย
- **Part 13 (Collections: Vec<T>)**: ใช้เปรียบเทียบเป็นจุดเริ่มต้นของบทนี้ — เราจะเริ่มจากปัญหาที่ `Vec<(K, V)>`
  แก้ได้ไม่ดีพอ แล้วโยงไปสู่ว่าทำไมต้องมี `HashMap` และรู้จัก `.iter()`, `.collect()` มาแล้วจาก Part นั้น
- **Part 14 (Collections: String และการจัดการข้อความ)**: ตัวอย่าง word-frequency counter ท้ายบทนี้ใช้ความรู้เรื่อง
  UTF-8, `.split_whitespace()`, `.to_lowercase()` จาก Part 14 มาประมวลผลข้อความไทย/อังกฤษผสมกันโดยตรง

ถ้าคุณยังไม่คุ้นกับ `Option<T>` (Part 11) แนะนำอย่างยิ่งให้กลับไปทวนก่อนอ่านบทนี้ต่อ เพราะเกือบทุก method ของ
`HashMap` ที่เกี่ยวกับการดึงค่าจะคืนผลลัพธ์เป็น `Option<T>` (หรือ `Option<&T>`) ทั้งหมด

## เนื้อหา

### 15.1 ปัญหาที่ hash-based collection แก้: การค้นหาด้วย key ใน `Vec` คือ O(n)

จาก Part 13 คุณรู้จัก `Vec<T>` มาแล้วในฐานะ collection ที่ขนาดเปลี่ยนแปลงได้ ลองนึกภาพสถานการณ์ที่พบบ่อยมาก: คุณมี
รายการสินค้าที่แต่ละตัวมี "ชื่อ" กับ "ราคา" และต้องการค้นหาราคาจาก **ชื่อสินค้า** — วิธีแรกที่ทำได้ด้วยความรู้เท่าที่
มีตอนนี้คือเก็บเป็น `Vec<(String, u32)>` แล้ววน loop หาทีละตัว:

```rust
fn find_price(inventory: &[(String, u32)], target_name: &str) -> Option<u32> {
    for (name, price) in inventory {
        if name == target_name {
            return Some(*price);
        }
    }
    None
}

fn main() {
    let inventory: Vec<(String, u32)> = vec![
        (String::from("ปากกา"), 15),
        (String::from("สมุด"), 25),
        (String::from("ยางลบ"), 5),
        (String::from("ไม้บรรทัด"), 10),
    ];

    match find_price(&inventory, "ยางลบ") {
        Some(price) => println!("ราคายางลบ: {price} บาท"),
        None => println!("ไม่พบสินค้านี้"),
    }

    match find_price(&inventory, "แม็ก") {
        Some(price) => println!("ราคาแม็ก: {price} บาท"),
        None => println!("ไม่พบสินค้านี้"),
    }
}
```

ผลลัพธ์:

```
ราคายางลบ: 5 บาท
ไม่พบสินค้านี้
```

โค้ดนี้**ถูกต้อง** และคุณอาจสังเกตว่าฟังก์ชัน `find_price` คืนค่าเป็น `Option<u32>` — ตรงกับที่เรียนมาใน Part 11 พอดี
เพราะ "การค้นหาอาจไม่พบ" คือสถานการณ์ classic ของ `Option<T>` แต่ปัญหาที่ซ่อนอยู่ไม่ใช่เรื่อง correctness
แต่เป็นเรื่อง **performance**: ทุกครั้งที่ค้นหา ฟังก์ชันนี้ต้อง**ไล่เช็คทีละสมาชิกตั้งแต่ตัวแรก** จนกว่าจะเจอ (หรือ
จนหมด vector ถ้าไม่เจอ) ในกรณีที่แย่ที่สุด (สินค้าที่ค้นหาอยู่ตัวสุดท้าย หรือไม่มีอยู่เลย) ต้องเช็ค **ทุกตัวใน
vector** — ถ้า vector มี `n` สมาชิก การค้นหาหนึ่งครั้งใช้เวลาสัดส่วนกับ `n` เราเรียก complexity แบบนี้ว่า
**O(n) — linear time**

สำหรับ vector เล็ก ๆ ไม่กี่สิบตัว O(n) ไม่มีผลกระทบที่สังเกตได้เลย แต่ลองนึกภาพระบบจริงที่มีสินค้า 100,000 รายการ
และมีการค้นหาราคาสินค้าเกิดขึ้นหลายพันครั้งต่อวินาที (เช่น ระบบ POS หน้าร้าน หรือ API ตรวจสอบราคา) — ถ้าค้นหาแต่ละ
ครั้งต้องไล่เช็คเฉลี่ย 50,000 ตัว (ครึ่งหนึ่งของ 100,000) ระบบจะช้าลงอย่างเห็นได้ชัดทันที และที่แย่กว่านั้นคือ
**ปัญหานี้จะยิ่งแย่ลงเรื่อย ๆ ตามขนาดข้อมูลที่โต** — นี่คือสิ่งที่วิศวกรเรียกว่า "ไม่ scale"

#### แนวคิดของ hash-based lookup: แลก memory เพื่อความเร็ว

`HashMap<K, V>` (และ `HashSet<T>`) แก้ปัญหานี้ด้วยแนวคิดที่แตกต่างไปจากการไล่เช็คทีละตัวโดยสิ้นเชิง: มันใช้
**hash function** แปลงคีย์ (key) ให้เป็นเลขจำนวนเต็ม (hash value) แล้วใช้เลขนั้นคำนวณ**ตำแหน่ง**ที่ควรเก็บค่านั้นไว้
ใน array ภายในโดยตรง (เรียกตำแหน่งเหล่านี้ว่า "bucket") เมื่อจะค้นหาคีย์ใดคีย์หนึ่ง ก็แค่ **คำนวณ hash ของคีย์นั้น
อีกครั้ง** แล้วกระโดดไปที่ bucket ตำแหน่งนั้นตรง ๆ — ไม่ต้องไล่เช็คทีละตัวเลย

ผลลัพธ์คือการค้นหา (และ insert, และ remove) ใช้เวลา **O(1) โดยเฉลี่ย (average case)** — ไม่ว่า collection จะมี
สมาชิก 10 ตัวหรือ 10 ล้านตัว เวลาค้นหาโดยเฉลี่ยแทบไม่เปลี่ยนแปลง (มีข้อยกเว้นทางทฤษฎีคือกรณี hash collision รุนแรง
ที่ทำให้ worst case กลายเป็น O(n) ได้ แต่ hash function ที่ดีและมี resize อัตโนมัติทำให้กรณีนี้เกิดยากมากในทางปฏิบัติ
— รายละเอียดเชิงลึกของ hash table internals อยู่นอกเหนือขอบเขตบทนี้ แต่สิ่งที่ต้องจำคือ **แลกกับความเร็วนี้ เราเสีย
อะไรไปบ้าง** ซึ่งจะเป็นประเด็นสำคัญของหัวข้อ 15.7):

| แนวทาง | ค้นหา | insert | ลำดับข้อมูล |
|---|---|---|---|
| `Vec<(K, V)>` + ไล่เช็คทีละตัว | O(n) | O(1) (แค่ push ท้าย) | รักษาลำดับที่ insert ไว้เสมอ |
| `HashMap<K, V>` | O(1) โดยเฉลี่ย | O(1) โดยเฉลี่ย | **ไม่มีลำดับที่แน่นอนเลย** |
| `BTreeMap<K, V>` | O(log n) | O(log n) | เรียงตามคีย์เสมอ |

ตารางนี้คือแผนที่ของบทนี้ทั้งบท — เราจะเรียน `HashMap` ก่อนในฐานะตัวเลือกที่เร็วที่สุดเมื่อไม่สนใจลำดับ จากนั้นเรียน
`HashSet` ในฐานะ "HashMap ที่สนใจแค่คีย์" และปิดท้ายด้วย `BTreeMap`/`BTreeSet` สำหรับกรณีที่ต้องการลำดับที่แน่นอน

### 15.2 `HashMap<K, V>`: การสร้างและ insert พื้นฐาน

`HashMap<K, V>` อยู่ใน `std::collections` ต่างจาก `Vec<T>` และ `String` ที่คุณใช้มาตลอดโดยไม่ต้องเขียน `use` เลย
เพราะทั้งสองอยู่ใน **prelude** (ชุด type ที่ Rust import ให้อัตโนมัติทุกไฟล์) แต่ `HashMap` **ไม่ได้อยู่ใน prelude**
ลองดูว่าเกิดอะไรขึ้นถ้าใช้ `HashMap` โดยไม่ import:

```rust
fn main() {
    let mut m = HashMap::new();
    m.insert(1, 2);
}
```

```
error[E0433]: failed to resolve: use of undeclared type `HashMap`
 --> src/main.rs:2:17
  |
2 |     let mut m = HashMap::new();
  |                 ^^^^^^^ use of undeclared type `HashMap`
  |
help: consider importing this struct
  |
1 + use std::collections::HashMap;
  |
```

สังเกตว่า compiler ช่วยเสนอ fix ให้ตรง ๆ อีกแล้ว (เหมือนที่เห็นมาตลอดทั้งหลักสูตร) — วิธีแก้คือเพิ่ม `use` ที่หัวไฟล์:

```rust
use std::collections::HashMap;

fn main() {
    let mut ages: HashMap<String, u32> = HashMap::new();
    ages.insert(String::from("สมชาย"), 30);
    ages.insert(String::from("สมหญิง"), 25);
    println!("จำนวนคนในระบบ: {}", ages.len());
    println!("{:?}", ages.get("สมชาย"));
}
```

ผลลัพธ์:

```
จำนวนคนในระบบ: 2
Some(30)
```

#### ทำไม `HashMap` ไม่อยู่ใน prelude — การตัดสินใจที่ตั้งใจ ไม่ใช่ความหลงลืม

นี่เป็นคำถามที่มือใหม่ถามบ่อยมาก: "ในเมื่อ `HashMap` ใช้บ่อยมากในโปรแกรมจริง ทำไม Rust ไม่ใส่ไว้ใน prelude ให้เลย
เหมือน `Vec` กับ `String`?" คำตอบมาจากปรัชญาการออกแบบ prelude ของ Rust ที่ตั้งใจให้**เล็กที่สุดเท่าที่จำเป็น**
เพราะทุกอย่างที่อยู่ใน prelude คือชื่อที่ **"จอง" ไว้ทั่วทั้งภาษาโดยปริยาย** — ถ้าคุณตั้งชื่อ struct ของคุณเองว่า
`HashMap` (ซึ่งเป็นชื่อที่คนอาจอยากใช้กับ struct wrapper ของตัวเอง) มันจะชนกับชื่อใน prelude ทันที ทำให้ต้องเขียน
disambiguation ที่ยุ่งยากขึ้น

Rust เลือกใส่ใน prelude เฉพาะสิ่งที่ **"เกือบทุกโปรแกรม Rust ต้องใช้แน่ ๆ"** เท่านั้น เช่น `String`, `Vec<T>`,
`Option<T>`, `Result<T, E>`, `Box<T>` — สิ่งเหล่านี้เป็นพื้นฐานของภาษาแทบทุกโปรแกรมจะเจอ แต่ `HashMap` (และ
`HashSet`, `BTreeMap`, `VecDeque`, `HashMap` ฯลฯ ทั้งหมดใน `std::collections`) ถูกมองว่าเป็น **collection ชนิด
เฉพาะทาง** — มีโปรแกรมจำนวนมาก (โดยเฉพาะโปรแกรมเล็ก ๆ, library, หรือโค้ดที่ทำงานกับข้อมูลแบบ sequential ล้วน ๆ)
ที่ไม่เคยต้องใช้ key-value lookup เลยตลอดทั้งโปรแกรม การบังคับให้ทุกไฟล์ "แบก" ชื่อ `HashMap` ไว้เผื่อใช้ทั้งที่ไม่ได้
ใช้จริง จึงไม่คุ้มเมื่อเทียบกับต้นทุนการจองชื่อ

หลักการเดียวกันนี้ยังสอดคล้องกับสิ่งที่คุณเห็นมาตั้งแต่ Part 3: Rust ให้ความสำคัญกับ **ความชัดเจนของสิ่งที่กำลังใช้
งาน** มากกว่าความสะดวกในการพิมพ์สั้น ๆ — การเห็น `use std::collections::HashMap;` ที่หัวไฟล์ทำให้คนอ่านโค้ดรู้ทันที
ว่าไฟล์นี้ใช้ hash-based collection อยู่ที่ไหนบ้าง โดยไม่ต้องเดา

#### insert หลายค่า และ method พื้นฐาน

`HashMap::new()` สร้าง map เปล่า ต้องมี `mut` ถ้าจะ insert เพิ่มค่า (ตรงตามกฎ mutability จาก Part 3 — การ insert
คือการแก้ไขค่าภายใน ต้องมี `mut` binding เสมอ) เมธอดพื้นฐานที่ควรรู้จักตั้งแต่ต้น:

- `.insert(key, value)` — เพิ่มคู่ key-value เข้าไป (หรืออัปเดตถ้า key มีอยู่แล้ว — รายละเอียดในหัวข้อ 15.5)
- `.len()` — จำนวนคู่ key-value ทั้งหมดในปัจจุบัน
- `.is_empty()` — เช็คว่า map ว่างหรือไม่ (เร็วกว่า `.len() == 0` เพราะไม่ต้องนับจริง — เหมือน `Vec`/`String`
  ที่คุณเคยเห็นมาแล้ว)

### 15.3 Ownership semantics เมื่อ insert: `String` ถูก move เข้า map เสมอ

จาก Part 6 คุณรู้แล้วว่า `String` ไม่ implement `Copy` — เมื่อส่ง `String` เข้าฟังก์ชัน หรือ assign ให้ตัวแปรอื่น
ค่านั้นจะถูก **move** ไป ตัวแปรเดิมใช้ต่อไม่ได้ กฎนี้ใช้กับการ `.insert()` เข้า `HashMap` **เหมือนกันทุกประการ**
เพราะ `.insert(key, value)` รับ parameter เป็น `K` และ `V` โดยตรง (ไม่ใช่ reference) — เมื่อคุณส่ง `String` เข้าไป
ก็คือส่งเข้าฟังก์ชันที่รับ ownership ธรรมดา ๆ นั่นเอง

ลองดูโค้ดที่พยายามใช้ตัวแปรเดิมหลัง insert:

```rust
use std::collections::HashMap;

fn main() {
    let mut ages: HashMap<String, u32> = HashMap::new();
    let name = String::from("สมชาย");
    ages.insert(name, 30);
    println!("ชื่อที่เพิ่งเพิ่ม: {name}");
}
```

โค้ดนี้ **compile ไม่ผ่าน**:

```
error[E0382]: borrow of moved value: `name`
 --> src/main.rs:7:35
  |
5 |     let name = String::from("สมชาย");
  |         ---- move occurs because `name` has type `String`, which does not implement the `Copy` trait
6 |     ages.insert(name, 30);
  |                 ---- value moved here
7 |     println!("ชื่อที่เพิ่งเพิ่ม: {name}");
  |                           ^^^^ value borrowed here after move
  |
help: consider cloning the value if the performance cost is acceptable
  |
6 |     ages.insert(name.clone(), 30);
  |                     ++++++++
```

นี่คือ error message เดียวกันในสไตล์เดียวกับที่คุณเคยเห็นตอนเรียน ownership ใน Part 6 — compiler บอกชัดเจนว่า
`name` ถูก move ไปแล้วที่บรรทัด `ages.insert(name, 30)` (เพราะ `String` ไม่ implement `Copy`) ดังนั้นการใช้ `name`
อีกครั้งในบรรทัดถัดไปจึงเป็นการอ้างถึงค่าที่ไม่มีเจ้าของอยู่ในตัวแปรนี้แล้ว และยังเสนอวิธีแก้ให้ตรง ๆ ด้วย
`help: consider cloning the value`

**เหตุผลเชิงลึกที่ Rust ออกแบบให้เป็นแบบนี้**: `HashMap` เป็นเจ้าของ (owns) ทุกคีย์และค่าที่อยู่ภายในมันอย่างสมบูรณ์
— มันไม่ได้แค่ "เก็บ pointer ไปยัง string ที่อื่น" แบบที่ hash table ใน C หรือ dictionary ใน Python มักทำ (ซึ่งเสี่ยง
ต่อ dangling pointer ถ้า string ต้นทางถูก free ไปแล้วในภาษาที่ไม่มี garbage collector หรือ borrow checker) การให้
`HashMap` **เป็นเจ้าของข้อมูลจริง ๆ** ทำให้มันการันตีได้ 100% ว่าข้อมูลภายในจะยังมีอยู่ตราบใดที่ map ยังไม่ถูก drop
— ไม่มีทางเกิด use-after-free หรือ dangling reference จากการอ่านค่าใน map ได้เลย ไม่ว่ากรณีใด

วิธีแก้ที่ถูกต้องคือ `.clone()` ก่อน insert ถ้าคุณต้องการใช้ตัวแปรเดิมต่อ:

```rust
use std::collections::HashMap;

fn main() {
    let mut ages: HashMap<String, u32> = HashMap::new();
    let name = String::from("สมชาย");
    ages.insert(name.clone(), 30); // clone ก่อน insert เพื่อให้ name ตัวเดิมยังใช้ได้ต่อ
    println!("ชื่อที่เพิ่งเพิ่ม: {name}");
    println!("ในระบบ: {:?}", ages.get(&name));
}
```

ผลลัพธ์:

```
ชื่อที่เพิ่งเพิ่ม: สมชาย
ในระบบ: Some(30)
```

การ `.clone()` มีต้นทุนจริง (ต้อง allocate memory ใหม่บน heap และ copy bytes ทั้งหมดของ string) — ถ้าคุณไม่ได้
ต้องการใช้ตัวแปรเดิมต่อจริง ๆ (เช่นในตัวอย่างแรกของหัวข้อ 15.2 ที่ insert แล้วไม่แตะตัวแปรเดิมอีก) การไม่ clone
คือทางเลือกที่ดีกว่าเสมอ เพราะปล่อยให้ ownership ย้ายเข้า map ไปตรง ๆ โดยไม่มี allocation ซ้ำซ้อน — หลักการเดียวกับ
ที่เราเน้นย้ำมาตั้งแต่ Part 6 และ Part 13: **`.clone()` คือทางออกฉุกเฉิน ไม่ใช่ default ที่ควรใส่ทุกที่ที่ compiler
บ่น** ก่อนใส่ `.clone()` ควรถามตัวเองก่อนว่า "จริง ๆ แล้วฉันจำเป็นต้องใช้ค่าเดิมต่อหรือแค่ต้องการให้ compiler ผ่าน
ไปก่อน?"

ค่าประเภท `Copy` เช่น `i32`, `u32`, `f64`, `bool`, `char` ไม่มีปัญหานี้เลย เพราะ insert จะ **copy ค่า** เข้าไปแทน
การ move (ตัวแปรเดิมยังใช้ต่อได้ปกติ) — นี่คือกฎเดียวกับ Part 6 ที่ใช้กับทุกที่ในภาษา ไม่ใช่กฎพิเศษของ `HashMap`

### 15.4 การเข้าถึงค่า: `.get()`, indexing, และ `.contains_key()`

#### `.get(&key)`: คืนค่าเป็น `Option<&V>` เสมอ

เมธอดหลักในการดึงค่าจาก `HashMap` คือ `.get()` ซึ่งรับ **reference ไปยังคีย์** (ไม่ใช่คีย์ตรง ๆ — เพราะการค้นหา
ไม่จำเป็นต้อง take ownership ของคีย์เลย) และคืนค่าเป็น **`Option<&V>`** — นี่คือจุดที่ความรู้จาก Part 11 มาบรรจบกับ
บทนี้โดยตรง เพราะ "การค้นหาคีย์ที่อาจไม่มีอยู่จริง" คือสถานการณ์ classic ของ `Option<T>` เช่นเดียวกับตัวอย่าง
`find_price` ในหัวข้อ 15.1

```rust
use std::collections::HashMap;

fn main() {
    let mut prices: HashMap<String, u32> = HashMap::new();
    prices.insert(String::from("ปากกา"), 15);
    prices.insert(String::from("สมุด"), 25);

    // .get() คืน Option<&V>
    let pen_price: Option<&u32> = prices.get("ปากกา");
    println!("{pen_price:?}");

    // unwrap_or: ให้ค่า default ถ้าไม่มี
    let eraser_price: u32 = *prices.get("ยางลบ").unwrap_or(&0);
    println!("ราคายางลบ (default 0): {eraser_price}");

    // map: แปลงค่าถ้ามี, ยังเป็น Option ต่อ
    let pen_price_with_vat: Option<u32> = prices.get("ปากกา").map(|p| p + (p / 10));
    println!("{pen_price_with_vat:?}");

    // and_then: ใช้ต่อเนื่องกับ operation ที่คืน Option อีกที
    let discounted = prices.get("สมุด").and_then(|&p| {
        if p > 10 {
            Some(p - 5)
        } else {
            None
        }
    });
    println!("{discounted:?}");

    // contains_key: เช็คก่อนโดยไม่ดึงค่า
    if prices.contains_key("ปากกา") {
        println!("มีปากกาขายอยู่");
    }

    // unwrap_or_else: คำนวณ default แบบ lazy (เรียกฟังก์ชันเฉพาะตอนไม่มีค่าจริง ๆ)
    let ruler_price = prices.get("ไม้บรรทัด").copied().unwrap_or_else(|| {
        println!("ไม่พบไม้บรรทัด กำลังคำนวณราคา default...");
        8
    });
    println!("ราคาไม้บรรทัด: {ruler_price}");
}
```

ผลลัพธ์ทั้งหมดของฟังก์ชัน `main` (รวมส่วนแรก):

```
Some(15)
ราคายางลบ (default 0): 0
Some(16)
Some(20)
มีปากกาขายอยู่
ไม่พบไม้บรรทัด กำลังคำนวณราคา default...
ราคาไม้บรรทัด: 8
```

สังเกตจุดที่ควรเข้าใจให้ลึกใน snippet ข้างบน:

- เราส่ง `"ปากกา"` ซึ่งเป็น `&str` ไปให้ `.get()` ที่คีย์เป็น `String` โดยตรง ไม่ต้องเขียน
  `&String::from("ปากกา")` ทั้งที่ type ของคีย์คือ `String` — เหตุผลคือ `.get()` เป็น generic method ที่รับ
  `&Q` โดย `Q` ต้อง implement `Borrow<Q>` ให้กับ `K` และ `String` implement `Borrow<str>` ไว้แล้ว (concept นี้
  เจาะลึกเรื่อง trait ที่ยังไม่ได้เรียน แต่ผลลัพธ์ในทางปฏิบัติคือ **คุณส่ง `&str` ไปค้นหาใน `HashMap<String, V>`
  ได้ตรง ๆ โดยไม่ต้องแปลงเป็น `String` ก่อน** ซึ่งสะดวกมากและเป็นสิ่งที่ทำได้เพราะการค้นหาไม่ต้องใช้ ownership
  ของคีย์เลย — เทียบกับ Part 8 ที่ `&str` และ `&String` deref ไปมาหากันได้ในลักษณะคล้ายกัน)
- `.unwrap_or(&0)` ต้องใส่ `&0` ไม่ใช่ `0` เพราะ `.get()` คืน `Option<&u32>` ไม่ใช่ `Option<u32>` — `unwrap_or`
  ต้องการค่า default ที่**เป็น type เดียวกับที่อยู่ใน `Option`** เสมอ (`&u32` ในที่นี้) แล้วเราค่อย dereference
  ด้วย `*` ทีเดียวตอนสุดท้ายเพื่อได้ `u32` จริง ๆ
- `.copied()` (หรือ `.cloned()` สำหรับ type ที่ implement `Clone` แต่ไม่ implement `Copy`) คือเทคนิคที่สะดวกมาก
  ในการแปลง `Option<&T>` เป็น `Option<T>` เมื่อ `T` implement `Copy` (เช่น `u32`) — หลังจากนั้นจะเรียก
  `.unwrap_or_else()` ต่อได้อย่างเป็นธรรมชาติโดยไม่ต้องยุ่งกับ `&` อีก
- `.map()` บน `Option<&V>` เปลี่ยนแค่ **ค่าด้านใน** ถ้ามี (`Some` ยังเป็น `Some` อยู่ แค่ค่าเปลี่ยนไปตาม closure)
  ส่วน `None` ยังเป็น `None` เหมือนเดิม — พฤติกรรมนี้เหมือนกับที่เรียนมาใน Part 11 ทุกประการ ไม่มีความแตกต่างใด ๆ
  เพียงแค่ตอนนี้ `Option` มาจาก `HashMap::get()` แทนที่จะมาจาก `.parse()` หรือฟังก์ชันอื่น ๆ
- `.and_then()` ใช้เมื่อ closure ของคุณเองก็คืนค่าเป็น `Option<T>` อีกที (ในที่นี้คือ "ถ้าราคามากกว่า 10 ค่อยลด
  ราคาให้ ไม่งั้นถือว่าไม่มีส่วนลด") — ถ้าใช้ `.map()` แทนจะได้ `Option<Option<u32>>` ซึ่งซ้อนกันเกินความจำเป็น
  `.and_then()` "แบน" (flatten) ชั้นซ้อนนี้ให้เหลือ `Option<u32>` ชั้นเดียว

#### Indexing ด้วย `map[&key]`: ทางลัดที่ panic ได้

`HashMap` ยัง implement trait `Index` ทำให้เขียน `map[&key]` ได้สั้น ๆ แบบเดียวกับ index array/`Vec` แต่มีข้อ
แตกต่างที่ **สำคัญมาก**: ถ้าคีย์นั้นไม่มีอยู่จริงใน map การ index จะ **panic ทันที** ไม่ใช่คืน `None` แบบ `.get()`

```rust
use std::collections::HashMap;

fn main() {
    let mut scores: HashMap<String, i32> = HashMap::new();
    scores.insert(String::from("Alice"), 90);
    let bob_score = scores[&String::from("Bob")];
    println!("{bob_score}");
}
```

โปรแกรมนี้ compile ผ่าน (syntax ถูกต้องสมบูรณ์) แต่ตอนรันจะ panic ด้วยข้อความ:

```
thread 'main' panicked at src/main.rs:6:27:
no entry found for key
note: run with `RUST_BACKTRACE=1` environment variable to display a backtrace
```

เหตุผลที่ trait `Index` ของ `HashMap` ถูกออกแบบมาให้ panic แทนที่จะคืน `Option` คือ **ข้อจำกัดของ trait `Index`
เอง** — signature ของ `Index::index` บังคับให้คืนค่าเป็น `&V` ตรง ๆ (ไม่ใช่ `Option<&V>`) เพราะ trait นี้ถูก
ออกแบบมาให้ใช้กับ array/slice เป็นหลักตั้งแต่แรก ซึ่งการ index ที่ไม่ถูกต้องก็ panic อยู่แล้ว (ตามที่เห็นมาใน
Part 3 หัวข้อ out-of-bounds) `HashMap` implement trait เดียวกันนี้เพื่อความสะดวกในการเขียนโค้ดสั้น ๆ แต่ผลข้างเคียง
คือมันสืบทอดพฤติกรรม "panic เมื่อเข้าถึงไม่ได้" มาด้วย

**ข้อแนะนำเชิงปฏิบัติ**: ใช้ `map[&key]` เฉพาะเมื่อคุณ**มั่นใจ 100%** ว่าคีย์นั้นมีอยู่แน่นอน (เช่น คุณเพิ่ง insert
เองในบรรทัดก่อนหน้า หรือมี invariant ของโปรแกรมที่การันตีไว้แล้ว) ในกรณีทั่วไปที่ไม่แน่ใจ — โดยเฉพาะเมื่อคีย์มาจาก
input ของผู้ใช้หรือแหล่งข้อมูลภายนอก — ให้ใช้ `.get()` แล้วจัดการ `Option` อย่างชัดเจนแทนเสมอ นี่คือหลักการเดียวกับ
"fail fast and loud" ที่เราเห็นซ้ำ ๆ ตลอดหลักสูตร (array indexing ใน Part 3, `.unwrap()` ใน Part 11) — panic
ไม่ใช่เรื่องผิด แต่ต้องเป็น panic ที่ **คุณตั้งใจให้เกิดขึ้นในสถานการณ์ที่การันตีไว้แล้วว่าไม่ควรเกิด** ไม่ใช่ panic
ที่หลุดมาจากการไม่ได้เผื่อกรณี key หาย

#### `.get_mut()`: แก้ไขค่าผ่าน mutable reference

ถ้าต้องการแก้ไขค่าที่อยู่ใน map โดยไม่ insert ทับใหม่ทั้งคู่ key-value ใช้ `.get_mut()` ซึ่งคืน `Option<&mut V>`:

```rust
use std::collections::HashMap;

fn main() {
    let mut stock: HashMap<String, u32> = HashMap::new();
    stock.insert(String::from("ปากกา"), 10);

    if let Some(qty) = stock.get_mut("ปากกา") {
        *qty += 5;
    }
    println!("{stock:?}");
}
```

ผลลัพธ์:

```
{"ปากกา": 15}
```

รูปแบบ `if let Some(qty) = stock.get_mut(...) { *qty += 5; }` คือ idiom ที่พบบ่อยมาก — ใช้ `if let` (จาก Part 10)
เพื่อจัดการเฉพาะกรณี `Some` โดยไม่สนใจ `None` เลย (ถ้าไม่มีคีย์นี้ก็ไม่ทำอะไร ไม่ panic ไม่ error) ตรงกับสไตล์ที่
Part 11 แนะนำไว้ว่า `if let` เหมาะกับกรณีที่สนใจแค่ pattern เดียวและไม่ต้องทำอะไรกับอีกกรณี

### 15.5 การอัปเดตค่า: overwrite, และ `.entry()` API

#### `.insert()` ที่คีย์มีอยู่แล้ว: overwrite และคืนค่าเก่าเป็น `Option<V>`

พฤติกรรมของ `.insert()` ที่หลายคนมองข้ามคือ **มันคืนค่ากลับมาเสมอ** — ถ้าคีย์นั้น**ไม่มี**อยู่มาก่อน จะคืน `None`
(เพราะไม่มีค่าเก่าให้คืน) แต่ถ้าคีย์นั้น**มีอยู่แล้ว** `.insert()` จะ **overwrite ค่าเดิมด้วยค่าใหม่** และคืนค่า
**เก่า**ที่ถูกแทนที่กลับมาเป็น `Some(ค่าเก่า)`:

```rust
use std::collections::HashMap;

fn main() {
    let mut prices: HashMap<String, u32> = HashMap::new();

    let old1 = prices.insert(String::from("ปากกา"), 15);
    println!("{old1:?}"); // None เพราะยังไม่มี key นี้มาก่อน

    let old2 = prices.insert(String::from("ปากกา"), 18); // อัปเดตราคาใหม่
    println!("{old2:?}"); // Some(15) คือค่าเก่าก่อนอัปเดต

    println!("ราคาปัจจุบัน: {:?}", prices.get("ปากกา"));
}
```

ผลลัพธ์:

```
None
Some(15)
ราคาปัจจุบัน: Some(18)
```

นี่คืออีกจุดที่ `Option<T>` จาก Part 11 โผล่มาแบบที่หลายคนไม่คาดคิด — การใช้ `.insert()` แล้ว**ไม่สนใจค่าที่คืนมา**
(เช่นเขียนแค่ `prices.insert(...)` โดด ๆ) เป็นเรื่องปกติมากในโค้ด แต่ถ้าธุรกิจของคุณต้องการรู้ว่า "การอัปเดตนี้ทับ
ค่าเดิมไปหรือไม่ และค่าเดิมคืออะไร" (เช่น เพื่อ log การเปลี่ยนแปลงราคา หรือแจ้งเตือนถ้าราคาที่กำลังจะบันทึกต่างจาก
ราคาเดิมมากเกินไป) ค่าที่ `.insert()` คืนกลับมาคือข้อมูลนี้พอดี ไม่ต้อง `.get()` ก่อน insert แยกต่างหากให้เสีย
เวลา hash คีย์ซ้ำสองรอบ

#### ปัญหา "เช็คก่อนว่ามีไหม แล้วค่อยเพิ่ม/อัปเดต" และทำไม naive `if/else` ไม่ดีพอ

สถานการณ์ที่พบบ่อยที่สุดอย่างหนึ่งในการเขียนโปรแกรมจริงคือ: "ถ้าคีย์นี้มีอยู่แล้ว ให้ทำอย่างหนึ่ง (เช่น เพิ่มค่า)
ถ้าไม่มี ให้สร้างขึ้นมาใหม่พร้อมค่าเริ่มต้น" ตัวอย่างคลาสสิกคือระบบสต็อกสินค้าที่รับรายการสั่งซื้อเข้ามาแล้วต้อง
บวกจำนวนเข้าไปในสต็อกที่มีอยู่ (หรือสร้างรายการสต็อกใหม่ถ้าสินค้านี้ยังไม่เคยมีในระบบ) วิธีตรงไปตรงมาที่สุดตาม
ความรู้ที่มีตอนนี้คือ:

```rust
use std::collections::HashMap;

fn main() {
    let mut stock: HashMap<String, u32> = HashMap::new();

    // naive แบบ contains_key + if/else (แต่ hash คีย์ 2 ครั้ง)
    let item = String::from("ปากกา");
    if stock.contains_key(&item) {
        *stock.get_mut(&item).unwrap() += 10;
    } else {
        stock.insert(item.clone(), 10);
    }
    println!("{stock:?}");
}
```

ผลลัพธ์:

```
{"ปากกา": 10}
```

โค้ดนี้ **ถูกต้องสมบูรณ์** และทำงานได้ตามต้องการ แต่มีปัญหาด้าน performance ที่ซ่อนอยู่: สังเกตว่าในกรณี branch
`if` เราต้องคำนวณ hash ของ `item` **สองครั้ง** — ครั้งแรกตอน `.contains_key(&item)` เพื่อเช็คว่ามีอยู่ไหม และครั้ง
ที่สองตอน `.get_mut(&item)` เพื่อหา bucket แล้วดึง mutable reference มาแก้ไข ทั้งที่จริง ๆ ทั้งสอง operation กำลัง
หา bucket **ตำแหน่งเดียวกัน** ซ้ำกันโดยไม่จำเป็น — สำหรับ `HashMap` เล็ก ๆ ต้นทุนนี้เล็กน้อยจนไม่รู้สึก แต่ถ้าโค้ด
แบบนี้ถูกเรียกในลูปที่รันหลายล้านครั้ง (เช่น ประมวลผล transaction log ขนาดใหญ่) การ hash ซ้ำสองเท่าทุกครั้งก็คือ
งานที่สูญไปโดยไม่จำเป็นจริง ๆ สะสมกันเป็นก้อนใหญ่

#### `.entry()`: hash คีย์แค่ครั้งเดียว

`HashMap` มี API ที่ออกแบบมาแก้ปัญหานี้ตรง ๆ ชื่อ `.entry(key)` ซึ่งคืนค่าเป็น type พิเศษชื่อ `Entry` ที่แทน
"ตำแหน่งของคีย์นี้ใน map ไม่ว่าจะมีอยู่แล้วหรือยังไม่มี" — เมธอดที่ใช้บ่อยที่สุดคือ `.or_insert(default)`:

```rust
use std::collections::HashMap;

fn main() {
    let mut stock: HashMap<String, u32> = HashMap::new();

    // entry API: hash แค่ครั้งเดียว
    *stock.entry(String::from("ปากกา")).or_insert(0) += 5;
    *stock.entry(String::from("กระดาษ")).or_insert(0) += 20;
    println!("{stock:?}");

    // or_insert_with: default ที่คำนวณแบบ lazy
    stock.entry(String::from("กาว")).or_insert_with(|| {
        println!("กาวยังไม่มีในสต็อก กำลังตั้งค่าเริ่มต้น...");
        0
    });
    println!("{stock:?}");
}
```

ผลลัพธ์:

```
{"กระดาษ": 20, "ปากกา": 5}
กาวยังไม่มีในสต็อก กำลังตั้งค่าเริ่มต้น...
{"กระดาษ": 20, "ปากกา": 5, "กาว": 0}
```

(หมายเหตุ: ลำดับที่แสดงในตัวอย่างนี้เป็นแค่ลำดับหนึ่งที่เป็นไปได้ — เราจะอธิบายว่าทำไมลำดับไม่แน่นอนแบบนี้ใน
หัวข้อ 15.7 ถัดไป อย่าเพิ่งยึดติดกับลำดับที่เห็นตรงนี้)

`.or_insert(0)` แปลว่า "ถ้าคีย์นี้ยังไม่มี ให้ insert ค่า `0` เข้าไปก่อน" ในทั้งสองกรณี (มีอยู่แล้ว หรือ เพิ่งสร้าง
ใหม่) `.or_insert()` จะคืนค่าเป็น **`&mut V`** กลับมาให้เสมอ — นี่คือกลไกที่ทำให้เราเขียน `*stock.entry(...)
.or_insert(0) += 5;` ต่อท้ายได้ในนัดเดียว: ไม่ว่าคีย์จะมีอยู่แล้วหรือไม่ เราจะได้ mutable reference ไปยังค่าใน
map เสมอ แล้ว `+= 5` ก็แค่แก้ไขผ่าน reference นั้นตรง ๆ **โดยไม่ต้องเช็ค `contains_key` แยก ไม่ต้อง `.unwrap()`
เลย และภายในกลไกของ `HashMap` เองก็คำนวณ hash และหา bucket แค่ครั้งเดียวเท่านั้น**

`.or_insert_with(|| ...)` ต่างจาก `.or_insert()` ตรงที่รับ **closure** แทนค่าตรง ๆ — closure นี้จะถูกเรียกก็
**ต่อเมื่อคีย์นั้นยังไม่มีอยู่จริง ๆ เท่านั้น** (เรียกว่า **lazy evaluation**) สังเกตจาก output ข้างบนว่าข้อความ
"กาวยังไม่มีในสต็อก..." ถูกพิมพ์ออกมาเพราะ `"กาว"` เป็นคีย์ใหม่ — ถ้าเราเรียก `.or_insert_with(...)` กับคีย์ที่มี
อยู่แล้ว (เช่น `"ปากกา"`) closure นี้จะ**ไม่ถูกเรียกเลย** ต่างจาก `.or_insert(default)` ที่ต้อง**ประเมินค่า
`default` ทุกครั้งไม่ว่าจะใช้จริงหรือไม่** (เพราะ `default` เป็น value ธรรมดา ไม่ใช่ closure) — ความแตกต่างนี้
สำคัญมากถ้าการคำนวณค่า default มีต้นทุนสูง (เช่น query database, allocate โครงสร้างข้อมูลขนาดใหญ่, หรือคำนวณอะไร
ที่ใช้เวลานาน) การเลือก `.or_insert_with()` ในกรณีนั้นช่วยหลีกเลี่ยงการคำนวณที่สูญเปล่าไปได้ทั้งหมด

ยังมี `.or_default()` ซึ่งเทียบเท่ากับ `.or_insert(Default::default())` แต่สั้นกว่า เหมาะกับ type ที่ implement
trait `Default` (เช่น `u32` มีค่า default เป็น `0` อยู่แล้ว):

```rust
use std::collections::HashMap;

fn main() {
    let mut counts: HashMap<String, u32> = HashMap::new();
    *counts.entry(String::from("ปากกา")).or_default() += 1;
    *counts.entry(String::from("ปากกา")).or_default() += 1;
    println!("{counts:?}");
}
```

ผลลัพธ์:

```
{"ปากกา": 2}
```

รูปแบบ `*map.entry(key).or_default() += 1;` คือ idiom ที่พบเจอบ่อยที่สุดในโค้ด Rust จริงสำหรับงาน "นับจำนวนครั้ง"
(counting) ทุกชนิด และคือแกนกลางของตัวอย่าง word-frequency counter ที่จะเห็นแบบเต็มรูปแบบในหัวข้อ 15.11

**ข้อสังเกตเรื่อง ownership ของ `.entry()`**: สังเกตว่า `.entry()` รับคีย์เป็น **value ตรง ๆ** (`String` ไม่ใช่
`&str`) ไม่ใช่ reference แบบ `.get()` — เหตุผลคือถ้าคีย์นั้นยังไม่มีอยู่ `.entry()` ต้องมี ownership ของคีย์พร้อม
ที่จะ insert เข้า map ทันที (เหมือน `.insert()` ปกติ) ซึ่งหมายความว่า **ทุกครั้งที่เรียก `.entry(String::from(...))`
คุณกำลัง allocate `String` ใหม่ขึ้นมาหนึ่งตัวเสมอ ไม่ว่าคีย์นั้นจะมีอยู่แล้วหรือไม่ก็ตาม** — ถ้าคุณมีคีย์เป็น
`String` ที่ owned อยู่แล้ว (เช่นตัวแปรที่ได้จากการวน loop) การส่งเข้า `.entry()` ตรง ๆ (ไม่ clone) จะประหยัดกว่า
การสร้าง `String::from(...)` ใหม่ทุกครั้งอย่างในตัวอย่างข้างบน — เราจะเห็นรูปแบบที่มีประสิทธิภาพกว่านี้ในตัวอย่าง
word-frequency counter ท้ายบท

### 15.6 การลบค่า: `.remove()` คืน `Option<V>`

`.remove(&key)` ลบคู่ key-value ออกจาก map และคืนค่าที่ถูกลบกลับมาเป็น **`Option<V>`** (ไม่ใช่ `&V` เพราะค่านั้น
ถูกดึงออกมาเป็นเจ้าของโดยผู้เรียก ไม่ใช่แค่ยืมดูอีกต่อไป) — `Some(value)` ถ้าคีย์นั้นมีอยู่และถูกลบสำเร็จ, `None`
ถ้าคีย์นั้นไม่มีอยู่เลย (ไม่มีอะไรให้ลบ):

```rust
use std::collections::HashMap;

fn main() {
    let mut cart: HashMap<String, u32> = HashMap::new();
    cart.insert(String::from("ปากกา"), 3);
    cart.insert(String::from("กระดาษ"), 2);

    let removed = cart.remove("ปากกา");
    println!("{removed:?}"); // Some(3)

    let removed_again = cart.remove("ปากกา");
    println!("{removed_again:?}"); // None เพราะถูกลบไปแล้ว

    println!("{cart:?}");
}
```

ผลลัพธ์:

```
Some(3)
None
{"กระดาษ": 2}
```

รูปแบบนี้ตรงกับหลักการที่เห็นมาตลอดบทนี้แล้ว: **operation ใดก็ตามของ `HashMap` ที่ "อาจไม่มีอะไรให้ทำ" จะคืนค่า
เป็น `Option<T>` เสมอ** ไม่ใช่ throw exception (ภาษาอื่นบางภาษา) ไม่ใช่คืนค่าพิเศษที่แปลว่า "เปล่า" แบบ `-1` หรือ
`null` (ภาษาอื่นที่ไม่มี type system เข้มงวด) — คุณต้องจัดการทั้งสองกรณีอย่างชัดเจนเสมอ ไม่ว่าจะด้วย `match`,
`if let`, หรือเทคนิคจาก Part 11 อื่น ๆ

### 15.7 การ iterate และปัญหาลำดับที่ไม่แน่นอน (สำคัญมาก)

`for (k, v) in &map` วน iterate ผ่านทุกคู่ key-value ได้ (ใช้ `&map` เพื่อยืมดูโดยไม่ take ownership — ตรงกับ
รูปแบบที่คุณเคยเห็นกับ `Vec` ใน Part 13):

```rust
use std::collections::HashMap;

fn main() {
    let mut scores: HashMap<String, u32> = HashMap::new();
    scores.insert(String::from("Alice"), 90);
    scores.insert(String::from("Bob"), 85);
    scores.insert(String::from("Carol"), 78);

    for (name, score) in &scores {
        println!("{name}: {score}");
    }

    // iterate เอาแค่ key หรือแค่ value
    for name in scores.keys() {
        println!("มีนักเรียนชื่อ {name}");
    }
    for score in scores.values() {
        println!("มีคะแนน {score}");
    }
}
```

ตัวอย่างผลลัพธ์ที่เป็นไปได้ (จากการรันจริงครั้งหนึ่ง):

```
Bob: 85
Carol: 78
Alice: 90
มีนักเรียนชื่อ Bob
มีนักเรียนชื่อ Carol
มีนักเรียนชื่อ Alice
มีคะแนน 85
มีคะแนน 78
มีคะแนน 90
```

สังเกตว่าลำดับที่ได้ **ไม่ตรงกับลำดับที่ insert เลย** (เรา insert Alice ก่อน แต่ Bob กลับมาก่อนตอน iterate) —
นี่ไม่ใช่บั๊ก และไม่ใช่เรื่องบังเอิญ แต่เป็น**พฤติกรรมที่ Rust การันตีไว้อย่างเป็นทางการ**: เอกสารของ `HashMap`
ระบุตรง ๆ ว่า **"the iteration order of a HashMap is not specified, and is subject to change"**

#### ทำไมลำดับไม่แน่นอน — และยิ่งไปกว่านั้น มันเปลี่ยนได้ทุกครั้งที่รันโปรแกรม

เหตุผลพื้นฐานที่สุดคือสิ่งที่อธิบายไปแล้วในหัวข้อ 15.1: `HashMap` เก็บข้อมูลโดยใช้ตำแหน่ง bucket ที่คำนวณจาก hash
ของคีย์ ไม่ใช่ตามลำดับที่ insert เข้ามา ดังนั้นการวน iterate ก็คือการไล่ดู bucket ตามลำดับที่มันเก็บอยู่ภายใน
(internal layout) ซึ่ง**ไม่มีความสัมพันธ์ใด ๆ กับลำดับ insert เลย** — นี่แตกต่างจาก `Vec` อย่างสิ้นเชิงที่รักษา
ลำดับ insert ไว้เสมอ (ตรงตามที่เรียนมาใน Part 13)

แต่ที่น่าสนใจกว่านั้นคือ Rust ยังไปอีกขั้น: **`HashMap` ของ std ใช้ hash function ที่มี seed สุ่มใหม่ทุกครั้งที่
โปรแกรมเริ่มรัน (per-process random seeding)** ลองสังเกตผลลัพธ์จากการรันโปรแกรมเดียวกัน (ไม่ได้แก้โค้ดแม้แต่นิด
เดียว) ซ้ำหลายครั้ง:

```
2 -> b
3 -> c
1 -> a
---
3 -> c
1 -> a
2 -> b
---
1 -> a
2 -> b
3 -> c
---
```

นี่คือผลจากการรัน **binary เดียวกัน** สี่ครั้งติดกัน (โค้ดแค่ `insert(1, "a")`, `insert(2, "b")`, `insert(3, "c")`
แล้ว iterate) — จะเห็นว่าลำดับที่ได้**เปลี่ยนไปในแต่ละครั้งที่รัน** ทั้งที่เป็นโปรแกรมเดียวกันเป๊ะ ไม่ได้ compile
ใหม่ด้วยซ้ำ

เหตุผลที่ Rust ตั้งใจทำแบบนี้เกี่ยวข้องกับ**ความปลอดภัย**: hash function ที่ std เลือกใช้เป็น default (ชื่อ
**SipHash**) ถูกสุ่ม seed ใหม่ทุกครั้งที่โปรแกรมเริ่มต้น (มาจาก randomness ของระบบปฏิบัติการ) เพื่อป้องกันการโจมตี
ที่เรียกว่า **"HashDoS" (Hash-flooding Denial of Service)** — ถ้า hash function ใช้ seed ตายตัวเหมือนกันทุกครั้ง
(เหมือนภาษาโปรแกรมมิ่งรุ่นเก่าหลายภาษาที่เคยมีปัญหานี้มาก่อน) ผู้โจมตีที่รู้ algorithm ของ hash function สามารถ
**สร้าง input ชุดหนึ่งที่ทำให้ทุกคีย์ hash ไปตกที่ bucket เดียวกันหมด** (เรียกว่า hash collision attack) ทำให้
`HashMap` เสื่อมสภาพจาก O(1) กลายเป็น O(n) ทุก operation โดยตั้งใจ — ถ้าระบบของคุณรับ input จากผู้ใช้ภายนอกมาใส่
เป็นคีย์ของ `HashMap` (เช่น query parameter ของ HTTP request, form field) ผู้โจมตีสามารถส่ง request ที่ออกแบบมา
เฉพาะเพื่อทำให้ server ช้าลงมหาศาลได้ (denial of service) การสุ่ม seed ใหม่ทุกครั้งที่โปรแกรมเริ่มทำให้ผู้โจมตี
**ไม่รู้ seed ล่วงหน้า** จึงสร้าง input โจมตีแบบเจาะจงไม่ได้อีกต่อไป — นี่คือรายละเอียดด้าน security ที่ฝังอยู่ใน
การออกแบบพื้นฐานที่สุดของ `HashMap` โดยที่ผู้ใช้ทั่วไปไม่รู้ตัวเลยว่ามันทำงานอยู่เบื้องหลัง

ผลข้างเคียงของการออกแบบเพื่อความปลอดภัยนี้คือสิ่งที่คุณเพิ่งเห็น: **ห้ามเขียนโค้ดที่พึ่งพาลำดับการ iterate ของ
`HashMap` โดยเด็ดขาด** ไม่ว่าจะเป็นลำดับ insert, ลำดับตามคีย์, หรือลำดับอะไรก็ตาม — แม้แต่การรันโปรแกรมเดียวกัน
สองครั้งก็ยังได้ลำดับต่างกันได้ ถ้าโค้ดของคุณต้องแสดงผลลัพธ์ให้ผู้ใช้ดูแบบมีลำดับที่คาดเดาได้ (เช่น เรียงตามชื่อ
ตัวอักษร หรือเรียงตามคะแนนมากไปน้อย) มีทางเลือกหลัก 2 ทาง:

1. **แปลงเป็น `Vec` แล้ว `.sort()` เอง** ก่อนแสดงผล (เห็นเต็มรูปแบบในตัวอย่างหัวข้อ 15.11)
2. **ใช้ `BTreeMap` แทน `HashMap`** ตั้งแต่แรก ถ้าต้องการลำดับตามคีย์เสมอโดยไม่ต้อง sort เพิ่มทุกครั้ง (หัวข้อ
   15.10)

### 15.8 ทำไมคีย์ของ `HashMap` ต้อง implement `Hash` และ `Eq`

ถ้าลองดูที่ type signature จริงของ `HashMap` ใน standard library (`HashMap<K, V, S = RandomState>` ที่มี trait
bound `K: Eq + Hash` ซ่อนอยู่ในทุก method ที่เกี่ยวกับการค้นหา) จะพบว่าคีย์ (`K`) ต้อง implement ทั้ง **`Hash`**
และ **`Eq`** เสมอ ไม่มีข้อยกเว้น เหตุผลมาจากวิธีทำงานภายในของ hash table ที่อธิบายไว้ในหัวข้อ 15.1: การเก็บและ
ค้นหาข้อมูลต้องใช้ **สองขั้นตอนที่ต่างกัน**

1. **`Hash`**: ใช้แปลงคีย์เป็นเลข hash เพื่อคำนวณว่า**ควรไปดูที่ bucket ไหน** — นี่คือขั้นแรกที่ทำให้ narrow
   ลงมาจากการค้นหาทั้ง collection เหลือแค่การดูใน bucket เดียว (หรือไม่กี่ bucket)
2. **`Eq`**: เมื่อไปถึง bucket ที่คาดว่าคีย์ควรอยู่แล้ว (อาจมีคีย์อื่นที่ hash ไปตำแหน่งเดียวกันโดยบังเอิญอยู่ใน
   bucket เดียวกันด้วย — เรียกว่า **hash collision** ซึ่งเกิดขึ้นได้เสมอในทางทฤษฎีไม่ว่า hash function จะดีแค่ไหน)
   ต้องมีวิธี**เทียบว่าคีย์ที่เจอใน bucket นั้นตรงกับคีย์ที่ค้นหาจริง ๆ เป๊ะ ๆ หรือไม่** — นี่คือหน้าที่ของ `Eq`

สองขั้นตอนนี้ต้อง**สอดคล้องกันเสมอ**: ถ้าสองค่าถือว่า "เท่ากัน" ตาม `Eq` (`a == b` เป็น `true`) มันต้อง**มี hash
เดียวกันเสมอ** (`hash(a) == hash(b)`) — ไม่งั้น hash table จะพังทันที (ค้นหาคีย์ที่ insert ไปแล้วไม่เจอ เพราะมัน
ไปมองหาใน bucket ผิดตำแหน่ง) นี่คือเหตุผลที่ Rust บังคับให้ต้อง implement ทั้งสอง trait คู่กันเสมอ ไม่ปล่อยให้
implement แค่ตัวเดียว

#### ทำไม `f64` ใช้เป็นคีย์ของ `HashMap` ไม่ได้ — ปัญหาของ `NaN`

นี่คือกับดักที่มือใหม่จำนวนมากเจอโดยไม่รู้ตัวว่าสาเหตุคืออะไร ลองดูโค้ดนี้:

```rust
use std::collections::HashMap;

fn main() {
    let mut prices: HashMap<f64, &str> = HashMap::new();
    prices.insert(9.99, "ถูก");
    println!("{:?}", prices.get(&9.99));
}
```

โค้ดนี้ **compile ไม่ผ่านเลย**:

```
error[E0599]: the method `insert` exists for struct `HashMap<f64, &str>`, but its trait bounds were not satisfied
 --> src/main.rs:5:12
  |
5 |     prices.insert(9.99, "ถูก");
  |            ^^^^^^
  |
  = note: the following trait bounds were not satisfied:
          `f64: Eq`
          `f64: Hash`

error[E0599]: the method `get` exists for struct `HashMap<f64, &str>`, but its trait bounds were not satisfied
 --> src/main.rs:6:29
  |
6 |     println!("{:?}", prices.get(&9.99));
  |                             ^^^ method cannot be called on `HashMap<f64, &str>` due to unsatisfied trait bounds
  |
  = note: the following trait bounds were not satisfied:
          `f64: Eq`
          `f64: Hash`

```

สังเกตว่า error ไม่ได้เกิดตอนประกาศ type `HashMap<f64, &str>` (ประกาศ type ผ่านได้เฉย ๆ) แต่เกิดตอนเรียกใช้
`.insert()` และ `.get()` จริง ๆ — เพราะ `HashMap<K, V>` เองไม่ได้บังคับ `K: Eq + Hash` ที่ระดับการประกาศ struct
แต่บังคับที่ระดับ **method** ที่เกี่ยวกับการค้นหา/แก้ไข (นี่คือรายละเอียดทาง type system ที่คุณจะเข้าใจลึกขึ้นมาก
ตอนเรียน generics และ trait bounds ใน Part 18-19 — ตอนนี้จำแค่ผลลัพธ์ที่เห็นตรงหน้าไว้ก่อน)

**เหตุผลที่ `f64` (และ `f32`) ไม่ implement `Eq`**: ทั้งสอง implement แค่ **`PartialEq`** เท่านั้น ไม่ implement
`Eq` เลย ต้นเหตุมาจากค่าพิเศษของ floating-point ตามมาตรฐาน IEEE 754 ที่คุณเคยเห็นเงา ๆ มาแล้วใน Part 3 เรื่อง
`0.1 + 0.2 != 0.3` นั่นคือค่า **`NaN` (Not a Number)** ซึ่งมีคุณสมบัติที่แปลกมากคือ **`NaN == NaN` ให้ผลเป็น
`false` เสมอ** (ตามมาตรฐาน IEEE 754 กำหนดไว้แบบนี้ตรง ๆ ไม่ใช่ bug ของ Rust) ลองดูตัวอย่าง:

```rust
fn main() {
    let x = f64::NAN;
    println!("{}", x == x); // false !!
}
```

การที่ค่าหนึ่งเทียบกับ**ตัวมันเอง**แล้วได้ `false` คือการละเมิดกฎพื้นฐานที่สุดของความสัมพันธ์แบบ **equivalence
relation** ในทางคณิตศาสตร์ ซึ่งต้องมีคุณสมบัติ **reflexive** (`a == a` ต้องเป็น `true` เสมอ) — Rust แยก concept
นี้ออกเป็นสอง trait ชัดเจน:

- **`PartialEq`**: บังคับแค่ symmetric (`a == b` ↔ `b == a`) และ transitive เท่านั้น **ไม่บังคับ reflexive**
  — `f64` implement ได้เพราะยอมรับกรณี `NaN == NaN` เป็น `false` ได้ (เป็น "partial" เพราะไม่ครอบคลุมทุกค่าให้
  equivalence เต็มรูปแบบ)
- **`Eq`**: เป็น trait ย่อยที่ **เพิ่มเงื่อนไข reflexive** เข้ามา (`a == a` ต้อง `true` เสมอไม่มีข้อยกเว้น) —
  `f64` ไม่สามารถ implement ได้เพราะ `NaN` ละเมิดกฎนี้ตรง ๆ

ถ้า `f64` ใช้เป็นคีย์ของ `HashMap` ได้จริง แล้วมีคนใส่ `NaN` เป็นคีย์เข้าไป จะเกิดสถานการณ์ที่ประหลาดมาก: คุณ
`insert(f64::NAN, value)` ไปแล้ว แต่พอ `.get(&f64::NAN)` ค้นหาด้วยคีย์เดียวกันเป๊ะ ก็จะ**หาไม่เจอ** เพราะระบบเช็ค
ความเท่ากันด้วย `==` ซึ่ง `NaN == NaN` เป็น `false` เสมอ — ค่านั้นจะกลายเป็น "หายไป" อยู่ใน map ตลอดกาล ไม่มีทาง
ค้นหาเจอได้อีกเลยแม้จะรู้คีย์เป๊ะ ๆ นี่คือบั๊กประเภทที่อันตรายมากเพราะไม่มีทาง detect ได้ตอน compile time ถ้า
ปล่อยให้ `f64` เป็นคีย์ได้ — Rust จึงเลือกป้องกันปัญหานี้ **ตั้งแต่ตอน compile time เลย** โดยไม่ให้ `f64`
implement `Eq`/`Hash` แต่แรก ทำให้ error นี้เกิดขึ้นทันทีที่คุณลองใช้ ไม่ต้องรอไปเจอบั๊กประหลาดตอน runtime ในอนาคต

**วิธีแก้เมื่อต้องการใช้ตัวเลขทศนิยมเป็นคีย์**: มีทางเลือกหลัก ๆ ตามความเหมาะสมของสถานการณ์

- **แปลงเป็น integer ก่อน**: ถ้าค่านั้นมีความละเอียดจำกัดที่รู้แน่นอน (เช่น ราคาสินค้าที่ละเอียดสุดแค่ 2 ตำแหน่ง)
  ให้เก็บเป็น "สตางค์" (คูณ 100 แล้ว round เป็น `u64`/`i64`) แบบเดียวกับที่ Part 3 แนะนำไว้สำหรับงานการเงินที่
  ต้องเลี่ยง float โดยตรงอยู่แล้ว วิธีนี้ได้ทั้งความแม่นยำและใช้เป็นคีย์ `HashMap` ได้ทันทีเพราะ integer
  implement `Eq`/`Hash` ครบ
- **ใช้ bit representation**: แปลง `f64` เป็น `u64` ด้วย `.to_bits()` แล้วใช้ `u64` นั้นเป็นคีย์แทน (`u64`
  implement `Eq`/`Hash` เพราะเป็นการเทียบ bit pattern ตรง ๆ ไม่ใช่ค่าทางคณิตศาสตร์ — วิธีนี้ทำให้ `NaN` กลายเป็น
  bit pattern ที่แน่นอนหนึ่งแบบ เทียบกันได้ปกติ แต่ต้องระวังว่า `NaN` มีได้หลาย bit pattern ที่ต่างกัน จึงยังมี
  ข้อจำกัดในกรณีขอบ)
- **ใช้ crate ภายนอกอย่าง `ordered-float`**: ห่อ `f64` ด้วย wrapper type ที่ implement `Eq`/`Hash`/`Ord` ให้
  ครบ (โดยกำหนดพฤติกรรม `NaN` ไว้ชัดเจนล่วงหน้า เช่น ให้ `NaN` มากกว่าทุกค่าเสมอ) — เหมาะกับโค้ดที่ต้องทำงานกับ
  float เป็นคีย์บ่อย ๆ และไม่อยากเขียน wrapper เองซ้ำ ๆ (crate ภายนอกจะเจาะลึกใน Part 17 เรื่อง Crates)

หมายเหตุ: ปัญหาเดียวกันนี้เกิดกับ `BTreeMap`/`BTreeSet` เช่นกัน แต่คนละ trait — `BTreeMap` ต้องการ `Ord` (การ
เรียงลำดับได้แบบสมบูรณ์) ซึ่ง `f64` ก็ไม่ implement เช่นกัน (มีแค่ `PartialOrd` เพราะ `NaN` เทียบมากกว่า/น้อยกว่า
กับอะไรไม่ได้เลย) จะเห็น error ที่คล้ายกันแต่พูดถึง `Ord` แทน `Eq`/`Hash` — จะกล่าวถึงอีกครั้งในหัวข้อ 15.10

### 15.9 `HashSet<T>`: "HashMap ที่สนใจแค่คีย์"

ถ้าคุณไม่ต้องการเก็บ "ค่า" ควบคู่กับคีย์เลย แค่ต้องการรู้ว่า **"มีสิ่งนี้อยู่ในกลุ่มหรือไม่"** (เช่น เช็คว่า
username นี้ถูกใช้ไปแล้วหรือยัง, tag นี้ถูกกำหนดให้สินค้าแล้วหรือยัง) `HashSet<T>` คือ collection ที่ออกแบบมา
เพื่องานนี้โดยตรง — ในทางเทคนิค `HashSet<T>` ใน standard library ของ Rust ถูก implement โดยใช้
`HashMap<T, ()>` ภายใน (คีย์คือค่าที่คุณสนใจ ส่วน value คือ unit type `()` ที่ไม่มีความหมายอะไรเลย นอกจาก "มี
อยู่") — พูดง่าย ๆ คือ `HashSet` แทบจะเป็น `HashMap` ตัวเดียวกันแค่ไม่แคร์ value

```rust
use std::collections::HashSet;

fn main() {
    let mut tags: HashSet<String> = HashSet::new();
    tags.insert(String::from("rust"));
    tags.insert(String::from("backend"));
    tags.insert(String::from("rust")); // ซ้ำ — ไม่เพิ่มอะไรใหม่

    println!("จำนวน tag ที่ไม่ซ้ำ: {}", tags.len());
    println!("มี tag 'rust' หรือไม่: {}", tags.contains("rust"));

    tags.remove("backend");
    println!("{tags:?}");
}
```

ผลลัพธ์:

```
จำนวน tag ที่ไม่ซ้ำ: 2
มี tag 'rust' หรือไม่: true
{"rust"}
```

สังเกตว่าการ `insert("rust")` ครั้งที่สองไม่ทำให้ `.len()` เพิ่มขึ้นเลย (ยังเป็น 2 ไม่ใช่ 3) — นี่คือคุณสมบัติหลัก
ของ set ในทางคณิตศาสตร์: **สมาชิกทุกตัวไม่ซ้ำกัน** เมธอกที่ใช้บ่อยของ `HashSet` มีสามตัวหลัก ตรงไปตรงมามาก:

- `.insert(value)` — คืน `bool`: `true` ถ้าเพิ่งเพิ่มเข้าไปใหม่จริง ๆ, `false` ถ้าค่านี้มีอยู่แล้ว (ไม่ได้เพิ่ม
  ซ้ำ) — ค่าที่คืนนี้เองก็มีประโยชน์ในการเช็คว่า "นี่คือครั้งแรกที่เจอค่านี้หรือไม่" โดยไม่ต้อง `.contains()`
  ก่อนแยก
- `.contains(&value)` — เช็คว่ามีค่านี้อยู่ในเซตหรือไม่ คืน `bool` ตรง ๆ (ไม่ใช่ `Option` เพราะไม่มี "ค่า" ที่ต้อง
  ดึงออกมา มีแค่ "อยู่หรือไม่อยู่")
- `.remove(&value)` — ลบค่าออก คืน `bool`: `true` ถ้ามีอยู่จริงและลบสำเร็จ, `false` ถ้าไม่มีอยู่ (ไม่มีอะไรให้ลบ)

#### Set operations: union, intersection, difference, symmetric_difference

จุดที่ `HashSet` มีประโยชน์เหนือกว่า `Vec` ที่เอา `.contains()` มาเช็คซ้ำ ๆ เองคือ**การดำเนินการทางเซตในเชิง
คณิตศาสตร์**ที่มีให้ใช้พร้อมแล้ว — เหมาะมากกับปัญหาจริงเช่น "หา tag ที่สินค้าสองตัวมีร่วมกัน" หรือ "หานักเรียนที่
ลงทั้งสองวิชา":

```rust
use std::collections::HashSet;

fn main() {
    let product_a_tags: HashSet<&str> = ["rust", "web", "backend", "opensource"].into_iter().collect();
    let product_b_tags: HashSet<&str> = ["rust", "cli", "opensource"].into_iter().collect();

    let mut common: Vec<&&str> = product_a_tags.intersection(&product_b_tags).collect();
    common.sort();
    println!("tag ที่มีร่วมกัน: {common:?}");

    let mut only_a: Vec<&&str> = product_a_tags.difference(&product_b_tags).collect();
    only_a.sort();
    println!("tag ที่มีเฉพาะสินค้า A: {only_a:?}");

    let mut all_tags: Vec<&&str> = product_a_tags.union(&product_b_tags).collect();
    all_tags.sort();
    println!("tag ทั้งหมดรวมกัน: {all_tags:?}");
}
```

ผลลัพธ์:

```
tag ที่มีร่วมกัน: ["opensource", "rust"]
tag ที่มีเฉพาะสินค้า A: ["backend", "web"]
tag ทั้งหมดรวมกัน: ["backend", "cli", "opensource", "rust", "web"]
```

อีกตัวอย่างที่เจอบ่อยในระบบการศึกษา/HR: หานักเรียนที่ลงทั้งสองวิชา, ลงแค่วิชาเดียว, หรือลงอย่างน้อยวิชาใดวิชาหนึ่ง:

```rust
use std::collections::HashSet;

fn main() {
    let rust_course: HashSet<&str> = ["Alice", "Bob", "Carol", "Dave"].into_iter().collect();
    let go_course: HashSet<&str> = ["Bob", "Erin", "Dave", "Frank"].into_iter().collect();

    let mut both: Vec<&&str> = rust_course.intersection(&go_course).collect();
    both.sort();
    println!("ลงทั้งสองวิชา: {both:?}");

    let mut only_rust: Vec<&&str> = rust_course.difference(&go_course).collect();
    only_rust.sort();
    println!("ลงแค่วิชา Rust: {only_rust:?}");

    let mut everyone: Vec<&&str> = rust_course.union(&go_course).collect();
    everyone.sort();
    println!("นักเรียนทั้งหมด (ไม่ซ้ำ): {everyone:?}");

    let mut either_not_both: Vec<&&str> = rust_course.symmetric_difference(&go_course).collect();
    either_not_both.sort();
    println!("ลงแค่วิชาเดียว (ไม่ใช่ทั้งสอง): {either_not_both:?}");
}
```

ผลลัพธ์:

```
ลงทั้งสองวิชา: ["Bob", "Dave"]
ลงแค่วิชา Rust: ["Alice", "Carol"]
นักเรียนทั้งหมด (ไม่ซ้ำ): ["Alice", "Bob", "Carol", "Dave", "Erin", "Frank"]
ลงแค่วิชาเดียว (ไม่ใช่ทั้งสอง): ["Alice", "Carol", "Erin", "Frank"]
```

สรุปความหมายทางคณิตศาสตร์ของ set operation ทั้งสี่ตัว:

| Method | ความหมาย | ตัวอย่าง (A = {1,2,3}, B = {2,3,4}) |
|---|---|---|
| `.intersection(&other)` | สมาชิกที่อยู่ **ทั้งสองเซต** | {2, 3} |
| `.union(&other)` | สมาชิกที่อยู่ **เซตใดเซตหนึ่ง** (ไม่ซ้ำ) | {1, 2, 3, 4} |
| `.difference(&other)` | สมาชิกที่อยู่ **เฉพาะเซตแรก** ไม่อยู่ในเซตที่สอง | {1} |
| `.symmetric_difference(&other)` | สมาชิกที่อยู่ **เซตใดเซตหนึ่งเท่านั้น** (ไม่อยู่ทั้งสอง) | {1, 4} |

จุดสำคัญที่ต้องสังเกตในโค้ด: ทั้งสี่ method นี้**คืนค่าเป็น iterator** (ไม่ใช่ `HashSet` ใหม่ตรง ๆ) — ต้องเรียก
`.collect()` ต่อถ้าต้องการเก็บเป็น collection จริง (ในตัวอย่างข้างบนเราเลือก `.collect()` เป็น `Vec` แล้ว `.sort()`
เพื่อให้ผลลัพธ์แสดงในลำดับที่คาดเดาได้เสมอสำหรับการแสดงผล — เหตุผลเดียวกับที่อธิบายไว้ในหัวข้อ 15.7 ว่าลำดับของ
`HashSet` ก็ไม่แน่นอนเช่นเดียวกับ `HashMap` เพราะใช้กลไก hash เดียวกันเป๊ะ) และสังเกตว่า type ที่ได้จาก
`.collect()` ในตัวอย่างนี้คือ `Vec<&&str>` (reference ซ้อน reference) เพราะ `product_a_tags` เป็น
`HashSet<&str>` ดังนั้นสมาชิกภายในมี type เป็น `&str` อยู่แล้ว การ iterate ผ่าน `.intersection()` (ที่ยืมดูโดย
ไม่ take ownership) จึงได้ `&&str` — ถ้าอยากได้ `Vec<&str>` ตรง ๆ ให้ใส่ `.copied()` ต่อท้าย `.collect()`

### 15.10 `BTreeMap` / `BTreeSet`: ทางเลือกที่เรียงลำดับได้

จากหัวข้อ 15.7 เราเห็นแล้วว่า `HashMap` ไม่การันตีลำดับการ iterate เลย ถ้าโปรแกรมของคุณ**ต้องการลำดับที่แน่นอน
เสมอ** (โดยเฉพาะเรียงตามคีย์) โดยไม่อยาก `.sort()` เพิ่มทุกครั้งที่ต้องแสดงผล — `BTreeMap<K, V>` และ
`BTreeSet<T>` คือคำตอบ

`BTreeMap` เก็บข้อมูลด้วยโครงสร้าง **B-tree** (ต้นไม้แบบสมดุลที่ออกแบบมาให้มีประสิทธิภาพดีบน memory จริง ไม่ใช่
แค่ในทางทฤษฎี) ซึ่งรักษาคีย์ให้**เรียงลำดับอยู่เสมอ**โดยธรรมชาติของโครงสร้าง — ไม่ว่าจะ insert คีย์ตามลำดับไหน
การ iterate จะได้ผลลัพธ์เรียงจากน้อยไปมากตามคีย์เสมอ 100% การันตี ไม่มีความสุ่มเข้ามาเกี่ยวข้องเลย:

```rust
use std::collections::BTreeMap;

fn main() {
    let mut scores: BTreeMap<String, u32> = BTreeMap::new();
    scores.insert(String::from("Carol"), 78);
    scores.insert(String::from("Alice"), 90);
    scores.insert(String::from("Bob"), 85);

    // เรียงตาม key เสมอ (Alice, Bob, Carol) ไม่ว่าจะ insert ลำดับไหน
    for (name, score) in &scores {
        println!("{name}: {score}");
    }
}
```

ผลลัพธ์ (เหมือนกันทุกครั้งที่รัน ไม่ว่าจะรันกี่รอบ):

```
Alice: 90
Bob: 85
Carol: 78
```

เทียบกับ `HashMap` ที่เราเห็นในหัวข้อ 15.7 ว่าลำดับเปลี่ยนไปทุกครั้งที่รัน — `BTreeMap` ให้ผลลัพธ์เดิมทุกครั้ง
เสมอ นี่คือความแตกต่างเชิง**การันตี** ที่สำคัญที่สุดระหว่างสองตัวนี้

`BTreeMap` และ `HashMap` มี API ส่วนใหญ่**เหมือนกันทุกประการ** — `.insert()`, `.get()`, `.remove()`,
`.contains_key()`, `.entry()` ทำงานแบบเดียวกันเป๊ะ (รวมถึงคืนค่าเป็น `Option<T>` ในสถานการณ์เดียวกันด้วย)
ความแตกต่างมีอยู่สองจุดหลัก

**ความแตกต่างที่ 1 — Trait bound ของคีย์**: `BTreeMap` ต้องการ `K: Ord` (เรียงลำดับได้แบบสมบูรณ์) แทน
`K: Eq + Hash` — นี่คือเหตุผลที่ `f64` ใช้เป็นคีย์ของ `BTreeMap` ไม่ได้เช่นกัน (ตามที่พูดถึงท้ายหัวข้อ 15.8):

```rust
use std::collections::BTreeMap;

fn main() {
    let mut prices: BTreeMap<f64, &str> = BTreeMap::new();
    prices.insert(9.99, "ถูก");
    println!("{prices:?}");
}
```

`f64` implement แค่ `PartialOrd` เท่านั้น ไม่ implement `Ord`

**ความแตกต่างที่ 2 — Performance characteristics**: `BTreeMap` ทำ operation หลัก (`get`, `insert`, `remove`)
ด้วยความซับซ้อน **O(log n)** ไม่ใช่ O(1) โดยเฉลี่ยแบบ `HashMap` — ช้ากว่า `HashMap` ในทางทฤษฎี แต่ O(log n) ก็ยัง
เร็วมากในทางปฏิบัติ (ข้อมูล 1 ล้านตัวใช้ประมาณ log₂(1,000,000) ≈ 20 ขั้นตอนเท่านั้น) ส่วนต่างนี้แทบไม่มีผลกระทบใน
โปรแกรมทั่วไป ยกเว้นกรณีที่ throughput สำคัญมากจริง ๆ (เช่น hot path ที่เรียกหลายล้านครั้งต่อวินาที)

#### `.range()`: ข้อดีเฉพาะตัวของ `BTreeMap` ที่ `HashMap` ทำไม่ได้เลย

เพราะคีย์ถูกเก็บแบบเรียงลำดับ `BTreeMap` จึงทำ **range query** ได้อย่างมีประสิทธิภาพ — ค้นหา "ทุกคีย์ที่อยู่
ในช่วงที่กำหนด" โดยไม่ต้องไล่เช็คทุกสมาชิกเลย (`HashMap` ทำแบบนี้ไม่ได้โดยธรรมชาติ เพราะไม่มีแนวคิดเรื่อง "ระหว่าง"
สำหรับข้อมูลที่กระจายแบบสุ่มตาม hash):

```rust
use std::collections::BTreeMap;

fn main() {
    let mut prices: BTreeMap<u32, &str> = BTreeMap::new();
    prices.insert(100, "ถุงเท้า");
    prices.insert(500, "เสื้อ");
    prices.insert(1500, "กระเป๋า");
    prices.insert(50, "พวงกุญแจ");

    // range query: หาสินค้าราคา 100-1000
    for (price, name) in prices.range(100..=1000) {
        println!("{name} ราคา {price} บาท");
    }
}
```

ผลลัพธ์:

```
ถุงเท้า ราคา 100 บาท
เสื้อ ราคา 500 บาท
```

`.range(100..=1000)` ใช้ syntax ของ range ตัวเดียวกับที่คุณเรียนมาแล้วใน Part 4 และ Part 8 (`start..=end` คือ
range ที่รวมค่าปลายทั้งสองด้าน, `start..end` คือ range ที่ไม่รวมปลายบน) เพียงแต่ตอนนี้นำมาใช้กรองคีย์ของ
`BTreeMap` โดยตรง — สังเกตว่า `1500` (กระเป๋า) และ `50` (พวงกุญแจ) ไม่ถูกดึงออกมา เพราะอยู่นอกช่วง `100..=1000`
พอดี การทำแบบนี้กับ `HashMap` เป็นไปไม่ได้เลยในหลักการ (ต้องไล่เช็คทุกตัวแล้วกรองเอง กลับไปเป็น O(n) เหมือนปัญหา
ตั้งต้นในหัวข้อ 15.1)

#### `BTreeSet<T>`: เหมือน `HashSet` แต่เรียงลำดับ

`BTreeSet<T>` มีความสัมพันธ์กับ `BTreeMap<T, ()>` แบบเดียวกับที่ `HashSet<T>` มีกับ `HashMap<T, ()>`:

```rust
use std::collections::BTreeSet;

fn main() {
    let mut unique_scores: BTreeSet<u32> = BTreeSet::new();
    unique_scores.insert(90);
    unique_scores.insert(85);
    unique_scores.insert(78);
    unique_scores.insert(85); // ซ้ำ ไม่เพิ่ม

    // iterate ได้ลำดับน้อยไปมากเสมอ: 78, 85, 90
    for score in &unique_scores {
        println!("{score}");
    }
}
```

ผลลัพธ์:

```
78
85
90
```

`BTreeSet` มี set operation ครบเหมือน `HashSet` (`.union()`, `.intersection()`, `.difference()`,
`.symmetric_difference()`) และยังได้ผลลัพธ์เรียงลำดับมาโดยธรรมชาติเพิ่มด้วย เหมาะกับกรณีที่ต้องแสดงผลลัพธ์แบบ
เรียงลำดับโดยไม่อยาก `.sort()` เพิ่มเอง

#### ตารางสรุป: เลือก `HashMap`/`HashSet` หรือ `BTreeMap`/`BTreeSet`

| ต้องการ | เลือก |
|---|---|
| ความเร็วสูงสุดในการค้นหา/insert/ลบ (O(1) โดยเฉลี่ย) ไม่สนใจลำดับเลย | `HashMap` / `HashSet` |
| ต้องการ iterate ได้ลำดับตามคีย์เสมอ โดยไม่อยาก sort เพิ่ม | `BTreeMap` / `BTreeSet` |
| ต้องการ range query (หาคีย์ที่อยู่ในช่วง [a, b]) | `BTreeMap` / `BTreeSet` เท่านั้น |
| ต้องการ output ที่ deterministic เหมือนกันทุกครั้งที่รัน (เช่น เพื่อ test หรือ reproducibility) | `BTreeMap` / `BTreeSet` |
| คีย์เป็น `f64`/`f32` โดยตรง | ทั้งสองแบบใช้ไม่ได้เลย — ต้องแปลงเป็น integer หรือใช้ wrapper type ก่อน |

หลักการเลือกแบบง่ายที่สุด: **เริ่มจาก `HashMap`/`HashSet` เป็น default เสมอ** (เพราะเร็วที่สุดในกรณีทั่วไป และ
เป็นตัวเลือกที่โปรแกรมเมอร์ Rust ส่วนใหญ่คุ้นเคยที่สุด) แล้วเปลี่ยนไปใช้ `BTreeMap`/`BTreeSet` **เฉพาะเมื่อมีเหตุผล
ชัดเจน** ว่าต้องการลำดับหรือ range query จริง ๆ — อย่าเลือก `BTreeMap` "เผื่อไว้" หรือเพราะรู้สึกว่าลำดับที่แน่นอน
"ดูปลอดภัยกว่า" ทั้งที่โปรแกรมไม่ได้ต้องการลำดับนั้นจริง เพราะจะเสีย performance โดยไม่ได้ประโยชน์อะไรกลับมา

### 15.11 ตัวอย่างจริง: Word-Frequency Counter จากข้อความไทย/อังกฤษผสม

มาประกอบทุกอย่างที่เรียนมาในบทนี้เข้าด้วยกันในตัวอย่างที่ใช้งานจริงได้: นับความถี่ของคำในข้อความ ซึ่งเป็นงาน
พื้นฐานของการวิเคราะห์ข้อความ (text analytics), ระบบค้นหา, หรือแม้แต่ spam filter อย่างง่าย ๆ — ตัวอย่างนี้ดึง
ความรู้เรื่อง UTF-8 และการจัดการ string จาก Part 14 มาผสมกับ `.entry()` API ของบทนี้โดยตรง:

```rust
use std::collections::HashMap;

fn word_frequency(text: &str) -> HashMap<String, u32> {
    let mut counts: HashMap<String, u32> = HashMap::new();
    for word in text.split_whitespace() {
        let normalized = word.to_lowercase();
        *counts.entry(normalized).or_insert(0) += 1;
    }
    counts
}

fn main() {
    let text = "rust คือภาษาที่ปลอดภัย rust เร็ว และ rust สนุกด้วย ภาษาที่ปลอดภัยและเร็วคือ rust";
    let counts = word_frequency(text);

    // HashMap ไม่มีลำดับที่แน่นอน จึงแปลงเป็น Vec แล้ว sort เพื่อแสดงผล
    let mut ranked: Vec<(&String, &u32)> = counts.iter().collect();
    ranked.sort_by(|a, b| b.1.cmp(a.1).then_with(|| a.0.cmp(b.0)));

    for (word, count) in ranked {
        println!("{word}: {count} ครั้ง");
    }
}
```

ผลลัพธ์:

```
rust: 4 ครั้ง
คือภาษาที่ปลอดภัย: 1 ครั้ง
ภาษาที่ปลอดภัยและเร็วคือ: 1 ครั้ง
สนุกด้วย: 1 ครั้ง
เร็ว: 1 ครั้ง
และ: 1 ครั้ง
```

มาแยกวิเคราะห์ทีละส่วน:

- **`text.split_whitespace()`**: จาก Part 14 คุณรู้แล้วว่า `&str` ใน Rust เก็บเป็น UTF-8 bytes ไม่ใช่ array ของ
  `char` — `.split_whitespace()` ทำงานถูกต้องกับข้อความ Unicode ทุกภาษา (รวมถึงภาษาไทย) เพราะมันแบ่งคำตามขอบเขต
  Unicode whitespace ไม่ใช่ตาม byte ตรง ๆ (ซึ่งจะพังกับ multi-byte character อย่างสิ้นเชิงถ้าเขียนแบบผิด ๆ)
  อย่างไรก็ตาม สังเกตว่าคำภาษาไทยที่ไม่มีช่องว่างคั่นระหว่างคำ (เช่น "คือภาษาที่ปลอดภัย" ที่จริงคือ 4 คำติดกัน)
  จะถูกมองเป็น**คำเดียว**ทั้งก้อน เพราะภาษาไทยไม่มีการเว้นวรรคระหว่างคำแบบภาษาอังกฤษ — การตัดคำภาษาไทยที่แม่นยำ
  จริง ๆ ต้องใช้ library เฉพาะทาง (word segmentation) ซึ่งอยู่นอกเหนือขอบเขตบทนี้ ตัวอย่างนี้จึงต้องเว้นวรรค
  ระหว่างคำไทยเองในข้อความตัวอย่าง เพื่อโฟกัสที่กลไกของ `HashMap` เป็นหลัก
- **`word.to_lowercase()`**: ทำให้ `"Rust"` และ `"rust"` ถูกนับเป็นคำเดียวกัน — จาก Part 14 คุณรู้ว่า
  `.to_lowercase()` ทำงานตามกฎ Unicode case folding เต็มรูปแบบ ไม่ใช่แค่ ASCII (แม้ในตัวอย่างนี้ใช้แค่ตัวอักษร
  ละติน แต่หลักการเดียวกันนี้ใช้ได้กับภาษาอื่นที่มี case เช่น เยอรมัน, กรีก, รัสเซีย)
- **`*counts.entry(normalized).or_insert(0) += 1`**: นี่คือแกนกลางของทั้งอัลกอริทึม — ใช้ `.entry()` API จาก
  หัวข้อ 15.5 ตรง ๆ: ถ้าเจอคำนี้ครั้งแรก จะ `or_insert(0)` ตั้งค่าเริ่มต้นเป็น 0 ก่อนบวก 1 (รวมเป็น 1) ถ้าเจอคำนี้
  ซ้ำ จะได้ `&mut V` ไปยังตัวนับที่มีอยู่แล้วโดยตรง แล้วบวกเพิ่มไปเรื่อย ๆ — ทั้งหมดนี้ด้วยการ hash คีย์แค่ครั้ง
  เดียวต่อคำ ไม่ต้อง `contains_key` แยก
- **`counts.iter().collect()` แล้ว `.sort_by()`**: นี่คือรูปแบบสำคัญที่สุดที่ต้องจำจากหัวข้อ 15.7 — เพราะ
  `HashMap` ไม่การันตีลำดับ iterate เลย การจะแสดงผลลัพธ์ "เรียงจากคำที่พบมากที่สุดไปน้อยที่สุด" ต้อง**แปลงเป็น
  `Vec` ก่อนแล้ว sort เอง** เสมอ — `counts.iter()` คืน iterator ของ `(&String, &u32)`, `.collect()` เก็บลงเป็น
  `Vec<(&String, &u32)>`, จากนั้น `.sort_by()` เรียงตาม closure ที่กำหนด: `b.1.cmp(a.1)` เรียงจากค่ามากไปน้อย
  (สลับ `a`/`b` เพื่อกลับทิศทางจาก ascending เป็น descending) แล้ว `.then_with(|| a.0.cmp(b.0))` เป็น tie-breaker
  — ถ้าจำนวนครั้งเท่ากัน ให้เรียงตามตัวอักษรของคำแทน (เพื่อให้ output คงที่แน่นอนทุกครั้งที่รัน ไม่ใช่แค่ "เรียง
  ตามจำนวนแล้วปล่อยให้ลำดับที่เท่ากันสุ่มไปตาม HashMap" ซึ่งจะทำให้ output เปลี่ยนไปมาระหว่างการรันแต่ละครั้ง)

รูปแบบ "เก็บด้วย `HashMap` เพื่อความเร็ว แล้วแปลงเป็น `Vec` sort ตอนจะแสดงผล" คือ pattern ที่พบเจอบ่อยที่สุดใน
โค้ด Rust จริงเมื่อทำงานกับ `HashMap` — มันให้ทั้งความเร็วของ hash-based lookup ตอนประมวลผล และความคาดเดาได้ของ
ลำดับตอนแสดงผลให้ผู้ใช้เห็น โดยเสีย cost แค่ครั้งเดียวตอนสุดท้าย (O(n log n) สำหรับ sort) ไม่ใช่ทุกครั้งที่ insert

### 15.12 ตัวอย่างจริง: ติดตามผู้เข้าชมที่ไม่ซ้ำด้วย `HashSet`

อีกตัวอย่างที่ใช้บ่อยมากในระบบจริง: การนับ **unique visitor** จาก log การเข้าชมที่อาจมีคนคนเดียวเข้ามาหลายครั้ง —
งานนี้คือสิ่งที่ `HashSet` ถูกออกแบบมาให้ทำได้ดีที่สุดโดยตรง:

```rust
use std::collections::HashSet;

fn main() {
    let visit_log = vec!["user_042", "user_017", "user_042", "user_099", "user_017", "user_042"];

    let mut unique_visitors: HashSet<&str> = HashSet::new();
    for user_id in &visit_log {
        unique_visitors.insert(*user_id);
    }

    println!("จำนวนการเข้าชมทั้งหมด: {}", visit_log.len());
    println!("จำนวนผู้ใช้ไม่ซ้ำ: {}", unique_visitors.len());

    if unique_visitors.insert("user_042") {
        println!("นี่คือผู้ใช้ใหม่");
    } else {
        println!("user_042 เคยเข้าชมมาแล้ว");
    }
}
```

ผลลัพธ์:

```
จำนวนการเข้าชมทั้งหมด: 6
จำนวนผู้ใช้ไม่ซ้ำ: 3
user_042 เคยเข้าชมมาแล้ว
```

สังเกตการใช้**ค่าที่คืนมาจาก `.insert()`** ในบรรทัดสุดท้าย — เราไม่ได้เรียก `.contains()` ก่อนแล้วค่อย `.insert()`
แยกกันสองบรรทัด (ซึ่งจะ hash ซ้ำสองครั้งแบบเดียวกับปัญหาที่อธิบายไว้ในหัวข้อ 15.5) แต่ใช้ค่า `bool` ที่
`.insert()` คืนกลับมาตรง ๆ: `true` แปลว่า "เพิ่งเพิ่มเข้าไปใหม่ (ไม่เคยมีมาก่อน)" ส่วน `false` แปลว่า "มีอยู่แล้ว
ไม่ได้เพิ่มซ้ำ" — รูปแบบนี้ใช้ hash คีย์แค่ครั้งเดียวเหมือนกับหลักการของ `.entry()` ที่เรียนมาก่อนหน้านี้ เพียงแต่
เป็น API ของ `HashSet` ที่ง่ายกว่าเพราะไม่มีเรื่อง value ต้องจัดการ

รูปแบบเดียวกันนี้ใช้ได้กับปัญหา **tag deduplication** (เก็บ tag ของสินค้าโดยไม่ให้ซ้ำ ถึงแม้ผู้ใช้จะพิมพ์ tag
เดียวกันซ้ำหลายครั้งตอนกรอกฟอร์ม) หรือ **การกันสแปม** (เช็คว่า request ID นี้เคยประมวลผลไปแล้วหรือยัง เพื่อป้องกัน
การประมวลผลซ้ำจาก network retry) — ทุกกรณีมีแกนกลางเดียวกันคือ "ต้องการรู้ว่าเคยเห็นค่านี้มาก่อนหรือยัง โดยไม่
สนใจว่าเห็นกี่ครั้ง"

## กับดักที่พบบ่อย (Common Pitfalls)

### 1. Insert คีย์/ค่าที่เป็น `String` แล้วพยายามใช้ตัวแปรเดิมต่อ (E0382)

```rust
use std::collections::HashMap;

fn main() {
    let mut ages: HashMap<String, u32> = HashMap::new();
    let name = String::from("สมชาย");
    ages.insert(name, 30);
    println!("{name}"); // name ถูก move เข้า map ไปแล้ว!
}
```

```
error[E0382]: borrow of moved value: `name`
 --> src/main.rs:6:15
  |
4 |     let name = String::from("สมชาย");
  |         ---- move occurs because `name` has type `String`, which does not implement the `Copy` trait
5 |     ages.insert(name, 30);
  |                 ---- value moved here
6 |     println!("{name}");
  |                ^^^^ value borrowed here after move
```

**วิธีแก้**: ถ้าต้องใช้ค่าเดิมต่อจริง ๆ ให้ `.clone()` ก่อน insert (`ages.insert(name.clone(), 30)`) ถ้าไม่ได้ใช้
ต่อจริง ๆ (แค่พลาดที่พยายามพิมพ์ค่าออกมาซ้ำ) ก็ตัดบรรทัดที่ใช้ตัวแปรเดิมออกไป หรือดึงค่าคืนจาก map ด้วย `.get()`
แทนการพึ่งพาตัวแปรเดิม

### 2. Index ด้วย `map[&key]` เมื่อคีย์อาจไม่มีอยู่จริง

```rust
use std::collections::HashMap;

fn main() {
    let scores: HashMap<String, i32> = HashMap::new();
    let x = scores["ไม่มีคีย์นี้"]; // panic ทันทีตอนรัน ไม่ compile error
    println!("{x}");
}
```

```
thread 'main' panicked at src/main.rs:5:13:
no entry found for key
note: run with `RUST_BACKTRACE=1` environment variable to display a backtrace
```

**วิธีแก้**: ใช้ `.get(&key)` แล้วจัดการ `Option<&V>` ที่ได้อย่างชัดเจนด้วยเทคนิคจาก Part 11 (`match`, `if let`,
`.unwrap_or()`) เสมอ เว้นแต่คุณมั่นใจ 100% ว่าคีย์นั้นมีอยู่แน่นอน (เช่น เพิ่ง insert เองในบรรทัดก่อนหน้าโดยตรง)

### 3. ใช้ `f64`/`f32` เป็นคีย์ของ `HashMap` หรือ `BTreeMap`

```rust
use std::collections::HashMap;

fn main() {
    let mut m: HashMap<f64, &str> = HashMap::new();
    m.insert(3.14, "pi"); // compile ไม่ผ่าน
}
```

```
error[E0599]: the method `insert` exists for struct `HashMap<f64, &str>`, but its trait bounds were not satisfied
  |
  = note: the following trait bounds were not satisfied:
          `f64: Eq`
          `f64: Hash`
```

**วิธีแก้**: แปลง `f64` เป็น integer ก่อน (เช่น คูณด้วย 100 แล้ว round เป็น `i64` ถ้าต้องการความละเอียด 2
ตำแหน่ง), ใช้ `.to_bits()` แปลงเป็น `u64` แล้วใช้ `u64` เป็นคีย์แทน, หรือใช้ crate อย่าง `ordered-float` ที่มี
wrapper type ซึ่ง implement `Eq`/`Hash`/`Ord` ให้ครบพร้อมกำหนดพฤติกรรม `NaN` ไว้ชัดเจนแล้ว

### 4. สมมติว่า `HashMap` มีลำดับตามที่ insert หรือลำดับตามคีย์

```rust
use std::collections::HashMap;

fn main() {
    let mut m: HashMap<i32, &str> = HashMap::new();
    m.insert(3, "c");
    m.insert(1, "a");
    m.insert(2, "b");

    for (k, v) in &m {
        println!("{k}: {v}"); // ห้ามคาดหวังว่าจะได้ 1, 2, 3 เรียงกัน!
    }
}
```

โค้ดนี้ compile ผ่านและรันได้ไม่มี error แต่**ลำดับที่ได้ไม่แน่นอน** และยิ่งอันตรายกว่านั้นคือมันดูเหมือนทำงานถูก
ต้องตอนทดสอบครั้งแรก (อาจได้ลำดับที่ดูเรียงพอดีโดยบังเอิญ) แล้วพังในโปรดักชันตอนรันครั้งอื่น — บั๊กประเภทนี้
อันตรายเพราะไม่มี error หรือ panic ใด ๆ เตือนเลย มีแต่ผลลัพธ์ที่ "ดูผิดจากที่คาดหวัง" เท่านั้น

**วิธีแก้**: ถ้าต้องการลำดับ ให้ (1) แปลงเป็น `Vec` แล้ว `.sort()` ก่อนแสดงผลหรือประมวลผลต่อ หรือ (2) เปลี่ยนไปใช้
`BTreeMap` ตั้งแต่แรกถ้าต้องการลำดับตามคีย์เสมอทุกครั้งที่ iterate

### 5. ถือ reference จาก `.get()` ค้างไว้พร้อมกับพยายามแก้ไข map (E0502)

```rust
use std::collections::HashMap;

fn main() {
    let mut scores: HashMap<String, i32> = HashMap::new();
    scores.insert(String::from("Alice"), 90);

    let alice_score = scores.get("Alice").unwrap();
    scores.insert(String::from("Bob"), 85); // แก้ไข map ทั้งที่ยังมี reference (alice_score) ค้างอยู่
    println!("{alice_score}");
}
```

```
error[E0502]: cannot borrow `scores` as mutable because it is also borrowed as immutable
 --> src/main.rs:8:5
  |
7 |     let alice_score = scores.get("Alice").unwrap();
  |                       ------ immutable borrow occurs here
8 |     scores.insert(String::from("Bob"), 85);
  |     ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^ mutable borrow occurs here
9 |     println!("{alice_score}");
  |                ----------- immutable borrow later used here
```

เหตุผลเชิงลึก: `.insert()` **อาจทำให้ map ต้อง resize/reallocate memory ใหม่ทั้งหมด** ถ้าจำนวนสมาชิกเกิน capacity
ปัจจุบัน (คล้ายกับที่ `Vec::push()` อาจทำให้ต้อง reallocate ตามที่เรียนใน Part 13) ถ้า reallocation เกิดขึ้นจริง
`&V` ที่ `alice_score` ถืออยู่จะกลายเป็น **dangling reference** ทันที (ชี้ไปที่ memory ที่ถูกปล่อยไปแล้ว) —
borrow checker ป้องกันสถานการณ์นี้อย่างเข้มงวดโดยไม่ยอมให้มี mutable borrow (`.insert()`) เกิดขึ้นพร้อมกับ
immutable borrow (`alice_score`) ที่ยังมีชีวิตอยู่เลย ไม่ว่าการ reallocate จะเกิดขึ้นจริงหรือไม่ในกรณีนั้น ๆ ก็ตาม

**วิธีแก้**: ดึงค่าที่ต้องการออกมาเป็นค่า owned (เช่น `.copied()`/`.cloned()` ถ้า value implement ได้) ก่อนที่จะ
แก้ไข map ต่อ หรือจัดลำดับโค้ดใหม่ให้จบการอ่านค่าทั้งหมดก่อนเริ่มแก้ไข map (แยก scope การอ่านกับการเขียนออกจากกัน
ให้ชัดเจน)

## สรุป

บทนี้ปิดท้าย "collections มินิ-arc" ที่เริ่มจาก `Vec<T>` (Part 13) ผ่าน `String` (Part 14) มาจนถึง key-value
และ set collections ในบทนี้ — เราเริ่มจากปัญหาที่เป็นรูปธรรมที่สุด: การค้นหาด้วยคีย์ใน `Vec<(K, V)>` ต้องไล่เช็ค
ทีละตัวแบบ O(n) แล้วเห็นว่า `HashMap<K, V>` แก้ปัญหานี้ด้วย hash function ที่คำนวณตำแหน่งข้อมูลได้ตรง ๆ ทำให้ได้
ความเร็ว O(1) โดยเฉลี่ย โดยแลกกับการไม่การันตีลำดับการ iterate เลย (ซึ่งเป็นการตัดสินใจเชิง security ด้วยเช่นกัน
ผ่านการสุ่ม seed ของ hash function ใหม่ทุกครั้งที่โปรแกรมเริ่มรัน เพื่อป้องกัน HashDoS)

เราเห็นว่า `Option<T>` จาก Part 11 ไม่ใช่แค่ทฤษฎีลอย ๆ แต่เป็นแกนกลางของ API ทั้งหมดของ `HashMap` — `.get()`,
`.insert()` (ที่คืนค่าเก่า), `.remove()` ทุกตัวคืน `Option<T>` เพื่อบังคับให้จัดการทั้งกรณี "มี" และ "ไม่มี" อย่าง
ชัดเจนเสมอ ไม่มีทางลืมเช็คได้เลยเพราะ compiler บังคับ นอกจากนี้เราเห็น `.entry()` API ที่แก้ปัญหา "เช็คก่อนแล้ว
ค่อยเพิ่ม/อัปเดต" ได้อย่างมีประสิทธิภาพกว่าการเขียน `if/else` เอง ซึ่งเป็นรูปแบบที่ใช้บ่อยที่สุดในโค้ด Rust จริง
สำหรับงานนับจำนวนและสะสมค่า

`HashSet<T>` แสดงให้เห็นว่าเป็น "`HashMap` ที่สนใจแค่คีย์" พร้อม set operation ทางคณิตศาสตร์ที่ใช้แก้ปัญหาจริง
(หา tag ร่วม, หานักเรียนที่ลงทั้งสองวิชา) ได้อย่างสั้นกระชับ ส่วน `BTreeMap`/`BTreeSet` เป็นทางเลือกที่แลกความเร็ว
เล็กน้อย (O(log n) แทน O(1)) เพื่อได้ลำดับตามคีย์ที่การันตีเสมอ พร้อม range query ที่ `HashMap` ทำไม่ได้เลย และ
เราเห็นว่าทั้งสอง trait `Hash`/`Eq` (สำหรับ `HashMap`) และ `Ord` (สำหรับ `BTreeMap`) ต่างพากันปฏิเสธ `f64` เป็นคีย์
ด้วยเหตุผลเดียวกัน: ปัญหาของ `NaN` ที่ละเมิดกฎพื้นฐานของความเท่ากันและการเรียงลำดับ

ด้วยบทนี้ คุณมี "collection พื้นฐานทั้งสี่ชนิด" ครบมือแล้ว (`Vec`, `String`, `HashMap`/`HashSet`,
`BTreeMap`/`BTreeSet`) ซึ่งครอบคลุมงานจัดเก็บและประมวลผลข้อมูลในโปรแกรม Rust ส่วนใหญ่ที่คุณจะเจอในโลกจริง ขั้นต่อ
ไปหลักสูตรจะเปลี่ยนโฟกัสจาก "ชนิดข้อมูลที่ใช้งาน" ไปสู่ "การจัดโครงสร้างและขยายขนาดของโค้ดเอง" — **Part 16** จะ
พาไปรู้จัก **modules** (`mod`, `pub`, `use`, `super`, `crate`) ซึ่งเป็นกลไกที่ทำให้โปรเจกต์ Rust ขนาดใหญ่จัด
ระเบียบโค้ดเป็นหมวดหมู่ที่ชัดเจนได้ ก่อนที่จะต่อไปยัง generics, traits, และ lifetimes ซึ่งเป็นเสาหลักสามเสาสุดท้าย
ที่ทำให้ Rust เป็นภาษาที่ทรงพลังอย่างที่มันเป็น
