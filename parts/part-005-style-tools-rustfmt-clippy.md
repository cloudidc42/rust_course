# Part 5: Comments, rustfmt และ Clippy

> โมดูล: เริ่มต้นใช้งาน Rust (Getting Started) | ระดับ: พื้นฐาน | เวลาโดยประมาณ: 55 นาที

## เป้าหมายของบทเรียน

หลังจากจบบทนี้ คุณจะสามารถ:

- เขียน comment ในโค้ด Rust ได้ถูกต้องครบทุกรูปแบบ (`//`, `/* */`, `///`, `//!`) และรู้ว่าแต่ละแบบใช้ตอนไหน
- เข้าใจปรัชญาเบื้องหลัง `rustfmt` ว่าทำไม community Rust ถึงยอมสละอิสระในการจัดรูปแบบโค้ดส่วนตัว เพื่อผลลัพธ์ที่ดีกว่าในระดับทีม
- ใช้คำสั่ง `cargo fmt` และ `cargo fmt --check` ได้อย่างคล่องแคล่ว พร้อมปรับแต่งพฤติกรรมผ่านไฟล์ `rustfmt.toml`
- เข้าใจว่า `clippy` คืออะไร ต่างจาก warning ปกติของ `rustc` อย่างไร และติดตั้ง/รันมันได้
- อ่านและแก้ไขโค้ดตาม suggestion ของ clippy ได้จริง จากตัวอย่าง lint 4 ตัวที่พบบ่อยที่สุดในโค้ดมือใหม่
- ปิด (silence) lint ที่ไม่ต้องการได้อย่างมีเหตุผล โดยไม่ปิดแบบเหมาเข่ง (blanket allow) ซึ่งเป็นนิสัยที่อันตราย
- เข้าใจแนวคิด "treat warnings as errors" ในสภาพแวดล้อม CI และรู้ข้อควรระวังของมันในการพัฒนาโค้ดประจำวัน

## เนื้อหา

### 5.1 ทำไม "สไตล์การเขียนโค้ด" ถึงสำคัญพอที่จะมีบทเรียนเฉพาะ

ก่อนจะลงลึกเรื่อง syntax และเครื่องมือ เรามาทำความเข้าใจ "ทำไม" กันก่อน เพราะมือใหม่จำนวนมากมองว่าการจัดรูปแบบโค้ด
(formatting) และ linter เป็นเรื่องเสริม ไม่สำคัญเท่า logic ของโปรแกรม แต่ในความเป็นจริง ทีมพัฒนาซอฟต์แวร์ระดับโลก
ใช้เวลาไม่น้อยไปกับ "code review ที่เถียงกันเรื่องสไตล์" — ควรใส่ brace ขึ้นบรรทัดใหม่หรือไม่ ควร indent 2 หรือ 4
space ควรเรียง `use` แบบไหน ฯลฯ ประเด็นเหล่านี้เรียกรวม ๆ ว่า **"bikeshedding"** (มาจากอุปมาว่าคนมักเถียงเรื่องเล็ก ๆ
อย่างสีของโรงเก็บจักรยานได้นานกว่าเรื่องใหญ่ ๆ อย่างงบประมาณโรงไฟฟ้า เพราะทุกคนมีความเห็นเรื่องสีได้ แต่ไม่ใช่ทุกคน
เข้าใจเรื่องวิศวกรรมไฟฟ้า)

Rust แก้ปัญหานี้ตั้งแต่ระดับ ecosystem ด้วยการมีเครื่องมือ **ทางการ (official)** สองตัวที่ทุกโปรเจกต์ Rust ในโลก
มักใช้ร่วมกัน:

1. **`rustfmt`** — จัดรูปแบบโค้ดให้เป็นมาตรฐานเดียวกันโดยอัตโนมัติ (ไม่ต้องเถียงเรื่อง style อีกต่อไป)
2. **`clippy`** — ตรวจจับโค้ดที่ compile ผ่านแต่ไม่ใช่วิธีเขียนที่ดีที่สุด (idiomatic) หรือมีความเสี่ยงเชิง logic

ทั้งสองตัวนี้ไม่ใช่แค่ "ของเสริม" แต่เป็นส่วนหนึ่งของ workflow มาตรฐานที่เราแนะนำไว้ตั้งแต่ Part 1 (หัวข้อ 1.9)
ตอนนี้ถึงเวลาที่เราจะเจาะลึกทั้งสองตัวอย่างจริงจัง พร้อมกับเรื่อง comment ที่เป็นส่วนหนึ่งของการเขียนโค้ดให้อ่านง่าย
เช่นกัน

### 5.2 Comment แบบ Line Comment (`//`)

Comment แบบพื้นฐานที่สุดใน Rust คือ `//` ซึ่งทำให้ทุกอย่างตั้งแต่ `//` ไปจนถึงท้ายบรรทัดนั้นถูกมองข้ามโดย compiler
โดยสิ้นเชิง — เหมือนกับ `//` ใน C++/Java/JavaScript หรือ `#` ใน Python

```rust
fn main() {
    // นี่คือ comment บรรทัดเดียว compiler จะไม่สนใจข้อความนี้เลย
    let price: f64 = 199.0; // สามารถเขียน comment ต่อท้ายโค้ดในบรรทัดเดียวกันได้เช่นกัน

    // สามารถเขียน comment หลายบรรทัดต่อกันได้
    // โดยขึ้นบรรทัดใหม่แล้วเริ่ม // ใหม่ทุกครั้ง
    // (Rust ไม่มี syntax พิเศษสำหรับ "comment block แบบ //" เหมือนบางภาษา)
    let quantity: u32 = 3;

    println!("ราคารวม: {}", price * quantity as f64);
}
```

**ข้อสังเกตสำคัญ:** Rust **ไม่มี** concept ของ comment แบบ "docstring" ที่อยู่ในรูปแบบ string literal เหมือน Python
(`"""..."""`) การ comment ทุกแบบใน Rust ใช้เครื่องหมาย `/` เสมอ ไม่ใช้ string literal

comment แบบ `//` ควรใช้อธิบาย **"ทำไม"** มากกว่า **"ทำอะไร"** เพราะโค้ดที่เขียนดีอยู่แล้วจะบอก "ทำอะไร" ได้ในตัวเอง
ตัวอย่างที่ไม่ค่อยมีประโยชน์:

```rust
let total = price * quantity as f64; // คูณราคาด้วยจำนวน
```

comment นี้ไม่มีประโยชน์ เพราะโค้ดเองก็บอกอยู่แล้วว่ากำลังคูณอะไร ตัวอย่างที่มีประโยชน์กว่า:

```rust
// ใช้ f64 แทน integer เพราะราคาสินค้ามีทศนิยม (สตางค์) และป้องกัน
// การ overflow เมื่อคูณกับจำนวนสินค้าจำนวนมากในระบบคลังสินค้าขนาดใหญ่
let total = price * quantity as f64;
```

comment แบบหลังอธิบาย "การตัดสินใจเชิง design" (ทำไมเลือก `f64`) ซึ่งเป็นข้อมูลที่โค้ดเพียงอย่างเดียวบอกไม่ได้

### 5.3 Comment แบบ Block Comment (`/* */`) และการซ้อนกันได้ (Nesting)

Rust รองรับ block comment แบบ `/* ... */` เช่นเดียวกับ C/C++/Java แต่มีจุดที่ **แตกต่างและสำคัญมาก**: **block comment
ของ Rust สามารถซ้อนกันได้ (nested)** ซึ่งภาษาอย่าง C และ C++ ทำไม่ได้

```rust
fn main() {
    /* นี่คือ block comment
       สามารถเขียนได้หลายบรรทัด
       โดยไม่ต้องใส่ // ซ้ำทุกบรรทัด */
    let stock_count = 42;

    /* Block comment ของ Rust ซ้อนกันได้ (nested comments) ต่างจาก C/C++
       /* comment ชั้นในนี้ยังอยู่ภายใน comment ชั้นนอกได้อย่างถูกต้อง */
       ข้อความนี้ก็ยังถือว่าอยู่ใน comment ชั้นนอกอยู่ */
    println!("จำนวนสินค้าในคลัง: {stock_count}");
}
```

ทำไมเรื่องนี้ถึงสำคัญ? ลองดูปัญหาที่เกิดขึ้นใน C/C++ ถ้าคุณลองคอมเมนต์โค้ดทั้งบล็อกที่**มี** block comment อยู่ข้างใน
อยู่แล้ว (เป็นเทคนิคที่โปรแกรมเมอร์มักใช้ตอน debug — comment ทิ้งทั้งฟังก์ชันชั่วคราว):

```c
/* เริ่ม comment ทั้งฟังก์ชันเพื่อ debug
int calculate() {
    /* คำนวณราคาพิเศษ */   // <-- ก้อนนี้จะปิด comment ทันที! ทำให้โค้ดที่เหลือ "หลุด" ออกมา
    return price * 2;
}
*/  // <-- เครื่องหมายนี้กลายเป็น syntax error เพราะ comment ถูกปิดไปแล้วตั้งแต่บรรทัดก่อน
```

ใน C/C++ โค้ดด้านบนจะ **compile error** หรือแย่กว่านั้นคือ compile ผ่านแบบผิดเจตนา เพราะ comment ตัวแรกที่เจอ `*/`
จะปิด comment ทันที ไม่สนใจว่ามี `/*` ซ้อนอยู่ก่อนหน้าหรือไม่ ทำให้โค้ดที่ตั้งใจจะ comment ทิ้งกลับ "โผล่" ออกมาเป็น
โค้ดจริงโดยไม่ตั้งใจ — เป็นบั๊กที่หาสาเหตุยากมากเพราะดูด้วยตาจะคิดว่าทุกอย่างถูก comment อยู่แล้ว

ใน Rust โค้ดแบบเดียวกันนี้ **ทำงานถูกต้องตามที่ตั้งใจ** เพราะ compiler จะนับจำนวน `/*` ที่เปิดไว้ และต้องมี `*/`
ปิดให้ครบเท่ากันจึงจะถือว่า comment สิ้นสุด:

```rust
/* เริ่ม comment ทั้งฟังก์ชันเพื่อ debug
fn calculate() -> f64 {
    /* คำนวณราคาพิเศษ */   // อยู่ใน comment ชั้นนอก ไม่ทำให้ comment ปิดก่อนเวลา
    200.0 * 2.0
}
*/  // ปิด comment ชั้นนอกที่ถูกต้อง ไม่มี error
```

ในทางปฏิบัติ นักพัฒนา Rust ส่วนใหญ่ใช้ `//` มากกว่า `/* */` เกือบตลอดเวลา เพราะเมื่อใช้ `//` ทุกบรรทัด การ comment
ทิ้งชั่วคราวหรือ uncomment กลับก็ทำได้ง่ายด้วยการเลือกหลายบรรทัดใน editor แล้วกด toggle comment (`Ctrl+/` ใน VS Code)
`/* */` มักถูกสงวนไว้สำหรับ comment สั้น ๆ กลางบรรทัด หรือกรณีพิเศษที่ต้อง comment เนื้อโค้ดขนาดใหญ่แบบรวดเร็ว

### 5.4 Doc Comments: `///` และ `//!` (แนะนำเบื้องต้น)

นอกจาก comment ปกติสองแบบข้างต้น Rust ยังมี comment พิเศษอีกสองแบบที่ **compiler และเครื่องมือ `rustdoc` มองเห็น
และนำไปประมวลผลจริง** ไม่ใช่แค่ข้อความที่ถูกข้ามเฉย ๆ เราจะเรียนเรื่องนี้แบบละเอียดมากใน **Part 34 (Documentation:
rustdoc, doc tests, docs.rs)** แต่ในบทนี้ขอแนะนำภาพรวมไว้ก่อน เพราะเป็นส่วนหนึ่งของ "การเขียน comment ที่ดี"

**`///` (triple-slash) — Outer doc comment**

ใช้เขียน**เหนือ**รายการ (item) ที่ต้องการอธิบาย เช่น เหนือฟังก์ชัน, struct, enum โดย doc comment นี้จะอธิบาย
"รายการที่อยู่ถัดจากมัน" (ข้างล่าง):

```rust
/// คำนวณราคาสุทธิหลังหักส่วนลด
///
/// # Arguments
/// * `price` - ราคาสินค้าตั้งต้น (ก่อนหักส่วนลด)
/// * `discount_percent` - เปอร์เซ็นต์ส่วนลด (0.0 ถึง 100.0)
///
/// # Examples
/// ```
/// let net = calculate_discounted_price(100.0, 10.0);
/// assert_eq!(net, 90.0);
/// ```
fn calculate_discounted_price(price: f64, discount_percent: f64) -> f64 {
    price * (1.0 - discount_percent / 100.0)
}
```

**`//!` (slash-bang) — Inner doc comment**

ใช้เขียน**ภายใน**module หรือ crate เพื่ออธิบาย "สิ่งที่ล้อมรอบมัน" (enclosing item) มักเขียนไว้บนสุดของไฟล์ `lib.rs`
หรือ `main.rs` เพื่ออธิบายภาพรวมของทั้ง crate/module:

```rust
//! ระบบจัดการสินค้าคงคลัง (Inventory Management System)
//!
//! Module นี้รวมฟังก์ชันสำหรับคำนวณราคา ส่วนลด และการติดตามจำนวนสินค้าในคลัง
//! ใช้เป็นตัวอย่างประกอบการสอนในหลักสูตร Rust ภาษาไทย

fn main() {
    println!("Inventory system starting...");
}
```

ความแตกต่างสำคัญระหว่าง `///` กับ `//!` คือ **ตำแหน่งที่มันอธิบาย**: `///` มองไป**ข้างหน้า** (อธิบายสิ่งที่ตามมา)
ส่วน `//!` มองไป**รอบตัว/ข้างบน** (อธิบายสิ่งที่ห่อหุ้มมันอยู่ เช่นตัวไฟล์หรือ module ทั้งก้อน) เมื่อคุณรัน
`cargo doc --open` (จะเรียนละเอียดใน Part 34) เนื้อหาในคอมเมนต์เหล่านี้จะถูกแปลงเป็นหน้าเว็บ HTML สวยงามโดยอัตโนมัติ
คล้ายกับ Javadoc ใน Java หรือ docstring ที่ผ่านการ generate ด้วย Sphinx ใน Python — นี่คือเหตุผลที่โปรเจกต์ Rust
คุณภาพสูงบน crates.io มักมีเอกสารประกอบสวยงามที่ docs.rs โดยที่ผู้เขียน crate แทบไม่ต้องเขียนเว็บเอกสารแยกเลย

สรุปสั้น ๆ สำหรับตอนนี้ (รายละเอียดเต็มรออยู่ที่ Part 34):

| รูปแบบ | ตำแหน่งที่เขียน | อธิบายอะไร | เครื่องมือที่อ่าน |
|---|---|---|---|
| `//` | ที่ไหนก็ได้ | ทุกอย่าง (ไม่ตรวจสอบ syntax) | ไม่มี (compiler ข้ามทิ้ง) |
| `/* */` | ที่ไหนก็ได้ (ซ้อนได้) | ทุกอย่าง | ไม่มี (compiler ข้ามทิ้ง) |
| `///` | เหนือ item | item ที่อยู่ถัดไป | `rustdoc`, `cargo doc` |
| `//!` | บนสุดของไฟล์/module | module/crate ที่ล้อมรอบ | `rustdoc`, `cargo doc` |

### 5.5 `rustfmt` คืออะไร และปรัชญาเบื้องหลังมัน

`rustfmt` คือเครื่องมือ **จัดรูปแบบโค้ดอัตโนมัติ (automatic code formatter)** สำหรับ Rust มันไม่เปลี่ยนความหมาย
(semantics) ของโค้ดแม้แต่นิดเดียว — มันแค่เปลี่ยน "หน้าตา" ของโค้ด: จำนวน space ในการ indent, ตำแหน่งขึ้นบรรทัดใหม่,
การจัดเรียง argument ที่ยาวเกินไปให้ wrap, การเว้นวรรครอบ operator ฯลฯ

ปรัชญาสำคัญที่สุดของ `rustfmt` คือ **"One True Style"** — มีวิธีจัดรูปแบบที่ "ถูก" อยู่เพียงหนึ่งเดียว (ตาม default
config) ซึ่งแตกต่างจากภาษาอื่นบางภาษาที่มี formatter หลายตัวแข่งกัน (เช่น JavaScript มีทั้ง Prettier, ESLint --fix,
StandardJS ที่มีกฎต่างกัน) การที่ Rust มี formatter ทางการเพียงตัวเดียวที่ทุกโปรเจกต์ยึดถือ ทำให้เกิดผลดีที่จับต้องได้
จริงหลายอย่าง:

1. **ไม่มีการเถียงเรื่อง style ใน code review อีกต่อไป** — เพราะไม่มีใครสามารถ "เลือก" style ที่ต่างจาก `rustfmt`
   ได้ ทุกคนแค่รัน `cargo fmt` แล้วจบ ประหยัดเวลาการ review ไปได้มาก โดยเฉพาะในทีมขนาดใหญ่ที่มีคนเขียนโค้ดหลายสิบคน
2. **Diff ใน git สะอาดขึ้น** — เมื่อทุกคนใช้ formatter เดียวกัน การเปลี่ยนแปลงโค้ดใน pull request จะแสดงเฉพาะการ
   เปลี่ยนแปลง logic จริง ๆ ไม่มี "noise" จากการจัดรูปแบบที่ต่างกันระหว่างคนเขียนโค้ดคนละคน
3. **โค้ดจากคนละที่อ่านง่ายขึ้นทันที** — เมื่อคุณเปิดโปรเจกต์ Rust โปรเจกต์ใหม่บน GitHub ที่คุณไม่เคยเห็นมาก่อน
   หน้าตาโค้ดจะคุ้นเคยทันที เพราะ 99% ของโปรเจกต์ Rust ใช้ `rustfmt` แบบ default settings
4. **มือใหม่ไม่ต้องเสียเวลาคิดเรื่อง style เลย** — สามารถโฟกัสกับการเขียน logic ให้ถูกต้องได้อย่างเดียว แล้วให้
   เครื่องจัดรูปแบบให้ทีหลัง

เปรียบเทียบกับภาษาอื่น: Python มี PEP 8 เป็น "แนวทาง" (guideline) แต่ไม่มีการบังคับ ทำให้ต้องพึ่ง third-party tool
อย่าง `black` หรือ `autopep8` ซึ่งชุมชนก็ยังแบ่งเป็นหลายฝ่าย ส่วน Go แก้ปัญหานี้แบบเดียวกับ Rust ด้วย `gofmt` ที่มาพร้อม
ตัวภาษาตั้งแต่ต้น (จริง ๆ แล้ว `rustfmt` ได้รับแรงบันดาลใจส่วนหนึ่งมาจากความสำเร็จของ `gofmt`)

### 5.6 การใช้งาน `cargo fmt`

`rustfmt` ถูกติดตั้งมาพร้อมกับ `rustup` โดย default อยู่แล้ว (เป็น component มาตรฐาน) ตรวจสอบได้ด้วย:

```bash
rustfmt --version
```

ผลลัพธ์ตัวอย่าง:

```
rustfmt 1.7.0-stable (90b35a6 2024-11-26)
```

ถ้าไม่มี ให้เพิ่ม component ด้วยคำสั่ง:

```bash
rustup component add rustfmt
```

**วิธีใช้งานหลัก:** ให้เข้าไปที่ root ของโปรเจกต์ cargo (ที่มีไฟล์ `Cargo.toml`) แล้วรัน:

```bash
cargo fmt
```

คำสั่งนี้จะจัดรูปแบบไฟล์ `.rs` **ทุกไฟล์**ในโปรเจกต์ (ทั้ง `src/main.rs`, ไฟล์ใน `src/` ที่แยก module ออกไป
รวมถึงไฟล์ test) **โดยเขียนทับไฟล์เดิมทันที** (in-place) มาดูตัวอย่างก่อน/หลังกัน สมมติเรามีไฟล์ที่จัดรูปแบบไม่เรียบร้อย:

**ก่อนรัน `cargo fmt`:**

```rust
struct Product{name:String,price:f64,quantity:u32}

fn calculate_total(products:&Vec<Product>)->f64{
let mut total=0.0;
    for p in products {
            total+=p.price*p.quantity as f64;
    }
total
}

fn main(){
    let products=vec![
        Product{name:"เมาส์".to_string(),price:299.0,quantity:2},
        Product{name:"คีย์บอร์ด".to_string(),price:890.0,quantity:1},
    ];
    println!("ยอดรวม: {}",calculate_total(&products));
}
```

โค้ดนี้ **compile ผ่านได้** (indent และ spacing ไม่มีผลต่อความหมายใน Rust) แต่อ่านยากมาก หลังรัน `cargo fmt`:

**หลังรัน `cargo fmt`:**

```rust
struct Product {
    name: String,
    price: f64,
    quantity: u32,
}

fn calculate_total(products: &Vec<Product>) -> f64 {
    let mut total = 0.0;
    for p in products {
        total += p.price * p.quantity as f64;
    }
    total
}

fn main() {
    let products = vec![
        Product {
            name: "เมาส์".to_string(),
            price: 299.0,
            quantity: 2,
        },
        Product {
            name: "คีย์บอร์ด".to_string(),
            price: 890.0,
            quantity: 1,
        },
    ];
    println!("ยอดรวม: {}", calculate_total(&products));
}
```

สังเกตว่า `rustfmt` จัดการทุกอย่างให้: เว้นวรรครอบ `:` และ `->`, จัด indent เป็น 4 space ตามมาตรฐาน, จัดฟิลด์ของ
`struct literal` ที่ยาวเกินความกว้างบรรทัด (default 100 ตัวอักษร) ให้ขึ้นบรรทัดใหม่โดยอัตโนมัติแบบสวยงาม — คุณไม่ต้อง
มานั่งกดตัดบรรทัดเองเลย

**`cargo fmt --check` — ตรวจสอบโดยไม่แก้ไขไฟล์**

ในสถานการณ์ที่คุณ**ไม่ต้องการให้แก้ไฟล์จริง** แต่ต้องการรู้แค่ว่า "โค้ดนี้ผ่านมาตรฐาน format หรือไม่" (ใช้บ่อยที่สุด
ใน CI pipeline) ให้เพิ่ม flag `--check`:

```bash
cargo fmt --check
```

ถ้าโค้ดทุกไฟล์จัดรูปแบบถูกต้องอยู่แล้ว คำสั่งนี้จะจบแบบเงียบ ๆ (exit code 0) แต่ถ้ามีไฟล์ที่ยังไม่ได้จัดรูปแบบ
มันจะแสดง diff ของสิ่งที่ **ควรจะเป็น** ออกมาทาง terminal และคืน **exit code ที่ไม่ใช่ 0** (fail) ซึ่งเป็นกลไกสำคัญ
ที่ทำให้ CI pipeline (จะเรียนเต็ม ๆ ใน Part 97) สามารถ "บล็อก" ไม่ให้ pull request ที่โค้ดไม่ได้ format ผ่านการ merge
ได้ ตัวอย่าง output เมื่อพบปัญหา:

```
Diff in /home/user/project/src/main.rs:1:
-struct Product{name:String,price:f64,quantity:u32}
+struct Product {
+    name: String,
+    price: f64,
+    quantity: u32,
+}
```

**ทำไม CI ควรใช้ `--check` ไม่ใช่รัน `cargo fmt` ตรง ๆ?** เพราะใน pipeline อัตโนมัติ เราไม่อยากให้ CI "แก้ไขโค้ดแทน
เรา" อย่างเงียบ ๆ (มันจะแก้ในเครื่อง CI ที่ไม่มีใครเห็น แล้วก็ทิ้งการเปลี่ยนแปลงไปเมื่อ job จบ ไม่ช่วยอะไรเลย)
เราต้องการให้ CI **แจ้งเตือน** ว่า "โค้ดนี้ยังไม่ได้ format" แล้วให้ผู้เขียนโค้ดรัน `cargo fmt` เองในเครื่องตัวเองแล้ว
commit กลับมาใหม่

### 5.7 ปรับแต่งพฤติกรรมด้วย `rustfmt.toml`

แม้ปรัชญาของ `rustfmt` คือ "ลด choice" แต่ก็ยังมี config บางอย่างที่ปรับแต่งได้ตามความเหมาะสมของแต่ละทีม/โปรเจกต์
โดยสร้างไฟล์ชื่อ `rustfmt.toml` (หรือ `.rustfmt.toml`) ไว้ที่ **root เดียวกับ `Cargo.toml`**

ตัวอย่าง `rustfmt.toml` ที่ใช้จริงในโปรเจกต์ทั่วไป:

```toml
# rustfmt.toml — วางไว้ที่ root ของโปรเจกต์ ระดับเดียวกับ Cargo.toml

# ความกว้างสูงสุดของแต่ละบรรทัด (ตัวอักษร) ก่อนที่ rustfmt จะพยายาม wrap ขึ้นบรรทัดใหม่
# ค่า default คือ 100 — บางทีมเลือกใช้ 80 ตามธรรมเนียมเก่าจากภาษาอื่น
max_width = 100

# ระบุ edition ของ Rust ที่ใช้ ต้องตรงกับ edition ใน Cargo.toml เพื่อให้ rustfmt เข้าใจ
# syntax ที่ถูกต้องของ edition นั้น (เช่น edition 2021 มีกฎเรื่อง closure capture ที่ต่างจาก 2018)
edition = "2021"

# ควบคุมว่า rustfmt จะจัดฟังก์ชัน/struct แบบ "กระชับในบรรทัดเดียว" เมื่อไหร่
# ค่าที่เป็นไปได้: "Default", "Off", "Max"
# "Max" = พยายามยัดทุกอย่างในบรรทัดเดียวให้มากที่สุดถ้าความกว้างพอ
use_small_heuristics = "Default"

# จำนวน space ต่อระดับ indent (ค่า default คือ 4 ซึ่งเป็นมาตรฐานของ Rust ทั้ง ecosystem)
tab_spaces = 4

# ใช้ tab character จริงแทน space หรือไม่ (แทบไม่มีใครเปิดตัวนี้ใน Rust — เป็นค่า default false)
hard_tabs = false

# จัดกลุ่มการเรียง use statement ให้อยู่ในลำดับ std -> external crate -> โมดูลภายในโปรเจกต์
group_imports = "StdExternalCrate"
```

**คำอธิบายเจาะจงแต่ละ key ที่ใช้บ่อยที่สุด:**

- **`max_width`** — ค่านี้เป็นตัวกำหนดว่าเมื่อบรรทัดยาวเกินเท่านี้ (นับตัวอักษร) `rustfmt` จะพยายามตัดขึ้นบรรทัดใหม่
  แบบสวยงามให้ (เช่น ตัด argument ของฟังก์ชันที่มีหลายตัวให้ลงบรรทัดละตัว) ค่า 100 เป็นค่ามาตรฐานที่ community ส่วนใหญ่
  เลือกใช้ เพราะจอภาพปัจจุบันกว้างพอที่จะแสดง 2 ไฟล์เคียงข้างกันได้สบาย ๆ ที่ความกว้างนี้
- **`edition`** — สำคัญมาก ต้องตรงกับ `edition` ที่ระบุใน `Cargo.toml` ของโปรเจกต์เสมอ ถ้าไม่ตรงกัน `rustfmt` อาจจัด
  รูปแบบโค้ดผิดเพี้ยนไปตามกฎของ edition ที่ไม่ตรงกับที่ compiler ใช้จริง (เราจะพูดถึง edition แบบละเอียดใน Part 17)
- **`use_small_heuristics`** — ควบคุม "ความยอมรับได้" ของการยัดโค้ดสั้น ๆ ให้อยู่บรรทัดเดียว เช่น struct ที่มีแค่
  2 field อาจจะยัดในบรรทัดเดียวได้ถ้าตั้งเป็น `"Max"` แต่ถ้าตั้งเป็น `"Off"` มันจะขึ้นบรรทัดใหม่ให้ทุก field เสมอ
  ไม่ว่าจะสั้นแค่ไหน ค่า default `"Default"` เป็นค่าที่สมดุลที่สุดสำหรับการอ่านง่าย
- **`group_imports`** — จัดกลุ่ม `use` statement ให้เป็นระเบียบ เช่นค่า `"StdExternalCrate"` จะเรียง `use std::...`
  ไว้กลุ่มบนสุด ตามด้วย external crate (เช่น `use serde::...`) แล้วค่อยเป็น `use crate::...`/`use super::...`
  ของโปรเจกต์เราเองไว้กลุ่มล่างสุด ทำให้เห็นภาพรวมของ dependency ได้ง่ายตั้งแต่มองบรรทัดแรก

**ข้อควรระวัง:** rustfmt มี option บางตัว (เช่น `format_strings`, `wrap_comments`) ที่ทำงานได้เฉพาะบน **nightly
toolchain** เท่านั้น (ต้องรันด้วย `cargo +nightly fmt`) หากใส่ key เหล่านี้ในไฟล์ config แล้วรันด้วย stable toolchain
`rustfmt` จะแค่แสดง warning เตือนแล้วข้าม key นั้นไปเฉย ๆ ไม่ error แต่ก็ไม่มีผลใด ๆ เช่นกัน ดังนั้นสำหรับหลักสูตรนี้
ที่ใช้ stable ตลอด ให้เลือกใช้เฉพาะ key ที่ทำงานได้บน stable (อย่างที่แสดงในตัวอย่างข้างต้นทั้งหมด)

หากไม่มีไฟล์ `rustfmt.toml` เลย `rustfmt` จะใช้ค่า default ทั้งหมด ซึ่งในทางปฏิบัติ **โปรเจกต์ Rust ส่วนใหญ่ในโลก
ไม่มีไฟล์ config นี้เลย** เพราะค่า default ถูกออกแบบมาให้ดีอยู่แล้ว — นี่คือจุดที่ตอกย้ำปรัชญา "One True Style" อีกครั้ง
ทีมส่วนใหญ่ปรับแต่งเพียง `max_width` หรือ `edition` เท่าที่จำเป็นจริง ๆ เท่านั้น

### 5.8 เชื่อมต่อ `rustfmt` กับ Editor (Format on Save)

จาก Part 1 หัวข้อ 1.6 เราได้แนะนำให้เปิด setting นี้ใน VS Code ไว้แล้ว:

```json
{
  "editor.formatOnSave": true
}
```

ตอนนี้เราเข้าใจแล้วว่ามันทำอะไร: ทุกครั้งที่กด `Ctrl+S` / `Cmd+S` เพื่อบันทึกไฟล์ `.rs` VS Code จะเรียก `rustfmt`
(ผ่าน rust-analyzer) มาจัดรูปแบบไฟล์ให้อัตโนมัติก่อนเขียนลงดิสก์ ทำให้คุณ**ไม่ต้องจำที่จะรัน `cargo fmt` เอง** และ
ไม่มีทางที่โค้ดจะ "หลุด" ออกไปแบบไม่ได้จัดรูปแบบ (ยกเว้นตั้งใจปิด feature นี้)

ข้อดีของ format-on-save เทียบกับการรัน `cargo fmt` แบบ manual เป็นระยะ ๆ:

1. **ไม่มีโอกาสลืม** — เพราะมันเกิดขึ้นทุกครั้งที่ save ไม่ต้องจำเป็น step แยก
2. **เห็นผลลัพธ์ทันที** — คุณจะเห็นว่าโค้ดที่พิมพ์ไปถูกจัดรูปแบบใหม่แบบ real-time ช่วยให้เรียนรู้ "หน้าตาโค้ด Rust
   ที่ถูกต้อง" ได้เร็วขึ้นโดยไม่รู้ตัว (โดยเฉพาะมือใหม่ที่ยังไม่คุ้นกับ convention การเว้นวรรค)
3. **Diff ใน git สะอาดจากจุดเริ่มต้น** — commit แรกที่คุณสร้างจะ format ถูกต้องอยู่แล้ว ไม่ต้องมี commit แยกที่มีแต่
   "run cargo fmt" ปนอยู่ในประวัติ (แม้ commit แบบนั้นก็ไม่ใช่เรื่องแปลกในโปรเจกต์จริงเช่นกัน)

editor อื่น ๆ ก็รองรับ format-on-save เช่นกัน (เช่น IntelliJ RustRover มี setting "Reformat code on save" ในลักษณะ
เดียวกัน) หลักการเหมือนกันหมดคือ: ให้เครื่องมือทำงานที่ซ้ำซากแทนคุณ เพื่อให้สมองมนุษย์โฟกัสกับ logic ที่สำคัญกว่า

### 5.9 `cargo clippy` คืออะไร

ถ้า `rustfmt` คือเครื่องมือที่ดูแล **"หน้าตา"** ของโค้ด `clippy` คือเครื่องมือที่ดูแล **"คุณภาพและความถูกต้องเชิง
logic"** ของโค้ด มันคือ **linter** — โปรแกรมที่วิเคราะห์โค้ดของคุณและแจ้งเตือนรูปแบบการเขียนที่มีปัญหา แม้โค้ดนั้นจะ
compile ผ่านได้อย่างสมบูรณ์แบบก็ตาม

จุดสำคัญที่ต้องเข้าใจคือ `clippy` **ไม่ใช่สิ่งเดียวกับ warning ของ `rustc`** แม้ทั้งสองจะแสดงผลในลักษณะคล้ายกัน:

- **`rustc` warning** — compiler ตัวจริงตรวจแค่สิ่งที่เกี่ยวกับความถูกต้องของภาษาโดยตรง เช่น ตัวแปรที่ประกาศแต่ไม่ได้
  ใช้ (`unused_variables`), ฟังก์ชันที่ไม่ถูกเรียกใช้ที่ไหนเลย (`dead_code`) เหล่านี้เป็น warning ระดับพื้นฐานที่มา
  พร้อม compiler เอง ไม่ต้องติดตั้งอะไรเพิ่ม
- **`clippy` lint** — เป็น**ชุดกฎเพิ่มเติมกว่า 750 กฎ** (และเพิ่มขึ้นเรื่อย ๆ ทุก release) ที่ตรวจลึกกว่ามาก เช่น
  การเขียนโค้ดที่ทำงานถูกต้องแต่ "ไม่ idiomatic" (ไม่ตรงตามธรรมเนียมที่ชุมชน Rust ยอมรับว่าดีที่สุด), โค้ดที่มี
  ความเสี่ยงด้าน performance โดยไม่จำเป็น, หรือแม้แต่ pattern ที่ "compile ผ่านแต่พฤติกรรมอาจไม่ตรงกับที่ผู้เขียน
  ตั้งใจ" ซึ่งเป็นสัญญาณของบั๊กที่ซ่อนอยู่

พูดง่าย ๆ คือ: `rustc` ตอบคำถามว่า **"โค้ดนี้ถูกต้องตามกฎภาษาไหม (compile ได้ไหม)"** ส่วน `clippy` ตอบคำถามที่ลึกกว่า
คือ **"โค้ดนี้ถูกต้องแล้ว แต่เป็นวิธีที่ดีที่สุดหรือยัง"**

ชื่อ "Clippy" มาจากมาสคอตรูปคลิปหนีบกระดาษของ Microsoft Office ในยุค 90s-2000s ที่ชอบเด้งขึ้นมาแนะนำ (บางครั้งก็
น่ารำคาญ) — ทีม Rust เลือกชื่อนี้อย่างขบขัน เพื่อสื่อว่าเครื่องมือนี้จะ "เด้งขึ้นมาแนะนำ" คุณบ่อย ๆ เช่นกัน แต่ต่างจาก
Clippy ตัวเดิมคือคำแนะนำของมันมีประโยชน์จริงและแม่นยำมาก

### 5.10 ติดตั้งและรัน `cargo clippy`

`clippy` เป็น **component เสริม** ของ `rustup` ไม่ได้ติดตั้งมาโดย default เหมือน `rustfmt` เสมอไป (ขึ้นกับว่าติดตั้ง
Rust ผ่านช่องทางไหน) ให้ตรวจสอบก่อนด้วย:

```bash
cargo clippy --version
```

ถ้าเจอ error แบบนี้:

```
error: no such command: `clippy`
```

ให้ติดตั้งด้วยคำสั่ง:

```bash
rustup component add clippy
```

จากนั้นตรวจสอบอีกครั้ง ควรได้ผลลัพธ์แบบนี้:

```
clippy 0.1.83 (90b35a6 2024-11-26)
```

**การรันพื้นฐาน:** เข้าไปที่ root ของโปรเจกต์ cargo แล้วรัน:

```bash
cargo clippy
```

`clippy` จะ compile โปรเจกต์ของคุณ (เหมือน `cargo check`) แต่ในระหว่างนั้นจะรันชุด lint เพิ่มเติมทั้งหมดไปด้วย
แล้วแสดงผลลัพธ์เป็น warning ทาง terminal พร้อมคำอธิบายว่า **"ควรแก้อย่างไร"** อย่างชัดเจน (ซึ่งเป็นจุดเด่นมากของ
clippy เทียบกับ linter ในหลายภาษา — มันไม่ได้บอกแค่ "ผิด" แต่บอก "แก้แบบนี้สิ" พร้อมโค้ดตัวอย่างเสร็จสรรพ)

### 5.11 หมวดหมู่ของ Lint ใน Clippy (Lint Categories)

Clippy จัดกลุ่ม lint กว่า 750 ตัวออกเป็นหลายหมวดหมู่ (category) ตามความเสี่ยงและความแน่ใจของกฎนั้น ๆ การเข้าใจ
หมวดหมู่เหล่านี้ช่วยให้คุณตัดสินใจได้ว่าจะเปิด/ปิด lint กลุ่มไหนในโปรเจกต์ของคุณ

| หมวดหมู่ | ความหมาย | เปิดโดย default? |
|---|---|---|
| `clippy::correctness` | โค้ดที่**ทำงานผิดพลาดแน่นอน** หรือมี undefined behavior — แทบไม่มี false positive เลย | ✅ เปิด (เป็น error โดย default) |
| `clippy::style` | โค้ดที่ทำงานถูกต้อง แต่ไม่ตรงตามธรรมเนียมการเขียนที่ชุมชนยอมรับ (idiomatic style) | ✅ เปิด |
| `clippy::complexity` | โค้ดที่เขียนซับซ้อนเกินความจำเป็น สามารถลดความซับซ้อนได้โดยพฤติกรรมไม่เปลี่ยน | ✅ เปิด |
| `clippy::perf` | โค้ดที่ทำงานถูกต้อง แต่มีวิธีที่เร็วกว่า/ใช้ทรัพยากรน้อยกว่าโดยไม่เสียอะไร | ✅ เปิด |
| `clippy::pedantic` | กฎที่ "เข้มงวดจัด" อาจมี false positive บ้าง เหมาะกับทีมที่ต้องการมาตรฐานสูงสุด | ❌ ปิด (ต้องเปิดเอง) |
| `clippy::nursery` | lint ใหม่ที่ยังอยู่ระหว่างทดสอบ/พัฒนา อาจมี bug หรือ false positive ได้ | ❌ ปิด (ต้องเปิดเอง) |
| `clippy::cargo` | ตรวจสอบปัญหาที่เกี่ยวกับไฟล์ `Cargo.toml` เอง (เช่น metadata ไม่ครบสำหรับ publish) | ❌ ปิด (ต้องเปิดเอง) |

โดย default เมื่อคุณรัน `cargo clippy` เปล่า ๆ จะเปิดใช้แค่ 4 หมวดแรก (`correctness`, `style`, `complexity`, `perf`)
ซึ่งเพียงพอสำหรับการเขียนโค้ดคุณภาพดีในระดับมาตรฐานทั่วไปแล้ว หากต้องการความเข้มงวดสูงสุด (มักใช้ในทีมที่ทำ
open-source library คุณภาพสูง หรือ production code ระดับ enterprise) สามารถเปิด `pedantic` เพิ่มได้ด้วย:

```bash
cargo clippy -- -W clippy::pedantic
```

แต่ระวัง: `pedantic` เข้มงวดมากจนบางครั้ง "จู้จี้" เกินความจำเป็น เช่น อาจแนะนำให้เติม `# Errors` section ใน doc
comment ของทุกฟังก์ชันที่ return `Result` แม้ในโปรเจกต์เล็ก ๆ ที่ไม่จำเป็นต้องมีเอกสารระดับ library ก็ตาม — ทีม
ส่วนใหญ่จึงเลือกเปิดเฉพาะบางกฎจาก `pedantic` ที่เห็นว่าเหมาะกับโปรเจกต์ตัวเอง ไม่เปิดทั้งหมวดตรง ๆ

### 5.12 ตัวอย่าง Lint จริงที่พบบ่อยที่สุด (พร้อม Before/After)

มาดูตัวอย่าง lint จริง 4 ตัวที่มือใหม่ Rust เจอบ่อยที่สุด พร้อมคำอธิบายว่าทำไม clippy ถึงแนะนำแบบนั้น — ทุกตัวอย่าง
ใช้ระบบจัดการสินค้าคงคลัง (inventory) เป็นบริบท เพื่อให้เห็นภาพการใช้งานจริง ไม่ใช่แค่ `foo`/`bar`

#### Lint #1: `clippy::needless_return`

**โค้ดก่อนแก้ (clippy จะเตือน):**

```rust
fn calculate_shipping_fee(weight_kg: f64) -> f64 {
    if weight_kg > 20.0 {
        return weight_kg * 15.0;
    } else {
        return weight_kg * 20.0;
    }
}

fn main() {
    println!("ค่าส่ง: {}", calculate_shipping_fee(25.0));
}
```

**คำเตือนจาก clippy (รูปแบบจริง):**

```
warning: unneeded `return` statement
 --> src/main.rs:3:9
  |
3 |         return weight_kg * 15.0;
  |         ^^^^^^^^^^^^^^^^^^^^^^^^ help: remove `return`
  |
  = note: `#[warn(clippy::needless_return)]` on by default
  = help: for further information visit https://rust-lang.github.io/rust-clippy/master/index.html#needless_return
```

**โค้ดหลังแก้:**

```rust
fn calculate_shipping_fee(weight_kg: f64) -> f64 {
    if weight_kg > 20.0 {
        weight_kg * 15.0
    } else {
        weight_kg * 20.0
    }
}
```

**เหตุผลเชิงลึก:** ใน Rust ทุก block (`{ ... }`) คือ **expression** และค่าของ statement สุดท้ายที่ไม่มี semicolon
ปิดท้ายจะกลายเป็น "ค่าที่ return กลับออกจาก block นั้นโดยอัตโนมัติ" นี่คือหัวใจของการที่ Rust เป็น
**expression-oriented language** (ต่างจาก C/Java ที่เป็น statement-oriented และต้องใช้ `return` เสมอเมื่อต้องการ
ส่งค่ากลับ) การใช้ `return` แบบชัดเจนตอนที่มันเป็น statement สุดท้ายของฟังก์ชันจึงเป็นสิ่งที่ **"เกิน" (needless)**
ความจำเป็น — ไม่ผิด แต่ไม่ idiomatic การไม่ใช้ `return` เมื่อไม่จำเป็นทำให้โค้ดกระชับและอ่านง่ายขึ้น อย่างไรก็ตาม
`return` ยังจำเป็นและถูกต้องเมื่อคุณต้องการ **ออกจากฟังก์ชันก่อนถึงจุดสุดท้าย** (early return) เช่นภายใน `if` ที่ยัง
มีโค้ดต่อจากนั้นอีก

#### Lint #2: `clippy::redundant_clone`

**โค้ดก่อนแก้ (clippy จะเตือน):**

```rust
struct Customer {
    name: String,
    email: String,
}

fn send_welcome_email(email: String) {
    println!("ส่งอีเมลต้อนรับไปที่ {email}");
}

fn main() {
    let customer = Customer {
        name: String::from("สมหญิง"),
        email: String::from("somying@example.com"),
    };

    // customer.email ไม่ได้ถูกใช้ที่ไหนอีกหลังจากบรรทัดนี้
    send_welcome_email(customer.email.clone());

    println!("ลูกค้าชื่อ: {}", customer.name);
}
```

**คำเตือนจาก clippy (รูปแบบจริง):**

```
warning: redundant clone
  --> src/main.rs:14:33
   |
14 |     send_welcome_email(customer.email.clone());
   |                                 ^^^^^^^^ help: remove this
   |
note: this value is not dropped or moved after `email`, and is not used after this point
   = note: `#[warn(clippy::redundant_clone)]` on by default
```

**โค้ดหลังแก้:**

```rust
fn main() {
    let customer = Customer {
        name: String::from("สมหญิง"),
        email: String::from("somying@example.com"),
    };

    send_welcome_email(customer.email);
    println!("ลูกค้าชื่อ: {}", customer.name);
}
```

**เหตุผลเชิงลึก:** `.clone()` สร้าง**สำเนา (copy) ของข้อมูลใน heap แยกต่างหาก** ซึ่งมีต้นทุนจริงด้าน CPU และหน่วยความจำ
(เราจะเข้าใจกลไก ownership/move เต็มรูปแบบใน Part 6) การ clone มีประโยชน์เมื่อคุณ**ยังต้องใช้ค่าเดิมต่อไปหลังจากส่ง
สำเนาออกไปแล้ว** แต่ในตัวอย่างข้างต้น `customer.email` ไม่ถูกใช้ที่ไหนอีกหลังจากส่งเข้า
`send_welcome_email` — เมื่อไม่มีการใช้ค่าเดิมต่อ การ `.clone()` จึงเป็นการเสียทรัพยากรแบบไม่มีประโยชน์ใด ๆ ตอบแทน
วิธีที่ถูกต้องคือ **move** ค่า `email` เข้าไปในฟังก์ชันตรง ๆ (เพราะ struct field แต่ละตัวสามารถถูก move แยกออกจาก
struct ได้ทีละส่วน หากไม่ได้ implement `Drop` ให้กับ struct นั้น) นี่คือตัวอย่างที่ชัดเจนว่า clippy ไม่ได้ตรวจแค่
"style" แต่ตรวจ **performance** ที่มีผลจริงต่อโปรแกรม โดยเฉพาะในโค้ดที่ clone `String` หรือ `Vec` ขนาดใหญ่ซ้ำ ๆ
ในลูปที่รันบ่อยมาก

#### Lint #3: `clippy::single_match`

**โค้ดก่อนแก้ (clippy จะเตือน):**

```rust
fn print_stock_warning(stock: Option<u32>) {
    match stock {
        Some(count) => println!("เหลือสินค้า {count} ชิ้น"),
        None => (),
    }
}

fn main() {
    print_stock_warning(Some(5));
    print_stock_warning(None);
}
```

**คำเตือนจาก clippy (รูปแบบจริง):**

```
warning: you seem to be trying to use `match` for destructuring a single pattern.
Consider using `if let`
 --> src/main.rs:2:5
  |
2 | /     match stock {
3 | |         Some(count) => println!("เหลือสินค้า {count} ชิ้น"),
4 | |         None => (),
5 | |     }
  | |_____^
  |
  = note: `#[warn(clippy::single_match)]` on by default
help: try
  |
2 ~     if let Some(count) = stock {
3 ~         println!("เหลือสินค้า {count} ชิ้น");
4 ~     }
```

**โค้ดหลังแก้:**

```rust
fn print_stock_warning(stock: Option<u32>) {
    if let Some(count) = stock {
        println!("เหลือสินค้า {count} ชิ้น");
    }
}
```

**เหตุผลเชิงลึก:** `match` เป็นเครื่องมือที่ทรงพลังมากสำหรับจัดการ **หลาย pattern** (เราจะเรียนละเอียดใน Part 10)
แต่เมื่อคุณมีแค่ 2 กรณี และกรณีหนึ่งใน 2 นั้นคือ "ไม่ทำอะไรเลย" (`None => ()`) การเขียน `match` เต็มรูปแบบถือเป็น
การ**เพิ่ม noise ที่ไม่จำเป็น** ให้กับผู้อ่านโค้ด `if let` ถูกออกแบบมาเฉพาะสำหรับสถานการณ์นี้: "ถ้า pattern นี้ตรง
ให้ทำสิ่งนี้ ไม่ตรงก็ไม่ต้องทำอะไร" ซึ่งสื่อเจตนาได้ตรงกว่าและกระชับกว่า `match` ที่มี arm หนึ่งเป็น no-op ข้อสังเกต
สำคัญ: ถ้าทั้งสอง arm ของ `match` ทำสิ่งที่ "มีความหมาย" ทั้งคู่ (ไม่ใช่แค่กรณีหนึ่งเป็น `()`) clippy จะ**ไม่เตือน**
lint นี้ เพราะในกรณีนั้น `match` ยังเป็นตัวเลือกที่เหมาะสมกว่า (แสดงทุก branch อย่างชัดเจนเท่ากัน)

#### Lint #4: `clippy::len_zero`

**โค้ดก่อนแก้ (clippy จะเตือน):**

```rust
struct Warehouse {
    items: Vec<String>,
}

fn check_warehouse_status(warehouse: &Warehouse) {
    if warehouse.items.len() == 0 {
        println!("คลังสินค้าว่างเปล่า ต้องสั่งสินค้าเพิ่ม");
    } else {
        println!("คลังสินค้ามีสินค้าอยู่ {} รายการ", warehouse.items.len());
    }
}
```

**คำเตือนจาก clippy (รูปแบบจริง):**

```
warning: length comparison to zero
 --> src/main.rs:6:8
  |
6 |     if warehouse.items.len() == 0 {
  |        ^^^^^^^^^^^^^^^^^^^^^^^^^^ help: using `is_empty` is clearer and more explicit: `warehouse.items.is_empty()`
  |
  = note: `#[warn(clippy::len_zero)]` on by default
```

**โค้ดหลังแก้:**

```rust
fn check_warehouse_status(warehouse: &Warehouse) {
    if warehouse.items.is_empty() {
        println!("คลังสินค้าว่างเปล่า ต้องสั่งสินค้าเพิ่ม");
    } else {
        println!("คลังสินค้ามีสินค้าอยู่ {} รายการ", warehouse.items.len());
    }
}
```

**เหตุผลเชิงลึก:** `Vec<T>`, `String`, และ collection มาตรฐานอื่น ๆ ใน Rust มี method `.is_empty()` ให้ใช้เสมอ
คู่กับ `.len()` (เป็นธรรมเนียมที่กำหนดไว้ผ่าน convention ของ standard library) การเขียน `.len() == 0` แทน
`.is_empty()` มีข้อเสีย 2 อย่าง: (1) **อ่านยากกว่าเล็กน้อย** — ผู้อ่านต้องแปลความหมาย "ความยาวเท่ากับศูนย์" เป็น
"ว่างเปล่า" ในหัว ในขณะที่ `.is_empty()` สื่อความหมายตรงตัวทันที และ (2) **อาจช้ากว่าในบาง type** — สำหรับบาง
collection แบบพิเศษ (เช่น linked list หรือ collection ที่คำนวณ length แบบ lazy) การเช็คว่า "ว่างหรือไม่" อาจทำได้เร็ว
กว่าการนับความยาวทั้งหมดมาก (`is_empty()` มักถูก implement ให้เช็คแค่ "มี element แรกหรือไม่" ซึ่งเร็วกว่าการวน
นับทั้งหมด) แม้ `Vec` เองจะคำนวณ `len()` แบบ O(1) อยู่แล้ว (เพราะเก็บค่า length ไว้เป็นตัวเลขตรง ๆ) แต่ `clippy`
เตือน lint นี้แบบครอบคลุมทุก type ที่มี trait `is_empty()` เพื่อส่งเสริม convention ที่ดีในทุกกรณี ไม่ต้องแยกคิดว่า
type ไหน "คุ้ม" ที่จะเปลี่ยนบ้าง

### 5.13 การปิด Lint ด้วย `#[allow(clippy::...)]`

บางครั้ง clippy อาจเตือนในสถานการณ์ที่คุณ**ตั้งใจ**เขียนแบบนั้นจริง ๆ ด้วยเหตุผลที่ดี (เช่น เพื่อความชัดเจนในเชิง
เอกสาร หรือเพราะ constraint บางอย่างที่ clippy มองไม่เห็น) ในกรณีเหล่านี้ Rust อนุญาตให้ปิด lint เฉพาะจุดได้ด้วย
attribute `#[allow(...)]`

```rust
struct Warehouse {
    items: Vec<String>,
}

impl Warehouse {
    // ตั้งใจเขียนแบบนี้เพื่อให้สอดคล้องกับ interface ของระบบเดิมที่ยังไม่ได้ย้ายมาใช้ is_empty()
    // ทั้งหมด (จะทยอยแก้ในงาน refactor รอบถัดไป — ดู ticket INV-204)
    #[allow(clippy::len_zero)]
    fn is_out_of_stock(&self) -> bool {
        self.items.len() == 0
    }
}
```

สังเกตแนวปฏิบัติที่ดีในตัวอย่างนี้: **การ `#[allow]` ควรมี comment อธิบายเหตุผลเสมอ** เพื่อให้คนอ่านโค้ด (รวมถึง
ตัวคุณเองในอนาคต) เข้าใจว่าทำไมถึงตัดสินใจปิด lint ตรงนี้ ไม่ใช่แค่ปิดแบบไม่มีคำอธิบาย

`#[allow(...)]` สามารถวางในระดับต่าง ๆ ได้ตามความเหมาะสม:

```rust
// ปิดเฉพาะ statement เดียว
#[allow(clippy::needless_return)]
fn example_one() -> i32 {
    return 42;
}

// ปิดทั้งฟังก์ชัน (ตัวอย่างข้างบน is_out_of_stock ก็เป็นแบบนี้)

// ปิดทั้ง module
#[allow(clippy::redundant_clone)]
mod legacy_code {
    // โค้ดเก่าทั้ง module ที่ยังไม่ได้ optimize
}

// ปิดทั้ง crate (เขียนไว้บนสุดของ main.rs หรือ lib.rs)
#![allow(clippy::single_match)]
```

**ทำไม `#![allow(clippy::all)]` แบบเหมาเข่งทั้ง crate ถึงเป็นความคิดที่ไม่ดี**

คุณอาจเคยเห็นโค้ดบางโปรเจกต์ (มักเป็นโปรเจกต์ของมือใหม่ที่รำคาญ warning) เขียนแบบนี้ไว้บนสุดของไฟล์:

```rust
#![allow(clippy::all)]
```

**อย่าทำแบบนี้** เหตุผลเชิงลึกมีดังนี้:

1. **`clippy::all` ปิดทั้ง 4 หมวดหมู่ที่เปิดโดย default ทีเดียว** รวมถึงหมวด **`correctness`** ซึ่งเป็นกฎที่ตรวจจับ
   โค้ดที่ **ทำงานผิดพลาดแน่นอน** (ไม่ใช่แค่เรื่อง style) การปิดหมวดนี้เท่ากับปิดตาไม่ให้เห็นบั๊กจริงที่ clippy
   พยายามเตือนคุณ
2. **มันซ่อนปัญหาใหม่ ๆ ที่จะเกิดในอนาคต** — เมื่อคุณเขียนโค้ดเพิ่มในไฟล์เดียวกัน (หรือ crate เดียวกัน) โค้ดใหม่ที่มี
   ปัญหาจริง ๆ ก็จะไม่ถูกเตือนเช่นกัน เพราะ `#![allow(clippy::all)]` มีผลกับทั้ง crate ไม่ใช่แค่โค้ดเดิมที่ตั้งใจ
   จะปิดตอนแรก
3. **มันทำลายจุดประสงค์ทั้งหมดของการมี linter** — ถ้าทีมของคุณรัน `cargo clippy` ใน CI เพื่อบังคับมาตรฐาน แต่มีคนเขียน
   `#![allow(clippy::all)]` ไว้ ทุกอย่างจะดูเหมือนผ่านหมด (เขียว) ทั้งที่จริง ๆ ไม่มีการตรวจสอบอะไรเกิดขึ้นเลย —
   เป็นการหลอกตัวเองและทีม

**แนวทางที่ถูกต้องกว่า:** ถ้า lint ตัวใดตัวหนึ่งเป็นปัญหาซ้ำ ๆ ในสไตล์การเขียนของทีมจริง ๆ (เช่น ทีมมีเหตุผลทาง
architecture ที่ต้องเขียนขัดกับ lint บางตัวเป็นประจำ) ให้ปิด **เฉพาะ lint ตัวนั้น** แบบเจาะจง (`#[allow(clippy::
lint_name)]`) ไม่ใช่ปิดทั้งหมวดหรือทั้ง `clippy::all` และควรเขียน comment อธิบายเหตุผลไว้เสมอตามที่แสดงตัวอย่างไว้
ข้างต้น

### 5.14 Treat Warnings as Errors: `#![deny(warnings)]` และ `RUSTFLAGS`

ในสภาพแวดล้อมการพัฒนาแบบทีม โดยเฉพาะใน CI pipeline หลายทีมต้องการบังคับว่า **"ห้ามมี warning หลงเหลืออยู่เลย"**
ไม่ว่าจะเป็น warning จาก `rustc` เองหรือจาก `clippy` มีสองวิธีหลักในการบังคับเรื่องนี้:

**วิธีที่ 1: `#![deny(warnings)]` ในโค้ด**

```rust
#![deny(warnings)]

fn main() {
    let unused_variable = 42; // จะเป็น compile error ทันที ไม่ใช่แค่ warning
    println!("Hello");
}
```

ผลลัพธ์เมื่อ compile:

```
error: unused variable: `unused_variable`
 --> src/main.rs:4:9
  |
4 |     let unused_variable = 42;
  |         ^^^^^^^^^^^^^^^^ help: if this is intentional, prefix it with an underscore: `_unused_variable`
  |
note: `#[deny(warnings)]` implied by `#![deny(warnings)]`
```

**วิธีที่ 2: `RUSTFLAGS="-D warnings"` (นิยมมากกว่าใน CI)**

```bash
RUSTFLAGS="-D warnings" cargo build
```

หรือสำหรับ clippy โดยเฉพาะ:

```bash
cargo clippy -- -D warnings
```

flag `-D` (deny) บอกให้ compiler/clippy **ถือว่า warning ทุกตัวเป็น error** ทำให้ build ล้มเหลวทันทีถ้ามี warning
หลงเหลืออยู่ ต่างจากวิธีที่ 1 ตรงที่ `RUSTFLAGS` เป็น **environment variable ที่ตั้งจากภายนอกโค้ด** ไม่ต้องแก้ไข
source code เลย ซึ่งเหมาะกับ CI มากกว่า เพราะทีมสามารถ**เลือก**ว่าจะบังคับความเข้มงวดนี้เฉพาะใน pipeline (ที่ควบคุม
ได้เต็มที่) โดยไม่กระทบกับนักพัฒนาที่กำลังเขียนโค้ดอยู่ในเครื่องตัวเอง

**⚠️ คำเตือนสำคัญ: อย่าใช้ `#![deny(warnings)]` แบบไม่ระมัดระวังในโค้ด production ที่ commit ลง repository**

นี่คือกับดักที่ทีมมืออาชีพหลายทีมเจอมาแล้วจริง ๆ: **compiler เวอร์ชันใหม่ ๆ ที่ออกมาทุก 6 สัปดาห์ อาจเพิ่ม warning
ใหม่ที่ไม่มีในเวอร์ชันเก่า** แม้โค้ดของคุณจะไม่เปลี่ยนแปลงเลยแม้แต่บรรทัดเดียว ตัวอย่างสถานการณ์จริงที่เกิดขึ้นได้:

1. ทีมของคุณเขียน `#![deny(warnings)]` ไว้ในโค้ด แล้ว commit ไว้ตั้งแต่ปีที่แล้ว ตอนนั้น build ผ่านสนิท
2. หกเดือนต่อมา มีคนรัน `rustup update` อัปเดต stable toolchain เป็นเวอร์ชันใหม่กว่า
3. เวอร์ชันใหม่นี้เพิ่ม lint ใหม่ (หรือขยายความครอบคลุมของ lint เดิม) ที่ตรวจพบ pattern ในโค้ด**เดิม**ที่ไม่เคยถูก
   เตือนมาก่อน
4. เพราะมี `#![deny(warnings)]` warning ใหม่นี้กลายเป็น **error ทันที** และ **build ทั้งโปรเจกต์ล้มเหลว** แม้ไม่มีใคร
   แก้โค้ดสักบรรทัดเลย — ปัญหานี้อาจเกิดขึ้นตอนที่ทีมกำลังเร่งปล่อย hotfix สำคัญ ทำให้เสียเวลาแก้ปัญหาที่ไม่เกี่ยวกับ
   งานที่ทำอยู่เลย

**แนวทางที่ปลอดภัยกว่า** ที่ทีมมืออาชีพส่วนใหญ่เลือกใช้:

- ใช้ `RUSTFLAGS="-D warnings"` หรือ `cargo clippy -- -D warnings` **เฉพาะใน CI pipeline** (Part 97 จะลงรายละเอียด
  เต็มรูปแบบ) ไม่ฝัง `#![deny(warnings)]` ไว้ใน source code ที่ commit ระยะยาว
- ถ้าจำเป็นต้องบังคับใน source code จริง ๆ ให้ **deny เฉพาะ lint ที่เจาะจง** (เช่น `#![deny(clippy::correctness)]`)
  แทนการ deny ทุก warning แบบเหมาเข่ง เพื่อลดโอกาสที่ lint ใหม่ในอนาคตจะทำให้ build พังโดยไม่คาดคิด
- ในเครื่องพัฒนาส่วนตัวประจำวัน ให้ warning เป็นแค่ warning (ไม่ deny) เพื่อให้ยังสามารถ build และทดสอบโค้ดที่ยัง
  เขียนไม่เสร็จได้ตามปกติ แล้วค่อยไปเข้มงวดตอน CI หรือก่อน merge

### 5.15 Pre-commit Hook และ CI: `cargo fmt --check && cargo clippy -- -D warnings`

เมื่อรวมทุกอย่างที่เรียนมาในบทนี้เข้าด้วยกัน แนวทางที่ทีมพัฒนา Rust ระดับมืออาชีพนิยมใช้กันมากที่สุดคือการรันคำสั่ง
สองอันนี้ต่อกันเป็น **gate (ประตูตรวจสอบ)** ก่อนที่โค้ดจะถูกยอมรับเข้าสู่ codebase หลัก:

```bash
cargo fmt --check && cargo clippy -- -D warnings
```

คำสั่งนี้ทำงานตามลำดับ: ตรวจสอบว่าโค้ด**จัดรูปแบบถูกต้อง**ก่อน (ถ้าไม่ผ่าน จะหยุดทันทีเพราะ `&&`) แล้วถ้าผ่าน จึงค่อย
ตรวจสอบว่า**ไม่มี clippy warning หลงเหลือ** (โดยถือว่า warning ทุกตัวเป็น error ด้วย `-D warnings`) การรันแบบนี้มัก
ถูกติดตั้งไว้ในสองจุด:

1. **Git pre-commit hook** — สคริปต์ที่รันอัตโนมัติทุกครั้งก่อนที่ `git commit` จะสำเร็จ (เก็บไว้ที่ `.git/hooks/
   pre-commit` หรือจัดการผ่าน tool อย่าง `pre-commit` framework หรือ `husky`-style สำหรับ Rust เช่น `cargo-husky`)
   ถ้าคำสั่งข้างต้น fail, การ commit จะถูกยกเลิกทันที บังคับให้ผู้เขียนโค้ดแก้ไขก่อน commit ได้จริง
2. **CI Pipeline** (เช่น GitHub Actions) — รันคำสั่งเดียวกันนี้ทุกครั้งที่มีการ push โค้ดหรือเปิด pull request
   เพื่อเป็นด่านสุดท้ายที่ป้องกันไม่ให้โค้ดที่ไม่ผ่านมาตรฐานถูก merge เข้า branch หลัก แม้ pre-commit hook บนเครื่อง
   ใครบางคนจะถูกข้ามไปด้วยเหตุผลใดก็ตาม (เช่นใช้ `git commit --no-verify`)

การมีทั้งสองด่าน (pre-commit + CI) สำคัญ เพราะ pre-commit hook เป็นเพียง **"ความสะดวก"** ที่ช่วยจับปัญหาได้เร็วที่สุด
บนเครื่องนักพัฒนาเอง แต่สามารถถูกข้ามได้เสมอ (ทั้งตั้งใจและไม่ตั้งใจ) ส่วน CI คือ **"ด่านที่บังคับจริง"** ที่ไม่มีใคร
ข้ามได้ถ้าตั้งค่าให้ CI ต้องผ่านก่อนจึง merge ได้ (เช่นตั้งเป็น "required status check" บน GitHub)

เรื่อง CI/CD แบบเต็มรูปแบบ (การตั้งค่า GitHub Actions workflow file, caching dependency ให้ build เร็วขึ้น, การรัน
matrix ทดสอบหลาย OS/toolchain พร้อมกัน ฯลฯ) เป็นเนื้อหาเชิงลึกที่รอคุณอยู่ใน **Part 97: CI/CD Pipeline ด้วย GitHub
Actions** ตอนนี้ขอให้เข้าใจแค่หลักการกว้าง ๆ ไว้ก่อนว่า **"fmt check + clippy deny warnings" คือ combo มาตรฐานที่
ควรอยู่ใน pipeline ของทุกโปรเจกต์ Rust ระดับมืออาชีพ**

## กับดักที่พบบ่อย (Common Pitfalls)

**1. รัน `cargo fmt` แล้วงงว่าทำไม diff ใน git ใหญ่ผิดปกติ**

มือใหม่หลายคนเขียนโค้ดโดยไม่เปิด format-on-save มาตั้งแต่ต้น พอมาสัปดาห์ที่ 3 ค่อยรัน `cargo fmt` ครั้งแรก ผลคือ
ทุกไฟล์ในโปรเจกต์ถูกจัดรูปแบบใหม่หมด ทำให้ diff ใน pull request มีการเปลี่ยนแปลงหลายร้อยบรรทัดที่ "ไม่เกี่ยวกับ
logic เลย" ปนอยู่กับการเปลี่ยนแปลงจริงเพียงไม่กี่บรรทัด ทำให้ reviewer แยกไม่ออกว่าอะไรคือการเปลี่ยนแปลงจริง

วิธีแก้: เปิด `editor.formatOnSave: true` ตั้งแต่วันแรกที่เริ่มโปรเจกต์ (ตามที่แนะนำใน Part 1) หรือถ้าเข้ามาทำงานกับ
โปรเจกต์ที่มีอยู่แล้วและยังไม่ได้ format ให้รัน `cargo fmt` แยกเป็น **commit เดี่ยว ๆ** ที่มีข้อความชัดเจนว่า
"chore: run cargo fmt" ไม่ปนกับ commit ที่มีการเปลี่ยน logic

**2. เจอ warning จาก clippy เยอะมากในโปรเจกต์ที่มีอยู่แล้ว แล้วรีบ `#![allow(clippy::all)]` ทิ้งทั้งหมด**

เมื่อรัน `cargo clippy` ในโปรเจกต์เก่าที่ไม่เคยรันมาก่อน อาจเจอ warning เป็นร้อยตัว ทำให้เกิดความรู้สึก overwhelm
แล้วแก้ปัญหาแบบลัดด้วยการปิดทุกอย่างทีเดียว (ตามที่อธิบายในหัวข้อ 5.13 ว่าทำไมถึงไม่ควรทำ)

วิธีแก้ที่ดีกว่า: ใช้คำสั่ง `cargo clippy --fix` ซึ่งจะ**แก้ไขให้อัตโนมัติ**สำหรับ lint ที่ clippy มั่นใจว่าแก้ได้อย่าง
ปลอดภัย (ส่วนใหญ่คือ lint ในหมวด `style` และ `complexity`) แล้วค่อยไล่ดู warning ที่เหลือทีละกลุ่ม โดยเริ่มจากหมวด
`correctness` ก่อนเสมอ (เพราะมีโอกาสเป็นบั๊กจริงมากที่สุด) ค่อยไล่ไปหมวดอื่นทีหลัง:

```bash
cargo clippy --fix --allow-dirty
```

(flag `--allow-dirty` จำเป็นถ้ามีการเปลี่ยนแปลงที่ยังไม่ commit อยู่ใน working directory — clippy จะเตือนให้ commit
ก่อนโดย default เพื่อป้องกันไม่ให้แก้ไขทับงานที่ยังไม่บันทึกโดยไม่ได้ตั้งใจ)

**3. สับสนระหว่าง `#[allow]` กับ `#[warn]` กับ `#[deny]`**

มือใหม่บางคนเข้าใจผิดว่า `#[allow(...)]` แปลว่า "เปิดการเตือน" (เพราะคำว่า allow ฟังดูเหมือน "อนุญาตให้เตือน")
แต่ความหมายจริงคือ **ตรงกันข้าม** — `#[allow(lint_name)]` แปลว่า **"อนุญาตให้โค้ดแบบนี้เกิดขึ้นได้ โดยไม่ต้องเตือน"**
(ปิดการเตือน) ส่วน `#[warn(lint_name)]` คือเปิดการเตือนแบบปกติ (เป็นค่า default ของ lint ส่วนใหญ่อยู่แล้ว) และ
`#[deny(lint_name)]` คือเปิดการเตือนแบบเข้มงวดที่สุด (ทำให้เป็น compile error ทันทีถ้าเจอ)

สรุปลำดับความเข้มงวดจากน้อยไปมาก: `allow` (ปิดเงียบ) → `warn` (เตือนแต่ยัง compile ผ่าน) → `deny` (error, compile
ไม่ผ่าน) → `forbid` (เข้มงวดที่สุด ห้ามแม้แต่ใช้ `#[allow]` มา override ในโค้ดย่อยที่อยู่ข้างในอีกที)

## แบบฝึกหัด (Exercises)

1. **[ง่าย]** สร้างไฟล์ Rust ที่มี comment ครบทั้ง 4 แบบที่เรียนในบทนี้ (`//`, `/* */`, `///`, `//!`) อย่างละ
   อย่างน้อย 1 ตำแหน่ง จัดวางให้ถูกต้องตามหน้าที่ของแต่ละแบบ (เช่น `//!` ต้องอยู่บนสุดของไฟล์, `///` ต้องอยู่เหนือ
   ฟังก์ชันที่มันอธิบาย) แล้วตรวจสอบว่า `cargo build` ยัง compile ผ่านปกติ

2. **[กลาง]** เขียนไฟล์ `main.rs` ที่มีโค้ดจัดรูปแบบไม่เรียบร้อย (ไม่มี space รอบ operator, indent ไม่สม่ำเสมอ,
   ตัวแปรชื่อ struct เขียนติดกันไม่มีบรรทัดใหม่) แล้วรัน `cargo fmt --check` เพื่อดู diff ที่ rustfmt แนะนำ ก่อนรัน
   `cargo fmt` จริงเพื่อแก้ไข สังเกตความแตกต่างระหว่างสองคำสั่งนี้ (hint: `--check` ไม่แก้ไฟล์ ส่วนไม่มี flag จะ
   แก้ไฟล์ทันที)

3. **[กลาง]** เขียนโปรแกรม Rust ที่จงใจมีโค้ดที่ผิด lint อย่างน้อย 3 จาก 4 ตัวที่เรียนในหัวข้อ 5.12
   (`needless_return`, `redundant_clone`, `single_match`, `len_zero`) รวมกันในไฟล์เดียว รัน `cargo clippy`
   แล้ว copy คำเตือนทั้งหมดมาบันทึกไว้ จากนั้นแก้ไขโค้ดตามคำแนะนำของ clippy จนกระทั่งรัน `cargo clippy` แล้วไม่มี
   warning เหลือเลย

4. **[ยาก/ประยุกต์]** ออกแบบระบบเล็ก ๆ สำหรับ "ระบบจองตั๋วภาพยนตร์" (ยังไม่ต้องซับซ้อนมาก แค่มี struct `Booking`
   เก็บชื่อผู้จอง จำนวนที่นั่ง และราคาต่อที่นั่ง กับฟังก์ชันคำนวณราคารวมและตรวจสอบว่าที่นั่งเต็มหรือไม่) เขียนโค้ด
   ให้ compile ผ่านแบบปกติก่อน จากนั้น: (ก) สร้างไฟล์ `rustfmt.toml` กำหนด `max_width = 80` แล้วสังเกตว่า `cargo fmt`
   จัดรูปแบบต่างจาก default (100) อย่างไร (ข) ตั้งใจปิด lint หนึ่งตัวด้วย `#[allow(clippy::...)]` พร้อมเขียน comment
   อธิบายเหตุผลที่สมเหตุสมผล (ค) ลองรัน `cargo clippy -- -D warnings` เพื่อยืนยันว่าไม่มี warning ที่ทำให้ build
   fail หลงเหลือ — นี่คือแบบฝึกหัดที่จำลอง workflow จริงของทีมพัฒนามืออาชีพก่อน merge code

## สรุป

ในบทนี้เราปิดท้าย**โมดูล 0: เริ่มต้นใช้งาน Rust** ด้วยการเรียนรู้เครื่องมือที่ดูแลคุณภาพโค้ดสองด้านที่เสริมกัน:
`rustfmt` ดูแล**หน้าตา**ของโค้ดให้เป็นมาตรฐานเดียวกันทั้ง ecosystem ผ่านปรัชญา "One True Style" ที่ตัดปัญหาการเถียง
เรื่อง style ใน code review ออกไปโดยสิ้นเชิง ส่วน `clippy` ดูแล**คุณภาพเชิง logic**ของโค้ดผ่าน lint กว่า 750 กฎที่
แบ่งเป็นหมวดหมู่ตามความเสี่ยง (`correctness`, `style`, `complexity`, `perf`, `pedantic`, `nursery`) เราได้เห็น
ตัวอย่าง lint จริง 4 ตัวที่พบบ่อยที่สุด พร้อมเหตุผลเชิงลึกว่าทำไม Rust ถึงแนะนำให้เขียนแบบนั้น เรียนรู้วิธีปิด lint
อย่างมีเหตุผลด้วย `#[allow(clippy::...)]` แทนการปิดแบบเหมาเข่ง และเข้าใจข้อควรระวังของการ treat warnings as errors
ในสภาพแวดล้อมพัฒนาจริง รวมถึงได้เห็นภาพรวมว่าเครื่องมือทั้งหมดนี้ถูกร้อยเรียงเข้าด้วยกันเป็น workflow มาตรฐานผ่าน
pre-commit hook และ CI pipeline อย่างไร

ตลอด 5 บทที่ผ่านมาในโมดูล 0 คุณได้ติดตั้งเครื่องมือครบชุด เข้าใจ Cargo และโครงสร้างโปรเจกต์ เขียนตัวแปรและ type
พื้นฐาน ควบคุมการทำงานของโปรแกรมด้วย control flow และตอนนี้รู้จักเครื่องมือดูแลคุณภาพโค้ดแล้ว — นี่คือ **"เครื่องมือ
พื้นฐานที่จำเป็นทั้งหมด"** สำหรับการเขียนโปรแกรม Rust ในระดับ syntax แต่สิ่งที่ทำให้ Rust **แตกต่างอย่างแท้จริง**
จากภาษาอื่นทุกภาษาที่คุณอาจเคยรู้จักมา ยังไม่ได้เริ่มขึ้นเลย

ใน **Part 6** เราจะเข้าสู่ **โมดูล 1: พื้นฐานภาษา Rust** อย่างเป็นทางการ ด้วยหัวข้อที่เป็น**หัวใจที่แท้จริง**ของ
ทั้งภาษา — **Ownership** ระบบที่ทำให้ Rust สามารถรับประกันความปลอดภัยของ memory ได้โดยไม่ต้องมี garbage collector
เลย แนวคิดเรื่อง move, copy, และ drop ที่เราแค่ "เกริ่น" ไว้ใน Part 1 (หัวข้อ 1.3) จะถูกอธิบายอย่างละเอียดครบถ้วน
พร้อมตัวอย่าง error จาก borrow checker จริง ๆ ที่คุณจะต้องเจอบ่อยมากในช่วงแรกของการเรียน Rust — และเมื่อเข้าใจมันแล้ว
คุณจะเข้าใจว่าทำไม Rust ถึงถูกออกแบบมาแบบนี้ และทำไมมันถึงคุ้มค่ากับความพยายามในการเรียนรู้
