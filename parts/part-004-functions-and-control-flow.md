# Part 4: ฟังก์ชันและ Control Flow

> โมดูล: เริ่มต้นใช้งาน Rust (Getting Started) | ระดับ: พื้นฐาน | เวลาโดยประมาณ: 90 นาที

## เป้าหมายของบทเรียน

หลังจากจบบทนี้ คุณจะสามารถ:

- ประกาศและเรียกใช้ฟังก์ชันใน Rust ด้วย syntax ที่ถูกต้อง พร้อมระบุ type ของ parameter และค่าที่ return ได้อย่างถูกต้อง
- อธิบายได้ว่าทำไม Rust ไม่มี default parameter value และ function overloading แบบภาษาอื่น พร้อมรู้จักวิธีแก้ปัญหาแบบ idiomatic
- แยกแยะความแตกต่างระหว่าง **statement** กับ **expression** ได้อย่างแม่นยำ — ซึ่งเป็นแนวคิดที่ลึกและสำคัญที่สุดของบทนี้
- ใช้ `if`/`else if`/`else` เป็น **expression** ที่คืนค่าได้ ไม่ใช่แค่ควบคุม flow แบบภาษาที่คุณคุ้นเคย
- ใช้ `loop`, `while`, และ `for` ได้อย่างถูกต้อง รวมถึงใช้ความสามารถพิเศษของ Rust อย่าง `break` ที่คืนค่าออกจาก `loop` ได้
- ใช้ loop label (`'outer: loop { ... }`) เพื่อควบคุม nested loop ได้อย่างแม่นยำ
- เข้าใจภาพรวมของ `match` ในระดับเบื้องต้น พอสำหรับใช้ในสถานการณ์ง่าย ๆ (รายละเอียดเต็มรออยู่ใน Part 10)
- เขียนโปรแกรมขนาดเล็กที่ผสมผสานฟังก์ชัน, if/else-as-expression, และ loop เข้าด้วยกันในสไตล์ที่ "เป็น Rust" จริง ๆ

## ความรู้ที่ต้องมีมาก่อน

บทนี้ต่อเนื่องจาก:

- **Part 1** — การติดตั้ง Rust toolchain, วิธีรันโปรแกรมด้วย `rustc`/`cargo`, และพื้นฐาน `println!`
- **Part 2** — Cargo, โครงสร้างโปรเจกต์ (`Cargo.toml`, `src/main.rs`), และคำสั่งพื้นฐานอย่าง `cargo run`, `cargo check`

## เนื้อหา

### 4.1 ฟังก์ชันใน Rust: ไวยากรณ์พื้นฐาน

ฟังก์ชันคือหน่วยพื้นฐานที่สุดในการจัดโครงสร้างโค้ด Rust — จริง ๆ แล้วคุณได้ใช้ฟังก์ชันมาตั้งแต่บทที่ 1 แล้ว เพราะ
`fn main() { ... }` ก็คือฟังก์ชันหนึ่งนั่นเอง เพียงแต่เป็นฟังก์ชันพิเศษที่ Rust ใช้เป็นจุดเริ่มต้นของโปรแกรม

รูปแบบไวยากรณ์เต็มของการประกาศฟังก์ชันคือ:

```rust
fn ชื่อฟังก์ชัน(พารามิเตอร์1: ชนิด1, พารามิเตอร์2: ชนิด2, ...) -> ชนิดที่คืนค่า {
    // ตัวฟังก์ชัน (function body)
}
```

มาดูตัวอย่างจริงที่ compile ได้:

```rust
fn add(a: i32, b: i32) -> i32 {
    a + b
}

fn main() {
    let sum = add(3, 5);
    println!("3 + 5 = {sum}");
}
```

ผลลัพธ์:

```
3 + 5 = 8
```

**อธิบายทีละส่วน:**

- `fn` คือ keyword สำหรับประกาศฟังก์ชัน (มาจาก "function")
- `add` คือชื่อฟังก์ชัน — ตามธรรมเนียม (convention) ของ Rust ชื่อฟังก์ชันและตัวแปรต้องเขียนแบบ **`snake_case`**
  (ตัวพิมพ์เล็กทั้งหมด คั่นคำด้วย underscore) ต่างจาก JavaScript/Java ที่นิยม `camelCase` หากคุณเขียน `addTwoNumbers`
  แบบ camelCase ใน Rust, compiler จะไม่ error แต่ `cargo clippy` (Part 5) จะเตือนว่าไม่ตรงตาม naming convention
- `(a: i32, b: i32)` คือรายการพารามิเตอร์ (parameters) — สังเกตว่า **ทุกพารามิเตอร์ต้องระบุชนิดข้อมูลเสมอ**
  เขียนแบบ `ชื่อ: ชนิด` คั่นด้วย comma นี่คือกฎที่ **ไม่มีข้อยกเว้น** ในภาษา Rust
- `-> i32` คือ "arrow syntax" ที่ระบุว่าฟังก์ชันนี้คืนค่าเป็นชนิด `i32` — ถ้าฟังก์ชันไม่คืนค่าอะไรเลย (เหมือน `void`
  ใน C/Java) ก็ไม่ต้องเขียนส่วนนี้เลย (จะอธิบายเรื่อง unit type `()` ในหัวข้อถัดไป)
- `a + b` คือบรรทัดสุดท้ายในตัวฟังก์ชัน **ไม่มี semicolon ต่อท้าย** — นี่คือกลไกการ return ค่าที่สำคัญที่สุดของ Rust
  ซึ่งเราจะเจาะลึกในหัวข้อ 4.4-4.5

ข้อสังเกตที่สำคัญอีกอย่าง: **ฟังก์ชันใน Rust เรียกก่อนหรือหลัง `main()` ก็ได้** ไม่ต้องประกาศฟังก์ชันไว้ก่อนจุดที่เรียกใช้
แบบภาษา C ที่ต้องมี forward declaration หรือ header file — Rust compiler จะสแกนทั้งไฟล์ (หรือทั้ง module) ก่อนแล้วค่อย
ตรวจสอบ ดังนั้นโค้ดนี้ compile ผ่านได้สบาย ๆ:

```rust
fn main() {
    greet(); // เรียกฟังก์ชันที่ประกาศ "หลัง" main() ก็ได้
}

fn greet() {
    println!("สวัสดีจาก Rust!");
}
```

#### เปรียบเทียบกับ Python และ JavaScript: ทำไม type annotation ถึงบังคับ

ถ้าคุณมาจาก Python หรือ JavaScript คุณอาจคุ้นเคยกับการประกาศฟังก์ชันแบบนี้:

**Python:**
```python
def add(a, b):
    return a + b
```

**JavaScript:**
```javascript
function add(a, b) {
    return a + b;
}
```

สังเกตว่าทั้งสองภาษาไม่ต้องระบุชนิดข้อมูลของ `a`, `b`, หรือค่าที่ return เลย — เพราะทั้งคู่เป็น **dynamically typed
language** คือ compiler/interpreter จะรู้ชนิดข้อมูลจริง ๆ ก็ตอน**รันโปรแกรม** (runtime) เท่านั้น ถ้าคุณเรียก `add("hello", 5)`
ใน Python มันจะพยายามรันจริง ๆ แล้วอาจ error ตอนรัน (เช่น `TypeError: can only concatenate str`) หรืออาจไม่ error เลยถ้า
โค้ดส่วนนั้นบังเอิญไม่ถูกเรียกใช้ในการรันครั้งนั้น — บั๊กแบบนี้จะไม่ถูกจับจนกว่าจะมีคน (หรือ test) รันโค้ด path นั้นจริง ๆ

Rust เป็น **statically typed language** ที่ compiler ต้องรู้ชนิดข้อมูลของทุกอย่าง**ก่อน**คอมไพล์เสร็จ (compile time)
สำหรับตัวแปรภายในฟังก์ชัน compiler ยังพอ **infer** (เดา) ชนิดข้อมูลจาก context ได้ในหลายกรณี (อย่างที่เราเห็นใน Part 3
ตอนเขียน `let x = 5;` โดยไม่ต้องบอกว่าเป็น `i32`) แต่สำหรับ **พารามิเตอร์ของฟังก์ชันและค่าที่ return กลับ Rust บังคับให้
ต้องเขียนชนิดข้อมูลชัดเจนเสมอ** ไม่มีการ infer ข้ามขอบฟังก์ชัน

**เหตุผลเชิงออกแบบ (design rationale) ที่สำคัญมี 2 ข้อ:**

1. **ฟังก์ชันคือ "สัญญา" (contract) ระหว่างผู้เขียนกับผู้เรียกใช้** — เมื่อคุณเห็น signature `fn add(a: i32, b: i32) -> i32`
   คุณรู้ทันทีว่าต้องส่งอะไรเข้ามา และจะได้อะไรกลับออกไป โดยไม่ต้องไปอ่านโค้ดข้างในฟังก์ชันเลย สิ่งนี้สำคัญมากในโปรเจกต์ขนาดใหญ่
   ที่มีคนเขียนโค้ดหลายคน หรือเวลาคุณเรียกใช้ library ที่ไม่ได้เขียนเอง — signature ที่ชัดเจนคือ documentation ที่ compiler
   บังคับให้ตรงกับความจริงเสมอ (ไม่มีทาง "เขียน comment ผิด" เพราะ signature ไม่ใช่ comment มันคือส่วนหนึ่งของโค้ดที่ต้อง compile ผ่าน)
2. **การ infer type ข้ามขอบฟังก์ชันทำได้ยากในทางเทคนิค และทำให้ error message แย่ลงมาก** — ถ้า Rust ยอมให้พารามิเตอร์ไม่มี type
   annotation compiler ต้องไปดูว่าฟังก์ชันนี้ถูกเรียกจากที่ไหนบ้าง ด้วย argument ชนิดอะไรบ้าง แล้วพยายามหาชนิดที่เข้ากันได้ทั้งหมด
   ซึ่งในโปรเจกต์ใหญ่ที่ฟังก์ชันหนึ่งอาจถูกเรียกจากหลายร้อยที่ การ infer แบบนี้จะช้ามาก (ทำให้ compile time แย่ลง) และเมื่อเกิด
   error ก็จะระบุตำแหน่งที่แท้จริงของปัญหาได้ยาก (error message จะชี้ไปที่จุดเรียกใช้ที่ผิด ไม่ใช่ตัวฟังก์ชันเอง)

พูดสั้น ๆ คือ: **Rust เลือกความชัดเจนที่ขอบของฟังก์ชัน (function boundary) แลกกับความสะดวกเล็กน้อยตอนเขียนโค้ด** เพื่อให้ได้
compile time ที่เร็วขึ้น, error message ที่แม่นยำขึ้น, และโค้ดที่อ่านเข้าใจได้โดยไม่ต้องรันจริง

### 4.2 หลายพารามิเตอร์ และรายละเอียดที่ควรรู้

ฟังก์ชันสามารถมีพารามิเตอร์ได้หลายตัว คั่นด้วย comma และแต่ละตัวสามารถเป็นชนิดข้อมูลต่างกันได้:

```rust
fn describe_person(name: &str, age: u8, height_cm: f64) {
    println!("{name} อายุ {age} ปี สูง {height_cm} เซนติเมตร");
}

fn main() {
    describe_person("สมชาย", 30, 175.5);
    describe_person("Alice", 28, 168.2);
}
```

ผลลัพธ์:

```
สมชาย อายุ 30 ปี สูง 175.5 เซนติเมตร
Alice อายุ 28 ปี สูง 168.2 เซนติเมตร
```

สังเกตว่าฟังก์ชัน `describe_person` ไม่มี `-> ชนิด` ต่อท้าย parentheses เลย นั่นเพราะมันไม่ได้ return ค่าอะไรออกไป
(มันแค่พิมพ์ข้อความแล้วจบ) ในความเป็นจริง **ทุกฟังก์ชันใน Rust จะ return ค่าเสมอ** แม้จะดูเหมือนไม่ได้ return อะไรก็ตาม
ฟังก์ชันที่ไม่ได้เขียน `-> ชนิด` จะ return ค่าพิเศษที่เรียกว่า **unit type** เขียนแทนด้วย `()` (วงเล็บเปล่า) ซึ่งเทียบได้
คร่าว ๆ กับ `void` ใน C/Java หรือ `None` ใน Python แต่จริง ๆ แล้วมันคือ "ค่า" ที่มีชนิดข้อมูลจริง เพียงแต่ไม่มีข้อมูลอะไร
อยู่ในนั้นเลย (zero-sized type) เราจะเห็นความสำคัญของ `()` อีกครั้งในหัวข้อ statements vs expressions ด้านล่าง

**ลำดับของพารามิเตอร์มีความหมาย** — ต่างจากภาษาที่รองรับ named argument (เช่น Python `describe_person(age=30, name="สมชาย")`)
Rust ไม่รองรับการเรียกฟังก์ชันโดยระบุชื่อพารามิเตอร์แบบนั้น (ไม่มี named argument ในตัวภาษาหลัก) คุณต้องส่ง argument
ตามลำดับที่ประกาศไว้เท่านั้น ถ้าสลับลำดับผิดชนิด compiler จะจับ error ให้ (เพราะ type ไม่ตรง) แต่ถ้าสลับลำดับแล้วชนิด
ข้อมูลบังเอิญตรงกัน (เช่น พารามิเตอร์ 2 ตัวเป็น `i32` ทั้งคู่) compiler จะไม่มีทางรู้ได้ว่าคุณตั้งใจสลับหรือไม่ — นี่คือ
ข้อจำกัดที่ต้องระมัดระวังเวลาฟังก์ชันมีพารามิเตอร์ชนิดเดียวกันติดกันหลายตัว (เช่น `fn create_point(x: f64, y: f64)`)

ฟังก์ชันยังสามารถรับพารามิเตอร์ที่เป็น compound type จาก Part 3 ได้ตามปกติ เช่น tuple หรือ array:

```rust
fn distance_from_origin(point: (f64, f64)) -> f64 {
    let (x, y) = point; // destructure tuple ออกมาเป็นตัวแปรย่อย (จะเรียนลึกใน Part 10)
    (x * x + y * y).sqrt()
}

fn sum_array(numbers: [i32; 5]) -> i32 {
    let mut total = 0;
    for n in numbers {
        total += n;
    }
    total
}

fn main() {
    let d = distance_from_origin((3.0, 4.0));
    println!("ระยะทาง: {d}"); // 5

    let s = sum_array([10, 20, 30, 40, 50]);
    println!("ผลรวม: {s}"); // 150
}
```

สังเกตว่า `sum_array` รับ `[i32; 5]` คือ array ที่มีขนาด**คงที่ 5 ตัวเป๊ะ** — ถ้าคุณส่ง array ขนาด 4 หรือ 6 เข้าไป
compiler จะปฏิเสธทันที เพราะขนาดของ array เป็นส่วนหนึ่งของชนิดข้อมูลใน Rust (ตามที่เรียนใน Part 3) ข้อจำกัดนี้จะหมดไป
เมื่อเราเรียนเรื่อง slice (`&[i32]`) ใน Part 8 ซึ่งรับ array ขนาดไหนก็ได้

### 4.3 ทำไม Rust ไม่มี default parameter value (และ function overloading)

ถ้าคุณเคยเขียน Python, JavaScript, C++, หรือ Kotlin คุณอาจคุ้นเคยกับการกำหนดค่า default ให้พารามิเตอร์ เช่น:

**Python:**
```python
def greet(name, greeting="Hello"):
    print(f"{greeting}, {name}!")

greet("สมชาย")            # ใช้ greeting="Hello" (default)
greet("สมชาย", "สวัสดี")   # override เป็น "สวัสดี"
```

**C++ (มี default parameter และ function overloading):**
```cpp
void greet(std::string name, std::string greeting = "Hello") {
    std::cout << greeting << ", " << name << "!\n";
}
```

**Rust ไม่มีทั้ง default parameter value และ function overloading เลย** — คุณไม่สามารถเขียน
`fn greet(name: &str, greeting: &str = "Hello")` และไม่สามารถประกาศ `fn area(side: f64)` กับ
`fn area(width: f64, height: f64)` (ชื่อเดียวกัน คนละ signature) ในที่เดียวกันได้ ถ้าลอง compiler จะฟ้อง:

```
error[E0428]: the name `area` is defined multiple times
```

**เหตุผลเชิงออกแบบ:**

1. **ความชัดเจนของ call site (จุดที่เรียกใช้)** — เมื่อคุณอ่านโค้ดที่เรียก `greet("สมชาย")` ใน Rust คุณรู้ทันทีว่ามันเรียก
   ฟังก์ชันไหน ด้วย argument ครบทุกตัวจริง ๆ ไม่ต้องเปิดไปดู definition เพื่อรู้ว่า "ค่า default คืออะไร" หรือ compiler
   เลือก overload ตัวไหนในกรณีที่ signature หลายตัวเข้าเงื่อนไขพร้อมกัน (ambiguous overload resolution เป็นปัญหาจริงที่
   เกิดขึ้นบ่อยใน C++ และทำให้ debug ยาก)
2. **ทีมออกแบบ Rust ให้ความสำคัญกับ "ความชัดเจน" มากกว่า "ความกระชับ"** เป็นหลักการทั่วไปของภาษา (ตรงข้ามกับ Ruby/Perl
   ที่เน้นความกระชับสุด ๆ) การไม่มี default parameter บังคับให้ผู้เรียกต้องเขียน argument ครบทุกตัวเสมอ ซึ่งแม้จะดูยาวกว่า
   เล็กน้อย แต่ทำให้โค้ด **grep และ refactor ได้ง่ายขึ้นมาก** เพราะทุกจุดที่เรียกฟังก์ชันจะเห็น argument ครบเสมอ

**วิธีแก้ปัญหาแบบ idiomatic Rust มี 3 แนวทางหลัก:**

**แนวทางที่ 1: ใช้ชื่อฟังก์ชันต่างกันสำหรับแต่ละกรณี (เลียนแบบ overloading)**

แทนที่จะพยายาม overload ชื่อเดียว ให้ตั้งชื่อฟังก์ชันที่สื่อความหมายต่างกันไปเลย:

```rust
fn square_area(side: f64) -> f64 {
    side * side
}

fn rectangle_area(width: f64, height: f64) -> f64 {
    width * height
}

fn main() {
    println!("พื้นที่สี่เหลี่ยมจัตุรัส: {}", square_area(4.0));
    println!("พื้นที่สี่เหลี่ยมผืนผ้า: {}", rectangle_area(4.0, 6.0));
}
```

วิธีนี้จริง ๆ แล้ว**ดีกว่า** overloading ในหลายกรณี เพราะชื่อฟังก์ชันสื่อความหมายชัดเจนกว่าการอนุมานจากจำนวน argument

**แนวทางที่ 2: ใช้ `Option<T>` แทนพารามิเตอร์ที่ "อาจจะไม่ส่งมา"**

`Option<T>` คือชนิดข้อมูลที่เก็บได้ทั้ง "มีค่า" (`Some(value)`) หรือ "ไม่มีค่า" (`None`) — เราจะเรียนเรื่องนี้เต็ม ๆ ใน
Part 11 แต่ตอนนี้ขอแนะนำแค่พอใช้งานได้:

```rust
fn greet(name: &str, greeting: Option<&str>) -> String {
    let g = match greeting {
        Some(custom) => custom,
        None => "Hello",
    };
    format!("{g}, {name}!")
}

fn main() {
    println!("{}", greet("สมชาย", None));         // ใช้ default
    println!("{}", greet("Alice", Some("สวัสดี"))); // override
}
```

ผลลัพธ์:

```
Hello, สมชาย!
สวัสดี, Alice!
```

จุดเด่นของวิธีนี้คือ **ผู้เรียกต้องเขียน `None` หรือ `Some(...)` อย่างชัดเจนเสมอ** ไม่มีทางลืมส่ง argument นี้ไปเฉย ๆ
(ต่างจาก default parameter ที่บางทีผู้เขียนโค้ดอาจ "ลืม" ไปว่ามันมี default value อยู่ ทำให้เข้าใจผิดว่าโปรแกรมทำงาน
อย่างหนึ่ง แต่จริง ๆ กำลังใช้ default ที่ไม่ได้ตั้งใจ) ข้อสังเกต: ในโค้ดข้างบนเราใช้ `match` แบบง่าย ๆ ไปแล้ว — นี่คือ
ตัวอย่างของ `match` ที่เราจะพูดถึงอย่างเป็นทางการในหัวข้อ 4.11 ของบทนี้ (และลงรายละเอียดเต็มใน Part 10)

**แนวทางที่ 3: Builder Pattern (สำหรับพารามิเตอร์ optional จำนวนมาก)**

เมื่อฟังก์ชัน (หรือการสร้างค่า) มีพารามิเตอร์ optional หลายตัวมาก ๆ (เช่น การตั้งค่า HTTP request ที่มี timeout, header,
retry count, ฯลฯ) การใช้ `Option<T>` หลายตัวจะทำให้ signature ยาวและอ่านยาก วิธีที่ idiomatic กว่าคือ **Builder Pattern**
ซึ่งใช้ `struct` และ method chaining โดยตั้งค่า default ไว้ในฟังก์ชัน `new()` แล้วให้ผู้ใช้ override เฉพาะค่าที่ต้องการผ่าน
method อื่น ๆ — เรายังไม่ได้เรียนเรื่อง `struct`/`impl` อย่างเป็นทางการ (จะเรียนใน Part 9) และ Builder Pattern แบบเต็ม
จะสอนอย่างละเอียดใน **Part 52** แต่เพื่อให้เห็นภาพคร่าว ๆ ว่ามันช่วยแก้ปัญหานี้ได้อย่างไร ลองดูตัวอย่างสั้น ๆ นี้:

```rust
struct RequestConfig {
    url: String,
    timeout_secs: u32,
    retries: u32,
}

impl RequestConfig {
    // ฟังก์ชันสร้างค่าเริ่มต้น (คล้าย constructor) — กำหนดค่า default ไว้ที่นี่
    fn new(url: &str) -> Self {
        RequestConfig {
            url: url.to_string(),
            timeout_secs: 30, // default
            retries: 3,       // default
        }
    }

    // method สำหรับ override timeout เฉพาะตอนที่ต้องการ
    fn timeout_secs(mut self, secs: u32) -> Self {
        self.timeout_secs = secs;
        self
    }
}

fn main() {
    let default_config = RequestConfig::new("https://example.com");
    let custom_config = RequestConfig::new("https://example.com").timeout_secs(5);

    println!("default timeout = {}", default_config.timeout_secs);
    println!("custom timeout = {}", custom_config.timeout_secs);
}
```

ผลลัพธ์:

```
default timeout = 30
custom timeout = 5
```

ยังไม่ต้องเข้าใจ `struct`, `impl`, หรือ `Self` แบบละเอียดตอนนี้ — ขอให้เห็นแค่แนวคิดว่า Rust แก้ปัญหา "พารามิเตอร์ optional
จำนวนมาก" ด้วยการแยกการสร้างค่าเริ่มต้น (`new()`) ออกจากการปรับแต่งค่าเพิ่มเติม (method อื่น ๆ ที่ต่อ chain กันได้)
แทนที่จะพยายามยัดทุกอย่างเข้าไปใน parameter list ของฟังก์ชันเดียว

### 4.4 Statements vs Expressions: แนวคิดที่สำคัญที่สุดของบทนี้

นี่คือหัวข้อที่สำคัญที่สุดในบทนี้ทั้งหมด และเป็นหนึ่งในแนวคิดที่ทำให้มือใหม่ Rust สับสนบ่อยที่สุด ถ้าคุณเข้าใจหัวข้อนี้
อย่างถ่องแท้ ทุกอย่างในบทนี้ (if-as-expression, loop-with-break-value, function return) จะเป็นเรื่องเดียวกันที่ต่อเนื่องกัน
ไปหมด

#### นิยาม

- **Statement (ข้อความสั่ง)** คือชุดคำสั่งที่**ทำงาน** (perform an action) แต่**ไม่คืนค่า**ใด ๆ ออกมา
- **Expression (นิพจน์)** คือชุดคำสั่งที่**ประเมินผลออกมาเป็นค่า** (evaluates to a value) เสมอ

หลายภาษาที่คุณรู้จัก (C, Java, Python แบบดั้งเดิม) แยกทั้งสองอย่างนี้ค่อนข้างชัดเจน เช่นใน C คุณเขียน
`if (x > 0) { y = 1; } else { y = 2; }` ไม่ได้เขียน `y = if (x > 0) { 1 } else { 2 };` ตรง ๆ (ต้องใช้ ternary operator
`y = (x > 0) ? 1 : 2;` แทน ซึ่งเป็นกลไกพิเศษแยกจาก `if` ธรรมดา)

**Rust เลือกให้ทุกอย่างเป็น expression มากที่สุดเท่าที่จะเป็นไปได้** ทั้ง `if/else`, `loop`, `match`, และแม้แต่ block
`{ }` เองก็เป็น expression ได้ทั้งหมด นี่คือสิ่งที่เรียกว่า **"expression-oriented language"** (ภาษาที่เน้น expression
เป็นหลัก) ซึ่งได้แรงบันดาลใจมาจากภาษาตระกูล ML/OCaml/Haskell (functional programming) ผสมกับ syntax ที่คุ้นเคยแบบ C

#### ตัวอย่างง่ายที่สุด: expression คือสิ่งที่มีค่า

```rust
fn main() {
    let a = 5;         // 5 คือ expression (literal ก็เป็น expression ที่ง่ายที่สุด)
    let b = a + 1;      // a + 1 คือ expression
    let c = { 10 };      // { 10 } คือ block expression — ค่าของ block คือ 10
    println!("a={a}, b={b}, c={c}");
}
```

ผลลัพธ์: `a=5, b=6, c=10`

สังเกตบรรทัด `let c = { 10 };` — นี่คือจุดสำคัญ: **block (`{ }`) ในภาษา Rust เป็น expression ที่มีค่าเป็นตัวมันเอง**
ค่าของ block คือค่าของ**บรรทัดสุดท้าย**ภายใน block นั้น **ถ้าบรรทัดสุดท้ายไม่มี semicolon ต่อท้าย**

ลองดูตัวอย่างที่ซับซ้อนขึ้นอีกนิด:

```rust
fn main() {
    let y = {
        let x = 3;
        let squared = x * x;
        squared + 1 // ไม่มี semicolon -> นี่คือค่าที่ block คืนกลับมา
    };
    println!("y = {y}"); // y = 10
}
```

ที่นี่ block `{ let x = 3; let squared = x * x; squared + 1 }` มี 3 บรรทัดข้างใน: สองบรรทัดแรก (`let x = 3;` และ
`let squared = x * x;`) เป็น **statement** (มี semicolon ปิดท้าย ไม่คืนค่าอะไรออกจาก block) ส่วนบรรทัดสุดท้าย
(`squared + 1`) **ไม่มี semicolon** จึงเป็น expression ที่กลายเป็นค่าของ block ทั้งก้อน — ผลคือ `y` ได้ค่า `10`
(เพราะ `x = 3`, `squared = 9`, `squared + 1 = 10`)

#### กฎสำคัญ: semicolon เปลี่ยน expression ให้กลายเป็น statement

นี่คือกฎที่ต้องจำให้ขึ้นใจ: **การเติม `;` ต่อท้าย expression จะเปลี่ยนมันให้กลายเป็น statement ที่คืนค่า `()` (unit)**
เสมอ ไม่ว่า expression ข้างหน้า semicolon จะมีค่าเป็นอะไรก็ตาม ค่านั้นจะถูก "ทิ้ง" (discard) ไป และค่าของ statement
ทั้งก้อนกลายเป็น `()`

```rust
fn main() {
    5 + 5;          // expression 5+5 มีค่า 10 แต่เติม ; ทำให้กลายเป็น statement ที่ทิ้งค่า 10 ไปเลย
    let x = 5 + 5;   // แบบนี้ค่อยเก็บค่าไว้ในตัวแปร x
    println!("{x}");
}
```

โค้ดบรรทัด `5 + 5;` ข้างบน compile ผ่านได้จริง (แต่ `cargo clippy` อาจเตือนว่าเป็น expression ที่ไม่มีผลข้างเคียง
(no side effect) ไม่มีประโยชน์อะไรที่จะเขียนไว้) มันแสดงให้เห็นว่า semicolon ไม่ใช่แค่ "ตัวคั่นบรรทัด" แบบใน Python
ที่ใช้ขึ้นบรรทัดใหม่แทนได้ แต่ semicolon ใน Rust มีความหมายทางไวยากรณ์ (syntactic meaning) จริง ๆ ที่ส่งผลต่อชนิดข้อมูล
และค่าที่ได้จากโค้ดส่วนนั้น

#### ค่าที่ฟังก์ชัน return: expression สุดท้าย หรือ `return` ที่ชัดเจน

จากความเข้าใจเรื่อง block-เป็น-expression ด้านบน ตอนนี้เราพร้อมเข้าใจกฎการ return ค่าของฟังก์ชันอย่างถ่องแท้แล้ว:
**ตัวฟังก์ชัน (function body) ก็คือ block `{ }` ก้อนหนึ่งนั่นเอง** ดังนั้นค่าที่ฟังก์ชัน return กลับไปก็คือ**ค่าของ block
นั้น** ซึ่งก็คือ**ค่าของบรรทัดสุดท้ายที่ไม่มี semicolon**

```rust
fn square(x: i32) -> i32 {
    x * x // นี่คือ expression สุดท้าย ไม่มี semicolon -> เป็นค่าที่ return กลับไป
}

fn main() {
    println!("{}", square(7)); // 49
}
```

นอกจากนี้ Rust ยังมี keyword `return` แบบภาษาอื่นให้ใช้ได้ (สำหรับกรณี return ก่อนถึงท้ายฟังก์ชัน เช่น early return
เมื่อเจอเงื่อนไขบางอย่าง):

```rust
fn classify_number(n: i32) -> &'static str {
    if n == 0 {
        return "ศูนย์"; // early return — ออกจากฟังก์ชันทันที ไม่ต้องรันโค้ดที่เหลือ
    }
    if n > 0 {
        return "บวก";
    }
    "ลบ" // ถ้าไม่เข้าเงื่อนไขไหนเลย ใช้ expression สุดท้ายเป็นค่า return
}

fn main() {
    println!("{}", classify_number(0));  // ศูนย์
    println!("{}", classify_number(5));  // บวก
    println!("{}", classify_number(-3)); // ลบ
}
```

> **หมายเหตุเรื่อง `&'static str`:** สังเกตว่า return type ที่นี่คือ `&'static str` ไม่ใช่ `&str` เฉย ๆ ส่วน
> `'static` คือ "lifetime annotation" ซึ่งเป็นแนวคิดที่เราจะเรียนอย่างละเอียดใน **Part 20** ตอนนี้ขอให้เข้าใจแค่ว่า
> `'static` หมายถึง "ค่านี้อยู่คงทนตลอดการรันโปรแกรม" ซึ่งเป็นจริงสำหรับ string literal (ข้อความที่เขียนตรง ๆ ในโค้ด
> เช่น `"บวก"`) เสมอ เพราะข้อความเหล่านี้ถูกฝังอยู่ใน binary ตั้งแต่ compile time ไม่ได้ถูกสร้างขึ้นมาใหม่ตอนรันโปรแกรม
> จึงไม่มีทาง "หมดอายุ" ก่อนโปรแกรมจบ

**การใช้ `return` ไม่ผิด** แต่สไตล์ที่ idiomatic ใน Rust นิยมใช้ expression สุดท้ายมากกว่าการเขียน `return` ทุกครั้ง
โดยจะใช้ `return` เฉพาะกรณี early return ที่ต้องออกจากฟังก์ชันกลางทางจริง ๆ เท่านั้น เหตุผลคือโค้ดที่ใช้ expression
ล้วน ๆ จะอ่านเป็น "การคำนวณค่าที่ไหลต่อกัน" (data flow) ได้ลื่นกว่า ไม่ต้องคอยไล่หา `return` หลายจุดกระจายอยู่ทั่วฟังก์ชัน

#### กับดักคลาสสิกของมือใหม่: เผลอเติม semicolon ท้าย expression ที่ควร return

นี่คือ error ที่มือใหม่ Rust เกือบทุกคนต้องเจอมาแล้วอย่างน้อยครั้งหนึ่ง ลองดูโค้ดนี้ (ที่ดูเผิน ๆ เหมือนถูกต้อง เพราะ
"ทุกบรรทัดควรมี semicolon" ใช่ไหม?):

```rust
fn plus_one(x: i32) -> i32 {
    x + 1; // ผิด! เผลอเติม semicolon
}
```

โค้ดนี้ **compile ไม่ผ่าน** เพราะการเติม `;` เปลี่ยน `x + 1` จาก expression (ที่มีค่าเป็น `i32`) ให้กลายเป็น statement
(ที่มีค่าเป็น `()`) ดังนั้นตัวฟังก์ชันจึง "implicitly return" ค่า `()` แทนที่จะ return `i32` ตามที่ signature สัญญาไว้
compiler จะฟ้อง error ประมาณนี้:

```
error[E0308]: mismatched types
 --> src/main.rs:3:1
  |
1 | fn plus_one(x: i32) -> i32 {
  |                        --- expected `i32` because of return type
2 |     x + 1;
  |          - help: consider removing this semicolon to return this value
3 | }
  | ^ expected `i32`, found `()`

For more information about this error, try `rustc --explain E0308`.
```

สังเกตว่า compiler **ฉลาดพอที่จะแนะนำวิธีแก้ให้เลย** ("help: consider removing this semicolon to return this value")
นี่คือตัวอย่างที่ดีของ error message ของ Rust ที่ไม่ได้แค่บอกว่า "ผิด" แต่บอกด้วยว่า "ทำไมถึงผิด" และ "แก้ยังไง"
ซึ่งเป็นจุดแข็งของ Rust compiler ที่ได้รับการยกย่องอย่างกว้างขวางในหมู่นักพัฒนา

**วิธีแก้คือลบ semicolon ออก:**

```rust
fn plus_one(x: i32) -> i32 {
    x + 1 // ถูกต้อง — ไม่มี semicolon, เป็น expression ที่ return ค่า i32
}

fn main() {
    println!("{}", plus_one(41)); // 42
}
```

**วิธีจำง่าย ๆ:** ให้นึกภาพว่า semicolon คือ "จุด" ที่บอกว่า "ค่าที่ได้จากตรงนี้ ไม่สำคัญแล้ว ทิ้งไปได้เลย ไปทำอย่างต่อไป"
ถ้าบรรทัดนั้นเป็นบรรทัดสุดท้ายของฟังก์ชันที่ต้อง return ค่า การเติม `;` จึงเท่ากับบอก compiler ว่า "ค่านี้ไม่สำคัญ"
ซึ่งขัดกับ signature ที่บอกว่าต้อง return `i32` ทันที

#### ตารางสรุป Statement vs Expression

| | Statement | Expression |
|---|---|---|
| คืนค่าหรือไม่ | ไม่คืนค่า (คืน `()`) | คืนค่าเสมอ |
| ตัวอย่าง | `let x = 5;`, `x = 6;`, `println!("hi");` | `5 + 5`, `x * 2`, `{ 10 }`, `if c { 1 } else { 2 }` |
| ลงท้ายด้วย `;` | ใช่ (บังคับ) | ถ้ามี `;` จะกลายเป็น statement |
| ใช้เป็นค่าทางขวาของ `let` ได้ไหม | ไม่ได้ | ได้ |
| ใช้เป็นค่า return ของฟังก์ชันได้ไหม | ไม่ได้ (จะได้ `()` แทน) | ได้ |

จำไว้ว่า: **`let x = 5;` ทั้งบรรทัดคือ statement** (เพราะมันไม่คืนค่าอะไรออกมาให้ใครใช้ต่อ) แต่ `5` ที่อยู่ข้างขวาของ `=`
คือ expression นี่คือจุดที่คนสับสนบ่อย: statement ก็**ประกอบด้วย**expression ข้างในได้ แต่ตัว statement เองไม่คืนค่า

### 4.5 `if`/`else if`/`else` ในฐานะ Expression

เมื่อเข้าใจเรื่อง statement/expression แล้ว ตอนนี้เรามาดูการประยุกต์ใช้ที่ทรงพลังที่สุดอย่างหนึ่ง: **`if` ใน Rust
เป็น expression** ไม่ใช่แค่ statement ควบคุม flow แบบ C/Java/JavaScript

#### if แบบธรรมดา (ใช้เป็น statement) — คุ้นเคยจากภาษาอื่น

```rust
fn main() {
    let temperature = 35;

    if temperature > 30 {
        println!("อากาศร้อนมาก!");
    } else if temperature > 20 {
        println!("อากาศกำลังดี");
    } else {
        println!("อากาศเย็น");
    }
}
```

โค้ดนี้ใช้ `if/else if/else` แบบเดียวกับที่คุณคุ้นเคยจากทุกภาษา — เรียก `println!` ต่างกันไปตามเงื่อนไข ไม่มีอะไรใหม่

#### if แบบ expression — จุดที่ Rust แตกต่าง

แต่ Rust ไปได้ไกลกว่านั้น เพราะ `if { ... } else { ... }` ทั้งก้อนเป็น expression ที่**มีค่า**ได้ จึงเขียนแบบนี้ได้:

```rust
fn main() {
    let n = 7;
    let parity = if n % 2 == 0 { "คู่" } else { "คี่" };
    println!("{n} เป็นเลข{parity}");
}
```

ผลลัพธ์: `7 เป็นเลขคี่`

สังเกตว่า `if n % 2 == 0 { "คู่" } else { "คี่" }` ทั้งก้อนถูกใช้เป็นค่าทางขวาของ `let parity = ...;` ตรง ๆ โดยไม่ต้องใช้
ตัวแปรกลาง (temporary variable) แบบที่คุณต้องทำใน C:

**C (ไม่มี if-as-expression แบบเต็ม ต้องใช้ ternary หรือตัวแปรกลาง):**
```c
int n = 7;
char *parity;
if (n % 2 == 0) {
    parity = "even";
} else {
    parity = "odd";
}
```

**Java (คล้าย C แต่มี ternary operator ช่วยกรณีง่าย ๆ):**
```java
int n = 7;
String parity = (n % 2 == 0) ? "even" : "odd";
```

**Rust (ใช้ if ตรง ๆ ได้เลย ไม่ต้องมี operator พิเศษแยก):**
```rust
let n = 7;
let parity = if n % 2 == 0 { "even" } else { "odd" };
```

จุดที่น่าสนใจคือ Rust **ไม่มี ternary operator** (`? :`) เลย เพราะไม่จำเป็น — `if/else` ที่เป็น expression ทำหน้าที่
แทนได้สมบูรณ์แบบอยู่แล้ว การมี syntax สองแบบที่ทำงานเหมือนกัน (`if/else` และ `? :`) จะเพิ่มความซับซ้อนให้ภาษาโดยไม่ได้
ประโยชน์อะไรเพิ่ม ทีมออกแบบ Rust จึงเลือกมีแบบเดียวที่ใช้ได้ทั้งสองสถานการณ์

#### กฎสำคัญ: ทุก branch ต้องมีชนิดข้อมูลตรงกัน

เพราะ `if/else` เป็น expression ที่ต้องมี "ค่า" และ "ชนิดข้อมูล" ที่แน่นอนหนึ่งอย่างเสมอ (Rust เป็น statically typed
ภาษา — compiler ต้องรู้ชนิดข้อมูลของทุก expression ตั้งแต่ compile time) **ทุก branch (`if`, `else if`, `else`) ต้อง
คืนค่าที่เป็นชนิดข้อมูลเดียวกันทั้งหมด** ไม่อย่างนั้น compiler จะไม่รู้ว่าจะกำหนดชนิดข้อมูลให้กับตัวแปรผลลัพธ์เป็นอะไร

ลองดูตัวอย่างที่ผิด:

```rust
fn main() {
    let n = 7;
    let result = if n > 0 {
        "positive" // &str
    } else {
        0 // ผิด! ชนิดไม่ตรงกับ branch แรก (integer แทน &str)
    };
    println!("{result}");
}
```

Error ที่ได้:

```
error[E0308]: mismatched types
 --> src/main.rs:6:9
  |
3 |     let result = if n > 0 {
  |                  -- expected because of this
4 |         "positive"
  |         ---------- expected because of this value
5 |     } else {
6 |         0
  |         ^ expected `&str`, found integer

For more information about this error, try `rustc --explain E0308`.
```

Compiler เห็น branch แรก (`if`) คืนค่า `&str` ก่อน จึง "คาดหวัง" (expect) ว่า branch อื่น ๆ ต้องคืนค่า `&str` เหมือนกัน
เมื่อ branch `else` คืนค่าตัวเลขซึ่งเป็นชนิด integer แทน มันจึง mismatch

**วิธีแก้:** ทำให้ทุก branch คืนค่าชนิดเดียวกัน เช่นแปลงเป็น `&str` ทั้งหมด หรือแปลงเป็นตัวเลขทั้งหมด:

```rust
fn main() {
    let n = 7;
    let result = if n > 0 { "positive" } else { "non-positive" };
    println!("{result}"); // positive
}
```

**เหตุผลเชิงลึกที่ Rust บังคับกฎนี้:** ในภาษา dynamically typed อย่าง Python หรือ JavaScript, ตัวแปรสามารถเปลี่ยนชนิด
ข้อมูลได้ตามการรันจริง (`result` อาจเป็น string ในรอบหนึ่ง แล้วเป็นตัวเลขในอีกรอบ) แต่ใน Rust ตัวแปรทุกตัวมีชนิดข้อมูล
**คงที่ตลอดชีวิตของตัวแปร** ที่กำหนดตั้งแต่ compile time (ระบบ memory layout ของ Rust ต้องรู้ล่วงหน้าว่าตัวแปรนี้กิน
พื้นที่ memory เท่าไหร่ ซึ่งขึ้นกับชนิดข้อมูล) การอนุญาตให้ `if` คืนค่าคนละชนิดกันในแต่ละ branch จะทำให้ compiler ไม่มี
ทางรู้ได้เลยว่าต้องจอง memory ไว้เท่าไหร่ให้กับตัวแปร `result` — นี่ไม่ใช่ข้อจำกัดที่ไร้เหตุผล แต่เป็นผลลัพธ์ตรงไปตรงมา
จากการที่ Rust เป็นภาษาที่ไม่มี garbage collector และต้องรู้ memory layout ทุกอย่างล่วงหน้า

ข้อสังเกตเพิ่มเติม: **`if` ที่ไม่มี `else` ก็เป็น expression ได้** แต่ค่าของมันจะเป็น `()` เท่านั้น (เพราะถ้าเงื่อนไข
เป็น false จะไม่มี branch ให้รันเลย ดังนั้นจึงคืนค่าอะไรไม่ได้นอกจาก unit) ดังนั้นถ้าคุณเขียน:

```rust
fn main() {
    let n = 7;
    let x = if n > 0 { 42 }; // ผิด! ไม่มี else แต่พยายาม return ค่า i32
    println!("{x}");
}
```

จะได้ error `if may be missing an else clause` เพราะ branch `if` คืนค่า `i32` แต่ branch ที่ "ไม่เข้าเงื่อนไข" (ไม่มี
`else`) จะคืนค่า `()` เสมอ ทำให้สองกรณีนี้มีชนิดข้อมูลไม่ตรงกัน — วิธีแก้คือเติม `else` ให้ครบ หรือถ้าตั้งใจใช้ `if`
แบบไม่คืนค่าจริง ๆ (แค่ทำ side effect เช่น print) ก็ไม่ต้องเก็บผลลัพธ์ไว้ในตัวแปรตั้งแต่แรก

### 4.6 `loop`: การวนซ้ำแบบไม่มีเงื่อนไข และความสามารถพิเศษ `break` พร้อมค่า

Rust มี loop 3 แบบหลัก: `loop`, `while`, และ `for` เราจะเริ่มจาก `loop` ซึ่งเป็นแบบที่ง่ายที่สุดในเชิงไวยากรณ์
แต่มีความสามารถพิเศษที่หาไม่ได้ในภาษาอื่นหลายภาษา

`loop` คือการวนซ้ำแบบ **ไม่มีเงื่อนไขหยุดในตัว** — มันจะวนไปเรื่อย ๆ จนกว่าจะเจอ `break` (หรือโปรแกรมถูกปิดไปเลย)

```rust
fn main() {
    let mut count = 0;

    loop {
        count += 1;
        println!("รอบที่ {count}");

        if count == 3 {
            break; // หยุดวน
        }
    }

    println!("จบการวนแล้ว");
}
```

ผลลัพธ์:

```
รอบที่ 1
รอบที่ 2
รอบที่ 3
จบการวนแล้ว
```

ถึงตรงนี้ `loop` ดูเหมือน `while (true)` ใน C/Java ธรรมดา — แต่ Rust มีความสามารถพิเศษที่ทำให้ `loop` **เป็น expression
ที่คืนค่าได้**: **`break` สามารถส่งค่ากลับออกจาก loop ได้** โดยเขียน `break ค่า;`

```rust
fn main() {
    let mut counter = 0;

    let result = loop {
        counter += 1;

        if counter == 10 {
            break counter * 2; // ออกจาก loop พร้อมส่งค่า counter*2 กลับไป
        }
    };

    println!("result = {result}"); // result = 20
}
```

**นี่คือฟีเจอร์ที่หาได้ยากมากในภาษาอื่น** — ใน C, Java, Python, JavaScript ไม่มีภาษาไหนที่ `while`/`for`/loop ธรรมดา
เป็น expression ที่คืนค่าออกมาได้แบบนี้ ถ้าคุณต้องทำสิ่งเดียวกันใน Java คุณต้องประกาศตัวแปรไว้ก่อนนอก loop แล้ว assign
ค่าให้มันข้างในทีหลัง:

**Java (ต้องประกาศตัวแปรไว้ก่อนนอก loop):**
```java
int counter = 0;
int result = 0; // ต้อง initialize ไว้ก่อน แม้จะยังไม่รู้ค่าจริง
while (true) {
    counter++;
    if (counter == 10) {
        result = counter * 2;
        break;
    }
}
```

**Rust (loop เป็น expression ตรง ๆ ไม่ต้องมีตัวแปรกลางที่ mutable):**
```rust
let mut counter = 0;
let result = loop {
    counter += 1;
    if counter == 10 {
        break counter * 2;
    }
};
```

สังเกตว่าโค้ด Rust ไม่ต้องมี "ตัวแปรกลางที่ mutable รอ assign" (`int result = 0;` ใน Java ที่ต้องตั้งค่าเริ่มต้นทั้งที่
ยังไม่รู้ค่าจริง) — `result` ใน Rust ถูกกำหนดค่าเพียงครั้งเดียวตอนที่ loop จบ (ไม่จำเป็นต้องเป็น `mut` เลยด้วยซ้ำ เพราะ
มัน bind ค่าแค่ครั้งเดียว) นี่คือตัวอย่างที่ชัดเจนของ **expression-oriented thinking** — การคิดแบบ "คำนวณค่าออกมา"
มากกว่า "ค่อย ๆ กลายพันธุ์ (mutate) ตัวแปรไปเรื่อย ๆ"

**เหตุผลเชิงลึกที่ทำไม `loop` (แต่ไม่ใช่ `while`/`for`) คืนค่าได้:** เดี๋ยวเราจะเห็นในหัวข้อถัดไปว่า `while` และ `for`
**ไม่สามารถ** `break` พร้อมค่าได้ (เป็นข้อจำกัดที่ตั้งใจ ไม่ใช่ bug) เหตุผลคือ compiler ต้องรู้ชนิดข้อมูลของ expression
`loop`/`while`/`for` เสมอ — สำหรับ `loop` ธรรมดา compiler รู้ว่า loop นี้จะจบได้ทางเดียวคือผ่าน `break` เท่านั้น (ไม่มี
เงื่อนไขจบในตัวของมันเอง) ดังนั้นถ้าคุณ `break` พร้อมค่า ชนิดของค่านั้นก็คือชนิดของ loop expression ทั้งก้อนได้อย่างไม่
กำกวม แต่ `while`/`for` มีเงื่อนไขจบในตัว (เมื่อเงื่อนไข false หรือ iterator หมด) ซึ่งเป็น "การจบแบบไม่มีค่า" (จบแบบ
`()`) การอนุญาตให้ `break value` ใน `while`/`for` จะทำให้เกิดความกำกวมว่า loop จบแบบมีค่าหรือไม่มีค่ากันแน่ — เราจะเห็น
error จริงของกรณีนี้ในหัวข้อ "กับดักที่พบบ่อย" ท้ายบท

### 4.7 `while`: วนซ้ำตามเงื่อนไข

`while` คือ loop แบบมีเงื่อนไขตรวจสอบก่อนแต่ละรอบ ทำงานเหมือนกับที่คุณคุ้นเคยจากภาษาอื่นเกือบทุกภาษา — วนซ้ำตราบใดที่
เงื่อนไขเป็น `true` และหยุดทันทีที่เงื่อนไขเป็น `false`

```rust
fn main() {
    let mut n = 5;

    while n != 0 {
        println!("{n}!");
        n -= 1;
    }

    println!("นับถอยหลังจบแล้ว!");
}
```

ผลลัพธ์:

```
5!
4!
3!
2!
1!
นับถอยหลังจบแล้ว!
```

ข้อสังเกตสำคัญ: **`while` ไม่ต้องมี parentheses ล้อมเงื่อนไข** (`while n != 0` ไม่ใช่ `while (n != 0)`) ต่างจาก C/Java
ที่บังคับต้องมี `()` — Rust ไม่บังคับ parentheses รอบเงื่อนไขของ `if`/`while` เลย (แต่ `{}` ล้อมตัว body บังคับเสมอ
ไม่มีข้อยกเว้นแบบ C ที่บางทีละ `{}` ได้ถ้ามีแค่ 1 บรรทัด — การบังคับ `{}` เสมอช่วยป้องกันบั๊กชนิดหนึ่งที่เคยเกิดขึ้นจริง
ในโค้ด C/C++ จำนวนมาก เรียกว่า **"dangling else" หรือ "Apple's goto fail bug"** ที่เกิดจากการลืมใส่ `{}` แล้วมีบรรทัด
ถัดมาที่ดู indent ถูกแต่ compiler ไม่ตีความว่าอยู่ใน block เดียวกัน)

`while` ก็เป็น expression ได้เหมือนกับทุกอย่างใน Rust แต่ **ค่าของมันคือ `()` เสมอ** เพราะเงื่อนไขที่ทำให้ loop จบ
(เงื่อนไขเป็น false) ไม่ได้มาพร้อมค่าอะไรให้คืน:

```rust
fn main() {
    let mut n = 3;
    let result = while n > 0 { // result มีชนิดเป็น () (unit)
        n -= 1;
    };
    println!("{result:?}"); // ()
}
```

โค้ดนี้ compile ผ่าน (แม้จะไม่มีประโยชน์อะไรที่จะเก็บ `()` ไว้ในตัวแปร — ในทางปฏิบัติจริงเราไม่เขียนแบบนี้ แสดงไว้เพื่อ
ให้เห็นว่า `while` ก็เป็น expression เหมือนกัน เพียงแต่ชนิดของมันคือ unit type เสมอ ไม่มีทางเป็นอย่างอื่น)

### 4.8 `for` และ Range: วิธีวนซ้ำที่ปลอดภัยที่สุด

`for` ใน Rust แตกต่างจาก C/Java/JavaScript อย่างมาก — มันไม่ใช่ "index-based for loop" แบบ `for (int i = 0; i < n; i++)`
แต่เป็น **"for-each"** ที่วนซ้ำผ่านค่าจาก **iterator** (แนวคิดที่จะเรียนเต็ม ๆ ใน Part 25-26) เสมอ

#### วนซ้ำผ่าน Range

**Range** คือชนิดข้อมูลที่แทนช่วงของตัวเลข เขียนด้วย `..` (exclusive — ไม่รวมค่าสุดท้าย) หรือ `..=` (inclusive — รวมค่า
สุดท้าย):

```rust
fn main() {
    print!("0..5   : ");
    for i in 0..5 {
        print!("{i} ");
    }
    println!();

    print!("0..=5  : ");
    for i in 0..=5 {
        print!("{i} ");
    }
    println!();
}
```

ผลลัพธ์:

```
0..5   : 0 1 2 3 4
0..=5  : 0 1 2 3 4 5
```

- `0..5` คือช่วง **exclusive** (ไม่รวมจุดสิ้นสุด) วนได้ค่า 0, 1, 2, 3, 4 (5 ตัว)
- `0..=5` คือช่วง **inclusive** (รวมจุดสิ้นสุดด้วย เครื่องหมาย `=` หลัง `..`) วนได้ค่า 0, 1, 2, 3, 4, 5 (6 ตัว)

การมี range ทั้งสองแบบให้เลือกช่วยลด "off-by-one error" (บั๊กคลาดเคลื่อนไปหนึ่งค่า) ที่เป็นปัญหาคลาสสิกในภาษาที่ใช้
index-based for loop เพราะคุณต้องเลือกเองอย่างชัดเจนว่าต้องการรวมค่าสุดท้ายหรือไม่ ไม่ต้องมานั่งคำนวณ `i <= n` หรือ
`i < n + 1` เอง

**เปรียบเทียบกับ C แบบ index-based for loop:**

```c
// C: ต้องเขียน 3 ส่วนเอง (init, condition, increment) — เสี่ยง off-by-one ถ้าเขียน < ผิดเป็น <=
for (int i = 0; i < 5; i++) {
    printf("%d ", i);
}
```

```rust
// Rust: บอกช่วงตรง ๆ ไม่ต้องจัดการ index เอง ไม่มีทางเขียน i++ ผิดพลาด เพราะไม่มี i++ ให้เขียน
for i in 0..5 {
    print!("{i} ");
}
```

ข้อดีเชิงความปลอดภัยที่สำคัญ: ใน C คุณสามารถเขียน `for (int i = 0; i <= 5; i++) { arr[i] = 0; }` กับ array ขนาด 5
โดยไม่ได้ตั้งใจ (เผลอใช้ `<=` ทำให้ index วิ่งไปถึง 5 ซึ่งเกินขนาด array) ทำให้เกิด **buffer overflow** ซึ่งเป็นสาเหตุ
ของช่องโหว่ความปลอดภัยจำนวนมากในประวัติศาสตร์ของซอฟต์แวร์ — ใน Rust ถ้าคุณเผลอ index เกินขนาด array/slice จริง ๆ
(ไม่ผ่าน range/iterator) โปรแกรมจะ **panic ทันทีตอนรันจริง** (runtime bounds checking) ไม่ปล่อยให้อ่าน/เขียน memory
นอกขอบเขตแบบ C — และเมื่อใช้ `for ... in range` วนผ่าน iterator แทน index-based loop ปัญหานี้จะยิ่งลดโอกาสเกิดลงไปอีก
เพราะไม่มี index ให้คำนวณผิดเลยตั้งแต่แรก

#### วนซ้ำผ่าน Array/Collection (Teaser — รายละเอียดเต็มใน Part 25-26)

`for` ยังใช้วนซ้ำผ่าน array และ collection อื่น ๆ ได้โดยตรง โดยไม่ต้องยุ่งกับ index เลย:

```rust
fn main() {
    let scores = [80, 92, 77, 65, 99];

    for score in scores {
        println!("คะแนน: {score}");
    }
}
```

ผลลัพธ์:

```
คะแนน: 80
คะแนน: 92
คะแนน: 77
คะแนน: 65
คะแนน: 99
```

สิ่งที่เกิดขึ้นเบื้องหลังคือ `for` แปลง `scores` ให้กลายเป็น **iterator** อัตโนมัติ (ผ่าน trait ชื่อ `IntoIterator`)
แล้ววนดึงค่าออกมาทีละตัวจนกว่าจะหมด — เรื่องนี้เกี่ยวพันกับแนวคิด **ownership และ borrowing** ที่เราจะเรียนอย่างเป็น
ทางการใน Part 6-7 ด้วย (เช่น การวนแบบ `for score in scores` กับ `for score in &scores` ให้ผลต่างกันเมื่อ `scores` เป็น
ชนิดข้อมูลที่ซับซ้อนกว่าตัวเลข) แต่สำหรับตัวเลขแบบนี้ (ที่เป็นชนิด `Copy` ตามที่เรียนใน Part 3) ทั้งสองแบบทำงานได้
เหมือนกันโดยไม่มีปัญหาเรื่อง ownership เข้ามาเกี่ยวข้อง ตอนนี้ขอให้จำไว้แค่ว่า **`for` คือวิธีวนซ้ำผ่าน collection ที่
ปลอดภัยและอ่านง่ายที่สุด** — เราจะเจาะลึกกลไกเบื้องหลังทั้งหมด (รวมถึง `.iter()`, `.into_iter()`, adapter อย่าง `.map()`,
`.filter()`) ใน Part 25-26

`for` เป็น expression เหมือน `while` — ค่าของมันคือ `()` เสมอ และ **ไม่รองรับ `break` พร้อมค่า** เช่นเดียวกับ `while`
(จะอธิบายเหตุผลและ error จริงในหัวข้อกับดักท้ายบท)

### 4.9 Loop Labels: ควบคุม Nested Loop อย่างแม่นยำ

เมื่อมี loop ซ้อนกันหลายชั้น (nested loop) บางครั้งเราต้องการ `break` หรือ `continue` loop **ชั้นนอก** จากข้างใน
loop ชั้นในสุด — ปัญหานี้พบได้บ่อยเวลาค้นหาค่าใน 2D grid, ตาราง, หรือ matrix

ถ้าไม่มี loop label เราจะทำได้แค่ `break` ออกจาก loop ที่ใกล้ที่สุด (loop ชั้นในสุด) เท่านั้น — หลายภาษา (เช่น Python,
C, JavaScript ธรรมดา) ไม่มีกลไกในตัวภาษาให้ break ออกจาก loop ชั้นนอกได้เลย ต้องใช้ตัวแปร flag ช่วยหรือแยกเป็นฟังก์ชัน
แล้ว `return` แทน (Java และบางภาษามี labeled break แบบเดียวกับ Rust แต่ไม่ใช่ทุกภาษา)

**Rust แก้ปัญหานี้ด้วย loop label** — เขียนโดยตั้งชื่อ label ขึ้นต้นด้วย `'` (เหมือน lifetime แต่ใช้คนละบริบท) ตามด้วย
`:` ก่อนหน้า loop:

```rust
fn main() {
    let mut found = None;

    'outer: for x in 0..5 {
        for y in 0..5 {
            if x * y == 6 {
                found = Some((x, y));
                break 'outer; // ออกจาก loop ชั้นนอก (x) ไม่ใช่แค่ loop ชั้นใน (y)
            }
        }
    }

    println!("{found:?}"); // Some((2, 3))
}
```

**อธิบาย:** โค้ดนี้ค้นหาคู่ตัวเลข `(x, y)` ที่คูณกันได้ 6 โดยวน `x` จาก 0-4 และ `y` จาก 0-4 ในแต่ละค่า `x` เมื่อเจอคู่
แรกที่คูณกันได้ 6 (ในที่นี้คือ `x=2, y=3` เพราะ 2×3=6) เราต้องการหยุด**ทั้งสอง loop ทันที** ไม่ใช่แค่หยุด loop ของ `y`
แล้ววน `x` ต่อไปเรื่อย ๆ — ถ้าเขียน `break;` ธรรมดา (ไม่มี label) มันจะออกจาก loop ของ `y` เท่านั้น แล้ว loop ของ `x`
จะวนต่อไปจนครบ 0-4 ซึ่งไม่ใช่พฤติกรรมที่เราต้องการ

ลองเปรียบเทียบกับกรณีที่ไม่มี label (แสดงพฤติกรรมที่ผิดพลาด):

```rust
fn main() {
    let mut checks = 0;

    for x in 0..5 {
        for y in 0..5 {
            checks += 1;
            if x * y == 6 {
                break; // ออกจาก loop y เท่านั้น! loop x จะวนต่อไปเรื่อย ๆ
            }
        }
    }

    println!("ตรวจสอบไปทั้งหมด {checks} รอบ"); // จะมากกว่ากรณีที่ใช้ label (เพราะ x ยังวนต่อจนครบ)
}
```

**Loop label ยังใช้กับ `continue` ได้ด้วย** เพื่อ "ข้ามไปทำ loop ชั้นนอกรอบต่อไป" (ไม่ใช่แค่ loop ชั้นในสุด):

```rust
fn main() {
    let mut count = 0;

    'counting_up: loop {
        let mut remaining = 10;

        loop {
            if remaining == 9 {
                break; // ออกจาก loop ชั้นใน กลับไปที่ loop 'counting_up
            }
            if count == 2 {
                break 'counting_up; // ออกจาก loop ชั้นนอกทันที
            }
            remaining -= 1;
        }

        count += 1;
    }

    println!("count สุดท้าย = {count}"); // count สุดท้าย = 2
}
```

**Label ตั้งชื่อได้ตามใจ** (ในตัวอย่างนี้ใช้ `'outer`, `'counting_up`) เพียงต้องขึ้นต้นด้วย `'` เสมอ — Rust เลือกใช้
สัญลักษณ์ `'` เดียวกับ lifetime (Part 20) เพราะทั้งสองอย่างเป็น "ชื่อที่ผูกกับ scope" ในทางแนวคิด แต่ context การใช้งาน
ต่างกันชัดเจน (loop label ใช้กับ `break`/`continue` เท่านั้น ไม่เกี่ยวกับ reference lifetime โดยตรง) เมื่อคุณเรียน
lifetime เต็ม ๆ ใน Part 20 จะเข้าใจว่าทำไม Rust เลือกใช้สัญลักษณ์เดียวกัน

### 4.10 `match` เบื้องต้น: ทางเลือกที่ปลอดภัยกว่า if/else (Teaser)

ก่อนปิดท้ายบท ขอแนะนำ `match` แบบสั้น ๆ พอให้คุณคุ้นหน้าคุ้นตาและใช้งานในกรณีง่าย ๆ ได้ — **`match` คือหนึ่งใน
ฟีเจอร์ที่ทรงพลังที่สุดของ Rust และมีรายละเอียดเยอะมาก** (pattern matching แบบเต็มรูปแบบ, match guard, binding
with `@`, matching บน enum ที่ซับซ้อน ฯลฯ) ซึ่งเราจะเรียนอย่างละเอียดครบถ้วนใน **Part 10** บทนี้ขอแค่ให้เห็นภาพว่า
`match` เอาไปใช้แทน `if/else` ที่มีหลายเงื่อนไขได้อย่างไรในกรณีพื้นฐานที่สุด

```rust
fn main() {
    let n = 3;

    match n {
        1 => println!("หนึ่ง"),
        2 => println!("สอง"),
        3 => println!("สาม"),
        _ => println!("อื่น ๆ"), // _ คือ "wildcard" หมายถึง "ค่าอื่นใดที่ไม่ตรงกับด้านบน"
    }
}
```

ผลลัพธ์: `สาม`

`match` เทียบเงื่อนไขจากบนลงล่าง เจอ pattern ไหนตรงกับค่าของ `n` ก่อน ก็จะรันโค้ดฝั่งขวาของ `=>` ทันทีแล้วออกจาก
`match` — สังเกตว่าเราต้องมี `_` (wildcard) เป็นเงื่อนไขสุดท้ายเสมอ เพราะ **`match` ใน Rust บังคับให้ครอบคลุมทุกกรณี
ที่เป็นไปได้ (exhaustive)** ถ้าคุณลบ `_ => ...` ออกไป (สมมติว่า `n` เป็นชนิด `i32` ที่มีค่าได้เป็นล้าน ๆ แบบ) compiler
จะฟ้อง error ทันทีว่า pattern ไม่ครอบคลุมครบ — นี่คือจุดที่ `match` "ปลอดภัยกว่า" `if/else` เพราะ `if/else` ธรรมดา
ไม่มีกลไกบังคับให้คุณคิดถึง "กรณีที่เหลือ" แบบนี้ (ลืมเขียน `else` ก็ไม่ error อะไร โปรแกรมแค่ไม่ทำอะไรเฉย ๆ ในกรณีนั้น
ซึ่งอาจกลายเป็นบั๊กที่ตรวจจับไม่ได้จนกว่าจะรันจริง)

`match` ก็เป็น expression เช่นเดียวกับ `if/else` — ใช้เป็นค่าทางขวาของ `let` ได้เลย:

```rust
fn main() {
    let is_weekend = true;

    let day_type = match is_weekend {
        true => "วันหยุด",
        false => "วันทำงาน",
    };

    println!("วันนี้เป็น{day_type}");
}
```

ผลลัพธ์: `วันนี้เป็นวันหยุด`

สำหรับ `bool` แบบนี้ `match` ต้องครอบคลุมทั้ง `true` และ `false` ครบทั้งสองค่า (ซึ่งครบตามธรรมชาติเพราะ `bool` มีแค่
สองค่าเท่านั้น ไม่ต้องมี `_` เพิ่ม) นี่เป็นตัวอย่างที่ดีว่า compiler รู้ "domain" ของแต่ละชนิดข้อมูลและตรวจสอบความ
ครอบคลุมให้อัตโนมัติ — เมื่อไปเรียน `enum` ใน Part 10 คุณจะเห็นว่าพลังของ `match` ร่วมกับ `enum` ทรงพลังมากขึ้นไปอีก
มาก เพราะ compiler จะบังคับให้คุณจัดการทุก "หน้า" ของ enum ที่คุณกำหนดเองด้วย ไม่ใช่แค่ `true`/`false` แบบนี้

**หมายเหตุสำคัญ:** หัวข้อนี้เป็นเพียงการแนะนำผิวเผินที่สุด ยังไม่ครอบคลุมเรื่อง pattern ที่ match ตัวเลขเป็นช่วง
(`1..=5 => ...`), match หลายค่าพร้อมกัน (`1 | 2 | 3 => ...`), match guard (`n if n > 0 => ...`), หรือการ destructure
โครงสร้างข้อมูลซับซ้อน — ทั้งหมดนี้รออยู่ใน **Part 10: Enums และ Pattern Matching**

### 4.11 ตัวอย่างประยุกต์: ระบบคำนวณค่าจัดส่งสินค้า (Shipping Cost Calculator)

มาถึงหัวข้อสุดท้ายของบทนี้ เราจะนำทุกอย่างที่เรียนมา — ฟังก์ชัน, if/else-as-expression, และ loop — มาประกอบกันเป็น
โปรแกรมเล็ก ๆ ที่ใช้งานได้จริง: **ระบบคำนวณค่าจัดส่งสินค้าตามน้ำหนัก** พร้อมเปรียบเทียบสไตล์การเขียนแบบ **idiomatic
Rust (เน้น expression)** กับสไตล์ **แบบภาษา C ทั่วไป (เน้น statement + mutation)** เพื่อให้เห็นความแตกต่างของ
"วิธีคิด" ชัดเจนขึ้น

**กำหนดเงื่อนไขค่าจัดส่ง (tier แบบขั้นบันได ตามน้ำหนักสินค้า):**

| น้ำหนัก (กก.) | ค่าจัดส่ง |
|---|---|
| ไม่เกิน 1 กก. | 30 บาท |
| ไม่เกิน 5 กก. | 50 บาท |
| ไม่เกิน 10 กก. | 80 บาท |
| เกิน 10 กก. | 80 บาท + (น้ำหนักส่วนเกิน × 10 บาท/กก.) |

#### เวอร์ชันที่ 1: สไตล์ idiomatic Rust (expression-oriented)

```rust
// ฟังก์ชันคำนวณค่าจัดส่งจากน้ำหนัก — เขียนแบบ expression ล้วน ไม่มี return หรือตัวแปรกลาง
fn shipping_cost(weight_kg: f64) -> f64 {
    if weight_kg <= 1.0 {
        30.0
    } else if weight_kg <= 5.0 {
        50.0
    } else if weight_kg <= 10.0 {
        80.0
    } else {
        80.0 + (weight_kg - 10.0) * 10.0
    }
}

fn main() {
    let orders_kg = [0.5, 3.0, 8.0, 15.0, 22.5];

    let mut total = 0.0;

    for weight in orders_kg {
        let cost = shipping_cost(weight);
        println!("น้ำหนัก {weight:.1} กก. -> ค่าจัดส่ง {cost:.2} บาท");
        total += cost;
    }

    println!("รวมค่าจัดส่งทั้งหมด: {total:.2} บาท");
}
```

ผลลัพธ์:

```
น้ำหนัก 0.5 กก. -> ค่าจัดส่ง 30.00 บาท
น้ำหนัก 3.0 กก. -> ค่าจัดส่ง 50.00 บาท
น้ำหนัก 8.0 กก. -> ค่าจัดส่ง 80.00 บาท
น้ำหนัก 15.0 กก. -> ค่าจัดส่ง 130.00 บาท
น้ำหนัก 22.5 กก. -> ค่าจัดส่ง 205.00 บาท
รวมค่าจัดส่งทั้งหมด: 495.00 บาท
```

**สังเกตความ "สะอาด" ของฟังก์ชัน `shipping_cost`:** ทุก branch ของ `if/else if/else` คือ expression ที่คืนค่า `f64`
ตรง ๆ ไม่มีตัวแปรกลาง ไม่มี `return` แม้แต่ตัวเดียว — ฟังก์ชันทั้งก้อนอ่านได้เหมือน "สูตรคำนวณ" ทางคณิตศาสตร์มากกว่า
"ชุดคำสั่งที่ค่อย ๆ เปลี่ยนสถานะ" ซึ่งเป็นแก่นของ **expression-oriented thinking**: คุณคิดในรูป "ค่านี้ **คือ**
อะไร" แทนที่จะคิดในรูป "ทำอย่างไรให้ตัวแปรค่อย ๆ กลายเป็นค่านี้"

#### เวอร์ชันที่ 2: สไตล์ C-like verbose (statement-oriented) — เพื่อเปรียบเทียบ

```rust
// ฟังก์ชันเดียวกัน แต่เขียนแบบ "กลายพันธุ์ตัวแปร" ทีละ branch (สไตล์ที่นักพัฒนาจากภาษา C/Java มักคุ้นเคย)
fn shipping_cost_verbose(weight_kg: f64) -> f64 {
    let cost; // ประกาศไว้ก่อน ยังไม่ initialize (Rust อนุญาตถ้ามั่นใจว่าทุก path จะ assign ก่อนใช้งาน)

    if weight_kg <= 1.0 {
        cost = 30.0;
    } else if weight_kg <= 5.0 {
        cost = 50.0;
    } else if weight_kg <= 10.0 {
        cost = 80.0;
    } else {
        cost = 80.0 + (weight_kg - 10.0) * 10.0;
    }

    cost // ต้องมี expression นี้ต่อท้ายเพื่อ return ค่าของ cost ออกไป
}

fn main() {
    let orders_kg = [0.5, 3.0, 8.0, 15.0, 22.5];

    let mut total = 0.0;
    let mut i = 0;

    // จำลองสไตล์ index-based for loop แบบ C/Java แม้ Rust จะไม่บังคับให้เขียนแบบนี้เลย
    while i < orders_kg.len() {
        let weight = orders_kg[i];
        let cost = shipping_cost_verbose(weight);

        println!("น้ำหนัก {:.1} กก. -> ค่าจัดส่ง {:.2} บาท", weight, cost);
        total += cost;
        i += 1;
    }

    println!("รวมค่าจัดส่งทั้งหมด: {:.2} บาท", total);
}
```

โค้ดเวอร์ชันนี้ **ให้ผลลัพธ์เหมือนกันทุกประการ** กับเวอร์ชันแรก และ**compile ผ่านได้จริง** (แม้ `cargo clippy` จะเตือน
หลายจุด เช่น แนะนำให้ใช้ `for weight in orders_kg` แทน manual index loop) แต่สังเกตความแตกต่าง:

1. **`let cost;` ที่ไม่ initialize** — Rust ยอมให้ประกาศตัวแปรไว้ก่อนโดยไม่ต้องให้ค่าเริ่มต้น **ตราบใดที่ compiler
   พิสูจน์ได้ว่าทุกเส้นทาง (path) ของโค้ดจะ assign ค่าให้มันก่อนถูกใช้งานจริงเสมอ** (เรียกว่า "definite assignment
   analysis") ถ้ามี path ไหนที่ลืม assign (เช่น ลบ `else` ทิ้งไป) compiler จะฟ้อง error `used binding cost isn't
   initialized` ทันที — นี่คือความปลอดภัยอีกชั้นที่ Rust มีให้ แม้จะเขียนสไตล์ mutation แบบนี้ก็ตาม
2. **ต้องมี `i` เป็นตัวแปร mutable แยกออกมาเพื่อจำลอง index** — ทั้งที่ Rust มี `for weight in orders_kg` ให้ใช้ตรง ๆ
   อยู่แล้ว การเขียนแบบ index-based เพิ่มโอกาสเกิด off-by-one error ให้ตัวเอง (เช่น เผลอเขียน `i <= orders_kg.len()`)
   และเพิ่มโค้ดที่ต้องดูแล (`i += 1;`) โดยไม่ได้ประโยชน์อะไรเพิ่มเลย
3. **ฟังก์ชัน `shipping_cost_verbose` ยาวกว่าและมีจุดที่ต้อง "ลืมไม่ได้" มากกว่า** — ถ้าคุณเพิ่ม branch ใหม่แล้วลืมเขียน
   `cost = ...;` ในบางเส้นทาง จะเกิด compile error (ซึ่งดี — Rust จับให้) แต่เทียบกับเวอร์ชัน expression ที่ไม่มีทาง
   ลืมได้เลยเพราะทุก branch **ต้อง** มีค่าอยู่แล้วโดยธรรมชาติของไวยากรณ์

**สรุปบทเรียนจากตัวอย่างนี้:** ทั้งสองเวอร์ชัน compile ผ่านและทำงานถูกต้องเหมือนกัน — Rust ไม่ได้บังคับให้คุณเขียน
แบบ expression-oriented เสมอไป แต่ **สไตล์ idiomatic ที่ชุมชน Rust นิยมและเครื่องมืออย่าง `clippy` (Part 5) จะแนะนำ**
คือสไตล์ expression-oriented เพราะมันลดจำนวนจุดที่บั๊กซ่อนตัวได้ (fewer mutable variables, fewer manual index
management) และทำให้โค้ดสั้นกระชับขึ้นโดยไม่เสียความชัดเจน — เมื่อคุณเขียน Rust ไปเรื่อย ๆ สไตล์แบบแรกจะกลายเป็น
ธรรมชาติมากขึ้น

#### ตัวอย่างเสริม: เกรดคำนวณจากคะแนน (ผสม if-as-expression + for loop)

ปิดท้ายด้วยอีกตัวอย่างสั้น ๆ ที่ใช้แนวคิดเดียวกัน แต่กับข้อมูลชุดคะแนนสอบ:

```rust
// คำนวณเกรดจากคะแนน 0-100 โดยใช้ if/else if เป็น expression คืนค่า char
fn grade_letter(score: u32) -> char {
    if score >= 80 {
        'A'
    } else if score >= 70 {
        'B'
    } else if score >= 60 {
        'C'
    } else if score >= 50 {
        'D'
    } else {
        'F'
    }
}

fn main() {
    let scores = [95, 82, 67, 58, 40, 73];

    for score in scores {
        let grade = grade_letter(score);
        println!("คะแนน {score} -> เกรด {grade}");
    }
}
```

ผลลัพธ์:

```
คะแนน 95 -> เกรด A
คะแนน 82 -> เกรด A
คะแนน 67 -> เกรด C
คะแนน 58 -> เกรด D
คะแนน 40 -> เกรด F
คะแนน 73 -> เกรด B
```

ฟังก์ชัน `grade_letter` มีโครงสร้างเดียวกับ `shipping_cost` เป๊ะ ๆ (if/else if แบบ expression, คืนค่าประเภทเดียวกัน
ทุก branch) เพียงแค่คืนค่าเป็น `char` แทน `f64` — นี่แสดงให้เห็นว่ารูปแบบ "if/else if เป็น expression" เป็น pattern
ที่นำไปใช้ได้กับสถานการณ์การจัดหมวดหมู่ (classification) ได้หลากหลายมาก ไม่ว่าจะเป็นค่าจัดส่ง, เกรด, ระดับความเสี่ยง,
หรือ tier ของสมาชิก ฯลฯ

## กับดักที่พบบ่อย (Common Pitfalls)

**1. เผลอเติม semicolon หลัง expression ที่ควรเป็นค่า return ของฟังก์ชัน**

นี่คือกับดักที่พบบ่อยที่สุดในบทนี้ (อธิบายละเอียดแล้วในหัวข้อ 4.4) สรุปสั้น ๆ อีกครั้ง:

```rust
fn double(x: i32) -> i32 {
    x * 2; // ผิด! semicolon ทำให้ตรงนี้กลายเป็น statement คืนค่า ()
}
```

Error:

```
error[E0308]: mismatched types
 --> src/main.rs:3:1
  |
1 | fn double(x: i32) -> i32 {
  |                      --- expected `i32` because of return type
2 |     x * 2;
  |          - help: consider removing this semicolon to return this value
3 | }
  | ^ expected `i32`, found `()`
```

**วิธีแก้:** ลบ semicolon ที่บรรทัดสุดท้ายออก (`x * 2` ไม่มี `;`) หรือถ้าตั้งใจเขียนแบบมี semicolon จริง ๆ ให้เพิ่ม
`return x * 2;` แทน หรือถ้าฟังก์ชันนี้ไม่ได้ตั้งใจ return ค่าอะไรเลย ให้ลบ `-> i32` ออกจาก signature ไปด้วย

**2. ชนิดข้อมูลของแต่ branch ใน if/else ไม่ตรงกัน**

```rust
fn main() {
    let temp_celsius = 25.0;

    let message = if temp_celsius > 30.0 {
        "ร้อน"
    } else if temp_celsius > 20.0 {
        "กำลังดี"
    } else {
        18 // ผิด! ชนิดเป็น integer ไม่ใช่ &str เหมือน branch อื่น
    };

    println!("{message}");
}
```

Error (สรุปย่อ):

```
error[E0308]: mismatched types
  |
  = note: expected `&str`, found integer
```

**วิธีแก้:** ตรวจสอบให้ทุก branch (รวม `else`) คืนค่าชนิดเดียวกันเสมอ ในตัวอย่างนี้ต้องเปลี่ยน `18` เป็น string เช่น
`"เย็น"` หรือแปลง branch อื่นให้เป็นตัวเลขทั้งหมดแทน — ข้อผิดพลาดแบบนี้พบบ่อยเวลาเพิ่ม branch ใหม่เข้าไปทีหลังแล้ว
พิมพ์ชนิดข้อมูลผิดโดยไม่ทันสังเกต (โดยเฉพาะเวลามี `if/else if` ยาวหลาย branch)

**3. พยายาม `break` พร้อมค่าออกจาก `while` หรือ `for` — ทำไม่ได้ (ใช้ได้กับ `loop` เท่านั้น)**

```rust
fn main() {
    let mut n = 0;

    let result = while n < 5 {
        n += 1;
        break n; // ผิด! break พร้อมค่าใช้ได้เฉพาะกับ loop เปล่า ๆ เท่านั้น
    };

    println!("{result}");
}
```

Error จริงจาก compiler:

```
error[E0571]: `break` with value from a `while` loop
 --> src/main.rs:5:9
  |
3 |     let result = while n < 5 {
  |                  ----------- you can't `break` with a value in a `while` loop
4 |         n += 1;
5 |         break n;
  |         ^^^^^^^ can only break with a value inside `loop`
```

**เหตุผล:** อธิบายไว้แล้วในหัวข้อ 4.6 — `while`/`for` มีทางจบสองแบบ (เจอ `break` หรือเงื่อนไข/iterator หมดตามธรรมชาติ)
ทางจบแบบหลังไม่มีค่าให้คืน (คืน `()`) ดังนั้นถ้ายอมให้ `break` พร้อมค่าได้ ก็จะเกิดความกำกวมว่า loop expression นี้มี
ชนิดข้อมูลเป็นอะไรกันแน่ (ชนิดของค่าที่ `break` หรือ `()`) — Rust เลือกห้ามไปเลยเพื่อไม่ให้เกิดความกำกวมนี้ **วิธีแก้**
คือถ้าต้องการคืนค่าจาก loop จริง ๆ ให้เปลี่ยนไปใช้ `loop` (ที่มีทางจบทางเดียวคือ `break` เท่านั้น) แล้วเขียนเงื่อนไข
หยุดด้วย `if` ข้างในเอง เช่น `loop { n += 1; if n >= 5 { break n; } }`

**4. Off-by-one จากการเลือก `..` (exclusive) ผิดเป็น `..=` (inclusive) หรือลืม `break` ใน `loop` จนเกิด infinite loop**

```rust
fn main() {
    let items = ["ก", "ข", "ค", "ง", "จ"]; // มี 5 ตัว, index 0-4

    // ตั้งใจอยากได้ index สุดท้าย (4) ด้วย แต่เขียน .. (exclusive) จึงพลาดตัวสุดท้ายไปโดยไม่รู้ตัว
    for i in 0..items.len() - 1 {
        println!("{}", items[i]); // จะพิมพ์ได้แค่ ก ข ค ง (ขาด จ)
    }
}
```

ในกรณีนี้ **compiler ไม่ error ให้** เพราะ syntax ถูกต้องทุกอย่าง แต่ผลลัพธ์ผิดจากที่ตั้งใจ (logic bug ไม่ใช่ compile
error) — นี่คือเหตุผลที่ควรฝึกเช็คให้ชัดเจนทุกครั้งว่าต้องการ `..` (exclusive) หรือ `..=` (inclusive) จริง ๆ วิธีแก้
ในตัวอย่างนี้คือใช้ `for i in 0..items.len()` ตรง ๆ (ไม่ต้อง `-1`) หรือดีกว่านั้นคือใช้ `for item in items` วนผ่านค่า
ตรง ๆ โดยไม่ต้องยุ่งกับ index เลย

ส่วนกรณี `loop` ที่ลืมเขียน `break` (หรือเขียนเงื่อนไขที่ไม่มีวันเป็นจริง) จะไม่ error ตอน compile เช่นกัน แต่โปรแกรม
จะรันวนไม่มีที่สิ้นสุด (infinite loop) กิน CPU และไม่มีทางจบ — ถ้าเจอโปรแกรม Rust ที่ "รันแล้วค้าง ไม่จบสักที" ให้
ตรวจสอบก่อนว่ามี `loop` ที่ลืมเขียนเงื่อนไข `break` ให้ครอบคลุมทุกกรณีหรือไม่ (กด `Ctrl+C` ที่ terminal เพื่อหยุด
โปรแกรมที่ค้างแบบนี้ได้)

## แบบฝึกหัด (Exercises)

1. **[ง่าย]** เขียนฟังก์ชัน `is_even(n: i32) -> bool` ที่คืนค่า `true` ถ้า `n` เป็นเลขคู่ (ใช้ `n % 2 == 0`) จากนั้น
   เขียน `main()` ที่เรียกฟังก์ชันนี้กับตัวเลข 3-4 ค่า แล้วใช้ `if`/`else` (แบบ statement ธรรมดาก่อนก็ได้) พิมพ์ข้อความ
   ว่าตัวเลขนั้นเป็นเลขคู่หรือคี่
   (hint: `if is_even(n) { println!("{n} เป็นเลขคู่"); } else { println!("{n} เป็นเลขคี่"); }`)

2. **[กลาง]** เขียนฟังก์ชัน `bmi_category(weight_kg: f64, height_m: f64) -> u8` ที่คำนวณค่า BMI ด้วยสูตร
   `BMI = weight_kg / (height_m * height_m)` แล้วคืนค่าตัวเลขหมวดหมู่โดยใช้ `if/else if` แบบ **expression** (ห้ามใช้
   `return` กลางฟังก์ชัน): คืนค่า `1` ถ้า BMI < 18.5 (ผอม), `2` ถ้า 18.5 ≤ BMI < 23 (ปกติ), `3` ถ้า 23 ≤ BMI < 25
   (น้ำหนักเกิน), `4` ถ้า BMI ≥ 25 (อ้วน) จากนั้นสร้างตัวแปร array ของ tuple `[(f64, f64); 3]` เก็บข้อมูล
   (น้ำหนัก, ส่วนสูง) ของคน 3 คน แล้วใช้ `for` loop พร้อม destructure tuple (`for &(w, h) in &people`) วนคำนวณและ
   พิมพ์หมวดหมู่ของแต่ละคนออกมา
   (hint: อย่าลืมว่าทุก branch ของ if/else ต้องคืนค่าชนิดเดียวกันคือ `u8`)

3. **[ยาก]** เขียนโปรแกรมค้นหาคู่ตัวเลข `(i, j)` โดย `i` และ `j` แต่ละตัวอยู่ในช่วง `1..=20` ที่คูณกันแล้วได้ผลลัพธ์
   เท่ากับตัวเลขที่กำหนด (เช่น `target = 84`) เมื่อเจอคู่แรกให้หยุดค้นหาทันทีด้วย **loop label** แล้วเก็บผลลัพธ์ไว้ใน
   ตัวแปรชนิด `Option<(i32, i32)>` ถ้าหาไม่พบเลยหลังวนครบทุกคู่ ให้ค่าคงเป็น `None` แล้วพิมพ์ผลลัพธ์ที่ได้ท้ายโปรแกรม
   ด้วย `{:?}` (hint: ประกาศ `let mut found: Option<(i32, i32)> = None;` ไว้ก่อนเริ่ม loop แล้วใช้ `'outer: for i in
   1..=20 { for j in 1..=20 { ... break 'outer; } }`)

4. **[ยาก/ประยุกต์]** เขียนฟังก์ชัน `electricity_bill(units: f64) -> f64` คำนวณค่าไฟฟ้าแบบ**ขั้นบันไดสะสม**
   (progressive tier — ต่างจากตัวอย่างค่าจัดส่งในบทที่คิดแบบ "เหมาทั้งก้อนตาม tier เดียว") กล่าวคือ 150 หน่วยแรกคิด
   หน่วยละ 3.0 บาท, หน่วยที่ 151-400 คิดหน่วยละ 4.5 บาท (เฉพาะส่วนที่เกิน 150), หน่วยที่เกิน 400 คิดหน่วยละ 6.0 บาท
   (เฉพาะส่วนที่เกิน 400) เช่นถ้าใช้ 500 หน่วย ค่าไฟ = (150×3.0) + (250×4.5) + (100×6.0) ให้ทดลองเขียนทั้งแบบใช้
   `loop`/`while` สะสมค่าทีละหน่วย (verbose) และแบบคำนวณตรงด้วย `if/else if` เป็น expression (idiomatic) เปรียบเทียบ
   ผลลัพธ์ว่าตรงกันหรือไม่ ทดสอบกับค่า `units` หลายค่า เช่น 100, 300, 500, 1000
   (hint แบบ idiomatic: คำนวณทีละช่วงแยกกัน เช่น `let tier3 = if units > 400.0 { (units - 400.0) * 6.0 } else { 0.0 };`
   แล้วรวมทุก tier เข้าด้วยกันเป็นค่าสุดท้าย — ไม่จำเป็นต้องใช้ loop เลยก็ได้ถ้าคิดแบบ expression แต่ให้ลองเขียนแบบ
   loop สะสมทีละหน่วยดูด้วยเพื่อเห็นความแตกต่างของแนวคิด)

## สรุป

ในบทนี้เราได้เรียนรู้พื้นฐานของฟังก์ชันและ control flow ใน Rust ซึ่งเป็นเสาหลักที่ทุกโปรแกรม Rust ต้องใช้ เริ่มจาก
วิธีประกาศฟังก์ชันที่บังคับให้ระบุชนิดข้อมูลของพารามิเตอร์และค่า return เสมอ (ต่างจาก Python/JavaScript ที่เป็น
dynamically typed) และเข้าใจว่า Rust ไม่มี default parameter value หรือ function overloading โดยตั้งใจ พร้อมรู้จัก
ทางเลือกที่ idiomatic กว่าอย่างการตั้งชื่อฟังก์ชันแยก, ใช้ `Option<T>`, หรือ builder pattern

หัวใจสำคัญที่สุดของบทนี้คือแนวคิด **statement vs expression** — Rust เป็นภาษา expression-oriented ที่ block `{ }`,
`if/else`, `loop`, และ `match` ทั้งหมดเป็น expression ที่มีค่าและชนิดข้อมูลได้ ไม่ใช่แค่ control flow แบบ C/Java
ธรรมดา การเข้าใจกฎ "semicolon เปลี่ยน expression ให้เป็น statement ที่คืนค่า `()`" คือกุญแจสำคัญที่จะทำให้คุณเข้าใจ
error message จำนวนมากที่จะเจอตลอดการเขียน Rust ต่อจากนี้ นอกจากนี้เรายังได้เรียน `loop`/`while`/`for` ทั้งสามแบบ
พร้อมความสามารถพิเศษของ Rust อย่าง `break` ที่คืนค่าได้ และ loop label ที่ควบคุม nested loop ได้อย่างแม่นยำ ปิดท้าย
ด้วยการแนะนำ `match` แบบเบื้องต้นและตัวอย่างโปรแกรมคำนวณค่าจัดส่งสินค้าที่แสดงให้เห็นความแตกต่างระหว่างสไตล์ idiomatic
Rust กับสไตล์ C-like verbose

ใน **Part 5** เราจะเรียนเรื่อง **Comments, rustfmt และ Clippy** — วิธีเขียน comment ที่ดี, การจัดรูปแบบโค้ดอัตโนมัติ
ด้วย `rustfmt`, และการใช้ `clippy` เพื่อตรวจจับโค้ดที่ไม่ idiomatic หรือมีข้อผิดพลาดเชิง logic ซึ่งจะช่วยขัดเกลาโค้ด
ที่เราเขียนในบทนี้ให้สะอาดและเป็นมาตรฐานมากยิ่งขึ้น ก่อนที่เราจะเข้าสู่โมดูล 1 (Core Language Fundamentals) ที่เริ่ม
เจาะลึก ownership, borrowing, structs, enums และ pattern matching แบบเต็มรูปแบบ
