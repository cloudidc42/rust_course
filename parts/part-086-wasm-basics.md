# Part 86: WebAssembly เบื้องต้นด้วย Rust

> โมดูล: Full-Stack และ WebAssembly | ระดับ: กลาง | เวลาโดยประมาณ: 240 นาที

## เป้าหมายของบทเรียน

หลังจากจบบทนี้ คุณจะสามารถ:

- อธิบายได้อย่างแม่นยำว่า **WebAssembly (WASM)** คืออะไรในทางเทคนิค (binary instruction format ที่ออกแบบมา
  ให้รันในสภาพแวดล้อมแบบ sandbox) ทำไมมันถึงถูกสร้างขึ้นมา (เบราว์เซอร์ต้องการ compilation target ที่เร็วกว่า
  JavaScript สำหรับงานที่ใช้ CPU หนัก และต้องการเปิดทางให้โค้ดจาก**ภาษาไหนก็ได้**มารันในเบราว์เซอร์ได้ ไม่ใช่แค่
  JavaScript) และทำไมโมเดลการทำงานของมันถึงต่างจาก JavaScript แบบ interpreted/JIT โดยสิ้นเชิง
- อธิบายได้ว่าทำไม **Rust เหมาะกับ WASM เป็นพิเศษ** เมื่อเทียบกับภาษาที่มี garbage collector (Go, C#) — เพราะ
  ภาษาที่มี GC ต้อง**แนบ runtime ของ GC เข้าไปในตัว WASM binary เองด้วย** ทำให้ไฟล์บวมขึ้นมาก ในขณะที่ Rust ไม่มี
  ปัญหานี้เพราะ ownership/borrow checker พิสูจน์ความปลอดภัยของหน่วยความจำไปแล้วตั้งแต่ compile time
- อธิบายโมเดล **linear memory** ของ WASM (หน่วยความจำทั้งหมดคือ byte array ต่อเนื่องผืนเดียว ตัวชี้คือแค่
  ตัวเลข offset เข้าไปในผืนนั้น) และเชื่อมโยงกับความเข้าใจเรื่อง raw pointer/memory layout ที่ได้เรียนไปแล้วใน
  Part 42
- ติดตั้งเครื่องมือที่จำเป็นสำหรับพัฒนา Rust+WASM ได้จริง (`rustup target add wasm32-unknown-unknown`,
  `wasm-pack`) สร้างโปรเจกต์ `cargo new --lib` แล้ว compile เป็น `.wasm` ได้จริง พร้อมอ่านผลลัพธ์ไฟล์ที่
  `wasm-pack build` สร้างให้ (`.wasm`, JS glue code, `.d.ts`) ออกว่าแต่ละไฟล์มีหน้าที่อะไร
- เขียนฟังก์ชัน Rust ธรรมดา compile เป็น WASM แล้วเรียกใช้จากหน้าเว็บ HTML+JavaScript จริงได้สำเร็จ พิสูจน์ผลลัพธ์
  ด้วยการรันจริง (ไม่ใช่แค่คัดลอกโค้ดจากเอกสาร)
- แยกแยะ compilation target สามแบบของ WASM ในโลก Rust (`wasm32-unknown-unknown`, `wasm32-wasip1`/WASI) ได้ว่า
  ใช้ต่างกันอย่างไรและทำไมบทนี้เลือกใช้ `wasm32-unknown-unknown` เป็นหลัก
- อธิบายได้ว่าทำไมการส่งค่าที่ซับซ้อนกว่าตัวเลข (เช่น `String`) ข้ามพรมแดน WASM/JavaScript โดยตรง**ทำไม่ได้อย่าง
  ปลอดภัย** โดยไม่มีตัวช่วย พร้อมเห็นปัญหานี้แบบเป็นรูปธรรมด้วยโค้ดจริง — ซึ่งเป็นแรงจูงใจตรงไปยัง Part 87 ที่จะ
  สอน `wasm-bindgen` เพื่อแก้ปัญหานี้อย่างเป็นระบบ
- ลดขนาดไฟล์ WASM binary ได้ด้วยการตั้งค่า `Cargo.toml` release profile (`opt-level = "z"`, `lto = true`) และ
  เครื่องมือ `wasm-opt` พร้อมวัดผลจริงว่าขนาดไฟล์ลดลงเท่าไหร่
- วาง WebAssembly ให้ถูกที่ในภาพรวมของ Rust web developer — เข้าใจว่ามันไม่ใช่สิ่งที่มาแทน Axum/server-side Rust
  ที่เรียนมาตลอดโมดูล 4 แต่เป็นเครื่องมือสำหรับรันโค้ด Rust **ในเบราว์เซอร์ของผู้ใช้** (หรือที่ edge)

## ความรู้ที่ต้องมีมาก่อน

- **Part 42 (Raw Pointers และ Memory Layout)**: หัวข้อ 86.2 ของบทนี้จะอธิบายโมเดล linear memory ของ WASM โดย
  อ้างอิงตรงกับสิ่งที่ Part 42 สอนไว้เรื่อง raw pointer เป็นแค่ "ที่อยู่ในหน่วยความจำ ไม่มีการรับประกันอะไรจาก
  compiler" — WASM ยกระดับความคิดนี้ขึ้นไปอีกขั้น: pointer ทั้งหมดในโลก WASM คือ**ตัวเลข offset เข้าไปในหน่วย
  ความจำผืนเดียวที่ต่อเนื่องกัน** ถ้าจำเรื่อง alignment/layout จาก Part 42 ไม่ชัด ควรทวนก่อน เพราะบทนี้จะอ้างอิง
  แนวคิดเดียวกันแต่ในบริบทของ WASM
- **Part 41 (Unsafe Rust เบื้องต้น)**: แนวคิดเรื่อง "compiler พิสูจน์ความปลอดภัยให้ล่วงหน้าที่ compile time
  แทนการเช็คที่ runtime" ที่ Part 41 ปูไว้ คือหัวใจของคำอธิบายในหัวข้อ 86.2 ว่าทำไม Rust ไม่ต้องแนบ runtime
  safety check ใด ๆ เข้าไปใน WASM binary เพิ่มเติมจากที่ sandbox ของ WASM มีให้อยู่แล้ว
- **Part 35 (Cargo ขั้นสูง: Profiles และ Workspaces)**: หัวข้อ 86.8 ของบทนี้ใช้คีย์ `opt-level`/`lto` ใน
  `[profile.release]` ที่ Part 35 สอนไว้อย่างละเอียดแล้วโดยตรง เพียงแต่เปลี่ยนเป้าหมายจาก "โปรแกรมที่รันบนเครื่อง
  ผู้ใช้" มาเป็น "ไฟล์ที่ต้องดาวน์โหลดผ่านเครือข่ายก่อนรัน" ซึ่งทำให้ขนาดไฟล์สำคัญกว่าที่เคยเป็นมา ถ้าจำความหมาย
  ของสองคีย์นี้ไม่ชัด ควรทวน Part 35 หัวข้อ 35.2 และ 35.4 ก่อน
- **Part 62-66 (Axum พื้นฐาน)** และภาพรวมทั้งโมดูล 4 (Part 61-85): บทนี้จะเทียบให้เห็นความต่างระหว่าง "Rust บน
  server" (สิ่งที่เรียนมาตลอดโมดูล 4) กับ "Rust ในเบราว์เซอร์" (สิ่งที่บทนี้เริ่ม) — ถ้ายังไม่ผ่านโมดูล 4 มาก่อน
  ควรอ่านอย่างน้อยบทสรุปของ Part 85 เพื่อเห็นภาพว่าเรากำลังเปลี่ยนฝั่งจากอะไรไปเป็นอะไร
- ความรู้พื้นฐานเรื่อง HTML/JavaScript ระดับเบามาก (รู้จัก `<script>` tag, `function`, `console.log`) — บทนี้จะ
  ไม่สอน JavaScript ตั้งแต่ต้น แต่ตัวอย่างที่ใช้เรียก WASM จากฝั่งเว็บจะมี JavaScript ปนอยู่บ้าง

## เนื้อหา

### 86.1 WebAssembly คืออะไรจริง ๆ และทำไมมันถึงถูกสร้างขึ้นมา

โมดูล 4 ที่ผ่านมาทั้งหมด (Part 61-85) Rust ทำหน้าที่เป็น**server** เสมอ — รับ HTTP request, ประมวลผล, ตอบกลับ
เป็น JSON แล้วจบ ไม่มีโค้ด Rust ตัวไหนเลยที่รันอยู่ใน**เบราว์เซอร์ของผู้ใช้** โมดูล 5 ที่เริ่มจากบทนี้เปลี่ยนมุมมอง
นี้โดยสิ้นเชิง คำถามแรกที่ต้องตอบให้ชัดก่อนคือ: **WebAssembly คืออะไรกันแน่?**

#### นิยามที่แม่นยำ

**WebAssembly (ย่อว่า WASM)** คือ **binary instruction format** — รูปแบบคำสั่งระดับต่ำที่เก็บเป็นไบต์ ไม่ใช่
ข้อความอ่านง่ายแบบ source code — ที่ถูกออกแบบมาให้เป็น**compilation target แบบพกพา (portable)** สำหรับรันใน
**สภาพแวดล้อมแบบ sandbox (sandboxed execution environment)** พูดให้เข้าใจง่ายขึ้น: มันคือ "ภาษาเครื่อง"
(machine code) แบบหนึ่งที่**ไม่ผูกกับ CPU จริงตัวไหนเลย** (ไม่ใช่ x86, ไม่ใช่ ARM) แต่เป็น CPU สมมติ (virtual
instruction set) ที่ทุกแพลตฟอร์มสร้าง interpreter/JIT ของตัวเองมารันมันได้เหมือนกันหมด — คล้ายกับที่ bytecode
ของ Java Virtual Machine (JVM) เป็น "ภาษาเครื่องสมมติ" ที่ JVM บนแต่ละแพลตฟอร์มมารันให้ แต่ WASM ถูกออกแบบมาให้
**เร็วกว่ามาก** เพราะมันใกล้เคียงกับภาษาเครื่องจริงของ CPU มากกว่า bytecode ของภาษาระดับสูงทั่วไป

คำว่า "sandboxed" สำคัญมาก — โค้ด WASM ที่รันอยู่**ไม่สามารถ**เข้าถึงหน่วยความจำหรือทรัพยากรอะไรนอกเหนือจากที่
สภาพแวดล้อมที่มันรันอยู่ (เรียกว่า **host** — อาจเป็นเบราว์เซอร์, Node.js, หรือ runtime แบบ standalone) **อนุญาต
ให้ผ่าน explicitly เท่านั้น** ไม่มีทางที่โค้ด WASM จะยิง syscall ตรง ๆ ไปขอไฟล์ในเครื่อง หรือเปิด socket เองได้
โดยไม่ผ่านการอนุญาตจาก host ก่อน — นี่คือเหตุผลที่มันปลอดภัยพอจะรันโค้ดจากคนแปลกหน้าบนอินเทอร์เน็ต (เว็บไซต์ที่
คุณเข้า) โดยไม่ต้องกลัวว่าจะแฮ็กเครื่องคุณได้ง่าย ๆ

#### ทำไมมันถึงถูกสร้างขึ้นมา: ปัญหาสองข้อที่ JavaScript แก้ไม่ได้ดีพอ

ก่อนมี WebAssembly เบราว์เซอร์มีภาษาให้เขียนโค้ดฝั่ง client ได้ทางเดียวคือ **JavaScript** เพียงอย่างเดียวมาเกือบ
30 ปี ทำไมถึงต้องมีอะไรมาเสริม? มีสองปัญหาหลักที่ผลักดันให้เกิด WebAssembly:

**ปัญหาที่ 1: ความเร็วไม่พอสำหรับงานที่ใช้ CPU หนัก**

JavaScript เป็นภาษาแบบ **interpreted/JIT (Just-In-Time compiled)** — เอนจินอย่าง V8 (ที่ Chrome ใช้) หรือ
SpiderMonkey (Firefox) อ่านโค้ด JS แล้วแปลงเป็นภาษาเครื่องแบบ **ขณะรันจริง (runtime)** ไม่ใช่ล่วงหน้าแบบ Rust
หรือ C++ แม้ JIT compiler สมัยใหม่จะเก่งมากในการเดา pattern แล้ว optimize โค้ดที่รันบ่อย ๆ (hot path) ให้เร็ว
ขึ้นเรื่อย ๆ แต่ยังมีข้อจำกัดที่แก้ไม่ได้ง่าย ๆ ด้วยธรรมชาติของภาษา:

- **Dynamic typing** — ตัวแปรใน JS เปลี่ยน type ได้ตลอดเวลา (`let x = 5; x = "hello";` คือโค้ดที่ valid) เอนจิน
  ต้องเช็ค type ที่ runtime ตลอด ทำให้ optimize ให้เท่ากับโค้ดที่รู้ type ล่วงหน้าแน่นอน (statically typed) แบบ
  Rust ได้ยากมาก
- **Garbage collection ที่ไม่คาดเดาได้** — JS มี GC คอยเก็บกวาดหน่วยความจำอัตโนมัติ ซึ่งดีสำหรับความสะดวก แต่ GC
  pause (ช่วงเวลาที่ GC หยุดโปรแกรมชั่วครู่เพื่อเก็บกวาด) ทำให้งานที่ต้องการ**เวลาแบบเนียนสม่ำเสมอ**ทุกมิลลิวินาที
  (เช่น เกม, การประมวลผลวิดีโอแบบ real-time) เจอปัญหา stutter ได้ง่าย

งานประเภทที่ต้องการความเร็วระดับใกล้เคียง native จริง ๆ เช่น **การประมวลผลภาพ/วิดีโอในเบราว์เซอร์, เกม 3D,
การเข้ารหัส/ถอดรหัสข้อมูล, การจำลองทางฟิสิกส์, CAD บนเว็บ** — งานเหล่านี้ JavaScript ทำได้ แต่ทำได้**ช้ากว่าที่
ควรจะเป็นมาก** เมื่อเทียบกับโปรแกรม native เดียวกันที่เขียนด้วย C++/Rust และ compile ตรงเป็นภาษาเครื่องของ CPU
จริง

**ปัญหาที่ 2: เบราว์เซอร์ผูกติดกับภาษาเดียว**

ก่อน WebAssembly ถ้าอยากรันโค้ดในเบราว์เซอร์ **ต้องเขียนเป็น JavaScript เท่านั้น** ไม่ว่าคุณจะมี library ที่
เขียนด้วย C/C++/Rust ไว้แล้วเป็นแสนบรรทัดที่ทำงานได้ดีอยู่แล้ว (เช่น engine ประมวลผลภาพ, decoder วิดีโอ,
library เข้ารหัสที่ผ่านการตรวจสอบความปลอดภัยมาแล้ว) คุณต้อง**เขียนใหม่เป็น JavaScript ทั้งหมด**ถ้าต้องการใช้ใน
เว็บ — เสียเวลา เสี่ยง bug ใหม่ และเสียโค้ดที่ผ่านการทดสอบมานานทิ้งไปเปล่า ๆ

มีความพยายามแก้ปัญหานี้มาก่อน WebAssembly ด้วยเทคนิคที่เรียกว่า **asm.js** (ประมาณปี 2013) ซึ่งคือ JavaScript
"เวอร์ชันจำกัด" ที่เขียนในรูปแบบเฉพาะ (ใช้แต่ตัวเลขและ pattern ที่กำหนดตายตัว) ให้เอนจิน JS optimize ได้เหมือน
ภาษาที่ type ชัดเจน แนวคิดคือ compile โค้ด C/C++ (ผ่าน Emscripten) เป็น asm.js แล้ว "หลอก" ให้ browser รันเร็ว
ขึ้นเพราะ pattern ที่จำกัดทำให้ JIT optimize ได้แน่นอนกว่า — asm.js ทำงานได้จริงและเร็วขึ้นกว่า JS ธรรมดามาก
แต่ยังมีข้อจำกัดสำคัญ: มันยังคือ**ข้อความ JavaScript** ที่ต้อง parse เป็น text ก่อน (ไฟล์ใหญ่ขึ้นเรื่อย ๆ ตาม
ขนาดโปรแกรม, parse ช้าลงตามขนาดไฟล์), และการ optimize ยังพึ่งพา "ความหวังว่า JIT จะจำ pattern นี้ได้" ไม่ใช่
การรับประกันจาก format เอง

**WebAssembly (ประกาศตัวปี 2015, กลายเป็น W3C recommendation ปี 2019)** ออกแบบมาแก้ทั้งสองปัญหาพร้อมกันตั้งแต่
ต้น โดยไม่ต้อง "หลอก" อะไรเลย:

- เป็น **binary format** ตั้งแต่แรก ไม่ใช่ text ที่ต้อง parse เป็นโครงสร้างก่อน — โหลดเร็วกว่า และเบราว์เซอร์
  แปลงเป็นภาษาเครื่องได้เร็วกว่า parse+JIT ข้อความ JS มาก
- เป็น **stack machine ที่ type ชัดเจนตายตัว** ทุก instruction รู้ type ของ operand แน่นอนตั้งแต่ต้น ไม่ต้อง
  เดาแบบ dynamic typing ของ JS
- เป็น **compilation target ที่เปิดกว้างสำหรับภาษาไหนก็ได้** — ไม่ผูกกับภาษาต้นทางเลย ตราบใดที่มี compiler ที่
  แปลงภาษานั้นเป็น WASM ได้ (Rust ผ่าน LLVM backend, C/C++ ผ่าน Emscripten, และภาษาอื่น ๆ อีกมาก) — นี่คือคำตอบ
  ของปัญหาที่ 2 โดยตรง: library ที่เขียนด้วย Rust/C++ อยู่แล้ว **compile ตรงเป็น WASM ได้เลย ไม่ต้องเขียนใหม่**

ตารางสรุปเปรียบเทียบ JavaScript กับ WebAssembly ในมิติที่สำคัญที่สุด:

| มิติ | JavaScript | WebAssembly |
|---|---|---|
| รูปแบบไฟล์ | Text (ต้อง parse เป็น AST ก่อน) | Binary (โครงสร้างพร้อมใช้ ไม่ต้อง parse ซับซ้อน) |
| การแปลงเป็นภาษาเครื่อง | Interpreted + JIT ขณะรัน (คาดเดา hot path) | Compile ล่วงหน้า (ahead-of-time) เป็นภาษาเครื่องของภาษาต้นทาง แล้วเบราว์เซอร์แปลง WASM → native code แบบรวดเร็วเพราะ format ใกล้เคียงกันอยู่แล้ว |
| Type system | Dynamic (type เปลี่ยนได้ตอนรัน) | Static (i32/i64/f32/f64 กำหนดตายตัวทุก instruction) |
| Garbage collection | มี GC ในตัวเอนจินเสมอ | **ไม่มี GC ในตัว WASM เอง** (ภาษาที่ต้องการ GC ต้องแนบมาเอง — ประเด็นสำคัญของหัวข้อ 86.2) |
| ภาษาต้นทางที่ใช้ได้ | JavaScript (หรือภาษาที่ transpile เป็น JS เช่น TypeScript) เท่านั้น | ภาษาไหนก็ได้ที่มี compiler แปลงเป็น WASM (Rust, C/C++, Go, C#, Zig, …) |
| ที่ทำงาน | เบราว์เซอร์ (และ Node.js) | เบราว์เซอร์, Node.js, และ**นอกเบราว์เซอร์ด้วย** (server-side/edge runtime ผ่าน WASI — หัวข้อ 86.6) |

**ใครรัน WASM ได้บ้าง**: engine หลักทั้งสามตัวที่ขับเคลื่อนเบราว์เซอร์ยุคใหม่รองรับ WASM มาตั้งแต่ MVP
(Minimum Viable Product — เวอร์ชันแรกที่ใช้งานได้จริง) เปิดตัวปี 2017 ทั้งหมด: **V8** (Chrome, Edge, Node.js,
Deno), **SpiderMonkey** (Firefox), และ **JavaScriptCore** (Safari) — พูดง่าย ๆ คือไฟล์ `.wasm` ตัวเดียวกัน
รันได้ในทุกเบราว์เซอร์หลักโดยไม่ต้องแก้ไขอะไรเลย (แนวคิด "compile ครั้งเดียว รันได้ทุกที่" แบบเดียวกับที่ WASM
ตั้งใจออกแบบมาตั้งแต่ต้น) ส่วนนอกเบราว์เซอร์ก็มี runtime แบบ standalone เกิดขึ้นตามมา เช่น **Wasmtime**,
**Wasmer**, **WasmEdge** — ที่ใช้รัน WASM ผ่าน WASI (หัวข้อ 86.6) โดยไม่มีเบราว์เซอร์เกี่ยวข้องเลย

#### WebAssembly ไม่ใช่แค่ "เรื่องเบราว์เซอร์" อีกต่อไป

ชื่อ "WebAssembly" มีคำว่า "Web" อยู่ในนั้นเพราะกำเนิดของมันคือปัญหาฝั่งเบราว์เซอร์ แต่ **แนวคิดหลัก — binary
format ที่กระชับ, portable, sandbox ปลอดภัย, ประสิทธิภาพใกล้ native — มีประโยชน์นอกเบราว์เซอร์ด้วย** ปัจจุบัน
WASM ถูกใช้เป็น**runtime แบบพกพาสำหรับรันโค้ดที่ไม่น่าเชื่อถือ (untrusted code)** ในบริบทอื่นด้วย เช่น:

- **Edge computing / serverless functions** — Cloudflare Workers, Fastly Compute@Edge รันโค้ดของผู้ใช้นับ
  พันคนบนเครื่องเดียวกัน โดยแต่ละคนไม่ควรแทะเงาะกันได้ — sandbox ของ WASM ตอบโจทย์นี้พอดี (เริ่ม instance ได้เร็ว
  กว่า container/VM มาก เพราะไม่ต้องบูต OS)
- **Plugin system ของแอปพลิเคชัน** — โปรแกรมบางตัวให้ผู้ใช้เขียน plugin เป็น WASM แทนการโหลด native library
  (`.so`/`.dll`) ตรง ๆ เพราะ WASM sandbox ป้องกัน plugin ที่มีบั๊กหรือมุ่งร้ายไม่ให้ทำลายโปรแกรมหลักได้
- **WASI (WebAssembly System Interface)** — มาตรฐานที่เปิดทางให้ WASM binary เข้าถึงทรัพยากรระดับ OS (ไฟล์,
  environment variable, เวลา) แบบพกพาข้ามแพลตฟอร์ม โดยไม่ต้องมีเบราว์เซอร์เลย (หัวข้อ 86.6 จะอธิบายละเอียด)

บทนี้เน้นไปที่เคสดั้งเดิมที่สุดและใช้กันมากที่สุด — **WASM ในเบราว์เซอร์** — แต่การรู้ว่ามันไปได้ไกลกว่านั้นช่วย
ให้เข้าใจภาพรวมของระบบนิเวศได้ถูกต้องตั้งแต่ต้น

### 86.2 ทำไม Rust เหมาะกับ WASM เป็นพิเศษ: เรื่อง Garbage Collector และ Linear Memory

คำถามต่อไป: มีหลายภาษาที่ compile เป็น WASM ได้ (C, C++, Go, C#, Rust, Zig, AssemblyScript, …) แล้วทำไม Rust
ถึงถูกมองว่าเป็นตัวเลือกที่ "เหมาะ" เป็นพิเศษสำหรับ WASM จนมีคนพูดกันว่า Rust+WASM คือคู่ที่เข้ากันโดยธรรมชาติ?
คำตอบมีสองส่วนที่เชื่อมกัน: **เรื่อง garbage collector** และ **เรื่องโมเดลหน่วยความจำที่ตรงกันพอดี**

#### ปัญหาของภาษาที่มี Garbage Collector บน WASM: ต้องแนบ Runtime ไปด้วย

อย่างที่หัวข้อ 86.1 บอกไว้ในตาราง: **WebAssembly ไม่มี garbage collector อยู่ในตัวมันเอง** (มีข้อเสนอมาตรฐานใหม่
ชื่อ WasmGC ที่กำลังพัฒนาอยู่ แต่ ณ ตอนที่เขียนบทนี้ยังไม่ใช่สิ่งที่ toolchain ส่วนใหญ่ใช้งานจริงเป็นค่าเริ่มต้น)
WASM เองรู้จักแค่ **linear memory** (จะอธิบายละเอียดในหัวข้อถัดไป) กับตัวเลขไม่กี่ชนิด (i32/i64/f32/f64) — ไม่มี
แนวคิด "object" หรือ "reference ที่ track ได้อัตโนมัติ" ในระดับ instruction เลย

คำถามคือ: ถ้าภาษาต้นทางของคุณ**ต้องมี** GC ในการทำงานปกติ (เช่น Go, C#, Java, Python) แล้วจะ compile เป็น WASM
ยังไง? คำตอบคือ: **ต้อง compile GC runtime ของภาษานั้นทั้งชุดให้เป็น WASM แล้วแนบเข้าไปในไฟล์ `.wasm` ด้วย**
พูดให้เป็นรูปธรรม: เวลาคุณ compile โปรแกรม Go เล็ก ๆ เป็น WASM ไฟล์ `.wasm` ที่ได้ไม่ได้มีแค่โค้ด logic ของ
โปรแกรมคุณ — มันมี **Go runtime ทั้งชุด (scheduler ของ goroutine, garbage collector, การจัดการ stack ของ
goroutine)** ห่ออยู่ข้างในด้วย เพราะ WASM ไม่มีอะไรพวกนี้ให้ใช้ฟรี ๆ ต้องพกไปเอง

นี่คือปัญหาที่เกิดขึ้นจริงและมีประวัติให้ตรวจสอบได้: โปรแกรม "Hello, World!" ภาษา Go ที่ compile เป็น WASM ด้วย
`GOOS=js GOARCH=wasm go build` ในหลายเวอร์ชันของ Go ได้ไฟล์ `.wasm` ขนาด **หลาย MB** (มากกว่า 2 MB ในหลาย
เวอร์ชัน) ทั้งที่โค้ด logic จริงมีแค่ไม่กี่บรรทัด — ส่วนใหญ่ของขนาดไฟล์คือ Go runtime ที่ต้องแนบไปด้วยเสมอ
ในทำนองเดียวกัน Blazor (framework ของ Microsoft ที่รัน C# ในเบราว์เซอร์ผ่าน WASM) ต้องแนบ **.NET runtime บาง
ส่วน**เข้าไปด้วยในโหมด WebAssembly เต็มรูปแบบ (แม้เวอร์ชันใหม่ ๆ จะพยายาม trim ให้เล็กลงมากแล้ว) ทำให้การโหลด
หน้าเว็บครั้งแรกที่ใช้ Blazor WebAssembly มักช้ากว่าที่ควรจะเป็นเพราะต้องดาวน์โหลด runtime มาก่อนโค้ดแอปจะรัน
ได้เลย

ทำไมถึงเป็นแบบนี้? เพราะ GC ไม่ใช่แค่ "ฟังก์ชันเดี่ยว ๆ" — มันคือระบบที่ต้อง**ติดตามทุก object ที่จองไว้ตลอดเวลา
โปรแกรมทำงาน** (ผ่านเทคนิคอย่าง reference counting, mark-and-sweep, generational collection) ต้องมี scheduler
คอยตัดสินใจว่าเมื่อไหร่ควรเก็บกวาด ต้องมี stack scanner ที่รู้ว่า reference ไหนยังถูกใช้อยู่ — โค้ดพวกนี้ทั้งชุด
ต้อง compile เป็น WASM แนบไปด้วย ไม่ว่าโปรแกรมของคุณจะเล็กแค่ไหนก็ตาม

#### Rust ไม่มีปัญหานี้: ไม่มี Runtime ที่ต้องแนบ

Rust **ไม่มี garbage collector เลย** — หน่วยความจำถูกจัดการผ่าน **ownership และ borrow checker ที่ทำงานที่
compile time เท่านั้น** (ทวนจาก Part 6-8) เมื่อ compile time ตัดสินใจไปแล้วว่าค่าไหนถูก drop ตอนไหน โค้ดที่ได้
คือ**คำสั่ง drop ที่ inline อยู่ตรง ๆ** ไม่มี process แยกที่ต้องรันคอยตรวจสอบ ไม่มี scheduler ไม่มี metadata
ที่ต้อง track ตลอดเวลาโปรแกรมทำงาน — พูดอีกแบบ: Rust compile แนวคิด "จัดการหน่วยความจำให้ปลอดภัย" ไปเป็น
**คำสั่งธรรมดาที่แทรกอยู่ในโค้ดปกติ** ไม่ใช่ระบบแยกที่ต้องพกไปด้วยเป็นชุด

ผลคือ: WASM binary ที่ compile จาก Rust **มีแค่โค้ด logic ของโปรแกรมคุณ (บวก std library เท่าที่ใช้จริง) โดย
ไม่มี "ค่าคงที่" ที่ต้องแนบไปเสมอเป็นชุดใหญ่แบบภาษาที่มี GC** — โปรแกรม `add(a, b)` ง่าย ๆ ที่จะเขียนในหัวข้อ 86.4
ได้ไฟล์ `.wasm` ขนาดแค่ไม่กี่กิโลไบต์ ไม่ใช่หลาย MB เหมือนตัวอย่าง Go/C# ข้างบน

#### ทำไม Rust ไม่ต้องมี Runtime Safety Check เพิ่มใน WASM

มีอีกมุมที่น่าสนใจ: WASM sandbox เองก็มีการ**เช็คความปลอดภัยของหน่วยความจำในระดับของมันเองอยู่แล้ว** — ทุกครั้ง
ที่โค้ด WASM เข้าถึงหน่วยความจำ (`load`/`store` instruction) runtime ของ host จะ**เช็คขอบเขต (bounds check)**
ว่า offset ที่เข้าถึงอยู่ในช่วงที่ linear memory มีจริงหรือไม่ — ถ้าเกินขอบเขต จะเกิด **trap** (คล้าย exception
แต่หยุดโปรแกรมทันที ไม่มีทาง "escape" ไปทำลายหน่วยความจำของ host ได้) นี่คือชั้นความปลอดภัยที่ WASM มีให้
**ทุกภาษาที่ compile เป็น WASM โดยไม่มีข้อยกเว้น**

คำถามที่น่าคิด: ถ้า WASM sandbox เช็ค memory safety ให้อยู่แล้วในระดับ runtime แบบนี้ ทำไม Rust ยังต้องมี
ownership/borrow checker ที่ compile time ด้วย? คำตอบคือ **มันเช็คคนละเรื่องกัน**:

- **WASM sandbox's bounds check** ป้องกันแค่ **"เข้าถึงหน่วยความจำนอกขอบเขตของ linear memory ที่จองไว้"** — ถ้า
  โค้ดของคุณมี use-after-free หรือ data race ภายใน**ขอบเขตที่ถูกต้อง**ของ memory ที่จองไว้ WASM sandbox **ไม่รู้
  และไม่เช็คให้** เพราะสำหรับมันแล้ว มันคือการเข้าถึงหน่วยความจำที่ valid ตาม bounds เฉย ๆ ไม่รู้เรื่อง "ค่านี้
  ควรถูกปล่อยไปแล้วหรือยัง" หรือ "สอง thread กำลังเขียนที่เดียวกันพร้อมกันหรือเปล่า"
- **Rust ownership/borrow checker** เช็คเรื่อง **use-after-free, double-free, data race** ที่ compile time
  ล่วงหน้า ก่อนที่โค้ดจะกลายเป็น WASM เสียอีก

พูดให้ชัด: **สองชั้นนี้เสริมกัน ไม่ได้ทำงานซ้ำกัน** — Rust ทำให้แน่ใจว่าโค้ดของคุณไม่มี memory bug ประเภทที่
ownership ป้องกันได้ตั้งแต่ก่อน compile เป็น WASM เลย ส่วน WASM sandbox เป็นชั้นป้องกันสุดท้ายที่รับประกันว่า
**แม้จะมี bug หลุดมาจริง (เช่นเขียนโค้ด `unsafe` ผิดใน Rust เอง) ผลกระทบก็จำกัดอยู่แค่ในขอบเขตของ linear memory
ของโปรแกรมนั้น ไม่ลามไปทำลายหน่วยความจำของ host หรือของ WASM module อื่นได้** — นี่คือเหตุผลที่ภาษาที่ปลอดภัย
เรื่องหน่วยความจำอยู่แล้วอย่าง Rust ไม่ต้องแบก **runtime safety check ซ้ำสอง**เข้าไปในตัว binary (เหมือนที่บาง
ภาษาต้อง insert bounds check ของตัวเองซ้ำกับที่ WASM มีให้ฟรีอยู่แล้ว) — เพราะ Rust "จ่ายค่าความปลอดภัย" ไปแล้ว
ที่ compile time ครั้งเดียว ไม่ต้องจ่ายซ้ำที่ runtime อีก

#### โมเดล Linear Memory: ผืนเดียว ต่อเนื่อง เป็น Byte Array

มาถึงแนวคิดที่สำคัญที่สุดของบทนี้ในเชิงเทคนิค — **linear memory** คือชื่อทางการของ "หน่วยความจำ" ในโลก WASM

ทวนจาก Part 42: ในโปรแกรม native ทั่วไป หน่วยความจำที่โปรแกรมมองเห็นคือ **virtual address space** ที่ OS จัดให้
(ทุก process มีของตัวเอง แยกกันโดย OS/hardware) pointer คือที่อยู่ในพื้นที่นั้น ส่วน WASM **ตัดความซับซ้อนทั้งหมด
นี้ออกไปเหลือแค่สิ่งเดียว**:

> **Linear memory คือ byte array ต่อเนื่องผืนเดียว** (`Vec<u8>` ที่ขยายขนาดได้ทีละ "หน้า" หน้าละ 64 KiB) ที่
> WASM module หนึ่งตัวมองเห็น — **pointer ในโลก WASM ไม่ใช่อะไรมากไปกว่าตัวเลข index (offset) เข้าไปใน byte
> array ผืนนี้**

นี่คือจุดที่ Part 42 มาบรรจบกับ WASM ได้อย่างสวยงาม: raw pointer ใน Rust (`*const T`/`*mut T`) ที่ Part 42
อธิบายว่า "แค่ที่อยู่ในหน่วยความจำ ไม่มีอะไรมากไปกว่านั้น" — เมื่อ Rust compile เป็น target `wasm32-unknown-
unknown` **pointer เหล่านั้นกลายเป็นตัวเลข `u32` ที่เป็น offset เข้าไปใน linear memory โดยตรง แบบเดียวกันเป๊ะ**
(คำว่า `wasm32` ในชื่อ target บอกอยู่แล้วว่า address space เป็นแบบ 32-bit — `usize` บน target นี้จึงมีขนาด 4
ไบต์ ไม่ใช่ 8 ไบต์แบบ `x86_64` ที่ใช้กันทั่วไป) ไม่มี virtual memory ที่ OS จัดการซับซ้อนแบบโปรแกรม native — มี
แค่ byte array ผืนเดียวที่โตขึ้นได้เมื่อโปรแกรมขอเพิ่ม (ผ่าน instruction `memory.grow`) และตัวเลข offset ที่ชี้
เข้าไปในนั้น

ผลจากโมเดลนี้ที่สำคัญมาก: **JavaScript ฝั่ง host มองเห็น linear memory ของ WASM module เป็นแค่
`ArrayBuffer`** — คุณสามารถ wrap มันด้วย `Uint8Array`/`Int32Array`/etc. ของ JavaScript แล้วอ่าน/เขียนไบต์ดิบ
เข้าไปตรง ๆ ได้ (จะเห็นตัวอย่างจริงในหัวข้อ 86.7) นี่คือกลไกพื้นฐานที่ทำให้การส่งข้อมูลข้าม WASM/JavaScript
เป็นไปได้เลย — ทุกอย่างสุดท้ายคือ**การอ่าน/เขียนไบต์ในผืนความจำเดียวกันที่ทั้งสองฝั่งมองเห็นร่วมกัน**

**ทำไมโมเดลนี้ตรงกับ Rust เป็นพิเศษ**: Rust คุ้นเคยกับการคิดเรื่องหน่วยความจำแบบ "ที่อยู่ + ขนาด + layout ที่
รู้แน่นอน" มาตั้งแต่ Part 42 อยู่แล้ว (สำหรับสร้าง safe abstraction อย่าง `MyVec<T>`) เมื่อเจอ WASM ที่ยกระดับ
โมเดลนี้ขึ้นไปอีกขั้น (จาก "virtual address space ที่ OS จัดการ" มาเป็น "byte array ผืนเดียวที่ง่ายกว่าด้วยซ้ำ")
มันไม่ใช่แนวคิดใหม่ที่ต้องเรียนรู้ตั้งแต่ต้น — มันคือแนวคิดเดียวกันที่**ง่ายลง** เพราะ Rust ไม่ต้องมี runtime มา
คอย "แปลความหมาย" pointer ให้ซับซ้อนกว่าที่ WASM ให้มา (ต่างจากภาษาที่มี GC ที่ runtime ต้องคอยแปล "object
reference" ของภาษานั้นให้เป็น offset ใน linear memory อีกชั้นหนึ่งเสมอ)

#### เปรียบเทียบกับภาษาอื่นที่ Compile เป็น WASM ได้: ใครต้องพก Runtime ไปด้วยบ้าง

สรุปเป็นตารางให้เห็นภาพรวมของระบบนิเวศทั้งหมด ไม่ใช่แค่ Rust กับ Go/C# ที่พูดถึงไปแล้ว — ภาษาที่นิยม compile
เป็น WASM มีสเปกตรัมของ "ภาระที่ต้องพกไปด้วย" ต่างกันชัดเจนตามว่ามี GC/runtime หนักแค่ไหน:

| ภาษา | มี GC ในตัวหรือไม่ | สิ่งที่ต้องพกไปกับ `.wasm` | ขนาด Binary โดยรวม (เทียบเชิงคุณภาพ) |
|---|---|---|---|
| **Rust** | ไม่มี — ownership ที่ compile time | แทบไม่มีอะไรเพิ่มนอกจาก logic ของโปรแกรมเอง (บวก allocator ขนาดเล็กที่ Rust std เตรียมไว้) | **เล็กที่สุด** — โปรแกรมเปล่า ๆ ได้ระดับร้อยไบต์ถึงไม่กี่กิโลไบต์ |
| **C / C++ (ผ่าน Emscripten)** | ไม่มี (จัดการหน่วยความจำเองแบบ manual เหมือนกัน) | คล้าย Rust มาก เพราะไม่มี GC ให้ต้องแนบ แต่ Emscripten อาจแนบ helper library เพิ่มเติมสำหรับจำลอง POSIX API บางส่วนถ้าโค้ดเรียกใช้ | เล็ก ใกล้เคียง Rust ในกรณีทั่วไป |
| **AssemblyScript** | ไม่มี GC เต็มรูปแบบแบบ Go (ออกแบบมาให้เขียนคล้าย TypeScript แต่ compile ตรงเป็น WASM โดยเจตนาให้เบาที่สุด) | runtime เล็กมากสำหรับจัดการ memory แบบพื้นฐาน | เล็ก — ถูกออกแบบมาแข่งกับ Rust/C ในแง่ขนาดโดยตรง |
| **Go** | **มี** (GC แบบ concurrent mark-and-sweep เต็มรูปแบบ) | **ต้องพก Go runtime ทั้งชุด** (GC, goroutine scheduler) ไปด้วยเสมอ | **ใหญ่กว่ามาก** แม้โปรแกรมจะเล็กแค่ไหนก็ตาม (เป็นที่รู้จักกันดีในวงการว่า "Hello World" ของ Go ที่ compile เป็น WASM มีขนาดหลาย MB) |
| **C# (Blazor WebAssembly)** | **มี** (.NET GC เต็มรูปแบบ) | **ต้องพก .NET runtime บางส่วน** ไปด้วย (แม้เวอร์ชันใหม่จะพยายาม trim ให้เล็กลงมากแล้วผ่านเทคนิคอย่าง AOT compilation และ trimming) | ใหญ่ — เป็นเหตุผลหลักที่ผู้ใช้ Blazor WebAssembly มักเจอ "loading..." นานกว่าที่ควรในการโหลดครั้งแรก |

**ข้อสังเกตที่สำคัญ**: ตำแหน่งของ Rust ในตารางนี้ไม่ใช่เรื่องบังเอิญหรือการโฆษณาเกินจริง — มันเป็นผลตรงจาก
การออกแบบภาษาที่ **ไม่มี GC มาตั้งแต่ต้น** (ตัดสินใจมาตั้งแต่ Part 6 ที่สอนเรื่อง ownership) เมื่อไม่มี GC ก็ไม่มี
อะไรให้ต้อง "พกไปด้วย" ในตัว WASM binary เลย — นี่คือเหตุผลที่บทความ/การพูดคุยในวงการเกี่ยวกับ Rust+WASM มักพูด
ถึงเรื่องนี้เป็นข้อได้เปรียบอันดับต้น ๆ เสมอ ไม่ใช่แค่เรื่อง "ความเร็วในการคำนวณ" อย่างเดียว

#### พิสูจน์ด้วยโค้ดจริง: Linear Memory โตขึ้นได้ผ่าน `memory.grow`

แนวคิดเรื่อง linear memory ที่อธิบายมาทั้งหมดไม่ต้องเชื่อแบบลอย ๆ — ลองพิสูจน์ว่ามัน **"โตขึ้นได้เมื่อโปรแกรม
ขอเพิ่ม"** จริงตามที่บอกไว้ เขียนฟังก์ชันที่จองหน่วยความจำก้อนใหญ่ (ใหญ่กว่าที่ linear memory เริ่มต้นมีให้แน่ ๆ)
แล้ววัดขนาด `memory.buffer` ก่อน/หลังเรียก:

```rust
#[no_mangle]
pub extern "C" fn allocate_big_buffer(n_bytes: usize) -> *mut u8 {
    let mut v: Vec<u8> = Vec::with_capacity(n_bytes);
    v.resize(n_bytes, 0);
    let ptr = v.as_mut_ptr();
    std::mem::forget(v); // ตั้งใจไม่คืนหน่วยความจำ เพื่อให้ตัวอย่างนี้เรียบง่ายที่สุด
    ptr
}
```

เรียกจาก Node.js ขอพื้นที่ 2 MiB (2 × 1024 × 1024 ไบต์ — มากกว่าที่ linear memory เริ่มต้นมีให้แน่นอน):

```javascript
console.log("ขนาด memory ก่อนขอพื้นที่เพิ่ม:", instance.exports.memory.buffer.byteLength);
const ptr = instance.exports.allocate_big_buffer(2 * 1024 * 1024);
console.log("ptr ที่ได้กลับมา:", ptr);
console.log("ขนาด memory หลังขอพื้นที่เพิ่ม:", instance.exports.memory.buffer.byteLength);
```

ผลลัพธ์จริงที่ได้ (คัดลอกตรงจากการรัน):

```
ขนาด memory ก่อนขอพื้นที่เพิ่ม: 1114112
ptr ที่ได้กลับมา: 1114120
ขนาด memory หลังขอพื้นที่เพิ่ม: 3276800
```

ตัวเลขเหล่านี้ยืนยันทฤษฎีในหัวข้อนี้ได้ครบทุกจุด:

1. **`1114112` ไบต์ ก่อนขอเพิ่ม** — หารด้วยขนาดหน้า (64 KiB = 65,536 ไบต์) ได้ **17 หน้าพอดี** (`1114112 / 65536
   = 17`) ตรงตามที่หัวข้อนี้อธิบายไว้ว่า linear memory จัดสรรเป็น "หน้า" ขนาดคงที่ ไม่ใช่ไบต์เดี่ยว ๆ
2. **`ptr = 1114120`** — เป็นตัวเลข**มากกว่า** ขนาด memory เดิม (1,114,112) เล็กน้อย ยืนยันตรงตามที่บอกไว้ว่า
   pointer ใน Rust ที่ compile เป็น WASM **คือตัวเลข offset เข้าไปใน linear memory โดยตรง** ไม่ใช่ "ที่อยู่" ใน
   ความหมายอื่นใดเลย — ตำแหน่งที่ Rust allocator เลือกจองให้อยู่ท้าย ๆ ของพื้นที่ที่มีอยู่แล้วพอดี
3. **`3276800` ไบต์ หลังขอเพิ่ม** — หารด้วย 65,536 ได้ **50 หน้าพอดี** — memory **โตขึ้นจริงจาก 17 หน้าเป็น 50
   หน้า** (เพิ่มขึ้น 33 หน้า ครอบคลุม 2 MiB ที่ขอไปพอดีแล้วเผื่อไว้อีกเล็กน้อยตามอัลกอริทึมของ allocator) —
   เบื้องหลังคือ Rust allocator เรียก instruction ระดับต่ำของ WASM ชื่อ `memory.grow` (ที่เห็นเป็นแนวคิดในไฟล์
   WAT ของหัวข้อก่อนหน้า แม้จะไม่ได้ปรากฏตรง ๆ ในตัวอย่างเล็ก ๆ นั้นเพราะไม่มีการจองหน่วยความจำแบบ dynamic)
   เพื่อขอ**หน้าเพิ่ม**จาก host — และที่สำคัญคือ **`instance.exports.memory.buffer` (object `ArrayBuffer` ของ
   JavaScript) ก็ขนาดโตขึ้นตามไปด้วยโดยอัตโนมัติ** เพราะมันคือผืนความจำเดียวกันกับที่ WASM มองเห็น ไม่ใช่สอง
   หน่วยความจำที่แยกจากกันแล้วต้อง sync

นี่คือหลักฐานที่จับต้องได้ว่า **linear memory ไม่ใช่แนวคิดเชิงทฤษฎี** — มันคือกลไกจริงที่ Rust allocator พึ่งพา
อยู่ทุกครั้งที่คุณเขียน `Vec::new()`/`String::new()`/`Box::new()` ในโค้ดที่ compile เป็น `wasm32-unknown-
unknown` และ JavaScript ฝั่ง host ก็เห็นการเปลี่ยนแปลงนี้แบบ real-time ผ่าน `ArrayBuffer` เดียวกันเสมอ

### 86.3 ติดตั้งเครื่องมือ: `rustup target add` และ `wasm-pack`

ถึงเวลาลงมือจริง — ทุกคำสั่งในหัวข้อนี้ถูกรันจริงแล้วในสภาพแวดล้อมที่ใช้เขียนบทนี้ ผลลัพธ์ที่แสดงคือผลลัพธ์จริง
ไม่ใช่คำสั่งที่คาดเดาไว้

#### ขั้นที่ 1: เพิ่ม compilation target `wasm32-unknown-unknown`

Rust toolchain ที่ติดตั้งผ่าน `rustup` โดย default จะมีแค่ target ของเครื่องที่คุณใช้อยู่ (เช่น
`x86_64-unknown-linux-gnu`) — การ compile เป็น WASM ต้องเพิ่ม target ใหม่เข้าไปก่อน:

```bash
rustup target add wasm32-unknown-unknown
```

ผลลัพธ์จริงจากการรัน (ถ้าเพิ่ม target นี้ไปแล้วก่อนหน้า จะได้ข้อความแบบนี้):

```
info: component rust-std for target wasm32-unknown-unknown is up to date
```

หรือถ้ายังไม่มี จะเห็นข้อความดาวน์โหลด:

```
info: downloading component 'rust-std' for 'wasm32-unknown-unknown'
info: installing component 'rust-std' for 'wasm32-unknown-unknown'
```

ชื่อ target `wasm32-unknown-unknown` อ่านตามรูปแบบเดียวกับ target triple อื่น ๆ ที่ Rust ใช้
(`arch-vendor-os`): `wasm32` คือ architecture (WASM แบบ 32-bit address space), `unknown` (vendor) หมายถึง
"ไม่ระบุผู้ผลิตแพลตฟอร์มเจาะจง", `unknown` (OS) หมายถึง **"ไม่มี OS อยู่เบื้องหลังเลย"** — นี่คือจุดสำคัญที่ทำให้
มันต่างจาก target อื่น ๆ ที่เคยใช้มาตลอดหลักสูตร: ไม่มี filesystem, ไม่มี network socket, ไม่มี thread ของ OS
ให้ใช้ตรง ๆ (หัวข้อ "กับดักที่พบบ่อย" ข้อ 3 ท้ายบทจะพิสูจน์ผลของเรื่องนี้ด้วยโค้ดจริง)

#### ขั้นที่ 2: ติดตั้ง `wasm-pack`

การ compile ด้วย `cargo build --target wasm32-unknown-unknown` ตรง ๆ ได้ไฟล์ `.wasm` ดิบ ๆ ออกมาก็จริง (จะลอง
ทำในหัวข้อ 86.4) แต่ในทางปฏิบัติ ทีมส่วนใหญ่ใช้ **`wasm-pack`** — เครื่องมือที่ครอบขั้นตอนทั้งหมดที่ต้องทำซ้ำ
ทุกครั้ง (compile → เรียก `wasm-bindgen` เพื่อสร้าง JS glue code → จัดไฟล์ให้พร้อม publish เป็น npm package)
ให้เป็นคำสั่งเดียว

ติดตั้งผ่าน `cargo install`:

```bash
cargo install wasm-pack --locked
```

ผลลัพธ์จริงจากการรัน (ตัดส่วน compile dependency ที่ยาวออก เหลือบรรทัดสำคัญ):

```
   Compiling wasm-pack v0.15.0
    Finished `release` profile [optimized] target(s) in 1m 30s
  Installing /root/.cargo/bin/wasm-pack
   Installed package `wasm-pack v0.15.0` (executable `wasm-pack`)
```

ตรวจสอบเวอร์ชันที่ติดตั้งจริง:

```bash
wasm-pack --version
```
```
wasm-pack 0.15.0
```

**หมายเหตุ**: `wasm-pack` ยังมีวิธีติดตั้งอื่น เช่น สคริปต์ `curl ... | sh` ที่ดาวน์โหลด binary สำเร็จรูปมาให้
ตรง ๆ (เร็วกว่าเพราะไม่ต้อง compile) ตามที่หน้าเอกสารทางการของ `wasm-pack` แนะนำ — แต่ `cargo install` เป็นวิธี
ที่ portable ที่สุดเพราะไม่ต้องพึ่งสคริปต์ติดตั้งเฉพาะแพลตฟอร์ม และสอดคล้องกับเครื่องมือที่ใช้มาตลอดหลักสูตร
(`cargo install` แบบเดียวกับที่ Part 5 ใช้ติดตั้ง `cargo-clippy`/formatter เสริม)

#### ขั้นที่ 3: สร้างโปรเจกต์ library เปล่า ๆ

WASM ที่จะ export function ให้ JavaScript เรียกได้ **ต้องเป็น library ไม่ใช่ binary** (executable ที่มี `fn
main()` ไม่มีความหมายในบริบทของเบราว์เซอร์ — ไม่มีใครมา "รัน `main`" ตรง ๆ แบบโปรแกรม command line) จึงต้องสร้าง
โปรเจกต์ด้วยแฟล็ก `--lib`:

```bash
cargo new --lib wasm_demo
cd wasm_demo
```

ได้โครงสร้างไฟล์มาตรฐาน (`Cargo.toml` + `src/lib.rs`) เหมือนที่ Part 2 สอนไว้ทุกประการ — สิ่งที่ต้องเพิ่มเข้าไป
เองคือ key `[lib] crate-type = ["cdylib"]` ใน `Cargo.toml` (จะอธิบายเหตุผลในหัวข้อถัดไปตอนลงมือ compile จริง)

### 86.4 ตัวอย่างแรก: Export ฟังก์ชันแบบดิบ ไม่มีตัวช่วยใด ๆ และพิสูจน์ Round Trip จริง

ก่อนจะไปแตะ `wasm-bindgen` (ตัวช่วยเต็มรูปแบบที่ `wasm-pack` ใช้ ซึ่ง Part 87 จะสอนละเอียด) มาดูก่อนว่า "WASM ดิบ
ๆ" หน้าตาเป็นยังไงโดยไม่มีตัวช่วยอะไรเลย — เพื่อให้เห็นภาพว่า WASM รู้จักอะไรบ้างในระดับต่ำที่สุดจริง ๆ

#### เขียนฟังก์ชัน `add` แบบ `extern "C"`

แก้ `Cargo.toml` ให้เป็น library แบบ `cdylib` (**c**ompiled **dy**namic **lib**rary — รูปแบบที่ WASM ต้องการ
เพื่อให้ export function เป็น WASM export จริง ไม่ใช่แค่ Rust ABI ภายใน) และตั้ง `opt-level = 3` ไว้ก่อน (จะ
เปลี่ยนไปเน้นขนาดในหัวข้อ 86.8):

```toml
[package]
name = "wasm_demo"
version = "0.1.0"
edition = "2021"

[lib]
crate-type = ["cdylib"]

[profile.release]
opt-level = 3
```

`src/lib.rs`:

```rust
// #[no_mangle] บอก compiler ว่า "ห้ามเปลี่ยนชื่อฟังก์ชันนี้ตอน compile" (ปกติ Rust จะเปลี่ยนชื่อฟังก์ชัน
// เป็นรูปแบบภายในที่มี hash ต่อท้ายเพื่อรองรับ generic/overload -- ที่นี่เราต้องการให้ชื่อ "add" คงเดิม
// เป๊ะ ๆ เพราะ JavaScript จะเรียกมันด้วยชื่อนี้ตรง ๆ)
//
// extern "C" บอกว่าฟังก์ชันนี้ใช้ ABI (calling convention) แบบ C -- WASM export ต้องใช้ ABI แบบนี้
// เพื่อให้ host (เบราว์เซอร์/Node.js) เรียกมันได้อย่างถูกต้องตามมาตรฐาน
#[no_mangle]
pub extern "C" fn add(a: i32, b: i32) -> i32 {
    a + b
}
```

สังเกตว่าฟังก์ชันนี้ใช้แค่ **`i32`** — ไม่มี `String`, ไม่มี `struct`, ไม่มี `Vec` เลย นี่ไม่ใช่ความบังเอิญ
หัวข้อ 86.7 จะอธิบายว่าทำไมถึงจำกัดตัวเองไว้แบบนี้

Compile ตรง ๆ ด้วย `cargo build` (ไม่ใช้ `wasm-pack` เลยในขั้นนี้ เพื่อเห็นผลลัพธ์ดิบที่สุด):

```bash
cargo build --release --target wasm32-unknown-unknown
```

#### พิสูจน์ Round Trip จริงด้วย Node.js `WebAssembly` API

นี่คือจุดสำคัญของหัวข้อนี้: **พิสูจน์ว่า WASM binary ที่ compile จาก Rust รันได้จริงและให้ผลลัพธ์ที่ถูกต้อง**
โดยไม่ต้องมี `wasm-bindgen` หรือตัวช่วยอะไรเลย ใช้แค่ **`WebAssembly` API มาตรฐาน** ที่มีอยู่ทั้งใน Node.js และ
ในเบราว์เซอร์ทุกตัว (มันคือ API เดียวกัน — เบราว์เซอร์ implement `WebAssembly` object แบบเดียวกับที่ V8 ใน
Node.js implement เพราะทั้งคู่ใช้เอนจิน V8 เหมือนกัน)

```javascript
// verify.mjs -- รันด้วย: node verify.mjs
import { readFile } from "node:fs/promises";

const bytes = await readFile("./target/wasm32-unknown-unknown/release/wasm_demo.wasm");
const { instance } = await WebAssembly.instantiate(bytes, {});

console.log("exports:", Object.keys(instance.exports));
console.log("add(2, 3) =", instance.exports.add(2, 3));
```

รันจริงด้วย `node verify.mjs` ผลลัพธ์จริงที่ได้:

```
exports: [ 'memory', 'add', '__data_end', '__heap_base' ]
add(2, 3) = 5
```

**นี่คือ round trip ที่สมบูรณ์**: โค้ด Rust `fn add(a: i32, b: i32) -> i32 { a + b }` ถูก compile เป็น binary
WASM แล้วถูกโหลดและเรียกจาก **JavaScript runtime จริง (V8 engine ตัวเดียวกับที่ขับเคลื่อน Google Chrome)** ผ่าน
`WebAssembly.instantiate()` มาตรฐาน แล้วได้ผลลัพธ์ `5` ตรงตามที่คาด — ไม่มีการจำลองหรือ mock อะไรเลยในขั้นตอนนี้

สังเกตรายการ `exports` ที่ได้: นอกจาก `add` ที่เราเขียนแล้ว ยังมี `memory` (คือ linear memory ที่หัวข้อ 86.2
อธิบายไว้ — WASM export มันออกมาให้ host มองเห็นและแก้ไขได้โดยตรงในรูปแบบ `ArrayBuffer`), `__data_end` และ
`__heap_base` (ตัวเลขที่ Rust runtime ใช้บอกขอบเขตของข้อมูลที่ compile ไว้ล่วงหน้า กับจุดเริ่มต้นของ heap ที่ยัง
ว่างให้จองเพิ่ม — ส่วนหนึ่งของ "โครงกระดูก" ขั้นต่ำที่ Rust ต้องมีเพื่อให้ allocator ทำงานได้แม้ในโลกที่ไม่มี OS)

#### เปิดดูเนื้อในไฟล์ `.wasm` จริง ๆ ด้วย `wasm2wat`: พิสูจน์ว่า WASM เป็น Stack Machine

หัวข้อ 86.1 บอกไว้ว่า WASM เป็น "stack machine ที่ type ชัดเจนตายตัว" — ข้อความนี้ไม่ต้องเชื่อแบบลอย ๆ เพราะ
พิสูจน์ได้จริงด้วยเครื่องมือแปลงไฟล์ binary `.wasm` กลับเป็น**ข้อความที่อ่านได้ (WAT — WebAssembly Text
Format)** ชื่อ `wasm2wat` (ส่วนหนึ่งของชุดเครื่องมือ **WABT — WebAssembly Binary Toolkit**) ลองสร้างโปรเจกต์
ที่มีแค่ฟังก์ชัน `add` ตัวเดียว (ไม่มี `get_greeting` ปนเพื่อให้ output อ่านง่ายที่สุด) compile ด้วย `opt-level
= "z", lto = true, strip = true` แล้วแปลงกลับเป็น WAT:

```bash
wasm2wat target/wasm32-unknown-unknown/release/tiny_add.wasm
```

ผลลัพธ์จริงที่ได้ (คัดลอกตรงจากการรัน ไม่มีการแก้ไข):

```wat
(module
  (type (;0;) (func (param i32 i32) (result i32)))
  (func (;0;) (type 0) (param i32 i32) (result i32)
    local.get 1
    local.get 0
    i32.add)
  (table (;0;) 1 1 funcref)
  (memory (;0;) 16)
  (global (;0;) (mut i32) (i32.const 1048576))
  (global (;1;) i32 (i32.const 1048576))
  (global (;2;) i32 (i32.const 1048576))
  (export "memory" (memory 0))
  (export "add" (func 0))
  (export "__data_end" (global 1))
  (export "__heap_base" (global 2)))
```

นี่คือ**เนื้อในทั้งหมด**ของไฟล์ `.wasm` ที่ compile จากฟังก์ชัน `add(a, b) { a + b }` เพียงบรรทัดเดียว — มาไล่ดู
ทีละส่วนเพื่อยืนยันแนวคิดที่อธิบายไว้ในหัวข้อ 86.1 และ 86.7:

- **`(type (;0;) (func (param i32 i32) (result i32)))`** — คือ **signature ของฟังก์ชัน** ที่ประกาศไว้ล่วงหน้า
  แยกจาก body ของฟังก์ชันเอง (`type section` ของไฟล์ WASM) สังเกตว่า type ที่ใช้ได้มีแค่ `i32` — ตรงตามที่
  หัวข้อ 86.7 อธิบายไว้ว่า WASM รู้จักแค่ `i32`/`i64`/`f32`/`f64` เท่านั้น ไม่มีแนวคิดเรื่อง "string" หรือ
  "struct" ในระดับ type ของ instruction เลย
- **`local.get 1` / `local.get 0` / `i32.add`** — คือ**ตัว body ของฟังก์ชันในรูปแบบ stack machine ตัวจริง**:
  `local.get 1` ดัน parameter ตัวที่สอง (index เริ่มจาก 0 คือ `b`) ขึ้นไปบน**stack**, `local.get 0` ดัน
  parameter ตัวแรก (`a`) ขึ้นไปทับอีกที, `i32.add` **ดึงค่าสองตัวบนสุดของ stack ออกมาบวกกัน แล้วดันผลลัพธ์กลับ
  เข้า stack** — ไม่มีแนวคิดเรื่อง "register" หรือ "ตัวแปรที่มีชื่อ" ในระดับ instruction เหมือนภาษาเครื่องของ
  CPU จริงอย่าง x86 เลย ทุกการคำนวณผ่านการ push/pop เข้า-ออกจาก stack ทีละค่า — นี่คือความหมายของคำว่า
  "**stack machine**" ที่หัวข้อ 86.1 พูดถึง (สังเกตด้วยว่าลำดับ `local.get 1` ก่อน `local.get 0` ไม่ใช่ความ
  ผิดพลาด — `i32.add` เป็นการบวกที่ลำดับไม่มีผลกับผลลัพธ์ compiler เลือกลำดับที่ให้ code เล็ก/เร็วที่สุดตามที่
  เห็นเหมาะสม)
- **`(memory (;0;) 16)`** — ประกาศ **linear memory** เริ่มต้นที่ 16 หน้า (แต่ละหน้า = 64 KiB ตามมาตรฐาน WASM
  ดังนั้นนี่คือ 1 MiB) แม้โปรแกรมนี้จะไม่ได้จองหน่วยความจำแบบ dynamic เลยก็ตาม (ไม่มี `Vec`/`String` ในโค้ด) —
  นี่คือ**พื้นที่ตั้งต้น**ที่ Rust runtime เตรียมไว้เผื่อใช้ (allocator ของ Rust ต้องมีพื้นที่ให้ทำงานแม้จะยังไม่
  ถูกใช้จริงในโปรแกรมนี้)
- **`(export "memory" ...)` / `(export "add" ...)`** — คือ **export section** ที่บอกว่า WASM module นี้เปิดให้
  host มองเห็นอะไรได้บ้างจากภายนอก ตรงกับที่เห็นในผลลัพธ์ `exports: [...]` ของ Node.js ข้างบนทุกประการ (memory,
  add, และตัวแปร global สองตัวที่ Rust ใช้ภายใน)

การเห็นเนื้อในแบบนี้ตรง ๆ ช่วยยืนยันสิ่งที่บทนี้อธิบายมาตลอดด้วยหลักฐานจริง ไม่ใช่แค่คำอธิบายเชิงทฤษฎี: **WASM
ไม่มีอะไรซับซ้อนไปกว่า instruction ตัวเลขไม่กี่ประเภทที่ทำงานบน stack และ linear memory ผืนเดียว** — ความ
ซับซ้อนทั้งหมดที่เห็นเมื่อใช้ `wasm-bindgen`/framework ระดับสูงในบทต่อ ๆ ไปของโมดูลนี้ ล้วนสร้างขึ้นมาบนพื้นฐาน
ที่เรียบง่ายเท่านี้เอง

### 86.5 `wasm-pack build` เต็มรูปแบบ: ไฟล์ที่ได้จริงและหน้าที่ของแต่ละไฟล์

หัวข้อก่อนหน้าโชว์ WASM แบบดิบที่สุด — แต่ในทางปฏิบัติแทบไม่มีใครทำงานแบบนั้นตรง ๆ เพราะการเรียก
`WebAssembly.instantiate()` มือทุกครั้งพร้อมจัดการ memory เองมันยุ่งยากเกินไปสำหรับโปรเจกต์จริง `wasm-pack`
ร่วมกับ `wasm-bindgen` (Part 87 จะสอนกลไกเบื้องหลังของมันละเอียด) ช่วยสร้าง**เลเยอร์ที่ใช้งานง่ายกว่ามาก**ให้
อัตโนมัติ

#### เพิ่ม `wasm-bindgen` และสั่ง build

สร้างโปรเจกต์ใหม่ (หรือแก้โปรเจกต์เดิม) ให้มี dependency `wasm-bindgen`:

```toml
[package]
name = "wasm_bindgen_demo"
version = "0.1.0"
edition = "2021"

[lib]
crate-type = ["cdylib"]

[dependencies]
wasm-bindgen = "0.2"
```

`src/lib.rs`:

```rust
use wasm_bindgen::prelude::*;

// #[wasm_bindgen] คือ attribute macro ที่ wasm-bindgen ใช้ -- มันทำหน้าที่คล้าย #[no_mangle] extern "C"
// ในหัวข้อก่อนหน้า แต่เก่งกว่ามาก: มันสร้างโค้ด "ตัวกลาง" ให้ทั้งฝั่ง Rust และฝั่ง JavaScript ที่แปลง type
// ที่ซับซ้อนกว่าตัวเลขให้ข้ามพรมแดนได้อัตโนมัติ (กลไกเบื้องหลังเต็มรูปแบบคือเนื้อหาทั้งหมดของ Part 87 --
// บทนี้ใช้มันแค่ในระดับ "เห็นว่ามันมีอยู่และทำอะไรได้" เพื่อโชว์ผลลัพธ์ที่ wasm-pack build ให้มา)
#[wasm_bindgen]
pub fn add(a: i32, b: i32) -> i32 {
    a + b
}
```

สั่ง build ด้วย `wasm-pack` (ระบุ `--target web` เพื่อให้ได้ ES module ที่ import ตรงในหน้า HTML ได้ทันทีโดยไม่
ต้องผ่าน bundler เช่น webpack — เป็น target ที่ตรงไปตรงมาที่สุดสำหรับตัวอย่างแรก):

```bash
wasm-pack build --target web
```

| **`package.json`** | ไฟล์มาตรฐานของ npm package — ทำให้โฟลเดอร์ `pkg/` นี้**พร้อม publish เป็น npm package** ได้ทันที (`npm publish` จากในโฟลเดอร์นี้) หรือให้โปรเจกต์ frontend อื่นติดตั้งผ่าน `npm install ../path/to/pkg` ได้ตรง ๆ |

```typescript
    readonly __wbindgen_start: () => void;
}
// ... (ฟังก์ชัน initSync / default export สำหรับโหลดโมดูล ถูกตัดออกเพื่อความกระชับ)
```

สังเกตสองจุด: (1) `i32` ของ Rust ถูกแปลงเป็น `number` ของ TypeScript ตรง ๆ (JavaScript/TypeScript ไม่มีแยก type
ตัวเลขเป็น i32/i64/f32/f64 แบบ Rust — มี `number` ตัวเดียวที่ครอบคลุมทุกกรณี ยกเว้น `i64`/`u64` ที่
`wasm-bindgen` แปลงเป็น `bigint` แทนเพื่อไม่ให้เสีย precision — รายละเอียดเรื่องการแปลง type แต่ละแบบคือเนื้อหา
ของ Part 87) (2) มีฟังก์ชัน/type เสริมอีกหลายตัวที่ `wasm-bindgen` generate ให้เอง (`initSync`, `InitOutput`,
`__wbindgen_start`) ที่ไม่ได้มาจากโค้ด Rust ที่เราเขียนตรง ๆ — เป็นส่วนหนึ่งของ "โครงกระดูก" ที่ JS glue code
ต้องมีเพื่อโหลดและ initialize WASM module ให้ถูกต้อง (กลไกเบื้องหลังละเอียดคือเนื้อหาของ Part 87)

#### พิสูจน์ Round Trip ในเบราว์เซอร์จริง

หัวข้อ 86.4 พิสูจน์ round trip ผ่าน Node.js ไปแล้วด้วย WASM ดิบ — ตอนนี้มาพิสูจน์กับไฟล์ที่ `wasm-pack` สร้างให้
ใน**เบราว์เซอร์จริง** สร้างไฟล์ `index.html` ในโฟลเดอร์เดียวกับ `pkg/`:

```html
<!DOCTYPE html>
<html lang="th">
<head>
  <meta charset="UTF-8">
  <title>Rust + WASM Demo</title>
</head>
<body>
  <h1>ผลลัพธ์: <span id="result">กำลังคำนวณ...</span></h1>

  <script type="module">
    // import ตรงจาก JS glue code ที่ wasm-pack build ให้ -- เพราะใช้ --target web จึงเป็น ES module
    // ที่ import ได้ตรง ๆ ในเบราว์เซอร์โดยไม่ต้องผ่าน bundler เลย
    import init, { add } from "./pkg/wasm_bindgen_demo.js";

    async function main() {
      // init() โหลดและ instantiate ไฟล์ .wasm ให้เสร็จก่อน -- ต้อง await ก่อนเรียกฟังก์ชันใด ๆ
      await init();

      const result = add(40, 2);
      console.log("add(40, 2) จาก WASM =", result);
      document.getElementById("result").textContent = String(result);
    }

    main();
  </script>
</body>
</html>
```

**สำคัญ**: ES module (`type="module"`) ที่ `import` ไฟล์อื่น **เปิดตรง ๆ ด้วย `file://` ไม่ได้** — เบราว์เซอร์
บังคับกฎ CORS ที่ปฏิเสธการ `fetch`/`import` ข้าม origin แบบ `file://` (จะเห็น error จริงในหัวข้อกับดักที่พบบ่อย
ข้อ 4) ต้อง serve ผ่าน HTTP server ธรรมดาก่อน:

```bash
npx http-server . -p 8080
```

จากนั้นเปิด `http://localhost:8080/index.html` ในเบราว์เซอร์จริง

**วิธีที่ใช้ยืนยันผลลัพธ์นี้จริงในการเขียนบทนี้**: environment ที่เขียนบทนี้ไม่มีจอแสดงผลให้เปิดเบราว์เซอร์ด้วย
มือ แต่มี **Chromium ตัวจริง** ติดตั้งไว้ล่วงหน้าผ่าน Playwright (`/opt/pw-browsers/chromium-1194`) จึงใช้สคริปต์
Node.js เปิด Chromium แบบ headless (ไม่มีหน้าต่าง แต่เป็น browser engine ตัวเดียวกับ Google Chrome เต็มรูปแบบ
ทุกกลไกภายใน ไม่ใช่ simulator) ไปโหลดหน้า `index.html` ที่ serve ผ่าน HTTP จริง แล้วดักฟัง `console.log` ที่หน้า
เว็บพิมพ์ออกมา — เทียบเท่ากับการเปิดเบราว์เซอร์ด้วยมือแล้วเปิด DevTools console ดูผลลัพธ์ทุกประการ เพียงแต่
อัตโนมัติ:

```javascript
// browser_test.cjs
const { chromium } = require("/opt/node22/lib/node_modules/playwright");

(async () => {
  const browser = await chromium.launch({
    executablePath: "/opt/pw-browsers/chromium-1194/chrome-linux/chrome",
  });
  const page = await browser.newPage();
  page.on("console", (msg) => console.log("[browser console]", msg.text()));
  page.on("pageerror", (err) => console.log("[page error]", err.message));

  await page.goto("http://localhost:8123/index.html");
  await page.waitForTimeout(800); // รอให้ init() ของ wasm-bindgen โหลดเสร็จ

  const text = await page.textContent("#result");
  console.log("DOM #result content:", text);

  await browser.close();
})();
```

ผลลัพธ์จริงที่ได้จากการรันสคริปต์นี้กับ Chromium จริง (คัดลอกตรงจากการรัน — บรรทัด 404 คือ favicon ที่เบราว์เซอร์
ขอเองตามปกติ ไม่เกี่ยวกับ WASM แต่อย่างใด แสดงไว้เพื่อความตรงไปตรงมาว่าไม่ได้ตัด output ที่ไม่สวยออก):

```
[browser console] Failed to load resource: the server responded with a status of 404 (Not Found)
[browser console] add(40, 2) จาก WASM = 42
DOM #result content: 42
```

นี่คือการพิสูจน์ที่สมบูรณ์ที่สุดของบทนี้: ไฟล์ `.wasm` ที่ compile จาก Rust ผ่าน `wasm-pack` ถูกโหลดเข้า **หน้า
เว็บ HTML จริงที่รันใน Chromium ตัวจริง** เรียกใช้งานผ่าน JavaScript glue code ที่ generate ให้ แล้วผลลัพธ์
`42` ที่คำนวณได้จาก Rust ถูกแสดงบน DOM ของหน้าเว็บได้สำเร็จ — round trip เต็มรูปแบบตั้งแต่ Rust source code จน
ถึงหน้าจอในเบราว์เซอร์

#### อีกวิธีในการทดสอบ: `wasm-pack test --node` (ไม่ต้องพึ่งเบราว์เซอร์เลย)

การเปิดเบราว์เซอร์จริงแบบข้างบนคือวิธีพิสูจน์ที่สมบูรณ์ที่สุด แต่ไม่ใช่ทุกสภาพแวดล้อมที่มีเบราว์เซอร์ (หรือ
Chromium headless) ให้ใช้สะดวก `wasm-pack` มีคำสั่งทดสอบในตัวที่รันผ่าน **Node.js อย่างเดียว ไม่ต้องพึ่ง
เบราว์เซอร์เลย** — เหมาะสำหรับ CI pipeline ที่อาจไม่มี browser driver ติดตั้งไว้ หรือเครื่องที่ไม่มีจอแสดงผล

เพิ่ม dev-dependency `wasm-bindgen-test` และเขียน test แบบเดียวกับ `#[test]` ปกติที่ Part 20 สอนไว้ (แค่เปลี่ยน
attribute เป็น `#[wasm_bindgen_test]`):

```toml
[dev-dependencies]
wasm-bindgen-test = "0.3"
```

```rust
use wasm_bindgen::prelude::*;

#[wasm_bindgen]
pub fn add(a: i32, b: i32) -> i32 {
    a + b
}

#[cfg(test)]
mod tests {
    use super::*;
    use wasm_bindgen_test::*;

    #[wasm_bindgen_test]
    fn test_add() {
        assert_eq!(add(40, 2), 42);
    }
}
```

รันด้วย:

```bash
wasm-pack test --node
```

ผลลัพธ์จริงจากการรัน (ตัดขั้นตอน compile dependency ที่ยาวออก เหลือส่วนสำคัญ):

```

    Finished `dev` profile [unoptimized + debuginfo] target(s) in 23.46s
[INFO]: Installing wasm-bindgen...
    Finished `test` profile [unoptimized + debuginfo] target(s) in 0.03s
```

**ข้อสังเกต**: `wasm-pack test --node` ทำงานโดย compile test เป็น WASM เหมือนเดิม แล้วรันผ่าน Node.js
`WebAssembly` API เบื้องหลัง (แนวคิดเดียวกับสคริปต์ `verify.mjs` มือ ๆ ในหัวข้อ 86.4 ทุกประการ แต่ `wasm-pack`
จัดการให้ครบทั้งการ compile, การโหลด, และการรายงานผลแบบ `cargo test` ที่คุ้นเคย) — ยังมีแฟล็ก `--chrome`/
`--firefox`/`--safari` สำหรับรัน test ผ่านเบราว์เซอร์จริงถ้าต้องการทดสอบ API ที่พึ่งพา DOM/Web API ที่ Node.js
ไม่มี (เช่น `web-sys` ที่เรียก `document.getElementById`) แต่สำหรับ logic ล้วน ๆ ที่ไม่ยุ่งกับ DOM แบบ `add`
ในตัวอย่างนี้ `--node` เพียงพอและเร็วกว่ามาก

#### `--target` ของ `wasm-pack build` มีมากกว่าหนึ่งแบบ: เลือกให้ตรงกับที่ใช้จริง

ตัวอย่างในบทนี้ใช้ `--target web` มาตลอดเพราะเป็นแบบที่ตรงไปตรงมาที่สุดสำหรับหน้า HTML ธรรมดา แต่ `wasm-pack
build` รองรับ target อื่นอีกหลายแบบ ขึ้นกับว่าโค้ด JavaScript ที่จะเรียกใช้ WASM นี้อยู่ในสภาพแวดล้อมไหน — เลือก
ผิดแบบจะทำให้ import ไม่ทำงานตามที่คาด (เช่นใช้ `import` แบบ ES module ไม่ได้ในสภาพแวดล้อมที่ไม่รองรับ):

| `--target` | ใช้เมื่อไหร่ | ลักษณะไฟล์ JS ที่ได้ |
|---|---|---|
| **`web`** | หน้า HTML ธรรมดาที่ import ตรง ๆ ด้วย `<script type="module">` โดยไม่ผ่าน bundler เลย (ตัวอย่างทั้งหมดในบทนี้ใช้แบบนี้) | ES module ที่มีฟังก์ชัน `init()` ต้อง `await` ก่อนใช้งาน export อื่น |
| **`bundler`** | โปรเจกต์ frontend ที่ใช้ bundler อย่าง webpack/Vite/Rollup (จะเจอในทางปฏิบัติเมื่อรวม WASM เข้ากับ framework อย่าง React/Vue ที่ไม่ใช่ Rust — หรือ Yew/Leptos/Dioxus ในบทถัดไปที่มักมี tooling ห่อให้อีกชั้น) | ES module ที่ bundler จัดการโหลดไฟล์ `.wasm` ให้เองตาม config ของ bundler นั้น ไม่ต้องเขียน `init()` มือ |
| **`nodejs`** | โค้ด Node.js ฝั่ง server/CLI tool (ไม่ใช่เบราว์เซอร์เลย) ที่ต้องการเรียก WASM ผ่าน `require(...)` แบบ CommonJS | ไฟล์ JS แบบ CommonJS module |
| **`no-modules`** | หน้า HTML แบบเก่าที่ยังไม่รองรับ ES module เลย (ต้องพึ่ง global variable บน `window` ตรง ๆ) | ไฟล์ JS ที่ผูก export เข้ากับ global scope ไม่ใช้ `import`/`export` เลย |

บทนี้และ Part 87 เลือกใช้ `web` เป็นหลักเพราะเข้าใจง่ายที่สุดสำหรับตัวอย่างเดี่ยว ๆ — แต่เมื่อไปถึง Part 88-90
ที่ใช้ framework เต็มรูปแบบ (Yew/Leptos/Dioxus) tooling ของแต่ละ framework มักเลือก target ที่เหมาะกับ build
pipeline ของตัวเองให้อัตโนมัติอยู่แล้ว ไม่ต้องตั้งค่าตรงนี้เองอีก

### 86.6 สามเป้าหมายการ Compile ของ WASM ในโลก Rust: อย่าสับสน Browser กับ WASI

บทนี้ใช้ target `wasm32-unknown-unknown` มาตลอด แต่ในระบบนิเวศ Rust+WASM มี target ให้เลือกมากกว่าหนึ่งแบบ และ
เป็นเรื่องที่**สับสนกันได้ง่ายมาก**สำหรับผู้เริ่มต้น เพราะชื่อคล้ายกันแต่ใช้งานคนละบริบทโดยสิ้นเชิง

| Target | ใช้ที่ไหน | มี OS-like capability ไหม | สถานะในบทนี้ |
|---|---|---|---|
| **`wasm32-unknown-unknown`** | เบราว์เซอร์ (ผ่าน `wasm-bindgen`/`wasm-pack`), หรือ JS runtime ทั่วไป (Node.js/Deno) | **ไม่มี** — ไม่มีแนวคิดเรื่องไฟล์/เครือข่ายในตัว target เอง ทุกอย่างต้องผ่าน JavaScript host เป็นตัวกลาง | **ใช้ตลอดบทนี้** — เป้าหมายคือรันในเบราว์เซอร์/frontend |
| **`wasm32-wasip1`** (เดิมชื่อ `wasm32-wasi`) | รันแบบ standalone นอกเบราว์เซอร์ ผ่าน WASM runtime อย่าง Wasmtime, Wasmer, หรือ edge platform ที่รองรับ WASI | **มี** ผ่านมาตรฐาน **WASI (WebAssembly System Interface)** — เปิดให้เข้าถึงไฟล์, environment variable, clock, random number ได้แบบพกพาข้ามแพลตฟอร์ม โดยไม่ต้องมีเบราว์เซอร์เลย | **ไม่ได้ใช้ในบทนี้** — เป็นหัวข้อของโมดูลอื่นถ้ามี เพราะโมดูล 5 นี้เน้น browser/frontend |
| **`wasm32-wasip2`** | รุ่นใหม่กว่าของ WASI (WASI Preview 2) ที่ใช้ component model และ interface types ที่ทันสมัยกว่า | มี (เวอร์ชันใหม่กว่า มาตรฐานยังพัฒนาต่อเนื่อง) | เกริ่นให้รู้จักชื่อไว้เท่านั้น |

`wasm32-wasip2` ต่างจาก `wasm32-wasip1` ในเชิงแนวคิดที่ลึกกว่าแค่เลขเวอร์ชัน — มันสร้างอยู่บน **component
model** ของ WASM ที่เพิ่งพัฒนาขึ้นมาทีหลัง แนวคิดคือให้ WASM module ประกาศ **interface** ของตัวเองแบบมีโครงสร้าง
ชัดเจนกว่าเดิม (คล้ายกับที่ Part 78 สอนเรื่องออกแบบ API ที่คาดเดาได้ แต่ในระดับของ binary interface ระหว่าง WASM
module ด้วยกันเอง) ทำให้ WASM module จากภาษาต่างกัน (Rust, Python, JavaScript ที่ compile เป็น WASM) เรียกกัน
ข้ามภาษาได้ง่ายขึ้นโดยไม่ต้องเขียน glue code เองแบบที่เห็นในหัวข้อ 86.7 — เป็นทิศทางที่น่าจับตาในระยะยาว แต่ ณ
ตอนที่เขียนบทนี้ยังไม่ใช่สิ่งที่ tooling ส่วนใหญ่ในระบบนิเวศ (รวมถึง `wasm-pack`/`wasm-bindgen` ที่บทนี้ใช้)
รองรับเป็นค่าเริ่มต้น จึงเกริ่นให้รู้จักชื่อไว้เฉย ๆ พอ ไม่ใช่สิ่งที่ต้องใช้จริงในโมดูล 5 นี้

**ประเด็นที่ต้องเข้าใจให้ชัดเพื่อไม่สับสน**: `wasm32-wasip1` **ไม่ใช่ target สำหรับรันในเบราว์เซอร์** — แม้ชื่อ
จะมีคำว่า "wasi" ที่ฟังดูเกี่ยวกับเว็บ แต่จุดประสงค์ของมันคือ**ตรงข้าม**กับ `wasm32-unknown-unknown`: มันออกแบบมา
ให้ WASM สามารถ**ทำสิ่งที่โปรแกรม native ทำได้** (เปิดไฟล์, อ่าน env var) แบบพกพา ในสภาพแวดล้อมที่**ไม่มี
เบราว์เซอร์เลย** — ใช้กันมากในบริบท server-side WASM, edge computing, หรือ plugin system ที่ต้องการให้ WASM
module เข้าถึงทรัพยากรระบบได้อย่างจำกัดและปลอดภัย (WASI ให้สิทธิ์แบบ capability-based — module ต้องได้รับสิทธิ์
เข้าถึง path/resource เจาะจงจาก host ก่อน ไม่ใช่เข้าถึงได้ทุกอย่างแบบโปรแกรม native ทั่วไป)

หากพยายามเอา WASM ที่ compile ด้วย `wasm32-wasip1` (ที่เรียกใช้ WASI import เช่นการเปิดไฟล์) ไปรันในเบราว์เซอร์
ตรง ๆ ผ่าน `WebAssembly.instantiate()` แบบธรรมดา **จะไม่ทำงาน** — เพราะเบราว์เซอร์ไม่มี WASI import เหล่านั้นให้
(ต้องมี polyfill พิเศษอย่าง `@bjorn3/browser_wasi_shim` มาเสริม ซึ่งไม่ใช่ทางเลือกที่ทีมส่วนใหญ่เลือกสำหรับงาน
frontend ทั่วไป) — และในทางกลับกัน โค้ดที่เขียนโดยหวังพึ่ง `wasm-bindgen`/DOM API (เช่นเรียก `document.
getElementById`) ก็ compile กับ `wasm32-wasip1` ไม่ได้เพราะ target นั้นไม่รู้จักแนวคิดเรื่อง DOM เลย — **สอง
target นี้คือคนละโลกที่ออกแบบมาแก้ปัญหาคนละอย่าง** โมดูล 5 ทั้งหมด (Part 86-95) เน้นไปที่โลกของ
`wasm32-unknown-unknown` เพราะเป้าหมายคือ frontend/full-stack ด้วย WASM ในเบราว์เซอร์

### 86.7 พรมแดนระหว่าง WASM กับ JavaScript: ตัวเลขข้ามได้เอง อย่างอื่นต้องมีตัวช่วย

หัวข้อ 86.2 อธิบายไปแล้วว่า linear memory คือ byte array ผืนเดียว — หัวข้อนี้จะขยายความว่า**อะไรข้ามพรมแดน
WASM/JavaScript ได้ "ฟรี" โดยไม่ต้องมีตัวช่วย และอะไรที่ต้องมี**

#### สิ่งที่ WASM รู้จักในระดับต่ำที่สุด: มีแค่ตัวเลขสี่ชนิด

พูดให้ชัดที่สุด: **instruction set ของ WASM รู้จักค่าอยู่แค่ 4 ชนิดเท่านั้น**: `i32`, `i64` (จำนวนเต็ม 32/64
บิต — ไม่แยก signed/unsigned ในระดับ storage เอง signedness เป็นเรื่องของ instruction ที่ใช้ตีความมันตอน
คำนวณ), `f32`, `f64` (เลขทศนิยม 32/64 บิต) — **ไม่มี type อื่นเลย** ไม่มี string, ไม่มี array, ไม่มี struct,
ไม่มี pointer ในความหมายที่ WASM เข้าใจเอง (pointer ที่เห็นในโค้ด Rust ก็แค่ `i32` ที่แทน offset อย่างที่หัวข้อ
86.2 อธิบายไว้)

ฟังก์ชัน `add(a: i32, b: i32) -> i32` ในหัวข้อ 86.4 ทำงานได้อย่างไม่มีปัญหาเลยเพราะมัน**อยู่ในเซตนี้พอดี** —
รับ `i32` สองตัว คืน `i32` หนึ่งตัว ไม่ต้องมีการแปลงหรือช่วยเหลืออะไรเพิ่ม เพราะทั้ง WASM instruction set และ
JavaScript number ต่างก็แทนค่าตัวเลขได้ตรง ๆ อยู่แล้ว

#### สิ่งที่ต้องมีตัวช่วย: อะไรก็ตามที่ "ซับซ้อนกว่าตัวเลขตัวเดียว"

ทันทีที่คุณต้องการส่ง `String`, `struct`, `Vec<T>`, หรือค่าอะไรก็ตามที่ไม่ใช่ตัวเลขเดี่ยว ๆ — เกิดปัญหาทันที
เพราะ WASM ไม่มีวิธี "ส่งค่า" พวกนี้ในระดับ instruction เลย มาดูให้เห็นเป็นรูปธรรมว่าเกิดอะไรขึ้นจริงถ้าลองส่ง
`String` กลับโดยไม่มีตัวช่วยใด ๆ (ไม่ใช้ `wasm-bindgen`):

```rust
#[no_mangle]
pub extern "C" fn get_greeting() -> String {
    String::from("hello from wasm")
}
```

Compile ด้วย `cargo build --release --target wasm32-unknown-unknown` — **มัน compile ผ่านจริง แต่มี warning**
ที่ตรงประเด็นมาก (คัดลอกตรงจากการรันจริง):

```
warning: `extern` fn uses type `String`, which is not FFI-safe
 --> src/lib.rs:8:37
  |
8 | pub extern "C" fn get_greeting() -> String {
  |                                     ^^^^^^ not FFI-safe
  |
  = help: consider adding a `#[repr(C)]` or `#[repr(transparent)]` attribute to this struct
  = note: this struct has unspecified layout
  = note: `#[warn(improper_ctypes_definitions)]` on by default
```

Compiler เตือนตรง ๆ ว่า `String` **ไม่ FFI-safe** — เหตุผลคือ `String` ใน Rust ไม่ใช่แค่ตัวเลขตัวเดียว มันคือ
struct ที่ข้างในมี pointer ไปยังข้อมูล + ความยาว + capacity (สามฟิลด์ ไม่ใช่ค่าเดียว) และ layout ของ struct นี้
**ไม่ได้ถูกกำหนดตายตัวไว้เป็นมาตรฐานข้ามภาษา** (`#[repr(Rust)]` ตามที่ Part 42 อธิบายไว้ — compiler มีสิทธิ์
จัดเรียง field ใหม่ยังไงก็ได้ตามที่เห็นว่าเหมาะสม) เมื่อไม่มี layout ที่แน่นอนตายตัว จะบอก host (JavaScript) ว่า
"ไปอ่านค่าตรงนี้แล้วจะได้ string" ไม่ได้เลย เพราะ host ไม่รู้ว่า struct นี้หน้าตาเป็นยังไงกันแน่

**แต่โค้ดยัง compile ผ่านได้ (เป็นแค่ warning ไม่ใช่ error)** — แล้วถ้าลองเรียกจริงจาก JavaScript จะเกิดอะไรขึ้น?
ลองด้วย Node.js `WebAssembly` API แบบเดียวกับหัวข้อ 86.4:

```javascript
const rawResult = instance.exports.get_greeting();
console.log("get_greeting() returned:", rawResult, "(typeof:", typeof rawResult, ")");
```

ผลลัพธ์จริงที่ได้:

```
get_greeting() returned: undefined (typeof: undefined )
```

**นี่คือปัญหาที่เป็นรูปธรรมที่สุด**: ไม่มี error ให้เห็นเลย แต่ผลลัพธ์ที่ได้คือ `undefined` — ไม่ใช่ string
"hello from wasm" ที่ตั้งใจจะคืนแต่อย่างใด เหตุผลเชิงเทคนิคคือ: เมื่อฟังก์ชันคืนค่าที่มีขนาดใหญ่กว่าหนึ่ง
register (เช่น struct ที่มีสามฟิลด์แบบ `String`) ABI ของ `extern "C"` บน WASM มักจะเปลี่ยนวิธีคืนค่าไปเป็นการ
**เขียนผลลัพธ์ผ่าน pointer ที่ผู้เรียกต้องเตรียมพื้นที่ไว้ล่วงหน้าแล้วส่งเข้ามาเป็น argument ซ่อน** (เทคนิคที่
เรียกว่า **sret — structure return**) — แต่เพราะเราเรียกจาก JavaScript โดยไม่รู้กลไกนี้ (ไม่ได้เตรียม/ส่ง
pointer ไหนเข้าไปเลย) การเรียกจึง "สำเร็จ" ในแง่ที่ไม่ throw exception แต่ผลลัพธ์ที่ได้ไม่มีความหมายอะไรเลย —
**นี่อันตรายกว่า error เสียอีก เพราะมันดูเหมือนทำงานได้แต่จริง ๆ ผิดโดยเงียบ ๆ**

#### ทางออกแบบ "มือ" ที่ทำได้ (แต่ยุ่งยากและเสี่ยงบั๊ก): Pointer + Length

ถ้าไม่ใช้ `wasm-bindgen` เลย แนวทางที่โปรแกรมเมอร์ C/C++ ใช้กันมานาน (และ Rust ทำได้เหมือนกัน) คือ**ส่ง string
เป็นคู่ pointer+length แทนการส่ง struct `String` ตรง ๆ**:

```rust
use std::alloc::{alloc, dealloc, Layout};

// คืนค่าเป็น pointer (offset ใน linear memory) ที่ข้อมูล string เริ่มต้น
// ผู้เรียกต้องรู้ความยาวจากที่อื่น (เช่นเรียกฟังก์ชันแยกที่คืนความยาว) แล้วมาอ่านไบต์เอาเอง
#[no_mangle]
pub extern "C" fn get_greeting_ptr() -> *const u8 {
    let s = "hello from wasm";
    s.as_ptr()
}

#[no_mangle]
pub extern "C" fn get_greeting_len() -> usize {
    "hello from wasm".len()
}
```

ฝั่ง JavaScript ต้องเรียกทั้งสองฟังก์ชัน แล้ว**อ่านหน่วยความจำดิบด้วยตัวเอง** ผ่าน `instance.exports.memory`
(ที่หัวข้อ 86.4 เห็นอยู่ใน `exports`):

```javascript
const ptr = instance.exports.get_greeting_ptr();
const len = instance.exports.get_greeting_len();
const bytes = new Uint8Array(instance.exports.memory.buffer, ptr, len);
const text = new TextDecoder("utf-8").decode(bytes);
console.log(text); // "hello from wasm"
```

วิธีนี้**ทำงานได้จริง** — และนี่คือกลไกพื้นฐานที่สุดที่ทุกการส่ง string ข้ามพรมแดน WASM/JS ต้องพึ่งพาไม่ทางใดก็
ทางหนึ่ง — แต่สังเกตว่ามันยุ่งยากและเสี่ยงบั๊กมาก: ต้องจำเรียกสองฟังก์ชันคู่กันเสมอ (ptr กับ len), ต้องรู้ว่า
string นี้ยังไม่ถูก deallocate ไปก่อนที่ JavaScript จะอ่านเสร็จ (ถ้า Rust คืนหน่วยความจำนี้กลับไปแล้ว
JavaScript จะอ่านค่าที่ garbage), และต้อง encode/decode UTF-8 เองให้ถูกต้องทุกจุด — ถ้าลืมข้อใดข้อหนึ่งจะได้
ข้อมูลผิดแบบเงียบ ๆ เหมือนที่เห็นไปแล้วกับ `undefined`

**นี่คือปัญหาที่ `wasm-bindgen` (Part 87) เข้ามาแก้อย่างเป็นระบบ**: มันทำสิ่งที่โค้ดข้างบนทำด้วยมือให้อัตโนมัติ
ทั้งหมด — เมื่อคุณเขียน `#[wasm_bindgen] pub fn get_greeting() -> String`, มันจะ generate โค้ดกลางทั้งฝั่ง
Rust (จัดการ ptr+len+การจอง/คืนหน่วยความจำที่ถูกต้อง) และฝั่ง JavaScript (เรียก TextDecoder ให้อัตโนมัติ) ให้
ครบ ทำให้คุณเขียน `const greeting = get_greeting();` แล้วได้ string จริงกลับมาตรง ๆ โดยไม่ต้องยุ่งกับ pointer
ใด ๆ เลย — บทนี้ตั้งใจไม่ลงรายละเอียดกลไกเบื้องหลังส่วนนี้เพราะเป็นเนื้อหาทั้งหมดของ Part 87 (การ generate
code สำหรับ `String`, `Vec<T>`, `struct` ที่ derive `Serialize`, และ `JsValue` สำหรับกรณีทั่วไปกว่านั้น)

### 86.8 ขนาด Binary: ทำไมสำคัญ และวิธีลดขนาดจริง

ในโปรแกรม native ทั่วไปที่ Part 35 สอนเรื่อง Cargo profile ไว้ ขนาด binary มีผลแค่กับพื้นที่ดิสก์ (ไม่ค่อยสำคัญ
มากในยุคที่ดิสก์ราคาถูก) — แต่สำหรับ WASM ที่ต้อง**ดาวน์โหลดผ่านเครือข่ายก่อนรันทุกครั้ง**ที่ผู้ใช้เปิดหน้าเว็บ
ขนาดไฟล์กลายเป็นเรื่องที่กระทบ**ประสบการณ์ผู้ใช้ตรง ๆ** — ไฟล์ใหญ่ = ผู้ใช้ต้องรอดาวน์โหลดนานขึ้นก่อนหน้าเว็บ
ทำงานได้ โดยเฉพาะบนเครือข่ายมือถือที่ความเร็วไม่แน่นอน

#### วิธีที่ 1: ปรับ Release Profile ด้วย `opt-level` และ `lto` (ทวนจาก Part 35)

Part 35 หัวข้อ 35.2 และ 35.4 สอนไว้แล้วว่า `opt-level` และ `lto` คือคีย์ที่มีผลต่อขนาด/ความเร็วของ binary มาก
ที่สุด สำหรับ WASM ที่เน้นขนาดเป็นพิเศษ ค่าที่แนะนำต่างจากโปรแกรม native ทั่วไปเล็กน้อย:

```toml
[profile.release]
opt-level = "z"   # เน้นขนาดไฟล์เล็กที่สุดเป็นอันดับแรก (ไม่ใช่ "s" ที่เน้นขนาดแต่ยังคำนึงความเร็วบ้าง
                  # และไม่ใช่ "3" ที่เน้นความเร็วสูงสุดแบบ native binary ทั่วไป)
lto = true        # เปิด Link-Time Optimization แบบ "fat" -- ทำให้ optimizer เห็นทั้งโปรแกรมพร้อมกัน
                  # ตัดโค้ดที่ไม่ถูกเรียกใช้จริง (dead code elimination) ได้ทั่วถึงกว่า
```

ทวนความหมายจาก Part 35: `opt-level = "z"` บอก LLVM ให้ **จัดลำดับความสำคัญของขนาดไฟล์เหนือความเร็วในการรัน**
ในทุกจุดที่ต้อง trade-off กัน (เช่น ไม่ inline ฟังก์ชันที่ทำให้โค้ดยาวขึ้นแม้จะเร็วขึ้นก็ตาม) ส่วน `lto = true`
เปิด **Link-Time Optimization** เต็มรูปแบบ ทำให้ compiler มองเห็นทุก crate (รวม dependency ทั้งหมด) พร้อมกันตอน
optimize แทนที่จะ optimize แต่ละ crate แยกกัน — ผลคือ **ตัดโค้ดที่ไม่มีการเรียกใช้งานจริงข้าม crate ได้ดีขึ้นมาก
กว่าเดิม** ซึ่งสำคัญเป็นพิเศษสำหรับ WASM เพราะทุกไบต์ที่ตัดออกได้คือเวลาดาวน์โหลดที่ลดลงจริง

#### วิธีที่ 2: `wasm-opt` จากชุดเครื่องมือ Binaryen

หลังจาก `rustc`/LLVM optimize แล้ว ยังมีเครื่องมือเฉพาะสำหรับ WASM โดยเฉพาะที่ optimize เพิ่มได้อีกชั้น — ชื่อ
**`wasm-opt`** ซึ่งเป็นส่วนหนึ่งของชุดเครื่องมือ **Binaryen** (ชุดเครื่องมือระดับ WASM-to-WASM optimization และ
compiler infrastructure ที่พัฒนาโดยทีม WebAssembly ของ Google) มันทำงานหลังจากที่ `rustc` compile เสร็จแล้ว
โดยรับไฟล์ `.wasm` เข้าไป วิเคราะห์และ optimize เพิ่มในระดับ WASM instruction โดยตรง (ไม่ใช่ในระดับ Rust source
อีกแล้ว) — ทำสิ่งที่ LLVM ทำไม่ได้ทั้งหมดเพราะ LLVM ไม่รู้จัก WASM-specific pattern บางอย่างที่เกิดขึ้นหลัง
compile เสร็จแล้ว

**ข่าวดี**: ถ้าใช้ `wasm-pack build` (อย่างที่ทำในหัวข้อ 86.5) มันจะ**เรียก `wasm-opt` ให้อัตโนมัติอยู่แล้ว**
ถ้าตรวจพบว่าติดตั้งไว้ในเครื่อง (สังเกตบรรทัด `[INFO]: 🔧 Optimizing wasm binaries with wasm-opt...` ในผลลัพธ์
การรันหัวข้อ 86.5) — แต่การเข้าใจว่ามันคือเครื่องมือแยกต่างหาก ไม่ใช่ส่วนหนึ่งของ `rustc`/Cargo เอง ช่วยให้เรียก
มันเองตรง ๆ ได้เมื่อต้องการควบคุมอย่างละเอียดกว่าที่ `wasm-pack` ตั้งค่า default ไว้ให้:

```bash
wasm-opt -Oz input.wasm -o output.wasm
```

แฟล็ก `-Oz` หมายถึง "optimize เน้นขนาดสูงสุด" (สอดคล้องแนวคิดเดียวกับ `opt-level = "z"` ของ Rust แต่ทำในระดับ
WASM instruction โดยตรง ไม่ใช่ระดับ LLVM IR)

#### วัดผลจริง: สามค่า Configuration เทียบกัน

วัดขนาดไฟล์ `.wasm` จริงของโปรเจกต์ `wasm_demo` จากหัวข้อ 86.4 (มีฟังก์ชัน `add` และ `get_greeting` รวมกัน) ใน
สาม configuration ต่อเนื่องกัน — ทุกตัวเลขคัดลอกตรงจากการรันจริงในสภาพแวดล้อมที่เขียนบทนี้ ไม่มีการประมาณ:

**Configuration A** — `opt-level = 3` (ค่า default ของ release profile ทั่วไป ตามที่ Part 35 สอนไว้ว่าเหมาะกับ
โปรแกรม native ที่เน้นความเร็ว):

```toml
[profile.release]
opt-level = 3
```

```bash
cargo build --release --target wasm32-unknown-unknown
wc -c target/wasm32-unknown-unknown/release/wasm_demo.wasm
```
```
17037 target/wasm32-unknown-unknown/release/wasm_demo.wasm
```

**Configuration B** — เปลี่ยนมาเน้นขนาดตามที่หัวข้อนี้แนะนำ (`opt-level = "z"`, `lto = true`, `strip = true`):

```toml
[profile.release]
opt-level = "z"
lto = true
strip = true
```

```bash
cargo clean --release --target wasm32-unknown-unknown
cargo build --release --target wasm32-unknown-unknown
wc -c target/wasm32-unknown-unknown/release/wasm_demo.wasm
```
```
6683 target/wasm32-unknown-unknown/release/wasm_demo.wasm
```

แค่เปลี่ยน profile settings ขนาดไฟล์ลดลงจาก **17,037 ไบต์ เหลือ 6,683 ไบต์ — ลดลงประมาณ 60.8%** โดยไม่ต้องแก้
โค้ด Rust แม้แต่บรรทัดเดียว

**Configuration C** — เอาไฟล์จาก Configuration B มารัน `wasm-opt -Oz` เพิ่มอีกชั้น:

```bash
wasm-opt -Oz target/wasm32-unknown-unknown/release/wasm_demo.wasm -o wasm_demo.opt.wasm
wc -c wasm_demo.opt.wasm
```
```
4655 wasm_demo.opt.wasm
```

ลดลงอีกจาก 6,683 ไบต์ เหลือ **4,655 ไบต์** — ลดลงอีกประมาณ 30.3% จาก Configuration B หรือคิดรวมจากจุดเริ่มต้น
(Configuration A) แล้วลดลงทั้งหมดประมาณ **72.7%**

สรุปเป็นตารางเปรียบเทียบ:

| Configuration | การตั้งค่า | ขนาดไฟล์ (ไบต์) | ลดจากจุดเริ่มต้น |
|---|---|---|---|
| A | `opt-level = 3` (default) | 17,037 | — |
| B | `opt-level = "z"`, `lto = true`, `strip = true` | 6,683 | -60.8% |
| C | B + `wasm-opt -Oz` | 4,655 | -72.7% |

**ข้อสังเกตสำคัญ**: สำหรับโปรแกรมเล็ก ๆ แบบนี้ ส่วนใหญ่ของขนาดไฟล์เดิม (17 KB) คือ**metadata มาตรฐานของรูปแบบ
ไฟล์ WASM เอง** (custom section ชื่อฟังก์ชันสำหรับ debug, ข้อมูล producer ที่บอกว่า compile ด้วย toolchain ไหน
ฯลฯ) ไม่ใช่ logic จริง — `strip = true` และ `wasm-opt` ตัด metadata ที่ไม่จำเป็นสำหรับการรันจริง (แต่จำเป็น
สำหรับ debug) ออกได้ ทำให้เห็นผลต่างชัดเจนมากเป็นพิเศษสำหรับโปรแกรมเล็ก ในขณะที่โปรแกรมใหญ่ขึ้น (มี logic จริง
มากขึ้น) สัดส่วนของ metadata เทียบกับขนาดรวมจะเล็กลงตามธรรมดา แต่ผลรวมของการ optimize ยังคุ้มค่าเสมอสำหรับไฟล์
ที่จะแจกจ่ายจริงผ่านเครือข่าย — ตัวเลขข้างบนคือหลักฐานที่วัดได้จริงว่าการตั้งค่าที่หัวข้อนี้แนะนำไม่ใช่คำแนะนำ
ลอย ๆ แต่ให้ผลต่างที่จับต้องได้จริงในระดับหลักสิบเปอร์เซ็นต์

**กฎการใช้งานจริง**: สำหรับโปรเจกต์ production ที่ compile เป็น WASM ควรตั้ง `opt-level = "z"` (หรือ `"s"` ถ้า
พบว่าความเร็วสำคัญกว่าขนาดสำหรับงานนั้น ๆ — ควร benchmark จริงเทียบกันเสมอไม่ใช่เดา), `lto = true`, `strip =
true` (ตัด debug symbol ที่ไม่จำเป็นสำหรับ production build) ใน `Cargo.toml` แล้วให้ `wasm-pack build --release`
เรียก `wasm-opt` ต่อให้อัตโนมัติ — นี่คือ pipeline มาตรฐานที่โปรเจกต์ Rust+WASM ระดับ production ส่วนใหญ่ใช้กัน

### 86.9 การ Debug WASM: ความยากที่จริงจัง และแนวทางที่ใช้ได้จริง

โปรแกรม native ทั่วไปที่เขียนมาตลอดหลักสูตร debug ได้ด้วย debugger เต็มรูปแบบ (เช่น `gdb`/`lldb`, หรือ
integration ใน VS Code) ที่ตั้ง breakpoint, step ทีละบรรทัด, ดูค่าตัวแปรได้ตรง ๆ — สำหรับ WASM ที่รันใน
เบราว์เซอร์ เรื่องนี้**ยากขึ้นอย่างมีนัยสำคัญ** และควรรู้ล่วงหน้าอย่างตรงไปตรงมาก่อนเจอด้วยตัวเอง

#### ทำไมมันยาก

1. **ไม่มี native debugger ที่ attach เข้ากับ WASM แบบเดียวกับโปรแกรม native** — `gdb`/`lldb` ถูกออกแบบมาสำหรับ
   debug โปรแกรมที่รันเป็น process บน OS จริง มี stack frame, register, symbol table ในรูปแบบที่มันเข้าใจ WASM
   ที่รันอยู่ **ภายใน JavaScript engine** (V8, SpiderMonkey) ไม่ใช่ process แยกที่ debugger ระดับ OS มองเห็นได้
   ตรง ๆ
2. **Stack trace ที่เห็นใน DevTools console เป็น WASM stack frame ดิบ ๆ** ที่ไม่มีชื่อฟังก์ชัน Rust ให้อ่าน
   (เห็นแค่ `wasm-function[42]` หรือ offset ตัวเลข) เว้นแต่จะมี **source map** ที่แปลงกลับไปยังชื่อ
   ฟังก์ชัน/บรรทัดของ Rust source จริง (หัวข้อถัดไป)
3. **`panic!` ใน Rust ที่รันเป็น WASM** โดย default จะกลายเป็น WASM `unreachable` trap (แบบที่เห็นในกับดักข้อ
   3 ท้ายบท) ซึ่งข้อความ error ที่ได้จาก JavaScript console เป็นแค่ `RuntimeError: unreachable executed` **ไม่
   มีข้อความ panic message ของ Rust ติดมาด้วยเลย** โดย default — ต้องตั้งค่าเพิ่มเพื่อให้เห็นข้อความที่มีประโยชน์

#### แนวทางที่ใช้ได้จริง: `console.log`-style Debugging ผ่าน `web-sys`

เพราะ debugger เต็มรูปแบบใช้ยาก แนวทางที่นักพัฒนา Rust+WASM ใช้กันมากที่สุดในทางปฏิบัติคือ**พิมพ์ค่าออกมาดูผ่าน
`console.log` ของเบราว์เซอร์** — ไม่ใช่ `println!` ธรรมดา (ซึ่งไม่มี stdout ให้เขียนในบริบทเบราว์เซอร์ — จะเงียบ
ไปเฉย ๆ ไม่มีที่ไหนแสดงผล) แต่ผ่าน crate **`web-sys`** ที่มี binding ไปยัง `console.log` ของ JavaScript ตรง ๆ:

```rust
// ตัวอย่างแนวคิด -- รายละเอียดเต็มเรื่อง web-sys/wasm-bindgen คือเนื้อหาของ Part 87
web_sys::console::log_1(&"debug: ค่า x คือ 42".into());
```

หรือใช้ macro สำเร็จรูปที่ครอบไว้ให้เขียนสะดวกขึ้นแบบ `println!`:

```rust
macro_rules! console_log {
    ($($t:tt)*) => (web_sys::console::log_1(&format!($($t)*).into()))
}
```

บทนี้ตั้งใจไม่ลงรายละเอียด setup เต็มรูปแบบของ `web-sys` (dependency, feature flag ที่ต้องเปิด) เพราะเป็นส่วน
หนึ่งของสิ่งที่ Part 87 จะสอนควบคู่กับ `wasm-bindgen` — สิ่งที่ควรรู้ตอนนี้คือ **แนวทางหลักของการ debug WASM ใน
ทางปฏิบัติคือการพิมพ์ค่าออกมาดู ไม่ใช่ step ผ่าน debugger แบบโปรแกรม native** และควรวางแผนเขียน log ที่มี
ประโยชน์ไว้ตั้งแต่ต้น เพราะการเพิ่ม log กลางทางที่โปรแกรมพังไปแล้วทำได้ยากกว่าโปรแกรม native ที่ attach
debugger เข้าไปได้ตอนนั้นเลย

#### แก้ปัญหา Panic Message ที่หายไป: `console_error_panic_hook`

หัวข้อก่อนหน้าและกับดักที่พบบ่อยข้อ 3 ท้ายบทแสดงให้เห็นแล้วว่า panic บน `wasm32-unknown-unknown` กลายเป็น
WASM trap แบบ `unreachable` ที่**ไม่มีข้อความ panic message ติดมาด้วยเลย** โดย default — เห็นแค่
`RuntimeError: unreachable` ใน console โดยไม่รู้ว่า panic เกิดจากอะไร บรรทัดไหน ปัญหานี้มีทางแก้ที่ใช้กันเป็น
มาตรฐานในระบบนิเวศ Rust+WASM: crate ชื่อ **`console_error_panic_hook`**

แนวคิดคือ: ตั้ง **panic hook** (ฟังก์ชันที่ Rust เรียกทุกครั้งก่อนที่โปรแกรมจะ panic จริง — เป็นกลไกมาตรฐานของ
`std::panic::set_hook` ที่มีอยู่ในทุก target ไม่ใช่แค่ WASM) ให้**ส่งข้อความ panic ไปยัง `console.error` ของ
JavaScript ก่อน**ที่โปรแกรมจะ trap ด้วย `unreachable` — วิธีตั้งค่าทั่วไปคือเรียกครั้งเดียวตอนโปรแกรมเริ่มทำงาน:

```rust
// เรียกครั้งเดียวตอนเริ่มโปรแกรม (เช่นใน constructor หรือฟังก์ชัน init ที่ JavaScript เรียกก่อนใช้งานอื่น)
console_error_panic_hook::set_once();
```

หลังตั้งค่านี้แล้ว panic message ของ Rust (ข้อความจาก `panic!(...)`, `.unwrap()` ที่ล้มเหลว, index array ที่
เกินขอบเขต ฯลฯ) จะปรากฏใน **DevTools console เป็นข้อความที่อ่านได้** พร้อม stack trace ของ WASM (แม้จะยังเป็น
`wasm-function[N]` ดิบ ๆ ถ้าไม่มี debug info แต่ก็ดีกว่า `unreachable` เปล่า ๆ มาก) — เป็นสิ่งที่แทบทุกโปรเจกต์
Rust+WASM ระดับ production ตั้งไว้เป็นมาตรฐานตั้งแต่ต้น เพราะต้นทุนในการเปิดใช้ต่ำมาก (แค่เพิ่ม dependency กับ
เรียกฟังก์ชันเดียว) แต่ประโยชน์ตอน debug จริงสูงมาก บทนี้ตั้งใจไม่ลงรายละเอียด setup เต็มรูปแบบ (เพราะต้องพึ่ง
`wasm-bindgen` ในการเรียก JS init อยู่ดี) แต่ควรรู้จักชื่อ crate นี้ไว้ตั้งแต่ตอนนี้ เพราะ Part 87 จะกลับมาใช้
มันเป็นส่วนหนึ่งของ setup มาตรฐาน

#### Source Maps: รู้จักไว้ระดับ Awareness

เบราว์เซอร์สมัยใหม่ (Chrome DevTools, Firefox Developer Tools) รองรับการ debug WASM ผ่าน **DWARF debug
information ที่ฝังไว้ในไฟล์ `.wasm`** (คล้ายกับ debug symbol ของโปรแกรม native) ทำให้ในบางกรณีสามารถตั้ง
breakpoint บนโค้ด Rust source จริงได้ตรง ๆ ผ่าน DevTools (ไม่ใช่ source map แบบเดียวกับ JavaScript ที่แปลง
minified code กลับไปยัง source เดิม แต่เป็นกลไกคู่ขนานที่ทำหน้าที่คล้ายกัน) — ต้อง build ด้วย `opt-level` ที่ต่ำ
(หรือ `debug = true`) เพื่อให้ debug info ถูกฝังไว้ครบถ้วน (ตรงข้ามกับหัวข้อ 86.8 ที่เน้นตัดทุกอย่างที่ไม่จำเป็น
ออกสำหรับ production — debug build กับ release build ที่เน้นขนาดจึงเป็นสอง configuration ที่ตั้งใจต่างกัน
ตามหลักการเดียวกับที่ Part 35 สอนไว้เรื่อง `[profile.dev]` vs `[profile.release]`) — บทนี้ให้รู้จักไว้ในระดับ
awareness เท่านั้น เพราะการตั้งค่าและใช้งานจริงต้องพึ่งพา DevTools เวอร์ชันที่รองรับและมักเปลี่ยนแปลงบ่อยตาม
เวอร์ชันเบราว์เซอร์ ไม่ใช่สิ่งที่ตายตัวพอจะสอนเป็นขั้นตอนคงที่ในบทเรียน

### 86.10 WASM อยู่ตรงไหนในชุดเครื่องมือของนักพัฒนา Rust: Server-Side เทียบกับ Browser

ก่อนปิดบท จำเป็นต้องวาง**กรอบความคิดที่ชัดเจน**ว่า WebAssembly ที่เริ่มเรียนในบทนี้สัมพันธ์กับทุกอย่างที่เรียน
มาตลอดโมดูล 4 (Part 61-85) อย่างไร — เพื่อไม่ให้เข้าใจผิดว่ามันคือ "อีกทางเลือกที่มาแทน Axum" หรือแนวคิดที่ขัดแย้ง
กัน

| มิติ | Rust บน Server (โมดูล 4) | Rust ในเบราว์เซอร์ผ่าน WASM (โมดูล 5) |
|---|---|---|
| รันที่ไหน | เครื่อง server ที่ทีมคุณควบคุมเต็มรูปแบบ | **เครื่องของผู้ใช้ปลายทาง** ผ่านเบราว์เซอร์ — คุณไม่ควบคุม hardware/OS ของเขาเลย |
| Framework หลัก | Axum, Actix-web (Part 62-69) | `wasm-bindgen` (Part 87), Yew/Leptos/Dioxus (Part 88-90) |
| การเข้าถึงทรัพยากร | เข้าถึง filesystem, database, network socket ได้ตรง ๆ ผ่าน std/crate ทั่วไป | **เข้าถึงอะไรนอกจาก CPU/memory ไม่ได้เลยโดยตรง** ต้องผ่าน JavaScript API ที่เบราว์เซอร์เปิดให้เท่านั้น (fetch สำหรับเครือข่าย, ไม่มี raw filesystem access) |
| เหตุผลหลักที่ใช้ | รับ-ตอบ HTTP request, คุยกับฐานข้อมูล, จัดการ business logic ฝั่งกลาง | งานที่ใช้ CPU หนักที่อยากให้เร็วกว่า JavaScript (ประมวลผลภาพ, เกม, crypto), หรือสร้าง UI ทั้งตัวด้วย Rust |
| ผู้ใช้เห็นโค้ดไหม | ไม่เห็นเลย (compile เป็น binary ที่รันบน server เท่านั้น) | **ไฟล์ `.wasm` ถูกดาวน์โหลดไปยังเครื่องผู้ใช้** — แม้จะ decompile ยากกว่า JS แต่ก็ไม่ใช่ "secret" ที่ปิดสนิท เหมือนซอร์สโค้ดที่รันบน server |
| ใครควบคุมเวอร์ชันที่กำลังรันอยู่ | ทีมคุณ — deploy เวอร์ชันใหม่แล้ว request ถัดไปทุกตัวใช้เวอร์ชันใหม่ทันที | **ผู้ใช้แต่ละคน** อาจรันเวอร์ชันเก่าที่ cache ไว้ในเบราว์เซอร์ค้างอยู่ จนกว่าจะโหลดหน้าใหม่ — ต้องคิดเรื่อง cache invalidation ของไฟล์ `.wasm`/JS glue ด้วย (ปัญหาเดียวกับที่ frontend ทุกแบบเจอ ไม่ใช่ปัญหาเฉพาะ WASM) |

พูดให้เป็นภาพที่จับต้องได้: ทีมที่สร้างเครื่องมือแก้ไขภาพบนเว็บ (ตัวอย่างในหัวข้อ 86.11) อาจมี Axum server
(โมดูล 4) ทำหน้าที่รับอัปโหลดไฟล์, จัดเก็บ metadata ลงฐานข้อมูล, และจัดการสิทธิ์ผู้ใช้ ในขณะที่**การประมวลผลภาพ
จริง ๆ เช่น apply filter หรือปรับความสว่าง** เกิดขึ้นทั้งหมดที่**ฝั่งเบราว์เซอร์ผ่าน WASM** ก่อนที่จะอัปโหลดผลลัพธ์
กลับไปเก็บที่ server เท่านั้น — สอง technology stack ทำงานคนละหน้าที่ที่เสริมกัน ไม่ใช่แข่งกัน และนี่คือ pattern
ที่จะเห็นซ้ำไปเรื่อย ๆ ตลอดโมดูล 5 ที่เหลือ

**ข้อสรุปที่สำคัญที่สุดของหัวข้อนี้**: WASM **ไม่ได้มาแทนที่**สิ่งที่เรียนในโมดูล 4 เลยแม้แต่นิดเดียว — ระบบ
จริงระดับ production จำนวนมากใช้**ทั้งสองอย่างพร้อมกัน**: server (Axum) รับ request, ประมวลผล business logic,
คุยกับฐานข้อมูล ตามที่เรียนมาตลอดโมดูล 4 ส่วน WASM ทำงานที่**ฝั่ง client** สำหรับงานเฉพาะที่เหมาะกับมัน (เช่น
ประมวลผลภาพก่อนอัปโหลดเพื่อลดขนาดไฟล์ที่ต้องส่งไป server, ทำ validation ที่ซับซ้อนแบบ real-time ในฟอร์มโดยไม่
ต้องรอ round-trip ไป server, หรือรัน UI ทั้งหน้าด้วย framework อย่าง Leptos ที่เรียก API ของ server ที่สร้างไว้
ในโมดูล 4 ผ่าน `fetch`) — **สอง alt สองฝั่งนี้ประกอบกันเป็นระบบ full-stack ที่โมดูล 5 ทั้งหมด (Part 86-95)
กำลังจะพาไปสร้าง** ไม่ใช่คู่แข่งที่ต้องเลือกอย่างใดอย่างหนึ่ง

### 86.11 กรณีใช้งานจริงของ WASM: ภาพรวมสั้น ๆ เพื่อปูทางที่เหลือของโมดูล

ปิดท้ายด้วยภาพรวมสั้น ๆ ว่า WASM ถูกใช้งานจริงที่ไหนบ้าง เพื่อให้เห็นภาพว่าโมดูล 5 ที่เหลือกำลังพาไปทางไหน —
เป็นการสำรวจแบบตรงไปตรงมา ไม่ใช่การโฆษณาเกินจริง

- **การประมวลผลภาพ/วิดีโอในเบราว์เซอร์** — เครื่องมือแก้ไขภาพ/ตัดต่อวิดีโอที่ทำงานทั้งหมดในเบราว์เซอร์โดยไม่ต้อง
  อัปโหลดไฟล์ไป server เลย (สำคัญมากสำหรับความเป็นส่วนตัวของผู้ใช้ และลดภาระ server) ใช้ WASM ทำงานหนักด้าน
  คำนวณที่ JavaScript ทำได้ช้าเกินไป เช่น การเข้ารหัส/ถอดรหัสภาพ, การใช้ filter ที่ซับซ้อน, resize ภาพขนาดใหญ่
- **เกม** — เกม 2D/3D ที่ต้องการ frame rate สม่ำเสมอ ได้ประโยชน์มากจากการไม่มี GC pause ที่คาดเดาไม่ได้ (อย่างที่
  หัวข้อ 86.1 อธิบายไว้) — **Bevy** (game engine ที่เขียนด้วย Rust ทั้งหมด) รองรับการ compile เป็น WASM ให้เกม
  รันในเบราว์เซอร์ได้ตรง ๆ โดยไม่ต้องติดตั้งอะไรเพิ่ม (Part 103 ของหลักสูตรจะพาไปสร้างเกมด้วย Bevy โดยละเอียด
  — WASM คือหนึ่งใน deployment target ที่ Bevy รองรับ)
- **Cryptography** — งานเข้ารหัส/ถอดรหัสที่ต้องการความเร็วและความแน่นอนของ timing (crypto ที่ timing ไม่แน่นอน
  อาจรั่วข้อมูลผ่าน timing attack ได้) เหมาะกับ WASM ที่ compile ล่วงหน้าและมี behavior ที่คาดเดาได้มากกว่า
  JavaScript ที่ JIT อาจ optimize ต่างกันไปตาม pattern การใช้งาน
- **Full frontend framework ด้วย Rust** — นี่คือทิศทางหลักที่โมดูล 5 ที่เหลือจะพาไป: **Yew** (Part 88, framework
  แบบ component คล้าย React แต่เขียนด้วย Rust ทั้งหมด), **Leptos** (Part 89, framework ที่เน้น full-stack —
  โค้ด Rust ตัวเดียวกันรันได้ทั้งฝั่ง server สำหรับ server-side rendering และฝั่ง client ผ่าน WASM), **Dioxus**
  (Part 90, framework ที่ครอบคลุมทั้งเว็บ, desktop, และ mobile ด้วยโมเดล component เดียว) — ทั้งสามนี้ใช้ WASM
  เป็นกลไกพื้นฐานเบื้องหลังในการรันโค้ด UI ที่เขียนด้วย Rust ในเบราว์เซอร์ ตรงตามที่บทนี้ปูพื้นฐานไว้ทั้งหมด
- **เครื่องมือ productivity/design ระดับมืออาชีพบนเว็บ** — แอปพลิเคชันประเภทเครื่องมือออกแบบ/แก้ไขเอกสารที่ทำงาน
  เต็มรูปแบบในเบราว์เซอร์ (ไม่ใช่แค่หน้าเว็บธรรมดา แต่เทียบเคียงกับโปรแกรม desktop) มักมีส่วนที่ใช้ WASM สำหรับ
  งานคำนวณหนัก เช่น การ render ภาพ vector ที่ซับซ้อน, การคำนวณ layout ของเอกสารขนาดใหญ่, หรือการเข้ารหัส/ถอดรหัส
  ข้อมูลฝั่ง client ก่อนส่งเข้า server (ใช้ WASM เพื่อไม่ต้องส่งข้อมูลดิบที่ยังไม่เข้ารหัสออกจากเครื่องผู้ใช้เลย)

**ข้อควรระวังที่ต้องพูดตรง ๆ**: WASM **ไม่ได้เร็วกว่า JavaScript เสมอไปทุกกรณี** — สำหรับงานเล็ก ๆ ที่เรียกไป
เรียกกลับข้ามพรมแดน WASM/JavaScript บ่อยมาก (เช่นเรียกฟังก์ชัน WASM ทีละค่าใน loop ที่วนหลายพันครั้ง) **ต้นทุน
ของการข้ามพรมแดนเอง** (การแปลง type, การ marshaling ข้อมูลตามที่หัวข้อ 86.7 อธิบายไว้) อาจสูงกว่าประโยชน์ที่ได้
จากความเร็วในการคำนวณเสียอีก — หลักการทั่วไปที่ใช้กันในทางปฏิบัติคือ **"ยิ่งเรียกข้ามพรมแดนน้อยครั้งแต่ทำงาน
มากต่อครั้งยิ่งดี"** (ส่ง array ทั้งก้อนเข้าไปประมวลผลทีเดียวใน WASM แทนการเรียกทีละ element จาก JavaScript) —
WASM เหมาะกับงานที่มี**การคำนวณหนักภายในตัวมันเอง**เป็นหลัก (loop จำนวนมากที่ทำงานอยู่ฝั่ง Rust ทั้งหมดโดยไม่
ต้องกลับไปคุยกับ JavaScript บ่อย ๆ) มากกว่างานที่แค่ "ห่อ logic ธรรมดาเป็น WASM" โดยไม่มีเหตุผลด้านประสิทธิภาพ
ที่ชัดเจนรองรับ — การเลือกใช้ WASM ควรมาจากการวัดผลจริงว่าช้าเกินไปสำหรับ JavaScript ก่อน ไม่ใช่ใช้เพราะ "ฟังดู
เท่กว่า"

ภาพรวมนี้ควรทำให้เห็นชัดว่า **บทนี้ (Part 86) คือฐานรากที่ทุกบทที่เหลือของโมดูล 5 ยืนอยู่บน** — ไม่ว่าจะเป็น
`wasm-bindgen` ที่ลึกขึ้นใน Part 87 หรือ framework เต็มรูปแบบใน Part 88-90 ทุกอย่างสร้างอยู่บนความเข้าใจพื้นฐาน
สามเรื่องที่บทนี้ปูไว้: **WASM คืออะไรและทำงานอย่างไร (86.1-86.2), เครื่องมือพื้นฐานที่ใช้พัฒนามันด้วย Rust
(86.3-86.5), และข้อจำกัด/ข้อควรระวังที่ต้องรู้ก่อนไปลึกกว่านี้ (86.6-86.9)**

## กับดักที่พบบ่อย (Common Pitfalls)

### 1. ลืมตั้ง `crate-type = ["cdylib"]` ใน `Cargo.toml`

โปรเจกต์ `cargo new --lib` ธรรมดาไม่มี key `crate-type` มาก่อน (default ของ Rust คือ `rlib` — รูปแบบสำหรับให้
crate อื่นใน Rust ecosystem `use` ต่อ ไม่ใช่รูปแบบที่ WASM ต้องการ) ถ้าลืมเพิ่ม `crate-type = ["cdylib"]` แล้ว
รัน `wasm-pack build` ตรง ๆ จะได้ error ที่ชัดเจนมาก (คัดลอกตรงจากการรันจริง):

```
Error: crate-type must be cdylib to compile to WebAssembly. Add the following to your Cargo.toml file:

[lib]
crate-type = ["cdylib", "rlib"]
```

**วิธีแก้**: เพิ่ม section `[lib]` พร้อม `crate-type = ["cdylib"]` (หรือ `["cdylib", "rlib"]` ถ้าต้องการให้
crate นี้ใช้เป็น dependency ของ crate อื่นในเวลาเดียวกันด้วย เช่นเขียน test แบบ native ควบคู่ไปกับ compile
เป็น WASM) ก่อน build เสมอ — `wasm-pack` แจ้ง error นี้ให้ตรงประเด็นมาก จึงแก้ได้เร็ว แต่ควรรู้ล่วงหน้าว่าทำไม
ต้องมี key นี้ (อธิบายไว้ในหัวข้อ 86.3): `cdylib` คือรูปแบบเดียวที่ทำให้ linker สร้าง export table ของ WASM
module ที่ host มองเห็นและเรียกได้จากนอก crate

### 2. ลืม `rustup target add wasm32-unknown-unknown` ก่อน Build

ถ้ายังไม่เคยเพิ่ม target นี้ (หรือเผลอลบไปด้วยคำสั่งอื่น) แล้วรัน `cargo build --target wasm32-unknown-unknown`
ตรง ๆ จะได้ error (คัดลอกตรงจากการรันจริง):

```
error[E0463]: can't find crate for `std`
  |
  = note: the `wasm32-unknown-unknown` target may not be installed
  = help: consider downloading the target with `rustup target add wasm32-unknown-unknown`

For more information about this error, try `rustc --explain E0463`.
error: could not compile `no_cdylib_probe` (lib) due to 1 previous error
```

**วิธีแก้**: รัน `rustup target add wasm32-unknown-unknown` ตามที่ error message บอกไว้ตรง ๆ อยู่แล้ว — สังเกต
ว่า error นี้ไม่ได้บอกว่า "target ไม่ถูกต้อง" แต่บอกว่า "**หา crate สำหรับ `std` ไม่เจอ**" เพราะ `std` เองก็
ต้อง compile แยกสำหรับแต่ละ target (คนละ platform มี syscall/ABI ต่างกัน) — `rustup target add` คือขั้นตอนที่
ดาวน์โหลด/compile `std` เวอร์ชันสำหรับ target นั้นมาให้ ถ้าไม่มีขั้นตอนนี้ compiler จะไม่มี `std` ให้ link เข้า
ไปเลยไม่ว่า Cargo.toml จะตั้งค่าอะไรก็ตาม

### 3. `std::fs`/I/O compile ผ่านได้ แต่ Trap ตอน Runtime — ไม่ใช่ Compile Error

จุดที่อันตรายที่สุดในบรรดากับดักทั้งหมด: โค้ดที่ใช้ `std::fs::File`, `std::net::TcpStream` หรือ I/O อื่น ๆ ที่
ต้องพึ่ง OS **compile ผ่านได้ปกติโดยไม่มี error หรือ warning ใด ๆ เลย** บน `wasm32-unknown-unknown` (เพราะ
`std` เวอร์ชันของ target นี้ยังมี type/function เหล่านี้ให้ประกาศ signature ไว้ครบ) — ปัญหาจะปรากฏ**ตอนรันจริง
เท่านั้น** ลองโค้ดนี้:

```rust
use std::fs::File;
use std::io::Write;

#[no_mangle]
pub extern "C" fn write_something() {
    let mut f = File::create("/tmp/x.txt").unwrap();
    f.write_all(b"hello").unwrap();
}
```

```bash
cargo build --release --target wasm32-unknown-unknown
```
```
    Finished `release` profile [optimized] target(s) in 0.33s
```

**Compile ผ่านสำเร็จ 100% ไม่มีคำเตือนเลยแม้แต่คำเดียว** — แต่พอเรียกฟังก์ชันนี้จริงจาก JavaScript/Node.js
(คัดลอกตรงจากการรันจริง):

```
runtime error caught: unreachable
```

เกิด **WASM trap แบบ `unreachable`** ทันทีที่เรียก เพราะ target `wasm32-unknown-unknown` ไม่มี OS อยู่เบื้อง
หลังให้ทำ syscall จริง (ตามที่หัวข้อ 86.3 อธิบายไว้) — `std` เวอร์ชันของ target นี้ implement ฟังก์ชันพวกนี้ไว้
เป็นแค่ **stub ที่จะ panic ทันทีเมื่อถูกเรียก** (และ panic บน target นี้โดย default ถูกแปลงเป็น `unreachable`
instruction เพราะไม่มี stack unwinding mechanism ให้ใช้) — ผลคือคุณจะไม่รู้ว่ามีปัญหานี้อยู่**จนกว่าจะรันจริง**
ซึ่งอาจไปพังตอนอยู่ใน production แล้วถ้าไม่ได้ทดสอบเส้นทางโค้ดนี้ก่อน

**วิธีแก้**: อย่าเขียนโค้ดที่พึ่ง OS-level I/O (`std::fs`, `std::net`, `std::process`, thread ของ OS ผ่าน
`std::thread::spawn`) ในโค้ดที่จะ compile เป็น `wasm32-unknown-unknown` เลย — ถ้าต้องการเข้าถึงเครือข่ายจาก
WASM ในเบราว์เซอร์ ต้องผ่าน JavaScript `fetch` API (เรียกผ่าน binding ของ `wasm-bindgen`/`web-sys` ซึ่ง Part 87
จะสอน) ไม่ใช่ `std::net` ตรง ๆ — และควรตรวจสอบโค้ดที่ import มาจาก dependency อื่นด้วยว่าไม่มีการเรียก I/O
แบบนี้ซ่อนอยู่ (เช่น library ที่เขียนมาสำหรับ native โดยไม่คำนึงถึง WASM อาจมี code path นี้อยู่โดยไม่รู้ตัว)

### 4. เปิด `index.html` ด้วย `file://` ตรง ๆ — ES Module ถูกบล็อกด้วย CORS

หลังจาก `wasm-pack build --target web` ได้ไฟล์ครบแล้ว การเปิดไฟล์ `index.html` **ดับเบิลคลิกตรง ๆ** (ซึ่งเปิด
ด้วย URL แบบ `file:///path/to/index.html`) แทนการ serve ผ่าน HTTP server จะเจอปัญหาทันที — เบราว์เซอร์บังคับกฎ
ความปลอดภัยที่ปฏิเสธการ `import` ES module ข้าม origin แบบ `file://` (แต่ละไฟล์ `file://` ถือเป็นคนละ origin
กันในสายตาเบราว์เซอร์) ข้อความ error ที่เห็นจริงใน DevTools console ของ Chrome มีลักษณะ (ข้อความอาจต่างกันเล็ก
น้อยตามเวอร์ชันเบราว์เซอร์):

```
Access to script at 'file:///path/to/pkg/wasm_bindgen_demo.js' from origin 'null' has been blocked by
CORS policy: Cross origin requests are only supported for protocol schemes: chrome, chrome-extension,
chrome-untrusted, data, http, https, isolated-app.
```

**วิธีแก้**: serve โฟลเดอร์ผ่าน HTTP server เสมอ แม้จะเป็นแค่การทดสอบเบื้องต้นในเครื่องตัวเองก็ตาม — วิธีที่เร็ว
ที่สุดคือ `npx http-server .` (หรือ `python3 -m http.server` ถ้าไม่ต้องการพึ่ง Node.js) แล้วเปิดผ่าน
`http://localhost:...` เสมอ ไม่ใช่ `file://` — นี่ไม่ใช่ปัญหาที่เกี่ยวกับ WASM โดยตรง (เป็นกฎ CORS มาตรฐานของ
เบราว์เซอร์สำหรับ ES module ทุกชนิด) แต่เป็นสิ่งที่ทุกคนที่เพิ่งเริ่มทำ Rust+WASM เจอแทบจะทุกคนในครั้งแรก เพราะ
ตัวอย่างโค้ดส่วนใหญ่ในเอกสารออนไลน์มักไม่พูดถึงขั้นตอนนี้ให้ชัดเจน

### 5. ทดสอบ `wasm32-wasip1` แล้วสงสัยว่าทำไม `web-sys`/DOM API ใช้ไม่ได้

ผู้เริ่มต้นที่เห็นชื่อ target `wasm32-wasip1`/`wasm32-wasi` (มีคำว่า "wasm" เหมือนกัน) แล้วลองใช้แทน
`wasm32-unknown-unknown` โดยเข้าใจผิดว่าเป็นตัวเลือกที่ "ใหม่กว่า" หรือ "ดีกว่า" สำหรับงานเบราว์เซอร์ จะเจอ
compile error ทันทีที่ใช้ crate อย่าง `web-sys`/`wasm-bindgen` (ซึ่งพึ่งพา JavaScript import ที่ target นี้ไม่
รู้จัก) หรือถ้า compile ผ่านได้บางส่วน ก็จะเรียกใช้ใน host ที่ไม่รองรับ WASI ไม่ได้เลย

**วิธีแก้**: กลับไปดูตารางในหัวข้อ 86.6 ให้ชัดก่อนเลือก target — ถ้าเป้าหมายคือ**เบราว์เซอร์** (ซึ่งคือทุกบท
ที่เหลือของโมดูล 5 นี้ Part 87-95) ใช้ `wasm32-unknown-unknown` เสมอ ถ้าเป้าหมายคือรัน WASM แบบ standalone
นอกเบราว์เซอร์ (server-side WASM runtime, plugin system, edge computing บางแพลตฟอร์ม) ค่อยพิจารณา
`wasm32-wasip1` — สองเป้าหมายนี้ไม่ทับซ้อนกัน การเลือกผิดจะเจอ error หรือพฤติกรรมที่ผิดคาดตั้งแต่ขั้นตอนแรก

### 6. Panic ที่ให้ข้อมูลแค่ `unreachable` โดยไม่มี Panic Message ติดมาด้วย

ต่อเนื่องจากกับดักข้อ 3 และหัวข้อ 86.9: เมื่อโค้ด Rust ที่ compile เป็น `wasm32-unknown-unknown` เกิด panic
(ไม่ว่าจะจาก `.unwrap()` ที่ล้มเหลว, `panic!(...)` ตรง ๆ, index array เกินขอบเขต, หรือ integer overflow ใน
debug build) สิ่งที่เห็นจาก JavaScript console โดย default มีแค่:

```
RuntimeError: unreachable executed
```

**ไม่มีข้อความ panic message ของ Rust ติดมาด้วยเลย** — ไม่รู้ว่า panic เกิดจากบรรทัดไหน ฟังก์ชันไหน ข้อความ
`.unwrap()` ที่เขียนไว้อธิบายปัญหาก็หายไปหมด (ต่างจากรันบนเครื่อง native ที่ `cargo run` ปกติจะพิมพ์
`thread 'main' panicked at ...` พร้อมข้อความและตำแหน่งบรรทัดให้เห็นตรง ๆ) ทำให้การหาสาเหตุยากกว่าที่ควรมาก
โดยเฉพาะกับผู้เริ่มต้นที่ยังไม่รู้จักกับดักนี้

**วิธีแก้**: ตั้งค่า panic hook ด้วย `console_error_panic_hook::set_once()` ตามที่หัวข้อ 86.9 อธิบายไว้ ตั้งแต่
ตอนเริ่มโปรแกรม (ปกติเรียกครั้งเดียวในฟังก์ชัน init ที่ JavaScript เรียกก่อนใช้งานฟังก์ชันอื่น) — หลังตั้งค่านี้
ข้อความ panic ของ Rust จะถูกส่งไปยัง `console.error` ก่อนที่ WASM จะ trap จริง ทำให้เห็นข้อความที่มีประโยชน์ใน
DevTools console แทนที่จะเห็นแค่ `unreachable` เปล่า ๆ — ถือเป็น setup มาตรฐานที่ทุกโปรเจกต์ Rust+WASM ควรมีไว้
ตั้งแต่วันแรกที่เริ่มเขียนโปรเจกต์ ไม่ใช่สิ่งที่ค่อยเพิ่มทีหลังตอนเจอปัญหาแล้ว

## แบบฝึกหัด (Exercises)

1. **(ง่าย)** สร้างโปรเจกต์ `cargo new --lib` ใหม่ ตั้งค่า `crate-type = ["cdylib"]` แล้วเขียนฟังก์ชัน
   `multiply(a: i32, b: i32) -> i32` แบบ `#[no_mangle] pub extern "C" fn` (ไม่ใช้ `wasm-bindgen`) compile ด้วย
   `cargo build --release --target wasm32-unknown-unknown` แล้วเขียนสคริปต์ Node.js สั้น ๆ (แบบเดียวกับหัวข้อ
   86.4) เรียกมันด้วยค่า `a = 6, b = 7` ตรวจว่าได้ `42` กลับมา
   *hint*: ใช้ `WebAssembly.instantiate()` กับ `readFile` เหมือนตัวอย่างในหัวข้อ 86.4 ทุกประการ เปลี่ยนแค่ชื่อ
   ฟังก์ชันและค่าที่ส่งเข้าไป

2. **(กลาง)** เพิ่ม `wasm-bindgen` เข้าไปในโปรเจกต์ข้อ 1 แปลง `multiply` ให้ใช้ `#[wasm_bindgen]` แทน แล้ว
   `wasm-pack build --target web` สร้างหน้า `index.html` ที่เรียก `multiply(6, 7)` แสดงผลลัพธ์บน DOM ผ่าน
   `document.getElementById(...)` เหมือนตัวอย่างในหัวข้อ 86.5 — serve ด้วย `npx http-server .` แล้วเปิดใน
   เบราว์เซอร์จริงตรวจสอบว่าเห็นเลข `42` บนหน้าเว็บ
   *hint*: อย่าลืมกับดักข้อ 4 — ห้ามเปิดด้วย `file://` เด็ดขาด ต้อง serve ผ่าน HTTP เท่านั้น

3. **(ยาก)** เขียนฟังก์ชัน `sum_array(ptr: *const i32, len: usize) -> i32` แบบ `extern "C"` (ไม่ใช้
   `wasm-bindgen`) ที่รับ pointer และความยาวของ array `i32` แล้วบวกทุกค่ารวมกัน (ใช้ `std::slice::from_raw_
   parts` เพื่อแปลง pointer+length กลับเป็น slice ที่วนลูปได้ ตามความรู้จาก Part 42) จากฝั่ง JavaScript ต้อง
   จองหน่วยความจำใน linear memory เอง (ผ่าน `instance.exports.memory.buffer`) เขียนค่าตัวเลขลงไปด้วย
   `Int32Array` แล้วส่ง pointer ที่ถูกต้องเข้าไปเรียกฟังก์ชันนี้ ตรวจว่าผลรวมถูกต้อง
   *hint*: ต้องรู้ว่า Rust allocator (ผ่าน `std::alloc::alloc`) ให้ pointer ที่ JavaScript ใช้เขียนข้อมูลลงไป
   ได้ก่อนเรียกฟังก์ชัน — export ฟังก์ชันเสริมที่ `alloc`/`dealloc` หน่วยความจำให้ JavaScript เรียกขอพื้นที่ได้
   ก่อน (นี่คือกลไกระดับล่างที่ `wasm-bindgen` ทำให้อัตโนมัติเวลาส่ง `Vec<T>`/`&[T]` — โจทย์นี้ให้ทำมือเพื่อเข้าใจ
   ว่ามันทำอะไรอยู่เบื้องหลังจริง ๆ)

4. **(ยาก/ประยุกต์ใช้งานจริง)** วัดขนาดไฟล์ `.wasm` ของโปรเจกต์ข้อ 2 (ที่ใช้ `wasm-bindgen`) เปรียบเทียบสาม
   configuration: (ก) `opt-level = 3` ธรรมดา (ข) `opt-level = "z", lto = true` (ค) เหมือน (ข) แต่รัน `wasm-opt
   -Oz` เพิ่มต่ออีกชั้นด้วยมือ (นอกเหนือจากที่ `wasm-pack` เรียกให้อัตโนมัติ) บันทึกขนาดไฟล์ทั้งสามกรณีเป็น
   ตารางเปรียบเทียบ แล้ววิเคราะห์ว่าขั้นไหนช่วยลดขนาดได้มากที่สุดตามสัดส่วน
   *hint*: ใช้ `wc -c` หรือ `ls -la` วัดขนาดไฟล์ `.wasm` ตรง ๆ ในแต่ละ configuration อย่าลืม `cargo clean`
   ก่อนสลับ profile แต่ละครั้งเพื่อไม่ให้ cache ของ build เก่าปนกัน

## สรุป

บทนี้เปิดประตูสู่โมดูล 5 ด้วยการตอบคำถามพื้นฐานที่สุดของ WebAssembly ให้ครบ: **มันคืออะไร** (binary instruction
format สำหรับรันใน sandbox ที่เร็วกว่า JavaScript แบบ interpreted/JIT เพราะ compile ล่วงหน้าและมี type ตายตัว),
**ทำไม Rust เหมาะกับมันเป็นพิเศษ** (ไม่มี garbage collector ที่ต้องแนบเข้าไปในตัว binary แบบภาษาอื่น ownership/
borrow checker พิสูจน์ความปลอดภัยไปแล้วที่ compile time โดยไม่ต้องเพิ่ม runtime check ซ้ำกับที่ WASM sandbox
มีให้อยู่แล้ว), และ**โมเดล linear memory** ที่เชื่อมกับความเข้าใจเรื่อง raw pointer จาก Part 42 ได้อย่างเป็น
ธรรมชาติ (pointer ใน WASM ก็แค่ offset เข้าไปใน byte array ผืนเดียว)

ในทางปฏิบัติ บทนี้พาไปติดตั้งเครื่องมือจริง (`rustup target add wasm32-unknown-unknown`, `wasm-pack`),
compile ฟังก์ชันเดี่ยว ๆ เป็น WASM ทั้งแบบดิบที่สุด (ไม่มีตัวช่วยเลย) และแบบที่ใช้ `wasm-bindgen`/`wasm-pack`
เต็มรูปแบบ พิสูจน์ทุกขั้นตอนด้วยการรันจริง — ทั้งผ่าน Node.js `WebAssembly` API และผ่าน Chromium จริงที่โหลด
หน้าเว็บ HTML แล้วเรียกฟังก์ชันจาก WASM ได้ผลลัพธ์ถูกต้อง — พร้อมทั้งเห็นข้อจำกัดที่เป็นรูปธรรมของพรมแดน
WASM/JavaScript (ตัวเลขข้ามได้ฟรี แต่ `String`/type ซับซ้อนต้องมีตัวช่วย ไม่มีตัวช่วยแล้วได้ `undefined` แบบ
เงียบ ๆ) ซึ่งเป็นแรงจูงใจตรงไปยัง Part 87 ที่จะสอน `wasm-bindgen` ให้ลึกและเป็นระบบมากขึ้น รวมถึงเรื่องขนาด
binary ที่วัดผลจริงว่า `opt-level`/`lto`/`wasm-opt` ช่วยลดขนาดได้แค่ไหน และวางกรอบความคิดที่ชัดเจนว่า WASM
ไม่ได้มาแทน Axum ที่เรียนมาตลอดโมดูล 4 แต่เป็นเครื่องมือใหม่สำหรับรัน Rust **ในเบราว์เซอร์ของผู้ใช้** ที่ทำงาน
ควบคู่กันได้

**ก้าวต่อไป**: Part 87 จะกลับไปแก้ปัญหาที่หัวข้อ 86.7 ทิ้งไว้อย่างเป็นระบบเต็มรูปแบบ — กลไกเบื้องหลังของ
`wasm-bindgen` ที่ทำให้ `String`, `Vec<T>`, `struct`, และ `JsValue` ข้ามพรมแดน WASM/JavaScript ได้อย่างปลอดภัย
โดยไม่ต้องเขียน pointer+length ด้วยมือแบบที่เห็นในหัวข้อ 86.7 พร้อมทั้งลงรายละเอียดเรื่อง `web-sys` สำหรับเรียก
Web API (DOM, console, fetch) จาก Rust โดยตรง — เป็นก้าวสำคัญที่ทำให้ Rust+WASM ใช้งานได้จริงในโปรเจกต์ frontend
เต็มรูปแบบ ก่อนที่ Part 88-90 จะพาไปสร้าง UI ทั้งหน้าด้วย framework อย่าง Yew, Leptos, และ Dioxus
