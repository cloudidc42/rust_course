# Part 51: Atomics และ Lock-free Programming

> โมดูล: ระดับสูง (Advanced) | ระดับ: สูง | เวลาโดยประมาณ: 250 นาที

## เป้าหมายของบทเรียน

หลังจากจบบทนี้ คุณจะสามารถ:

- อธิบายได้อย่างแม่นยำว่า "atomic operation" ที่ Part 39 และ Part 40 ใช้คำนี้แบบผิวเผินมาตลอด (บอกแค่ว่ามันคือ
  "คำสั่งระดับ CPU ที่ไม่มีใครมาแทรกกลางทางได้") จริง ๆ แล้วทำงานอย่างไร และรู้จัก type ทั้งตระกูลใน
  `std::sync::atomic` (`AtomicBool`, `AtomicI32`/`AtomicU32`/`AtomicI64`/`AtomicUsize` ฯลฯ) พร้อม operation
  พื้นฐาน `.load()`, `.store()`, `.fetch_add()`, `.fetch_sub()`, `.compare_exchange()`
- สร้าง shared counter ข้าม thread ด้วย `Arc<AtomicI32>` แทน `Arc<Mutex<i32>>` จาก Part 39 ได้ พิสูจน์ด้วยโค้ด
  จริงที่รันซ้ำหลายสิบครั้งว่าให้ผลลัพธ์ถูกต้อง 100% เหมือนกัน แต่ **ไม่ต้องใช้ lock เลย** และเข้าใจภาพรวมว่าทำไม
  มันมักจะเร็วกว่า `Mutex` สำหรับ operation ง่าย ๆ แบบนี้
- อธิบาย **memory ordering** ได้อย่างลึกซึ้ง — เข้าใจว่าทำไม CPU และ compiler ถึง "จัดลำดับใหม่" (reorder)
  คำสั่งได้ตั้งแต่แรก, ความแตกต่างเชิงประกันของ `Ordering::Relaxed`, `Ordering::Acquire`,
  `Ordering::Release`, `Ordering::AcqRel`, และ `Ordering::SeqCst` ในระดับที่ใช้งานได้จริง พร้อมรู้คำแนะนำเชิง
  ปฏิบัติว่าเมื่อไหร่ควรใช้ตัวไหน
- ใช้ `compare_exchange`/`compare_exchange_weak` เขียน **CAS retry loop** ซึ่งเป็นหน่วยการสร้าง (building
  block) พื้นฐานที่สุดของอัลกอริทึม lock-free ทั้งหมดได้ด้วยตัวเอง ผ่านตัวอย่างที่รันจริงและพิสูจน์ความถูกต้อง
- อธิบายนิยามที่ถูกต้องแม่นยำของคำว่า **"lock-free"** (ซึ่งถูกเข้าใจผิดกันบ่อยมาก) แยกความแตกต่างจาก
  **"wait-free"** และ "blocking" (`Mutex`) ได้ พร้อมเชื่อมโยงกับปัญหา deadlock/priority inversion ที่เรียนใน
  Part 39
- อธิบาย **ABA problem** ได้อย่างเป็นรูปธรรม (ปัญหาคลาสสิกที่สุดของ CAS-based algorithm) รู้จักแนวทางบรรเทา
  ปัญหา (generation counter, tagged pointer) ในระดับที่พอเข้าใจว่ามันแก้ปัญหาอะไร
- ตัดสินใจได้อย่างมีเหตุผลในงานจริงว่าเมื่อไหร่ควรใช้ `Mutex`/`RwLock` (Part 39) เมื่อไหร่ควรลองใช้ atomics ตรง ๆ
  และเมื่อไหร่ควรพึ่งพา crate ที่ผ่านการทดสอบมาอย่างหนัก (เช่น `crossbeam`) แทนการเขียน lock-free data
  structure เองตั้งแต่ต้น

## ความรู้ที่ต้องมีมาก่อน

บทนี้เป็นบทที่ **เปิดกล่องที่ Part 39 และ Part 40 ปิดไว้โดยตั้งใจ** ทั้งสองบทใช้คำว่า "atomic" ซ้ำแล้วซ้ำอีกเพื่อ
อธิบายว่าทำไม `Arc<T>` ปลอดภัยข้าม thread ในขณะที่ `Rc<T>` ไม่ปลอดภัย แต่ทั้งสองบทก็บอกตรง ๆ ว่า "รายละเอียดเต็ม
รูปแบบของ atomic operation และ lock-free programming เป็นเรื่องของ Part 51" — นี่คือ Part 51 ที่ถูกสัญญาไว้:

- **Part 39 (Mutex, Arc และ Shared-State Concurrency)** — นี่คือความรู้ที่จำเป็นที่สุดสำหรับบทนี้ บทนี้จะ
  สร้าง shared counter ตัวเดียวกันเป๊ะกับที่ Part 39 หัวข้อ 39.7 สร้างด้วย `Arc<Mutex<i32>>` ขึ้นมาใหม่อีกรอบ
  ด้วย `Arc<AtomicI32>` เพื่อเทียบให้เห็นตรง ๆ ว่าทั้งสองวิธีแก้ปัญหาเดียวกันได้ถูกต้อง 100% เหมือนกัน แต่ใช้
  กลไกเบื้องหลังต่างกันโดยสิ้นเชิง — คุณควรเข้าใจ `Mutex<T>`, `MutexGuard<T>`, การ block thread อื่น, และ
  deadlock จาก Part 39 อย่างแม่นยำก่อนอ่านบทนี้ เพราะบทนี้จะเทียบกับสิ่งเหล่านั้นตลอดเวลา
  (โดยเฉพาะหัวข้อ 51.9 ที่เชื่อมกลับไปที่การอภิปราย deadlock ในหัวข้อ 39.9)
- **Part 40 (Send, Sync และความปลอดภัยของ Concurrency)** — Part 40 อธิบายไปแล้วว่า `Arc<T>` implement `Send`
  ได้เพราะตัวนับภายในของมันเป็น atomic (ไม่ใช่ `Cell<usize>` ธรรมดาแบบ `Rc<T>`) และบอกไว้ตรง ๆ ในหัวข้อ 40.7
  ว่า "Part 51 เรื่อง Atomics จะเจาะรายละเอียดต้นทุนนี้เพิ่ม" — บทนี้คือคำตอบเต็มรูปแบบของประโยคนั้น คุณต้องเข้าใจ
  ความหมายของ `Send`/`Sync` มาก่อน เพราะทุก type ใน `std::sync::atomic` เป็นทั้ง `Send` และ `Sync` โดยธรรมชาติ
  ของการออกแบบ (มันถูกสร้างมาเพื่อแบ่งกันใช้ข้าม thread โดยตรง)
- **Part 37 (Threads พื้นฐาน)** — `std::thread::spawn`, `move` closure, และ `JoinHandle::join()` ถูกใช้ในทุก
  ตัวอย่างของบทนี้เหมือนเดิม เพราะทุกตัวอย่างต้องสร้างหลาย thread จริงเพื่อพิสูจน์ความถูกต้องของ atomic operation
  ภายใต้การแข่งขันจริง
- **Part 41-42 (Unsafe Rust เบื้องต้น, Raw Pointers และ Memory Layout)** — บทนี้จะพูดถึง `AtomicPtr<T>`
  ซึ่งเป็น atomic operation บน raw pointer (`*mut T` จาก Part 42) โดยตรง และการ dereference ค่าที่ได้จากมัน
  ต้องอยู่ใน `unsafe` block เสมอ (กฎเดียวกับ Part 41) — ถ้ายังไม่คุ้นกับ raw pointer และ `unsafe fn`/`unsafe`
  block ควรทวน Part 41-42 ก่อน แม้บทนี้จะพูดถึง `AtomicPtr<T>` แค่ในระดับ awareness ไม่ลงลึกการสร้าง data
  structure เต็มรูปแบบ
- **Part 12 (Result\<T, E\>)** — `compare_exchange` คืนค่าเป็น `Result<T, T>` (ไม่ใช่ `Result<T, E>` ทั่วไป —
  ทั้ง `Ok` และ `Err` เก็บค่าชนิดเดียวกัน) การอ่าน pattern `match`/`Ok`/`Err` จาก Part 12 จะถูกใช้ตลอดบทนี้

บทนี้เป็นบทแรกในสามบทสุดท้ายของสายเนื้อหาเชิงระบบล้วน ๆ ของโมดูล 3 (Part 51 เรื่อง atomics ตามด้วย Part 52-53
เรื่อง design patterns ที่กลับมาสู่ Rust แบบ "ใช้งานประจำวัน" มากขึ้น และ Part 54-56 เรื่อง performance ที่จะ
กลับมาแตะเรื่อง memory ordering อีกครั้งจากมุมมองการวัดผลจริง)

## เนื้อหา

### 51.1 ทวนความจำ: กล่องที่ Part 39-40 ปิดไว้ ตอนนี้เปิดแล้ว

ใน Part 39 หัวข้อ 39.6 เราเจอประโยคนี้ตอนอธิบายว่าทำไม `Arc<T>` ปลอดภัยข้าม thread ในขณะที่ `Rc<T>` ไม่ปลอดภัย:

> "'Atomic operation' ในความหมายที่ใช้งานได้จริงตรงนี้ (ไม่ลงลึกทฤษฎี lock-free เต็มรูปแบบ ซึ่งเป็นเนื้อหาของ
> Part 51) คือ: **คำสั่งระดับ CPU ที่รับประกันว่าจะทำงาน 'ครบทั้งหมดในครั้งเดียวโดยไม่มีใครมาแทรกกลางทางได้'**"

และ Part 40 หัวข้อ 40.7 ก็ทิ้งท้ายไว้อีกครั้งว่า:

> "atomic operation แม้จะไม่ได้ช้ามาก แต่ก็ยังช้ากว่า plain integer operation อย่างมีนัยสำคัญเมื่อเรียกบ่อย
> ขนาดนี้ Part 51 เรื่อง Atomics จะเจาะรายละเอียดต้นทุนนี้เพิ่ม"

ทั้งสองประโยคนี้ให้ภาพที่ **เพียงพอสำหรับใช้งาน `Arc<T>` อย่างถูกต้อง** แต่ยังเป็นภาพที่ "เชื่อไว้ก่อน" — เรารู้ว่า
`Arc<T>` มีตัวนับที่ "เป็น atomic" และรู้ว่ามันทำให้ `Arc<T>` เป็น `Send`/`Sync` ได้ แต่เราไม่รู้ว่า:

1. `AtomicUsize` (ชนิดจริงที่ `Arc<T>` ใช้เก็บตัวนับภายใน) มี API หน้าตาแบบไหน และเราเขียนโค้ดที่ใช้ atomic
   type ตรง ๆ เองได้อย่างไร (ไม่ต้องพึ่ง `Arc<T>`/`Mutex<T>` เสมอไป)
2. "ไม่มีใครมาแทรกกลางทางได้" ใน operation เดียว (เช่น `fetch_add`) นั้นเพียงพอแค่ไหนสำหรับการเขียนโปรแกรม
   จริง ที่มักต้องทำ **หลาย** atomic operation เรียงกัน (เช่น อ่านค่า A แล้วเขียนค่า B ตามค่าที่อ่านมา) — คำตอบ
   คือ **ไม่พอเสมอไป** และนี่คือที่มาของแนวคิดเรื่อง memory ordering ที่จะเป็นหัวใจของบทนี้
3. Lock-free programming จริง ๆ แปลว่าอะไร ทำไมมันถึง "ยาก" กว่าที่คำว่า "แค่ใช้ atomic แทน mutex" ฟังดูเป็น
   ในตอนแรก และมีข้อผิดพลาดคลาสสิกอะไรที่รอดักอยู่ (ABA problem)

บทนี้จะตอบทั้งสามข้อนี้เต็มรูปแบบ โดยเริ่มจากการรู้จัก type ทั้งตระกูลใน `std::sync::atomic` ก่อน

### 51.2 `std::sync::atomic`: ตระกูล Atomic Types และ Operation พื้นฐาน

Rust standard library มี atomic type ให้ครบทุก integer type พื้นฐาน (ทั้งมีเครื่องหมายและไม่มีเครื่องหมาย ทุก
ขนาด) บวกกับ `AtomicBool` และ `AtomicPtr<T>` (จะพูดถึงในหัวข้อ 51.12) — รายชื่อหลักที่ใช้บ่อยที่สุด:

| Atomic type | เทียบเท่า type ปกติ |
|---|---|
| `AtomicBool` | `bool` |
| `AtomicI8`/`AtomicU8` | `i8`/`u8` |
| `AtomicI16`/`AtomicU16` | `i16`/`u16` |
| `AtomicI32`/`AtomicU32` | `i32`/`u32` |
| `AtomicI64`/`AtomicU64` | `i64`/`u64` |
| `AtomicIsize`/`AtomicUsize` | `isize`/`usize` (ตัวที่ `Arc<T>`/`Rc<T>` ใช้เก็บตัวนับ) |
| `AtomicPtr<T>` | `*mut T` (raw pointer จาก Part 42) |

สังเกตว่านี่**ไม่ใช่ generic type** แบบ `Atomic<T>` ที่รับ `T` อะไรก็ได้ — แต่ละ type ถูกกำหนดตายตัวไว้ทีละชนิด
เหตุผลคือ atomic operation ต้องแปลไปเป็นคำสั่ง CPU จริงที่ฮาร์ดแวร์รองรับ (เช่น `LOCK XADD` บน x86-64,
`LDXR`/`STXR` บน ARM) ซึ่งมีอยู่แค่สำหรับขนาดข้อมูลที่ CPU จัดการได้ในคำสั่งเดียว (ปกติคือ 8/16/32/64 บิต ตรงกับ
register ทั่วไป) — ไม่มีทางมี "atomic operation" สำหรับ struct ขนาดใหญ่ตามใจชอบได้ในระดับฮาร์ดแวร์ ดังนั้น
`std::sync::atomic` จึงจำกัดไว้เฉพาะ type ที่ฮาร์ดแวร์รองรับจริง

(หมายเหตุเรื่อง platform: บนสถาปัตยกรรม 32-bit บางแบบที่เก่ามาก ๆ `AtomicI64`/`AtomicU64` อาจไม่มีให้ใช้เพราะ
ฮาร์ดแวร์ไม่รองรับ atomic operation ขนาด 64 บิตในคำสั่งเดียว — Rust จะไม่ให้ compile ผ่านเลยถ้า target ไม่
รองรับ ไม่ใช่การ fallback แบบเงียบ ๆ ไปใช้ lock ภายในแทน ในทางปฏิบัติสำหรับเครื่อง desktop/server สมัยใหม่ทั้ง
x86-64 และ ARM64 ทุกตัวรองรับ 64-bit atomic ครบทุกตัวอยู่แล้ว จึงไม่ต้องกังวลเรื่องนี้ในโค้ดส่วนใหญ่)

ทุก atomic type มี method หลักชุดเดียวกัน (ชื่อ method เหมือนกันทุก type แค่เปลี่ยน type ของ argument/return):

- **`.load(order)`** — อ่านค่าปัจจุบันแบบ atomic คืนค่าเป็น type ปกติ (ไม่ใช่ atomic)
- **`.store(value, order)`** — เขียนค่าใหม่แบบ atomic ไม่คืนค่าอะไร
- **`.fetch_add(value, order)`** — บวกค่าเข้าไปแบบ atomic (อ่าน-บวก-เขียน เป็น operation เดียวไม่มีใครแทรกได้)
  คืนค่า**ก่อน**บวก (ค่าเก่า)
- **`.fetch_sub(value, order)`** — เหมือน `fetch_add` แต่ลบแทนบวก
- **`.compare_exchange(current, new, success_order, failure_order)`** — "ถ้าค่าตอนนี้ยังเป็น `current`
  เหมือนที่คาดไว้ ให้เปลี่ยนเป็น `new`; ไม่ใช่ ให้บอกค่าจริงตอนนี้กลับมา" (รายละเอียดเต็มในหัวข้อ 51.8)

สังเกตว่าทุก method รับ parameter ชื่อ `order` ที่มี type เป็น `std::sync::atomic::Ordering` — นี่คือสิ่งที่
Part 39/40 ไม่ได้อธิบาย และจะเป็นหัวข้อหลักของบทนี้ตั้งแต่หัวข้อ 51.4 เป็นต้นไป ตอนนี้ให้ใช้ `Ordering::SeqCst`
ไปก่อน (ตัวที่ประกันแน่นที่สุด เข้าใจง่ายที่สุด) เพื่อโฟกัสที่ operation ก่อน:

```rust
use std::sync::atomic::{AtomicBool, AtomicI32, AtomicUsize, Ordering};

fn main() {
    // AtomicBool: .load() / .store()
    let flag = AtomicBool::new(false);
    println!("flag เริ่มต้น: {}", flag.load(Ordering::SeqCst));
    flag.store(true, Ordering::SeqCst);
    println!("flag หลัง store: {}", flag.load(Ordering::SeqCst));

    // AtomicI32: .fetch_add() / .fetch_sub()
    let counter = AtomicI32::new(10);
    let old = counter.fetch_add(5, Ordering::SeqCst);
    println!("fetch_add คืนค่าเก่า: {}, ค่าใหม่ตอนนี้: {}", old, counter.load(Ordering::SeqCst));
    let old2 = counter.fetch_sub(3, Ordering::SeqCst);
    println!("fetch_sub คืนค่าเก่า: {}, ค่าใหม่ตอนนี้: {}", old2, counter.load(Ordering::SeqCst));

    // AtomicUsize: .compare_exchange()
    let version = AtomicUsize::new(1);
    let result = version.compare_exchange(1, 2, Ordering::SeqCst, Ordering::SeqCst);
    println!("compare_exchange(expected=1, new=2) เมื่อค่าจริงคือ 1: {:?}", result);
    println!("version ตอนนี้: {}", version.load(Ordering::SeqCst));

    let result2 = version.compare_exchange(1, 99, Ordering::SeqCst, Ordering::SeqCst);
    println!("compare_exchange(expected=1, new=99) เมื่อค่าจริงคือ 2: {:?}", result2);
    println!("version ตอนนี้: {}", version.load(Ordering::SeqCst));
}
```

ผลลัพธ์ (รันจริง):

```
flag เริ่มต้น: false
flag หลัง store: true
fetch_add คืนค่าเก่า: 10, ค่าใหม่ตอนนี้: 15
fetch_sub คืนค่าเก่า: 15, ค่าใหม่ตอนนี้: 12
compare_exchange(expected=1, new=2) เมื่อค่าจริงคือ 1: Ok(1)
version ตอนนี้: 2
compare_exchange(expected=1, new=99) เมื่อค่าจริงคือ 2: Err(2)
version ตอนนี้: 2
```

สังเกตผลของ `compare_exchange` สองครั้งให้ชัด: ครั้งแรกคาดหวังค่า `1` และค่าจริงตอนนั้นก็คือ `1` พอดี — สำเร็จ
(`Ok`) เปลี่ยนเป็น `2` จริง ครั้งที่สองยังคาดหวังค่า `1` เหมือนเดิม (เขียนโค้ดผิดโดยตั้งใจเพื่อสาธิต) แต่ค่าจริง
ตอนนี้กลายเป็น `2` ไปแล้วจากการเปลี่ยนครั้งก่อน — ล้มเหลว (`Err`) และ **ไม่มีการเขียนอะไรเกิดขึ้นเลย** ค่ายังคง
เป็น `2` เหมือนเดิม พร้อมกับ**บอกค่าจริงปัจจุบัน (`2`) กลับมาให้ทันที** ผ่าน `Err(2)` — นี่คือจุดสำคัญที่สุดของ
`compare_exchange` ที่จะเป็นหัวใจของหัวข้อ 51.8: มันไม่ได้แค่บอกว่า "ล้มเหลว" เฉย ๆ แต่บอกค่าจริงที่ควรใช้ต่อไป
ในคราวเดียวกัน ทำให้เขียน retry loop ได้โดยไม่ต้อง `.load()` แยกอีกรอบ

### 51.3 สร้าง Shared Counter ใหม่ด้วย `Arc<AtomicI32>`: ไม่ต้องมี Lock เลย

มาลองสร้างตัวอย่าง shared counter ตัวเดียวกันเป๊ะกับที่ Part 39 หัวข้อ 39.7 สร้างด้วย `Arc<Mutex<i32>>` ขึ้นมา
ใหม่อีกรอบ แต่คราวนี้ใช้ `Arc<AtomicI32>` แทน — สร้าง 3 thread ที่แต่ละตัวเพิ่มค่าตัวนับคนละครั้ง:

```rust
use std::sync::atomic::{AtomicI32, Ordering};
use std::sync::Arc;
use std::thread;

fn main() {
    let counter = Arc::new(AtomicI32::new(0));
    let mut handles = vec![];

    for _ in 0..3 {
        let counter = Arc::clone(&counter);
        let handle = thread::spawn(move || {
            counter.fetch_add(1, Ordering::SeqCst);
        });
        handles.push(handle);
    }

    for handle in handles {
        handle.join().unwrap();
    }

    println!("Result: {}", counter.load(Ordering::SeqCst));
    assert_eq!(counter.load(Ordering::SeqCst), 3);
    println!("assert_eq! ผ่าน: ค่าถูกต้อง 100% ไม่มี increment สูญหาย");
}
```

ผลลัพธ์ (รันจริง — และตรวจซ้ำด้วยการรันโปรแกรมนี้ **30 ครั้ง** ผลลัพธ์เหมือนกันทุกครั้งไม่มีข้อยกเว้น):

```
Result: 3
assert_eq! ผ่าน: ค่าถูกต้อง 100% ไม่มี increment สูญหาย
```

เทียบกับโค้ด `Arc<Mutex<i32>>` ของ Part 39 หัวข้อ 39.7 ตรง ๆ:

| ขั้นตอน | `Arc<Mutex<i32>>` (Part 39) | `Arc<AtomicI32>` (บทนี้) |
|---|---|---|
| สร้างตัวนับร่วม | `Arc::new(Mutex::new(0))` | `Arc::new(AtomicI32::new(0))` |
| แบ่งให้แต่ละ thread | `Arc::clone(&counter)` | `Arc::clone(&counter)` (**เหมือนกันเป๊ะ**) |
| เพิ่มค่า | `*counter.lock().unwrap() += 1;` (ต้องขอ lock ก่อน) | `counter.fetch_add(1, Ordering::SeqCst);` (ไม่มี lock ให้ขอเลย) |
| อ่านค่าสุดท้าย | `*counter.lock().unwrap()` | `counter.load(Ordering::SeqCst)` |
| กลไกป้องกัน race | OS-level หรือ userspace lock (block thread อื่นถ้าถือ lock อยู่) | CPU instruction เดียวที่แบ่งแยกไม่ได้ (ไม่มี thread ไหนต้อง "block" รอปลดล็อกเลย) |

สิ่งที่หายไปโดยสิ้นเชิงคือ **การ block** — ไม่มี `MutexGuard<T>` ให้ถือ ไม่มี thread ไหนต้อง "รอคิว" ให้ thread
อื่นปลดล็อกก่อนแบบที่เห็นในตัวอย่าง Part 39 หัวข้อ 39.4 (ที่ thread B ต้องรอจนถึง ~300ms กว่าจะได้ lock) —
`fetch_add` ของทุก thread จะทำงานสำเร็จทันทีที่ CPU ประมวลผลคำสั่งนั้นถึง ไม่มีแนวคิดเรื่อง "block" อยู่ในระดับนี้
เลย เพราะฮาร์ดแวร์ (ผ่านกลไก cache coherency protocol ของ CPU หลาย core) รับประกันว่าคำสั่ง fetch-and-add จาก
หลาย core ที่มาชนกันพร้อมกันเป๊ะ ๆ จะถูก**เรียงลำดับทำให้เสร็จทีละตัว**เสมอที่ระดับฮาร์ดแวร์ — ไม่มี thread ใด
ต้อง "หยุดทำงานไปรอ" จริง ๆ (แม้ในทางฟิสิกส์อาจมี core หนึ่งต้องรอ core อื่นเขียน cache line เสร็จก่อนไม่กี่
นาโนวินาที แต่นั่นเป็นความล่าช้าระดับฮาร์ดแวร์ที่เล็กกว่าการ context switch ของ OS lock มากมาย ไม่ใช่การ "block"
แบบที่ scheduler ต้องเข้ามาจัดการ)

ลองพิสูจน์ความถูกต้องภายใต้ load ที่หนักขึ้นมาก (แบบเดียวกับที่ Part 39 แบบฝึกหัดข้อ 2 ให้ทำนายผลก่อนรัน) —
8 thread เพิ่มค่าคนละ 100,000 ครั้ง คาดว่าผลรวมต้องเป็น 800,000 เป๊ะเสมอ ไม่ว่า thread จะ schedule มาลำดับไหน:

```rust
use std::sync::atomic::{AtomicI64, Ordering};
use std::sync::Arc;
use std::thread;

fn main() {
    let counter = Arc::new(AtomicI64::new(0));
    let mut handles = vec![];

    for _ in 0..8 {
        let counter = Arc::clone(&counter);
        handles.push(thread::spawn(move || {
            for _ in 0..100_000 {
                counter.fetch_add(1, Ordering::SeqCst);
            }
        }));
    }

    for h in handles {
        h.join().unwrap();
    }

    let result = counter.load(Ordering::SeqCst);
    println!("ผลรวมสุดท้าย: {}", result);
    assert_eq!(result, 800_000);
}
```

ผลลัพธ์ (รันจริง — ตรวจซ้ำด้วยการรัน **20 ครั้ง** ทุกครั้งได้ `800000` เป๊ะ ไม่มี increment สูญหายแม้แต่ครั้ง
เดียวจากการแข่งขันจริงของ 800,000 operation ที่กระจายอยู่ใน 8 thread พร้อมกัน):

```
ผลรวมสุดท้าย: 800000
```

ทำไม `fetch_add` ถึงไม่มีทาง "สูญหาย" การเพิ่มค่าแม้ 8 thread จะแข่งกันเรียกพร้อมกันจริง ๆ ในขณะที่ Part 40
หัวข้อ 40.4 พิสูจน์ให้เห็นว่าตัวนับธรรมดา (`count += 1` แบบ read-modify-write ปกติ) ของ `Rc<T>` **สูญหาย**การ
อัปเดตได้จากการแข่งขันแบบเดียวกัน? คำตอบคือ `fetch_add` **ไม่ได้แยกเป็นสามขั้นตอน** (อ่าน → บวก → เขียน) ที่
thread อื่นมีโอกาสมาแทรกกลางทางได้ — มันคือ**คำสั่งเดียว** (หรือกลุ่มคำสั่งที่ฮาร์ดแวร์บังคับให้ทำสำเร็จเป็นหน่วย
เดียวที่แบ่งแยกไม่ได้จริง ๆ) พูดอีกแบบ: การที่ตัวนับของ `Rc<T>` พังจากการแข่งขันไม่ใช่เพราะ "การบวกเลขมันพังได้"
แต่เพราะ**มันไม่ได้ใช้ atomic operation ตั้งแต่แรก** — พอเปลี่ยนมาใช้ `fetch_add` ที่เป็น atomic operation
จริง ปัญหานั้นหายไปทันทีโดยไม่ต้องมี lock ใด ๆ เข้ามาเกี่ยวข้องเลย

#### เปรียบเทียบประสิทธิภาพคร่าว ๆ: Atomic vs Mutex สำหรับ Operation ง่าย ๆ

เหตุผลที่ atomic operation มัก**เร็วกว่า** `Mutex` สำหรับสถานการณ์แบบนี้ (ตัวแปรเดี่ยว ๆ ที่แค่ต้องการ
increment/decrement/compare-and-swap) มาจากสิ่งที่ `Mutex::lock()` ต้องทำเพิ่มเติมจาก atomic operation ตรง ๆ:
`Mutex` ต้องมี "คิว" ของ thread ที่รออยู่ (ถ้าแข่งกันมาก), อาจต้องพึ่ง syscall ของ OS (เช่น `futex` บน Linux)
เพื่อให้ thread ที่รออยู่ "หลับ" แทนที่จะกิน CPU วนรอเปล่า ๆ (busy-wait) และการปลุก thread ที่หลับอยู่กลับมาก็มี
ต้นทุนของ context switch — ทั้งหมดนี้เป็นงานที่ **มากกว่า** การรันคำสั่ง CPU ตัวเดียวของ `fetch_add` มาก มาลอง
วัดจริงเพื่อเห็นตัวเลข (4 thread เพิ่มค่าคนละ 500,000 ครั้ง เทียบเวลาที่ใช้ทั้งหมด):

```rust
use std::sync::atomic::{AtomicI64, Ordering};
use std::sync::{Arc, Mutex};
use std::thread;
use std::time::Instant;

const THREADS: usize = 4;
const ITERS: usize = 500_000;

fn bench_mutex() -> u128 {
    let counter = Arc::new(Mutex::new(0i64));
    let start = Instant::now();
    let mut handles = vec![];
    for _ in 0..THREADS {
        let counter = Arc::clone(&counter);
        handles.push(thread::spawn(move || {
            for _ in 0..ITERS {
                let mut guard = counter.lock().unwrap();
                *guard += 1;
            }
        }));
    }
    for h in handles {
        h.join().unwrap();
    }
    start.elapsed().as_millis()
}

fn bench_atomic() -> u128 {
    let counter = Arc::new(AtomicI64::new(0));
    let start = Instant::now();
    let mut handles = vec![];
    for _ in 0..THREADS {
        let counter = Arc::clone(&counter);
        handles.push(thread::spawn(move || {
            for _ in 0..ITERS {
                counter.fetch_add(1, Ordering::SeqCst);
            }
        }));
    }
    for h in handles {
        h.join().unwrap();
    }
    start.elapsed().as_millis()
}

fn main() {
    let mutex_ms = bench_mutex();
    let atomic_ms = bench_atomic();
    println!("Mutex<i64>:   {} ms  ({} threads x {} increments)", mutex_ms, THREADS, ITERS);
    println!("AtomicI64:    {} ms  ({} threads x {} increments)", atomic_ms, THREADS, ITERS);
}
```

ผลลัพธ์ (รันจริงในสภาพแวดล้อมที่ใช้เขียนบทนี้ — ตัวเลขที่ได้ในเครื่องของคุณจะ**ต่างออกไปแน่นอน** ขึ้นกับจำนวน
CPU core, สถาปัตยกรรม, และภาระงานอื่น ๆ ของระบบตอนนั้น ตัวเลขด้านล่างนี้มีไว้เพื่อแสดง**สัดส่วนคร่าว ๆ** เท่านั้น
ไม่ใช่ค่าอ้างอิงที่รับประกันซ้ำได้เป๊ะทุกเครื่อง):

```
Mutex<i64>:   64 ms  (4 threads x 500000 increments)
AtomicI64:    23 ms  (4 threads x 500000 increments)
```

ในการรันซ้ำหลายครั้งบนเครื่องเดียวกัน `AtomicI64` ใช้เวลาน้อยกว่า `Mutex<i64>` อยู่ในช่วงประมาณ 1.5-3 เท่าอย่าง
สม่ำเสมอสำหรับ workload แบบนี้โดยเฉพาะ (increment ตัวแปรเดี่ยว ๆ ล้วน ๆ ไม่มีงานอื่นแทรก) — นี่คือเหตุผลที่ควร
จำไว้เป็นภาพรวม (ไม่ใช่กฎเหล็กที่ใช้ได้ทุกกรณี): **ถ้าสิ่งที่ต้องการป้องกัน race คือค่าตัวเดียวที่ทำ operation
ง่าย ๆ (increment, flag on/off, compare-and-swap) atomic type ตรง ๆ มักเป็นตัวเลือกที่คุ้มค่ากว่า `Mutex` ทั้ง
ในแง่ความเร็วและในแง่ที่ไม่มีความเสี่ยง deadlock/poisoning เลย** — แต่ถ้าต้องป้องกันหลายค่าที่ต้อง**สัมพันธ์กัน**
พร้อมกัน (เช่นตัวอย่างระบบธนาคารใน Part 39 ที่ต้องหักเงินจากบัญชีหนึ่งแล้วเพิ่มให้อีกบัญชีเป็น atomic operation
เดียวจริง ๆ) `Mutex` ยังจำเป็นอยู่ เพราะ atomic type แต่ละตัวรับประกันความถูกต้องได้แค่ตัวมันเองเดี่ยว ๆ เท่านั้น
ไม่มีทางทำให้การเปลี่ยนแปลงสองตัวแปรเกิดขึ้น "พร้อมกันเป็นหน่วยเดียว" ได้เลยด้วย atomic ตรง ๆ (หัวข้อ 51.11 จะ
กลับมาขยายประเด็นนี้เต็มรูปแบบ)

### 51.4 Memory Ordering: ทำไม "Atomic ครั้งเดียว" ยังไม่พอ

ตัวอย่างในหัวข้อ 51.3 ทั้งหมดมีจุดร่วมกันอย่างหนึ่งที่อาจไม่ทันสังเกต: **มันเกี่ยวข้องกับตัวแปร atomic แค่ตัว
เดียว** และแต่ละ thread ก็แค่เรียก operation เดียว (`fetch_add`) ต่อรอบ ซึ่งเป็นสถานการณ์ที่ตรงไปตรงมาที่สุด —
แต่โปรแกรมจริงมักซับซ้อนกว่านั้น: บ่อยครั้งเราต้องการเขียนข้อมูล**หลายค่า**ให้ thread อื่นเห็น**ตามลำดับที่
ถูกต้อง** เช่น:

```
Thread A (producer):
  1. เขียนข้อมูลจริงลงในตัวแปรธรรมดา (ไม่ใช่ atomic) -- เช่น payload = 42
  2. เขียน flag บอกว่า "ข้อมูลพร้อมแล้ว" -- ready = true (เป็น atomic)

Thread B (consumer):
  3. รออ่าน ready จนเห็น true
  4. อ่าน payload -- คาดหวังว่าต้องเห็น 42 แน่นอน เพราะ ready บอกว่า "พร้อมแล้ว"
```

คำถามที่ดูเหมือนไม่น่าจะมีปัญหาอะไร: ถ้า thread B เห็น `ready == true` แล้ว มันจะเห็น `payload == 42` เสมอ
ไหม? **คำตอบคือ "ไม่แน่นอน" ถ้าไม่ระบุ memory ordering ให้ถูกต้อง** — และนี่คือประเด็นที่ลึกและสำคัญที่สุดของ
บทนี้ ต้องเข้าใจให้ทะลุจริง ๆ ว่าทำไม

#### ทำไม CPU และ Compiler ถึง "จัดลำดับใหม่" คำสั่งได้

ทั้ง **compiler** (ตอน optimize โค้ด) และ **CPU** (ตอนรันคำสั่งจริงในฮาร์ดแวร์) มีสิทธิ์ **จัดลำดับการทำงานของ
คำสั่งใหม่** (reorder) ได้ ตราบใดที่ผลลัพธ์ที่มองจาก**เธรดเดียวกัน**ยังคงถูกต้องเหมือนเดิมทุกประการ — นี่ไม่ใช่
บั๊ก แต่เป็น**การ optimize ที่จำเป็นมาก**สำหรับความเร็วของโปรแกรมสมัยใหม่:

- **Compiler reordering**: ถ้า compiler เห็นว่าสองคำสั่งไม่มี data dependency ระหว่างกันจากมุมมองของ
  single-thread (เช่น เขียนตัวแปร A แล้วเขียนตัวแปร B ที่ไม่เกี่ยวกันเลย) มันอาจสลับลำดับการ generate
  instruction ของทั้งสองเพื่อจัดวาง register/instruction pipeline ให้มีประสิทธิภาพที่สุด — ในโลกที่มีแค่
  thread เดียว ไม่มีใครสังเกตความแตกต่างได้เลยไม่ว่าจะเขียน A ก่อน B หรือ B ก่อน A เพราะผลลัพธ์สุดท้ายที่
  thread เดียวกันเห็นเหมือนกันทุกกรณี
- **CPU reordering (out-of-order execution)**: CPU สมัยใหม่ทุกตัวไม่ได้รันคำสั่งเรียงตามลำดับที่เขียนในโค้ด
  ตรง ๆ เป๊ะ ๆ — มันมี pipeline หลายขั้นตอนและ execution unit หลายตัวที่ทำงานคู่ขนานกันได้ ถ้าคำสั่งสองตัวไม่มี
  dependency กัน CPU อาจรันคำสั่งที่มาทีหลังในโค้ดให้เสร็จก่อนคำสั่งที่มาก่อนได้จริง (เพื่อไม่ให้ execution unit
  ว่างเปล่ารอ data ที่ยังมาไม่ถึง) นอกจากนี้ยังมี **store buffer** ที่ทำให้การเขียนค่าไปที่ memory จริง ๆ อาจ
  "ล่าช้า" กว่าที่โค้ดเขียนไว้ก็ได้ (CPU core ที่เขียนเห็นค่าใหม่ทันทีจาก store buffer ของตัวเอง แต่ core อื่น
  ที่มองผ่าน cache/memory อาจยังไม่เห็นค่านั้นในเวลาเดียวกัน)

ทั้งสองอย่างนี้ **ปลอดภัย 100% สำหรับโปรแกรม single-thread เสมอ** เพราะ compiler และ CPU รับประกันเสมอว่า
"จากมุมมองของโค้ดในเธรดเดียวกันเอง ทุกอย่างต้องดูเหมือนรันตามลำดับที่เขียนไว้เป๊ะ" (concept นี้เรียกว่า
**sequential consistency ภายในเธรดเดียว** — เป็นสัญญาที่ CPU ทุกตัวและ compiler ทุกตัวต้องรักษาไว้อยู่แล้ว โดย
ไม่เกี่ยวกับ `Ordering` ของ Rust เลย) แต่ปัญหาเกิดขึ้นทันทีที่มี **อีกเธรดหนึ่งกำลังมองเข้ามา** — เธรดอื่นไม่ได้
รับประกันแบบเดียวกันเลยว่าจะเห็นลำดับการเขียนของ memory ตรงกับลำดับที่โค้ดต้นฉบับเขียนไว้ ถ้าไม่มีกลไกพิเศษเข้า
มาบังคับลำดับนั้นให้ชัดเจน — นี่แหละคือหน้าที่ของ **memory ordering**: มันคือ**สัญญาที่คุณให้กับ compiler และ
CPU** ว่า "ห้ามจัดลำดับใหม่ข้าม operation นี้ในทิศทางที่กำหนด" เพื่อให้เธรดอื่นมองเห็นลำดับที่ถูกต้องได้จริง

Rust นำเข้าโมเดล memory ordering มาจาก C++11/C++20 memory model ตรง ๆ (ผ่าน `std::sync::atomic::Ordering`
ซึ่งมี variant ตรงกับ `std::memory_order` ของ C++) — โมเดลนี้มี 5 ระดับ ที่จะอธิบายทีละตัวในหัวข้อถัดไป:
`Relaxed`, `Acquire`, `Release`, `AcqRel`, และ `SeqCst`

### 51.5 `Ordering::Relaxed`: ประกันแค่ Atomicity ไม่ประกันลำดับ

`Ordering::Relaxed` คือระดับที่ **อ่อนที่สุด** — มันประกันแค่สิ่งเดียว: **operation นั้นเป็น atomic จริง**
(ไม่มีทาง "อ่านเห็นค่าที่เขียนไปครึ่ง ๆ กลาง ๆ" ค่าที่เห็นต้องเป็นค่าที่เคยถูก `.store()`/`.fetch_add()` ฯลฯ
เขียนไว้จริงเสมอค่าหนึ่งค่าใด ไม่มีทาง "ผสม" กันระหว่างสองค่า) **แต่ไม่ประกันอะไรเกี่ยวกับลำดับที่ operation นี้
สัมพันธ์กับ operation อื่น** (ทั้ง atomic operation ตัวอื่นและ operation ปกติที่ไม่ใช่ atomic รอบข้าง) —
compiler และ CPU มีสิทธิ์จัดลำดับ operation ที่ใช้ `Relaxed` ใหม่ได้อย่างเสรีเมื่อเทียบกับ operation อื่นรอบข้าง
ตราบใดที่ยังคง atomicity ของตัวมันเองไว้

พูดให้เป็นรูปธรรม: `Relaxed` เหมาะกับสถานการณ์ที่ **ตัวแปร atomic ตัวนั้นไม่ได้ใช้เป็น "สัญญาณ" ให้ข้อมูลตัวอื่น
เลย** — ตัวอย่างคลาสสิกที่สุดคือ counter ที่ใช้เก็บสถิติเฉย ๆ (เช่นตัวอย่าง statistics tracker ในหัวข้อ 51.14)
ที่แต่ละ thread แค่ต้องการเพิ่มค่าให้ถูกต้อง ไม่ได้ใช้ค่าของ counter เป็นตัวบอกว่า "ข้อมูลอื่นพร้อมแล้วหรือยัง"
เลยแม้แต่นิดเดียว ในกรณีแบบนี้ `Relaxed` ให้ประสิทธิภาพสูงสุด (compiler/CPU มีอิสระในการ optimize มากที่สุด)
โดยไม่เสียความถูกต้องอะไรเลย เพราะสิ่งที่โปรแกรมต้องการ (ผลรวมที่ถูกต้องเป๊ะ) ก็คือสิ่งเดียวที่ `Relaxed`
รับประกัน (atomicity ของตัวมันเอง)

แต่ในสถานการณ์ของหัวข้อ 51.4 (producer เขียน `payload` แล้วเขียน `ready` เพื่อ "ประกาศ" ให้ consumer อ่าน)
`Relaxed` **ไม่พอ** — เพราะตัวแปร `ready` ถูกใช้เป็นสัญญาณบอกลำดับของข้อมูลตัวอื่น (`payload`) แต่ `Relaxed`
ไม่ประกันความสัมพันธ์เชิงลำดับใด ๆ ให้เลย เราจะเห็นตัวอย่างที่เขียนแบบนี้ผิด ๆ ในหัวข้อ "กับดักที่พบบ่อย" — ตอน
นี้ให้จำไว้ก่อนว่า **ถ้าตัวแปร atomic ของคุณถูกใช้เป็น "flag ประกาศความพร้อม" หรือ "signal" ให้ข้อมูลตัวอื่นเลย
แม้แต่นิดเดียว `Relaxed` ไม่เพียงพอ** ต้องใช้ `Acquire`/`Release` (หัวข้อถัดไป) หรือ `SeqCst`

### 51.6 `Ordering::Acquire`/`Ordering::Release`/`Ordering::AcqRel`: คู่ "ปลดล็อก-ล็อก" ของ Memory Ordering

นี่คือคู่ ordering ที่ตรงกับสถานการณ์ producer/consumer ในหัวข้อ 51.4 พอดี และเป็นแนวคิดที่ลึกที่สุดของบทนี้ —
เข้าใจให้ทะลุตรงนี้แล้วส่วนที่เหลือของบทจะง่ายขึ้นมาก

**สัญชาตญาณที่ใช้ได้จริง**: ให้นึกถึงคำว่า "ปลดล็อก" (release) กับ "ล็อก" (acquire) ตรงตามชื่อจริง ๆ —
เหมือนกับ `Mutex` จาก Part 39 ที่ **ปลดล็อก (release) จบการถือ critical section** กับ **ล็อกได้ (acquire)
เริ่มถือ critical section ใหม่** เพียงแค่ตอนนี้เราทำแนวคิดเดียวกันนี้ **โดยไม่ต้องมี lock จริงเลย** ผ่าน atomic
operation ตัวเดียว:

- **`Ordering::Release`** (ใช้กับ `.store()` หรือฝั่งที่ "เขียน" ค่า) — รับประกันว่า **operation ทุกตัวที่
  เขียนไว้ก่อนหน้านี้ในโค้ดของเธรดเดียวกัน (รวมถึง operation ที่ไม่ใช่ atomic ด้วย!) ต้องเกิดขึ้นจริงและมองเห็น
  ได้แล้วก่อนที่ operation ที่ใช้ `Release` นี้จะเกิดขึ้น** — compiler/CPU ห้ามสลับให้ operation ที่มาก่อน
  `Release` ใน source code ไปเกิด**ทีหลัง** `Release` ได้เด็ดขาด
- **`Ordering::Acquire`** (ใช้กับ `.load()` หรือฝั่งที่ "อ่าน" ค่า) — รับประกันว่า **operation ทุกตัวที่เขียน
  ไว้หลังจากนี้ในโค้ดของเธรดเดียวกัน จะไม่ถูกสลับให้ไปเกิด**ก่อน**การอ่านค่าที่ใช้ `Acquire` นี้ได้** — และที่
  สำคัญที่สุด: ถ้า `Acquire` load นี้ **อ่านเห็นค่าที่มาจาก `Release` store ตัวใดตัวหนึ่ง** จะเกิดสิ่งที่เรียกว่า
  **happens-before relationship**: **ทุก operation ที่เกิดก่อน `Release` store (ในเธรดที่เขียน) จะถูก
  รับประกันว่า "มองเห็นได้แล้ว" กับทุก operation ที่เกิดหลัง `Acquire` load นี้ (ในเธรดที่อ่าน)**
- **`Ordering::AcqRel`** — ใช้กับ operation ที่ทั้ง**อ่านและเขียน**ในตัวเดียว (เช่น `fetch_add`,
  `compare_exchange` ที่สำเร็จ) รวมพฤติกรรมของทั้ง `Acquire` (ฝั่งอ่าน) และ `Release` (ฝั่งเขียน) เข้าด้วยกัน

พูดให้เป็นภาพเดียวชัด ๆ: `Release` คือการ "ปิดผนึกกล่อง" ที่บรรจุการเขียนทั้งหมดที่เกิดก่อนหน้าเข้าไปด้วย แล้ว
"ส่งกล่อง" นั้นผ่าน atomic store ตัวหนึ่งไปให้เธรดอื่น — `Acquire` คือการ "เปิดกล่อง" ที่รับมาจาก `Release`
เดียวกัน แล้วมองเห็นทุกอย่างที่ถูกปิดผนึกไว้ข้างในอย่างถูกต้องสมบูรณ์ ถ้าไม่มีการจับคู่ `Release`-`Acquire` กันจริง
(เช่นใช้ `Relaxed` ทั้งสองฝั่ง) ก็เหมือนไม่มีกล่องให้เปิดเลย — เธรดที่อ่านอาจเห็น "บางส่วน" ของสิ่งที่เธรดเขียน
เขียนไว้ก่อนหน้าเท่านั้น (หรือไม่เห็นเลย)

มาดูโค้ดที่ใช้ `Acquire`/`Release` ถูกต้องสำหรับสถานการณ์ producer/consumer ในหัวข้อ 51.4:

```rust
use std::sync::atomic::{AtomicBool, AtomicI32, Ordering};
use std::sync::Arc;
use std::thread;

struct SharedData {
    payload: AtomicI32,
    ready: AtomicBool,
}

fn main() {
    let shared = Arc::new(SharedData {
        payload: AtomicI32::new(0),
        ready: AtomicBool::new(false),
    });

    let producer_shared = Arc::clone(&shared);
    let producer = thread::spawn(move || {
        // เขียนข้อมูลจริงก่อน ด้วย Relaxed ก็พอ เพราะความถูกต้องไม่ได้มาจาก ordering ของ store นี้เอง
        producer_shared.payload.store(42, Ordering::Relaxed);
        // แล้ว "ประกาศ" ว่าพร้อมแล้ว ด้วย Release
        // Release ทำหน้าที่เป็น "รั้ว": operation ที่เขียนไว้ก่อนหน้านี้ในโค้ด (payload.store)
        // ต้องเกิดขึ้นจริงก่อน store(true, Release) นี้เสมอ ไม่ถูกสลับลำดับมาทีหลังได้
        producer_shared.ready.store(true, Ordering::Release);
    });

    let consumer_shared = Arc::clone(&shared);
    let consumer = thread::spawn(move || {
        // วนรออ่าน ready ด้วย Acquire จนกว่าจะเห็น true
        while !consumer_shared.ready.load(Ordering::Acquire) {
            thread::yield_now();
        }
        // เพราะ ready ถูกอ่านด้วย Acquire ที่จับคู่กับ Release ของฝั่งเขียน
        // เราจึงรับประกันได้ 100% ว่า payload ที่อ่านต่อไปนี้ต้องเห็นค่า 42 แล้วเสมอ ไม่ใช่ 0
        let value = consumer_shared.payload.load(Ordering::Relaxed);
        println!("consumer เห็น payload = {}", value);
        assert_eq!(value, 42);
    });

    producer.join().unwrap();
    consumer.join().unwrap();
    println!("Acquire/Release รับประกัน happens-before ได้ถูกต้อง");
}
```

ผลลัพธ์ (รันจริง — ตรวจซ้ำด้วยการรัน **30 ครั้ง** ทุกครั้งได้ผลเหมือนกันเป๊ะ ไม่มีข้อยกเว้นเลยแม้แต่ครั้งเดียว):

```
consumer เห็น payload = 42
Acquire/Release รับประกัน happens-before ได้ถูกต้อง
```

จุดที่ต้องสังเกตให้ดี: `payload.store()` ใน producer และ `payload.load()` ใน consumer ทั้งคู่ใช้ `Relaxed`
ธรรมดา (ไม่ใช่ `Acquire`/`Release`) — นี่ไม่ใช่ความผิดพลาด แต่เป็นการออกแบบที่ถูกต้อง: **ความถูกต้องของโปรแกรม
นี้ไม่ได้มาจาก ordering ของ `payload` เอง มาจาก ordering ของคู่ `ready` (`Release`/`Acquire`) ที่สร้าง
happens-before ครอบคลุมทุก operation ที่เกิดก่อน-หลังมันในแต่ละเธรด** — `payload.store` เกิดก่อน
`ready.store(..., Release)` ในเธรด producer และ `payload.load` เกิดหลัง `ready.load(..., Acquire)` ใน
เธรด consumer พอดี ทำให้ `payload.store` (แม้จะเป็น `Relaxed`) ก็ยังถูก "ครอบ" อยู่ในขอบเขตของ happens-before
ที่คู่ `ready` สร้างไว้อยู่ดี — นี่คือรูปแบบมาตรฐานที่แท้จริงของการ "publish" ข้อมูลข้ามเธรดด้วย atomic:
**ใช้ `Relaxed` กับข้อมูลจริง แล้วใช้ `Release`/`Acquire` กับ flag ตัวเดียวที่บอกว่า "ข้อมูลพร้อมแล้ว"**

#### กรณีศึกษา: `Arc<T>` เลือกใช้ Ordering แบบไหนจริง ๆ ภายในตัวมันเอง

ตอนนี้เรามีความรู้พอที่จะกลับไปปิดวงคำถามที่ Part 39/40 ทิ้งไว้แบบสมบูรณ์ที่สุด: **`Arc<T>` เลือกใช้ ordering
แบบไหนสำหรับ `strong_count` ของมัน?** (ตัวนับที่ Part 39 หัวข้อ 39.6 อธิบายไปแล้วว่าเป็น atomic แต่ไม่ได้ลงราย
ละเอียดเรื่อง ordering) คำตอบจาก source code จริงของ Rust standard library เป็นตัวอย่างที่สอนเรื่อง
`Relaxed`/`Release`/`Acquire` ได้ชัดเจนมาก เพราะมันใช้**ทั้งสามแบบ**ในจุดที่ต่างกันอย่างมีเหตุผลชัดเจน:

- **`Arc::clone()` (เพิ่มตัวนับ)**: ใช้ **`Ordering::Relaxed`** — เพราะการเพิ่มตัวนับไม่ต้องสร้าง
  happens-before กับข้อมูลตัวอื่นเลย มันแค่ต้องการความถูกต้องของตัวเลขเอง (atomicity) เท่านั้น ไม่มี "ข้อมูล
  อื่น" ที่ต้องพ่วงไปกับการ clone — ตรงกับเงื่อนไขในหัวข้อ 51.5 ที่ `Relaxed` เพียงพอ
- **`Drop` ของ `Arc<T>` (ลดตัวนับ)**: ใช้ **`Ordering::Release`** — เพราะการลดตัวนับ**ต้อง**รับประกันว่าทุก
  operation ที่เกิดขึ้นกับข้อมูลข้างใน (ผ่าน `&T` ที่ `Arc` ตัวนี้ถืออยู่) ก่อนหน้าการ drop นี้ ต้อง "มองเห็น
  แล้วเสร็จสมบูรณ์" ก่อนที่การลดตัวนับจะเกิดขึ้น — ถ้าตัวนับกลายเป็น 0 หลังจากนี้ (แปลว่าจะมีการทำลายข้อมูล
  จริง) ต้องมั่นใจว่าไม่มี thread ไหนยังทำงานกับข้อมูลนั้นค้างอยู่โดยที่ยังไม่เขียนเสร็จ
- **ก่อนทำลายข้อมูลจริง (ตอนตัวนับเหลือ 0)**: ใช้ **memory fence แบบ `Ordering::Acquire`** (เทคนิคเดียวกับ
  `fence()` ในหัวข้อ 51.13) — เพื่อรับประกันว่า thread ที่กำลังจะทำลายข้อมูล (เรียก `Drop` ของ `T` จริง) จะ
  มองเห็น**ทุกการเขียน**ที่ `Arc` ตัวอื่น ๆ (ที่เพิ่ง drop ไปก่อนหน้าด้วย `Release`) ทำไว้กับข้อมูลนั้นครบถ้วน
  ก่อนจะเริ่มทำลายมันจริง — ถ้าขาด fence ตัวนี้ไป มีความเป็นไปได้ในทางทฤษฎีที่ thread สุดท้ายที่ทำลายข้อมูลจะ
  "มองไม่เห็น" การเขียนบางส่วนที่ thread อื่นทำไว้ก่อนจะ drop ของตัวเอง ทั้งที่ตัวนับบอกว่าไม่มีใครใช้งานแล้ว

นี่คือเหตุผลที่แม่นยำที่สุดว่าทำไม `Arc<T>` ถึง**ไม่ได้ใช้ `SeqCst` ทุกจุด** ทั้งที่หัวข้อ 51.7 แนะนำให้เริ่ม
จาก `SeqCst` เป็นค่าเริ่มต้นเสมอ — คำตอบคือทีมพัฒนา standard library **ได้ทำการวิเคราะห์อย่างละเอียดมาแล้ว
ว่า `Relaxed`/`Release`/`Acquire` ผสมกันแบบนี้เพียงพอสำหรับความถูกต้อง 100%** (ผ่านการพิสูจน์เชิงทฤษฎีและการ
ทดสอบอย่างเข้มข้นที่ทีมงานเฉพาะทางทำไว้ให้) และ `Arc<T>` ถูกเรียกใช้บ่อยมากในโปรแกรม Rust ทุกตัว (ทุกครั้งที่
`.clone()`/drop) จนความต่างของประสิทธิภาพระหว่าง `Relaxed` กับ `SeqCst` มีผลสะสมที่วัดได้จริงในระดับ
ecosystem ทั้งหมด — นี่คือตัวอย่างที่ตรงกับคำแนะนำในหัวข้อ 51.7 เป๊ะ: **การใช้ ordering ที่อ่อนกว่า `SeqCst`
ควรเกิดขึ้นหลังจากมีการวิเคราะห์/พิสูจน์อย่างละเอียดแล้วเท่านั้น ไม่ใช่การเดา** — ทีม std ทำสิ่งนี้ได้เพราะ
`Arc<T>` เป็นโค้ดที่ถูกใช้งานมากที่สุดตัวหนึ่งในทั้ง ecosystem และคุ้มค่ากับการลงทุนวิเคราะห์ระดับนี้ ในขณะที่
โค้ด business logic ทั่วไปในโปรเจกต์ของคุณมักไม่คุ้มค่ากับการลงทุนระดับเดียวกัน (จนกว่า profiling จะชี้ชัดว่า
จำเป็นจริง ๆ)

### 51.7 `Ordering::SeqCst`: แน่นที่สุด เข้าใจง่ายที่สุด แพงที่สุด

`Ordering::SeqCst` ("Sequentially Consistent") คือระดับที่ **แน่นที่สุด** ในบรรดา 5 ระดับ — มันรับประกันทุก
อย่างที่ `Acquire`/`Release`/`AcqRel` รับประกัน **บวกกับ**สิ่งที่แข็งแกร่งกว่าอีกขั้น: **มี "ลำดับเดียว"
(single total order) ของ SeqCst operation ทั้งหมดในโปรแกรม ที่ทุกเธรดมองเห็นตรงกันหมด** ไม่ใช่แค่ระหว่างสอง
เธรดที่จับคู่กันแบบ `Acquire`/`Release`

พูดให้เข้าใจง่าย: ด้วย `Acquire`/`Release` ธรรมดา เป็นไปได้ในทางทฤษฎีที่เธรด C ซึ่งไม่เกี่ยวข้องกับคู่ A-B โดยตรง
จะ "มองเห็นลำดับของ operation ต่างจากที่เธรด A และ B มองเห็นกัน" ในบางสถานการณ์ที่ซับซ้อนมาก (เกี่ยวข้องกับ
มากกว่าสองเธรดที่ต่างคนต่างอ่าน-เขียนตัวแปรหลายตัวพร้อมกัน) — แต่ `SeqCst` ปิดช่องนี้สนิท: **ทุกเธรดในโปรแกรม
เห็นลำดับของทุก `SeqCst` operation ตรงกันเป๊ะเสมอ เหมือนกับว่าโปรแกรมทั้งหมดถูกรันแบบสลับกันไปมาทีละคำสั่งใน
ลำดับ global เดียว** (แม้ในความเป็นจริงจะรันพร้อมกันจริงบนหลาย core ก็ตาม) — นี่คือระดับที่ **ตรงกับสัญชาตญาณ
ของโปรแกรมเมอร์ทั่วไปมากที่สุด** เพราะมันคือสิ่งที่คนส่วนใหญ่ "คิดว่า" concurrency ควรทำงานแบบนั้นอยู่แล้วโดย
สัญชาตญาณ (ทุกคนเห็นลำดับเดียวกัน ไม่มีมุมมองที่ขัดแย้งกัน)

ต้นทุนของ `SeqCst` มาจากการที่ CPU ต้องเพิ่ม memory barrier ที่แน่นหนากว่า `Acquire`/`Release` ธรรมดา
(โดยเฉพาะบนสถาปัตยกรรมที่มี memory model ค่อนข้างอ่อนอย่าง ARM — บน x86-64 ซึ่งมี memory model ที่แข็งอยู่แล้ว
โดยธรรมชาติของฮาร์ดแวร์ ความต่างของต้นทุนระหว่าง `SeqCst` กับ `Acquire`/`Release` มักจะน้อยกว่าที่คิด แต่ก็ยังมี
อยู่จริงในหลายกรณี) — พูดง่าย ๆ คือ `SeqCst` ปลอดภัยที่สุดและคิดตามได้ง่ายที่สุด แต่ก็มีโอกาสเสียประสิทธิภาพไป
บ้างเมื่อเทียบกับการเลือก ordering ที่อ่อนกว่าอย่างระมัดระวัง

#### คำแนะนำเชิงปฏิบัติ: เริ่มจาก `SeqCst` เสมอ

นี่คือคำแนะนำที่สำคัญที่สุดของหัวข้อนี้ และควรยึดถือเป็นกฎเหล็กสำหรับโค้ด concurrency ส่วนใหญ่ที่คุณจะเขียน:

> **ใช้ `Ordering::SeqCst` เป็นค่าเริ่มต้นเสมอ จนกว่าคุณจะมีเหตุผลที่เข้าใจอย่างแท้จริงว่าทำไมต้องใช้ตัวที่อ่อน
> กว่า (เช่นหลังจาก profile แล้วพบว่า memory ordering เป็นคอขวดจริง ๆ ในเส้นทางที่ hot ที่สุดของโปรแกรม)**

เหตุผลที่คำแนะนำนี้สำคัญมาก: **memory ordering ที่ผิดไม่ทำให้ compiler ปฏิเสธ compile เลย** — ต่างจากทุก
ตัวอย่างใน Part 39/40 ที่เราเห็น compiler ปฏิเสธ `E0382`/`E0277` ตั้งแต่ compile time ทันทีที่เขียนโค้ด
ownership/Send/Sync ผิด บั๊กจาก memory ordering ผิดจะ**compile ผ่านได้ปกติเสมอ** (type ของ `Ordering` แค่เป็น
enum ธรรมดา ไม่มีการตรวจอะไรพิเศษ) และบ่อยครั้งจะ**รันผ่านได้ปกติด้วย** บนฮาร์ดแวร์ที่มี memory model แข็ง
(อย่าง x86-64) เพราะฮาร์ดแวร์เองก็ปกปิด race ที่ควรจะเกิดไว้ให้อยู่แล้วโดยไม่ได้ตั้งใจ — บั๊กแบบนี้จะโผล่มาแค่ใน
สถานการณ์ที่หายาก: สถาปัตยกรรมที่ memory model อ่อนกว่า (ARM, RISC-V), เมื่อ compiler optimize รุนแรงขึ้นในบาง
build configuration, หรือภาระงาน/timing ที่ต่างออกไปพอที่จะเปิดช่องให้ race แสดงตัว — พูดอีกแบบคือ **บั๊กแบบนี้
เป็น Heisenbug เต็มรูปแบบ** (แนวคิดที่ Part 40 หัวข้อ 40.1.1 เอ่ยถึงตอนเทียบกับ C++) ที่ตรวจจับได้ยากที่สุด
ประเภทหนึ่งในโปรแกรมมิ่งเลย ดังนั้น**ความปลอดภัยที่ได้จากการเลือก `SeqCst` เป็นค่าเริ่มต้นคุ้มค่ากับต้นทุน
ประสิทธิภาพที่เสียไปมาก** ในโค้ดส่วนใหญ่ที่ไม่ได้อยู่บน hot path จริง ๆ — การไปปรับ ordering ให้อ่อนลงเพื่อ
ประสิทธิภาพเป็นเรื่องที่ควรทำ**หลัง**การ profile (Part 54-55 ในอนาคต) พบว่ามันเป็นคอขวดจริงเท่านั้น ไม่ใช่การ
เดาล่วงหน้าโดยไม่มีข้อมูล

### 51.8 `compare_exchange`/`compare_exchange_weak`: หน่วยสร้างพื้นฐานของ Lock-free Algorithm

ตอนนี้เรามาถึงเครื่องมือที่ทรงพลังที่สุดของ atomic operation ทั้งหมด — **compare-and-swap (CAS)** ที่ Rust
ให้มาผ่าน `.compare_exchange()` และ `.compare_exchange_weak()` — นี่คือ building block ที่อัลกอริทึม
lock-free แทบทุกตัวในโลกถูกสร้างขึ้นมาจากมัน

แนวคิดของ CAS สรุปเป็นประโยคเดียวได้ว่า:

> **"ถ้าค่าปัจจุบันยังเป็นค่าที่ฉันคาดไว้ (expected) ให้เปลี่ยนเป็นค่าใหม่ (new) แบบ atomic; ถ้าไม่ใช่ ให้บอก
> ค่าจริงปัจจุบันกลับมาให้ฉันเลย"**

ลายเซ็นเต็มของ `compare_exchange` (ตัวอย่างสำหรับ `AtomicI64`):

```rust
// pub fn compare_exchange(
//     &self,
//     current: i64,       // ค่าที่คาดว่าน่าจะเป็นอยู่ตอนนี้
//     new: i64,            // ค่าใหม่ที่จะเปลี่ยนเป็น ถ้าค่าปัจจุบันตรงกับ current จริง
//     success: Ordering,   // ordering ที่ใช้ถ้าสำเร็จ (การเขียนเกิดขึ้นจริง)
//     failure: Ordering,   // ordering ที่ใช้ถ้าล้มเหลว (แค่การอ่าน ไม่มีการเขียน)
// ) -> Result<i64, i64>;   // Ok(ค่าเก่าก่อนเปลี่ยน) หรือ Err(ค่าจริงปัจจุบัน ไม่ตรงกับที่คาดไว้)
```

สังเกต return type `Result<i64, i64>` — **ทั้ง `Ok` และ `Err` เก็บค่าชนิดเดียวกัน** (`i64` ทั้งคู่) ต่างจาก
`Result<T, E>` ทั่วไปที่ Part 12 สอนไว้ที่มักมี `T` กับ `E` เป็นคนละ type กัน — ที่นี่ `Ok(v)` คือค่าเก่าก่อน
เปลี่ยน (ซึ่งก็คือ `current` ที่คุณส่งเข้าไปนั่นเอง ถ้าสำเร็จ) และ `Err(v)` คือ**ค่าจริงปัจจุบัน**ที่ทำให้
compare ไม่ตรง — นี่คือจุดสำคัญที่ทำให้ CAS ต่างจากการเขียน `.load()` แล้วเทียบเองแบบ manual: **ถ้าล้มเหลว มัน
บอกค่าจริงกลับมาให้ในคราวเดียวกัน โดยไม่มีช่องว่างของเวลาระหว่างการอ่านกับการเทียบเลย** (ถ้าแยก `.load()` กับ
การเทียบเองเป็นสองขั้นตอน จะมีช่องว่างที่ thread อื่นแทรกมาเปลี่ยนค่าได้ระหว่างสองขั้นตอนนั้น ทำให้ข้อมูลที่ใช้
เทียบล้าสมัยไปแล้วตั้งแต่ก่อนจะเทียบด้วยซ้ำ)

#### รูปแบบ CAS Retry Loop

เพราะ CAS อาจ "ล้มเหลว" ได้เสมอเมื่อมี thread อื่นมาแก้ไขค่าไปก่อน (ไม่ใช่ error ที่ต้อง panic แต่เป็นสัญญาณให้
"ลองใหม่") อัลกอริทึม lock-free แทบทุกตัวจึงใช้ pattern มาตรฐานที่เรียกว่า **CAS retry loop**:

```
loop {
    current = อ่านค่าปัจจุบัน
    new_value = คำนวณค่าใหม่จาก current
    ลอง compare_exchange(current, new_value)
    ถ้าสำเร็จ -> จบ ได้ผลลัพธ์แล้ว
    ถ้าล้มเหลว -> ได้ค่าจริงปัจจุบันกลับมา ใช้มันแทน current แล้ววนกลับไปคำนวณใหม่
}
```

มาดูตัวอย่างที่เป็นรูปธรรม: ฟังก์ชัน "อัปเดตค่า max ที่แบ่งกันใช้ข้ามหลาย thread" — เปลี่ยนค่าตัวแปรร่วมให้เป็น
ค่าที่มากขึ้นเท่านั้น ถ้าค่าที่ส่งมาน้อยกว่าหรือเท่ากับค่าปัจจุบันให้ไม่ทำอะไร (แนวคิดคล้ายการติดตามคะแนนสูงสุด
ของเกม, ค่า latency สูงสุดที่เคยพบของระบบ ฯลฯ ข้ามหลาย thread พร้อมกัน โดยไม่ต้องใช้ `Mutex` เลย):

```rust
use std::sync::atomic::{AtomicI64, Ordering};
use std::sync::Arc;
use std::thread;

/// อัปเดตค่า max แบบ atomic: เปลี่ยน shared_max เป็น candidate เฉพาะเมื่อ candidate มากกว่าค่าปัจจุบันจริง
/// คืนค่า max ล่าสุดหลังจากอัปเดต (อาจไม่ใช่ candidate เองก็ได้ ถ้ามี thread อื่นตั้งค่าที่มากกว่าไปก่อนแล้ว)
fn update_max(shared_max: &AtomicI64, candidate: i64) -> i64 {
    let mut current = shared_max.load(Ordering::Relaxed);
    loop {
        if candidate <= current {
            // ค่าปัจจุบันมากกว่าหรือเท่ากับ candidate อยู่แล้ว ไม่ต้องทำอะไรต่อ
            return current;
        }
        // "ถ้า shared_max ยังเป็น current เหมือนที่อ่านล่าสุด ให้เปลี่ยนเป็น candidate"
        // ถ้ามี thread อื่นมาแก้ไขค่าไปแล้วระหว่างนี้ compare_exchange จะคืนค่าจริงปัจจุบันกลับมาใน Err
        match shared_max.compare_exchange(current, candidate, Ordering::SeqCst, Ordering::SeqCst) {
            Ok(_) => return candidate, // สำเร็จ: เปลี่ยนค่าได้จริงโดยไม่มีใครแทรกกลางทาง
            Err(actual) => {
                // มีคนอื่นเปลี่ยนค่าไปแล้ว -> อ่านค่าจริงปัจจุบันมาลองใหม่ (นี่คือหัวใจของ CAS retry loop)
                current = actual;
            }
        }
    }
}

fn main() {
    let shared_max = Arc::new(AtomicI64::new(i64::MIN));
    let mut handles = vec![];

    let candidates = [42, 17, 999, 3, 12345, 7, 500, 12345, 1, 999_999, -50, 888_888];

    for &value in candidates.iter() {
        let shared_max = Arc::clone(&shared_max);
        handles.push(thread::spawn(move || {
            update_max(&shared_max, value);
        }));
    }

    for h in handles {
        h.join().unwrap();
    }

    let result = shared_max.load(Ordering::SeqCst);
    println!("ค่า max สุดท้าย: {}", result);
    assert_eq!(result, 999_999);
    println!("assert_eq! ผ่าน: max ถูกต้อง 100% ไม่ว่า thread จะ schedule มาลำดับไหน");
}
```

ผลลัพธ์ (รันจริง — ตรวจซ้ำด้วยการรัน **30 ครั้ง** ได้ค่า `999999` ถูกต้องทุกครั้งไม่มีข้อยกเว้น แม้ 12 thread
จะแข่งกันเรียก `update_max` พร้อมกันแบบสุ่มลำดับไม่ซ้ำกันเลยในแต่ละรอบ):

```
ค่า max สุดท้าย: 999999
assert_eq! ผ่าน: max ถูกต้อง 100% ไม่ว่า thread จะ schedule มาลำดับไหน
```

สังเกตว่าโค้ดนี้ **ไม่มี `Mutex` แม้แต่ตัวเดียว** แต่ก็ยังถูกต้อง 100% ภายใต้การแข่งขันจริงจากหลาย thread —
เหตุผลคือ retry loop รับประกันว่า **การเขียนที่สำเร็จจริง ๆ จะเกิดขึ้นแค่ในตอนที่ compare_exchange ยืนยันแล้ว
ว่าไม่มีใครแทรกกลางทาง** — ถ้ามีใครแทรก ก็แค่วนกลับไปคำนวณใหม่จากค่าล่าสุด ไม่มีทางเขียนค่าที่ "ผิดพลาดจาก
ข้อมูลเก่า" ลงไปได้เลย นี่คือสิ่งที่ทำให้ CAS retry loop เป็นรูปแบบพื้นฐานที่สุดของโปรแกรมมิ่งแบบ lock-free

#### `compare_exchange` vs `compare_exchange_weak`

Rust ให้ทั้งสองตัวเพราะ ARM และสถาปัตยกรรมบางแบบ implement CAS ด้วยคำสั่งคู่ **LL/SC (load-linked /
store-conditional)** ซึ่งมีธรรมชาติที่ต่างจาก x86 (ที่มีคำสั่ง CAS ตัวเดียวจบ): LL/SC มีโอกาส "ล้มเหลวปลอม"
(spurious failure) ได้แม้ค่าที่เทียบจะตรงกันจริง ๆ ก็ตาม (เช่นเพราะมี interrupt เข้ามาคั่นระหว่างสองคำสั่งย่อย)
— `compare_exchange` (ตัวธรรมดา) **รับประกันว่าจะไม่ล้มเหลวปลอม** โดยที่ compiler จะแปลงเป็น loop ภายในให้เอง
บนสถาปัตยกรรมที่จำเป็น (เสียประสิทธิภาพเล็กน้อยจาก loop ที่แอบซ่อนอยู่) ส่วน `compare_exchange_weak`
**อนุญาตให้ล้มเหลวปลอมได้** (คืน `Err` ทั้งที่ค่าจริงตรงกับที่คาดไว้พอดี) แลกกับการไม่ต้องมี loop แอบซ่อนอยู่
ภายใน ทำให้เร็วกว่าเล็กน้อยบนสถาปัตยกรรมแบบ LL/SC

ข้อแนะนำเชิงปฏิบัติ: **ถ้าคุณเขียน CAS อยู่ใน retry loop อยู่แล้ว (แบบตัวอย่าง `update_max` ข้างบน) ให้ใช้
`compare_exchange_weak` แทน `compare_exchange` ธรรมดาได้เลย** เพราะ loop ของคุณเองจะจัดการกับความล้มเหลว
(ไม่ว่าจะเป็นความล้มเหลวจริงจาก thread อื่น หรือความล้มเหลวปลอมจาก LL/SC) ด้วยการวนลองใหม่อยู่แล้วเหมือนกัน —
ผลคือได้ประสิทธิภาพที่ดีกว่าเล็กน้อยบนสถาปัตยกรรมที่เกี่ยวข้อง โดยไม่เสียความถูกต้องอะไรเลย แต่ถ้าคุณเรียก
`compare_exchange` แค่**ครั้งเดียว**โดยไม่มี loop ครอบ (เช่นเช็คครั้งเดียวแล้วไปทำ error path ถ้าไม่ตรง) ให้ใช้
`compare_exchange` ตัวธรรมดาเสมอ เพราะคุณไม่มี loop ที่จะไปจัดการกับความล้มเหลวปลอมให้

### 51.9 "Lock-free" คืออะไรจริง ๆ: นิยามที่ถูกเข้าใจผิดบ่อยที่สุด

คำว่า "lock-free" ถูกใช้ผิดความหมายในบทสนทนาทั่วไปบ่อยมาก หลายคนใช้มันแทนคำว่า "เร็ว" หรือ "ไม่มี `Mutex`" —
แต่นิยามที่ถูกต้องตามศัพท์วิชาการของ concurrent programming นั้นเจาะจงกว่านั้นมาก และสำคัญมากที่ต้องเข้าใจให้
ถูกต้อง เพราะมันคือคุณสมบัติเชิง**การันตี** ไม่ใช่คุณสมบัติเชิง**ความเร็ว**

> **นิยามที่ถูกต้อง**: อัลกอริทึมหนึ่งเป็น **lock-free** ก็ต่อเมื่อมันรับประกันว่า **ระบบโดยรวมจะมีความคืบหน้า
> เสมอ** (system-wide progress) — พูดให้ชัด: **ไม่ว่า thread ใด thread หนึ่งจะถูกหยุด (suspend), ทำงานช้า
> ผิดปกติ, หรือถูก scheduler ไม่เลือกให้ทำงานเลยเป็นเวลานานเพียงใดก็ตาม (แม้กระทั่งถูก kill ไปเลย) ก็ยังมี
> อย่างน้อยหนึ่ง thread ในระบบที่สามารถทำงานสำเร็จต่อไปได้เสมอ** ไม่มีสถานการณ์ที่ระบบทั้งหมด "ค้าง" รอ
> thread ตัวใดตัวหนึ่งที่มีปัญหา

จุดที่ต้องเน้นเป็นพิเศษ: **นิยามนี้ไม่ได้พูดถึง thread แต่ละตัวเป็นการส่วนตัวเลย** มันพูดถึง**ระบบโดยรวม**
เท่านั้น — เป็นไปได้อย่างสมบูรณ์ที่ thread หนึ่งใน CAS retry loop จะ "โดนแทง" (ถูกแทรกจาก thread อื่นซ้ำแล้ว
ซ้ำอีก ทำให้ compare_exchange ล้มเหลวไปเรื่อย ๆ) ไปนานมากในทางทฤษฎี — ตราบใดที่ **การที่มันล้มเหลวนั้นเป็นเพราะ
thread อื่นสำเร็จไปแทน** (ไม่มีทางที่ CAS จะล้มเหลวได้โดยไม่มีใครสำเร็จเลย เพราะ CAS ล้มเหลวก็ต่อเมื่อค่าเปลี่ยน
ไปจริง ๆ จากการที่อีก thread เขียนสำเร็จ) ระบบโดยรวมก็ยังถือว่า "มีความคืบหน้าเสมอ" อยู่ดี — thread ที่โดนแทง
ซ้ำ ๆ อาจรู้สึกว่า "ไม่คืบหน้า" จากมุมมองของมันเอง แต่ระบบทั้งระบบยังคืบหน้าไปเรื่อย ๆ (มีงานสำเร็จเพิ่มขึ้นตลอด
เวลา แค่ไม่ใช่งานของ thread ตัวนั้นตัวเดียว)

#### เปรียบเทียบกับ Blocking (`Mutex`) — เชื่อมกลับไปที่ Deadlock ของ Part 39

นี่คือจุดที่ต่างจาก `Mutex` อย่างสิ้นเชิง — ย้อนกลับไป Part 39 หัวข้อ 39.9 ที่อธิบาย **deadlock**: ถ้า thread
หนึ่งถือ `MutexGuard<T>` อยู่แล้วถูก**หยุดกลางทาง** (เช่น panic แล้ว mutex ถูก poison ตามหัวข้อ 39.3, หรือใน
สถานการณ์ที่ร้ายแรงกว่านั้นคือถูก suspend/kill โดย OS ในระบบปฏิบัติการบางแบบ) **thread อื่นทุกตัวที่กำลังรอ
`.lock()` ตัวเดียวกันจะติดค้างตลอดไปด้วย** — ระบบทั้งระบบหยุดชะงักเพราะ thread เดียวมีปัญหา นี่คือสิ่งที่คำว่า
"blocking" หมายถึงตรง ๆ: **การรับประกันความคืบหน้าของทั้งระบบขึ้นอยู่กับความคืบหน้าของ thread ที่ถือ lock**
ถ้า thread นั้นมีปัญหา ระบบทั้งระบบก็มีปัญหาตามไปด้วย

ปัญหาแบบเดียวกันนี้มีชื่อเรียกในวงการ operating system ว่า **priority inversion** — สถานการณ์ที่ thread
priority ต่ำถือ lock ที่ thread priority สูงต้องการอยู่ ทำให้ thread priority สูง (ที่ควรจะได้ทำงานก่อนเสมอ
ตามหลักการของ scheduler) ต้องมารอ thread priority ต่ำอย่างขัดกับเจตนาของระบบ priority ทั้งหมด (เคสที่โด่งดัง
ที่สุดในโลกจริงคือปัญหาของยานสำรวจดาวอังคาร Mars Pathfinder ปี 1997 ที่ระบบต้อง reset ตัวเองซ้ำ ๆ จาก
priority inversion บน RTOS ที่ใช้ mutex เชื่อมกับ watchdog) — lock-free algorithm ไม่มีปัญหาแบบนี้เลยโดย
ธรรมชาติ เพราะไม่มี "การถือ lock" ให้ thread priority ต่ำไปกันไม่ให้ thread อื่นทำงานได้เลยแม้แต่ช่วงเวลาสั้น ๆ

#### Lock-free ไม่ใช่ "เร็ว" และไม่ใช่ "Wait-free" — มีระดับการันตีที่แข็งแรงกว่าอีกขั้น

ต้องแยกสามคำนี้ให้ชัดเจน เพราะมักถูกใช้ปนกันผิด ๆ:

- **Blocking (เช่น `Mutex`)** — thread ที่ไม่ได้ lock ต้อง**หยุดรอ**จนกว่า thread ที่ถือ lock จะปลดล็อก — ไม่
  มีการรับประกันความคืบหน้าของระบบถ้า thread ที่ถือ lock มีปัญหา (ตามที่อธิบายข้างบน)
- **Lock-free (เช่น CAS retry loop)** — ไม่มี thread ไหน "หยุดรอ" ใครแบบ blocking แต่**อาจต้องวนลองใหม่ไป
  เรื่อย ๆ** ถ้าโดนแทงซ้ำ ๆ — ระบบโดยรวมรับประกันว่ามีความคืบหน้าเสมอ แต่**ไม่รับประกันว่า thread ตัวใดตัวหนึ่ง
  โดยเฉพาะจะได้ทำงานสำเร็จภายในเวลาที่จำกัด** (ในทางทฤษฎี thread หนึ่งอาจโดนแทงซ้ำไม่จำกัดจำนวนครั้งถ้าโชค
  ร้ายพอ แม้ในทางปฏิบัติจริงโอกาสแบบนี้จะต่ำมากกับ workload ทั่วไป)
- **Wait-free** — การรับประกันที่**แข็งแรงกว่า lock-free อีกขั้น**: **ทุก thread** (ไม่ใช่แค่ "อย่างน้อยหนึ่ง
  thread" แบบ lock-free) รับประกันว่าจะทำงานสำเร็จได้ภายใน**จำนวนขั้นตอนที่จำกัด** (bounded number of steps)
  ไม่ว่า thread อื่นจะทำอะไรอยู่ก็ตาม — พูดง่าย ๆ คือไม่มี thread ไหนถูก "แทงซ้ำไม่จำกัด" ได้เลย ทุก thread
  การันตีว่าจะเสร็จงานแน่ ๆ ภายในเวลาที่คำนวณล่วงหน้าได้ — **wait-free เป็นคุณสมบัติที่หายากและยากที่จะออกแบบ
  มากกว่า lock-free มาก** อัลกอริทึม wait-free ในทางปฏิบัติมีน้อยกว่า lock-free มาก และมักมีความซับซ้อนสูงกว่า
  มาก (บางครั้งต้องแลกกับการใช้ memory มากขึ้นเพื่อให้แต่ละ thread มี "พื้นที่ทำงานส่วนตัว" ที่ไม่ต้องแข่งกับ
  ใคร)

| คุณสมบัติ | Blocking (`Mutex`) | Lock-free (CAS loop) | Wait-free |
|---|---|---|---|
| การันตีความคืบหน้าของระบบ | ไม่มี ถ้า thread ที่ถือ lock มีปัญหา | มีเสมอ (อย่างน้อย 1 thread คืบหน้า) | มีเสมอ (**ทุก** thread คืบหน้า) |
| การันตีต่อ thread แต่ละตัว | ได้ทำงานสำเร็จเมื่อได้ lock (แต่เวลารอไม่จำกัด) | อาจถูกแทงซ้ำได้ไม่จำกัดในทางทฤษฎี | สำเร็จภายในจำนวนขั้นตอนที่จำกัดเสมอ |
| เสี่ยง priority inversion | มี | ไม่มี | ไม่มี |
| เสี่ยง deadlock | มี (Part 39 หัวข้อ 39.9) | ไม่มี (ไม่มี lock ให้ deadlock) | ไม่มี |
| ความซับซ้อนในการเขียน/พิสูจน์ถูก | ต่ำ-กลาง (คิดเรื่อง lock ordering) | สูงมาก (ต้องคิดเรื่อง memory ordering, ABA) | สูงที่สุด |
| ความเร็วในทางปฏิบัติ | ดีพอสำหรับงานส่วนใหญ่ | มักเร็วกว่าสำหรับ operation ง่าย ๆ ที่แข่งขันสูง | ไม่แน่นอน (บางครั้งช้ากว่า lock-free เพราะ overhead ของการรับประกันที่แข็งแรงกว่า) |

ข้อคิดสำคัญจากตารางนี้: **"lock-free" ไม่ได้แปลว่า "เร็วกว่าเสมอ" และไม่ได้แปลว่า "ทุก thread ได้ผลลัพธ์เร็ว
เท่ากันเสมอ"** — มันเป็นแค่การรับประกันที่**ต่างชนิด**จาก `Mutex` (การันตีว่าระบบไม่ค้างสนิท แทนที่จะการันตีว่า
ทุกคนได้ทำงานอย่างเป็นธรรม) การเลือกระหว่าง blocking กับ lock-free ควรขึ้นอยู่กับว่า**สถานการณ์ของคุณกลัวอะไร
มากกว่า**: กลัว thread หลักค้างเพราะ lock (เลือก lock-free) หรือยอมรับความเสี่ยงนั้นได้และต้องการความง่ายใน
การเขียน/debug มากกว่า (เลือก `Mutex`)

น่าสังเกตว่า Rust standard library เอง**ไม่ได้ให้ lock-free data structure ระดับสูงมาให้ใช้ตรง ๆ เลย** (ไม่มี
`std::collections::LockFreeQueue` หรืออะไรทำนองนี้) — สิ่งที่ std ให้มาคือแค่ atomic type ระดับพื้นฐาน
(หัวข้อ 51.2) ที่เป็น**หน่วยสร้าง**เท่านั้น ส่วนโครงสร้างข้อมูลระดับสูงที่ประกอบขึ้นจากหน่วยสร้างเหล่านี้ (queue,
stack, hash map แบบ lock-free) ถูกทิ้งให้เป็นหน้าที่ของ crate ในระบบนิเวศ (เช่น `crossbeam` ที่จะพูดถึงในหัวข้อ
51.11) — นี่ไม่ใช่ความบกพร่องของภาษา แต่เป็นการตัดสินใจเชิงออกแบบที่ตรงกับปรัชญาของ Rust standard library
โดยรวม: เก็บ std ให้เล็กและมั่นคง (stable) ที่สุด แล้วปล่อยให้ crate เฉพาะทางที่อัปเดตได้บ่อยกว่าและแข่งขันกัน
พัฒนาต่อยอด เป็นผู้รับผิดชอบ data structure ที่ซับซ้อนและมีพื้นที่ให้ปรับปรุง trade-off ได้หลากหลายแบบ

### 51.10 ABA Problem: กับดักคลาสสิกที่สุดของ CAS-based Algorithm

ตอนนี้มาถึงปัญหาที่ทำให้ lock-free programming ยากกว่าที่มันดูในตอนแรกมาก — **ABA problem** ชื่อของมันมาจาก
สถานการณ์ที่ค่าของตัวแปรเปลี่ยนจาก **A → B → A** และ CAS ที่เทียบแค่ "bit pattern" ของค่าตรงกันหรือไม่ จะ
**เข้าใจผิดว่าไม่มีอะไรเปลี่ยนแปลงเลย** ทั้งที่จริง ๆ มีการเปลี่ยนแปลงเกิดขึ้นถึงสองครั้งระหว่างนั้น

#### สถานการณ์ปัญหา

ลองนึกภาพ lock-free stack แบบง่าย ๆ ที่เก็บ "top" เป็น pointer/address ไปยัง node บนสุด การ pop จะทำ CAS
เปลี่ยน top จาก node ปัจจุบันไปเป็น `node.next` — ลำดับเวลาที่ทำให้เกิดปัญหา:

1. **Thread R (reader)** อ่านค่า `top` เห็นว่าชี้ไปที่ node **A** (จะใช้ค่านี้ทำ CAS ในอีกไม่นาน)
2. Thread R **ถูก preempt** (ระบบสลับให้ thread อื่นทำงานก่อน — เกิดขึ้นได้ปกติในระบบ multi-threading จริง)
3. **Thread I (interferer)** เข้ามาทำงาน: pop node A ออกจริง (`top` เปลี่ยนจาก A ไปเป็น B)
4. Thread I ทำงานต่อ: push node ใหม่ที่ดันมี**ตำแหน่งความจำเดียวกันกับที่ node A เคยอยู่**เข้าไป (เกิดได้จริง
   ในระบบที่ใช้ memory allocator แบบ reuse — พอ node A ถูกคืนความจำ allocator ตัวถัดไปที่ขอความจำอาจได้
   ตำแหน่งเดิมกลับมาใช้ซ้ำพอดี) — `top` ตอนนี้ชี้ไปที่ตำแหน่งเดิมของ A อีกครั้ง แต่**เป็น node คนละตัวกับ A
   เดิมโดยสิ้นเชิง** (แค่บังเอิญได้ address ซ้ำกัน)
5. **Thread R กลับมาทำงานต่อ** และทำ `compare_exchange(expected = A_address, new = A.next_ที่เคยอ่านไว้)`
   — เพราะ `top` ตอนนี้มีค่า**ตรงกับ A_address เป๊ะ** (bit pattern เหมือนกัน) **compare_exchange จะสำเร็จ!**
   ทั้งที่ node ที่อยู่ ณ ตำแหน่งนั้นไม่ใช่ node A เดิมอีกแล้ว

ผลคือ Thread R เขียนค่าที่**ผิดพลาดโดยสิ้นเชิง** (ค่า `next` ของ node A เดิมที่ถูกทำลายไปแล้ว) ลงไปเป็น `top`
ใหม่ ทำให้โครงสร้างข้อมูลพังทันที (stack อาจสูญเสีย node ที่ยังใช้งานอยู่จริง หรือแม้แต่เกิด use-after-free)

มาดูตัวอย่างที่จำลองสถานการณ์นี้ให้เห็นจริง — ใช้ `AtomicUsize` แทนที่อยู่ (address) แบบตัวเลขตรง ๆ เพื่อไม่ต้อง
ยุ่งกับ unsafe pointer dereference จริง และใช้ `Barrier` (จาก `std::sync`) ร่วมกับ `thread::sleep` เพื่อบังคับ
ลำดับการสลับ thread ให้ตรงกับสถานการณ์ข้างบนแบบเป๊ะ ๆ ซ้ำได้ทุกครั้ง:

```rust
use std::sync::atomic::{AtomicUsize, Ordering};
use std::sync::{Arc, Barrier};
use std::thread;
use std::time::Duration;

fn main() {
    // จำลอง "top" ของ lock-free stack แบบง่าย ๆ ด้วยตัวเลขแทน address ของ node
    // (lock-free stack จริงใช้ AtomicPtr<Node<T>> แต่ที่นี่ใช้ AtomicUsize แทนที่อยู่ เพื่อไม่ต้องยุ่งกับ
    // unsafe pointer dereference จริง และเห็นตัวเลขตรง ๆ ชัดเจน)
    let top = Arc::new(AtomicUsize::new(100)); // top ชี้ไปที่ node "A" ซึ่งอยู่ที่ address 100
    let barrier = Arc::new(Barrier::new(2));

    let top_reader = Arc::clone(&top);
    let barrier_reader = Arc::clone(&barrier);
    let reader = thread::spawn(move || {
        // ขั้นตอนที่ 1: thread นี้อ่านค่า top ปัจจุบัน (เห็น node A ที่ address 100)
        let observed = top_reader.load(Ordering::SeqCst);
        println!("[reader] อ่านค่า top เห็น address {} (node A)", observed);

        barrier_reader.wait(); // ให้ thread แทรก (interferer) เริ่มทำงานพร้อมกันหลังจุดนี้

        // จำลองว่า thread นี้ "ถูก preempt" (ระบบสลับให้ thread อื่นทำงานก่อน) ไปพักหนึ่ง
        // ก่อนจะกลับมาทำ compare_exchange จริง -- ช่วงเวลานี้คือช่องโหว่ที่ ABA problem อาศัยอยู่
        thread::sleep(Duration::from_millis(200));

        // ขั้นตอนที่ 3: พยายาม pop node A ออก โดยตั้งค่า top ใหม่เป็น "node A.next" (จำลองเป็น address 999)
        // reader คิดว่า "ถ้า top ยังเป็น 100 (node A) เหมือนตอนที่อ่านไปครั้งแรก แปลว่าไม่มีใครแก้ไขระหว่างนี้เลย"
        match top_reader.compare_exchange(observed, 999, Ordering::SeqCst, Ordering::SeqCst) {
            Ok(_) => println!(
                "[reader] compare_exchange สำเร็จ! -- reader เข้าใจผิดว่า pop node A ได้อย่างปลอดภัย \
                 (นี่คือจุดที่ ABA problem หลอกโปรแกรม!)"
            ),
            Err(actual) => println!("[reader] compare_exchange ล้มเหลว, top จริงตอนนี้คือ {}", actual),
        }
    });

    let top_interferer = Arc::clone(&top);
    let barrier_interferer = Arc::clone(&barrier);
    let interferer = thread::spawn(move || {
        barrier_interferer.wait(); // รอให้ reader อ่านค่า top (=A) เสร็จก่อนแน่ ๆ

        // ขั้นตอนที่ 2a: thread นี้ pop node A ออกจริง (top: 100 -> 200, สมมติ node B อยู่ที่ address 200)
        top_interferer.store(200, Ordering::SeqCst);
        println!("[interferer] pop node A ออกจริง, top เปลี่ยนเป็น address 200 (node B)");
        thread::sleep(Duration::from_millis(50));

        // ขั้นตอนที่ 2b: จากนั้น allocator คืน memory ของ node A (address 100) มาใช้ซ้ำสำหรับ node ใหม่
        // (เกิดได้จริงกับ memory pool/allocator แบบ reuse address) แล้ว push node ใหม่นี้กลับเข้า stack
        // -- โน้ตว่านี่คือ node คนละตัวกับ node A เดิมเป๊ะ แค่ "บังเอิญ" ได้ address เดียวกันมาใช้ซ้ำ
        top_interferer.store(100, Ordering::SeqCst);
        println!(
            "[interferer] push node ใหม่ (คนละ node กับ A เดิม แต่ allocator คืน address 100 ซ้ำ) \
             -> top กลับมาเป็น 100"
        );
    });

    reader.join().unwrap();
    interferer.join().unwrap();

    let final_top = top.load(Ordering::SeqCst);
    println!("ค่า top สุดท้าย: {} (ควรเป็น 200 ถ้าไม่มี ABA problem แทรก แต่กลับกลายเป็น 999!)", final_top);
    // ค่าที่ถูกต้องควรเป็น 200 (node B ที่ interferer pop มาเจอ) แต่ ABA ทำให้ reader เขียนทับด้วย 999
    // ซึ่งเป็นค่า "next" ของ node A เดิม (ที่ถูกทำลายไปแล้ว!) -- นี่คือ stack ที่พังจากการเชื่อ CAS ผิด ๆ
    assert_eq!(final_top, 999, "แสดงให้เห็นว่า ABA problem ทำให้ CAS สำเร็จอย่างผิดพลาดจริง");
}
```

ผลลัพธ์ (รันจริง — ตรวจซ้ำด้วยการรัน **15 ครั้ง** ได้ลำดับเหตุการณ์และผลลัพธ์เหมือนกันเป๊ะทุกครั้ง เพราะ
`Barrier` บังคับให้ทั้งสอง thread ซิงค์จุดเริ่มต้นตรงกันเสมอ และ `sleep(200ms)` นานพอที่ interferer จะทำงาน
ทั้งสองขั้นตอนเสร็จก่อน reader จะตื่นมาทำ `compare_exchange` แน่นอน):

```
[reader] อ่านค่า top เห็น address 100 (node A)
[interferer] pop node A ออกจริง, top เปลี่ยนเป็น address 200 (node B)
[interferer] push node ใหม่ (คนละ node กับ A เดิม แต่ allocator คืน address 100 ซ้ำ) -> top กลับมาเป็น 100
[reader] compare_exchange สำเร็จ! -- reader เข้าใจผิดว่า pop node A ได้อย่างปลอดภัย (นี่คือจุดที่ ABA problem หลอกโปรแกรม!)
ค่า top สุดท้าย: 999 (ควรเป็น 200 ถ้าไม่มี ABA problem แทรก แต่กลับกลายเป็น 999!)
```

เห็นได้ชัดจากผลลัพธ์: `top` สุดท้ายกลายเป็น `999` (ค่าที่ reader คิดว่าเป็น "next" ของ node A เดิม) ทั้งที่ค่าที่
**ถูกต้อง**ควรเป็น `200` (node B ที่ interferer เจอจริง ๆ ตอน pop) — node B และทุก node ที่อาจเชื่อมต่อถัดจากมัน
**หายไปจากระบบเลย** โดยไม่มีสัญญาณเตือนใด ๆ ทั้งสิ้น (`compare_exchange` รายงานว่า "สำเร็จ" อย่างมั่นใจ!) นี่คือ
ความน่ากลัวของ ABA problem: มันไม่ทำให้โปรแกรม panic หรือ crash แต่ทำให้**ข้อมูลเสียหายอย่างเงียบ ๆ**

#### ทำไม ABA Problem ถึงสำคัญเฉพาะกับ CAS-based Algorithm

สังเกตว่าปัญหานี้เกิดขึ้นเพราะ `compare_exchange` เทียบแค่ **"ค่าตอนนี้ตรงกับค่าที่คาดไว้หรือไม่"** โดยไม่มีทาง
รู้เลยว่า**ระหว่างช่วงเวลาที่อ่านค่าไปจนถึงตอนที่ทำ compare_exchange มีการเปลี่ยนแปลงเกิดขึ้นไปแล้วกี่ครั้ง** —
ถ้าค่าสุดท้ายที่เห็นตรงกับค่าเริ่มต้นเป๊ะ (ไม่ว่าจะผ่านไปกี่รอบของการเปลี่ยนแปลงระหว่างนั้น) CAS จะมองว่า "ไม่มี
อะไรเปลี่ยน" เสมอ — นี่คือข้อจำกัดโดยธรรมชาติของการเทียบแค่ "ค่าปัจจุบัน" โดยไม่มี "ประวัติ" ประกอบ

#### แนวทางบรรเทาปัญหาในโลกจริง (ระดับ Awareness)

lock-free data structure ที่ผ่านการทดสอบมาอย่างหนักในโลกจริง (เช่นใน crate `crossbeam` ที่จะพูดถึงในหัวข้อ
51.11) มักแก้ปัญหานี้ด้วยเทคนิคสองแนวทางหลัก (รู้จักไว้ในระดับแนวคิด ไม่ต้อง implement เต็มรูปแบบเอง):

1. **Generation counter / tagged value** — แทนที่จะเก็บแค่ "ค่า" เดี่ยว ๆ ให้เก็บคู่ (ค่า, เลขรุ่น) แล้วเพิ่ม
   เลขรุ่นทุกครั้งที่มีการเปลี่ยนแปลงเกิดขึ้น (ไม่ว่าค่าจะเปลี่ยนไปเป็นอะไรก็ตาม) — การทำ CAS จะเทียบทั้งคู่
   (ค่า, เลขรุ่น) พร้อมกัน แม้ค่าจะกลับมาเป็น A เดิม แต่เลขรุ่นจะไม่เท่ากับตอนที่อ่านครั้งแรกแล้วแน่นอน (เพราะ
   ผ่านการเปลี่ยนแปลงมาแล้วอย่างน้อยสองครั้ง) ทำให้ CAS ล้มเหลวอย่างถูกต้องแทนที่จะสำเร็จอย่างผิดพลาด — เทคนิค
   นี้มักถูกเรียกว่า **tagged pointer** เมื่อนำเลขรุ่นไปฝังไว้ในบิตที่ไม่ได้ใช้ของ pointer จริง (บน CPU
   สถาปัตยกรรม 64-bit จำนวนมาก pointer จริงมักใช้ address space ไม่ครบ 64 บิต เหลือบิตบนสุดว่างให้ใช้เก็บ
   ข้อมูลเสริมแบบนี้ได้)
2. **Hazard pointer / epoch-based reclamation** — แนวทางที่ซับซ้อนกว่า: ไม่คืน memory ของ node ที่ถูก pop
   ออกไปทันที แต่รอจนกว่าจะแน่ใจว่า**ไม่มี thread ไหนกำลังถือ reference ไปยัง node นั้นอยู่แล้วจริง ๆ**
   (ผ่านการติดตาม "epoch" หรือ "hazard pointer" ของแต่ละ thread) — วิธีนี้ป้องกัน ABA problem ได้ที่ต้นเหตุ
   เพราะ memory ของ node A จะไม่ถูกนำไปใช้ซ้ำเลยจนกว่าจะปลอดภัย 100% ป้องกันไม่ให้เกิดสถานการณ์ "address เดิม
   ถูกใช้ซ้ำ" ได้ตั้งแต่ต้น — crate `crossbeam-epoch` (ส่วนหนึ่งของ ecosystem `crossbeam`) implement เทคนิคนี้
   ไว้ให้ใช้งานจริงแล้ว

ทั้งสองเทคนิคนี้มีรายละเอียดการ implement ที่ซับซ้อนมาก (เหตุผลหนึ่งที่ทำให้หัวข้อ 51.11 แนะนำให้พึ่งพา crate
ที่ทดสอบมาแล้วแทนการเขียนเอง) — สิ่งที่ควรจำจากหัวข้อนี้คือ **ABA problem มีอยู่จริง เป็นเรื่องที่ subtle มาก
และมีวิธีแก้ไขที่เป็นที่ยอมรับในวงการ ไม่ใช่ปัญหาที่ไม่มีทางออก** แต่การ implement ทางแก้เหล่านี้เองถูกต้อง
100% เป็นงานที่ยากกว่าที่คิดมาก

### 51.11 คำแนะนำเชิงวิศวกรรมที่ซื่อสัตย์: Mutex ก่อน, Profile แล้วค่อยคิดเรื่อง Atomics

หลังจากเห็นความซับซ้อนของ memory ordering (หัวข้อ 51.4-51.7) และ ABA problem (หัวข้อ 51.10) แล้ว ควรตั้งคำถาม
ที่สำคัญที่สุดของบทนี้: **เมื่อไหร่ที่ควรใช้ atomics/lock-free ตรง ๆ ในโค้ดจริง?**

คำตอบที่ซื่อสัตย์และตรงกับแนวทางที่ใช้กันจริงในวงการ (คล้ายกับที่ Part 41 หัวข้อเป้าหมายวางกรอบเรื่อง `unsafe`
ไว้ตั้งแต่ต้นบท — ว่ามันเป็นเครื่องมือที่จำเป็นแต่ต้องใช้ด้วยความรับผิดชอบสูง ไม่ใช่ตัวเลือกแรกที่ควรกระโดดไปใช้)
คือ:

> **ในโค้ด production ส่วนใหญ่ ให้เริ่มจาก `Mutex`/`RwLock` (Part 39) เสมอ — มัน correct โดยง่าย, เขียน/อ่าน
> เข้าใจได้ง่าย, และ debug ได้ง่ายกว่ามาก จากนั้น profile โปรแกรมจริง (Part 54-55 ในอนาคต) เพื่อยืนยันว่า lock
> contention เป็นคอขวดจริง ๆ (ไม่ใช่แค่ความรู้สึกว่า "atomic ต้องเร็วกว่าแน่ ๆ") แล้วค่อยพิจารณาเปลี่ยนไปใช้
> atomics ตรง ๆ สำหรับ**เฉพาะจุดที่วัดได้จริงว่าคุ้มค่า**เท่านั้น**

เหตุผลของคำแนะนำนี้มีอยู่หลายชั้น:

1. **Correctness ของ `Mutex` พิสูจน์ได้ง่ายกว่ามาก**: ทุกอย่างที่อยู่ใน critical section ของ `MutexGuard<T>`
   รับประกันความถูกต้องโดยอัตโนมัติ (ไม่มีใครเข้าถึงพร้อมกันได้เลย) — ในขณะที่การใช้ atomics ตรง ๆ ต้องคิดเรื่อง
   memory ordering ที่ถูกต้องเอง (หัวข้อ 51.4-51.7) และถ้าต้องอัปเดตหลายค่าให้สัมพันธ์กัน การทำแบบ lock-free
   ให้ถูกต้องเต็มรูปแบบนั้นยากกว่าที่คิดมาก — ตัวอย่างเช่น การย้ายเงินข้ามสองบัญชีของ Part 39 (หัวข้อ 39.11)
   ถ้าจะทำแบบ lock-free จริง ต้องคิดเรื่องการอัปเดตสองค่า (ยอดบัญชี A และ B) ให้เป็น "atomic operation เดียว"
   ซึ่ง `AtomicI64` เดี่ยว ๆ ทำไม่ได้เลย (มันรับประกันความถูกต้องได้แค่ตัวมันเองตัวเดียว) — ต้องพึ่งเทคนิคที่
   ซับซ้อนกว่ามาก (เช่น double-CAS หรือโครงสร้างข้อมูลที่ออกแบบมาเฉพาะ) ในขณะที่ `Mutex` ตัวเดียวครอบทั้งสอง
   ค่าไว้ด้วยกันแก้ปัญหานี้ได้อย่างตรงไปตรงมา
2. **บั๊กจาก memory ordering ผิดตรวจจับยากกว่าบั๊กจาก deadlock มาก**: deadlock (Part 39) แม้จะเป็นปัญหาที่
   น่ารำคาญ แต่อย่างน้อยมัน**สังเกตได้ชัด** — โปรแกรมค้างสนิท ไม่ตอบสนอง ตรวจจับได้ง่ายทั้งในการทดสอบและใน
   production (เพราะมันหยุดทำงานไปเลย ไม่ใช่ทำงานผิด) ในขณะที่บั๊กจาก memory ordering ที่ผิด (หัวข้อ 51.7)
   อาจ**ทำงานถูกได้เป็นปี ๆ บนฮาร์ดแวร์บางแบบ** ก่อนจะแสดงตัวออกมาในสถานการณ์ที่หายากมาก — ประเภทของบั๊กที่
   "เงียบและยากตรวจจับ" นี้อันตรายกว่ามากในเชิงวิศวกรรมความเสี่ยง
3. **หลักการวิศวกรรมที่ดี: optimize ตามข้อมูลจริง ไม่ใช่ตามสัญชาตญาณ**: การเปลี่ยนจาก `Mutex` เป็น atomics
   เป็น **micro-optimization** ระดับที่คุ้มค่าเฉพาะเมื่อ profiling (เครื่องมือเช่น `perf`, flamegraph — จะ
   เรียนใน Part 55) ชี้ชัดว่า lock contention บนจุดนั้นกินเวลาไปมากจริง ๆ เทียบกับส่วนอื่นของโปรแกรม — การ
   เปลี่ยนไปใช้ atomics/lock-free ก่อนมีข้อมูลจากการ profile มักเป็นการเสียเวลาเปลี่ยนโค้ดให้ซับซ้อนขึ้นและ
   เสี่ยงบั๊กมากขึ้น เพื่อแก้ปัญหาที่ (ยัง) ไม่รู้ด้วยซ้ำว่ามีอยู่จริงหรือไม่

#### เมื่อไหร่ที่ atomics ตรง ๆ เหมาะสมจริง ๆ

สถานการณ์ที่ atomics ตรง ๆ (ไม่ใช่ lock-free data structure เต็มรูปแบบ แค่ใช้ atomic type เดี่ยว ๆ) เหมาะสม
และปลอดภัยที่จะทำเองได้ โดยไม่ต้องพึ่ง crate เสริม:

- **Counter/statistics ที่แต่ละค่าเป็นอิสระจากกัน** ไม่ต้องสัมพันธ์กับค่าอื่นเป๊ะ ๆ ในเวลาเดียวกัน (ตัวอย่าง
  ในหัวข้อ 51.14) — นี่คือ "sweet spot" ที่แท้จริงของ atomics: เรียบง่าย, ปลอดภัย, ไม่ต้องคิดเรื่อง ABA เลย
  (ไม่มี compare_exchange เกี่ยวข้อง แค่ `fetch_add` ตรง ๆ)
- **Flag บอกสถานะเปิด/ปิดง่าย ๆ** (เช่น `AtomicBool` สำหรับ "should_shutdown" ที่หลาย thread อ่านเช็คเป็นระยะ)
- **CAS retry loop สำหรับค่าเดี่ยว ๆ ที่ไม่มีปัญหา ABA** (เช่นตัวอย่าง `update_max` ในหัวข้อ 51.8 — ไม่มี ABA
  problem เกี่ยวข้องเพราะเราไม่ได้ทำงานกับ pointer/address ที่อาจถูกนำมาใช้ซ้ำ แค่ตัวเลขธรรมดาที่เทียบค่ากันตรง
  ๆ ได้อย่างสมบูรณ์)

#### เมื่อไหร่ที่ควรพึ่งพา Crate เช่น `crossbeam`

สำหรับ **lock-free data structure เต็มรูปแบบ** (queue, stack, skip list, hash map แบบ lock-free) ที่ต้อง
จัดการกับ pointer ที่ถูกใช้ซ้ำ (เสี่ยง ABA problem โดยตรง) หรือต้องมี memory reclamation ที่ปลอดภัย —
คำแนะนำที่ตรงกับแนวทางวิศวกรรมที่รับผิดชอบคือ **ใช้ crate ที่ผ่านการทดสอบและ audit มาอย่างหนักแล้ว** เช่น
`crossbeam` (ให้ `crossbeam::queue::SegQueue`, `crossbeam::queue::ArrayQueue` และโครงสร้างข้อมูล lock-free
อื่น ๆ ที่ผ่านการพิสูจน์และทดสอบอย่างละเอียดมาแล้วโดยทีมที่เชี่ยวชาญเฉพาะด้านนี้) แทนการเขียนเองตั้งแต่ต้น —
เหตุผลตรงไปตรงมา: **lock-free data structure ที่เขียนเองมักมีบั๊กที่ subtle มาก ซ่อนอยู่ในมุมที่แสดงตัวออกมา
เฉพาะภายใต้ timing หรือฮาร์ดแวร์บางแบบเท่านั้น** — บั๊กประเภทนี้อาจไม่แสดงตัวใน test suite ที่รันซ้ำนับพันครั้ง
บนเครื่อง CI เครื่องเดียว แต่แสดงตัวใน production หลังจากรันมาหลายเดือนบนฮาร์ดแวร์ที่มี core จำนวนมากกว่าและ
timing ต่างออกไป — ทีมที่ดูแล `crossbeam` มีความเชี่ยวชาญเฉพาะด้านนี้และมีชุดการทดสอบที่ครอบคลุมกว่าที่ทีม
ทั่วไปจะสร้างขึ้นเองได้ในเวลาที่เหมาะสม

`crossbeam` ไม่ได้มีแค่ lock-free queue/stack เท่านั้น — ระบบนิเวศของมันยังมีเครื่องมือที่เกี่ยวข้องอีกหลายตัว
ที่ควรรู้จักไว้ในระดับ awareness เช่นกัน: **`crossbeam::channel`** เป็น multi-producer multi-consumer (MPMC)
channel ที่เร็วกว่า `std::sync::mpsc` ของ Part 38 อย่างมีนัยสำคัญในหลายสถานการณ์ (`std::sync::mpsc` รองรับแค่
multi-producer **single**-consumer ตามชื่อ ส่วน `crossbeam::channel` รองรับผู้รับได้หลายคนพร้อมกันด้วย) และ
ภายในของมันก็ใช้เทคนิค lock-free/atomics ที่เรียนมาทั้งบทนี้ผสมกับ `Mutex` แบบ hybrid เพื่อให้ได้ทั้งความเร็ว
และความถูกต้อง — **`crossbeam::epoch`** คือ implementation ของเทคนิค epoch-based memory reclamation ที่
กล่าวถึงในหัวข้อ 51.10 ให้ใช้งานจริงโดยไม่ต้องเขียนเอง และ **`crossbeam::atomic::AtomicCell<T>`** คือ atomic
wrapper ที่รองรับ type ใดก็ได้ (ไม่จำกัดแค่ integer/bool/pointer แบบ `std::sync::atomic`) โดยใช้ lock ขนาดเล็ก
ภายใน (spinlock) สำหรับ type ที่ใหญ่เกินกว่าที่ฮาร์ดแวร์จะทำ atomic operation ได้ในคำสั่งเดียว — เป็นตัวอย่าง
ที่ดีว่า "lock-free เต็มรูปแบบ" ไม่ใช่คำตอบเดียวเสมอไป บางครั้ง hybrid approach ที่ใช้ lock ขนาดเล็กมาก ๆ
ผสมกับ atomics ก็เป็นทางออกที่สมเหตุสมผลกว่า

สรุปเป็นลำดับการตัดสินใจที่แนะนำ (ลำดับความเสี่ยงจากต่ำไปสูง):

```
1. Mutex<T>/RwLock<T> (Part 39)                  <- เริ่มที่นี่เสมอ
        |
        v  (profile พบว่า lock contention เป็นคอขวดจริง)
2. Atomic type เดี่ยว ๆ (counter, flag, CAS ค่าเดียว)  <- ปลอดภัยพอที่จะทำเอง
        |
        v  (ต้องการ lock-free data structure เต็มรูปแบบ)
3. Crate ที่ผ่านการทดสอบแล้ว เช่น crossbeam         <- อย่าเขียนเอง เว้นแต่จำเป็นจริง ๆ
        |
        v  (สถานการณ์เฉพาะทางมากจริง ๆ ที่ crate ที่มีอยู่ไม่ตอบโจทย์)
4. เขียน lock-free data structure เอง               <- ระวังสูงสุด, ต้องมี test/review อย่างละเอียด
```

### 51.12 `AtomicPtr<T>`: Atomic Operation บน Raw Pointer

`AtomicPtr<T>` (จาก `std::sync::atomic`) คือ atomic type ที่เก็บ **raw pointer** (`*mut T` จาก Part 42) โดย
ตรง — มัน implement `.load()`/`.store()`/`.compare_exchange()` แบบเดียวกับ atomic type ตัวอื่นทุกประการ เพียง
แต่ค่าที่เก็บอยู่เป็น pointer แทนตัวเลข:

```rust
use std::sync::atomic::{AtomicPtr, Ordering};

fn main() {
    let mut value_a = 10;
    let mut value_b = 20;

    let atomic_ptr = AtomicPtr::new(&mut value_a as *mut i32);

    // load(): อ่าน raw pointer ที่เก็บอยู่ตอนนี้ (Part 42: *mut T คือ raw pointer)
    let loaded = atomic_ptr.load(Ordering::SeqCst);
    unsafe {
        println!("ค่าที่ pointer ปัจจุบันชี้ไป: {}", *loaded);
    }

    // สลับให้ atomic_ptr ชี้ไปที่ value_b แทน แบบ atomic
    // (thread อื่นที่ load พร้อมกันจะไม่เห็น pointer ที่ครึ่ง ๆ กลาง ๆ)
    atomic_ptr.store(&mut value_b as *mut i32, Ordering::SeqCst);
    let loaded2 = atomic_ptr.load(Ordering::SeqCst);
    unsafe {
        println!("ค่าที่ pointer ชี้ไปหลัง store: {}", *loaded2);
    }
}
```

ผลลัพธ์ (รันจริง):

```
ค่าที่ pointer ปัจจุบันชี้ไป: 10
ค่าที่ pointer ชี้ไปหลัง store: 20
```

สังเกตว่าการ **dereference** pointer ที่ได้จาก `.load()` (คือ `*loaded`) ยังคงต้องอยู่ใน `unsafe` block เสมอ
ตามกฎของ Part 41-42 — `AtomicPtr<T>` แค่ทำให้การ**อ่าน/เขียนตัว pointer เอง**เป็น atomic (ไม่มีทาง
"อ่านเห็น pointer ที่ผสมกันครึ่ง ๆ" จากหลาย thread) แต่**ไม่ได้ทำให้การ dereference สิ่งที่ pointer นั้นชี้ไป
ปลอดภัยอัตโนมัติ** — ความปลอดภัยของข้อมูลที่ pointer ชี้ไป (เช่น มันยังไม่ถูก free ไปแล้วหรือยัง, มีคนอื่นแก้ไข
พร้อมกันอยู่หรือไม่) ยังเป็นความรับผิดชอบของผู้เขียนโค้ดเต็มรูปแบบเหมือนกับ raw pointer ทั่วไปทุกประการ

นี่คือ building block ที่แท้จริงที่ **lock-free linked list, lock-free queue, และ lock-free stack** ในโลกจริง
(รวมถึงที่อยู่ภายใน `crossbeam`) ใช้ภายในตัวเองสำหรับการ swap "node ถัดไป"/"top ของ stack" แบบ atomic — การ
สร้างโครงสร้างข้อมูลเหล่านี้ให้ปลอดภัย 100% เต็มรูปแบบต้องผสมทั้ง `AtomicPtr<T>`, memory ordering ที่ถูกต้อง
(หัวข้อ 51.4-51.7), และเทคนิคป้องกัน ABA problem (หัวข้อ 51.10) เข้าด้วยกันทั้งหมด — ซึ่งตรงกับคำแนะนำในหัวข้อ
51.11 ว่าทำไมงานระดับนี้เหมาะกับการพึ่งพา crate ที่ทดสอบมาแล้วมากกว่าการเขียนเองตั้งแต่ต้น

### 51.13 `fence()`: Memory Fence แบบ Standalone (Awareness Level)

นอกจาก ordering ที่ผูกกับ atomic operation ตัวใดตัวหนึ่งโดยตรง (เช่น `.load(Ordering::Acquire)`) Rust ยังมี
`std::sync::atomic::fence()` ที่สร้าง **memory fence แบบ standalone** — คือรั้ว ordering ที่ **ไม่ผูกกับ
atomic operation ตัวใดตัวหนึ่งโดยเฉพาะ** แต่คุม operation ทั้งหมด (ทั้ง atomic และไม่ใช่ atomic) ที่อยู่
**ก่อน/หลังจุดที่เรียก `fence()`** ในเธรดเดียวกัน:

```rust
use std::sync::atomic::{fence, AtomicBool, AtomicI32, Ordering};
use std::sync::Arc;
use std::thread;

struct Shared {
    payload: AtomicI32,
    flag: AtomicBool,
}

fn publish(shared: &Shared, value: i32) {
    shared.payload.store(value, Ordering::Relaxed);
    // fence(Release) บังคับว่า operation ก่อนหน้านี้ทั้งหมด (payload.store) ต้อง "มองเห็นแล้วเสร็จสมบูรณ์"
    // ก่อนที่ operation หลังจากนี้ (flag.store) จะเกิดขึ้น -- คล้ายกับใส่ Ordering::Release ให้ store ข้างบน
    // แต่ fence คุมทุก atomic operation ในเธรดนี้ ไม่ผูกกับตัวแปรตัวเดียวแบบพารามิเตอร์ ordering ปกติ
    fence(Ordering::Release);
    shared.flag.store(true, Ordering::Relaxed);
}

fn try_consume(shared: &Shared) -> Option<i32> {
    if shared.flag.load(Ordering::Relaxed) {
        // fence(Acquire) จับคู่กับ fence(Release) ของฝั่งเขียน รับประกัน happens-before เช่นเดียวกับ
        // Ordering::Acquire ปกติ แต่คุมทุก atomic operation ก่อนหน้าในเธรดนี้พร้อมกัน
        fence(Ordering::Acquire);
        Some(shared.payload.load(Ordering::Relaxed))
    } else {
        None
    }
}

fn main() {
    let shared = Arc::new(Shared {
        payload: AtomicI32::new(0),
        flag: AtomicBool::new(false),
    });

    let producer_shared = Arc::clone(&shared);
    let producer = thread::spawn(move || {
        publish(&producer_shared, 77);
    });

    let consumer_shared = Arc::clone(&shared);
    let consumer = thread::spawn(move || loop {
        if let Some(v) = try_consume(&consumer_shared) {
            println!("consumer อ่านค่าได้: {}", v);
            assert_eq!(v, 77);
            break;
        }
        thread::yield_now();
    });

    producer.join().unwrap();
    consumer.join().unwrap();
    println!("fence() ทำงานถูกต้องเหมือนกับใช้ Ordering::Acquire/Release ตรง ๆ");
}
```

ผลลัพธ์ (รันจริง — ตรวจซ้ำด้วยการรัน **30 ครั้ง** ได้ผลเหมือนกันทุกครั้ง):

```
consumer อ่านค่าได้: 77
fence() ทำงานถูกต้องเหมือนกับใช้ Ordering::Acquire/Release ตรง ๆ
```

`fence()` มีประโยชน์ในสถานการณ์เฉพาะทางที่ต้องการรั้ว ordering ที่คุม**หลาย** atomic operation พร้อมกันโดยไม่
อยากผูก ordering เข้ากับตัวใดตัวหนึ่งเป็นการเฉพาะ (เช่น กรณีที่ operation ที่จะเรียกต่อไปเป็น `Relaxed` ล้วน ๆ
เพื่อความเร็ว แต่ต้องการรั้วเพียงจุดเดียวมาคุมทั้งหมดพร้อมกันในบางเงื่อนไข) — ในทางปฏิบัติ `fence()` ถูกใช้ใน
โค้ดระดับสูงน้อยกว่า ordering ที่ผูกกับ operation ตรง ๆ มาก และมักปรากฏเฉพาะในโค้ดของ lock-free data structure
ที่ซับซ้อนมาก (เช่นภายใน implementation ของ `crossbeam-epoch`) — สำหรับบทนี้ ให้รู้จักไว้แค่ในระดับ **awareness**
ว่ามันมีอยู่และแก้ปัญหาอะไร ไม่จำเป็นต้องใช้มันในโค้ดทั่วไป

### 51.14 ตัวอย่างจริง: ตัวติดตามความคืบหน้า (Progress/Statistics Tracker) แบบ Lock-free เต็มรูปแบบ

ปิดท้ายเนื้อหาด้วยตัวอย่างที่ตรงกับ **sweet spot ที่แท้จริง** ของ atomics ในงานจริง (ตามที่สรุปไว้ในหัวข้อ
51.11): ระบบประมวลผลงานแบบ batch ที่มีหลาย worker thread ทำงานพร้อมกัน แต่ละตัวต้องอัปเดตสถิติ "ประมวลผลสำเร็จ
แล้วกี่ชิ้น (processed)", "ล้มเหลวกี่ชิ้น (failed)", และ "ข้ามไปกี่ชิ้น (skipped)" — และมี main thread ที่อ่าน
ค่าเหล่านี้เป็นระยะเพื่อรายงานความคืบหน้าแบบ **ใกล้เคียง real-time** ระหว่างที่ worker ยังทำงานอยู่ (ไม่ต้องรอ
`.join()` ทุกตัวก่อนถึงจะรู้ความคืบหน้าได้เลย):

```rust
use std::sync::atomic::{AtomicU64, Ordering};
use std::sync::Arc;
use std::thread;
use std::time::Duration;

struct Stats {
    processed: AtomicU64,
    failed: AtomicU64,
    skipped: AtomicU64,
}

impl Stats {
    fn new() -> Self {
        Stats {
            processed: AtomicU64::new(0),
            failed: AtomicU64::new(0),
            skipped: AtomicU64::new(0),
        }
    }

    /// อ่านค่าทั้งสามตัวพร้อมกัน (แยก .load() สามครั้ง -- อาจมี inconsistency เล็กน้อยระหว่างสามค่านี้ได้
    /// ในระดับ "ผลรวมอาจไม่ตรง 100% ตอนที่ยังทำงานอยู่" แต่เป็นเรื่องปกติและรับได้สำหรับ progress reporting
    /// เพราะแต่ละ counter ก็ยังถูกต้อง 100% ในตัวเองเสมอ -- ค่าสุดท้ายหลัง join() เท่านั้นที่ต้อง exact)
    fn snapshot(&self) -> (u64, u64, u64) {
        (
            self.processed.load(Ordering::Relaxed),
            self.failed.load(Ordering::Relaxed),
            self.skipped.load(Ordering::Relaxed),
        )
    }
}

fn classify(item: u32) -> &'static str {
    if item % 13 == 0 {
        "failed"
    } else if item % 7 == 0 {
        "skipped"
    } else {
        "processed"
    }
}

fn main() {
    let stats = Arc::new(Stats::new());
    let total_items: u32 = 100_000;
    let worker_count: u32 = 8;
    let items_per_worker = total_items / worker_count;

    let mut handles = vec![];
    for worker_id in 0..worker_count {
        let stats = Arc::clone(&stats);
        let start = worker_id * items_per_worker;
        let end = start + items_per_worker;
        handles.push(thread::spawn(move || {
            for item in start..end {
                // ไม่มี Mutex เกี่ยวข้องเลยตรงนี้ -- แต่ละ worker เพิ่มค่า counter ของตัวเองแบบ atomic
                // โดยไม่ต้องรอใครปลดล็อกอะไรทั้งสิ้น
                match classify(item) {
                    "failed" => stats.failed.fetch_add(1, Ordering::Relaxed),
                    "skipped" => stats.skipped.fetch_add(1, Ordering::Relaxed),
                    _ => stats.processed.fetch_add(1, Ordering::Relaxed),
                };
            }
            thread::sleep(Duration::from_millis(30));
        }));
    }

    // main thread อ่านความคืบหน้าเป็นระยะ ๆ ระหว่างที่ worker ยังทำงานอยู่ -- ไม่ต้องรอ .join() ครบก่อนเลย
    let mut report_count = 0;
    while handles.iter().any(|h| !h.is_finished()) {
        let (p, f, s) = stats.snapshot();
        println!(
            "progress: processed={} failed={} skipped={} total_so_far={}",
            p, f, s, p + f + s
        );
        report_count += 1;
        thread::sleep(Duration::from_millis(15));
        if report_count > 50 {
            break; // กันไม่ให้ log ยาวเกินไปถ้า scheduler ช้าผิดปกติ
        }
    }

    for h in handles {
        h.join().unwrap();
    }

    let (p, f, s) = stats.snapshot();
    println!("สรุปสุดท้าย: processed={} failed={} skipped={} total={}", p, f, s, p + f + s);
    assert_eq!(p + f + s, total_items as u64);
    println!("assert_eq! ผ่าน: ไม่มีงานหายไปแม้แต่ 1 ชิ้น จากการอัปเดต counter แบบไม่มี mutex เลย");
}
```

ผลลัพธ์ (รันจริง — ตัวอย่างการรันครั้งหนึ่ง; ตรวจซ้ำด้วยการรัน **10 ครั้ง** `assert_eq!` ผ่านทุกครั้ง จำนวน
บรรทัด "progress" ที่พิมพ์ออกมาอาจต่างกันในแต่ละครั้งตามธรรมชาติของ scheduler แต่ผลรวมสุดท้ายถูกต้องเป๊ะเสมอ):

```
progress: processed=0 failed=0 skipped=0 total_so_far=0
progress: processed=79120 failed=7693 skipped=13187 total_so_far=100000
progress: processed=79120 failed=7693 skipped=13187 total_so_far=100000
สรุปสุดท้าย: processed=79120 failed=7693 skipped=13187 total=100000
assert_eq! ผ่าน: ไม่มีงานหายไปแม้แต่ 1 ชิ้น จากการอัปเดต counter แบบไม่มี mutex เลย
```

ตัวอย่างนี้แสดงจุดแข็งที่แท้จริงของ atomics ให้เห็นครบทุกด้าน:

1. **ความเรียบง่าย**: ไม่มี `Mutex`, ไม่มี `MutexGuard`, ไม่มีความเสี่ยง deadlock หรือ poisoning เลยแม้แต่
   นิดเดียว — แค่ `fetch_add(1, Relaxed)` ตรง ๆ ในทุกจุดที่ต้องอัปเดต
2. **ความถูกต้อง**: ผลรวมทั้งหมดต้องตรงกับ `total_items` เป๊ะเสมอ ไม่ว่า 8 thread จะแข่งกันเรียก
   `fetch_add` พร้อมกันหนาแน่นแค่ไหนก็ตาม — พิสูจน์แล้วด้วยการรันซ้ำหลายครั้งทุกครั้งผ่าน
3. **การอ่านความคืบหน้าแบบ "อิสระ" จากงานที่กำลังทำ**: main thread เรียก `.snapshot()` ได้ตลอดเวลาโดยไม่มี
   ผลกระทบต่อ worker thread เลย (ไม่ต้องรอ lock, ไม่ทำให้ worker ช้าลงจากการถูก block) — ต่างจากถ้าใช้
   `Arc<Mutex<Stats>>` ที่ทุกครั้งที่ main thread อ่านค่า จะมีโอกาสทำให้ worker thread ที่กำลังจะเขียนค่าต้อง
   รอคิวสั้น ๆ อยู่บ้าง (แม้จะเล็กน้อยมากสำหรับ operation ที่เบาแบบนี้ก็ตาม)
4. **ใช้ `Ordering::Relaxed` ได้อย่างถูกต้องปลอดภัย**: เพราะ counter ทั้งสามตัวเป็นอิสระจากกันโดยสมบูรณ์
   (ไม่มี "ข้อมูลอื่น" ที่ต้องอ่าน/เขียนพร้อมกันเป็นชุดเดียวกับมันเลย) ตรงกับเงื่อนไขที่หัวข้อ 51.5 อธิบายไว้ว่า
   `Relaxed` เพียงพอ — ไม่จำเป็นต้องใช้ `SeqCst` ที่แพงกว่าในสถานการณ์แบบนี้เลย (แม้คำแนะนำทั่วไปในหัวข้อ 51.7
   จะบอกให้เริ่มจาก `SeqCst` แต่นี่คือตัวอย่างที่เข้าเงื่อนไข "เข้าใจแล้วว่าทำไมใช้ตัวที่อ่อนกว่าได้" อย่างชัดเจน)

## กับดักที่พบบ่อย (Common Pitfalls)

### 1. เข้าใจผิดว่า `Relaxed` ให้การรับประกัน ordering ข้ามตัวแปร (แต่ compiler ไม่เตือนเลย)

```rust
use std::sync::atomic::{AtomicBool, AtomicI32, Ordering};
use std::sync::Arc;
use std::thread;

struct SharedData {
    payload: AtomicI32,
    ready: AtomicBool,
}

fn main() {
    let shared = Arc::new(SharedData {
        payload: AtomicI32::new(0),
        ready: AtomicBool::new(false),
    });

    let producer_shared = Arc::clone(&shared);
    let producer = thread::spawn(move || {
        producer_shared.payload.store(42, Ordering::Relaxed);
        // กับดัก: ใช้ Relaxed ตรงนี้ด้วย โดยเข้าใจผิดว่า "แค่เป็น atomic ก็พอแล้ว ไม่ต้องคิดเรื่อง ordering"
        producer_shared.ready.store(true, Ordering::Relaxed);
    });

    let consumer_shared = Arc::clone(&shared);
    let consumer = thread::spawn(move || {
        while !consumer_shared.ready.load(Ordering::Relaxed) {
            thread::yield_now();
        }
        let value = consumer_shared.payload.load(Ordering::Relaxed);
        println!("consumer เห็น payload = {}", value);
    });

    producer.join().unwrap();
    consumer.join().unwrap();
}
```

โค้ดนี้ **compile ผ่านได้ปกติ 100%** และในทางปฏิบัติ **มักจะรันผ่านได้ปกติด้วย** บนสถาปัตยกรรม x86-64 ที่ใช้
เขียนบทนี้ (เพราะฮาร์ดแวร์ x86-64 มี memory model ที่แข็งอยู่แล้วโดยธรรมชาติ ทำให้บั๊กนี้ยากที่จะแสดงตัวออกมา
ให้เห็นจริง) — **นี่คือความน่ากลัวที่สุดของกับดักนี้**: ไม่มี error, ไม่มี panic, ไม่มีสัญญาณเตือนใด ๆ เลยทั้ง
ตอน compile และตอนรันบนเครื่องพัฒนาทั่วไป **วิธีแก้**: จำกฎง่าย ๆ ไว้เสมอ — **ถ้าตัวแปร atomic ตัวหนึ่งถูกใช้
เป็น "สัญญาณ" บอกว่าข้อมูลตัวอื่น (atomic หรือไม่ก็ตาม) พร้อมใช้งานแล้ว ต้องใช้ `Release` (ฝั่งเขียน flag)
คู่กับ `Acquire` (ฝั่งอ่าน flag) เสมอ ไม่ใช่ `Relaxed` ทั้งสองฝั่ง** — ดูตัวอย่างที่ถูกต้องในหัวข้อ 51.6
(เปลี่ยนแค่ `Ordering::Relaxed` เป็น `Ordering::Release`/`Ordering::Acquire` สำหรับตัวแปร `ready` เท่านั้น)
หรือถ้าไม่แน่ใจเลยว่าควรใช้ ordering ไหน ให้ใช้ `SeqCst` ทุกที่ไปก่อนตามคำแนะนำในหัวข้อ 51.7 — ไม่มีทางเสีย
ความถูกต้องจากการใช้ `SeqCst` มากเกินความจำเป็นเลย มีแต่เสียประสิทธิภาพเล็กน้อยเท่านั้น

### 2. ABA Problem: เชื่อว่า `compare_exchange` สำเร็จ = ไม่มีอะไรเปลี่ยนแปลงเลย

ตามที่พิสูจน์ด้วยโค้ดจริงในหัวข้อ 51.10 — การเขียน CAS retry loop สำหรับโครงสร้างข้อมูลที่เกี่ยวข้องกับ pointer
หรือ index ที่**อาจถูกนำมาใช้ซ้ำได้** (เช่น การจัดการ memory pool, free list, หรือ lock-free stack/queue ที่
คืนความจำ node กลับไปให้ allocator ใช้ซ้ำ) มีความเสี่ยงต่อ ABA problem เสมอ ถ้าไม่ได้ป้องกันไว้ — สัญญาณเตือนว่า
โค้ดของคุณอาจเสี่ยง ABA problem: **`compare_exchange` เทียบค่าที่อาจ "วนกลับมาเป็นค่าเดิม" ได้ในทางทฤษฎี**
(ตัวเลข address, index ที่ recycle, หรือ enum ที่มีค่าจำกัดจำนวนแบบวนซ้ำได้) **วิธีแก้**: ถ้าโครงสร้างข้อมูลของ
คุณมีความเสี่ยงแบบนี้ ให้ใช้เทคนิค generation counter/tagged pointer หรือ epoch-based reclamation ตามที่แนะนำ
ในหัวข้อ 51.10 — หรือทางที่ปลอดภัยและเรียบง่ายกว่ามากในโค้ด production ทั่วไป คือ**ใช้ crate ที่ป้องกันปัญหานี้
ไว้ให้แล้ว** เช่น `crossbeam` (หัวข้อ 51.11) แทนการเขียน lock-free data structure ที่ต้อง reuse memory เอง
ตั้งแต่ต้น

### 3. False Sharing: โค้ด "ถูกต้อง" 100% แต่ช้าลงอย่างไม่มีเหตุผลชัดเจน

```rust
use std::sync::atomic::{AtomicU64, Ordering};

struct WithoutPadding {
    counter_a: AtomicU64, // สอง field นี้มักถูกจัดวางให้อยู่ใน cache line เดียวกัน (64 bytes ทั่วไปบน x86-64)
    counter_b: AtomicU64,
}
```

โค้ดแบบนี้ **ไม่มีบั๊กเชิง logic เลยแม้แต่นิดเดียว** — ถ้าสอง thread ต่างคนต่างแก้ไข `counter_a` และ
`counter_b` ของตัวเอง (ไม่ได้แก้ไขข้อมูลร่วมกันเลย ไม่มี data race ทาง logic) ผลลัพธ์ก็ยังถูกต้อง 100% เสมอ —
แต่ประสิทธิภาพอาจ**แย่กว่าที่คาดไว้มาก** เพราะ CPU cache coherency protocol (ที่ทำให้ atomic operation ทำงาน
ถูกต้องตั้งแต่แรก) ทำงานที่ระดับ **cache line ทั้งก้อน** (ปกติ 64 bytes) ไม่ใช่ระดับ byte เดียว — ถ้า `core A`
เขียน `counter_a` และ `core B` เขียน `counter_b` พร้อมกันบ่อย ๆ แต่ทั้งสองตัวอยู่ใน cache line เดียวกัน แต่ละ
ครั้งที่ core หนึ่งเขียน จะบังคับให้ core อื่นต้อง invalidate cache line ทั้งก้อนของตัวเองและโหลดใหม่ ทั้งที่
ข้อมูลที่ core นั้นสนใจจริง ๆ (`counter_b` ในตัวอย่าง) ไม่ได้เปลี่ยนเลย — ปรากฏการณ์นี้เรียกว่า **false
sharing** (แบ่งกัน "เท็จ" เพราะทาง logic ไม่ได้แบ่งข้อมูลกันเลย แต่ทาง hardware กลับถูกมองว่าแบ่งกันเพราะอยู่
cache line เดียวกัน) **วิธีแก้ (ระดับ awareness — ไม่จำเป็นต้องทำทุกครั้ง เฉพาะเมื่อ profiling พบว่าเป็น
คอขวดจริง)**: ใช้ `#[repr(align(64))]` แยก struct ให้ counter แต่ละตัว (หรือกลุ่มที่แต่ละ thread เขียนบ่อย)
อยู่คนละ cache line กัน:

```rust
#[repr(align(64))]
struct PaddedCounter {
    value: std::sync::atomic::AtomicU64,
}

struct WithPadding {
    counter_a: PaddedCounter,
    counter_b: PaddedCounter,
}
```

การ padding แบบนี้แลกกับการใช้ memory มากขึ้นอย่างมีนัยสำคัญ (แต่ละ `PaddedCounter` กินพื้นที่เต็ม cache line
แม้ข้อมูลจริงจะใช้แค่ 8 bytes) ดังนั้น**ไม่ควรทำเป็นนิสัยกับทุก struct** — เหมาะกับเฉพาะจุดที่ profiling
(Part 54-55) ยืนยันแล้วว่า false sharing เป็นคอขวดจริงในเส้นทางที่ hot มาก ๆ เท่านั้น

### 4. เขียน CAS Retry Loop ผิด: ไม่อัปเดตค่าจากสาขา `Err` ทำให้ Infinite Loop ภายใต้ Contention จริง

```rust
use std::sync::atomic::{AtomicI64, Ordering};

// เวอร์ชัน "ผิด": compile ผ่านสมบูรณ์ ไม่มี error ใด ๆ เลย เพราะ compiler ตรวจแค่ type ถูกต้อง
// แต่ตรวจ "ตรรกะ" ของ retry loop ให้ไม่ได้
fn buggy_update_max(shared_max: &AtomicI64, candidate: i64) -> i64 {
    let current = shared_max.load(Ordering::Relaxed); // <- current ไม่ใช่ mut!
    loop {
        if candidate <= current {
            return current;
        }
        match shared_max.compare_exchange(current, candidate, Ordering::SeqCst, Ordering::SeqCst) {
            Ok(_) => return candidate,
            Err(_actual) => {
                // บั๊ก: ไม่ได้เขียน current = _actual; ตรงนี้ -- ถ้ามี thread อื่นแก้ไขค่าไปแล้วจริง ๆ
                // compare_exchange ตัวถัดไปจะพยายามเทียบกับ current ตัวเดิม (ล้าสมัย) ซ้ำไปเรื่อย ๆ
                continue; // กลายเป็น infinite loop ภายใต้การแข่งขันจริงจากหลาย thread
            }
        }
    }
}

fn main() {
    // รันแบบ single-thread เพื่อพิสูจน์ว่า "compile และ syntax ถูกต้อง" เท่านั้น -- ในสถานการณ์นี้ไม่มี
    // thread อื่นมาแทรก ดังนั้น compare_exchange ครั้งแรกจะสำเร็จเสมอ (ไม่มีการแข่งขันให้เกิดบั๊ก)
    let shared_max = AtomicI64::new(0);
    let result = buggy_update_max(&shared_max, 50);
    println!("ผลลัพธ์ (single-thread, ไม่มีการแข่งขัน): {}", result);
    assert_eq!(result, 50);
    println!("โค้ดนี้คอมไพล์และรันผ่านในกรณีง่าย ๆ -- แต่มีบั๊ก infinite loop แอบอยู่ภายใต้ contention จริง");
}
```

ผลลัพธ์ (รันจริง):

```
ผลลัพธ์ (single-thread, ไม่มีการแข่งขัน): 50
โค้ดนี้คอมไพล์และรันผ่านในกรณีง่าย ๆ -- แต่มีบั๊ก infinite loop แอบอยู่ภายใต้ contention จริง
```

โค้ดนี้ **compile ผ่านได้ปกติ** (แม้ Rust compiler จะบังคับ `current` ต้องเป็น `mut` ถ้าจะ reassign มันในสาขา
`Err` — ถ้าเผลอลืม reassign แบบตัวอย่างข้างบน `current` ไม่ต้องเป็น `mut` เลยด้วยซ้ำ เพราะไม่มีจุดไหนพยายาม
เปลี่ยนค่ามันจริง ๆ — **compiler ไม่มีทางรู้ได้เลยว่า "ควร" ต้องอัปเดตค่านี้ตามหลัก logic ของ CAS retry loop**)
และในสถานการณ์ที่ไม่มีการแข่งขัน (single-thread, หรือ multi-thread ที่บังเอิญไม่ชนกันเลย) โค้ดนี้จะรันผ่านได้
ปกติทุกครั้งเพราะ `compare_exchange` ครั้งแรกสำเร็จเสมอ — **บั๊กจะแสดงตัวเฉพาะภายใต้ contention จริงเท่านั้น**:
ถ้ามี thread อื่นเปลี่ยนค่า `shared_max` ไปจริง ๆ ระหว่างที่ loop นี้กำลังวนอยู่ `compare_exchange` จะล้มเหลว
ซ้ำแล้วซ้ำอีกด้วย `current` ตัวเดิมที่ล้าสมัยไปแล้วตลอดกาล ไม่มีทางสำเร็จได้เลย กลายเป็น **infinite loop ที่กิน
CPU 100% ของ core นั้นตลอดไป** (spin loop ที่ไม่มีทางออก) **วิธีแก้**: ทุกครั้งที่เขียน CAS retry loop ต้อง
**อัปเดตตัวแปรที่ใช้เทียบจากค่าใน `Err(actual)` เสมอ** ก่อนวนรอบถัดไป (ดูเวอร์ชันที่ถูกต้องในหัวข้อ 51.8 —
`current = actual;` ในสาขา `Err`) — นี่คือเหตุผลที่ **ทุกครั้งที่เขียน CAS retry loop ควรตรวจสอบให้แน่ใจว่า
ทุกสาขา `Err` มีการอัปเดตค่าที่ใช้เทียบในรอบถัดไปเสมอ ไม่มีข้อยกเว้น** — พิจารณาเขียน unit test ที่จำลอง
contention จริงด้วยหลาย thread เสมอสำหรับ CAS retry loop ทุกตัวที่เขียนขึ้น (แบบเดียวกับตัวอย่างในหัวข้อ 51.8
ที่รันด้วยหลาย thread พร้อมกันจริง) เพื่อจับบั๊กแบบนี้ก่อนจะไปถึง production

### 5. เข้าใจผิดว่าการใช้ Atomic Type หลายตัวพร้อมกัน = การอัปเดตพร้อมกันแบบ Atomic

```rust
use std::sync::atomic::{AtomicI64, Ordering};
use std::sync::Arc;
use std::thread;

struct Account {
    balance: AtomicI64,
}

// กับดัก: คิดว่า "ทั้งสอง field เป็น Atomic แล้ว การโอนเงินก็ต้องปลอดภัยอัตโนมัติ"
fn transfer_wrong(from: &Account, to: &Account, amount: i64) {
    // ขั้นตอนนี้เป็น atomic ในตัวมันเอง (การลบค่าออกจาก from.balance ถูกต้อง 100%)
    from.balance.fetch_sub(amount, Ordering::SeqCst);
    // แต่ระหว่างบรรทัดนี้กับบรรทัดบน "ไม่มีอะไรครอบคลุมทั้งสองบรรทัดให้เป็นหน่วยเดียว" เลย
    // thread อื่นที่กำลังอ่าน from.balance และ to.balance พร้อมกันในช่วงนี้ อาจเห็นสถานะที่ "เงินหายไปกลางทาง"
    // (หักจาก from ไปแล้ว แต่ยังไม่เข้า to) ได้จริง ทั้งที่ operation ย่อยแต่ละตัวเป็น atomic สมบูรณ์แบบ
    to.balance.fetch_add(amount, Ordering::SeqCst);
}

fn main() {
    let from = Arc::new(Account { balance: AtomicI64::new(1000) });
    let to = Arc::new(Account { balance: AtomicI64::new(0) });

    let f = Arc::clone(&from);
    let t = Arc::clone(&to);
    let transfer_thread = thread::spawn(move || {
        transfer_wrong(&f, &t, 1000);
    });

    // observer thread อาจ (ในทางทฤษฎี) อ่านเจอสถานะที่ from=0, to=0 พร้อมกัน -- เงินหายไปชั่วขณะ!
    let f2 = Arc::clone(&from);
    let t2 = Arc::clone(&to);
    let observer = thread::spawn(move || {
        let snapshot_from = f2.balance.load(Ordering::SeqCst);
        let snapshot_to = t2.balance.load(Ordering::SeqCst);
        println!("observer เห็น from={}, to={} (ผลรวมอาจไม่ครบ 1000 ในช่วงกลางการโอน)", snapshot_from, snapshot_to);
    });

    transfer_thread.join().unwrap();
    observer.join().unwrap();
}
```

โค้ดนี้ **compile ผ่านสมบูรณ์และแต่ละ `fetch_sub`/`fetch_add` ก็ทำงานถูกต้อง 100% ในตัวมันเอง** — นี่คือ
กับดักเชิงความเข้าใจที่พบบ่อยที่สุดของผู้ที่เพิ่งเรียนรู้ atomics: **การที่ operation ย่อยแต่ละตัวเป็น atomic
ไม่ได้แปลว่าการรวมหลาย atomic operation เข้าด้วยกันจะเป็น atomic ไปด้วย** — ระหว่างที่ `from.balance` ถูกลด
ค่าไปแล้ว แต่ `to.balance` ยังไม่ถูกเพิ่มค่า มี **"ช่องว่างเวลา" ที่เปิดโอกาสให้ thread อื่น** ที่กำลังมองทั้งสอง
ค่าพร้อมกัน (เช่น thread ที่คำนวณยอดรวมทั้งระบบเพื่อแสดงรายงาน) เห็นสถานะที่เงินรวมทั้งระบบ**ไม่ตรง**กับความเป็น
จริงชั่วขณะหนึ่งได้ — ในทางปฏิบัติช่องว่างนี้แคบมาก (แค่ไม่กี่คำสั่ง CPU) จึงมักไม่แสดงตัวให้เห็นง่าย ๆ ในการรัน
ทั่วไปแบบสุ่ม (ต้อง observer thread เข้ามาอ่านตรงจังหวะพอดีเป๊ะ ๆ) แต่ **การที่มันหายากไม่ได้แปลว่ามันไม่มีอยู่
จริง** — ในระบบที่มีการแข่งขันสูงมาก (thread จำนวนมาก, เรียกบ่อยมาก) โอกาสที่จะเจอสถานะกลาง ๆ แบบนี้จะสูงขึ้น
ตามสัดส่วน และเป็นบั๊กประเภท Heisenbug แบบเดียวกับที่หัวข้อ 51.7 เตือนไว้ — ตรงกับปัญหาเดียวกันเป๊ะที่ Part 39
หัวข้อ 39.11 พูดถึงตอนอธิบายว่าทำไม
`withdraw` แยกจาก `deposit` (สองครั้ง `.lock()`) ถึงไม่ปลอดภัยพอสำหรับ `transfer` และทำไมต้องรวมเป็น
`.lock()` ครั้งเดียวที่ครอบทั้งสองการกระทำ **วิธีแก้**: ถ้าต้องอัปเดตหลายค่าให้เป็น "หน่วยเดียวที่แบ่งแยกไม่
ได้" จริง ๆ **ไม่มี atomic type เดี่ยว ๆ ตัวไหนทำสิ่งนี้ให้ได้เลย** ไม่ว่าจะมีกี่ตัวก็ตาม — ต้องกลับไปใช้
`Mutex<T>` ที่ครอบทั้งสองค่าไว้ในโครงสร้างเดียวกัน (ตามที่ Part 39 สอนไว้) หรือถ้าจำเป็นต้องทำแบบ lock-free
จริง ๆ ต้องออกแบบให้ข้อมูลที่ต้องสัมพันธ์กันทั้งหมดถูกเก็บรวมเป็นค่าเดียวที่ทำ CAS ได้ในการเรียกเดียว (เช่น
เก็บ `(from_balance, to_balance)` เป็นค่าเดียวที่ยัดใส่ใน integer ตัวเดียวถ้าขนาดพอ หรือใช้เทคนิคที่ซับซ้อนกว่า
มาก) — กฎที่จำง่าย: **"หลาย atomic ตัวไม่เคยรวมกันเป็น atomic เดียวโดยอัตโนมัติ ไม่ว่าจะเขียนติดกันแค่ไหนก็ตาม"**

## แบบฝึกหัด (Exercises)

1. **(ง่าย)** เขียนโปรแกรมที่สร้าง `Arc<AtomicU32>` เริ่มต้นที่ 0 แล้ว spawn thread จำนวน 10 ตัว โดยแต่ละ
   thread เรียก `.fetch_add(1, Ordering::SeqCst)` จำนวน 1,000 ครั้ง หลัง `join()` ครบทุก thread แล้ว พิมพ์ค่า
   สุดท้ายออกมา และตรวจสอบด้วย `assert_eq!` ว่าค่าต้องเป็น `10,000` เป๊ะ — รันโปรแกรมนี้ซ้ำอย่างน้อย 10 ครั้ง
   เพื่อพิสูจน์ว่าไม่มีครั้งใดที่ผลลัพธ์ผิดเพี้ยนจาก data race เลย (คำใบ้: โครงสร้างโค้ดเหมือนตัวอย่างในหัวข้อ
   51.3 เกือบทั้งหมด แค่เปลี่ยนชนิดข้อมูลและจำนวนรอบ) — ลองเปลี่ยน `Ordering::SeqCst` เป็น `Ordering::Relaxed`
   ดูด้วยว่าผลลัพธ์ยังถูกต้องเหมือนเดิมหรือไม่ และอธิบายว่าทำไม (คำใบ้: ทวนหัวข้อ 51.5 — `fetch_add` เป็น
   operation เดียวที่รวมอ่าน-บวก-เขียนไว้ในคำสั่งเดียวอยู่แล้ว ไม่ได้ใช้ ordering เป็น "สัญญาณ" ให้ข้อมูลอื่นเลย)

2. **(กลาง)** เขียนฟังก์ชัน `try_decrement_if_positive(counter: &AtomicI32) -> bool` ที่ใช้ CAS retry loop
   (แบบเดียวกับ `update_max` ในหัวข้อ 51.8) เพื่อลดค่าของ `counter` ลง 1 **เฉพาะเมื่อค่าปัจจุบันมากกว่า 0**
   เท่านั้น (ถ้าค่าปัจจุบันเป็น 0 หรือติดลบอยู่แล้ว ให้คืน `false` ทันทีโดยไม่ทำอะไร) คืนค่า `true` ถ้าลดค่าสำเร็จ
   จริง — ใช้ฟังก์ชันนี้จำลองสถานการณ์ "ตั๋วคอนเสิร์ตเหลือ 100 ใบ" โดยสร้าง 200 thread ที่แต่ละตัวพยายามซื้อ
   ตั๋วหนึ่งใบพร้อมกัน (เรียก `try_decrement_if_positive` ครั้งเดียว) หลังจบให้นับว่ามีกี่ thread ที่ซื้อสำเร็จ
   (คืน `true`) และตรวจสอบด้วย `assert_eq!` ว่าต้องได้พอดี 100 thread เท่านั้น ไม่มากไม่น้อย (คำใบ้: ระวังเรื่อง
   การอัปเดตค่าที่ใช้เทียบในสาขา `Err` ตามที่อธิบายในกับดักที่พบบ่อยข้อ 4 — ถ้าลืมจะกลายเป็น infinite loop หรือ
   นับผิด) หลังจากทำสำเร็จแล้ว ลองตอบคำถามต่อไปนี้เป็นข้อความสั้น ๆ: ฟังก์ชันนี้เป็น lock-free ตามนิยามในหัวข้อ
   51.9 หรือไม่ และเป็น wait-free หรือไม่ พร้อมอธิบายเหตุผลอ้างอิงจากตารางเปรียบเทียบในหัวข้อนั้น

3. **(ยาก)** เขียนโครงสร้าง `struct SpscFlag` (single-producer single-consumer flag) ที่มี field
   `data: AtomicI64` และ `ready: AtomicBool` (แบบเดียวกับตัวอย่างในหัวข้อ 51.6) แล้วเพิ่ม method
   `publish(&self, value: i64)` (เขียน `data` แล้วประกาศ `ready` ด้วย ordering ที่ถูกต้อง) และ
   `try_consume(&self) -> Option<i64>` (เช็ค `ready`, ถ้าพร้อมแล้วให้อ่าน `data` กลับมาด้วย ordering ที่ถูกต้อง
   คืน `None` ถ้ายังไม่พร้อม) จากนั้นเขียนโปรแกรมทดสอบที่ spawn producer thread หนึ่งตัวเรียก `publish` ด้วยค่า
   สุ่ม 10,000 ค่าติดต่อกัน (ต้องออกแบบให้ consumer อ่านค่าที่ publish ไปแล้วให้ทันก่อน producer จะ publish
   ค่าถัดไปทับ — คำใบ้: อาจต้องเพิ่ม field `consumed: AtomicBool` อีกตัวเพื่อให้ producer รอจนกว่า consumer จะ
   อ่านค่าเดิมเสร็จก่อนจะ publish ค่าใหม่ คล้ายกับการทำ "handshake" ง่าย ๆ ด้วย atomic สองตัว) แล้วให้ consumer
   thread อ่านค่าทั้ง 10,000 ค่าและสะสมผลรวม เปรียบเทียบผลรวมที่ consumer อ่านได้กับผลรวมจริงที่ producer ส่งไป
   ด้วย `assert_eq!` ว่าต้องตรงกันเป๊ะทุกค่า ไม่มีค่าใดสูญหายหรือถูกอ่านซ้ำ (คำใบ้เพิ่มเติม: ลองทดลองเปลี่ยน
   `Ordering::Release`/`Ordering::Acquire` ของคุณให้เป็น `Ordering::Relaxed` ทั้งคู่ชั่วคราวเพื่อดูว่าโปรแกรม
   ยังคง "ดูเหมือน" ทำงานถูกต้องบนเครื่องของคุณหรือไม่ — ถ้ายังผ่านอยู่ ให้ทบทวนหัวข้อ 51.7 และกับดักข้อ 1 ว่า
   ทำไมนี่ไม่ได้แปลว่าโค้ดนั้นถูกต้องจริง แล้วเปลี่ยนกลับเป็น `Release`/`Acquire` ก่อนส่งงาน)

4. **(ประยุกต์ใช้งานจริง)** ขยายตัวอย่างระบบติดตามความคืบหน้าในหัวข้อ 51.14 ให้สมบูรณ์ขึ้นสำหรับสถานการณ์จริง
   มากขึ้น: เพิ่ม field `AtomicU64` อีกตัวชื่อ `retried` (จำนวนงานที่ถูกจัดว่า "ต้อง retry" — สมมติว่า item ที่
   หาร 5 ลงตัวพอดีถือเป็น "retried" แทนที่จะไปนับใน `failed`/`skipped`/`processed`) และเพิ่ม method
   `total(&self) -> u64` ที่รวมทุก field เข้าด้วยกัน แล้วเขียนฟังก์ชัน `is_complete(&self, total_items: u64)
   -> bool` ที่ตรวจสอบว่างานเสร็จครบหรือยัง (`self.total() >= total_items`) — ใช้ฟังก์ชันนี้ในลูปของ main
   thread แทนการเช็ค `handles.iter().any(|h| !h.is_finished())` แบบเดิม (นั่นคือให้ main thread รู้ความคืบหน้า
   ครบ 100% ได้จากการอ่านค่า atomic เพียงอย่างเดียว โดยไม่ต้องพึ่ง `JoinHandle::is_finished()` เลย) ทดสอบด้วย
   worker 16 thread ประมวลผลรวม 1,000,000 item และวัดเวลาที่ใช้ทั้งหมดด้วย `std::time::Instant` เทียบกับ
   เวอร์ชันที่ใช้ `Arc<Mutex<Stats>>` แทน (ห่อทั้งสาม/สี่ field ไว้ใน struct เดียวภายใต้ `Mutex` ตัวเดียว) แล้ว
   เขียนสรุปสั้น ๆ ว่าความต่างของเวลาที่วัดได้ตรงกับที่คาดไว้จากหัวข้อ 51.3 หรือไม่ และทำไม (คำใบ้เพิ่มเติม:
   ลองรันการวัดเวลาซ้ำ 5 รอบทั้งสองเวอร์ชัน แล้วดูว่าความแปรปรวนของตัวเลขระหว่างรอบต่างกันมากน้อยแค่ไหน —
   เวอร์ชันที่ใช้ `Mutex` มักมีความแปรปรวนสูงกว่าเพราะขึ้นกับพฤติกรรมของ OS scheduler ตอนจัดการ thread ที่รอ
   lock ในขณะที่เวอร์ชัน atomic ล้วน ๆ มักให้ตัวเลขที่สม่ำเสมอกว่าในการรันซ้ำแต่ละครั้ง)

## สรุป

บทนี้เป็นบทแรกในสามบทสุดท้ายของสาย concurrency ที่เข้มข้นที่สุดในหลักสูตรทั้งหมด (Part 37-40, 51) และเปิดกล่อง
ที่ Part 39 และ Part 40 ปิดไว้โดยตั้งใจตลอดสองบทนั้น — เราเริ่มจากการรู้จักตระกูล type เต็ม
รูปแบบใน `std::sync::atomic` (`AtomicBool`, `AtomicI32`/`AtomicU32`/`AtomicI64`/`AtomicUsize` ฯลฯ) พร้อม
operation พื้นฐาน `.load()`, `.store()`, `.fetch_add()`, `.fetch_sub()`, และ `.compare_exchange()` แล้วสร้าง
shared counter จาก Part 39 หัวข้อ 39.7 ขึ้นมาใหม่ด้วย `Arc<AtomicI32>` แทน `Arc<Mutex<i32>>` — พิสูจน์ด้วยการ
รันจริงหลายสิบครั้งว่าให้ผลลัพธ์ถูกต้อง 100% เหมือนกัน แต่ **ไม่มี lock ให้ thread ไหนต้องรอเลย** พร้อมตัวเลข
วัดจริงที่แสดงว่า atomic operation มักเร็วกว่า `Mutex` สำหรับ operation ง่าย ๆ แบบนี้

จากนั้นเราลงลึกในส่วนที่ยากที่สุดของบทนี้: **memory ordering** — เข้าใจว่าทำไม compiler และ CPU ถึงมีสิทธิ์
จัดลำดับคำสั่งใหม่ได้ (เพื่อประสิทธิภาพ ในโลก single-thread ไม่มีใครสังเกตความต่างได้) แต่การจัดลำดับใหม่นี้อาจ
สร้างพฤติกรรมที่ผิดพลาดข้าม thread ได้ถ้าไม่มีการควบคุมที่ถูกต้อง — เราไล่ทำความเข้าใจทั้ง 5 ระดับ:
`Relaxed` (ประกันแค่ atomicity ของตัวมันเอง เหมาะกับ counter/สถิติที่เป็นอิสระ), `Acquire`/`Release`/`AcqRel`
(คู่ "ปลดล็อก-ล็อก" ที่สร้าง happens-before relationship ให้ operation รอบข้าง เหมาะกับการ publish ข้อมูลข้าม
เธรดผ่าน flag), และ `SeqCst` (แน่นที่สุด เข้าใจง่ายที่สุด แพงที่สุด — คำแนะนำเชิงปฏิบัติคือให้ใช้เป็นค่าเริ่มต้น
เสมอจนกว่าจะมีเหตุผลที่เข้าใจจริง ๆ ว่าทำไมต้องใช้ตัวที่อ่อนกว่า) — เราเน้นย้ำจุดที่อันตรายที่สุด: **บั๊กจาก
memory ordering ผิดไม่ทำให้ compile ผิดพลาด และมักรันผ่านได้ปกติบนฮาร์ดแวร์ทั่วไปด้วย** ต่างจากบั๊ก
ownership/Send/Sync ทุกตัวที่ Part 6-40 สอนมาซึ่ง compiler ปฏิเสธให้เห็นทันทีตั้งแต่ compile time

เราเรียนรู้ `compare_exchange`/`compare_exchange_weak` ในฐานะหน่วยสร้างพื้นฐานที่สุดของ lock-free algorithm
ทั้งหมด ผ่าน CAS retry loop pattern ที่พิสูจน์ด้วยตัวอย่าง "อัปเดตค่า max ร่วม" ที่รันถูกต้อง 100% ภายใต้การ
แข่งขันจริงจากหลาย thread — แล้วมาถึงนิยามที่แม่นยำของคำว่า **"lock-free"** ที่ถูกเข้าใจผิดกันบ่อย: มันคือการ
รับประกัน**ความคืบหน้าของระบบโดยรวม** (อย่างน้อยหนึ่ง thread คืบหน้าเสมอ แม้ thread อื่นจะมีปัญหา) ไม่ใช่
คำพ้องกับ "เร็ว" — เชื่อมโยงกับ deadlock และ priority inversion จาก Part 39 เพื่อแสดงว่า `Mutex` (blocking)
เสี่ยงต่อปัญหาที่ lock-free ไม่มีเลย และแยกแยะจาก **wait-free** ที่การันตีแข็งแรงกว่าอีกขั้น (ทุก thread คืบหน้า
ภายในจำนวนขั้นตอนที่จำกัด) ผ่านตารางเปรียบเทียบสามระดับให้เห็นชัด

เราพิสูจน์ **ABA problem** ให้เห็นจริงด้วยโค้ดที่จำลองการ preempt ระหว่าง CAS retry loop ผ่าน `Barrier` และ
`thread::sleep` — แสดงให้เห็นว่า `compare_exchange` ที่ "สำเร็จ" อาจหลอกโปรแกรมได้จริงเมื่อค่าวนกลับมาเป็นค่า
เดิม (A → B → A) ทั้งที่มีการเปลี่ยนแปลงเกิดขึ้นจริงระหว่างนั้น พร้อมรู้จักแนวทางบรรเทา (generation
counter/tagged pointer, epoch-based reclamation) ในระดับที่พอเข้าใจว่ามันแก้ปัญหาอะไร — และปิดท้ายด้วยคำแนะนำ
เชิงวิศวกรรมที่ซื่อสัตย์ (เทียบกับกรอบที่ Part 41 วางไว้สำหรับ `unsafe`): **`Mutex`/`RwLock` ก่อนเสมอ, profile
ยืนยันว่า contention เป็นคอขวดจริง, แล้วค่อยพิจารณา atomics/crossbeam** — ไม่ใช่การกระโดดไปเขียน lock-free
data structure เองตั้งแต่ต้น เพราะบั๊กที่ subtle ที่สุดในโปรแกรมมิ่ง concurrent มักซ่อนอยู่ในโค้ดประเภทนี้พอดี

บทนี้ยังแนะนำ `AtomicPtr<T>` (เชื่อมกับ raw pointer จาก Part 42) และ `fence()` (memory fence แบบ standalone)
ในระดับ awareness ว่ามันคือ building block ที่ lock-free data structure จริงในโลก (รวมถึงใน `crossbeam`) ใช้
ภายในตัวเอง และปิดท้ายเนื้อหาด้วยตัวอย่างที่ตรงกับจุดแข็งที่แท้จริงของ atomics มากที่สุด: ตัวติดตามความคืบหน้า
ของงาน batch ที่หลาย worker thread อัปเดต counter หลายตัวพร้อมกันโดยไม่มี `Mutex` เลยแม้แต่ตัวเดียว ในขณะที่
main thread อ่านความคืบหน้าได้แบบอิสระจากงานที่กำลังทำอยู่ตลอดเวลา

(`Mutex`/`Arc`), Part 40 (`Send`/`Sync`), และมาจบที่ Part 51 (atomics/lock-free) ก็สมบูรณ์เต็มรูปแบบแล้ว — ทุก
คำว่า "atomic" ที่ถูกใช้แบบไม่เป็นทางการมาตลอดตอนนี้มีความหมายที่แม่นยำและพิสูจน์ได้ด้วยโค้ดจริงครบทุกมุม
บทต่อไป **Part 52 (Design Patterns ใน Rust: Builder, Strategy, Observer)** จะพาออกจากช่วงเนื้อหาเชิงระบบ
ล้วน ๆ ที่เข้มข้นมาตั้งแต่ Part 41 (unsafe/raw pointers/FFI/proc macros/async/atomics) กลับไปสู่ Rust ที่ใช้
งานในชีวิตประจำวันมากขึ้น — การออกแบบ API และโครงสร้างโค้ดที่อ่านง่าย ดูแลง่าย ด้วย pattern ที่คุ้นเคยจากภาษา
อื่นแต่ปรับให้เข้ากับ ownership/trait system ของ Rust โดยเฉพาะ ก่อนจะกลับมาแตะเรื่อง memory ordering อีกครั้ง
จากมุมมองการวัดผลจริงใน Part 54-55 (Performance Optimization และ Profiling) ในภายหลัง
