# Part 37: Threads พื้นฐาน (std::thread, join, move closures)

> โมดูล: ระดับกลาง (Intermediate) | ระดับ: กลาง | เวลาโดยประมาณ: 220 นาที

## เป้าหมายของบทเรียน

หลังจากจบบทนี้ คุณจะสามารถ:

- อธิบายได้อย่างแม่นยำว่า **data race** คืออะไร ทำไม concurrency ถึงเป็นหนึ่งในเรื่องที่อันตรายที่สุดในภาษา
  โปรแกรมมิ่งส่วนใหญ่ และเข้าใจ **"fearless concurrency"** ซึ่งเป็นคำขวัญที่ Rust ใช้เรียกตัวเอง — พร้อมเห็นด้วยตา
  ตัวเองว่ากฎ ownership/borrowing เดียวกันจาก Part 6-7 ที่ป้องกันบั๊ก memory ตอน compile time นั้น **ป้องกัน data
  race ตอน compile time ได้ด้วย** โดยไม่ต้องมี garbage collector หรือ runtime check เพิ่มเติมใด ๆ เลย
- สร้าง thread ใหม่ได้ด้วย `std::thread::spawn()` เข้าใจว่า closure ที่ส่งเข้าไปต้อง implement `FnOnce() -> T`
  (เชื่อมกับ Part 24) และรู้ว่า `spawn()` คืนค่าอะไรกลับมา (`JoinHandle<T>`)
- ใช้ `.join()` รอให้ thread ทำงานจบ อธิบายได้ว่าทำไม `.join()` คืนค่าเป็น `thread::Result<T>` ไม่ใช่ `T` ตรง ๆ
  และรู้ว่าจะเกิดอะไรขึ้นถ้า**ไม่**เรียก `.join()` เลย (พิสูจน์ด้วยโค้ดจริงที่รันแล้วเห็นผลต่างชัดเจน)
- อธิบายได้ว่าทำไม `thread::spawn` ต้องการ closure ที่เป็น `'static` เสมอ อ่าน error message จริง **E0373**
  ("closure may outlive the current function") ออกได้ และแก้ไขด้วย `move` keyword ได้อย่างเข้าใจกลไกจริง ไม่ใช่
  แค่ "ใส่ `move` เพราะ compiler บอกให้ใส่"
- spawn หลาย thread พร้อมกันในลูป เก็บ `JoinHandle` ไว้ใน `Vec` แล้ว join ทั้งหมดทีหลัง — pattern ที่ใช้บ่อยที่สุด
  ในโค้ด concurrency ของ Rust จริง ๆ พร้อมดึงค่า return จากแต่ละ thread ผ่าน `JoinHandle<T>::join()`
- อธิบายได้ว่าเกิดอะไรขึ้นเมื่อ thread หนึ่ง panic (การ unwind ถูก "จับ" ไว้ที่ขอบของ thread นั้น ไม่ทำให้โปรแกรม
  ทั้งหมดล่ม) และเขียนโค้ดที่ handle `Err` จาก `.join()` ได้อย่างเหมาะสมโดยไม่ต้อง crash ทั้งโปรแกรม
- เข้าใจ**ขีดจำกัด**ของสิ่งที่บทนี้สอน: `thread::spawn` + `move` แก้ปัญหา "ownership ข้าม thread" ได้ แต่**ไม่ได้
  แก้ปัญหา** "หลาย thread ต้องแก้ไขข้อมูลชุดเดียวกันร่วมกัน" — เห็น compile error จริงตอนพยายามแชร์ mutable state
  แบบไร้เดียงสาข้าม thread และรู้ว่า Part 38 (channels) กับ Part 39 (`Mutex`/`Arc`) คือสองทางออกที่ต่างกัน
- ประยุกต์ทุกอย่างเขียนโปรแกรม **parallel chunk processing** จริง: แบ่งข้อมูลยอดขายออกเป็นหลายก้อน กระจายให้แต่ละ
  thread คำนวณผลรวมย่อยแบบ `move`, join ทุก thread, แล้วรวมผลลัพธ์เป็นยอดรวมสุดท้าย

## ความรู้ที่ต้องมีมาก่อน

- **Part 6 (Ownership เบื้องต้น)** และ **Part 7 (Borrowing และ References)**: หัวใจของบทนี้คือการนำกฎ ownership/
  borrowing แบบเดียวกันที่คุณรู้จักมาแล้วมาใช้ "ข้าม thread" — ทุกอย่างที่เคยเรียนเรื่อง move, borrow, lifetime,
  dangling reference จะกลับมาอีกครั้งในบริบทใหม่ ถ้ายังไม่แน่นเรื่องนี้ บทนี้จะยากขึ้นมากเพราะ error message
  ส่วนใหญ่ที่เจอในบทนี้คือ error ตัวเดิมจาก Part 6-7 ที่ compiler รายงานในสถานการณ์ที่ซับซ้อนขึ้น (ข้าม thread)
- **Part 24 (Closures)**: `thread::spawn()` รับ argument เป็น closure ที่ implement `FnOnce() -> T` โดยตรง —
  บทนี้จะใช้ความเข้าใจเรื่อง capture mode (`Fn`/`FnMut`/`FnOnce`) และเฉพาะเจาะจงที่สุดคือ **`move` keyword** จาก
  หัวข้อ 24.6 ที่ Part 24 เกริ่นไว้ตรง ๆ ว่า "ตัวอย่างคลาสสิกที่สุดที่ต้องใช้ `move` คือการส่ง closure เข้า thread
  ใหม่ ... รายละเอียดเต็มรูปแบบจะอยู่ใน Part 37" — นี่คือ Part 37 ที่ Part 24 พูดถึง เราจะปิดคำใบ้นั้นให้ครบในหัวข้อ
  37.4
- **Part 28 (Smart Pointers: Rc<T> และ RefCell<T>)**: บทนั้นสร้าง pattern `Rc<RefCell<T>>` สำหรับ "หลายเจ้าของที่
  แก้ไขข้อมูลร่วมกันได้" แบบ single-thread และบอกไว้ตรง ๆ ว่า **`Rc<T>` และ `RefCell<T>` ไม่ thread-safe เลย**
  เพราะตัวนับ/ตัวตรวจ borrow ภายในของมันไม่ได้ synchronize ข้าม thread — บทนี้จะพิสูจน์คำกล่าวนั้นด้วย compile
  error จริง (E0277) ในหัวข้อ 37.9 และ Part 39 จะแนะนำ `Arc<Mutex<T>>` เป็นเวอร์ชัน thread-safe ของ pattern
  เดียวกัน
- **Part 12 (Result<T,E> และ Error Handling)**: `.join()` คืนค่าเป็น `Result<T, E>` แบบเดียวกับที่เรียนมา
  (`thread::Result<T>` คือ type alias ของ `Result<T, Box<dyn Any + Send + 'static>>`) การ `match`, `.unwrap()`,
  `.expect()` ที่เรียนมาแล้วทั้งหมดใช้กับผลลัพธ์จาก `.join()` ได้ตรง ๆ ไม่มีอะไรใหม่ในส่วนนี้
- Part นี้เป็นบทแรกของ **arc concurrency ปิดโมดูล 2**: Part 37 (threads พื้นฐาน — บทนี้) → Part 38 (channels,
  message passing) → Part 39 (Mutex, Arc, shared-state concurrency) → Part 40 (Send, Sync และทำไมทุกอย่างในสาม
  บทนี้ compile ผ่านได้อย่างปลอดภัย) คุณยังไม่ต้องรู้เรื่อง channel หรือ Mutex มาก่อนเพื่ออ่านบทนี้ — บทนี้จะจบด้วย
  การเปิดปัญหาที่ยังแก้ไม่ได้ไว้ให้สองบทถัดไปมาปิดให้ครบ

## เนื้อหา

### 37.1 ทำไม Concurrency ถึง "อันตราย" ในภาษาส่วนใหญ่: Data Race คืออะไรกันแน่

ก่อนจะเขียน thread แรกของเรา ต้องเข้าใจก่อนว่าเรากำลังป้องกันอะไรอยู่ เพราะถ้าไม่เข้าใจปัญหา ทุกกฎที่ Rust บังคับใน
บทนี้จะดูเหมือน "ข้อจำกัดที่น่ารำคาญ" แทนที่จะเป็น "เกราะป้องกันที่ช่วยชีวิตเรา"

**นิยามที่แม่นยำของ data race** (ใช้กันทั่วไปในวงการ systems programming รวมถึงใน Rust reference เอง) คือ
สถานการณ์ที่เกิดขึ้นเมื่อครบทั้ง 3 เงื่อนไขนี้พร้อมกัน:

1. มี **สอง thread หรือมากกว่า** เข้าถึง**หน่วยความจำตำแหน่งเดียวกัน** (same memory location)
2. อย่างน้อย**หนึ่งใน**การเข้าถึงนั้นคือการ **เขียน** (write) ไม่ใช่แค่อ่าน
3. การเข้าถึงเหล่านั้น**ไม่มีการ synchronize กัน** (ไม่มี lock, ไม่มี atomic operation, ไม่มีกลไกใด ๆ ที่บังคับ
   ลำดับก่อน-หลังที่แน่นอน)

ถ้าครบทั้งสามข้อ ผลลัพธ์ของโปรแกรมจะ**ไม่แน่นอน** (undefined หรือ ไม่กำหนดชัดเจน) ขึ้นอยู่กับว่า OS scheduler
สลับการทำงานของแต่ละ thread ในจังหวะไหนพอดี ซึ่งอาจต่างกันไปทุกครั้งที่รัน ทุกเครื่อง ทุก build

**เหตุผลที่ข้อ 3 (ไม่ synchronize) เป็นตัวร้ายที่แท้จริง**: ถ้ามีแค่ thread เดียวเข้าถึงหน่วยความจำจุดนั้น หรือ
ทุก thread แค่**อ่าน**เฉย ๆ ไม่มีใครเขียน หรือมีการ synchronize กันอย่างถูกต้อง (เช่นผ่าน lock ที่จะเรียนใน Part
39) การเข้าถึงพร้อมกันแบบนั้น**ไม่เป็นปัญหาเลย** — ปัญหาเกิดขึ้นเฉพาะตอนที่ "การเขียน" กับ "การเขียนหรืออ่านอื่น ๆ"
ชนกันโดยไม่มีใครควบคุมลำดับ

#### Data Race ใน C/C++: Undefined Behavior ที่มองไม่เห็นตอน Compile

ในภาษา C/C++ การเขียนโค้ดที่มี data race **ไม่ใช่ compile error และไม่ใช่แม้แต่ runtime error ที่แน่นอน** —
มันคือ **undefined behavior (UB)** ตามมาตรฐานภาษา ซึ่งหมายความว่า compiler มีสิทธิ์ทำอะไรก็ได้กับโค้ดนั้น
(optimize จนพฤติกรรมเพี้ยนไปจากที่ตั้งใจ, ให้ผลลัพธ์ผิดแบบเงียบ ๆ, หรือ crash) ลองดูตัวอย่าง pseudocode สไตล์ C++
ที่คุ้นเคย (ไม่ใช่ syntax ที่เราจะ compile เพราะบทนี้เป็นเรื่อง Rust แต่เขียนให้เห็นภาพปัญหา):

```cpp
// ตัวอย่างเชิงแนวคิดสไตล์ C++ (ไม่ใช่โค้ดที่จะ compile ในบทนี้ แค่แสดงปัญหา)
int counter = 0;

void increment_many_times() {
    for (int i = 0; i < 100000; i++) {
        counter++; // อ่าน counter, บวก 1, เขียนกลับ -> ไม่ใช่ atomic operation เดียว!
    }
}

// สมมติสร้างสอง thread ที่เรียก increment_many_times() พร้อมกัน แล้วรอทั้งสองจบ
// ผลลัพธ์ที่ "คาดหวัง" คือ counter == 200000
// ผลลัพธ์จริงที่ได้: มักจะน้อยกว่า 200000 และไม่แน่นอนว่าจะได้เท่าไหร่ในแต่ละครั้งที่รัน
```

ปัญหาคือ `counter++` แม้จะดูเป็นบรรทัดเดียว แต่ในระดับเครื่องจริงมันคือ**สามขั้นตอน**: อ่านค่า `counter`
ปัจจุบันเข้า register, บวก 1 เข้า register นั้น, แล้วเขียนค่าใหม่กลับไปที่หน่วยความจำ ถ้าสอง thread ทำสามขั้นตอนนี้
สลับกันในจังหวะที่ไม่ดี (เช่น thread A อ่านค่า 5 ไปแล้ว ก่อนที่ thread A จะเขียนค่า 6 กลับไป thread B ก็อ่านค่า 5
ไปด้วย แล้วทั้งคู่เขียน 6 กลับไปพร้อมกัน — การเพิ่มค่าของ thread หนึ่ง "หายไป" เฉย ๆ) ผลคือ `counter` จะเพิ่มน้อยกว่า
ที่ควรจะเป็นแบบไม่แน่นอน และที่แย่กว่านั้นคือ **compiler ไม่เตือนอะไรเลยตอน compile** โค้ดนี้ compile ผ่านสบาย ๆ
100% ปัญหาจะโผล่มาแค่ "บางครั้ง" ตอน run จริงภายใต้ load สูง ๆ เท่านั้น — นี่คือ**สิ่งที่เรียกกันในวงการว่า
"Heisenbug"**: บั๊กที่พฤติกรรมเปลี่ยนไปทุกครั้งที่พยายามสังเกตหรือ debug มัน (เพิ่ม print statement เข้าไปเพื่อ
debug ก็เปลี่ยนจังหวะเวลาจนบั๊กหายไปเฉย ๆ ทำให้ตามหาสาเหตุยากมาก บางทีอยู่ใน production เป็นเดือน ๆ กว่าจะโผล่)

#### Data Race ในภาษาที่มี Garbage Collector (Java, Go, Python): ปลอดภัยกว่าแต่ก็ไม่ป้องกัน

ภาษาที่มี garbage collector อย่าง Java หรือ Go **ไม่มี undefined behavior แบบ C/C++** เวลาเจอ data race (จะไม่
ทำให้เกิด memory corruption ระดับ raw pointer เพราะไม่มี raw pointer ให้เพี้ยน) แต่ก็**ไม่ได้ป้องกัน data race
เลย** — โปรแกรมยังคง compile ผ่านได้ปกติแม้จะมีหลาย thread/goroutine แก้ไขตัวแปรร่วมกันโดยไม่มี lock ผลลัพธ์คือค่า
ที่ผิดเพี้ยนแบบเดียวกับตัวอย่าง C++ ข้างบน (ค่านับผิด, ข้อมูลไม่ตรงกัน) เพียงแต่ไม่ crash แบบรุนแรงเท่า — Python
มี Global Interpreter Lock (GIL) ที่ป้องกัน byte-code หลายอันชนกันได้ในระดับหนึ่ง แต่ก็ยังเกิด race condition ใน
ระดับ logic ของแอปพลิเคชันได้อยู่ดี (เช่น เช็คแล้วค่อยเขียนสองขั้นตอนที่ไม่ atomic กัน) ทุกภาษาที่กล่าวมาปล่อยให้
**ผู้เขียนโค้ดต้องจำเอาเองว่าตรงไหนต้อง lock** — compiler ไม่ช่วยตรวจสอบให้เลยไม่ว่าภาษาไหนก็ตาม

#### Rust: "Fearless Concurrency" — คำกล่าวอ้างที่ใหญ่มาก และเราจะพิสูจน์มันทีละขั้น

Rust ใช้คำว่า **"fearless concurrency"** (concurrency แบบไม่ต้องกลัว) เป็นหนึ่งในจุดขายหลักของภาษา คำกล่าวอ้างนี้
ใหญ่กว่าที่คิด: มันบอกว่า **กฎ ownership และ borrowing แบบเดียวกันที่คุณเรียนมาตั้งแต่ Part 6-7 (ที่ป้องกัน
use-after-free, dangling reference, และ "ยืมพร้อมกันได้หลายที่แต่แก้ไขได้แค่ที่เดียว" ตอน compile time) จะป้องกัน
data race ตอน compile time ได้ด้วยเช่นกัน** — ไม่ต้องมี garbage collector, ไม่ต้องมี runtime race detector,
ไม่ต้องพึ่งวินัยของผู้เขียนโค้ดว่าจะจำ lock ครบทุกจุดหรือไม่ **compiler จะปฏิเสธไม่ยอม compile โค้ดที่มี data race
ที่อาจเกิดขึ้นได้ตั้งแต่แรก**

นี่คือความต่างที่สำคัญมากเมื่อเทียบกับภาษาที่กล่าวมาทั้งหมด: C/C++ เจอ data race แล้วคือ UB (อันตรายที่สุด),
Java/Go/Python เจอ data race แล้วคือค่าผิดเพี้ยนแบบ silent bug (ไม่ crash ทันทีแต่ผลลัพธ์เชื่อไม่ได้), ส่วน Rust
เจอโค้ดที่**มีความเป็นไปได้**ที่จะเกิด data race แล้วคือ **compile error** — โปรแกรมที่มีปัญหานี้จะไม่มีทาง
สร้าง binary ออกมาได้เลยตั้งแต่ต้น

คำกล่าวอ้างนี้ฟังดูเหลือเชื่อถ้าพูดลอย ๆ แบบนี้ — งั้นเราจะไม่พูดลอย ๆ อีกต่อไป ตลอดบทนี้เราจะ**พิสูจน์**มันด้วยโค้ด
จริงทีละขั้น: หัวข้อ 37.5 จะแสดง compile error จริง (E0373) ตอนพยายามส่ง reference ที่อาจ dangling ข้าม thread
และหัวข้อ 37.10 จะแสดง compile error จริงอีกชุด (E0373, E0499, E0277) ตอนพยายามแชร์ข้อมูลที่แก้ไขได้ข้าม thread
แบบไม่ปลอดภัย — ทุก error ที่เจอในบทนี้คือกลไกป้องกันที่ทำงานจริง ไม่ใช่แค่ทฤษฎี

#### เปรียบเทียบสรุป: แต่ละภาษาจัดการปัญหา Data Race อย่างไร

เพื่อให้เห็นภาพรวมชัดเจนก่อนลงมือเขียนโค้ด Rust จริง มาสรุปเปรียบเทียบแนวทางของภาษาหลัก ๆ ที่ใช้เขียนโปรแกรม
concurrent กันเป็นตาราง (คุณไม่จำเป็นต้องรู้จักภาษาเหล่านี้มาก่อนเพื่อเข้าใจตาราง — จุดสำคัญคือดูคอลัมน์ "ใครเป็นคน
รับผิดชอบป้องกัน data race" กับ "เมื่อไหร่ที่ปัญหาจะถูกจับได้"):

| ภาษา | โมเดล thread | ใครรับผิดชอบป้องกัน data race | เมื่อไหร่ที่ปัญหาจะถูกจับได้ |
|---|---|---|---|
| **C / C++** | OS thread จริง (`pthread`, `std::thread`) | ผู้เขียนโค้ด 100% — ภาษาไม่ช่วยตรวจสอบให้เลย | ไม่แน่นอน — อาจไม่โผล่เลยในการทดสอบ แล้วมาพังใน production (UB) |
| **Java** | OS thread จริง (`java.lang.Thread`) พร้อม `synchronized`/`volatile` ให้เลือกใช้ | ผู้เขียนโค้ด — ภาษาให้เครื่องมือ (`synchronized`) แต่ไม่บังคับให้ใช้ตรงจุดที่จำเป็น | Runtime — ค่าที่ผิดเพี้ยนแบบ silent bug ไม่ crash ทันที (ยกเว้นบางกรณีที่ throw `ConcurrentModificationException`) |
| **Go** | Goroutine (thread น้ำหนักเบาที่ runtime จัดสรรลง OS thread ให้เอง) พร้อม channel เป็นแนวทางหลัก | ผู้เขียนโค้ด — แต่ Go มี `go run -race` (race detector) ช่วยตรวจตอน**ทดสอบ**เท่านั้น ไม่ใช่ตอน compile | Runtime ระหว่างทดสอบด้วย race detector เท่านั้น — โค้ด production ที่ไม่เคยรันผ่าน race detector มาก่อนอาจมีบั๊กซ่อนอยู่ |
| **Python** | OS thread จริง แต่มี Global Interpreter Lock (GIL) คุม bytecode ระดับต่ำ | ผู้เขียนโค้ด — GIL ป้องกันบางกรณีได้เอง (เช่น `list.append` เดี่ยว ๆ) แต่ไม่ป้องกัน race condition ระดับ logic ของแอป (เช่น เช็คแล้วค่อยเขียนหลายขั้นตอน) | Runtime — ค่าผิดเพี้ยนแบบ silent bug เหมือนภาษาอื่นที่ไม่มี compile-time check |
| **Rust** | OS thread จริง (`std::thread::spawn`) — บทนี้จะพิสูจน์ทุกขั้น | **Compiler** — ผ่านกฎ ownership/borrowing (Part 6-7) และ trait `Send`/`Sync` (Part 40) | **Compile time** — โค้ดที่มีความเป็นไปได้จะเกิด data race ไม่มีทาง compile ผ่านได้เลย |

สังเกตคอลัมน์ขวาสุด — Rust เป็นภาษาเดียวในตารางนี้ที่ปัญหาถูกจับได้ **ตอน compile time** แทนที่จะเป็น "ตอนทดสอบ"
(Go ด้วย race detector ซึ่งต้องเปิดใช้เองและอาจไม่ครอบคลุมทุก code path ที่ทดสอบ) หรือ "ตอน production" (ภาษาอื่น
ทั้งหมด) — ความแตกต่างนี้สำคัญมากในทางปฏิบัติ เพราะ **error ที่ compiler จับได้ คือ error ที่คุณเห็น 100% ของเวลา
ที่คุณ build โค้ด** ในขณะที่ error ที่จับได้แค่ "ตอนทดสอบ" หรือ "ตอน production" คือ error ที่คุณเห็น**เฉพาะตอนที่
จังหวะเวลาบังเอิญทำให้มันโผล่มา** ซึ่งเป็นสิ่งที่ควบคุมไม่ได้และคาดเดาไม่ได้เลย — นี่คือน้ำหนักที่แท้จริงของคำว่า
"fearless concurrency"

### 37.2 `std::thread::spawn()`: สร้าง Thread แรกของคุณ

มาเริ่มเขียนโค้ดจริงกัน ฟังก์ชันหลักที่ใช้สร้าง thread ใหม่ใน Rust คือ `std::thread::spawn()` ซึ่งมี signature
ประมาณนี้ (คัดลอกมาจาก standard library ตรง ๆ เพียงแต่เติม body ปลอมด้วย `unimplemented!()` เพื่อให้ snippet นี้
compile ผ่านได้ในตัวมันเอง — ตัว implementation จริงอยู่ใน std library):

```rust
use std::thread::JoinHandle;

pub fn spawn<F, T>(f: F) -> JoinHandle<T>
where
    F: FnOnce() -> T,
    F: Send + 'static,
    T: Send + 'static,
{
    let _ = f; // ในความเป็นจริง compiler จะเรียก f() บน thread ใหม่ — ที่นี่แค่แสดง signature เฉย ๆ
    unimplemented!()
}
```

อ่าน signature นี้ทีละส่วน (คุณคุ้นเคยกับ generic bound แบบนี้มาแล้วตั้งแต่ Part 18, 22):

- **`f: F`** — พารามิเตอร์ตัวเดียวที่ `spawn` รับคือ closure (หรือ function pointer ก็ได้ เพราะ `fn` ธรรมดาก็
  implement `FnOnce` ได้เช่นกัน) ที่จะถูกรันบน thread ใหม่
- **`F: FnOnce() -> T`** — closure นั้นต้อง implement `FnOnce() -> T` เชื่อมตรงกับ Part 24: มันคือ closure ที่รับ
  **ไม่มี parameter เลย** และคืนค่ากลับมาเป็น type `T` อะไรก็ได้ (`()` ถ้าไม่ return อะไรเลย, หรือค่าจริงอย่าง
  `i32`, `String`, ฯลฯ) การที่ bound เป็น `FnOnce` (ผ่อนคลายที่สุดในสามตัวตามลำดับชั้นที่เรียนใน 24.5.5) หมายความ
  ว่า `spawn` **เรียก closure นี้แค่ครั้งเดียวเท่านั้น** — สมเหตุสมผลเพราะ thread แต่ละตัวก็รันงานของมันแค่ครั้ง
  เดียวจบ ไม่ใช่ถูกเรียกซ้ำหลายรอบแบบ callback
- **`F: Send + 'static`** และ **`T: Send + 'static`** — สอง bound นี้คือหัวใจของบทนี้ (`Send` จะเรียนเต็มรูปแบบ
  ใน Part 40 ตอนนี้ให้เข้าใจแบบคร่าว ๆ ว่ามันคือ "ปลอดภัยที่จะย้ายค่าไปทำงานบน thread อื่น") ส่วน **`'static`** คือ
  ตัวที่เราจะเจาะลึกในหัวข้อ 37.4 — มันคือที่มาของ error E0373 ที่มือใหม่ทุกคนต้องเจอตอนเริ่มเขียน thread ครั้งแรก

**ค่าที่ `spawn()` คืนกลับมา** คือ **`JoinHandle<T>`** — มันไม่ใช่ผลลัพธ์ของ closure ตรง ๆ (closure ยังไม่ได้ทำงาน
เสร็จตอนที่ `spawn()` return ด้วยซ้ำ เพราะ thread ใหม่ทำงาน**คู่ขนาน**กับ thread ที่เรียก `spawn()`) แต่คือ **"มือจับ"
(handle)** ที่ใช้อ้างอิงถึง thread ที่กำลังทำงานอยู่นั้น เอาไว้ใช้รอผลลัพธ์ (`.join()`) ทีหลัง

ลองดูตัวอย่างที่ง่ายที่สุดก่อน:

```rust
use std::thread;

fn main() {
    let handle = thread::spawn(|| {
        for i in 1..=3 {
            println!("thread ลูก: กำลังทำงานรอบที่ {i}");
        }
        println!("thread ลูก: ทำงานเสร็จแล้ว");
    });

    println!("thread หลัก: สร้าง thread ลูกเรียบร้อย กำลังรอด้วย join()");
    handle.join().unwrap();
    println!("thread หลัก: join() คืนค่าแล้ว โปรแกรมจบการทำงาน");
}
```

รันจริงได้ผลลัพธ์นี้ (รันซ้ำหลายครั้งได้ผลเหมือนกันทุกครั้ง เพราะเราเรียก `.join()` ทันทีหลัง print บรรทัดเดียว
ก่อนที่ thread ลูกจะมีโอกาสแทรกคิวมาพิมพ์อะไรก่อนได้ทัน):

```
thread หลัก: สร้าง thread ลูกเรียบร้อย กำลังรอด้วย join()
thread ลูก: กำลังทำงานรอบที่ 1
thread ลูก: กำลังทำงานรอบที่ 2
thread ลูก: กำลังทำงานรอบที่ 3
thread ลูก: ทำงานเสร็จแล้ว
thread หลัก: join() คืนค่าแล้ว โปรแกรมจบการทำงาน
```

สังเกตว่า `thread::spawn(...)` **คืนค่ากลับมาทันที** ไม่รอให้ closure ข้างในทำงานจบก่อน — บรรทัด `println!` ของ
thread หลัก (`สร้าง thread ลูกเรียบร้อย...`) พิมพ์ออกมาก่อนที่ thread ลูกจะพิมพ์อะไรเลยด้วยซ้ำ เพราะ OS ต้องใช้เวลา
เล็กน้อยในการสร้าง thread ใหม่ขึ้นมาจริง ๆ ก่อนที่มันจะเริ่มรันโค้ดข้างใน — นี่คือธรรมชาติของ **concurrency**:
สอง thread ทำงาน**คู่ขนานกัน** (หรืออย่างน้อยก็ "สลับกันทำงาน" ถ้า CPU มี core ไม่พอ) ไม่ใช่ทำงานทีละบรรทัดตามลำดับ
เหมือนโค้ดปกติที่เราเขียนกันมาตลอดหลักสูตรนี้

**closure ที่ไม่รับ parameter ใน `spawn`**: สังเกตว่า closure ที่ส่งเข้า `thread::spawn` เขียนเป็น `|| { ... }`
— pipe คู่ที่ไม่มีอะไรอยู่ระหว่างกลาง หมายถึง closure ที่ไม่รับ parameter เลย ตรงกับ `FnOnce()` ใน signature
(วงเล็บว่าง) ตรงกับที่เรียนมาตั้งแต่ Part 24 ว่า pipe `| |` คือที่สำหรับใส่ parameter ของ closure — ถ้าไม่มี
parameter ก็ปล่อยว่างไว้แค่นั้น

#### `thread::spawn` สร้าง OS Thread จริงหนึ่งตัว: ต้นทุนที่ควรรู้

จุดที่สำคัญมากและมักถูกมองข้าม: `std::thread::spawn()` สร้าง **thread จริงในระดับ operating system** (เรียกว่า
โมเดล **"1:1 threading"** — หนึ่ง thread ของภาษาตรงกับหนึ่ง thread ของ OS เป๊ะ ๆ ต่างจากภาษาอย่าง Go ที่ goroutine
เป็น thread น้ำหนักเบาที่ runtime ของภาษาจัดสรรลง OS thread ที่มีจำนวนน้อยกว่าอีกทีหนึ่ง) การสร้าง OS thread มี
**ต้นทุนจริง**ที่ไม่ใช่ศูนย์: ต้องขอ stack memory ก้อนใหม่จาก OS (ปกติหลาย KB ถึงไม่กี่ MB), ต้องให้ OS scheduler
มาลงทะเบียน thread ใหม่ไว้ และการสลับ (context switch) ระหว่าง thread ก็มีต้นทุนของมันเองเช่นกัน

**ความหมายเชิงปฏิบัติ**: การ spawn thread เหมาะกับงานที่ **มีขนาดใหญ่พอที่จะคุ้มกับต้นทุนการสร้าง thread** (เช่น
ตัวอย่าง chunk processing ในหัวข้อ 37.11 ที่แต่ละ thread ประมวลผลข้อมูลหลายรายการ) แต่ **ไม่เหมาะกับการ spawn
thread ใหม่ทุกครั้งสำหรับงานเล็ก ๆ ในลูปที่ทำงานถี่มาก** (เช่น spawn thread ใหม่ทุกครั้งที่มีการคลิกปุ่ม หรือทุก
ครั้งที่ประมวลผลข้อมูล 1 รายการ) เพราะต้นทุนการสร้าง/ทำลาย thread จะสูงกว่าประโยชน์ที่ได้จากการทำงานคู่ขนานเสียอีก
— situation แบบนี้คือที่มาของแนวคิด **thread pool** (สร้าง thread จำนวนคงที่ไว้ล่วงหน้า แล้วแจกงานให้ทำซ้ำ ๆ
ไม่ต้องสร้างใหม่ทุกครั้ง) ซึ่งเป็นรากฐานสำคัญของ async runtime อย่าง Tokio ที่จะเรียนใน Part 46-50 — Tokio ใช้
thread pool ขนาดเล็กจำนวนคงที่ (เรียกว่า worker thread) รัน "งาน" (task) น้ำหนักเบาจำนวนมากได้พร้อมกัน แทนที่จะ
สร้าง OS thread ใหม่สำหรับทุกงาน

#### รู้จำนวน CPU ที่มีจริงด้วย `thread::available_parallelism()`

คำถามที่ตามมาโดยธรรมชาติคือ "แล้วควร spawn กี่ thread ดี?" — คำตอบมาตรฐานคือ **ให้ใกล้เคียงกับจำนวน logical CPU
core ที่เครื่องมีจริง** (spawn มากกว่านั้นแทบไม่ได้ประโยชน์เพิ่มสำหรับงานที่ใช้ CPU หนัก เพราะ CPU core มีจำกัด
thread ส่วนเกินก็แค่ผลัดกันรอ CPU) ตั้งแต่ Rust 1.59 มีฟังก์ชัน `std::thread::available_parallelism()` ให้ใช้
โดยตรง:

```rust
use std::thread;

fn main() {
    let cores = thread::available_parallelism()
        .map(|n| n.get())
        .unwrap_or(1); // ถ้า query ไม่ได้ (เช่นบางระบบที่ sandbox ไว้) ให้ fallback เป็น 1 อย่างปลอดภัย

    println!("จำนวน logical CPU ที่ระบบมองเห็น: {cores}");
}
```

รันจริงบนเครื่องที่ใช้เขียนบทนี้ได้ผลลัพธ์ (ตัวเลขจะต่างกันไปตามเครื่องของคุณเองอย่างแน่นอน — นี่คือค่าที่ขึ้นกับ
hardware จริง ไม่ใช่ค่าคงที่):

```
จำนวน logical CPU ที่ระบบมองเห็น: 4
```

`available_parallelism()` คืนค่าเป็น `Result<NonZeroUsize, std::io::Error>` (อาจ error ได้ในบางระบบที่ query
ไม่สำเร็จ เช่น container ที่ตั้งค่า CPU affinity แปลก ๆ) — นี่คือเหตุผลที่โค้ดข้างบนใช้ `.map(|n| n.get())` แปลง
`NonZeroUsize` เป็น `usize` ธรรมดา แล้ว `.unwrap_or(1)` เป็น fallback ที่ปลอดภัยเสมอ (อย่างน้อยก็มี 1 core ที่
ทำงานได้แน่ ๆ) เราจะกลับมาใช้ฟังก์ชันนี้จริงในตัวอย่างใหญ่ของหัวข้อ 37.11 เพื่อเลือกจำนวน thread แบบไดนามิกตาม
เครื่องที่รันจริง แทนที่จะ hardcode ตัวเลขคงที่ไว้

#### `thread::Builder`: ตั้งชื่อ Thread และปรับแต่งค่าอื่น ๆ

`thread::spawn()` ที่ใช้มาตลอดบทนี้จริง ๆ แล้วเป็นแค่ **shortcut ที่สะดวก** ของ API ที่ยืดหยุ่นกว่าอีกตัวคือ
**`thread::Builder`** — ใช้เมื่อต้องการปรับแต่งค่าเพิ่มเติม เช่น **ตั้งชื่อ thread** (มีประโยชน์มากตอน debug หรือ
อ่าน panic message เพราะชื่อ thread จะโผล่ในข้อความ panic ด้วย) หรือกำหนดขนาด stack เอง:

```rust
use std::thread;

fn main() {
    let builder = thread::Builder::new().name("worker-1".to_string());

    let handle = builder
        .spawn(|| {
            let current = thread::current();
            println!("กำลังรันบน thread ชื่อ: {:?}", current.name());
        })
        .expect("สร้าง thread ไม่สำเร็จ");

    handle.join().unwrap();
}
```

```
กำลังรันบน thread ชื่อ: Some("worker-1")
```

สังเกตความต่างสำคัญ: **`Builder::spawn()` คืนค่าเป็น `io::Result<JoinHandle<T>>`** (ไม่ใช่ `JoinHandle<T>` ตรง ๆ
แบบ `thread::spawn()`) เพราะการสร้าง thread ผ่าน `Builder` **อาจล้มเหลวได้จริง** ในระดับ OS (เช่น ระบบมี thread
ทำงานอยู่มากเกินไปจนไม่มี resource เหลือให้สร้างใหม่) — `thread::spawn()` ธรรมดาจัดการกรณีนี้ให้ด้วยการ `panic!`
โดยอัตโนมัติถ้าสร้าง thread ไม่สำเร็จ (สะดวกสำหรับกรณีทั่วไปที่ไม่คาดว่าจะล้มเหลว) แต่ `Builder::spawn()` ให้คุณ
`match` หรือ `.expect()` จัดการกรณีล้มเหลวได้ตรง ๆ ด้วยตัวเอง เหมาะกับโปรแกรมที่ต้องทนทานต่อความล้มเหลวระดับ
ระบบปฏิบัติการจริง ๆ — สำหรับตัวอย่างส่วนใหญ่ในบทนี้ที่ไม่ต้องปรับแต่งอะไรพิเศษ `thread::spawn()` ธรรมดาก็เพียงพอ
และกระชับกว่า

### 37.3 `.join()`: รอให้ Thread ลูกทำงานจบ — และสิ่งที่เกิดขึ้นถ้าไม่เรียกมันเลย

`.join()` เป็น method ของ `JoinHandle<T>` มี signature ประมาณนี้ (จำลอง `JoinHandle<T>` แบบง่าย ๆ ขึ้นมาเองในตัวอย่าง
นี้เพื่อให้ signature ของ `join` compile ผ่านได้ในตัวมันเอง — struct จริงใน std ซับซ้อนกว่านี้มาก แต่ signature ของ
`join` เหมือนกันเป๊ะ):

```rust
use std::thread;

struct JoinHandle<T>(std::marker::PhantomData<T>);

impl<T> JoinHandle<T> {
    pub fn join(self) -> thread::Result<T> {
        unimplemented!()
    }
}
```

สังเกตว่า `join` รับ `self` แบบ **by value** (ไม่ใช่ `&self`) — หมายความว่าเรียก `.join()` ได้**ครั้งเดียว**เท่านั้น
ต่อ `JoinHandle` หนึ่งตัว (การเรียกจะ move ตัว handle ไปใช้จนหมด) สมเหตุสมผลเพราะ thread หนึ่งตัวก็จบการทำงานแค่
ครั้งเดียว ไม่มีอะไรให้ join ซ้ำสองครั้ง

**`.join()` ทำสองอย่างพร้อมกัน**: (1) **บล็อก (block)** ให้ thread ที่เรียกมันหยุดรอ จนกว่า thread ลูกจะทำงานจบ
จริง ๆ (ไม่ใช่แค่ "เช็คว่าจบหรือยัง" แบบ non-blocking) และ (2) **คืนค่าผลลัพธ์**ของ closure ที่ thread ลูกรันไป
กลับมาให้ ถ้า thread ลูกจบแบบปกติ (ไม่ panic)

#### ทำไมถ้าไม่ Join Thread ลูกอาจถูก "ตัดจบ" กลางทาง

นี่คือจุดที่มือใหม่มักไม่ทันคิดถึง: **thread ลูกที่ spawn ออกไปมี "อายุ" ที่เป็นอิสระจากใครเลย** — มันไม่ผูกกับ
scope ของฟังก์ชันที่ spawn มันขึ้นมา ตัวโปรแกรม Rust ทั้งโปรแกรมจะจบก็ต่อเมื่อ **`main()` return** (ธรรมดาเหมือน
โปรแกรมทั่วไปในทุกภาษา) — และเมื่อ `main()` จบ **ทุก thread ที่ยังทำงานไม่เสร็จจะถูกตัดจบไปเฉย ๆ ทันที** ไม่ว่ามัน
จะทำงานไปถึงไหนแล้วก็ตาม เหมือนกับที่หลาย OS ฆ่า process ลูกทั้งหมดทันทีที่ process หลักจบการทำงาน

ลองดูตัวอย่างที่พิสูจน์เรื่องนี้ให้เห็นชัด ๆ — spawn thread ที่ตั้งใจพิมพ์ 5 รอบโดยหยุดรอสั้น ๆ ระหว่างรอบ (ใช้
`thread::sleep` ซึ่งจะอธิบายเต็มรูปแบบในหัวข้อ 37.6) แต่ thread หลัก**ไม่เรียก `.join()` เลย**:

```rust
use std::thread;
use std::time::Duration;

fn main() {
    thread::spawn(|| {
        for i in 1..=5 {
            println!("thread ลูก: กำลังทำงานรอบที่ {i}");
            thread::sleep(Duration::from_millis(1));
        }
        println!("thread ลูก: ทำงานเสร็จสมบูรณ์ครบ 5 รอบ");
    });

    println!("thread หลัก: ทำงานจบแล้ว ไม่ได้เรียก join() เลย");
    // main จบตรงนี้ -> โปรแกรมทั้งหมดอาจจบก่อน thread ลูกทำงานครบ
}
```

รันโค้ดนี้จริง 5 ครั้งติดกันบนเครื่องที่ใช้เขียนบทนี้ ได้ผลลัพธ์**เหมือนกันทุกครั้ง**:

```
thread หลัก: ทำงานจบแล้ว ไม่ได้เรียก join() เลย
```

สังเกตว่า **ไม่มีบรรทัดของ thread ลูกโผล่มาเลยแม้แต่บรรทัดเดียว** — ไม่ใช่ 5 บรรทัดตามที่ตั้งใจ ไม่ใช่แม้แต่
1 บรรทัด! เหตุผลคือ: `thread::spawn()` คืนค่ากลับมาแทบจะทันที (การสร้าง thread ใหม่ในระดับ OS ใช้เวลาน้อยมากแต่ก็
ไม่ใช่ศูนย์) จากนั้น `main()` ก็พิมพ์บรรทัดของตัวเองแล้ว **return ทันที** — เร็วกว่าที่ thread ลูกจะได้เริ่มรันโค้ด
ข้างในด้วยซ้ำ (thread ลูกยังไม่ทันได้พิมพ์รอบแรกเลย เพราะมันต้องรอ OS scheduler จัดสรร CPU ให้ก่อน) เมื่อ `main`
จบ ทั้งโปรแกรม (รวมถึง thread ลูกที่ยังไม่ทันเริ่ม) ก็ถูกปิดไปพร้อมกันทั้งหมด

> **สำคัญ**: ผลลัพธ์นี้**ไม่ใช่ 100% แน่นอนตามกฎภาษา** — มันขึ้นอยู่กับ OS scheduler ว่าจะให้ thread ไหนได้ทำงาน
> ก่อนในทางเทคนิค แต่ในทางปฏิบัติแทบทุกครั้ง (และในการทดสอบจริงของบทนี้คือ 5 ใน 5 ครั้ง) thread หลักที่ทำงานสั้น ๆ
> แค่ print บรรทัดเดียวแล้ว return จะจบเร็วกว่า thread ลูกที่ต้อง sleep รอ เสมอ นี่คือเหตุผลว่าทำไมบั๊กแบบนี้
> อันตรายมาก: มันดู "ทำงานได้" ในการทดสอบสั้น ๆ บางครั้ง (ถ้า thread ลูกเบามากจนทำเสร็จก่อน main จบพอดี) แต่จะ
> เสียข้อมูลแบบไม่แน่นอนใน production จริง

ทีนี้เพิ่ม `.join()` เข้าไปให้ครบ:

```rust
use std::thread;
use std::time::Duration;

fn main() {
    let handle = thread::spawn(|| {
        for i in 1..=5 {
            println!("thread ลูก: กำลังทำงานรอบที่ {i}");
            thread::sleep(Duration::from_millis(1));
        }
        println!("thread ลูก: ทำงานเสร็จสมบูรณ์ครบ 5 รอบ");
    });

    println!("thread หลัก: ทำงานจบแล้ว กำลังรอ thread ลูกด้วย join()");
    handle.join().unwrap();
    println!("thread หลัก: thread ลูกจบแล้วจริง ๆ โปรแกรมปิดได้อย่างปลอดภัย");
}
```

บรรทัดสุดท้ายและไม่ให้ `main` return) จนกว่า thread ลูกจะทำงานจบสมบูรณ์จริง ๆ **นี่คือเหตุผลเชิงปฏิบัติที่สำคัญ
ที่สุดว่าทำไมควรเรียก `.join()` เกือบทุกครั้งที่ spawn thread** — ไม่ใช่แค่ "ธรรมเนียมที่ดี" แต่คือการันตีว่าผลลัพธ์
ของงานที่ thread ลูกทำจะถูกใช้ครบถ้วนก่อนโปรแกรมจบจริง

### 37.4 `thread::Result<T>`: กลไกจับ Panic ข้าม Thread Boundary (เกริ่นก่อน เจาะลึกในหัวข้อ 37.7)

สังเกตว่าตัวอย่างข้างบนเรียก `handle.join().unwrap()` — ทำไมต้อง `.unwrap()` ทั้งที่ตัวอย่างแรกในหัวข้อ 37.2 ก็
เรียกแบบเดียวกัน? เพราะ `.join()` **ไม่คืนค่า `T` ตรง ๆ** แต่คืนค่าเป็น:

```rust
type Result<T> = std::result::Result<T, Box<dyn std::any::Any + Send + 'static>>;
```

(นี่คือ `std::thread::Result<T>` — type alias ที่ประกาศไว้ใน module `std::thread` ไม่ใช่ `std::result::Result`
ตัวที่เราคุ้นเคยมาตั้งแต่ Part 12 ตรง ๆ แต่เป็น `Result<T, E>` ตัวเดิมนั้นแหละ เพียงแค่ล็อก `E` ไว้เป็น
`Box<dyn Any + Send + 'static>` ให้เฉพาะเจาะจงสำหรับบริบทของ thread)

เหตุผลที่ `E` เป็น `Box<dyn Any + Send + 'static>` (ไม่ใช่ error type ปกติแบบที่เรียนใน Part 12) คือ **`.join()`
ไม่ได้ใช้แทน error handling ปกติของโปรแกรม — มันคือกลไกรายงานว่า "thread ลูก panic หรือไม่"** ถ้า thread ลูกทำงาน
จบแบบปกติ (ไม่ panic) `.join()` คืนค่า `Ok(T)` ที่มีผลลัพธ์จริงของ closure อยู่ข้างใน แต่ถ้า thread ลูก **panic**
กลางทาง (เช่นเรียก `.unwrap()` บน `None`, index array เกินขอบ, `panic!()` ตรง ๆ) `.join()` จะคืนค่า `Err(...)`
ที่เก็บ **payload ของ panic นั้นไว้** (ส่วนใหญ่คือ error message ที่ห่อด้วย `Box<dyn Any>` เพราะ payload ของ
panic อาจเป็น type อะไรก็ได้ ไม่จำกัดแค่ `String`)

นี่คือสิ่งที่เรียกว่า **panic เป็น "จับได้" ที่ขอบของ thread** — จำได้จาก Part 12 ว่า panic ปกติจะ **unwind stack**
ไปเรื่อย ๆ จนถึงจุดที่ไม่มีอะไรจับมันไว้ แล้วปิดโปรแกรมทั้งหมด แต่เมื่อ panic เกิดขึ้น**ภายใน thread ที่ spawn ไว้**
runtime ของ Rust จะ unwind stack ของ**เฉพาะ thread นั้น**เท่านั้น (ไม่ลามไปยัง thread อื่น) แล้ว**แปลง panic นั้น
เป็นค่า `Err`** ที่ส่งกลับมาให้ผ่าน `.join()` — thread อื่น ๆ รวมถึง thread หลักยังทำงานต่อได้ตามปกติ **ไม่ crash
ตามไปด้วย** เราจะเห็นตัวอย่างที่รันได้จริงเต็มรูปแบบในหัวข้อ 37.7 ตอนนี้ให้จำไว้ก่อนว่า **`.unwrap()` บน
`.join()` เป็นการบอกว่า "ถ้า thread ลูก panic ให้ panic ตามไปด้วยเลย"** — ซึ่งบางครั้งเหมาะสม (เช่นตัวอย่างสั้น ๆ
ในบทนี้ที่ไม่คาดหวังให้ panic เกิดขึ้นเลย) แต่ในโปรแกรมจริงที่ต้องการความทนทาน ควร `match` หรือจัดการ `Err` แบบ
สุภาพกว่านั้น

### 37.5 `'static` Bound และปัญหาคลาสสิก: ทำไมต้อง `move` เมื่อ Spawn Thread

ตอนนี้เรามาถึงจุดสำคัญที่สุดของบทนี้ — จุดที่ Part 24 เกริ่นทิ้งไว้ให้เราปิดให้ครบ

#### ทวนความจำ: `'static` Bound คืออะไร

จาก signature ของ `thread::spawn` ในหัวข้อ 37.2 เราเห็น bound `F: Send + 'static` — closure ที่ส่งเข้าไปต้อง
**เป็น `'static`** สังเกตว่านี่ไม่ใช่ lifetime ของ**ค่าที่ closure ยืมมา** (แบบ `'a` ที่เรียนใน Part 20/23) แต่
เป็นเงื่อนไขว่า **closure ทั้งก้อนต้องไม่มี reference ที่ชี้ไปยังอะไรที่มีอายุสั้นกว่าโปรแกรมทั้งหมด** — พูดง่าย ๆ
คือ **closure ที่ส่งเข้า `thread::spawn` ต้องไม่ "ยืม" (borrow) อะไรจาก scope ที่มันถูกสร้างขึ้นมาเลย** ต้องเป็น
เจ้าของข้อมูลทุกอย่างที่มันใช้ (หรือใช้ข้อมูลที่มีอายุยาวเท่าโปรแกรมจริง ๆ เช่น string literal `&'static str`)

**เหตุผลว่าทำไม Rust ต้องบังคับกฎนี้อย่างเข้มงวด**: thread ลูกที่ spawn ออกไปมี**อายุที่เป็นอิสระ**จาก thread ที่
spawn มันขึ้นมา (ตามที่อธิบายไว้ในหัวข้อ 37.3) — compiler **ไม่มีทางรู้ล่วงหน้า**ว่า thread หลักจะเรียก `.join()`
เมื่อไหร่ (หรือจะเรียกเลยหรือไม่) เทียบกับ thread ลูกจะทำงานจบตอนไหน ทั้งสองเป็นไปได้ทั้งคู่: thread หลักอาจจบ
ก่อน thread ลูก (แบบที่เห็นในหัวข้อ 37.3) หรือ thread ลูกอาจจบก่อนก็ได้ — ถ้า closure ของ thread ลูก**ยืม** ตัวแปร
local จาก scope ของ thread หลัก (เช่น `&Vec<i32>` ที่ชี้กลับไปยัง `Vec` ใน `main`) แล้ว scope นั้นจบไปก่อน (ตัวแปร
ต้นทางถูก `drop`) ก่อนที่ thread ลูกจะได้ใช้ reference นั้น — reference นั้นจะกลายเป็น **dangling reference** ที่
ชี้ไปยังหน่วยความจำที่ถูกคืนไปแล้ว ทันทีที่ thread ลูกพยายามอ่านมัน นี่คือ **use-after-free ข้าม thread** ซึ่ง
อันตรายไม่ต่างจาก use-after-free แบบ single-thread ที่ borrow checker ป้องกันมาตั้งแต่ Part 6-7 — เพียงแต่ตอนนี้
มันเกิดข้าม thread และ compiler **ไม่สามารถพิสูจน์ได้แน่ชัดว่า thread ลูกจะไม่มีวันทำงานนานกว่า scope ต้นทาง**
เพราะขึ้นอยู่กับ OS scheduler ตอน runtime ทั้งหมด compiler จึง**ปฏิเสธไปเลยตั้งแต่ compile time** ถ้า closure
ไม่ใช่ `'static` — นี่คือ**การพิสูจน์ข้อแรก**ของ "fearless concurrency" ที่กล่าวไว้ในหัวข้อ 37.1: กฎ borrow
checker แบบเดียวกับ Part 6-7 ถูกนำมาบังคับใช้ข้าม thread ได้อย่างสมบูรณ์

#### เห็น Error จริง E0373: `closure may outlive the current function`

ลองพยายามส่ง closure ที่ borrow ตัวแปร local เข้า `thread::spawn` โดยไม่ใส่ `move`:

```rust
use std::thread;

fn main() {
    let numbers = vec![1, 2, 3, 4, 5];

    let handle = thread::spawn(|| {
        let total: i32 = numbers.iter().sum();
        println!("ผลรวม: {total}");

}
```

  — compiler เตือนตรง ๆ ว่า closure ตัวนี้**อาจ**ทำงานนานกว่าอายุของฟังก์ชัน `main` เอง (เพราะมันถูกส่งไปทำงานบน

  signature ของ `thread::spawn` ที่กล่าวไปในหัวข้อ 37.2
- **`help: to force the closure to take ownership of numbers ... use the move keyword`** — compiler แนะนำวิธี
  แก้ให้ตรง ๆ เหมือนเดิม

#### แก้ด้วย `move`: ยึด Ownership เข้าไปในตัว Closure ทั้งก้อน

```rust
use std::thread;

fn main() {
    let numbers = vec![1, 2, 3, 4, 5];

    let handle = thread::spawn(move || {
        let total: i32 = numbers.iter().sum();
        println!("ผลรวม: {total}");
    });

    handle.join().unwrap();
}
```

```
ผลรวม: 15
```

เมื่อเพิ่ม `move` เข้าไป `numbers` (ทั้งตัว `Vec<i32>` ไม่ใช่แค่ reference) ถูก **move เข้าไปเป็นส่วนหนึ่งของตัว
closure โดยตรง** ตามกลไก `move` ที่เรียนมาแล้วเต็มรูปแบบใน Part 24.6-24.9 — closure ที่มี `move` จะเก็บ
`numbers: Vec<i32>` เป็น field ของตัวเองตรง ๆ ไม่ใช่ `&Vec<i32>` ที่ชี้กลับไปยัง `main` อีกต่อไป เมื่อ `spawn`
ส่ง closure ตัวนี้ไปทำงานบน thread ใหม่ **ข้อมูลจริงของ `Vec` เดินทางไปกับมันด้วย** ไม่ว่า `main` จะทำอะไรต่อไป
หรือ scope เดิมจะจบไปแล้วหรือไม่ก็ตาม เพราะไม่มี reference ใด ๆ ที่ชี้กลับไปยัง `main` เหลืออยู่เลย — ปัญหา
dangling reference ข้าม thread จึงเป็นไปไม่ได้ตั้งแต่ต้น เพราะไม่มี reference ให้ dangling

**นี่คือหัวใจของกฎ `move` + thread**: `move` ไม่ได้เป็นแค่ "syntax ที่ต้องจำให้ใส่" — มันคือการเปลี่ยนโมเดลข้อมูล
จาก "ยืมดู แล้วหวังว่าต้นทางจะยังอยู่นานพอ" (ซึ่งพิสูจน์ไม่ได้ข้าม thread) เป็น "โอนกรรมสิทธิ์ไปให้เจ้าของใหม่เต็ม
ตัว ไม่ต้องพึ่งพาต้นทางอีกต่อไป" (ซึ่งพิสูจน์ได้ 100% ตอน compile time ด้วยกฎ move semantics เดิมจาก Part 6)
สังเกตว่าหลัง `move` แล้ว **`numbers` ใน `main` ใช้ต่อไม่ได้อีก** (ถ้าเขียน `println!("{numbers:?}")` ต่อจาก
`thread::spawn(move || ...)` จะเจอ E0382 "use of moved value" แบบเดียวกับที่เรียนมาตั้งแต่ Part 6) — นี่คือ
"ราคา" ที่ต้องจ่ายเพื่อความปลอดภัย: เมื่อ move ข้อมูลเข้า thread ไปแล้ว thread เดิมจะไม่มีสิทธิ์เข้าถึงมันอีก
ซึ่งเป็นข้อแลกเปลี่ยนที่สมเหตุสมผลมาก เพราะถ้าทั้งสอง thread ยังเข้าถึงข้อมูลเดียวกันได้พร้อมกัน (แม้ผ่านการ
"ยึดมาแล้ว" ก็ตาม) นั่นจะเปิดช่องให้เกิด data race กลับมาอีก — เราจะเห็นว่า `move` เพียงอย่างเดียวไม่พอสำหรับ
กรณีที่ต้อง**แชร์**ข้อมูลจริง ๆ ในหัวข้อ 37.10

#### ข้อสังเกตเชิงลึก: `'static` หมายถึง "Type ไม่มี Reference ที่อายุสั้น" ไม่ใช่ "ค่าต้องอยู่ตลอดไป"

มีความเข้าใจผิดที่พบบ่อยมากตอนเจอ `'static` bound ครั้งแรก: คนมักคิดว่า **"`'static` แปลว่าค่านั้นต้องอยู่ไปตลอด
โปรแกรม (เหมือน global variable)"** ซึ่ง**ไม่ถูกต้อง** — ความหมายที่แม่นยำกว่าคือ **"type ของค่านั้นไม่มี reference
ที่มีอายุสั้นกว่าโปรแกรมทั้งหมดฝังอยู่ข้างในเลย"** สองอย่างนี้ต่างกันมาก

ลองดูตัวอย่าง `numbers` จากหัวข้อก่อนหน้า: `Vec<i32>` ที่ถูก `move` เข้าไปใน closure นั้น **ไม่ได้อยู่ตลอดไปเลย**
— มันจะถูก `drop` ตามปกติทันทีที่ closure (และ thread ที่รันมัน) ทำงานจบ หน่วยความจำของมันถูกคืนกลับให้ระบบตาม
กฎ ownership ปกติจาก Part 6 ทุกประการ **สิ่งที่ `'static` bound ต้องการจริง ๆ คือ**: type `Vec<i32>` เป็น type ที่
**เป็นเจ้าของข้อมูลของตัวเองเต็มตัว ไม่มี `&'a T` หรือ `&'a mut T` ที่มี lifetime `'a` แบบไหนก็ได้ที่ไม่ใช่
`'static` ฝังอยู่ข้างในเลย** — `Vec<i32>` ผ่านเงื่อนไขนี้ได้อัตโนมัติเพราะมันไม่มี reference ฝังอยู่ข้างในเลย
(มันเก็บข้อมูลของตัวเองบน heap ทั้งหมด ไม่ได้ "ยืม" อะไรจากใคร) เช่นเดียวกับ `i32`, `String`, `bool` และ type
ทั่วไปที่ไม่มี lifetime parameter — ทั้งหมดนี้ถือว่าเป็น `'static` **โดยธรรมชาติ** ไม่ว่าค่าของมันจะถูกสร้างขึ้นมา
ตอนไหนหรือถูก `drop` เร็วแค่ไหนก็ตาม

ในทางกลับกัน type ที่ **มี** reference ฝังอยู่ข้างใน เช่น `&'a str` หรือ struct ที่มี field เป็น `&'a T` (จาก
Part 20/23) จะเป็น `'static` ได้ก็ต่อเมื่อ `'a` นั้นคือ `'static` จริง ๆ (เช่น string literal `&'static str` ที่
ฝังอยู่ใน binary ตลอดไป) — นี่คือเหตุผลที่ `numbers: &Vec<i32>` (reference ที่ชี้กลับไปยัง `main`) ไม่ผ่าน
`'static` bound: มันมี lifetime ที่ผูกกับ scope ของ `main` ซึ่งสั้นกว่าโปรแกรมทั้งหมดแน่นอน แต่ `numbers: Vec<i32>`
(ค่าที่ถูก move มาเป็นเจ้าของเอง ไม่มี reference ใด ๆ ฝังอยู่) ผ่านได้ทันทีไม่ว่ามันจะมีอายุสั้นแค่ไหนก็ตาม —
**สรุปสั้น ๆ**: `T: 'static` อ่านว่า **"T ไม่มี reference ที่ยืมมาจากที่อื่นซึ่งอาจตายก่อนได้"** ไม่ใช่ **"ค่าของ
T ต้องมีชีวิตอยู่ตลอดไป"** ความเข้าใจผิดจุดนี้ทำให้มือใหม่หลายคนงงว่า "ทำไม `Vec<i32>` ที่จะถูก `drop` ทิ้งหลัง
thread จบถึงผ่าน `'static` ได้" — คำตอบคือมันผ่านเพราะ**โครงสร้าง type ของมัน** ไม่ใช่เพราะ**อายุการใช้งานจริง**
ของค่านั้น

### 37.6 Spawn หลาย Thread พร้อมกัน: เก็บ `JoinHandle` ไว้ใน `Vec`

pattern ที่พบบ่อยที่สุดในโค้ด concurrency จริงคือการ spawn thread **หลายตัว**ในลูป แล้วเก็บ `JoinHandle` ของแต่ละ
ตัวไว้ใน `Vec<JoinHandle<T>>` เพื่อ join ทั้งหมดทีหลัง (ไม่ join ทันทีในลูป เพราะถ้า join ทันทีจะกลายเป็นรอ
thread หนึ่งจบก่อนค่อย spawn ตัวถัดไป ซึ่งเสียประโยชน์ของการทำงานคู่ขนานไปหมด)

```rust
use std::thread;

fn main() {
    let mut handles = Vec::new();

    for id in 0..5 {
        // move ยึด id (เป็น i32 ธรรมดา, Copy ได้) เข้าไปในแต่ละ closure แยกกัน
        // แต่ละ thread ได้ id เป็นของตัวเองคนละค่า ไม่ชนกัน
        let handle = thread::spawn(move || {
            println!("thread หมายเลข {id}: เริ่มทำงาน");
            id * id
        });
        handles.push(handle);
    }

    let mut results = Vec::new();
    for handle in handles {
        let squared = handle.join().unwrap();
        results.push(squared);
    }

    results.sort();
    println!("ผลลัพธ์ทั้งหมด (เรียงแล้ว): {results:?}");
}
```

รันจริงได้ผลลัพธ์ตัวอย่างนี้ (ลำดับบรรทัด `เริ่มทำงาน` ของแต่ละ thread **ไม่แน่นอน** — สลับกันได้ทุกครั้งที่รัน
เพราะ OS scheduler เป็นคนตัดสินใจว่าจะให้ thread ไหนได้ CPU ก่อน แต่ผลลัพธ์สุดท้ายหลังเรียง**แน่นอนเสมอ**):

```
thread หมายเลข 0: เริ่มทำงาน
thread หมายเลข 2: เริ่มทำงาน
thread หมายเลข 3: เริ่มทำงาน
thread หมายเลข 4: เริ่มทำงาน
thread หมายเลข 1: เริ่มทำงาน
ผลลัพธ์ทั้งหมด (เรียงแล้ว): [0, 1, 4, 9, 16]
```

สังเกตจุดสำคัญสามจุด:

1. **ทำไมต้อง `move` ใน closure ของลูปนี้**: ตัวแปร `id` มาจากตัวแปรวนซ้ำของ `for id in 0..5` — แต่ละรอบของ
   ลูปสร้าง `id` ตัวใหม่ (เป็นค่า ไม่ใช่ reference กลับไปยังตัวแปรที่ใช้ร่วมกัน) แต่ตัว `id` ตัวนั้นก็ยังเป็นตัวแปร
   local ของฟังก์ชัน `main` อยู่ดี — ถ้าไม่ใส่ `move` closure จะพยายามยืมมันมา ซึ่งชนกับ `'static` bound แบบ
   เดียวกับหัวข้อ 37.5 ทุกประการ (compiler จะรายงาน E0373 เหมือนกัน ลองเอา `move` ออกดูได้)
2. **ลำดับการเริ่มทำงานไม่แน่นอน แต่ผลลัพธ์ที่รวบรวมมาแน่นอน**: นี่คือใจความสำคัญของ concurrency — สิ่งที่
   **ไม่แน่นอน**คือ**ลำดับเวลา**ที่แต่ละ thread ทำงาน (interleaving) แต่สิ่งที่**แน่นอน**คือ**ผลลัพธ์สุดท้าย**
   ตราบใดที่แต่ละ thread ทำงานอย่างเป็นอิสระจากกันโดยไม่แชร์ข้อมูลที่แก้ไขร่วมกัน (ซึ่งเป็นกรณีนี้เป๊ะ ๆ — แต่ละ
   thread แค่คำนวณ `id * id` ของตัวเองแล้ว return ไม่ได้ไปแก้ไขอะไรที่ thread อื่นใช้เลย)
3. **การ join ในลูปที่สองรอตามลำดับที่ push ไว้ ไม่ใช่ตามลำดับที่จบจริง**: `for handle in handles` วนตามลำดับ
   index ใน `Vec` (0, 1, 2, 3, 4) — ถ้า thread หมายเลข 3 ทำงานเสร็จเร็วกว่าหมายเลข 0 แต่ loop จะ join หมายเลข 0
   ก่อนอยู่ดี (`.join()` แค่รอเฉย ๆ ถ้ามันจบไปแล้วก็คืนค่าทันที ไม่ได้ทำให้ thread หมายเลข 3 ที่จบไปแล้วต้องรอ
   อะไรเพิ่ม) จึงไม่มีปัญหาเรื่องประสิทธิภาพจากลำดับการ join แต่อย่างใด — ผลลัพธ์ท้ายสุดยัง deterministic เพราะ
   เราจงใจ `.sort()` ก่อน print

#### Mental Model: มองภาพรวมของ Fork-Join ด้วย Timeline

ก่อนไปต่อ ให้วาดภาพจังหวะเวลาของโค้ดในหัวข้อนี้ออกมาเป็น timeline คร่าว ๆ เพื่อให้เห็นภาพรวมทั้งหมดชัดเจนขึ้น
(ตัวเลขเวลาเป็นแค่ตัวแทนสมมติเพื่อให้เห็นภาพ ไม่ใช่ค่าจริงที่วัดได้ตายตัว เพราะขึ้นกับ OS scheduler เสมอตามที่
อธิบายไปแล้ว):

```
เวลา →   0ms        1ms        2ms        3ms        4ms
main:    │─ spawn×5 ─│───────── join(0) join(1) join(2) join(3) join(4) ─→
                      │
thread0: └────────────── id*0*0=0 ────────┘
thread1:              └──── id*1*1=1 ──────────┘
thread2:              └── id*2*2=4 ───┘
thread3:              └────── id*3*3=9 ─────┘
thread4:              └─ id*4*4=16 ┘
```

สังเกตจากภาพ: **"fork"** คือช่วงที่ `main` เรียก `thread::spawn` ห้าครั้งติดกันอย่างรวดเร็ว (แทบไม่กินเวลาเลยเมื่อ
เทียบกับงานที่ thread ทำ) แยกงานออกเป็นห้าเส้นทางที่ทำงาน**คู่ขนาน**กัน — สังเกตว่าแต่ละ thread ใช้เวลาไม่เท่ากัน
(สมมติในภาพ) และ**จบไม่ตามลำดับที่ spawn** (thread4 จบก่อน thread3 ในภาพตัวอย่างนี้) จากนั้น **"join"** คือช่วง
ที่ `main` หยุดรอทีละตัวตามลำดับ index ใน `Vec` (`join(0)`, `join(1)`, ...) — ถ้า thread ที่กำลังจะ join ยังไม่
จบ `main` ก็บล็อกรอจนกว่าจะจบ แต่ถ้า thread นั้นจบไปแล้วก่อนที่ `main` จะมาถึงมัน (เช่น `join(3)` ในภาพที่ thread3
อาจจบไปแล้วก่อนที่ main จะไล่มาถึง) `.join()` จะคืนค่ากลับมา**ทันที**ไม่ต้องรออะไรเพิ่ม — นี่คือเหตุผลที่ลำดับ
การ join ใน `Vec` ไม่กระทบประสิทธิภาพโดยรวม (สังเกตจากข้อ 3 ก่อนหน้านี้) เพราะ `main` แค่ไล่เก็บผลลัพธ์ที่พร้อม
อยู่แล้ว หรือรอเท่าที่จำเป็นจริง ๆ เท่านั้น — เวลาที่ `main` ใช้ทั้งหมดในการ join จะเท่ากับเวลาของ **thread ที่
ใช้เวลานานที่สุด** เท่านั้น (ในภาพคือ thread0 ที่ยาวที่สุด) ไม่ใช่ผลรวมของเวลาทุก thread — นี่คือประโยชน์หลักของ
การทำงานคู่ขนาน: **เวลารวมทั้งหมด ≈ เวลาของงานที่หนักที่สุดเพียงงานเดียว** ไม่ใช่ผลรวมของทุกงานเหมือนการทำงาน
แบบ sequential (ทำทีละงานตามลำดับ)

### 37.7 ส่งค่ากลับจาก Thread: การใช้งาน `JoinHandle<T>` ให้เกิดประโยชน์จริง

ตัวอย่างในหัวข้อ 37.6 แสดงให้เห็นแล้วว่า `T` ใน `JoinHandle<T>` คือ return type ของ closure — แต่ให้ย้ำอีกครั้ง
ด้วยตัวอย่างที่ตรงประเด็นกว่า เพื่อให้เห็นภาพว่าทำไมความสามารถนี้มีประโยชน์มากในการเขียนโปรแกรมแบบ **"แบ่งงาน
ออกเป็นส่วน ๆ ให้แต่ละ thread ทำแยกกัน แล้วรวมผลลัพธ์"** (หรือที่เรียกกันว่า **fork-join pattern** — สิ่งที่บทนี้
จะจบด้วยตัวอย่างใหญ่ในหัวข้อ 37.10)

หลักการคือ: **`spawn` แต่ละครั้งไม่จำเป็นต้องคืนค่า `()` เสมอไป** — closure สามารถคำนวณอะไรบางอย่างแล้ว `return`
(หรือปล่อยให้ expression สุดท้ายเป็นค่านั้น ตามกฎ implicit return ที่เรียนมาตั้งแต่ Part 4) ค่านั้นจะถูกเก็บไว้ใน
`JoinHandle<T>` รอให้ `.join()` มาดึงออกมา — ทำให้ thread ทำหน้าที่เหมือน "ฟังก์ชันที่รันคู่ขนาน" ได้เต็มรูปแบบ
ไม่ใช่แค่ทำ side effect (print) แล้วทิ้งไป

```rust
use std::thread;

/// คำนวณผลรวมของตัวเลขในช่วง [start, end) โดยรันบน thread แยก
fn spawn_range_sum(start: i64, end: i64) -> thread::JoinHandle<i64> {
    thread::spawn(move || {
        let sum: i64 = (start..end).sum();
        println!("thread สำหรับช่วง [{start}, {end}): ผลรวม = {sum}");
        sum
    })
}

fn main() {
    // แบ่งการคำนวณผลรวม 1..=1_000_000 ออกเป็น 4 ช่วงเท่า ๆ กัน คำนวณคู่ขนาน
    let ranges = [(1, 250_001), (250_001, 500_001), (500_001, 750_001), (750_001, 1_000_001)];

    let handles: Vec<_> = ranges
        .iter()
        .map(|&(start, end)| spawn_range_sum(start, end))
        .collect();

    let total: i64 = handles.into_iter().map(|h| h.join().unwrap()).sum();

    println!("ผลรวมสุดท้ายจากทุก thread: {total}");
    println!("ตรวจสอบด้วยสูตร n(n+1)/2: {}", 1_000_000_i64 * 1_000_001 / 2);
}
```

รันจริงได้ผลลัพธ์นี้ (ลำดับสี่บรรทัดแรกของแต่ละช่วงอาจสลับกันได้ในการรันครั้งต่อ ๆ ไป ตามเหตุผลเดียวกับหัวข้อ 37.6
แต่ผลรวมสุดท้ายสองบรรทัดท้ายจะตรงกันเสมอ):

```
thread สำหรับช่วง [1, 250001): ผลรวม = 31250125000
thread สำหรับช่วง [500001, 750001): ผลรวม = 156250125000
thread สำหรับช่วง [250001, 500001): ผลรวม = 93750125000
thread สำหรับช่วง [750001, 1000001): ผลรวม = 218750125000
ผลรวมสุดท้ายจากทุก thread: 500000500000
ตรวจสอบด้วยสูตร n(n+1)/2: 500000500000
```

โค้ดนี้เขียนแบบกระชับกว่าหัวข้อ 37.6 โดยใช้ `.map()` แทน `for` loop (เชื่อมกับ Part 25-26 เรื่อง iterator) — จุดที่
ควรสังเกตคือ `handles.into_iter().map(|h| h.join().unwrap()).sum()` เป็น pattern ที่กระชับมากสำหรับ **join ทุก
thread แล้วรวมผลลัพธ์เป็นค่าเดียวในบรรทัดเดียว** — `.into_iter()` (ไม่ใช่ `.iter()`) เพราะเราต้องการ **ยึด
ownership** ของแต่ละ `JoinHandle` เพื่อเรียก `.join(self)` ที่รับ `self` by value ตามที่อธิบายไว้ในหัวข้อ 37.3

### 37.8 `thread::sleep` และ `std::time::Duration`: เครื่องมือช่วยสาธิตจังหวะเวลา

ตลอดบทนี้เราใช้ `thread::sleep(Duration::from_millis(...))` ไปแล้วหลายครั้งโดยไม่ได้อธิบายละเอียด — มาดูให้ครบกัน
สั้น ๆ (บทนี้ไม่ใช่บทที่เจาะลึกเรื่อง timing ของระบบ แค่ให้พอใช้ประกอบตัวอย่างและโปรแกรมทั่วไปได้)

- **`std::time::Duration`** คือ struct ที่แทนช่วงเวลา (ไม่ใช่ "จุดเวลา" แบบ `Instant` หรือ `SystemTime`) สร้างได้
  หลายวิธี: `Duration::from_millis(500)`, `Duration::from_secs(2)`, `Duration::from_micros(100)`, ฯลฯ
- **`thread::sleep(duration)`** สั่งให้ **thread ปัจจุบัน** (thread ที่เรียกมัน) หยุดทำงานอย่างน้อยตามเวลาที่
  กำหนด (OS อาจปลุกช้ากว่าที่ขอเล็กน้อยถ้าระบบมี load สูง แต่จะไม่ปลุกเร็วกว่าที่ขอ) มันบล็อกแค่ thread ที่เรียก
  มันเท่านั้น thread อื่น ๆ ยังทำงานต่อได้ตามปกติ

ตัวอย่างที่ใช้ `sleep` เพื่อควบคุมลำดับการทำงานให้สังเกตได้ชัดเจน (มีประโยชน์มากตอนสาธิตหรือทดสอบ concurrency
เพราะทำให้ผลลัพธ์เดาได้ง่ายขึ้น แม้ยังไม่ใช่การ synchronize จริงจัง):

```rust
use std::thread;
use std::time::Duration;

fn main() {
    let handle_a = thread::spawn(|| {
        thread::sleep(Duration::from_millis(30));
        println!("thread A: ตื่นแล้ว (รอ 30ms)");
    });

    let handle_b = thread::spawn(|| {
        thread::sleep(Duration::from_millis(10));
        println!("thread B: ตื่นแล้ว (รอ 10ms)");
    });

    handle_a.join().unwrap();
    handle_b.join().unwrap();
    println!("main: ทั้งสอง thread จบการทำงานแล้ว");
}
```

รันจริง 3 ครั้งติดกันได้ผลลัพธ์**เหมือนกันทุกครั้ง**:

```
thread B: ตื่นแล้ว (รอ 10ms)
thread A: ตื่นแล้ว (รอ 30ms)
main: ทั้งสอง thread จบการทำงานแล้ว
```

thread B ตื่นก่อน A เสมอ เพราะมัน sleep สั้นกว่า (10ms < 30ms) — สังเกตว่า `handle_a.join()` ถูกเรียกก่อน
`handle_b.join()` ในโค้ด แต่**ผลลัพธ์ที่พิมพ์ออกมาไม่ได้เรียงตามลำดับการ join** เพราะ `println!` เกิดขึ้น**ภายใน**
closure ของแต่ละ thread เอง (ตอน thread นั้นตื่นจาก sleep) ไม่ใช่ตอนที่ thread หลักเรียก `.join()` — `.join()`
แค่รอให้ thread นั้นจบเท่านั้น ไม่ได้กำหนดว่า print จะเกิดขึ้นตอนไหน การเรียก `handle_a.join()` ก่อนแค่ทำให้
thread หลัก**รอ A ให้จบก่อน B** แต่ระหว่างที่รอ A (30ms) นั้นเอง B ก็ทำงานคู่ขนานไปด้วยและตื่นก่อน (ที่ 10ms)
จึงพิมพ์ก่อน A ที่ยังไม่ตื่น — นี่คือตัวอย่างที่ดีที่แสดงว่า **ลำดับการเรียก `.join()` ในโค้ด ไม่ใช่ตัวกำหนดลำดับ
การทำงานจริงของ thread เหล่านั้นเลย** `.join()` เป็นแค่จุดที่ thread หลัก "หยุดรอ" ไม่ใช่ตัวสั่งการลำดับการทำงาน
ของ thread ลูก

> **ข้อควรระวังสำคัญ**: อย่าใช้ `sleep` เป็นวิธี "แก้" ปัญหา synchronization จริงจัง (เช่น สั่งให้ thread A sleep
> นานกว่า thread B เพื่อ "หวังว่า" B จะเสร็จก่อน A แน่ ๆ) เพราะเวลาที่ thread ใช้จริงขึ้นกับ load ของระบบตอนนั้น
> ซึ่งไม่แน่นอน — `sleep` เหมาะสำหรับสาธิต/ทดสอบ/หรือหน่วงเวลาจริง ๆ ที่ต้องการ (เช่น retry with backoff) เท่านั้น
> ไม่ใช่เครื่องมือ synchronize การทำงานระหว่าง thread — Part 38-39 จะแนะนำเครื่องมือที่ synchronize ได้จริง
> (channel, `Mutex`) ที่การันตีลำดับได้แน่นอน ไม่ใช่แค่ "น่าจะ" แน่นอน

### 37.9 เมื่อ Thread Panic: การจับ Panic ที่ขอบ Thread แบบเต็มรูปแบบ

หัวข้อ 37.4 เกริ่นไว้แล้วว่า panic ใน thread ลูกถูก "จับ" ไว้ที่ขอบของ thread นั้น ไม่ลามไปทั้งโปรแกรม มาดูตัวอย่าง
ที่รันได้จริงเต็มรูปแบบ:

```rust
use std::thread;

fn main() {
    let handle = thread::spawn(|| {
        println!("thread ลูก: กำลังจะเจอปัญหา...");
        let data: Vec<i32> = vec![1, 2, 3];
        let _boom = data[10]; // index out of bounds -> panic
        println!("บรรทัดนี้ไม่มีทางถูกพิมพ์");
    });

    match handle.join() {
        Ok(_) => println!("thread หลัก: thread ลูกทำงานสำเร็จ"),
        Err(_) => println!("thread หลัก: thread ลูก panic แต่โปรแกรมหลักยังทำงานต่อได้ปกติ"),
    }

    println!("thread หลัก: จบการทำงานตามปกติ ไม่ได้ล้มไปด้วย");
}
```

รันจริงได้ผลลัพธ์นี้ (ส่วนของ panic message และ stack backtrace มาจาก stderr ซึ่งเป็น output จริงที่ Rust runtime
พิมพ์ให้อัตโนมัติทุกครั้งที่มี panic เกิดขึ้น ไม่ว่า panic นั้นจะถูก "จับ" ด้วย `.join()` หรือไม่ก็ตาม — การ join
แค่ป้องกันไม่ให้ panic ลามไปปิดโปรแกรมทั้งหมด แต่ไม่ได้ปิดกั้นข้อความแจ้งเตือนที่พิมพ์ออกมา):

```
thread ลูก: กำลังจะเจอปัญหา...

thread '<unnamed>' panicked at src/main.rs:7:25:
index out of bounds: the len is 3 but the index is 10
note: run with `RUST_BACKTRACE=1` environment variable to display a backtrace
thread หลัก: thread ลูก panic แต่โปรแกรมหลักยังทำงานต่อได้ปกติ
thread หลัก: จบการทำงานตามปกติ ไม่ได้ล้มไปด้วย
```

สังเกตประเด็นสำคัญที่พิสูจน์คำกล่าวในหัวข้อ 37.4 ให้เห็นเป็นรูปธรรม:

1. **`บรรทัดนี้ไม่มีทางถูกพิมพ์` ไม่ปรากฏเลย** — ยืนยันว่า panic หยุดการทำงานของ closure ตรงจุดที่มันเกิดขึ้น
   (เหมือนกับ panic ปกติแบบที่เรียนมาตั้งแต่ Part 12) โค้ดหลังจากบรรทัดที่ panic ใน closure เดียวกันจะไม่ทำงานเลย
2. **`match handle.join()` เข้า branch `Err(_)`** — เพราะ thread ลูก panic การเรียก `.join()` จึงคืนค่า `Err`
   ไม่ใช่ `Ok` ตามกลไกที่อธิบายไว้ในหัวข้อ 37.4
3. **โปรแกรมทำงานต่อไปได้จนจบตามปกติ** — บรรทัด `thread หลัก: จบการทำงานตามปกติ...` พิมพ์ออกมาสำเร็จ และโปรแกรม
   จบด้วย exit code 0 (ปกติ) ไม่ใช่ exit code ของ panic (101) — **นี่คือความต่างที่สำคัญที่สุด**: panic ที่เกิดขึ้น
   ใน thread ลูก **ไม่ทำให้ทั้งโปรแกรม crash** ตราบใดที่ thread หลักจัดการ `Err` จาก `.join()` อย่างเหมาะสม (ไม่
   เรียก `.unwrap()` ทับมันซ้ำ ซึ่งจะเห็นผลตรงข้ามในหัวข้อกับดักถัดไป)

**ความหมายเชิงปฏิบัติที่สำคัญมาก**: pattern นี้ทำให้ Rust สามารถเขียนระบบที่ **ทนทานต่อความล้มเหลวเฉพาะจุด**
(fault isolation) ได้ในระดับ thread — ถ้าคุณมีระบบที่ประมวลผลงานหลายชิ้นแยกกันคนละ thread (เช่น เว็บเซิร์ฟเวอร์ที่
แต่ละ request จัดการโดย thread แยก) การที่ request หนึ่งพัง (panic) ไม่จำเป็นต้องทำให้ request อื่น ๆ ที่กำลัง
ทำงานอยู่พังตามไปด้วย — thread หลัก (หรือ thread ที่คอย join) แค่บันทึก error แล้วทำงานต่อได้ตามปกติ ต่างจาก
หลายภาษาที่ exception ข้าม thread จัดการได้ยากกว่ามาก หรือทำให้ทั้ง process ต้อง crash เพื่อความปลอดภัย

### 37.10 สิ่งที่บทนี้ยังไม่แก้ให้: การแชร์ Mutable State ระหว่าง Thread

ถึงตอนนี้เราได้พิสูจน์ไปครึ่งหนึ่งของคำกล่าวอ้าง "fearless concurrency" แล้ว — เราเห็นว่า Rust ป้องกัน **dangling
reference ข้าม thread** ได้ตั้งแต่ compile time (ผ่าน `'static` bound + E0373 ในหัวข้อ 37.5) แต่ยังมีปัญหา
concurrency อีกครึ่งหนึ่งที่ยังไม่ได้แก้เลย: **จะให้หลาย thread แก้ไขข้อมูลชุดเดียวกันร่วมกันได้อย่างไร** (เช่น
หลาย thread เพิ่มค่าตัวนับตัวเดียวกันพร้อมกัน) — และนี่คือจุดที่เตรียมทางไปสู่ Part 38 และ Part 39

#### ความพยายามแบบไร้เดียงสาที่ 1: แชร์ Mutable Reference ตรง ๆ

ลองนึกภาพว่าเราต้องการให้ 5 thread ช่วยกันเพิ่มค่าตัวนับตัวเดียวกัน (เช่น นับจำนวนงานที่ทำสำเร็จรวมจากหลาย
worker):

```rust
use std::thread;

fn main() {
    let mut counter = 0;
    let mut handles = Vec::new();

    for _ in 0..5 {
        let handle = thread::spawn(|| {
            counter += 1;
        });
        handles.push(handle);
    }

    for h in handles {
        h.join().unwrap();
    }

    println!("counter = {counter}");
}
```

  `&mut counter` ไว้อยู่ (เพราะมันอาจถูกเรียกเมื่อไหร่ก็ได้บน thread ของมัน ไม่รู้ว่าเมื่อไหร่) closure ของรอบที่

  ยังมี `&mut counter` ที่ closure ถืออยู่ (อาจ) ยังไม่คืนกลับมา — จะอ่านพร้อมกับที่อาจมีคนแก้ไขอยู่ไม่ได้เด็ดขาด

**สรุปสิ่งที่ compiler กำลังปกป้องเราจากอะไร**: ถ้าโค้ดนี้ compile ผ่านได้จริง (ลองสมมติว่า Rust ไม่มี borrow
checker) 5 thread จะพยายามอ่าน-บวก-เขียน `counter` พร้อมกันแบบไม่มีการควบคุมลำดับเลย — ผลลัพธ์จะเป็นแบบเดียวกับ
ตัวอย่าง C++ ในหัวข้อ 37.1 เป๊ะ ๆ: `counter` อาจไม่เท่ากับ 5 ตอนจบ (อาจได้ 3, 4 หรือค่าอื่นแบบไม่แน่นอน ขึ้นกับ
จังหวะที่ OS สลับ thread) **แต่ Rust ไม่ยอมให้โค้ดที่มีความเป็นไปได้แบบนี้ compile ผ่านได้เลยตั้งแต่แรก** — นี่คือ
สิ่งที่ "fearless concurrency" หมายถึงจริง ๆ: มันไม่ใช่แค่ "compiler ช่วยเตือน" แต่คือ **compiler ปฏิเสธสร้าง
binary ออกมาเลย** จนกว่าคุณจะแก้ปัญหาการแชร์ mutable state ให้ปลอดภัยจริง

#### ความพยายามแบบไร้เดียงสาที่ 2: `move` ช่วยแค่เรื่อง Ownership ไม่ได้ช่วยเรื่อง "แชร์"

อาจมีคนคิดว่า "ก็ใส่ `move` สิ" — แต่ลองดูว่าเกิดอะไรขึ้นจริงถ้าทำแบบนั้นกับ type ที่เป็น `Copy` อย่าง `i32`:

```rust
use std::thread;

fn main() {
    let counter = 0;
    let mut handles = Vec::new();

    for id in 0..5 {
        let handle = thread::spawn(move || {
            let mut local_counter = counter; // i32 เป็น Copy -> แต่ละ thread ได้สำเนาของตัวเองแยกกัน
            local_counter += 1;
            println!("thread {id}: local_counter = {local_counter}");
        });
        handles.push(handle);
    }

    for h in handles {
        h.join().unwrap();
    }

    // counter ต้นฉบับใน main ไม่เคยถูกแก้ไขเลย เพราะแต่ละ thread ได้แค่ "สำเนา" ไปคนละก้อน
    println!("counter ใน main (ไม่เปลี่ยนแปลง): {counter}");
}
```

โค้ดนี้ **compile ผ่านและรันได้จริง** (ไม่มี error เลย) แต่ผลลัพธ์ที่ได้เผยให้เห็นว่า `move` ไม่ได้แก้ปัญหาที่เรา
ต้องการแก้เลย:

```
thread 1: local_counter = 1
thread 2: local_counter = 1
thread 3: local_counter = 1
thread 0: local_counter = 1
thread 4: local_counter = 1
counter ใน main (ไม่เปลี่ยนแปลง): 0
```

ทุก thread พิมพ์ `local_counter = 1` เหมือนกันหมด (ไม่ใช่ 1, 2, 3, 4, 5 ตามที่ "ตัวนับที่แชร์กันจริง" ควรจะเป็น)
และ `counter` ใน `main` ยังเป็น `0` เหมือนเดิมไม่เปลี่ยนแปลง — เหตุผลคือ `i32` เป็น type ที่ `Copy` (เรียนมาตั้งแต่
Part 6) การ `move counter` เข้า closure จริง ๆ แล้วเป็นการ**สร้างสำเนาใหม่ให้แต่ละ thread คนละก้อนแยกกันโดย
สมบูรณ์** ไม่มีการ "แชร์" เกิดขึ้นเลยสักนิด แต่ละ thread ได้ `counter` เวอร์ชันของตัวเองที่เริ่มจาก 0 เหมือนกันหมด
บวก 1 แล้วก็จบไป ไม่มีใครเห็นการเปลี่ยนแปลงของใครเลย

**นี่คือบทเรียนสำคัญที่ต้องจำให้แม่น**: `move` แก้ปัญหา **"ownership ข้าม thread"** ได้อย่างสมบูรณ์ (ไม่มี
dangling reference, ไม่มี `'static` violation) แต่มันแก้ปัญหาด้วยการ **"ตัดการเชื่อมโยงกับต้นทางออกไปเลย"** —
ถ้าโจทย์ของคุณคือ "แค่ให้ thread แต่ละตัวใช้ข้อมูลของตัวเองแยกกัน" (เหมือนตัวอย่าง chunk processing ที่จะเห็นใน
หัวข้อ 37.11) `move` คือคำตอบที่สมบูรณ์แบบ แต่ถ้าโจทย์ของคุณคือ **"หลาย thread ต้องเห็นและแก้ไขข้อมูลชุดเดียวกัน
จริง ๆ"** (เช่นตัวนับที่ต้องสะสมค่าจากทุก thread) `move` เพียงอย่างเดียว**ไม่พอ** — คุณต้องการเครื่องมือที่
**อนุญาตให้แชร์ mutable state ข้าม thread ได้อย่างปลอดภัย**

#### ความพยายามแบบไร้เดียงสาที่ 3: เอา `Rc<RefCell<T>>` จาก Part 28 มาใช้ข้าม Thread

เมื่อ `move` เพียว ๆ ไม่พอ คนที่เคยเรียน Part 28 มาอาจนึกถึง `Rc<RefCell<T>>` — pattern ที่ให้ "หลายเจ้าของแก้ไข
ข้อมูลร่วมกันได้" ที่เรียนไปแล้ว ลองเอามาใช้ข้าม thread ดู:

```rust
use std::cell::RefCell;
use std::rc::Rc;
use std::thread;

fn main() {
    let shared = Rc::new(RefCell::new(0));

    let handle = thread::spawn(move || {
        *shared.borrow_mut() += 1;
    });

    handle.join().unwrap();
}
```

(`Rc<RefCell<i32>>` cannot be sent between threads safely)** — error message บอกตรงจุดที่แม่นยำที่สุด:
**`the trait Send is not implemented for Rc<RefCell<i32>>`**

จำได้จากหัวข้อ 37.2 ว่า `thread::spawn` ต้องการ closure ที่ implement `Send` (ค่าทั้งหมดที่ closure ยึดมา
ต้อง**ปลอดภัยที่จะย้ายไปทำงานบน thread อื่น**) แต่ `Rc<T>` **ไม่ implement `Send` เลยไม่ว่ากรณีใด** — และนี่คือ
การพิสูจน์คำเตือนที่ Part 28 บอกไว้ตรง ๆ ในหัวข้อ 28.8 ว่า **"`Rc<T>` และ `RefCell<T>` ไม่ thread-safe"**: เหตุผล
เชิงกลไกคือ **ตัวนับ reference ภายในของ `Rc<T>` เป็นแค่ `Cell<usize>` ธรรมดา** (เพิ่ม/ลดค่าแบบไม่มีการ
synchronize ข้าม thread เลย เพื่อความเร็วสูงสุดในกรณี single-thread) — ถ้าสอง thread เรียก `Rc::clone` หรือ
`drop` พร้อมกันจริง ๆ การเพิ่ม/ลดตัวนับนั้นเองจะกลายเป็น **data race** ตามนิยามในหัวข้อ 37.1 ทันที (สอง thread
เขียนตัวเลขตัวเดียวกันพร้อมกันโดยไม่ synchronize) ในทำนองเดียวกัน `RefCell<T>` ก็ตรวจสอบกฎ borrow ด้วยตัวนับที่
ไม่ thread-safe เช่นกัน (ตัวที่ทำให้เกิด `BorrowError`/`BorrowMutError` ตอน runtime ตามที่เรียนใน Part 28)

**นี่คือการพิสูจน์ "fearless concurrency" อีกชั้นที่ลึกกว่าเดิม**: ครั้งนี้ปัญหาไม่ใช่แค่ ownership/lifetime
(ที่ borrow checker จาก Part 6-7 จับได้อยู่แล้ว) แต่เป็นปัญหาที่ **type ทั้ง type ถูกออกแบบมาไม่ให้ปลอดภัยข้าม
thread** — Rust แก้ปัญหานี้ด้วยระบบ trait ใหม่ที่ชื่อ **`Send`** (และคู่หูของมันคือ `Sync` ที่จะเรียนเต็มรูปแบบใน
Part 40) ซึ่งเป็น **marker trait** (trait ที่ไม่มี method ใด ๆ เลย แค่ใช้เป็น "ป้ายกำกับ" บอกว่า type นี้ปลอดภัย
สำหรับสถานการณ์ไหน) — type ที่ implement `Send` คือ type ที่ **โอน ownership ข้าม thread ได้อย่างปลอดภัย** และ
`Rc<T>`/`RefCell<T>` ถูกออกแบบมาให้**ไม่** implement มันโดยตั้งใจ เพื่อบังคับให้ compiler ปฏิเสธโค้ดแบบนี้ตั้งแต่
compile time — ไม่ต้องรอให้เกิด data race ตอน runtime แล้วค่อยมาแก้ทีหลัง

**ห้ามพยายามใช้ `unsafe` เพื่อ "บังคับ" ให้ `Rc<RefCell<T>>` ทำงานข้าม thread เด็ดขาด** เพราะตัวนับที่ไม่
synchronize จะทำให้เกิด data race บนตัวนับเองได้จริง (undefined behavior แม้จะเขียนด้วย Rust ก็ตาม ถ้าเลี่ยงผ่าน
`unsafe`) — วิธีแก้ที่ถูกต้องคือเปลี่ยนไปใช้ **`Arc<Mutex<T>>`** ซึ่งเป็นเวอร์ชัน thread-safe ของ pattern เดียวกัน
ที่จะเรียนเต็มรูปแบบใน **Part 39**

#### ทางออกสองทางที่รออยู่ข้างหน้า: Message Passing กับ Shared-State

บทนี้จงใจปิดท้ายด้วยปัญหาที่ยังไม่มีคำตอบ เพื่อให้คุณเห็นภาพรวมของ arc concurrency ทั้งหมดก่อนเข้าสองบทถัดไป —
Rust (และวงการ concurrency โดยรวม) มีสองแนวทางหลักในการแก้ปัญหา "หลาย thread ต้องแชร์ข้อมูลกัน":

| แนวทาง | หลักการ | บทที่จะเรียน |
|---|---|---|
| **Message Passing (การส่งข้อความ)** | thread ไม่แชร์ข้อมูลกันเลย แต่ **ส่งข้อมูลผ่านกันเป็น "ข้อความ"** ผ่าน channel — เจ้าของข้อมูลเปลี่ยนมือไปเรื่อย ๆ ทีละ thread ไม่มีสองที่เป็นเจ้าของพร้อมกัน (คติที่มีชื่อเสียงจาก Go: "Don't communicate by sharing memory; share memory by communicating") | **Part 38 (Channels, mpsc)** |
| **Shared-State (สถานะที่แชร์กัน)** | ยอมให้หลาย thread เข้าถึงข้อมูลชุดเดียวกันได้จริง แต่บังคับผ่าน **lock** (`Mutex`) ที่การันตีว่า**มีแค่ thread เดียวเท่านั้น**ที่แก้ไขข้อมูลได้ในแต่ละขณะ ผสานกับ **`Arc<T>`** (เวอร์ชัน thread-safe ของ `Rc<T>`) เพื่อให้หลาย thread เป็น "เจ้าของร่วม" ของ lock นั้นได้อย่างปลอดภัย | **Part 39 (Mutex, Arc)** |

ทั้งสองแนวทางแก้ปัญหาเดียวกันด้วยมุมมองที่ต่างกันสุดขั้ว — แนวทางแรกหลีกเลี่ยงการแชร์ mutable state ตั้งแต่ต้น
(ไม่มีของให้แข่งกันแก้ไข ก็ไม่มี data race) ส่วนแนวทางที่สองยอมรับว่าต้องแชร์ แต่ควบคุมการเข้าถึงให้ปลอดภัยด้วย
กลไก lock ที่ compiler ช่วยการันตีว่าคุณลืม lock ไม่ได้ (ต่างจาก C/C++ ที่ต้องจำเอาเองทั้งหมด) — ทั้งสองบทถัดไปจะ
แสดงให้เห็นว่าทั้งคู่ compile ผ่านได้อย่างปลอดภัยเพราะระบบ trait `Send`/`Sync` (Part 40) ทำงานร่วมกับ ownership
system ตรวจสอบให้ครบทุกจุด — ปิดคำกล่าวอ้าง "fearless concurrency" ให้สมบูรณ์ในท้ายที่สุด

### 37.11 ตัวอย่างประยุกต์ใช้งานจริง: Parallel Chunk Processing สำหรับข้อมูลยอดขาย

มารวมทุกอย่างที่เรียนมาในบทนี้เข้าด้วยกันในตัวอย่างที่ใกล้เคียงงานจริง: ระบบวิเคราะห์ยอดขายที่มีข้อมูลจำนวนมาก
(ในตัวอย่างนี้ย่อขนาดลงให้อ่านง่าย แต่หลักการเดียวกันนี้ใช้ได้กับข้อมูลระดับล้านรายการจริง) เราจะ**แบ่งข้อมูลออก
เป็นก้อน (chunk)** กระจายให้แต่ละ thread คำนวณผลรวมย่อยแบบคู่ขนาน (**ไม่มีการแชร์ข้อมูลกันเลยระหว่าง thread** —
แต่ละ thread เป็นเจ้าของ chunk ของตัวเอง 100% ผ่าน `move` ตามที่เรียนมาในหัวข้อ 37.5 นี่คือเหตุผลว่าทำไมตัวอย่างนี้
จึงไม่ต้องพึ่งพา `Mutex`/`Arc`/channel เลย — โจทย์นี้ **"แบ่งงานแยกกันทำ ไม่มีจุดร่วม"** พอดี ต่างจากโจทย์ตัวนับที่
แชร์กันในหัวข้อ 37.10) แล้วจึง join ทุก thread และรวมผลลัพธ์เป็นยอดรวมสุดท้าย:

```rust
use std::thread;

/// จำลองข้อมูลยอดขายรายวันของสาขาต่าง ๆ (หน่วย: บาท) รวม 20 รายการ
fn generate_sales_data() -> Vec<i32> {
    vec![
        1200, 950, 1800, 2200, 700, 1350, 990, 1600, 2100, 800,
        1450, 1700, 2000, 600, 1100, 1950, 850, 1300, 2400, 750,
    ]
}

/// แบ่ง Vec<i32> ออกเป็น N ก้อน (chunk) ให้ขนาดใกล้เคียงกันที่สุด
/// รับ ownership ของ `data` ตรง ๆ (by value) เพราะเราจะย้าย element ของมันออกไปเป็นก้อนย่อย ๆ
fn split_into_chunks(data: Vec<i32>, num_chunks: usize) -> Vec<Vec<i32>> {
    // ceiling division: ปัดขึ้นเสมอ เพื่อให้ num_chunks ก้อนครอบคลุมข้อมูลทั้งหมดพอดี
    let chunk_size = (data.len() + num_chunks - 1) / num_chunks;
    data.chunks(chunk_size).map(|c| c.to_vec()).collect()
}

fn main() {
    let sales_data = generate_sales_data();
    let total_records = sales_data.len();
    println!("จำนวนรายการยอดขายทั้งหมด: {total_records} รายการ");

    let num_threads = 4;
    let chunks = split_into_chunks(sales_data, num_threads);

    let mut handles = Vec::with_capacity(chunks.len());

    for (chunk_id, chunk) in chunks.into_iter().enumerate() {
        // move ยึด ownership ของ chunk (Vec<i32> ก้อนของตัวเอง) เข้าไปใน thread โดยตรง
        // แต่ละ thread เป็นเจ้าของข้อมูลก้อนของตัวเอง 100% ไม่มีการแชร์ข้อมูลกันเลย
        // -> ไม่มี 'static violation (E0373), ไม่มี data race ที่เป็นไปได้เลยตั้งแต่ต้น
        let handle = thread::spawn(move || {
            let partial_sum: i32 = chunk.iter().sum();
            println!(
                "thread {chunk_id}: ประมวลผล {} รายการ ผลรวมย่อย = {partial_sum}",
                chunk.len()
            );
            partial_sum
        });
        handles.push(handle);
    }

    let mut grand_total = 0;
    for handle in handles {
        let partial = handle.join().expect("thread ย่อยไม่ควร panic ในตัวอย่างนี้");
        grand_total += partial;
    }

    println!("ยอดขายรวมทั้งหมดจากทุก thread: {grand_total} บาท");

    // ตรวจสอบผลลัพธ์: คำนวณแบบ single-thread ธรรมดาต้องได้ค่าเท่ากัน
    let expected: i32 = generate_sales_data().iter().sum();
    assert_eq!(grand_total, expected);
    println!("ตรวจสอบผ่าน: ผลลัพธ์ตรงกับการคำนวณแบบ single-thread ({expected} บาท)");
}
```

รันจริงได้ผลลัพธ์นี้:

```
จำนวนรายการยอดขายทั้งหมด: 20 รายการ
thread 0: ประมวลผล 5 รายการ ผลรวมย่อย = 6850
thread 1: ประมวลผล 5 รายการ ผลรวมย่อย = 6840
thread 2: ประมวลผล 5 รายการ ผลรวมย่อย = 6850
thread 3: ประมวลผล 5 รายการ ผลรวมย่อย = 7250
ยอดขายรวมทั้งหมดจากทุก thread: 27790 บาท
ตรวจสอบผ่าน: ผลลัพธ์ตรงกับการคำนวณแบบ single-thread (27790 บาท)
```

(ลำดับบรรทัด `thread N: ประมวลผล...` อาจสลับกันได้ในการรันครั้งต่อ ๆ ไป ตามที่อธิบายไว้ในหัวข้อ 37.6 — แต่ตัวเลข
`ยอดขายรวมทั้งหมด` และผลการ `assert_eq!` จะเหมือนกันทุกครั้งเสมอ เพราะการบวกเลขไม่ขึ้นกับลำดับ)

มาดูว่าทำไม pattern นี้ปลอดภัยและถูกต้องอย่างสมบูรณ์:

- **`split_into_chunks` รับ `data: Vec<i32>` by value** — ไม่ใช่ `&Vec<i32>` — เพราะเราตั้งใจ**ย้าย** element
  ของมันออกไปเป็นก้อนย่อย ๆ ผ่าน `data.chunks(chunk_size)` (ให้ `&[i32]` แต่ละก้อน) แล้ว `.to_vec()` ยึด ownership
  ของแต่ละก้อนเป็น `Vec<i32>` ใหม่ที่แยกกันสมบูรณ์ (ไม่มีการแบ่ง reference กันข้าม chunk เลย — แต่ละ `Vec` ใหม่
  เป็นเจ้าของข้อมูลของตัวเอง 100%)
- **`chunks.into_iter().enumerate()`** — `.into_iter()` (ไม่ใช่ `.iter()`) เพื่อ**ยึด ownership** ของแต่ละ
  `Vec<i32>` chunk ออกมาทีละก้อน ให้พร้อมสำหรับ `move` เข้า closure ในบรรทัดถัดไปได้เลย ถ้าใช้ `.iter()` แทน
  จะได้ `&Vec<i32>` ซึ่งไม่ใช่ `'static` แล้วจะเจอ E0373 แบบเดียวกับหัวข้อ 37.5 ทันที
- **`move || { ... chunk ... }`** — แต่ละ closure ยึด `chunk` (ของตัวเอง คนละก้อนกับ thread อื่น) และ `chunk_id`
  เข้ามาเป็นเจ้าของเต็มตัว พิสูจน์ได้ตั้งแต่ compile time ว่าไม่มี thread ไหนแตะข้อมูลของ thread อื่นเลย — **นี่
  คือเหตุผลที่โจทย์นี้ไม่ต้องใช้ `Mutex` เลย**: มันไม่ใช่โจทย์ "แชร์ข้อมูลเดียวกัน" (แบบตัวนับในหัวข้อ 37.10)
  แต่เป็นโจทย์ **"แบ่งข้อมูลแยกกันคนละก้อน ประมวลผลแยกกัน แล้วรวมผลลัพธ์ทีหลัง"** ซึ่งเป็นรูปแบบที่พบบ่อยมากในงาน
  ประมวลผลข้อมูลจริง (เรียกกันว่า **"embarrassingly parallel"** — งานที่แบ่งคู่ขนานได้ง่ายมากเพราะแต่ละส่วนไม่
  ขึ้นกับกัน) และเป็นกรณีที่ `thread::spawn` + `move` + `join` เพียวๆ ก็เพียงพอแล้วโดยไม่ต้องใช้เครื่องมือ
  synchronization ใด ๆ เพิ่มเติมเลย
- **การรวมผลลัพธ์ (`grand_total += partial`) เกิดขึ้นที่ thread หลักเท่านั้น หลังจาก join ทุก thread แล้ว** —
  ไม่มีการบวกสะสมข้าม thread พร้อมกันเลย (ต่างจากตัวนับที่แชร์กันในหัวข้อ 37.10) เพราะแต่ละ thread แค่ return
  ผลรวมย่อยของตัวเองออกมาผ่าน `JoinHandle<i32>` แล้วให้ thread หลักที่ทำงานคนเดียว (ไม่มีคู่แข่ง) เป็นคนบวกรวม
  ทีหลัง — จุดนี้คือกุญแจสำคัญที่ทำให้ **fork-join pattern แบบนี้ไม่มี data race ได้โดยไม่ต้องใช้ lock เลย**: การ
  "join" (รวมผลลัพธ์) เกิดขึ้น**หลัง**การ "fork" (แยกงาน) จบสมบูรณ์แล้วเท่านั้น ไม่มีจังหวะไหนที่สอง thread พยายาม
  เขียนตัวแปรตัวเดียวกันพร้อมกันเลย
- **`assert_eq!` ท้ายโปรแกรม** ยืนยันว่าผลลัพธ์จากการคำนวณแบบคู่ขนานตรงกับการคำนวณแบบ single-thread เป๊ะ ๆ —
  หลักการนี้สำคัญมากในการเขียนโปรแกรม concurrent จริง: **ผลลัพธ์ต้องถูกต้องเหมือนกันไม่ว่าจะรันแบบ single-thread
  หรือ multi-thread** (correctness ไม่ควรขึ้นกับจำนวน thread) ความคู่ขนานควรเป็นแค่เรื่อง**ประสิทธิภาพ** (ทำงาน
  เร็วขึ้นเพราะใช้หลาย CPU core พร้อมกัน) ไม่ใช่เรื่องที่ทำให้ผลลัพธ์เปลี่ยนไป

#### ตัวแปรที่ดีกว่า: เลือกจำนวน Thread ตามจำนวน CPU จริง ไม่ Hardcode

ตัวอย่างข้างบน hardcode `num_threads = 4` ไว้ตรง ๆ เพื่อความง่ายต่อการอธิบาย แต่โค้ดจริงที่ดีกว่าควรใช้
`thread::available_parallelism()` ที่เรียนไปในหัวข้อ 37.2 เพื่อปรับจำนวน thread ให้เหมาะกับเครื่องที่รันจริง
โดยอัตโนมัติ:

```rust
use std::thread;

fn main() {
    let sales_data = generate_sales_data();

    // เลือกจำนวน thread แบบไดนามิกตามจำนวน CPU จริงของเครื่อง แทนที่จะ hardcode
    let num_threads = thread::available_parallelism()
        .map(|n| n.get())
        .unwrap_or(1)
        .min(sales_data.len()); // ไม่ spawn thread มากกว่าจำนวนข้อมูลที่มี (ไม่มีประโยชน์ และก้อนสุดท้ายจะว่างเปล่า)

    println!("จะใช้ {num_threads} thread ตามจำนวน CPU ที่ตรวจพบ");

    let chunks = split_into_chunks(sales_data, num_threads);
    let handles: Vec<_> = chunks
        .into_iter()
        .map(|chunk| thread::spawn(move || chunk.iter().sum::<i32>()))
        .collect();

    let grand_total: i32 = handles.into_iter().map(|h| h.join().unwrap()).sum();
    println!("ยอดขายรวม: {grand_total} บาท");
}
```

(ฟังก์ชัน `generate_sales_data` และ `split_into_chunks` เหมือนกับที่ประกาศไว้ในตัวอย่างก่อนหน้าทุกประการ — ตัด
ออกในที่นี้เพื่อความกระชับ) รันจริงบนเครื่องที่ใช้เขียนบทนี้ (ที่มี 4 logical CPU) ได้:

```
จะใช้ 4 thread ตามจำนวน CPU ที่ตรวจพบ
ยอดขายรวม: 27790 บาท
```

`.min(sales_data.len())` ป้องกันกรณีข้อมูลมีน้อยกว่าจำนวน CPU (เช่นมีข้อมูลแค่ 2 รายการแต่เครื่องมี 8 core) —
ถ้าไม่ใส่ `.min()` ไว้ `split_into_chunks` อาจสร้าง chunk เปล่า ๆ ออกมาซึ่งไม่มีประโยชน์ (spawn thread ขึ้นมาเปล่า
ๆ แค่เพิ่มต้นทุนโดยไม่ได้งานอะไรเพิ่ม) — นี่คือรายละเอียดเล็ก ๆ ที่สะท้อนบทเรียนจากหัวข้อ 37.2 เรื่องต้นทุนของการ
สร้าง thread: **spawn เท่าที่จำเป็นจริง ๆ เท่านั้น ไม่ใช่ spawn ให้มากที่สุดเท่าที่จะทำได้**

## กับดักที่พบบ่อย (Common Pitfalls)

### 1. ลืม `move` — เจอ E0373 ทุกครั้งที่ Closure แตะตัวแปร Local

นี่คือ error ที่มือใหม่ทุกคนต้องเจอตอนเขียน `thread::spawn` ครั้งแรก ๆ (อธิบายเต็มรูปแบบแล้วในหัวข้อ 37.5):

```rust
use std::thread;

fn main() {
    let message = String::from("สวัสดีจาก thread");
    let handle = thread::spawn(|| {
        println!("{message}");
    });
    handle.join().unwrap();
}
```

```
error[E0373]: closure may outlive the current function, but it borrows `message`, which is owned by the current function
 --> src/main.rs:5:32
  |
5 |     let handle = thread::spawn(|| {
  |                                ^^ may outlive borrowed value `message`
6 |         println!("{message}");
  |                    ------- `message` is borrowed here
  |
help: to force the closure to take ownership of `message` (and any other referenced variables), use the `move` keyword
  |
5 |     let handle = thread::spawn(move || {
  |                                ++++
```

**วิธีแก้**: เพิ่ม `move` เข้าไปหน้า closure เสมอเมื่อมันจะถูกส่งเข้า `thread::spawn` และ body ของมันแตะตัวแปร
local ใด ๆ จาก scope รอบตัวมัน — ถ้า closure ไม่แตะตัวแปร local เลย (เช่น `thread::spawn(|| println!("สวัสดี"))`
ที่ไม่ capture อะไรเลย) จะไม่มีปัญหานี้และไม่ต้องใส่ `move` ก็ได้ (แต่ใส่ไว้ก็ไม่ผิด เป็นธรรมเนียมที่หลายคนทำเพื่อ
ความชัดเจนว่า "closure นี้ไม่ได้ยืมอะไรจากข้างนอกแน่ ๆ")

### 2. คิดว่า `move` แก้ปัญหา "แชร์ข้อมูลข้าม Thread" ได้ด้วย

อธิบายละเอียดแล้วในหัวข้อ 37.10 — สรุปสั้น ๆ ที่นี่: `move` แก้ปัญหา **ownership/lifetime** เท่านั้น มันทำให้แต่ละ
thread ได้ **สำเนา** (ถ้า type เป็น `Copy`) หรือ **ยึด ownership เต็มตัว** (ถ้าไม่ใช่ `Copy`) ของค่าที่ capture มา
— ไม่ว่ากรณีไหนก็ตาม **ค่านั้นจะไม่ถูก "แชร์" กับ thread อื่นอีกต่อไป** ถ้าโจทย์ของคุณต้องการให้หลาย thread เห็น
การเปลี่ยนแปลงของกันและกันจริง ๆ (เช่นตัวนับที่สะสมค่าข้าม thread) `move` เพียว ๆ **ไม่มีทางทำได้** ต้องใช้
`Arc<Mutex<T>>` (Part 39) หรือส่งข้อมูลผ่าน channel (Part 38) แทน

### 3. พยายามใช้ `Rc<RefCell<T>>` ข้าม Thread — เจอ E0277 เพราะ `Rc<T>` ไม่ `Send`

อธิบายละเอียดแล้วในหัวข้อ 37.10 — สรุปสั้น ๆ: `Rc<T>` และ `RefCell<T>` (จาก Part 28) ถูกออกแบบมาสำหรับ
single-thread โดยเฉพาะ ไม่ implement `Send` เพราะตัวนับ/ตัวตรวจสอบภายในของมันไม่ thread-safe:

```
error[E0277]: `Rc<RefCell<i32>>` cannot be sent between threads safely
  = help: within `{closure@...}`, the trait `Send` is not implemented for `Rc<RefCell<i32>>`
```

**วิธีแก้**: เปลี่ยนเป็น `Arc<Mutex<T>>` (Part 39) ซึ่งใช้ atomic operations สำหรับตัวนับ และ OS-level lock
สำหรับป้องกันการแก้ไขข้อมูลพร้อมกัน ทำให้ปลอดภัยข้าม thread ได้จริง

### 4. เรียก `.join().unwrap()` โดยไม่คิดว่า Thread ลูกอาจ Panic — Panic ลามมาที่ Thread หลักด้วย

`.unwrap()` บน `Result` ที่เป็น `Err` จะทำให้ **thread ที่เรียก `.unwrap()` นั้น panic ต่อ** — ถ้า thread หลัก
เรียก `handle.join().unwrap()` แล้ว thread ลูก panic ไปแล้ว thread หลักก็จะ panic ตามไปด้วย (ซึ่งถ้าไม่มีใครจับ
panic ของ thread หลักอีกที โปรแกรมทั้งหมดจะปิดตัวจริง ๆ):

```rust
use std::thread;

fn main() {
    let handle = thread::spawn(|| {
        panic!("เกิดปัญหาใน thread ลูก");
    });

    let _ = handle.join().unwrap(); // ไม่ handle Err -> panic ซ้ำที่ main
    println!("บรรทัดนี้ไม่มีทางถูกพิมพ์");
}
```

รันจริงได้:

```
thread '<unnamed>' panicked at src/main.rs:5:9:
เกิดปัญหาใน thread ลูก
note: run with `RUST_BACKTRACE=1` environment variable to display a backtrace

thread 'main' panicked at src/main.rs:8:27:
called `Result::unwrap()` on an `Err` value: Any { .. }
note: run with `RUST_BACKTRACE=1` environment variable to display a backtrace
```

โปรแกรมจบด้วย exit code 101 (panic) — ต่างจากตัวอย่างในหัวข้อ 37.9 ที่ใช้ `match` แล้วโปรแกรมทำงานต่อได้ปกติ
(exit code 0) โดยสิ้นเชิง **`.unwrap()` บน `.join()` เหมาะสำหรับกรณีที่คุณ "ไม่คาดหวัง" ให้ thread panic เลยจริง ๆ
และยินดีให้โปรแกรมทั้งหมดล่มตามไปถ้ามันเกิดขึ้น** (เช่นตัวอย่างสั้น ๆ ในบทเรียน หรือโปรแกรมที่ไม่มีทางกู้คืนได้
อยู่แล้วถ้า thread สำคัญพัง) แต่ในโปรแกรมจริงที่ต้องทนทานต่อความล้มเหลว ควร `match` หรือใช้ `if let Err(e) = ...`
เพื่อบันทึก log แล้วทำงานต่อแบบที่เห็นในหัวข้อ 37.9

### 5. ปล่อย `JoinHandle` ทิ้งโดยไม่เก็บไว้เลย (ไม่ join) — Thread อาจถูกตัดจบก่อนทำงานเสร็จ

อธิบายละเอียดแล้วในหัวข้อ 37.3 — สรุปสั้น ๆ: ถ้า spawn thread แล้วไม่เก็บ `JoinHandle` ไว้เลย (หรือเก็บไว้แต่ไม่
เรียก `.join()` ก่อนโปรแกรมจบ) thread ลูกจะกลายเป็น **"detached"** (แยกตัวออกไปทำงานเป็นอิสระ) และมีความเสี่ยงสูง
ที่จะถูกตัดจบกลางทางถ้า `main()` จบไปก่อน — ให้เก็บ `JoinHandle` ไว้ใน `Vec` เสมอเมื่อ spawn หลาย thread และ join
ให้ครบทุกตัวก่อนจบโปรแกรม เว้นแต่คุณ**ตั้งใจ**ให้ thread นั้นทำงานเป็น background แยกอิสระโดยไม่สนใจว่ามันจะทำ
จบหรือไม่ (ซึ่งเป็นกรณีที่พบน้อยกว่ามากในโปรแกรมทั่วไป)

### 6. ใช้ `thread::sleep` เป็นเครื่องมือ Synchronize แทน Lock/Channel จริง

เห็นตัวอย่างในหัวข้อ 37.8 ว่า `sleep` ทำให้ลำดับการทำงานเดาได้ในการสาธิต — แต่ **ห้ามใช้เทคนิคนี้ในโปรแกรมจริง**
เพื่อ "หวังว่า" thread หนึ่งจะเสร็จก่อนอีกตัว (เช่น `thread::sleep(Duration::from_millis(100))` แล้วสมมติว่า
thread อื่นต้องทำงานเสร็จภายใน 100ms แน่ ๆ) เพราะเวลาที่ thread ใช้จริงขึ้นกับ load ของ CPU ตอนนั้น ซึ่งไม่แน่นอน
บนเครื่องที่ช้ากว่าหรือมี load สูงกว่า สมมติฐานนี้อาจผิดได้เสมอ นำไปสู่บั๊กแบบ intermittent ที่หายากพอ ๆ กับ
Heisenbug ในหัวข้อ 37.1 — ใช้ `.join()` (ถ้าต้องการรอให้จบแน่ ๆ), channel (Part 38, ถ้าต้องการส่งสัญญาณ/ข้อมูล),
หรือ `Mutex`/`Condvar` (Part 39) แทนเสมอเมื่อต้องการควบคุมลำดับการทำงานจริง ๆ

### 7. Spawn Thread ใหม่สำหรับงานเล็ก ๆ ในลูปที่ทำงานถี่มาก — Overhead มากกว่าประโยชน์

จากหัวข้อ 37.2 เราเรียนไปแล้วว่า `thread::spawn` สร้าง **OS thread จริง** ซึ่งมีต้นทุนไม่ใช่ศูนย์ (ขอ stack memory
ใหม่, ลงทะเบียนกับ OS scheduler) กับดักที่พบบ่อยในหมู่ผู้เริ่มเขียน concurrency คือเห็นว่า `thread::spawn` "ทำให้
งานเร็วขึ้น" แล้วเลย spawn thread ใหม่**ในทุกรอบของลูปที่ทำงานถี่มาก** สำหรับงานที่เบามาก เช่น:

```rust
use std::thread;
use std::time::Instant;

fn main() {
    let n: usize = 10_000;

    // วิธีที่ผิด: spawn thread ใหม่หนึ่งตัวต่องานหนึ่งงาน ทั้งที่งานแต่ละอันเบามาก (บวกเลขครั้งเดียว)
    let start = Instant::now();
    let mut handles = Vec::with_capacity(n);
    for i in 0..n {
        handles.push(thread::spawn(move || i + 1));
    }
    let mut total_threaded: usize = 0;
    for h in handles {
        total_threaded += h.join().unwrap();
    }
    let threaded_elapsed = start.elapsed();

    // วิธีเทียบ: loop ธรรมดาบน thread เดียว ทำงานเดียวกันทุกประการ
    let start2 = Instant::now();
    let mut total_single: usize = 0;
    for i in 0..n {
        total_single += i + 1;
    }
    let single_elapsed = start2.elapsed();

    println!("แบบ spawn thread ทีละงาน ({n} thread): {threaded_elapsed:?} (ผลรวม {total_threaded})");
    println!("แบบ loop ธรรมดา:                    {single_elapsed:?} (ผลรวม {total_single})");
}
```

รันจริง 3 ครั้งติดกันได้ผลลัพธ์ (ตัวเลขเวลาแน่นอนจะต่างกันไปตามเครื่องที่รัน แต่**สัดส่วนความต่างระดับล้านเท่า**นี้
สอดคล้องกันเสมอ — เครื่องที่ใช้เขียนบทนี้มี 4 CPU core):

```
แบบ spawn thread ทีละงาน (10000 thread): 411.34823ms (ผลรวม 50005000)
แบบ loop ธรรมดา:                    57ns (ผลรวม 50005000)
```

ผลรวมตรงกันทั้งสองวิธี (50005000 ทั้งคู่ — ถูกต้อง ไม่มีบั๊ก) แต่เวลาที่ใช้ต่างกันมหาศาล: **ประมาณ 57 นาโนวินาที
เทียบกับ 411 มิลลิวินาที** — คิดเป็นสัดส่วนหลาย**ล้านเท่า**สำหรับงานที่เนื้อแท้แล้วเบามาก (บวกเลขครั้งเดียว) ต้นทุน
ของการสร้าง/ทำลาย OS thread 10,000 ตัว (แต่ละตัวต้อง allocate stack, ลงทะเบียนกับ OS scheduler, แล้ว join) ครอบงำ
เวลาทั้งหมดไปหมด — งานจริง (`i + 1`) แทบไม่มีผลต่อเวลารวมเลยเมื่อเทียบกับ overhead ของการจัดการ thread

**วิธีแก้**: ใช้ pattern แบบ chunk processing ในหัวข้อ 37.11 เสมอ (แบ่งงานจำนวนมากออกเป็น**ก้อนใหญ่**เท่ากับจำนวน
CPU ที่มี ไม่ใช่ spawn ทีละงานเล็ก ๆ) หรือถ้างานมีจำนวนมากและแต่ละงานเล็กจริง ๆ ให้พิจารณาใช้ thread pool (เช่น
crate `rayon` สำหรับงาน data-parallel ที่พบบ่อยมาก หรือ async runtime อย่าง Tokio สำหรับงาน I/O-bound ที่จะเรียน
ใน Part 46-50) แทนการสร้าง raw OS thread เอง

## แบบฝึกหัด (Exercises)

1. **(ง่าย) แก้ Compile Error**: เขียนฟังก์ชัน `main` ที่สร้างตัวแปร `city = String::from("เชียงใหม่")` แล้ว
   `thread::spawn` closure ที่ print `"อากาศวันนี้ที่ {city} สดใส"` จากนั้น `.join()` ให้ถูกต้อง โค้ดเริ่มต้นของ
   คุณจะไม่ compile ผ่าน (เจอ E0373) — หน้าที่ของคุณคือแก้ไขให้ compile ผ่านและรันได้ถูกต้อง
   *(hint: ปัญหาคือ closure ยืม `city` แต่ต้องเป็น `'static` — วิธีแก้คือใส่ `move` หน้า closure)*

2. **(กลาง) หลาย Thread คำนวณ Factorial**: เขียนโปรแกรมที่ spawn 6 thread โดย thread ตัวที่ `n` (n ตั้งแต่ 1
   ถึง 6) คำนวณค่า factorial ของ `n` (`n!`) แล้ว return ค่านั้นกลับผ่าน `JoinHandle<u64>` เก็บ handle ทั้งหมดไว้
   ใน `Vec` จากนั้น join ทุก thread รวบรวมผลลัพธ์เป็น `Vec<u64>` เรียงตามหมายเลข thread (1! ถึง 6!) แล้ว print
   ออกมาให้ตรงกับ `[1, 2, 6, 24, 120, 720]`
   *(hint: ใช้ `move` capture ตัวแปร `n` จาก loop เข้าไปในแต่ละ closure; คำนวณ factorial ด้วย
   `(1..=n).product()`)*

3. **(ยาก) จำลอง Race Condition แล้วแก้ด้วยการออกแบบใหม่ (ไม่ใช้ Mutex)**: เขียนโปรแกรมที่มี `Vec<i32>` ของคะแนน
   สอบนักเรียน 100 คน ต้องการคำนวณ (ก) ค่าเฉลี่ย (ข) คะแนนสูงสุด (ค) จำนวนคนที่สอบผ่าน (คะแนน >= 50) โดยใช้ 3
   thread แยกกัน ให้แต่ละ thread รับ **สำเนา** ของข้อมูลที่จำเป็น (ไม่ใช่แชร์ mutable reference เดียวกัน) คำนวณค่า
   ของตัวเอง แล้ว return ผลลัพธ์กลับมาผ่าน `JoinHandle` ที่ thread หลัก join แล้ว print สรุปทั้งสามค่า
   *(hint: `Vec<i32>` implement `Clone` — ให้แต่ละ thread `.clone()` ข้อมูลที่ต้องใช้ก่อน `move` เข้า closure
   ของตัวเอง เพราะแต่ละ thread แค่ "อ่าน" ข้อมูลไปคำนวณ ไม่ต้องแก้ไขข้อมูลต้นฉบับเลย โจทย์นี้จงใจให้เห็นว่าการ
   "อ่านอย่างเดียว" ไม่จำเป็นต้องมี lock เลย ต่างจากโจทย์ที่ต้อง "เขียน" ร่วมกัน)*

4. **(ยากมาก / ประยุกต์ใช้งานจริง) Parallel Word Counter**: เขียนโปรแกรมที่มี `Vec<String>` แทนบรรทัดข้อความ
   จำนวน 40 บรรทัด (สร้างข้อความจำลองเอง หรือใช้ข้อความซ้ำ ๆ ก็ได้) ต้องการนับจำนวนคำทั้งหมดในทุกบรรทัดรวมกัน
   โดยแบ่งบรรทัดออกเป็น 4 ก้อนเท่า ๆ กัน (ใช้ pattern เดียวกับ `split_into_chunks` ในหัวข้อ 37.11) spawn 4 thread
   ให้แต่ละ thread นับจำนวนคำใน chunk ของตัวเอง (ใช้ `.split_whitespace().count()` ของแต่ละบรรทัดบวกกัน) แล้ว
   join รวมผลลัพธ์เป็นยอดรวมสุดท้าย จากนั้นเพิ่ม `assert_eq!` ตรวจสอบว่าผลลัพธ์ตรงกับการนับแบบ single-thread
   ธรรมดา (loop ตรงไปตรงมาไม่มี thread) เพื่อพิสูจน์ความถูกต้อง — ทำเวลา (ใช้ `std::time::Instant::now()` และ
   `.elapsed()`) เทียบกันระหว่างสองวิธีด้วยข้อมูลจำลองขนาดใหญ่ขึ้น (เช่น 400,000 บรรทัด) เพื่อสังเกตว่า
   multi-thread เร็วขึ้นจริงหรือไม่บนเครื่องของคุณ (คำเตือน: ผลอาจไม่เร็วขึ้นเสมอไปถ้าข้อมูลเล็กเกินไป เพราะการ
   สร้าง thread เองก็มี overhead)
   *(hint: `String` ไม่ implement `Copy` แต่ `Vec<String>` implement `Clone` — เหมือนหัวข้อ 37.11 ให้
   `split_into_chunks` รับ `Vec<String>` by value แล้ว `.to_vec()` สร้างก้อนย่อยที่เป็นเจ้าของ `String` ของ
   ตัวเอง 100% ก่อน `move` เข้า thread)*

## สรุป

บทนี้เปิดประตูสู่โลกของ concurrency ใน Rust อย่างเป็นทางการ โดยเริ่มจากการทำความเข้าใจ **data race** — ปัญหาที่
ทำให้ concurrency เป็นเรื่องอันตรายในภาษาส่วนใหญ่ (undefined behavior ใน C/C++, silent bug ในภาษาที่มี garbage
collector) แล้วตั้งคำกล่าวอ้าง **"fearless concurrency"** ของ Rust เป็นแกนหลักของบท ก่อนพิสูจน์มันทีละขั้นด้วย
โค้ดจริงที่ compile และรันได้จริงทั้งหมด:

- `std::thread::spawn()` สร้าง thread ใหม่จาก closure ที่ implement `FnOnce() -> T` (เชื่อมกับ Part 24) คืนค่า
  เป็น `JoinHandle<T>` ที่ใช้ `.join()` รอผลลัพธ์และรับค่า return กลับมาได้
- ถ้าไม่ `.join()` thread ลูกอาจถูกตัดจบก่อนทำงานเสร็จเมื่อ `main()` จบ — เราพิสูจน์ด้วยการรันจริง 5 ครั้งเห็น
  ผลลัพธ์ของ thread ลูกหายไปทุกครั้งเมื่อไม่ join เทียบกับครบถ้วนทุกครั้งเมื่อ join
- `thread::spawn` ต้องการ closure ที่เป็น `'static` เสมอ เพราะ thread ลูกมีอายุเป็นอิสระจาก scope ที่สร้างมัน —
  นี่คือการนำกฎ borrow checker จาก Part 6-7 มาบังคับใช้ข้าม thread และเป็นเหตุผลที่ต้องใช้ `move` closure (ปิด
  คำใบ้ที่ Part 24 ทิ้งไว้อย่างสมบูรณ์) พร้อมเห็น error จริง **E0373** และวิธีแก้
  ด้วยการ`move`ยึด ownership เข้าไปในตัว closure
- spawn หลาย thread เก็บ `JoinHandle` ไว้ใน `Vec` แล้ว join ทั้งหมดทีหลัง เป็น pattern พื้นฐานที่ใช้บ่อยที่สุด
  พร้อมส่งค่ากลับผ่าน `JoinHandle<T>` ทำ fork-join pattern ได้เต็มรูปแบบ
- panic ใน thread ลูกถูกจับไว้ที่ขอบของ thread นั้นผ่าน `thread::Result<T>` ไม่ทำให้ทั้งโปรแกรม crash ตราบใดที่
  thread หลักจัดการ `Err` อย่างเหมาะสม (ไม่ `.unwrap()` ทับมันซ้ำ)
- `thread::sleep`/`Duration` เป็นเครื่องมือช่วยสาธิต/หน่วงเวลา ไม่ใช่เครื่องมือ synchronize ที่ควรพึ่งพาจริงจัง
- ที่สำคัญที่สุด: บทนี้แสดงให้เห็นว่า **`move` แก้ปัญหา ownership ข้าม thread ได้ แต่ไม่ได้แก้ปัญหา "แชร์ mutable
  state ข้าม thread"** — เราเห็น compile error จริงถึง 3 ตัว (E0373, E0499, E0502) ตอนพยายามแชร์ mutable
  reference ตรง ๆ และเห็น E0277 ตอนพยายามเอา `Rc<RefCell<T>>` จาก Part 28 มาใช้ข้าม thread (เพราะไม่
  implement `Send`) — พิสูจน์คำเตือนของ Part 28 ให้เป็นรูปธรรม
- ตัวอย่างใหญ่ปิดท้าย (parallel chunk processing ของข้อมูลยอดขาย) แสดงให้เห็นว่าโจทย์ประเภท **"แบ่งงานแยกกันทำ
  ไม่มีจุดร่วม"** (embarrassingly parallel) แก้ได้สมบูรณ์ด้วย `spawn` + `move` + `join` เพียว ๆ โดยไม่ต้องพึ่ง
  เครื่องมือ synchronization เพิ่มเติมเลย

บทนี้จงใจปิดท้ายด้วยปัญหาที่ยังไม่มีคำตอบ: **จะให้หลาย thread แชร์และแก้ไขข้อมูลชุดเดียวกันร่วมกันได้อย่างไร**
สองบทถัดไปจะตอบคำถามนี้ด้วยสองแนวทางที่ต่างกัน — **Part 38 (Channels)** สอนแนวทาง **message passing** ที่หลีก
เลี่ยงการแชร์ mutable state ตั้งแต่ต้น ด้วยการส่งข้อมูลผ่านกันเป็น "ข้อความ" ระหว่าง thread แทน ส่วน **Part 39
(Mutex, Arc และ Shared-State Concurrency)** สอนแนวทาง **shared-state** ที่ยอมให้แชร์ข้อมูลได้จริง แต่ควบคุมด้วย
lock ที่ compiler การันตีว่าคุณลืมล็อกไม่ได้ — ทั้งสองบทจะพึ่งพาความเข้าใจเรื่อง `thread::spawn`, `move`, และ
`JoinHandle` จากบทนี้เป็นพื้นฐานตลอดทาง ก่อนที่ **Part 40 (Send, Sync)** จะเฉลยกลไกเบื้องหลังทั้งหมดว่าทำไมทุก
อย่างในสามบทนี้ compile ผ่านได้อย่างปลอดภัยในเชิง type system
