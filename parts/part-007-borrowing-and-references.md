# Part 7: Borrowing และ References

> โมดูล: พื้นฐานภาษา Rust (Core Language Fundamentals) | ระดับ: พื้นฐาน | เวลาโดยประมาณ: 150 นาที

## เป้าหมายของบทเรียน

หลังจากจบบทนี้ คุณจะสามารถ:

- อธิบายได้ว่าทำไม ownership เพียงอย่างเดียว (จาก Part 6) ยังไม่พอสำหรับเขียนโปรแกรมที่ใช้งานได้จริง และ reference แก้ปัญหานี้อย่างไร
- ใช้ immutable reference (`&T`) เพื่อ "ยืม" ค่าไปใช้ในฟังก์ชันโดยที่เจ้าของเดิมยังเก็บ ownership ไว้ได้เหมือนเดิม
- ใช้ mutable reference (`&mut T`) เพื่อแก้ไขค่าของผู้อื่นผ่านการยืมได้ โดยไม่ต้องโอน ownership
- ท่องจำและอธิบายเชิงลึกได้ว่าทำไม **กฎของ borrowing ทั้งสองข้อ** ถึงสำคัญ โดยเฉพาะกฎ "mutable ได้แค่หนึ่งตัว หรือ immutable ได้หลายตัว แต่ไม่ทั้งสองพร้อมกัน" ที่ป้องกัน data race ได้ตั้งแต่ compile time
- อ่านและแก้ error จาก borrow checker ที่พบบ่อยที่สุด (`E0499`, `E0502`, `E0106`) ได้ด้วยตัวเอง
- เข้าใจว่า Non-Lexical Lifetimes (NLL) ทำให้ borrow checker สมัยใหม่ "ฉลาด" กว่าที่มือใหม่หลายคนกลัวกันไว้มาก
- อธิบายได้ว่าทำไม dangling reference ถึงเกิดขึ้นไม่ได้เลยในโค้ด Rust ที่ compile ผ่าน และรู้ว่าเรื่องนี้เกี่ยวข้องกับ "lifetime" ที่จะเรียนเต็ม ๆ ใน Part หลัง ๆ

## ความรู้ที่ต้องมีมาก่อน

บทนี้ต่อยอดจาก **Part 6: Ownership เบื้องต้น** โดยตรงและหนักมาก แนะนำให้ทบทวนก่อนอ่านบทนี้ถ้ายังไม่แน่นใจ เพราะทุกแนวคิด
ในบทนี้ตั้งอยู่บนความเข้าใจเรื่อง ownership ทั้งหมด โดยเฉพาะ:

- **3 กฎของ ownership** จาก Part 6: (1) ทุกค่ามีเจ้าของเพียงหนึ่งเดียวในเวลาใดเวลาหนึ่ง (2) มีเจ้าของได้แค่หนึ่งคนในเวลาเดียวกัน
  (3) เมื่อเจ้าของหมด scope ค่านั้นจะถูก drop ทันที
- **Move semantics** — การส่งค่าที่ไม่ implement `Copy` (เช่น `String`) ให้ตัวแปรอื่นหรือฟังก์ชันอื่น จะ "ย้าย" ownership ไป
  ทำให้ตัวแปรต้นทางใช้งานต่อไม่ได้อีก (compiler จะฟ้อง error ทันทีถ้าพยายามใช้)
- **`.clone()`** — วิธี copy ข้อมูลบน heap แบบลึก (deep copy) เพื่อให้มีสอง ownership ที่แยกจากกันจริง ๆ แต่มี cost ด้าน
  performance ที่ต้องคิดให้ดีก่อนใช้
- **`Copy` trait** — ทำไม type ง่าย ๆ อย่าง `i32`, `f64`, `bool`, `char` ถึงไม่ถูก move แต่ถูก copy โดยอัตโนมัติแทน
- นอกจากนี้ยังใช้ความรู้จาก **Part 3** (ตัวแปร, `mut`, array `[T; N]`, tuple) และ **Part 4** (ฟังก์ชัน, parameter, return value,
  `for` loop) มาประกอบกันเป็นตัวอย่างตลอดบท

ถ้าคุณจำ "ปัญหา" ที่ Part 6 ทิ้งไว้ตอนจบได้ — คำถามที่ว่า **"ถ้าฟังก์ชันแค่ต้องการอ่านข้อมูล ไม่ได้ต้องการเป็นเจ้าของมันจริง ๆ
จะทำอย่างไรไม่ให้ ownership ถูกย้ายไปโดยไม่จำเป็น?"** — นั่นคือคำถามที่บทนี้จะตอบให้แบบละเอียดที่สุด

## เนื้อหา

### 7.1 ปัญหาที่ Ownership เพียงอย่างเดียวแก้ไม่ได้

ย้อนกลับไปที่ตัวอย่างคลาสสิกจาก Part 6: ฟังก์ชันที่รับ `String` เข้ามาเพื่อคำนวณความยาวของมัน

```rust
fn calculate_length(s: String) -> usize {
    s.len()
}

fn main() {
    let s1 = String::from("สวัสดี Rust");
    let len = calculate_length(s1); // s1 ถูก "move" เข้าไปในฟังก์ชัน ownership ย้ายไปแล้ว
    println!("ความยาวของ '{s1}' คือ {len}"); // ❌ ใช้ s1 ไม่ได้อีกแล้ว!
}
```

โค้ดนี้ **compile ไม่ผ่าน** ด้วย error ที่เราคุ้นเคยจาก Part 6:

```
error[E0382]: borrow of moved value: `s1`
 --> src/main.rs:7:38
  |
6 |     let len = calculate_length(s1);
  |                                 -- value moved here
7 |     println!("ความยาวของ '{s1}' คือ {len}");
  |                                       ^^ value borrowed here after move
  |
note: consider changing this parameter type in function `calculate_length` to borrow instead if owning the value isn't necessary
 --> src/main.rs:1:26
  |
1 | fn calculate_length(s: String) -> usize {
  |    ----------------    ^^^^^^ this parameter takes ownership of the value
  = note: this error originates in the macro `$crate::format_args_nl` (in Nightly builds, run with -Z macro-backtrace for more info)
help: consider cloning the value if the performance cost is acceptable
  |
6 |     let len = calculate_length(s1.clone());
  |                                  ++++++++
```

สังเกตว่า compiler เองก็แนะนำ hint สำคัญไว้ตรง ๆ เลยว่า **"consider changing this parameter type ... to borrow instead if
owning the value isn't necessary"** — นี่คือใจความสำคัญที่สุดของบทนี้ทั้งบท: ฟังก์ชัน `calculate_length` ไม่ได้ต้องการ
**เป็นเจ้าของ** `String` เลยจริง ๆ มันแค่อยากจะ "อ่าน" ความยาวของมันเท่านั้น การรับ `String` แบบเต็ม ๆ (by value) จึงเป็นการ
ออกแบบที่ "แรงเกินความจำเป็น" — เหมือนยืมหนังสือเพื่อนไปอ่านหนึ่งหน้า แต่ต้องเซ็นโอนกรรมสิทธิ์หนังสือทั้งเล่มให้ตัวเองก่อน

#### ทางแก้แบบเดียวที่มีถ้าไม่รู้จัก reference: คืนค่ากลับไปด้วย

ก่อนที่จะรู้จัก reference วิธีเดียวที่จะแก้ปัญหานี้ด้วยความรู้จาก Part 6 คือ **คืน ownership กลับไปให้ผู้เรียกด้วย** โดยห่อ
มันไว้ในค่าที่ return ออกมา:

```rust
fn calculate_length(s: String) -> (String, usize) {
    let length = s.len(); // อ่านความยาวได้ตามปกติ เพราะ s ยังเป็นเจ้าของอยู่ในฟังก์ชันนี้
    (s, length)           // ส่ง ownership ของ s กลับไปพร้อมกับผลลัพธ์ length
}

fn main() {
    let s1 = String::from("สวัสดี Rust");
    let (s1, len) = calculate_length(s1); // รับ ownership คืนมา พร้อมกับความยาว (shadowing s1 เดิม)
    println!("ความยาวของ '{s1}' คือ {len}"); // ✅ ใช้ s1 ได้ตามปกติ
}
```

โค้ดนี้ compile ผ่านและทำงานถูกต้อง แต่สังเกตว่า **มันน่าเกลียดมาก** เมื่อเทียบกับความตั้งใจเดิมที่ต้องการแค่ "อ่านความยาว"
เราต้อง:

1. เปลี่ยน return type ของฟังก์ชันจาก `usize` เดี่ยว ๆ ไปเป็น tuple `(String, usize)`
2. จำไว้ทุกครั้งที่เรียกฟังก์ชันว่าต้อง destructure ผลลัพธ์กลับมาเป็นสองส่วน
3. เขียน `(s, length)` ที่ท้ายฟังก์ชันแทนแค่ `length` ตรง ๆ

และปัญหานี้ **ยิ่งบานปลายขึ้นเรื่อย ๆ** เมื่อฟังก์ชันต้องอ่านค่าหลายตัว ลองดูตัวอย่างฟังก์ชันที่ต้องอ่าน `String` สองตัว
เพื่อรวมความยาว:

```rust
fn total_length(a: String, b: String) -> (String, String, usize) {
    let total = a.len() + b.len();
    (a, b, total) // ต้องคืน ownership ของทั้ง a และ b กลับไปด้วย ไม่งั้นผู้เรียกใช้ต่อไม่ได้
}

fn main() {
    let s1 = String::from("Hello");
    let s2 = String::from("Rust");
    let (s1, s2, total) = total_length(s1, s2); // destructure 3 ค่า เพื่อคำนวณสิ่งที่ควรจะง่ายมาก
    println!("{s1} + {s2} = {total} ตัวอักษรรวม");
}
```

ยิ่งฟังก์ชันรับพารามิเตอร์ที่ต้อง "อ่านอย่างเดียว" มากขึ้นเท่าไหร่ ความยุ่งยากของการคืนค่ากลับก็เพิ่มขึ้นเป็นเงาตามตัว —
ถ้าฟังก์ชันหนึ่งต้องอ่านค่า 5 ตัว เราจะต้องคืน tuple ที่มี 5+ สมาชิกกลับไปทุกครั้ง ทั้ง ๆ ที่ฟังก์ชันนั้นไม่ได้แก้ไขค่า
เหล่านั้นเลยแม้แต่นิดเดียว นี่คือปัญหาเชิง **ergonomics** (ความสะดวกในการเขียน/อ่านโค้ด) ที่ร้ายแรงมากถ้า Rust ไม่มีทางออก
ที่ดีกว่านี้ — และทางออกนั้นคือ **reference** ซึ่งเป็นหัวใจของบทนี้

### 7.2 References: การ "ยืม" ค่าโดยไม่ต้องเป็นเจ้าของ (`&T`)

Rust มี syntax พิเศษที่ให้คุณส่ง "ตัวชี้ไปยังค่า" (pointer to a value) แทนการส่งค่าจริงเข้าไปในฟังก์ชัน โดยที่ **ownership
ของค่านั้นยังคงอยู่กับเจ้าของเดิมเสมอ** สิ่งนี้เรียกว่า **reference** เขียนด้วยเครื่องหมาย `&` นำหน้า type หรือนำหน้าตัวแปร
กระบวนการส่ง reference แทนการส่งค่าจริงแบบนี้เรียกว่า **borrowing** (การยืม) — คำนี้สื่อความหมายตรงตัวมาก: คุณ "ยืม" สิทธิ์
เข้าถึงข้อมูลไปใช้ชั่วคราว แล้ว "คืน" มันให้เจ้าของเดิมเมื่อยืมเสร็จ (ในทางเทคนิคคือ reference หมด scope) โดยไม่มีการโอน
กรรมสิทธิ์เกิดขึ้นเลยตลอดกระบวนการ

มาแก้ตัวอย่าง `calculate_length` ด้วย reference:

```rust
fn calculate_length(s: &String) -> usize { // รับ &String (reference ไปยัง String) แทน String ตรง ๆ
    s.len() // เรียก method .len() ผ่าน reference ได้ตามปกติ — Rust auto-deref ให้เอง
}

fn main() {
    let s1 = String::from("สวัสดี Rust");
    let len = calculate_length(&s1); // ส่ง &s1 (reference ไปยัง s1) เข้าไป ไม่ใช่ s1 ตรง ๆ
    println!("ความยาวของ '{s1}' คือ {len}"); // ✅ s1 ยังใช้งานได้ตามปกติ! ไม่ถูก move
}
```

ผลลัพธ์:

```
ความยาวของ 'สวัสดี Rust' คือ 12
```

สังเกตความแตกต่างสำคัญ 2 จุดจากโค้ดเดิม:

1. **ที่ signature ของฟังก์ชัน**: พารามิเตอร์เปลี่ยนจาก `s: String` เป็น `s: &String` — บอก compiler ว่าฟังก์ชันนี้แค่
   "ยืม" `String` มาใช้ ไม่ได้ต้องการเป็นเจ้าของมัน
2. **ที่จุดเรียกใช้**: เราส่ง `&s1` (สร้าง reference ไปยัง `s1`) เข้าไป แทนที่จะส่ง `s1` ตรง ๆ

และที่สำคัญที่สุด: **`s1` ในฟังก์ชัน `main` ยังคงเป็นเจ้าของ `String` นั้นอยู่ตลอดเวลา** ไม่มีการ move เกิดขึ้นเลย เพราะสิ่งที่
ถูกส่งเข้าฟังก์ชันคือ "ตัวชี้เล็ก ๆ ที่บอกตำแหน่งของข้อมูล" ไม่ใช่ข้อมูลจริงหรือ ownership ของมัน

#### ภาพในหัวสำหรับ reference: ตัวชี้ที่ไม่มี ownership

เพื่อให้เห็นภาพชัดขึ้น ลองนึกถึง memory layout ของ `String` ที่เราเรียนจาก Part 6: `String` เก็บ pointer ไปยังข้อมูลบน heap,
ความยาว (`len`), และ capacity ไว้บน stack ส่วน reference อย่าง `&String` ก็เป็นแค่ **ตัวชี้อีกชั้นหนึ่ง** ที่ชี้ไปยังตำแหน่ง
ของตัวแปร `String` นั้นบน stack อีกที (ไม่ใช่ชี้ตรงไปที่ข้อมูลบน heap โดยตรง) พูดง่าย ๆ คือ:

```
s1 (บน stack)               ข้อมูลบน heap
┌─────────────┐             ┌───────────────────┐
│ ptr  ───────┼────────────▶│ ส วั ส ดี  R u s t │
│ len  = 12   │             └───────────────────┘
│ capacity = 12│
└─────────────┘
      ▲
      │ ชี้กลับมาที่ตำแหน่งของ s1
      │
┌─────────────┐
│  &s1 (reference)  │  ← ตัวแปร s ในฟังก์ชัน calculate_length ก็คือตัวนี้
└─────────────┘
```

`&s1` ไม่ได้แบก ownership ของอะไรเลยแม้แต่นิดเดียว — มันเป็นเพียง "ที่อยู่" (address) ที่บอกว่า "ข้อมูลจริงอยู่ที่ตัวแปร
`s1` นะ" เมื่อ reference นี้หมด scope (เมื่อฟังก์ชัน `calculate_length` จบลง) **จะไม่มีอะไรถูก drop เลย** เพราะ reference
ไม่ใช่เจ้าของ ไม่มีสิทธิ์ทำลายข้อมูล — เจ้าของตัวจริง (`s1` ใน `main`) เท่านั้นที่มีสิทธิ์นั้น และจะ drop ข้อมูลก็ต่อเมื่อ
`s1` เองหมด scope เท่านั้น

นี่คือเหตุผลที่ตัวอย่างข้างบน `s1` ยังใช้งานต่อได้ปกติหลังเรียก `calculate_length(&s1)` — เพราะไม่มีการ move เกิดขึ้นเลย
ตลอดกระบวนการ มีแต่การ "ให้ที่อยู่ชั่วคราว" ไปเท่านั้น

#### Dereference Operator (`*`): เมื่อไหร่ต้องใช้ เมื่อไหร่ไม่ต้อง

เครื่องหมาย `*` (asterisk) ในบริบทของ reference เรียกว่า **dereference operator** — มันทำหน้าที่ตรงข้ามกับ `&` ถ้า `&x`
คือ "สร้าง reference ไปยัง `x`" แล้ว `*r` (เมื่อ `r` เป็น reference) คือ "ดึงค่าจริงที่ `r` ชี้ไปกลับมา":

```rust
fn main() {
    let x = 5;
    let r = &x;

    println!("ค่าของ x ผ่าน r โดยตรง (ไม่ dereference): {r}"); // 5 — println! dereference ให้อัตโนมัติ
    println!("ค่าของ x ผ่านการ dereference ด้วยมือ: {}", *r);   // 5 — เหมือนกัน แค่เขียน * เอง

    assert_eq!(*r, x); // *r เท่ากับ x เป๊ะ ๆ — dereference คืนค่าจริงที่ reference ชี้ไป
    println!("*r เท่ากับ x จริง!");
}
```

คำถามที่มือใหม่สงสัยบ่อยที่สุดคือ **"แล้วทำไมตอนเรียก `s.len()` ผ่าน `&String` เมื่อกี้ เราไม่ต้องเขียน `(*s).len()` เลย?"**
คำตอบคือ Rust มีกลไกที่เรียกว่า **auto-deref (automatic dereferencing)** ทำงานเฉพาะตอน **เรียก method ผ่าน `.`** เท่านั้น
— compiler จะ dereference ให้อัตโนมัติกี่ชั้นก็ตามเท่าที่จำเป็นเพื่อหา method ที่ตรงกับชื่อที่เรียก แต่ **auto-deref จะ
ไม่ทำงานในสถานการณ์อื่น** เช่นการกำหนดค่าตรง ๆ หรือการเข้าถึงค่าดิบเพื่อคำนวณ ซึ่งคุณต้องเขียน `*` ด้วยตัวเองเสมอ

กฎง่าย ๆ ที่ใช้แยกแยะได้แม่นยำ:

| สถานการณ์ | ต้องเขียน `*` เองหรือไม่ |
|---|---|
| เรียก method ผ่าน `.` (เช่น `s.len()`, `s.push_str()`) | **ไม่ต้อง** — auto-deref ทำงานให้เสมอ |
| ใช้ใน `println!`/`format!` (macro พิมพ์ค่า) | **ไม่ต้อง** — trait `Display`/`Debug` ทำงานผ่าน reference ได้โดยตรง |
| แก้ไข/กำหนดค่าตรง ๆ ผ่าน `&mut T` (เช่น `*counter += 1`) | **ต้อง** — เพราะเป็นการเข้าถึงค่าจริงเพื่อเขียนทับ ไม่ใช่การเรียก method |
| เปรียบเทียบ/คำนวณค่าตัวเลขดิบ ๆ ที่ต้องได้ type `T` ไม่ใช่ `&T` | **ต้อง** ในหลายกรณี (แม้บางกรณี Rust จะช่วยผ่าน operator overload สำหรับ reference ให้บางส่วนอัตโนมัติ) |

เราจะเห็นตัวอย่างที่ต้องใช้ `*` อย่างชัดเจนอีกครั้งในหัวข้อ 7.4 (ฟังก์ชันที่แก้ไขค่าผ่าน `&mut i32`) และในหัวข้อ 7.9
(ฟังก์ชัน `apply_bonus` ที่ต้อง `*score += bonus`)

#### Immutable Reference ไม่ได้ขึ้นอยู่กับว่าตัวแปรต้นทางเป็น `mut` หรือไม่

จุดที่มือใหม่สับสนบ่อยมากอีกจุดหนึ่ง: **แม้ตัวแปรต้นทางจะประกาศด้วย `mut` ก็ตาม ถ้าคุณสร้าง reference แบบ `&T` (ไม่ใส่
`mut`) reference ตัวนั้นก็ยังคง "อ่านได้อย่างเดียว" เสมอ** — mutability ของ reference ขึ้นอยู่กับว่าคุณเขียน `&` หรือ
`&mut` ตอนสร้างมันเท่านั้น ไม่เกี่ยวกับว่าตัวแปรต้นทางเป็น `mut` หรือไม่:

```rust
fn main() {
    let mut x = 5; // x เป็น mut
    let r = &x;    // แต่สร้าง reference แบบ & (immutable) ไปยังมัน

    *r = 6; // ❌ พยายามเขียนผ่าน r ซึ่งเป็น immutable reference
    println!("{r}");
}
```

```
error[E0594]: cannot assign to `*r`, as `r` is a `&` reference
 --> src/main.rs:5:5
  |
5 |     *r = 6;
  |     ^^^^^^ `r` is a `&` reference, so the data it refers to cannot be written
  |
help: consider changing this to be a mutable reference
  |
3 |     let r = &mut x;
  |              +++
```

มองแบบเปรียบเทียบง่าย ๆ: **`mut` ของตัวแปรต้นทาง (`let mut x`) แค่บอกว่า "อนุญาตให้สร้าง `&mut` reference ไปยังมันได้"
ถ้าคุณเลือกไม่สร้าง (สร้าง `&` เฉย ๆ) reference ที่ได้ก็ยังอ่านได้อย่างเดียวอยู่ดี** พูดอีกแบบ: `mut` ที่ตัวแปรต้นทางคือ
"สิทธิ์ที่เปิดไว้ให้เลือกใช้" ส่วน `&` กับ `&mut` ตอนสร้าง reference คือ "การเลือกใช้สิทธิ์นั้นจริง ๆ หรือไม่" — คุณ
สามารถมีตัวแปร `mut` แล้วสร้าง reference แบบอ่านอย่างเดียวไปเรื่อย ๆ ได้ตามสบาย ตราบใดที่ไม่มีจุดใดพยายามเขียนผ่าน
reference ที่ไม่ใช่ `&mut` เท่านั้น

#### แก้ปัญหา "อ่านค่าหลายตัว" ด้วย reference: จบสวยงามกว่ามาก

กลับไปที่ตัวอย่าง `total_length` ที่น่าเกลียดจากหัวข้อก่อน มาแก้ด้วย reference:

```rust
fn total_length(a: &String, b: &String) -> usize {
    a.len() + b.len() // อ่านทั้งสองค่าผ่าน reference ไม่ต้องคืนอะไรกลับไปเลย
}

fn main() {
    let s1 = String::from("Hello");
    let s2 = String::from("Rust");

    let total = total_length(&s1, &s2);

    println!("{s1} + {s2} = {total} ตัวอักษรรวม"); // s1, s2 ใช้งานได้ตามปกติทั้งคู่
}
```

ผลลัพธ์:

```
Hello + Rust = 9 ตัวอักษรรวม
```

เทียบกับเวอร์ชันที่ต้องคืน tuple 3 สมาชิกก่อนหน้านี้ โค้ดเวอร์ชันนี้ **กระชับ ตรงไปตรงมา และสื่อความหมายชัดเจนกว่ามาก**:
แค่มองที่ signature `fn total_length(a: &String, b: &String) -> usize` ก็รู้ทันทีว่าฟังก์ชันนี้ "แค่อ่าน" `a` กับ `b`
ไม่มีทางแก้ไขหรือเอา ownership ไปไหนได้เลย ยิ่งฟังก์ชันมีพารามิเตอร์ที่ต้องอ่านมากขึ้นเท่าไหร่ ข้อได้เปรียบของการใช้
reference ก็ยิ่งเห็นชัดเจนขึ้นเรื่อย ๆ

#### เปรียบเทียบกับภาษาอื่นที่คุณอาจรู้จัก

แนวคิด "ส่งตัวชี้ไปยังข้อมูลแทนตัวข้อมูลจริง" ไม่ใช่เรื่องใหม่ในโลกโปรแกรมมิ่ง แต่ Rust ทำมันได้ปลอดภัยกว่าภาษาส่วนใหญ่มาก:

| ภาษา | มีแนวคิด reference/pointer หรือไม่ | compiler ตรวจสอบความปลอดภัยของ reference หรือไม่ |
|---|---|---|
| **C++** | มี `T&` (reference) และ `T*` (pointer) แยกจากกัน | ไม่ตรวจสอบ — reference ที่ dangling (ชี้ไปยัง memory ที่ถูกปล่อยไปแล้ว) คือ undefined behavior ที่ compiler ไม่จับให้ |
| **Python** | ทุก object ถูกอ้างอิงแบบ "reference" อยู่แล้วโดย default (ไม่มีการ copy ค่าโดยอัตโนมัติสำหรับ object ที่ mutable) | ไม่มีแนวคิด borrow checker เลย ใช้ garbage collector (reference counting + cycle detection) จัดการอายุของข้อมูลแทน |
| **JavaScript** | object/array ถูกส่งแบบ "by reference" โดย default, ค่า primitive (number, string, boolean) ส่งแบบ by value | ไม่มี borrow checker เช่นกัน ใช้ garbage collector |
| **Rust** | มี `&T` / `&mut T` (reference แบบปลอดภัย) แยกชัดเจนจาก raw pointer (`*const T` / `*mut T` ที่ใช้ใน `unsafe` เท่านั้น — Part 41-42) | **ตรวจสอบเข้มงวดตอน compile time** ด้วย borrow checker — โค้ด "safe Rust" ที่ compile ผ่านจะไม่มี dangling reference หลุดไปทำงานตอน runtime ได้เลย |

จุดที่ทำให้ Rust แตกต่างจาก C++ อย่างสิ้นเชิงคือ **Rust ไม่ต้องพึ่ง garbage collector เพื่อความปลอดภัยของ reference เหมือน
Python/JavaScript แต่ก็ไม่ต้องเสี่ยง undefined behavior เหมือน C++** — มันทำได้ทั้งสองอย่างพร้อมกันด้วยการตรวจสอบตอน
compile time ผ่าน **borrow checker** ซึ่งเราจะเจาะลึกกฎของมันในหัวข้อต่อไป

#### หมายเหตุ: `&String` vs `&str`

คุณอาจสังเกตว่าตัวอย่างข้างบนใช้ `&String` เป็น parameter type ในทางปฏิบัติจริง โค้ด Rust แบบ idiomatic มักจะรับ **`&str`**
แทน `&String` สำหรับพารามิเตอร์ที่อ่านอย่างเดียว เพราะ `&str` ยืดหยุ่นกว่า (รับได้ทั้ง `&String` และ string literal ตรง ๆ)
— แต่เหตุผลเชิงลึกของเรื่องนี้เกี่ยวข้องกับแนวคิด **slice** ซึ่งเป็นเนื้อหาทั้งหมดของ **Part 8** ที่กำลังจะมาถัดจากบทนี้
ตอนนี้เราจะใช้ `&String` ไปก่อนเพื่อโฟกัสที่แนวคิด "reference" ให้แน่นก่อน แล้วจะกลับไปอธิบายเรื่อง `&str` แบบเต็ม ๆ ในบทหน้า

### 7.3 กฎของ Borrowing: หัวใจสำคัญที่สุดของบทนี้

Rust ยอมให้คุณสร้าง reference ได้อย่างเสรี แต่มี **กฎเหล็ก 2 ข้อ** ที่ borrow checker (ส่วนหนึ่งของ `rustc`) บังคับใช้อย่าง
เคร่งครัดตลอดเวลา ไม่มีข้อยกเว้น (นอกจากใน `unsafe` block ที่จะเรียนใน Part 41 ซึ่งเป็นกรณีพิเศษที่คุณรับผิดชอบความปลอดภัย
เองทั้งหมด) กฎทั้งสองข้อนี้คือ:

> **กฎข้อที่ 1**: ในเวลาใดเวลาหนึ่ง คุณสามารถมี **mutable reference (`&mut T`) ได้เพียงหนึ่งตัวเท่านั้น** หรือมี
> **immutable reference (`&T`) ได้กี่ตัวก็ได้ไม่จำกัดจำนวน** — แต่ **ห้ามมีทั้งสองแบบพร้อมกันเด็ดขาด**

> **กฎข้อที่ 2**: **reference ทุกตัวต้องอ้างอิงถึงข้อมูลที่ยังมีชีวิตอยู่จริงเสมอ** (ห้ามเกิด dangling reference — reference
> ที่ชี้ไปยังข้อมูลที่ถูกทำลายไปแล้ว)

สองกฎนี้ดูสั้นและเรียบง่ายมาก แต่มีนัยที่ลึกซึ้งมหาศาลอยู่เบื้องหลัง เราจะแยกอธิบายทีละกฎอย่างละเอียดในหัวข้อถัดไป โดยเริ่ม
จากการทำความรู้จัก mutable reference ก่อน (เพราะกฎข้อที่ 1 จะเข้าใจได้ชัดที่สุดก็ตอนที่เราเห็น `&mut T` ทำงานจริง ๆ)

### 7.4 References ที่แก้ไขค่าได้: `&mut T`

`&T` ที่เราเห็นมาตลอดหัวข้อ 7.2 ให้สิทธิ์แค่ **อ่าน** ข้อมูลเท่านั้น ถ้าคุณลองแก้ไขค่าผ่าน `&T` จะถูก compiler ปฏิเสธทันที
เพราะโดย default ตัวแปรที่ reference ชี้ไปก็ immutable เหมือนตัวแปรทั่วไป (ตามกฎ `let` immutable-by-default จาก Part 3)

ถ้าต้องการให้ฟังก์ชันที่ยืมค่าไป **แก้ไขค่านั้นได้จริง** โดยไม่ต้องรับ ownership เต็ม ๆ ต้องใช้ **mutable reference**
เขียนด้วย `&mut T`:

```rust
fn add_exclamation(s: &mut String) {
    s.push_str("!"); // แก้ไขค่าจริงผ่าน mutable reference
}

fn main() {
    let mut greeting = String::from("สวัสดี"); // ต้องมี mut เพราะค่าจะถูกแก้ไขจริง
    add_exclamation(&mut greeting);             // ส่ง mutable reference เข้าไป
    println!("{greeting}"); // สวัสดี!
}
```

ผลลัพธ์:

```
สวัสดี!
```

สังเกตว่ามี **3 จุดที่ต้องเขียน `mut`/`&mut` ให้ตรงกันหมด**:

1. `let mut greeting` — ตัวแปรต้นทางต้องเป็น `mut` ก่อน (ไม่งั้นจะสร้าง mutable reference ไปยังมันไม่ได้เลยตั้งแต่แรก)
2. `add_exclamation(&mut greeting)` — ตอนเรียกใช้ ต้องส่ง `&mut greeting` (มี `mut` ในการสร้าง reference)
3. `fn add_exclamation(s: &mut String)` — signature ของฟังก์ชันต้องประกาศรับ `&mut String` ไม่ใช่แค่ `&String`

ถ้าขาดข้อใดข้อหนึ่งไป compiler จะฟ้อง error ทันที เช่นถ้าลืม `mut` ตอนประกาศตัวแปร:

```rust
fn add_exclamation(s: &mut String) {
    s.push_str("!");
}

fn main() {
    let greeting = String::from("สวัสดี"); // ลืม mut
    add_exclamation(&mut greeting);
    println!("{greeting}");
}
```

```
error[E0596]: cannot borrow `greeting` as mutable, as it is not declared as mutable
 --> src/main.rs:6:22
  |
5 |     let greeting = String::from("สวัสดี");
  |         -------- help: consider changing this to be mutable: `mut greeting`
6 |     add_exclamation(&mut greeting);
  |                      ^^^^^^^^^^^^ cannot borrow as mutable
```

นี่คือความสอดคล้องกันของระบบ mutability ทั้งหมดใน Rust: **การจะได้ mutable reference มา ตัวแปรต้นทางต้องประกาศเป็น `mut`
เสมอ** ไม่มีทางลัด — สิ่งนี้ทำให้แค่มองที่การประกาศตัวแปร คุณก็รู้ทันทีว่ามันมีโอกาสถูกแก้ไขที่ไหนสักที่ในโปรแกรมหรือไม่

#### ตัวอย่างเพิ่มเติม: แก้ไขค่าตัวเลขดิบผ่าน `&mut` (ต้องใช้ `*` เสมอ)

ตัวอย่าง `add_exclamation` ข้างบนไม่ต้องเขียน `*` เลย เพราะ `push_str` เป็น **method call** (auto-deref ทำงานให้ตามที่
อธิบายไว้ในหัวข้อ 7.2) แต่ถ้าฟังก์ชันต้องแก้ไขค่าตัวเลขดิบ ๆ ผ่าน `&mut` โดยไม่ผ่าน method คุณต้อง dereference ด้วย `*`
เสมอ:

```rust
fn increment(counter: &mut i32) {
    *counter += 1; // ต้องมี * เพราะนี่คือการเข้าถึง/เขียนทับค่าจริงตรง ๆ ไม่ใช่การเรียก method
}

fn double_value(value: &mut i32) {
    *value = *value * 2; // อ่านค่าปัจจุบันด้วย *value แล้วเขียนค่าใหม่ทับด้วย *value = ...
}

fn main() {
    let mut score = 10;

    increment(&mut score);
    println!("หลังเพิ่ม 1 ครั้ง: {score}"); // 11

    double_value(&mut score);
    println!("หลังคูณ 2: {score}"); // 22
}
```

ผลลัพธ์:

```
หลังเพิ่ม 1 ครั้ง: 11
หลังคูณ 2: 22
```

ถ้าลืมเขียน `*` ในฟังก์ชัน `increment` (เขียน `counter += 1;` ตรง ๆ โดยไม่ dereference) จะได้ error ทันที เพราะ `counter`
มี type เป็น `&mut i32` ไม่ใช่ `i32` — operator `+=` ไม่ได้ถูก implement ไว้สำหรับ type `&mut i32` ตรง ๆ ต้อง dereference
ก่อนเสมอเพื่อเข้าถึงค่า `i32` จริงที่อยู่เบื้องหลัง reference นั้น นี่คือความแตกต่างสำคัญจาก method call: **method call
ผ่าน `.` มี auto-deref ช่วย แต่ operator ตัวเลขดิบ ๆ อย่าง `+=`, `-=`, `=` ไม่มี auto-deref ช่วยในลักษณะเดียวกัน**

#### กฎข้อที่ 1 ในทางปฏิบัติ: mutable reference ต้อง "ใช้คนเดียว"

ทีนี้มาดูใจความสำคัญของกฎข้อที่ 1: **ในเวลาเดียวกัน คุณมี mutable reference ไปยังค่าหนึ่ง ๆ ได้แค่ตัวเดียวเท่านั้น** ลองสร้าง
mutable reference สองตัวไปยังค่าเดียวกันพร้อมกันดู:

```rust
fn main() {
    let mut s = String::from("hello");

    let r1 = &mut s;
    let r2 = &mut s; // ❌ พยายามสร้าง mutable reference ตัวที่สองไปยัง s ขณะที่ r1 ยังมีชีวิตอยู่

    println!("{r1}, {r2}");
}
```

โค้ดนี้ **compile ไม่ผ่าน** ด้วย error ที่ตรงตัวมาก:

```
error[E0499]: cannot borrow `s` as mutable more than once at a time
 --> src/main.rs:5:14
  |
4 |     let r1 = &mut s;
  |              ------ first mutable borrow occurs here
5 |     let r2 = &mut s;
  |              ^^^^^^ second mutable borrow occurs here
6 |
7 |     println!("{r1}, {r2}");
  |               ---- first borrow later used here
```

compiler บอกตรง ๆ เลยว่า: มี mutable borrow ครั้งแรกเกิดขึ้นที่ `r1` (ยังจะถูกใช้ต่อในบรรทัด `println!`) แล้วคุณพยายามสร้าง
mutable borrow ครั้งที่สองที่ `r2` **ในขณะที่ครั้งแรกยังไม่หมดอายุ** นี่คือสิ่งที่กฎข้อที่ 1 ห้ามไว้โดยตรง

#### วิธีแก้: ทำให้ scope ของ mutable reference ไม่ทับซ้อนกัน

ถ้าคุณต้องการ mutable reference สองตัวจริง ๆ (คนละช่วงเวลากัน ไม่ใช่พร้อมกัน) ให้จัดการให้ scope ของ reference ตัวแรก
จบลงก่อนที่จะสร้างตัวที่สอง:

```rust
fn main() {
    let mut s = String::from("hello");

    {
        let r1 = &mut s;
        r1.push_str(", world"); // ใช้ r1 จนจบงานที่ต้องการ
    } // r1 หมด scope ตรงนี้ — mutable borrow ของ r1 สิ้นสุดลงแล้ว

    let r2 = &mut s; // ✅ ตอนนี้สร้าง r2 ได้แล้ว เพราะ r1 ไม่มีชีวิตอยู่แล้ว
    r2.push_str("!");

    println!("{s}"); // hello, world!
}
```

ผลลัพธ์:

```
hello, world!
```

โค้ดนี้ compile ผ่านเพราะ **ในทุกจุดของโปรแกรม มี mutable reference ไปยัง `s` ที่ "มีชีวิตอยู่" ได้แค่ตัวเดียวในเวลาเดียวกัน
เสมอ** — `r1` ตายไปแล้ว (หมด scope) ก่อนที่ `r2` จะถือกำเนิด ไม่มีจุดใดในโปรแกรมที่ทั้งสองมีชีวิตอยู่พร้อมกันเลย

### 7.5 ทำไมกฎข้อที่ 1 ถึงสำคัญมาก: การป้องกัน Data Race ตั้งแต่ Compile Time

กฎข้อที่ 1 อาจดูเหมือน "ข้อจำกัดที่น่ารำคาญ" สำหรับมือใหม่ในตอนแรก แต่มันคือหนึ่งใน**นวัตกรรมที่สำคัญที่สุด**ของ Rust
ในฐานะภาษาโปรแกรมมิ่ง — เพราะมันคือกลไกที่ทำให้ Rust **การันตีได้ว่าจะไม่มี data race เกิดขึ้นเลยในโค้ด safe Rust**
โดยไม่ต้องมี garbage collector, lock, หรือ runtime overhead ใด ๆ ทั้งสิ้น

#### Data Race คืออะไร

**Data race** (ในความหมายทางเทคนิคที่แม่นยำ) เกิดขึ้นเมื่อมีเงื่อนไขครบทั้ง 3 ข้อนี้พร้อมกัน:

1. มี **pointer/reference สองตัวหรือมากกว่า** เข้าถึงข้อมูลชิ้นเดียวกัน
2. **อย่างน้อยหนึ่งใน pointer/reference เหล่านั้นกำลังเขียน (write)** ข้อมูล
3. **ไม่มีกลไก synchronize** การเข้าถึงข้อมูลระหว่าง pointer/reference เหล่านั้น (ไม่มีอะไรมาบังคับให้ทำทีละอย่าง)

เมื่อครบทั้ง 3 ข้อ ผลลัพธ์ของโปรแกรมจะ**ไม่แน่นอน** (undefined/unpredictable) — ค่าที่อ่านได้อาจเป็นค่าครึ่งเก่าครึ่งใหม่
ที่ไม่มีความหมาย, โปรแกรมอาจ crash แบบสุ่ม, หรือแย่ที่สุดคืออาจเป็นช่องโหว่ความปลอดภัยที่เปิดให้โจมตีได้ ในภาษาอย่าง C/C++
data race ประเภทนี้เป็นสาเหตุของบั๊กที่ **หายากที่สุดและแก้ยากที่สุด** เพราะมันมักไม่เกิดซ้ำเหมือนกันทุกครั้งที่รัน
(reproduce ไม่ได้แน่นอน ขึ้นกับ timing ของ CPU/OS scheduler ในขณะนั้น)

#### กฎข้อที่ 1 ตัดความเป็นไปได้ของ data race ออกไปทั้งหมดตั้งแต่ต้นตอ

ลองไล่ดูว่ากฎ "mutable ได้แค่หนึ่งตัว หรือ immutable ได้หลายตัว แต่ไม่ทั้งสองพร้อมกัน" ตัดเงื่อนไขของ data race ออกได้
อย่างไร:

- **ถ้ามีแต่ immutable reference (`&T`) หลายตัว**: ไม่มีใครเขียนข้อมูลเลย (อ่านได้ทุกตัว แต่เขียนไม่ได้สักตัว) —
  เงื่อนไขข้อ 2 ของ data race ("มีการเขียน") จึงไม่เกิดขึ้นเลย ไม่ว่าจะมี `&T` กี่ตัวพร้อมกันก็ปลอดภัย 100%
- **ถ้ามี mutable reference (`&mut T`) แค่ตัวเดียว**: มีแค่ผู้เขียนเดียวเท่านั้นที่เข้าถึงข้อมูลได้ในเวลานั้น ไม่มีใครอื่น
  เข้าถึงพร้อมกันเลย (เพราะกฎห้ามมี reference อื่นซ้อนอยู่) — เงื่อนไขข้อ 1 ของ data race ("มีมากกว่าหนึ่งตัวเข้าถึง")
  จึงไม่เกิดขึ้น

พูดอีกแบบ: กฎข้อที่ 1 ทำให้ **"ผู้เขียน" (writer) กับ "ผู้อ่านคนอื่น" ไม่มีทางอยู่ร่วมกันในเวลาเดียวกันได้เลย** ซึ่งเป็น
เงื่อนไขที่เพียงพอ (sufficient condition) สำหรับการไม่มี data race — และที่น่าทึ่งคือ **compiler ตรวจสอบสิ่งนี้ได้ทั้งหมด
ตอน compile time** โดยไม่ต้องรอให้โปรแกรมรันจริงเลย ถ้าโค้ดของคุณ compile ผ่าน คุณมั่นใจได้ 100% ว่าจะไม่มี data race
ชนิดนี้เกิดขึ้นตอน runtime แน่นอน

#### เหตุผลที่กฎนี้ยังสำคัญแม้ในโค้ด single-threaded

มือใหม่หลายคนสงสัยว่า "ในตัวอย่างที่ผ่านมาทั้งหมดเราเขียนโค้ด single-threaded (ไม่มี thread เลย) แล้วทำไมต้องกังวลเรื่อง
data race ด้วย?" คำตอบคือ **กฎข้อที่ 1 ไม่ได้ถูกออกแบบมาเพื่อป้องกัน data race ระหว่าง thread เท่านั้น** มันยังป้องกัน
"aliasing bug" อีกประเภทที่เกิดได้แม้ใน single-threaded code เช่น: ฟังก์ชันหนึ่งถือ mutable reference ไปยัง `Vec` อยู่
แล้วมีอีกส่วนของโค้ดพยายามอ่านหรือแก้ไข `Vec` เดียวกันนั้นผ่าน reference อื่นในเวลาเดียวกัน (เช่น loop ที่ iterate อยู่
ขณะเดียวกันก็พยายาม insert สมาชิกใหม่เข้าไปในตัวมันเอง) ซึ่งอาจทำให้ pointer ภายในของ `Vec` เปลี่ยนตำแหน่งกลางทาง
(เพราะ `Vec` อาจ reallocate memory เมื่อขนาดเกิน capacity) ทำให้ reference ตัวแรกกลายเป็น dangling ทันที **กฎข้อที่ 1
ป้องกันสถานการณ์แบบนี้ได้พร้อมกันไปในตัวเลย** แม้จะไม่มี thread เกี่ยวข้องแม้แต่นิดเดียว

#### ทำไมเรื่องนี้ยิ่งสำคัญขึ้นไปอีกเมื่อพูดถึง Concurrency (preview Part 39-40)

ในบทที่เหลือของโมดูลนี้เรายังไม่แตะเรื่อง thread เลย แต่กฎข้อที่ 1 ที่คุณกำลังเรียนอยู่ตอนนี้คือ **รากฐานที่แท้จริง**
ของสิ่งที่ทำให้ Rust ได้ชื่อว่าเป็นภาษาที่เขียน concurrent program ได้ปลอดภัยที่สุดภาษาหนึ่งของโลก:

- ใน **Part 39 (Mutex, Arc และ Shared-State Concurrency)** คุณจะเห็นว่า `Mutex<T>` คือการนำแนวคิด "mutable reference
  ได้แค่ตัวเดียวในเวลาเดียวกัน" มาบังคับใช้ **ตอน runtime ข้าม thread** แทนที่จะบังคับแค่ตอน compile time ในแต่ละ thread
  เดี่ยว ๆ — เมื่อ thread หนึ่งได้ lock ของ `Mutex` ไปแล้ว (เทียบเท่ากับได้ `&mut T` มา) thread อื่นจะต้องรอจนกว่า lock
  จะถูกปล่อย (เทียบเท่ากับ reference นั้นหมด scope) แนวคิดตั้งต้นเหมือนกับกฎที่คุณเรียนอยู่ตอนนี้เป๊ะ ๆ เพียงแค่ย้ายจาก
  "ตรวจตอน compile time ภายใน thread เดียว" ไปเป็น "ตรวจตอน runtime ข้าม thread"
- ใน **Part 40 (`Send`, `Sync` และความปลอดภัยของ Concurrency)** คุณจะเห็นว่า trait `Sync` (บอกว่า type หนึ่งปลอดภัยที่จะ
  ให้หลาย thread เข้าถึงพร้อมกันแบบอ่านอย่างเดียว) กับ `Send` (บอกว่า type หนึ่งปลอดภัยที่จะย้าย ownership ข้าม thread ได้)
  ถูกสร้างขึ้นบนพื้นฐานเดียวกันกับกฎ borrowing ที่คุณเรียนอยู่นี้เลย — compiler ใช้กฎเดียวกันนี้ตรวจสอบทั้งโค้ดที่รันบน
  thread เดียวและโค้ดที่กระจายงานไปหลาย thread โดยไม่ต้องมีชุดกฎแยกกันสองชุด

พูดให้ชัดที่สุด: **สิ่งที่คุณเรียนอยู่ในหัวข้อนี้ไม่ใช่แค่ "กฎแปลก ๆ ของ syntax" แต่คือรากฐานทางคณิตศาสตร์/วิศวกรรมที่ทำให้
Rust สามารถการันตี memory safety และ thread safety ไปพร้อมกันได้โดยไม่ต้องมี garbage collector หรือ runtime lock
ที่มี cost สูง** — นี่คือเหตุผลที่หนังสือ/บทความเกี่ยวกับ Rust จำนวนมากยกให้ borrow checker เป็น "หัวใจ" ของภาษาทั้งภาษา

### 7.6 ผสม `&` และ `&mut` พร้อมกัน: ข้อผิดพลาดที่พบบ่อยที่สุดของมือใหม่

กฎข้อที่ 1 ไม่ได้ห้ามแค่ "mutable สองตัวพร้อมกัน" เท่านั้น แต่ยังห้าม **"mutable หนึ่งตัว พร้อมกับ immutable อีกตัวหรือ
มากกว่า" ในเวลาเดียวกันด้วย** — เหตุผลก็ตรงไปตรงมาจากหัวข้อก่อนหน้า: ถ้ามี `&mut T` อยู่แล้ว แสดงว่ามี "ผู้เขียน" อยู่
การอนุญาตให้มี `&T` (ผู้อ่าน) เข้ามาอ่านพร้อมกันจะทำให้ผู้อ่านนั้นมีโอกาสเห็นข้อมูลที่กำลังถูกเขียนอยู่ครึ่ง ๆ กลาง ๆ ได้
ซึ่งเป็นสถานการณ์เดียวกับ data race ที่อธิบายไว้ในหัวข้อก่อน

ลองดูตัวอย่างคลาสสิกที่แสดงปัญหานี้:

```rust
fn main() {
    let mut s = String::from("hello");

    let r1 = &s;     // ไม่มีปัญหา — immutable borrow
    let r2 = &s;     // ไม่มีปัญหา — immutable borrow อีกตัว (มีได้หลายตัว)
    let r3 = &mut s; // ❌ ปัญหาใหญ่ — พยายามสร้าง mutable borrow ขณะที่ r1, r2 ยังมีชีวิตอยู่

    println!("{r1}, {r2}, and {r3}");
}
```

Error ที่ได้:

```
error[E0502]: cannot borrow `s` as mutable because it is also borrowed as immutable
 --> src/main.rs:6:14
  |
4 |     let r1 = &s;
  |              -- immutable borrow occurs here
5 |     let r2 = &s;
6 |     let r3 = &mut s;
  |              ^^^^^^ mutable borrow occurs here
7 |
8 |     println!("{r1}, {r2}, and {r3}");
  |               -- immutable borrow later used here
```

ข้อความ error นี้บอกไว้ชัดมาก: `r1` (immutable) ยังจะถูกใช้ต่อใน `println!` ข้างล่าง (มี "immutable borrow later used
here") ดังนั้นในช่วงเวลาที่คุณพยายามสร้าง `r3` (mutable) borrow ของ `r1` ก็ยังไม่หมดอายุ — ทำให้เกิดการทับซ้อนกันระหว่าง
mutable borrow กับ immutable borrow ซึ่งกฎข้อที่ 1 ห้ามไว้โดยตรง

#### วิธีแก้แบบดั้งเดิม: จำกัด scope ของ immutable reference ด้วย block

วิธีแก้ที่ตรงไปตรงมาที่สุดคือทำให้ `r1` และ `r2` หมด scope ก่อนที่จะสร้าง `r3`:

```rust
fn main() {
    let mut s = String::from("hello");

    {
        let r1 = &s;
        let r2 = &s;
        println!("{r1} and {r2}");
    } // r1, r2 หมด scope ตรงนี้ — immutable borrow ทั้งสองสิ้นสุดลงแล้ว

    let r3 = &mut s; // ✅ ตอนนี้สร้างได้แล้ว เพราะไม่มี immutable borrow ใดค้างอยู่
    r3.push_str(" world");

    println!("{s}"); // hello world
}
```

โค้ดนี้ compile ผ่านได้เพราะ block `{ }` บีบให้ `r1`, `r2` มีชีวิตอยู่แค่ในช่วงเวลาสั้น ๆ ที่กำหนดไว้ชัดเจน วิธีนี้
**ใช้ได้ผลจริงและถูกต้องเสมอ** — แต่เดี๋ยวเราจะเห็นในหัวข้อถัดไปว่า Rust สมัยใหม่ฉลาดพอที่จะทำให้คุณไม่ต้องเขียน block
ซ้อนแบบนี้เลยในหลายกรณี

### 7.7 Non-Lexical Lifetimes (NLL): Borrow Checker ที่ฉลาดขึ้น

ในยุคแรกของ Rust (ช่วงก่อน edition 2018) borrow checker ตัดสิน "อายุ" ของ reference แบบง่าย ๆ ตาม **lexical scope**
(ขอบเขตของ `{ }` ในซอร์สโค้ด) ล้วน ๆ — พูดคือ ถ้า reference ถูกประกาศในบล็อกไหน มันจะถูกมองว่า "มีชีวิตอยู่" ไปจนกว่าจะ
ถึงปีกกาปิดของบล็อกนั้นเสมอ **ไม่ว่าคุณจะใช้มันครั้งสุดท้ายที่บรรทัดไหนก็ตาม** นี่คือสาเหตุที่โค้ดในหัวข้อ 7.6 จำเป็นต้อง
เขียน block `{ }` ซ้อนเพื่อ "บีบ" อายุของ `r1`, `r2` ให้สั้นลงด้วยมือ

ตั้งแต่มีการนำ **Non-Lexical Lifetimes (NLL)** มาใช้ (stabilize เต็มรูปแบบราวปี 2018 คู่กับ Rust edition 2018 และ
ภายหลังก็ถูกนำมาใช้กับ edition 2015 ด้วยเช่นกัน) borrow checker เปลี่ยนวิธีคิดไปเป็นแบบ **flow-sensitive**: มันจะวิเคราะห์
โค้ดจริง ๆ ว่า reference แต่ละตัว **ถูกใช้งานครั้งสุดท้ายที่บรรทัดไหน** แล้วถือว่า borrow นั้น "หมดอายุ" ทันทีหลังจากจุดนั้น
โดยไม่ต้องรอให้ถึงปีกกาปิดของ scope เลย

ลองดูโค้ดเดียวกันกับหัวข้อ 7.6 แต่**ไม่มี block ซ้อน**:

```rust
fn main() {
    let mut s = String::from("hello");

    let r1 = &s;
    let r2 = &s;
    println!("{r1} and {r2}"); // r1, r2 ถูกใช้งาน "ครั้งสุดท้าย" ที่บรรทัดนี้

    let r3 = &mut s; // ✅ compile ผ่าน! เพราะ NLL รู้ว่า r1, r2 ไม่ถูกใช้อีกแล้วหลังจากบรรทัดก่อนหน้า
    r3.push_str(" world");

    println!("{s}"); // hello world
}
```

โค้ดนี้ **compile ผ่านสบาย ๆ ใน Rust สมัยใหม่** ทั้ง ๆ ที่ `r1` และ `r2` อยู่ใน scope เดียวกันกับ `r3` เป๊ะ ๆ (ไม่มี block
`{ }` แยกเลย) เหตุผลคือ borrow checker วิเคราะห์ได้ว่า **การใช้งานครั้งสุดท้ายของ `r1` และ `r2` คือที่บรรทัด `println!`
ก่อนหน้า** ดังนั้น immutable borrow ของทั้งคู่จึง "ตาย" ไปแล้วตั้งแต่ก่อนที่ `r3` จะถือกำเนิด — ไม่มีการทับซ้อนของ borrow
เกิดขึ้นเลยตามการวิเคราะห์แบบ flow-sensitive นี้

#### ทำไมเรื่องนี้ถึงสำคัญสำหรับมือใหม่

มือใหม่ Rust จำนวนมาก (โดยเฉพาะที่เคยอ่านตำราหรือบทความเก่า ๆ ที่เขียนก่อนปี 2018) มักกลัวว่าจะต้องเขียนโค้ดแบบ "scope
gymnastics" — สร้าง block ซ้อนเป็นชั้น ๆ เพื่อบีบอายุของ reference ด้วยมือทุกครั้งที่มี borrow ชนกัน แต่ในความเป็นจริง
**Rust สมัยใหม่ (edition 2018 เป็นต้นไป) ฉลาดพอที่จะจัดการเรื่องนี้ให้เองในกรณีส่วนใหญ่** คุณแทบไม่ต้องเขียน block พิเศษ
เพื่อ "หลอก" borrow checker เลย ตราบใดที่คุณเขียนโค้ดตามลำดับการใช้งานที่เป็นธรรมชาติอยู่แล้ว (ใช้ `r1`, `r2` เสร็จก่อน
แล้วค่อยสร้าง `r3` ทีหลัง) — NLL จะเข้าใจเจตนาของคุณได้เองโดยไม่ต้องเขียนอะไรเพิ่ม

อย่างไรก็ตาม **กฎข้อที่ 1 เองไม่เคยเปลี่ยนแปลงเลย** สิ่งที่เปลี่ยนไปคือ**วิธีคำนวณว่า borrow หนึ่งตัว "มีชีวิตอยู่" นานแค่ไหน**
เท่านั้น ถ้าคุณลองสลับลำดับโค้ดใน 7.7 ให้ `r1` หรือ `r2` ถูกใช้งาน**หลังจาก** `r3` ถูกสร้างขึ้น (เช่นย้าย `println!("{r1}
and {r2}");` ไปไว้ท้ายสุดของฟังก์ชัน) ก็จะกลับไปเจอ error `E0502` เดิมทันที เพราะตอนนั้น borrow ของ `r1`/`r2` จะยัง
"มีชีวิตอยู่" ทับซ้อนกับ `r3` จริง ๆ ตามการวิเคราะห์ NLL

### 7.8 Dangling References: ทำไม Rust ไม่ยอมให้ Reference "ตกค้าง"

ทีนี้มาดูกฎข้อที่ 2: **reference ทุกตัวต้องอ้างอิงถึงข้อมูลที่ยังมีชีวิตอยู่จริงเสมอ** ลองดูตัวอย่างที่ละเมิดกฎนี้ —
ฟังก์ชันที่พยายามคืน reference ไปยังตัวแปร local ของตัวเอง:

```rust
fn dangle() -> &String { // ❌ พยายามคืน reference ออกจากฟังก์ชัน
    let s = String::from("hello");
    &s
} // s หมด scope ที่นี่ และถูก drop ไป — &s ที่คืนออกไปจะชี้ไปยัง memory ที่ไม่มีข้อมูลอยู่แล้ว!

fn main() {
    let reference_to_nothing = dangle();
    println!("{reference_to_nothing}");
}
```

โค้ดนี้ **compile ไม่ผ่านตั้งแต่ตอนประกาศฟังก์ชัน** ด้วย error:

```
error[E0106]: missing lifetime specifier
 --> src/main.rs:1:16
  |
1 | fn dangle() -> &String {
  |                ^ expected named lifetime parameter
  |
  = help: this function's return type contains a borrowed value, but there is no value for it to be borrowed from
help: consider using the `'static` lifetime, but this is uncommon unless you're returning a borrowed value from a `const`
or a `static`
  |
1 | fn dangle() -> &'static String {
  |                 +++++++
```

#### ทำไม Rust ต้องปฏิเสธโค้ดนี้: อธิบายเชิงลึก

ลองไล่ดูว่าจะเกิดอะไรขึ้นถ้า Rust **ยอมให้** โค้ดนี้ compile ผ่าน (สมมติเหมือนใน C/C++ ที่ยอมให้ทำแบบนี้ได้):

1. ฟังก์ชัน `dangle` ถูกเรียก → ตัวแปร `s` (ที่เป็น `String`) ถูกสร้างขึ้นบน stack พร้อมข้อมูลบน heap
2. ฟังก์ชันคืนค่า `&s` ซึ่งเป็น reference ที่ชี้ไปยังตำแหน่งของ `s` บน stack frame ของ `dangle`
3. ฟังก์ชัน `dangle` จบการทำงาน → stack frame ของมันถูก "คืน" กลับไปให้ระบบใช้งานต่อได้ (ในทางเทคนิคคือ stack pointer
   เลื่อนกลับ) ตามกฎ ownership ข้อ 3 จาก Part 6, `s` หมด scope และค่าของมันถูก `drop` — memory บน heap ที่ `s` เคยชี้ไป
   ถูกปล่อยคืนกลับให้ระบบ
4. ตัวแปร `reference_to_nothing` ใน `main` ได้รับ reference ที่ **ชี้ไปยัง stack frame ที่ไม่มีอยู่แล้ว และข้อมูลบน heap
   ที่ถูกปล่อยไปแล้ว** — นี่คือ **dangling reference** โดยสมบูรณ์
5. ถ้าคุณพยายาม `println!("{reference_to_nothing}")` โปรแกรมจะพยายามอ่าน memory ที่ไม่ได้เป็นของมันอีกต่อไป ซึ่งอาจ
   อ่านได้ข้อมูลขยะ (garbage), อ่านข้อมูลของตัวแปรอื่นที่เข้ามาใช้ตำแหน่งความจำนั้นต่อ, หรือแม้แต่ทำให้โปรแกรม crash —
   นี่คือ **undefined behavior** แบบเดียวกับที่เกิดขึ้นจริงในภาษา C/C++ เวลามีคนคืน pointer ไปยัง local variable

ในภาษาที่ไม่มี borrow checker (C, C++) บั๊กประเภทนี้จะไม่ถูกจับตอน compile time เลย โปรแกรมจะ compile ผ่านสบาย ๆ แล้ว
ไปพังตอน runtime แบบสุ่ม ๆ ไม่คงเส้นคงวา (บางทีรันแล้วได้ค่าที่ดูเหมือนถูก บางทีก็ได้ค่าผิดหรือ crash) ทำให้เป็นบั๊กที่
debug ยากมากในทางปฏิบัติ — แต่ **Rust จับบั๊กนี้ได้ตั้งแต่ก่อนโปรแกรมจะรันด้วยซ้ำ** ผ่าน borrow checker ที่วิเคราะห์ได้ว่า
"ค่าที่ reference นี้ชี้ไปกำลังจะหมดอายุก่อนที่ reference เองจะหมดอายุ" ซึ่งเป็นการละเมิดกฎข้อที่ 2 โดยตรง

#### ทางแก้: คืน ownership กลับไปแทนการคืน reference

วิธีแก้ปัญหานี้ที่ถูกต้องคือ**อย่าคืน reference ไปยังค่าที่สร้างขึ้นภายในฟังก์ชัน** ถ้าฟังก์ชันต้องการ "ส่งข้อมูลออกไป
ให้ผู้เรียกใช้ต่อ" ให้คืน ownership ของข้อมูลนั้นออกไปตรง ๆ (ย้อนกลับไปใช้ความรู้จาก Part 6):

```rust
fn no_dangle() -> String {
    let s = String::from("hello");
    s // ส่ง ownership ของ s ออกไปให้ผู้เรียก ไม่มี reference เกี่ยวข้องเลย จึงไม่มีทาง dangling ได้
}

fn main() {
    let s = no_dangle(); // s ใน main กลายเป็นเจ้าของข้อมูลนี้โดยตรง ไม่ผ่าน reference
    println!("{s}"); // hello
}
```

โค้ดนี้ compile ผ่านสบาย ๆ เพราะ **ไม่มี reference คืนออกมาเลย** — ownership ของ `String` ถูกย้ายออกจากฟังก์ชัน `no_dangle`
ไปให้ `main` ตรง ๆ ตามกลไก move semantics ปกติจาก Part 6 เมื่อ `s` ภายใน `no_dangle` "หมด scope" ตามหลักไวยากรณ์
ownership ของมันได้ถูกย้ายออกไปแล้ว (ไม่ใช่ถูก drop) จึงไม่มีข้อมูลอะไรถูกทำลายทิ้งเลย

#### ทำไม error ถึงชื่อว่า "missing lifetime specifier" — ทีเซอร์สู่ Part 20/23

สังเกตว่า error message ที่ได้ไม่ได้บอกตรง ๆ ว่า "dangling reference" แต่บอกว่า **"missing lifetime specifier"**
(ขาดการระบุ lifetime) — นี่เป็นเพราะเหตุผลที่ Rust ปฏิเสธ `fn dangle() -> &String` **ไม่ใช่เพราะมันตรวจจับ dangling
reference ได้โดยตรงในทุกกรณี** แต่เป็นเพราะ **มันไม่มีทางรู้ได้เลยว่า reference ที่คืนออกมาควรจะ "มีอายุยืนเท่ากับอะไร"**
ในเมื่อไม่มี reference parameter ใดๆ ให้ผูกอายุด้วยเลย (สังเกตว่าฟังก์ชัน `dangle` ไม่มี parameter แม้แต่ตัวเดียว)

**Lifetime** คือแนวคิดที่ Rust ใช้อธิบาย "reference ตัวนี้ควรจะมีอายุยืนได้นานแค่ไหน โดยเทียบกับ reference ตัวอื่น หรือ
ข้อมูลต้นทาง" ซึ่งเป็นกลไกที่ borrow checker ใช้พิสูจน์ว่ากฎข้อที่ 2 (ห้าม dangling) จะไม่ถูกละเมิดในทุกกรณีที่เป็นไปได้
เมื่อฟังก์ชันคืน reference ออกมาโดยไม่มี reference parameter ให้ผูกไว้เลย compiler ไม่มีทางพิสูจน์ความปลอดภัยนี้ได้เลย
จึงต้องขอให้คุณระบุ **lifetime annotation** (สัญลักษณ์แบบ `'a`) อย่างชัดเจน — ในกรณีของ `dangle()` ไม่มีทางระบุ lifetime
ที่ถูกต้องได้เลยจริง ๆ (เพราะข้อมูลถูกสร้างและทำลายภายในฟังก์ชันเอง) ซึ่งเป็นสัญญาณที่ชัดเจนว่า **design ของฟังก์ชันนี้
ผิดตั้งแต่ต้น** — ควรคืน ownership ไม่ใช่คืน reference

เราจะเรียนเรื่อง lifetime annotation (`'a`) และกฎ **lifetime elision** (กฎที่ทำให้ compiler เดา lifetime ให้อัตโนมัติ
ในกรณีง่าย ๆ โดยไม่ต้องเขียน `'a` เองเลย เช่นฟังก์ชันที่มี reference parameter แค่ตัวเดียวและคืน reference ออกมา)
อย่างเป็นทางการใน **Part 20 (Lifetimes เบื้องต้น)** และเจาะลึกกรณีซับซ้อนกว่านั้น (struct ที่เก็บ reference, higher-ranked
lifetime) ใน **Part 23 (Lifetimes ขั้นสูง)** — ตอนนี้จำแค่หลักการสำคัญที่สุดไว้ก่อน: **reference ที่ฟังก์ชันคืนออกมา
ต้องมีที่มาจาก reference parameter ที่รับเข้ามา (หรือจากข้อมูลที่มีอายุยืนพอ เช่น `'static`) เสมอ ไม่สามารถ "สร้างขึ้นมา
ลอย ๆ" จากตัวแปร local ภายในฟังก์ชันได้เลย**

### 7.9 ตัวอย่างจริง: ระบบคะแนนนักเรียน (Student Roster) ด้วย Array Reference

มาสรุปทุกอย่างที่เรียนมาในบทนี้ผ่านตัวอย่างที่ใกล้เคียงงานจริง — ระบบเก็บคะแนนสอบของนักเรียนในห้องเรียนหนึ่ง ที่ต้องมี
ทั้งฟังก์ชันที่ **อ่านอย่างเดียว** (คำนวณค่าเฉลี่ย, หาคะแนนสูงสุด) และฟังก์ชันที่ **แก้ไขข้อมูลจริง** (ปรับคะแนนโบนัส)
โดยทั้งหมดทำผ่าน reference ไม่มีการ move ข้อมูล array ออกจาก `main` เลยแม้แต่ครั้งเดียว

(หมายเหตุ: เพื่อความง่าย ตัวอย่างนี้จำกัดจำนวนนักเรียนไว้ที่ห้องละ 5 คน โดยใช้ array ขนาดคงที่ `[i32; 5]` ที่เรียนมาจาก
Part 3 — ในความเป็นจริงจำนวนนักเรียนต่อห้องมักไม่แน่นอนและเปลี่ยนแปลงได้ ซึ่งจะเหมาะกับ **slice (`&[T]`)** ที่เราจะเรียน
ใน **Part 8** ถัดจากบทนี้ทันที หรือ **`Vec<T>`** ที่ยืดหยุ่นเต็มรูปแบบซึ่งจะเรียนใน **Part 13** — ตอนนี้ใช้ array ขนาดตายตัว
ไปก่อนเพื่อโฟกัสที่แนวคิด reference ให้แน่นที่สุด)

```rust
// ฟังก์ชันอ่านอย่างเดียว: รับ &[i32; 5] (immutable reference ไปยัง array) — ไม่แก้ไขอะไรเลย
fn calculate_average(scores: &[i32; 5]) -> f64 {
    let mut sum = 0;
    for score in scores {
        // score มี type &i32 (จากการ iterate ผ่าน reference ของ array)
        // std มี operator overload ที่ยอม AddAssign<&i32> for i32 ให้เขียนแบบนี้ได้ตรง ๆ
        sum += score;
    }
    sum as f64 / scores.len() as f64
}

// ฟังก์ชันอ่านอย่างเดียวอีกตัว: หาคะแนนสูงสุดในกลุ่ม
fn find_highest(scores: &[i32; 5]) -> i32 {
    let mut highest = scores[0];
    for &score in scores {
        // pattern &score ดึงค่า i32 ออกมาจาก &i32 ที่ iterator คืนให้ (dereference ผ่าน pattern)
        if score > highest {
            highest = score;
        }
    }
    highest
}

// ฟังก์ชันแก้ไขข้อมูลจริง: รับ &mut [i32; 5] เพื่อปรับคะแนนโบนัสให้ทุกคนในห้อง
fn apply_bonus(scores: &mut [i32; 5], bonus: i32) {
    for score in scores {
        // score มี type &mut i32 ในกรณีนี้ ต้อง dereference ด้วย * ก่อนแก้ไขค่าจริง
        *score += bonus;
    }
}

fn main() {
    let mut class_a_scores: [i32; 5] = [88, 92, 79, 95, 84];

    // 1. อ่านค่าเฉลี่ยและคะแนนสูงสุด — ยืมแบบ immutable ทั้งคู่ ไม่แก้ไขอะไร
    let average = calculate_average(&class_a_scores);
    let highest = find_highest(&class_a_scores);

    println!("คะแนนก่อนปรับ: {:?}", class_a_scores);
    println!("คะแนนเฉลี่ย: {average:.2}");
    println!("คะแนนสูงสุด: {highest}");

    // class_a_scores ยังใช้งานได้ตามปกติทุกประการ เพราะสองฟังก์ชันข้างบนแค่ "ยืม" ไปอ่าน ไม่ได้ move ออกไปเลย

    // 2. ให้โบนัสคะแนน 3 คะแนนกับทุกคนในห้อง — ยืมแบบ mutable เพื่อแก้ไขค่าจริง
    apply_bonus(&mut class_a_scores, 3);

    println!("คะแนนหลังปรับโบนัส: {:?}", class_a_scores);

    // 3. คำนวณค่าเฉลี่ยใหม่อีกครั้งหลังปรับโบนัส — ยืมแบบ immutable อีกครั้ง (คนละเวลากับตอน mutable borrow)
    let new_average = calculate_average(&class_a_scores);
    println!("คะแนนเฉลี่ยใหม่: {new_average:.2}");
}
```

ผลลัพธ์เมื่อรัน:

```
คะแนนก่อนปรับ: [88, 92, 79, 95, 84]
คะแนนเฉลี่ย: 87.60
คะแนนสูงสุด: 95
คะแนนหลังปรับโบนัส: [91, 95, 82, 98, 87]
คะแนนเฉลี่ยใหม่: 90.60
```

สังเกตว่าตัวอย่างนี้ใช้ทุกกฎที่เรียนมาในบทนี้อย่างครบถ้วน:

- `calculate_average` และ `find_highest` รับ **`&[i32; 5]`** (immutable reference) เพราะแค่ต้องการอ่าน — `main` ยังเป็น
  เจ้าของ `class_a_scores` ตลอดเวลา ไม่มีการ move เกิดขึ้นเลย
- `apply_bonus` รับ **`&mut [i32; 5]`** (mutable reference) เพราะต้องแก้ไขค่าจริง — `class_a_scores` ต้องประกาศด้วย `mut`
  ตั้งแต่แรกใน `main` เพื่อให้สร้าง mutable reference ไปยังมันได้
- **ไม่มีจุดใดในโปรแกรมที่ immutable reference กับ mutable reference มีชีวิตอยู่ทับซ้อนกันเลย** — เราเรียก
  `calculate_average(&class_a_scores)` และ `find_highest(&class_a_scores)` เสร็จสิ้นสมบูรณ์ (ทั้งสองเป็น immutable
  borrow ชั่วครู่เดียวที่จบก่อนบรรทัดถัดไป) ก่อนที่จะเรียก `apply_bonus(&mut class_a_scores, 3)` (mutable borrow อีกครั้ง)
  เป็นไปตามกฎข้อที่ 1 อย่างเป็นธรรมชาติ โดยไม่ต้องเขียน block ซ้อนใด ๆ เลย เพราะ NLL จัดการให้เรียบร้อย
- ไม่มี dangling reference เกิดขึ้นเลย เพราะทุก reference ที่สร้างขึ้นมีอายุสั้นกว่า `class_a_scores` เสมอ (สร้างขึ้นตอน
  เรียกฟังก์ชัน แล้วหมดอายุทันทีที่ฟังก์ชันนั้นคืนค่า)

นี่คือรูปแบบการเขียนโค้ด Rust ที่ idiomatic ที่สุด: **ให้ตัวแปรหลักเป็นเจ้าของข้อมูลอยู่ที่เดียว แล้วส่ง reference
(immutable หรือ mutable ตามความจำเป็น) ไปให้ฟังก์ชันต่าง ๆ ยืมใช้ชั่วคราว** — ownership ไม่กระจัดกระจาย ติดตามง่าย
compiler ช่วยตรวจสอบความถูกต้องให้ทั้งหมด และไม่มี runtime cost เพิ่มขึ้นจากการยืมเหล่านี้เลยแม้แต่นิดเดียว (reference
เป็นแค่ pointer ธรรมดา ไม่มี overhead ใด ๆ ซ่อนอยู่ — เป็นไปตามหลัก zero-cost abstraction ที่เราพูดถึงตั้งแต่ Part 1)

### 7.10 ตัวอย่างจริงที่สอง: ระบบบัญชีธนาคารอย่างง่าย (Read Access vs Write Access ผ่าน Reference)

ตัวอย่างที่สองนี้เน้นให้เห็นภาพว่าการเลือกใช้ `&` หรือ `&mut` ไม่ใช่แค่เรื่อง syntax แต่เป็น **decision เชิง design** ที่
สื่อความหมายทางธุรกิจได้ชัดเจนมาก: ฟังก์ชัน "ตรวจสอบยอดเงิน" ควรรับแค่ `&` เพราะไม่มีสิทธิ์แก้ไขอะไรเลย ส่วนฟังก์ชัน
"ฝาก/ถอนเงิน" ต้องรับ `&mut` เพราะมันเปลี่ยนสถานะจริง — แค่มองที่ signature ของฟังก์ชัน เราก็รู้ทันทีว่าฟังก์ชันไหน
"ปลอดภัย" ที่จะเรียกใช้พร่ำเพรื่อโดยไม่มีผลข้างเคียง (อ่านอย่างเดียว) และฟังก์ชันไหนที่ "มีผลข้างเคียงจริง" (แก้ไขยอดเงิน)
— สิ่งนี้เรียกว่า **self-documenting code** (โค้ดที่อธิบายตัวเองผ่าน type system โดยไม่ต้องอ่าน comment เลย) ซึ่งเป็น
ข้อดีที่มาพร้อมกับระบบ ownership/borrowing ของ Rust แบบที่ภาษาอื่นให้ไม่ได้ในระดับเดียวกัน

(เก็บยอดเงินเป็น "สตางค์" แบบ integer แทนทศนิยม ด้วยเหตุผลเดียวกับตัวอย่างระบบสินค้าคงคลังใน Part 3 หัวข้อ 3.13 — เพื่อ
เลี่ยงปัญหาความไม่เที่ยงตรงของ floating point ที่เราเรียนไปแล้ว)

```rust
// ฟังก์ชันอ่านอย่างเดียว: ตรวจสอบว่ายอดเงินเพียงพอสำหรับถอนจำนวนที่ต้องการหรือไม่
// รับ &i64 เพราะแค่ต้องการ "ดู" ยอดปัจจุบัน ไม่มีสิทธิ์แก้ไขอะไรเลย
fn has_sufficient_balance(balance_cents: &i64, amount_cents: i64) -> bool {
    *balance_cents >= amount_cents
}

// ฟังก์ชันแก้ไขค่าจริง: ฝากเงินเข้าบัญชี ต้องรับ &mut i64 เพราะเปลี่ยนยอดเงินจริง
fn deposit(balance_cents: &mut i64, amount_cents: i64) {
    *balance_cents += amount_cents;
}

// ฟังก์ชันแก้ไขค่าจริงอีกตัว: ถอนเงิน คืน true ถ้าสำเร็จ, false ถ้ายอดไม่พอ (ไม่แก้ไขอะไรถ้าถอนไม่ได้)
fn withdraw(balance_cents: &mut i64, amount_cents: i64) -> bool {
    // ส่ง balance_cents (type &mut i64) ต่อไปให้ has_sufficient_balance ที่รับ &i64 ได้ตรง ๆ
    // เพราะ Rust ยอมให้ "reborrow" &mut T เป็น &T ชั่วคราวได้เสมอ (เหมือนยืมกุญแจตู้เซฟไปให้อ่านมิเตอร์แว่บเดียว
    // แล้วได้กุญแจคืนมาทันที) การ reborrow แบบนี้ปลอดภัยเสมอ เพราะไม่มี reference อื่นเข้ามาแทรกได้ในช่วงนั้น
    if has_sufficient_balance(balance_cents, amount_cents) {
        *balance_cents -= amount_cents;
        true
    } else {
        false
    }
}

fn main() {
    let mut balance_cents: i64 = 1_000_00; // เริ่มต้นด้วย 1,000.00 บาท (เก็บเป็นสตางค์)

    println!("ยอดเงินเริ่มต้น: {}.{:02} บาท", balance_cents / 100, balance_cents % 100);

    // 1. ตรวจสอบยอดก่อนถอน — ยืมแบบ immutable เท่านั้น ไม่แก้ไขอะไร
    let want_to_withdraw: i64 = 300_00; // 300 บาท
    if has_sufficient_balance(&balance_cents, want_to_withdraw) {
        println!(
            "ยอดเงินเพียงพอสำหรับถอน {}.{:02} บาท",
            want_to_withdraw / 100,
            want_to_withdraw % 100
        );
    }

    // 2. ฝากเงินเพิ่ม 500 บาท — ยืมแบบ mutable เพื่อแก้ไขยอดจริง
    deposit(&mut balance_cents, 500_00);
    println!("หลังฝาก 500 บาท: {}.{:02} บาท", balance_cents / 100, balance_cents % 100);

    // 3. ถอนเงิน 300 บาท — ยืมแบบ mutable อีกครั้ง
    let success = withdraw(&mut balance_cents, 300_00);
    println!(
        "ถอน 300 บาท: {} (ยอดล่าสุด {}.{:02} บาท)",
        if success { "สำเร็จ" } else { "ไม่สำเร็จ" },
        balance_cents / 100,
        balance_cents % 100
    );

    // 4. พยายามถอนเงินเกินยอด — ควรล้มเหลวอย่างปลอดภัย ไม่ทำให้ยอดติดลบ
    let over_withdraw = withdraw(&mut balance_cents, 999_999_00);
    println!(
        "พยายามถอน 999,999 บาท: {} (ยอดล่าสุด {}.{:02} บาท ไม่เปลี่ยนแปลง)",
        if over_withdraw { "สำเร็จ" } else { "ไม่สำเร็จ" },
        balance_cents / 100,
        balance_cents % 100
    );
}
```

ผลลัพธ์เมื่อรัน:

```
ยอดเงินเริ่มต้น: 1000.00 บาท
ยอดเงินเพียงพอสำหรับถอน 300.00 บาท
หลังฝาก 500 บาท: 1500.00 บาท
ถอน 300 บาท: สำเร็จ (ยอดล่าสุด 1200.00 บาท)
พยายามถอน 999,999 บาท: ไม่สำเร็จ (ยอดล่าสุด 1200.00 บาท ไม่เปลี่ยนแปลง)
```

สังเกตประเด็นสำคัญ 3 อย่างจากตัวอย่างนี้:

1. **ทุกฟังก์ชันในโปรแกรมนี้ทำงานผ่าน reference ทั้งหมด** — ไม่มีจุดใดที่ `balance_cents` ถูก move ออกจาก `main` เลย
   ตัวแปร `balance_cents` ใน `main` เป็นเจ้าของยอดเงินอยู่ตลอดทั้งโปรแกรม ฟังก์ชันต่าง ๆ แค่ "ยืม" สิทธิ์เข้าถึงชั่วคราว
   ตามความจำเป็นของแต่ละครั้งเท่านั้น
2. **การ reborrow `&mut T` เป็น `&T` ชั่วคราว** (ในฟังก์ชัน `withdraw` ที่เรียก `has_sufficient_balance`) เป็นรูปแบบที่
   ปลอดภัยและพบได้บ่อยมากในโค้ด Rust จริง — เพราะตราบใดที่ยังอยู่ภายใต้การควบคุมของ `&mut` ตัวเดิม (ไม่มีใครอื่นถือ
   reference ไปยังข้อมูลเดียวกันอยู่แล้ว) การ "มองผ่านมันแบบอ่านอย่างเดียวชั่วคราว" ย่อมไม่ละเมิดกฎข้อที่ 1 เลย
3. **ไม่มีจุดใดในโปรแกรมที่ borrow ทับซ้อนกันจนต้องเขียน block พิเศษ** เพราะแต่ละการเรียกฟังก์ชัน (`has_sufficient_balance`,
   `deposit`, `withdraw`) เป็น borrow ที่มีอายุสั้น ๆ แค่ช่วงเวลาที่ฟังก์ชันนั้นทำงานอยู่เท่านั้น เมื่อฟังก์ชันคืนค่า
   ออกมา borrow นั้นก็หมดอายุไปตาม NLL ทันที — สอดคล้องกับสิ่งที่เราเรียนในหัวข้อ 7.7 พอดี

## กับดักที่พบบ่อย (Common Pitfalls)

**1. ลืมใส่ `&` ตอนเรียกฟังก์ชันที่รับ reference**

```rust
fn print_length(s: &String) {
    println!("{}", s.len());
}

fn main() {
    let name = String::from("Rustacean");
    print_length(name); // ลืมใส่ & ข้างหน้า name
}
```

```
error[E0308]: mismatched types
 --> src/main.rs:7:18
  |
7 |     print_length(name);
  |     ------------ ^^^^ expected `&String`, found `String`
  |     |
  |     arguments to this function are incorrect
  |
note: function defined here
 --> src/main.rs:1:4
  |
1 | fn print_length(s: &String) {
  |    ^^^^^^^^^^^^ ----------
help: consider borrowing here
  |
7 |     print_length(&name);
  |                  +
```

**วิธีแก้**: เติม `&` หน้าตัวแปรตอนเรียกใช้ (`print_length(&name)`) จุดสังเกตง่าย ๆ คือ **type ของตัวแปรที่ประกาศไว้กับ
type ของพารามิเตอร์ที่ฟังก์ชันต้องการต้องตรงกันเป๊ะ** ถ้าฟังก์ชันรับ `&String` คุณต้องส่ง `&String` เข้าไป (สร้างด้วย `&`)
ไม่ใช่ส่ง `String` ตรง ๆ แม้ว่าค่าจริงเบื้องหลังจะ "เกี่ยวข้องกัน" ก็ตาม — Rust ไม่มีการแปลง type แบบ implicit ให้เลย
(สอดคล้องกับหลักการเดียวกันที่เราเห็นเรื่องการแปลง type ตัวเลขใน Part 3)

**2. สร้าง mutable reference สองตัวไปยังค่าเดียวกันโดยไม่ทันสังเกตว่าตัวแรกยังไม่หมดอายุ**

```rust
fn main() {
    let mut inventory_count = String::from("มีสินค้า 10 ชิ้น");

    let updater1 = &mut inventory_count;
    let updater2 = &mut inventory_count; // ยังไม่ได้ใช้ updater1 เสร็จ แต่สร้างตัวใหม่ทับไปแล้ว

    updater1.push_str(" (กำลังอัปเดต)");
    updater2.push_str(" (อัปเดตซ้ำ)");

    println!("{updater1}");
}
```

```
error[E0499]: cannot borrow `inventory_count` as mutable more than once at a time
 --> src/main.rs:5:17
  |
4 |     let updater1 = &mut inventory_count;
  |                    -------------------- first mutable borrow occurs here
5 |     let updater2 = &mut inventory_count;
  |                    ^^^^^^^^^^^^^^^^^^^^ second mutable borrow occurs here
6 |
7 |     updater1.push_str(" (กำลังอัปเดต)");
  |     -------- first borrow later used here
```

**วิธีแก้**: ใช้ `updater1` ให้เสร็จงานทั้งหมดก่อน (หรือจำกัด scope ด้วย block) แล้วค่อยสร้าง `updater2` ทีหลัง — หรือถ้า
ทั้งสองตัวจำเป็นต้องแก้ไขค่าเดียวกันจริง ๆ ในเวลาเดียวกัน (ซึ่งพบน้อยมากในโค้ดปกติ) ให้กลับไปคิดใหม่ว่า design ของโค้ด
ควรจะมี "ผู้แก้ไขค่านี้" กี่คนกันแน่ในจุดนั้น ๆ ของโปรแกรม — บั๊กแบบนี้มักเป็นสัญญาณของ logic ที่สับสนตั้งแต่ต้น มากกว่า
เป็นแค่ syntax error ธรรมดา

**3. สร้าง mutable reference ทั้งที่ยังมี immutable reference ค้างอยู่ (สลับลำดับจากตัวอย่างในเนื้อหา)**

```rust
fn main() {
    let mut balance = String::from("1,000 บาท");

    let current = &mut balance;
    let snapshot = &balance; // ❌ ยืมแบบ immutable ขณะที่ current (mutable) ยังจะถูกใช้ต่อ
    current.push_str(" (pending)");

    println!("{snapshot}");
}
```

```
error[E0502]: cannot borrow `balance` as immutable because it is also borrowed as mutable
 --> src/main.rs:5:20
  |
4 |     let current = &mut balance;
  |                   ------------ mutable borrow occurs here
5 |     let snapshot = &balance;
  |                    ^^^^^^^^ immutable borrow occurs here
6 |     current.push_str(" (pending)");
  |     ------- mutable borrow later used here
```

สังเกตว่านี่คือ error เดียวกับหัวข้อ 7.6 แต่**สลับลำดับ** — คราวนี้ mutable ถูกสร้างก่อน แล้วพยายามสร้าง immutable ทีหลัง
ขณะที่ mutable ตัวเดิมยังต้องถูกใช้ต่อ **วิธีแก้**: ใช้ `current` ให้เสร็จงานที่ต้องการก่อน (หรือจัดลำดับให้ `current`
ไม่ต้องถูกใช้อีกหลังจากจุดที่สร้าง `snapshot`) แล้วค่อยอ่านค่าผ่าน `snapshot` ทีหลัง — กฎข้อที่ 1 ใช้กับทั้งสองทิศทาง
เท่ากันเสมอ ไม่สำคัญว่า mutable หรือ immutable ถูกสร้างก่อนกัน สิ่งที่สำคัญคือ **ช่วงเวลาที่ทั้งสอง "มีชีวิตอยู่" ห้าม
ทับซ้อนกันเลย**

**4. พยายาม move ค่าออกจาก reference (ไม่ใช่ยืมอ่าน แต่พยายามเอา ownership ออกมา)**

```rust
fn extract_owned(s: &String) -> String {
    let owned: String = *s; // พยายาม dereference แล้ว move ค่า String ออกมาจาก reference
    owned
}

fn main() {
    let name = String::from("Rustacean");
    let extracted = extract_owned(&name);
    println!("{extracted}");
}
```

```
error[E0507]: cannot move out of `*s` which is behind a shared reference
 --> src/main.rs:2:26
  |
2 |     let owned: String = *s;
  |                         ^^ move occurs because `*s` has type `String`, which does not implement the `Copy` trait
  |
help: consider cloning the value if the performance cost matters
  |
2 |     let owned: String = s.clone();
  |                         ~~~~~~~~
```

**วิธีแก้**: เมื่อคุณมีแค่ reference (`&String`) และต้องการ `String` ที่เป็นเจ้าของจริง ๆ (owned value) คุณ**ไม่มีสิทธิ์
เอา ownership ออกมาจากข้อมูลที่คนอื่นเป็นเจ้าของ** เพราะนั่นจะละเมิดกฎ ownership ข้อ 2 จาก Part 6 ทันที (เจ้าของเดิมก็ยัง
คิดว่าตัวเองเป็นเจ้าของอยู่) ทางเลือกที่ถูกต้องมีสองทาง: (1) ถ้าแค่ต้องการอ่านค่า ให้ใช้งานผ่าน `s` (หรือ `&*s`) ตรง ๆ
โดยไม่ต้อง move ออกมาเลย หรือ (2) ถ้าจำเป็นต้องมี owned copy จริง ๆ (เช่นต้องเก็บไว้ใช้นานกว่า reference เดิม) ให้ใช้
`.clone()` อย่างตั้งใจ (`s.clone()`) เพื่อสร้างข้อมูลใหม่ที่แยกจากต้นฉบับอย่างสมบูรณ์ — นี่คือเหตุผลที่ error message
แนะนำ `.clone()` ให้ตรง ๆ เลย

**5. คืน reference ไปยังตัวแปร local โดยไม่รู้ตัว (dangling reference)**

ปัญหานี้พบบ่อยมากในฟังก์ชันที่พยายาม "สร้างค่าใหม่ในฟังก์ชันแล้วคืน reference ของมันออกไป" ซึ่งเราเห็นตัวอย่างเต็ม ๆ
ไปแล้วในหัวข้อ 7.8 (`fn dangle() -> &String`) **วิธีแก้ที่จำง่ายที่สุด**: ถ้าข้อมูลถูกสร้างขึ้น**ภายใน**ฟังก์ชัน (ไม่ได้
รับมาจาก parameter) แล้วต้องการส่งออกไปให้ผู้เรียกใช้ต่อ ให้**คืน ownership** (คืน `String` ไม่ใช่ `&String`) เสมอ —
reference ที่คืนออกจากฟังก์ชันได้อย่างปลอดภัยต้อง "สืบทอด" อายุมาจาก reference parameter ที่รับเข้ามาเท่านั้น (รายละเอียด
เต็มรูปแบบจะเรียนใน Part 20/23 เรื่อง lifetimes)

**6. (กับดักเชิง design ไม่ใช่ compile error) หนีปัญหา borrow checker ด้วยการ `.clone()` ทุกอย่างแบบไม่คิด**

มือใหม่ที่เจอ error จาก borrow checker บ่อยครั้งจะเลือกทางลัดที่ดูเหมือนแก้ปัญหาได้ทันที คือใส่ `.clone()` ทุกจุดที่
compiler บ่น จนกว่าโค้ดจะ compile ผ่าน:

```rust
fn calculate_total(prices: Vec<i32>) -> i32 { // (ตัวอย่างเชิงแนวคิด — Vec<T> จะเรียนเต็ม ๆ ใน Part 13)
    prices.iter().sum()
}

fn main() {
    let cart = vec![100, 250, 75];
    let total = calculate_total(cart.clone()); // clone ทั้ง ๆ ที่แค่ต้องการอ่าน ไม่จำเป็นต้อง clone เลย
    println!("ยอดรวม {total} จากตะกร้า {cart:?}");
}
```

โค้ดนี้ **compile ผ่านและทำงานถูกต้อง** แต่มันคือการแก้ปัญหาแบบ "ผิดที่ต้นเหตุ" — จริง ๆ แล้ว `calculate_total` ควรรับ
`&Vec<i32>` (หรือ `&[i32]` แบบที่เราเห็นในหัวข้อ 7.9) เพราะมันแค่ต้องการอ่านผลรวม ไม่ได้ต้องการเป็นเจ้าของ `Vec` เลย
การ `.clone()` ในกรณีนี้สร้างการ copy ข้อมูลทั้งชุดบน heap ขึ้นมาใหม่ทุกครั้งที่เรียกฟังก์ชัน ซึ่งมี cost ด้าน performance
ที่ไม่จำเป็นเลย **วิธีแก้ที่ถูกต้อง**: ทุกครั้งที่ compiler บ่นเรื่อง ownership/borrowing ให้ **ถามตัวเองก่อนว่า "ฟังก์ชันนี้
จำเป็นต้องเป็นเจ้าของค่านี้จริง ๆ หรือแค่ต้องการอ่าน/แก้ไขมันชั่วคราว"** — ถ้าคำตอบคือ "แค่ต้องการอ่าน/แก้ไข" ให้เปลี่ยน
เป็นรับ reference (`&T`/`&mut T`) แทนการรับค่าตรง ๆ แล้ว `.clone()` จะไม่จำเป็นเลยในกรณีส่วนใหญ่ — สงวน `.clone()` ไว้ใช้
เฉพาะเมื่อคุณ**ต้องการ**ข้อมูลชุดใหม่ที่เป็นเจ้าของแยกจากต้นฉบับจริง ๆ เท่านั้น (เช่นต้องเก็บไว้ใช้ในโครงสร้างข้อมูลอื่นที่
มีอายุยืนกว่าต้นฉบับ)

**7. ลืมว่า `mut` ที่ตัวแปรต้นทางไม่ได้ทำให้ reference แบบ `&` (ไม่ใส่ `mut`) เขียนได้**

มือใหม่บางคนเห็นว่าตัวแปรต้นทางประกาศด้วย `mut` แล้วคิดว่า reference ที่สร้างจากมันจะแก้ไขได้เสมอ (ตามที่อธิบายเจาะลึก
ไปแล้วในหัวข้อ 7.2):

```rust
fn main() {
    let mut config_value = 100;
    let view = &config_value; // สร้าง & เฉย ๆ ไม่ใช่ &mut
    *view += 1; // ❌ view เป็น immutable reference ถึงแม้ config_value จะเป็น mut ก็ตาม
    println!("{view}");
}
```

จะได้ error `E0594: cannot assign to *view, as view is a & reference` ทันที **วิธีแก้**: ต้องสร้าง reference เป็น
`&mut config_value` ตั้งแต่แรกถ้าต้องการแก้ไขค่าผ่านมัน จำหลักไว้ว่า **`mut` ที่ตัวแปรต้นทางแค่ "อนุญาต" ให้สร้าง
`&mut` ได้ ไม่ได้ทำให้ reference ทุกตัวที่สร้างจากมันแก้ไขได้โดยอัตโนมัติ** — mutability ของ reference กำหนดที่จุด
สร้าง reference นั้นเอง (`&` หรือ `&mut`) เสมอ

## แบบฝึกหัด (Exercises)

1. **[ง่าย]** โค้ดต่อไปนี้ compile ไม่ผ่าน หาสาเหตุและแก้ไขให้ถูกต้อง **โดยไม่เปลี่ยน signature ของฟังก์ชัน `describe`
   เลย** (แก้แค่ตอนเรียกใช้ในฟังก์ชัน `main` เท่านั้น):
   ```rust
   fn describe(product_name: &String, price: &i32) {
       println!("{product_name} ราคา {price} บาท");
   }

   fn main() {
       let name = String::from("หูฟังบลูทูธ");
       let price = 590;
       describe(name, price);
   }
   ```
   (hint: ทั้ง `name` และ `price` ต้องส่งเข้าไปแบบ reference เพราะ `describe` รับ `&String` และ `&i32` — ลองเติม `&`
   ให้ถูกจุดทั้งสองที่ แล้วสังเกตว่า `name` และ `price` ยังใช้งานต่อได้ใน `main` หลังเรียกฟังก์ชันหรือไม่)

2. **[ง่าย-กลาง]** เขียนฟังก์ชัน `fn double_all(numbers: &mut [i32; 4])` ที่รับ mutable reference ไปยัง array ขนาด 4
   แล้วคูณค่าทุกตัวในนั้นด้วย 2 (แก้ไขในตำแหน่งเดิม ไม่สร้าง array ใหม่) จากนั้นเขียน `main` ที่สร้าง
   `let mut numbers = [1, 2, 3, 4];` เรียก `double_all(&mut numbers)` แล้วพิมพ์ `numbers` ออกมาดูผลลัพธ์
   (hint: ต้องวน loop แล้ว dereference ด้วย `*` ก่อนคูณค่า เช่น `for n in numbers { *n *= 2; }` — ลองคิดดูว่าทำไมต้องมี
   `*` แต่ตอนอ่านค่าอย่างเดียว (เช่นในหัวข้อ 7.9 ฟังก์ชัน `calculate_average`) กลับไม่จำเป็นต้องมี `*` เสมอไป)

3. **[กลาง]** โค้ดต่อไปนี้มี borrow checker error ให้หาว่า error คืออะไร ("error code" อะไร) และแก้ไขให้ compile ผ่าน
   ด้วย **2 วิธีที่แตกต่างกัน**: วิธีที่ 1 คือปรับลำดับการใช้งานตัวแปรให้ NLL ช่วยได้เอง (ไม่ต้องใช้ block) วิธีที่ 2
   คือใช้ block `{ }` แบบดั้งเดิมจำกัด scope อย่างชัดเจน:
   ```rust
   fn main() {
       let mut wallet = String::from("500 บาท");

       let receipt = &wallet;
       let updater = &mut wallet;
       updater.push_str(" (หลังหักค่าใช้จ่าย)");

       println!("ใบเสร็จอ้างอิง: {receipt}");
       println!("กระเป๋าเงินล่าสุด: {wallet}");
   }
   ```
   (hint: error คือ `E0502` เพราะ `receipt` (immutable) ยังจะถูกใช้ที่ `println!` ท้ายฟังก์ชัน ขณะที่ `updater` (mutable)
   ถูกสร้างและใช้งานก่อนหน้านั้น ทำให้ทับซ้อนกัน — ลองย้ายบรรทัด `println!("ใบเสร็จอ้างอิง: {receipt}");` ไปไว้ก่อน
   สร้าง `updater` ดูว่า NLL ช่วยแก้ปัญหาให้เองได้หรือไม่)

4. **[ยาก/ประยุกต์]** ขยายตัวอย่างระบบคะแนนนักเรียนจากหัวข้อ 7.9 ให้ครอบคลุมมากขึ้น โดยเพิ่มฟังก์ชันใหม่ 2 ฟังก์ชัน:
   (ก) `fn find_lowest(scores: &[i32; 5]) -> i32` หาคะแนนต่ำสุดในห้อง (แบบอ่านอย่างเดียว คล้าย `find_highest`) และ
   (ข) `fn cap_at_maximum(scores: &mut [i32; 5], max: i32)` ที่ปรับคะแนนทุกคนที่**เกิน** `max` ให้เท่ากับ `max` พอดี
   (แบบแก้ไขค่าจริง ใช้ `saturating_sub`/`if` ตามความเหมาะสม — คะแนนที่ไม่เกินให้คงค่าเดิมไว้) จากนั้นเขียน `main`
   ที่เรียกใช้ทั้ง 4 ฟังก์ชัน (`calculate_average`, `find_highest`, `find_lowest`, `cap_at_maximum`) เรียงลำดับให้สมเหตุสมผล
   ตามความหมายทางธุรกิจ (เช่น หาค่าเฉลี่ย/สูงสุด/ต่ำสุดก่อนปรับ แล้วจำกัดคะแนนสูงสุดไม่ให้เกิน 100 แล้วคำนวณค่าเฉลี่ยใหม่
   อีกครั้งหลังปรับ) และตอบคำถามสั้น ๆ (3-5 บรรทัด): **ทำไมการเรียงลำดับการเรียกฟังก์ชัน (อ่านก่อน แก้ไขทีหลัง) ถึงสำคัญ
   ต่อการไม่ให้เกิด borrow checker error ในตัวอย่างนี้?**
   (hint: `cap_at_maximum` ต้องใช้ `&mut` ซึ่งกฎข้อที่ 1 ห้ามไม่ให้มี `&` (immutable) ค้างอยู่ในเวลาเดียวกัน — ถ้าคุณเก็บ
   ผลลัพธ์จาก `find_highest`/`find_lowest` ไว้ในตัวแปรแล้วค่อยพิมพ์**หลัง**เรียก `cap_at_maximum` ก็ยังทำได้ตราบใดที่
   ตัวแปรเหล่านั้นเป็น `i32` ที่ copy ค่ามาแล้ว ไม่ใช่ reference ที่ยังผูกอยู่กับ array ต้นฉบับ — สังเกตความแตกต่างระหว่าง
   "เก็บผลลัพธ์ที่เป็นค่า (`i32`, มี `Copy`)" กับ "เก็บ reference ที่ยังมีชีวิตผูกกับข้อมูลต้นฉบับอยู่")

## สรุป

บทนี้คือจุดเปลี่ยนสำคัญของทั้งหลักสูตร เราเริ่มจากปัญหาที่ ownership เพียงอย่างเดียว (จาก Part 6) ทิ้งไว้: การส่งค่าที่ไม่ใช่
`Copy` เข้าไปในฟังก์ชันทำให้ ownership ถูกย้ายไปเสมอ บังคับให้เราต้องคืนค่ากลับมาอย่างน่าเกลียดถ้าต้องการใช้ค่านั้นต่อ —
**Reference** (`&T` และ `&mut T`) แก้ปัญหานี้ได้อย่างสมบูรณ์ ด้วยการให้ฟังก์ชัน "ยืม" สิทธิ์เข้าถึงข้อมูลไปใช้ชั่วคราว
โดยไม่ต้องโอนกรรมสิทธิ์เลยแม้แต่นิดเดียว

เราเจาะลึก **กฎของ borrowing ทั้งสองข้อ**: กฎข้อที่ 1 (mutable ได้แค่หนึ่งตัว หรือ immutable ได้หลายตัว แต่ไม่ทั้งสองพร้อมกัน)
ที่ป้องกัน data race และ aliasing bug ได้ตั้งแต่ compile time โดยไม่ต้องมี garbage collector หรือ lock ตอน runtime เลย
และกฎข้อที่ 2 (reference ต้องไม่ dangling) ที่ป้องกัน undefined behavior จากการอ้างอิงข้อมูลที่ถูกทำลายไปแล้ว เราเห็น
error message จริงที่พบบ่อยที่สุดจาก borrow checker (`E0499` สำหรับ mutable ซ้อนกัน, `E0502` สำหรับผสม mutable กับ
immutable, `E0106` สำหรับ dangling reference) พร้อมวิธีแก้ที่ถูกต้องของแต่ละกรณี และเข้าใจว่า **Non-Lexical Lifetimes
(NLL)** ทำให้ borrow checker สมัยใหม่ฉลาดพอที่จะไม่บังคับให้เราเขียน "scope gymnastics" แบบที่มือใหม่หลายคนกลัวกันไว้

ที่สำคัญที่สุด: **ownership (Part 6) กับ borrowing (บทนี้) คือสองเสาหลักที่ทำงานร่วมกันเป็นระบบเดียว** ownership ตอบคำถาม
ว่า "ใครมีสิทธิ์ทำลายข้อมูลนี้ และเมื่อไหร่" ส่วน borrowing ตอบคำถามว่า "ใครมีสิทธิ์เข้าถึงข้อมูลนี้ชั่วคราว และในรูปแบบไหน
(อ่านอย่างเดียว หรือแก้ไขได้)" เมื่อรวมสองระบบนี้เข้าด้วยกัน compiler จึงสามารถพิสูจน์ได้อย่างสมบูรณ์ตั้งแต่ก่อนโปรแกรมจะรัน
ว่า: จะไม่มี use-after-free, ไม่มี double-free, ไม่มี dangling pointer, และไม่มี data race เกิดขึ้นเลยในโค้ด "safe Rust"
— **นี่คือคำตอบที่แท้จริงของคำถามที่ Part 1 ทิ้งไว้ตั้งแต่บทแรก**: Rust ทำอย่างไรถึงได้ทั้ง "เร็วเท่า C/C++" และ "ปลอดภัย
เท่าภาษาที่มี garbage collector" พร้อมกันในเวลาเดียวกัน คำตอบคือระบบ ownership + borrowing ที่ทำงานทั้งหมดตอน compile
time โดยไม่เหลือ cost ใด ๆ ไว้ตอน runtime เลยแม้แต่นิดเดียว — เป็นไปตามหลัก zero-cost abstraction อย่างสมบูรณ์แบบที่สุด

ใน **Part 8** เราจะเรียนรู้ **Slices (`&str`, `&[T]`)** ซึ่งเป็นรูปแบบพิเศษของ reference ที่ชี้ไปยัง "ส่วนหนึ่ง" ของข้อมูล
ต่อเนื่องกัน (เช่น ส่วนหนึ่งของ string หรือส่วนหนึ่งของ array) แทนที่จะชี้ไปยังข้อมูลทั้งชุด นี่คือเหตุผลที่ฟังก์ชันใน
Rust แบบ idiomatic มักรับ `&str` แทน `&String` และรับ `&[T]` แทน `&Vec<T>` หรือ `&[T; N]` ที่เราใช้ในตัวอย่างท้ายบทนี้ —
slice จะทำให้โค้ดที่เราเขียนในบทนี้ยืดหยุ่นขึ้นไปอีกขั้น โดยยังคงหลักการ ownership และ borrowing ที่เราเพิ่งเรียนมาทั้งหมด
