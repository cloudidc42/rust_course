# Part 13: Collections: Vec<T>

> โมดูล: พื้นฐานภาษา Rust (Core Language Fundamentals) | ระดับ: พื้นฐาน | เวลาโดยประมาณ: 150 นาที

## เป้าหมายของบทเรียน

หลังจากจบบทนี้ คุณจะสามารถ:

- อธิบายได้ว่าทำไม array (`[T; N]`) ที่เรียนมาจาก Part 3 และ Part 8 ถึง "ไม่พอ" สำหรับงานจริงจำนวนมาก และรู้จัก
  `Vec<T>` ในฐานะ collection ที่จองพื้นที่บน heap และ**ปรับขนาดได้ตอน runtime**
- สร้าง `Vec<T>` ได้ทั้ง 3 วิธีหลัก (`Vec::new()`, macro `vec![...]`, `Vec::with_capacity(n)`) และอธิบายได้ว่า
  ทำไมการจอง capacity ล่วงหน้าถึงส่งผลต่อประสิทธิภาพจริง โดยเชื่อมโยงกับต้นทุนของการจอง heap memory ที่เรียนใน Part 6
- อธิบายโครงสร้างภายในของ `Vec<T>` ในเชิง memory (pointer + length + capacity) และเปรียบเทียบกับ `&[T]` slice
  (pointer + length เท่านั้น ไม่มี ownership) จาก Part 8 ได้อย่างชัดเจนว่าต่างกันอย่างไรและทำไม
- ใช้ method หลักในการเพิ่ม/ลบ/ค้นหา/เรียงลำดับสมาชิกของ `Vec<T>` ได้อย่างถูกต้อง (`push`, `pop`, `insert`, `remove`,
  `extend`, `sort`, `sort_by`, `sort_by_key`, `binary_search`, `contains`) พร้อมเข้าใจ trade-off ด้าน performance
  ของแต่ละตัว
- เลือกใช้ indexing (`v[i]`) กับ `.get(i)` ได้อย่างถูกสถานการณ์ โดยเข้าใจปรัชญาเดียวกันกับ `Option<T>` ที่เรียนใน
  Part 11 — และอธิบายได้ว่าทำไม Rust จึงให้ทางเลือกทั้งแบบ panic และแบบไม่ panic ไว้คู่กันเสมอ
- อธิบายได้ว่าทำไมการถือ reference ไปยังสมาชิกตัวหนึ่งของ `Vec` พร้อมกับพยายาม `push` ลง `Vec` ตัวเดียวกัน ถึงเป็น
  ข้อผิดพลาดที่ compiler ปฏิเสธตั้งแต่ compile time (E0502) ไม่ใช่ข้อจำกัดที่ไม่มีเหตุผล แต่ป้องกันบั๊กร้ายแรงระดับ
  memory safety ที่ภาษาอย่าง C++ ปล่อยให้เกิดขึ้นได้จริง
- เขียนโปรแกรมจัดการข้อมูลจริงที่ผสม `Vec<T>` เข้ากับ struct (Part 9), `Option<T>` (Part 11), และ slice (Part 8)
  เพื่อสร้างระบบจัดการสินค้าคงคลังที่ใช้งานได้จริง

## ความรู้ที่ต้องมีมาก่อน

- **Part 3**: ชนิดข้อมูล array (`[T; N]`) — รู้ว่าความยาวเป็นส่วนหนึ่งของ type และต้องรู้ตายตัวตั้งแต่ compile time
- **Part 6**: Ownership, move, การจองและคืนหน่วยความจำบน heap (`String::from` จองพื้นที่ heap, ตัวแปรคืนพื้นที่
  อัตโนมัติเมื่อออกจาก scope ผ่าน `Drop`) — `Vec<T>` ทำงานบนหลักการเดียวกันทุกประการ เพียงเก็บข้อมูลชนิดใดก็ได้
  ไม่ใช่แค่ตัวอักษร
- **Part 7**: Borrowing, `&T`/`&mut T`, กฎการยืม (ยืมอ่านพร้อมกันได้หลายตัว ยืมเขียนได้ทีละตัว ห้ามยืมเขียนพร้อมยืมอ่าน)
  และ Non-Lexical Lifetimes (NLL) — กฎเดียวกันนี้จะกลับมาเป็นหัวใจของหัวข้อ 13.7 ในบทนี้
- **Part 8**: Slice (`&[T]`, `&mut [T]`) — บทนี้ **ต่อยอดตรงจาก Part 8** อย่างที่ตัวบทนั้นได้ทีเซอร์ไว้แล้วว่า
  `&[T]` คือฐานที่ `Vec<T>` สร้างต่อยอด ถ้าคุณเข้าใจ slice มาแน่นแล้ว เนื้อหาส่วนใหญ่ของบทนี้จะเป็นการนำแนวคิดเดิมมา
  ขยายผลเท่านั้น
- **Part 9**: Structs และ method ผ่าน `impl` block — ตัวอย่างท้ายบทจะใช้ `struct Product` สไตล์เดียวกับที่เรียนใน
  Part 9 มาสร้างเป็น `Vec<Product>`
- **Part 11**: `Option<T>` — `.pop()`, `.get()`, `.first()`, `.last()` ของ `Vec<T>` ทุกตัวคืนค่าเป็น `Option<T>`
  หรือ `Option<&T>` เสมอ ถ้ายังไม่แน่นเรื่อง `Option`, `match`, `unwrap()`, `unwrap_or()` ควรย้อนไปทวนก่อน
- **Part 12**: `Result<T, E>` และ `?` operator — เราจะใช้ `.parse()` ที่คืน `Result` ในตัวอย่างบางจุด และอ้างอิงหลัก
  การจัดการ error แบบเดียวกัน

ถ้าคุณเข้าใจ Part 6-8 มาอย่างแน่น บทนี้จะรู้สึกเหมือน "ปลดล็อกข้อจำกัดสุดท้าย" ของ array ที่ค้างมาตั้งแต่ Part 3 —
ทุกกฎเรื่อง ownership และ borrowing ที่เรียนมาไม่มีอะไรเปลี่ยนแปลงเลยแม้แต่นิดเดียวใน `Vec<T>` มีแค่โครงสร้างข้อมูล
เปลี่ยนจาก "ขนาดตายตัว" เป็น "ขนาดปรับได้" เท่านั้น

## เนื้อหา

### 13.1 ปัญหาเริ่มต้น: ทำไม array ไม่เพียงพอสำหรับงานจริงจำนวนมาก

จาก Part 3 เราเรียนว่า array คือชุดข้อมูลชนิดเดียวกันที่มี **ความยาวคงที่ ซึ่งเป็นส่วนหนึ่งของ type เอง**
(`[T; N]` — `N` ต้องรู้ตายตัวตั้งแต่ compile time) นี่คือข้อจำกัดที่ฟังดูเล็กน้อยตอนเรียน Part 3 แต่พอเริ่มเขียน
โปรแกรมที่ใกล้เคียงงานจริงมากขึ้น ข้อจำกัดนี้จะกลายเป็นปัญหาใหญ่ทันที ลองดูสถานการณ์ที่พบได้ทุกวันในงานเขียนโปรแกรม
จริง: **ระบบตะกร้าสินค้าที่ผู้ใช้เพิ่มสินค้าไปเรื่อย ๆ โดยไม่รู้จำนวนล่วงหน้า**

```rust
fn main() {
    let mut cart: [&str; 3] = ["ปากกา", "ยางลบ", "สมุด"];
    cart.push("ไม้บรรทัด");
    println!("{:?}", cart);
}
```

โค้ดนี้ **compile ไม่ผ่านเลย** เพราะ array ไม่มี method ชื่อ `push` อยู่จริง ๆ:

```
error[E0599]: no method named `push` found for array `[&str; 3]` in the current scope
 --> src/main.rs:3:10
  |
3 |     cart.push("ไม้บรรทัด");
  |          ^^^^ method not found in `[&str; 3]`
```

Error message ตรงไปตรงมามาก: `[&str; 3]` ไม่มี method นี้ และในความเป็นจริง **มันไม่มีทางมี method แบบนี้ได้เลย**
ไม่ว่าคุณจะพยายามแค่ไหน เพราะความยาว `3` ถูกฝังอยู่ใน type ของตัวแปรตั้งแต่ตอนประกาศ — การ "เพิ่มสมาชิก" หมายถึงการ
เปลี่ยน type จาก `[&str; 3]` เป็น `[&str; 4]` ซึ่งเป็นชนิดข้อมูลคนละชนิดกันโดยสิ้นเชิงในสายตา compiler (เหมือนที่เรียน
ใน Part 3 ว่า `mut` อนุญาตให้เปลี่ยน**ค่า**ภายใน**ชนิดเดิม**เท่านั้น ไม่ใช่เปลี่ยนชนิด)

บางคนอาจคิดจะแก้ปัญหาด้วยการ "จองไว้ให้เยอะเกินพอ" แล้วใช้ตัวแปรนับจำนวนที่ใช้จริงแยกไว้อีกตัว:

```rust
fn main() {
    let mut cart: [&str; 100] = [""; 100]; // จองไว้ 100 ช่อง เผื่อไว้ก่อน
    let mut cart_len = 0;

    cart[cart_len] = "ปากกา";
    cart_len += 1;
    cart[cart_len] = "ยางลบ";
    cart_len += 1;

    println!("สินค้าในตะกร้า {cart_len} รายการ: {:?}", &cart[..cart_len]);
}
```

โค้ดนี้ compile ผ่านและทำงานได้ แต่มันคือ **วิธีแก้ปัญหาแบบเลี่ยงบาลี** ที่แย่ในหลายมิติ:

1. **สิ้นเปลืองหน่วยความจำ** — จอง 100 ช่องไว้ตลอด แม้จะใช้จริงแค่ 2 ช่อง หน่วยความจำ 98 ช่องที่เหลือถูกจองทิ้งไว้
   เฉย ๆ (และค่า `""` ที่เติมไว้ก็ต้องคำนวณตอนสร้าง array ด้วย ไม่ใช่ของฟรี)
2. **ยังมีเพดานตายตัวอยู่ดี** — ถ้าผู้ใช้ใส่สินค้าเกิน 100 รายการ โปรแกรมจะ panic ทันทีตอนเขียนเกินขอบ (index out of
   bounds — เราจะเห็น error แบบนี้ชัด ๆ ในหัวข้อ 13.5) การเดา "จำนวนสูงสุดที่เป็นไปได้" ล่วงหน้าเป็นเรื่องเสี่ยงเสมอ
   ในโปรแกรมจริง
3. **ต้องดูแลตัวแปรสองตัวให้ตรงกันเอง** (`cart` กับ `cart_len`) — compiler ไม่ได้ช่วยตรวจสอบความสัมพันธ์ระหว่างสอง
   ตัวแปรนี้ให้เลย ถ้าเขียนโค้ดผิดที่ไหนสักที่จนสองตัวแปรนี้ไม่ตรงกัน (เช่น ลืม `+= 1`) จะได้บั๊กที่ตรวจจับยาก

ปัญหานี้ไม่ใช่เรื่องของ "เขียนให้ฉลาดขึ้น" แต่เป็นข้อจำกัดพื้นฐานของ array ที่**ไม่มีทางแก้ไขได้ในตัวมันเอง** — ลอง
ดูอีกตัวอย่างที่แสดงข้อจำกัดนี้ชัดกว่าเดิม: การพยายามให้ความยาว array ขึ้นกับค่าที่รู้เฉพาะตอน runtime

```rust
fn main() {
    let item_count: usize = 5; // สมมติว่าค่านี้มาจาก input ผู้ใช้ตอน runtime จริง ๆ
    let orders: [String; item_count] = Default::default();
    println!("{:?}", orders);
}
```

```
error[E0435]: attempt to use a non-constant value in a constant
 --> src/main.rs:3:26
  |
3 |     let orders: [String; item_count] = Default::default();
  |                          ^^^^^^^^^^ non-constant value
  |
help: consider using `const` instead of `let`
  |
2 -     let item_count: usize = 5; // สมมติว่าค่านี้มาจาก input ผู้ใช้ตอน runtime จริง ๆ
2 +     const item_count: usize = 5; // สมมติว่าค่านี้มาจาก input ผู้ใช้ตอน runtime จริง ๆ
  |
```

Error นี้ชี้ประเด็นสำคัญที่สุดของหัวข้อนี้ตรง ๆ: **`[T; N]` ต้องการให้ `N` เป็นค่าคงที่ที่ compiler รู้ตั้งแต่ตอน
compile (constant expression) เท่านั้น** ต่อให้ `item_count` เป็นตัวแปรที่ในทางปฏิบัติจะมีค่าเดียวตายตัวตลอดการรัน
โปรแกรมครั้งนั้น (ไม่ได้เปลี่ยนไปมา) แต่ในสายตาของ compiler มันคือ "ค่าที่รู้แค่ตอน runtime" — และ compiler ต้อง
ตัดสินใจเรื่องขนาด stack ของ `orders` **ตั้งแต่ตอน compile** ไม่สามารถรอดูผลตอนรันจริงได้เลย help message ที่แนะนำ
ให้เปลี่ยนเป็น `const` ก็ยืนยันประเด็นนี้ชัดเจน — แต่ในสถานการณ์จริง ค่าที่มาจาก input ผู้ใช้ไม่มีทางเป็น `const`
ได้อยู่แล้ว (const ต้องคำนวณได้ตอน compile time ตามที่เรียนใน Part 3)

**สรุปปัญหาที่แท้จริง**: เราต้องการชนิดข้อมูลที่:

1. เก็บสมาชิกหลายตัวชนิดเดียวกัน (เหมือน array)
2. เข้าถึงสมาชิกด้วย index ได้เร็ว (เหมือน array)
3. **แต่ความยาวปรับเปลี่ยนได้ตอน runtime** โดยไม่ต้องรู้ล่วงหน้าตอน compile
4. **และไม่ต้องดูแลตัวแปรความยาวแยกเองด้วยมือ** — collection ควรรู้จักความยาวของตัวเองเสมอ

นี่คือสิ่งที่ `Vec<T>` (อ่านว่า "Vector of T" หรือสั้น ๆ ว่า "Vec") ถูกออกแบบมาเพื่อแก้ปัญหาตรงนี้โดยเฉพาะ — มันคือ
collection ที่ **จองพื้นที่บน heap** (แนวคิดเดียวกับ `String` ที่เราใช้มาตั้งแต่ Part 6) และสามารถ **ขยายพื้นที่นั้น
ได้เองตอน runtime** เมื่อมีสมาชิกเพิ่มเข้ามา โดยที่ผู้ใช้งานไม่ต้องดูแลเรื่องหน่วยความจำเองแม้แต่นิดเดียว

### 13.2 สร้าง `Vec<T>`: `Vec::new()`, macro `vec![...]`, และ `Vec::with_capacity(n)`

Rust มี 3 วิธีหลักในการสร้าง `Vec<T>` ซึ่งแต่ละวิธีเหมาะกับสถานการณ์ต่างกัน

#### วิธีที่ 1: `Vec::new()` — สร้าง Vec ว่างเปล่า แล้วเติมทีหลัง

```rust
fn main() {
    let mut numbers: Vec<i32> = Vec::new();
    numbers.push(10);
    numbers.push(20);
    numbers.push(30);

    println!("{:?}", numbers);
}
```

ผลลัพธ์:

```
[10, 20, 30]
```

**อธิบายโค้ดทีละส่วน:**

- `Vec::new()` — สร้าง `Vec<T>` ที่**ว่างเปล่าสนิท** (ยังไม่มีสมาชิกและยังไม่จองพื้นที่ heap เลยแม้แต่ byte เดียว
  ในตอนนี้)
- `let mut numbers` — สังเกตว่าต้องมี `mut` เสมอถ้าจะเรียก `.push()` ทีหลัง เพราะ `.push()` ต้องการ mutable borrow
  ของ `numbers` (กฎเดียวกับที่เรียนใน Part 3 และ Part 7 ทุกประการ — ไม่มีข้อยกเว้นให้กับ `Vec` เลย)
- `Vec<i32>` — เขียน type annotation ตรง ๆ ว่าเก็บ `i32` เพราะตอนสร้างด้วย `Vec::new()` ยังไม่มีค่าอะไรให้ compiler
  infer ชนิดข้อมูลได้ (ต่างจาก `vec![10, 20, 30]` ที่ compiler เดา `i32` ได้จากตัวเลขข้างในทันที) เราจะพูดถึงเรื่อง
  `Vec<T>` เป็น generic type อย่างเป็นทางการในหัวข้อ 13.11

#### วิธีที่ 2: macro `vec![...]` — สร้าง Vec พร้อมค่าเริ่มต้นทันที

ถ้ารู้ค่าเริ่มต้นอยู่แล้ว การใช้ macro `vec!` สะดวกกว่ามาก:

```rust
fn main() {
    let fruits = vec!["แอปเปิล", "กล้วย", "ส้ม"];
    println!("{:?}", fruits);

    // vec! ยังรองรับ syntax "ค่าเดิม; จำนวนซ้ำ" เหมือน array literal จาก Part 3
    let zeros = vec![0; 5];
    println!("{:?}", zeros);
}
```

ผลลัพธ์:

```
["แอปเปิล", "กล้วย", "ส้ม"]
[0, 0, 0, 0, 0]
```

`vec![a, b, c]` เทียบเท่ากับการสร้าง `Vec::new()` แล้ว `.push()` ทีละตัวตามลำดับ ส่วน `vec![0; 5]` เทียบเท่ากับ
"สร้าง `Vec` ที่มีสมาชิก 5 ตัว ค่าเริ่มต้นเป็น `0` ทั้งหมด" — syntax เดียวกันกับ array literal `[0; 5]` ที่เรียน
ใน Part 3 เป๊ะ ๆ ต่างกันแค่ผลลัพธ์เป็น `Vec<i32>` (ปรับขนาดได้) ไม่ใช่ `[i32; 5]` (ขนาดตายตัว) — `vec!` คือหนึ่งใน
macro มาตรฐานที่ใช้บ่อยที่สุดในโค้ด Rust ทุกโปรแกรม เพราะมันสั้นและอ่านง่ายกว่าการเรียก `Vec::new()` แล้ว `.push()`
ทีละบรรทัดอย่างมาก เมื่อรู้ค่าเริ่มต้นอยู่แล้ว

#### วิธีที่ 3: `Vec::with_capacity(n)` — จองพื้นที่ล่วงหน้าเพื่อประสิทธิภาพ

```rust
fn main() {
    let mut ids: Vec<u32> = Vec::with_capacity(1000);
    println!("len = {}, capacity = {}", ids.len(), ids.capacity());

    ids.push(1);
    println!("หลัง push 1 ตัว: len = {}, capacity = {}", ids.len(), ids.capacity());
}
```

ผลลัพธ์:

```
len = 0, capacity = 1000
หลัง push 1 ตัว: len = 1, capacity = 1000
```

สังเกตความแตกต่างสำคัญ: `Vec::with_capacity(1000)` สร้าง `Vec` ที่**ยังว่างเปล่า** (`len() == 0`) เหมือน
`Vec::new()` แต่**จองพื้นที่ heap ไว้ล่วงหน้าเผื่อสมาชิกได้ถึง 1000 ตัวทันที** (`capacity() == 1000`) — นี่คือความ
แตกต่างที่สำคัญมากระหว่าง **length** (จำนวนสมาชิกที่มีอยู่จริงตอนนี้) กับ **capacity** (จำนวนสมาชิกสูงสุดที่จอง
พื้นที่ไว้แล้ว โดยไม่ต้องขอพื้นที่เพิ่มจากระบบปฏิบัติการอีก) เราจะเจาะลึกความสัมพันธ์ของทั้งสองค่านี้แบบละเอียดใน
หัวข้อ 13.3-13.4

#### ทำไมการจอง capacity ล่วงหน้าถึงสำคัญต่อประสิทธิภาพจริง

จาก Part 6 เราเรียนว่าการจองหน่วยความจำบน heap (เช่นตอนสร้าง `String::from(...)`) **ไม่ใช่ของฟรี** — มันต้องขอ
พื้นที่จากระบบปฏิบัติการ (ผ่าน memory allocator) ซึ่งมีต้นทุนเวลาสูงกว่าการใช้ค่าบน stack มาก `Vec<T>` ก็ทำงานบน
หลักการเดียวกันทุกประการ: ทุกครั้งที่ `Vec` ต้องขยายพื้นที่ (เพราะสมาชิกเกิน capacity เดิม) มันต้อง:

1. ขอพื้นที่ heap ก้อนใหม่ที่ใหญ่กว่าเดิมจากระบบปฏิบัติการ
2. **คัดลอกสมาชิกทั้งหมดจากพื้นที่เก่าไปยังพื้นที่ใหม่** (memcpy)
3. คืนพื้นที่เก่าให้ระบบปฏิบัติการ

ถ้าคุณรู้อยู่แล้วว่ากำลังจะเพิ่มสมาชิกจำนวนมาก (เช่น อ่านข้อมูล 10,000 แถวจากไฟล์เข้า `Vec` ทีละแถว) การเรียก
`Vec::new()` เฉย ๆ แล้วปล่อยให้มันขยายพื้นที่ไปเรื่อย ๆ ตามธรรมชาติ (ซึ่งเราจะเห็นว่าขยายแบบ**เพิ่มเป็นสองเท่า**ทุก
ครั้งในหัวข้อ 13.4) หมายความว่าอาจต้องเกิดขั้นตอนขอพื้นที่ใหม่+คัดลอกข้อมูลซ้ำ ๆ หลายรอบ (แม้จะไม่บ่อยเท่าที่คิดเพราะ
กลยุทธ์เพิ่มเป็นสองเท่า แต่ก็ยังมีต้นทุนอยู่) ในทางกลับกัน ถ้าคุณเรียก `Vec::with_capacity(10_000)` ตั้งแต่แรก **จะ
ไม่มีการขยายพื้นที่เกิดขึ้นเลยแม้แต่ครั้งเดียว** ตราบใดที่สมาชิกไม่เกิน 10,000 ตัว — ประหยัดทั้งเวลาขอพื้นที่และเวลา
คัดลอกข้อมูลไปได้มาก

**หลักการปฏิบัติ**: ถ้าคุณพอเดาจำนวนสมาชิกสูงสุดที่จะเก็บได้ล่วงหน้า (แม้จะเป็นการเดาแบบหยาบ ๆ) ให้ใช้
`Vec::with_capacity(n)` เสมอ — มันไม่มีข้อเสียเลยถ้าเดาผิดไปทางน้อยกว่าจริง (แค่ขยายเพิ่มตามธรรมชาติเหมือนไม่ได้
จองไว้) แต่ถ้าเดาถูกหรือใกล้เคียง ประสิทธิภาพจะดีขึ้นชัดเจนโดยเฉพาะกับข้อมูลจำนวนมาก ในทางกลับกัน ถ้าไม่รู้จำนวน
ล่วงหน้าเลย (เช่น รับ input จากผู้ใช้แบบไม่รู้จบ) การใช้ `Vec::new()` ธรรมดาก็สมเหตุสมผลที่สุด เพราะกลยุทธ์การขยาย
พื้นที่อัตโนมัติของ `Vec` ถูกออกแบบมาให้มีประสิทธิภาพดีอยู่แล้วในกรณีทั่วไป (จะพิสูจน์เชิงคณิตศาสตร์ให้ดูในหัวข้อ 13.4)

### 13.3 โครงสร้างภายในของ `Vec<T>`: "fat owned buffer" เทียบกับ `&[T]` slice

จาก Part 8 เราเรียนว่า `&[T]` คือ **fat pointer** ที่เก็บคู่ `(pointer, length)` — ชี้ไปยังข้อมูลของคนอื่นโดยไม่ได้
เป็นเจ้าของ `Vec<T>` มีโครงสร้างที่คล้ายกันแต่เพิ่มอีกหนึ่ง field เข้ามา และที่สำคัญที่สุดคือ **มันเป็นเจ้าของข้อมูล
ของตัวเอง** (owns the heap buffer) ไม่ใช่แค่ยืมมา

มายืนยันด้วยขนาดจริงในหน่วยความจำ เหมือนที่เราทำกับ `&str` กับ `&String` ใน Part 8:

```rust
fn main() {
    println!("ขนาดของ Vec<i32>: {} bytes", std::mem::size_of::<Vec<i32>>());
    println!("ขนาดของ &[i32] (slice): {} bytes", std::mem::size_of::<&[i32]>());
    println!("ขนาดของ &Vec<i32>: {} bytes", std::mem::size_of::<&Vec<i32>>());
    println!("ขนาดของ usize: {} bytes", std::mem::size_of::<usize>());
}
```

ผลลัพธ์บนเครื่อง 64-bit ทั่วไป:

```
ขนาดของ Vec<i32>: 24 bytes
ขนาดของ &[i32] (slice): 16 bytes
ขนาดของ &Vec<i32>: 8 bytes
ขนาดของ usize: 8 bytes
```

ตัวเลขเหล่านี้เผยโครงสร้างภายในได้ชัดมาก:

- **`&Vec<i32>` มีขนาด 8 bytes** (thin pointer ธรรมดา ตัวเดียว) — เพราะ `Vec<i32>` เองเป็นชนิดข้อมูลที่มีขนาดคงที่
  รู้แน่นอนตอน compile time (ต่างจาก `[i32]` แบบ unsized ที่เรียนใน Part 8) reference ที่ชี้ไปยังมันจึงเป็น
  pointer เปล่า ๆ เหมือน `&String` ใน Part 8
- **`Vec<i32>` เองมีขนาด 24 bytes = 3 × usize (8 bytes × 3)** — เพราะภายใน `Vec<T>` (แบบง่ายที่สุด ไม่นับ
  รายละเอียดของ allocator ที่ซับซ้อนกว่านี้ในความเป็นจริง) ประกอบด้วย 3 field:

  1. **pointer** — ตำแหน่งของ heap buffer ที่เก็บสมาชิกจริง
  2. **length** (`usize`) — จำนวนสมาชิกที่มีอยู่จริงตอนนี้
  3. **capacity** (`usize`) — จำนวนสมาชิกสูงสุดที่ buffer ปัจจุบันรองรับได้ก่อนต้องขยาย

- **`&[i32]` มีขนาด 16 bytes = 2 × usize** — มีแค่ `(pointer, length)` เท่านั้น **ไม่มี capacity เลย** เพราะ slice
  ไม่ได้เป็นเจ้าของข้อมูล มันแค่ "มองเข้าไป" ในช่วงหนึ่งที่ตายตัวแล้ว ไม่มีสิทธิ์ (และไม่มีความจำเป็น) ต้องรู้ว่า
  buffer ต้นทางมีที่เหลือให้ขยายอีกแค่ไหน

ตารางเปรียบเทียบสรุปความแตกต่างระหว่างสองชนิดข้อมูลนี้ ซึ่งเป็นหัวใจสำคัญที่สุดของบทนี้:

| ประเด็น | `&[T]` (slice, Part 8) | `Vec<T>` (บทนี้) |
|---|---|---|
| Ownership | **ไม่เป็นเจ้าของ** — ยืมข้อมูลจากที่อื่น (array, `String`/heap ของ `Vec` อื่น) | **เป็นเจ้าของ** — จองและดูแล heap buffer ของตัวเอง |
| โครงสร้างภายใน | `(pointer, length)` — 16 bytes บนเครื่อง 64-bit | `(pointer, length, capacity)` — 24 bytes บนเครื่อง 64-bit |
| ปรับขนาดได้ไหม | **ไม่ได้** — ความยาวถูกกำหนดตายตัวตอนสร้าง slice นั้น | **ได้** — `push`/`pop`/`insert`/`remove` เปลี่ยน length และ (บางครั้ง) capacity ได้ตลอด |
| ต้องมี lifetime ผูกกับข้อมูลต้นทางไหม | **ต้องมี** (ต้องไม่มีชีวิตยาวกว่าข้อมูลที่มันยืม — จะเจาะลึกใน Part 20) | **ไม่ต้อง** — เป็นเจ้าของข้อมูลเอง ไม่ได้ยืมจากใคร |
| การ Drop ตอนหมด scope | ไม่ต้องทำอะไร (ไม่ได้ owns อะไรให้ปล่อย) | **ต้อง** — คืน heap memory อัตโนมัติผ่าน `Drop` (เชื่อม Part 6) |
| สร้างได้จากอะไร | slice จาก array, `String`, หรือ `Vec` อื่นที่มีอยู่แล้ว | สร้างขึ้นใหม่ได้เองด้วย `Vec::new()`/`vec![]`/`with_capacity()` |

#### แผนภาพ memory layout: `Vec<T>` เทียบกับ `&[T]`

ลองจินตนาการภาพหน่วยความจำแบบง่าย ๆ เพื่อให้เห็นความแตกต่างชัดเจนขึ้นไปอีก สมมติเรามี
`let v = vec![10, 20, 30, 40];` แล้วสร้าง `let s = &v[1..3];` (slice ของสมาชิกตำแหน่ง 1-2):

```
ตัวแปรบน stack:                          heap buffer ของ v (capacity = 4):
┌─────────────────────────┐              ┌────┬────┬────┬────┐
│ v: Vec<i32>              │              │ 10 │ 20 │ 30 │ 40 │
│  ptr      ──────────────┼─────────────▶└────┴────┴────┴────┘
│  len  = 4                │                     ▲
│  capacity = 4             │                     │
└─────────────────────────┘                     │
┌─────────────────────────┐                     │
│ s: &[i32]                │                     │
│  ptr      ──────────────┼─────────────────────┘
│  len  = 2                │
└─────────────────────────┘
```

จากภาพจะเห็นชัดว่า: `v` เก็บ 3 ค่า (`ptr`, `len`, `capacity`) และ **เป็นเจ้าของ** heap buffer ทั้งก้อนที่มันชี้ไป
ในขณะที่ `s` เก็บแค่ 2 ค่า (`ptr`, `len`) และ **ชี้เข้าไปกลาง buffer เดียวกันของ `v`** (เริ่มที่ตำแหน่งสมาชิกที่ 1
ความยาว 2) — `s` ไม่มี concept ของ "capacity" เลยเพราะมันไม่มีสิทธิ์ขยายอะไร มันแค่ยืมดูช่วงที่ตายตัวแล้วเท่านั้น
นี่คือเหตุผลเชิงภาพที่อธิบายว่าทำไม `&[T]` จึงมีขนาดเล็กกว่า `Vec<T>` และทำไม "การขยับ/ขยาย buffer ของ `v`"
(เช่นตอน `.push()` ทำให้ reallocate) จึงกระทบ `s` ได้โดยตรง ถ้า borrow checker ไม่ป้องกันไว้ก่อน — ประเด็นนี้จะ
กลับมาเป็นหัวใจสำคัญของหัวข้อ 13.7

ข้อสังเกตที่สำคัญมากคือ **`Vec<T>` ไม่ใช่ชนิดข้อมูลที่แข่งขันกับ `&[T]`** — มันคือ**ฐานที่ผลิต `&[T]` ออกมาได้**
(ผ่าน deref coercion ที่เราเห็นตัวอย่างมาแล้วใน Part 8 ตอนพูดถึง array และจะเห็นอีกครั้งกับ `Vec` ในหัวข้อ 13.10)
พูดง่าย ๆ คือ: **`&[T]` คือ "หน้าต่างมองเข้าไปดูข้อมูล" ส่วน `Vec<T>` คือ "เจ้าของบ้านที่ข้อมูลนั้นอาศัยอยู่จริง"**
ฟังก์ชันที่คุณเขียนรับ `&[T]` (ตามคำแนะนำใน Part 8) จะรับทั้ง array และ `Vec` ได้โดยไม่ต้องแก้โค้ดแม้แต่บรรทัดเดียว

### 13.4 เพิ่ม/ลบสมาชิก: `push`, `pop`, `insert`, `remove`, `extend`, และกลยุทธ์การขยายพื้นที่

#### method พื้นฐานสำหรับเพิ่ม/ลบสมาชิก

```rust
fn main() {
    let mut v = vec![10, 20, 30];
    v.push(40);
    println!("หลัง push(40): {:?}", v);

    let last = v.pop();
    println!("pop() คืนค่า: {:?}, v ตอนนี้: {:?}", last, v);

    v.insert(1, 15);
    println!("หลัง insert(1, 15): {:?}", v);

    let removed = v.remove(0);
    println!("remove(0) คืนค่า: {removed}, v ตอนนี้: {:?}", v);

    v.extend([100, 200, 300]);
    println!("หลัง extend: {:?}", v);

    let mut empty: Vec<i32> = Vec::new();
    let popped_empty = empty.pop();
    println!("pop() จาก vec ว่าง: {:?}", popped_empty);
}
```

ผลลัพธ์:

```
หลัง push(40): [10, 20, 30, 40]
pop() คืนค่า: Some(40), v ตอนนี้: [10, 20, 30]
หลัง insert(1, 15): [10, 15, 20, 30]
remove(0) คืนค่า: 10, v ตอนนี้: [15, 20, 30]
หลัง extend: [15, 20, 30, 100, 200, 300]
pop() จาก vec ว่าง: None
```

**อธิบาย method ทีละตัว:**

- **`.push(value)`** — เพิ่มสมาชิกใหม่ **ต่อท้าย** (ตำแหน่งสุดท้าย) ของ `Vec` เสมอ ไม่คืนค่าอะไร (return type คือ
  `()` — unit type จาก Part 3)
- **`.pop()`** — เอาสมาชิก**ตัวสุดท้าย**ออกและคืนค่านั้นออกมาเป็น **`Option<T>`** — ถ้า `Vec` มีสมาชิกอยู่ คืน
  `Some(value)`, ถ้า `Vec` ว่างเปล่า คืน `None` **นี่คือจุดที่เชื่อมกับ Part 11 โดยตรง**: การลบสมาชิกออกจากท้าย
  `Vec` ที่อาจว่างเปล่าอยู่แล้วเป็นสถานการณ์ที่ "ไม่มีคำตอบที่ถูกต้องเสมอไป" (จะเอาอะไรออกมาจาก `Vec` ที่ไม่มี
  อะไรอยู่เลย?) — Rust เลือกบังคับให้คุณจัดการทั้งสองกรณี (`Some`/`None`) อย่างชัดเจนผ่าน type system แทนการคืน
  ค่า "ปลอม" อย่างเช่น `-1` หรือทำให้โปรแกรม crash โดยไม่มีการเตือนล่วงหน้า
- **`.insert(index, value)`** — แทรกสมาชิกใหม่ **ที่ตำแหน่งที่กำหนด** สมาชิกเดิมตั้งแต่ตำแหน่งนั้นเป็นต้นไปจะถูก
  **เลื่อนไปทางขวาทั้งหมด** (ทำให้ operation นี้มีต้นทุน O(n) ในกรณีแย่ที่สุด ต่างจาก `.push()` ที่ไม่ต้องเลื่อน
  อะไรเลย)
- **`.remove(index)`** — ลบสมาชิกที่ตำแหน่งที่กำหนด **และคืนค่าที่ถูกลบออกมาตรง ๆ** (ไม่ใช่ `Option<T>` เพราะถ้า
  `index` เกินขอบเขต มันจะ **panic ทันที** — เราจะพูดถึงเหตุผลของความไม่สมมาตรนี้ต่อในหัวข้อ 13.5) สมาชิกที่เหลือ
  หลัง `index` จะถูกเลื่อนมาทางซ้ายเติมช่องว่าง (ต้นทุน O(n) เช่นกัน)
- **`.extend(iterable)`** — เพิ่มสมาชิกหลายตัวเข้าไปต่อท้าย `Vec` ทีเดียว โดยรับอะไรก็ได้ที่วนอ่านได้ (iterable —
  ในตัวอย่างนี้คือ array `[100, 200, 300]`) เทียบเท่ากับการเรียก `.push()` ทีละตัวตามลำดับ แต่เขียนสั้นกว่าและ
  มักมีประสิทธิภาพดีกว่าเล็กน้อย (เพราะ `Vec` รู้ล่วงหน้าว่าต้องขยายพื้นที่แค่ครั้งเดียวสำหรับสมาชิกทั้งหมดที่จะ
  เพิ่ม ไม่ต้องเช็ค capacity ทีละตัว)

#### กลยุทธ์การขยายพื้นที่: เพิ่มเป็นสองเท่า (doubling) และ amortized O(1) push

นี่คือคำถามสำคัญที่ควรถามตัวเอง: เมื่อ `Vec` เต็ม capacity แล้วมีการ `.push()` เพิ่มอีก มันขยายพื้นที่**เท่าไหร่**?
มาดูพฤติกรรมจริงกัน:

```rust
fn main() {
    let mut v: Vec<i32> = Vec::new();
    println!("เริ่มต้น: len = {}, capacity = {}", v.len(), v.capacity());

    for i in 1..=10 {
        v.push(i);
        println!("push({i}): len = {}, capacity = {}", v.len(), v.capacity());
    }
}
```

ผลลัพธ์ (บน implementation มาตรฐานปัจจุบันของ `Vec<i32>`):

```
เริ่มต้น: len = 0, capacity = 0
push(1): len = 1, capacity = 4
push(2): len = 2, capacity = 4
push(3): len = 3, capacity = 4
push(4): len = 4, capacity = 4
push(5): len = 5, capacity = 8
push(6): len = 6, capacity = 8
push(7): len = 7, capacity = 8
push(8): len = 8, capacity = 8
push(9): len = 9, capacity = 16
push(10): len = 10, capacity = 16
```

สังเกต pattern ให้ดี: capacity เดินตามลำดับ **0 → 4 → 8 → 16** — **เพิ่มเป็นสองเท่าทุกครั้งที่เต็ม** (ตัวเลขจุด
เริ่มต้นที่แน่นอน เช่น กระโดดจาก 0 ไป 4 ทันทีในการ push ครั้งแรก เป็นรายละเอียดภายในของ standard library ที่อาจ
เปลี่ยนแปลงได้ในเวอร์ชันอนาคต — **สิ่งที่ garantee แน่นอนและไม่เปลี่ยนคือ "เพิ่มเป็นสองเท่า" (doubling) เมื่อ
capacity เดิมไม่พอ** ไม่ใช่ตัวเลขจุดเริ่มต้นที่ตายตัว) ลองดูอีกตัวอย่างที่กำหนด capacity เริ่มต้นเองเพื่อเห็น
pattern การเพิ่มเป็นสองเท่าให้ชัดกว่านี้:

```rust
fn main() {
    let mut v: Vec<i32> = Vec::with_capacity(3);
    println!("เริ่มต้น: len = {}, capacity = {}", v.len(), v.capacity());

    for i in 1..=3 {
        v.push(i);
        println!("push({i}): len = {}, capacity = {}", v.len(), v.capacity());
    }

    // push ตัวที่ 4 เกิน capacity เดิม (3) -> ต้อง reallocate
    v.push(4);
    println!("push(4): len = {}, capacity = {}", v.len(), v.capacity());
}
```

ผลลัพธ์:

```
เริ่มต้น: len = 0, capacity = 3
push(1): len = 1, capacity = 3
push(2): len = 2, capacity = 3
push(3): len = 3, capacity = 3
push(4): len = 4, capacity = 6
```

ครั้งนี้เห็นชัดมาก: capacity เดิมคือ `3`, พอ push ตัวที่ 4 (เกิน capacity) มันขยายเป็น `6` — **เพิ่มเป็นสองเท่าของ
capacity เดิมพอดี** (3 × 2 = 6) นี่คือกลยุทธ์ที่เรียกว่า **doubling growth strategy**

#### ทำไมต้องเพิ่มเป็น "สองเท่า" ไม่ใช่ "เพิ่มทีละ 1" หรือ "เพิ่มทีละค่าคงที่"

ลองจินตนาการกลยุทธ์ทางเลือกที่ดูเผิน ๆ เหมือนจะประหยัดความจำกว่า: **ทุกครั้งที่เต็ม ให้ขยายเพิ่มแค่ทีละ 1**
(หรือทีละค่าคงที่เล็ก ๆ เช่น 10) — วิธีนี้จะประหยัดความจำจริง (ไม่จองเผื่อเกินจำเป็น) แต่ **ต้นทุนด้านเวลารวมจะ
แพงกว่ามากอย่างมีนัยสำคัญ** เมื่อสมาชิกมีจำนวนมาก มาดูเลขคณิตง่าย ๆ ที่อธิบายเหตุผล:

**ถ้าเพิ่มทีละ 1**: การ push สมาชิกตัวที่ `n` (เมื่อ `Vec` มี `n-1` ตัวอยู่แล้วเต็ม capacity พอดี) ต้องคัดลอกสมาชิก
เดิมทั้งหมด `n-1` ตัวไปยัง buffer ใหม่ ถ้า push ไปเรื่อย ๆ จนมี `N` ตัว **ต้นทุนการคัดลอกรวมทั้งหมด**คือ
`1 + 2 + 3 + ... + (N-1)` ซึ่งเท่ากับ `N(N-1)/2` — เติบโตแบบ **O(N²)** เมื่อ `N` มีค่ามาก (เช่น `N = 10,000`
ต้นทุนรวมจะประมาณ 50 ล้าน operation ของการคัดลอก ทั้ง ๆ ที่มีสมาชิกจริงแค่หมื่นตัว)

**ถ้าเพิ่มเป็นสองเท่า**: จำนวนครั้งที่ต้อง reallocate ทั้งหมดสำหรับ `N` สมาชิก มีประมาณ `log₂(N)` ครั้งเท่านั้น
(เพราะ capacity โต 1, 2, 4, 8, 16, 32, ... เพิ่มเป็นสองเท่าไปเรื่อย ๆ จนถึง `N`) และต้นทุนการคัดลอกรวมทั้งหมด
(ผลรวมของอนุกรมเรขาคณิต `1 + 2 + 4 + 8 + ... ` จนถึง `N`) จะไม่เกิน **`2N`** — เติบโตแบบ **O(N)** เท่านั้น ถูกกว่า
กลยุทธ์แรกอย่างมหาศาลเมื่อ `N` ใหญ่ขึ้น

จากตรงนี้เราได้ข้อสรุปสำคัญที่เรียกว่า **amortized O(1) push**: แม้ operation `.push()` แต่ละครั้ง**อาจจะ**มีต้นทุน
O(n) ในบางครั้ง (ตอนที่บังเอิญเต็ม capacity พอดีต้อง reallocate) แต่เมื่อ **เฉลี่ยรวมต้นทุนทั้งหมดของการ push
ทุกครั้งหารด้วยจำนวนครั้งที่ push** (นี่คือความหมายของคำว่า "amortized" — เฉลี่ยตลอดช่วงเวลา ไม่ใช่แค่ครั้งเดียว)
จะได้ค่าเฉลี่ยที่เป็น **O(1)** คือคงที่ไม่ขึ้นกับ `N` — พูดง่าย ๆ คือ **ถึงแม้บางครั้ง push จะช้ากว่าปกติเพราะต้อง
ขยายพื้นที่ แต่โดยเฉลี่ยแล้ว push หนึ่งครั้งเร็วเท่ากันเสมอไม่ว่า `Vec` จะมีสมาชิกอยู่แล้วกี่ตัว** นี่คือเหตุผลที่
`.push()` ถือเป็น operation ที่ "เร็ว" ในทางปฏิบัติ แม้ภายในจะมีความซับซ้อนเรื่องการขยายพื้นที่ซ่อนอยู่

#### เปรียบเทียบกลยุทธ์การขยายพื้นที่กับภาษาอื่นที่คุณอาจรู้จัก

กลยุทธ์ "เพิ่มเป็นสองเท่า" ไม่ใช่สิ่งที่ Rust คิดค้นขึ้นมาใหม่ — มันคือแนวทางมาตรฐานที่ dynamic array/list ของ
ภาษาโปรแกรมมิ่งหลัก ๆ ใช้กันเหมือนกันหมด เพราะเหตุผลเชิงคณิตศาสตร์ (amortized O(1)) เป็นสิ่งที่เป็นจริงในทุกภาษา
ไม่ได้ขึ้นกับ syntax ของภาษานั้น ๆ:

| ภาษา | ชนิดข้อมูล | กลยุทธ์ขยายพื้นที่ | เปิดเผยให้ผู้ใช้เห็น capacity ไหม |
|---|---|---|---|
| **Rust** | `Vec<T>` | เพิ่มเป็นสองเท่า (doubling) | เห็นชัดเจนผ่าน `.capacity()`, ควบคุมได้ผ่าน `with_capacity()` |
| **C++** | `std::vector<T>` | เพิ่มเป็นสองเท่า (ปกติ 1.5x-2x ขึ้นกับ implementation) | เห็นผ่าน `.capacity()`, ควบคุมได้ผ่าน `.reserve()` |
| **Python** | `list` | เพิ่มแบบไม่ใช่สองเท่าเป๊ะ ๆ แต่ยังเป็น geometric growth (over-allocate) | **ไม่เห็นเลย** ไม่มี method ให้เช็ค capacity ปัจจุบัน |
| **JavaScript** | `Array` | ขึ้นกับ engine (V8 ฯลฯ) แต่หลักการ geometric growth เดียวกัน | **ไม่เห็นเลย** เป็นรายละเอียดภายใน engine ทั้งหมด |
| **Java** | `ArrayList<T>` | เพิ่มเป็น 1.5 เท่า (ปกติ) | เห็นผ่าน `.ensureCapacity()`/ไม่มี getter ตรง ๆ แต่ปรับ initial capacity ได้ |

จะเห็นว่า **หลักการพื้นฐาน (geometric/doubling growth เพื่อได้ amortized O(1) push) เหมือนกันในทุกภาษา** — สิ่งที่
Rust ต่างจากภาษาส่วนใหญ่ (ยกเว้น C++) คือ **เปิดเผยรายละเอียดนี้ให้ผู้เขียนโปรแกรมควบคุมได้เต็มที่ผ่าน
`Vec::with_capacity()` และ `.capacity()`** สอดคล้องกับปรัชญาการออกแบบของ Rust ที่เน้นให้ผู้เขียนโปรแกรมมีอำนาจ
ควบคุมประสิทธิภาพระดับต่ำได้เมื่อจำเป็น โดยไม่ต้องแลกกับความปลอดภัยของ memory เลย — ต่างจาก Python/JavaScript ที่
ซ่อนรายละเอียดนี้ไว้ทั้งหมดเพื่อความง่ายในการใช้งาน (แลกกับการควบคุมประสิทธิภาพที่ทำได้น้อยกว่า)

#### `Vec<T>` และ `Drop`: คืนหน่วยความจำอัตโนมัติเมื่อหมด scope

จาก Part 6 เราเรียนว่า `String` คืนพื้นที่ heap อัตโนมัติผ่าน trait `Drop` ทันทีที่ตัวแปรออกจาก scope — `Vec<T>`
implement `Drop` แบบเดียวกันทุกประการ และที่สำคัญกว่านั้นคือ **`Vec<T>` จะเรียก `Drop` ของสมาชิกแต่ละตัวข้างในให้
ด้วย** ก่อนที่จะคืนพื้นที่ buffer ของตัวเอง มาดูให้เห็นภาพจริงด้วย struct ที่ implement `Drop` เอง แล้ว print ข้อความ
ตอนถูกทำลาย:

```rust
struct Ticket {
    id: u32,
}

impl Drop for Ticket {
    fn drop(&mut self) {
        println!("คืนพื้นที่ของ Ticket #{}", self.id);
    }
}

fn main() {
    println!("สร้าง Vec<Ticket>");
    let tickets = vec![
        Ticket { id: 1 },
        Ticket { id: 2 },
        Ticket { id: 3 },
    ];
    println!("มี ticket ทั้งหมด {} ใบ", tickets.len());
    println!("จบ scope ของ main แล้ว...");
}
```

ผลลัพธ์:

```
สร้าง Vec<Ticket>
มี ticket ทั้งหมด 3 ใบ
จบ scope ของ main แล้ว...
คืนพื้นที่ของ Ticket #1
คืนพื้นที่ของ Ticket #2
คืนพื้นที่ของ Ticket #3
```

สังเกตลำดับผลลัพธ์: ข้อความ `"คืนพื้นที่ของ Ticket #..."` ปรากฏขึ้น**หลัง**บรรทัด `"จบ scope ของ main แล้ว..."`
เสมอ นั่นเพราะ `tickets` (ตัวแปร `Vec<Ticket>`) ยังไม่ถูก drop จนกว่าจะถึงจุดสิ้นสุดของ `fn main()` จริง ๆ — และ
เมื่อถึงจุดนั้น **`Vec` จะวนเรียก `drop()` ของสมาชิกทุกตัวตามลำดับที่เก็บอยู่ (index 0, 1, 2, ...)** แล้วจึงคืน
heap buffer ของตัวเองเป็นขั้นตอนสุดท้าย — นี่คือเหตุผลที่ `Vec<T>` "เป็นเจ้าของ" สมาชิกทุกตัวข้างในอย่างแท้จริง
ไม่ใช่แค่เก็บ pointer ไปยังสมาชิกที่คนอื่นดูแลอยู่ (ถ้าเป็นแบบนั้น `Vec` จะไม่มีสิทธิ์ไปเรียก `drop()` ของสมาชิก
เองได้เลย เพราะนั่นจะเป็นการทำลายข้อมูลที่คนอื่นเป็นเจ้าของอยู่ — ละเมิดกฎ ownership จาก Part 6 โดยตรง)

### 13.5 เข้าถึงสมาชิก: indexing (`v[i]`) เทียบกับ `.get(i)`

`Vec<T>` ให้เข้าถึงสมาชิกด้วย index ได้ 2 วิธี ซึ่งมีพฤติกรรมต่างกันอย่างมากเมื่อ index เกินขอบเขต

#### วิธีที่ 1: indexing ด้วย `[]` — panic เมื่อ index เกินขอบเขต

```rust
fn main() {
    let products = vec!["ปากกา", "ยางลบ", "สมุด"];
    println!("สินค้าตัวแรก: {}", products[0]);
    println!("สินค้าตัวที่ 10: {}", products[10]);
}
```

บรรทัดแรกทำงานปกติ แต่บรรทัดที่สอง **panic ทันทีตอนรันจริง**:

```
สินค้าตัวแรก: ปากกา

thread 'main' panicked at src/main.rs:4:40:
index out of bounds: the len is 3 but the index is 10
note: run with `RUST_BACKTRACE=1` environment variable to display a backtrace
```

Error message บอกข้อมูลที่จำเป็นครบถ้วน: **"the len is 3 but the index is 10"** — ความยาวจริงของ `Vec` คือ 3
(index ที่ใช้ได้คือ 0, 1, 2 เท่านั้น) แต่พยายามเข้าถึง index 10 ซึ่งไม่มีอยู่จริง โปรแกรม**หยุดทำงานทันที**
(ไม่ใช่แค่คืนค่าขยะหรือ `undefined behavior` แบบภาษา C/C++ — จะเปรียบเทียบเรื่องนี้ให้ชัดในหัวข้อถัดไป)

#### วิธีที่ 2: `.get(i)` — คืน `Option<&T>` ไม่ panic เด็ดขาด

```rust
fn main() {
    let v = vec![10, 20, 30];

    match v.get(1) {
        Some(value) => println!("พบค่าที่ index 1: {value}"),
        None => println!("ไม่มีสมาชิกที่ index นี้"),
    }

    match v.get(10) {
        Some(value) => println!("พบค่าที่ index 10: {value}"),
        None => println!("ไม่มีสมาชิกที่ index 10"),
    }

    let safe = v.get(10).copied().unwrap_or(0);
    println!("ใช้ unwrap_or แทนค่า default: {safe}");
}
```

ผลลัพธ์:

```
พบค่าที่ index 1: 20
ไม่มีสมาชิกที่ index 10
ใช้ unwrap_or แทนค่า default: 0
```

`.get(i)` คืนค่าเป็น **`Option<&T>`** เสมอ — `Some(&value)` ถ้า index มีอยู่จริง, `None` ถ้า index เกินขอบเขต
**ไม่มีทาง panic ได้เลยไม่ว่า index จะเป็นค่าอะไรก็ตาม** เพราะมันเปลี่ยน "ความล้มเหลว" ให้กลายเป็นค่าที่ต้อง
จัดการอย่างชัดเจนผ่าน type system (เหมือนหลักการทั้งหมดของ Part 11) `.copied()` ในตัวอย่างสุดท้ายแปลง
`Option<&i32>` เป็น `Option<i32>` (คัดลอกค่าออกมา เพราะ `i32` เป็น `Copy` — เชื่อม Part 6) แล้ว `.unwrap_or(0)`
ให้ค่า default ถ้าเป็น `None`

#### คำถามสำคัญ: ทำไม Rust ถึงให้ทั้งสองวิธีไว้คู่กัน ไม่เลือกแบบเดียว?

นี่คือคำถามเดียวกันกับที่เราเจอตลอด Part 11: **ทำไม Rust ไม่บังคับให้ใช้ `Option` ทุกที่ไปเลย ในเมื่อมันปลอดภัย
กว่า?** คำตอบคือ **ความปลอดภัยมี "ต้นทุนทางไวยากรณ์" เสมอ** — การ `match` หรือ `unwrap_or` ทุกครั้งที่เข้าถึง
สมาชิกทำให้โค้ดยาวและอ่านยากขึ้นในสถานการณ์ที่ **คุณมั่นใจอยู่แล้วจริง ๆ** ว่า index ถูกต้องแน่นอน (เช่น กำลังวน
`for i in 0..v.len()` แล้วเข้าถึง `v[i]` — index ไม่มีทางเกินขอบเขตได้เลยในบริบทนี้) การบังคับ `Option` ในทุกกรณี
จะเป็นการเพิ่มความรกโดยไม่ได้ประโยชน์อะไรเพิ่ม

Rust จึงเลือกให้**ทั้งสองทาง**พร้อมกัน โดยมี**สัญญาณที่ต่างกันอย่างจงใจ**:

- **`v[i]`** — สื่อความหมายว่า **"ผมมั่นใจว่า index นี้ถูกต้องแน่นอน ถ้าผมคิดผิด ให้โปรแกรม panic ทันทีเพื่อบอกผม
  อย่างชัดเจนที่สุด"** เหมาะกับ index ที่คำนวณมาอย่างมีเหตุผลรองรับ (เช่น มาจาก `.enumerate()`, มาจาก
  `0..v.len()`)
- **`.get(i)`** — สื่อความหมายว่า **"index นี้อาจจะถูกหรือผิดก็ได้ ผมยังไม่รู้ ให้บอกผมด้วย `Option` แล้วผมจะ
  ตัดสินใจว่าจะทำอะไรต่อในแต่ละกรณี"** เหมาะกับ index ที่มาจากแหล่งที่ไม่น่าเชื่อถือ (เช่น input จากผู้ใช้,
  ผลลัพธ์จากการค้นหาที่อาจไม่พบ)

นี่คือปรัชญาเดียวกันที่เราเห็นซ้ำแล้วซ้ำอีกในหลักสูตรนี้ตั้งแต่ Part 3 (`unwrap()` vs การเช็คก่อน), Part 11
(`unwrap()` vs `match`/`unwrap_or()`), และตอนนี้กับ `Vec` — **Rust ไม่ได้บังคับให้คุณเลือกความปลอดภัยเสมอ แต่บังคับ
ให้คุณ "เลือกอย่างตั้งใจ" และเห็นความแตกต่างชัดเจนในโค้ดว่าคุณเลือกทางไหน** ไม่มีทางเผลอเข้าถึง index ที่ผิดโดย
ไม่รู้ตัวแบบเงียบ ๆ เหมือนภาษา C ที่ `array[10]` ที่ไม่มีอยู่จริงอาจอ่านค่าขยะจาก memory ตำแหน่งอื่นออกมาได้โดยไม่
เตือนอะไรเลย (undefined behavior) — พฤติกรรมของ Rust ทั้ง `v[i]` (panic ทันที ป้องกันไม่ให้อ่านขยะออกมา) และ
`.get(i)` (คืน `None` อย่างปลอดภัย) **ทั้งคู่ปลอดภัยกว่า C เสมอ** ต่างกันแค่ "ปลอดภัยแบบหยุดทำงานทันที" กับ
"ปลอดภัยแบบให้ตัดสินใจต่อเอง" เท่านั้น

### 13.6 การวนลูปบน `Vec<T>`: by reference, by value, และ by mutable reference

Rust มี 3 รูปแบบหลักในการวน `for` loop บน `Vec<T>` (และจริง ๆ ก็ใช้กับ collection อื่นแบบเดียวกันด้วย) ซึ่งแต่ละ
แบบมีความหมายด้าน ownership ต่างกันอย่างสิ้นเชิง — เนื้อหานี้เป็นแค่ teaser เบื้องต้น เพราะกลไกเบื้องหลังจริง ๆ
(trait `Iterator`, `IntoIterator`) จะเจาะลึกเต็มรูปแบบใน **Part 25-26**

```rust
fn main() {
    let numbers = vec![1, 2, 3];

    // 1) วนแบบ by reference — ไม่ consume vec, ใช้ vec ต่อได้หลัง loop
    for n in &numbers {
        print!("{n} ");
    }
    println!();
    println!("numbers ยังใช้ได้ต่อ: {:?}", numbers);

    // 2) วนแบบ mutable reference — แก้ไขสมาชิกได้ระหว่างวน
    let mut mutable_numbers = vec![1, 2, 3];
    for n in &mut mutable_numbers {
        *n *= 10;
    }
    println!("หลังคูณ 10 ทุกตัว: {:?}", mutable_numbers);

    // 3) วนแบบ by value — consume vec ไปเลย (ใช้ vec ต่อไม่ได้อีกหลัง loop)
    let owned_numbers = vec![String::from("a"), String::from("b")];
    for s in owned_numbers {
        println!("เป็นเจ้าของ: {s}");
    }
}
```

ผลลัพธ์:

```
1 2 3 
numbers ยังใช้ได้ต่อ: [1, 2, 3]
หลังคูณ 10 ทุกตัว: [10, 20, 30]
เป็นเจ้าของ: a
เป็นเจ้าของ: b
```

**อธิบายทั้ง 3 รูปแบบทีละแบบ:**

- **`for n in &numbers`** — วนแบบ **immutable borrow** ตัวแปร `n` ในแต่ละรอบมี type เป็น `&i32` (reference ไปยัง
  สมาชิกแต่ละตัว ไม่ใช่ค่าตรง ๆ) เพราะเราแค่ "ยืมดู" ทีละตัว **`numbers` ไม่ถูก consume** ยังใช้งานต่อได้ตามปกติ
  หลัง loop จบ — นี่คือรูปแบบที่**ใช้บ่อยที่สุด**ในโค้ด Rust จริง เพราะส่วนใหญ่เราต้องการแค่ "อ่าน" สมาชิกไปทำ
  อะไรสักอย่าง ไม่ได้ต้องการเป็นเจ้าของมันจริง ๆ
- **`for n in &mut mutable_numbers`** — วนแบบ **mutable borrow** ตัวแปร `n` มี type เป็น `&mut i32` ต้องใช้
  `*n` (dereference — เรียนจาก Part 7) เพื่อเข้าถึง**ค่าจริง**ที่ `n` ชี้ไป แล้วแก้ไขมันได้ตรง ๆ เหมาะกับ
  สถานการณ์ที่ต้องการแก้ไขสมาชิกทุกตัว (หรือบางตัว) "ในที่เดิม" โดยไม่ต้องสร้าง `Vec` ใหม่
- **`for s in owned_numbers`** — วนแบบ **by value** — **`owned_numbers` ถูก consume (move) เข้าไปใน loop
  ทั้งก้อน** ตัวแปร `s` ในแต่ละรอบเป็นเจ้าของค่านั้นจริง ๆ (type `String` ตรง ๆ ไม่ใช่ reference) เมื่อ loop จบ
  `owned_numbers` **ใช้งานต่อไม่ได้อีกแล้ว** เพราะมันถูก move ไปหมดแล้ว (กฎ ownership เดียวกับ Part 6 ทุกประการ)
  เหมาะกับสถานการณ์ที่ต้องการ "โยนความเป็นเจ้าของ" ของสมาชิกแต่ละตัวออกไปให้ที่อื่น (เช่น ส่งเข้าฟังก์ชันที่รับ
  ownership, เก็บเข้า collection ใหม่)

#### กับดักที่พบบ่อย: ใช้ `Vec` ต่อหลังวนแบบ by value

ลองดูว่าเกิดอะไรขึ้นถ้าพยายามใช้ `Vec` ต่อหลังวนแบบที่ 3 (by value):

```rust
fn main() {
    let names = vec![String::from("สมชาย"), String::from("สมหญิง")];

    for name in names {
        println!("สวัสดี {name}");
    }

    println!("จำนวนสมาชิกทั้งหมด: {}", names.len());
}
```

Error นี้อธิบายตัวเองได้ดีมาก: **"`names` moved due to this implicit call to `.into_iter()`"** — `for name in
names` ที่ดูเหมือน syntax เปล่า ๆ จริง ๆ แล้วมีการเรียก `.into_iter()` ซ่อนอยู่เบื้องหลัง (จะเห็นกลไกที่แท้จริง
ใน Part 25) ซึ่ง method นี้ **รับ ownership ของ `self` ไปเต็ม ๆ** — เท่ากับว่า `names` ถูก move เข้า loop ไปแล้ว
ตั้งแต่บรรทัดที่เริ่ม loop วิธีแก้ตามที่ compiler แนะนำตรง ๆ (`help:`) คือเปลี่ยนเป็น `for name in &names`
(วนแบบ by reference แทน) ถ้าแค่ต้องการอ่านค่าโดยไม่จำเป็นต้องเป็นเจ้าของมันจริง ๆ

**หลักการเลือก**: ใช้ `for x in &v` เป็นค่าเริ่มต้นเสมอถ้าไม่แน่ใจ — เปลี่ยนไปใช้ `for x in v` (by value) เฉพาะ
เมื่อคุณตั้งใจจริง ๆ ที่จะ "จบชีวิตของ `Vec` ตัวนั้น" หลัง loop (เช่น กำลังแปลง `Vec` หนึ่งไปเป็นอีกรูปแบบหนึ่ง
โดยไม่ต้องใช้ตัวเดิมอีกแล้ว)

### 13.7 Ownership และ Borrowing กับ `Vec<T>`: กฎเดิมจาก Part 7 ยังใช้ได้เสมอ ไม่มีข้อยกเว้น

นี่คือหัวข้อที่สำคัญที่สุดของบทนี้ และเป็นบั๊กที่มือใหม่ Rust เกือบทุกคนเจอมาแล้วอย่างน้อยหนึ่งครั้งจริง ๆ ใน
โลกการทำงาน ลองดูโค้ดต่อไปนี้ ซึ่งดูเผิน ๆ เหมือนไม่มีอะไรผิด:

```rust
fn main() {
    let mut scores = vec![10, 20, 30];

    let first = &scores[0];

    scores.push(40);

    println!("สมาชิกตัวแรก: {first}");
}
```

โค้ดนี้ **compile ไม่ผ่านเลย**:

```
error[E0502]: cannot borrow `scores` as mutable because it is also borrowed as immutable
 --> src/main.rs:6:5
  |
4 |     let first = &scores[0];
  |                  ------ immutable borrow occurs here
5 |
6 |     scores.push(40);
  |     ^^^^^^^^^^^^^^^ mutable borrow occurs here
7 |
8 |     println!("สมาชิกตัวแรก: {first}");
  |                            ----- immutable borrow later used here
```

#### วิเคราะห์ว่าเกิดอะไรขึ้น ทีละขั้นตอน ด้วยกฎจาก Part 7

1. `let first = &scores[0];` — สร้าง **immutable borrow** ของ `scores` (ยืมเพื่ออ่าน element ตัวแรก)
2. `scores.push(40);` — `.push()` ต้องการ **mutable borrow** ของ `scores` เพราะมันแก้ไข `Vec`
3. `println!("... {first}");` — **ใช้งาน `first` ต่อ** ซึ่งหมายความว่า immutable borrow จากขั้นตอนที่ 1
   **ยังมีชีวิตอยู่จนถึงจุดนี้** (ตาม NLL — borrow จะ "อยู่" ตราบใดที่ยังมีการใช้งานค่านั้นต่อในอนาคต เหมือนที่
   เรียนใน Part 7 และเห็นอีกครั้งกับ `&str` ใน Part 8)

เมื่อรวม 3 ข้อนี้: มี immutable borrow ที่ยังไม่หมดอายุ (เพราะ `first` ถูกใช้ต่อ) แต่ตรงกลางพยายามสร้าง mutable
borrow (`.push()`) ซ้อนทับ — **ละเมิดกฎยืมข้อสำคัญที่สุดจาก Part 7**: ห้ามมี mutable borrow พร้อมกับ immutable
borrow ที่ยังมีชีวิตอยู่เด็ดขาด

#### ทำไมกฎนี้ต้องเข้มงวดกับ `Vec` ขนาดนี้ — เหตุผลเชิงลึกเรื่อง memory safety

คำถามที่ควรถามคือ: `scores.push(40)` แก้ไข "ท้าย" ของ `Vec` ส่วน `first` ชี้ไปที่ "ตัวแรก" (`index 0`) — ทำไม
compiler ถึงไม่ยอมให้ทำสองอย่างนี้พร้อมกัน ในเมื่อดูเหมือนไม่เกี่ยวกันเลย? คำตอบอยู่ที่**สิ่งที่เรียนมาในหัวข้อ 13.4
เรื่องการขยายพื้นที่**: **`.push()` อาจทำให้ `Vec` ต้อง reallocate** (ถ้า capacity เดิมไม่พอ) และเมื่อ
reallocate เกิดขึ้น **สมาชิกทั้งหมดถูกคัดลอกไปยัง heap buffer ใหม่ทั้งหมด แล้ว buffer เก่าถูกคืนกลับให้ระบบ
ปฏิบัติการ (free)**

ถ้า compiler ยอมให้โค้ดข้างบน compile ผ่าน สถานการณ์ที่อาจเกิดขึ้นจริงคือ: `first` ถือ pointer ที่ชี้ไปยังตำแหน่ง
เดิมใน buffer เก่า พอ `.push(40)` ทำให้เกิด reallocate จริง buffer เก่าถูก free ไปแล้ว — `first` จะกลายเป็น
**dangling pointer** (pointer ที่ชี้ไปยังหน่วยความจำที่ไม่ได้เป็นของโปรแกรมแล้ว) ทันที การใช้งาน `first` ต่อใน
`println!` จะเป็นการอ่านหน่วยความจำที่**ไม่ปลอดภัยเลย** — อาจจะได้ค่าขยะ, อาจจะไปชนกับข้อมูลของโปรแกรมอื่น, หรือ
ทำให้โปรแกรม crash แบบที่ทำนายไม่ได้ นี่คือ **use-after-free bug** ระดับ memory safety ที่ร้ายแรงที่สุดประเภท
หนึ่งในภาษาอย่าง C++ (ที่ `std::vector::push_back` มีพฤติกรรม invalidate iterator/pointer เดิมแบบเดียวกัน แต่
compiler ของ C++ **ไม่มีทางตรวจจับได้เลย** ปล่อยให้เป็นความรับผิดชอบของโปรแกรมเมอร์ทั้งหมด ซึ่งเป็นสาเหตุของบั๊ก
security-critical จำนวนมากในซอฟต์แวร์จริงตลอดหลายสิบปีที่ผ่านมา)

**Rust ป้องกันบั๊กนี้ได้ 100% ตั้งแต่ compile time** โดยไม่ต้องมี runtime check เพิ่มเติมแม้แต่นิดเดียว — borrow
checker มองว่า `first` คือ borrow ของ "`scores` ทั้งตัว" (ไม่ได้วิเคราะห์ลึกว่า `.push()` อาจจะไม่กระทบตำแหน่งที่
`first` ชี้ไปจริง ๆ ถ้าบังเอิญไม่ reallocate รอบนี้ — เหมือนกับที่เรียนใน Part 8 เรื่องการยืม mutable slice สอง
ช่วงที่ไม่ทับกัน compiler ก็ conservative แบบเดียวกัน) เพราะ**ไม่มีทางรู้ล่วงหน้าตอน compile time ว่า `.push()`
ครั้งนี้จะ reallocate จริงหรือไม่** (ขึ้นกับ capacity ตอนรันจริง ซึ่งเป็นข้อมูล runtime) — วิธีที่ปลอดภัยที่สุด
คือ**ปฏิเสธไปเลยทุกกรณีที่มี mutable borrow ซ้อนกับ immutable borrow ที่ยังมีชีวิตอยู่** ไม่ว่าจริง ๆ แล้วรอบนี้
จะ reallocate หรือไม่ก็ตาม — **นี่คือ trade-off ที่ตั้งใจ**: ยอมปฏิเสธโค้ดบางส่วนที่ในทางปฏิบัติอาจจะปลอดภัยจริง
(ถ้าบังเอิญไม่ reallocate) เพื่อแลกกับการันตี **100% ว่าไม่มีทาง compile โค้ดที่มี use-after-free ได้เลย**

#### วิธีแก้ไข: 2 แนวทางหลัก

**แนวทางที่ 1 — ใช้ `first` ให้จบก่อนที่จะ `.push()`** (อาศัย NLL — ทันทีที่ `first` ไม่ถูกใช้งานต่อ borrow จะ
หมดอายุ ไม่ต้องรอปิด scope):

```rust
fn main() {
    let mut scores = vec![10, 20, 30];

    let first = &scores[0];
    println!("สมาชิกตัวแรก: {first}"); // ใช้ first จบตรงนี้ borrow หมดอายุ

    scores.push(40); // ตอนนี้ push ได้แล้ว ไม่มี borrow ค้าง
    println!("{:?}", scores);
}
```

**แนวทางที่ 2 — คัดลอกค่าออกมาก่อน แทนการถือ reference** (ถ้า `T` เป็น `Copy` เช่น `i32` — เชื่อม Part 6 เรื่อง
`Copy` trait):

```rust
fn main() {
    let mut scores = vec![10, 20, 30];

    let first_value = scores[0]; // copy ค่าออกมา ไม่ใช่ reference แล้ว
    scores.push(40); // push ได้เลย เพราะไม่มีใครยืม scores อยู่

    println!("สมาชิกตัวแรก: {first_value}, v = {:?}", scores);
}
```

แนวทางที่ 2 ทำงานได้เพราะ **`scores[0]` (ไม่มี `&`) คัดลอกค่าออกมาเป็น `i32` ใหม่ ตัดขาดความสัมพันธ์กับ `scores`
โดยสิ้นเชิง** — `first_value` ไม่ได้เป็น borrow ของ `scores` อีกต่อไป มันเป็นค่า `i32` อิสระที่มีชีวิตเป็นของตัวเอง
(เหมือนหลักการ `Copy` ที่เรียนใน Part 6) การเลือกระหว่างสองแนวทางนี้ขึ้นกับสถานการณ์จริง: ถ้า `T` ไม่ใช่ `Copy`
(เช่น `String`) แนวทางที่ 2 จะต้องใช้ `.clone()` แทน ซึ่งมีต้นทุนการจอง heap เพิ่ม (เชื่อม Part 6) — ต้องชั่งน้ำหนัก
กับความสะดวกที่ได้

### 13.8 `Vec<String>` เทียบกับ `Vec<&str>`: เลือกใช้แบบไหน

เมื่อเก็บข้อความหลายรายการใน `Vec` เรามีตัวเลือก 2 แบบหลัก คือ `Vec<String>` (แต่ละสมาชิกเป็นเจ้าของข้อมูลตัวเอง)
กับ `Vec<&str>` (แต่ละสมาชิกยืมข้อมูลมาจากที่อื่น)

```rust
fn greet_all(names: &[String]) {
    for name in names {
        println!("สวัสดี {name}");
    }
}

fn main() {
    // Vec<String>: แต่ละสมาชิกเป็นเจ้าของข้อมูลตัวเอง (heap ของตัวเอง)
    let owned_names: Vec<String> = vec![
        String::from("สมชาย"),
        String::from("สมหญิง"),
    ];
    greet_all(&owned_names);

    // Vec<&str>: แต่ละสมาชิกยืมข้อมูลมาจากที่อื่น (string literal หรือ String ตัวอื่น)
    let borrowed_names: Vec<&str> = vec!["สมชาย", "สมหญิง"];
    for name in &borrowed_names {
        println!("ยืมมา: {name}");
    }

    println!(
        "owned_names ใช้ heap {} ก้อนแยกกัน (ไม่รวม buffer ของ Vec เอง)",
        owned_names.len()
    );
}
```

ผลลัพธ์:

```
สวัสดี สมชาย
สวัสดี สมหญิง
ยืมมา: สมชาย
ยืมมา: สมหญิง
owned_names ใช้ heap 2 ก้อนแยกกัน (ไม่รวม buffer ของ Vec เอง)
```

#### หลักการเลือก

| สถานการณ์ | ควรใช้ |
|---|---|
| `Vec` ต้องมีชีวิตอยู่ยาวนาน เป็นอิสระจากข้อมูลต้นทาง (เช่น เก็บใน struct, ส่งกลับจากฟังก์ชัน, เก็บใน field ของ object ที่จะอยู่ไปอีกนาน) | **`Vec<String>`** — แต่ละสมาชิกเป็นเจ้าของตัวเอง ไม่ต้องกังวลเรื่อง lifetime เลย |
| `Vec` ใช้งานแค่ชั่วคราวในฟังก์ชันเดียว โดยข้อมูลต้นทาง (เช่น `String` ใหญ่ตัวหนึ่ง หรือ string literal) ยังมีชีวิตอยู่ตลอดช่วงที่ใช้ | **`Vec<&str>`** — ประหยัดกว่า ไม่ต้องจอง heap ซ้ำสำหรับแต่ละสมาชิก (เช่นผลลัพธ์จาก `.split(' ')` ที่เรียนใน Part 8) |
| ไม่แน่ใจ หรือกำลังออกแบบ API สาธารณะที่คนอื่นจะเรียกใช้ | มักเริ่มจาก `Vec<String>` ก่อน (ปลอดภัยกว่า ไม่มีปัญหาเรื่อง lifetime annotation ที่ซับซ้อนขึ้นเมื่อ struct มี `&str` เป็น field — ประเด็นนี้ Part 9 ได้ทีเซอร์ไว้แล้วว่าซับซ้อนกว่า `String` เห็นได้ชัด) |

**ข้อควรระวังเรื่อง lifetime ของ `Vec<&str>`**: เพราะสมาชิกแต่ละตัวใน `Vec<&str>` เป็น **borrow** (ไม่ใช่
ownership) ทำให้ **`Vec<&str>` เองก็ต้องมี lifetime ผูกติดกับข้อมูลต้นทางไปด้วย** เหมือนที่ `&str` เดี่ยว ๆ ต้อง
ผูกกับต้นทางในหัวข้อ 8.6 — ถ้าข้อมูลต้นทางถูกทำลายไปก่อน (เช่น `String` ที่สมาชิกยืมมาถูก drop ไปแล้ว) borrow
checker จะปฏิเสธไม่ให้ `Vec<&str>` นั้นมีชีวิตยาวเกินข้อมูลต้นทางไปได้เลย รายละเอียดเชิงลึกเรื่องการเขียน
lifetime annotation ให้กับ struct/collection ที่เก็บ reference จะเรียนอย่างเป็นทางการใน **Part 20** — ตอนนี้
จำหลักปฏิบัติง่าย ๆ ไว้ก่อน: **ถ้าไม่แน่ใจเรื่อง lifetime ให้เลือก `Vec<String>` ไปก่อน แล้วค่อย optimize เป็น
`Vec<&str>` ทีหลังเมื่อเห็นความจำเป็นจริง ๆ ด้าน performance**

### 13.9 เรียงลำดับและค้นหา: `sort`, `sort_by`, `sort_by_key`, `binary_search`, `contains`

```rust
fn main() {
    let mut numbers = vec![5, 3, 8, 1, 9, 2];
    numbers.sort();
    println!("sort แล้ว: {:?}", numbers);

    let found = numbers.binary_search(&8);
    println!("binary_search(&8): {:?}", found);

    let not_found = numbers.binary_search(&100);
    println!("binary_search(&100): {:?}", not_found);

    println!("contains(&9): {}", numbers.contains(&9));
    println!("contains(&42): {}", numbers.contains(&42));

    let mut words = vec!["banana", "apple", "cherry"];
    words.sort_by(|a, b| b.cmp(a)); // เรียงจาก z -> a (กลับด้าน)
    println!("sort_by (กลับด้าน): {:?}", words);

    #[derive(Debug)]
    struct Person {
        name: String,
        age: u32,
    }

    let mut people = vec![
        Person { name: String::from("สมชาย"), age: 35 },
        Person { name: String::from("สมหญิง"), age: 22 },
        Person { name: String::from("มานะ"), age: 40 },
    ];

    people.sort_by_key(|p| p.age);
    for p in &people {
        println!("{} อายุ {}", p.name, p.age);
    }
}
```

ผลลัพธ์:

```
sort แล้ว: [1, 2, 3, 5, 8, 9]
binary_search(&8): Ok(4)
binary_search(&100): Err(6)
contains(&9): true
contains(&42): false
sort_by (กลับด้าน): ["cherry", "banana", "apple"]
สมหญิง อายุ 22
สมชาย อายุ 35
มานะ อายุ 40
```

**อธิบาย method ทีละตัว:**

- **`.sort()`** — เรียงสมาชิกจากน้อยไปมาก **แก้ไข `Vec` ตรง ๆ ในที่เดิม** (in-place — ไม่คืนค่าอะไร ต้องมี `mut`)
  ใช้ได้กับชนิดข้อมูลที่ implement trait `Ord` เท่านั้น (ตัวเลข, `String`, `&str` implement ให้อยู่แล้ว)
- **`.binary_search(&value)`** — ค้นหาค่าด้วยวิธี **binary search** (ต้องเรียงลำดับก่อนเสมอ ไม่งั้นผลลัพธ์ไม่มี
  ความหมาย) เร็วกว่าการวนหาทีละตัวมาก (**O(log n)** เทียบกับ **O(n)** ของการวนหาตรง ๆ) คืนค่าเป็น **`Result`**
  (เชื่อม Part 12): `Ok(index)` ถ้าเจอ (บอกตำแหน่งที่เจอ), `Err(index)` ถ้าไม่เจอ — แต่ `index` ใน `Err` ก็ยัง
  มีประโยชน์ มันคือ **ตำแหน่งที่ควรแทรกค่านี้เข้าไปเพื่อให้ยัง sort อยู่** (จากผลลัพธ์ `Err(6)` ของการหา `100` ใน
  `[1, 2, 3, 5, 8, 9]` — บอกว่าถ้าจะแทรก 100 เข้าไปโดยให้ยัง sort อยู่ ต้องแทรกที่ index 6 คือต่อท้ายสุด)
- **`.contains(&value)`** — เช็คง่าย ๆ ว่ามีค่านี้อยู่ใน `Vec` หรือไม่ คืน `bool` ตรง ๆ (ใช้การวนหาทีละตัว O(n)
  ภายใน ไม่ได้ใช้ binary search แม้ `Vec` จะ sort อยู่แล้วก็ตาม — ถ้ารู้ว่า sort อยู่แล้วและ `Vec` มีขนาดใหญ่
  `.binary_search()` จะเร็วกว่า `.contains()` มาก)
- **`.sort_by(|a, b| ...)`** — เรียงลำดับแบบกำหนด**ฟังก์ชันเปรียบเทียบเอง** (closure ที่รับสองค่ามาเทียบกัน คืน
  `Ordering` — เราจะเจาะลึก closure อย่างเป็นทางการใน Part 24 ตอนนี้มองว่ามันคือ "ฟังก์ชันไม่มีชื่อที่เขียนสั้น ๆ
  ตรงจุดที่ใช้" ก็พอ) `b.cmp(a)` (สลับด้าน a กับ b) ทำให้ผลลัพธ์เรียงจากมากไปน้อยแทนน้อยไปมาก
- **`.sort_by_key(|p| ...)`** — เรียงลำดับตาม "key" ที่ดึงออกมาจากแต่ละสมาชิก สะดวกกว่า `.sort_by()` มากเมื่อ
  ต้องการเรียงตาม field เดียวของ struct (ในตัวอย่างนี้คือ `.age`) — Rust จะเรียก closure นี้เพื่อดึง key ออกมา
  แล้วเทียบ key นั้นให้เราโดยอัตโนมัติ ไม่ต้องเขียนฟังก์ชันเปรียบเทียบเต็มรูปแบบเอง

### 13.10 `Vec<T>` กับ Slice: Deref Coercion สู่ `&[T]`

จาก Part 8 เราเรียนว่า array แบบตายตัว (`[T; N]`) แปลงเป็น `&[T]` ได้อัตโนมัติผ่าน deref coercion — `Vec<T>` ก็
ทำงานบนหลักการเดียวกันทุกประการ เพราะ `Vec<T>` implement `Deref<Target = [T]>` (แบบเดียวกับที่ `String`
implement `Deref<Target = str>` ที่เรียนใน Part 8):

```rust
fn max_in_slice(data: &[i32]) -> i32 {
    let mut max = data[0];
    for &x in data.iter() {
        if x > max {
            max = x;
        }
    }
    max
}

fn main() {
    let v = vec![10, 50, 20, 80, 30];

    // เรียกฟังก์ชันที่รับ &[i32] ด้วย &v ตรง ๆ ผ่าน deref coercion (Vec<T> -> &[T])
    println!("max ทั้งหมด: {}", max_in_slice(&v));

    // slice ช่วงย่อยของ Vec ก็ได้ &[T] เหมือนกัน
    let middle: &[i32] = &v[1..3];
    println!("middle: {:?}", middle);
    println!("max ของ middle: {}", max_in_slice(middle));

    // สามารถเรียก method ของ slice ได้ตรง ๆ บน Vec เลย (เพราะ deref coercion)
    println!("v.len() = {}, v.first() = {:?}, v.last() = {:?}", v.len(), v.first(), v.last());
}
```

ผลลัพธ์:

```
max ทั้งหมด: 80
middle: [50, 20]
max ของ middle: 50
v.len() = 5, v.first() = Some(10), v.last() = Some(30)
```

**ประเด็นสำคัญที่สุดของหัวข้อนี้**: ฟังก์ชัน `max_in_slice` **ไม่รู้เลยและไม่จำเป็นต้องรู้** ว่าข้อมูลที่ส่งเข้ามา
มาจาก array, `Vec`, หรือ slice ช่วงย่อยของอะไรก็ได้ — มันรับแค่ `&[i32]` และทำงานได้เหมือนกันหมด **นี่คือคุณค่าที่
แท้จริงของคำแนะนำใน Part 8** ("รับ `&[T]` เป็น parameter เสมอ ไม่ใช่ `&Vec<T>` หรือ `&[T; N]`") ฟังก์ชันที่คุณ
เขียนตอนเรียน Part 8 (ตอนที่ยังไม่รู้จัก `Vec` ด้วยซ้ำ) ใช้งานกับ `Vec` ได้ทันทีโดยไม่ต้องแก้โค้ดแม้แต่บรรทัดเดียว
— และ `&v[1..3]` (slice ช่วงย่อยของ `Vec`) ก็ใช้ range syntax เดียวกันกับที่เรียนใน Part 8 เป๊ะ ๆ อีกด้วย

`.first()` และ `.last()` ในตัวอย่างสุดท้ายเป็น method ของ **slice** (ไม่ใช่ของ `Vec` โดยตรง) แต่เรียกผ่าน `v`
(ซึ่งเป็น `Vec`) ได้ตรง ๆ เพราะ deref coercion — ทั้งสอง method คืนค่าเป็น `Option<&T>` (เชื่อม Part 11 อีกครั้ง:
`Vec`/slice ที่ว่างเปล่าจะไม่มี "ตัวแรก" หรือ "ตัวสุดท้าย" ให้คืน จึงต้องเป็น `Option` เสมอ)

#### สรุปสายสัมพันธ์ Array → Vec → Slice

ตอนนี้เราเห็นภาพครบวงจรแล้วว่าชนิดข้อมูล collection พื้นฐาน 3 ตัวที่เรียนมาสัมพันธ์กันอย่างไร:

```
[T; N]  (array, Part 3)  ─┐
                          ├─→  Deref coercion  →  &[T]  (slice, Part 8)
Vec<T>  (บทนี้)         ─┘
```

array และ `Vec` คือ**ผู้ผลิตข้อมูล** (แหล่งที่แท้จริงที่ข้อมูลอาศัยอยู่) — ต่างกันแค่ array ขนาดตายตัว ส่วน `Vec`
ขนาดปรับได้ ในขณะที่ `&[T]` คือ**หน้าต่างสำหรับมองเข้าไปดูข้อมูล** ที่ใช้ได้กับทั้งสองแหล่งเหมือนกันหมด — ฟังก์ชัน
ที่ออกแบบมาอย่างดีตาม idiomatic Rust ควรรับ `&[T]` เป็น parameter เสมอเมื่อแค่ต้องการ "อ่าน" ข้อมูล เพื่อให้ใช้
งานได้กว้างที่สุดโดยไม่เสียอะไรเลย

### 13.11 `Vec<T>` เป็น Generic Type

สังเกตว่าตลอดบทนี้เราเขียน `Vec<i32>`, `Vec<String>`, `Vec<&str>`, `Vec<Product>` (จะเห็นในหัวข้อถัดไป) ได้
เหมือนกันหมดโดยไม่ต้องมีชนิดข้อมูล `Vec` แยกสำหรับแต่ละชนิด — นั่นเป็นเพราะ `Vec` ถูกประกาศไว้ใน standard library
เป็น **generic type** ประมาณว่า `struct Vec<T> { ... }` (โครงสร้างจริงซับซ้อนกว่านี้มากเพราะต้องจัดการ memory
allocator เอง แต่แนวคิดหลักคือแบบนี้) `T` ในที่นี้คือ **type parameter** — ช่องว่างสำหรับ "ชนิดข้อมูลอะไรก็ได้"
ที่จะถูกแทนที่ตอนใช้งานจริง (`i32`, `String`, `Product`, หรือแม้แต่ `Vec<i32>` ซ้อนกันเป็น `Vec<Vec<i32>>` ก็ทำ
ได้) นี่คือเหตุผลที่ `Vec<T>` เขียน method อย่าง `.push(value: T)`, `.pop() -> Option<T>` ได้เพียงครั้งเดียวใน
standard library แล้วใช้ได้กับข้อมูลทุกชนิดที่มีอยู่และที่จะถูกสร้างขึ้นในอนาคต โดยไม่ต้องเขียนโค้ดซ้ำสำหรับแต่ละ
ชนิดข้อมูลเลย เราจะเรียนวิธีเขียน generic type และ generic function ของตัวเองอย่างเป็นทางการใน **Part 18** —
`Vec<T>` ที่ใช้มาตลอดบทนี้คือตัวอย่างของ generic ที่ดีที่สุดและใช้บ่อยที่สุดในภาษา Rust ทั้งหมด

#### ผลที่ตามมาของความเป็น generic: `Vec<Vec<T>>` ก็ทำได้เช่นกัน

เพราะ `T` ใน `Vec<T>` แทนที่ด้วยชนิดข้อมูล**อะไรก็ได้** และ `Vec<i32>` เองก็เป็นชนิดข้อมูลชนิดหนึ่ง ไม่มีอะไรห้าม
ไม่ให้เอา `Vec<i32>` ไปเป็น `T` ของ `Vec` อีกชั้นหนึ่ง — ได้ผลลัพธ์เป็น **`Vec<Vec<i32>>`** ซึ่งเป็นวิธีมาตรฐานใน
Rust สำหรับแทนข้อมูลแบบ 2 มิติ (ตาราง, กระดานหมากรุก, ภาพ grid) ที่แต่ละแถวสามารถมีความยาวต่างกันได้ (ต่างจาก
array 2 มิติ `[[T; M]; N]` ที่ทุกแถวต้องยาวเท่ากันเสมอ เพราะขนาดเป็นส่วนหนึ่งของ type):

```rust
fn main() {
    let grid: Vec<Vec<i32>> = vec![
        vec![1, 2, 3],
        vec![4, 5, 6],
        vec![7, 8, 9],
    ];

    for row in &grid {
        for cell in row {
            print!("{cell:>3}");
        }
        println!();
    }

    println!("แถวที่ 1 คอลัมน์ที่ 2: {}", grid[1][2]);
}
```

ผลลัพธ์:

```
  1  2  3
  4  5  6
  7  8  9
แถวที่ 1 คอลัมน์ที่ 2: 6
```

`grid[1][2]` คือการ index ซ้อนกันสองชั้น: `grid[1]` ได้ `Vec<i32>` ตัวที่สอง (index เริ่มจาก 0 เหมือนเดิม — คือ
`vec![4, 5, 6]`) แล้ว `[2]` ต่อท้ายอีกชั้นดึงสมาชิกตัวที่สามของแถวนั้นออกมา (`6`) — กฎ index ทุกอย่างเหมือนกับที่
เรียนในหัวข้อ 13.5 ทุกประการ เพียงแค่ซ้อนกันสองชั้นเท่านั้น รวมถึงกฎ panic เมื่อ index เกินขอบเขตก็ใช้ทั้งสองชั้น
เช่นกัน (ถ้า `grid[1]` มีแค่ 3 สมาชิก แล้วพยายาม `grid[1][10]` ก็จะ panic ด้วย error message แบบเดียวกับหัวข้อ
13.5 ทุกประการ)

### 13.12 ตัวอย่างจริง: ระบบจัดการสินค้าคงคลังด้วย `Vec<Product>`

ปิดท้ายบทนี้ด้วยตัวอย่างที่รวมทุกอย่างที่เรียนมาเข้าด้วยกัน — ระบบจัดการสินค้าคงคลังอย่างง่ายที่ใช้ `Vec<Product>`
(struct สไตล์เดียวกับที่เรียนใน Part 9) ผสมกับ `Option<T>` (Part 11) และ slice (Part 8) เพื่อสร้างฟังก์ชัน
เพิ่ม/ลบ/ค้นหา/รวมมูลค่าที่ใช้งานได้จริง

```rust
#[derive(Debug)]
struct Product {
    name: String,
    price: f64,
    quantity: u32,
}

impl Product {
    fn new(name: &str, price: f64, quantity: u32) -> Product {
        Product {
            name: name.to_string(),
            price,
            quantity,
        }
    }

    fn stock_value(&self) -> f64 {
        self.price * self.quantity as f64
    }
}

/// เพิ่มสินค้าใหม่เข้าคลัง
fn add_product(inventory: &mut Vec<Product>, product: Product) {
    inventory.push(product);
}

/// หาตำแหน่งสินค้าจากชื่อ (คืน index เพื่อใช้ภายในโมดูลนี้เท่านั้น)
fn find_index_by_name(inventory: &[Product], name: &str) -> Option<usize> {
    for (i, p) in inventory.iter().enumerate() {
        if p.name == name {
            return Some(i);
        }
    }
    None
}

/// ค้นหาสินค้าจากชื่อ คืนเป็น reference แบบอ่านอย่างเดียว (Option<&Product>)
fn find_product<'a>(inventory: &'a [Product], name: &str) -> Option<&'a Product> {
    let index = find_index_by_name(inventory, name)?;
    inventory.get(index)
}

/// ลบสินค้าออกจากคลังด้วยชื่อ คืนค่าตัวที่ถูกลบออกมา (Option<Product>) ถ้าไม่พบคืน None
fn remove_product(inventory: &mut Vec<Product>, name: &str) -> Option<Product> {
    let index = find_index_by_name(inventory, name)?;
    Some(inventory.remove(index))
}

/// รวมมูลค่าสินค้าทั้งหมดในคลัง (ราคา x จำนวน ของทุกตัว)
fn total_value(inventory: &[Product]) -> f64 {
    let mut sum = 0.0;
    for p in inventory {
        sum += p.stock_value();
    }
    sum
}

/// คืนรายชื่อสินค้าที่เหลือน้อยกว่าเกณฑ์ที่กำหนด (ใช้เตือนให้สั่งซื้อเพิ่ม)
fn low_stock<'a>(inventory: &'a [Product], threshold: u32) -> Vec<&'a Product> {
    let mut result = Vec::new();
    for p in inventory {
        if p.quantity < threshold {
            result.push(p);
        }
    }
    result
}

fn print_inventory(inventory: &[Product]) {
    for p in inventory {
        println!(
            "  - {:<10} ราคา {:>8.2} บาท จำนวน {:>3} ชิ้น มูลค่ารวม {:>10.2} บาท",
            p.name, p.price, p.quantity, p.stock_value()
        );
    }
}

fn main() {
    let mut inventory: Vec<Product> = Vec::with_capacity(4);

    add_product(&mut inventory, Product::new("ปากกา", 5.0, 100));
    add_product(&mut inventory, Product::new("ยางลบ", 3.5, 60));
    add_product(&mut inventory, Product::new("สมุด", 25.0, 8));
    add_product(&mut inventory, Product::new("ไม้บรรทัด", 10.0, 3));

    println!("=== รายการสินค้าทั้งหมด ===");
    print_inventory(&inventory);
    println!("มูลค่ารวมทั้งคลัง: {:.2} บาท", total_value(&inventory));

    println!();
    println!("=== ค้นหาสินค้า ===");
    match find_product(&inventory, "สมุด") {
        Some(p) => println!("พบ: {} เหลือ {} ชิ้น", p.name, p.quantity),
        None => println!("ไม่พบสินค้าที่ค้นหา"),
    }
    match find_product(&inventory, "ดินสอ") {
        Some(p) => println!("พบ: {} เหลือ {} ชิ้น", p.name, p.quantity),
        None => println!("ไม่พบสินค้า 'ดินสอ' ในคลัง"),
    }

    println!();
    println!("=== สินค้าที่เหลือน้อยกว่า 10 ชิ้น (ควรสั่งเพิ่ม) ===");
    for p in low_stock(&inventory, 10) {
        println!("  - {} เหลือแค่ {} ชิ้น!", p.name, p.quantity);
    }

    println!();
    println!("=== ลบสินค้า 'ยางลบ' ออกจากคลัง ===");
    match remove_product(&mut inventory, "ยางลบ") {
        Some(removed) => println!("ลบ {} ออกไปแล้ว ({} ชิ้น)", removed.name, removed.quantity),
        None => println!("ไม่พบสินค้าที่ต้องการลบ"),
    }

    println!();
    println!("=== รายการสินค้าหลังลบ ===");
    print_inventory(&inventory);
    println!("มูลค่ารวมทั้งคลัง: {:.2} บาท", total_value(&inventory));

    println!();
    println!("=== เรียงสินค้าตามมูลค่ารวม (มากไปน้อย) ===");
    inventory.sort_by(|a, b| b.stock_value().partial_cmp(&a.stock_value()).unwrap());
    print_inventory(&inventory);
}
```

**อธิบายภาพรวมของสถาปัตยกรรมโปรแกรมนี้:**

- **`inventory: Vec<Product>`** คือ "แหล่งความจริงเดียว" (single source of truth) ของข้อมูลสินค้าคงคลังทั้งหมด
  — ทุกฟังก์ชันทำงานผ่าน `&Vec<Product>`/`&mut Vec<Product>`/`&[Product]` เท่านั้น ไม่มีการคัดลอกข้อมูลสินค้า
  ทั้งชุดไปมาโดยไม่จำเป็นเลย
- **ฟังก์ชันที่แค่ "อ่าน" ข้อมูล** (`find_index_by_name`, `find_product`, `total_value`, `low_stock`,
  `print_inventory`) **รับ parameter เป็น `&[Product]`** ตามหลักการจาก Part 8 — ทำให้เรียกได้ทั้งกับ
  `&inventory` (ทั้ง `Vec`) ตรง ๆ ผ่าน deref coercion โดยไม่ต้องแปลงอะไรเลย
- **ฟังก์ชันที่ "แก้ไข" ข้อมูล** (`add_product`, `remove_product`) **รับ parameter เป็น `&mut Vec<Product>`**
  เพราะต้องเรียก `.push()`/`.remove()` ซึ่งอาจเปลี่ยนความยาวของ `Vec` (สังเกตว่าใช้ `&mut Vec<Product>` ไม่ใช่
  `&mut [Product]` เพราะ `.push()`/`.remove()` เป็น method ของ `Vec` โดยเฉพาะ ไม่มีใน slice — slice มีความยาว
  ตายตัว เปลี่ยนจำนวนสมาชิกไม่ได้ตามที่เรียนใน Part 8)
- **`find_product` และ `remove_product` ใช้ `find_index_by_name` เป็นฟังก์ชันช่วยร่วมกัน** (คืน `Option<usize>`)
  แล้วใช้ operator `?` (เชื่อม Part 12) เพื่อ "คืน `None` ทันทีถ้าไม่พบ" — ลดการเขียน `match` ซ้อนกันหลายชั้น
- **`low_stock` คืนค่าเป็น `Vec<&'a Product>`** — สังเกตว่านี่คือ `Vec` ที่เก็บ**reference** ไปยัง `Product` ใน
  `inventory` เดิม (ไม่ใช่คัดลอก `Product` ทั้งก้อนออกมาใหม่) ประหยัดทั้งเวลาและหน่วยความจำ เพราะฟังก์ชันนี้แค่
  ต้องการ "ชี้บอก" ว่าตัวไหนน่าสนใจ ไม่ได้ต้องการเป็นเจ้าของสินค้าตัวใหม่ — lifetime `'a` ผูก `Vec<&'a Product>`
  ที่คืนออกมาเข้ากับ `inventory` ต้นทาง (คล้ายกับที่ `first_word` ใน Part 8 ผูก `&str` ที่คืนออกมาเข้ากับ `s`
  ต้นทาง) ทำให้ compiler การันตีได้ว่า reference เหล่านี้จะไม่กลายเป็น dangling pointer
- **`inventory.sort_by(...)` ที่ท้ายโปรแกรม** แสดงให้เห็นว่า method ของ `Vec` (`.sort_by()`) และ struct ที่มี
  method ของตัวเอง (`.stock_value()`) ทำงานร่วมกันได้อย่างเป็นธรรมชาติ — `partial_cmp` ใช้เพราะ `f64` ไม่
  implement `Ord` แบบเต็ม (ค่า `NaN` ของ float เทียบลำดับไม่ได้แน่นอนเสมอไปตามมาตรฐาน IEEE 754 ที่เรียนใน Part 3)
  จึงต้อง `.unwrap()` ผลลัพธ์ `Option<Ordering>` ออกมา (ในบริบทนี้เรามั่นใจว่าไม่มี `NaN` เกิดขึ้นจริง เพราะราคา
  และจำนวนเป็นค่าปกติเสมอ)

โปรแกรมนี้แสดงให้เห็นว่า `Vec<T>` ไม่ได้เป็นแค่ "array ที่ขยายได้" เฉย ๆ — มันคือรากฐานสำคัญที่ทำให้เราสร้างระบบ
จัดการข้อมูลที่ซับซ้อนขึ้นได้จริง โดยยังคงกฎ ownership/borrowing ที่ปลอดภัยทุกประการจาก Part 6-7 ผสมกับความสะดวก
ของ `Option`/`Result` จาก Part 11-12 และพลังของ slice จาก Part 8 เข้าด้วยกันอย่างกลมกลืน

## กับดักที่พบบ่อย (Common Pitfalls)

**1. Index เกินขอบเขต ทำให้โปรแกรม panic**

```rust
fn main() {
    let products = vec!["ปากกา", "ยางลบ", "สมุด"];
    println!("สินค้าตัวแรก: {}", products[0]);
    println!("สินค้าตัวที่ 10: {}", products[10]);
}
```

```
สินค้าตัวแรก: ปากกา

thread 'main' panicked at src/main.rs:4:40:
index out of bounds: the len is 3 but the index is 10
note: run with `RUST_BACKTRACE=1` environment variable to display a backtrace
```

**วิธีแก้**: ถ้า index มาจากแหล่งที่ไม่มั่นใจ 100% ว่าถูกต้องเสมอ (เช่น input จากผู้ใช้ หรือค่าคำนวณที่อาจผิดพลาด)
ให้ใช้ `.get(index)` แทน (คืน `Option<&T>`) ตามที่เรียนในหัวข้อ 13.5 — เก็บ `v[i]` ไว้ใช้เฉพาะเมื่อมั่นใจจริง ๆ
ว่า index ถูกต้องแน่นอน (เช่น มาจาก `0..v.len()`)

**2. ถือ reference ไปยังสมาชิกตัวหนึ่งของ `Vec` พร้อมกับพยายาม `.push()` (E0502) — กับดักที่พบบ่อยที่สุดในบทนี้**

```rust
fn main() {
    let mut scores = vec![10, 20, 30];

    let first = &scores[0];

    scores.push(40);

    println!("สมาชิกตัวแรก: {first}");
}
```

```
error[E0502]: cannot borrow `scores` as mutable because it is also borrowed as immutable
 --> src/main.rs:6:5
  |
4 |     let first = &scores[0];
  |                  ------ immutable borrow occurs here
5 |
6 |     scores.push(40);
  |     ^^^^^^^^^^^^^^^ mutable borrow occurs here
7 |
8 |     println!("สมาชิกตัวแรก: {first}");
  |                            ----- immutable borrow later used here
```

**เหตุผลเชิงลึก**: `.push()` อาจทำให้ `Vec` ต้อง reallocate heap buffer ใหม่ทั้งก้อน (ตามกลยุทธ์เพิ่มเป็นสองเท่า
ในหัวข้อ 13.4) ถ้า reallocate เกิดขึ้นจริง buffer เก่าที่ `first` ชี้ไปจะถูกคืนกลับให้ระบบปฏิบัติการ ทำให้ `first`
กลายเป็น dangling pointer ทันที — compiler ปฏิเสธโค้ดนี้เพื่อป้องกัน use-after-free bug ระดับ memory safety
100% ตั้งแต่ compile time (ดูคำอธิบายฉบับเต็มในหัวข้อ 13.7)

**วิธีแก้**: ใช้ `first` ให้จบก่อน `.push()` (อาศัย NLL) หรือคัดลอกค่าออกมาก่อน (`let first_value = scores[0];`
ถ้า `T` เป็น `Copy`) — ดูตัวอย่างโค้ดที่แก้แล้วทั้งสองแบบในหัวข้อ 13.7

**3. วนลูปแบบ by value (`for x in v`) แล้วพยายามใช้ `v` ต่อหลัง loop**

```rust
fn main() {
    let names = vec![String::from("สมชาย"), String::from("สมหญิง")];

    for name in names {
        println!("สวัสดี {name}");
    }

    println!("จำนวนสมาชิกทั้งหมด: {}", names.len());
}
```

```
error[E0382]: borrow of moved value: `names`
 --> src/main.rs:8:40
  |
2 |     let names = vec![String::from("สมชาย"), String::from("สมหญิง")];
  |         ----- move occurs because `names` has type `Vec<String>`, which does not implement the `Copy` trait
3 |
4 |     for name in names {
  |                 ----- `names` moved due to this implicit call to `.into_iter()`
...
8 |     println!("จำนวนสมาชิกทั้งหมด: {}", names.len());
  |                                     ^^^^^ value borrowed here after move
  |
help: consider iterating over a slice of the `Vec<String>`'s content to avoid moving into the `for` loop
  |
4 |     for name in &names {
  |                 +
```

**วิธีแก้**: เปลี่ยนเป็น `for name in &names` (วนแบบ by reference) ถ้าแค่ต้องการอ่านค่าโดยไม่ต้องการเป็นเจ้าของ
มันจริง ๆ — ดูรายละเอียดเต็มในหัวข้อ 13.6

**4. ลืมเขียน `mut` แล้วพยายามเรียก method ที่แก้ไข `Vec`**

```rust
fn main() {
    let numbers = vec![1, 2, 3];
    numbers.push(4);
    println!("{:?}", numbers);
}
```

```
error[E0596]: cannot borrow `numbers` as mutable, as it is not declared as mutable
 --> src/main.rs:3:5
  |
3 |     numbers.push(4);
  |     ^^^^^^^ cannot borrow as mutable
  |
help: consider changing this to be mutable
  |
2 |     let mut numbers = vec![1, 2, 3];
  |         +++
```

**วิธีแก้**: เติม `mut` ตอนประกาศตัวแปร (`let mut numbers = ...`) — กับดักนี้เป็นแค่การนำกฎ `mut`/immutable
default จาก Part 3 มาใช้กับ `Vec` เท่านั้น ไม่มีกฎใหม่เพิ่มเติมเลย แต่พบบ่อยมากตอนเพิ่งเริ่มเขียนโค้ดที่ใช้ `Vec`
เพราะมือใหม่มักไม่ทันคิดว่า `.push()`/`.insert()`/`.remove()`/`.sort()` ทุกตัวต้องการ mutable borrow เสมอ

**5. เข้าใจผิดว่า `vec!` รับสมาชิกได้หลายชนิดข้อมูลผสมกัน**

```rust
fn main() {
    let mixed = vec![1, "two", 3.0];
    println!("{:?}", mixed);
}
```

```
error[E0308]: mismatched types
 --> src/main.rs:2:25
  |
2 |     let mixed = vec![1, "two", 3.0];
  |                         ^^^^^ expected integer, found `&str`
```

**เหตุผลเชิงลึก**: `Vec<T>` เก็บได้เพียง**ชนิดข้อมูลเดียว** (`T` ตัวเดียว) เสมอ ตามที่เรียนในหัวข้อ 13.11 ว่า
`Vec<T>` เป็น generic type — เมื่อ compiler เห็นสมาชิกตัวแรกเป็น `1` มันจะ infer ว่า `T = i32` (หรือชนิด integer
ที่เหมาะสม) ทันที สมาชิกตัวต่อไปทุกตัวจึง**ต้องเป็นชนิดเดียวกันนั้นเท่านั้น** — ถ้าต้องการเก็บชนิดข้อมูลต่างกันใน
collection เดียว ต้องใช้ enum ที่ครอบชนิดข้อมูลเหล่านั้นไว้ (เทคนิคนี้จะเรียนเมื่อกลับไปทวน Part 10 ผสมกับความรู้
เรื่อง `Vec` ในบทนี้) หรือใช้ trait object (`Box<dyn Trait>`) ซึ่งเป็นเรื่องขั้นสูงกว่าที่จะเรียนใน Part 21

**วิธีแก้**: ตรวจสอบว่าสมาชิกทุกตัวเป็นชนิดข้อมูลเดียวกัน (เช่นแปลงให้เป็น `String` ทั้งหมดถ้าต้องการเก็บทั้ง
ตัวเลขและข้อความปนกันแบบข้อความล้วน)

**6. คิดว่า `.remove(i)` และ `.swap_remove(i)` ทำงานเหมือนกัน (ต้นทุนและผลลัพธ์ต่างกันจริง)**

```rust
fn main() {
    let mut v = vec![10, 20, 30, 40, 50];
    let removed = v.remove(1);
    println!("remove(1) = {removed}, v = {:?}", v);

    let mut v2 = vec![10, 20, 30, 40, 50];
    let removed2 = v2.swap_remove(1);
    println!("swap_remove(1) = {removed2}, v2 = {:?}", v2);
}
```

```
remove(1) = 20, v = [10, 30, 40, 50]
swap_remove(1) = 20, v2 = [10, 50, 30, 40]
```

**เหตุผลเชิงลึก**: `.remove(i)` **เลื่อนสมาชิกทุกตัวหลังตำแหน่ง `i` มาทางซ้ายหนึ่งช่อง** เพื่อปิดช่องว่าง —
รักษาลำดับเดิมไว้ครบ แต่มีต้นทุน **O(n)** ในกรณีแย่ที่สุด (ลบตัวแรกของ `Vec` ขนาดใหญ่ ต้องเลื่อนสมาชิกทุกตัวที่
เหลือ) ส่วน `.swap_remove(i)` **เอาสมาชิกตัวสุดท้ายมาแทนตำแหน่งที่ลบทันที** (สลับตำแหน่ง) ทำให้มีต้นทุนแค่
**O(1)** เสมอ ไม่ว่า `Vec` จะใหญ่แค่ไหน แต่**ลำดับของสมาชิกเปลี่ยนไป** (สังเกตจากผลลัพธ์ `v2` ที่ `50` และ `30`
สลับตำแหน่งกัน)

**วิธีแก้**: ถ้าลำดับของสมาชิกใน `Vec` มีความหมายสำคัญ (เช่น ลำดับการเข้าคิว, ลำดับเวลา) ต้องใช้ `.remove(i)`
เท่านั้น แต่ถ้าลำดับไม่สำคัญและต้องการความเร็วสูงสุด (เช่น ลบ item ออกจาก object pool ที่ไม่สนใจลำดับ) ให้ใช้
`.swap_remove(i)` แทน — เลือกให้ตรงกับความหมายทางธุรกิจจริง ไม่ใช่เลือกตามความเคยชิน

## แบบฝึกหัด (Exercises)

1. **[ง่าย]** เขียนฟังก์ชัน `fn sum_all(data: &[i32]) -> i32` ที่รวมผลบวกของสมาชิกทั้งหมดใน slice จากนั้นสร้าง
   `Vec<i32>` ด้วย `vec![...]` แล้วทดสอบเรียกฟังก์ชันนี้ทั้งกับ `&v` (ทั้ง `Vec`) และกับ `&v[1..4]` (ช่วงย่อย)
   สุดท้ายลองใช้ `.get(100)` กับ `v` เพื่อยืนยันว่าได้ `None` กลับมา ไม่ panic
   (hint: วน `for &x in data` แล้วบวกสะสมเข้าตัวแปร `mut total`, การเรียกฟังก์ชันกับ `&v[1..4]` จะได้ `&[i32]`
   อยู่แล้วตรง ๆ ไม่ต้องแปลงอะไรเพิ่ม เพราะ range slice ของ `Vec` คืน `&[T]` เหมือนที่เรียนในหัวข้อ 13.10)

2. **[กลาง]** เขียนฟังก์ชัน `fn dedupe_keep_order(items: Vec<i32>) -> Vec<i32>` ที่รับ `Vec<i32>` เข้ามา (รับแบบ
   by value เพราะฟังก์ชันนี้ตั้งใจ "จบชีวิต" ของ `Vec` เดิมแล้วคืน `Vec` ใหม่) แล้วคืน `Vec<i32>` ใหม่ที่ตัดค่า
   ที่ซ้ำออก **โดยรักษาลำดับการปรากฏครั้งแรกไว้** เช่น input `[1, 2, 2, 3, 1, 4]` ต้องได้ output `[1, 2, 3, 4]`
   ทดสอบกับ input ที่มีค่าซ้ำหลายแบบ
   (hint: สร้าง `Vec` ผลลัพธ์เปล่า ๆ ด้วย `Vec::new()` แล้ววนอ่าน `items` ทีละตัว — ก่อน push ค่าใหม่ ให้เช็คก่อน
   ด้วย `.contains(&value)` ว่ามีอยู่ใน `Vec` ผลลัพธ์แล้วหรือยัง ถ้ายังไม่มีค่อย push เพิ่ม)

3. **[ยาก]** โค้ดต่อไปนี้ compile ไม่ผ่าน (ละเมิดกฎเดียวกับหัวข้อ 13.7 — E0502) ให้แก้ไขให้ compile ผ่านได้
   **2 วิธีที่แตกต่างกัน** (เหมือนที่สอนในหัวข้อ 13.7: แบบที่ 1 จัดลำดับโค้ดใหม่โดยอาศัย NLL, แบบที่ 2 คัดลอกค่า
   ออกมาก่อน) แล้วอธิบายด้วยคำพูดของตัวเอง 2-3 บรรทัดว่าทำไม `.push()` ถึงเป็นตัวการที่ทำให้โค้ดนี้อันตราย ถ้า
   compiler ยอมให้ผ่าน:
   ```rust
   fn main() {
       let mut inventory = vec![100, 200, 300];
       let cheapest = &inventory[0];
       inventory.push(50);
       println!("ราคาที่ถูกที่สุด (เดิม): {cheapest}");
   }
   ```
   (hint: ดูตัวอย่างการแก้ทั้งสองวิธีในหัวข้อ 13.7 แล้วปรับชื่อตัวแปรให้ตรงกับโจทย์นี้)

4. **[ยาก/ประยุกต์]** ขยายตัวอย่างระบบสินค้าคงคลังในหัวข้อ 13.12 โดยเพิ่มฟังก์ชันใหม่
   `fn restock(inventory: &mut Vec<Product>, name: &str, extra_quantity: u32) -> Option<u32>` ที่ทำหน้าที่
   "เติมสต็อก" สินค้าที่มีชื่อตรงกับ `name` (เพิ่ม `quantity` ของสินค้านั้นด้วย `extra_quantity`) แล้วคืนค่า
   จำนวนสินค้าที่เหลือ**หลังเติมแล้ว**เป็น `Some(จำนวนใหม่)` ถ้าพบสินค้านั้นในคลัง หรือ `None` ถ้าไม่พบสินค้าที่
   ชื่อนี้เลย (ไม่ต้องสร้างสินค้าใหม่ให้ ถ้าไม่พบ) จากนั้นเขียน `main` ทดสอบเรียก `restock` ทั้งกรณีพบและไม่พบ
   สินค้า พร้อมพิมพ์ผลลัพธ์ทั้งสองกรณีให้ชัดเจน
   (hint: ใช้ `find_index_by_name` ที่มีอยู่แล้วเพื่อหา index ก่อน ใช้ `?` เพื่อคืน `None` ทันทีถ้าไม่พบ (เชื่อม
   Part 11-12) จากนั้นใช้ `inventory[index].quantity += extra_quantity;` เพื่อแก้ไขค่าตรง ๆ ผ่าน mutable
   indexing แล้วคืน `Some(inventory[index].quantity)` — สังเกตว่าโจทย์นี้รวม `Vec` mutable access, `Option`,
   และ `?` operator ไว้ในฟังก์ชันเดียวกันหมด)

## สรุป

ในบทนี้เราเริ่มจากข้อจำกัดที่ค้างมาตั้งแต่ Part 3: array มีความยาวตายตัวที่เป็นส่วนหนึ่งของ type ทำให้ไม่สามารถ
"เพิ่มสมาชิก" ได้เลยไม่ว่าจะพยายามแค่ไหน — **`Vec<T>`** แก้ปัญหานี้ด้วยการเป็น collection ที่จองพื้นที่บน heap
และปรับขนาดได้ตอน runtime เราเรียนวิธีสร้างมันทั้ง 3 แบบ (`Vec::new()`, `vec![...]`, `Vec::with_capacity(n)`)
พร้อมเข้าใจเหตุผลเชิงประสิทธิภาพของการจอง capacity ล่วงหน้า จากนั้นเจาะลึกโครงสร้างภายในของ `Vec<T>` ในฐานะ
**"fat owned buffer"** ที่เก็บ `(pointer, length, capacity)` เทียบกับ `&[T]` slice จาก Part 8 ที่มีแค่
`(pointer, length)` และไม่ได้เป็นเจ้าของอะไรเลย

เราเห็นกลไกการเพิ่ม/ลบสมาชิก (`push`, `pop`, `insert`, `remove`, `extend`) พร้อมพิสูจน์ด้วยตัวเลขจริงว่า `Vec`
ขยาย capacity แบบ**เพิ่มเป็นสองเท่า**ทุกครั้งที่เต็ม ทำให้ `.push()` มีต้นทุนเฉลี่ยแบบ **amortized O(1)** แม้บาง
ครั้งจะมีการ reallocate ที่ต้นทุนสูงกว่าปกติซ่อนอยู่ก็ตาม เราเข้าใจว่าทำไม Rust ให้ทั้ง `v[i]` (panic ทันทีเมื่อ
index ผิด) และ `.get(i)` (คืน `Option<&T>` อย่างปลอดภัย) ไว้คู่กัน — ปรัชญาเดียวกับที่เห็นซ้ำแล้วซ้ำอีกตลอด
หลักสูตรตั้งแต่ Part 3 และ Part 11

หัวข้อที่สำคัญที่สุดของบทนี้คือ **การถือ reference ไปยังสมาชิกของ `Vec` พร้อมกับพยายาม `.push()` (E0502)** —
เราเห็นว่านี่ไม่ใช่ข้อจำกัดที่ไม่มีเหตุผล แต่ป้องกัน use-after-free bug ระดับ memory safety ที่ร้ายแรงที่สุด
ประเภทหนึ่ง ซึ่งภาษาอย่าง C++ ปล่อยให้เกิดขึ้นได้จริงในโปรแกรมจำนวนมาก — Rust ปฏิเสธโค้ดแบบนี้ตั้งแต่ compile
time เสมอ โดยอาศัยกฎการยืมเดิมจาก Part 7 ทุกประการ ไม่มีกฎใหม่เพิ่มเติมเลย

ปิดท้ายด้วยการเชื่อมทุกอย่างเข้าด้วยกัน: `Vec<String>` vs `Vec<&str>`, การเรียงลำดับและค้นหา
(`sort`/`sort_by`/`sort_by_key`/`binary_search`/`contains`), deref coercion จาก `Vec<T>` สู่ `&[T]` ที่ทำให้
ฟังก์ชันที่เขียนรับ slice ใช้ได้กับทั้ง array และ `Vec` โดยไม่ต้องแก้โค้ด, ข้อเท็จจริงว่า `Vec<T>` เป็น generic
type ที่จะเรียนเจาะลึกใน Part 18, และตัวอย่างระบบจัดการสินค้าคงคลังจริงที่ผสม `Vec<Product>` เข้ากับ `Option<T>`
และ slice อย่างกลมกลืน

ใน **Part 14** เราจะเจาะลึก **`String`** อย่างเต็มรูปแบบ — ซึ่งที่จริงคือ `Vec<u8>` ที่การันตีว่าข้อมูลภายในเป็น
UTF-8 ที่ถูกต้องเสมอ! ความรู้เรื่อง `Vec<T>` ที่เรียนมาทั้งหมดในบทนี้ (การจอง capacity, การขยายพื้นที่แบบ doubling,
กฎ ownership/borrowing กับ `.push()`) จะนำไปใช้อธิบาย `String` ได้โดยตรงแทบทุกจุด เพราะโครงสร้างภายในเหมือนกัน
ทุกประการ ต่างกันแค่ `String` บังคับว่า byte ที่เก็บต้องประกอบกันเป็น UTF-8 ที่ถูกต้องเท่านั้น
