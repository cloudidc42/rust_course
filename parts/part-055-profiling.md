# Part 55: Profiling Rust Applications

> โมดูล: ระดับสูง (Advanced) | ระดับ: สูง | เวลาโดยประมาณ: 200 นาที

## เป้าหมายของบทเรียน

หลังจากจบบทนี้ คุณจะสามารถ:

- อธิบายความแตกต่างระหว่าง **benchmarking** (Part 54 — วัดว่าโค้ดจุดที่คุณสงสัยอยู่แล้วเร็วแค่ไหน) กับ
  **profiling** (บทนี้ — หาว่าในโปรแกรมทั้งตัว เวลาไปอยู่ที่จุดไหนกันแน่) และรู้ว่าทั้งสองอย่างต้องใช้**คู่กัน**
  ตามลำดับที่ถูกต้องในงาน optimization จริง ไม่ใช่เลือกใช้อย่างใดอย่างหนึ่ง
- อธิบายหลักการทำงานของ **sampling profiler** กับ **instrumenting profiler** ได้ว่าต่างกันอย่างไร แต่ละแบบมี
  overhead และความแม่นยำต่างกันอย่างไร และรู้ว่าเครื่องมือ profiling ส่วนใหญ่ในโลก Rust ใช้หลักการไหน
- ใช้ `perf record`/`perf report` บน Linux เพื่อหา hot function จริงในโปรแกรม พร้อมรู้ว่าทำไม **debug symbol**
  (คีย์ `debug` ใน profile ที่ Part 35 สอนไว้) ถึงเป็นเงื่อนไขจำเป็นที่ทำให้ผลลัพธ์อ่านออกได้จริง
- สร้างและอ่าน **flame graph** ได้ — รู้ว่าแกน X/Y ของภาพหมายถึงอะไร และใช้ `cargo flamegraph` เพื่อสร้างภาพจาก
  โปรแกรมจริงได้
- ใช้ `perf stat` เพื่อดูภาพรวมระดับสูง (instructions, cache misses, branch mispredictions) ก่อนลงรายละเอียด
  ด้วย sampling profiler แบบเต็มรูปแบบ และรู้จักเครื่องมือ memory profiling (`massif`, `dhat`) ว่าทำไม CPU
  profiler เพียงอย่างเดียวไม่พอสำหรับปัญหาบางประเภท
- อ่านผลลัพธ์จาก profiler อย่างมีวิจารณญาณ — รู้ว่าการ profile debug build, การ profile บนเครื่อง/environment
  ที่ไม่เหมือน production, หรือการไล่ตามฟังก์ชันที่ report โชว์ไว้แต่กินเวลาน้อยมาก ล้วนนำไปสู่ข้อสรุปที่ผิดได้
- ทำ workflow ครบวงจรได้จริง: profile โปรแกรมที่ไม่มีประสิทธิภาพ → หา bottleneck จากข้อมูล profiler จริง →
  แก้ไข → profile ซ้ำเพื่อพิสูจน์ด้วยตัวเลขจริงว่าแก้ถูกจุด

## ความรู้ที่ต้องมีมาก่อน

- **Part 54 (Performance Optimization และ Benchmarking ด้วย criterion)**: ต้องเข้าใจวิธีใช้ `criterion` เพื่อวัด
  ความเร็วของโค้ดจุดที่คุณ**สงสัยอยู่แล้ว**ว่าเป็นปัญหา (benchmarking แบบ micro-level) และต้องจำหลักการปิดท้ายของ
  Part 54 ได้ — **"วัดก่อน อย่าเพิ่งปรับให้เร็วขึ้นแบบเดา" (measure first, don't optimize blindly)** — บทนี้จะ
  ขยายหลักการนั้นไปอีกขั้น: ก่อนจะรู้ว่า "จุดไหนที่ต้อง benchmark" คุณต้อง**หาจุดนั้นให้เจอก่อน** ด้วย profiling
- **Part 35 (Cargo ขั้นสูง)**: ต้องเข้าใจ `[profile.*]` ทุกคีย์ โดยเฉพาะ `debug`/`strip`/`opt-level` และต้องจำ
  custom profile ชื่อ `profiling` ที่ Part 35 หัวข้อ 35.9 สร้างไว้ (inherit จาก `release` แต่ตั้ง `debug = true`,
  `strip = false`) ได้ — Part 35 บอกไว้ตรง ๆ ว่า profile นี้ "จะได้ใช้จริงใน Part 55" นี่คือบทนั้น
- **Part 6 (Ownership เบื้องต้น)** และ **Part 13 (`Vec<T>`)**: ต้องจำได้ว่า heap allocation มีต้นทุนสูงกว่า
  stack เพราะต้องผ่าน allocator ค้นหาพื้นที่ว่าง และ `Vec` ที่ไม่ได้จอง capacity ล่วงหน้าต้อง reallocate ซ้ำ ๆ —
  บทนี้จะโยงกลับไปหาเรื่องนี้ตอนพูดถึง memory profiling
- **Part 15 (HashMap และ Sets)**: ใช้ `HashMap` เป็นเครื่องมือแก้ไขปัญหา O(n²) ในตัวอย่าง worked example ของบทนี้
- **Part 41 (Unsafe Rust เบื้องต้น)**: เคยเห็น **Miri** มาแล้วในฐานะเครื่องมือตรวจ undefined behavior — บทนี้จะ
  ชี้ให้ชัดว่า Miri **ไม่ใช่** profiler และห้ามเอาผลจาก Miri มาสรุปเรื่องความเร็ว

## เนื้อหา

### 55.1 จาก Benchmark (Part 54) สู่ Profiling: เริ่มต้นจากไหนเมื่อโปรแกรม "ช้า"

ลองนึกภาพสถานการณ์จริงที่ทีมพัฒนาเจอกันบ่อยที่สุด: มีคนบอกว่า **"โปรแกรมช้า"** — อาจเป็น CLI tool ที่ผู้ใช้บ่นว่า
กว่าจะประมวลผลไฟล์เสร็จ, หรือ API endpoint ที่ response time พุ่งขึ้นตอนโหลดสูง, หรือ batch job ที่กินเวลานาน
เกินคาด คำถามที่ตามมาทันทีคือ **"ช้าที่ตรงไหน?"** — และนี่คือจุดที่มือใหม่จำนวนมากพลาดตั้งแต่ก้าวแรก

**สิ่งที่ Part 54 สอนไว้ไม่ใช่คำตอบของคำถามนี้** — `criterion` เป็นเครื่องมือที่ตอบคำถามประเภท **"ฟังก์ชัน
`parse_line()` ตัวนี้เร็วแค่ไหน เทียบกับ implementation อีกแบบ"** — มันตอบได้ดีมาก แต่มันต้องการให้คุณ**บอกมันก่อน
แล้วว่าจะวัดฟังก์ชันไหน** ปัญหาคือในโปรแกรมขนาดจริงที่มีหลายร้อยหลายพันฟังก์ชัน คุณจะรู้ได้อย่างไรว่าควรเอา
ฟังก์ชันไหนไป benchmark? ถ้าเดาผิด คุณอาจ optimize ฟังก์ชันที่ทำงานเร็วอยู่แล้วให้เร็วขึ้นอีก 2 เท่า ในขณะที่
ฟังก์ชันตัวจริงที่กินเวลา 80% ของโปรแกรมทั้งหมดไม่ถูกแตะเลยแม้แต่นิดเดียว — เวลาที่เสียไปกับการ optimize ผิดจุด
นี่แหละคือสิ่งที่ profiling มีไว้ป้องกัน

**Profiling คือขั้นตอนที่มาก่อน benchmarking ในเวิร์กโฟลว์ optimization จริง** ลำดับที่ถูกต้องคือ:

```
1. โปรแกรมช้า (สังเกตจากผู้ใช้/monitoring/ความรู้สึก)
       │
       ▼
2. PROFILE โปรแกรมทั้งตัวขณะทำงานจริง (หรือใกล้เคียงจริงที่สุด)
   → ได้คำตอบว่า "เวลา/instruction/memory ไปอยู่ที่ฟังก์ชันไหนกันแน่"
       │
       ▼
3. เลือก "ผู้ต้องสงสัยตัวจริง" จากข้อมูล profiler (ไม่ใช่จากความรู้สึก)
       │
       ▼
4. BENCHMARK ด้วย criterion (Part 54) เพื่อเทียบ candidate fix หลายแบบสำหรับจุดที่พบ
   → ได้คำตอบว่า "implementation ไหนของจุดนี้เร็วที่สุด"
       │
       ▼
5. แก้โค้ดจริงด้วย implementation ที่ชนะจาก benchmark
       │
       ▼
6. PROFILE ซ้ำ เพื่อพิสูจน์ว่าโปรแกรมทั้งตัวเร็วขึ้นจริง ไม่ใช่แค่ฟังก์ชันเดี่ยว ๆ เร็วขึ้นในสูญญากาศ
```

สังเกตว่า **profiling ปรากฏสองครั้ง** — ครั้งแรกเพื่อหาว่าจะแก้ตรงไหน ครั้งที่สองเพื่อพิสูจน์ว่าแก้สำเร็จจริง
ส่วน **benchmarking ปรากฏหนึ่งครั้ง** ตรงกลาง เพื่อเลือกวิธีแก้ที่ดีที่สุดสำหรับจุดที่ profiling ชี้ไว้แล้ว
นี่คือความสัมพันธ์ที่แม่นยำระหว่างสองเครื่องมือ: **profiling ตอบคำถาม "ที่ไหน" (where), benchmarking ตอบคำถาม
"แบบไหนเร็วกว่า" (which) สำหรับจุดที่ profiling บอกมาแล้ว**

หลักการปิดท้ายของ Part 54 — "วัดก่อน อย่าเพิ่งปรับให้เร็วขึ้นแบบเดา" — จริง ๆ แล้วมีอีกครึ่งหนึ่งที่ซ่อนอยู่ ซึ่ง
บทนี้จะเปิดเผยให้เห็นตรง ๆ: **ก่อนจะ "วัด" ด้วย criterion ได้ คุณต้องรู้ก่อนว่าจะวัดอะไร — และการรู้ว่าจะวัดอะไร
ก็ต้องมาจากการวัดอีกแบบหนึ่งเช่นกัน (คือ profiling) ไม่ใช่จากการเดา** ทั้งบทนี้และ Part 54 จึงเป็นสอง**ครึ่ง**ของ
หลักการเดียวกัน: "อย่าเดา ให้วัด" — Part 54 สอนวิธีวัดขนาดเล็ก (micro) ส่วนบทนี้สอนวิธีวัดขนาดใหญ่ (macro) ที่ต้อง
มาก่อน

### 55.2 Sampling Profiler vs Instrumenting Profiler: หลักการที่ต้องเข้าใจก่อนใช้เครื่องมือใด ๆ

เครื่องมือ profiling ทั้งหมดที่มีอยู่ในโลกทำงานตามหลักการใดหลักการหนึ่งจากสองแบบนี้ — เข้าใจความต่างให้ชัดก่อน
จะช่วยให้คุณอ่านผลลัพธ์จากเครื่องมือไหนก็ตามได้อย่างถูกต้อง และรู้ว่าเมื่อไรควรเชื่อตัวเลขที่เห็นมากแค่ไหน

#### Sampling Profiler: "แวบมาดูเป็นระยะ ๆ"

หลักการ: โปรแกรม profiler **สั่งให้ระบบปฏิบัติการขัดจังหวะ (interrupt) โปรแกรมที่กำลัง profile เป็นระยะ ๆ
อย่างสม่ำเสมอ** (เช่น ทุก ๆ 1 มิลลิวินาที หรือทุก ๆ N instruction ที่ CPU ประมวลผลไปแล้ว) แล้ว**บันทึก call
stack ณ ขณะนั้น** ไว้เป็นหนึ่ง "sample" ทำแบบนี้ซ้ำ ๆ หลายพันหรือหลายหมื่นครั้งตลอดการทำงานของโปรแกรม จากนั้นนำ
sample ทั้งหมดมา**รวมกันทางสถิติ** — ฟังก์ชันไหนที่ปรากฏใน call stack บ่อยที่สุดในบรรดา sample ทั้งหมด ก็สรุปได้ว่า
ฟังก์ชันนั้น**น่าจะ**กินเวลาไปมากที่สุด

จุดสำคัญคือคำว่า "น่าจะ" — นี่เป็นการประมาณค่าทางสถิติ ไม่ใช่การนับที่แน่นอน 100% ถ้า sample น้อยเกินไป (โปรแกรม
รันเร็วมากจนมี sample ได้ไม่กี่ครั้ง) ผลลัพธ์อาจมี noise สูง แต่ถ้า sample มากพอ (โปรแกรมรันนานพอ หรือปรับความถี่
sampling ให้สูงขึ้น) ผลลัพธ์ทางสถิติจะสะท้อนสัดส่วนเวลาจริงได้แม่นยำมากขึ้นเรื่อย ๆ

**ข้อดี**: overhead ต่ำมาก (แค่ interrupt เป็นระยะ ไม่ต้องแก้โค้ดโปรแกรมเลย) จึงเหมาะกับการ profile โปรแกรมที่
กำลังรันแบบใกล้เคียง production จริงมากที่สุด แทบไม่กระทบพฤติกรรมเวลาของโปรแกรมเลย
**ข้อเสีย**: ความแม่นยำขึ้นกับจำนวน sample — ฟังก์ชันที่รันเร็วมาก (กินเวลาน้อยกว่าช่วงเวลาระหว่าง sample) อาจไม่
ถูกจับได้เลยแม้จะถูกเรียกหลายพันครั้ง (เพราะ sample ไม่บังเอิญไปตกตรงจังหวะที่มันทำงาน)

`perf` บน Linux คือตัวอย่างที่ใช้กันมากที่สุดของ sampling profiler — และเครื่องมือ profiling ส่วนใหญ่ในโลก Rust
(รวมถึง `cargo flamegraph` ที่จะเห็นในหัวข้อ 55.5) ก็เป็นแค่ **wrapper** ที่เรียก `perf` (หรือเครื่องมือ sampling
ระดับ OS อื่น เช่น Instruments บน macOS, ETW บน Windows) แล้วนำผลลัพธ์มาแสดงในรูปแบบที่อ่านง่ายขึ้นเท่านั้น — โลก
Rust ไม่ได้สร้าง sampling profiler ของตัวเองขึ้นมาใหม่ แต่ยืมของ OS มาใช้ เพราะการเขียน sampling profiler ที่ดี
ต้องเข้าถึง timer interrupt และ stack unwinding ระดับต่ำมาก ซึ่งเป็นงานของ OS อยู่แล้ว

#### Instrumenting Profiler: "แทรกโค้ดจับเวลาเข้าไปเอง"

หลักการ: profiler **แก้ไขโปรแกรม (หรือรันผ่าน interpreter/simulator ของตัวเอง) เพื่อแทรกโค้ดจับเวลา/นับ
instruction ไว้ที่จุดเข้า-ออกของทุกฟังก์ชัน (หรือทุก basic block)** ทำให้ได้ตัวเลข**แม่นยำแบบนับจริง** ไม่ใช่การ
ประมาณทางสถิติ — รู้เป๊ะว่าฟังก์ชันนี้ถูกเรียกกี่ครั้ง แต่ละครั้งกิน instruction กี่ตัว

**ข้อดี**: ความแม่นยำสูงมาก ได้ตัวเลขที่นับจริงไม่ใช่ประมาณ เหมาะกับการวิเคราะห์เจาะลึกระดับ instruction/cache
**ข้อเสีย**: การแทรกโค้ด/รันผ่าน simulator ทำให้โปรแกรมช้าลงอย่างมหาศาล (มักช้าลง 20-100 เท่าจากความเร็วปกติ) และ
ที่สำคัญกว่านั้นคือ**เปลี่ยนพฤติกรรมเวลาของโปรแกรมไปจากที่ควรจะเป็น** — ถ้าโปรแกรมมีเงื่อนไข race condition หรือ
พฤติกรรมที่ขึ้นกับ timing (เช่น cache warm-up, thread scheduling) ผลจาก instrumenting profiler อาจไม่สะท้อน
พฤติกรรมจริงตอนรันแบบปกติเลย นี่คือปรากฏการณ์ที่เรียกกันเล่น ๆ ว่า **"observer effect"** (คล้ายฟิสิกส์ quantum
ที่การสังเกตเปลี่ยนสิ่งที่สังเกต) — เครื่องมือที่ใช้เพื่อวัดความเร็ว กลับเปลี่ยนความเร็วที่กำลังวัดไปด้วยตัวมันเอง

`valgrind --tool=callgrind` ที่จะใช้จริงในหัวข้อ 55.4 คือตัวอย่างของ instrumenting profiler แบบเต็มรูปแบบ — มัน
ไม่ได้แค่แทรกโค้ดจับเวลา แต่**รันโปรแกรมทั้งตัวผ่าน CPU simulator ของ Valgrind เอง** จำลองการทำงานของ CPU จริง
ทีละ instruction เพื่อนับจำนวน instruction ที่ประมวลผลไปอย่างแม่นยำ 100% (ไม่ใช่การประมาณทางสถิติ) แต่แลกมาด้วย
ความช้าที่มหาศาล — โปรแกรมที่ปกติรัน 0.1 วินาที อาจใช้เวลาหลายวินาทีถึงหลายสิบวินาทีเมื่อรันผ่าน callgrind

| | Sampling (เช่น `perf`) | Instrumenting (เช่น `callgrind`) |
|---|---|---|
| หลักการ | interrupt เป็นระยะ, สุ่มเก็บ call stack | แทรกโค้ด/รันผ่าน simulator, นับทุก instruction |
| Overhead ต่อโปรแกรม | ต่ำมาก (ไม่กี่ % ) | สูงมาก (ช้าลง 20-100 เท่า) |
| ความแม่นยำ | ประมาณทางสถิติ (แม่นขึ้นถ้า sample มากพอ) | นับจริงแบบ deterministic |
| เหมาะกับ | profile โปรแกรมที่รันแบบใกล้เคียง production | วิเคราะห์เจาะลึกระดับ instruction/cache, โปรแกรมทดสอบขนาดเล็ก |
| ตัวอย่าง | `perf`, macOS Instruments, Windows ETW | `valgrind --tool=callgrind`, `valgrind --tool=cachegrind` |

**ข้อสรุปเชิงปฏิบัติ**: ไม่มีแบบไหนที่ "ดีกว่า" อีกแบบเสมอไป — sampling เหมาะกับการหาภาพรวมของโปรแกรมจริงที่รัน
แบบปกติ ในขณะที่ instrumenting เหมาะกับการยืนยันตัวเลขที่แม่นยำสำหรับโปรแกรมทดสอบขนาดเล็กที่ไม่ต้องสนใจ overhead
ที่เพิ่มมา บทนี้จะใช้ทั้งสองแบบ — อธิบายหลักการและวิธีอ่านผลของ `perf` (sampling, เครื่องมือหลักของโลกจริง) และใช้
`callgrind` (instrumenting) เป็นเครื่องมือที่**รันจริงได้ในทุก environment** เพื่อสาธิต workflow แบบครบวงจร

### 55.3 `perf`: เครื่องมือพื้นฐานที่สุดบน Linux และทำไม debug symbol ถึงสำคัญ

`perf` คือชุดคำสั่ง profiling ที่มาพร้อม Linux kernel เอง (เป็นส่วนหนึ่งของ kernel source tree ภายใต้
`tools/perf/`) มันคือเครื่องมือที่**หาได้ง่ายที่สุดและใช้กันแพร่หลายที่สุด**สำหรับ profiling โปรแกรมบน Linux ไม่
ว่าจะเขียนด้วยภาษาอะไรก็ตาม (C, C++, Rust, Go ฯลฯ) เพราะมันทำงานที่ระดับ **CPU + kernel** ไม่สนใจว่าโปรแกรมที่
กำลัง profile เขียนด้วยภาษาไหน — มันแค่ต้องอ่าน machine code และ symbol table ของ binary ที่รันอยู่

#### การติดตั้ง

บน distro ที่ใช้ APT (Ubuntu/Debian) มักติดตั้งผ่าน:

```bash
sudo apt-get install linux-tools-common linux-tools-generic
```

**ข้อควรรู้ที่มักเจอปัญหาจริง**: patch version ของ `perf` ต้อง**ตรงกับเวอร์ชัน kernel ที่กำลังรันอยู่** เพราะ
`perf` คุยกับ kernel ผ่าน syscall `perf_event_open()` ที่มี ABI ผูกกับเวอร์ชัน kernel นั้น ๆ ถ้าเครื่อง (หรือ
container) รัน custom kernel หรือ kernel เวอร์ชันที่ไม่ตรงกับ package `linux-tools-generic` ที่ repository มีให้
การติดตั้งอาจล้มเหลวตรง ๆ — ตัวอย่างจริงจากการเตรียมเนื้อหาบทนี้: เครื่องที่ใช้เขียนบทนี้รัน custom kernel เวอร์ชัน
`6.18.44` แต่ Ubuntu package repository มี `linux-tools-generic` ให้แค่รุ่น `6.8.0-106` (คนละเวอร์ชันกันเลย) ทำให้
`apt-get install` ล้มเหลวด้วย error `404 Not Found` เพราะไม่มี package รุ่นที่ตรงกับ kernel ให้ดาวน์โหลด — นี่คือ
เหตุผลสำคัญที่ต่อไปนี้บทนี้จะแสดงทั้งวิธีใช้ `perf` แบบมาตรฐาน (สำหรับเครื่อง Linux ทั่วไปที่ package ตรงกับ
kernel) และวิธีสำรองด้วย `valgrind` (ซึ่งไม่ผูกกับเวอร์ชัน kernel เลย เพราะทำงานเป็น user-space process ล้วน ๆ)
สำหรับสถานการณ์ที่ `perf` ใช้ไม่ได้ เช่น container บางประเภทหรือ cloud environment ที่ไม่มีสิทธิ์เพียงพอ

#### สิทธิ์การเข้าถึง: `perf_event_paranoid`

Linux kernel มี security setting ชื่อ `/proc/sys/kernel/perf_event_paranoid` ที่ควบคุมว่า process ธรรมดา
(ไม่ใช่ root) จะเข้าถึง performance counter ของ CPU ได้แค่ไหน — ค่ายิ่งสูง ยิ่งจำกัดสิทธิ์มาก:

| ค่า | ความหมาย |
|---|---|
| `-1` | ไม่จำกัดเลย ใครก็ profile ได้ (ค่าที่หลายเครื่อง development ตั้งไว้) |
| `0` หรือ `1` | จำกัดบางส่วน แต่ยัง profile process ของตัวเองได้โดยไม่ต้องเป็น root |
| `2` | จำกัดมาก — profile ได้แค่ process ของตัวเองที่รันแบบ non-privileged เท่านั้น หลาย container ตั้งค่านี้เป็น default |
| `3` | ปิดสนิท ต้องเป็น root เท่านั้นถึงจะ profile ได้เลย |

**นี่คือปัญหาที่พบบ่อยมากในสภาพแวดล้อมแบบ container/cloud/CI** — Docker container จำนวนมาก (โดยเฉพาะที่รันแบบ
ไม่ได้ให้สิทธิ์ `--privileged` หรือ `--cap-add=SYS_ADMIN`/`--cap-add=PERFMON` ตรง ๆ) จะบล็อกการเรียก
`perf_event_open()` แม้ `perf_event_paranoid` จะตั้งไว้ต่ำก็ตาม เพราะ container runtime บล็อก syscall นี้ไว้ที่
ระดับ seccomp/namespace โดยไม่สนใจค่า setting ของ kernel เลย — สิ่งนี้เกิดขึ้นจริงกับเครื่องที่ใช้เตรียมเนื้อหา
บทนี้: แม้จะติดตั้ง `linux-tools` สำเร็จ (ถ้าเวอร์ชันตรงกัน) `perf record` ก็อาจยังใช้งานไม่ได้ในบาง container
เพราะสิทธิ์ที่ container runtime จำกัดไว้อีกชั้นหนึ่ง วิธีตรวจสอบเบื้องต้นคืออ่านค่านี้:

```bash
cat /proc/sys/kernel/perf_event_paranoid
```

ถ้าคุณควบคุม container ได้เอง (เช่นเขียน `Dockerfile`/`docker run` เอง) วิธีแก้คือเพิ่ม capability ให้ container
ตรง ๆ ตอนรัน:

```bash
docker run --cap-add=SYS_PTRACE --cap-add=PERFMON --security-opt seccomp=unconfined ...
```

แต่ถ้าคุณทำงานบน environment ที่ควบคุมสิทธิ์ไม่ได้ (เช่น CI runner ที่บริษัทจัดให้, cloud sandbox, hosted CI) และ
`perf` ใช้ไม่ได้จริง ๆ ไม่ว่าจะพยายามอย่างไร — **นี่เป็นสถานการณ์ที่เกิดขึ้นบ่อยกว่าที่คิด** และหัวข้อ 55.4 จะ
แสดงวิธีสำรองที่ยังทำ workflow แบบเดียวกันได้จริงด้วย `valgrind`

#### ทำไม debug symbol (คีย์ `debug` จาก Part 35) ถึงเป็นเงื่อนไขจำเป็น

`perf` (และ profiler สาย sampling ทุกตัว) ทำงานโดยบันทึก **memory address** ของ instruction ที่กำลังรันอยู่ ณ
ขณะที่ interrupt เกิดขึ้น — address ดิบ ๆ แบบนี้ไม่มีความหมายอะไรกับมนุษย์เลย (`0x0000555555559a3c` บอกอะไรคุณไม่ได้)
สิ่งที่แปลง address เหล่านี้กลับมาเป็น **ชื่อฟังก์ชัน + ชื่อไฟล์ + เลขบรรทัด** ที่อ่านรู้เรื่องได้คือ **debug
symbol** — ข้อมูลที่ Part 35 หัวข้อ 35.3 อธิบายไว้ว่าถูกควบคุมด้วยคีย์ `debug` ใน `[profile.*]`

ถ้า build ด้วย `[profile.release]` ปกติ (ค่า default `debug = false`) แล้วเอามา profile ด้วย `perf`, สิ่งที่คุณ
จะเห็นในรายงานคือ:

```
23.41%  logcount  logcount  [.] 0x0000000000012a3c
19.02%  logcount  logcount  [.] 0x0000000000012b91
```

**เห็นแค่ hex address ไม่มีชื่อฟังก์ชันเลย** — รู้ว่ามี "จุดหนึ่ง" ในโปรแกรมที่กินเวลา 23.41% แต่ไม่รู้ว่าจุดนั้น
คือฟังก์ชันไหน ทำอะไร ต้องไปเปิด disassembly เทียบ address เอาเองซึ่งแทบทำไม่ได้จริงในโปรแกรมขนาดใหญ่ นี่คือ
เหตุผลที่ **Part 35 หัวข้อ 35.9 สร้าง custom profile ชื่อ `profiling` ไว้ล่วงหน้าสำหรับบทนี้โดยเฉพาะ**:

```toml
[profile.profiling]
inherits = "release"    # ได้ opt-level = 3 และการ optimize เต็มรูปแบบเหมือน release
debug = true              # แต่เก็บ debug symbol ไว้ ทำให้ profiler อ่านชื่อฟังก์ชัน/เลขบรรทัดได้
strip = false              # และไม่ strip symbol table ออกหลัง link
```

build ด้วย profile นี้:

```bash
cargo build --profile profiling
```

ได้ binary ที่ **optimize เท่า release แต่ profiler อ่านชื่อฟังก์ชันได้เหมือน debug build** — เมื่อ profile
binary ตัวนี้ด้วย `perf` (หรือเครื่องมืออื่นใดก็ตาม) รายงานที่ได้จะมีชื่อฟังก์ชันจริง เช่น
`logcount::Counter::record` แทนที่จะเป็น hex address ล้วน ๆ — นี่คือจุดที่ทำให้คำสอนของ Part 35 กับบทนี้เชื่อม
กันสนิท: **profile ที่ Part 35 "เกริ่นไว้ล่วงหน้า" คือสิ่งที่คุณต้องใช้จริงทุกครั้งที่จะ profile โปรแกรม**

#### ชื่อฟังก์ชันที่ profiler แสดงอาจ "เพี้ยน": Rust name mangling และ `rustfilt`

แม้ debug symbol จะครบ บางครั้งชื่อฟังก์ชันที่ profiler แสดงออกมาอาจไม่ใช่ชื่อที่คุณเขียนในโค้ดตรง ๆ แต่เป็นชื่อที่
ผ่านกระบวนการที่เรียกว่า **name mangling** — compiler ต้องเปลี่ยนชื่อฟังก์ชัน/type ให้เป็น symbol name ที่ไม่ซ้ำ
กันเลยในระดับ binary (เพราะ Rust รองรับ generic, module path ซ้อนกันหลายชั้น, และ trait implementation หลาย
ตัวที่อาจมีชื่อฟังก์ชันเหมือนกันได้) ชื่อที่ demangle แล้วอย่าง `logcount::Counter::record` อาจถูกเก็บใน symbol
table จริง ๆ เป็นสตริงที่ยาวและอ่านยากกว่ามาก ในรูปแบบที่ขึ้นต้นด้วย `_ZN` ตาม Itanium C++ ABI mangling scheme ที่
Rust ยืมมาใช้ (มีการดัดแปลงเพิ่มเล็กน้อยสำหรับ feature ที่ C++ ไม่มี เช่น generic ข้าม crate)

เครื่องมืออย่าง `perf report` และ `cargo flamegraph` **demangle ชื่อให้อ่านง่ายโดยอัตโนมัติ**อยู่แล้วในเวอร์ชัน
ปัจจุบันส่วนใหญ่ แต่ถ้าคุณเจอเครื่องมือรุ่นเก่าหรือ workflow ที่ยังแสดงชื่อแบบ mangled อยู่ (เช่นตอนอ่าน
`perf.data` ผ่านเครื่องมืออื่นที่ไม่รู้จัก Rust mangling scheme) มี crate ชื่อ `rustfilt` ที่ทำหน้าที่ demangle
ชื่อ Rust โดยเฉพาะ ติดตั้งและใช้แบบ pipe ต่อจากคำสั่งเดิมได้ตรง ๆ:

```bash
cargo install rustfilt
perf report --stdio | rustfilt
```

ถ้าเห็นชื่อแบบนี้ในผลลัพธ์ดิบ:

```
23.41%  logcount  logcount  [.] _ZN8logcount7Counter6record17h3f8a2b1c9d0e4f5aE
```

หลังผ่าน `rustfilt` จะกลายเป็น:

```
23.41%  logcount  logcount  [.] logcount::Counter::record
```

ส่วนท้ายของชื่อ mangled ที่เป็น hex ยาว ๆ (`17h3f8a2b1c9d0e4f5a`) คือ **hash ที่ compiler เติมเข้าไปเพื่อแยกความ
กำกวมระหว่าง instantiation ของ generic ตัวเดียวกันที่ต่างชนิดข้อมูลกัน** (เช่น `Vec::<u32>::push` กับ
`Vec::<String>::push` เป็นฟังก์ชันคนละตัวกันจริง ๆ ในระดับ machine code แม้เขียนโค้ดต้นฉบับเหมือนกัน) — เมื่อเจอ
hash แบบนี้ต่อท้ายชื่อฟังก์ชัน generic ใน profiler report ไม่ต้องแปลกใจ มันเป็นเรื่องปกติของภาษาที่มี monomorphized
generic แบบ Rust (Part 18/22 อธิบายไว้ว่า generic ของ Rust ถูก compile แยกเป็นโค้ดจริงสำหรับแต่ละชนิดข้อมูลที่ใช้
ไม่ใช่ใช้โค้ดเดียวกันทุก type แบบ dynamic dispatch)

#### ปรับความถี่ sampling ด้วย `-F`: trade-off ระหว่างความละเอียดกับ overhead

ค่า default ของ `perf record` มักตั้ง sampling frequency ไว้ที่ประมาณ 1000 ครั้งต่อวินาที (`1000 Hz`) ปรับได้ผ่าน
แฟล็ก `-F`:

```bash
perf record -F 99 -g -- ./target/profiling/logcount     # 99 samples/sec - overhead ต่ำ เหมาะกับ production
perf record -F 9999 -g -- ./target/profiling/logcount   # 9999 samples/sec - ละเอียดมาก เหมาะกับโปรแกรมที่รันเร็ว/สั้น
```

**ทำไมบางทีมเลือกใช้ค่าคี่ ๆ อย่าง `99` แทน `100`?** เพื่อเลี่ยง**การซิงค์กันเอง (aliasing)** กับ periodic event
อื่นในระบบที่มักเกิดที่ความถี่กลม ๆ เช่น timer ของ OS scheduler ที่มักตั้งไว้ที่ 100 Hz หรือ 1000 Hz พอดี — ถ้า
sampling frequency ของ `perf` ไปตรงกับความถี่ของ event periodic อื่นเป๊ะ ๆ อาจเกิด**bias เชิงระบบ**ที่ทำให้
sample กระจุกไปตกที่จังหวะเดียวกันซ้ำ ๆ (เช่น sample ตกตรงจังหวะที่ scheduler กำลังทำงานพอดีบ่อยเกินสัดส่วนจริง)
เลขคี่อย่าง `99`/`999` ช่วยลดโอกาสเกิด aliasing แบบนี้ นี่เป็นรายละเอียดเล็ก ๆ ที่ไม่กระทบการเรียนรู้พื้นฐานของ
บทนี้มากนัก แต่มีประโยชน์เมื่อคุณ profile production ระยะยาวและต้องการความแม่นยำทางสถิติสูงสุด

**Trade-off ที่ต้องจำ**: ความถี่สูง (`-F 9999`) ให้ sample มากขึ้น ความแม่นยำทางสถิติสูงขึ้น แต่ overhead ต่อ
โปรแกรมที่กำลัง profile ก็สูงขึ้นตามไปด้วย (ต้อง interrupt บ่อยขึ้น) — สำหรับ production ที่ต้องรัน `perf record`
ควบคู่กับ traffic จริงโดยไม่กระทบผู้ใช้มากเกินไป มักเลือกความถี่ต่ำ (`-F 99`) และรันเก็บ sample เป็นเวลานานขึ้น
เพื่อชดเชยจำนวน sample ที่น้อยกว่าต่อวินาที ส่วนการ profile โปรแกรมทดสอบขนาดเล็กที่รันจบเร็ว (แบบ `logcount` ใน
หัวข้อ 55.4) มักต้องใช้ความถี่สูงกว่าปกติมาก เพราะโปรแกรมรันจบเร็วเกินกว่าจะมี sample จำนวนมากพอที่ความถี่ default

#### คำสั่งพื้นฐาน: `perf record` และ `perf report`

รูปแบบการใช้งานมาตรฐาน (สมมติว่า `perf_event_open()` ใช้งานได้ในเครื่องของคุณ):

```bash
# บันทึกข้อมูล sample พร้อม call graph (-g) ขณะรัน binary
perf record -g -- ./target/profiling/logcount

# เปิดดูรายงานแบบ interactive (หรือใช้ --stdio เพื่อพิมพ์ออกมาตรง ๆ ไม่ต้องโต้ตอบ)
perf report --stdio
```

`perf record` จะรันโปรแกรมของคุณตามปกติ พร้อม sampling call stack เป็นระยะ (ค่า default มักอยู่ที่ประมาณ 1000
ครั้งต่อวินาที ปรับได้ผ่าน `-F`) แล้วเขียนผลลัพธ์เป็นไฟล์ `perf.data` ในโฟลเดอร์ปัจจุบัน แฟล็ก `-g` สำคัญมาก —
มันบอกให้ `perf` เก็บ**ทั้ง call stack** ไม่ใช่แค่ instruction pointer ตัวเดียว ทำให้รู้ได้ว่าฟังก์ชันที่กินเวลา

### 55.4 ทดลองจริง (1): เขียนโปรแกรม log analyzer ที่ตั้งใจให้ไม่มีประสิทธิภาพ แล้ว profile หา bottleneck

ถึงเวลาทำ workflow เต็มรูปแบบกับโปรแกรมจริง — เขียน log analyzer เล็ก ๆ ที่จำลองสถานการณ์ที่พบได้บ่อยจริง:
นับจำนวนครั้งที่ user แต่ละคนปรากฏใน access log แต่ตั้งใจเขียนให้มี**บั๊กเชิงประสิทธิภาพที่พบบ่อยมาก**ซ่อนอยู่ —
การใช้โครงสร้างข้อมูลที่ต้อง scan แบบ linear เพื่อเช็คว่า "เคยเห็น key นี้มาก่อนหรือยัง" ทั้งที่ปัญหาแบบนี้ควรใช้
`HashMap` (Part 15) ตั้งแต่แรก

**หมายเหตุเกี่ยวกับเครื่องมือที่ใช้ในหัวข้อนี้**: เครื่องที่เตรียมเนื้อหาบทนี้เป็น container ที่ `perf` ใช้งาน
ไม่ได้จริง (ตามที่อธิบายไว้ในหัวข้อ 55.3 — ทั้งปัญหาเวอร์ชัน `linux-tools` ไม่ตรงกับ kernel และสิทธิ์
`perf_event_open()` ที่ถูกจำกัดในสภาพแวดล้อมแบบ sandbox) ทุกตัวเลขในหัวข้อนี้จึงมาจาก **`valgrind
--tool=callgrind`** (instrumenting profiler จากหัวข้อ 55.2) ซึ่งรันได้จริงในทุก environment เพราะทำงานเป็น
user-space process ล้วน ๆ ไม่ต้องพึ่ง kernel permission พิเศษใด ๆ — ตัวเลขทุกตัวที่แสดงต่อไปนี้เป็นตัวเลขที่รัน
จริงและจับผลลัพธ์จริงมา ไม่ใช่ตัวเลขสมมติ ส่วนวิธีอ่านผล `perf`/flamegraph จะอธิบายควบคู่กันไปเป็นความรู้ที่ต้อง
ใช้เมื่อคุณทำงานบนเครื่อง Linux ทั่วไปที่ `perf` ใช้งานได้ (ซึ่งเป็นกรณีส่วนใหญ่ในโลกจริง — เครื่อง development
ปกติหรือ VM ที่ตั้งค่าเองไม่มีปัญหานี้)

#### เขียนโปรแกรม "ก่อนแก้"

```toml
# Cargo.toml
[package]
name = "logcount"

[profile.release]
debug = false

inherits = "release"

```

```rust
// src/main.rs
// logcount: จำลอง log analyzer ที่นับจำนวนครั้งที่ user id แต่ละตัวปรากฎใน access log
// เวอร์ชันนี้ "ตั้งใจ" เขียนแบบไม่มีประสิทธิภาพ เพื่อใช้เป็นตัวอย่าง profiling

struct Counter {
    // เก็บเป็น Vec ของ (user_id, count) แล้วค้นหาด้วย linear scan ทุกครั้ง
    // -- นี่คือจุดที่จะกลายเป็น O(n^2) เมื่อจำนวน unique user มาก
    entries: Vec<(String, u64)>,
}

impl Counter {
    fn new() -> Self {
        Counter { entries: Vec::new() }
    }

    fn record(&mut self, user_id: &str) {
        // ค้นหาว่ามี user_id นี้อยู่แล้วหรือยัง ด้วยการไล่ทีละตัว (linear search)
        for entry in self.entries.iter_mut() {
            if entry.0 == user_id {
                entry.1 += 1;
                return;
            }
        }
        // ไม่เจอ -> เพิ่มใหม่ (ต้อง allocate String ใหม่ทุกครั้ง)
        self.entries.push((user_id.to_string(), 1));
    }

    fn total_unique(&self) -> usize {
        self.entries.len()
    }

    fn top_n(&self, n: usize) -> Vec<(String, u64)> {
        let mut sorted = self.entries.clone();
        sorted.sort_by(|a, b| b.1.cmp(&a.1));
        sorted.into_iter().take(n).collect()
    }
}

fn generate_log_lines(total_lines: usize, unique_users: usize) -> Vec<String> {
    // จำลอง log line: "user_id=<n> path=/api/resource status=200"
    let mut lines = Vec::with_capacity(total_lines);
    for i in 0..total_lines {
        let uid = i % unique_users;
        lines.push(format!("user_id=user{uid} path=/api/resource status=200"));
    }
    lines
}

fn extract_user_id(line: &str) -> Option<&str> {
    // ดึงค่าระหว่าง "user_id=" กับช่องว่างถัดไป
    let rest = line.strip_prefix("user_id=")?;
    let end = rest.find(' ').unwrap_or(rest.len());
    Some(&rest[..end])
}

fn main() {
    let total_lines = 60_000;
    let unique_users = 4_000;

    let lines = generate_log_lines(total_lines, unique_users);

    let mut counter = Counter::new();
    for line in &lines {
        if let Some(uid) = extract_user_id(line) {
            counter.record(uid);
        }
    }

    println!("total lines processed = {}", lines.len());
    println!("unique users = {}", counter.total_unique());
    let top5 = counter.top_n(5);
    for (uid, count) in &top5 {
        println!("  {uid}: {count} requests");
    }
}
```

โปรแกรมนี้อ่าน log 60,000 บรรทัด (จำลอง user 4,000 คนไม่ซ้ำ วนซ้ำแต่ละคนประมาณ 15 ครั้ง) แล้วนับจำนวนครั้งที่แต่
ละ user ปรากฏ — logic ถูกต้อง 100% แต่ `Counter::record` ทำ **linear search** ผ่าน `self.entries` ทุกครั้งที่
เรียก ซึ่งหมายความว่ายิ่งมี unique user มาก ยิ่งค้นหานานขึ้นเรื่อย ๆ (เฉลี่ยแล้วต้องไล่ผ่านครึ่งหนึ่งของ entries
ที่มีอยู่ในแต่ละครั้ง) รวมทั้งโปรแกรมทำให้เกิด **O(n²)** โดยรวม ทั้งที่ปัญหานี้แก้ได้ใน O(n) ด้วย `HashMap`

บวกเปอร์เซ็นต์ 4 อันดับแรกดู: `57.87% + 21.78% + 8.59% + 4.30% = 92.54%` — **เกือบ 93% ของ instruction ทั้งหมด

เปรียบเทียบหน่วยความจำแบบ vectorized ของ libc ที่ Rust เรียกใช้ภายในตอนเทียบ `&str`/`String` ด้วย `==`, ส่วน

compile มาให้)

นี่ตรงกับสมมติฐานที่ตั้งไว้ตอนออกแบบโปรแกรม: `Counter::record` ทำ linear search โดยเทียบ `entry.0 == user_id`
ทุกรอบ (Part 14 อธิบายไว้ว่า string comparison ต้องเทียบทีละ byte จนกว่าจะรู้ผล) — เมื่อมี unique user ถึง 4,000
คน การ insert แต่ละครั้งอาจต้องไล่เทียบ string นับพันครั้งก่อนจะรู้ว่า "ไม่เจอ" แล้วค่อยเพิ่มใหม่ ผลลัพธ์คือ**การ
เทียบ string กลายเป็นสิ่งที่กินเวลาส่วนใหญ่ของทั้งโปรแกรม** ไม่ใช่การอ่านไฟล์ ไม่ใช่การ format ข้อความ ไม่ใช่การ
เรียง top-N — แต่เป็น**การค้นหาแบบ linear ที่ควรใช้ hash-based lookup ตั้งแต่แรก**

#### จุดที่ต้องระวัง: inlining ทำให้ต้นเหตุ "หาย" จากบรรทัดที่คุณเขียน

สังเกตให้ดี ๆ ว่าบรรทัดที่**คุณเขียนเอง**ในโค้ด (`if entry.0 == user_id`) ถูก attribute ให้แค่ **2.66%**
(`src/main.rs:logcount::main`) ในขณะที่ต้นทุนจริงของการเปรียบเทียบ (92%+) ถูก attribute ไปยัง**ไฟล์ของ standard
library และ libc** แทน — ทำไมถึงเป็นแบบนี้?

คำตอบคือ **compiler inline โค้ดของ `PartialEq for str`/`memcmp` เข้าไปอยู่ในจุดที่เรียกใช้จริง** (ที่
`opt-level = 3` ซึ่ง profile `profiling` inherit มาจาก `release`) ทำให้ตอนที่ profiler บันทึกว่า "instruction
นี้อยู่ที่ไหน" มันเห็น instruction ที่ถูก inline มาจาก source ของ library ไม่ใช่เห็นแค่ "อยู่ในฟังก์ชัน
`record`" อีกต่อไป — สามหัวข้อของ `callgrind_annotate` ที่ชื่อ `slice/cmp.rs`, `ptr/non_null.rs`, และ
`slice/iter/macros.rs` **ทั้งหมดคือส่วนหนึ่งของ chain การเปรียบเทียบที่ถูก inline เข้าไปในฟังก์ชัน `main`**
(สังเกตว่า `file:function` ของทั้งสามบรรทัดระบุ `function` เป็น `logcount::main` เหมือนกันหมด แม้ `file` จะเป็น
ไฟล์ของ standard library) — นี่คือเหตุผลสำคัญว่าทำไมการอ่านผล profiler ต้อง**มองภาพรวมของ call chain ทั้งหมด
ไม่ใช่แค่มองบรรทัดในไฟล์ของตัวเองเพียงอย่างเดียว** — ถ้าคุณกรองดูแค่ `src/main.rs` แล้วเห็นแค่ 2.66% คุณอาจสรุป
ผิดว่าโค้ดตรงนี้ไม่ใช่ปัญหา ทั้งที่จริง ๆ มันคือต้นเหตุของ 92%+ ที่กระจายไปอยู่ใน library หลายไฟล์ที่ถูก inline
เข้ามา

ดูรายละเอียดระดับ source line ด้วย auto-annotation ของ `callgrind_annotate` ยืนยันจุดนี้ตรง ๆ:

```

                    for entry in self.entries.iter_mut() {
73,662,500 ( 2.64%)              if entry.0 == user_id {
   112,000 ( 0.00%)                  entry.1 += 1;
```

บรรทัด `if entry.0 == user_id {` เองถูก attribute เพียง 73,662,500 instruction (2.64%) — แต่บรรทัดนี้คือจุดที่
**เรียก** เครื่องจักรเปรียบเทียบ string ทั้งหมดที่ถูก inline ไปกินเวลาอีก 90% ที่เหลือ การชี้ไปที่บรรทัดนี้ยังคง
ถูกต้อง (มันคือสาเหตุของปัญหาจริง) แต่ตัวเลข % ที่ profiler แสดงตรงบรรทัดนี้เพียงอย่างเดียว**ไม่สะท้อนต้นทุนที่
แท้จริง**ทั้งหมด — นี่คือความแตกต่างที่สำคัญระหว่าง "การมองแค่ตัวเลข % ตรงหน้า" กับ "การเข้าใจ call chain ทั้ง
เส้นที่นำไปสู่ตัวเลขนั้น"

### 55.5 Flame Graph: อ่านภาพที่บอกได้ในพริบตาว่าฟังก์ชันไหน "กิน" เวลาไปเท่าไหร่

ตัวเลขในตารางของ `perf report`/`callgrind_annotate` มีประโยชน์มาก แต่สำหรับโปรแกรมขนาดใหญ่ที่มี call stack ลึก
หลายสิบชั้น การไล่อ่านตารางตัวเลขทีละแถวอาจทำให้มองภาพรวมไม่ออก — **flame graph** (คิดค้นและเผยแพร่โดย Brendan
Gregg) คือวิธีแสดงข้อมูล profiling เดียวกันในรูปแบบภาพที่ทำให้มองเห็น bottleneck ได้ทันทีในพริบตาเดียว

#### แกน X และ Y หมายถึงอะไร

```
                    ┌──────────────┐
                    │ parse_config │  <- ชั้นบนสุด: ฟังก์ชันที่ลึกที่สุดใน stack ตอนถูก sample
                    └──────────────┘
        ┌───────────────────────────────────────┐
        │              record()                  │  <- ฟังก์ชันที่เรียก parse_config (และอื่น ๆ)
        └───────────────────────────────────────┘
┌─────────────────────────────────────────────────────────────┐
│                       main()                                  │  <- ชั้นล่างสุด: จุดเริ่ม stack
└─────────────────────────────────────────────────────────────┘
 0%                          ความกว้าง = สัดส่วนเวลา/sample                          100%
```

- **แกน Y (แนวตั้ง)**: แสดง**ความลึกของ call stack** — ชั้นล่างสุดคือฟังก์ชันที่อยู่บนสุดของ call chain (มักเป็น
  `main` หรือจุดเริ่ม thread) ยิ่งขึ้นไปชั้นบน ยิ่งลึกเข้าไปใน call stack (ฟังก์ชันที่ถูกเรียกซ้อนกันลงไปเรื่อย ๆ)
- **แกน X (แนวนอน)**: แสดง**สัดส่วนของเวลา (หรือจำนวน sample) ที่ฟังก์ชันนั้นกินไป** — ความกว้างของกล่องแต่ละ
  กล่องเป็นสัดส่วนตรง ๆ กับเวลาที่ใช้ ไม่ใช่ลำดับเวลาที่เกิดขึ้นจริง (สำคัญมาก: **แกน X ไม่ใช่ timeline**! กล่อง
  ที่อยู่ซ้ายไม่ได้แปลว่า "เกิดก่อน" กล่องที่อยู่ขวา — มันแค่ถูกจัดเรียงตามตัวอักษร/ลำดับ call เพื่อให้ดูง่าย)
- **สีของกล่อง**: ส่วนใหญ่ **ไม่มีความหมายเชิงตัวเลขใด ๆ** — เป็นแค่สีสุ่ม (หรือไล่เฉด) เพื่อช่วยแยกกล่องข้าง
  เคียงออกจากกันด้วยตา ไม่ได้บอกว่า "สีแดง = แย่" แบบ heat map (บางเครื่องมือ เช่น differential flame graph
  อาจใช้สีเพื่อบอกว่าฟังก์ชันไหนเร็วขึ้น/ช้าลงเมื่อเทียบสอง run แต่นั่นเป็นการใช้งานพิเศษ ไม่ใช่ค่า default)

**สิ่งที่ทำให้ flame graph มีประโยชน์มาก**: ฟังก์ชันที่กิน "เวลารวมมากที่สุด" จะปรากฏเป็น**กล่องที่กว้างที่สุด**
ในภาพ — สายตามนุษย์จับความกว้างที่แตกต่างกันได้เร็วกว่าการไล่อ่านตัวเลขในตารางมาก ถ้ามีฟังก์ชันหนึ่งกิน 60% ของ
เวลาทั้งโปรแกรม คุณจะเห็น "แถบกว้าง ๆ" พาดยาวตรงกลางภาพทันทีโดยไม่ต้องอ่านตัวเลขเลย — นี่คือเหตุผลที่ flame
graph เป็นเครื่องมือแรกที่วิศวกร performance จำนวนมากเปิดดูก่อนจะลงไปดูตัวเลขละเอียดในตาราง

#### `cargo flamegraph`: wrapper ที่รวม `perf` เข้ากับการวาดภาพ

`cargo-flamegraph` (แพคเกจ `flamegraph` บน crates.io) คือ cargo subcommand ที่**เรียก `perf record` ให้
โดยอัตโนมัติ** แล้วนำผลลัพธ์ไปแปลงเป็นไฟล์ SVG ผ่าน crate `inferno` (Rust reimplementation ของสคริปต์
`flamegraph.pl` ต้นฉบับของ Brendan Gregg) — มันไม่ได้เป็น profiler ของตัวเอง แต่เป็น**ตัวประสานงาน**ที่ทำให้คุณ
ไม่ต้องพิมพ์คำสั่ง `perf record` → แปลงข้อมูล → เรียกสคริปต์วาดภาพ ทีละขั้นตอนด้วยมือ

ติดตั้งครั้งเดียวผ่าน:

```bash
cargo install flamegraph
```

ใช้งานกับโปรแกรมของบทนี้:

```bash
cargo flamegraph --profile profiling --bin logcount
```

คำสั่งนี้จะ build ด้วย profile `profiling` (debug symbol ครบ ตามที่อธิบายไว้ในหัวข้อ 55.3) แล้วเรียก `perf
record -g` ให้อัตโนมัติ จากนั้นสร้างไฟล์ `flamegraph.svg` ที่เปิดดูในเว็บเบราว์เซอร์ได้ทันที — ภาพ SVG ที่ได้
สามารถ**คลิกที่กล่องใดก็ได้เพื่อ "ซูม"** เข้าไปดูเฉพาะ subtree ของฟังก์ชันนั้น และ hover เมาส์เพื่อดูตัวเลข %
ที่แน่นอนของแต่ละกล่อง (ความสามารถ interactive นี้คือข้อดีสำคัญที่ตารางตัวเลขธรรมดาให้ไม่ได้)

**หมายเหตุตรงไปตรงมาจากการเตรียมเนื้อหานี้**: `cargo-flamegraph` ติดตั้งสำเร็จโดยไม่มีปัญหา (มันเป็นแค่โปรแกรม
Rust ธรรมดาที่ compile ได้ปกติ) แต่ตอนรันจริงบนเครื่องที่เตรียมบทนี้ กลับได้ error ตรง ๆ:

```
Error: perf is not installed or not present in $PATH
```

นี่ยืนยันสิ่งที่อธิบายไว้ในหัวข้อ 55.3 อย่างชัดเจนที่สุด — `cargo flamegraph` **ไม่ใช่ profiler ของตัวเอง**
มันแค่**เรียก `perf` เป็น dependency ระดับ binary ที่ต้องมีอยู่แล้วใน `$PATH`** ถ้า `perf` ใช้ไม่ได้ (เพราะ
เวอร์ชันไม่ตรง kernel, ไม่มีสิทธิ์, หรือกำลังรันใน container ที่บล็อกไว้) `cargo flamegraph` ก็ใช้ไม่ได้ตามไป
ด้วยเสมอ — ไม่มีทางเลี่ยง เพราะมันไม่มี fallback ไปใช้เครื่องมืออื่นโดยอัตโนมัติ (บน macOS มันจะสลับไปใช้
`dtrace` แทน แต่บน Linux มีแค่ทางเดียวคือ `perf`) นี่คือเหตุผลที่หัวข้อ 55.4 เลือกใช้ `valgrind` เป็นเครื่องมือ
สาธิตหลักแทน — เพราะทำงานได้ในทุก environment โดยไม่ต้องพึ่ง `perf` เป็น dependency

#### สิ่งที่ flame graph ของโปรแกรมในหัวข้อ 55.4 จะแสดง (ถ้า `perf` ใช้งานได้ในเครื่องคุณ)

จากข้อมูล callgrind ที่วัดได้จริงในหัวข้อ 55.4 (memcmp/string comparison กิน ~92% ของ instruction ทั้งหมด)
flame graph ที่สร้างจาก sampling บนเครื่องที่ `perf` ใช้งานได้จะมีรูปร่างลักษณะนี้:

```
┌────────────────────────────────────────────────────────────────────────┐  <- __memcmp_avx2_movbe (~61%, แถบกว้างที่สุด)
└────────────────────────────────────────────────────────────────────────┘
┌──────────────────────────────────────────────────────────────────────────┐  <- str::eq / PartialEq (~89%, กว้างกว่าอีกนิด เพราะครอบ memcmp ไว้)
└──────────────────────────────────────────────────────────────────────────┘
┌────────────────────────────────────────────────────────────────────────────┐  <- Counter::record (~90%)
└────────────────────────────────────────────────────────────────────────────┘
┌──────────────────────────────────────────────────────────────────────────────────┐  <- main (100%, ฐานเต็มความกว้างภาพ)
└──────────────────────────────────────────────────────────────────────────────────┘
```

สิ่งที่คุณจะสังเกตเห็นทันทีจากภาพจริง (ไม่ต้องอ่านตัวเลขเลย): **มีแถบเดียวที่พาดยาวเกือบเต็มความกว้างของภาพ
ตั้งแต่ชั้น `main` ขึ้นไปจนถึง `__memcmp_avx2_movbe`** — นี่คือสัญญาณที่ชัดเจนว่ามี "เส้นทางเดียว" ที่กิน
เวลาส่วนใหญ่ของทั้งโปรแกรม (ตรงข้ามกับโปรแกรมที่ performance กระจายสม่ำเสมอไปทั่วหลายฟังก์ชัน ซึ่งจะเห็นเป็น
กล่องเล็ก ๆ จำนวนมากแทนที่จะเป็นแถบกว้างเดียว) — รูปร่างแบบนี้บอกตรง ๆ ว่า "แก้จุดเดียวนี้ก็เพียงพอที่จะได้
ผลลัพธ์ที่ต่างไปมาก" ซึ่งตรงกับสิ่งที่หัวข้อ 55.10 จะพิสูจน์ด้วยตัวเลขจริง

#### Differential Flame Graph: เปรียบเทียบ "ก่อน" กับ "หลัง" เป็นภาพเดียว

เมื่อทำ workflow ครบวงจรแบบหัวข้อ 55.4/55.10 (profile ก่อนแก้ → แก้ไข → profile หลังแก้) คุณจะได้ไฟล์ flame
graph สองไฟล์ — วิธีเทียบทั้งสองภาพที่ตรงไปตรงมาที่สุดคือเปิดดูคู่กันแล้วเทียบด้วยตา (ความกว้างของแถบ
`Counter::record` ในภาพ "ก่อน" ควรกว้างกว่าภาพ "หลัง" อย่างเห็นได้ชัด) แต่สำหรับกรณีที่ความต่างเล็กกว่านี้มาก
จนตาเปล่าเทียบยาก มีเทคนิคที่เรียกว่า **differential flame graph** — นำข้อมูล sample จากสอง run มารวมกันในภาพ
เดียว โดยใช้**สี**แทนความหมายพิเศษเป็นครั้งเดียว (ต่างจากที่อธิบายไว้ก่อนหน้าว่าสีปกติไม่มีความหมาย): สีแดงหมายถึง
"กินเวลามากขึ้นใน run หลัง" สีน้ำเงินหมายถึง "กินเวลาน้อยลงใน run หลัง" ความเข้มของสีบอกขนาดของความต่าง — เครื่องมือ
`inferno` (ตัวเดียวกันที่ `cargo flamegraph` ใช้สร้าง SVG ภายใน) มีคำสั่งย่อย `inferno-diff-folded` สำหรับสร้าง
ภาพแบบนี้จากไฟล์ folded-stack สองไฟล์ตรง ๆ — เป็นเทคนิคที่มีประโยชน์มากตอนทำ regression testing เชิง performance
(เช่นเช็คว่า PR ใหม่ทำให้ hot path ไหนช้าลงขึ้นมาโดยไม่ตั้งใจหรือไม่) แต่สำหรับความต่างขนาดใหญ่แบบในบทนี้ (20 เท่า)
การเทียบสองภาพแยกกันด้วยตาก็เพียงพอแล้ว ไม่จำเป็นต้องใช้เทคนิคนี้เสมอไป

### 55.6 `perf stat`: ภาพรวมระดับสูงก่อนลงรายละเอียด

ก่อนจะลงไปดู call stack แบบละเอียดด้วย `perf record`/`perf report`, บางครั้งสิ่งที่มีประโยชน์กว่าคือการดู
**ภาพรวมระดับ CPU counter** ก่อน — `perf stat` ทำหน้าที่นี้: มันรันโปรแกรมของคุณตามปกติ (ไม่ sample call stack
เลย) แล้วรายงานตัวเลขสรุปจาก **hardware performance counter** ของ CPU เมื่อโปรแกรมจบ

```bash
perf stat ./target/profiling/logcount
```

รูปแบบผลลัพธ์ทั่วไปที่ `perf stat` ให้ (ตัวอย่างลักษณะ output ตามเอกสารและพฤติกรรมมาตรฐานของเครื่องมือนี้):

```
 Performance counter stats for './target/profiling/logcount':

            265.42 msec task-clock                #    0.998 CPUs utilized
                12      context-switches          #    0.045 K/sec
                 0      cpu-migrations            #    0.000 K/sec
               412      page-faults               #    1.552 K/sec
     1,203,552,891      cycles                     #    4.534 GHz
     2,794,481,203      instructions               #    2.32  insn per cycle
       412,003,551      branches                   #    1.552 G/sec
        18,220,441      branch-misses              #    4.42% of all branches
       142,993,004      cache-references           #    0.539 G/sec
        21,448,955      cache-misses               #   15.00% of all cache-refs

       0.265912234 seconds time elapsed
```

ตัวเลขที่ควรดูเป็นอันดับแรก:

- **`instructions` / `cycles` (IPC — instructions per cycle)**: บอกว่า CPU ทำงานได้ "คุ้ม" แค่ไหนต่อรอบสัญญาณ
  นาฬิกา — IPC สูง (เข้าใกล้หรือเกิน 2-3) แปลว่า CPU ไม่ค่อยติดขัด ทำงานได้ต่อเนื่อง IPC ต่ำมาก (ใกล้ 0.5 หรือ
  น้อยกว่า) มักแปลว่าโปรแกรมติด**รอ memory** บ่อย (cache miss สูง) หรือมี branch misprediction บ่อยจนต้อง
  ยกเลิก instruction ที่ speculative ไปแล้วทิ้ง
- **`branch-misses`**: สัดส่วนที่ CPU **ทำนายผิด**ว่า if/loop จะไปทางไหน (CPU สมัยใหม่ทำนายผลของ conditional
  ล่วงหน้าเพื่อประมวลผลต่อแบบ speculative — ถ้าทำนายผิด ต้องยกเลิกงานที่ทำไปแล้วทั้งหมดแล้วเริ่มใหม่ทางที่ถูก
  ซึ่งมีต้นทุนสูง) โค้ดที่มี branch เดา่ยากมาก (เช่นเงื่อนไขที่สุ่มไม่มีรูปแบบ) จะมี branch-misses สูง
- **`cache-misses`**: สัดส่วนที่ CPU หาข้อมูลใน CPU cache ไม่เจอ ต้องไปอ่านจาก RAM ซึ่งช้ากว่า cache มากเป็น
  ร้อยเท่า — โค้ดที่เข้าถึง memory แบบสุ่ม/กระจัดกระจาย (เช่น linked list ยาว ๆ, hashmap ที่ hash กระจายทั่ว
  memory) มักมี cache-misses สูงกว่าโค้ดที่เข้าถึง memory แบบต่อเนื่อง (เช่น loop ไล่ทีละสมาชิกใน `Vec`)

**วิธีใช้ในทางปฏิบัติ**: รัน `perf stat` ก่อนเป็นอันดับแรกเพื่อ**ตั้งสมมติฐาน** — ถ้า IPC ต่ำมากพร้อม
cache-misses สูง สมมติฐานคือปัญหาอยู่ที่ **memory access pattern** (ควรไปดู memory profiling ต่อในหัวข้อ 55.7
หรือปรับ data structure ให้ cache-friendly ขึ้น) แต่ถ้า IPC ปกติดีและ cache-misses ต่ำ แต่โปรแกรมยังช้า
สมมติฐานคือปัญหาอยู่ที่**จำนวน instruction ที่มากเกินไป** (เช่น algorithm ที่ไม่มีประสิทธิภาพแบบ O(n²) ในตัวอย่าง
หัวข้อ 55.4) ซึ่งต้องไปดู `perf record`/flame graph ต่อเพื่อหาว่าฟังก์ชันไหนสร้าง instruction เยอะขนาดนั้น —
`perf stat` ช่วยให้คุณ**เลือกเครื่องมือขั้นต่อไปได้ถูกทาง**แทนที่จะเดาสุ่ม

**ปรับ event ที่จะวัดได้ด้วย `-e`**: ค่า default ของ `perf stat` (ไม่ใส่ flag เพิ่ม) จะแสดง event ที่ใช้บ่อยที่สุด
เพียงชุดหนึ่งเท่านั้น (ตามตัวอย่างข้างบน) แต่ CPU สมัยใหม่มี hardware performance counter ให้เลือกวัดได้อีกหลาย
สิบตัว — ดูรายการทั้งหมดที่ CPU ของคุณรองรับได้ด้วย:

```bash
perf list
```

แล้วเลือกวัดเฉพาะ event ที่สนใจผ่าน `-e` (คั่นด้วยจุลภาคถ้าอยากดูหลายตัวพร้อมกัน):

```bash
perf stat -e cycles,instructions,L1-dcache-load-misses,branch-misses ./target/profiling/logcount
```

วิธีนี้มีประโยชน์เมื่อคุณสงสัยปัญหาเฉพาะทาง (เช่น TLB miss สำหรับโปรแกรมที่เข้าถึง memory กระจายในพื้นที่กว้างมาก
หรือ context-switch สำหรับโปรแกรมที่ใช้ thread จำนวนมาก) และไม่ต้องการให้ output รกไปด้วย event อื่นที่ไม่เกี่ยว
ข้องกับสมมติฐานที่กำลังตรวจสอบอยู่

#### ยืนยันด้วยตัวเลขจริง: cache/branch statistics ก่อน-หลังแก้ไขโปรแกรม `logcount`

เพื่อไม่ให้หัวข้อนี้เป็นแค่ทฤษฎีล้วน ๆ ลองดูตัวเลข cache/branch ระดับ hardware counter จริงของโปรแกรม `logcount`
จากหัวข้อ 55.4/55.10 ทั้งสองเวอร์ชัน — เนื่องจาก `perf stat` ใช้งานไม่ได้ในเครื่องที่เตรียมบทนี้ (เหตุผลเดียวกับ
หัวข้อ 55.3/55.4) จึงใช้ `valgrind --tool=cachegrind --cache-sim=yes --branch-sim=yes` แทน — คนละเครื่องมือกับ
`perf stat` แต่วัด**แนวคิดเดียวกัน** (จำลอง cache/branch predictor ของ CPU แทนที่จะอ่านจาก hardware counter จริง
เหมือน `perf stat`) ทำให้ได้ตัวเลขที่เทียบเคียงกันได้ในเชิงสัดส่วน แม้ตัวเลขดิบจะไม่ได้มาจาก hardware counter
ตัวจริงเป๊ะ ๆ:

```bash
valgrind --tool=cachegrind --cache-sim=yes --branch-sim=yes ./target/profiling/logcount
```

**ก่อนแก้ (Vec linear search, O(n²)):**

```
D refs:          786,777,678  (704,803,818 rd   + 81,973,860 wr)
D1  misses:       90,060,270  ( 89,881,244 rd   +    179,026 wr)
D1  miss rate:          11.4% (       12.8%     +        0.2%  )

Branches:        712,442,512  (637,766,904 cond +  74,675,608 ind)
Mispredicts:       6,890,321  (  6,769,963 cond +    120,358 ind)
Mispred rate:            1.0% (        1.1%     +        0.2%   )
```

**หลังแก้ (HashMap):**

```
D refs:           31,754,514  ( 19,277,141 rd   + 12,477,373 wr)
D1  misses:          478,379  (    348,710 rd   +    129,669 wr)
D1  miss rate:           1.5% (        1.8%     +        1.0%  )

Branches:         12,915,067  ( 11,509,525 cond +  1,405,542 ind)
Mispredicts:          81,126  (     80,766 cond +        360 ind)
Mispred rate:            0.6% (        0.7%     +        0.0%   )
```

สองตัวเลขที่สำคัญที่สุดในการเทียบนี้:

- **D1 miss rate ลดลงจาก 11.4% เหลือ 1.5%** — ก่อนแก้ ทุก ๆ 100 ครั้งที่โปรแกรมอ่าน/เขียน memory มีถึง ~11 ครั้ง
  ที่ CPU หาข้อมูลใน L1 data cache ไม่เจอ ต้องไปดึงจาก cache ระดับที่ไกลกว่า (L2/L3/RAM) ซึ่งช้ากว่ามาก — สาเหตุ
  ตรงไปตรงมา: `Vec<(String, u64)>` เก็บ `String` แต่ละตัวเป็น pointer แยกไปยัง heap คนละตำแหน่งที่กระจัดกระจาย
  กันไปทั่ว memory (Part 6/13 อธิบายไว้ว่า `String` คือ pointer + length + capacity ที่ชี้ไปยัง heap แยกต่างหาก
  จากตัว struct เอง) ทุกครั้งที่ linear search เดินไล่ทีละ entry เพื่อเทียบ string มันต้อง **dereference
  pointer ไปยัง heap คนละที่กันในแต่ละรอบ** ซึ่งแทบไม่มีทางอยู่ใน cache line เดียวกันได้เลยเมื่อ entries มีเป็น
  พัน ๆ ตัว — นี่คือสิ่งที่เรียกว่า **cache-unfriendly memory layout** ที่หัวข้อ 55.7 (memory profiling) จะพูดถึง
  ต่อในมุมของปริมาณ allocation หลังแก้เป็น `HashMap` แล้ว การ lookup ยังต้อง dereference pointer ไปยัง heap
  เหมือนกัน แต่**จำนวนครั้งที่ต้องทำน้อยลงมหาศาล** (O(1) เฉลี่ยต่อครั้ง ไม่ใช่ O(n)) ทำให้ D1 miss rate ลดลงตาม
- **Branch mispredict rate ลดลงจาก 1.0% เหลือ 0.6%** — แม้จะดูเป็นตัวเลขเล็ก ๆ แต่จำนวน mispredict จริงลดลงจาก
  6,890,321 เหลือ 81,126 ครั้ง (ลดลง ~85 เท่า) เพราะ linear search มี branch (`if entry.0 == user_id`) ที่ถูก
  ประเมินซ้ำ ๆ นับล้านครั้งต่อการ insert หนึ่งครั้ง ในขณะที่ `HashMap` มี branch ที่เกี่ยวข้องกับการค้นหาน้อยกว่า
  มากต่อการ insert หนึ่งครั้ง

ตัวเลขเหล่านี้ยืนยันสิ่งที่หัวข้อ 55.4/55.10 พบด้วย `callgrind` (การนับ instruction ล้วน ๆ) จากอีกมุมมองหนึ่ง —
ไม่ใช่แค่ "instruction น้อยลง" แต่ยัง **"CPU ทำงานได้อย่างมีประสิทธิภาพต่อ instruction มากขึ้นด้วย"** (เพราะรอ
memory น้อยลง, เดา branch ผิดน้อยลง) ทั้งสองปัจจัยรวมกันคือเหตุผลที่ wall time เร็วขึ้นถึง 20.4 เท่า ทั้งที่
instruction count ลดลงแค่ ~30.9 เท่า (ถ้า CPU ทำงานได้ efficiency เท่ากันทั้งก่อนและหลัง ตัวเลขทั้งสองควรจะใกล้
เคียงกันมากกว่านี้ — ความต่างเล็กน้อยที่เห็นสะท้อนว่าประสิทธิภาพต่อ instruction เปลี่ยนไปด้วยเช่นกัน ไม่ใช่แค่
จำนวน instruction ที่เปลี่ยน)

### 55.7 Memory Profiling: เมื่อ CPU profiler เพียงอย่างเดียวไม่พอ

ทุกเครื่องมือที่พูดถึงมาจนถึงตอนนี้ (`perf`, `callgrind`, flame graph) วัด**เวลา/instruction ของ CPU** เป็นหลัก
แต่มีปัญหาด้าน performance อีกประเภทหนึ่งที่ CPU profiler อาจ**มองไม่เห็นชัดเจน**เลย — ปัญหาจาก **การ allocate
memory มากเกินไป** Part 6 และ Part 13 อธิบายไว้แล้วว่า heap allocation มีต้นทุนสูงกว่าการใช้ค่าบน stack เพราะต้อง
ผ่าน allocator ค้นหาพื้นที่ว่าง แต่ปัญหาที่ลึกไปกว่านั้นคือ **allocation ที่มากเกินไปทำให้ memory layout กระจัดกระจาย
(cache-unfriendly)** ซึ่งสร้างผลเสียทางอ้อมที่ตรวจจับยาก — โปรแกรมอาจใช้เวลาส่วนใหญ่ไปกับการ**รอ RAM** (คือ
cache miss ที่หัวข้อ 55.6 พูดถึง) แทนที่จะ "ทำงาน" จริง ๆ ซึ่ง CPU profiler แบบ sampling ทั่วไปจะเห็นแค่ว่า
"เวลาไปอยู่ที่ตรงนี้" โดยไม่บอกตรง ๆ ว่า "เพราะกำลังรอ memory" — ต้องใช้เครื่องมือเฉพาะทางที่ติดตาม**การเรียก
allocator โดยตรง**ถึงจะเห็นภาพนี้ชัดเจน

#### `valgrind --tool=massif`: heap profiler ที่ติดตามทุก allocation

`massif` คือ tool อีกตัวของ Valgrind ที่**ไม่สนใจเวลา CPU เลย** แต่ติดตาม**ทุกครั้ง**ที่โปรแกรมเรียก
allocator (`malloc`/`free` ที่ Rust's global allocator เรียกใช้ภายใน) แล้วสร้างกราฟแสดง**ขนาด heap ที่ใช้อยู่
ตามเวลา** พร้อม**call stack ของจุดที่ allocate** สำหรับช่วงที่ heap โตสูงสุด (peak)

รันกับ binary ตัวเดียวกันจากหัวข้อ 55.4 (เวอร์ชันที่แก้ไขแล้วด้วย `HashMap`, รายละเอียดการแก้อยู่ในหัวข้อ 55.10):

```bash
valgrind --tool=massif --massif-out-file=massif.out ./target/profiling/logcount
ms_print massif.out
```

ผลลัพธ์จริง (กราฟ ASCII แสดงขนาด heap ตามเวลา — แกน Y คือขนาด memory เป็น MB, แกน X คือเวลา):

```

8.011^                                                                     #
     |                                      @::::::::::::@::::@:::::@::::@:#
     |                                  ::::@::::::: ::::@::::@:::::@::::@:#
     |                     ... (ทรงกราฟไต่ขึ้นเรื่อย ๆ ตามจำนวน user ที่เพิ่มเข้ามา) ...
   0 +----------------------------------------------------------------------->Mi
     0                                                                   67.05

Number of snapshots: 93
 Detailed snapshots: [14, 20, 38, 53, 63, 73, 83, 87 (peak)]
```

heap โตขึ้นเรื่อย ๆ แบบขั้นบันไดตลอดการรันจนถึง**จุดสูงสุด (peak) ที่ snapshot #87** ซึ่ง `ms_print` แสดง call
stack ของจุดนั้นให้ดูละเอียด:


Heap สูงสุดที่ใช้จริงคือ **8,399,992 bytes (~8.4 MB)** และ **60% ของ heap ณ จุดสูงสุด (5,040,000 bytes)** ถูก
สืบไปได้ตรง ๆ ถึงบรรทัด `format!("user_id=user{uid} ...")` ใน `generate_log_lines` — นี่คือข้อมูลที่ **CPU
profiler บอกไม่ได้ตรง ๆ**: ในผล `callgrind_annotate` ของหัวข้อ 55.4/55.10 ฟังก์ชัน `generate_log_lines` และ
`format!` ไม่ได้ติดอันดับ hot function เลย (เพราะการ format string ใช้ instruction ไม่มากเมื่อเทียบกับการ
เปรียบเทียบ string ใน linear search) แต่จากมุมมองของ**การใช้ heap memory** มันคือแหล่ง allocation ที่ใหญ่ที่สุด
ในโปรแกรมทั้งตัว — **นี่คือตัวอย่างที่ชัดเจนที่สุดว่าทำไม CPU profiling อย่างเดียวไม่พอ**: ปัญหาสองประเภทนี้
(CPU time กับ memory pressure) เป็นมิติที่ต่างกัน ฟังก์ชันที่กิน CPU time มากไม่จำเป็นต้องเป็นฟังก์ชันที่กิน
memory มากที่สุด และในทางกลับกัน โปรแกรมที่ allocate มากเกินไปอาจทำให้ทั้งระบบช้าลงทางอ้อมผ่าน cache pressure
โดยที่ CPU profiler มองเห็นแค่ "เวลากระจายไปทั่ว ๆ" อย่างคลุมเครือ ไม่มีฟังก์ชันเดียวที่โดดเด่นให้เห็นชัดแบบใน
หัวข้อ 55.4

#### `dhat`: ทางเลือกอื่นที่เน้นนับจำนวนครั้งของ allocation

`dhat` (Dynamic Heap Analysis Tool, มาเป็นอีก tool หนึ่งใน Valgrind หรือใช้ผ่าน crate `dhat-rs` แบบฝัง instrument
ในโค้ด Rust โดยตรง) เน้นตอบคำถามที่ต่างจาก massif เล็กน้อย — แทนที่จะโฟกัสที่ "ขนาด heap ตามเวลา" มันโฟกัสที่
**"จำนวนครั้งที่ allocate/deallocate เกิดขึ้น"** และ **"อายุเฉลี่ยของแต่ละ allocation"** ซึ่งมีประโยชน์มากสำหรับ
จับปัญหาแบบ "allocate เล็ก ๆ ซ้ำ ๆ นับล้านครั้งในลูป" (เช่นการเรียก `.to_string()`/`.clone()` ในลูปที่รันบ่อย
มาก) แม้แต่ละครั้งจะเล็กจนไม่กระทบขนาด heap สูงสุดเลย แต่จำนวนครั้งที่มากมายนั้นเองที่กิน CPU time ไปกับการเรียก
allocator ซ้ำ ๆ — สำหรับ Rust โดยเฉพาะ ใช้ crate `dhat-rs` ฝัง global allocator ของตัวเองเข้าไปในโปรแกรมได้ตรง ๆ:

```toml
[dependencies]
dhat = "0.3"
```

```rust
#[cfg(feature = "dhat-heap")]
#[global_allocator]
static ALLOC: dhat::Alloc = dhat::Alloc;

fn main() {
    #[cfg(feature = "dhat-heap")]
    let _profiler = dhat::Profiler::new_heap();

    // ... โค้ดโปรแกรมตามปกติ ...
}
```

เมื่อรันโปรแกรมที่ compile ด้วย feature `dhat-heap` เปิดไว้ มันจะสร้างไฟล์ `dhat-heap.json` ที่เปิดดูผ่านเว็บ
viewer ของ DHAT ได้ แสดงรายการ allocation ที่กินพื้นที่/จำนวนครั้งมากที่สุด พร้อม call stack — จุดสำคัญที่ต้อง
รู้คือ `dhat-rs` ทำงานโดย**แทนที่ global allocator ของโปรแกรมทั้งหมด** ดังนั้นต้อง build แยกด้วย feature flag
เฉพาะสำหรับ profiling session ไม่ควรเปิดไว้ใน production build ปกติ (คล้ายกับที่ profile `profiling` แยกจาก
`release` ใน Part 35 — เครื่องมือ profiling มักต้องการ build แยกเฉพาะของตัวเอง)

**ระดับความรู้ที่ต้องมีในบทนี้**: memory profiling เป็นหัวข้อที่ลึกพอจะเขียนเป็นบทแยกได้ทั้งบท เป้าหมายของหัวข้อ
นี้คือให้คุณ**ตระหนัก (awareness)** ว่าเครื่องมือแบบนี้มีอยู่และรู้ว่าใช้เมื่อไร (เมื่อสงสัยว่าปัญหาไม่ได้อยู่ที่
CPU time ตรง ๆ แต่อยู่ที่ปริมาณ/ความถี่ของ allocation) ไม่จำเป็นต้องจำรายละเอียดทุก flag ของ `massif`/`dhat` ได้
ทั้งหมด — เมื่อถึงจุดที่ต้องใช้จริง กลับมาอ่านเอกสารของเครื่องมือแต่ละตัวเพิ่มได้เสมอ

### 55.8 Miri ไม่ใช่ profiler: แยกให้ชัดระหว่างเครื่องมือ correctness กับ performance

Part 41 หัวข้อ 41.11 แนะนำ **Miri** ในฐานะเครื่องมือตรวจจับ **undefined behavior (UB)** — มันตีความโปรแกรม Rust
ผ่าน MIR (Mid-level Intermediate Representation) พร้อมโมเดลความหมายของภาษาที่เข้มงวด เพื่อจับบั๊กประเภท use
of uninitialized memory, invalid pointer dereference, การละเมิดกฎ aliasing ของ reference ฯลฯ ที่ compiler
ปกติตรวจจับไม่ได้ทั้งหมด

**ข้อควรระวังสำคัญที่นักเรียนสับสนกันบ่อย**: Miri **ไม่ใช่และไม่มีทางเป็น profiler ได้เลย** แม้จะ "รันโปรแกรม
แบบต่างออกไป" เหมือนกับเครื่องมืออื่น ๆ ในบทนี้ก็ตาม — เหตุผลเชิงเทคนิคคือ Miri **interpret** โปรแกรมทีละ MIR
statement (ไม่ compile เป็น native machine code เลย) ทำให้**ความเร็วสัมพัทธ์ระหว่างส่วนต่าง ๆ ของโปรแกรมภายใต้
Miri ไม่มีความสัมพันธ์ใด ๆ กับความเร็วจริงตอนรันแบบ native** — ฟังก์ชันที่ Miri ใช้เวลานานอาจไม่ใช่ฟังก์ชันที่ช้า
จริงเลยตอน compile ปกติด้วย `rustc` (และในทางกลับกัน) เพราะ interpreter overhead ของ Miri ไม่ scale ตาม
ลักษณะงานแบบเดียวกับที่ native code ทำ (เช่น Miri อาจมี overhead สูงมากเป็นพิเศษกับโค้ดที่ใช้ pointer arithmetic
เข้มข้น เพราะต้องตรวจสอบ aliasing rule ทุกครั้ง ในขณะที่ native code ทำ pointer arithmetic แบบนั้นได้ในไม่กี่
cycle)

ตารางสรุปให้เห็นชัดว่าเครื่องมือทั้งสองประเภทตอบคำถามคนละแบบ:

| | Miri (Part 41) | Profiler (บทนี้) |
|---|---|---|
| ตอบคำถาม | "โค้ดนี้มี undefined behavior ซ่อนอยู่หรือไม่" | "เวลา/memory ไปอยู่ที่ไหนตอนรันจริง" |
| วิธีทำงาน | interpret MIR พร้อมตรวจสอบ semantic rule เข้มงวด | รันโค้ดที่ compile จริง แล้ววัดเวลา/นับ instruction/allocation |
| ความเร็วที่รายงาน | **ไม่มีความหมายเชิง performance เลย** (ช้ากว่า native มาก เพราะเป็น interpreter) | สะท้อนความเร็วจริง (หรือใกล้เคียงจริงมากที่สุดเท่าที่ overhead ของเครื่องมือจะเอื้อ) |
| ใช้ตอนไหน | ระหว่างพัฒนา/ก่อน merge โค้ดที่มี `unsafe` | เมื่อสงสัยว่าโปรแกรมช้า และต้องหาว่าช้าตรงไหน |

**กฎง่าย ๆ ที่จำไว้**: ถ้าคำถามคือ "โค้ดนี้ปลอดภัยไหม (ไม่มี UB)" ให้ใช้ Miri — ถ้าคำถามคือ "โค้ดนี้เร็วพอไหม/ช้า
ตรงไหน" ให้ใช้เครื่องมือจากบทนี้ (`perf`, `callgrind`, flame graph, `massif`) **ห้ามเอาเวลาที่ Miri รายงาน (ถ้า
มันรายงานเวลาออกมาด้วยตอน verbose) มาสรุปเรื่อง performance โดยเด็ดขาด** เพราะมันสะท้อนความช้าของ interpreter
เอง ไม่ใช่ความช้าของ logic ในโปรแกรมของคุณ

### 55.9 อ่านผล Profiler อย่างมีวิจารณญาณ: กับดักเชิงสิ่งแวดล้อมที่ทำให้ตัวเลขโกหกได้

การได้ตัวเลขจาก profiler มาไม่ได้แปลว่าคุณมี "ความจริง" อยู่ในมือทันที — ตัวเลขที่ได้อาจสะท้อนความจริงที่**ผิด
บริบท** ถ้าคุณไม่ระวังเงื่อนไขของการวัด สามหัวข้อย่อยนี้คือกับดักเชิงการตีความที่พบบ่อยที่สุด

#### อันตรายของการ profile debug build

Part 35 อธิบายไว้แล้วว่า debug build (`opt-level = 0`, `debug-assertions = true`, `overflow-checks = true`)
ต่างจาก release build อย่างมาก — และความต่างนี้**ไม่ใช่แค่ "ช้าลงเท่า ๆ กันทุกจุด"** แต่ **ช้าลงไม่เท่ากันในแต่
ละฟังก์ชัน** ขึ้นกับว่าฟังก์ชันนั้นได้ประโยชน์จาก inlining/vectorization/dead-code-elimination มากแค่ไหนตอน
optimize — ผลคือ **สัดส่วนเวลาที่แต่ละฟังก์ชันกินไปในโปรไฟล์ของ debug build อาจไม่ตรงกับสัดส่วนจริงใน release
build เลย**

พิสูจน์ด้วยตัวเลขจริงจากโปรแกรม `logcount` ในหัวข้อ 55.4 (เวอร์ชัน "ก่อนแก้" ที่ยังมี O(n²)):

```bash
cargo build                          # dev profile (debug build ปกติ)
cargo build --profile profiling      # profiling profile (optimize เท่า release)

time ./target/debug/logcount
time ./target/profiling/logcount
```

```
# dev profile (opt-level = 0, debug-assertions = true)
real    0m1.254s
user    0m1.229s

# profiling profile (opt-level = 3, เหมือน release)
real    0m0.265s
user    0m0.263s
```

debug build ช้ากว่า release/profiling build ถึง **~4.7 เท่า** สำหรับโปรแกรมตัวเดียวกัน — ถ้าคุณ profile
debug build แล้วเห็นว่าฟังก์ชัน A กิน 40% ของเวลา คุณ**ไม่สามารถสรุปได้เลย**ว่าฟังก์ชัน A จะยังกิน 40% เท่ากัน
ใน release build จริง เพราะ optimizer อาจ inline/vectorize ฟังก์ชัน A ได้ดีเป็นพิเศษ (ทำให้สัดส่วนลดลงมากใน
release) หรืออาจ optimize ได้แย่กว่าฟังก์ชันอื่น (ทำให้สัดส่วนเพิ่มขึ้นสัมพัทธ์ใน release) — **ทางเดียวที่จะรู้
สัดส่วนจริงคือ profile release build (หรือ custom profile ที่ inherit จาก release อย่าง `profiling`) เท่านั้น**
debug build มีประโยชน์แค่ตอนหา correctness bug (มี debug-assertions/overflow-checks ช่วยจับบั๊กเร็ว) แต่ไม่มี
ประโยชน์เลยสำหรับการหา performance bottleneck ที่สะท้อนความเป็นจริง

#### อันตรายของการ profile บนเครื่อง/environment ที่ไม่เหมือน production

แม้จะ profile release build ที่ถูกต้องแล้วก็ตาม ตัวเลขที่ได้ยังผูกกับ**เครื่องที่ใช้รัน**อย่างมาก — ปัจจัยที่ทำ
ให้ผลต่างกันได้ระหว่างเครื่อง development กับเครื่อง production จริง:

- **จำนวน/รุ่นของ CPU core และขนาด cache**: เครื่อง laptop นักพัฒนามักมี cache ต่อ core เยอะกว่า server บาง
  ประเภท (โดยเฉพาะ cloud VM ราคาถูกที่แบ่ง core กันหลาย tenant) โปรแกรมที่ cache-friendly บน laptop อาจมี
  cache-miss สูงกว่ามากบน production server ที่ cache ต่อ core น้อยกว่าหรือถูกแบ่งกับ process อื่น
- **CPU frequency scaling / thermal throttling**: เครื่อง cloud VM มักจำกัด CPU frequency ไว้คงที่เพื่อความ
  predictable ในขณะที่เครื่อง development อาจ boost frequency สูงขึ้นชั่วขณะ ทำให้เวลาที่วัดได้ต่างกันโดยไม่
  เกี่ยวกับโค้ดเลย
- **Container/VM overhead**: production ที่รันใน container (Docker, Kubernetes) มี overhead จาก cgroup/
  namespace ที่เครื่อง development แบบ bare-metal ไม่มี — และอย่างที่หัวข้อ 55.3 พูดถึง container บางประเภทอาจ
  บล็อกการเข้าถึง `perf_event_open()` ไปเลย ทำให้ profile ตรงบน production container ไม่ได้จริง ต้อง profile
  บนเครื่อง staging ที่ config ใกล้เคียงที่สุดแทน
- **ข้อมูล/รูปแบบ traffic ที่แตกต่างกัน**: ข้อมูลทดสอบที่ใช้ตอน profile (เช่น log สังเคราะห์ 60,000 บรรทัดใน
  หัวข้อ 55.4) อาจมีรูปแบบต่างจาก traffic จริงมาก (เช่น production อาจมี unique user นับล้านคน ไม่ใช่แค่ 4,000
  คน ทำให้ผลกระทบของ O(n²) รุนแรงกว่าที่ทดสอบมากในสัดส่วนที่ไม่เป็นเส้นตรงด้วยซ้ำ)

**หลักการปฏิบัติ**: profile บนเครื่อง development ยังมีประโยชน์เสมอสำหรับหา bottleneck เชิง**อัลกอริทึม**
(เช่น O(n²) ที่หัวข้อ 55.4 เจอ — ปัญหานี้จะแย่ลงเรื่อย ๆ ไม่ว่าเครื่องไหนก็ตาม เพราะเป็นปัญหาเชิงคณิตศาสตร์ ไม่
ใช่เชิง hardware) แต่สำหรับการ**ยืนยันตัวเลขที่แน่นอน** (เช่น "การแก้นี้จะทำให้ production เร็วขึ้นกี่ % จริง")
ควร profile บนเครื่องที่ config ใกล้เคียง production ที่สุดเท่าที่ทำได้ และถ้าเป็นไปได้ ควร profile ด้วยข้อมูล
ที่มีขนาด/ลักษณะใกล้เคียงของจริงด้วย ไม่ใช่แค่ข้อมูลทดสอบขนาดเล็ก

#### หลักการที่สำคัญที่สุด: Profiler บอก "ที่ไหน" แต่ไม่บอก "ควรทำอะไร"

ต่อให้ profiler ชี้ตรงไปยังฟังก์ชันที่กินเวลามากที่สุดได้อย่างแม่นยำ 100% มันก็**ไม่ได้บอกคุณว่าควรแก้อย่างไร**
— นั่นยังคงเป็นงานของวิศวกรที่ต้องใช้ความเข้าใจ domain/algorithm ตัดสินใจ ในตัวอย่างหัวข้อ 55.4 profiler บอกแค่ว่า
"string comparison กินเวลา 92%" — มันไม่ได้บอกว่า "ให้ใช้ `HashMap`" คุณต้องรู้เอง (จาก Part 15) ว่า linear
search ที่มี key เป็น string ควรแทนที่ด้วย hash-based lookup — profiler ทำหน้าที่แค่**ลดพื้นที่การค้นหา**จาก
"ทั้งโปรแกรม" ลงมาเหลือ "ฟังก์ชันนี้เท่านั้น" ส่วนที่เหลือ (การเลือกวิธีแก้ที่ถูกต้อง และการยืนยันด้วย benchmark
ตาม Part 54) ยังเป็นความรับผิดชอบของคุณเสมอ

### 55.10 ทดลองจริง (2): แก้บั๊ก แล้ว profile ซ้ำเพื่อพิสูจน์ว่าแก้ถูกจุดจริง

ถึงขั้นตอนสุดท้ายของ workflow — นำ bottleneck ที่พบในหัวข้อ 55.4 (linear search แบบ O(n²) ใน `Counter::record`)
มาแก้ด้วย `HashMap` (Part 15) แล้ว profile ซ้ำเพื่อพิสูจน์ด้วยตัวเลขจริงว่าการแก้นี้ได้ผลจริง ไม่ใช่แค่ "รู้สึกว่า
เร็วขึ้น"

#### แก้โค้ด

```rust
use std::collections::HashMap;

struct Counter {
    // แก้แล้ว: ใช้ HashMap เพื่อให้ record() เป็น O(1) โดยเฉลี่ย แทน linear scan O(n)
    entries: HashMap<String, u64>,
}

impl Counter {
    fn new() -> Self {
        Counter { entries: HashMap::new() }
    }

    fn record(&mut self, user_id: &str) {
        // entry API: หาแล้วเพิ่มค่าในครั้งเดียว ไม่ต้อง scan ทั้ง map เอง
        // (Part 15 อธิบาย entry API นี้ไว้แล้วว่าหลีกเลี่ยง double-lookup)
        *self.entries.entry(user_id.to_string()).or_insert(0) += 1;
    }

    fn total_unique(&self) -> usize {
        self.entries.len()
    }

    fn top_n(&self, n: usize) -> Vec<(String, u64)> {
        let mut sorted: Vec<(String, u64)> =
            self.entries.iter().map(|(k, v)| (k.clone(), *v)).collect();
        sorted.sort_by(|a, b| b.1.cmp(&a.1));
        sorted.into_iter().take(n).collect()
    }
}
```

ส่วนที่เหลือของโปรแกรม (`generate_log_lines`, `extract_user_id`, `main`) **ไม่ต้องแก้อะไรเลย** — นี่คือจุดสำคัญ
ที่ profiling ช่วยไว้: มันชี้ตรงไปที่ `Counter` เท่านั้น ไม่ต้องเสียเวลาไปแก้ส่วนอื่นที่ไม่ใช่ bottleneck จริง

การณ์ได้: wall time ยังมี overhead อื่นที่ไม่ใช่ instruction execution ล้วน ๆ ปนอยู่ (เช่น เวลาที่ OS ใช้ schedule

ไม่มี noise จากปัจจัยภายนอกเลย — **ทั้งสองตัวเลขยืนยันไปในทางเดียวกันอย่างชัดเจน**: การแก้ไขนี้ได้ผลจริง ไม่ใช่
ภาพลวงตาจากการวัดเวลาผิดพลาด

โปรไฟล์ใหม่ **"แบนลง" อย่างเห็นได้ชัด** — ไม่มีฟังก์ชันไหนกินเกิน 11% เลย เทียบกับก่อนแก้ที่ฟังก์ชันเดียวกิน
57.87% นี่คือรูปแบบปกติที่เกิดขึ้นเมื่อคุณแก้ bottleneck ตัวใหญ่ที่สุดสำเร็จ: เวลาที่เหลือกระจายไปยังงาน "พื้น
ฐาน" ที่หลีกเลี่ยงไม่ได้ของโปรแกรม (การ allocate memory ผ่าน `malloc`/`free`, การคำนวณ hash ด้วย SipHash ที่
Rust's `HashMap` ใช้เป็น default, การ format ตัวเลขเป็น string) — ไม่มีจุดเดียวที่โดดเด่นให้ "แก้ต่อได้ง่าย ๆ"
อีกแล้ว ถ้าอยากเร็วขึ้นกว่านี้ต้องเจาะลงไปที่รายละเอียดเล็กลงเรื่อย ๆ (เช่น เปลี่ยนไปใช้ hasher ที่เร็วกว่า
SipHash สำหรับกรณีที่ไม่ต้องการความปลอดภัยจาก hash-flooding attack, หรือลด allocation ของ `String` ที่ไม่จำเป็น
ใน `to_string()`) — งานแบบนี้คือสิ่งที่ **Part 54's `criterion`** เหมาะจะเข้ามาเทียบ candidate ทีละตัวต่อไป
เพราะความต่างที่เหลือเล็กลงมากจนต้องวัดด้วยความละเอียดสูงกว่าการจับเวลาแบบ `time` ธรรมดา

ข้อสังเกตเพิ่มเติมที่เชื่อมกับหัวข้อ 55.7: สัดส่วนของ `malloc`/`free`/`_int_malloc`/`_int_free` รวมกันตอนนี้อยู่
ที่ประมาณ **10.44% + 9.00% + 5.97% + 3.85% = 29.26%** ของ instruction ทั้งหมด — เกือบ 1 ใน 3 ของงานที่โปรแกรม
ทำตอนนี้คือการ allocate/deallocate memory ล้วน ๆ นี่คือสัญญาณที่ชัดเจนว่าถ้าจะ optimize รอบต่อไป จุดที่ควรมองคือ
การลด allocation (เช่น เปลี่ยน `user_id.to_string()` ให้ allocate เฉพาะตอนที่ key ยังไม่มีอยู่จริง ๆ แทนที่จะ
allocate ทุกครั้งที่เรียก `record()` แล้วปล่อยทิ้งถ้า key มีอยู่แล้ว) ซึ่งเป็นโจทย์ที่ปล่อยให้ลองในแบบฝึกหัดข้อ 2

**สรุปผลการทดลองทั้งวงจร**: จากสมมติฐานตอนต้น ("โปรแกรมช้า ไม่รู้ว่าช้าตรงไหน") → profile ด้วย `callgrind` พบว่า
92%+ ของงานอยู่ที่ string comparison ใน linear search → เปลี่ยนเป็น `HashMap` ตาม Part 15 → profile ซ้ำพิสูจน์
ว่า wall time เร็วขึ้น 20.4 เท่า, instruction count ลดลง 30.9 เท่า, และ hot function ตัวเดิมหายไปจาก top list
โดยสิ้นเชิง — นี่คือ workflow แบบเดียวกันที่คุณจะใช้ซ้ำได้กับโปรแกรมจริงทุกขนาด ไม่ว่าจะใหญ่หรือซับซ้อนแค่ไหน

### 55.11 เปรียบเทียบกับเครื่องมือ profiling ในภาษาอื่น

หลักการของ profiling (sampling vs instrumenting, การอ่าน call stack, flame graph) เป็นแนวคิดที่**ข้ามภาษา**ได้
เกือบทั้งหมด — ถ้าคุณเคย profile โปรแกรมในภาษาอื่นมาก่อน แนวคิดที่เรียนในบทนี้จะถ่ายโอนไปใช้ได้ทันที เพียงแค่
เปลี่ยนชื่อเครื่องมือ

#### Python: `cProfile` (instrumenting) และ `py-spy` (sampling)

Python มีเครื่องมือ profiling มาตรฐานในตัวชื่อ `cProfile` ซึ่งเป็น **instrumenting profiler** (เหมือน
`callgrind` ในบทนี้) — มันแทรก hook เข้าไปที่ทุกการเรียกฟังก์ชันผ่าน Python interpreter เอง (`sys.setprofile`)
ทำให้ได้ตัวเลขจำนวนครั้งที่เรียกและเวลารวมของแต่ละฟังก์ชันแบบแม่นยำ แต่มี overhead สูงมากเมื่อโปรแกรมเรียก
ฟังก์ชันเล็ก ๆ ถี่มาก (คล้ายกับที่ `callgrind` ทำให้โปรแกรมช้าลง 20-100 เท่าในบทนี้):

```bash
python -m cProfile -s cumulative my_script.py
```

ในทางกลับกัน `py-spy` เป็น **sampling profiler** สำหรับ Python โดยเฉพาะ (เขียนด้วย Rust!) ที่ attach เข้าไปยัง
process Python ที่กำลังรันอยู่จากภายนอก แล้ว sample call stack เป็นระยะแบบเดียวกับ `perf` — ข้อดีคือ overhead
ต่ำมากจนใช้ profile production ตรง ๆ ได้โดยไม่ต้องแก้โค้ดหรือ restart โปรแกรมเลย:

```bash
py-spy record -o profile.svg --pid 12345    # สร้าง flame graph ตรง ๆ จาก process ที่รันอยู่
```

สังเกตว่า `py-spy` สร้าง**flame graph โดยตรง** เหมือนกับ `cargo flamegraph` ในบทนี้ทุกประการในเชิงแนวคิด — sample
call stack เป็นระยะ แล้ววาดเป็นภาพที่ความกว้าง = สัดส่วนเวลา

#### Go: `pprof`

Go มี profiling framework ในตัวชื่อ `pprof` ที่ผนวกเข้ากับ runtime โดยตรง — โปรแกรม Go เปิด HTTP endpoint
(`net/http/pprof`) ที่ให้ดึงข้อมูล CPU profile สด ๆ จาก process ที่กำลังรันอยู่ได้ (สถานการณ์นี้ใกล้เคียงกับการ
profile production server ที่หัวข้อ 55.9 พูดถึง — Go ทำให้ทำได้ง่ายกว่า Rust ตรงจุดนี้เพราะ built-in มาให้เลย):

```go
import _ "net/http/pprof"
// เปิด HTTP server ที่ endpoint /debug/pprof/ ให้ดึงข้อมูลได้
```

```bash
go tool pprof http://localhost:6060/debug/pprof/profile?seconds=30
```

`pprof` ใช้หลักการ **sampling** เหมือน `perf` (interrupt เป็นระยะ, sample call stack) และมีคำสั่ง `web` ที่สร้าง
graph วิเคราะห์คล้าย flame graph ได้ทันที — ระบบนิเวศ Go จึงมีข้อได้เปรียบเรื่อง**ความง่ายในการ setup** เพราะ
tooling ผนวกเข้ากับ standard library โดยตรง ในขณะที่ Rust ต้องพึ่งเครื่องมือระดับ OS (`perf`) ที่อยู่ภายนอก
ecosystem ของภาษาเอง (ตามที่อธิบายไว้ในหัวข้อ 55.2 — Rust ไม่ได้สร้าง sampling profiler ของตัวเอง)

#### Node.js/JavaScript: `--prof` และ Chrome DevTools

Node.js มีแฟล็ก `--prof` ที่สั่งให้ V8 engine (JavaScript engine ที่ Node.js ใช้) เก็บ log การทำงานภายในไว้
(sampling-based เช่นกัน) แล้วประมวลผลด้วย `node --prof-process`:

```bash
node --prof my_script.js
node --prof-process isolate-*.log > processed.txt
```

หรือใช้ Chrome DevTools's "Performance" tab attach เข้ากับ Node.js process ผ่าน `--inspect` เพื่อดู flame chart
แบบ interactive ในเบราว์เซอร์โดยตรง — แนวคิดเรื่อง flame chart ของ Chrome DevTools นี้แทบจะเหมือนกับ flame graph
ของ `cargo flamegraph` ทุกประการ (แกน Y คือความลึกของ call stack, แกน X คือเวลา) เพียงแต่ Chrome DevTools มี
"call chart" อีกแบบที่**แกน X เป็น timeline จริง**ควบคู่ไปด้วย (ต่างจาก flame graph แบบมาตรฐานที่แกน X ไม่ใช่
timeline อย่างที่อธิบายไว้ในหัวข้อ 55.5) — ต้องดูให้ดีว่ากำลังอ่านภาพแบบไหนอยู่ก่อนตีความ

#### สิ่งที่เหมือนกันข้ามทุกภาษา

ไม่ว่าจะเป็นภาษาไหน หลักการ 3 ข้อจากบทนี้ใช้ได้เสมอ: (1) **sampling profiler มี overhead ต่ำกว่า instrumenting
profiler เสมอ แลกกับความแม่นยำทางสถิติที่ต่ำกว่าเล็กน้อย**, (2) **ต้องมี debug/symbol information ให้ profiler
อ่านชื่อฟังก์ชันได้ ไม่ว่าภาษาไหนก็ตาม** (Python ต้องรันโค้ดต้นฉบับจริงไม่ใช่ bytecode ที่ strip comment/ชื่อออก,
Go ต้อง compile โดยไม่ปิด symbol table, JavaScript ที่ผ่าน minifier/bundler ต้องมี source map ให้ DevTools แปลง
ตำแหน่งกลับไปยังโค้ดต้นฉบับ — concept เดียวกับ `debug = true` ของ Rust ทุกประการ), และ (3) **profiling ควรมาก่อน
การเดา optimize เสมอ ไม่ว่าเขียนโปรแกรมด้วยภาษาอะไร** — นี่คือหลักการที่ข้ามภาษาได้อย่างสมบูรณ์ เพราะมันไม่ใช่
เรื่องของ syntax แต่เป็นเรื่องของ**วิธีคิดเชิงวิศวกรรม**

## กับดักที่พบบ่อย (Common Pitfalls)

**1. Profile debug build แล้วเข้าใจผิดว่าเจอ bottleneck ตัวจริง**

```bash
cargo build          # ลืมใส่ --release หรือ --profile profiling
perf record -g -- ./target/debug/my_program
```

debug build (`opt-level = 0`) ไม่มีการ inline/vectorize/dead-code-elimination เลย ทำให้ **สัดส่วนเวลาของแต่ละ
ฟังก์ชันบิดเบือนไปจากที่ optimizer จะทำจริงใน release** อย่างที่พิสูจน์ด้วยตัวเลขจริงในหัวข้อ 55.9 (debug build
ช้ากว่า profiling build ถึง 4.7 เท่าสำหรับโปรแกรมเดียวกัน) — วิธีแก้คือ**เสมอ**ต้อง build ด้วย `--release`
หรือ custom profile ที่ inherit จาก `release` (เช่น `profiling` จาก Part 35) ก่อน profile ทุกครั้ง ไม่มีข้อยกเว้น

**2. ไม่มี debug symbol ทำให้ report อ่านไม่ออก**

```toml
[profile.release]
strip = true    # ค่าที่หลายโปรเจกต์ตั้งไว้เพื่อลดขนาด binary ที่แจกจ่ายจริง
```

ถ้าเอา binary ที่ `strip = true` (หรือ `debug = false`) มา profile ตรง ๆ ผลที่ได้จะเป็นแค่ hex address:

```
23.41%  my_program  my_program  [.] 0x0000000000012a3c
```

ไม่มีชื่อฟังก์ชันให้อ่านเลย ต้องสร้าง custom profile แยกสำหรับ profiling โดยเฉพาะ (ตาม Part 35 หัวข้อ 35.9) ที่
ตั้ง `debug = true` และ `strip = false` ไว้ตรง ๆ — **อย่า** พยายาม profile production binary ตัวเดียวกับที่แจก
จ่ายจริง (ที่ strip symbol ออกเพื่อลดขนาดไฟล์) ให้ build binary แยกสำหรับ profiling session เท่านั้น

**3. Profile บนเครื่อง development แล้วเชื่อว่าตัวเลขจะตรงกับ production เป๊ะ**

เครื่อง development (laptop, workstation) มักมี CPU/cache/frequency scaling ต่างจาก production server หรือ
cloud VM มาก ยิ่งถ้า production รันใน container ที่มี resource limit/cgroup overhead หรือแบ่ง CPU กับ tenant
อื่น ตัวเลข % ที่ profile ได้บนเครื่อง development อาจไม่ตรงกับสัดส่วนจริงบน production เลย — bottleneck เชิง
**อัลกอริทึม** (เช่น O(n²) ในตัวอย่างหัวข้อ 55.4) ยังเชื่อถือได้เสมอไม่ว่าจะ profile บนเครื่องไหน (เพราะเป็น
ปัญหาทางคณิตศาสตร์ ไม่ใช่ hardware) แต่การ**ยืนยันตัวเลขที่แน่นอน**ว่า "เร็วขึ้นกี่ %" ควร profile บนเครื่องที่
config ใกล้เคียง production ที่สุดเท่าที่ทำได้เสมอ

**4. เห็นฟังก์ชันแปลก ๆ ใน report แล้วรีบไป "optimize" มันทั้งที่กินเวลาแค่ 0.3%**

```
    Self  Command    Symbol
  61.42%  my_program [.] hot_function_that_matters
   0.31%  my_program [.] some_deeply_nested_helper
```

profiler มักแสดงรายการยาว ๆ ที่มีฟังก์ชันหลายสิบตัว บางตัวมีชื่อดูซับซ้อน/น่าสนใจทางเทคนิค แต่กินเวลาแค่เศษเสี้ยว
เปอร์เซ็นต์ — การไปเสียเวลา "optimize" ฟังก์ชันที่กิน 0.3% ให้เร็วขึ้นเป็นสองเท่า (ได้ผลลัพธ์สุทธิ 0.15% ของ
โปรแกรมทั้งตัว) ไม่คุ้มค่าเวลาที่เสียไปเลย เทียบกับการโฟกัสที่ฟังก์ชันซึ่งกิน `Self` สูงสุดเพียงไม่กี่ตัวแรกเท่า
นั้น — จำกฎ 80/20 ไว้เสมอ: ในโปรแกรมส่วนใหญ่ เวลาส่วนใหญ่กระจุกอยู่ใน**ฟังก์ชันจำนวนน้อยมาก** (อย่างตัวอย่าง
หัวข้อ 55.4 ที่ฟังก์ชันเดียวกิน 57.87%) — เรียงตาม `Self` มากไปน้อยเสมอ แล้วหยุดสนใจรายการที่กินต่ำกว่าเกณฑ์ที่
มีความหมายจริง (เช่นต่ำกว่า 1-2%) เว้นแต่คุณกำลังไล่ล่าหาความเร็วในระดับที่ไม่มีจุดใหญ่เหลือให้แก้แล้วจริง ๆ
(สถานการณ์แบบหัวข้อ 55.10 หลังแก้ไข ที่โปรไฟล์ "แบน" แล้ว)

**5. เชื่อผล sampling run เดียวโดยไม่รู้ว่ามันคือค่าประมาณทางสถิติ**

หัวข้อ 55.2 อธิบายไว้ว่า sampling profiler (`perf`) ให้ผลลัพธ์เป็น**การประมาณทางสถิติ** ไม่ใช่การนับที่แน่นอน —
ถ้า sample จำนวนน้อย (โปรแกรมรันเร็วมาก หรือตั้ง sampling frequency ต่ำ) ตัวเลข % ที่ได้ในแต่ละครั้งที่รันอาจ
**แตกต่างกันพอสมควร**ระหว่าง run แม้จะ profile โปรแกรมเดียวกันด้วย input เดียวกันซ้ำ ๆ ก็ตาม (เพราะจุดที่ interrupt
เกิดขึ้นแต่ละครั้งไม่ได้ตรงกันเป๊ะทุก run — ขึ้นกับ timing เล็ก ๆ ของ OS scheduler ที่ควบคุมไม่ได้ 100%) มือใหม่
มักรัน `perf record` เพียงครั้งเดียวแล้วเชื่อตัวเลขที่ได้ทันทีว่าเป็น "ความจริงที่แน่นอน" ทั้งที่ควร**รันซ้ำหลาย
ครั้ง**เพื่อดูว่าตัวเลขคงที่พอจะเชื่อได้หรือไม่ — โดยเฉพาะเมื่อความต่างระหว่างฟังก์ชันสองตัวที่กำลังเทียบกันนั้น
เล็กมาก (เช่น 24% เทียบกับ 22%) ความต่างระดับนี้อาจเป็นแค่ noise ทางสถิติของการ sampling เอง ไม่ใช่ความต่างที่มี
นัยสำคัญจริง — ยิ่งความต่างระหว่างสอง candidate เล็กเท่าไร ยิ่งต้อง sample มากขึ้น (เพิ่ม `-F` หรือรันโปรแกรม
นานขึ้น) หรือเปลี่ยนไปใช้ `criterion` (Part 54) ที่ออกแบบมาเพื่อวัดความต่างเล็ก ๆ ระดับนี้อย่างมีนัยสำคัญทาง
สถิติโดยเฉพาะ — ตัวอย่างในบทนี้ (57.87% เทียบกับฟังก์ชันอื่นที่เหลือไม่ถึง 10%) ต่างกันมากพอจนไม่ต้องกังวลเรื่อง
noise แบบนี้ แต่เมื่อคุณ optimize จนโปรไฟล์ "แบน" แล้ว (แบบหัวข้อ 55.10 หลังแก้) ปัญหานี้จะสำคัญขึ้นมาก เพราะความ
ต่างระหว่างฟังก์ชันแต่ละตัวเล็กลงเรื่อย ๆ

## แบบฝึกหัด (Exercises)

1. **(ง่าย)** เขียนโปรแกรมเล็ก ๆ ที่มีฟังก์ชันหนึ่งทำงานหนักอย่างเห็นได้ชัด (เช่น ฟังก์ชันเช็คว่าตัวเลขเป็นจำนวน
   เฉพาะหรือไม่ด้วยวิธี trial division ธรรมดา แล้วเรียกเช็คตัวเลขหลักแสนตัวติดกัน) สร้าง custom profile ชื่อ
   `profiling` ใน `Cargo.toml` ตามที่ Part 35/บทนี้สอน (`inherits = "release"`, `debug = true`, `strip =
   false`) แล้ว build ด้วย `cargo build --profile profiling` จากนั้นใช้ `valgrind --tool=callgrind` ตามด้วย
   `callgrind_annotate` เพื่อยืนยันว่าฟังก์ชันเช็คจำนวนเฉพาะคือตัวที่กิน instruction มากที่สุดจริง (hint: เทียบ
   เปอร์เซ็นต์ที่ได้กับความคาดหวังของคุณ ถ้าไม่ตรงกันให้ลองอธิบายว่าทำไม)

2. **(กลาง)** นำโปรแกรม `logcount` เวอร์ชันที่แก้แล้ว (ใช้ `HashMap`) จากหัวข้อ 55.10 มา profile ต่ออีกรอบ โดย
   สังเกตจากผลในหัวข้อนั้นว่า `malloc`/`free` รวมกันกิน instruction ไปเกือบ 30% — ลองแก้ `Counter::record` ให้
   allocate `String` **เฉพาะตอนที่ key ยังไม่มีอยู่จริง** (ปัจจุบันเรียก `user_id.to_string()` ทุกครั้งแม้ key
   จะมีอยู่แล้วก็ตาม) แล้ว profile ซ้ำเพื่อพิสูจน์ว่า allocation ลดลงจริง (hint: ใช้ `HashMap::get_mut` เช็คก่อน
   แล้วค่อย `insert` เฉพาะตอนที่ยังไม่เจอ เพื่อเลี่ยงการสร้าง `String` ทิ้งเปล่า ๆ ตอน key ซ้ำ)

3. **(ยาก)** เขียนโปรแกรมที่มี**สอง**จุดที่ดูน่าสงสัยว่าจะเป็น bottleneck พร้อมกัน — เช่น ฟังก์ชัน A ที่ทำ string
   concatenation ด้วย `+=` ในลูปยาว (ทำให้ reallocate ซ้ำ ๆ ตาม Part 13) และฟังก์ชัน B ที่ทำ substring search
   แบบ naive O(n×m) ทั้งสองฟังก์ชันถูกเรียกในโปรแกรมเดียวกัน ก่อน profile ให้เขียนคำทำนายของคุณเองไว้ก่อนว่าคิด
   ว่าอันไหนจะกินเวลามากกว่า แล้ว profile จริงด้วย `callgrind` เพื่อดูว่าคำทำนายถูกหรือผิด (hint: ผลลัพธ์อาจ
   ทำให้คุณประหลาดใจ — บ่อยครั้งที่ intuition ของโปรแกรมเมอร์เกี่ยวกับ "อะไรน่าจะช้า" ผิดจากความจริงที่ profiler
   แสดง นี่คือเหตุผลที่ต้อง profile จริงเสมอ ไม่ใช่เดาจากความรู้สึก)

4. **(ยาก/ประยุกต์ใช้งานจริง)** สมมติสถานการณ์นี้: ทีมของคุณ profile API server บนเครื่อง laptop นักพัฒนาด้วย
   `perf`/flamegraph แล้วพบว่าฟังก์ชัน `serialize_response()` กินเวลา 45% ทีมจึงเสนอให้ optimize ฟังก์ชันนี้เป็น
   งานเร่งด่วน แต่วิศวกรอีกคนตั้งข้อสังเกตว่า production server รันบน cloud VM ที่มี CPU รุ่นเก่ากว่าและแบ่ง core
   กับ tenant อื่น อธิบาย (เป็นข้อความสั้น ๆ 4-6 บรรทัด ไม่ต้องเขียนโค้ด) ว่าทำไมตัวเลข "45%" ที่วัดบน laptop
   อาจไม่สะท้อนความจริงบน production, เสนอวิธี profile ที่น่าเชื่อถือกว่าสำหรับสถานการณ์นี้, และอธิบายว่าเมื่อทีม
   หา bottleneck ตัวจริงบน production-like environment ได้แล้ว ควรใช้เครื่องมือจาก Part 54 (`criterion`) ต่อ
   อย่างไรก่อนจะ merge การแก้ไขจริงเข้า production (hint: คำตอบที่ดีควรพูดถึงทั้งเรื่อง hardware ที่ต่างกัน,
   ความเสี่ยงของการ optimize ผิดจุดถ้าเชื่อตัวเลขจาก environment ที่ไม่ตรงกัน, และลำดับขั้นตอน profile →
   benchmark candidate fix → verify ซ้ำ ตามที่บทนี้และ Part 54 สอนไว้)

## สรุป

บทนี้ปิดวงจร mini-arc เรื่อง performance ที่เริ่มจาก Part 54 อย่างสมบูรณ์: **Part 54 สอนวิธีวัดความเร็วของโค้ด
จุดที่คุณสงสัยอยู่แล้ว (benchmarking) ส่วนบทนี้สอนวิธีหาว่าควรสงสัยจุดไหนในโปรแกรมทั้งตัว (profiling)** — ทั้งสอง
เครื่องมือประกอบกันเป็น workflow เดียว: profile ก่อนเพื่อหา bottleneck จากข้อมูลจริง ไม่ใช่จากความรู้สึก →
benchmark candidate fix หลายแบบสำหรับจุดที่พบเพื่อเลือกวิธีที่ดีที่สุด → แก้โค้ดจริง → profile ซ้ำเพื่อพิสูจน์ว่า
โปรแกรมทั้งตัวเร็วขึ้นจริง เราได้เห็นหลักการของ sampling profiler (`perf`, ใช้กันแพร่หลายที่สุดในโลกจริง) เทียบกับ
instrumenting profiler (`callgrind`, แม่นยำกว่าแต่ overhead สูงกว่ามาก) ได้เห็นว่าทำไม debug symbol (คีย์ `debug`
ที่ Part 35 สอนไว้ล่วงหน้าผ่าน custom profile `profiling`) เป็นเงื่อนไขจำเป็นที่ทำให้ผล profiler อ่านออกได้จริง
ได้ลงมือ profile โปรแกรม log analyzer ที่มีบั๊ก O(n²) ซ่อนอยู่ด้วยข้อมูลจริงจนพบว่า string comparison กินไปถึง
92%+ ของงานทั้งหมด แก้ด้วย `HashMap` ตาม Part 15 แล้วพิสูจน์ด้วยตัวเลขจริงว่าเร็วขึ้น 20.4 เท่า และได้เห็นว่าทำไม
CPU profiling อย่างเดียวไม่พอสำหรับปัญหาบางประเภท (memory profiling ด้วย `massif` เผยให้เห็นแหล่ง allocation
ที่ CPU profiler มองไม่เห็นชัดเจน) พร้อมทั้งเรียนรู้กับดักเชิงการตีความที่สำคัญที่สุด — debug build, environment
ที่ไม่ตรงกับ production, และการไล่ตามตัวเลขที่ไม่มีความหมาย — ที่ทำให้ตัวเลขจาก profiler "โกหก" ได้ถ้าอ่านไม่
ระมัดระวัง

แต่คำถามที่ยังไม่ได้ตอบให้ลึกพอในบทนี้คือ: **ทำไม `HashMap` ยังต้อง allocate เยอะขนาดนั้น (30% ของ instruction
หลังแก้) ทั้งที่มัน "เร็ว" กว่า linear search มาก? ทำไม String ถึงมีต้นทุนสูงกว่าที่ควรจะเป็นในหลายกรณี? และ
"zero-cost abstraction" ที่ Rust โฆษณาไว้ตลอดหลักสูตรนี้ มันจริงแค่ไหนในทางปฏิบัติ?** **Part 56 (Memory
Management ขั้นสูง และ Zero-cost Abstractions)** จะพาคุณกลับไปดูโมเดลความเป็นเจ้าของ (ownership) และ allocator
ในระดับที่ลึกกว่าที่ Part 6/13 เคยพูดถึง พร้อมตรวจสอบอย่างเข้มงวดว่าข้ออ้าง "zero-cost" ของ abstraction ต่าง ๆ
ใน Rust (iterator, generic, trait object) เป็นจริงแค่ไหนเมื่อพิสูจน์ด้วยเครื่องมือที่คุณเพิ่งเรียนรู้จบไปในบทนี้
