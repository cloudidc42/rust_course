# Part 14: Collections: String และการจัดการข้อความ (UTF-8)

> โมดูล: พื้นฐานภาษา Rust (Core Language Fundamentals) | ระดับ: พื้นฐาน | เวลาโดยประมาณ: 150 นาที

## เป้าหมายของบทเรียน

หลังจากจบบทนี้ คุณจะสามารถ:

- อธิบายได้ว่า `String` คือ struct ที่ **wrap** `Vec<u8>` เอาไว้ (พร้อมการันตีว่าข้อมูลข้างในเป็น UTF-8 ที่ถูกต้องเสมอ)
  และเห็นความสัมพันธ์ระหว่าง `String` กับ `&str` ว่าเดินตามรูปแบบเดียวกันเป๊ะกับ `Vec<T>` กับ `&[T]` ที่เรียนมาจาก Part 13
- เลือกวิธีสร้าง `String` ได้อย่างเหมาะสมระหว่าง `String::new()`, `String::from()`, `.to_string()`, `.to_owned()`
  และ `String::with_capacity()` พร้อมอธิบายความแตกต่างเชิงลึกของแต่ละวิธี
- ทำให้ `String` เติบโตได้ด้วย `.push()`, `.push_str()`, ตัวดำเนินการ `+`, และ macro `format!()` พร้อมอธิบายได้ว่าทำไม
  `String + &str` ถึง**บริโภค (consume)** ตัวแปรฝั่งซ้ายไปเลยในเชิง ownership
- อธิบายหลักการของ **UTF-8 encoding** ได้อย่างถูกต้อง (variable-width, 1-4 bytes ต่อ Unicode scalar value) และเข้าใจ
  อย่างละเอียดกว่าที่ Part 8 เคยแนะนำไว้ว่าทำไมการ slice ผิดตำแหน่งถึง panic
- อธิบายได้อย่างตรงไปตรงมาว่า **ตัวอักษรไทย 1 ตัวที่มองเห็นด้วยตา ไม่เท่ากับ 1 `char` ของ Rust เสมอไป** เพราะภาษาไทยมี
  วรรณยุกต์และสระลอยที่เป็น Unicode scalar value แยกต่างหาก (combining marks) และรู้จักแนวคิด **grapheme cluster**
  รวมถึง crate `unicode-segmentation` ที่แก้ปัญหานี้ได้จริง
- แยกแยะการมองสตริงได้ 3 แบบ (`.bytes()`, `.chars()`, `.char_indices()`) และอธิบายได้ว่าทำไม Rust มาตรฐาน (std) จึง
  **ตั้งใจไม่มี** method สำหรับดึง "grapheme ตัวที่ N" ให้ใช้ตรง ๆ
- อธิบายได้ว่าทำไม `s[0]` ไม่ compile บน `String`/`&str` (ต่างจาก array/`Vec` ที่ index ตรง ๆ ได้จาก Part 13) และมองว่า
  นี่คือการออกแบบที่ตั้งใจ ไม่ใช่ข้อจำกัดที่ลืมทำ
- ใช้ method จัดการข้อความที่สำคัญที่สุดของ `str` ได้อย่างคล่องแคล่ว (`.split()`, `.split_whitespace()`, `.lines()`,
  `.trim()`, `.replace()`, `.contains()`, `.starts_with()`/`.ends_with()`, `.to_uppercase()`/`.to_lowercase()`,
  `.parse::<T>()`) และเขียนฟังก์ชันตัดสตริงให้ปลอดภัยจาก UTF-8 panic ด้วย `.char_indices()`

## ความรู้ที่ต้องมีมาก่อน

- **Part 8 (Slices)**: เข้าใจว่า `&str` คือ fat pointer (`ptr` + `len`), เข้าใจว่า string literal เป็น `&str` มาตั้งแต่
  Part 1, และที่สำคัญที่สุดสำหรับบทนี้คือ **หัวข้อ 8.4** ที่แสดง panic จริงตอน slice สตริงภาษาไทยผิดตำแหน่ง byte boundary
  (`byte index 1 is not a char boundary; it is inside 'ส' (bytes 0..3) of \`สวัสดี\``) พร้อม **teaser ว่า `.chars()`
  คือทางเลือกที่ปลอดภัยกว่า และเนื้อหาเต็มของมันถูกเลื่อนมาไว้ที่ Part 14 — ก็คือบทนี้เอง** เราจะไม่สอนซ้ำเรื่อง byte
  boundary panic จากศูนย์ แต่จะ**ต่อยอด**จากจุดที่ Part 8 ทิ้งไว้โดยตรง
- **Part 12 (Result\<T, E\>)**: เข้าใจว่า operation ที่อาจล้มเหลวควรคืนค่าเป็น `Result<T, E>` แทนการ panic ตรง ๆ และรู้จัก
  `.unwrap()`, `match`, และ `?` operator เบื้องต้น — บทนี้จะใช้ความรู้นี้ตอนพูดถึง `.parse::<T>()` ซึ่งคืนค่าเป็น
  `Result<T, ParseIntError>` (หรือ error type อื่นตามชนิดที่ parse)
- **Part 13 (Collections: Vec\<T\>)**: เข้าใจว่า `Vec<T>` คือ struct ที่เก็บ `ptr`, `len`, `capacity` และจองพื้นที่บน heap
  แบบเติบโตได้ (growable), รู้จักความสัมพันธ์ `Vec<T>` กับ `&[T]` ผ่าน deref coercion แบบเดียวกับ `String` กับ `&str`
  ใน Part 8 — บทนี้จะดึงความรู้เรื่อง `Vec<T>` มาใช้อธิบายว่า **`String` แท้จริงแล้วก็คือ `Vec<u8>` ที่มีข้อบังคับเพิ่มขึ้นมา
  หนึ่งชั้นเท่านั้นเอง** ไม่ใช่ชนิดข้อมูลที่แปลกใหม่ไปคนละทางเลย

ถ้าคุณยังจำภาพจาก Part 8 ไม่ได้ ลองย้อนอ่านหัวข้อ 8.3-8.4 อีกครั้งก่อนเริ่มบทนี้ เพราะบทนี้จะพูดถึงคำว่า "fat pointer",
"character boundary", และ "`.chars()`" ซ้ำ ๆ โดยสมมติว่าคุณคุ้นคำเหล่านี้อยู่แล้ว

## เนื้อหา

### 14.1 `String` คืออะไรกันแน่: มันคือ `Vec<u8>` ที่มีข้อบังคับเพิ่ม

ใน Part 13 เราเรียนว่า `Vec<T>` คือ struct ที่เก็บ 3 ค่า: pointer ไปยัง heap buffer, ความยาวปัจจุบัน (`len`), และ
ความจุที่จองไว้ (`capacity`) และเรารู้จาก Part 8 ว่า `String` ก็เป็นชนิดข้อมูลที่ "จองพื้นที่บน heap และเติบโตได้"
เหมือนกัน — คำถามคือ ทั้งสองเกี่ยวข้องกันแค่ไหน?

คำตอบคือ **เกี่ยวข้องกันเกือบ 100%** เพราะ source code จริงของ `String` ใน standard library นิยามไว้แบบนี้ (ปรับให้
อ่านง่ายขึ้นเล็กน้อย แต่ยังตรงตามโครงสร้างจริง):

```rust
// นี่คือ (ประมาณ) นิยามจริงของ String ใน std::string
pub struct String {
    vec: Vec<u8>,
}
```

พูดตรง ๆ คือ **`String` เป็นแค่ struct ที่มี field เดียว ชื่อ `vec` ชนิด `Vec<u8>`** — ไม่มีอะไรซับซ้อนไปกว่านี้เลยในเชิง
memory layout ทุกอย่างที่คุณรู้จัก `Vec<u8>` มาแล้วจาก Part 13 (การจองพื้นที่แบบ amortized growth, การ realloc เมื่อ
capacity เต็ม, ความสัมพันธ์กับ slice) ใช้ได้กับ `String` ทุกประการ เพราะข้างใต้มันคือของสิ่งเดียวกัน

มายืนยันด้วยขนาดจริงในหน่วยความจำ (รันจริงบนเครื่อง 64-bit ด้วย `rustc` edition 2021):

```rust
fn main() {
    println!("size_of::<String>()  = {} bytes", std::mem::size_of::<String>());
    println!("size_of::<Vec<u8>>() = {} bytes", std::mem::size_of::<Vec<u8>>());
    println!("size_of::<&str>()    = {} bytes", std::mem::size_of::<&str>());
    println!("size_of::<&[u8]>()   = {} bytes", std::mem::size_of::<&[u8]>());
}
```

ผลลัพธ์จริงบนเครื่อง 64-bit:

```
size_of::<String>()  = 24 bytes
size_of::<Vec<u8>>() = 24 bytes
size_of::<&str>()    = 16 bytes
size_of::<&[u8]>()   = 16 bytes
```

สังเกตความเท่ากันแบบเป๊ะ ๆ: **`String` และ `Vec<u8>` มีขนาดเท่ากันทั้งคู่คือ 24 bytes** (ptr 8 bytes + len 8 bytes +
capacity 8 bytes บนเครื่อง 64-bit) และ **`&str` กับ `&[u8]` ก็มีขนาดเท่ากันคือ 16 bytes** (ptr 8 bytes + len 8 bytes —
fat pointer ที่ไม่มี capacity เพราะเป็นแค่ "หน้าต่าง" มองเข้าไปดูข้อมูล ไม่ได้เป็นเจ้าของและไม่ต้องรู้ว่าจองพื้นที่ไว้
เผื่อโตต่อได้อีกแค่ไหน) นี่ไม่ใช่ความบังเอิญ — มันคือผลลัพธ์ตรงไปตรงมาจากการที่ `String` เป็น `Vec<u8>` และ `&str`
เป็น slice ของ `[u8]` ในเชิง layout จริง ๆ

#### ตารางเปรียบเทียบคู่ที่ขนานกันเป๊ะ ๆ

นี่คือจุดที่สำคัญที่สุดของหัวข้อนี้ ควรจำภาพนี้ไว้ให้แม่นเพราะจะใช้อธิบายพฤติกรรมของ `String` ทุกอย่างในบทนี้ต่อจากนี้:

| แนวคิด | ฝั่ง "ทั่วไป" (Part 13) | ฝั่ง "ข้อความ" (บทนี้) |
|---|---|---|
| ชนิดที่เป็นเจ้าของข้อมูล เติบโตได้ อยู่บน heap | `Vec<T>` | `String` (= `Vec<u8>` ที่มีข้อบังคับเพิ่ม) |
| ชนิด slice ที่ยืมข้อมูลมาดู ไม่เป็นเจ้าของ | `&[T]` | `&str` (= `&[u8]` ที่มีข้อบังคับเพิ่ม) |
| element ที่เก็บอยู่ข้างใน | `T` ชนิดใดก็ได้ | `u8` เท่านั้น (**ไม่ใช่ `char`!**) |
| เพิ่มสมาชิกท้าย | `.push(value: T)` | `.push(ch: char)` (เพิ่มทีละ**ตัวอักษร**) และ `.push_str(s: &str)` |
| ความจุ/การเติบโต | `.capacity()`, `.reserve()`, amortized doubling | เหมือนกันทุกประการ (`.capacity()`, `.reserve()` ใช้ได้จริง) |
| อ่านเป็น reference ล้วน ๆ | `&vec[..]` deref coercion เป็น `&[T]` | `&string[..]` deref coercion เป็น `&str` |

แถวที่ต้องเน้นเป็นพิเศษคือแถวที่สาม: **`String` ไม่ได้เก็บข้อมูลเป็น array ของ `char`** (ที่กิน 4 bytes ต่อตัวเสมอตาม
ที่เรียนใน Part 3) แต่เก็บเป็น **`u8` ดิบ ๆ ที่เข้ารหัสแบบ UTF-8** ซึ่งตัวอักษรหนึ่งตัวอาจกินตั้งแต่ 1 ถึง 4 `u8`
ไม่เท่ากัน — นี่คือกฎเข้ารหัสที่เราจะเจาะลึกในหัวข้อ 14.4 แต่ตอนนี้ให้จำภาพไว้ก่อนว่า: **`String` คือ `Vec<u8>` บวก
"สัญญา" (invariant) ข้อเดียวที่การันตีไว้ตลอดเวลาว่า bytes ข้างในต้องเป็น valid UTF-8 เท่านั้น** — สัญญาข้อนี้เองคือ
สิ่งที่ทำให้ `String` **ไม่ใช่แค่** `Vec<u8>` เฉย ๆ แต่เป็นชนิดข้อมูลที่ปลอดภัยกว่ามากในการใช้แทนข้อความ เพราะทุก method
ของ `String` ที่แก้ไขเนื้อหา (เช่น `.push()`, `.push_str()`, `.truncate()`) จะตรวจสอบ (หรือรับประกันโดยการออกแบบ) ว่า
ผลลัพธ์ยังเป็น valid UTF-8 อยู่เสมอ ไม่มีทางที่ `String` จะมีเนื้อหาที่ผิดกฎ UTF-8 อยู่ข้างในได้เลยผ่าน API สาธารณะปกติ

#### พิสูจน์ความสัมพันธ์นี้ด้วยการแปลงไปมาจริง

Rust เปิดช่องให้เราสลับไปมาระหว่าง `String` กับ `Vec<u8>` ได้ตรง ๆ ผ่าน method คู่หนึ่งที่แสดงความสัมพันธ์นี้อย่าง
ชัดเจนที่สุด:

```rust
fn main() {
    let s = String::from("Rust ดี");

    // มองเข้าไปโดยไม่เอาความเป็นเจ้าของ (borrow) -> ได้ &[u8]
    let bytes_view: &[u8] = s.as_bytes();
    println!("{:?}", bytes_view);

    // ดึงความเป็นเจ้าของออกมาเป็น Vec<u8> จริง ๆ (s ถูก consume ไปเลย)
    let owned_bytes: Vec<u8> = s.into_bytes();
    println!("{:?}", owned_bytes);

    // แปลงกลับจาก Vec<u8> เป็น String — ต้อง "ตรวจสอบ" ว่ายังเป็น UTF-8 ที่ถูกต้องอยู่ไหม
    // จึงคืนค่าเป็น Result ไม่ใช่ String ตรง ๆ
    let back: String = String::from_utf8(owned_bytes).unwrap();
    println!("{back}");
}
```

ผลลัพธ์จริง:

```
[82, 117, 115, 116, 32, 224, 184, 148, 224, 184, 181]
[82, 117, 115, 116, 32, 224, 184, 148, 224, 184, 181]
Rust ดี
```

สังเกตตัวเลข 5 ตัวสุดท้ายในทั้งสองบรรทัดแรก (`224, 184, 148` และ `224, 184, 181`) — นี่คือ bytes ที่เข้ารหัส UTF-8 ของ
ตัวอักษร "ด" และ "ี" ตามลำดับ (แต่ละตัวใช้ 3 bytes ตามกฎ UTF-8 ของอักษรไทยที่เราจะเจาะลึกในหัวข้อ 14.4) และคำว่า "Rust "
5 ตัวอักษรแรกก็คือ ASCII code ปกติ (`R`=82, `u`=117, `s`=115, `t`=116, เว้นวรรค=32) ที่ใช้ **1 byte ต่อตัว**

จุดที่น่าสนใจที่สุดคือ `String::from_utf8()` **คืนค่าเป็น `Result<String, FromUtf8Error>`** ไม่ใช่ `String` ตรง ๆ —
นี่คือสิ่งที่ตอกย้ำ "สัญญา UTF-8" ที่พูดถึงข้างบน: การแปลง `Vec<u8>` (ที่เป็น bytes อะไรก็ได้ ไม่รู้ประวัติ) ให้กลายเป็น
`String` (ที่ต้องการันตี valid UTF-8 เสมอ) **ต้องมีการตรวจสอบ** ก่อนเสมอ เพราะไม่มีทางรู้ล่วงหน้าว่า `Vec<u8>` ที่ส่งเข้ามา
มี bytes ที่ผิดกฎ UTF-8 ปนอยู่หรือไม่ ลองดูกรณีที่ตรวจสอบแล้วล้มเหลว:

```rust
fn main() {
    // 0xff และ 0xfe ไม่ใช่ byte เริ่มต้นที่ถูกต้องของ UTF-8 เลยแม้แต่ pattern เดียว
    let invalid_bytes: Vec<u8> = vec![0xff, 0xfe, 0x00];
    let result = String::from_utf8(invalid_bytes);
    println!("{:?}", result);
}
```

ผลลัพธ์จริง:

```
Err(FromUtf8Error { bytes: [255, 254, 0], error: Utf8Error { valid_up_to: 0, error_len: Some(1) } })
```

`Err` บอกเราอย่างละเอียดว่า bytes ที่ให้มา **ไม่ใช่ UTF-8 ที่ถูกต้อง** (`valid_up_to: 0` หมายความว่าไม่มี byte ไหนใน
ลำดับนี้เลยที่ถูกต้องแม้แต่ตัวแรก) — ถ้า `String::from_utf8()` คืนค่า `String` ตรง ๆ โดยไม่ผ่าน `Result` เราจะได้
`String` ที่มีข้อมูลข้างในผิดกฎ UTF-8 ซ่อนอยู่ ซึ่งจะทำให้ method อื่น ๆ ของ `String` (เช่น `.chars()`, การ print,
การ slice) พังโดยไม่ทันตั้งตัวในภายหลัง — การบังคับให้ตรวจสอบตั้งแต่จุดสร้างคือการ "ปิดประตูปัญหา" ตั้งแต่ต้นทาง ตรงกับ
หลักการ **"parse, don't validate"** ที่ Rust ใช้ซ้ำ ๆ ทั้งหลักสูตรผ่าน type system (เราเห็นแนวคิดคล้ายกันมาแล้วตอน
`Result<T, E>` ใน Part 12 — สร้างค่าที่ผ่านการตรวจสอบแล้วเก็บไว้ใน type ที่รับประกันได้ ดีกว่าเก็บค่าดิบแล้วไปเช็คทีหลัง
ทุกครั้งที่ใช้งาน)

ถ้าคุณไม่ต้องการให้ operation ล้มเหลวเป็น `Err` แต่ต้องการ "กู้ข้อมูลเท่าที่กู้ได้" แทน (เช่น ตอนอ่านไฟล์ที่ไม่แน่ใจ
ว่า encoding ถูกต้อง 100% หรือไม่ แต่ยังอยากได้เนื้อหาส่วนที่อ่านได้ออกมาใช้งานต่อ) มี method ทางเลือกชื่อ
**`String::from_utf8_lossy()`** ที่ไม่คืนค่าเป็น `Result` แต่แทนที่ byte ที่ผิดกฎ UTF-8 ทุกจุดด้วยตัวอักษรพิเศษ
**`�`** (REPLACEMENT CHARACTER, `U+FFFD`) แทน:

```rust
fn main() {
    let mixed_bytes: Vec<u8> = vec![0xff, 0xfe, 0x00, 82, 117, 115, 116]; // byte เสียปนกับคำว่า "Rust"
    let lossy: std::borrow::Cow<str> = String::from_utf8_lossy(&mixed_bytes);
    println!("{lossy}");
    println!("{:?}", lossy);
}
```

ผลลัพธ์จริง:

```
�� Rust
"��\0Rust"
```

สังเกตว่า byte ที่ผิดกฎ (`0xff`, `0xfe`) ถูกแทนที่ด้วย `�` ส่วน byte ที่เหลือ (`0x00` ตามด้วยคำว่า `Rust` ที่เป็น
ASCII ถูกต้อง) ยังคงอยู่ครบ — `from_utf8_lossy()` คืนค่าเป็น `Cow<str>` (ชนิดข้อมูลที่จะเรียนอย่างเป็นทางการใน
Part 29 ตอนนี้จำแค่ว่ามันคือ "อาจเป็น `&str` ที่ยืมมา หรืออาจเป็น `String` ใหม่ที่จองขึ้นมา ขึ้นอยู่กับว่าต้องแก้ไข
เนื้อหาจริงหรือไม่" — ถ้า bytes ที่ให้มาถูกต้องทั้งหมดอยู่แล้ว มันจะยืมแบบไม่ copy เลย แต่ถ้ามี byte ผิดกฎต้องแทนที่
มันจะจอง `String` ใหม่ขึ้นมาเก็บผลลัพธ์) — เหมาะกับงานที่ให้ความสำคัญกับ "โปรแกรมไม่ crash" มากกว่า "ข้อมูลต้อง
ถูกต้องสมบูรณ์แบบ" เช่นการแสดงตัวอย่าง log ไฟล์ที่อาจมีข้อมูลเสียปนอยู่บางจุด

### 14.2 สร้าง `String`: 5 วิธีหลัก และเมื่อไหร่ควรใช้แบบไหน

Rust มีหลายวิธีในการสร้าง `String` ซึ่งแต่ละวิธีมีเหตุผลและบริบทการใช้งานที่ต่างกันชัดเจน ไม่ใช่แค่ "สไตล์การเขียนที่
ต่างกัน" เฉย ๆ

#### `String::new()`: สร้างสตริงเปล่า ไม่มีการจอง heap เลย

```rust
fn main() {
    let s: String = String::new();
    println!("len = {}, capacity = {}", s.len(), s.capacity());
}
```

ผลลัพธ์:

```
len = 0, capacity = 0
```

`String::new()` สร้าง `String` ที่ pointer เป็นค่าพิเศษ (dangling แบบปลอดภัยที่ไม่มีการจอง heap จริง — เทคนิคเดียวกัน
กับที่ `Vec::new()` ทำใน Part 13) — ยังไม่มีการเรียก allocator เลยแม้แต่ครั้งเดียว จะจองพื้นที่จริงก็ตอนที่คุณเริ่ม
`.push()` หรือ `.push_str()` ครั้งแรกเท่านั้น เหมาะกับสถานการณ์ที่คุณจะ**สร้างสตริงขึ้นทีละส่วนในลูป** (pattern ที่จะเห็น
ในหัวข้อ 14.3 และตัวอย่างจริงท้ายบท)

#### `String::from(&str)`: แปลง string literal หรือ `&str` เป็น `String` ที่เป็นเจ้าของ

```rust
fn main() {
    let s: String = String::from("สวัสดีประเทศไทย");
    println!("{s}");
}
```

`String::from()` รับ `&str` เข้ามา แล้วจอง heap buffer ใหม่ **คัดลอกเนื้อหาทั้งหมด** เข้าไปเก็บเป็นของตัวเอง — นี่คือ
วิธีที่ตรงไปตรงมาที่สุดเมื่อคุณมี literal อยู่แล้วและต้องการ "แปลงร่าง" มันให้เป็นข้อมูลที่ตัวเองเป็นเจ้าของ (เช่น
เพื่อจะเอาไป `.push_str()` ต่อทีหลัง เพราะ `&str` แก้ไขไม่ได้)

#### `.to_string()`: เรียกผ่าน trait `ToString` ใช้ได้กับทุกชนิดที่ implement `Display`

```rust
fn main() {
    let from_str: String = "hello".to_string();
    let from_int: String = 42.to_string();
    let from_float: String = 3.14.to_string();

    println!("{from_str} {from_int} {from_float}");
}
```

ผลลัพธ์:

```
hello 42 3.14
```

`.to_string()` เป็น method จาก trait `ToString` ซึ่ง Rust implement ให้กับ**ทุกชนิดข้อมูลที่ implement `Display`**
โดยอัตโนมัติ (มี blanket implementation ให้อยู่แล้วใน std) นี่คือสาเหตุที่ `.to_string()` ใช้ได้ทั้งกับ `&str`, `i32`,
`f64`, และชนิดข้อมูล custom ของคุณเองในอนาคต ตราบใดที่คุณ implement `Display` ให้มัน (เราจะเรียนการ implement trait
เองใน Part 19) — ข้อสังเกตสำคัญ: **`.to_string()` เป็น method ทั่วไปที่ทำงานผ่าน `Display::fmt()` ข้างใต้** ซึ่งหมายความ
ว่ามันมี overhead เล็กน้อยจากการ format ผ่านกลไก formatting ทั่วไป (แม้จะน้อยมากจนไม่มีผลในการใช้งานทั่วไป)

#### `.to_owned()`: ทำสำเนาผ่าน trait `ToOwned` — ทางเลือกที่ตรงประเด็นกว่าสำหรับ `&str` โดยเฉพาะ

```rust
fn main() {
    let borrowed: &str = "hello";
    let owned: String = borrowed.to_owned();
    println!("{owned}");
}
```

`.to_owned()` มาจาก trait `ToOwned` ซึ่งออกแบบมาสำหรับ "แปลงจากชนิดที่ยืมมา (borrowed) ให้กลายเป็นชนิดที่เป็นเจ้าของ
(owned) ของมันโดยเฉพาะ" — สำหรับ `&str` การเรียก `.to_owned()` จะได้ `String` กลับมาเหมือนกับ `.to_string()` เป๊ะ ๆ
ในทางผลลัพธ์ แต่**เส้นทางการทำงานข้างใต้ตรงประเด็นกว่า**: `ToOwned` ของ `&str` แค่ copy bytes ดิบ ๆ เข้า heap buffer
ใหม่ตรง ๆ (implementation เฉพาะสำหรับ `str -> String` ที่เขียนไว้ตรง ๆ ใน std) ในขณะที่ `.to_string()` ต้องเดินทาง
ผ่าน `Display::fmt()` แบบทั่วไปก่อน ในทางปฏิบัติ **ทั้งสองแบบให้ผลลัพธ์เหมือนกันทุกประการและเร็วพอ ๆ กันในเวอร์ชัน
compiler ปัจจุบัน** (compiler มัก optimize เส้นทางทั้งสองให้เหลือแค่ `memcpy` เหมือนกัน) — ความแตกต่างจริง ๆ ที่ควร
จำไว้คือเรื่อง**ความหมายในโค้ด** มากกว่าประสิทธิภาพ:

| Method | ใช้เมื่อ |
|---|---|
| `.to_string()` | ต้นทางเป็นชนิดข้อมูลที่ implement `Display` ทั่วไป (ตัวเลข, ชนิด custom ที่ทำ `Display` เอง) หรือแค่ต้องการ "format เป็นสตริง" |
| `.to_owned()` | ต้นทางเป็น `&str` (หรือ borrowed type อื่น ๆ ที่มี `ToOwned` เฉพาะ เช่น `&[T]` -> `Vec<T>`) และคุณต้องการสื่อความหมายชัด ๆ ว่า "แปลงจากของที่ยืมมา ให้เป็นของที่เราเป็นเจ้าของเอง" |

โค้ดจริงในโปรเจกต์ Rust ส่วนใหญ่ใช้ `.to_string()` เป็นหลักเพราะสั้นและคุ้นตากว่า แต่ถ้าคุณเจอ `.to_owned()` ในโค้ด
คนอื่น ก็ให้เข้าใจว่ามันทำงานเหมือน `.to_string()` สำหรับ `&str` นั่นเอง — เลือกใช้แบบไหนก็ compile ผ่านและได้ผลลัพธ์
เหมือนกันในกรณีของ `&str`

#### `String::with_capacity(n)`: จองพื้นที่ล่วงหน้าเพื่อลดการ reallocate

```rust
fn main() {
    let mut s = String::with_capacity(10);
    println!("เริ่มต้น: len={}, capacity={}", s.len(), s.capacity());

    for _ in 0..5 {
        s.push('x');
    }
    println!("หลัง push 5 ตัว: len={}, capacity={}", s.len(), s.capacity());
}
```

ผลลัพธ์จริง:

```
เริ่มต้น: len=0, capacity=10
หลัง push 5 ตัว: len=5, capacity=10
```

สังเกตว่า `capacity` ยังเป็น `10` เท่าเดิมหลัง push 5 ตัว — เพราะเราจองไว้ล่วงหน้าพอแล้ว ไม่ต้องขยาย (realloc) เลย
นี่คือหลักการเดียวกันกับ `Vec::with_capacity()` ที่เรียนใน Part 13 เป๊ะ ๆ: **ถ้าคุณรู้ล่วงหน้าคร่าว ๆ ว่าสตริงจะยาว
ประมาณเท่าไหร่ (เช่น กำลังจะสร้างสตริงในลูปที่รันซ้ำหลายพันครั้ง) การจอง capacity ล่วงหน้าช่วยลดจำนวนครั้งที่ต้อง
reallocate + copy ข้อมูลทั้งหมดไปยัง buffer ใหม่ ซึ่งเป็น operation ที่มีค่าใช้จ่ายสูงถ้าเกิดขึ้นบ่อย** — ในโค้ดทั่วไป
ที่ไม่ได้ใส่ใจ performance ระดับสูง การใช้ `String::new()` เฉย ๆ ก็เพียงพอ เพราะกลยุทธ์ amortized growth ของ Rust
ทำให้ต้นทุนเฉลี่ยต่อการ push ยังคง O(1) อยู่ดี (เหมือนที่อธิบายไว้ใน Part 13) แต่ `with_capacity` ช่วยตัดการ realloc
ที่ไม่จำเป็นออกไปได้ทั้งหมดถ้าประมาณขนาดได้แม่นยำ

### 14.3 การเติบโตของ `String`: `.push()`, `.push_str()`, `+`, และ `format!()`

#### `.push(char)`: เพิ่มตัวอักษรเดียวต่อท้าย

```rust
fn main() {
    let mut s = String::from("Rus");
    s.push('t');
    s.push('!');
    println!("{s}");
}
```

ผลลัพธ์: `Rust!`

สังเกตว่า `.push()` รับ parameter เป็น **`char` ตัวเดียว** (ไม่ใช่ `&str`) — ตรงกับที่ตารางในหัวข้อ 14.1 บอกไว้ว่า
`.push(value: T)` ของ `Vec<T>` เทียบเท่ากับ `.push(ch: char)` ของ `String` ข้างใต้ `.push()` จะเข้ารหัส `char` ตัวนั้น
เป็น UTF-8 bytes (1-4 bytes ตามกฎที่จะเรียนในหัวข้อ 14.4) แล้วต่อเข้าไปที่ปลาย buffer

#### `.push_str(&str)`: เพิ่มหลายตัวอักษรพร้อมกัน (ต่อสตริงทั้งก้อน)

```rust
fn main() {
    let mut s = String::from("Hello");
    s.push_str(", ");
    s.push_str("World");
    s.push('!');
    println!("{s}");
}
```

ผลลัพธ์: `Hello, World!`

`.push_str()` รับ `&str` (ไม่ใช่ `String`) เพราะมันแค่**อ่าน**เนื้อหาของ argument ไปคัดลอกต่อท้าย ไม่ได้ต้องการเป็น
เจ้าของ argument นั้นเลย — ตรงกับหลักการออกแบบพารามิเตอร์ที่เรียนใน Part 8 หัวข้อ 8.7 (ฟังก์ชัน/method ที่แค่ "อ่าน"
สตริง ควรรับ `&str` เพื่อความยืดหยุ่นสูงสุด) เพราะ `.push_str()` รับ `&str` จึงใช้ได้ทั้งกับ string literal และ
`&owned_string` ผ่าน deref coercion แบบเดียวกัน

#### ตัวดำเนินการ `+`: ทำงานผ่าน `impl Add<&str> for String` — และทำไมฝั่งซ้ายถูก "บริโภค"

Rust อนุญาตให้ต่อสตริงด้วย `+` ได้ แต่มีกฎที่เข้มงวดกว่าที่คิด:

```rust
fn main() {
    let s1 = String::from("Hello, ");
    let s2 = String::from("World!");

    let s3 = s1 + &s2; // สังเกต &s2 (ต้องมี & นำหน้า)
    println!("{s3}");
}
```

ผลลัพธ์: `Hello, World!`

ทำไมต้องมี `&` หน้า `s2` แต่ `s1` ไม่มี `&`? คำตอบอยู่ที่ signature จริงของ operator `+` สำหรับ `String` ซึ่งมาจาก
trait `Add` (trait ที่ทำให้ operator overloading เกิดขึ้นได้ — เราจะเรียนกลไก operator overloading แบบเต็มใน Part 19)
signature (ประมาณตามจริงใน std) หน้าตาแบบนี้:

```rust
// ประมาณ signature จริงของ std::ops::Add ที่ String implement ให้
// (หมายเหตุ: นี่คือโค้ดจำลองมาจาก source ภายใน std เพื่ออธิบายแนวคิดเท่านั้น
// คุณเขียน impl แบบนี้ในโค้ดของคุณเองไม่ได้ เพราะ orphan rule ของ Rust ห้าม
// implement trait ที่มาจากที่อื่น (std::ops::Add) ให้กับ type ที่มาจากที่อื่น (String)
// พร้อมกันทั้งคู่ — กฎนี้ใช้ได้เฉพาะเมื่ออย่างน้อยหนึ่งใน trait หรือ type เป็นของ crate
// ตัวเองเท่านั้น เราจะเจาะลึก orphan rule ใน Part 19 ตอนเรียน trait อย่างเป็นทางการ)
impl std::ops::Add<&str> for String {
    type Output = String;

    fn add(self, other: &str) -> String {
        todo!() // ในโค้ดจริงของ std คือ logic ต่อ bytes ของ other เข้าไปที่ปลาย buffer ของ self
    }
}
```

จุดที่สำคัญที่สุดคือ **`fn add(self, other: &str)`** — parameter แรก `self` **รับโดยค่า (by value) ไม่ใช่ by
reference** ซึ่งหมายความว่า **`s1 + &s2` เทียบเท่ากับการเรียก `s1.add(&s2)` ที่ `self` คือ `s1` แบบเต็มค่า** — และ
เพราะ `String` ไม่ implement `Copy` (จำได้จาก Part 6: ชนิดข้อมูลที่จองพื้นที่ heap ไม่มีทาง implement `Copy` ได้ เพราะ
การ copy จริง ๆ ต้อง clone heap buffer ด้วย ซึ่งมีค่าใช้จ่ายสูงเกินกว่าจะเกิดขึ้นแบบเงียบ ๆ) — **`s1` จึงถูก move
เข้าไปใน `add()` และไม่สามารถใช้งานต่อได้อีกหลังจากบรรทัดนี้**

มายืนยันด้วยการลองใช้ `s1` ต่อหลัง `+`:

```rust
fn main() {
    let s1 = String::from("Hello, ");
    let s2 = String::from("World!");

    let s3 = s1 + &s2;
    println!("{s3}");
    println!("{s1}"); // พยายามใช้ s1 ต่อ ทั้งที่ถูก move ไปแล้ว
}
```

โค้ดนี้ **compile ไม่ผ่าน** ด้วย error จริง:

```
error[E0382]: borrow of moved value: `s1`
 --> src/main.rs:6:20
  |
2 |     let s1 = String::from("Hello, ");
  |         -- move occurs because `s1` has type `String`, which does not implement the `Copy` trait
3 |     let s2 = String::from("World!");
4 |     let s3 = s1 + &s2;
  |              -- value moved here
5 |     println!("{s3}");
6 |     println!("{s1}"); // พยายามใช้ s1 ต่อ ทั้งที่ถูก move ไปแล้ว
  |                ^^ value borrowed here after move
  |
help: consider cloning the value if the performance cost is acceptable
  |
4 |     let s3 = s1.clone() + &s2;
  |                ++++++++
```

นี่คือ error แบบเดียวกันเป๊ะกับที่เรียนใน Part 6 ตอน `String` ถูก move — Rust ไม่ได้ปฏิบัติต่อ `+` เป็นกรณีพิเศษที่
"ยกเว้น" กฎ ownership เลยแม้แต่นิดเดียว มันเป็นแค่ syntax sugar ของการเรียก method `add(self, ...)` ธรรมดา ๆ ที่ยึด
กฎ ownership เดียวกันกับทุกฟังก์ชันในหลักสูตรนี้ **การออกแบบให้ `self` รับ by value แทน by reference ไม่ใช่เรื่อง
บังเอิญ** — มันมีเหตุผลด้าน performance ที่ชัดเจน: เพราะ `Add::add` ได้ความเป็นเจ้าของ `s1` มาเต็ม ๆ มันสามารถ**ใช้
heap buffer เดิมของ `s1` ต่อยอดโดยตรง** (ถ้า capacity เหลือพอ ก็แค่ต่อ bytes ของ `s2` เข้าไปที่ปลาย buffer เดิม โดย
ไม่ต้องจอง heap ใหม่เลย) ต่างจากถ้า signature เป็น `fn add(&self, ...)` ซึ่งจะบังคับให้ต้องจอง buffer ใหม่เสมอเพื่อ
คืนค่า `String` ใหม่ออกมาโดยไม่แก้ไข `self` เดิม (เพราะยืมมาแค่อ่าน แก้ไม่ได้) — การออกแบบแบบนี้จึงทำให้ `s1 + &s2 +
&s3 + &s4 + ...` ในเชิงทฤษฎีมีโอกาสได้ต้นทุนที่ต่ำกว่าการต่อสตริงทีละคู่ด้วยวิธีอื่นที่ต้อง clone ทุกครั้ง

**สรุปกฎที่ต้องจำ**: `+` สำหรับสตริงเขียนได้แค่รูปแบบ **`String + &str`** เท่านั้น (ฝั่งซ้ายต้อง `String` ที่เป็น
เจ้าของ ฝั่งขวาต้อง `&str` หรือ `&String` ที่ deref coercion เป็น `&str` ได้) เขียน `String + String` ตรง ๆ ไม่ได้:

```rust
fn main() {
    let s1 = String::from("Hello, ");
    let s2 = String::from("World!");
    let s3 = s1 + s2; // s2 ไม่มี & — ผิด type
    println!("{s3}");
}
```

```
error[E0308]: mismatched types
 --> src/main.rs:4:17
  |
4 |     let c = a + b; // ผิด: ต้องเป็น &b
  |                 ^ expected `&str`, found `String`
  |
help: consider borrowing here
  |
4 |     let c = a + &b; // ผิด: ต้องเป็น &b
  |                 +
```

(ข้อความ error ด้านบนเป็นผลจริงจาก `rustc` เมื่อรันโค้ดที่มีโครงสร้างเดียวกันนี้ — `expected &str, found String` บอก
ตรง ๆ ว่า `Add<&str> for String` ไม่รู้จัก `String` ตรง ๆ ฝั่งขวาเลย ต้องยืมด้วย `&` เสมอ)

#### `format!()`: ทางเลือกทั่วไปที่สุด ไม่มีปัญหาเรื่อง ownership เลย

เมื่อต้องต่อสตริงหลายส่วนเข้าด้วยกันในรูปแบบที่ซับซ้อนกว่าการต่อท้ายตรง ๆ macro `format!()` (ที่คุณคุ้นเคยกับพี่น้อง
ของมัน `println!()` มาตั้งแต่ Part 1) คือทางเลือกที่สะดวกและปลอดภัยที่สุด เพราะมันแค่**อ่าน** ค่าทุกตัวที่ส่งเข้าไป
(ไม่บริโภค ownership ของใครเลย) แล้วคืนค่าเป็น `String` ใหม่ทั้งก้อน:

```rust
fn main() {
    let s1 = String::from("Hello, ");
    let s2 = String::from("World!");

    let s3 = format!("{s1}{s2}"); // อ่าน s1, s2 เฉย ๆ ไม่ move ทั้งคู่
    println!("{s3}");

    // ยังใช้ s1, s2 ต่อได้ปกติ เพราะ format! ไม่ยึด ownership ไปจากใคร
    println!("s1 ยังใช้ได้: {s1}");
    println!("s2 ยังใช้ได้: {s2}");
}
```

ผลลัพธ์:

```
Hello, World!
s1 ยังใช้ได้: Hello, 
s2 ยังใช้ได้: World!
```

`format!()` เหมาะกับกรณีที่ (1) ต้องการต่อสตริงมากกว่า 2 ส่วนในบรรทัดเดียว (2) ต้องการแทรกค่าที่ไม่ใช่สตริงปนเข้าไป
ด้วย (ตัวเลข, `bool`, ชนิด custom ที่ implement `Display`/`Debug`) หรือ (3) ต้องการควบคุมการจัดรูปแบบ (padding,
ความแม่นยำทศนิยม ฯลฯ) ที่เรียนมาตั้งแต่การใช้ `println!()` — เพราะ `format!()` ใช้ syntax เดียวกันกับ `println!()`
ทุกประการ (ต่างกันแค่ `println!()` พิมพ์ออก stdout ทันที ส่วน `format!()` คืนค่าเป็น `String` ให้เราเก็บไปใช้ต่อ)

#### ตารางสรุปวิธีเติบโต `String`

| วิธี | รับ parameter ชนิดไหน | บริโภค (move) อะไรบ้าง | เหมาะกับกรณี |
|---|---|---|---|
| `.push(ch)` | `char` | ไม่บริโภคอะไร (`&mut self`) | เพิ่มตัวอักษรเดียว เช่นในลูปสร้างสตริงทีละตัว |
| `.push_str(s)` | `&str` | ไม่บริโภคอะไร (`&mut self`) | ต่อท้ายด้วยสตริงทั้งก้อน (สั้น ตรงไปตรงมา) |
| `a + &b` | `&str` ฝั่งขวา | **บริโภค `a` ทั้งตัว** | ต่อ 2 สตริงครั้งเดียว แล้วไม่ต้องใช้ตัวซ้ายอีก |
| `format!("{a}{b}")` | อะไรก็ได้ที่ `Display` | **ไม่บริโภคอะไรเลย** | ต่อหลายส่วน/ผสมชนิดข้อมูล/ควบคุม format |

หลักปฏิบัติทั่วไป: ใช้ `.push_str()`/`.push()` เมื่อกำลังสร้างสตริงขึ้นทีละส่วนใน `mut` binding เดิม, ใช้ `format!()`
เมื่อต้องการต่อหลายส่วนโดยไม่สนใจ ownership ของต้นทาง, และใช้ `+` เฉพาะกรณีที่ต่อ 2 ค่าครั้งเดียวและไม่ต้องใช้ค่าซ้าย
อีกแล้วจริง ๆ (พบน้อยกว่าอีกสามแบบในโค้ดจริง)

### 14.4 UTF-8 คืออะไรกันแน่: กฎการเข้ารหัสแบบ variable-width

จาก Part 8 หัวข้อ 8.4 เราเห็นแล้วว่าการ slice สตริงภาษาไทยผิดตำแหน่งทำให้ panic ด้วยข้อความ `byte index 1 is not a
char boundary` — ตอนนี้เราจะเจาะลึกว่า **ทำไม** ปัญหานี้ถึงเกิดขึ้นได้ โดยเข้าใจกฎการเข้ารหัส UTF-8 อย่างจริงจัง

**Unicode** คือมาตรฐานที่กำหนด "หมายเลขประจำตัว" (เรียกว่า **code point**) ให้กับตัวอักษรทุกตัวในโลก ตั้งแต่ `U+0000`
ถึง `U+10FFFF` (รวมกว่าล้านตำแหน่ง แม้จะไม่ได้ใช้ทั้งหมด) — แต่ Unicode เป็นแค่ "การกำหนดหมายเลข" เท่านั้น มันไม่ได้
บอกว่า**จะเก็บหมายเลขเหล่านี้ในหน่วยความจำ/ไฟล์เป็น bytes ยังไง** — นี่คือหน้าที่ของ **encoding** ซึ่ง UTF-8 คือ
encoding ที่ Rust เลือกใช้เป็นค่า default สำหรับ `String`/`&str` ทั้งหมด (และเป็น encoding ที่ใช้แพร่หลายที่สุดใน
โลกอินเทอร์เน็ตปัจจุบันด้วย)

**กฎของ UTF-8** คือ **encoding แบบความยาวแปรผัน (variable-width)** — ตัวอักษรแต่ละตัวใช้ตั้งแต่ **1 ถึง 4 bytes**
ขึ้นอยู่กับว่า code point ของมันอยู่ในช่วงไหน:

| ช่วง code point | จำนวน bytes ที่ใช้ | ตัวอย่างตัวอักษร |
|---|---|---|
| `U+0000` – `U+007F` | 1 byte | ตัวอักษร ASCII ทั้งหมด (a-z, A-Z, 0-9, สัญลักษณ์พื้นฐาน) |
| `U+0080` – `U+07FF` | 2 bytes | อักษรละตินเสริม (é, ñ), อักษรกรีก, ซีริลลิก, **อักษรอาหรับ, ฮีบรู** |
| `U+0800` – `U+FFFF` | 3 bytes | **อักษรไทยทั้งหมด**, อักษรจีน/ญี่ปุ่น/เกาหลี (CJK) ส่วนใหญ่ |
| `U+10000` – `U+10FFFF` | 4 bytes | emoji ส่วนใหญ่ (😻, 🚀), อักษรจีนโบราณหายาก |

สิ่งที่ต้องสังเกตทันที: **อักษรไทยทั้งหมดตกอยู่ในช่วง 3 bytes** (Thai script อยู่ใน Unicode block `U+0E00`–`U+0E7F`
ซึ่งอยู่ในช่วง `U+0800`–`U+FFFF`) — นี่คือเหตุผลที่ตัวอย่างในหัวข้อ 8.4 ใช้ 3 bytes ต่อตัวอักษรไทย 1 ตัวอย่างสม่ำเสมอ
ต่างจากภาษาอังกฤษที่ใช้แค่ 1 byte เท่านั้น (3 เท่า!) — โปรแกรมที่คำนวณ "ความยาวข้อความ" โดยใช้จำนวน byte ตรง ๆ
(เช่น จำกัดความยาวข้อความไว้ที่ N bytes) จะได้ผลลัพธ์ที่ผิดเพี้ยนอย่างมากเมื่อใช้กับภาษาไทย เพราะ 30 ตัวอักษรไทย
ใช้พื้นที่ประมาณ 90 bytes ในขณะที่ 30 ตัวอักษรอังกฤษใช้แค่ 30 bytes เท่านั้น

#### กลไกที่ทำให้ UTF-8 "แยกขอบตัวอักษรได้เอง" โดยไม่ต้องรู้ล่วงหน้าว่าอ่านมาจากไหน

จุดที่ทำให้ UTF-8 ฉลาดกว่า encoding แบบ fixed-width (เช่น UTF-32 ที่ใช้ 4 bytes ตายตัวทุกตัวอักษร) คือ **byte แรก
ของแต่ละตัวอักษรมี "ลายเซ็น" (bit pattern) บอกทันทีว่าตัวอักษรนี้ยาวกี่ bytes**:

- byte ที่ขึ้นต้นด้วย bit `0.......` (คือค่า 0-127) → เป็นตัวอักษร ASCII ยาว 1 byte เท่านั้น (byte เดียวจบ)
- byte ที่ขึ้นต้นด้วย bit `110.....` → เป็น**byte แรก**ของตัวอักษรยาว 2 bytes
- byte ที่ขึ้นต้นด้วย bit `1110....` → เป็น**byte แรก**ของตัวอักษรยาว 3 bytes (**นี่คือ pattern ของอักษรไทย!**)
- byte ที่ขึ้นต้นด้วย bit `11110...` → เป็น**byte แรก**ของตัวอักษรยาว 4 bytes
- byte ที่ขึ้นต้นด้วย bit `10......` → เป็น **continuation byte** (ไม่ใช่จุดเริ่มต้นของตัวอักษรใหม่ แต่เป็น byte
  ที่ 2, 3, หรือ 4 ของตัวอักษรที่เริ่มก่อนหน้านี้)

นี่คือกฎที่ compiler/runtime ของ Rust ใช้ตรวจสอบว่า "ตำแหน่ง byte นี้เป็นจุดเริ่มต้นของตัวอักษรใหม่หรือไม่" (เรียกว่า
**character boundary**) — ทุกครั้งที่คุณ slice สตริงด้วย `&s[a..b]` Rust จะเช็คว่า `a` และ `b` **ทั้งคู่**ตกอยู่ที่
byte ที่มี bit pattern แบบ "จุดเริ่มต้นตัวอักษร" (ไม่ใช่ `10......`) เท่านั้น — ถ้าตำแหน่งใดตำแหน่งหนึ่งตกอยู่ตรง
continuation byte (คือ "กลาง" ตัวอักษรหลาย byte) มันจะ panic ทันทีตามที่เห็นใน Part 8

มาดู bytes จริงของคำว่า "สวัสดี" (ที่ Part 8 ใช้เป็นตัวอย่าง) โดยแปลงเป็นเลขฐาน 2 เพื่อยืนยัน pattern ข้างบน:

```rust
fn main() {
    let greeting = "สวัสดี";
    for b in greeting.bytes() {
        println!("{:>3} = {:08b}", b, b);
    }
}
```

ผลลัพธ์บางส่วน (3 bytes แรก ซึ่งคือตัวอักษร "ส" ตัวเดียว):

```
224 = 11100000
184 = 10111000
170 = 10101010
```

ตรงตามที่คาด: **byte แรก `11100000` ขึ้นต้นด้วย `1110`** (สัญลักษณ์ของตัวอักษร 3 bytes) และ **อีกสอง byte ถัดมาขึ้น
ต้นด้วย `10`** (continuation bytes) — ถ้าคุณ slice ที่ตำแหน่ง byte 1 (`&greeting[0..1]`) คุณจะได้ byte เดียว
(`11100000`) ที่ไม่ครบตัวอักษร และถ้าคุณ slice ที่ byte 2 (`&greeting[0..2]`) คุณก็ยังไม่ครบ (ขาด byte สุดท้าย)
มีแค่ตำแหน่ง byte 0 หรือ byte 3 (จุดเริ่มต้นของตัวอักษรถัดไป) เท่านั้นที่เป็น character boundary ที่ถูกต้องรอบตัวอักษร
"ส" นี้ — Rust ตรวจสอบเรื่องนี้ให้เราโดยอัตโนมัติทุกครั้งที่ slice และ panic ทันทีถ้าผิดกฎ **ไม่มีทาง**ที่ Rust จะ
ยอมให้คุณสร้าง `&str` ที่มีข้อมูลผิดกฎ UTF-8 ผ่านการ slice ธรรมดาได้เลย (ต่างจากภาษาที่จัดการ byte แบบดิบ ๆ อย่าง C
ที่การตัดสตริงกลางตัวอักษรจะไม่มี error อะไรเลย แค่ได้ข้อมูลเสีย ๆ ออกมาแบบเงียบ ๆ — Rust เลือกที่จะ panic ให้เห็นชัด
ๆ ทันที ดีกว่าปล่อยให้ข้อมูลเสียหลุดออกไปโดยไม่รู้ตัว)

### 14.5 ตัวอักษรไทยกับ Combining Marks: ทำไม `.chars().count()` นับได้ไม่เท่ากับที่ตาเห็น

ตอนนี้เรามาถึงหัวข้อที่สำคัญที่สุดของบทนี้สำหรับหลักสูตรภาษาไทยโดยเฉพาะ — และเป็นเรื่องที่ตำราภาษา Rust ภาษาอังกฤษ
ส่วนใหญ่ไม่เคยต้องพูดถึงอย่างจริงจัง เพราะภาษาอังกฤษไม่มีปัญหานี้

จาก Part 3 เราเรียนว่า `char` ใน Rust แทน **1 Unicode Scalar Value เต็มรูปแบบเสมอ** และจาก Part 8 หัวข้อ 8.4 เราเห็น
ตัวอย่างที่ `.chars()` แยก "สวัสดี" ออกมาเป็น `[ส][ว][ั][ส][ด][ี]` — สังเกตว่ามี **6 ช่อง** ทั้งที่คำว่า "สวัสดี" ตอน
มองด้วยตาดูเหมือนมี **5 ตัวอักษร** (ส-ว-ั-ส-ดี ไม่ใช่ ส-ว-ั-ส-ด-ี) ทำไมถึงเป็นแบบนั้น?

คำตอบอยู่ที่โครงสร้างของอักษรไทยในระบบ Unicode: **อักษรไทยประกอบด้วยพยัญชนะฐาน (base consonant) และเครื่องหมาย
กำกับเสียง/สระที่ "ลอย" อยู่เหนือหรือใต้พยัญชนะ (combining marks)** เช่น **ไม้หันอากาศ (ั)**, **วรรณยุกต์ (่ ้ ๊ ๋)**,
**สระบน (ิ ี ึ ื)**, **สระล่าง (ุ ู)** — สิ่งเหล่านี้ในระบบ Unicode ถูกกำหนดให้เป็น **code point แยกเป็นของตัวเอง
ต่างหากจากพยัญชนะที่มันเกาะอยู่** เมื่อ**แสดงผล**บนหน้าจอ ระบบ rendering (font renderer ของ OS/browser) จะนำ
combining mark เหล่านี้มาวางซ้อนทับกับพยัญชนะข้างหน้าให้ดูเหมือนเป็น "ตัวอักษรเดียว" แต่ **ในทาง Unicode/ในทาง
memory มันคือ scalar value 2 ตัวที่แยกกันอย่างสิ้นเชิง** — คำว่า "วั" ที่ตาเห็นเป็นหนึงตัวอักษร จึงประกอบด้วย
`char` สองตัวคือ `'ว'` (U+0E27) และ `'ั'` (U+0E31, ไม้หันอากาศ) ต่อกัน

ลองพิสูจน์เรื่องนี้ให้ชัดเจนที่สุดด้วยคำว่า **"ก่อน"** ซึ่งเป็นคำง่าย ๆ ที่คนไทยมองแล้วนับได้ทันทีว่ามี **3 ตัวอักษร
ที่มองเห็น** (ก่, อ, น):

```rust
fn main() {
    let word = "ก่อน";

    println!("จำนวน Unicode scalar values (.chars().count()): {}", word.chars().count());
    println!("จำนวน bytes (.len()): {}", word.len());

    for (i, ch) in word.chars().enumerate() {
        println!("  chars()[{i}] = {:?}  (U+{:04X})", ch, ch as u32);
    }
}
```

ผลลัพธ์จริง (รันผ่าน `rustc --edition 2021` และ compile/execute จริงเพื่อยืนยันตัวเลข ไม่ใช่การเดา):

```
จำนวน Unicode scalar values (.chars().count()): 4
จำนวน bytes (.len()): 12
  chars()[0] = 'ก'  (U+0E01)
  chars()[1] = '\u{e48}'  (U+0E48)
  chars()[2] = 'อ'  (U+0E2D)
  chars()[3] = 'น'  (U+0E19)
```

**นี่คือตัวเลขจริงที่ยืนยันแล้ว ไม่ใช่การเดา**: `.chars().count()` ของ `"ก่อน"` คือ **4** ไม่ใช่ 3 อย่างที่คนไทยจะนับ
ด้วยตา — เพราะ `char` ตัวที่สอง (`'\u{e48}'`) คือ **ไม้เอก (่)** ซึ่ง Unicode กำหนดเป็น scalar value `U+0E48` แยก
ต่างหากจาก `'ก'` (U+0E01) พยัญชนะข้างหน้ามันโดยสิ้นเชิง — เมื่อ render ออกมา ไม้เอกจะถูกวางซ้อนไว้เหนือ "ก" ให้ดู
เหมือนตัวอักษรเดียวคือ "ก่" แต่ในความเป็นจริงทาง Unicode มันคือ **`char` 2 ตัวติดกัน**

ผลกระทบตรง ๆ ของเรื่องนี้: **`s.chars().count()` ไม่ใช่ "จำนวนตัวอักษรที่มองเห็น" เสมอไปสำหรับข้อความไทย** มันคือ
"จำนวน Unicode scalar value" ซึ่งเป็นแนวคิดที่ต่างออกไป ถ้าคุณเขียนโค้ดที่สมมติว่า `.chars().count()` เท่ากับจำนวน
ตัวอักษรที่ผู้ใช้มองเห็น (เช่น ระบบจำกัดจำนวนตัวอักษรในกล่องข้อความ, การนับความยาวชื่อผู้ใช้) คุณจะได้ผลลัพธ์ที่
"ดูเหมือนสั้นกว่าที่ควร" เสมอเมื่อข้อความมีวรรณยุกต์/สระลอยปนอยู่ — และภาษาไทยเกือบทุกประโยคมีสิ่งเหล่านี้ปนอยู่
เป็นปกติ ไม่ใช่กรณีพิเศษที่พบยาก

#### แนวคิด "Grapheme Cluster": สิ่งที่ตรงกับสัญชาตญาณของมนุษย์จริง ๆ

สิ่งที่คนไทย (หรือมนุษย์ทั่วไป) "นับว่าเป็น 1 ตัวอักษร" ในทาง Unicode มีชื่อเรียกอย่างเป็นทางการว่า **grapheme
cluster** — คือกลุ่มของ scalar value หนึ่งตัวหรือมากกว่า ที่มนุษย์**รับรู้ว่าเป็นหน่วยเดียวกันเมื่อมองด้วยตา**
สำหรับคำว่า "ก่อน" grapheme cluster ที่ถูกต้องคือ `["ก่", "อ", "น"]` (3 clusters) ซึ่งตรงกับสัญชาตญาณของคนไทยเป๊ะ ๆ
แต่**Rust standard library ไม่มี concept ของ grapheme cluster ให้ใช้เลย** — ไม่มี method ชื่อ `.graphemes()` หรือ
`nth_grapheme()` ใด ๆ ทั้งสิ้นใน `std`

#### ทำไม std ถึง**ตั้งใจ**ไม่มี grapheme cluster ให้ใช้

นี่ไม่ใช่ความบกพร่องที่ทีม Rust "ลืมทำ" แต่เป็นการตัดสินใจด้านการออกแบบที่ตั้งใจ เหตุผลหลักคือ **การแบ่ง grapheme
cluster ที่ถูกต้อง 100% ต้องพึ่งพากฎที่ซับซ้อนและ (ในบางกรณี) ขึ้นกับภาษา/locale** มาตรฐานที่ใช้กำหนดกฎนี้คือ
**Unicode Text Segmentation (UAX #29)** ซึ่งมีรายละเอียดจำนวนมาก (เช่น กฎการรวม emoji ที่มี modifier สีผิว, กฎการ
รวมตัวอักษรเกาหลี Hangul, กฎเฉพาะของอักษรอินเดียบางตระกูล) — กฎเหล่านี้ **เปลี่ยนแปลงและปรับปรุงตามเวอร์ชันของ
Unicode ที่อัปเดตทุกปี** ซึ่งขัดกับปรัชญาของ Rust std ที่ต้องการ **เสถียรภาพ (stability) ระดับสูงสุด** — เมื่อ
API หนึ่งอยู่ใน std แล้ว มันแทบจะเปลี่ยนพฤติกรรมไม่ได้เลยตลอดกาล (Rust สัญญาความ backward compatibility ที่เข้มงวด
มาก) แต่กฎการแบ่ง grapheme cluster ที่ถูกต้องกลับต้องอัปเดตตามข้อมูล Unicode ที่เปลี่ยนไปเรื่อย ๆ — การผูก concept
ที่เปลี่ยนแปลงได้ไว้กับ std ที่ต้องนิ่งตลอดกาล จึงเป็นทางเลือกที่ไม่เหมาะสม

เหตุผลรองอีกข้อคือ **ขนาดของข้อมูลตาราง Unicode segmentation มีขนาดใหญ่พอสมควร** (ต้องอ้างอิงตาราง property ของ
ทุก code point ที่มีในระบบ) ซึ่งจะทำให้ทุกโปรแกรม Rust (ไม่ว่าจะใช้ฟีเจอร์นี้หรือไม่) ต้องพก binary ที่หนักขึ้นถ้า
ฝังไว้ใน std ตรงกับปรัชญา **"pay only for what you use"** ที่ Rust ยึดถือมาตลอดทั้งหลักสูตร (เราเห็นแนวคิดนี้ตอน
zero-cost abstraction ใน Part 1 และ 3) — ทีม Rust จึงเลือกแยก concept นี้ออกไปเป็น **crate ภายนอก** ที่คนเลือกใช้
เฉพาะเมื่อจำเป็นจริง ๆ

crate มาตรฐานของ ecosystem สำหรับงานนี้ชื่อ **`unicode-segmentation`** (ดูแลโดยทีม `unicode-rs` ซึ่งเป็นกลุ่มเดียว
กับที่ดูแล crate สำคัญด้าน Unicode อื่น ๆ ของ Rust ecosystem) มันมี method ชื่อ `.graphemes(true)` ที่คืน iterator
ของ grapheme cluster ที่ถูกต้องตามมาตรฐาน UAX #29 จริง ๆ — บทนี้จะ**ไม่สอนวิธีใช้ crate นี้แบบเจาะลึก** (เพราะยัง
ไม่ได้เรียนเรื่อง external crate/`Cargo.toml` dependency อย่างเป็นทางการจนกว่าจะถึง Part 17) แต่ควรรู้จักไว้ว่า
**ถ้าคุณต้องเขียนโปรแกรมที่ต้อง "นับตัวอักษรที่มองเห็นจริง ๆ" สำหรับข้อความไทย (หรือภาษาที่มี combining mark อื่น ๆ
เช่น ภาษาเวียดนาม, ภาษาฮินดี, ภาษาอาหรับ) อย่างถูกต้อง 100% ทางออกที่ถูกต้องคือใช้ `unicode-segmentation` ไม่ใช่
`.chars().count()`** — สำหรับตอนนี้ (ยังไม่มี external crate) จำหลักไว้ว่า: **`.chars().count()` นับ Unicode
scalar value ไม่ใช่ตัวอักษรที่มองเห็น และสำหรับข้อความไทยตัวเลขทั้งสองนี้มักไม่เท่ากัน**

#### ตัวอย่างที่แสดงผลกระทบเชิงปฏิบัติ: การนับความยาวเพื่อจำกัด input

```rust
fn main() {
    let name1 = "สมชาย";      // ไม่มี combining mark เลย
    let name2 = "น้องพลอย";   // มีวรรณยุกต์ (ไม้โท บน "น" ตัวแรก)

    println!("'{}' -> chars = {}", name1, name1.chars().count());
    println!("'{}' -> chars = {}", name2, name2.chars().count());
}
```

ผลลัพธ์จริง:

```
'สมชาย' -> chars = 5
'น้องพลอย' -> chars = 8
```

`"สมชาย"` มี 5 ตัวอักษรที่มองเห็น และ `.chars().count()` ก็ได้ 5 พอดี (เพราะไม่มี combining mark เลยในคำนี้) แต่
`"น้องพลอย"` ที่คนไทยนับด้วยตาได้ **7 ตัวอักษร** (น้-อ-ง-พ-ล-อ-ย) กลับได้ `.chars().count()` เท่ากับ **8** เพราะ
"น้" ประกอบด้วย `char` สองตัว (น + ไม้โท) — ถ้าระบบของคุณจำกัดให้ชื่อผู้ใช้ยาวไม่เกิน N ตัวอักษรโดยเช็คด้วย
`.chars().count() <= n` ผู้ใช้ที่ตั้งชื่อมีวรรณยุกต์มากจะรู้สึกว่า "ระบบนับตัวอักษรผิด" เพราะสิ่งที่พวกเขามองว่า
7 ตัวอักษร ระบบกลับมองว่ายาว 8 หน่วย — เป็นตัวอย่างที่จับต้องได้ว่าทำไมความเข้าใจเรื่องนี้จึงสำคัญมากสำหรับ
นักพัฒนาที่เขียนระบบรองรับภาษาไทย

### 14.6 สามมุมมองของสตริง: `.bytes()`, `.chars()`, และเหตุผลที่ไม่มี "grapheme ตัวที่ N"

Rust ให้เรามองสตริงเดียวกันได้ 3 ระดับความละเอียดต่างกัน แต่ละแบบเหมาะกับงานคนละประเภท มาดูทั้งสามแบบพร้อมกันกับ
คำว่า `"ก่อน"` เพื่อเห็นความแตกต่างชัด ๆ:

```rust
fn main() {
    let word = "ก่อน";

    print!("bytes():         ");
    for b in word.bytes() {
        print!("{b} ");
    }
    println!();

    print!("chars():         ");
    for c in word.chars() {
        print!("{c:?} ");
    }
    println!();

    print!("char_indices():  ");
    for (i, c) in word.char_indices() {
        print!("({i},{c:?}) ");
    }
    println!();
}
```

ผลลัพธ์จริง:

```
bytes():         224 184 129 224 184 136 224 184 173 224 184 153 
chars():         'ก' '\u{e48}' 'อ' 'น' 
char_indices():  (0,'ก') (3,'\u{e48}') (6,'อ') (9,'น') 
```

- **`.bytes()`** — คืน iterator ของ `u8` ดิบ ๆ ตามที่เก็บอยู่จริงใน memory (12 ค่า สำหรับคำนี้ที่มี 4 ตัวอักษร ×
  3 bytes ต่อตัว) ใช้เมื่อต้องทำงานระดับ byte จริง ๆ (เช่น เขียนไฟล์, ส่งผ่าน network, คำนวณ checksum) — **นี่คือ
  ระดับที่ "เร็วที่สุด" เพราะไม่ต้องตีความอะไรเลย ตรงไปตรงมาที่สุด**
- **`.chars()`** — คืน iterator ของ `char` (Unicode scalar value, 4 ค่า) ใช้เมื่อต้องการทำงานที่เกี่ยวกับ "ตัวอักษร"
  ในความหมายของ Unicode เช่นตรวจว่าเป็นตัวเลข/ตัวอักษร (`.is_numeric()`, `.is_alphabetic()`) หรือแปลงตัวพิมพ์
  (`.to_uppercase()` ระดับ `char` เดี่ยว) — **แต่อย่างที่เห็นในหัวข้อ 14.5 นี่ไม่ใช่ "จำนวนตัวอักษรที่มองเห็น"
  เสมอไปสำหรับภาษาไทย**
- **`.char_indices()`** — คืน iterator ของ **`(usize, char)`** คือคู่ของ "ตำแหน่ง byte ที่ตัวอักษรนี้เริ่ม" กับ
  ตัว `char` เอง (ตำแหน่ง 0, 3, 6, 9 ตรงกับที่แต่ละตัวอักษรไทยกิน 3 bytes) นี่คือเครื่องมือสำคัญที่จะใช้แก้ปัญหา
  "หาตำแหน่ง byte ที่ปลอดภัยสำหรับ slice" ในหัวข้อ 14.10 — มันให้ทั้งตัวอักษรและตำแหน่งของมันพร้อมกันในครั้งเดียว
  โดยไม่ต้องคำนวณเองด้วยมือเลย

สังเกตว่า**ไม่มีตัวเลือกที่ 4** สำหรับ "grapheme cluster ตัวที่ N" ตามที่อธิบายเหตุผลไว้แล้วในหัวข้อ 14.5 — Rust
บังคับให้คุณเลือกระหว่างมุมมองที่ "แม่นยำระดับ byte" (`.bytes()`) กับมุมมองที่ "แม่นยำระดับ Unicode scalar value"
(`.chars()`/`.char_indices()`) เท่านั้น เพราะทั้งสองระดับนี้มีนิยามที่**ตายตัวและไม่เปลี่ยนแปลงตามเวลา** (กฎ UTF-8
เข้ารหัสอย่างไร และ Unicode scalar value คืออะไร เป็นสิ่งที่นิยามไว้ตายตัวใน spec) ต่างจาก grapheme cluster ที่กฎ
การแบ่งอาจเปลี่ยนได้ตามเวอร์ชัน Unicode ใหม่ ๆ ที่ออกมา ตามที่อธิบายไปแล้ว

### 14.7 ทำไม `s[0]` compile ไม่ผ่าน: การออกแบบที่ตั้งใจ ไม่ใช่ข้อจำกัด

จาก Part 13 เราคุ้นเคยกับการ index `Vec<T>`/array ด้วย `[]` ตรง ๆ อย่าง `numbers[0]` ได้ทันที — คำถามที่ผู้เรียนใหม่
ถามบ่อยที่สุดตอนเจอ `String` ครั้งแรกคือ "ทำไม `s[0]` ถึงใช้ไม่ได้บ้าง?" มาดู error จริงกัน:

```rust
fn main() {
    let s = String::from("hello");
    let c = s[0];
    println!("{}", c);
}
```

ผลลัพธ์จาก `rustc` จริง:

```
error[E0277]: the type `str` cannot be indexed by `{integer}`
 --> src/main.rs:3:15
  |
3 |     let c = s[0];
  |               ^ string indices are ranges of `usize`
  |
  = help: the trait `SliceIndex<str>` is not implemented for `{integer}`
  = note: you can use `.chars().nth()` or `.bytes().nth()`
          for more information, see chapter 8 in The Book: <https://doc.rust-lang.org/book/ch08-02-strings.html#indexing-into-strings>
  = note: required for `String` to implement `Index<{integer}>`
```

(สังเกตว่า error พูดถึง type `str` ไม่ใช่ `String` ตรง ๆ — เป็นเพราะ `s[0]` deref coercion จาก `String` ไปเป็น
`str` ก่อนตรวจสอบ index ตามหลักการ deref coercion ที่เรียนใน Part 8 หัวข้อ 8.7 แต่บรรทัดสุดท้ายของ error ยืนยัน
ตรง ๆ ว่า `required for String to implement Index<{integer}>` — ข้อจำกัดนี้จึงครอบคลุมทั้ง `String` และ `&str`
เหมือนกันทั้งคู่)

เทียบกับ error ตอนพยายาม index array ด้วยชนิดที่ไม่ใช่ `usize` จาก Part 3:

```
error[E0277]: the type `[i32]` cannot be indexed by `i32`
 --> src/main.rs:4:22
  |
4 |     println!("{}", numbers[index]);
  |                      ^^^^^^^^^^^^ slice indices are of type `usize` or ranges of `usize`
```

สังเกตความคล้ายกันของ error message ทั้งสองแบบ ("cannot be indexed by") — แต่มีความแตกต่างเชิงสาระสำคัญ: **error
ของ array บอกว่า "ต้องใช้ `usize` แทน `i32`"** (แค่ผิด**ชนิด**ของ index เฉย ๆ ถ้าเปลี่ยนเป็น `usize` ก็ compile ผ่าน
ทันที) แต่ **error ของ `String` บอกว่า "ไม่มี `SliceIndex<str>` implement ให้ตัวเลขจำนวนเต็มเลยแม้แต่ตัวเดียว"** —
ถ้าคุณเปลี่ยน `s[0]` เป็น `s[0usize]` ก็**ยังไม่ compile ผ่าน** เพราะ Rust **ไม่มีทาง** ให้ index สตริงด้วยตัวเลข
เดี่ยว ๆ ได้เลยไม่ว่าจะเป็นชนิดไหนก็ตาม (แต่ index ด้วย **range** เช่น `s[0..1]` compile ได้ ตราบใดที่ตรง
character boundary ตามที่เรียนในหัวข้อ 14.4 — นี่คือความแตกต่างที่สำคัญ)

#### เหตุผลเชิงลึก: O(1) byte index ≠ O(1) character index

นี่คือแก่นสำคัญที่สุดของการออกแบบนี้ **สำหรับ `Vec<T>`/array การ index ด้วยตำแหน่งเป็นปฏิบัติการที่ O(1) เสมอ**
เพราะสมาชิกทุกตัวมีขนาดเท่ากัน (`T` ตายตัว) — ถ้ารู้ว่าต้องการสมาชิกตัวที่ `i` ก็แค่คำนวณ `ptr + i * size_of::<T>()`
ได้ตรง ๆ ไม่ต้องอ่านข้อมูลอะไรมาก่อนเลย

แต่สำหรับ `String` การเข้ารหัสแบบ UTF-8 เป็น **variable-width** ตามที่เรียนในหัวข้อ 14.4 — ตัวอักษรตัวที่ 1 อาจใช้
1 byte แต่ตัวที่ 2 อาจใช้ 3 bytes แล้วตัวที่ 3 อาจใช้ 1 byte อีก **ไม่มีทางรู้ว่า "ตัวอักษรที่ N" อยู่ที่ byte ไหน
โดยไม่อ่านและตีความ bytes ทั้งหมดตั้งแต่ต้นสตริงมาก่อน** — ถ้า Rust ยอมให้เขียน `s[5]` แล้วตีความว่า "ตัวอักษรตัวที่ 5"
มันจะกลายเป็น operation ที่ **O(n)** (ต้องเดิน bytes จากต้นสตริงมาเรื่อย ๆ จนกว่าจะนับครบ 5 ตัวอักษร) **ซึ่งขัดกับ
สัญชาตญาณของโปรแกรมเมอร์ทุกคนที่คุ้นเคยว่า `[]` คือ operation ที่เร็วมาก (O(1)) เสมอ** — Rust มองว่าการเปิดช่องให้
เขียน syntax ที่ "ดูเหมือนเร็ว" แต่จริง ๆ ช้า (O(n)) แบบเงียบ ๆ โดยไม่มีสัญญาณเตือนอะไรเลย **เป็นการหลอกผู้เขียนโค้ด
โดยไม่ตั้งใจ** และอาจนำไปสู่บั๊กด้าน performance ที่ซ่อนอยู่ลึกมาก (เช่น loop ที่เขียน `for i in 0..s.len() { s[i]
}` จะกลายเป็น O(n²) โดยที่คนเขียนไม่รู้ตัวเลย ถ้า Rust ยอมให้ทำแบบนั้นได้)

นี่คือเหตุผลที่ Rust **บังคับให้คุณเลือกวิธีอย่างชัดเจน** ตาม error message ที่บอกไว้ (`.chars().nth()` หรือ
`.bytes().nth()`) — ทั้งสองแบบ**ก็ยังเป็น O(n) เหมือนกัน** แต่การต้องเขียน `.chars().nth(5)` ตรง ๆ (แทนที่จะเขียน
`s[5]` สั้น ๆ) ทำให้**เห็นได้ชัดในโค้ดว่านี่คือ operation ที่ต้องเดินอ่านสตริงทั้งหมด** ไม่ใช่ operation ที่ดูเผิน ๆ
เหมือนเร็วแต่จริง ๆ ช้า — Rust เลือก **ความชัดเจนของ cost model** มากกว่า **ความสะดวกของ syntax สั้น ๆ** ซึ่งเป็น
แนวคิดเดียวกันกับที่เห็นซ้ำ ๆ ทั้งหลักสูตรนี้ (เทียบกับ `mut`-by-default ที่ปฏิเสธใน Part 3, หรือ borrow checker
ที่ปฏิเสธ dangling reference ใน Part 7-8)

```rust
fn main() {
    let word = "ก่อน";

    // ต้องเขียนแบบนี้ตรง ๆ — เห็นชัดว่าเป็น O(n)
    let third_char: Option<char> = word.chars().nth(2);
    println!("{:?}", third_char);
}
```

ผลลัพธ์: `Some('อ')`

### 14.8 Method จัดการข้อความที่ใช้บ่อยที่สุดของ `str`

หัวข้อนี้จะรวบรวม method ของ `str` ที่ใช้บ่อยที่สุดในงานจริง — ทั้งหมดทำงานอย่างปลอดภัยกับ UTF-8 โดยอัตโนมัติ
(ไม่ต้องกังวลเรื่อง character boundary panic เลย เพราะ method เหล่านี้จัดการ boundary ให้ถูกต้องเสมอข้างใน)

#### `.split(delimiter)`: แบ่งสตริงตามตัวคั่น

```rust
fn main() {
    let csv_line = "สมชาย,30,กรุงเทพ";
    let fields: Vec<&str> = csv_line.split(',').collect();
    println!("{:?}", fields);
}
```

ผลลัพธ์: `["สมชาย", "30", "กรุงเทพ"]`

`.split()` คืน iterator ของ `&str` (slice ที่ยืมมาจากสตริงต้นทาง ไม่ได้ copy ข้อมูลใหม่เลย — ตรงกับหลักการ slice
จาก Part 8) รับ delimiter ได้หลายรูปแบบ (`char` เดี่ยว, `&str` ทั้งก้อน, หรือแม้แต่ closure ที่เรียนใน Part 24)
`.collect()` (ที่จะเจาะลึกใน Part 25-26) ใช้รวบรวม iterator ให้เป็น `Vec<&str>` ตัวจริง

#### `.split_whitespace()`: แบ่งตามช่องว่างและยุบช่องว่างซ้ำอัตโนมัติ

```rust
fn main() {
    let messy = "สวัสดี   Rust    คือภาษาที่ดี  มาก";
    let words: Vec<&str> = messy.split_whitespace().collect();
    println!("{:?}", words);
    println!("จำนวนคำ: {}", words.len());
}
```

ผลลัพธ์:

```
["สวัสดี", "Rust", "คือภาษาที่ดี", "มาก"]
จำนวนคำ: 4
```

ต่างจาก `.split(' ')` ตรง ๆ ซึ่งจะสร้าง `&str` ว่างเปล่าขึ้นมาทุกครั้งที่เจอช่องว่างติดกันหลายตัว (เช่น `"a  b".
split(' ')` จะได้ `["a", "", "b"]` เพราะเจอ 2 ช่องว่างติดกัน) — **`.split_whitespace()` ยุบช่องว่างต่อเนื่อง (ไม่ว่า
จะเป็น space, tab, newline กี่ตัวติดกันก็ตาม) ให้เหลือเป็นตัวคั่นเดียวโดยอัตโนมัติ และไม่สร้าง `&str` ว่างเปล่าปน
เข้ามาเลย** ทำให้เหมาะกับการนับคำในข้อความจริงที่ผู้ใช้พิมพ์เข้ามา (ซึ่งมักมีช่องว่างเกินโดยไม่ตั้งใจ) มากกว่า
`.split(' ')`

#### `.lines()`: แบ่งตามบรรทัด

```rust
fn main() {
    let report = "รายงานประจำวัน\nยอดขาย: 1500\nลูกค้า: 42";
    for line in report.lines() {
        println!("บรรทัด: [{line}]");
    }
}
```

ผลลัพธ์:

```
บรรทัด: [รายงานประจำวัน]
บรรทัด: [ยอดขาย: 1500]
บรรทัด: [ลูกค้า: 42]
```

`.lines()` แบ่งตาม `\n` (และจัดการ `\r\n` แบบ Windows ให้ถูกต้องอัตโนมัติ ไม่เหลือ `\r` ติดท้ายบรรทัดเลย) — สะดวก
มากเมื่อประมวลผลไฟล์ text หรือ log ที่มีหลายบรรทัด

#### `.trim()`, `.trim_start()`, `.trim_end()`: ตัดช่องว่างที่ขอบ

```rust
fn main() {
    let padded = "   สวัสดี Rust   ";

    println!("[{}]", padded.trim_start()); // ตัดซ้ายเท่านั้น
    println!("[{}]", padded.trim_end());   // ตัดขวาเท่านั้น
    println!("[{}]", padded.trim());       // ตัดทั้งสองข้าง
}
```

ผลลัพธ์จริง:

```
[สวัสดี Rust   ]
[   สวัสดี Rust]
[สวัสดี Rust]
```

ทั้งสาม method คืนค่าเป็น **`&str` ที่ยืมมาจากต้นฉบับ ไม่ได้ copy ข้อมูลใหม่** (เหมือนกับ slice ทุกตัวที่เรียนมา
จาก Part 8) — มันแค่ขยับตำแหน่ง `(ptr, len)` ของ slice ให้ไม่รวม whitespace ที่ขอบเท่านั้นเอง จึงเป็น operation
ที่เร็วมาก (แค่คำนวณตำแหน่งใหม่ ไม่มีการจอง heap เพิ่ม)

#### `.replace()`, `.contains()`, `.starts_with()`, `.ends_with()`

```rust
fn main() {
    let sentence = "Rust is fast, Rust is safe";

    let replaced: String = sentence.replace("Rust", "Ferris");
    println!("{replaced}");

    println!("{}", sentence.contains("safe"));
    println!("{}", sentence.starts_with("Rust"));
    println!("{}", sentence.ends_with("safe"));
}
```

ผลลัพธ์:

```
Ferris is fast, Ferris is safe
true
true
true
```

สังเกตว่า `.replace()` **คืนค่าเป็น `String` ใหม่ทั้งก้อน** (ต่างจาก `.trim()`/`.split()` ที่คืน `&str`/slice) —
เพราะการแทนที่เนื้อหาอาจเปลี่ยนความยาวรวมของสตริง (`"Rust"` ยาว 4 ตัว ส่วน `"Ferris"` ยาว 6 ตัว) ทำให้ผลลัพธ์ไม่มี
ทางเป็น slice ของสตริงต้นฉบับได้อีกต่อไป (memory layout ไม่ตรงกันแล้ว) จึงต้องจอง heap buffer ใหม่มาเก็บผลลัพธ์
เสมอ ในขณะที่ `.contains()`/`.starts_with()`/`.ends_with()` คืนค่าเป็น `bool` ล้วน ๆ (แค่ตรวจสอบ ไม่ต้องสร้างข้อมูล
ใหม่เลย)

#### `.to_uppercase()` / `.to_lowercase()`: ระมัดระวังเรื่อง locale-sensitivity และความยาวที่เปลี่ยนได้

```rust
fn main() {
    let word = "RUST เร็ว";
    println!("{}", word.to_lowercase());
}
```

ผลลัพธ์: `rust เร็ว`

ดูเผิน ๆ เหมือนใช้งานง่าย แต่มีจุดที่ต้องระวังสองเรื่อง: **(1) การแปลงตัวพิมพ์เป็นเรื่อง locale-sensitive** — ตัวอักษร
บางตัวแปลงพิมพ์ใหญ่/เล็กต่างกันไปตามภาษา (ตัวอย่างคลาสสิกคือตัวอักษรตุรกี `İ`/`i` ที่กฎแปลงต่างจากภาษาอังกฤษ) แต่
`.to_uppercase()`/`.to_lowercase()` มาตรฐานของ Rust ใช้กฎ **Unicode default case conversion** (ไม่ผูกกับ locale
เฉพาะ) ซึ่งเพียงพอสำหรับงานทั่วไป 99% แต่ถ้าต้องรองรับกฎเฉพาะของบางภาษาแบบเป๊ะ ๆ ต้องพึ่ง crate เสริม (นอกเหนือ
เนื้อหาบทนี้)

**(2) ความยาวของผลลัพธ์อาจเปลี่ยนไปจากต้นฉบับ** — นี่คือจุดที่คนมักคาดไม่ถึง ลองดูตัวอย่างภาษาเยอรมันกับตัวอักษร
`ß` (sharp S):

```rust
fn main() {
    let s = "straße";
    println!("ต้นฉบับ: {} | bytes={} | chars={}", s, s.len(), s.chars().count());

    let upper = s.to_uppercase();
    println!("ตัวพิมพ์ใหญ่: {} | bytes={} | chars={}", upper, upper.len(), upper.chars().count());
}
```

ผลลัพธ์จริง:

```
ต้นฉบับ: straße | bytes=7 | chars=6
ตัวพิมพ์ใหญ่: STRASSE | bytes=7 | chars=7
```

สังเกตให้ดี: **`"straße"` มี 6 `char`** (`s-t-r-a-ß-e`) **แต่ `"STRASSE"` มี 7 `char`** (`S-T-R-A-S-S-E`) — เพราะกฎ
Unicode กำหนดให้ตัวพิมพ์ใหญ่ของ `ß` คือ **`SS` สองตัว** ไม่ใช่ตัวเดียว! นี่คือหลักฐานที่ชัดเจนว่า **การแปลงตัวพิมพ์
ไม่ใช่การ "แปลงแบบ 1-ต่อ-1" เสมอไป** — ถ้าโค้ดของคุณสมมติว่า `s.to_uppercase().len() == s.len()` (จำนวน byte
เท่ากันก่อนและหลังแปลง) หรือสมมติว่าจำนวน `char` เท่ากัน จะพังกับกรณีแบบนี้ได้ทันที เป็นบทเรียนเดียวกันกับที่เรียน
เรื่อง floating-point ใน Part 3: **อย่าสมมติเรื่องความเท่ากันของค่าที่มาจาก operation ที่ดูเผิน ๆ เหมือนตรงไปตรงมา
โดยไม่ตรวจสอบก่อน**

### 14.9 การแปลงสตริงเป็นตัวเลข: `.parse::<T>()` แบบเจาะลึก

จาก Part 12 เราคุ้นเคยกับแนวคิดว่า operation ที่อาจล้มเหลวควรคืนค่าเป็น `Result<T, E>` — `.parse::<T>()` คือตัวอย่าง
ที่ใช้บ่อยที่สุดของแนวคิดนี้ในโลกจริง เพราะ **input จากผู้ใช้ (คีย์บอร์ด, ไฟล์, network) เป็น `&str` เสมอ** และไม่มี
ทางรู้ล่วงหน้าว่าเนื้อหาจะแปลงเป็นตัวเลขได้จริงหรือไม่จนกว่าจะลองแปลงดูก่อน

```rust
fn main() {
    let good: Result<i32, _> = "42".parse();
    let bad: Result<i32, _> = "abc".parse();

    println!("{:?}", good);
    println!("{:?}", bad);
}
```

ผลลัพธ์จริง:

```
Ok(42)
Err(ParseIntError { kind: InvalidDigit })
```

`.parse()` เป็น **generic method** — มันไม่รู้ล่วงหน้าว่าคุณต้องการแปลงเป็นชนิดไหน (`i32`? `f64`? `u8`?) ต้องบอกมัน
ผ่าน type annotation ของตัวแปรที่รับผลลัพธ์ (`let good: Result<i32, _> = ...`) หรือผ่าน **turbofish syntax**
`::<T>` ตรง ๆ ก็ได้ผลเหมือนกัน:

```rust
fn main() {
    let n = "42".parse::<i32>().unwrap();
    let f = "3.14".parse::<f64>().unwrap();
    println!("{n} {f}");
}
```

ผลลัพธ์: `42 3.14`

Turbofish (`::<i32>`) มีประโยชน์เมื่อคุณต้องการ chain method ต่อทันทีโดยไม่อยากประกาศตัวแปรกลางแยก (เช่น
`.parse::<i32>().unwrap_or(0)`) — เลือกใช้แบบไหนก็ได้ผลลัพธ์เหมือนกัน ขึ้นกับว่าอ่านง่ายกว่าในบริบทนั้นแบบไหน

ในทางปฏิบัติ ควรจัดการกับ `Err` อย่างเหมาะสม ไม่ใช้ `.unwrap()` ตรง ๆ ในโค้ด production (เพราะ `.unwrap()` จะ
panic ทันทีถ้า parse ล้มเหลว) — ใช้ `match` หรือ `?` operator ตามที่เรียนใน Part 12:

```rust
fn parse_age(input: &str) -> Result<u32, String> {
    input
        .trim()
        .parse::<u32>()
        .map_err(|_| format!("'{input}' ไม่ใช่ตัวเลขอายุที่ถูกต้อง"))
}

fn main() {
    match parse_age("  25  ") {
        Ok(age) => println!("อายุ: {age}"),
        Err(msg) => println!("ผิดพลาด: {msg}"),
    }

    match parse_age("ยี่สิบห้า") {
        Ok(age) => println!("อายุ: {age}"),
        Err(msg) => println!("ผิดพลาด: {msg}"),
    }
}
```

ผลลัพธ์:

```
อายุ: 25
ผิดพลาด: 'ยี่สิบห้า' ไม่ใช่ตัวเลขอายุที่ถูกต้อง
```

สังเกตว่าเราเรียก `.trim()` ก่อน `.parse()` เสมอ — เพราะ input จากผู้ใช้ (เช่นจากฟอร์ม, จากไฟล์ CSV) มักมีช่องว่าง
หรือ newline ติดมาโดยไม่ตั้งใจ ซึ่งจะทำให้ `.parse::<u32>()` ล้มเหลวทั้งที่เนื้อหาจริง ๆ ถูกต้อง (`.parse()` **ไม่**
ตัดช่องว่างให้อัตโนมัติ ต้อง `.trim()` เองก่อนเสมอถ้าไม่แน่ใจเรื่อง whitespace ที่อาจติดมา)

### 14.10 `.char_indices()`: หาตำแหน่ง byte ที่ปลอดภัยสำหรับ slice

ตอนนี้เรามาถึงจุดที่เชื่อมทุกอย่างในบทนี้เข้าด้วยกัน: จาก Part 8 เราเห็นว่าการ slice สตริงด้วย byte index ตรง ๆ
เสี่ยง panic มาก (`&s[0..1]` บนคำว่า "สวัสดี" panic เพราะตกกลางตัวอักษร) — `.char_indices()` คือเครื่องมือที่ทำให้
เราหาตำแหน่ง byte ที่ **ตรง character boundary เสมอ** ได้อย่างปลอดภัย โดยไม่ต้องคำนวณ/เดาเอง

ทวนโครงสร้างผลลัพธ์ของมันอีกครั้ง: `.char_indices()` คืน iterator ของคู่ **`(usize, char)`** — `usize` คือตำแหน่ง
byte ที่ `char` ตัวนั้น**เริ่ม** (ไม่ใช่ตำแหน่งกลางหรือจบ) เพราะตำแหน่งเริ่มต้นของตัวอักษรคือ character boundary
ที่ถูกต้องเสมอตามกฎ UTF-8 ในหัวข้อ 14.4 — เราจึงใช้ตำแหน่งพวกนี้มา slice ได้อย่างปลอดภัย 100%

```rust
fn main() {
    let greeting = "สวัสดี";

    for (byte_pos, ch) in greeting.char_indices() {
        println!("byte {byte_pos} -> {:?}", ch);
    }
}
```

ผลลัพธ์จริง:

```
byte 0 -> 'ส'
byte 3 -> 'ว'
byte 6 -> 'ั'
byte 9 -> 'ส'
byte 12 -> 'ด'
byte 15 -> 'ี'
```

ทุกตำแหน่ง (0, 3, 6, 9, 12, 15) คือ byte offset ที่ปลอดภัยสำหรับใช้เป็นขอบของ range slice — เทียบกับหัวข้อ 8.4
ที่ `&greeting[0..1]` panic เพราะ `1` ไม่ใช่ตำแหน่งในรายการนี้เลย แต่ `&greeting[0..3]` (ตรงกับตำแหน่ง byte 3
ในรายการ) จะปลอดภัยเสมอเพราะมันคือขอบเขตของตัวอักษร "ส" พอดี

#### ตัวอย่างการใช้งานจริง: หาตำแหน่ง byte ของตัวอักษรตัวที่ N อย่างปลอดภัย

```rust
fn nth_char_byte_position(s: &str, n: usize) -> Option<usize> {
    s.char_indices().nth(n).map(|(byte_pos, _)| byte_pos)
}

fn main() {
    let word = "ก่อน";

    for n in 0..=word.chars().count() {
        println!("ตำแหน่ง byte ของ char ตัวที่ {n}: {:?}", nth_char_byte_position(word, n));
    }
}
```

ผลลัพธ์จริง:

```
ตำแหน่ง byte ของ char ตัวที่ 0: Some(0)
ตำแหน่ง byte ของ char ตัวที่ 1: Some(3)
ตำแหน่ง byte ของ char ตัวที่ 2: Some(6)
ตำแหน่ง byte ของ char ตัวที่ 3: Some(9)
ตำแหน่ง byte ของ char ตัวที่ 4: None
```

สังเกตว่าตัวเลือก `n = 4` (เกินจำนวน `char` ที่มีอยู่จริงคือ 4 ตัว นับจาก 0) คืน `None` อย่างปลอดภัย — ไม่ panic
ไม่มีทาง crash เลย เพราะเราใช้ `.nth()` ที่คืน `Option` (จาก Part 11) ตลอดทาง แทนการเดา index ด้วยการคำนวณตัวเลข
เอง — นี่คือรูปแบบที่ปลอดภัยที่สุดในการหาตำแหน่ง byte ที่ต้องการ ก่อนจะเอาไปใช้ slice จริง เราจะเห็นรูปแบบนี้ใน
ตัวอย่างจริงของหัวข้อถัดไป

### 14.11 ตัวอย่างจริง: ระบบตรวจสอบ/จัดรูปแบบข้อความสองภาษา (ไทย-อังกฤษ)

มาปิดท้ายเนื้อหาด้วยตัวอย่างที่รวมทุกอย่างที่เรียนมาในบทนี้เข้าด้วยกัน — ระบบเล็ก ๆ ที่ (1) นับจำนวนคำในข้อความ
ผสมไทย-อังกฤษ และ (2) ตัดข้อความให้ยาวไม่เกิน N ตัวอักษร (character) **โดยไม่ทำให้ตัวอักษรหลาย byte ขาดครึ่ง และ
ไม่ panic ไม่ว่าข้อความจะเป็นภาษาอะไรก็ตาม** — เหมาะกับสถานการณ์จริงเช่น การแสดงตัวอย่างข้อความรีวิวสินค้าแบบตัด
ท้ายด้วย "..." ในหน้าเว็บ ที่ต้องรองรับทั้งรีวิวภาษาไทยและภาษาอังกฤษปนกัน

```rust
/// นับจำนวนคำในข้อความ โดยถือว่า "คำ" คือกลุ่มตัวอักษรที่คั่นด้วยช่องว่าง
/// ทำงานได้ทั้งข้อความไทย อังกฤษ หรือผสมกัน เพราะ .split_whitespace()
/// ไม่สนใจว่าตัวอักษรแต่ละตัวเป็นภาษาไหน มันสนใจแค่ตำแหน่งของ whitespace เท่านั้น
fn count_words(text: &str) -> usize {
    text.split_whitespace().count()
}

/// ตัดสตริงให้เหลือไม่เกิน `max_chars` ตัวอักษร (นับแบบ Unicode scalar value / .chars())
/// ปลอดภัยจาก UTF-8 panic เสมอ เพราะใช้ .char_indices() หาตำแหน่ง byte ที่ถูกต้อง
/// ไม่ใช่การเดาตำแหน่ง byte เอง
///
/// หมายเหตุสำคัญ: ฟังก์ชันนี้นับ "Unicode scalar value" ไม่ใช่ "grapheme cluster ที่มองเห็น"
/// (ตามข้อจำกัดที่อธิบายไว้ในหัวข้อ 14.5-14.6) ดังนั้นสำหรับข้อความไทยที่มีวรรณยุกต์/สระลอย
/// การตัดอาจ "ดูสั้นกว่า" ที่คาดไปเล็กน้อยในบางกรณี แต่จะไม่ panic และไม่ทำให้ byte เสียหายแน่นอน
fn safe_truncate(s: &str, max_chars: usize) -> &str {
    match s.char_indices().nth(max_chars) {
        // เจอตำแหน่งของ char ตัวที่ max_chars -> ตัดก่อนตำแหน่งนั้น
        Some((byte_idx, _)) => &s[..byte_idx],
        // ถ้าตัวอักษรทั้งหมดมีน้อยกว่าหรือเท่ากับ max_chars อยู่แล้ว ไม่ต้องตัดเลย
        None => s,
    }
}

/// จัดรูปแบบข้อความรีวิวสำหรับแสดงตัวอย่าง: ตัดให้สั้นแล้วเติม "..." ถ้าถูกตัดจริง
fn format_preview(text: &str, max_chars: usize) -> String {
    let total_chars = text.chars().count();
    let truncated = safe_truncate(text, max_chars);

    if total_chars > max_chars {
        format!("{truncated}...")
    } else {
        truncated.to_string()
    }
}

fn main() {
    let reviews = [
        "สินค้าดีมากค่ะ ส่งเร็ว บริการประทับใจ แนะนำเลยค่ะ",
        "Great product! Fast shipping and excellent customer service.",
        "คุณภาพ OK ราคาคุ้มค่า แต่ delivery ช้าไปหน่อย โดยรวม good มากครับ",
        "ก่อน",
    ];

    for review in reviews {
        let words = count_words(review);
        let preview = format_preview(review, 15);

        println!("รีวิว: {review}");
        println!("  จำนวนคำ: {words}");
        println!("  ตัวอย่าง (15 ตัวอักษร): {preview}");
        println!();
    }
}
```

ผลลัพธ์จริง (compile และ run แล้วยืนยันตัวเลขทุกตัว):

```

  จำนวนคำ: 4
  ตัวอย่าง (15 ตัวอักษร): สินค้าดีมากค่ะ ส...

รีวิว: Great product! Fast shipping and excellent customer service.
  จำนวนคำ: 8
  ตัวอย่าง (15 ตัวอักษร): Great product!...

รีวิว: คุณภาพ OK ราคาคุ้มค่า แต่ delivery ช้าไปหน่อย โดยรวม good มากครับ
  จำนวนคำ: 10
  ตัวอย่าง (15 ตัวอักษร): คุณภาพ OK ราคาค...

  จำนวนคำ: 1
  ตัวอย่าง (15 ตัวอักษร): ก่อน
```

**สังเกตจุดสำคัญ 3 ข้อ:**

1. **`count_words` ทำงานถูกต้องทั้งข้อความไทยล้วน อังกฤษล้วน และผสมกัน** โดยไม่ต้องเขียน logic แยกตามภาษาเลย เพราะ
   `.split_whitespace()` สนใจแค่ตำแหน่งของ whitespace เท่านั้น ไม่สนใจว่า "คำ" ที่คั่นอยู่เป็นภาษาไหน — วิธีนี้ใช้ได้
   ดีกับข้อความที่แบ่งคำด้วยช่องว่างชัดเจน (ภาษาอังกฤษ, ภาษาไทยที่คนเขียนเว้นวรรคระหว่างประโยค/กลุ่มคำ) แต่ควรรู้
   ข้อจำกัดไว้ว่า **ภาษาไทยที่เขียนแบบเป็นทางการจริง ๆ (ไม่เว้นวรรคระหว่างคำในประโยคเดียวกัน) จะไม่มี whitespace
   ให้แบ่งคำเลย** — การตัดคำภาษาไทยแบบสมบูรณ์ (word segmentation) ต้องใช้ dictionary หรือ machine learning model
   ซึ่งเป็นเรื่องนอกเหนือขอบเขตของ `std` ไปไกลมาก (ต้องใช้ crate เฉพาะทาง เช่น `libthai`-based bindings) — ในบทนี้
   เราจึงตั้งใจใช้ตัวอย่างที่เว้นวรรคระหว่างกลุ่มคำ ซึ่งเป็นวิธีเขียนที่พบได้บ่อยในข้อความไทยแบบไม่เป็นทางการ (chat,
   รีวิวสินค้า) ตรงตามขอบเขตของบทนี้ที่โฟกัสที่ UTF-8/Unicode ไม่ใช่ NLP
2. **`safe_truncate` ไม่ panic เลยไม่ว่าข้อความไหน** แม้แต่รีวิวสุดท้าย `"ก่อน"` ที่มีความยาวน้อยกว่า 15 ตัวอักษร
   (`match` เข้า branch `None` แล้วคืนสตริงทั้งก้อนโดยไม่ตัดเลย ไม่เติม `"..."` เพราะ `total_chars > max_chars`
   เป็น `false`)
3. **การตัดที่ 15 ตัวอักษรของรีวิวแรก** (`"สินค้าดีมากค่ะ ส..."`) หยุดที่ตำแหน่งกลาง ๆ ของคำว่า "ส่ง" (แสดงแค่ "ส")
   — นี่คือผลจากการนับแบบ Unicode scalar value ตามที่เตือนไว้ในคอมเมนต์ของฟังก์ชัน: มันตัดตรง 15 `char` แน่นอน
   (ไม่ panic, ไม่ทำ byte เสียหาย) แต่ผลลัพธ์อาจดู "แปลกเล็กน้อย" ในบางตำแหน่งถ้ามองในเชิงภาษาศาสตร์ — นี่คือ
   trade-off ที่ยอมรับได้และเป็นธรรมชาติของการทำงานกับ `std` ล้วน ๆ ถ้าต้องการผลลัพธ์ที่ "สวยงามในเชิงภาษา" กว่านี้
   (เช่น ตัดที่ขอบคำเสมอ ไม่ตัดกลางคำ) จะต้องเพิ่ม logic หาตำแหน่งช่องว่างที่ใกล้ที่สุดก่อนตำแหน่งตัดจริง ซึ่งเป็น
   ส่วนขยายที่ทำได้ไม่ยากจากพื้นฐานที่มีอยู่แล้วในบทนี้ (ลองทำเป็นแบบฝึกหัดข้อ 4 ท้ายบท)

### 14.12 เปรียบเทียบกับภาษาอื่น: "ความยาวสตริง" ไม่มีนิยามเดียวที่ใช้ได้ทุกที่

ก่อนปิดเนื้อหา ควรเห็นภาพกว้างว่าปัญหา "1 ตัวอักษรที่มองเห็น ไม่เท่ากับ 1 หน่วยข้อมูลภายใน" ไม่ใช่เรื่องที่ Rust
สร้างขึ้นมาเอง แต่เป็นปัญหาที่**ทุกภาษาโปรแกรมมิ่งต้องเลือกวิธีจัดการ** เพียงแต่ Rust เลือกที่จะ**ไม่ปิดบัง**ความ
ซับซ้อนนี้ไว้ (ต่างจากบางภาษาที่ทำให้ดูเหมือนง่าย แต่จริง ๆ ซ่อนพฤติกรรมที่ผิดเพี้ยนไว้ข้างใต้)

| ภาษา | `len()`/`.length` วัดอะไร | พฤติกรรมกับอักษรไทย/emoji |
|---|---|---|
| **Rust** `.len()` | จำนวน **byte** ของ UTF-8 | ตรงไปตรงมา แต่ต้องแยกเรียก `.chars().count()` เอง ถ้าต้องการนับ scalar value |
| **Rust** `.chars().count()` | จำนวน **Unicode scalar value** | ถูกต้องกว่า `.len()` แต่ยังไม่ใช่ grapheme cluster ที่มองเห็น (หัวข้อ 14.5) |
| **Python 3** `len(s)` | จำนวน **Unicode code point** (คล้าย `.chars().count()` ของ Rust) | `len("ก่อน")` ให้ผลเท่ากับ `4` เหมือน Rust เป๊ะ เพราะ Python 3 string ก็เก็บเป็นลำดับ code point ไม่ใช่ grapheme — ปัญหาเดียวกับ Rust แต่ Python **ไม่มี**คำเตือนหรือ compile-time distinction ระหว่าง "byte" กับ "code point" ให้เห็นชัดแบบ Rust |
| **JavaScript** `s.length` | จำนวน **UTF-16 code unit** | ซับซ้อนกว่าทุกภาษาในตาราง — emoji ส่วนใหญ่ (นอก BMP) ใช้ 2 code unit (surrogate pair) ทำให้ `"😻".length === 2` ทั้งที่มองเห็นตัวเดียว ส่วนอักษรไทยอยู่ใน BMP จึงนับได้ 1 code unit ต่อ scalar value เหมือน Rust แต่ปัญหา combining mark ก็ยังเหมือนกัน |
| **Java** `s.length()` | จำนวน UTF-16 code unit (เหมือน JavaScript เพราะ `String` ของ Java ก็เก็บเป็น UTF-16 ภายใน) | ปัญหาเดียวกับ JavaScript เป๊ะ (ตรงกับที่ Part 3 หัวข้อ 3.7 เทียบ `char` ของ Java ไว้แล้ว) |
| **Swift** `s.count` | จำนวน **grapheme cluster** (นับตามที่มองเห็นจริง!) | **Swift เป็นภาษาหลักไม่กี่ภาษาที่ `String` ผูก grapheme cluster segmentation ไว้เป็นค่า default ของ `.count` ไปเลย** ทำให้ `"ก่อน".count` ใน Swift จะได้ `3` ตรงกับที่ตาเห็น แต่แลกกับ performance ที่ต่ำกว่า (ต้องรันกฎ segmentation ทุกครั้งที่นับ) และเป็นเหตุผลที่ Apple เลือกยอมรับ overhead นี้เพราะ Swift เน้นงาน UI/text-heavy เป็นหลัก |

จุดที่ควรสรุปจากตารางนี้คือ **Rust เลือกจุดกึ่งกลางที่ตรงไปตรงมาที่สุด**: แยกให้เห็นชัดระหว่าง "byte" (`.len()`)
กับ "Unicode scalar value" (`.chars().count()`) และ**ปฏิเสธที่จะแอบผูก grapheme cluster segmentation** ไว้กับ
method พื้นฐานเหมือนที่ Swift ทำ เพราะเหตุผลด้าน stability และ zero-cost abstraction ที่อธิบายไว้แล้วในหัวข้อ 14.5
— ถ้าคุณมาจากพื้นฐาน Python หรือ JavaScript ควรระวังว่า **สัญชาตญาณเรื่อง "ความยาวสตริง" จากภาษาเดิมอาจไม่ตรงกับ
พฤติกรรมของ Rust แม้จะดูคล้ายกันก็ตาม** โดยเฉพาะกับ JavaScript/Java ที่ใช้ UTF-16 ภายใน (ซึ่งมีปัญหา surrogate pair
เพิ่มเข้ามาอีกชั้นสำหรับ emoji ที่ Rust ไม่มีปัญหานี้เลยเพราะ `char` คือ 4 bytes เต็มเสมอตามที่เรียนใน Part 3)

## กับดักที่พบบ่อย (Common Pitfalls)

**1. พยายาม index สตริงตรง ๆ ด้วย `s[0]` เพราะติดความเคยชินจาก `Vec`/array**

```rust
fn main() {
    let name = String::from("สมชาย");
    let first = name[0]; // ผิด — String ไม่รองรับ index ด้วยตัวเลขเดี่ยว
    println!("{first}");
}
```

```
error[E0277]: the type `str` cannot be indexed by `{integer}`
 --> src/main.rs:3:19
  |
3 |     let first = name[0];
  |                     ^ string indices are ranges of `usize`
  |
  = help: the trait `SliceIndex<str>` is not implemented for `{integer}`
```

**วิธีแก้**: ใช้ `.chars().nth(0)` เพื่อได้ `Option<char>` ของตัวอักษรตัวแรก หรือถ้าต้องการ `&str` ของตัวอักษรแรก
ใช้ `.chars().next()` ร่วมกับ `.char_indices()` เพื่อหาตำแหน่ง byte ตามหัวข้อ 14.10 — จำไว้ว่าไม่มีทางลัดที่เป็น
`O(1)` แบบ array ให้ใช้เลย เพราะเป็นข้อจำกัดโดยธรรมชาติของ variable-width encoding ตามที่อธิบายในหัวข้อ 14.7

**2. slice สตริงด้วย byte index ที่คำนวณมาแบบไม่ตรวจสอบ character boundary**

```rust
fn main() {
    let name = "น้องพลอย";
    let short = &name[0..2]; // เดา byte index มาแบบไม่รู้ว่าตรงขอบตัวอักษรหรือไม่
    println!("{short}");
}
```

```
thread 'main' panicked at src/main.rs:3:18:
byte index 2 is not a char boundary; it is inside 'น' (bytes 0..3) of `น้องพลอย`
```

`"น้องพลอย"` ขึ้นต้นด้วยตัวอักษร **"น"** (U+0E19) ซึ่งอยู่ในช่วง 3 bytes ต่อตัวตามกฎ UTF-8 ของอักษรไทย (หัวข้อ 14.4)
คือกิน byte 0, 1, 2 — การ slice ที่ตำแหน่ง byte `2` จึงตกอยู่**กลาง**ตัวอักษร "น" พอดี ทำให้ panic ทันที

จุดที่ต้องระวังยิ่งกว่าคือ **ถ้าคุณบังเอิญเดาถูกว่าตำแหน่งใดเป็น character boundary แต่ตัด "ไม่ตรงกับ grapheme
cluster ที่มองเห็น" โปรแกรมจะไม่ panic เลย แต่ผลลัพธ์จะผิดแบบเงียบ ๆ** ลองดู `&name[0..3]` (byte 3 คือจุดเริ่มต้น
ของตัวอักษรถัดไปพอดี จึงเป็น character boundary ที่ "ถูกต้อง" ในทาง UTF-8):

```rust
fn main() {
    let name = "น้องพลอย";
    let short = &name[0..3]; // ตรง character boundary พอดี ไม่ panic แต่ผลลัพธ์ "แหว่ง"
    println!("{short}");
}
```

ผลลัพธ์จริง (compile และรันผ่าน ไม่มี panic เลย):

```
น
```

โค้ดนี้**ไม่ panic แม้แต่นิดเดียว** เพราะ byte 3 คือขอบเขตของตัวอักษรที่ถูกต้องตามกฎ UTF-8 (จุดเริ่มต้นของ
**ไม้โท (่้ — ในคำนี้คือ U+0E49)** ที่เกาะอยู่บน "น") แต่สิ่งที่ได้กลับมาคือ **"น" ตัวเดียวโดยไม่มีไม้โทติดมาด้วย**
— ตัดตรงพอดีในเชิง Unicode scalar value แต่ตัด**ผ่ากลาง grapheme cluster** ที่มนุษย์มองว่าเป็นตัวอักษรเดียวกัน
("น้") ไปพอดี นี่คือบั๊กที่**อันตรายกว่า panic เสียอีก** เพราะไม่มีสัญญาณเตือนใด ๆ เลยตอน compile หรือตอน runtime
— โปรแกรมทำงาน "สำเร็จ" แต่ผลลัพธ์ที่ผู้ใช้เห็นผิดเพี้ยนไปจากที่ตั้งใจ (แสดงว่าเกาะ "น้อง" เหลือแค่ "น" เฉย ๆ)

**วิธีแก้**: ห้ามเดา/คำนวณ byte index ด้วยมือเด็ดขาดถ้าไม่รู้เนื้อหาสตริง 100% ให้ใช้ `.char_indices()` หาตำแหน่งที่
ถูกต้องเสมอ (หัวข้อ 14.10) — แต่ก็ต้องตระหนักไว้เสมอว่าแม้จะปลอดภัยจาก **panic** ระดับ byte ได้แน่นอนแล้ว ก็ยังไม่ได้
การันตีว่าตัดตรง**ขอบตัวอักษรที่มองเห็น (grapheme cluster)** เสมอไปตามที่อธิบายไว้ในหัวข้อ 14.5 — ถ้าความถูกต้อง
ระดับภาพที่มองเห็นสำคัญมาก (ไม่ใช่แค่ไม่ panic) ต้องพึ่ง `unicode-segmentation` เท่านั้นจึงจะแม่นยำ 100%

**3. ต่อสตริงด้วย `+` แล้วพยายามใช้ตัวแปรฝั่งซ้ายต่อ (ไม่รู้ว่า `+` บริโภคค่าไปแล้ว)**

```rust
}
```

**วิธีแก้**: ตามที่อธิบายในหัวข้อ 14.3 — ถ้าต้องใช้ตัวแปรฝั่งซ้ายของ `+` ต่อ ให้ `.clone()` ก่อน หรือเปลี่ยนไปใช้

**4. สมมติว่า `.chars().count()` เท่ากับจำนวนตัวอักษรที่มองเห็นสำหรับข้อความไทย**

```rust
fn is_valid_username(name: &str) -> bool {
    name.chars().count() <= 12 // จำกัดชื่อผู้ใช้ไม่เกิน 12 ตัวอักษร (ที่คิดว่า "มองเห็น")
}

fn main() {
    // คนไทยนับด้วยตาได้ 11 หน่วยที่มองเห็น: น้-ำ-ใ-จ-ดี-ม-า-ก-ๆ-น-ะ
    // ("น้" คือ น + ไม้โท รวมกัน 1 หน่วย, "ดี" คือ ด + สระอี รวมกัน 1 หน่วย)
    let username = "น้ำใจดีมากๆนะ";
    println!("chars count = {}", username.chars().count());
    println!("ผ่านเกณฑ์ไหม: {}", is_valid_username(username));
}
```

ผลลัพธ์จริง (คำนี้มีวรรณยุกต์/สระลอยปนกัน 2 ตำแหน่ง ทำให้ `.chars().count()` มากกว่าจำนวนหน่วยที่มองเห็น):

```
chars count = 13
ผ่านเกณฑ์ไหม: false
```

ผู้ใช้ที่มองคำว่า "น้ำใจดีมากๆนะ" แล้วนับได้ **11 หน่วยที่มองเห็น** (สั้นกว่าเกณฑ์ 12 อย่างชัดเจนในสายตาของเขา) จะ
รู้สึกว่าระบบปฏิเสธชื่อของเขาอย่างไม่มีเหตุผล ทั้งที่ "ดูสั้น" กว่าเกณฑ์ที่กำหนดไว้อย่างเห็นได้ชัด — เพราะ
`.chars().count()` นับได้ **13** (มากกว่าจำนวนที่มองเห็นถึง 2 หน่วย เพราะมี combining mark 2 ตำแหน่งคือไม้โทบน "น"
และสระอีบน "ด") ซึ่งเกินเกณฑ์ 12 ไปพอดี ทั้งที่ในทางความรู้สึกของผู้ใช้ ชื่อของเขาสั้นกว่าเกณฑ์ที่กำหนดไว้ 1 หน่วย
ด้วยซ้ำ — นี่คือตัวอย่างที่จับต้องได้ตรง ๆ ว่าทำไมความเข้าใจเรื่องนี้จึงสำคัญมากสำหรับนักพัฒนาที่เขียนระบบรองรับ
ภาษาไทย ไม่ใช่แค่ทฤษฎีลอย ๆ

**วิธีแก้**: ยอมรับความจริงว่า `std` ล้วน ๆ ไม่มีทางนับ "ตัวอักษรที่มองเห็น" ได้แม่นยำ 100% สำหรับภาษาไทย — ถ้าการ
จำกัดความยาวมีความสำคัญมากในเชิงธุรกิจ (เช่น จำกัดความยาวชื่อในระบบที่มีข้อบังคับด้าน UI จริง ๆ) ให้ใช้
`unicode-segmentation` crate (`.graphemes(true).count()`) แทน `.chars().count()` มิฉะนั้นควรตั้งเกณฑ์ให้กว้างพอ
รองรับ scalar value ที่มากกว่าจำนวนตัวอักษรที่มองเห็นจริงไว้เผื่อเสมอ (เช่น จำกัดที่ byte length หรือ `.chars().
count()` ที่มากกว่าที่ต้องการจริงสัก 30-50%)

**5. สมมติว่า `.to_uppercase()`/`.to_lowercase()` ไม่เปลี่ยนความยาวของสตริง**

```rust
fn shout(s: &str) -> String {
    let upper = s.to_uppercase();
    assert_eq!(upper.chars().count(), s.chars().count()); // สมมติผิด!
    upper
}

fn main() {
    println!("{}", shout("straße"));
}
```

โปรแกรมนี้ **compile ผ่าน แต่ panic ตอนรัน** เพราะ `assert_eq!` ล้มเหลว (`"straße"` มี 6 chars แต่ `"STRASSE"` มี
7 chars ตามที่พิสูจน์ไว้ในหัวข้อ 14.8):

```
thread 'main' panicked at src/main.rs:3:5:
assertion `left == right` failed
  left: 7
 right: 6
```

**วิธีแก้**: ห้ามสมมติเรื่องความสัมพันธ์ 1-ต่อ-1 ระหว่างต้นฉบับกับผลลัพธ์ของการแปลงตัวพิมพ์เด็ดขาด ถ้า logic ของคุณ
ต้องพึ่งพาความยาวที่คงที่ (เช่น การจัด layout ข้อความ, การเทียบ index ระหว่างสตริงต้นฉบับกับสตริงที่แปลงแล้ว) ให้
คิดใหม่โดยไม่อิงกับสมมติฐานนี้ หรือทำงานกับตำแหน่งบนสตริงต้นฉบับเท่านั้นก่อนแปลง

**6. เข้าใจผิดว่า `Vec<T>` กับ `String` index แบบเดียวกันได้เพราะทั้งคู่จองพื้นที่บน heap เหมือนกัน**

```rust
fn main() {
    let letters: Vec<char> = vec!['a', 'b', 'c'];
    println!("{}", letters[0]); // ใช้ได้ — Vec<char> index ตรง ๆ ได้เพราะ char ขนาดเท่ากันเสมอ (4 bytes)

    let word = String::from("abc");
    println!("{}", word[0]); // ใช้ไม่ได้ — String เก็บเป็น u8 ไม่ใช่ char
}
```

จุดที่สับสนบ่อยคือ `Vec<char>` (ที่แปลงสตริงเป็น `Vec` ของ `char` แต่ละตัวจริง ๆ ด้วย `.chars().collect()`) **index
ตรง ๆ ได้** เพราะ `char` มีขนาดคงที่ 4 bytes เสมอ (Part 3) ทำให้ `Vec<char>` มีคุณสมบัติ fixed-width เหมือน `Vec<T>`
ทั่วไป — **แต่ `String` ไม่ใช่ `Vec<char>`** มันคือ `Vec<u8>` ที่เข้ารหัสแบบ variable-width (หัวข้อ 14.1, 14.4)
ทั้งสองดูคล้ายกันมากในนามธรรม (ต่างเป็น "ลำดับของตัวอักษร") แต่ต่างกันโดยสิ้นเชิงในเชิง memory layout — ถ้าคุณ
ต้องการ index ตัวอักษรได้บ่อย ๆ แลกกับการเสียพื้นที่ความจำ (4 bytes ต่อตัวอักษรเสมอ แม้จะเป็น ASCII ที่ใช้แค่ 1 byte
ก็ตาม) การแปลงเป็น `Vec<char>` ด้วย `.chars().collect()` ก่อน แล้ว index ตรง ๆ ก็เป็นทางเลือกที่ถูกต้องและใช้ได้จริง
เพียงแต่ต้องรู้ตัวว่ากำลังแลก **memory** เพื่อได้ **O(1) index** มา (ตรงข้ามกับ `String` ที่ประหยัด memory แต่ต้อง
ยอม index แบบ O(n))

**7. สับสนระหว่าง "จำกัดความยาวเป็น byte" กับ "จำกัดความยาวเป็นตัวอักษร" เวลาต่อกับระบบภายนอก (ฐานข้อมูล, API)**

```rust
fn main() {
    let name = "ก้องภพ"; // ชื่อไทยที่มีวรรณยุกต์ 1 ตัว
    println!("chars = {}", name.chars().count()); // มองว่า "สั้น" แค่ 6 หน่วย
    println!("bytes = {}", name.len());            // แต่กิน 18 bytes จริง ๆ

    // ระบบฐานข้อมูลจำนวนมาก (เช่น MySQL คอลัมน์ VARCHAR(20) ที่ใช้ charset utf8mb4)
    // นับความยาวคอลัมน์เป็น "จำนวนตัวอักษร" ไม่ใช่ byte แต่ตัวอักษร 1 ตัวใน utf8mb4
    // อาจใช้ได้ถึง 4 bytes ต่อตัว — ตรงข้ามกับสมมติฐานที่คนเขียนโค้ด Rust มักคิดว่า
    // "20 ตัวอักษรไทย ก็แค่ 20 หน่วยเท่าภาษาอังกฤษ" ซึ่งไม่จริงเรื่อง byte เลย
    let over_20_chars = name.chars().count() > 20;
    let over_20_bytes = name.len() > 20;
    println!("เกิน 20 chars ไหม: {over_20_chars}, เกิน 20 bytes ไหม: {over_20_bytes}");
}
```

ผลลัพธ์จริง:

```
chars = 6
bytes = 18
เกิน 20 chars ไหม: false, เกิน 20 bytes ไหม: false
```

กับดักนี้ไม่ได้อยู่ที่ตัวเลขในตัวอย่างนี้ (ซึ่งยังไม่เกินทั้งคู่) แต่อยู่ที่ **การเขียนโค้ดตรวจสอบความยาวโดยเลือกหน่วย
วัดผิด** เมื่อไปต่อกับระบบภายนอก เช่นถ้า API ภายนอกจำกัด **"payload ต้องไม่เกิน 255 bytes"** (ข้อจำกัดที่พบได้บ่อย
ในระบบเก่าหรือ protocol ระดับต่ำ) แต่โค้ด Rust ตรวจสอบด้วย `.chars().count() <= 255` แทน `.len() <= 255` ข้อความ
ภาษาไทยที่มี 250 ตัวอักษร (ผ่านเกณฑ์ char แน่นอน) อาจกินพื้นที่จริงถึง 750 bytes (3 bytes ต่อตัวอักษรไทย) ซึ่ง
**เกินขีดจำกัดจริงไปมากกว่าเท่าตัว** โดยที่โค้ด Rust มองว่า "ผ่านเกณฑ์" อย่างสนิทใจ

**วิธีแก้**: ก่อนเขียนเงื่อนไขตรวจสอบความยาวใด ๆ ให้ถามตัวเองก่อนเสมอว่า **ข้อจำกัดที่ระบุมาจากภายนอกนั้น "นับ
อย่างไร"** — ถ้าเป็นข้อจำกัดของ storage/network/protocol มักหมายถึง **byte** (`.len()`) ถ้าเป็นข้อจำกัดที่มนุษย์
เป็นคนกำหนด (เช่น "ชื่อผู้ใช้ต้องไม่เกิน 20 ตัวอักษร" ในเชิง UX) มักหมายถึง**ตัวอักษรที่มองเห็น** (grapheme cluster
— ต้องพึ่ง `unicode-segmentation` ถ้าต้องการความแม่นยำสูงตามหัวข้อ 14.5) และ `.chars().count()` เป็นเพียง
ค่าประมาณที่ใกล้เคียงกว่า `.len()` แต่ก็ยังไม่แม่นยำ 100% สำหรับข้อความไทยที่มีวรรณยุกต์ — **ไม่มีทางลัดตัวเดียว
ที่ตอบทุกสถานการณ์ได้ ต้องเลือกหน่วยวัดให้ตรงกับสิ่งที่ระบบปลายทางจริง ๆ ใช้**
