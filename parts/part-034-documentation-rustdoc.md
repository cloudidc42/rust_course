# Part 34: Documentation: rustdoc, doc tests, docs.rs

> โมดูล: ระดับกลาง (Intermediate) | ระดับ: กลาง | เวลาโดยประมาณ: 90 นาที

## เป้าหมายของบทเรียน

หลังจากจบบทนี้ คุณจะสามารถ:

- แยกความแตกต่างระหว่าง `///` (outer doc comment) กับ `//!` (inner doc comment) ได้อย่างถูกต้อง 100% และรู้ว่าแต่ละแบบ
  "อธิบายอะไร" — ไม่ใช่แค่จำ syntax แต่เข้าใจกลไกที่อยู่เบื้องหลัง
- เขียน Markdown ภายใน doc comment (หัวข้อ, list, code block, link) และรู้ว่ามันจะถูก render เป็นเอกสาร HTML จริง
  ไม่ใช่แค่ข้อความเปล่า ๆ
- ใช้ `cargo doc --open` เพื่อ generate และเปิดดูเอกสาร HTML ของโปรเจกต์ตัวเองได้ พร้อมเข้าใจโครงสร้างไฟล์ที่ถูกสร้างขึ้น
- เขียน doc comment ตามธรรมเนียมมาตรฐานของ community Rust ด้วย section `# Examples`, `# Panics`, `# Errors`,
  และ `# Safety` ได้อย่างถูกต้องตามบริบทของฟังก์ชันแต่ละแบบ
- เข้าใจและใช้งาน **doc tests** — โค้ดตัวอย่างใน doc comment ที่ถูก compile และรันจริงโดย `cargo test` — พร้อมควบคุม
  พฤติกรรมของมันด้วย attribute `no_run`, `ignore`, `should_panic` และเทคนิคซ่อนบรรทัดด้วย `#`
- เขียน doc test สำหรับฟังก์ชันที่ return `Result` โดยใช้ `?` operator ได้อย่างถูกต้อง
- เชื่อมโยงระหว่าง item ต่าง ๆ ในเอกสารด้วย intra-doc link (`[Type]`, `[crate::module::function]`) และรู้วิธีให้
  rustdoc ตรวจจับ link ที่เสียโดยอัตโนมัติ
- เขียนเอกสารระดับ crate/module ด้วย `//!` ตามแบบที่ crate คุณภาพสูงบน crates.io ใช้จริง และเข้าใจว่าทำไม docs.rs
  ถึงทำให้เรื่องนี้สำคัญกว่าที่คิด

## ความรู้ที่ต้องมีมาก่อน

บทนี้เป็นบทที่ 4 ของ**โมดูล 2: ระดับกลาง (Intermediate)** ต่อจากเรื่อง Testing โดยตรง จึงจำเป็นต้องผ่านเนื้อหาต่อไปนี้
มาก่อน:

- **Part 5** (Comments, rustfmt และ Clippy) — ในหัวข้อ 5.4 เราได้แนะนำภาพรวมของ `///` และ `//!` ไว้แบบสั้น ๆ
  พร้อมบอกตรง ๆ ว่า "รายละเอียดเต็มรออยู่ที่ Part 34" — บทนี้คือการ**คืนสัญญา**นั้น เราจะอธิบายทุกอย่างที่ Part 5
  แค่แย้มไว้ให้ครบถ้วนและลึกที่สุด รวมถึงสิ่งที่ Part 5 ยังไม่ได้พูดถึงเลย เช่น doc tests
- **Part 12** (`Result<T, E>` และ Error Handling เบื้องต้น) — จำเป็นมากเพราะ section `# Errors` ในบทนี้ต้องอธิบาย
  เงื่อนไขที่ฟังก์ชันคืน `Err` ได้อย่างถูกต้อง คุณต้องเข้าใจ `Result`, `?` operator, และการ `match` บน `Result` มาก่อน
- **Part 16** (Modules และการจัดระเบียบโค้ด) — จำเป็นเพราะ `//!` มักถูกใช้อธิบาย module และเราจะพูดถึงการแบ่งเอกสาร
  ข้าม module หลายไฟล์
- **Part 17** (Packages, Crates, Workspaces) — โดยเฉพาะหัวข้อ 17.10 ที่พูดถึงการ publish package ขึ้น crates.io
  และ metadata ที่บังคับต้องมี (เช่น `license`, `description`) เพราะบทนี้จะอธิบายว่า docs.rs เชื่อมโยงกับการ publish
  นั้นโดยตรงอย่างไร
- **Part 32** (Testing: Unit Tests) และ **Part 33** (Testing: Integration Tests และการจัดระเบียบ test suite) —
  จำเป็นที่สุด เพราะ **doc test คือรูปแบบหนึ่งของ test** ที่ `cargo test` รันจริง คุณต้องเข้าใจแนวคิดพื้นฐานของ
  `#[test]`, `assert!`/`assert_eq!`, และ `#[should_panic]` มาก่อนแล้ว เพื่อจะเห็นว่า doc test เป็นแค่ "test อีกชนิด
  หนึ่ง" ที่ถูกเขียนอยู่ในคอมเมนต์ แทนที่จะอยู่ใน `#[test] fn` ตรง ๆ

ถ้ายังไม่ผ่านบทใดบทหนึ่งข้างต้น แนะนำให้กลับไปทำความเข้าใจก่อน โดยเฉพาะเรื่อง `Result`/`?` และ testing พื้นฐาน
เพราะบทนี้จะอ้างอิงถึงทั้งสองเรื่องอยู่ตลอดเวลา

## เนื้อหา

### 34.1 ทำไม Documentation ถึงเป็นจุดแข็งของ Rust Ecosystem

ก่อนลงรายละเอียด syntax เรามาทำความเข้าใจ "ทำไม" กันก่อน เพราะมือใหม่จำนวนมากมองว่าการเขียนเอกสารเป็นงานที่ทำ
"หลังจากเขียนโค้ดเสร็จแล้วถ้ามีเวลาเหลือ" แต่ใน ecosystem ของ Rust เอกสารถูกยกระดับให้เป็น **first-class citizen**
ของภาษา ไม่ใช่แค่ธรรมเนียมที่ทีมใดทีมหนึ่งเลือกทำ

เหตุผลเชิงโครงสร้างมีสามข้อหลัก:

1. **มี syntax เฉพาะในตัวภาษาสำหรับเอกสาร** (`///` และ `//!`) ที่ compiler และ toolchain รู้จักโดยตรง ไม่ใช่แค่
   comment ธรรมดาที่ทีมตกลงกันเอาว่า "บรรทัดที่ขึ้นต้นด้วย `// Doc:` คือเอกสาร" แบบที่บางภาษาต้องทำผ่าน convention
   ที่ไม่มีการบังคับ
2. **มีเครื่องมือทางการ (`rustdoc`) ที่มาพร้อม toolchain ทุกเครื่อง** ไม่ต้องติดตั้งเพิ่ม ไม่ต้องเลือกว่าจะใช้ Sphinx,
   Javadoc, JSDoc หรือ Doxygen ตัวไหนดี — มีคำตอบเดียวที่ทุกโปรเจกต์ Rust ในโลกใช้ร่วมกัน
3. **เอกสารสามารถถูกทดสอบได้จริง** ผ่าน doc test ซึ่งเป็นจุดที่ไม่มีภาษาแพร่หลายภาษาไหนทำได้ดีเท่า Rust — โค้ดตัวอย่าง
   ในเอกสารไม่ใช่แค่ "ข้อความอธิบาย" ที่อาจ outdated ไปตามเวลา แต่เป็นโค้ดที่ compiler รันจริงทุกครั้งที่ `cargo test`
   ถ้าโค้ดตัวอย่างพังเพราะ API เปลี่ยนไปแล้ว `cargo test` จะ**ล้มเหลวทันที** — เอกสารจึง "โกหกไม่ได้" ในความหมายที่ว่า
   ตัวอย่างการใช้งานจะไม่มีวัน compile ไม่ผ่านหรือให้ผลลัพธ์ผิดโดยที่ไม่มีใครรู้

ผลลัพธ์เชิงปฏิบัติของทั้งสามข้อนี้คือ: crate คุณภาพสูงบน crates.io (เช่น `serde`, `tokio`, `regex`) มีหน้าเอกสารที่
สมบูรณ์ อ่านง่าย และมีตัวอย่างที่ **ทำงานได้จริงเสมอ** เพราะทุกครั้งที่ผู้เขียน crate เหล่านี้เปลี่ยน API พวกเขาจะเห็น
ทันทีว่าตัวอย่างเก่าใน doc comment compile ไม่ผ่าน (CI จะ fail) — บทนี้จะพาคุณสร้างสิ่งเดียวกันนี้ด้วยตัวเอง

### 34.2 `///` — Outer Doc Comment: อธิบาย "รายการที่อยู่ถัดไป"

จาก Part 5 หัวข้อ 5.4 เราได้เห็นภาพรวมของ `///` มาแล้ว ตอนนี้เรามาดูกลไกอย่างละเอียด

`///` (triple-slash) เขียนไว้**เหนือ** item ที่ต้องการอธิบาย โดย "item" ในความหมายของ Rust หมายถึงสิ่งที่ประกาศได้
ในระดับ top-level เช่น `fn`, `struct`, `enum`, `trait`, `impl` block, `mod`, `const`, `static`, หรือแม้แต่ field
ภายใน struct/enum แต่ละตัว

```rust
/// คำนวณค่าส่งสินค้าตามน้ำหนัก (กิโลกรัม)
///
/// อัตราค่าส่ง: 15 บาทต่อกิโลกรัมสำหรับน้ำหนักที่เกิน 20 กก. และ 20 บาทต่อกิโลกรัม
/// สำหรับน้ำหนักที่ไม่เกิน 20 กก. (ราคาต่อหน่วยจะถูกกว่าเมื่อสั่งของหนัก เพราะต้นทุนคงที่
/// ต่อรอบขนส่งถูกเฉลี่ยได้ดีกว่า)
fn calculate_shipping_fee(weight_kg: f64) -> f64 {
    if weight_kg > 20.0 {
        weight_kg * 15.0
    } else {
        weight_kg * 20.0
    }
}

fn main() {
    println!("ค่าส่ง: {}", calculate_shipping_fee(25.0));
}
```

จุดสำคัญที่ต้องเข้าใจให้แม่นคือ **`///` ต้องอยู่ติดกับ item ที่มันอธิบายเสมอ ไม่มีบรรทัดว่างคั่นระหว่างกัน** ถ้ามี
บรรทัดว่างคั่น หรือถ้า `///` ถูกเขียนไว้ในตำแหน่งที่ไม่มี item ตามมา (เช่น เขียนไว้เหนือ `let` statement ภายใน
function body) `///` จะไม่ทำหน้าที่เป็น doc comment อีกต่อไป — เราจะเห็น warning จริงจาก compiler เรื่องนี้ใน
หัวข้อ "กับดักที่พบบ่อย" ท้ายบท

`///` สามารถเขียนซ้อนกันได้กับ struct field และ enum variant แต่ละตัว ซึ่งมีประโยชน์มากในการอธิบายความหมายของ
field แต่ละตัวแยกกัน:

```rust
/// สินค้าหนึ่งรายการในคลัง
struct Product {
    /// ชื่อสินค้า ใช้เป็น key เวลาเก็บในคลังสินค้า
    name: String,
    /// ราคาต่อหน่วย (บาท) ต้องไม่ติดลบ
    price: f64,
    /// จำนวนที่มีอยู่ในคลัง ณ ขณะนี้
    quantity: u32,
}
```

เมื่อ generate เอกสาร HTML ด้วย `cargo doc` (จะเรียนใน 34.5) แต่ละ field จะแสดงคำอธิบายของตัวเองแยกกันในหน้า
เอกสารของ struct — ซึ่งมีประโยชน์มากสำหรับ struct ที่มี field จำนวนมากและความหมายไม่ชัดเจนจากชื่อเพียงอย่างเดียว

**ข้อสังเกตเชิงกลไก:** `///` ที่คอมไพเลอร์มองเห็นจริง ๆ แล้วถูกแปลงภายใน (internally) เป็น attribute
`#[doc = "..."]` ที่แนบอยู่กับ item — คุณสามารถเขียนแบบ attribute ตรง ๆ ได้เหมือนกัน (แม้ในทางปฏิบัติแทบไม่มีใครทำ
เพราะ `///` อ่านง่ายกว่ามาก):

```rust
#[doc = "คำนวณค่าส่งสินค้าตามน้ำหนัก (กิโลกรัม)"]
fn calculate_shipping_fee_v2(weight_kg: f64) -> f64 {
    weight_kg * 15.0
}
```

โค้ดสองแบบข้างต้นมีความหมายเหมือนกันทุกประการในมุมของ compiler — `///` เป็นแค่ **syntax sugar** ที่อ่านง่ายกว่า
`#[doc = "..."]` การรู้เรื่องนี้ช่วยอธิบายว่าทำไม doc comment ถึงต้อง**นำหน้า item เสมอ**: เพราะโดยกลไกแล้วมันคือ
attribute ที่ต้องแนบกับ item หนึ่งตัวเสมอ ไม่ต่างจาก `#[derive(Debug)]` หรือ `#[test]` ที่เราเคยเห็นมาแล้ว

### 34.3 `//!` — Inner Doc Comment: อธิบาย "สิ่งที่ล้อมรอบมัน"

ตรงข้ามกับ `///` ที่มองไป**ข้างหน้า** `//!` (slash-bang) มองไป**รอบตัว/ข้างบน** — มันอธิบาย item ที่**ล้อมรอบ**มันอยู่
ไม่ใช่ item ที่ตามมา ตำแหน่งที่ใช้บ่อยที่สุดคือบรรทัดบนสุดของไฟล์ `lib.rs` (เพื่ออธิบายทั้ง crate) หรือบรรทัดบนสุดของ
ไฟล์ที่เป็น module (`mod.rs` หรือไฟล์ที่ประกาศด้วย `mod xxx;`) เพื่ออธิบาย module นั้นทั้งก้อน

```rust
//! ระบบจัดการสินค้าคงคลัง (Inventory Management System)
//!
//! Crate นี้รวมฟังก์ชันสำหรับคำนวณราคา ส่วนลด และการติดตามจำนวนสินค้าในคลัง
//! ใช้เป็นตัวอย่างประกอบการสอนในหลักสูตร Rust ภาษาไทย

fn main() {
    println!("Inventory system starting...");
}
```

นอกจากใช้ที่บนสุดของไฟล์แล้ว `//!` ยังใช้ได้ **ภายใน** `mod` block ที่ประกาศแบบ inline เพื่ออธิบาย module นั้นจาก
ข้างในตัวเองได้เช่นกัน:

```rust
mod pricing {
    //! Module นี้รวมฟังก์ชันคำนวณราคาและส่วนลดทั้งหมดของระบบ
    //!
    //! แยกออกมาจาก logic หลักเพื่อให้ทดสอบกฎการคิดราคาได้อย่างเป็นเอกเทศ

    /// คำนวณราคาสุทธิหลังหักส่วนลด (เปอร์เซ็นต์)
    pub fn apply_discount(price: f64, discount_percent: f64) -> f64 {
        price * (1.0 - discount_percent / 100.0)
    }
}

fn main() {
    println!("{}", pricing::apply_discount(100.0, 10.0));
}
```

สังเกตความแตกต่างของ**ตำแหน่ง**อย่างชัดเจน: `//!` ในตัวอย่างข้างต้นถูกเขียนไว้เป็นบรรทัดแรก ๆ **ภายใน** `mod pricing`
block — มันอธิบาย `mod pricing` เอง (สิ่งที่ล้อมรอบมันอยู่) ไม่ใช่อธิบาย `apply_discount` ที่ตามมา (ซึ่งถูกอธิบายด้วย
`///` ตามปกติแยกต่างหาก)

**คำถามที่มือใหม่มักสงสัย: ทำไมไม่ใช้ `///` เขียนไว้เหนือ `mod pricing;` แทนไปเลย?** คำตอบคือ**ทำได้เหมือนกัน** และ
ให้ผลลัพธ์การ render คล้ายกันมาก แต่ความแตกต่างเชิงปฏิบัติคือ:

- `///` เหนือ `mod pricing;` (ที่ไฟล์ parent ที่ประกาศ `mod`) เหมาะกับกรณีที่คุณอยากให้ **คนที่เห็นไฟล์ parent**
  เข้าใจภาพรวมของ module ลูกโดยไม่ต้องเปิดไฟล์ลูก
- `//!` **ภายใน** ไฟล์ของ module เอง (หรือภายใน `mod` block เอง) เหมาะกับกรณีที่คุณอยากให้เอกสารของ module อยู่
  **ติดกับโค้ดของ module นั้นเอง** ไม่ต้องเปิดไฟล์อื่นเพื่อดูว่า module นี้มีไว้ทำอะไร — นี่คือรูปแบบที่ community
  Rust นิยมมากกว่า เพราะโค้ดกับเอกสารของมันอยู่ใกล้กันที่สุด (locality of information) ลดโอกาสที่เอกสารจะ "หลุด"
  จากโค้ดจริงเวลามีคนย้ายไฟล์หรือ refactor

ในทางปฏิบัติ **crate ระดับ production ทุกตัวที่มีคุณภาพจะมี `//!` อยู่บรรทัดบนสุดของ `lib.rs` เสมอ** เพราะนี่คือสิ่ง
แรกที่คนเข้ามาดูเอกสารของ crate (ที่ docs.rs หรือผ่าน `cargo doc --open`) จะเห็น — เราจะเขียนตัวอย่างแบบสมบูรณ์ใน
หัวข้อ 34.11

| รูปแบบ | มองไปทางไหน | ตัวอย่างตำแหน่งที่ใช้ | Attribute ที่แปลงเป็นภายใน |
|---|---|---|---|
| `///` | ข้างหน้า (item ที่ตามมา) | เหนือ `fn`, `struct`, `enum`, field | `#[doc = "..."]` แนบกับ item ที่ตามมา |
| `//!` | รอบตัว/ข้างบน (item ที่ล้อมรอบ) | บรรทัดบนสุดของ `lib.rs`/`mod.rs` หรือในตัว `mod {}` block | `#![doc = "..."]` แนบกับ crate/module ที่ล้อมรอบ |

### 34.4 Markdown ใน Doc Comment: เอกสารที่ Render ได้จริง ไม่ใช่แค่ Plain Text

จุดที่ทำให้ doc comment ต่างจาก comment ธรรมดาอย่างสิ้นเชิงคือ **เนื้อหาข้างในถูกตีความเป็น Markdown** โดย `rustdoc`
แล้วแปลงเป็น HTML ที่จัดรูปแบบสวยงามจริง ไม่ใช่แค่ข้อความดิบที่แสดงบนหน้าเว็บตรง ๆ

ลองดูตัวอย่างที่ใช้ฟีเจอร์ Markdown หลากหลายรูปแบบ:

```rust
/// คำนวณราคาสุทธิหลังหักส่วนลดของสินค้า
///
/// # ภาพรวม
///
/// ฟังก์ชันนี้รับราคาตั้งต้นและเปอร์เซ็นต์ส่วนลด แล้วคืนราคาสุทธิ โดยมีเงื่อนไขดังนี้:
///
/// - `discount_percent` ต้องอยู่ในช่วง `0.0` ถึง `100.0`
/// - ผลลัพธ์จะถูก **ปัดเศษ** ตามค่า floating point ปกติ ไม่มีการปัดขึ้น/ลงพิเศษ
/// - ดูฟังก์ชันที่เกี่ยวข้องที่ [`calculate_shipping_fee`](crate::calculate_shipping_fee)
///
/// อ้างอิงสูตร: `net = price * (1 - discount / 100)`
///
/// # ตัวอย่าง
///
/// ```
/// let net = 100.0 * (1.0 - 10.0 / 100.0);
/// assert_eq!(net, 90.0);
/// ```
///
/// เอกสารเพิ่มเติมดูได้ที่ [เว็บไซต์ทางการของ Rust](https://www.rust-lang.org)
fn calculate_discounted_price(price: f64, discount_percent: f64) -> f64 {
    price * (1.0 - discount_percent / 100.0)
}

fn calculate_shipping_fee(weight_kg: f64) -> f64 {
    weight_kg * 15.0
}

fn main() {
    println!("{}", calculate_discounted_price(100.0, 10.0));
}
```

เมื่อ generate เป็น HTML ด้วย `cargo doc` ตัวอย่างข้างต้นจะกลายเป็นหน้าเอกสารที่มี:

- หัวข้อ "ภาพรวม" แสดงเป็น `<h1>` จริง (ตัวหนา ขนาดใหญ่)
- bullet list สามข้อ แสดงเป็น `<ul><li>` จริง พร้อม bold text ที่ขีดเส้นใต้ตัวหนาจริง
- ` `net = ...` ` ที่ครอบด้วย backtick เดี่ยว จะกลายเป็น **inline code** (font แบบ monospace) เหมือนใน Markdown
  ทั่วไป
- link `[calculate_shipping_fee](crate::calculate_shipping_fee)` จะกลายเป็น hyperlink ที่คลิกได้จริง พาไปยังหน้า
  เอกสารของฟังก์ชันนั้น (เราจะพูดถึง intra-doc link แบบนี้ละเอียดใน 34.10)
- code block สามบรรทัดที่ครอบด้วย ` ``` ` จะถูก render เป็น **code block ที่มี syntax highlighting** และ (สำคัญ
  ที่สุด) จะถูกดึงออกไป**รันเป็น test จริง** โดย `cargo test` — นี่คือหัวใจของบทนี้ที่เราจะพูดถึงใน 34.7
- link ปกติแบบ Markdown ไปยัง URL ภายนอก (`[เว็บไซต์ทางการของ Rust](https://www.rust-lang.org)`) ก็ทำงานได้ตามปกติ

ฟีเจอร์ Markdown ที่ rustdoc รองรับเป็น **CommonMark** (มาตรฐาน Markdown ที่ใช้กันแพร่หลาย) ครอบคลุมสิ่งที่ใช้บ่อย
ที่สุดทั้งหมด: heading (`#`, `##`, ...), list (`-`, `1.`), bold (`**...**`), italic (`*...*`), inline code
(`` `...` ``), code block (` ``` `), link (`[text](url)`), table (`| ... | ... |`), และ blockquote (`>`)

**ทำไมเรื่องนี้สำคัญเชิง design?** เพราะมันหมายความว่าคุณไม่ต้องเรียนรู้ syntax เอกสารแบบใหม่เลย — ถ้าคุณเคยเขียน
README บน GitHub มาก่อน (ซึ่งใช้ Markdown เหมือนกัน) คุณเขียน doc comment ของ Rust ได้ทันทีโดยใช้ความรู้เดิม
เปรียบเทียบกับ Javadoc ที่ต้องใช้ HTML tag ตรง ๆ ในคอมเมนต์ (เช่น `<p>`, `<code>`, `{@link ...}`) ซึ่งอ่านยากกว่ามาก
ตอนเขียนใน source code ดิบ ๆ (แม้ผลลัพธ์ที่ render ออกมาจะคล้ายกัน)

### 34.5 `cargo doc --open`: สร้างและเปิดดูเอกสาร HTML

หลังจากเขียน doc comment แล้ว การสร้างเอกสารจริงทำได้ด้วยคำสั่งเดียว:

```bash
cargo doc
```

คำสั่งนี้จะ compile crate ของคุณ (คล้าย `cargo check`) แล้วดึง doc comment ทั้งหมดออกมาประมวลผลเป็นหน้า HTML
เก็บไว้ที่ `target/doc/` ถ้าต้องการให้เปิดเบราว์เซอร์แสดงผลทันทีหลัง generate เสร็จ ใช้:

```bash
cargo doc --open
```

โดย default `cargo doc` จะ generate เอกสารของ **ทุก dependency** ที่โปรเจกต์ใช้ด้วย (เพื่อให้คุณคลิก link ไปดู
เอกสารของ `serde`, `tokio` ฯลฯ ที่โปรเจกต์คุณพึ่งพาได้จากหน้าเดียวกัน) ซึ่งมีประโยชน์มากตอนพัฒนา แต่ถ้าคุณสนใจแค่
เอกสารของ crate ตัวเองล้วน ๆ (เช่น ตอนตรวจสอบว่าตัวเองเขียนเอกสารครบหรือยัง) ใช้ flag `--no-deps` เพื่อให้เร็วขึ้น
มาก:

```bash
cargo doc --no-deps --open
```

**โครงสร้างไฟล์ที่ `cargo doc` สร้างขึ้น (ตรวจสอบจริงจากการรัน):** สมมติเรามี crate ชื่อ `mini_inventory` ที่มี
`struct Product`, `struct Inventory`, `enum InventoryError`, และ module ย่อยชื่อ `report` ที่มีฟังก์ชัน `summarize`
หลังรัน `cargo doc --no-deps` จะได้โครงสร้างไฟล์ประมาณนี้ (ตัดมาจากผลลัพธ์จริง):

```
target/doc/mini_inventory/
├── index.html                 <- หน้าแรกของ crate (มาจาก //! ที่บนสุดของ lib.rs)
├── all.html                   <- รายการ item ทั้งหมดของ crate แบบเรียงตัวอักษร
├── sidebar-items.js           <- ข้อมูลสำหรับ sidebar navigation
├── struct.Product.html        <- หน้าเอกสารของ struct Product (จาก ///)
├── struct.Inventory.html      <- หน้าเอกสารของ struct Inventory
├── enum.InventoryError.html   <- หน้าเอกสารของ enum InventoryError
└── report/
    ├── index.html              <- หน้าแรกของ module report (มาจาก //! ในไฟล์ report.rs)
    ├── fn.summarize.html       <- หน้าเอกสารของฟังก์ชัน summarize
    └── sidebar-items.js
```

สังเกตหลักการสำคัญ: **หนึ่ง item หลัก (struct, enum, trait, fn ระดับ module) ได้หน้า HTML ของตัวเองหนึ่งหน้า** และ
ทุกหน้าเชื่อมโยงกันด้วย hyperlink อัตโนมัติ (จาก intra-doc link ที่เราเขียน หรือจาก type signature ที่ rustdoc
วิเคราะห์เอง เช่น ถ้าฟังก์ชันคืนค่า `Product` มันจะลิงก์ไปหน้า `struct.Product.html` ให้อัตโนมัติโดยไม่ต้องเขียน
link เอง) โครงสร้างแบบนี้คล้ายกับ Javadoc ของ Java มาก แต่ต่างที่ rustdoc generate ให้ทั้งหมดจาก comment ในโค้ด
โดยตรง ไม่ต้องตั้งค่า tool แยกหรือเขียน config ไฟล์ใด ๆ เพิ่มเติม

หน้า `index.html` ของ crate เองจะแสดงเนื้อหาจาก `//!` ที่บนสุดของ `lib.rs` เป็น **ส่วนแรกของหน้า** (มักเรียกว่า
"crate-level documentation") ตามด้วยตาราง**รายการ item ทั้งหมด**ที่ crate export ออกมา (structs, enums, traits,
functions, modules) พร้อมคำอธิบายบรรทัดแรกของแต่ละ item (ดึงมาจากบรรทัดแรกของ `///` ของ item นั้น) — นี่คือเหตุผล
ที่**บรรทัดแรกของ doc comment ควรสั้นและสรุปใจความสำคัญที่สุด** เพราะมันถูกใช้เป็น "summary" ในหลายที่ (หน้า index,
ผลการค้นหา, tooltip เวลา hover ใน IDE) — เป็นธรรมเนียมที่ community Rust ยึดถือกันอย่างเคร่งครัด

### 34.6 โครงสร้างมาตรฐานของ Doc Comment: `# Examples`, `# Panics`, `# Errors`, `# Safety`

แม้ Rust compiler **ไม่บังคับ** ให้ doc comment มีโครงสร้าง section แบบใดแบบหนึ่ง (คุณเขียนข้อความอะไรก็ได้) แต่
community Rust ได้พัฒนา**ธรรมเนียมโดยพฤตินัย (de facto convention)** ที่ crate คุณภาพสูงเกือบทั้งหมดใช้ร่วมกัน
โดยใช้ Markdown heading ระดับ 1 (`# ชื่อ section`) เป็นตัวแบ่งหมวด สี่ section ที่พบบ่อยที่สุดคือ:

1. **`# Examples`** — ตัวอย่างการใช้งานจริง แทบทุกฟังก์ชัน public ควรมี section นี้ (และตัวอย่างในนี้จะกลายเป็น
   doc test โดยอัตโนมัติ — ดู 34.7)
2. **`# Panics`** — อธิบายว่าฟังก์ชันนี้ **panic เมื่อไหร่และทำไม** ใช้เมื่อฟังก์ชัน**มีโอกาส panic** (ไม่ว่าจาก
   `panic!` ตรง ๆ, `.unwrap()`, `.expect()`, หรือ `assert!` ภายใน) — ผู้ใช้ไลบรารีจำเป็นต้องรู้เรื่องนี้ล่วงหน้า
   เพื่อป้องกันไม่ให้ input ที่จะทำให้ panic ไหลเข้ามาถึงฟังก์ชันนี้ในโค้ด production
3. **`# Errors`** — สำหรับฟังก์ชันที่คืน `Result<T, E>` อธิบายว่า**เงื่อนไขไหนทำให้คืน `Err`** และ `Err` แต่ละ
   variant มีความหมายอะไร ต่างจาก `# Panics` ตรงที่นี่คือ error ที่ผู้เรียก**ต้องจัดการเอง** (ผ่าน `match`, `?`,
   ฯลฯ) ไม่ใช่ error ที่ทำให้โปรแกรม crash ทันที
4. **`# Safety`** — สำหรับ `unsafe fn` เท่านั้น อธิบาย **invariant ที่ผู้เรียกต้องรักษาไว้** ก่อนเรียกฟังก์ชันนี้
   (บทนี้จะพูดถึงแบบสั้น ๆ เท่านั้น เพราะความลึกเต็มรูปแบบของ `unsafe` รออยู่ในบทที่เกี่ยวกับ unsafe Rust โดยตรงในช่วง
   หลังของหลักสูตร — ที่นี่เราแค่ต้องรู้ว่า section นี้มีไว้ทำอะไรและเขียนอย่างไร)

**สิ่งสำคัญที่ต้องเข้าใจ: compiler ไม่ตรวจสอบว่าคุณเขียน section เหล่านี้ถูกต้องหรือครบหรือไม่** มันเป็นแค่ Markdown
heading ธรรมดาในสายตาของ `rustc`/`rustdoc` — ความ "บังคับ" มาจาก **social convention ของ community** และจาก
**clippy** ที่มี lint กลุ่ม `pedantic` (ที่เราเรียนใน Part 5 หัวข้อ 5.11) ที่จะเตือนถ้าฟังก์ชันคืน `Result` แต่ไม่มี
`# Errors` หรือฟังก์ชันเป็น `unsafe fn` แต่ไม่มี `# Safety` — lint เหล่านี้ปิดโดย default เพราะเข้มงวดเกินไปสำหรับ
โปรเจกต์ทั่วไป แต่ทีมที่ทำ library คุณภาพสูงระดับ production มักเปิดใช้เพื่อบังคับมาตรฐานเอกสารในทีม

มาดูตัวอย่างฟังก์ชันที่เขียนเอกสารครบทุก section ที่เกี่ยวข้องอย่างสมจริง:

```rust
use std::collections::HashMap;

/// ตัดสินค้าออกจากคลังจำนวนหนึ่ง (เช่น ตอนขายสินค้า)
///
/// # Errors
///
/// - คืน `Err("not found")` ถ้าไม่พบสินค้าชื่อนี้ในคลังเลย
/// - คืน `Err("insufficient stock")` ถ้าจำนวนที่ต้องการตัดมากกว่าจำนวนที่มีอยู่จริง
///   ฟังก์ชันจะ**ไม่**ตัดสต็อกบางส่วนแล้วปล่อยให้ค้างครึ่ง ๆ กลาง ๆ (all-or-nothing) เพื่อป้องกัน
///   ข้อมูลคลังสินค้าไม่สอดคล้องกัน
///
/// # Examples
///
/// ```
/// use std::collections::HashMap;
///
/// let mut stock: HashMap<String, u32> = HashMap::new();
/// stock.insert("เมาส์".to_string(), 10);
///
/// // ฟังก์ชันตัวอย่างในบทนี้แสดง signature เท่านั้น รายละเอียดจริงจะสมบูรณ์ในหัวข้อ 34.14
/// assert_eq!(stock.get("เมาส์"), Some(&10));
/// ```
fn remove_stock(stock: &mut HashMap<String, u32>, name: &str, amount: u32) -> Result<(), String> {
    let current = stock.get(name).copied().ok_or_else(|| "not found".to_string())?;
    if current < amount {
        return Err("insufficient stock".to_string());
    }
    stock.insert(name.to_string(), current - amount);
    Ok(())
}

fn main() {
    let mut stock = HashMap::new();
    stock.insert("เมาส์".to_string(), 10);
    remove_stock(&mut stock, "เมาส์", 3).unwrap();
    println!("{:?}", stock.get("เมาส์"));
}
```

และตัวอย่างฟังก์ชันที่มีทั้ง `# Panics` และ `# Examples` (ไม่มี `# Errors` เพราะฟังก์ชันนี้ไม่คืน `Result`):

```rust
/// สร้างสินค้าใหม่ด้วยชื่อ ราคา และจำนวน
///
/// # Panics
///
/// ฟังก์ชันนี้จะ panic ทันทีถ้า `price` เป็นค่าลบ เพราะราคาสินค้าติดลบไม่มีความหมายทางธุรกิจ
/// และเป็นสัญญาณของบั๊กที่ควรถูกจับให้เร็วที่สุด ณ จุดที่สร้างข้อมูลผิดพลาด
///
/// # Examples
///
/// ```
/// # struct Product { name: String, price: f64, quantity: u32 }
/// # fn new_product(name: &str, price: f64, quantity: u32) -> Product {
/// #     assert!(price >= 0.0);
/// #     Product { name: name.to_string(), price, quantity }
/// # }
/// let p = new_product("คีย์บอร์ด", 890.0, 5);
/// assert_eq!(p.name, "คีย์บอร์ด");
/// ```
fn new_product_doc_demo() {}
```

(ตัวอย่างที่สองข้างต้นใช้เทคนิคซ่อนบรรทัดด้วย `#` ที่เราจะอธิบายละเอียดใน 34.8 — สังเกตไว้ก่อนว่ามันมีอยู่จริงและ
ใช้งานได้)

และตัวอย่าง `unsafe fn` ที่มี `# Safety` (บทนี้แสดงแบบสั้น รายละเอียดเต็มของ `unsafe` อยู่ในบทว่าด้วย unsafe Rust
โดยตรงในช่วงท้ายหลักสูตร):

```rust
/// อ่านค่า `i32` จากตำแหน่ง pointer ที่กำหนด
///
/// # Safety
///
/// ผู้เรียกต้องมั่นใจว่า:
///
/// - `ptr` ไม่เป็น null
/// - `ptr` ชี้ไปยังหน่วยความจำที่ถูกจัดสรรไว้อย่างถูกต้องและมีขนาดอย่างน้อยเท่ากับ `i32` (4 byte)
/// - หน่วยความจำที่ `ptr` ชี้ไปมีค่าที่ถูก initialize แล้ว (ไม่ใช่ memory ที่ยังไม่ได้กำหนดค่า)
/// - ไม่มี thread อื่นเขียนทับหน่วยความจำนี้พร้อมกันในขณะที่ฟังก์ชันนี้ทำงาน (ไม่เกิด data race)
///
/// การละเมิดเงื่อนไขข้างต้นข้อใดข้อหนึ่งจะทำให้เกิด **undefined behavior** ซึ่งเป็นสิ่งที่ Rust
/// พยายามป้องกันด้วย type system ในโค้ด `safe` — แต่เมื่อเข้าสู่ `unsafe`
/// ภาระการรับประกันความถูกต้องทั้งหมดตกไปอยู่ที่ผู้เรียก ไม่ใช่ compiler อีกต่อไป
pub unsafe fn read_i32_at(ptr: *const i32) -> i32 {
    *ptr
}

fn main() {
    let x = 42i32;
    // การเรียก unsafe fn ต้องอยู่ใน unsafe block เสมอ เพื่อ "ยืนยัน" ว่าผู้เรียกได้ตรวจสอบ
    // เงื่อนไขใน # Safety แล้วจริง ๆ — นี่คือสิ่งที่เราจะเรียนลึกในบท unsafe Rust
    let value = unsafe { read_i32_at(&x as *const i32) };
    println!("{value}");
}
```

**เหตุผลเชิงลึกที่ `# Safety` สำคัญมากสำหรับ `unsafe fn`:** เมื่อคุณประกาศฟังก์ชันเป็น `unsafe fn` คุณกำลังบอก
compiler ว่า "ฟังก์ชันนี้มีเงื่อนไขบางอย่างที่ type system ของ Rust ตรวจสอบให้ไม่ได้ ผู้เรียกต้องรับผิดชอบตรวจสอบเอง"
แต่ compiler **ไม่มีทางรู้ว่าเงื่อนไขนั้นคืออะไร** — มันรู้แค่ว่า "ต้องมี unsafe block ครอบตอนเรียก" เท่านั้น ถ้าคุณ
ไม่เขียน `# Safety` อธิบายเงื่อนไขเหล่านั้นเป็นภาษาที่มนุษย์อ่านได้ ผู้เรียกฟังก์ชันของคุณจะไม่มีทางรู้เลยว่าต้อง
ระวังอะไรบ้าง — นี่คือช่องว่างที่เอกสารต้องเข้ามาเติมเต็ม เพราะ type system เติมให้ไม่ได้ในจุดนี้

### 34.7 Doc Tests: เอกสารที่ไม่มีวันโกหก เพราะมันถูกทดสอบจริง

นี่คือหัวใจสำคัญที่สุดของบทนี้ และเป็นฟีเจอร์ที่ทำให้ documentation ของ Rust แตกต่างจากภาษาอื่นอย่างชัดเจนที่สุด

**กลไก:** ทุก code block ที่ครอบด้วย ` ``` ` ภายใน doc comment (`///` หรือ `//!`) **จะถูก `rustdoc` ดึงออกมา
compile และรันเป็น test จริง** โดยอัตโนมัติเมื่อคุณรัน `cargo test` — โดย**ไม่ต้อง**เขียน `#[test]` หรือ setup
อะไรเพิ่มเติมเลย เพียงแค่เขียนโค้ดตัวอย่างใน ` ```rust ` (หรือ ` ``` ` เปล่า ๆ ซึ่ง rustdoc จะสมมติว่าเป็น Rust
โดย default) ก็เพียงพอ

จาก Part 32-33 เราเข้าใจแล้วว่า `cargo test` รัน unit test และ integration test — ตอนนี้เราจะเห็นว่ามันรัน
**test ชนิดที่สาม** ด้วย นั่นคือ **doc test** ซึ่งถูกแสดงเป็นส่วนแยกในผลลัพธ์ชื่อ **"Doc-tests"**

มาดูตัวอย่างจริง สมมติเรามีฟังก์ชันนี้ในไฟล์ `src/lib.rs`:

```rust
pub struct Product {
    pub name: String,
    pub price: f64,
    pub quantity: u32,
}

impl Product {
    /// คำนวณมูลค่ารวมของสินค้ารายการนี้ (ราคา คูณ จำนวน)
    ///
    /// # Examples
    ///
    /// ```
    /// use mini_inventory::Product;
    ///
    /// let p = Product::new("จอมอนิเตอร์", 4500.0, 3);
    /// assert_eq!(p.total_value(), 13500.0);
    /// ```
    pub fn total_value(&self) -> f64 {
        self.price * self.quantity as f64
    }
}
```

โค้ดสามบรรทัดภายในตัวอย่าง (`use mini_inventory::Product;`, `let p = ...`, `assert_eq!(...)`) จะถูก `rustdoc`
นำไป**wrap** ให้กลายเป็นโปรแกรมสมบูรณ์แบบหนึ่งโปรแกรม (โดยอัตโนมัติ ถ้าคุณไม่ได้เขียน `fn main()` เอง) แล้ว compile
และรันจริงเหมือนเป็น binary เล็ก ๆ หนึ่งตัว — ถ้า `assert_eq!` fail หรือ code compile ไม่ผ่าน **`cargo test` จะ
ล้มเหลว** เหมือนกับ unit test ที่ fail ทุกประการ

เมื่อเรารัน `cargo test` บน crate ที่มี doc test แบบนี้ (ตัวอย่างจริงจาก crate `mini_inventory` ที่เราจะสร้างแบบ
สมบูรณ์ในหัวข้อ 34.14) ผลลัพธ์จริงที่ได้คือ:

```

สังเกตรายละเอียดสำคัญจากผลลัพธ์จริงนี้:

- ผลลัพธ์มีสอง section แยกกัน: section แรก (`running 0 tests`) คือ unit test ปกติจาก `#[test]` (ในตัวอย่างนี้
  ยังไม่มี unit test เลย) ส่วน section ที่สองคือ **`Doc-tests {ชื่อ crate}`** ซึ่งเป็นการรัน doc test ทั้งหมด
  แยกออกมาต่างหาก
- ชื่อของแต่ละ doc test บอกทั้ง**ไฟล์**และ**item**ที่มันแนบอยู่ พร้อม**เลขบรรทัด**ของ code block นั้นในไฟล์ source
  (เช่น `Inventory::add_product (line 172)`) ทำให้เวลา test fail คุณรู้ทันทีว่าต้องเปิดไฟล์ไหน บรรทัดไหน
- test บางตัวมีข้อความต่อท้ายบอกโหมดพิเศษ เช่น `- compile` (มาจาก attribute `no_run` — compile แต่ไม่รัน) และ
  `- should panic` (มาจาก attribute `should_panic`) — เราจะอธิบายทั้งสอง attribute นี้ละเอียดในหัวข้อถัดไป

**เหตุผลเชิงปรัชญาที่สำคัญที่สุด:** ลองนึกภาพเอกสารแบบเดิม ๆ ที่เขียนแยกจากโค้ด (เช่น wiki, README แยกไฟล์, หรือ
เอกสารที่ generate จาก docstring ในภาษาที่ไม่มีการทดสอบ) — เมื่อผู้เขียน library เปลี่ยน signature ของฟังก์ชัน
(เช่น เปลี่ยนชื่อ parameter, เพิ่ม parameter ใหม่, เปลี่ยน return type) เอกสารที่แยกจากโค้ดจะ**ไม่มีวันรู้เรื่อง
การเปลี่ยนแปลงนี้เลย** ตัวอย่างการใช้งานในเอกสารจะกลาย "ผิด" (outdated) ทันทีแต่ไม่มีอะไรเตือน — ผู้ใช้ library
ที่ก๊อปโค้ดตัวอย่างจากเอกสารไปใช้จะเจอ compile error โดยไม่รู้ว่าทำไม

ใน Rust สถานการณ์นี้**เกิดขึ้นไม่ได้** เพราะ doc test เป็นส่วนหนึ่งของ test suite ที่ `cargo test` รันทุกครั้ง
(และมักถูกรันใน CI ทุก pull request) ถ้าผู้เขียน library เปลี่ยน signature แล้วลืมอัปเดตตัวอย่างในเอกสาร
**`cargo test` จะ fail ทันที** บังคับให้ต้องแก้เอกสารให้ตรงกับโค้ดจริงก่อนจะ merge ได้ — นี่คือที่มาของประโยค
ที่ community Rust พูดกันติดปากว่า **"documentation that cannot lie"** (เอกสารที่โกหกไม่ได้)

### 34.8 ควบคุมพฤติกรรมของ Doc Test: Hidden Lines, `no_run`, `ignore`, `should_panic`

ในทางปฏิบัติ ไม่ใช่ทุกตัวอย่างในเอกสารจะเหมาะกับการ "compile และรันตรง ๆ" เสมอไป บางครั้งเราต้องการซ่อนโค้ด setup
ที่รกหูรกตาออกจากหน้าเอกสาร (แต่ยังให้มัน compile), บางครั้งตัวอย่างมี side effect ที่ไม่ควรรันซ้ำ ๆ ตอน test,
และบางครั้งตัวอย่างเป็นแค่ pseudocode ประกอบแนวคิดที่ compile ไม่ได้เลยด้วยซ้ำ — rustdoc มีเครื่องมือรองรับทุก
สถานการณ์เหล่านี้

#### 34.8.1 ซ่อนบรรทัด Setup ด้วย `#` นำหน้า

บรรทัดใดในโค้ดตัวอย่างที่ขึ้นต้นด้วย `#` (ตามด้วย space) จะถูก **compile และรันตามปกติ แต่ถูกซ่อนจากหน้าเอกสารที่
render ออกมา** ผู้อ่านเอกสารจะไม่เห็นบรรทัดเหล่านี้เลย แต่ compiler ยังเห็นและรันมันจริง — ใช้บ่อยที่สุดสำหรับ
ซ่อน `use` statement ที่ซ้ำซาก หรือซ่อน boilerplate ของ `fn main()` ที่ผู้อ่านไม่จำเป็นต้องเห็นเพื่อเข้าใจ "แก่น"
ของตัวอย่าง

```rust
/// ตัดสินค้าออกจากคลังจำนวนหนึ่ง
///
/// # Examples
///
/// ```
/// # use mini_inventory::{Inventory, Product};
/// # fn main() -> Result<(), mini_inventory::InventoryError> {
/// let mut inventory = Inventory::new();
/// inventory.add_product(Product::new("เมาส์", 299.0, 10))?;
///
/// inventory.remove_stock("เมาส์", 3)?;
/// assert_eq!(inventory.get("เมาส์").unwrap().quantity, 7);
/// # Ok(())
/// # }
/// ```
pub fn remove_stock_doc_demo() {}
```

ในหน้าเอกสารที่ render ออกมา ผู้อ่านจะเห็นเฉพาะ:

```
let mut inventory = Inventory::new();
inventory.add_product(Product::new("เมาส์", 299.0, 10))?;

inventory.remove_stock("เมาส์", 3)?;
assert_eq!(inventory.get("เมาส์").unwrap().quantity, 7);
```

สั้น กระชับ ตรงประเด็น — ไม่มี `use` ที่ซ้ำซาก ไม่มี `fn main()` wrapper ที่รกตา แต่**compiler ยังคง compile
และรันทั้งหมดจริง** รวมบรรทัดที่ซ่อนไว้ด้วย เพราะฉะนั้นตัวอย่างนี้ยังเป็น doc test ที่ตรวจสอบความถูกต้องได้เต็มรูปแบบ
เหมือนเดิม ไม่ได้ "โกง" การทดสอบแต่อย่างใด

**ทำไมไม่ใช้ `//` (comment ธรรมดา) ซ่อนแทน?** เพราะ `//` จะทำให้บรรทัดนั้น**ไม่ถูก compile เลย** — ถ้าคุณ comment
`use mini_inventory::Product;` ทิ้งด้วย `//` โค้ดที่ตามมาจะ compile ไม่ผ่านเพราะหา `Product` ไม่เจอ ในขณะที่ `#`
เป็นกลไกพิเศษของ rustdoc โดยเฉพาะที่แปลว่า "compile บรรทัดนี้ แต่ไม่ต้องแสดงในหน้าเอกสาร" — สอง concept ที่แตกต่าง
กันโดยสิ้นเชิง

**ข้อควรระวังเล็กน้อย:** บรรทัดที่ต้องการให้เป็น `#` แท้ ๆ ที่มีเครื่องหมาย `#` เป็นส่วนหนึ่งของโค้ดจริง (เช่น
attribute `#[derive(Debug)]` ที่อยู่ในตัวอย่าง) จะไม่ถูกซ่อนโดยไม่ตั้งใจ เพราะกลไกนี้มองแค่ `#` ที่ตามด้วย **space**
ที่อยู่**ต้นบรรทัด**เท่านั้น ส่วน `#[derive(Debug)]` มี `#` ตามด้วย `[` ไม่ใช่ space จึงไม่ถูกตีความเป็นบรรทัดซ่อน

#### 34.8.2 `no_run`: Compile แต่ไม่รัน

บางตัวอย่างมี **side effect ที่ไม่เหมาะจะรันซ้ำ ๆ ทุกครั้งที่ `cargo test`** เช่น การเขียนไฟล์ลงดิสก์, การเชื่อมต่อ
เครือข่าย, การลบข้อมูล, หรือการรันโปรแกรมที่ใช้เวลานาน — เราต้องการให้ compiler ยืนยันว่า**syntax ถูกต้องและ
สอดคล้องกับ API จริง** (ถ้า signature เปลี่ยน ตัวอย่างนี้จะ compile ไม่ผ่านเหมือนเดิม) แต่**ไม่ต้องรันจริง**

```rust
/// บันทึกข้อมูลคลังสินค้าทั้งหมดลงไฟล์ข้อความ
///
/// ตัวอย่างนี้ใช้ `no_run` เพราะการรันจริงจะสร้างไฟล์ลงดิสก์ (side effect) ทุกครั้งที่
/// `cargo test` รัน doc test ซึ่งไม่เหมาะสม (อาจชนกับสิทธิ์การเขียนไฟล์ใน CI หรือทำให้
/// test ไม่ deterministic)
///
/// # Examples
///
/// ```no_run
/// use mini_inventory::{Inventory, Product};
///
/// let mut inventory = Inventory::new();
/// inventory.add_product(Product::new("เมาส์", 299.0, 10)).unwrap();
///
/// inventory.save_to_file("inventory_report.txt")?;
/// # Ok::<(), std::io::Error>(())
/// ```
pub fn save_to_file_doc_demo() {}
```

ในผลลัพธ์ของ `cargo test` doc test ที่ใช้ `no_run` จะแสดงคำว่า **`- compile`** ต่อท้ายชื่อ test (ตามที่เราเห็น
จริงในหัวข้อ 34.7: `Inventory::save_to_file (line 274) - compile ... ok`) บอกให้รู้ทันทีว่า test นี้ถูก compile
เท่านั้น ไม่ได้ถูกรันจริง

**หลักการเลือกใช้ `no_run`:** ใช้เมื่อตัวอย่างมี side effect ที่ไม่ deterministic หรือมีผลกระทบต่อ environment
ภายนอก เช่น I/O บนไฟล์ระบบ, การเรียก network API จริง, การอ่าน environment variable ที่อาจไม่มีในเครื่อง CI,
หรือโค้ดที่ใช้เวลารันนานเกินควรสำหรับ test suite (เช่น sleep หลายวินาที) — สิ่งที่ `no_run` **ยังคงยืนยันได้** คือ
ความถูกต้องของ syntax และ type ทั้งหมด ซึ่งดีกว่าไม่ตรวจสอบอะไรเลย

#### 34.8.3 `ignore`: ไม่ Compile เลย

ในบางกรณี ตัวอย่างในเอกสารเป็นแค่ **pseudocode ประกอบแนวคิด** ที่อ้างถึง type หรือฟังก์ชันที่ไม่มีอยู่จริงใน crate
นี้ (เช่น แสดงการเชื่อมต่อกับระบบภายนอกในเชิงสมมติฐาน หรือแสดงตัวอย่างในภาษา/framework อื่นเพื่อเปรียบเทียบ) ถ้าใช้
` ``` ` เปล่า ๆ หรือ ` ```rust ` ธรรมดา ตัวอย่างนี้จะถูก compile และ**ล้มเหลวแน่นอน** เพราะ type ที่อ้างถึงไม่มีจริง
— attribute `ignore` แก้ปัญหานี้โดยบอก rustdoc ว่า **"ไม่ต้อง compile บล็อกนี้เลย"**

```rust
/// # แผนอนาคต (แนวคิดเท่านั้น ยังไม่มีอยู่จริงใน crate นี้)
///
/// ในอนาคตไลบรารีนี้อาจรองรับการซิงค์ข้อมูลกับเครื่อง POS (point-of-sale) หน้าร้านโดยตรง
/// โค้ดตัวอย่างด้านล่างเป็นเพียงแนวคิดประกอบ (`PosTerminal` ไม่มีอยู่จริงใน crate นี้ ณ ตอนนี้)
/// จึงถูกทำเครื่องหมายด้วย `ignore` เพื่อไม่ให้ rustdoc พยายาม compile มัน:
///
/// ```ignore
/// let pos = PosTerminal::connect("192.168.1.50:9100")?;
/// pos.sync_inventory(&inventory)?;
/// ```
fn future_plans_doc_demo() {}
```

จากการตรวจสอบจริง ตัวอย่างที่ใช้ `ignore` จะปรากฏในผลลัพธ์ `cargo test` เป็นบรรทัดที่ลงท้ายด้วย **`... ignored`**
(ไม่ใช่ `ok` หรือ `FAILED`) และ**ไม่ถูกนับรวมในจำนวน `passed`** — ตัวอย่างผลลัพธ์จริงเมื่อมี doc test แบบนี้ปนอยู่:

```
running 12 tests
test src/lib.rs - (line 26) ... ignored
test src/lib.rs - (line 8) ... ok
...
test result: ok. 11 passed; 0 failed; 1 ignored; 0 measured; 0 filtered out; finished in 0.09s
```

**หลักการเลือกใช้ `ignore` เทียบกับ `no_run`:** ใช้ `ignore` เมื่อตัวอย่าง**compile ไม่ผ่านแน่นอน** (เพราะอ้างถึง
สิ่งที่ไม่มีอยู่จริง หรือเป็นแค่แนวคิดร่าง ๆ) ในขณะที่ใช้ `no_run` เมื่อตัวอย่าง**compile ผ่านได้จริง** แค่ไม่อยากให้
รัน — ถ้าคุณใช้ `ignore` กับตัวอย่างที่จริง ๆ compile ผ่านได้ คุณกำลัง**เสียโอกาส**ในการตรวจสอบความถูกต้องของ
ตัวอย่างนั้นไปโดยไม่จำเป็น เพราะ rustdoc จะไม่ตรวจสอบอะไรเลยกับบล็อกที่ `ignore`

#### 34.8.4 `should_panic`: คาดหวังว่าจะ Panic

สอดคล้องกับ `#[should_panic]` ที่เราเรียนใน Part 32 สำหรับ unit test ปกติ — doc test ก็มี attribute เดียวกันนี้
สำหรับกรณีที่**ตัวอย่างมีไว้เพื่อแสดงว่าฟังก์ชันจะ panic ในสถานการณ์ไหน**

```rust
/// สร้างสินค้าใหม่
///
/// # Panics
///
/// ฟังก์ชันนี้จะ panic ทันทีถ้า `price` เป็นค่าลบ
///
/// ```should_panic
/// # struct Product;
/// # impl Product {
/// #     fn new(name: &str, price: f64, quantity: u32) -> Self {
/// #         assert!(price >= 0.0, "ราคาสินค้าห้ามติดลบ: {price}");
/// #         Product
/// #     }
/// # }
/// let _ = Product::new("ของเสีย", -50.0, 1); // ราคาห้ามติดลบ -> panic
/// ```
fn new_product_panic_demo() {}
```

ถ้าไม่ใส่ `should_panic` doc test นี้จะ**ล้มเหลวทันที** เพราะโปรแกรมภายในเกิด panic จริง (exit code ไม่ใช่ 0)
ส่วนถ้าใส่ `should_panic` แล้วโค้ดกลับ**ไม่** panic จริง (เช่น อนาคตมีคนแก้ `Product::new` ให้ handle ค่าลบแบบอื่น
โดยไม่ panic) doc test นี้ก็จะล้มเหลวเช่นกัน (เพราะคาดหวัง panic แต่ไม่เกิดขึ้น) — behavior นี้เหมือนกับ
`#[should_panic]` ของ unit test ทุกประการ เพียงแค่ย้ายมาอยู่ในบริบทของ doc comment

ในผลลัพธ์ `cargo test` จริง (จากหัวข้อ 34.7) doc test นี้แสดงเป็น
`Product::new (line 105) - should panic ... ok` — คำว่า `- should panic` บอกโหมดพิเศษ และ `ok` บอกว่า "panic
เกิดขึ้นจริงตามที่คาดหวัง" (ไม่ใช่ว่าโค้ดทำงานสำเร็จแบบไม่ panic)

**สรุปตารางทั้งสี่กลไกที่ใช้ควบคุม doc test:**

| กลไก | Compile? | รันจริง? | ใช้เมื่อ |
|---|---|---|---|
| (ไม่มี attribute) | ✅ | ✅ | กรณีปกติทั่วไป ต้องการยืนยันทั้ง compile และผลลัพธ์ที่ถูกต้อง |
| บรรทัดขึ้นต้นด้วย `#` | ✅ (บรรทัดนั้นด้วย) | ✅ | ซ่อน setup/boilerplate จากหน้าเอกสาร แต่ยังตรวจสอบจริง |
| `no_run` | ✅ | ❌ | มี side effect (I/O, network) ที่ไม่ควรรันซ้ำตอน test |
| `ignore` | ❌ | ❌ | pseudocode/แนวคิดที่อ้างถึงสิ่งที่ไม่มีจริงใน crate นี้ |
| `should_panic` | ✅ | ✅ (คาดหวัง panic) | แสดงเงื่อนไขที่ฟังก์ชันจะ panic ตามที่บอกไว้ใน `# Panics` |

หมายเหตุ: attribute เหล่านี้เขียนต่อจาก ` ``` ` ได้โดยตรง (เช่น ` ```no_run `) และสามารถรวมกันได้ในบางกรณี เช่น
` ```no_run,should_panic ` ถ้าต้องการทั้ง compile-only และคาดหวัง panic (พบไม่บ่อยแต่เป็นไปได้ตาม syntax)

### 34.9 Doc Test กับฟังก์ชันที่ Return `Result` และ `?` Operator

จาก Part 12 เราทราบว่า `?` operator ใช้ได้เฉพาะภายในฟังก์ชันที่ return type เข้ากันได้ (เช่น `Result<T, E>` หรือ
`Option<T>`) คำถามคือ: ในเมื่อ rustdoc สร้าง `fn main()` ให้อัตโนมัติเมื่อตัวอย่างไม่ได้เขียน `fn main()` เอง แล้ว
`fn main()` แบบปริยาย (implicit) นั้น return type อะไร ถึงจะให้ `?` ใช้ได้?

คำตอบคือ: **ถ้าตัวอย่างมี `?` แต่ไม่ได้เขียน `fn main()` เอง `rustdoc` จะสร้าง `fn main() -> Result<(), impl
std::fmt::Debug>` ให้อัตโนมัติ** ทำให้ `?` ใช้งานได้ทันทีโดยไม่ต้องเขียน wrapper เอง:

```rust
/// เพิ่มสินค้าลงในคลัง
///
/// # Examples
///
/// ```
/// use mini_inventory::{Inventory, Product};
///
/// let mut inventory = Inventory::new();
/// inventory.add_product(Product::new("เมาส์", 299.0, 10))?;
/// assert_eq!(inventory.total_value(), 2990.0);
/// # Ok::<(), mini_inventory::InventoryError>(())
/// ```
fn add_product_doc_demo() {}
```

สังเกตว่าตัวอย่างข้างต้นมี `?` อยู่ในบรรทัดที่สาม (`inventory.add_product(...)?;`) โดยไม่มี `fn main()`
ที่มองเห็นในหน้าเอกสาร — แต่ก็ยังใช้งานได้เพราะ rustdoc แทรก wrapper ให้เอง อย่างไรก็ตาม **เรายังคงต้องเขียนบรรทัด
`# Ok::<(), mini_inventory::InventoryError>(())` ที่ซ่อนไว้ด้วย `#`** เพื่อบอก compiler ว่า "จบฟังก์ชันด้วยการ
คืน `Ok(())`" — เพราะ rustdoc รู้แค่ว่าต้อง wrap เป็น `fn main() -> Result<(), E>` แต่**ไม่รู้ว่า E คือ type
ไหน** และไม่รู้ว่าจะคืนค่าอะไรตอนจบฟังก์ชัน คุณต้องระบุเองเสมอ

**ทางเลือกที่สอง — เขียน `fn main()` เต็มรูปแบบเอง (มักใช้เมื่อ error type ซับซ้อนหรือต้องการความชัดเจน):**

```rust
/// ตัดสินค้าออกจากคลังจำนวนหนึ่ง
///
/// # Examples
///
/// ```
/// use mini_inventory::{Inventory, Product};
///
/// # fn main() -> Result<(), mini_inventory::InventoryError> {
/// let mut inventory = Inventory::new();
/// inventory.add_product(Product::new("เมาส์", 299.0, 10))?;
///
/// inventory.remove_stock("เมาส์", 3)?;
/// assert_eq!(inventory.get("เมาส์").unwrap().quantity, 7);
/// # Ok(())
/// # }
/// ```
fn remove_stock_doc_demo_2() {}
```

รูปแบบนี้เขียน `fn main() -> Result<(), mini_inventory::InventoryError>` เองตรง ๆ (ซ่อนไว้ด้วย `#` เพื่อไม่ให้
รกหน้าเอกสาร) แล้วปิดด้วย `Ok(())` และ `}` (ก็ซ่อนไว้เช่นกัน) — ข้อดีของวิธีนี้คือ**ชัดเจนกว่า**ว่า error type
คืออะไรเป๊ะ ๆ โดยไม่ต้องพึ่งการอนุมานของ rustdoc ส่วนวิธีแรก (`# Ok::<(), E>(())`) กระชับกว่าและเพียงพอสำหรับ
กรณีทั่วไปที่ไม่ซับซ้อน — ทั้งสองแบบใช้กันจริงในโค้ด production แล้วแต่ความชอบของทีม แต่รูปแบบที่สองเป็นที่นิยม
มากกว่าเพราะสื่อความหมาย (self-documenting) ว่า "ฟังก์ชันนี้อาจ error ด้วย type X" ได้ชัดเจนกว่า

**เหตุผลเชิงลึกที่ต้องเข้าใจ:** doc test แต่ละบล็อกถูก**คอมไพล์แยกเป็นโปรแกรมเดี่ยว ๆ ของตัวเอง** ไม่ต่างจาก
`fn main()` ปกติในไฟล์ `main.rs` ทุกกฎของภาษาที่ใช้กับ `fn main()` ทั่วไป (เช่น `?` ต้องมี return type ที่รองรับ)
ก็ใช้กับ doc test เหมือนกันทุกประการ — นี่คือเหตุผลที่ยืนยันอีกครั้งว่า doc test ไม่ใช่ "ข้อความตัวอย่าง" แต่เป็น
**โปรแกรม Rust จริง**ที่ compiler ปฏิบัติต่อมันเหมือนโค้ดทุกชิ้นในโปรเจกต์

### 34.10 เชื่อมโยงระหว่าง Item ด้วย Intra-doc Links

เราได้เห็นการใช้ `[Type]` และ `[crate::module::function]` แบบผ่าน ๆ มาแล้วในหัวข้อก่อนหน้า ตอนนี้เรามาดูกลไกนี้
อย่างละเอียด **Intra-doc link** คือ syntax พิเศษที่ให้คุณ**ลิงก์ไปยัง item อื่นภายใน crate เดียวกัน (หรือ crate
dependency)** โดยไม่ต้องเขียน URL แบบเต็ม — rustdoc จะคำนวณ URL ที่ถูกต้องให้เองตอน generate เอกสาร

รูปแบบพื้นฐานที่สุดคือครอบชื่อ item ด้วย backtick แล้วครอบด้วย `[]`:

```rust
/// ข้อผิดพลาดที่อาจเกิดขึ้นจากการดำเนินการกับ [`Inventory`]
pub enum InventoryError {
    /// ไม่พบสินค้าชื่อนี้ในคลัง
    ProductNotFound(String),
}

pub struct Inventory;
```

`rustdoc` จะพยายาม**resolve** ชื่อ `Inventory` โดยดูจาก scope ปัจจุบัน (เหมือนกับที่ compiler resolve ชื่อ type
ตอน compile จริง) แล้วสร้าง hyperlink ที่ถูกต้องให้ ถ้า `Inventory` เป็น struct ที่ประกาศไว้ในไฟล์เดียวกันหรือ
import มาแล้ว ลิงก์นี้จะพาไปหน้า `struct.Inventory.html` โดยอัตโนมัติ

สำหรับการลิงก์ไปยัง**เจาะจงเมธอดหรือ associated item** ใช้ `::` คั่นแบบเดียวกับ path ปกติในโค้ด Rust:

```rust
/// สร้างด้วย [`Product::new`] แล้วเพิ่มลงคลังด้วย [`Inventory::add_product`]
pub struct Product;
```

และสำหรับการลิงก์แบบระบุ path เต็มจาก root ของ crate (มีประโยชน์เมื่อ item ที่ต้องการลิงก์ไม่ได้อยู่ใน scope
เดียวกัน หรือเมื่อต้องการความชัดเจนไม่ให้สับสน) ใช้ `crate::` นำหน้า:

```rust
//! ดูฟังก์ชันสร้างรายงานที่ module [`crate::report`]
//! หรือลิงก์แบบเจาะจงไปที่ [`crate::report::summarize`]
```

นอกจากนี้ยังมี keyword พิเศษ `[crate]` ที่ลิงก์กลับไปหน้าเอกสารหลักของ crate เอง (หน้า `index.html` ที่มาจาก
`//!` บนสุดของ `lib.rs`) มีประโยชน์เมื่อคุณอยู่ในหน้าเอกสารของ struct ลึก ๆ แล้วต้องการให้ผู้อ่านย้อนกลับไปดู
"ภาพรวมทั้งหมด" ได้ง่าย ๆ

**จุดที่ทำให้ intra-doc link ทรงพลังกว่าการเขียน Markdown link ปกติ (`[text](url)`) มาก:** ลิงก์แบบ Markdown ปกติ
ต้องเขียน URL ตรง ๆ ซึ่งจะ**เสีย (break)** ทันทีถ้าโครงสร้างไฟล์เปลี่ยน หรือถ้า item ที่ลิงก์ไปถูก rename — แต่
intra-doc link ใช้**ชื่อ item ในโค้ด** เป็นตัวอ้างอิง ถ้าชื่อยังตรงกับที่ประกาศไว้จริง ลิงก์จะทำงานถูกต้องเสมอไม่ว่า
โครงสร้างไฟล์ HTML จะเปลี่ยนไปอย่างไร และที่สำคัญกว่านั้นคือ **rustdoc ตรวจสอบความถูกต้องของลิงก์เหล่านี้ได้จริง**
— ถ้าคุณพิมพ์ชื่อ item ผิด (เช่น `[Inventory::add_produkt]` สะกดผิด) rustdoc จะตรวจพบว่า**ไม่มี item ชื่อนี้อยู่จริง**

โดย default การพบลิงก์ที่เสียแบบนี้จะแสดงเป็นแค่ **warning** ตอนรัน `cargo doc` แต่ถ้าคุณต้องการให้เข้มงวดขึ้น
(บังคับให้ลิงก์เสียกลายเป็น compile error ทันที ไม่ใช่แค่ warning ที่มองข้ามได้) ใส่ attribute นี้ที่บนสุดของ
`lib.rs`:

```rust
#![deny(rustdoc::broken_intra_doc_links)]
```

เมื่อเปิด lint นี้แล้ว ถ้ามี intra-doc link ที่เสียอยู่ในโค้ด `cargo doc` จะ**ล้มเหลวทันที** (ไม่ generate เอกสาร
ให้เลย) เราจะเห็น error message จริงจากกรณีนี้ในหัวข้อ "กับดักที่พบบ่อย" ท้ายบท

**ทำไมเรื่องนี้สำคัญเชิง maintenance?** โปรเจกต์ขนาดใหญ่มักมี refactor บ่อย ๆ — เปลี่ยนชื่อฟังก์ชัน, ย้าย struct
ไปอีก module, ลบ field ที่ไม่ใช้แล้ว ถ้าเอกสารมี cross-reference จำนวนมาก (ซึ่งเป็นสิ่งที่ควรมีเพื่อให้ผู้อ่าน
เอกสารนำทางไปมาระหว่าง item ได้ง่าย) การเปลี่ยนชื่อ item หนึ่งตัวอาจทำให้ลิงก์ในเอกสารที่อื่นเสียโดยไม่มีใครรู้ตัว
— `#![deny(rustdoc::broken_intra_doc_links)]` เปลี่ยนปัญหานี้จาก "บั๊กเงียบที่ค้นพบทีหลัง" ให้กลายเป็น "compile
error ที่บังคับต้องแก้ก่อน merge" ทันที เช่นเดียวกับที่ doc test บังคับให้ตัวอย่างโค้ดต้องถูกต้องเสมอ

### 34.11 Documenting ทั้ง Crate ด้วย `//!`: Elevator Pitch Pattern

ตอนนี้เรามาดูวิธีเขียนเอกสารระดับ crate ที่สมบูรณ์ตามแบบที่ crate คุณภาพสูงบน crates.io ใช้จริง รูปแบบที่พบมากที่สุด
เรียกกันในหมู่ community ว่า **"elevator pitch" pattern** — ตั้งชื่อตามแนวคิด "อธิบายให้จบภายในเวลาที่ลิฟต์วิ่ง
ไม่กี่ชั้น" คือต้องสื่อสารคุณค่าหลักของ crate ได้อย่างรวดเร็วตั้งแต่ประโยคแรก ก่อนจะลงรายละเอียด

โครงสร้างที่นิยมใช้กันมีสามส่วนเรียงตามลำดับ:

1. **ชื่อ crate เป็น heading ระดับ 1** พร้อมประโยคสรุปสั้น ๆ ว่า crate นี้ทำอะไร (elevator pitch)
2. **ตัวอย่างการใช้งานพื้นฐานที่สุด** แสดงให้เห็น flow การใช้งานหลักในไม่กี่บรรทัด (และเป็น doc test ที่รันจริง
   ด้วยเช่นกัน)
3. **ลิงก์ไปยัง item สำคัญ** ที่ผู้อ่านควรไปดูต่อ (ผ่าน intra-doc link)

```rust
//! # mini_inventory
//!
//! ไลบรารีขนาดเล็กสำหรับจัดการสินค้าคงคลัง (inventory) ของร้านค้า
//! ใช้เป็นตัวอย่างประกอบการสอนเรื่อง documentation ในหลักสูตร Rust ภาษาไทย
//!
//! ## ตัวอย่างการใช้งานเบื้องต้น
//!
//! ```
//! use mini_inventory::{Inventory, Product};
//!
//! let mut inventory = Inventory::new();
//! inventory.add_product(Product::new("เมาส์", 299.0, 10)).unwrap();
//!
//! assert_eq!(inventory.total_value(), 2990.0);
//! ```
//!
//! ดูรายละเอียดเพิ่มเติมที่ [`Inventory`] และ [`Product`]
//! ส่วนฟังก์ชันสร้างรายงานอยู่ที่ module [`report`]
```

โน้ตสิ่งสำคัญที่ทำให้รูปแบบนี้มีประสิทธิภาพ:

- **ประโยคแรกสั้นและตรงประเด็น** — ผู้อ่านที่เพิ่งเจอ crate นี้ครั้งแรก (เช่น ผ่านการค้นหาบน crates.io) ควรเข้าใจ
  "crate นี้มีไว้ทำอะไร" ภายในไม่กี่วินาที ก่อนจะตัดสินใจว่าจะอ่านต่อหรือไม่
- **ตัวอย่างการใช้งานอยู่สูงที่สุดเท่าที่จะทำได้** — เพราะผู้อ่านส่วนใหญ่ (โดยเฉพาะที่มีประสบการณ์ Rust มาบ้าง)
  เรียนรู้ API ได้เร็วที่สุดจากการอ่านตัวอย่างโค้ด มากกว่าอ่านคำอธิบายเป็นพารากราฟยาว ๆ และตัวอย่างนี้**เป็น doc
  test ด้วย** — ถ้าวันหนึ่ง API หลักของ crate เปลี่ยนจนตัวอย่างนี้ใช้ไม่ได้อีก `cargo test` จะแจ้งทันที
- **ลิงก์นำทางไปยัง item สำคัญที่ท้าย** — ทำหน้าที่เป็น "สารบัญแบบย่อ" ให้ผู้อ่านรู้ว่าควรไปดูต่อที่ไหน แทนที่จะ
  ต้อง scroll เองไปหาในตาราง item ทั้งหมดของหน้า index

รูปแบบนี้เมื่อ generate ด้วย `cargo doc --open` จะกลายเป็น**หน้าแรก**ของเอกสาร crate ทั้งหมด — เป็นสิ่งแรกที่คนเห็น
ทั้งตอนรัน locally และตอนดูบน docs.rs (ซึ่งเราจะพูดถึงในหัวข้อถัดไป) การลงทุนเวลาเขียน `//!` แบบนี้ให้ดีจึงคุ้มค่า
มากเมื่อเทียบกับเวลาที่ใช้ เพราะมันเป็น "หน้าปก" ของทั้งไลบรารี

### 34.12 ซ่อน Item จากเอกสารด้วย `#[doc(hidden)]`

ในการเขียนไลบรารีจริง บางครั้งมี item ที่ต้องเป็น `pub` (เพราะโค้ดส่วนอื่นของ crate ต้องเรียกใช้ได้ข้าม module
หรือ integration test ต้องเข้าถึงได้) แต่**ไม่ใช่ส่วนหนึ่งของ "สัญญา" (API contract)** ที่ผู้ใช้ไลบรารีภายนอกควร
พึ่งพาหรือรับรู้ — เช่น ฟังก์ชัน helper ภายในที่ถูก export ออกมาด้วยเหตุผลทางเทคนิคเท่านั้น attribute
`#[doc(hidden)]` แก้ปัญหานี้โดยบอก rustdoc ว่า **"item นี้เป็น public จริง (compile ได้ เรียกใช้ได้) แต่ไม่ต้อง
แสดงในหน้าเอกสารที่ generate ออกมา"**

```rust
/// รายการ item ที่มีอยู่ในระบบภายใน แต่ไม่ต้องการให้แสดงในเอกสารสาธารณะ (public docs)
///
/// ฟังก์ชันนี้ต้องเป็น `pub` เพราะโค้ดส่วนอื่นของ crate (หรือ integration test) ต้องเรียกใช้ได้
/// แต่ไม่ใช่ส่วนหนึ่งของ "สัญญา" (contract) ที่ผู้ใช้ไลบรารีภายนอกควรพึ่งพา จึงซ่อนจากหน้า docs.rs
/// ด้วย `#[doc(hidden)]`
#[doc(hidden)]
pub fn internal_row_count() -> usize {
    42
}
```

เมื่อ generate เอกสารด้วย `cargo doc` ฟังก์ชัน `internal_row_count` จะ**ไม่ปรากฏ**ในหน้า index ของ module,
ไม่ปรากฏในตาราง item, และไม่มีหน้า `fn.internal_row_count.html` ถูกสร้างขึ้นเลย (เราตรวจสอบพฤติกรรมนี้จริงในการ
สร้างตัวอย่างประกอบบทนี้ — ดูหัวข้อ 34.14) แต่โค้ดจากภายนอก crate ที่ `use` ฟังก์ชันนี้เข้ามาตรง ๆ ยังคง compile
และเรียกใช้ได้ปกติทุกประการ เพราะ `#[doc(hidden)]` มีผลแค่กับ**การ generate เอกสาร** ไม่มีผลใด ๆ กับ visibility
หรือการ compile

**สถานการณ์จริงที่ใช้ `#[doc(hidden)]` บ่อยที่สุด:**

1. **Macro-generated code** — macro (ที่เราจะเรียนใน Part 36) มักต้อง generate ฟังก์ชันหรือ struct ที่ `pub`
   เพื่อให้ macro ทำงานข้าม module ได้ แต่ผู้ใช้ macro ไม่ควรเรียกใช้สิ่งเหล่านี้ตรง ๆ ด้วยตัวเอง
2. **Re-export สำหรับ internal linking เท่านั้น** — เมื่อ crate มีโครงสร้าง internal ที่ซับซ้อนและต้อง re-export
   บางอย่างข้าม module แต่ไม่อยากให้ผู้ใช้ภายนอกเห็นรายละเอียด internal เหล่านั้น
3. **Deprecated item ที่ยังต้องคงไว้เพื่อ backward compatibility** — บางครั้งใช้ร่วมกับ `#[deprecated]` เพื่อ
   คงไว้ให้โค้ดเก่ายัง compile ผ่านได้ แต่ไม่อยากให้คนใหม่เห็นและเริ่มใช้มันในเอกสาร

**ข้อควรระวัง:** `#[doc(hidden)]` **ไม่ใช่กลไก security** — มันเป็นเพียงการซ่อนจากหน้าเอกสารที่ generate ออกมา
เท่านั้น item ที่ `#[doc(hidden)]` ยัง**เป็น public API จริง** ที่ใครก็ตามที่รู้ชื่อ (เช่น อ่านจาก source code
โดยตรง หรือใช้ IDE ที่แสดง symbol ทั้งหมดไม่สนใจ hidden) ก็สามารถเรียกใช้ได้ ถ้าต้องการซ่อนจริง ๆ ไม่ให้เรียกจาก
ภายนอก crate ได้เลย ต้องใช้ visibility modifier เช่น `pub(crate)` (จำกัด scope ให้เห็นได้แค่ภายใน crate เดียวกัน
— เรียนมาแล้วใน Part 16) ไม่ใช่ `#[doc(hidden)]`

### 34.13 docs.rs: เอกสารสาธารณะฟรีสำหรับทุก Crate บน crates.io

จาก Part 17 หัวข้อ 17.10 เราได้เรียนเรื่องการ publish package ขึ้น crates.io พร้อม metadata ที่บังคับต้องมี เช่น
`license` และ `description` — ตอนนี้เรามาต่อยอดเรื่องนี้ด้วยข้อเท็จจริงที่สำคัญมากของ ecosystem Rust:

**ทุกครั้งที่มีคน publish crate เวอร์ชันใหม่ขึ้น crates.io เอกสารของ crate เวอร์ชันนั้นจะถูก build และ host ให้
ฟรีโดยอัตโนมัติที่ [docs.rs](https://docs.rs)** โดยผู้เขียน crate**ไม่ต้องทำอะไรเพิ่มเติมเลย** — ไม่ต้องตั้งค่า
CI แยก, ไม่ต้อง deploy เว็บเอกสารเอง, ไม่ต้องเสียค่าใช้จ่ายใด ๆ ทั้งสิ้น ระบบของ docs.rs จะดึงโค้ดจาก crates.io
มา รัน `cargo doc` ให้ (ในสภาพแวดล้อมที่ควบคุมและตรงกับ metadata ของ crate นั้น) แล้ว host ผลลัพธ์ HTML ที่ได้
ไว้ที่ URL รูปแบบ `https://docs.rs/{ชื่อ-crate}/{เวอร์ชัน}/{ชื่อ-crate}/`

ตัวอย่าง URL จริงที่ทุกคนเข้าถึงได้: `https://docs.rs/serde/latest/serde/` (เอกสารของ crate `serde` เวอร์ชัน
ล่าสุด) หรือ `https://docs.rs/tokio/1.40.0/tokio/` (เอกสารของ crate `tokio` เวอร์ชันที่ระบุเจาะจง)

**ทำไมเรื่องนี้ยกระดับความสำคัญของการเขียน doc comment ให้ดีขึ้นไปอีกขั้น?** เพราะ doc comment ของคุณ**ไม่ใช่แค่
เอกสารสำหรับทีมตัวเองอีกต่อไป** — มันคือ**หน้าตาสาธารณะ (public-facing)** ของ crate ที่**ใครก็ตามในโลก**ที่กำลัง
พิจารณาว่าจะเพิ่ม crate ของคุณเป็น dependency หรือไม่ จะเห็นก่อนตัดสินใจ นี่คือความแตกต่างเชิงจิตวิทยาที่สำคัญมาก
เมื่อเทียบกับการเขียนคอมเมนต์ในโปรเจกต์ภายในบริษัทที่มีแต่ทีมตัวเองเห็น:

1. **Crate ที่มีเอกสารดีบน docs.rs มักถูกเลือกใช้มากกว่า crate ที่ทำหน้าที่เหมือนกันแต่ไม่มีเอกสาร** — เพราะ
   นักพัฒนาที่กำลังเลือก dependency มักเปิด docs.rs เป็นจุดแรกในการประเมิน ก่อนจะอ่าน source code จริงด้วยซ้ำ
2. **Badge "docs.rs" ที่แสดงสถานะ build** (มักติดไว้บน README ของ repository) เป็นสัญญาณความน่าเชื่อถือ — ถ้า
   docs.rs build เอกสารไม่สำเร็จ (เช่น เพราะ doc test บางตัว fail ตอน generate หรือ code ใช้ feature ที่ไม่รองรับ
   ใน environment ของ docs.rs) มันจะแสดงสถานะ "failed" ต่อสาธารณะทันที เป็นแรงกดดันทางบวกให้ผู้เขียน crate ดูแล
   เอกสารให้ดีอยู่เสมอ
3. **เพราะ doc test ถูกรันจริงตอน build เอกสารด้วย** (docs.rs รัน `cargo doc` ซึ่งต้อง compile ทุกตัวอย่างให้ผ่าน
   แม้ไม่ได้รัน `cargo test` เต็มรูปแบบ) ตัวอย่างในเอกสารของ crate สาธารณะบน docs.rs จึง**การันตีได้ในระดับหนึ่งว่า
   compile ผ่านจริง** ไม่ใช่ตัวอย่างลวงที่เขียนทิ้งไว้เฉย ๆ

พูดสรุปให้เห็นภาพรวม: ระบบทั้งหมดที่เราเรียนในบทนี้ — `///`/`//!`, Markdown rendering, doc test, intra-doc link —
ทำงานประสานกันเป็น **pipeline อัตโนมัติเดียว** ที่เริ่มจากการเขียนคอมเมนต์ในโค้ดของคุณ ไปจนถึงหน้าเอกสารสาธารณะ
ที่ทดสอบแล้วว่าใช้งานได้จริง โดยไม่ต้องมีขั้นตอน manual คั่นกลางเลยแม้แต่ขั้นตอนเดียว — นี่คือเหตุผลที่ทำให้
documentation ถูกยกให้เป็นหนึ่งในจุดแข็งที่สุดของ Rust ecosystem เมื่อเทียบกับภาษาโปรแกรมมิ่งอื่น ๆ ส่วนใหญ่

### 34.14 ตัวอย่างจริงแบบสมบูรณ์: เอกสารทั้งหมดของ `mini_inventory`

ถึงเวลารวมทุกอย่างที่เรียนมาในบทนี้เข้าด้วยกัน เราจะเขียนเอกสารแบบสมบูรณ์สำหรับไลบรารีจัดการสินค้าคงคลังขนาดเล็ก
ชื่อ `mini_inventory` — ครอบคลุม crate-level `//!`, module-level `//!` (แยกไฟล์), `///` บนทุก public item,
`# Examples`/`# Panics`/`# Errors` ที่ถูกใช้อย่างเหมาะสม, doc test มากกว่า 10 ตัว, และครบทั้งสี่ attribute ที่
เรียนมา (`no_run`, `ignore`, `should_panic`, และบรรทัดซ่อนด้วย `#`)

ตัวอย่างนี้ถูกสร้างเป็นโปรเจกต์ cargo จริงและตรวจสอบด้วย `cargo test` และ `cargo doc` จริงแล้ว (ดูวิธีตรวจสอบใน
ท้ายบท) — โครงสร้างไฟล์คือ:

```
mini_inventory/
├── Cargo.toml
└── src/
    ├── lib.rs      <- crate-level doc, Product, Inventory, InventoryError
    └── report.rs   <- module report แยกไฟล์ พร้อม module-level doc ของตัวเอง
```

**`src/lib.rs` (ฉบับสมบูรณ์):**

```rust
//! # mini_inventory
//!
//! ไลบรารีขนาดเล็กสำหรับจัดการสินค้าคงคลัง (inventory) ของร้านค้า
//! ใช้เป็นตัวอย่างประกอบการสอนเรื่อง documentation ในหลักสูตร Rust ภาษาไทย
//!
//! ## ตัวอย่างการใช้งานเบื้องต้น
//!
//! ```
//! use mini_inventory::{Inventory, Product};
//!
//! let mut inventory = Inventory::new();
//! inventory.add_product(Product::new("เมาส์", 299.0, 10)).unwrap();
//!
//! assert_eq!(inventory.total_value(), 2990.0);
//! ```
//!
//! ดูรายละเอียดเพิ่มเติมที่ [`Inventory`] และ [`Product`]
//! ส่วนฟังก์ชันสร้างรายงานอยู่ที่ module [`report`]
//!
//! ## แผนอนาคต (แนวคิดเท่านั้น ยังไม่มีอยู่จริงใน crate นี้)
//!
//! ในอนาคตไลบรารีนี้อาจรองรับการซิงค์ข้อมูลกับเครื่อง POS (point-of-sale) หน้าร้านโดยตรง
//! โค้ดตัวอย่างด้านล่างเป็นเพียงแนวคิดประกอบ (`PosTerminal` ไม่มีอยู่จริงใน crate นี้ ณ ตอนนี้)
//! จึงถูกทำเครื่องหมายด้วย `ignore` เพื่อไม่ให้ rustdoc พยายาม compile มัน:
//!
//! ```ignore
//! let pos = PosTerminal::connect("192.168.1.50:9100")?;
//! pos.sync_inventory(&inventory)?;
//! ```

#![deny(rustdoc::broken_intra_doc_links)]

use std::collections::HashMap;
use std::fmt;

pub mod report;

/// ข้อผิดพลาดที่อาจเกิดขึ้นจากการดำเนินการกับ [`Inventory`]
#[derive(Debug, PartialEq)]
pub enum InventoryError {
    /// ไม่พบสินค้าชื่อนี้ในคลัง
    ProductNotFound(String),
    /// จำนวนที่ต้องการตัดออกมากกว่าจำนวนที่มีอยู่จริง
    InsufficientStock {
        name: String,
        available: u32,
        requested: u32,
    },
}

impl fmt::Display for InventoryError {
    fn fmt(&self, f: &mut fmt::Formatter<'_>) -> fmt::Result {
        match self {
            InventoryError::ProductNotFound(name) => {
                write!(f, "ไม่พบสินค้าชื่อ '{name}' ในคลัง")
            }
            InventoryError::InsufficientStock {
                name,
                available,
                requested,
            } => write!(
                f,
                "สินค้า '{name}' มีเหลือ {available} ชิ้น แต่ต้องการตัด {requested} ชิ้น"
            ),
        }
    }
}

impl std::error::Error for InventoryError {}

/// สินค้าหนึ่งรายการในคลัง
///
/// สร้างด้วย [`Product::new`] แล้วเพิ่มลงคลังด้วย [`Inventory::add_product`]
#[derive(Debug, Clone, PartialEq)]
pub struct Product {
    /// ชื่อสินค้า ใช้เป็น key เวลาเก็บใน [`Inventory`]
    pub name: String,
    /// ราคาต่อหน่วย (บาท) ต้องไม่ติดลบ
    pub price: f64,
    /// จำนวนที่มีอยู่ในคลัง ณ ขณะนี้
    pub quantity: u32,
}

impl Product {
    /// สร้างสินค้าใหม่
    ///
    /// # Panics
    ///
    /// ฟังก์ชันนี้จะ panic ทันทีถ้า `price` เป็นค่าลบ เพราะราคาสินค้าติดลบไม่มีความหมาย
    /// ทางธุรกิจ และเป็นสัญญาณของบั๊กที่ควรถูกจับให้เร็วที่สุด ณ จุดที่สร้างข้อมูลผิดพลาด
    /// ไม่ใช่ปล่อยให้ค่าที่ผิดไหลต่อไปจนเกิดผลลัพธ์ประหลาดในส่วนอื่นของโปรแกรม
    ///
    /// # Examples
    ///
    /// ```
    /// use mini_inventory::Product;
    ///
    /// let p = Product::new("คีย์บอร์ด", 890.0, 5);
    /// assert_eq!(p.name, "คีย์บอร์ด");
    /// assert_eq!(p.quantity, 5);
    /// ```
    ///
    /// ตัวอย่างที่ทำให้เกิด panic (ใช้ยืนยันพฤติกรรม panic โดยไม่รันจริงจนโปรแกรมล่ม):
    ///
    /// ```should_panic
    /// use mini_inventory::Product;
    ///
    /// let _ = Product::new("ของเสีย", -50.0, 1); // ราคาห้ามติดลบ -> panic
    /// ```
    pub fn new(name: &str, price: f64, quantity: u32) -> Self {
        assert!(price >= 0.0, "ราคาสินค้าห้ามติดลบ: {price}");
        Product {
            name: name.to_string(),
            price,
            quantity,
        }
    }

    /// คำนวณมูลค่ารวมของสินค้ารายการนี้ (ราคา คูณ จำนวน)
    ///
    /// # Examples
    ///
    /// ```
    /// use mini_inventory::Product;
    ///
    /// let p = Product::new("จอมอนิเตอร์", 4500.0, 3);
    /// assert_eq!(p.total_value(), 13500.0);
    /// ```
    pub fn total_value(&self) -> f64 {
        self.price * self.quantity as f64
    }
}

/// คลังสินค้า เก็บสินค้าหลายรายการ โดยใช้ชื่อสินค้าเป็น key
///
/// ดูภาพรวมการใช้งานที่หน้าเอกสารของ crate ([`crate`]) และดูฟังก์ชันสร้างรายงานที่
/// module [`report`]
#[derive(Debug, Default)]
pub struct Inventory {
    products: HashMap<String, Product>,
}

impl Inventory {
    /// สร้างคลังสินค้าเปล่า
    ///
    /// # Examples
    ///
    /// ```
    /// use mini_inventory::Inventory;
    ///
    /// let inventory = Inventory::new();
    /// assert_eq!(inventory.total_value(), 0.0);
    /// ```
    pub fn new() -> Self {
        Inventory {
            products: HashMap::new(),
        }
    }

    /// เพิ่มสินค้าลงในคลัง ถ้ามีสินค้าชื่อเดียวกันอยู่แล้วจะถูกแทนที่ทั้งรายการ
    ///
    /// # Errors
    ///
    /// ปกติแล้วฟังก์ชันนี้ไม่คืน error (คืน `Ok(())` เสมอในเวอร์ชันปัจจุบัน) แต่ signature
    /// เป็น `Result` ไว้ล่วงหน้า เพราะเวอร์ชันถัดไปมีแผนจะตรวจสอบชื่อสินค้าซ้ำแบบเข้มงวดขึ้น
    /// และคืน [`InventoryError`] เมื่อพบความขัดแย้ง — การออกแบบ API ให้คืน `Result` ไว้ก่อน
    /// ช่วยให้ผู้ใช้ไลบรารีเขียนโค้ดที่รองรับ error handling ไว้ตั้งแต่ต้น โดยไม่ต้องแก้ signature
    /// (breaking change) ในอนาคต
    ///
    /// # Examples
    ///
    /// ```
    /// use mini_inventory::{Inventory, Product};
    ///
    /// let mut inventory = Inventory::new();
    /// inventory.add_product(Product::new("เมาส์", 299.0, 10))?;
    /// assert_eq!(inventory.total_value(), 2990.0);
    /// # Ok::<(), mini_inventory::InventoryError>(())
    /// ```
    pub fn add_product(&mut self, product: Product) -> Result<(), InventoryError> {
        self.products.insert(product.name.clone(), product);
        Ok(())
    }

    /// ดึงข้อมูลสินค้าจากชื่อ (คืน `None` ถ้าไม่พบ)
    pub fn get(&self, name: &str) -> Option<&Product> {
        self.products.get(name)
    }

    /// ตัดสินค้าออกจากคลังจำนวนหนึ่ง (เช่น ตอนขายสินค้า)
    ///
    /// # Errors
    ///
    /// - คืน [`InventoryError::ProductNotFound`] ถ้าไม่พบสินค้าชื่อนี้ในคลังเลย
    /// - คืน [`InventoryError::InsufficientStock`] ถ้าจำนวนที่ต้องการตัด (`amount`)
    ///   มากกว่าจำนวนที่มีอยู่จริง — ฟังก์ชันจะ**ไม่**ตัดสต็อกบางส่วนแล้วปล่อยให้ค้างครึ่ง ๆ
    ///   กลาง ๆ (all-or-nothing) เพื่อป้องกันข้อมูลคลังสินค้าไม่สอดคล้องกัน
    ///
    /// # Examples
    ///
    /// ```
    /// use mini_inventory::{Inventory, Product};
    ///
    /// # fn main() -> Result<(), mini_inventory::InventoryError> {
    /// let mut inventory = Inventory::new();
    /// inventory.add_product(Product::new("เมาส์", 299.0, 10))?;
    ///
    /// inventory.remove_stock("เมาส์", 3)?;
    /// assert_eq!(inventory.get("เมาส์").unwrap().quantity, 7);
    /// # Ok(())
    /// # }
    /// ```
    ///
    /// ตัวอย่างกรณี error เมื่อสต็อกไม่พอ:
    ///
    /// ```
    /// use mini_inventory::{Inventory, InventoryError, Product};
    ///
    /// let mut inventory = Inventory::new();
    /// inventory.add_product(Product::new("เมาส์", 299.0, 5)).unwrap();
    ///
    /// let result = inventory.remove_stock("เมาส์", 100);
    /// assert!(matches!(result, Err(InventoryError::InsufficientStock { .. })));
    /// ```
    pub fn remove_stock(&mut self, name: &str, amount: u32) -> Result<(), InventoryError> {
        let product = self
            .products
            .get_mut(name)
            .ok_or_else(|| InventoryError::ProductNotFound(name.to_string()))?;

        if product.quantity < amount {
            return Err(InventoryError::InsufficientStock {
                name: name.to_string(),
                available: product.quantity,
                requested: amount,
            });
        }

        product.quantity -= amount;
        Ok(())
    }

    /// คำนวณมูลค่ารวมของสินค้าทั้งหมดในคลัง
    ///
    /// # Examples
    ///
    /// ```
    /// use mini_inventory::{Inventory, Product};
    ///
    /// let mut inventory = Inventory::new();
    /// inventory.add_product(Product::new("เมาส์", 299.0, 10)).unwrap();
    /// inventory.add_product(Product::new("คีย์บอร์ด", 890.0, 2)).unwrap();
    ///
    /// assert_eq!(inventory.total_value(), 299.0 * 10.0 + 890.0 * 2.0);
    /// ```
    pub fn total_value(&self) -> f64 {
        self.products.values().map(Product::total_value).sum()
    }

    /// บันทึกข้อมูลคลังสินค้าทั้งหมดลงไฟล์ข้อความ (รูปแบบง่าย ๆ หนึ่งบรรทัดต่อสินค้า)
    ///
    /// ตัวอย่างในเอกสารของฟังก์ชันนี้ใช้ attribute `no_run` เพราะการรันจริงจะสร้างไฟล์ลงดิสก์
    /// (side effect) ทุกครั้งที่ `cargo test` รัน doc-test ซึ่งไม่เหมาะสม (อาจชนกับสิทธิ์การเขียน
    /// ไฟล์ใน CI หรือทำให้ test ไม่ deterministic) แต่เรายังต้องการให้ compiler ยืนยันว่าโค้ด
    /// ตัวอย่าง**compile ผ่านจริง** สอดคล้องกับ signature ปัจจุบันของฟังก์ชัน
    ///
    /// # Errors
    ///
    /// คืน `std::io::Error` ถ้าเปิดหรือเขียนไฟล์ที่ path ที่ระบุไม่สำเร็จ เช่น โฟลเดอร์ปลายทาง
    /// ไม่มีอยู่จริง หรือไม่มีสิทธิ์เขียนไฟล์ในตำแหน่งนั้น
    ///
    /// # Examples
    ///
    /// ```no_run
    /// use mini_inventory::{Inventory, Product};
    ///
    /// let mut inventory = Inventory::new();
    /// inventory.add_product(Product::new("เมาส์", 299.0, 10)).unwrap();
    ///
    /// inventory.save_to_file("inventory_report.txt")?;
    /// # Ok::<(), std::io::Error>(())
    /// ```
    pub fn save_to_file(&self, path: &str) -> std::io::Result<()> {
        use std::io::Write;
        let mut file = std::fs::File::create(path)?;
        for product in self.products.values() {
            writeln!(file, "{}: {} x {}", product.name, product.price, product.quantity)?;
        }
        Ok(())
    }
}

## กับดักที่พบบ่อย (Common Pitfalls)

### 1. เขียน `///` เหนือ statement ธรรมดา — ได้ warning "unused doc comment"

มือใหม่มักเข้าใจผิดว่า `///` ใช้ comment อะไรก็ได้เหมือน `//` แค่ "ดูเป็นทางการกว่า" แต่จริง ๆ แล้ว `///` **ต้อง
แนบกับ item** (fn, struct, enum, ...) เท่านั้น ถ้าเขียนไว้เหนือ statement ภายใน function body (เช่น `let`)
compiler จะไม่ error แต่จะเตือนด้วย warning นี้ (ทดสอบจริง):

```
warning: unused doc comment
 --> test1.rs:2:5
  |
2 |     /// นี่คือ comment ที่ตั้งใจจะอธิบายตัวแปร แต่ doc comment ใช้กับ statement ไม่ได้
  |     ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^
3 |     let x = 5;
  |     ---------- rustdoc does not generate documentation for statements
  |
  = help: use `//` for a plain comment
  = note: `#[warn(unused_doc_comments)]` (part of `#[warn(unused)]`) on by default
```

**วิธีแก้:** ถ้าต้องการอธิบาย statement ภายใน function body ให้ใช้ `//` (comment ธรรมดา) เสมอ `///` สงวนไว้
สำหรับ item ระดับ top-level หรือ field ภายใน struct/enum เท่านั้น

### 2. ลืม `use` ใน doc test แล้ว compile ไม่ผ่าน

doc test แต่ละบล็อกถูก compile แบบแยกเดี่ยว **ไม่ได้ import อะไรจาก scope ของไฟล์ที่มันอยู่โดยอัตโนมัติ** ผู้เขียน
ต้อง `use` ทุกอย่างที่ต้องใช้เองเสมอ เหมือนเขียนโปรแกรมใหม่ทั้งโปรแกรม ถ้าลืม `use` จะได้ error แบบนี้ (ทดสอบจริงจาก
การลบบรรทัด `use mini_inventory::Product;` ออกจากตัวอย่างใน `Product::new`):

```
---- src/lib.rs - Product::new (line 84) stdout ----
error[E0433]: failed to resolve: use of undeclared type `Product`
  --> src/lib.rs:85:9
   |
85 | let p = Product::new("คีย์บอร์ด", 890.0, 5);
   |         ^^^^^^^ use of undeclared type `Product`
   |
help: consider importing one of these items
   |
84 + use std::iter::Product;
   |
84 + use mini_inventory::Product;
   |

error: aborting due to 1 previous error
Couldn't compile the test.
```

สังเกตจุดที่น่าสนใจ: compiler แนะนำ `use std::iter::Product;` ให้ด้วย (เพราะ `Product` เป็นชื่อ trait ที่มีอยู่จริง
ใน `std::iter` สำหรับการคูณค่าใน iterator) นี่คือตัวอย่างจริงที่แสดงให้เห็นว่า error message ของ compiler พยายาม
ช่วยแนะนำทุกความเป็นไปได้ที่ชื่อนั้นตรงกัน แต่ไม่ได้แปลว่าคำแนะนำทุกอันจะถูกต้องกับเจตนาที่เราต้องการเสมอไป —
ในกรณีนี้ตัวเลือกที่ถูกต้องคือ `use mini_inventory::Product;` **วิธีแก้:** ตรวจสอบให้แน่ใจว่าทุก type/function ที่
ใช้ในตัวอย่างถูก `use` มาอย่างครบถ้วน เหมือนกำลังเขียนโปรแกรมเดี่ยว ๆ ใหม่ทั้งหมด

### 3. Doc test panic โดยไม่ได้ตั้งใจ (ลืมใส่ `should_panic`)

ถ้าโค้ดในตัวอย่างเกิด panic จริงระหว่างรัน แต่ไม่ได้ทำเครื่องหมาย ` ```should_panic ` ไว้ `cargo test` จะรายงาน
ว่า test นี้ **FAILED** ทันที (ทดสอบจริงจากการลบ `should_panic` ออกจากตัวอย่างที่ตั้งใจให้ panic):

```

Test executable failed (exit status: 101).

stderr:

thread 'main' (23379) panicked at src/lib.rs:100:9:
ราคาสินค้าห้ามติดลบ: -50
stack backtrace:
   0: __rustc::rust_begin_unwind
   ...

failures:
    src/lib.rs - Product::new (line 94)

test result: FAILED. 10 passed; 1 failed; 0 ignored; 0 measured; 0 filtered out; finished in 0.10s

**วิธีแก้:** ถ้าตัวอย่างมีไว้เพื่อ**แสดงเงื่อนไขที่ทำให้ฟังก์ชัน panic** (ตรงกับที่บอกไว้ใน `# Panics`) ต้องทำ
เครื่องหมาย ` ```should_panic ` เสมอ ไม่ใช่ปล่อยให้ panic เกิดขึ้นโดยไม่บอก rustdoc ล่วงหน้า — ในทางกลับกัน ถ้า
ตัวอย่างนี้ panic โดยไม่ได้ตั้งใจ (คือเป็นบั๊กจริง ไม่ใช่พฤติกรรมที่ต้องการโชว์) นี่คือสัญญาณเตือนว่าโค้ดในไลบรารี
มีปัญหาที่ต้องแก้ ไม่ใช่แค่แก้ที่เอกสาร

### 4. Intra-doc link เสีย เมื่อเปิด `#![deny(rustdoc::broken_intra_doc_links)]`

ถ้าพิมพ์ชื่อ item ในลิงก์ผิด (เช่น สะกดผิด หรือ item ถูก rename ไปแล้วแต่ลิงก์เก่ายังไม่ได้แก้) และเปิด
`#![deny(rustdoc::broken_intra_doc_links)]` ไว้ `cargo doc` จะ**ล้มเหลวทันที** ไม่ generate เอกสารให้เลย
(ทดสอบจริงจากการพิมพ์ `add_product` เป็น `add_produkt` โดยไม่ได้ตั้งใจ):

```
error: unresolved link to `Inventory::add_produkt`
  --> src/lib.rs:62:54
   |
62 | /// สร้างด้วย [`Product::new`] แล้วเพิ่มลงคลังด้วย [`Inventory::add_produkt`]
   |                                               ^^^^^^^^^^^^^^^^^^^^^^ the struct `Inventory` has no field or associated item named `add_produkt`
   |
note: the lint level is defined here
  --> src/lib.rs:20:9
   |
20 | #![deny(rustdoc::broken_intra_doc_links)]
   |         ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^

error: could not document `mini_inventory`
```

**วิธีแก้:** ตรวจสอบชื่อ item ในลิงก์ให้ตรงกับที่ประกาศไว้จริงเสมอ — ข้อดีของการเปิด lint นี้ตั้งแต่แรกคือทำให้
ปัญหาแบบนี้ถูกจับได้ทันทีตอน build เอกสาร (หรือใน CI) ไม่ใช่ปล่อยให้ลิงก์เสียหลุดไปถึงหน้าเอกสารสาธารณะจริงบน
docs.rs โดยไม่มีใครสังเกตเห็น

### 5. ใช้ `ignore` ทั้งที่ตัวอย่าง compile ผ่านได้จริง — เสียการตรวจสอบไปโดยไม่จำเป็น

มือใหม่บางคนเจอ doc test ที่ compile ไม่ผ่านเพราะเขียนโค้ดผิด แล้วแก้ปัญหาแบบลัดด้วยการใส่ ` ```ignore ` ทับไปเลย
เพื่อให้ `cargo test` ผ่าน โดยไม่ได้แก้โค้ดตัวอย่างให้ถูกต้องจริง ๆ — วิธีนี้ทำให้ `cargo test` "เขียว" ก็จริง แต่
**เสียประโยชน์ทั้งหมด**ของการมี doc test ไปเลย เพราะตัวอย่างนั้นจะไม่ถูกตรวจสอบอะไรอีกต่อไปตลอดไป แม้ API จะ
เปลี่ยนไปในอนาคตจนตัวอย่างนั้น "ผิด" มากขึ้นเรื่อย ๆ ก็ไม่มีอะไรเตือน

**วิธีแก้:** ใช้ `ignore` เฉพาะเมื่อตัวอย่าง**อ้างถึงสิ่งที่ไม่มีอยู่จริง** (pseudocode, แนวคิดอนาคต) เท่านั้น ถ้า
ตัวอย่างอ้างถึง API ที่มีอยู่จริงแต่ compile ไม่ผ่านเพราะเขียนผิด ต้องแก้โค้ดตัวอย่างให้ถูกต้อง ไม่ใช่ปิดการตรวจสอบ
ทิ้งไปเฉย ๆ

### 6. เข้าใจผิดว่า `#[doc(hidden)]` คือกลไก security

ตามที่อธิบายในหัวข้อ 34.12 — `#[doc(hidden)]` ซ่อนแค่จากหน้าเอกสารที่ generate เท่านั้น item ยังเป็น `pub` จริง
ที่เรียกใช้ได้จากภายนอก crate เสมอ ถ้าต้องการจำกัด visibility จริง ๆ (ไม่ให้เรียกจากนอก crate ได้เลย) ต้องใช้
`pub(crate)` หรือลด visibility ลงตามความเหมาะสม ไม่ใช่หวังพึ่ง `#[doc(hidden)]`

## แบบฝึกหัด (Exercises)

1. **ระดับง่าย:** เขียน doc comment แบบ `///` ให้ฟังก์ชันนี้ให้ครบถ้วน (มี summary หนึ่งบรรทัด และ section
   `# Examples` ที่มี doc test อย่างน้อยหนึ่งตัวอย่าง ทดสอบด้วย `assert_eq!`):

   ```rust
   pub fn celsius_to_fahrenheit(celsius: f64) -> f64 {
       celsius * 9.0 / 5.0 + 32.0
   }
   ```

   *Hint:* ลองคำนวณด้วยมือก่อนว่า 0°C, 100°C ควรได้ผลลัพธ์เป็นองศาฟาเรนไฮต์เท่าไหร่ แล้วใช้ค่านั้นเป็น assertion
   ในตัวอย่าง อย่าลืมว่าฟังก์ชันนี้ไม่ panic และไม่คืน `Result` จึงไม่ต้องมี `# Panics` หรือ `# Errors`

2. **ระดับกลาง:** กำหนดฟังก์ชันนี้ (ที่ตั้งใจให้ panic เมื่อ `divisor` เป็น 0 และคืน `Err` เมื่อผลลัพธ์เป็นค่าลบ
   ซึ่งถือว่าไม่ valid ในบริบทธุรกิจสมมติของเรา) เขียนเอกสารให้ครบทั้ง `# Panics`, `# Errors`, และ `# Examples`
   พร้อม doc test อย่างน้อย 2 ตัวอย่าง (กรณีปกติ และกรณี error):

   ```rust
   pub fn calculate_ratio(numerator: i32, divisor: i32) -> Result<i32, String> {
       let result = numerator / divisor; // panic ถ้า divisor == 0
       if result < 0 {
           return Err(format!("อัตราส่วนติดลบไม่ valid: {result}"));
       }
       Ok(result)
   }
   ```

   *Hint:* ตัวอย่างสำหรับกรณี panic ควรใช้ ` ```should_panic ` และควรอธิบายให้ชัดว่า divisor เป็น 0 ทำให้เกิด
   division by zero panic จาก runtime ของ Rust เอง ไม่ใช่ `panic!` ที่เขียนเอง — ถือเป็นพฤติกรรมที่ต้องบอกผู้ใช้
   ไว้ล่วงหน้าเหมือนกัน

3. **ระดับยาก:** นำ struct และ module ด้านล่างมาเพิ่ม `//!` ระดับ module ให้ `mod pricing`, เพิ่ม intra-doc link
   เชื่อมระหว่าง `Coupon` กับฟังก์ชัน `apply_coupon`, เปิด `#![deny(rustdoc::broken_intra_doc_links)]` ที่บนสุด
   ของไฟล์ แล้วรัน `cargo doc` เพื่อยืนยันว่าไม่มีลิงก์เสีย — จากนั้นลองพิมพ์ชื่อ item ในลิงก์ผิดโดยตั้งใจ สังเกต
   error message ที่ได้ แล้วแก้กลับให้ถูกต้อง:

   ```rust
   pub struct Coupon {
       pub code: String,
       pub discount_percent: f64,
   }

   pub mod pricing {
       use super::Coupon;

       pub fn apply_coupon(price: f64, coupon: &Coupon) -> f64 {
           price * (1.0 - coupon.discount_percent / 100.0)
       }
   }
   ```

   *Hint:* `//!` ต้องอยู่ที่บรรทัดแรก ๆ ภายใน `mod pricing { ... }` (ถ้าใช้ inline module แบบนี้) ส่วน intra-doc
   link ข้าม module ต้องใช้ path แบบเต็มหรือ `super::`/`crate::` ให้ rustdoc resolve ได้ถูกต้อง

4. **ระดับยาก/ประยุกต์ใช้งานจริง:** สร้างโปรเจกต์ cargo library ใหม่ (`cargo new --lib`) แล้วนำ struct
   `Coupon`/`pricing` module จากข้อ 3 มาสร้างเป็นไลบรารีเล็ก ๆ ที่สมบูรณ์ — เพิ่มฟังก์ชันสมมติ `sync_coupons_from_api`
   ที่มี side effect (เชื่อมต่อ network จริงหรือจำลองด้วย `std::thread::sleep`) แล้วเขียน doc test ด้วย `no_run`
   ให้เหมาะสม, เพิ่ม crate-level `//!` แบบ elevator pitch พร้อมตัวอย่างการใช้งานเบื้องต้น, รัน `cargo test` และ
   `cargo doc --open` จริง แล้วตรวจสอบว่า:
   - ส่วน "Doc-tests" ในผลลัพธ์ `cargo test` แสดงจำนวน test ที่ผ่านถูกต้องตามที่คาดไว้
   - หน้า `cargo doc --open` แสดง crate-level doc เป็นหน้าแรกอย่างถูกต้อง
   - ลองใส่ `#[doc(hidden)]` กับฟังก์ชัน helper หนึ่งตัว แล้วตรวจสอบว่ามันหายไปจากหน้าเอกสารจริง (เปิดไฟล์ HTML
     ใน `target/doc/` ตรวจสอบด้วยตาก็ได้ หรือ `grep` หา element ที่คาดว่าจะมี)

   *Hint:* ถ้าไม่มี network จริงให้ทดสอบ ให้จำลองด้วย `std::thread::sleep(std::time::Duration::from_millis(100))`
   แทนการเรียก HTTP จริง ประเด็นสำคัญของข้อนี้คือฝึกกระบวนการ**คิดว่าตัวอย่างไหนควรเป็น `no_run`** ไม่ใช่ความ
   ซับซ้อนของ network code จริง

## สรุป

บทนี้เราได้เติมเต็มสัญญาที่ Part 5 ทิ้งไว้อย่างครบถ้วน — `///` และ `//!` ไม่ใช่แค่ comment ที่ "ดูเป็นทางการ" แต่เป็น
กลไกภาษาที่แปลงเป็น `#[doc = "..."]`/`#![doc = "..."]` จริง ที่ `rustdoc` นำไป render เป็นเอกสาร HTML ผ่าน
Markdown ได้อย่างสมบูรณ์ พร้อมด้วยธรรมเนียมมาตรฐานของ community อย่าง `# Examples`/`# Panics`/`# Errors`/
`# Safety` ที่ทำให้เอกสารทุก crate ใน ecosystem มีโครงสร้างที่คุ้นเคยกัน

จุดที่สำคัญที่สุดของบทนี้คือ **doc test** — ความจริงที่ว่าโค้ดตัวอย่างในเอกสารถูก compile และรันจริงโดย
`cargo test` (แสดงผลใน section "Doc-tests" แยกจาก unit test) ทำให้เอกสารของ Rust "โกหกไม่ได้" ในแบบที่ภาษาอื่น
ส่วนใหญ่ทำไม่ได้ เราได้เห็นวิธีควบคุมพฤติกรรมของมันอย่างละเอียดผ่านบรรทัดซ่อนด้วย `#`, `no_run` สำหรับตัวอย่างที่
มี side effect, `ignore` สำหรับ pseudocode, และ `should_panic` สำหรับตัวอย่างที่ตั้งใจแสดงพฤติกรรม panic รวมถึง
วิธีใช้ `?` operator ภายใน doc test ที่คืน `Result` ได้อย่างถูกต้อง

เรายังได้เรียนเรื่อง intra-doc link ที่ rustdoc ตรวจสอบความถูกต้องได้จริง (และบังคับให้เป็น error ได้ด้วย
`#![deny(rustdoc::broken_intra_doc_links)]`), การเขียนเอกสารระดับ crate ด้วย pattern "elevator pitch",
`#[doc(hidden)]` สำหรับซ่อน item ที่ไม่ใช่ส่วนหนึ่งของ public contract, และปิดท้ายด้วยความเข้าใจว่า docs.rs
ทำให้ทุกสิ่งที่เราเรียนมาไม่ใช่แค่ "ของเล่นในเครื่องตัวเอง" แต่เป็น**หน้าตาสาธารณะของ crate**ที่ทั้งโลกจะเห็น
ทันทีที่ publish ขึ้น crates.io — เชื่อมโยงกลับไปยัง Part 17 ที่เราเรียนเรื่อง metadata สำหรับการ publish ไว้ก่อน
หน้านี้
