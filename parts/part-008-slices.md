## เป้าหมายของบทเรียน

หลังจากจบบทนี้ คุณจะสามารถ:

- อธิบายได้ว่าทำไมการคืนค่าเป็น `usize` index เพื่อ "ชี้" ตำแหน่งข้อมูลใน `String` ถึงเป็นวิธีที่เปราะบางและก่อบั๊กได้จริง
  พร้อมยกตัวอย่างสถานการณ์ที่บั๊กนั้นเกิดขึ้นจริงเป็นรูปธรรม
- ใช้ string slice (`&str`) ผ่าน syntax ช่วง (range) ทั้ง 4 รูปแบบ (`[start..end]`, `[start..]`, `[..end]`, `[..]`) ได้อย่างถูกต้อง
  และอธิบายได้ว่า `&str` คืออะไรในเชิง memory layout (pointer + length)
- อธิบายได้ว่า string literal (`"hello"`) เป็น `&str` มาตั้งแต่ต้น และรู้ความแตกต่างระหว่างข้อมูลที่ `&str` ชี้ไปยัง
  หน่วยความจำแบบ heap (จาก `String`) กับข้อมูลที่ฝังอยู่ในไบนารีโปรแกรม (จาก string literal)
- ระมัดระวังและแก้ปัญหาการ slice สตริงผิดตำแหน่ง character boundary ของ UTF-8 ได้ (โดยเฉพาะกับข้อความภาษาไทยที่มีหลาย byte
  ต่อตัวอักษร) และรู้จัก `.chars()` เป็นทางเลือกที่ปลอดภัยกว่าในการวนอ่านตัวอักษร
- เขียนฟังก์ชันที่คืนค่าเป็น `&str` แทน `usize` และอธิบายได้ว่าทำไม borrow checker (จาก Part 7) ถึงป้องกันบั๊กที่เจอในหัวข้อ
  แรกของบทนี้ได้โดยอัตโนมัติตั้งแต่ compile time
- เลือกออกแบบ parameter ของฟังก์ชันให้เป็น `&str` แทน `&String` ได้อย่างเข้าใจเหตุผล (deref coercion) และใช้ slice ทั่วไป
  `&[T]` กับ `&mut [T]` กับข้อมูลชนิด array ได้ ทั้งแบบอ่านอย่างเดียวและแบบแก้ไขได้

## ความรู้ที่ต้องมีมาก่อน

  ต่างจาก string literal, เข้าใจ `usize` ว่าคือชนิดที่ใช้เป็น index/ความยาวของ collection เสมอ

- **Part 7**: เข้าใจ reference `&T`/`&mut T`, กฎการยืม (borrow rules — ยืมแบบอ่านได้พร้อมกันหลายตัว แต่ยืมแบบเขียนได้ทีละตัว
  และห้ามยืมเขียนพร้อมกับยืมอ่าน), และ Non-Lexical Lifetimes (NLL) ที่ทำให้ borrow "หมดอายุ" ทันทีที่ไม่ได้ใช้งานต่อ
  ไม่ต้องรอถึงปิด scope

แต่ชี้ไปที่ **ช่วงหนึ่งที่ต่อเนื่องกัน (contiguous) ภายในข้อมูล** พร้อมพก "ความยาว" ของช่วงนั้นไปด้วย ถ้าคุณเข้าใจ Part 7

## เนื้อหา

### 8.1 ปัญหาเริ่มต้น: ฟังก์ชันหา "คำแรก" ของประโยค

ลองจินตนาการสถานการณ์ที่พบได้บ่อยมาก: เรามีสตริงหนึ่งประโยค และต้องการฟังก์ชันที่คืน **"คำแรก"** ของประโยคนั้นออกมา
ก่อนที่ Rust จะมี slice เราอาจคิดวิธีแก้แบบตรงไปตรงมาที่สุดก่อน คือ **หาตำแหน่ง (index) ของช่องว่างตัวแรก แล้วคืนค่า
index นั้นออกมาเป็น `usize`** ผู้เรียกก็ค่อยเอา index ไปตัดสตริงเอาเอง:

```rust
fn first_word_index(s: &String) -> usize {
    let bytes = s.as_bytes();

    for (i, &b) in bytes.iter().enumerate() {
        if b == b' ' {
            return i;
        }
    }

    s.len()
}

fn main() {
    let sentence = String::from("hello world");
    let word_end = first_word_index(&sentence);
    println!("คำแรกยาว {word_end} bytes");
}
```

ผลลัพธ์:

```
คำแรกยาว 5 bytes
```

**อธิบายโค้ดทีละส่วน:**

- `s.as_bytes()` — แปลง `&String` (หรือ `&str`) ให้เป็น `&[u8]` คือ slice ของ byte ดิบ ๆ ตามที่สตริงถูกเข้ารหัสด้วย UTF-8
  จริง ๆ ในหน่วยความจำ (เราจะพูดถึง `&[u8]` ในฐานะ slice ทั่วไปในหัวข้อ 8.8 — ตอนนี้มองว่าเป็น "array ของเลข 0-255"
  ที่แทนตัวอักษรแต่ละ byte ก็พอ)
- `bytes.iter().enumerate()` — `.iter()` วนอ่านค่าทีละตัวแบบ reference (`&u8`), `.enumerate()` แนบเลข index (`usize`)
  เข้าไปคู่กับแต่ละค่า ทำให้ได้คู่ `(index, &byte)` ทีละคู่ (เราจะเรียนเรื่อง iterator และ method พวกนี้แบบเจาะลึกจริง ๆ
  ใน **Part 25-26** ตอนนี้จำแค่ว่ามันคือวิธีวนลูปพร้อมนับตำแหน่งไปด้วย)
- `if b == b' '` — `b' '` คือ byte literal ของอักขระ "เว้นวรรค" (space, ASCII code 32) — เราเทียบ byte ตรง ๆ ไม่ใช่ `char`
  เพราะ ASCII space ใช้แค่ 1 byte เสมอ ปลอดภัยที่จะเทียบแบบนี้
- ถ้าเจอช่องว่าง คืนค่า `i` (ตำแหน่ง byte ของช่องว่างนั้น) ทันที ถ้าวนจนสุดไม่เจอช่องว่างเลย (ประโยคมีคำเดียว) คืนค่า
  `s.len()` คือความยาวทั้งหมดของสตริง

ฟังก์ชันนี้ compile ผ่านและทำงานถูกต้องตามที่ตั้งใจ — สำหรับ `"hello world"` มันคืนค่า `5` ซึ่งคือตำแหน่ง byte ของช่องว่าง
ระหว่าง `"hello"` กับ `"world"` ดูเผิน ๆ เหมือนไม่มีปัญหาอะไร แต่ลองมาดูกันว่าทำไมวิธีนี้ถึง **"เปราะบาง" (fragile)**
กว่าที่คิด

### 8.2 ทำไม `usize` index ถึงเปราะบาง — บั๊กที่เกิดขึ้นได้จริง

ปัญหาของ `first_word_index` ไม่ได้อยู่ที่ตัวมันเองตอนคืนค่า แต่อยู่ที่ **สิ่งที่เกิดขึ้นได้หลังจากนั้น** ค่า `usize`
ที่คืนออกมาเป็นแค่ "ตัวเลขเปล่า ๆ" ไม่มีอะไรเชื่อมโยงมันเข้ากับ `String` ต้นทางในทาง type system เลย — มันเป็นคนละค่า
คนละชนิดข้อมูลกันโดยสิ้นเชิง ไม่มีอะไรห้ามไม่ให้เราไปแก้ไข `String` ต้นทางหลังจากได้ index มาแล้ว:

```rust
fn first_word_index(s: &String) -> usize {
    let bytes = s.as_bytes();

    for (i, &b) in bytes.iter().enumerate() {
        if b == b' ' {
            return i;
        }
    }

    s.len()
}

fn main() {
    let mut sentence = String::from("hello world");
    let word_end = first_word_index(&sentence);

    sentence.clear(); // ล้างเนื้อหาข้างในสตริงจนว่างเปล่า

    println!("คำแรกยาว {word_end} bytes");
    println!("ประโยคตอนนี้: '{sentence}'");
}
```

โค้ดนี้ **compile ผ่านสบาย ๆ ไม่มี error หรือ warning ใด ๆ เลย** และรันได้ผลลัพธ์ดังนี้:

```
คำแรกยาว 5 bytes
ประโยคตอนนี้: ''
```

สังเกตให้ดี — โปรแกรมพิมพ์ว่า **"คำแรกยาว 5 bytes"** ทั้ง ๆ ที่ `sentence` ตอนนี้ **ว่างเปล่าไปแล้ว** ค่า `word_end`
ที่เก็บไว้เป็น `5` นั้นกลายเป็นข้อมูลที่ **ไม่มีความหมายอะไรอีกต่อไป** มันคือ index ที่ชี้ไปยังตำแหน่งในสตริงที่ไม่มีอยู่จริง
แล้ว แต่ตัวโปรแกรมไม่มีทางรู้เรื่องนี้ได้เอง เพราะ `usize` เป็นแค่ตัวเลขที่ไม่ได้ผูกติดกับสถานะของ `sentence` เลย

ถ้าเราลองเอา `word_end` ไปใช้งานต่อจริง ๆ (เช่นตัดสตริงด้วย index นี้) ปัญหาจะแสดงออกมาชัดเจนกว่าเดิมมาก:

```rust
fn first_word_index(s: &String) -> usize {
    let bytes = s.as_bytes();

    for (i, &b) in bytes.iter().enumerate() {
        if b == b' ' {
            return i;
        }
    }

    s.len()
}

fn main() {
    let mut sentence = String::from("hello world");
    let word_end = first_word_index(&sentence);

    sentence.clear();

    let first_word = &sentence[..word_end];
    println!("คำแรก: '{first_word}'");
}
```

โค้ดนี้ก็ยัง **compile ผ่าน** เหมือนเดิม (compiler ยังไม่รู้อะไรผิด) แต่พอรันจริง โปรแกรมจะ **panic** ทันทีด้วยข้อความ:

```
thread 'main' panicked at src/main.rs:19:31:
byte index 5 is out of bounds of ``
```

เพราะ `sentence` ถูก `.clear()` จนความยาวเหลือ `0` แล้ว แต่เราพยายามตัดมันที่ตำแหน่ง byte `5` ซึ่งไม่มีอยู่จริงอีกต่อไป
`` (สังเกตว่า error message แสดงเนื้อหาสตริงปัจจุบันเป็นค่าว่างในเครื่องหมาย backtick คู่ที่ไม่มีอะไรอยู่ข้างใน — นั่นคือ
สตริงที่ว่างเปล่าจริง ๆ)

#### หัวใจของปัญหา: ไม่มีอะไรเชื่อม `usize` เข้ากับ `String` ต้นทางเลย

นี่คือประเด็นสำคัญที่สุดของหัวข้อนี้: **`first_word_index` คืนค่าที่ "แยกขาด" จากข้อมูลต้นทางโดยสิ้นเชิงในทาง type
system** เมื่อฟังก์ชันคืนค่า `usize` มันเหมือนพูดว่า "นี่คือตัวเลข 5 เฉย ๆ นะ" — compiler ไม่มีทางรู้เลยว่าตัวเลขนี้
"มีความหมาย" เฉพาะตอนที่ `sentence` ยังมีเนื้อหาเหมือนตอนที่คำนวณ index นี้ขึ้นมาเท่านั้น ทันทีที่ `sentence` เปลี่ยนแปลง
(ไม่ว่าจะ `.clear()`, `.push_str()`, หรือวิธีอื่นใดที่แก้ไขเนื้อหา) ค่า `word_end` ที่ถืออยู่ก็ **กลายเป็นขยะทันที**
โดยไม่มีสัญญาณเตือนอะไรเลยจนกว่าจะเอาไปใช้จริงแล้วพัง

ลองย้อนคิดถึงสิ่งที่เรียนใน **Part 7**: ปัญหาแบบนี้คือญาติสนิทของปัญหา **dangling reference** ที่ borrow checker
ป้องกันไว้ได้ — ถ้าเราคืน `&T` ที่ชี้ไปยังข้อมูลที่ตายไปแล้ว compiler จะปฏิเสธไม่ให้ compile ผ่านตั้งแต่แรก แต่ปัญหาของ
`usize` ในหัวข้อนี้ **แย่กว่านั้นอีก** เพราะมันไม่ใช่ reference เลย — มันเป็นแค่ตัวเลขล้วน ๆ ไม่มี lifetime ไม่มีอะไร
ให้ borrow checker ตรวจสอบได้ มันจึง "เป็น dangling ได้แบบเงียบ ๆ" โดยไม่มีอะไรมาห้าม

**คำถามที่ควรถามตัวเองตรงนี้คือ**: จะดีกว่าไหม ถ้าค่าที่ฟังก์ชันคืนออกมา **"พกความเชื่อมโยง" กับสตริงต้นทางไปด้วยเสมอ**
โดยที่ compiler รู้เรื่องความเชื่อมโยงนี้ และตรวจสอบให้เราโดยอัตโนมัติว่าตราบใดที่ค่านั้นยังถูกใช้งานอยู่ ห้ามใครมาแก้ไข
ข้อมูลต้นทางเด็ดขาด — นี่คือสิ่งที่ **slice** ถูกออกแบบมาเพื่อแก้ปัญหาโดยตรง

### 8.3 String Slice (`&str`): นิยามและ syntax

**Slice** คือ reference ชนิดหนึ่งที่ชี้ไปยัง **ช่วงข้อมูลต่อเนื่องกัน (contiguous sequence)** ภายในข้อมูลที่ใหญ่กว่า
โดยไม่ได้เป็นเจ้าของข้อมูลนั้น (ตรงกับหลัก borrowing ที่เรียนใน Part 7 เป๊ะ ๆ) จุดที่ slice ต่างจาก `&T` ธรรมดาคือ
slice **พก "ความยาว" ของช่วงที่ชี้ไปด้วยเสมอ** ไม่ใช่ชี้ไปที่จุดเดียวแล้วปล่อยให้ผู้ใช้เดาว่ายาวแค่ไหน

`&str` คือ slice ของข้อมูลสตริง เขียนโดยใช้ **range syntax** ในเครื่องหมาย `[]` ต่อท้ายสตริงหรือ `String`:

```rust
fn main() {
    let s = String::from("hello world");

    let hello = &s[0..5];   // byte 0 ถึงก่อน byte 5 (ไม่รวม 5) คือ "hello"
    let world = &s[6..11];  // byte 6 ถึงก่อน byte 11 คือ "world"

    println!("{hello} {world}");
}
```

ผลลัพธ์:

```
hello world
```

สังเกตว่า `0..5` คือ **range แบบไม่รวมขอบขวา (exclusive end)** เหมือนกับ range ที่ใช้ใน `for i in 0..5` — ได้ค่า
`0, 1, 2, 3, 4` รวม 5 ตัว ในกรณีของสตริง มันหมายถึง "byte ที่ 0 ถึง byte ที่ 4" (นับรวม) ซึ่งพอดีกับตัวอักษร `h`, `e`,
`l`, `l`, `o` — 5 ตัวอักษรของคำว่า "hello"

Rust มี syntax ย่อ 4 รูปแบบสำหรับการเขียน range ใน slice ซึ่งครอบคลุมทุกกรณีที่ใช้บ่อย:

| Syntax | ความหมาย |
|---|---|
| `&s[0..5]` | ตั้งแต่ byte 0 ถึงก่อน byte 5 |
| `&s[..5]` | ตั้งแต่ต้น (byte 0) ถึงก่อน byte 5 — ละเลขเริ่มต้นได้เมื่อเริ่มจาก 0 |
| `&s[6..]` | ตั้งแต่ byte 6 ไปจนสุดความยาวของสตริง — ละเลขจบได้เมื่อจบที่ปลายสุด |
| `&s[..]` | ทั้งสตริงตั้งแต่ต้นจนจบ — slice ของสตริงทั้งก้อน |

ลองรันทุกรูปแบบพร้อมกัน:

```rust
fn main() {
    let s = String::from("hello world");

    let hello = &s[0..5];
    let world = &s[6..11];
    let hello2 = &s[..5];
    let world2 = &s[6..];
    let whole = &s[..];

    println!("{hello} {world}");
    println!("{hello2} {world2}");
    println!("{whole}");
}
```

ผลลัพธ์:

```
hello world
hello world
hello world
```

ทั้งสามบรรทัดพิมพ์เหมือนกันทุกตัวอักษร เพราะ `&s[0..5]` กับ `&s[..5]` คือช่วง byte เดียวกันเป๊ะ ๆ ต่างกันแค่วิธีเขียนย่อ
เท่านั้น เลือกใช้แบบที่อ่านง่ายที่สุดในบริบทนั้น ๆ — โดยทั่วไปโค้ด idiomatic Rust จะใช้รูปแบบย่อ (`..5`, `6..`, `..`)
เมื่อขอบของ range ตรงกับต้น/จบของสตริงพอดี เพื่อลดความรกของโค้ด

#### string literal คือ `&str` มาตั้งแต่ Part 1 แล้ว!

ย้อนกลับไปที่ Part 1 เราเขียน `println!("Hello, World!");` และตั้งแต่ Part 3 เราก็ใช้ string literal เช่น
`let name = "สมชาย";` มาตลอดโดยไม่ได้บอก type อย่างเป็นทางการ — ตอนนี้เราพร้อมที่จะเปิดเผยความจริงแล้ว:
**string literal ทุกตัวมีชนิดข้อมูลเป็น `&str` มาตั้งแต่ต้น**:

```rust
fn main() {
    let literal: &str = "hello"; // เขียน type annotation ให้เห็นชัด ๆ ว่ามันคือ &str
    println!("literal คือ &str: {literal}");
}
```

ผลลัพธ์:

```
literal คือ &str: hello
```

นี่คือเหตุผลที่ในหัวข้อ 3.7 เราบอกไว้ว่า `'A'` (single quote) คือ `char` ตัวเดียว ส่วน `"A"` (double quote) คือ
`&str` ที่มีความยาว 1 ตัวอักษร — ตอนนี้เราเข้าใจแล้วว่า `&str` ที่พูดถึงนั้นคืออะไรกันแน่ในทางเทคนิค: มันคือ **string
slice** ชนิดหนึ่งเช่นเดียวกับที่เรากำลังเรียนอยู่นี้เอง เพียงแต่ตอนนั้นเรายังไม่มีความรู้เรื่อง reference และ borrowing
(Part 7) มาก่อน จึงยังอธิบายเชิงลึกไม่ได้

#### `&str` คืออะไรกันแน่ใน memory: "fat pointer" (pointer + length)

จาก Part 7 เราเรียนว่า reference ธรรมดา (`&T`) คือ pointer ตัวหนึ่งที่ชี้ไปยังตำแหน่งของค่า `T` ใน memory —
เป็น **"thin pointer"** (pointer เปล่า ๆ ตัวเดียว) แต่ `&str` มีความพิเศษกว่านั้น เพราะ `str` (ไม่มี `&` นำหน้า)
เป็นชนิดข้อมูลที่เรียกว่า **unsized type** (หรือ `?Sized`) — compiler **ไม่รู้ขนาดของ `str` ตั้งแต่ compile time**
เพราะสตริงแต่ละตัวยาวไม่เท่ากัน (ต่างจาก `i32` ที่รู้แน่นอนว่ากิน 4 bytes เสมอ) ด้วยเหตุนี้ Rust จึงไม่อนุญาตให้ประกาศ
ตัวแปรชนิด `str` ตรง ๆ เลย (`let x: str = ...;` compile ไม่ผ่าน) — คุณเข้าถึง `str` ได้ผ่าน pointer ชนิดใดชนิดหนึ่ง
เท่านั้น (`&str`, `Box<str>` ฯลฯ) และเนื่องจากตัว `str` เองไม่พกความยาวติดตัวมา (มันเป็นแค่ลำดับของ byte) **reference
ที่ชี้ไปยังมันจึงต้องพกความยาวไปด้วยเสมอ** เพื่อให้รู้ว่า "จะอ่านไปถึงไหน" — เราจึงเรียก `&str` ว่า **"fat pointer"**
(pointer ที่ "อ้วน" กว่าปกติ เพราะมี 2 field ไม่ใช่ 1)

มายืนยันด้วยขนาดจริงในหน่วยความจำ:

```rust
fn main() {
    println!("ขนาดของ &str บนเครื่องนี้: {} bytes", std::mem::size_of::<&str>());
    println!("ขนาดของ &String บนเครื่องนี้: {} bytes", std::mem::size_of::<&String>());
    println!("ขนาดของ usize บนเครื่องนี้: {} bytes", std::mem::size_of::<usize>());
}
```

ผลลัพธ์บนเครื่อง 64-bit ทั่วไป:

```
ขนาดของ &str บนเครื่องนี้: 16 bytes
ขนาดของ &String บนเครื่องนี้: 8 bytes
ขนาดของ usize บนเครื่องนี้: 8 bytes
```

สังเกตความแตกต่างที่น่าสนใจมาก: **`&str` มีขนาด 16 bytes (สองเท่าของ `usize` หนึ่งตัว)** เพราะมันคือคู่ `(ptr, len)`
— ตำแหน่ง pointer 8 bytes บวกกับความยาว (`usize`) อีก 8 bytes ในขณะที่ **`&String` มีขนาดเพียง 8 bytes เท่านั้น**
เพราะ `String` เป็นชนิดข้อมูลที่ **มีขนาดคงที่ที่รู้แน่นอนตอน compile time** (มันคือ struct ที่ประกอบด้วย pointer,
length, capacity รวมกันเป็นก้อนเดียวที่มีขนาดตายตัว) — reference ที่ชี้ไปยัง `String` จึงเป็นแค่ pointer ตัวเดียวเหมือน
reference ทั่วไปที่เรียนใน Part 7 พอดี ไม่ต้องพกอะไรเพิ่ม เพราะจะรู้ขนาดของสิ่งที่ชี้ไปอยู่แล้วจาก type

ทำไมเรื่องนี้สำคัญ? เพราะมันอธิบายว่า **`&str` ไม่ใช่แค่ "reference ไปยัง `str`"** แบบตรงไปตรงมา — มันคือ
**"หน้าต่าง (window) เข้าไปดูข้อมูลบางส่วนของสตริงที่ใหญ่กว่า"** พร้อมบอกขนาดของหน้าต่างนั้นไปด้วยในตัว นี่คือกลไก
เดียวกันที่ทำให้ `&s[0..5]` สามารถ "ชี้เข้าไปตรงกลาง" ของ `String` ได้โดยไม่ต้องคัดลอกข้อมูลออกมาใหม่เลย — มันแค่เก็บ
`(ตำแหน่งเริ่มต้น, ความยาว 5)` เท่านั้น ข้อมูลจริง ๆ ยังอยู่ที่เดิมในหน่วยความจำของ `String` ต้นทาง

#### `&str` ชี้ไปที่ไหนได้บ้าง: heap ของ `String` หรือ static memory ของโปรแกรม

ส่วน "pointer" ของ `&str` สามารถชี้ไปยังตำแหน่งข้อมูลได้ 2 แบบหลัก ๆ ขึ้นอยู่กับที่มาของมัน:

1. **ชี้ไปยัง heap buffer ของ `String`** — เมื่อ `&str` เกิดจากการ slice ค่า `String` (เช่น `&s[0..5]`) pointer จะชี้เข้า
   ไปยังตำแหน่งภายในหน่วยความจำ heap ที่ `String` นั้นจองไว้ (จำเรื่อง `String` เป็น heap-allocated growable type
   จากบทก่อน ๆ ได้ใช่ไหม) — ข้อมูลจึงอยู่ในที่เดียวกัน ไม่มีการคัดลอกเกิดขึ้น
2. **ชี้ไปยัง static memory ของไบนารีโปรแกรมเอง** — เมื่อ `&str` มาจาก string literal เช่น `"hello"` เนื่องจากเนื้อหา
   ของ literal รู้แน่นอนตั้งแต่ตอน compile (ไม่เปลี่ยนแปลงเลยตลอดการรันโปรแกรม) compiler จะฝังข้อมูลนี้ไว้ใน**ส่วน
   read-only ของไฟล์ binary ที่คอมไพล์ออกมาโดยตรง** (มักเรียกว่า `.rodata` section) แล้ว string literal ก็เป็นแค่
   `&str` ที่ pointer ชี้ไปยังตำแหน่งนั้น — **ไม่มีการจอง heap เลยแม้แต่ byte เดียว** และเพราะมันอยู่กับโปรแกรมไปตลอด
   การรัน มันจึงมี lifetime พิเศษที่ชื่อ `'static` (เรานัดเจอกับ lifetime อย่างเป็นทางการใน **Part 20** — ตอนนี้จำแค่
   ว่า string literal มีอายุยาวเท่าตัวโปรแกรมเลย ไม่มีทางถูกทำลายก่อน)

นี่คือเหตุผลที่ string literal **"เร็วกว่า" และ "ไม่มี overhead จากการจองหน่วยความจำ"** เมื่อเทียบกับการสร้าง `String`
ใหม่ทุกครั้ง — ถ้าคุณมีข้อความคงที่ที่ไม่เปลี่ยนแปลงเลย (เช่นข้อความ error, ชื่อ config) การใช้ string literal
(`&str`) จึงมีประสิทธิภาพดีกว่าการสร้าง `String` เสมอ ตราบใดที่คุณไม่ต้องการแก้ไขเนื้อหาของมันในอนาคต

### 8.4 กับดักของ UTF-8: byte index ไม่เท่ากับ character boundary

จากหัวข้อ 3.7 เราเรียนไปแล้วว่า `String`/`&str` ใน Rust **ไม่ได้เก็บข้อมูลเป็น array ของ `char`** แต่เก็บเป็น
**raw UTF-8 bytes** โดยตรง — ตัวอักษรภาษาอังกฤษ (ASCII) แต่ละตัวใช้ 1 byte แต่ตัวอักษรไทย, จีน, ญี่ปุ่น, หรือ emoji
มักใช้ 2-4 bytes ต่อตัวอักษร นี่คือจุดที่การ slice สตริงด้วย byte index **อันตรายมากถ้าไม่ระมัดระวัง** — ถ้าคุณ slice
ตรงตำแหน่งที่ตกอยู่ **กลางตัวอักษรหลาย byte** โปรแกรมจะ panic ทันที

มาดูตัวอย่างจริงกับข้อความภาษาไทย ซึ่งเป็นภาษาที่ใช้ 3 bytes ต่อตัวอักษรใน UTF-8 (สำหรับตัวอักษรไทยส่วนใหญ่):

```rust
fn main() {
    let greeting = String::from("สวัสดี");
    println!("ความยาวเป็น byte: {}", greeting.len());

    let broken = &greeting[0..1];
    println!("{broken}");
}
```

`greeting.len()` จะพิมพ์ `18` (6 ตัวอักษร × 3 bytes ต่อตัว) แต่พอพยายาม slice `&greeting[0..1]` — ตัดเอาแค่ byte
แรกเพียง byte เดียว ซึ่งตกอยู่ **กลางตัวอักษร "ส" ตัวแรก** (เพราะ "ส" ใช้ 3 bytes คือ byte 0, 1, 2 — การตัดที่ byte 1
จึงหยุดอยู่กลางตัวอักษรนี้พอดี) โปรแกรมจะ panic ทันทีด้วยข้อความ:

```
thread 'main' panicked at src/main.rs:5:19:
byte index 1 is not a char boundary; it is inside 'ส' (bytes 0..3) of `สวัสดี`
```

อ่าน error message นี้ให้ละเอียด — มันบอกข้อมูลครบถ้วนมาก: **"byte index 1 is not a char boundary"** (ตำแหน่ง byte
ที่ 1 ไม่ใช่ขอบของตัวอักษร) **"it is inside 'ส' (bytes 0..3)"** (มันตกอยู่ข้างในตัวอักษร 'ส' ซึ่งกินตำแหน่ง byte
0 ถึงก่อน 3) **"of `สวัสดี`"** (ของสตริงต้นฉบับ "สวัสดี") — นี่คือปรัชญาการออกแบบ error message ของ Rust ที่เราเห็น
มาตลอดทั้งหลักสูตร: ให้ข้อมูลมากที่สุดเท่าที่จะช่วยแก้บั๊กได้ ไม่ใช่แค่บอกว่า "ผิด"

#### slice ให้ถูกตำแหน่ง character boundary

ถ้า slice ที่ตำแหน่งที่ตรงกับขอบของตัวอักษรจริง ๆ (เช่น byte 0, 3, 6, 9, ... สำหรับข้อความนี้ที่ทุกตัวอักษรใช้ 3 bytes
เท่ากันหมด) จะไม่มีปัญหาใด ๆ เลย:

```rust
fn main() {
    let greeting = String::from("สวัสดี");

    // byte 0..6 คือ 2 ตัวอักษรแรกพอดี เพราะแต่ละตัวใช้ 3 bytes
    let first_two_chars = &greeting[0..6];
    println!("{first_two_chars}");
}
```

ผลลัพธ์:

```
สว
```

แต่ปัญหาคือ **ในโลกจริง ตัวอักษรแต่ละตัวไม่ได้ใช้จำนวน byte เท่ากันเสมอไป** แม้แต่ในภาษาไทยเอง (สระ วรรณยุกต์ลอย
บางตัวอาจประกอบกันหลาย code point) การพยายามคำนวณตำแหน่ง byte ที่ "ตรงตัวอักษรพอดี" ด้วยมือจึงเสี่ยงผิดพลาดสูงมาก
และยิ่งเสี่ยงกว่านั้นถ้า index มาจากค่าที่คำนวณแบบไม่รู้เนื้อหาสตริงล่วงหน้า (เช่น input จากผู้ใช้, ค่าคงที่ที่เขียน
เดาไว้) — **นี่คือเหตุผลที่ Rust ไม่มี `s[0]` แบบภาษาอื่นที่คืนตัวอักษรตรง ๆ**: มันตั้งใจไม่ให้คุณทำสิ่งที่ดูปลอดภัย
แต่จริง ๆ เสี่ยง panic ได้ง่าย ๆ

#### `.chars()` ทางเลือกที่ปลอดภัยกว่า (teaser สำหรับ Part 14)

ถ้าคุณต้องการวนอ่านสตริงทีละ "ตัวอักษร Unicode" อย่างปลอดภัยโดยไม่ต้องยุ่งกับตำแหน่ง byte เอง ใช้ method `.chars()`
ซึ่งคืน iterator ของ `char` (ชนิดข้อมูลที่เรียนใน Part 3 — 4 bytes เสมอ, 1 ตัวแทน 1 Unicode Scalar Value เต็มรูปแบบ):

```rust
fn main() {
    let greeting = String::from("สวัสดี");

    for ch in greeting.chars() {
        print!("[{ch}]");
    }
    println!();
}
```

ผลลัพธ์:

```
[ส][ว][ั][ส][ด][ี]
```

`.chars()` จัดการเรื่องขอบ byte ให้เราโดยอัตโนมัติ ไม่มีทาง panic จากปัญหา character boundary ได้เลย เพราะมันแบ่ง
ตัวอักษรให้ถูกต้องตามกฎ UTF-8 เสมอ (สังเกตว่า "ั" ถูกแยกเป็น `char` ของตัวเอง 1 ตัว เพราะในทาง Unicode มันคือ combining
mark ที่เป็น scalar value แยกจาก "ว" แม้จะแสดงผลรวมกันเป็นตัวอักษรเดียวเมื่อมองด้วยตา) เรื่องรายละเอียดของ `String`,
UTF-8, การนับความยาว "ตัวอักษรที่มองเห็น" เทียบกับ "Unicode scalar value" และ method อื่น ๆ สำหรับจัดการข้อความ
(`.char_indices()`, `.split_whitespace()`, grapheme cluster ฯลฯ) จะเป็นเนื้อหาเต็มรูปแบบของ **Part 14** — ตอนนี้
จำแค่หลักการง่าย ๆ ไว้ก่อน: **ถ้าไม่มั่นใจเรื่อง byte boundary ให้ใช้ `.chars()` แทนการ slice ด้วยตัวเลขตรง ๆ เสมอ**

### 8.5 เขียน `first_word` ใหม่ให้คืน `&str` แทน `usize`

ตอนนี้เรามีเครื่องมือครบแล้ว มาแก้ปัญหาจากหัวข้อ 8.1-8.2 กันจริง ๆ — แทนที่จะคืนแค่ตำแหน่ง `usize` เปล่า ๆ เราจะคืน
**slice ของสตริงต้นทางเลย**:

```rust
fn first_word(s: &str) -> &str {
    let bytes = s.as_bytes();

    for (i, &b) in bytes.iter().enumerate() {
        if b == b' ' {
            return &s[..i];
        }
    }

    &s[..]
}

fn main() {
    let sentence = String::from("hello world");
    let word = first_word(&sentence);
    println!("คำแรก: '{word}'");
}
```

ผลลัพธ์:

```
คำแรก: 'hello'
```

**เปรียบเทียบกับเวอร์ชันเดิม:**

- **parameter เปลี่ยนจาก `&String` เป็น `&str`** — เราจะอธิบายเหตุผลเบื้องหลังการเลือกนี้แบบละเอียดในหัวข้อ 8.7 ถัดไป
  ตอนนี้ขอให้สังเกตไว้ก่อนว่ามันยังใช้กับ `&sentence` (ซึ่งเป็น `&String`) ได้ตามปกติ
- **return type เปลี่ยนจาก `usize` เป็น `&str`** — นี่คือการเปลี่ยนแปลงที่สำคัญที่สุด แทนที่จะคืน "ตำแหน่ง" เราคืน
  **"ช่วงข้อมูลที่ยืมมาจาก `s` โดยตรง"**
- บรรทัด `return &s[..i]` — เมื่อเจอช่องว่างที่ตำแหน่ง `i` เราคืนค่า slice ตั้งแต่ต้นสตริงจนถึงก่อนตำแหน่งนั้น
  (`&s[..i]` คือรูปแบบย่อของ `&s[0..i]`)
- บรรทัด `&s[..]` ตอนจบฟังก์ชัน (กรณีไม่เจอช่องว่างเลย ทั้งประโยคคือคำเดียว) — คืน slice ของสตริงทั้งก้อน

สังเกตอีกจุดที่สำคัญมาก: **เราไม่ต้องเขียน lifetime annotation ใด ๆ เลยในตัวอย่างนี้** (`fn first_word(s: &str) ->
&str` ไม่มี `'a` โผล่มาที่ไหน) ทั้ง ๆ ที่ค่าที่คืนออกมาเป็น reference ที่ต้องเชื่อมโยงกับ `s` — นี่เป็นเพราะ Rust มี
กฎที่เรียกว่า **lifetime elision** ซึ่งช่วย "เดา" ความสัมพันธ์ของ lifetime ให้อัตโนมัติในกรณีที่ไม่กำกวม (ที่นี่มี
input reference เดียว คือ `s` ผลลัพธ์ที่เป็น reference จึงต้องมาจาก `s` แน่นอน compiler เดาได้เอง) เราจะเจาะลึกเรื่อง
lifetime และกฎ elision แบบเป็นทางการใน **Part 20** ตอนนี้จำแค่ว่า **compiler รู้แล้วว่า `&str` ที่คืนออกมา "มีอายุ
ผูกติดอยู่กับ `s`"** — และความรู้นี้เองคือกุญแจสำคัญของหัวข้อถัดไป

### 8.6 payoff: บั๊กจากหัวข้อ 8.1-8.2 กลายเป็น "เขียนไม่ได้" ตั้งแต่ compile time

นี่คือจุดสำคัญที่สุดของบทนี้ ลองเอาโค้ดที่ทำให้เกิดบั๊กในหัวข้อ 8.2 มาเขียนใหม่ด้วยฟังก์ชันเวอร์ชัน `&str`:

```rust
fn first_word(s: &str) -> &str {
    let bytes = s.as_bytes();

    for (i, &b) in bytes.iter().enumerate() {
        if b == b' ' {
            return &s[..i];
        }
    }

    &s[..]
}

fn main() {
    let mut sentence = String::from("hello world");

    let word = first_word(&sentence);

    sentence.clear();

    println!("คำแรก: '{word}'");
}
```

ลองสังเกตว่าโค้ดนี้ทำทุกอย่างเหมือนกับโค้ดที่พังในหัวข้อ 8.2 ทุกประการ (เรียกฟังก์ชันหาคำแรก → เก็บผลลัพธ์ → ล้างสตริง →
พิมพ์ผลลัพธ์) — เปลี่ยนแค่ฟังก์ชันจากคืน `usize` เป็นคืน `&str` เท่านั้น แต่ผลลัพธ์ต่างกันโดยสิ้นเชิง **โค้ดนี้
compile ไม่ผ่านเลย**:

```
error[E0502]: cannot borrow `sentence` as mutable because it is also borrowed as immutable
  --> src/main.rs:18:5
   |
16 |     let word = first_word(&sentence);
   |                           --------- immutable borrow occurs here
17 |
18 |     sentence.clear();
   |     ^^^^^^^^^^^^^^^^ mutable borrow occurs here
19 |
20 |     println!("คำแรก: '{word}'");
   |                        ---- immutable borrow later used here
```

**นี่คือของขวัญที่แท้จริงจาก type system ของ Rust**: เราไม่ต้องเขียน logic เพิ่มเติมแม้แต่บรรทัดเดียวเพื่อป้องกันบั๊ก
นี้ — compiler ปฏิเสธไม่ให้โค้ดที่มีความเสี่ยงคอมไพล์ผ่านได้เลยตั้งแต่แรก มาดูกันว่าทำไมมันถึงเกิดขึ้น โดยใช้กฎที่เรียน
จาก **Part 7**:

1. `let word = first_word(&sentence);` — ที่นี่เราสร้าง **immutable borrow** ของ `sentence` (คือ `&sentence`) แล้ว
   ส่งเข้าฟังก์ชัน ผลลัพธ์ที่ได้ (`word: &str`) ก็คือ **immutable borrow ตัวเดียวกันนั้นเอง** ที่ถูกส่งกลับออกมา —
   เพราะอย่างที่อธิบายในหัวข้อ 8.5 lifetime ของ `word` ผูกติดกับ `sentence` โดยตรง ตัว compiler จึงมองว่า
   **`sentence` ยังถูกยืมแบบอ่านอยู่ ตราบใดที่ `word` ยังมีชีวิตอยู่ (ยังถูกใช้งานต่อ)**
2. `sentence.clear();` — method `.clear()` ต้องการ **mutable borrow** ของ `sentence` (เพราะมันแก้ไขเนื้อหาข้างใน)
3. `println!("... {word}");` — บรรทัดนี้ **ใช้งาน `word` ต่อ** ซึ่งหมายความว่า immutable borrow จากขั้นตอนที่ 1
   **ยังมีชีวิตอยู่จนถึงจุดนี้** (ตาม NLL ที่เรียนใน Part 7 — borrow จะ "อยู่" ตราบใดที่ยังมีการใช้งานค่านั้นต่อในอนาคต)

เมื่อนำ 3 ข้อนี้มารวมกัน: เรามี immutable borrow ของ `sentence` ที่ยังไม่หมดอายุ (เพราะ `word` ถูกใช้ต่อในบรรทัดที่ 3)
แต่ตรงกลางกลับพยายามสร้าง mutable borrow (`.clear()`) ขึ้นมาซ้อนทับ — นี่คือการละเมิดกฎยืมข้อที่สำคัญที่สุดจาก
**Part 7 โดยตรง**: **"ห้ามมี mutable borrow พร้อมกับ immutable borrow ที่ยังมีชีวิตอยู่เด็ดขาด"** ไม่ว่า borrow
เหล่านั้นจะมาในรูปของ `&T`/`&mut T` ธรรมดา หรือมาในรูปของ slice ก็ตาม — **กฎเดียวกันทุกประการ ไม่มีข้อยกเว้น**

พูดอีกแบบหนึ่ง: **บั๊กจากหัวข้อ 8.1-8.2 (การใช้ `usize` index ที่ล้าสมัยไปแล้วหลังจากสตริงถูกแก้ไข) ตอนนี้ "เขียนไม่ได้"
อีกต่อไปแล้ว** เพราะ `&str` ที่คืนออกมาไม่ใช่แค่ตัวเลขเปล่า ๆ อีกต่อไป มันคือ **การยืมข้อมูลจริง ๆ** ที่ borrow checker
ติดตามได้ ถ้าคุณพยายามแก้ไขต้นทางในขณะที่ยังมีคนยืมอยู่ compiler จะจับได้ทันทีตั้งแต่ก่อน binary ถูกสร้างขึ้นด้วยซ้ำ
ไม่ต้องรอให้โปรแกรม panic ตอนรันจริงแบบที่เห็นในหัวข้อ 8.2 เลย — **นี่คือคุณค่าที่แท้จริงของ slice**: มันเปลี่ยนบั๊ก
ที่ตรวจจับได้แค่ตอน runtime (หรือแย่กว่านั้น ตรวจจับไม่ได้เลยจนกว่าจะสร้างความเสียหายจริง) ให้กลายเป็น **compile error
ที่เห็นได้ทันทีตอนเขียนโค้ด**

### 8.7 `&str` vs `&String` เป็น parameter ของฟังก์ชัน: Deref Coercion

ในหัวข้อ 8.5 เราเปลี่ยน parameter ของ `first_word` จาก `&String` เป็น `&str` — การเปลี่ยนนี้ไม่ใช่เรื่องบังเอิญ
แต่เป็น **หลักการออกแบบฟังก์ชันที่ idiomatic ที่สุดใน Rust**: **ฟังก์ชันที่แค่ต้องการ "อ่าน" สตริง ควรรับ parameter
เป็น `&str` เสมอ ไม่ใช่ `&String`** เหตุผลคือ `&str` **ใช้งานได้กว้างกว่า** `&String` มาก โดยไม่เสียอะไรเลย

ลองดูว่าถ้าเรายังใช้ `&String` เป็น parameter จะเกิดอะไรขึ้นเมื่อพยายามส่ง string literal เข้าไปตรง ๆ:

```rust
fn first_word_bad(s: &String) -> &str {
    let bytes = s.as_bytes();

    for (i, &b) in bytes.iter().enumerate() {
        if b == b' ' {
            return &s[..i];
        }
    }

    &s[..]
}

fn main() {
    // literal เป็น &str ไม่ใช่ &String — ส่งเข้าฟังก์ชันที่รับ &String ตรง ๆ ไม่ได้
    let word = first_word_bad("hello world");
    println!("{word}");
}
```

โค้ดนี้ compile ไม่ผ่าน:

```
error[E0308]: mismatched types
  --> src/main.rs:15:31
   |
15 |     let word = first_word_bad("hello world");
   |                -------------- ^^^^^^^^^^^^^ expected `&String`, found `&str`
   |                |
   |                arguments to this function are incorrect
```

เพราะ `"hello world"` มี type เป็น `&str` (มาตั้งแต่หัวข้อ 8.3) จะบังคับให้ตรงกับ parameter ที่ประกาศเป็น `&String`
ตรง ๆ ไม่ได้ ผู้เรียกต้องเสียเวลาสร้าง `String` ขึ้นมาก่อน (`&String::from("hello world")`) ทั้ง ๆ ที่ไม่มีความจำเป็น
ต้องจองหน่วยความจำ heap เพิ่มเลย เพราะฟังก์ชันแค่ **อ่าน** ข้อมูล ไม่ได้แก้ไขอะไร

ในทางกลับกัน ถ้าเปลี่ยน parameter เป็น `&str` ตามที่ทำในหัวข้อ 8.5 ฟังก์ชันจะใช้งานได้ **ทั้งสองแบบ**:

```rust
fn first_word(s: &str) -> &str {
    let bytes = s.as_bytes();

    for (i, &b) in bytes.iter().enumerate() {
        if b == b' ' {
            return &s[..i];
        }
    }

    &s[..]
}

fn main() {
    let owned = String::from("hello world");

    // ใช้กับ &String ได้ ผ่าน deref coercion (&String -> &str อัตโนมัติ)
    let word_from_string = first_word(&owned);

    // ใช้กับ string literal ได้ตรง ๆ (literal เป็น &str อยู่แล้ว)
    let word_from_literal = first_word("goodbye friend");

    println!("{word_from_string} {word_from_literal}");
}
```

ผลลัพธ์:

```
hello goodbye
```

#### ทำไม `&owned` (ซึ่งเป็น `&String`) ใช้กับ parameter ที่ประกาศเป็น `&str` ได้?

คำตอบคือกลไกที่เรียกว่า **deref coercion** — Rust รู้ว่า `String` implement trait ชื่อ `Deref` โดยกำหนด
`Target = str` (พูดง่าย ๆ คือ `String` "ประกาศตัวเองไว้" ว่าสามารถถูกมองเป็น `str` ได้เสมอ เพราะภายใน `String` ก็คือ
buffer ของ UTF-8 bytes ที่ถูกต้องอยู่แล้ว เหมือนกับที่ `str` เป็น) เมื่อ compiler เห็นว่าคุณส่ง `&String` เข้าไปในจุด
ที่ต้องการ `&str` มันจะ **แปลงให้อัตโนมัติแบบไม่มีค่าใช้จ่ายเพิ่ม (zero-cost)** — ไม่มีการคัดลอกข้อมูลใด ๆ เกิดขึ้น
แค่สร้าง `&str` ตัวใหม่ที่ชี้ไปยัง buffer เดียวกันของ `String` นั้น (จำได้จากหัวข้อ 8.3 ว่า `&str` คือคู่ `(ptr, len)`
— compiler แค่หยิบ pointer และความยาวจาก `String` มาประกอบเป็น `&str` เท่านั้นเอง) เราจะเจาะลึก trait `Deref` และ
กลไก deref coercion แบบเต็มรูปแบบใน **Part 28-29** ตอนนี้จำหลักการปฏิบัติง่าย ๆ ไว้พอ:

| Parameter ประกาศเป็น | รับ `&String` ได้ไหม | รับ string literal (`&str`) ได้ไหม |
|---|---|---|
| `&str` | ได้ (ผ่าน deref coercion อัตโนมัติ) | ได้ตรง ๆ |
| `&String` | ได้ตรง ๆ | **ไม่ได้** ต้องแปลงเป็น `String` ก่อน |

**หลักการจำง่าย ๆ**: ถ้าฟังก์ชันของคุณแค่ต้องการ "อ่าน" เนื้อหาสตริง ไม่ได้ต้องการเรียก method ที่มีแค่ใน `String`
เท่านั้น (เช่น `.push_str()`, `.clear()` ที่แก้ไขความยาว/เนื้อหา) ให้รับ parameter เป็น `&str` เสมอ — มันจะใช้งานได้
กว้างที่สุดโดยไม่เสียอะไรเลย ในทางกลับกัน `&String` ควรใช้เฉพาะเมื่อคุณต้องการเรียก method เฉพาะของ `String` จริง ๆ
ซึ่งในทางปฏิบัติพบน้อยมาก เพราะเหตุผลด้าน ownership ในตัวอย่างส่วนใหญ่มักออกแบบให้ฟังก์ชันแก้ไข `String` รับ
`&mut String` ไปเลยแทน (เจาะลึกอีกใน Part 9 เมื่อเราเริ่มออกแบบ method ของ struct)

### 8.8 Slice ทั่วไป: `&[T]`

แนวคิดของ slice ไม่ได้ผูกติดอยู่กับสตริงเท่านั้น — Rust สรุปแนวคิดนี้ให้ใช้กับ **ข้อมูลชนิดใดก็ได้ที่เก็บแบบต่อเนื่อง
กันใน memory** ผ่านชนิด **`&[T]`** (อ่านว่า "slice ของ `T`") ซึ่งใช้ได้กับ array `[T; N]` ที่เรียนมาจาก Part 3
ได้ทันที syntax ก็เหมือนกับ string slice เป๊ะ ๆ:

```rust
fn main() {
    let numbers: [i32; 5] = [10, 20, 30, 40, 50];

    let middle = &numbers[1..3]; // [20, 30]
    println!("{:?}", middle);
}
```

ผลลัพธ์:

```
[20, 30]
```

`&numbers[1..3]` คือ slice ที่ชี้ไปยังสมาชิกตำแหน่ง 1 และ 2 ของ array (ไม่รวมตำแหน่ง 3) — เหมือนกับ range ที่ใช้กับ
สตริงทุกประการ เพียงแต่หน่วยตอนนี้คือ "จำนวนสมาชิก" ไม่ใช่ "จำนวน byte" (เพราะ array มีสมาชิกทุกตัวขนาดเท่ากันเสมอ
ไม่ต้องกังวลเรื่อง character boundary แบบ UTF-8)

มาดูตัวอย่างที่ใกล้เคียงงานจริงมากขึ้น: ระบบเก็บค่าจากเซนเซอร์วัดอุณหภูมิที่บันทึกทุกชั่วโมง แล้วต้องการหาค่าสูงสุด
ในบางช่วงเวลา (เช่น ช่วงเที่ยงวัน) โดยไม่ต้องไปยุ่งกับข้อมูลทั้งวัน:

```rust
fn max_in_slice(data: &[f64]) -> f64 {
    let mut max = data[0];

    for i in 1..data.len() {
        if data[i] > max {
            max = data[i];
        }
    }

    max
}

fn main() {
    let sensor_readings: [f64; 8] = [21.5, 22.0, 23.8, 30.1, 29.9, 24.4, 22.2, 21.0];

    let whole_max = max_in_slice(&sensor_readings);
    println!("ค่าสูงสุดทั้งวัน: {whole_max}");

    let midday = &sensor_readings[3..6];
    let midday_max = max_in_slice(midday);
    println!("ค่าสูงสุดช่วงเที่ยง: {midday_max}");

    let morning_max = max_in_slice(&sensor_readings[0..3]);
    println!("ค่าสูงสุดช่วงเช้า: {morning_max}");
}
```

ผลลัพธ์:

```
ค่าสูงสุดทั้งวัน: 30.1
ค่าสูงสุดช่วงเที่ยง: 30.1
ค่าสูงสุดช่วงเช้า: 23.8
```

**อธิบายโค้ดทีละส่วน:**

- **parameter ของ `max_in_slice` ประกาศเป็น `&[f64]`** — ไม่ใช่ `&[f64; 8]` ที่ผูกกับขนาด 8 ตายตัว สังเกตว่าเราเรียก
  ฟังก์ชันนี้ทั้งกับ `&sensor_readings` (ทั้ง array ขนาด 8) และกับ `midday`/`&sensor_readings[0..3]` (ช่วงย่อยขนาด
  3) — **ฟังก์ชันตัวเดียวใช้ได้กับข้อมูลความยาวเท่าไหร่ก็ได้** เพราะ `&[T]` ไม่ได้ผูกความยาวไว้ใน type เลย
  ความยาวคือ "ค่า" ที่เก็บอยู่ในตัว slice เอง (จำได้จากหัวข้อ 8.3 — `&[T]` ก็เป็น fat pointer แบบเดียวกับ `&str`
  คือคู่ `(ptr, len)` เหมือนกัน แค่ `T` เปลี่ยนจาก `u8` เป็นชนิดข้อมูลอะไรก็ได้)
- **`&sensor_readings` (type `&[f64; 8]`) แปลงเป็น `&[f64]` ได้อัตโนมัติ** — นี่คือ deref coercion แบบเดียวกับที่
  เราเห็นระหว่าง `&String` กับ `&str` ในหัวข้อ 8.7 เป๊ะ ๆ! array แบบตายตัว `[T; N]` implement `Deref<Target =
  [T]>` เช่นกัน ดังนั้นฟังก์ชันที่รับ `&[T]` จะรับ reference ของ array ขนาดเท่าไหร่ก็ได้โดยอัตโนมัติ ไม่ต้องแปลง
  เองแม้แต่นิดเดียว — หลักการเดียวกัน แค่คนละชนิดข้อมูล

#### ทำไมควรรับ `&[T]` แทน `&[T; N]` เป็น parameter

ลองสมมติว่าเราประกาศ `max_in_slice` ให้รับ `&[f64; 8]` ตรง ๆ (ผูกความยาวไว้ในลายเซ็นฟังก์ชันเลย) ฟังก์ชันนั้นจะใช้
ได้แค่กับ array ที่มีความยาว 8 พอดีเท่านั้น เรียกกับ array ขนาดอื่น หรือกับ sub-slice ที่ตัดมาแล้ว (ซึ่งความยาวไม่แน่นอน
ล่วงหน้าตอน compile) จะทำไม่ได้เลย — เราจะเห็น error จริงของกรณีนี้ในหัวข้อ "กับดักที่พบบ่อย" ท้ายบท **การรับ `&[T]`
(ไม่ผูกความยาว) จึงเป็นวิธีที่ยืดหยุ่นกว่าและเป็น idiomatic Rust เสมอ** เว้นแต่คุณมีเหตุผลจำเพาะที่ต้องการบังคับความยาว
ตายตัวจริง ๆ (ซึ่งพบน้อยมากในทางปฏิบัติ)

#### `&[T]` คือฐานที่ `Vec<T>` จะสร้างต่อยอด (teaser สำหรับ Part 13)

จากหัวข้อ 3.9 เราเรียนไปแล้วว่า array มีข้อจำกัดสำคัญคือ **ความยาวต้องรู้ตายตัวตั้งแต่ compile time** ถ้าต้องการ
collection ที่ขนาดเปลี่ยนแปลงได้ตอน runtime ต้องใช้ **`Vec<T>`** ซึ่งเราจะเรียนเต็มรูปแบบใน **Part 13** — ข่าวดีคือ
**ฟังก์ชันที่คุณเขียนรับ `&[T]` ในวันนี้ จะใช้ได้กับ `Vec<T>` ในอนาคตทันทีโดยไม่ต้องแก้โค้ดแม้แต่บรรทัดเดียว** เพราะ
`Vec<T>` ก็ implement `Deref<Target = [T]>` เช่นเดียวกับ array — มันคือ "array ที่ขยายขนาดได้บน heap" ที่ภายใต้ผิว
ยังคงใช้กลไก slice แบบเดียวกันนี้ทุกอย่างในการส่งข้อมูลแบบอ่านอย่างเดียวให้ฟังก์ชันอื่น ๆ นี่คือเหตุผลที่การเข้าใจ
`&[T]` ให้แน่นตั้งแต่ตอนนี้จะช่วยให้ Part 13 เรียนได้ง่ายขึ้นมาก — แนวคิดหลักไม่เปลี่ยนเลย เปลี่ยนแค่ว่าข้อมูลต้นทาง
มาจาก array (ขนาดตายตัว) หรือ `Vec` (ขนาดปรับได้) เท่านั้น

### 8.9 Mutable Slice: `&mut [T]`

จนถึงตอนนี้ slice ทุกตัวที่เราเห็นเป็น **immutable** (`&[T]`, `&str`) — ใช้อ่านข้อมูลอย่างเดียว แต่ Rust ก็มี slice
แบบแก้ไขได้เช่นกัน คือ **`&mut [T]`** ซึ่งทำงานตามกฎ mutable borrow ที่เรียนจาก **Part 7** ทุกประการ (ยืมแก้ไขได้
ทีละคนเท่านั้น และห้ามมี immutable borrow ค้างอยู่พร้อมกัน)

ตัวอย่าง: ฟังก์ชันที่คูณค่าทุกตัวใน slice ด้วย 2:

```rust
fn double_all(values: &mut [i32]) {
    for i in 0..values.len() {
        values[i] *= 2;
    }
}

fn main() {
    let mut scores = [10, 20, 30, 40, 50];

    double_all(&mut scores);
    println!("{:?}", scores);

    double_all(&mut scores[1..3]);
    println!("{:?}", scores);
}
```

ผลลัพธ์:

```
[20, 40, 60, 80, 100]
[20, 80, 120, 80, 100]
```

**อธิบายโค้ดทีละส่วน:**

- `values: &mut [i32]` — parameter เป็น mutable slice รับได้ทั้ง array ทั้งก้อนหรือช่วงย่อย เหมือนกับ `&[T]` ทุกอย่าง
  ต่างกันแค่ว่า **แก้ไขค่าข้างในได้**
- `values[i] *= 2;` — เข้าถึงสมาชิกด้วย index แล้วแก้ไขค่าตรง ๆ ทำได้เพราะ `values` เป็น mutable reference (เหมือน
  การแก้ไขผ่าน `&mut T` ธรรมดาที่เรียนใน Part 7 — ที่นี่แค่ "T" คือสมาชิกแต่ละตัวในช่วงที่ slice ชี้ไปเท่านั้น)
- `double_all(&mut scores)` — เรียกครั้งแรกกับ array ทั้งก้อน (ผ่าน deref coercion จาก `&mut [i32; 5]` เป็น
  `&mut [i32]` — deref coercion ใช้ได้กับทั้งฝั่ง mutable และ immutable) ผลคือทุกตัวถูก double หมด `[20, 40, 60,
  80, 100]`
- `double_all(&mut scores[1..3])` — เรียกครั้งที่สองกับแค่ช่วงย่อย ตำแหน่ง 1 และ 2 เท่านั้น (`40` และ `60` จาก
  รอบก่อน) ทำให้ได้ `80` และ `120` ส่วนตำแหน่งอื่น (`20`, `80`, `100` ที่เหลือ) **ไม่ถูกแก้ไขเลย** เพราะ mutable
  slice จำกัดการแก้ไขไว้เฉพาะช่วงที่มันชี้ไปเท่านั้นจริง ๆ — ไม่มีทางที่ฟังก์ชันจะไปแก้ข้อมูลนอกช่วงที่ได้รับมาได้เลย

#### กฎการยืมของ Part 7 ยังใช้กับ mutable slice ทุกประการ — ไม่มีข้อยกเว้น

เพราะ `&mut [T]` ก็คือ mutable borrow ชนิดหนึ่ง กฎ "ห้ามมี mutable borrow ซ้อนกับ borrow อื่นที่ยังมีชีวิตอยู่"
จาก Part 7 จึงบังคับใช้เต็มรูปแบบ ลองดูตัวอย่างที่แสดงให้เห็นชัด:

```rust
fn double_all(values: &mut [i32]) {
    for i in 0..values.len() {
        values[i] *= 2;
    }
}

fn main() {
    let mut scores = [10, 20, 30, 40, 50];

    let top_half = &mut scores[0..3];

    println!("สมาชิกตัวที่ 4: {}", scores[4]);

    double_all(top_half);
}
```

โค้ดนี้ compile ไม่ผ่าน:

```
error[E0502]: cannot borrow `scores[_]` as immutable because it is also borrowed as mutable
  --> src/main.rs:12:36
   |
10 |     let top_half = &mut scores[0..3];
   |                         ------ mutable borrow occurs here
11 |
12 |     println!("สมาชิกตัวที่ 4: {}", scores[4]);
   |                                ^^^^^^^^^ immutable borrow occurs here
13 |
14 |     double_all(top_half);
   |                -------- mutable borrow later used here
```

สาเหตุคือ `top_half` เป็น mutable borrow ของ `scores` ที่ยังมีชีวิตอยู่ (เพราะถูกใช้ต่อในบรรทัด `double_all
(top_half)`) แต่ตรงกลางเราพยายามอ่าน `scores[4]` ซึ่งต้องการ immutable borrow ของ `scores` — แม้ในทางความหมาย
จริง `top_half` จะครอบคลุมแค่ตำแหน่ง 0-2 และ `scores[4]` เป็นคนละตำแหน่งกันเลย แต่ **borrow checker มองการยืมผ่าน
`[]` (index/slice operator) ในระดับของ "ตัวแปรทั้งตัว" ไม่ได้วิเคราะห์ลึกถึงระดับว่าตำแหน่งไหนซ้อนกับตำแหน่งไหนบ้าง**
มันจึงระวังไว้ก่อนอย่างเข้มงวด (conservative) เพื่อความปลอดภัย — นี่คือพฤติกรรมเดียวกับที่เราเห็นใน Part 7 ตอนพูดถึง
ข้อจำกัดของ borrow checker ที่บางครั้ง "เข้มงวดกว่าที่จำเป็นจริง ๆ" เพื่อความง่ายและความแน่นอนของการตรวจสอบ

(หมายเหตุ: ถ้าคุณต้องการยืม mutable slice สองช่วงที่ **ไม่ทับกันจริง ๆ พร้อมกัน** เช่นแบ่ง array ออกเป็นครึ่งซ้าย
ครึ่งขวาแล้วแก้ไขทั้งสองฝั่งพร้อมกัน standard library มี method ชื่อ `split_at_mut` ที่ทำสิ่งนี้ได้อย่างปลอดภัย
โดยพิสูจน์ให้ borrow checker เชื่อว่าสองช่วงนั้นไม่ทับกันจริง — เป็นเรื่องที่ค่อนข้างขั้นสูงและใช้ `unsafe` อยู่ภายใน
เพียงเพื่อให้เห็นว่ามีทางออกสำหรับสถานการณ์นี้ โดยไม่ต้องเจาะลึกตอนนี้)

### 8.10 ตัวอย่างจริง: รวม String Slice และ Array Slice — พาร์สข้อมูลเซนเซอร์แบบ CSV-like

มาปิดท้ายบทนี้ด้วยตัวอย่างที่ผสมทั้ง `&str` และ `&[T]` เข้าด้วยกัน ซึ่งเป็นสถานการณ์ที่พบได้บ่อยมากในงานจริง เช่น
ระบบ IoT ที่ต้องอ่าน log บรรทัดหนึ่งจากเซนเซอร์ แยกส่วนหัว (station ID) ออกจากข้อมูลตัวเลข แล้วนำตัวเลขไปวิเคราะห์
ต่อเป็นช่วง ๆ:

```rust
fn max_in_slice(data: &[f64]) -> f64 {
    let mut max = data[0];

    for i in 1..data.len() {
        if data[i] > max {
            max = data[i];
        }
    }

    max
}

fn station_id(line: &str) -> &str {
    match line.find(':') {
        Some(colon_index) => &line[..colon_index],
        None => line,
    }
}

fn readings_part(line: &str) -> &str {
    match line.find(':') {
        Some(colon_index) => &line[colon_index + 1..],
        None => "",
    }
}

fn main() {
    let log_line = "SENSOR_A:21.5,22.0,23.8,30.1,29.9,24.4,22.2,21.0";

    let id = station_id(log_line);
    let readings_csv = readings_part(log_line);

    println!("รหัสสถานี: {id}");
    println!("ข้อมูลดิบ: {readings_csv}");

    let mut readings: [f64; 8] = [0.0; 8];
    let mut i = 0;
    for part in readings_csv.split(',') {
        readings[i] = part.parse().expect("ค่าที่อ่านได้ต้องเป็นตัวเลข");
        i += 1;
    }

    println!("อ่านค่าได้ {i} จุด: {:?}", readings);

    let morning = &readings[0..3];
    let afternoon = &readings[3..6];
    let evening = &readings[6..8];

    println!("[{id}] สูงสุดช่วงเช้า: {}", max_in_slice(morning));
    println!("[{id}] สูงสุดช่วงบ่าย: {}", max_in_slice(afternoon));
    println!("[{id}] สูงสุดช่วงเย็น: {}", max_in_slice(evening));
    println!("[{id}] สูงสุดทั้งวัน: {}", max_in_slice(&readings));
}
```

ผลลัพธ์:

```
รหัสสถานี: SENSOR_A
ข้อมูลดิบ: 21.5,22.0,23.8,30.1,29.9,24.4,22.2,21.0
อ่านค่าได้ 8 จุด: [21.5, 22.0, 23.8, 30.1, 29.9, 24.4, 22.2, 21.0]
[SENSOR_A] สูงสุดช่วงเช้า: 23.8
[SENSOR_A] สูงสุดช่วงบ่าย: 30.1
[SENSOR_A] สูงสุดช่วงเย็น: 22.2
[SENSOR_A] สูงสุดทั้งวัน: 30.1
```

**อธิบายโค้ดทีละส่วน:**

- **`station_id` และ `readings_part` ใช้ string slice แยกส่วนหัวออกจากข้อมูล** — `line.find(':')` คืนค่า
  `Option<usize>` (ตำแหน่ง byte ของอักขระ `:` ตัวแรก ถ้าเจอ) เราใช้ `match` (จะเรียนอย่างเป็นทางการใน Part 10)
  เพื่อดึงตำแหน่งออกมา แล้ว slice สตริงตามตำแหน่งนั้น: **ก่อน** `:` คือ station ID, **หลัง** `:` คือข้อมูลตัวเลข
  ทั้งหมด (`colon_index + 1` เพื่อข้ามตัว `:` เองไปด้วย) สังเกตว่าไม่มีการคัดลอกข้อมูลเกิดขึ้นเลยในสองฟังก์ชันนี้
  — ทั้งคู่แค่คืน slice ที่ชี้เข้าไปในสตริงต้นฉบับ `log_line` เท่านั้น
- **`readings_csv.split(',')` แยกข้อมูลตัวเลขออกเป็นส่วน ๆ ตาม comma** — `.split(',')` คืนค่าที่วนอ่านได้ (แต่ละค่า
  ที่ได้คือ `&str` ของช่วงระหว่าง comma แต่ละคู่) เราวนลูปด้วย `for part in readings_csv.split(',')` แล้วใช้
  `part.parse()` แปลงแต่ละส่วนเป็น `f64` (แบบเดียวกับ `.parse()` ที่เรียนในหัวข้อ 3.10) เก็บเข้า array ที่จองไว้
  ล่วงหน้าด้วยตัวนับ `i` เอง เพราะเรารู้จำนวนค่าที่แน่นอน (8 ค่า) จึงยังใช้ array ธรรมดาได้โดยไม่ต้องพึ่ง `Vec`
  (ที่ยังไม่ได้เรียนจนถึง Part 13)
- **`&readings[0..3]`, `&readings[3..6]`, `&readings[6..8]` คือ array slice แบ่งช่วงเวลา** — เช้า/บ่าย/เย็น
  แต่ละช่วงส่งเข้า `max_in_slice` (ฟังก์ชันเดียวกันจากหัวข้อ 8.8) เพื่อหาค่าสูงสุดของแต่ละช่วงแยกกัน ในขณะที่
  `&readings` (ทั้ง array ผ่าน deref coercion) ใช้หาค่าสูงสุดของทั้งวัน — **ฟังก์ชันเดียวใช้ได้กับทุกกรณีเลย**
  เพราะมันรับ `&[f64]` ไม่ใช่ array ขนาดตายตัว

ตัวอย่างนี้แสดงให้เห็นว่า **string slice และ array slice ทำงานร่วมกันได้อย่างเป็นธรรมชาติ**: เราใช้ `&str` slicing
เพื่อ "แยกโครงสร้าง" ของข้อความดิบให้เป็นชิ้นที่มีความหมาย แล้วใช้ `&[T]` slicing เพื่อ "แบ่งช่วง" ข้อมูลตัวเลขที่แปลง
ได้แล้วสำหรับการวิเคราะห์ต่อ ทั้งหมดนี้เกิดขึ้นโดยแทบไม่มีการคัดลอกข้อมูลส่วนเกินเลย (ยกเว้นตอน `.parse()` ที่ต้อง
สร้างค่า `f64` ใหม่จากข้อความ ซึ่งเป็นเรื่องที่หลีกเลี่ยงไม่ได้อยู่แล้ว) — นี่คือเหตุผลที่ slice เป็นเครื่องมือที่ทรง
พลังและใช้บ่อยที่สุดตัวหนึ่งในโค้ด Rust ระดับ production จริง

## กับดักที่พบบ่อย (Common Pitfalls)

**1. Slice ตำแหน่งที่ไม่ตรง character boundary ของ UTF-8**

```rust
fn main() {
    let greeting = String::from("สวัสดี");
    let broken = &greeting[0..1];
    println!("{broken}");
}
```

```
thread 'main' panicked at src/main.rs:3:19:
byte index 1 is not a char boundary; it is inside 'ส' (bytes 0..3) of `สวัสดี`
```

**วิธีแก้**: ห้ามคำนวณตำแหน่ง byte สำหรับ slice สตริงด้วยการเดา/นับตัวอักษรที่ "มองเห็น" ตรง ๆ โดยเฉพาะกับข้อความ
ที่ไม่ใช่ ASCII ล้วน (ภาษาไทย, จีน, ญี่ปุ่น, emoji) — ถ้าต้องการวนอ่านทีละตัวอักษรอย่างปลอดภัย ใช้ `.chars()` แทน
(ตามหัวข้อ 8.4) หรือถ้าจำเป็นต้อง slice จริง ๆ ให้ใช้ method ที่คำนวณตำแหน่ง byte ที่ถูกต้องให้อัตโนมัติ เช่น
`.find()` (แบบที่ใช้ในหัวข้อ 8.10) ซึ่งจะคืนตำแหน่งที่ตรง character boundary เสมอ

**2. Slice เกินขอบเขตความยาวจริงของสตริง**

```rust
fn main() {
    let s = String::from("hello");
    let out = &s[0..10]; // s ยาวแค่ 5 bytes แต่พยายามตัดถึง byte ที่ 10
    println!("{out}");
}
```

```
thread 'main' panicked at src/main.rs:3:16:
byte index 10 is out of bounds of `hello`
```

**วิธีแก้**: ตรวจสอบว่าขอบขวาของ range ไม่เกิน `.len()` ของสตริงเสมอ ก่อน slice ในโค้ดจริง หากความยาวของข้อมูลไม่แน่นอน
(เช่นมาจาก input ผู้ใช้) ควรใช้ method ที่ปลอดภัยกว่าการ slice ด้วย `[]` ตรง ๆ เช่น `.get(0..10)` ที่คืนค่าเป็น
`Option<&str>` (`None` เมื่อ range ไม่ถูกต้อง แทนการ panic) — เราจะเห็น pattern การใช้ `Option<T>` แบบนี้ชัดเจนขึ้น
มากใน **Part 11**

**3. เก็บ `usize` index ไว้ใช้ต่อ หลังจากแก้ไขข้อมูลต้นทางไปแล้ว**

```rust
fn first_word_index(s: &String) -> usize {
    let bytes = s.as_bytes();
    for (i, &b) in bytes.iter().enumerate() {
        if b == b' ' {
            return i;
        }
    }
    s.len()
}

fn main() {
    let mut sentence = String::from("hello world");
    let word_end = first_word_index(&sentence);

    sentence.clear();

    println!("คำแรกยาว {word_end} bytes"); // ยังพิมพ์ 5 ทั้งที่ sentence ว่างไปแล้ว!
}
```

โค้ดนี้ **compile ผ่านโดยไม่มี error หรือ warning เลย** และพิมพ์ค่า `5` ที่ไม่มีความหมายอะไรอีกต่อไปออกมาแบบเงียบ ๆ
— นี่คือปัญหาที่อธิบายละเอียดในหัวข้อ 8.1-8.2 **วิธีแก้**: ให้ฟังก์ชันคืนค่าเป็น slice (`&str` หรือ `&[T]`) แทน
`usize`/index เปล่า ๆ เสมอ เมื่อไหร่ที่ค่าที่คืนออกมา "มีความหมายเฉพาะช่วงที่ข้อมูลต้นทางยังไม่เปลี่ยนแปลง"
เพราะ slice จะผูก lifetime เข้ากับข้อมูลต้นทางให้ borrow checker ช่วยตรวจสอบแทนเราโดยอัตโนมัติ (ตามหัวข้อ 8.5-8.6)

**4. พยายามแก้ไข `String`/array ต้นทาง ขณะที่ยังมี slice ยืมอยู่ (`E0502`)**

```rust
fn first_word(s: &str) -> &str {
    let bytes = s.as_bytes();
    for (i, &b) in bytes.iter().enumerate() {
        if b == b' ' {
            return &s[..i];
        }
    }
    &s[..]
}

fn main() {
    let mut sentence = String::from("hello world");

    let word = first_word(&sentence);

    sentence.push_str("!!!"); // พยายามต่อท้ายสตริง ขณะที่ word ยังยืมอยู่

    println!("{word}");
}
```

```
error[E0502]: cannot borrow `sentence` as mutable because it is also borrowed as immutable
  --> src/main.rs:16:5
   |
14 |     let word = first_word(&sentence);
   |                           --------- immutable borrow occurs here
15 |
16 |     sentence.push_str("!!!");
   |     ^^^^^^^^^^^^^^^^^^^^^^^^ mutable borrow occurs here
17 |
18 |     println!("{word}");
   |                ---- immutable borrow later used here
```

**วิธีแก้** มีสองแบบหลัก เลือกตามความหมายที่ต้องการจริง ๆ:

- **แบบที่ 1 — จัดลำดับโค้ดใหม่ให้ใช้ `word` ให้จบก่อนที่จะแก้ไข `sentence`** (อาศัย NLL จาก Part 7 — เมื่อ `word`
  ไม่ถูกใช้งานต่ออีก immutable borrow จะหมดอายุทันที ไม่ต้องรอปิด scope):

  ```rust
  fn first_word(s: &str) -> &str {
      let bytes = s.as_bytes();
      for (i, &b) in bytes.iter().enumerate() {
          if b == b' ' {
              return &s[..i];
          }
      }
      &s[..]
  }

  fn main() {
      let mut sentence = String::from("hello world");

      let word = first_word(&sentence);
      println!("{word}"); // ใช้ word ให้จบตรงนี้ — borrow หมดอายุแล้ว

      sentence.push_str("!!!"); // ตอนนี้แก้ไขได้แล้ว ไม่มี borrow ค้าง
      println!("{sentence}");
  }
  ```

- **แบบที่ 2 — ทำสำเนาเป็น `String` ของตัวเองด้วย `.to_string()` เมื่อต้องการใช้ค่านั้นต่อไปนาน ๆ โดยไม่อยากผูกกับ
  ต้นทางอีก** (แลกกับการจองหน่วยความจำ heap เพิ่ม แต่ตัดขาดความสัมพันธ์กับ `sentence` ได้เด็ดขาด — นี่คือ trade-off
  ระหว่าง borrow กับ ownership ที่เรียนมาตั้งแต่ Part 6):

  ```rust
  fn first_word(s: &str) -> &str {
      let bytes = s.as_bytes();
      for (i, &b) in bytes.iter().enumerate() {
          if b == b' ' {
              return &s[..i];
          }
      }
      &s[..]
  }

  fn main() {
      let mut sentence = String::from("hello world");

      let word = first_word(&sentence).to_string(); // เป็นเจ้าของสำเนาตัวเอง ไม่ยืมจาก sentence แล้ว

      sentence.push_str("!!!"); // แก้ไขได้เลย เพราะ word ไม่ได้ยืมอะไรจาก sentence อีกต่อไป

      println!("{word}");
  }
  ```

**5. ประกาศ parameter ของฟังก์ชันเป็น slice ขนาดตายตัว (`&[T; N]`) ทั้งที่ควรเป็น `&[T]`**

```rust
fn sum_five(data: &[i32; 5]) -> i32 {
    let mut total = 0;
    for i in 0..5 {
        total += data[i];
    }
    total
}

fn main() {
    let small: [i32; 3] = [1, 2, 3];
    let total = sum_five(&small); // small มีแค่ 3 สมาชิก ไม่ใช่ 5
    println!("{total}");
}
```

```
error[E0308]: mismatched types
  --> src/main.rs:11:26
   |
11 |     let total = sum_five(&small);
   |                 -------- ^^^^^^ expected an array with a size of 5, found one with a size of 3
```

**วิธีแก้**: เปลี่ยน parameter จาก `&[i32; 5]` (ผูกความยาวไว้ตายตัวใน type) เป็น `&[i32]` (slice ที่ไม่ผูกความยาว)
เหมือนที่อธิบายในหัวข้อ 8.8 — ฟังก์ชันจะยืดหยุ่นขึ้นมาก ใช้ได้กับ array ความยาวใดก็ได้ (แค่เปลี่ยนวิธีคำนวณผลรวมจาก
`0..5` เป็น `0..data.len()` เพื่อไม่ผูกกับเลข 5 ตายตัวด้วย) — จำหลักไว้ว่า: **ผูกความยาวไว้ใน type ของ parameter
เฉพาะเมื่อความยาวนั้นมีความหมายทางธุรกิจจริง ๆ ที่ต้องบังคับตายตัว (พบน้อยมาก) ส่วนกรณีทั่วไปให้ใช้ `&[T]` เสมอ**

## สรุป

ในบทนี้เราเริ่มจากปัญหาที่ดูเหมือนเล็กแต่พบได้บ่อยมากในโค้ดจริง: การคืนค่า `usize` index เพื่อ "ชี้" ตำแหน่งข้อมูล
ในสตริง ซึ่งดูเหมือนใช้งานได้ แต่กลับเปราะบางมาก เพราะไม่มีอะไรผูกมันเข้ากับข้อมูลต้นทางในทาง type system เลย — เมื่อ
ต้นทางเปลี่ยนแปลง (เช่นถูก `.clear()`) index เดิมก็กลายเป็นขยะที่ไม่มีความหมายโดยไม่มีสัญญาณเตือนใด ๆ **Slice**
แก้ปัญหานี้ได้อย่างสมบูรณ์ด้วยการเป็น **reference ชนิดพิเศษที่พกทั้งตำแหน่งและความยาวไปด้วยกัน (fat pointer)** และ
ผูก lifetime เข้ากับข้อมูลต้นทางโดยอัตโนมัติ ทำให้ borrow checker จาก Part 7 สามารถตรวจจับความพยายามแก้ไขข้อมูล
ต้นทางขณะที่ยังมี slice ยืมอยู่ได้ตั้งแต่ compile time — เปลี่ยนบั๊กที่ตรวจจับได้แค่ตอน runtime ให้กลายเป็น
compile error ที่เห็นได้ทันที

เราเรียนรู้ **string slice (`&str`)** ทั้ง syntax ของ range (`[start..end]`, `[..end]`, `[start..]`, `[..]`),
โครงสร้างภายในของมันในฐานะคู่ `(pointer, length)`, ความจริงที่ว่า string literal เป็น `&str` มาตั้งแต่ Part 1,
และกับดักสำคัญที่สุดของการจัดการสตริง — การ slice ผิดตำแหน่ง UTF-8 character boundary ที่ทำให้โปรแกรม panic
(โดยเฉพาะกับข้อความภาษาไทยที่ใช้หลาย byte ต่อตัวอักษร) เราเข้าใจว่าทำไมฟังก์ชันที่ต้องการแค่ "อ่าน" สตริงควรรับ
parameter เป็น `&str` แทน `&String` ผ่านกลไก **deref coercion** ที่ทำให้ `&str` ใช้งานได้กว้างกว่าโดยไม่เสียอะไรเลย

จากนั้นเราสรุปแนวคิดเดียวกันให้ใช้กับข้อมูลชนิดใดก็ได้ผ่าน **`&[T]`** (slice ทั่วไป) และ **`&mut [T]`** (mutable
slice ที่ยังต้องเคารพกฎการยืมของ Part 7 ทุกประการ) พร้อมเห็นว่า array ก็ deref coercion เป็น slice ได้เช่นเดียว
กับ `String` และ `&str` — และที่สำคัญคือ **`&[T]` คือฐานที่ `Vec<T>` (Part 13) จะสร้างต่อยอด** ฟังก์ชันที่เขียน
รับ `&[T]` วันนี้จะใช้ได้กับทั้ง array และ `Vec` ในอนาคตโดยไม่ต้องแก้โค้ดเลย ปิดท้ายด้วยตัวอย่างจริงที่รวมทั้ง
string slice และ array slice เข้าด้วยกันในการพาร์สข้อมูลเซนเซอร์แบบ CSV-like

ใน **Part 9** เราจะนำ ownership (Part 6), borrowing (Part 7), และ slice (บทนี้) ที่เรียนมาทั้งหมดไปใช้ออกแบบ
**Structs** — วิธีสร้างชนิดข้อมูลของตัวเองที่รวมหลาย field เข้าด้วยกันอย่างมีความหมาย (ต่างจาก tuple ที่เข้าถึง
สมาชิกด้วย `.0`/`.1` เท่านั้น) พร้อม method ที่ผูกกับ struct ผ่าน `impl` block ซึ่งจะทำให้เราเริ่มเขียนโค้ดที่มี
โครงสร้างใกล้เคียงกับระบบจริงมากขึ้นอย่างเห็นได้ชัด และจะได้เห็น slice กลับมาเป็น field/parameter ของ method อีก
หลายครั้งในบทต่อ ๆ ไปของหลักสูตรนี้
