# Part 6: Ownership เบื้องต้น

> โมดูล: พื้นฐานภาษา Rust (Core Language Fundamentals) | ระดับ: พื้นฐาน | เวลาโดยประมาณ: 150 นาที

## เป้าหมายของบทเรียน

หลังจากจบบทนี้ คุณจะสามารถ:

- อธิบายได้ว่าการจัดการ memory มีกี่แนวทางหลัก ๆ (manual, garbage collection, ownership) แต่ละแนวทางมีข้อดี-ข้อเสียอะไร
  และทำไม Rust จึงเลือกแนวทาง ownership ที่ตรวจสอบตอน compile time
- อธิบายความแตกต่างระหว่าง stack กับ heap ได้อย่างชัดเจน และบอกได้ว่าทำไม Rust จึงให้ความสำคัญกับความแตกต่างนี้มากกว่า
  ภาษาระดับสูงทั่วไป
- ท่องกฎ 3 ข้อของ ownership ได้ และอธิบายด้วยตัวอย่างโค้ดจริงว่ากฎแต่ละข้อทำงานอย่างไรตอน runtime
- อธิบายว่า `Drop` คืออะไร ทำงานตอนไหน และทำไมมันจึงทำให้ Rust ไม่ต้องมี garbage collector แต่ก็ไม่มี memory leak/double-free
- แยกแยะ **move semantics** ออกจากการ copy ได้อย่างแม่นยำ อ่าน error `E0382` ที่เกิดจากการใช้ค่าหลัง move ได้ และรู้วิธีแก้
- ใช้ `.clone()` ได้อย่างมีเหตุผล เข้าใจว่ามันทำ deep copy จริง ๆ และรู้ต้นทุน (cost) ที่ต้องแลกเมื่อเรียกมัน
- อธิบายได้ว่าทำไม `i32`, `bool`, `char`, `f64` และ tuple ของชนิดเหล่านี้ถึงไม่ต้อง move (implement trait `Copy`) ต่างจาก
  `String`
- อธิบายและเขียนโค้ดแสดงว่าการส่งค่าเข้าฟังก์ชัน และการ return ค่าจากฟังก์ชัน มีผลต่อ ownership อย่างไร
- เขียนโปรแกรมจำลองสถานการณ์จริง (ระบบคลังสินค้า) ที่มีการโอนกรรมสิทธิ์ของข้อมูลระหว่างฟังก์ชันหลายตัวได้อย่างถูกต้อง

## ความรู้ที่ต้องมีมาก่อน

บทนี้เป็น**บทแรกของโมดูล 1: พื้นฐานภาษา Rust** และเป็นบทที่สำคัญที่สุดในหลักสูตรทั้งหมด เพราะ Ownership คือแนวคิดที่ทำให้
Rust แตกต่างจากภาษาอื่นทุกภาษาที่คุณอาจเคยรู้จักมาก่อน คุณต้องผ่านโมดูล 0 มาแล้วทั้งหมด:

- **Part 1** — เข้าใจภาพกว้างว่า Rust แก้ปัญหา "เร็วแต่เสี่ยง (C/C++)" กับ "ปลอดภัยแต่ช้า (ภาษาที่มี GC)" ด้วยแนวคิด
  ownership + borrow checker ที่ทำงานตอน compile time บทนี้จะอธิบายเรื่องนี้แบบเจาะลึกเป็นครั้งแรก
- **Part 2** — สร้างและรันโปรเจกต์ด้วย `cargo new`, `cargo run` ได้แล้ว (ทุกตัวอย่างในบทนี้ควรลองรันจริงใน `src/main.rs`)
- **Part 3** — รู้จัก `let`, `mut`, shadowing, scalar type (`i32`, `bool`, `char`, `f64`) และ compound type (tuple, array)
  รวมถึงเคยเห็น string literal (`&str`) มาแล้วในรูปแบบข้อความในเครื่องหมายคำพูด เช่น `"สวัสดี"` — บทนี้จะแนะนำ `String`
  (ชนิดข้อมูลที่จัดสรร memory บน heap ตัวแรกของหลักสูตร) และอธิบายว่ามันต่างจาก `&str` อย่างไร
- **Part 4** — เขียนฟังก์ชัน (`fn`), รับพารามิเตอร์, return ค่า, ใช้ `if`/`else`, `loop`, `while`, `for` ได้แล้ว
  (บทนี้จะใช้ฟังก์ชันเป็นเครื่องมือหลักในการสาธิตเรื่อง ownership)
- **Part 5** — คุ้นเคยกับ `cargo fmt`/`cargo clippy` (ไม่จำเป็นต่อความเข้าใจ ownership โดยตรง แต่ควรรันตรวจโค้ดของคุณเองต่อไป)

**สิ่งที่ยังไม่ได้เรียนและจะไม่ปรากฏในบทนี้**: `struct` แบบเต็มรูปแบบ (Part 9), reference/borrowing (`&`, `&mut` — Part 7),
slice (Part 8) — บทนี้จะพูดถึง `String` ในฐานะ "เจ้าของข้อมูลบน heap" เท่านั้น ยังไม่ยืมข้อมูลใครทั้งสิ้น ทุกอย่างที่เกิดขึ้น
ในบทนี้คือการ "โอนกรรมสิทธิ์" แบบเต็มรูปแบบเสมอ — Part 7 จะมาแก้ปัญหาความไม่สะดวกที่คุณจะเจอในบทนี้

## เนื้อหา

### 6.1 ปัญหาคลาสสิกที่ทุกภาษาต้องเลือก: ใครจัดการ memory

ใน Part 1 เราพูดถึงคร่าว ๆ ว่า Rust "แก้ปัญหาความขัดแย้งระหว่างเร็วกับปลอดภัย" ตอนนี้เรามาดูรายละเอียดจริง ๆ ว่าปัญหานั้นคืออะไร

ทุกโปรแกรมที่ทำงานจริงต้องขอ memory มาใช้ระหว่างทำงาน (เช่น ตอนสร้าง string ยาว ๆ, list ที่ขยายขนาดได้, ข้อมูลที่โครงสร้าง
ซับซ้อน) และต้อง**คืน memory นั้นให้ระบบปฏิบัติการเมื่อไม่ใช้แล้ว** ไม่อย่างนั้นโปรแกรมจะกิน memory ไปเรื่อย ๆ จนเครื่องค้าง
(memory leak) ประวัติศาสตร์ของภาษาโปรแกรมมิ่งแบ่งวิธีแก้ปัญหานี้ออกเป็น 2 แนวทางหลักมาหลายสิบปี ก่อนที่ Rust จะเสนอแนวทางที่ 3

#### แนวทางที่ 1: จัดการเอง (Manual Memory Management) — C, C++ แบบดั้งเดิม

ในภาษาอย่าง C คุณต้องขอ memory ด้วยมือ (`malloc`) และคืนด้วยมือ (`free`) เอง ลองดูตัวอย่าง pseudo-code สไตล์ C
(นี่ไม่ใช่โค้ด Rust — เขียนไว้เพื่อเปรียบเทียบเท่านั้น):

```c
// นี่คือตัวอย่างภาษา C เพื่อการเปรียบเทียบ ไม่ใช่โค้ด Rust
char *name = malloc(20);           // ขอ memory 20 bytes บน heap ด้วยมือ
strcpy(name, "สมชาย");
free(name);                        // คืน memory ด้วยมือ

printf("%s\n", name);              // (1) USE-AFTER-FREE: ใช้ memory ที่คืนไปแล้ว! undefined behavior
free(name);                        // (2) DOUBLE-FREE: คืน memory ซ้ำอีกครั้ง! ทำให้ heap เสียหาย
```

นี่คือปัญหาคลาสสิก 2 แบบที่เกิดจากการจัดการ memory ด้วยมือ:

1. **Use-after-free** — โปรแกรมยังพยายามอ่าน/เขียน memory ที่ถูกคืน (free) ไปแล้ว ผลลัพธ์ที่ได้คือ **undefined behavior**
   (อาจได้ค่าขยะ, อาจ crash, หรือแม้แต่กลายเป็นช่องโหว่ความปลอดภัยร้ายแรงที่แฮกเกอร์ใช้ยึดโปรแกรมได้ — คลาสของบั๊กนี้ชื่อ
   "use-after-free vulnerability" เป็นสาเหตุของ CVE (ช่องโหว่ความปลอดภัย) จำนวนมากในซอฟต์แวร์ที่เขียนด้วย C/C++)
2. **Double-free** — คืน memory ชิ้นเดียวกันสองครั้ง ทำให้ allocator ภายในสับสน (โครงสร้างข้อมูลภายในของ heap allocator
   พัง) มักนำไปสู่ crash หรือถูกโจมตีเพื่อรันโค้ดอันตราย

ถ้าคุณ**ลืม**เรียก `free` เลย จะเกิด **memory leak** — memory ก้อนนั้นจะไม่ถูกคืนตลอดการทำงานของโปรแกรม ถ้าเกิดซ้ำ ๆ
(เช่นในลูปที่รันตลอดเวลาแบบ web server) โปรแกรมจะกิน memory เพิ่มขึ้นเรื่อย ๆ จนเครื่อง crash ในที่สุด

ปัญหาของแนวทางนี้ไม่ใช่ว่า "โปรแกรมเมอร์เขียนโค้ดแย่" แต่เป็นปัญหาเชิงโครงสร้าง — **compiler ของ C/C++ ไม่ได้ตรวจสอบ
ให้คุณเลยว่า pointer ตัวนี้ยังใช้ได้อยู่หรือไม่** มันเชื่อคุณ 100% แม้ในโปรเจกต์ขนาดหลายแสนบรรทัดที่มีคนเขียนหลายสิบคน
การไล่ดูด้วยตาว่า memory แต่ละก้อนถูก free ที่ไหน กี่ครั้ง ใครยังอ้างอิงอยู่บ้าง กลายเป็นงานที่เป็นไปไม่ได้ในทางปฏิบัติ
เมื่อโปรเจกต์ใหญ่ขึ้น รายงานของ Microsoft (2019) และ Google ระบุว่าประมาณ **70% ของช่องโหว่ความปลอดภัยร้ายแรง**
ในโปรเจกต์ C/C++ ของพวกเขา มีต้นตอมาจากบั๊กเกี่ยวกับ memory safety แบบนี้

#### แนวทางที่ 2: Garbage Collection (GC) — Java, Python, JavaScript, Go, C#

แนวทางที่สองคือให้ **runtime** ของภาษาคอยตรวจสอบเองว่า memory ก้อนไหนไม่มีใครใช้แล้ว แล้วคืนให้อัตโนมัติ โปรแกรมเมอร์
ไม่ต้องเรียก `free` เองเลย:

```python
# ตัวอย่างภาษา Python เพื่อเปรียบเทียบ ไม่ใช่โค้ด Rust
def create_and_forget():
    name = "สมชาย" * 1000       # จัดสรร memory ให้ string
    return None                  # ออกจากฟังก์ชัน — ไม่ต้อง free อะไรเลย
    # Garbage Collector จะรู้เองว่าไม่มีใครอ้างอิง name แล้ว
    # แล้วคืน memory ให้ตอนที่มัน "สะดวก" จะทำ — ไม่ใช่ทันที และไม่ใช่ตอนที่เราสั่ง
```

วิธีนี้ปลอดภัยกว่าแนวทาง manual มาก — ไม่มีทาง use-after-free หรือ double-free เกิดขึ้นได้เลย เพราะ GC จะไม่คืน memory
ก้อนที่ยังมีใครอ้างอิงอยู่ แต่แนวทางนี้แลกมาด้วยต้นทุน 2 อย่างที่หลีกเลี่ยงไม่ได้:

1. **Runtime overhead** — ต้องมีโปรแกรมอีกตัวหนึ่ง (garbage collector) ทำงานคู่กับโปรแกรมหลักของคุณตลอดเวลา คอยไล่สแกนว่า
   object ไหนยังมีคนใช้อยู่บ้าง (เทคนิคที่ใช้กันมีหลายแบบ เช่น reference counting, mark-and-sweep, generational GC)
   การสแกนนี้ **ใช้ CPU และ memory เพิ่มเติม** ที่ไม่ได้เกี่ยวกับ logic ของโปรแกรมคุณเลยแม้แต่นิดเดียว
2. **Unpredictable pause (GC pause / "stop-the-world")** — ในหลายระบบ GC ต้อง**หยุดโปรแกรมหลักชั่วคราว**เพื่อสแกนและ
   จัดเรียง memory ให้เรียบร้อย ช่วงเวลานี้เรียกว่า "stop-the-world pause" ซึ่งคาดเดาได้ยากว่าจะเกิดขึ้นตอนไหนและนานแค่ไหน
   สำหรับงานทั่วไป (เว็บแอปธรรมดา) นี่ไม่ใช่ปัญหาใหญ่ แต่สำหรับงานที่ต้องการ latency ต่ำและสม่ำเสมอมาก ๆ เช่น
   real-time audio processing, high-frequency trading, game engine ที่ต้องเรนเดอร์ 60+ เฟรมต่อวินาทีแบบไม่มีสะดุด
   การหยุดแบบไม่คาดเดาได้แม้เพียงไม่กี่มิลลิวินาที ก็ถือเป็นปัญหาใหญ่ นี่คือเหตุผลที่ Discord ย้าย service สำคัญจาก Go
   (ที่มี GC) มาเป็น Rust — เพื่อกำจัด latency spike ที่มาจาก garbage collector โดยเฉพาะ (ตามที่กล่าวถึงใน Part 1)

#### แนวทางที่ 3: Ownership — วิธีของ Rust

Rust เลือกทางที่สาม: ให้ **compiler** เป็นคนตรวจสอบกฎเรื่องการใช้ memory ให้ทั้งหมด **ตอน compile time** โดยอาศัยระบบ
Ownership ที่เราจะเรียนในบทนี้ ผลลัพธ์คือ:

| ประเด็น | Manual (C/C++) | Garbage Collection (Java/Python/Go) | Ownership (Rust) |
|---|---|---|---|
| ใครรับผิดชอบคืน memory | โปรแกรมเมอร์ (มือ) | Runtime (garbage collector) | Compiler (ตรวจตอน compile time) |
| Use-after-free / double-free | เกิดได้ (เสี่ยงมาก) | เกิดไม่ได้ | เกิดไม่ได้ (compile ไม่ผ่านถ้าเสี่ยง) |
| Runtime overhead จาก memory management | ไม่มี | มี (GC ทำงานคู่ตลอดเวลา) | **ไม่มี** — ตรวจจบตอน compile แล้ว |
| Pause ที่คาดเดาไม่ได้ | ไม่มี | มี (GC pause) | ไม่มี |
| ต้นทุนที่ต้องจ่าย | เขียนผิดง่าย บั๊กร้ายแรง | ความเร็ว/memory เสียให้ GC | เรียนรู้ borrow checker (เรียนยากช่วงแรก) |

นี่คือสิ่งที่ทำให้ Rust พิเศษ: **คุณได้ความปลอดภัยระดับเดียวกับภาษาที่มี GC โดยไม่ต้องมี GC เลย** เพราะ compiler ปฏิเสธ
ไม่ให้โค้ดที่มีความเสี่ยงต่อ memory bug คอมไพล์ผ่านตั้งแต่แรก ต้นทุนที่คุณต้องจ่ายคือ "เรียนรู้กฎของ ownership" ซึ่งอาจดู
เข้มงวดในช่วงแรก (คนเรียก Rust ช่วงแรกว่าต้อง "สู้กับ borrow checker") แต่เมื่อเข้าใจแล้ว กฎเหล่านี้กลับกลายเป็นเครื่องมือ
ที่ช่วยให้คุณออกแบบโปรแกรมได้ดีขึ้นตั้งแต่แรก ไม่ใช่แค่ป้องกันบั๊ก

ที่สำคัญที่สุด: **กฎของ ownership ถูกตรวจสอบและ "หายไป" หมดตอน compile time** — โปรแกรมที่ compile ผ่านแล้ว ไม่มี
ส่วนใดของ binary ที่ต้องคอยตรวจสอบเรื่องนี้อีกต่อไปตอนรัน (runtime) นี่คือความหมายของคำว่า **"zero-cost abstraction"**
ที่กล่าวถึงใน Part 1 — คุณได้ความปลอดภัยแบบเต็มรูปแบบ โดยที่ compiled binary ทำงานเร็วเทียบเท่า C ที่ไม่มีการตรวจสอบใด ๆ เลย

### 6.2 Stack กับ Heap: ทำไม Rust ถึงสนใจเรื่องนี้มากเป็นพิเศษ

ก่อนจะเข้าใจกฎของ ownership เราต้องเข้าใจก่อนว่า memory ของโปรแกรมแบ่งเป็น 2 บริเวณหลักคือ **stack** และ **heap**
ภาษาระดับสูงหลายภาษา (Python, JavaScript) ซ่อนความแตกต่างนี้ไว้จนคุณไม่ต้องรู้เลยก็เขียนโปรแกรมได้ แต่ **Rust ให้คุณ
เห็นความแตกต่างนี้อย่างชัดเจน** เพราะกฎของ ownership เกือบทั้งหมดมีเหตุผลมาจากความแตกต่างระหว่าง stack กับ heap โดยตรง

#### Stack: เร็ว, เป็นระเบียบ, แต่ต้องรู้ขนาดตั้งแต่ compile time

Stack ทำงานแบบ **LIFO (Last In, First Out)** เหมือนกองจานที่วางซ้อนกัน — จานล่าสุดที่วางจะถูกหยิบออกก่อนเสมอ
การขอ ("push") และคืน ("pop") memory บน stack เร็วมาก เพราะ**ไม่ต้องค้นหาที่ว่าง** — ตำแหน่งถัดไปที่จะวางข้อมูลรู้อยู่แล้ว
เสมอ (คือตำแหน่งบนสุดของ stack) แต่ stack มีข้อจำกัดสำคัญ: **ค่าทุกตัวที่เก็บบน stack ต้องมีขนาดคงที่ที่รู้แน่นอนตอน
compile time**

```
STACK (เร็ว, LIFO, ทุกค่าต้องรู้ขนาดตายตัวตอน compile time)
┌──────────────────────┐
│  x: i32  = 5          │  4 bytes  — รู้ขนาดแน่นอน (i32 เท่ากับ 4 bytes เสมอ)
├──────────────────────┤
│  active: bool = true  │  1 byte   — รู้ขนาดแน่นอน (bool เท่ากับ 1 byte เสมอ)
├──────────────────────┤
│  ปุ่ม push/pop ทำงาน  │
│  แค่เลื่อน "ตัวชี้ตำแหน่ง │
│  บนสุด" ขึ้น/ลง ไม่ต้อง│
│  ค้นหาที่ว่างเลย       │
└──────────────────────┘
```

`i32` มีขนาด 4 bytes เสมอไม่ว่าจะเก็บค่าอะไร (ตั้งแต่ `-2147483648` ถึง `2147483647` ก็ใช้ 4 bytes เท่ากันหมด) `bool`
ใช้ 1 byte เสมอ `char` ใช้ 4 bytes เสมอ (ตามที่เรียนใน Part 3) — ชนิดข้อมูลแบบนี้เรียกว่า **fixed-size type** และเก็บบน
stack ได้อย่างมีประสิทธิภาพ

#### Heap: ยืดหยุ่นกว่า แต่ช้ากว่าและวุ่นวายกว่า

ในทางกลับกัน ข้อมูลบางอย่างเรา**ไม่รู้ขนาดล่วงหน้าตอน compile time** เช่น ข้อความ (string) ที่ผู้ใช้พิมพ์เข้ามา
ยาวไม่เท่ากันในแต่ละครั้งที่โปรแกรมรัน หรือรายการสินค้าที่จำนวนเปลี่ยนไปตามข้อมูลจริง สำหรับข้อมูลแบบนี้ Rust (และภาษาอื่น
ส่วนใหญ่) ต้องขอพื้นที่จาก **heap** ซึ่งเป็นบริเวณ memory ที่ใหญ่กว่าและยืดหยุ่นกว่า แต่การขอ ("allocate") ต้องผ่าน
`allocator` ที่ต้อง**ค้นหาพื้นที่ว่างที่มีขนาดพอ** แล้วคืน **pointer** (ตัวเลขที่บอกตำแหน่ง) กลับมาให้ ขั้นตอนนี้ช้ากว่า
การ push ค่าลง stack มาก เพราะต้องทำงานค้นหา/จัดสรรจริง ๆ

```
HEAP (ยืดหยุ่น, ขนาดปรับได้ระหว่างรัน, แต่ต้องขอ/คืนผ่าน allocator — ช้ากว่า stack)

allocator ค้นหาพื้นที่ว่างขนาด 5 bytes ให้ แล้วคืน pointer กลับมา:

              pointer (ตำแหน่ง) ───────────┐
                                            ▼
                                   ┌───┬───┬───┬───┬───┐
                                   │'h'│'e'│'l'│'l'│'o'│   <- ข้อมูลจริงอยู่ตรงนี้
                                   └───┴───┴───┴───┴───┘
```

ข้อมูลที่อยู่บน heap **เข้าถึงได้ผ่าน pointer เท่านั้น** — pointer ตัวนั้น (พร้อมข้อมูลเสริมอย่างความยาวปัจจุบันและ
ความจุ) ถูกเก็บไว้บน stack เพื่อให้ CPU เข้าถึงได้เร็ว ส่วนข้อมูลจริง (ตัวอักษรจริง ๆ) อยู่บน heap — โครงสร้างแบบ
"ตัวชี้อยู่บน stack, ข้อมูลจริงอยู่บน heap" นี่แหละคือกลไกที่ `String` ใช้ ซึ่งเราจะดูรายละเอียดในหัวข้อถัดไปทันที

#### ทำไม heap allocation ถึง "ช้ากว่า" stack จริง ๆ ในทางเทคนิค

เพื่อให้เห็นภาพชัดว่าทำไม Rust ถึงพยายามหลีกเลี่ยงการจัดสรร heap ที่ไม่จำเป็น (และทำไม `.clone()` จึงมีต้นทุนที่
ควรระวัง ตามที่จะเห็นในหัวข้อ 6.7) ลองดูขั้นตอนที่เกิดขึ้นจริงเปรียบเทียบกัน:

- **การ push ค่าลง stack**: CPU แค่เลื่อนค่า "stack pointer" (ตัวเลขที่บอกตำแหน่งบนสุดของ stack ปัจจุบัน) แล้วเขียน
  ข้อมูลลงไปตรงนั้นทันที ใช้เวลาระดับ **1-2 CPU instruction** เท่านั้น ไม่ต้องค้นหาอะไรเลยเพราะตำแหน่งรู้อยู่แล้ว
- **การขอ memory บน heap** (เช่นตอนเรียก `String::from(...)`): ต้องเรียก allocator (เช่น `malloc` ภายใน หรือตัวจัดการ
  memory ของระบบปฏิบัติการ) ซึ่งต้อง (1) ค้นหาว่ามีพื้นที่ว่างขนาดพอในที่ใดบ้าง (2) จองพื้นที่นั้นและปรับปรุงโครงสร้าง
  ข้อมูลภายในของ allocator เพื่อไม่ให้พื้นที่นี้ถูกจ่ายซ้ำให้คนอื่น (3) ถ้าโปรแกรมมีหลาย thread อาจต้องมีการ lock
  เพื่อป้องกัน thread อื่นมาขอ memory พร้อมกัน (4) คืนค่า pointer กลับมา ขั้นตอนนี้ใช้เวลามากกว่าการ push ค่าลง stack
  ได้ตั้งแต่หลายสิบไปจนถึงหลายร้อยเท่า ขึ้นกับสถานะของ heap ในขณะนั้นและว่าโปรแกรม multi-thread หรือไม่

นี่คือเหตุผลเชิงวิศวกรรมที่แท้จริงว่าทำไมโปรแกรมที่จัดสรร/คืน heap memory บ่อย ๆ แบบไม่จำเป็น (เช่นสร้าง `String`
ใหม่ในลูปที่รันนับล้านครั้งทั้ง ๆ ที่ใช้ข้อมูลเดิมซ้ำ ๆ ได้) จะช้ากว่าโปรแกรมที่ออกแบบให้ใช้ stack ให้มากที่สุดและ
จัดสรร heap เท่าที่จำเป็นจริง ๆ — Rust ทำให้ต้นทุนนี้ **มองเห็นได้ชัดในโค้ด** (ทุกจุดที่จัดสรร heap ใหม่จะมีคำสั่งที่
สังเกตได้ เช่น `String::from`, `.clone()`, `Vec::new()` ที่จะเรียนต่อไป) ต่างจากภาษาที่มี GC ซึ่งมักซ่อนการจัดสรร heap
ไว้เบื้องหลัง operator ธรรมดา ๆ จนมองไม่เห็นเลยว่าตรงไหนมีต้นทุนแฝงอยู่บ้าง

#### ทำไมความแตกต่างนี้ถึงสำคัญมากสำหรับ Rust

ภาษาที่มี GC (Python, Java, JavaScript) ซ่อนความแตกต่างนี้ไว้ทั้งหมด — คุณสร้าง object ยังไงก็ได้ ไม่ต้องคิดว่ามันอยู่
ที่ไหนใน memory ระบบ (runtime + GC) จะจัดการให้เอง Rust **เลือกไม่ซ่อน** ความแตกต่างนี้ เพราะกฎของ ownership ที่จะช่วย
ให้ compiler ตรวจสอบความปลอดภัยของ memory ได้โดยไม่ต้องมี GC นั้น **สร้างขึ้นมาจากความรู้เรื่อง stack/heap โดยตรง**:

- ค่าบน **stack** (`i32`, `bool`, `char`, `f64`, tuple ของค่าเหล่านี้) — copy ได้ทันทีแบบไม่มีต้นทุนสูง (แค่ copy
  bytes บน stack ไม่กี่ตัว) จึงไม่จำเป็นต้องมีกฎ ownership ที่เข้มงวดกับมัน — ให้ copy ไปมาได้เลยอย่างอิสระ นี่คือ
  ที่มาของ trait **`Copy`** ที่เราจะเรียนในหัวข้อ 6.8
- ค่าที่มีข้อมูลอยู่บน **heap** (`String` และเกือบทุก collection ที่จะเรียนในโมดูลถัดไป เช่น `Vec<T>`) — การ copy
  ข้อมูลบน heap มีต้นทุนสูงกว่ามาก (ต้องขอ memory ใหม่ + copy ข้อมูลจริงทั้งหมด) จึงต้องมีกฎเข้มงวดว่า **"ใครเป็น
  เจ้าของข้อมูลนี้ ณ เวลาใดเวลาหนึ่ง"** เพื่อให้ระบบรู้แน่ชัดว่าต้องคืน (deallocate) memory ก้อนนี้ตอนไหน โดยไม่คืน
  ซ้ำสองครั้ง (double-free) และไม่ลืมคืนเลย (memory leak) — นี่คือหัวใจของทั้งบทนี้

พูดสั้น ๆ: **Ownership คือระบบที่ Rust สร้างขึ้นมาเพื่อจัดการข้อมูลบน heap ให้ปลอดภัยโดยไม่ต้องมี GC** ส่วนข้อมูลบน
stack อย่าง `i32` ไม่ได้รับผลกระทบจากกฎ ownership มากนัก (เพราะ copy ได้อย่างอิสระอยู่แล้ว) เมื่อคุณเข้าใจภาพนี้แล้ว
กฎทั้งหมดที่จะตามมาจะดูสมเหตุสมผลทันที

### 6.3 `String`: ชนิดข้อมูลที่จัดสรร memory บน heap ตัวแรกที่เราเรียน

จาก Part 3 คุณรู้จัก `&str` มาแล้วในรูปแบบ **string literal** เช่น `"สวัสดี"` — แต่ตอนนั้นเราไม่ได้อธิบายลึกว่ามันคือ
อะไรกันแน่ ตอนนี้ถึงเวลาต้องพูดให้ชัด: `"สวัสดี"` เป็นค่าคงที่ที่**ถูกฝังไว้ในตัวโปรแกรม (binary) ตั้งแต่ตอน compile
เรียบร้อยแล้ว** ไม่สามารถเปลี่ยนขนาดได้เลยตอน runtime (เหมือน `const` ที่เรียนใน Part 3) เพราะ compiler รู้เนื้อหา
และขนาดของมันแน่นอนตั้งแต่ก่อนโปรแกรมรันด้วยซ้ำ

แต่ในความเป็นจริง เรามักต้องการข้อความที่**ขนาดไม่รู้ล่วงหน้า** เช่น ข้อความที่ผู้ใช้พิมพ์เข้ามาทาง keyboard,
ข้อความที่โหลดมาจากไฟล์หรือเครือข่าย, ข้อความที่เราต่อ (concatenate) หลายส่วนเข้าด้วยกันขณะโปรแกรมรัน — string literal
ทำสิ่งเหล่านี้ไม่ได้เลย เพราะขนาดของมันตายตัวแล้วตั้งแต่ compile time ด้วยเหตุนี้ Rust จึงมีชนิดข้อมูลอีกตัวชื่อ
**`String`** ซึ่งเป็นชนิดข้อมูล**owned heap type ตัวแรก**ที่เราเจอในหลักสูตรนี้ — มันจัดสรร buffer ของตัวเองบน heap
และสามารถขยาย/ย่อขนาดได้ระหว่างโปรแกรมทำงาน

```rust
fn main() {
    let greeting: &str = "สวัสดี";                    // string literal: ฝังอยู่ใน binary, ขนาดตายตัว
    let mut owned_greeting: String = String::from("สวัสดี"); // String: จัดสรร buffer บน heap เอง, ขนาดปรับได้

    owned_greeting.push_str(", สบายดีไหมครับ"); // ต่อข้อความเพิ่มได้ เพราะเป็นเจ้าของ buffer บน heap เอง

    println!("literal: {greeting}");
    println!("owned:   {owned_greeting}");
}
```

ผลลัพธ์:

```
literal: สวัสดี
owned:   สวัสดี, สบายดีไหมครับ
```

สังเกตว่า `push_str` (เพิ่มข้อความต่อท้าย) ใช้ได้กับ `owned_greeting` (`String`) เพราะมันมี buffer ของตัวเองบน heap
ที่ขอขนาดเพิ่มได้เมื่อจำเป็น แต่ `greeting` (`&str`) **ไม่มี method นี้เลย** ลองดูว่าเกิดอะไรขึ้นถ้าพยายามเรียก
`push_str` กับ string literal ตรง ๆ:

```rust
fn main() {
    let greeting = "สวัสดี";
    greeting.push_str(", ครับ"); // &str ไม่มี method นี้
    println!("{greeting}");
}
```

จะได้ error:

```
error[E0599]: no method named `push_str` found for reference `&str` in the current scope
 --> src/main.rs:3:14
  |
3 |     greeting.push_str(", ครับ");
  |              ^^^^^^^^ method not found in `&str`
```

นี่ยืนยันว่า `&str` และ `String` เป็น**ชนิดข้อมูลคนละชนิดกันโดยสิ้นเชิง** แม้จะดูคล้ายกันเวลาพิมพ์ (`println!("{}")`
ใช้ได้กับทั้งคู่) แต่มีความสามารถและการจัดการ memory ที่ต่างกันมาก ตารางสรุปเปรียบเทียบ:

| ประเด็น | `&str` (string literal) | `String` (owned heap type) |
|---|---|---|
| อยู่ที่ไหน | ข้อมูลฝังอยู่ใน binary (เรียกว่า "read-only data" ของโปรแกรม) | ข้อมูลจัดสรรบน heap ตอน runtime |
| ขนาด | ตายตัว รู้ตอน compile time | ปรับได้ระหว่างรัน (`push_str`, `push`, `+=`) |
| แก้ไข/ต่อข้อความได้ไหม | ไม่ได้เลย (immutable โดยธรรมชาติ) | ได้ ถ้า binding เป็น `mut` |
| เป็นเจ้าของข้อมูลหรือไม่ | ไม่ (มันคือ**การอ้างอิง**ไปยังข้อมูลที่อยู่ที่อื่น — จะเรียนละเอียดเรื่อง reference ใน Part 7) | เป็น (owned) — เจ้าของ buffer บน heap โดยตรง |
| สร้างยังไง | เขียนข้อความในเครื่องหมายคำพูดตรง ๆ `"..."` | `String::from("...")`, `"...".to_string()`, `String::new()` |

#### วิธีสร้าง `String` มีหลายแบบ — ทั้งหมดคือการจัดสรร heap ใหม่เสมอ

เนื่องจาก `String` เป็นชนิดข้อมูลที่ใช้บ่อยมาก Rust จึงมีหลายวิธีสร้างมันขึ้นมา ทุกวิธีล้วนจัดสรร heap buffer ใหม่
เหมือนกันหมด เพียงแต่สะดวกคนละแบบ:

```rust
fn main() {
    let a = String::from("สวัสดี");      // วิธีที่พบบ่อยที่สุด: แปลงจาก &str ตรง ๆ
    let b = "สวัสดี".to_string();         // เทียบเท่ากับข้างบน แต่เขียนแบบ method call บน &str
    let c = String::new();                // สร้าง String เปล่า (ความยาว 0) แล้วค่อยเติมทีหลังด้วย push_str
    let mut d = String::new();
    d.push_str("สวัสดี");

    println!("{a} {b} {c:?} {d}"); // c คือ "" (string เปล่า) พิมพ์ด้วย {:?} จะเห็นเครื่องหมายคำพูดคู่ว่าง ๆ
}
```

ผลลัพธ์:

```
สวัสดี สวัสดี "" สวัสดี
```

`String::from("...")` และ `"...".to_string()` ทำงานเหมือนกันทุกประการ (ทั้งคู่ implement ผ่าน trait `From<&str>`
และ `ToString` ที่เชื่อมโยงกันอยู่ภายใน — เป็นรายละเอียดเรื่อง trait ที่จะเรียนลึกใน Part 19) เลือกใช้แบบไหนก็ได้ตาม
ความอ่านง่ายในบริบทนั้น ๆ ส่วน `String::new()` เหมาะกับกรณีที่ยังไม่มีข้อความเริ่มต้น แล้วจะค่อย ๆ เติมด้วย `push_str`/
`push` ทีหลัง (เช่น สร้าง buffer เปล่าไว้ก่อนแล้วต่อข้อความในลูป) — ไม่ว่าจะสร้างด้วยวิธีไหน ทุกตัวเป็น**เจ้าของ heap
buffer ของตัวเอง**และปฏิบัติตามกฎ ownership ทั้ง 3 ข้อเหมือนกันหมด

จุดที่สำคัญที่สุดที่ต้องจำไว้ตลอดบทนี้: **`String` คือชนิดข้อมูลแรกในหลักสูตรที่ "เป็นเจ้าของ" ข้อมูลบน heap อย่างแท้จริง**
กฎของ ownership ที่เรากำลังจะเรียนต่อจากนี้ทั้งหมดจะใช้ `String` เป็นตัวอย่างหลัก เพราะมันคือชนิดข้อมูลที่ง่ายที่สุด
ที่แสดงปัญหา (และวิธีแก้) ของการจัดการ heap memory ได้ชัดเจนที่สุด

### 6.4 กฎ 3 ข้อของ Ownership

นี่คือกฎ 3 ข้อที่เป็นรากฐานของทั้งภาษา Rust — จำให้ได้ เพราะทุกอย่างที่เหลือในบทนี้ (และอีกหลายบทข้างหน้า) คือการอธิบาย
ผลลัพธ์ของกฎ 3 ข้อนี้เท่านั้น:

> 1. **ทุกค่า (value) ใน Rust มีตัวแปรที่เป็น "เจ้าของ" (owner) ของมัน**
> 2. **ในเวลาใดเวลาหนึ่ง ค่านั้นมีเจ้าของได้เพียงหนึ่งเดียวเท่านั้น**
> 3. **เมื่อเจ้าของออกจาก scope (ขอบเขตที่มันมีชีวิตอยู่) ค่านั้นจะถูกทำลาย (dropped) โดยอัตโนมัติทันที**

มาดูกฎเหล่านี้ทำงานจริงผ่านโค้ด:

```rust
fn main() {
    // (1) s เป็นเจ้าของ String ที่ถูกสร้างขึ้น — ไม่มีใครอื่นเป็นเจ้าของค่านี้
    let s = String::from("สวัสดีจาก heap");
    println!("{s}");

    // (3) เมื่อ main() จบลง (จบ scope) — s ออกจาก scope
    //     ค่า String ที่ s เป็นเจ้าของจะถูก drop (คืน memory บน heap) โดยอัตโนมัติทันที
    //     ไม่ต้องเรียก free() เอง ไม่ต้องรอ garbage collector
}
```

ผลลัพธ์:

```
สวัสดีจาก heap
```

ดูเผิน ๆ โค้ดนี้เรียบง่ายมาก — แต่สิ่งที่เกิดขึ้น "เบื้องหลัง" ตอนบรรทัดสุดท้ายของ `main()` (ปีกกาปิด `}`) คือกลไกสำคัญ
ที่สุดของ Rust: compiler **แทรกโค้ดคืน memory ให้อัตโนมัติ** ณ จุดที่ `s` ออกจาก scope โดยไม่ต้องให้คุณเขียนอะไรเพิ่ม
เลย และไม่มี garbage collector ตัวไหนมาคอยสแกนหาว่ามันหมดอายุหรือยัง — compiler **รู้แน่นอนตอน compile time** ว่า `s`
จะหมดอายุที่จุดไหน เพราะมันเห็น scope ของ `s` ชัดเจนอยู่ในโค้ด นี่คือหัวข้อถัดไปที่เราจะเจาะลึก

### 6.5 `Drop`: กลไกที่ทำให้กฎข้อ 3 เกิดขึ้นจริง

กระบวนการ "ทำลายค่าเมื่อออกจาก scope" ในกฎข้อ 3 มีชื่อทางเทคนิคว่า **`Drop`** — ทุกชนิดข้อมูลที่เป็นเจ้าของ resource
บางอย่าง (เช่น memory บน heap, file handle, network connection) จะมีโค้ดพิเศษที่ทำงานอัตโนมัติตอนหมดอายุ สำหรับ `String`
โค้ดพิเศษนี้คือการคืน (deallocate) buffer บน heap ที่มันเป็นเจ้าของอยู่

#### ลำดับการ drop: จากในสุดไปนอกสุด และย้อนกลับตามลำดับที่ประกาศ

Rust drop ค่าตาม 2 กฎย่อยที่สำคัญ: **scope ที่ลึกกว่าจะ drop ก่อน scope ที่อยู่ข้างนอก** และ **ภายใน scope เดียวกัน
ตัวแปรจะถูก drop เรียงจากตัวที่ประกาศ "หลังสุด" ไปยัง "ก่อนสุด"** (ย้อนลำดับกับที่สร้าง เหมือนกองจาน LIFO บน stack
ที่เราคุยกันในหัวข้อ 6.2) มาดูตัวอย่าง:

```rust
fn main() {
    let first = String::from("หนึ่ง");
    let second = String::from("สอง");
    let third = String::from("สาม");

    println!("สร้างครบทั้งสามตัวแล้ว");

    // จบ main() — Rust จะ drop ตามลำดับย้อนกลับ: third -> second -> first
}
```

ผลลัพธ์ (จากมุมมองการทำงานจริงเบื้องหลัง แม้เราจะไม่เห็น output ตรง ๆ เพราะ `String` ไม่พิมพ์อะไรตอน drop):

```
สร้างครบทั้งสามตัวแล้ว
```

เพื่อให้ "เห็น" ลำดับการ drop จริง ๆ ด้วยตา เราต้องมีวิธีสั่งให้พิมพ์ข้อความตอนค่าถูก drop — ใน Rust ทำได้โดยการ
implement trait ชื่อ `Drop` ให้กับชนิดข้อมูลของเราเอง (การสร้างชนิดข้อมูลของตัวเองด้วย `struct` จะเรียนแบบเต็มรูปแบบ
ใน **Part 9** ตอนนี้ให้มองโค้ดด้านล่างเป็นแค่ "กล่อง" ที่ห่อ `String` ไว้ข้างในเพื่อสาธิตเรื่อง `Drop` เท่านั้น
ไม่ต้องเข้าใจ syntax `struct`/`impl` ทั้งหมดตอนนี้):

```rust
struct Announcer(String); // "กล่อง" ที่ห่อ String ไว้ข้างใน (จะเรียน struct เต็มรูปแบบใน Part 9)

impl Drop for Announcer {
    // method นี้จะถูกเรียกโดย Rust โดยอัตโนมัติ ตอนค่าตัวนี้ออกจาก scope
    // เราไม่เคยเรียก .drop() เองตรง ๆ ด้วยมือ — Rust ห้ามเรียกเองด้วยซ้ำ
    fn drop(&mut self) {
        println!("กำลังทำลาย: {}", self.0);
    }
}

fn main() {
    let _first = Announcer(String::from("หนึ่ง"));
    let _second = Announcer(String::from("สอง"));
    let _third = Announcer(String::from("สาม"));

    println!("สร้างครบทั้งสามตัวแล้ว กำลังจะออกจาก main()...");

    // จบ main() ตรงนี้ — สังเกตลำดับการพิมพ์ที่จะเกิดขึ้นด้านล่าง
}
```

ผลลัพธ์:

```
สร้างครบทั้งสามตัวแล้ว กำลังจะออกจาก main()...
กำลังทำลาย: สาม
กำลังทำลาย: สอง
กำลังทำลาย: หนึ่ง
```

เห็นชัดเจนว่าลำดับการ drop คือ **third → second → first** ย้อนกลับกับลำดับที่ประกาศเป๊ะ ๆ (คล้ายการหยิบจานออกจาก
กองจานที่ซ้อนกันอยู่ — จานที่วางล่าสุดจะถูกหยิบออกก่อน) นี่ไม่ใช่เรื่องบังเอิญ — มันคือกฎที่ Rust การันตีเสมอ ทำให้
พฤติกรรมของโปรแกรมคาดเดาได้แน่นอน 100% ต่างจาก garbage collector ที่คุณไม่รู้เลยว่า object จะถูกเก็บกวาดตอนไหน

**ข้อสังเกตสำคัญเรื่อง `_` นำหน้าชื่อตัวแปร**: เราตั้งชื่อ `_first`, `_second`, `_third` (มี underscore นำหน้า)
เพราะในตัวอย่างนี้เราไม่ได้ "ใช้" ตัวแปรเหล่านี้เลยหลังจากสร้าง (ไม่มีการอ่านค่าออกมาใช้ต่อ) — ถ้าตั้งชื่อธรรมดาไม่มี
`_` นำหน้า `cargo clippy`/`rustc` จะเตือน `unused variable` เพราะมองว่าเราอาจสร้างตัวแปรมาผิดโดยไม่ตั้งใจ การใส่ `_`
นำหน้าคือวิธีบอก compiler อย่างชัดเจนว่า "ฉันตั้งใจไม่ใช้ตัวแปรนี้ แต่ต้องการให้มันมีชีวิตอยู่จนจบ scope" (ต่างจากการ
ตั้งชื่อเป็น `_` เดี่ยว ๆ ซึ่งจะทำให้ค่าถูก drop **ทันที** ในบรรทัดนั้นเลย ไม่รอจนจบ scope — เป็นรายละเอียดเล็ก ๆ ที่
ควรรู้ไว้)

**สำคัญ**: คุณจะไม่ได้เขียน `impl Drop` บ่อยเลยในการเขียนโปรแกรม Rust ทั่วไป (ชนิดข้อมูลจากมาตรฐาน library เช่น
`String`, `Vec<T>`, `File` implement มันให้คุณเรียบร้อยแล้ว) ตัวอย่างข้างบนมีไว้เพื่อ**สาธิตให้เห็นว่ากลไกการ drop
มีอยู่จริงและทำงานตอนไหนแน่ ๆ** เท่านั้น เราจะเรียนวิธีสร้าง `struct` และ `impl` แบบเต็มรูปแบบใน Part 9 — ตอนนี้ให้
จำแค่ใจความสำคัญ: **ทุกค่าที่เป็นเจ้าของ resource (memory, file, connection) จะมีโค้ดคืน resource ทำงานอัตโนมัติทันที
ตอนออกจาก scope เสมอ ไม่มีข้อยกเว้น** และนี่คือสิ่งที่ทำให้ Rust ไม่มี memory leak แบบที่เกิดจาก "ลืม free" ได้เลย
(ยกเว้นกรณีพิเศษมาก ๆ ที่ตั้งใจทำ เช่น `std::mem::forget` ซึ่งไม่ใช่เรื่องที่ต้องกังวลตอนนี้)

#### สั่ง drop ก่อนเวลาได้ด้วยฟังก์ชัน `drop()`

บางครั้งคุณอาจต้องการคืน resource ของค่าหนึ่ง**ก่อน**ที่มันจะหมด scope ตามธรรมชาติ (เช่น ต้องการปิด file handle
ให้เร็วที่สุดก่อนเปิดไฟล์อื่นในฟังก์ชันเดียวกัน) Rust มีฟังก์ชันชื่อ `drop()` อยู่ใน prelude (เรียกใช้ได้ทันทีโดยไม่ต้อง
`use` อะไรเพิ่ม) ที่รับกรรมสิทธิ์ของค่าเข้าไปแล้ว "ไม่ทำอะไรเลยนอกจากปล่อยให้มันถูก drop ทันที":

```rust
struct Announcer(String);

impl Drop for Announcer {
    fn drop(&mut self) {
        println!("กำลังทำลาย: {}", self.0);
    }
}

fn main() {
    let a = Announcer(String::from("ข้อมูลชั่วคราว"));
    println!("ก่อนสั่ง drop");
    drop(a); // สั่งให้ a หมดอายุทันที ไม่ต้องรอจนจบ scope ของ main
    println!("หลังสั่ง drop — a ใช้ต่อไม่ได้แล้ว");
}
```

ผลลัพธ์:

```
ก่อนสั่ง drop
กำลังทำลาย: ข้อมูลชั่วคราว
หลังสั่ง drop — a ใช้ต่อไม่ได้แล้ว
```

สังเกตว่าข้อความ "กำลังทำลาย" พิมพ์ออกมา**ทันทีที่เรียก `drop(a)`** ไม่ใช่ตอนจบ `main()` — เพราะ `drop()` รับ `a`
เข้าไปแบบ by-value (โอนกรรมสิทธิ์เข้าไปในฟังก์ชัน) แล้วตัวมันเองก็จบ scope ทันทีในบรรทัดนั้น ทำให้ `a` (ในชื่อใหม่
ภายในฟังก์ชัน `drop`) ถูก drop ไปพร้อมกัน — ถ้าคุณพยายามใช้ `a` อีกหลังบรรทัดนี้จะได้ error `E0382` แบบเดียวกับที่
เราเห็นมาตลอดบทนี้ เพราะโดยแท้จริงแล้ว `drop(a)` ก็คือการส่งค่าเข้าฟังก์ชันแบบธรรมดาที่เรียนในหัวข้อ 6.9 นั่นเอง
เพียงแต่ฟังก์ชันนี้ไม่ทำอะไรกับค่าที่รับมาเลยนอกจากปล่อยให้มันหมดอายุ

**ข้อสำคัญที่ควรรู้**: คุณเรียก `a.drop()` (method call ตรง ๆ) ด้วยตัวเอง**ไม่ได้เด็ดขาด** แม้ว่า `Announcer` จะมี
method ชื่อ `drop` อยู่จริงก็ตาม (จาก `impl Drop for Announcer { fn drop(&mut self) { ... } }`) ลองดู:

```rust
fn main() {
    let a = Announcer(String::from("ทดสอบ"));
    a.drop(); // พยายามเรียก destructor เอง
}

struct Announcer(String);
impl Drop for Announcer {
    fn drop(&mut self) {
        println!("กำลังทำลาย: {}", self.0);
    }
}
```

จะได้ error:

```
error[E0040]: explicit use of destructor method
 --> src/main.rs:3:7
  |
3 |     a.drop();
  |       ^^^^ explicit destructor calls not allowed
  |
help: consider using `drop` function
  |
3 -     a.drop();
3 +     drop(a);
  |
```

Rust ห้ามเรียก `.drop()` ตรง ๆ เพราะจะทำให้เกิดความเสี่ยง**double-drop** ได้ (เรียก destructor เอง แล้ว Rust ก็ยัง
จะพยายามเรียกมันอีกครั้งตอนจบ scope ตามปกติ กลายเป็นการคืน resource ซ้ำสอง) วิธีที่ถูกต้องเพียงทางเดียวคือใช้ฟังก์ชัน
`drop()` จาก prelude อย่างที่แสดงไว้ข้างบน ซึ่ง compiler รู้วิธีจัดการให้ปลอดภัยเสมอ (มันแค่โอนกรรมสิทธิ์เข้าไปเป็น
พารามิเตอร์ ทำให้ scope ปิดตามธรรมชาติ ไม่ใช่การเรียก destructor ตรง ๆ)

### 6.6 Move Semantics: เมื่อการกำหนดค่าไม่ใช่การ copy เสมอไป

ตอนนี้เรามาถึงหัวใจสำคัญที่สุดของบทนี้ ในภาษาส่วนใหญ่ที่คุณอาจคุ้นเคย เมื่อเขียน `let b = a;` คุณอาจคาดหวังว่า `b`
จะเป็น "สำเนา" ของ `a` (ถ้าเป็นค่าพื้นฐาน) หรือ `a`/`b` จะ "ชี้ไปที่ object เดียวกัน" (ถ้าเป็น object ในภาษาที่มี GC
เช่น Python/JavaScript) แต่ Rust ทำงานแบบที่สามที่คุณอาจไม่เคยเจอมาก่อน — เรียกว่า **move**

ลองดูตัวอย่างนี้ก่อน:

```rust
fn main() {
    let s1 = String::from("hello");
    let s2 = s1;

    println!("{s1}, world!"); // จะเกิดอะไรขึ้น?
}
```

ถ้าคุณเคยเขียน Python มาก่อน คุณอาจคิดว่านี่คือการให้ `s1` กับ `s2` ชี้ไปยัง string เดียวกัน แล้ว `println!` ก็ควร
พิมพ์ `hello, world!` ได้ตามปกติ — แต่โค้ดนี้ **compile ไม่ผ่านเลย!** ได้ error:

```
error[E0382]: borrow of moved value: `s1`
 --> src/main.rs:4:15
  |
2 |     let s1 = String::from("hello");
  |         -- move occurs because `s1` has type `String`, which does not implement the `Copy` trait
3 |     let s2 = s1;
  |              -- value moved here
4 |     println!("{s1}, world!");
  |               ^^^^ value borrowed here after move
```

เกิดอะไรขึ้นกันแน่? มาดูโครงสร้างของ `String` ให้ละเอียดขึ้น — จากหัวข้อ 6.2 เราบอกว่า `String` เก็บ pointer/length/
capacity ไว้บน stack และข้อมูลจริง (ตัวอักษร) อยู่บน heap โดยละเอียด `String` บนเครื่อง 64-bit มีขนาด 24 bytes บน
stack (ptr 8 bytes + len 8 bytes + capacity 8 bytes) ก่อนบรรทัด `let s2 = s1;` สถานะของ memory เป็นแบบนี้:

```
ก่อน let s2 = s1;

s1  ┌───────────────┐
    │ ptr  ─────────┼──────┐
    │ len  = 5      │      │
    │ cap  = 5      │      ▼
    └───────────────┘   ┌───┬───┬───┬───┬───┐
     (บน stack)          │'h'│'e'│'l'│'l'│'o'│  (บน heap)
                          └───┴───┴───┴───┴───┘
```

ตอนรัน `let s2 = s1;` — Rust **copy** ข้อมูลสามช่อง (ptr, len, cap) จาก `s1` ไปยัง `s2` เท่านั้น (การ copy 24 bytes
บน stack เร็วมาก แทบไม่มีต้นทุน) แต่ **ไม่ได้ copy ข้อมูลจริงบน heap เลย** ผลลัพธ์คือทั้ง `s1` และ `s2` จะชี้ไปยัง
buffer เดียวกันบน heap ชั่วขณะหนึ่ง:

```
ทันทีหลัง copy ptr/len/cap (ก่อนที่ Rust จะ invalidate s1)

s1  ┌───────────────┐
    │ ptr  ─────────┼──────┐
    │ len  = 5      │      │
    │ cap  = 5      │      ▼
    └───────────────┘   ┌───┬───┬───┬───┬───┐
                          │'h'│'e'│'l'│'l'│'o'│  (บน heap)
                          └───┴───┴───┴───┴───┘
s2  ┌───────────────┐      ▲
    │ ptr  ─────────┼──────┘
    │ len  = 5      │
    │ cap  = 5      │
    └───────────────┘
```

ถ้า Rust หยุดอยู่แค่นี้ นี่จะกลายเป็นปัญหาใหญ่ทันที: เมื่อ `s1` และ `s2` ออกจาก scope ทั้งคู่จะพยายาม drop (คืน)
buffer เดียวกันบน heap **ซ้ำสองครั้ง** — นี่คือ **double-free** ที่เราพูดถึงในหัวข้อ 6.1 ว่าเป็นบั๊กร้ายแรงใน C/C++!

Rust แก้ปัญหานี้ด้วยกฎข้อ 2 ของ ownership ("ค่าหนึ่งมีเจ้าของได้เพียงหนึ่งเดียวในเวลาใดเวลาหนึ่ง") อย่างเข้มงวด:
ทันทีที่ `let s2 = s1;` เกิดขึ้น Rust จะถือว่า **`s1` ถูก "ย้าย" (moved) กรรมสิทธิ์ไปให้ `s2` แล้ว** และ **`s1` จะถูก
compiler ทำให้ใช้งานต่อไม่ได้อีกเลย** (เรียกว่า `s1` ถูก invalidate) — นี่ไม่ใช่แค่ "convention" หรือ "คำแนะนำ" แต่
เป็นกฎที่ compiler **บังคับตรวจสอบจริง** ถ้าคุณพยายามใช้ `s1` อีกหลัง move จะ compile ไม่ผ่านทันที (อย่างที่เห็นใน
error ด้านบน) สถานะหลังการ move จริง ๆ คือ:

```
หลัง move เสร็จสมบูรณ์

s1  (invalid — compiler ห้ามใช้งานต่อ ไม่มีตัวตนอีกต่อไปในทางตรรกะของ ownership)

s2  ┌───────────────┐
    │ ptr  ─────────┼──────┐
    │ len  = 5      │      │
    │ cap  = 5      │      ▼
    └───────────────┘   ┌───┬───┬───┬───┬───┐
                          │'h'│'e'│'l'│'l'│'o'│  (บน heap — ตอนนี้มี s2 เป็นเจ้าของเพียงผู้เดียว)
                          └───┴───┴───┴───┴───┘
```

ตอนนี้มีเจ้าของ buffer นี้เพียงหนึ่งเดียวคือ `s2` เท่านั้น (ตรงตามกฎข้อ 2 เป๊ะ ๆ) เมื่อ `s2` ออกจาก scope จะมีการ drop
เกิดขึ้น**เพียงครั้งเดียว** ไม่มีทางเกิด double-free ได้เลย — และสิ่งทั้งหมดนี้ **compiler ตรวจสอบและบังคับให้ตอน
compile time โดยไม่มี runtime cost ใด ๆ เลย** ไม่ต้องมีตัวนับ reference (reference counting) หรือ garbage collector
มาคอยดูแลตอนโปรแกรมรันจริงแต่อย่างใด

#### แก้ error: ใช้ `s2` แทน หรือจะ clone ก็ได้ (หัวข้อถัดไป)

วิธีแก้ error ด้านบนตรงไปตรงมาที่สุดคือใช้ `s2` (เจ้าของปัจจุบัน) แทน `s1` (ที่ถูก move ไปแล้ว):

```rust
fn main() {
    let s1 = String::from("hello");
    let s2 = s1; // s1 ถูก move เข้า s2 แล้ว

    println!("{s2}, world!"); // ใช้ s2 ซึ่งเป็นเจ้าของตัวจริงในตอนนี้
}
```

ผลลัพธ์:

```
hello, world!
```

โค้ดนี้ compile ผ่านสบาย ๆ เพราะเราใช้ `s2` (เจ้าของปัจจุบันของค่านั้น) ไม่ใช่ `s1` (ที่ถูก move ไปแล้วและไม่มีตัวตน
อีกต่อไปในทางตรรกะของ ownership) ถ้าคุณต้องการให้ทั้ง `s1` และ `s2` ใช้งานได้พร้อมกันจริง ๆ (คือต้องการสอง**สำเนา**
ที่เป็นอิสระจากกัน) คุณต้องขอ Rust ทำ deep copy อย่างชัดเจน ซึ่งคือหัวข้อถัดไปพอดี

#### เกร็ดสำหรับผู้มีพื้นฐาน C++: Move ใน Rust ต่างจาก `std::move` ใน C++ อย่างไร

ถ้าคุณเคยเขียน C++11 ขึ้นไปมาก่อน คุณอาจรู้จัก **move semantics** ของ C++ ผ่าน `std::move` อยู่แล้ว และอาจสงสัยว่า
Rust ทำสิ่งเดียวกันหรือไม่ — คำตอบคือ **แนวคิดคล้ายกันมาก แต่การบังคับใช้ต่างกันโดยสิ้นเชิง** ซึ่งเป็นความต่างที่สำคัญ
มากพอจะเข้าใจไว้:

| ประเด็น | C++ (`std::move`) | Rust (move อัตโนมัติ) |
|---|---|---|
| เกิดขึ้นเมื่อไหร่ | ต้องขอเองผ่าน `std::move(x)` (เป็นแค่การ cast บอก compiler ว่า "อนุญาตให้ move ได้") | เกิดอัตโนมัติทุกครั้งที่ assign/ส่งค่าที่ไม่ใช่ `Copy` โดยไม่ต้องเขียนอะไรเพิ่ม |
| ตัวแปรต้นทางหลัง move | ยังใช้งานได้ต่อ! อยู่ในสถานะ **"valid but unspecified"** (compiler ไม่ห้ามใช้ แต่ผลลัพธ์ไม่รับประกัน ขึ้นกับว่า move constructor ของ type นั้นเขียนไว้ยังไง) | **compiler ปฏิเสธการใช้งานทันที** (compile error `E0382`) — ไม่มีทางพลาดใช้ค่าที่ moved ไปแล้วได้เลย |
| ตรวจสอบโดยใคร | ไม่มีการตรวจสอบอัตโนมัติ — ขึ้นกับดุลยพินิจและวินัยของโปรแกรมเมอร์ | Borrow checker ของ `rustc` ตรวจสอบให้ทุกครั้ง ไม่มีข้อยกเว้น |
| ความเสี่ยงที่เหลืออยู่ | ใช้ตัวแปรหลัง move โดยไม่ตั้งใจ (แม้จะไม่ crash แต่ได้ผลลัพธ์ที่ไม่คาดคิด — เป็นบั๊กเชิง logic ที่หาสาเหตุยาก) | ไม่มีเลย — compile ไม่ผ่านตั้งแต่แรกถ้าพลาด |

พูดให้เจาะจงกว่านั้น: ใน C++ การ move คือ**สัญญาทางสังคม** (โปรแกรมเมอร์ "สัญญา" ว่าจะไม่ใช้ตัวแปรต้นทางในสถานะที่มี
ความหมายอีกหลัง move — แต่ compiler ไม่ตรวจสอบสัญญานี้ให้) ส่วนใน Rust การ move คือ**กฎที่ compiler บังคับจริง**
ผ่านระบบ type และ borrow checker — คุณไม่มีทาง "พลาด" ใช้ค่าที่ moved ไปแล้วได้เลยแม้แต่ครั้งเดียว เพราะโปรแกรมจะ
compile ไม่ผ่านตั้งแต่ต้น นี่คือตัวอย่างที่ดีที่สุดอย่างหนึ่งที่แสดงปรัชญาของ Rust: **แปลงสิ่งที่ภาษาอื่นทำได้แค่
"เตือนด้วยเอกสาร/convention" ให้กลายเป็น "กฎที่ compiler ตรวจสอบจริงทางคณิตศาสตร์"**

### 6.7 `Clone`: เมื่อคุณต้องการสำเนาจริง ๆ บน heap

ถ้าคุณต้องการให้ `s1` ยังใช้งานได้อยู่ **พร้อมกับ** `s2` ที่มีข้อมูลเหมือนกัน คุณต้องขอให้ Rust จัดสรร buffer ใหม่
บน heap แล้ว copy ข้อมูลจริงลงไปทั้งหมด — เรียกว่า **deep copy** ทำได้ผ่าน method `.clone()`:

```rust
fn main() {
    let s1 = String::from("hello");
    let s2 = s1.clone(); // ขอสำเนาแยกต่างหากบน heap อย่างชัดเจน

    println!("s1 = {s1}, s2 = {s2}"); // ใช้งานได้ทั้งคู่ เพราะเป็นเจ้าของข้อมูลของตัวเองแยกกัน
}
```

ผลลัพธ์:

```
s1 = hello, s2 = hello
```

หลังเรียก `.clone()` สถานะของ memory จะกลายเป็น:

```
s1  ┌───────────────┐
    │ ptr  ─────────┼──────┐
    │ len  = 5      │      │
    │ cap  = 5      │      ▼
    └───────────────┘   ┌───┬───┬───┬───┬───┐
                          │'h'│'e'│'l'│'l'│'o'│  (heap allocation #1 — เป็นของ s1 คนเดียว)
                          └───┴───┴───┴───┴───┘

s2  ┌───────────────┐
    │ ptr  ─────────┼──────┐
    │ len  = 5      │      │
    │ cap  = 5      │      ▼
    └───────────────┘   ┌───┬───┬───┬───┬───┐
                          │'h'│'e'│'l'│'l'│'o'│  (heap allocation #2 — เป็นของ s2 คนเดียว, คนละก้อนกับ s1)
                          └───┴───┴───┴───┴───┘
```

สังเกตว่าตอนนี้มี**สอง heap allocation แยกกันโดยสิ้นเชิง** — ไม่ใช่การชี้ไปที่ก้อนเดียวกันแบบตอนก่อน move อีกต่อไป
`s1` และ `s2` เป็นอิสระจากกันเต็มที่ 100% ถ้าคุณแก้ไข `s2` ในอนาคต (สมมติประกาศเป็น `mut`) `s1` จะไม่ได้รับผลกระทบ
เลยแม้แต่นิดเดียว เพราะมันคือข้อมูลคนละก้อนกันจริง ๆ ไม่ใช่แค่ pointer สองตัวที่ชี้ไปที่เดียวกัน

#### ทำไม Rust ทำให้ `.clone()` ต้องเรียกอย่างชัดเจนเสมอ

นี่คือจุดออกแบบที่สำคัญมากของ Rust: **การ copy ข้อมูลจริงบน heap (deep copy) จะไม่เกิดขึ้นเองโดยอัตโนมัติเด็ดขาด**
คุณต้องเรียก `.clone()` ด้วยตัวเองเสมอ ต่างจากภาษาที่มี GC บางภาษาที่อาจซ่อนการ copy ไว้เบื้องหลัง operator บางตัว
โดยที่คุณไม่รู้ตัว เหตุผลมี 2 ข้อหลัก:

1. **ต้นทุนด้านประสิทธิภาพที่มองเห็นได้ (visible cost)** — การ deep copy string ยาว 1 ล้านตัวอักษรใช้เวลาและ memory
   มากกว่าการ copy pointer 3 ตัว (24 bytes) อย่างเทียบกันไม่ได้เลย Rust ต้องการให้**ทุกครั้งที่มีต้นทุนสูงแบบนี้เกิดขึ้น
   ต้องปรากฏชัดเจนในโค้ดด้วยคำว่า `.clone()`** เพื่อให้คนอ่านโค้ด (รวมถึงตัวคุณเองในอนาคต) รู้ทันทีว่าตรงนี้มีการ
   จัดสรร memory ใหม่และ copy ข้อมูลจริงเกิดขึ้น ไม่ใช่แค่การ copy ตัวเลขไม่กี่ตัวแบบที่เกิดกับ `i32`
2. **ป้องกันบั๊กจากการเข้าใจผิดเรื่อง aliasing** — ถ้า assignment ธรรมดา (`let s2 = s1;`) ทำ deep copy ให้อัตโนมัติเสมอ
   คุณจะไม่มีวิธีบอกได้เลยจากการอ่านโค้ดว่า "ตรงนี้ใช้ข้อมูลเดียวกันกับตัวแปรอื่นอยู่หรือไม่" (aliasing) การที่ Rust
   เลือก move เป็นพฤติกรรม default (แทน copy) และให้ `.clone()` เป็นสิ่งที่ต้องขอเอง ทำให้กฎ "ค่าหนึ่งมีเจ้าของเดียว
   เสมอ" (กฎข้อ 2) ยังคงเป็นจริงเสมอในทุกจุดของโปรแกรมโดยไม่ต้องมีข้อยกเว้น

**คำแนะนำเชิงปฏิบัติ**: `.clone()` ไม่ใช่สิ่งเลวร้ายที่ต้องหลีกเลี่ยงเสมอไป — ในโค้ดจริงจำนวนมาก การ clone string
สั้น ๆ ไม่กี่สิบตัวอักษรแทบไม่มีผลต่อประสิทธิภาพเลย และบางครั้งการ clone ก็เป็นวิธีที่ **ง่ายและถูกต้องที่สุด**
ในการเขียนโค้ดให้ทำงานได้ก่อน แล้วค่อยไปปรับปรุงประสิทธิภาพทีหลังถ้าจำเป็นจริง ๆ (มี mantra ในวงการ Rust ว่า
**"clone to make it compile, optimize later if it matters"**) แต่สำหรับข้อมูลขนาดใหญ่ (เช่น string ยาวหลายพัน/หมื่น
ตัวอักษร, collection ที่มีสมาชิกจำนวนมาก) หรือเมื่อเรียกในลูปที่รันซ้ำนับล้านครั้ง การ clone พร่ำเพรื่อก็สร้าง
ปัญหาด้านประสิทธิภาพได้จริง — วิธีแก้ปัญหานี้แบบสมบูรณ์ (ไม่ต้อง clone แต่ยังใช้ข้อมูลร่วมกันได้อย่างปลอดภัย) คือ
**Borrowing** ซึ่งเป็นเนื้อหาหลักของ **Part 7** ถัดไป

### 6.8 `Copy` Trait: ทำไม `i32`, `bool`, `char`, `f64` ไม่ต้อง move

กลับไปที่หัวข้อ 6.2 — เราบอกว่าค่าที่อยู่บน stack ทั้งหมด (ไม่มีส่วนใดอยู่บน heap) copy ได้อย่างอิสระโดยไม่มีความเสี่ยง
เรื่อง double-free เลย เพราะไม่มี heap resource ใด ๆ ที่ต้องกังวลว่าใครเป็นเจ้าของ ลองเทียบโค้ดนี้กับตัวอย่าง `String`
ก่อนหน้าดู:

```rust
fn main() {
    let x = 5;
    let y = x; // นี่คือการ COPY ไม่ใช่ move!

    println!("x = {x}, y = {y}"); // ใช้ทั้งสองตัวได้ปกติ ไม่มี error!
}
```

ผลลัพธ์:

```
x = 5, y = 5
```

โค้ดนี้ **compile ผ่านโดยไม่มีปัญหาใด ๆ เลย** ต่างจากตัวอย่าง `String` ในหัวข้อ 6.6 อย่างสิ้นเชิง แม้ทั้งสองตัวอย่าง
จะเขียนด้วยรูปแบบ syntax เดียวกันเป๊ะ (`let b = a;`) ทำไมถึงเป็นแบบนี้?

คำตอบคือ `i32` implement **trait ชื่อ `Copy`** (จะเรียนเรื่อง trait แบบเต็มรูปแบบใน Part 19 แต่ตอนนี้ให้เข้าใจแค่ว่า
มันคือ "ป้ายกำกับ" ที่บอก compiler ว่าชนิดข้อมูลนี้ปฏิบัติแบบไหน) เมื่อชนิดข้อมูลใด implement `Copy` แล้ว การเขียน
`let y = x;` จะไม่ทำให้ `x` ถูก invalidate อีกต่อไป — Rust จะ **copy ค่าไปเลยแบบตรงไปตรงมา ทั้ง `x` และ `y` ใช้งานได้
อย่างเป็นอิสระจากกันต่อไปโดยไม่ต้อง move**

#### เปรียบเทียบแบบเคียงข้างกัน: `String` (move) vs `i32` (copy)

```rust
fn main() {
    // --- String: ไม่ implement Copy ---
    let s1 = String::from("hello");
    let s2 = s1; // s1 ถูก MOVE เข้า s2 -> s1 ใช้ต่อไม่ได้แล้ว

    // --- i32: implement Copy ---
    let n1 = 5;
    let n2 = n1; // n1 ถูก COPY เข้า n2 -> n1 ยังใช้ต่อได้ปกติ!

    // println!("{s1}"); // ผิด! จะได้ E0382 borrow of moved value
    println!("{s2}");     // OK

    println!("{n1}");     // OK — n1 ยังใช้ได้ปกติ เพราะแค่ถูก copy ไม่ใช่ move
    println!("{n2}");     // OK
}
```

ผลลัพธ์:

```
hello
5
5
```

ชนิดข้อมูลที่ implement `Copy` ในหลักสูตรจนถึงตอนนี้ (ที่เรียนมาแล้วใน Part 3) ได้แก่:

| ชนิดข้อมูล | Implement `Copy`? | เหตุผล |
|---|---|---|
| `i8`, `i16`, `i32`, `i64`, `i128`, `isize` | ใช่ | ทุกตัวเป็นตัวเลขขนาดคงที่บน stack |
| `u8`, `u16`, `u32`, `u64`, `u128`, `usize` | ใช่ | เช่นเดียวกับข้างบน |
| `f32`, `f64` | ใช่ | ตัวเลขทศนิยมขนาดคงที่บน stack |
| `bool` | ใช่ | 1 byte บน stack |
| `char` | ใช่ | 4 bytes บน stack เสมอ |
| Tuple ที่สมาชิก**ทุกตัว**เป็น `Copy` เช่น `(i32, bool)`, `(f64, f64, char)` | ใช่ | Tuple เป็น `Copy` ก็ต่อเมื่อสมาชิกทุกตัวเป็น `Copy` |
| `String` | **ไม่** | เป็นเจ้าของ buffer บน heap ที่ต้อง deallocate ตอน drop |

ตัวอย่าง tuple ที่เป็น `Copy` เพราะสมาชิกทุกตัวเป็น `Copy`:

```rust
fn main() {
    let point1 = (3, 5.5, true); // (i32, f64, bool) — ทุกสมาชิกเป็น Copy
    let point2 = point1;          // copy ทั้ง tuple ได้เลย ไม่ move

    println!("point1 = {:?}", point1); // ใช้ได้ปกติ
    println!("point2 = {:?}", point2);
}
```

ผลลัพธ์:

```
point1 = (3, 5.5, true)
point2 = (3, 5.5, true)
```

แต่ถ้า tuple มีสมาชิกที่ไม่เป็น `Copy` แม้แต่ตัวเดียว (เช่น `String`) ทั้ง tuple จะไม่เป็น `Copy` ทันที และจะเกิด move
ทั้ง tuple:

```rust
fn main() {
    let mixed1 = (3, String::from("สาม")); // (i32, String) — มี String อยู่ ไม่เป็น Copy
    let mixed2 = mixed1; // ทั้ง tuple ถูก move

    println!("{:?}", mixed2); // OK
    println!("{:?}", mixed1); // ผิด! mixed1 ถูก move ไปแล้วทั้งก้อน (แม้ตัวเลข 3 จะเป็น Copy ก็ตาม)
}
```

จะได้ error:

```
error[E0382]: borrow of moved value: `mixed1`
 --> src/main.rs:6:22
  |
2 |     let mixed1 = (3, String::from("สาม"));
  |         ------ move occurs because `mixed1` has type `(i32, String)`, which does not implement the `Copy` trait
3 |     let mixed2 = mixed1;
  |                  ------ value moved here
...
6 |     println!("{:?}", mixed1);
  |                       ^^^^^^ value borrowed here after move
```

จุดสำคัญที่ต้องจำ: **`Copy` เป็นสมบัติของ "ทั้งชนิดข้อมูล" ไม่ใช่สมบัติที่แยกเป็นส่วน ๆ** — tuple/struct จะเป็น `Copy`
ได้ก็ต่อเมื่อ**ทุกส่วนประกอบ**เป็น `Copy` ทั้งหมด แม้จะมีแค่ส่วนเดียวที่ไม่เป็น `Copy` (เช่น `String` แม้จะอยู่แค่
ตำแหน่งเดียวใน tuple ที่มีสมาชิก 5 ตัว) ทั้งก้อนจะไม่เป็น `Copy` ทันที

#### ทำไม `Copy` และ `Clone` ถึงไม่เหมือนกัน (แม้ทำงานคล้ายกัน)

`Copy` กับ `Clone` (จากหัวข้อ 6.7) ดูคล้ายกันเพราะทั้งคู่ "ทำสำเนา" แต่ต่างกันในสาระสำคัญ:

| ประเด็น | `Copy` | `Clone` |
|---|---|---|
| เรียกยังไง | อัตโนมัติ — ไม่มี syntax พิเศษ (`let y = x;` ก็ copy ให้แล้ว) | ต้องเรียก `.clone()` ด้วยตัวเองเสมอ |
| ต้นทุน (cost) | ต่ำมากเสมอ (copy bytes ไม่กี่ตัวบน stack) | อาจสูงมาก (จัดสรร heap ใหม่ + copy ข้อมูลจริงทั้งหมด) |
| ใช้กับชนิดข้อมูลแบบไหน | เฉพาะข้อมูลที่อยู่บน stack ทั้งหมด ไม่มีส่วนใดจัดการ heap resource | ใช้ได้กับทุกชนิดข้อมูล (รวมถึงที่มี heap resource ด้วย) |
| มองเห็นในโค้ดหรือไม่ | มองไม่เห็น (implicit) — เกิดขึ้นเองแบบเงียบ ๆ | มองเห็นชัดเจน (explicit) — มีคำว่า `.clone()` ปรากฏในโค้ดเสมอ |

ทุกชนิดข้อมูลที่เป็น `Copy` จะเป็น `Clone` ด้วยเสมอ (เพราะ `Copy` เป็น "subset" พิเศษของ `Clone` ที่บอกว่า "การ clone
มันถูกเหมือน copy ธรรมดา ไม่มีต้นทุนแฝง") แต่ในทางกลับกันไม่จริง — `String` เป็น `Clone` (เรียก `.clone()` ได้)
แต่ **ไม่เป็น `Copy`** เพราะการ "copy" มันมีต้นทุนที่ซ่อนไม่ได้ (ต้องจัดสรร heap ใหม่) Rust จึงบังคับให้ต้นทุนแบบนี้
ต้องปรากฏชัดในโค้ดผ่าน `.clone()` เสมอ ไม่ยอมให้เกิดแบบเงียบ ๆ ผ่าน `Copy`

### 6.9 Ownership กับฟังก์ชัน: การส่งค่าเข้าฟังก์ชันคือการโอนกรรมสิทธิ์

กฎเรื่อง move/copy ที่เราเรียนมาทั้งหมด **ใช้กับการส่งค่าเข้าฟังก์ชันด้วยเช่นกัน** เพราะในทางเทคนิค การส่งค่าเข้า
พารามิเตอร์ของฟังก์ชันมีความหมายเหมือนกับการทำ `let` ให้กับตัวแปรใหม่ (คือพารามิเตอร์นั้นเอง) ทุกประการ

```rust
fn takes_ownership(some_string: String) {
    println!("ได้รับกรรมสิทธิ์: {some_string}");
    // เมื่อฟังก์ชันนี้จบลง some_string ออกจาก scope -> ค่าถูก drop ที่นี่เลย!
}

fn main() {
    let s = String::from("สวัสดี");

    takes_ownership(s); // s ถูก MOVE เข้าไปในฟังก์ชัน

    println!("{s}"); // ผิด! s ถูก move ไปแล้ว ใช้ต่อไม่ได้
}
```

Error ที่ได้:

```
error[E0382]: borrow of moved value: `s`
 --> src/main.rs:9:15
  |
7 |     let s = String::from("สวัสดี");
  |         - move occurs because `s` has type `String`, which does not implement the `Copy` trait
8 |     takes_ownership(s);
  |                     - value moved here
9 |     println!("{s}");
  |               ^^^ value borrowed here after move
```

สิ่งที่เกิดขึ้นคือ: ตอนเรียก `takes_ownership(s)` — กรรมสิทธิ์ของค่าที่ `s` เป็นเจ้าของถูกโอนไปให้พารามิเตอร์
`some_string` ของฟังก์ชัน (เหมือนที่ `let s2 = s1;` โอนกรรมสิทธิ์จาก `s1` ไป `s2`) เมื่อฟังก์ชัน `takes_ownership`
ทำงานจบและ`some_string`ออกจาก scope ของมัน (ปีกกาปิดของฟังก์ชัน) — ค่านั้นก็ถูก **drop ไปเรียบร้อยแล้ว** ตั้งแต่ตรงนั้น
`main` ไม่มีทางเข้าถึงมันได้อีกเลย เพราะมันไม่มีตัวตนอยู่แล้ว การที่ compiler ปฏิเสธไม่ให้ `main` ใช้ `s` ต่อ (แม้จะดู
"เข้มงวดเกินไป" สำหรับมือใหม่) จริง ๆ แล้วคือการป้องกัน use-after-free ที่แม่นยำที่สุด — ถ้า Rust ยอมให้ใช้ `s` ต่อ
นั่นจะเท่ากับการอ่าน memory ที่ถูกคืนไปแล้ว!

#### เปรียบเทียบ: ส่ง `i32` (Copy) เข้าฟังก์ชัน ไม่เกิด move

```rust
fn takes_copy(number: i32) {
    println!("ได้รับ (copy): {number}");
}

fn main() {
    let n = 42;

    takes_copy(n); // n ถูก copy เข้าไปในฟังก์ชัน ไม่ใช่ move

    println!("ยังใช้ n ต่อได้ปกติ: {n}"); // OK! เพราะ i32 เป็น Copy
}
```

ผลลัพธ์:

```
ได้รับ (copy): 42
ยังใช้ n ต่อได้ปกติ: 42
```

เพราะ `i32` implement `Copy` การส่ง `n` เข้าฟังก์ชันจึงเป็นการ copy ค่า 4 bytes ไปให้พารามิเตอร์ `number` เท่านั้น
`n` ใน `main` ยังคงเป็นเจ้าของค่า `42` ของตัวเองอยู่ต่อไปตามปกติ ไม่มีอะไรถูกโอนไปไหน — ตารางสรุปเปรียบเทียบให้เห็น
ภาพชัดเจนอีกครั้ง:

| การกระทำ | ชนิดที่เป็น `Copy` (เช่น `i32`) | ชนิดที่ไม่เป็น `Copy` (เช่น `String`) |
|---|---|---|
| `let b = a;` | copy — `a` ใช้ต่อได้ | move — `a` ใช้ต่อไม่ได้ |
| `func(a);` | copy เข้าฟังก์ชัน — `a` ใช้ต่อได้หลังเรียก | move เข้าฟังก์ชัน — `a` ใช้ต่อไม่ได้หลังเรียก |
| ต้นทุนของการส่งค่า | ต่ำมาก คงที่ (copy 4-16 bytes) | ต่ำเช่นกัน! (copy แค่ ptr/len/cap บน stack ไม่ copy ข้อมูลบน heap) |

จุดที่มือใหม่มักเข้าใจผิด: การ **move** ไม่ได้ "ช้า" หรือ "แพง" กว่า copy เลย — ในทางเทคนิคทั้งคู่ทำสิ่งเดียวกันคือ
copy ข้อมูลบน stack (ptr/len/cap สำหรับ `String`, หรือ 4 bytes สำหรับ `i32`) ความแตกต่างมีแค่**เรื่องกฎ**: หลัง move
ต้นตัวแปรใช้ต่อไม่ได้ (เพื่อป้องกัน double-free ของข้อมูลบน heap ที่ยังชี้ไปที่เดียวกัน) แต่หลัง copy ต้นตัวแปรใช้ต่อ
ได้ (เพราะไม่มี heap resource ต้องกังวลเรื่อง double-free เลย) — **move ไม่ใช่ปัญหาด้านประสิทธิภาพ มันคือกฎด้าน
ความปลอดภัยของ memory**

### 6.10 การคืนกรรมสิทธิ์จากฟังก์ชัน (Returning Ownership)

ถ้าฟังก์ชันรับกรรมสิทธิ์ของค่าเข้าไปแล้ว "กิน" มันไปเลยทุกครั้ง โปรแกรมจะเขียนยากมาก เพราะทุกครั้งที่ส่งค่าเข้าฟังก์ชัน
ตัวแปรเดิมจะใช้ต่อไม่ได้อีก — ข่าวดีคือฟังก์ชันสามารถ **return ค่ากลับ** เพื่อ "คืนกรรมสิทธิ์" ให้ผู้เรียกได้เช่นกัน

```rust
fn gives_ownership() -> String {
    let some_string = String::from("ของขวัญจากฟังก์ชัน");
    some_string // return ค่านี้ — โอนกรรมสิทธิ์ออกจากฟังก์ชันไปให้ผู้เรียก
}

fn main() {
    let s1 = gives_ownership(); // s1 ได้รับกรรมสิทธิ์จากฟังก์ชัน
    println!("{s1}");
}
```

ผลลัพธ์:

```
ของขวัญจากฟังก์ชัน
```

สังเกตว่า `some_string` **ไม่ได้ถูก drop** ตอนฟังก์ชัน `gives_ownership` จบ ทั้ง ๆ ที่มันคือตัวแปร local ของฟังก์ชันนั้น
— เพราะมันถูก return ออกไป (โอนกรรมสิทธิ์ให้ `s1` ใน `main`) เสียก่อนที่จะถึงจุดจบ scope ของฟังก์ชัน กฎข้อ 3 ของ
ownership ("เมื่อเจ้าของหมด scope ค่าจะถูก drop") ยังเป็นจริงเสมอ แต่ ณ จุดที่ฟังก์ชันจบลง `some_string` **ไม่ใช่
เจ้าของค่านั้นแล้ว** (กรรมสิทธิ์ถูกโอนออกไปตั้งแต่ตอน return) — เจ้าของใหม่คือ `s1` ใน `main` ต่างหาก

เราสามารถผสมทั้งการรับและคืนกรรมสิทธิ์ในฟังก์ชันเดียวกันได้ — ฟังก์ชันรับกรรมสิทธิ์เข้ามา ทำงานกับมัน แล้ว "คืน"
กรรมสิทธิ์กลับไปให้ผู้เรียกผ่าน return:

```rust
fn takes_and_gives_back(a_string: String) -> String {
    println!("กำลังประมวลผล: {a_string}");
    a_string // คืนกรรมสิทธิ์กลับไปให้ผู้เรียกที่เดิม
}

fn main() {
    let s1 = String::from("ข้อความต้นฉบับ");
    let s2 = takes_and_gives_back(s1); // s1 ถูก move เข้าไป แล้วได้กรรมสิทธิ์คืนมาเป็น s2

    println!("s2 = {s2}");
    // println!("s1 = {s1}"); // ผิด! s1 ถูก move เข้าฟังก์ชันไปแล้ว แม้ฟังก์ชันจะ "คืน" ค่ากลับมา
    //                        // แต่ค่ากลับมาในชื่อใหม่ (s2) ไม่ใช่ s1 ตัวเดิม
}
```

ผลลัพธ์:

```
กำลังประมวลผล: ข้อความต้นฉบับ
s2 = ข้อความต้นฉบับ
```

สังเกตข้อสำคัญ: แม้ฟังก์ชันจะ "คืนค่ากลับมาให้" แต่ **มันคืนมาในชื่อตัวแปรใหม่ (`s2`)** ไม่ใช่การทำให้ `s1` เดิม
ใช้งานต่อได้อีก — `s1` ยังถูก move เข้าไปในฟังก์ชันอยู่ดี (invalidate ไปแล้วตอนเรียก `takes_and_gives_back(s1)`)
เพียงแต่ค่าที่มันเคยเป็นเจ้าของ ถูกส่งกลับมาให้เจ้าของใหม่ (`s2`) รับช่วงต่อเท่านั้น

#### ปัญหาที่เห็นได้ชัดแล้ว: นี่มันยุ่งยากเกินไปสำหรับกรณีง่าย ๆ!

ลองนึกภาพว่าคุณอยากเขียนฟังก์ชันที่แค่ **"อ่าน" ความยาวของ string** โดยไม่จำเป็นต้องเปลี่ยนแปลงมันเลย ถ้าใช้ความรู้
ที่มีแค่ตอนนี้ (เรียนแค่การโอนกรรมสิทธิ์แบบเต็ม) คุณจะต้องเขียนแบบนี้:

```rust
fn calculate_length_the_hard_way(s: String) -> (String, usize) {
    let length = s.len(); // .len() คืนค่า usize (ความยาวเป็นจำนวน byte)
    (s, length) // ต้อง return s กลับไปด้วย ไม่งั้นผู้เรียกจะเสีย s ไปตลอดกาล!
}

fn main() {
    let s1 = String::from("สวัสดีครับ");

    let (s2, len) = calculate_length_the_hard_way(s1); // ต้องรับ tuple กลับมาแยกเป็น s2 และ len

    println!("ความยาวของ \"{s2}\" คือ {len} bytes");
}
```

ผลลัพธ์:

```
ความยาวของ "สวัสดีครับ" คือ 15 bytes
```

โค้ดนี้ compile ผ่านและทำงานถูกต้อง แต่ **ดูยุ่งยากอย่างไม่มีเหตุผลเลย** — เราแค่ต้องการ "แอบดู" ความยาวของ string
ไม่ได้ต้องการเปลี่ยนแปลงหรือทำลายมันแม้แต่นิดเดียว แต่ด้วยกฎที่เรียนมาทั้งหมดในบทนี้ (การส่งค่าเข้าฟังก์ชัน = โอน
กรรมสิทธิ์แบบเต็ม) เราถูกบีบให้ต้อง "รับคืน" ค่าเดิมกลับมาด้วยตัวเองผ่าน tuple ทุกครั้ง ถ้าฟังก์ชันมีความซับซ้อนมากขึ้น
(เรียกใช้หลายค่า หลายฟังก์ชันต่อกันเป็นสาย) โค้ดแบบนี้จะรกและอ่านยากขึ้นเรื่อย ๆ อย่างรวดเร็ว

นี่คือคำถามที่ควรผุดขึ้นในหัวคุณตอนนี้: **"จะดีกว่าไหมถ้าฟังก์ชันสามารถ 'ยืม' ค่ามาดูชั่วคราว โดยไม่ต้องรับกรรมสิทธิ์
ไปเต็ม ๆ แล้วค่อยคืนกลับ?"** — คำตอบคือ **"ได้แน่นอน"** และกลไกที่ทำสิ่งนี้ได้คือ **Borrowing** ซึ่งเป็นเนื้อหาทั้งหมด
ของ **Part 7** ถัดไป เราจะย้อนกลับมาแก้ฟังก์ชัน `calculate_length_the_hard_way` ให้เขียนได้อย่างง่ายดายในบทนั้นทันที

### 6.11 ตัวอย่างจากโลกจริง: ระบบคลังสินค้า — ห่วงโซ่การโอนกรรมสิทธิ์ระหว่างฟังก์ชัน

มาดูตัวอย่างที่สมจริงมากขึ้น สมมติเรากำลังเขียนโปรแกรมส่วนหนึ่งของระบบจัดการคลังสินค้า (warehouse management system)
ที่ต้อง: **สร้างชื่อสินค้าใหม่ → ลงทะเบียนสินค้าเข้าระบบ → พิมพ์ป้ายติดชั้นวาง** โดยแต่ละขั้นตอนเป็นฟังก์ชันแยกกัน
และ "ชื่อสินค้า" (`String`) ต้องถูกโอนกรรมสิทธิ์ผ่านแต่ละขั้นตอนไปเรื่อย ๆ:

```rust
// ขั้นที่ 1: สร้างชื่อสินค้าใหม่ (สมมติว่าในระบบจริงอาจอ่านมาจากฐานข้อมูลหรือ input ของผู้ใช้)
fn create_item_name(raw_name: &str) -> String {
    // แปลงจาก &str (ข้อมูลชั่วคราว) เป็น String (ข้อมูลที่ระบบเป็นเจ้าของเต็มรูปแบบ)
    let mut name = String::from(raw_name);
    name.push_str(" (ของแท้)"); // เพิ่มข้อความยืนยันสถานะสินค้า
    name
}

// ขั้นที่ 2: ลงทะเบียนสินค้าเข้าระบบคลัง — รับกรรมสิทธิ์เข้ามา บันทึกลง log แล้วคืนกรรมสิทธิ์กลับไป
fn register_item(name: String) -> String {
    println!("[LOG] ลงทะเบียนสินค้าใหม่เข้าคลัง: {name}");
    name // คืนกรรมสิทธิ์กลับไปให้ผู้เรียก เพื่อให้ขั้นตอนถัดไปใช้ต่อได้
}

// ขั้นที่ 3: พิมพ์ป้ายติดชั้นวาง — รับกรรมสิทธิ์เข้ามาเป็นขั้นตอนสุดท้าย ไม่คืนกลับ (จบสาย)
fn print_shelf_label(name: String) {
    println!("+---------------------------+");
    println!("| ป้ายชั้นวาง: {name:<12} |");
    println!("+---------------------------+");
    // name ออกจาก scope ตรงนี้ -> ถูก drop โดยอัตโนมัติ หมดหน้าที่ของมันแล้ว
}

fn main() {
    let item_name = create_item_name("เครื่องชงกาแฟ");        // main ได้กรรมสิทธิ์ตัวแรก
    let item_name = register_item(item_name);                  // โอนเข้า register_item แล้วได้กรรมสิทธิ์คืน (shadowing)
    print_shelf_label(item_name);                               // โอนเข้า print_shelf_label เป็นขั้นตอนสุดท้าย

    println!("จบกระบวนการรับสินค้าเข้าคลังเรียบร้อยแล้ว");
}
```

ผลลัพธ์:

```
[LOG] ลงทะเบียนสินค้าใหม่เข้าคลัง: เครื่องชงกาแฟ (ของแท้)
+---------------------------+
| ป้ายชั้นวาง: เครื่องชงกาแฟ (ของแท้) |
+---------------------------+
จบกระบวนการรับสินค้าเข้าคลังเรียบร้อยแล้ว
```

(หมายเหตุ: การจัดตำแหน่งด้วย `{name:<12}` เป็นการจัดชิดซ้ายกว้าง 12 ตัวอักษร แต่เนื่องจากตัวอักษรไทยกว้างกว่า ASCII
เมื่อแสดงผลจริงบน terminal กรอบอาจไม่ตรงเป๊ะเสมอไป — เป็นรายละเอียดเรื่อง Unicode/การแสดงผลที่เราจะพูดถึงลึกกว่านี้ใน
Part 14 ตอนนี้ให้สนใจแค่ผลลัพธ์เชิง logic ของ ownership เป็นหลัก)

สังเกตการใช้ **shadowing** (`let item_name = register_item(item_name);`) ที่เรียนมาแล้วใน Part 3 — เราตั้งใจใช้ชื่อ
`item_name` ซ้ำทุกครั้งที่ได้กรรมสิทธิ์คืนมา เพราะมันคือ "แนวคิดเดียวกัน" (ชื่อสินค้าตัวนี้) เพียงแต่ผ่านการประมวลผล
คนละขั้นตอนกัน — สังเกตด้วยว่านี่คือ**ห่วงโซ่การโอนกรรมสิทธิ์ (move chain)**: `create_item_name` → `main` →
`register_item` → `main` (คืนกลับ) → `print_shelf_label` (จบสาย ไม่คืน) กรรมสิทธิ์ของ `String` ตัวเดียวนี้ถูกส่งต่อ
มือใครมือเจ้าของกันไปเรื่อย ๆ ตลอดทาง โดยมีเจ้าของเพียงหนึ่งเดียวเสมอในแต่ละช่วงเวลา ตรงตามกฎข้อ 2 ของ ownership
เป๊ะ ๆ

#### จะเกิดอะไรถ้าเราพยายามใช้ `item_name` ต่อหลัง `print_shelf_label`?

มาดูว่าจะเกิดอะไรถ้าทีมพัฒนาลืมกฎเรื่อง move แล้วพยายามใช้ `item_name` อีกครั้งหลังจากที่มันถูกโอนกรรมสิทธิ์ให้
`print_shelf_label` ไปแล้ว (ซึ่งเป็นขั้นตอนสุดท้ายที่ไม่คืนกรรมสิทธิ์กลับมา):

```rust
fn print_shelf_label(name: String) {
    println!("ป้ายชั้นวาง: {name}");
}

fn main() {
    let item_name = String::from("เครื่องชงกาแฟ");
    print_shelf_label(item_name);

    // ทีมพัฒนาลืมว่า item_name ถูกโอนกรรมสิทธิ์ไปแล้ว พยายามส่งไปบันทึกสถิติเพิ่ม
    log_item_processed(item_name); // ผิด! item_name ถูก move ไปแล้วตั้งแต่บรรทัดก่อนหน้า
}

fn log_item_processed(name: String) {
    println!("บันทึกสถิติ: ประมวลผลสินค้า {name} เรียบร้อย");
}
```

จะได้ error:

```
error[E0382]: use of moved value: `item_name`
 --> src/main.rs:11:25
  |
7  |     let item_name = String::from("เครื่องชงกาแฟ");
   |         --------- move occurs because `item_name` has type `String`, which does not implement the `Copy` trait
8  |     print_shelf_label(item_name);
   |                        --------- value moved here
...
11 |     log_item_processed(item_name);
   |                         ^^^^^^^^^ value used here after move
```

ในสถานการณ์จริง นี่คือบั๊กเชิง logic ที่พบได้บ่อยมากในระบบที่ซับซ้อน (พยายามใช้ข้อมูลตัวเดียวกันในหลายจุดของ workflow
โดยไม่คิดล่วงหน้าว่าใครควรเป็น "เจ้าของ" มันในแต่ละช่วง) — **ข่าวดีคือ Rust จับบั๊กนี้ได้ตั้งแต่ตอน compile time**
ไม่ต้องรอให้โปรแกรม deploy ขึ้น production แล้วพัง หรือรอให้ QA เจอในการทดสอบ compiler บอกตำแหน่งที่แน่นอนและวิธีแก้
ให้ตรง ๆ เลย — วิธีแก้ในสถานการณ์นี้มีหลายทาง เช่น เรียก `log_item_processed` ก่อน `print_shelf_label` (สลับลำดับ),
หรือ `.clone()` ถ้าจำเป็นต้องใช้สองที่จริง ๆ, หรือ (วิธีที่ดีที่สุดในกรณีนี้ที่จะเรียนใน Part 7) ให้ทั้งสองฟังก์ชัน
**ยืม** ข้อมูลมาดูแทนการรับกรรมสิทธิ์ไปเต็ม ๆ ตั้งแต่แรก

#### ประมวลผลสินค้าหลายรายการในลูป: ทำไม `&str` ใช้ซ้ำในลูปได้สบาย ๆ แต่ `String` ทำไม่ได้

ขยายตัวอย่างคลังสินค้าให้สมจริงขึ้นอีกขั้น — สมมติว่าสินค้าใหม่เข้ามาทีละหลายรายการ เราต้องวนลูปประมวลผลทีละตัว:

```rust
fn process_item(raw_name: &str) {
    let owned = String::from(raw_name); // สร้าง String ใหม่ (heap allocation ใหม่) ทุกครั้งที่เรียก
    println!("กำลังประมวลผลสินค้า: {owned}");
}

fn main() {
    let raw_names = ["เครื่องชงกาแฟ", "หูฟังบลูทูธ", "แป้นพิมพ์ไร้สาย"]; // [&str; 3]

    for raw_name in raw_names {
        process_item(raw_name); // raw_name เป็น &str ซึ่งเป็น Copy — วนซ้ำได้ไม่มีปัญหาเรื่อง move เลย
    }

    // raw_names ยังใช้งานได้ปกติหลังลูป เพราะอาร์เรย์ของชนิดที่เป็น Copy (&str) ก็เป็น Copy ไปด้วย
    // (กฎเดียวกับ tuple ของ Copy type ที่เรียนในหัวข้อ 6.8 ใช้กับอาร์เรย์ได้เช่นกัน)
    println!("จำนวนสินค้าที่ประมวลผลทั้งหมด: {}", raw_names.len());
}
```

ผลลัพธ์:

```
กำลังประมวลผลสินค้า: เครื่องชงกาแฟ
กำลังประมวลผลสินค้า: หูฟังบลูทูธ
กำลังประมวลผลสินค้า: แป้นพิมพ์ไร้สาย
จำนวนสินค้าที่ประมวลผลทั้งหมด: 3
```

จุดที่น่าสนใจ: `raw_name` แต่ละตัวใน `raw_names` มีชนิดเป็น `&str` ซึ่ง**เป็น `Copy`** (เพราะ `&str` เป็นแค่ pointer +
ความยาว ไม่ได้เป็นเจ้าของข้อมูลบน heap เลย — มันแค่ "ชี้ไปดู" ข้อมูลที่ฝังอยู่ใน binary) การวนลูปเรียก `process_item`
ซ้ำ ๆ จึงไม่มีปัญหาเรื่อง move แม้แต่นิดเดียว และตัวแปร `raw_names` เองก็ยังใช้ `.len()` ต่อได้หลังจบลูป เพราะอาร์เรย์
ของชนิดที่เป็น `Copy` ก็เป็น `Copy` ไปด้วยทั้งก้อน (เหมือนกฎ tuple-of-Copy-is-Copy ในหัวข้อ 6.8 แต่ใช้กับอาร์เรย์ได้
เหมือนกัน) — ถ้าเราเปลี่ยน `raw_names` ให้เป็นอาร์เรย์ของ `String` แทน (ซึ่งไม่ใช่ `Copy`) การวนลูปแบบเดียวกันนี้จะ
"กิน" ค่าของอาร์เรย์เข้าไปทีละตัวจริง ๆ และ `raw_names.len()` หลังลูปจะ compile ไม่ผ่าน (เพราะอาร์เรย์ถูก move เข้า
ลูปไปแล้วทั้งก้อน) — นี่คือตัวอย่างที่ตอกย้ำอีกครั้งว่าความแตกต่างระหว่าง `&str` (ยืม/Copy) กับ `String` (เป็นเจ้าของ/
move) ส่งผลกับพฤติกรรมของโปรแกรมโดยตรง ไม่ใช่แค่เรื่องทางทฤษฎี

#### Ownership ไม่ได้จำกัดอยู่แค่ `String`

ตลอดบทนี้เราใช้ `String` เป็นตัวอย่างหลักเพราะมันคือ owned heap type ที่ง่ายที่สุด แต่กฎ ownership ทั้ง 3 ข้อ, move
semantics, `Clone`, และ `Copy` **ใช้กับทุกชนิดข้อมูลใน Rust เหมือนกันหมด ไม่มีข้อยกเว้น** ในโมดูลถัดไปของหลักสูตรนี้
คุณจะเจอชนิดข้อมูลอื่นที่เป็นเจ้าของ heap resource เช่นเดียวกับ `String` และปฏิบัติตามกฎเดียวกันนี้ทุกประการ:

- **`Vec<T>`** (Part 13) — list ที่ขยายขนาดได้ เก็บ pointer/len/capacity บน stack เหมือน `String` เป๊ะ (ที่จริง
  `String` ภายในก็คือ `Vec<u8>` ที่การันตีว่าเนื้อหาเป็น UTF-8 ที่ถูกต้องเสมอ)
- **`HashMap<K, V>`** (Part 15) — ตารางแฮชที่เป็นเจ้าของข้อมูลทั้ง key และ value บน heap
- **`Box<T>`** (Part 22) — "กล่อง" สำหรับเก็บค่าใดค่าหนึ่งไว้บน heap โดยตรง (ใช้เมื่อต้องการควบคุม memory layout
  แบบพิเศษ หรือเมื่อขนาดของชนิดข้อมูลไม่รู้แน่นอนตอน compile time)
- **`File`** (จาก `std::fs`) — เป็นเจ้าของ file handle ของระบบปฏิบัติการ และ `Drop` ของมันจะปิดไฟล์ให้อัตโนมัติ
  ทันทีที่หมด scope เหมือนที่ `String` คืน heap memory ให้อัตโนมัติ

เมื่อคุณเข้าใจ ownership กับ `String` แล้ว คุณเข้าใจ**หลักการเดียวกันนี้กับทุกชนิดข้อมูลที่เป็นเจ้าของ resource ใน
Rust ทั้งหมด** — นี่คือเหตุผลที่บทนี้ถูกจัดให้เป็นบทแรกของโมดูล 1 และสำคัญที่สุดในหลักสูตร เพราะทุกอย่างที่ตามมาสร้าง
อยู่บนพื้นฐานนี้ทั้งหมด

**หมายเหตุล่วงหน้าสำหรับอนาคต**: กฎข้อ 2 ("ค่าหนึ่งมีเจ้าของได้เพียงหนึ่งเดียวในเวลาใดเวลาหนึ่ง") ที่เราย้ำมาตลอดบทนี้
เป็นกฎที่ใช้ได้กับ **owned type ทั่วไปทั้งหมด** แต่ในโมดูลที่ลึกขึ้น (smart pointers) คุณจะเจอชนิดข้อมูลพิเศษชื่อ
`Rc<T>` (reference counted) และ `Arc<T>` (atomic reference counted สำหรับใช้ข้าม thread) ที่อนุญาตให้มี **"เจ้าของ
ร่วม" หลายตัว** พร้อมกันได้อย่างปลอดภัย โดยนับจำนวนเจ้าของอยู่ภายในและ drop ค่าจริงก็ต่อเมื่อเจ้าของตัวสุดท้ายหมด
scope ไปแล้ว — นี่ไม่ใช่การ "แหกกฎ" ของ ownership แต่เป็นการนำกฎเดิมมาประยุกต์ใช้อย่างชาญฉลาดในกรณีพิเศษที่จำเป็น
ต้องมีเจ้าของร่วมกันจริง ๆ (เช่น โครงสร้างข้อมูลแบบ graph หรือ tree ที่หลาย node ต้องอ้างอิงกัน) ตอนนี้ยังไม่ต้อง
เข้าใจรายละเอียด — จำแค่ว่ากฎที่เรียนในบทนี้คือ**กรณีปกติ** ที่คุณจะเจอ 95% ของเวลาในการเขียนโปรแกรม Rust ทั่วไป

### 6.12 มองภาพรวม: Ownership ของ Rust คือ RAII ที่ compiler บังคับใช้จริง

ถ้าคุณมีพื้นฐาน C++ มาก่อน แนวคิดที่คุณเพิ่งเรียนไปทั้งบทนี้อาจฟังดูคุ้น ๆ — เพราะมันคือแนวคิดเดียวกับ **RAII**
(Resource Acquisition Is Initialization) ที่ C++ ใช้มาตั้งแต่ทศวรรษ 1990 หลักการของ RAII คือ "ผูกการขอ resource
(memory, file, lock) ไว้กับช่วงชีวิตของ object หนึ่งตัว เมื่อ object นั้นถูกทำลาย (destructor ทำงาน) resource ก็จะ
ถูกคืนไปด้วยอัตโนมัติ" — ฟังดูเหมือนกฎข้อ 3 ของ ownership และกลไก `Drop` ที่เราเรียนในหัวข้อ 6.5 เป๊ะเลยใช่ไหม?
เพราะมันคือแนวคิดเดียวกันจริง ๆ!

ความต่างที่สำคัญที่สุดคือ **Rust บังคับใช้ RAII อย่างเข้มงวดกว่า C++ มาก** ผ่าน compiler:

| ประเด็น | C++ (RAII ด้วย destructor/`unique_ptr`) | Rust (ownership + `Drop`) |
|---|---|---|
| ต้องใช้ RAII จริงจังหรือไม่ | เป็น convention/best-practice ที่โปรแกรมเมอร์**เลือก**ทำตาม — เขียน raw pointer + `new`/`delete` แบบเก่าก็ยังคอมไพล์ผ่านได้ (ไม่ปลอดภัย แต่ไม่ผิด syntax) | เป็น**กฎบังคับของภาษา** — ไม่มีทาง "หนี" ออกจากระบบ ownership ได้เลยใน safe Rust |
| ตรวจสอบว่ามีคนใช้ resource ที่ถูกคืนไปแล้วหรือไม่ | ไม่ตรวจ — ต้องระวังเองว่า raw pointer ที่เหลืออยู่ไม่ถูกใช้ต่อ (dangling pointer) | ตรวจโดย compiler เสมอ (`E0382`) ทำให้ไม่มีทาง use-after-free ได้เลยใน safe Rust |
| Double-free จาก copy หลาย object ชี้ resource เดียวกัน | เกิดได้ถ้าใช้ raw pointer/reference นับจำนวนไม่ถูกต้อง (ต้องพึ่ง `unique_ptr`/`shared_ptr` ถึงจะปลอดภัยขึ้น) | เกิดไม่ได้เลย เพราะกฎ "เจ้าของเดียว" บังคับใช้กับทุกชนิดข้อมูลโดยไม่มีทางเลี่ยง |

พูดให้ชัดที่สุด: **`unique_ptr` ใน C++ คือความพยายามเลียนแบบ ownership แบบที่ Rust ทำ แต่เป็นแค่ library-level
solution ที่ยังต้องพึ่งวินัยของโปรแกรมเมอร์ในการเลือกใช้มันอย่างถูกต้อง** ส่วน Rust ทำให้แนวคิดนี้เป็น**ส่วนหนึ่งของ
ตัวภาษาเองและถูกบังคับใช้กับทุกชนิดข้อมูลโดย compiler อย่างเลี่ยงไม่ได้** — นี่คือสิ่งที่ทำให้ Rust สามารถอ้างได้ว่า
โปรแกรมที่ compile ผ่านใน safe Rust จะไม่มี use-after-free, double-free หรือ memory leak (จากการลืม free) เลย
ซึ่งเป็นการันตีที่ C++ ให้ไม่ได้แม้จะมี RAII มานานหลายสิบปีแล้วก็ตาม

### 6.13 ทบทวนความเข้าใจก่อนไปต่อ: ถาม-ตอบสั้น ๆ

ก่อนไปดูกับดักที่พบบ่อยและแบบฝึกหัด ลองถามตัวเองด้วยคำถามเหล่านี้ ถ้าตอบได้ครบทุกข้อ แสดงว่าคุณเข้าใจแกนหลักของ
Ownership แล้วอย่างแท้จริง ไม่ใช่แค่จำ syntax:

**ถาม: ทำไม `let s2 = s1;` (ที่ `s1` เป็น `String`) ทำให้ `s1` ใช้ต่อไม่ได้ ทั้งที่ `let y = x;` (ที่ `x` เป็น `i32`)
กลับใช้ `x` ต่อได้ปกติ?**

ตอบ: เพราะ `String` เป็นเจ้าของ buffer บน heap ที่ต้อง deallocate ตอน drop ถ้า Rust ยอมให้ทั้ง `s1` และ `s2` ชี้ไปที่
buffer เดียวกันได้พร้อมกันโดยไม่ invalidate ตัวใดตัวหนึ่ง ทั้งคู่จะพยายาม deallocate buffer เดียวกันตอนหมด scope
กลายเป็น double-free — Rust จึงบังคับให้มีเจ้าของเดียวเสมอโดย invalidate `s1` ทันทีที่ move เกิดขึ้น ส่วน `i32` ไม่มี
heap resource ให้ต้องกังวลเรื่องนี้เลย การ copy 4 bytes ไปมาจึงไม่มีความเสี่ยงอะไร ทำให้ `i32` implement `Copy`
และไม่ต้อง invalidate ตัวต้นทาง

**ถาม: `.clone()` กับการ assign ธรรมดา (`let b = a;`) ต่างกันตรงไหนในเชิง memory?**

ตอบ: การ assign ธรรมดาสำหรับ `String` คือ move — copy แค่ ptr/len/capacity (24 bytes บน stack) โดยไม่แตะข้อมูลจริง
บน heap เลย และทำให้ตัวต้นทางใช้ต่อไม่ได้ ส่วน `.clone()` คือการขอจัดสรร heap buffer ใหม่ทั้งก้อน แล้ว copy ข้อมูล
จริงทุก byte ลงไปในบัฟเฟอร์ใหม่นั้น ทำให้ได้สอง buffer ที่เป็นอิสระจากกันโดยสิ้นเชิง และตัวต้นทางยังใช้ต่อได้ปกติ
เพราะมันไม่ได้ถูก move ไปไหน

**ถาม: ทำไม Rust ไม่ทำให้ `.clone()` เกิดขึ้นอัตโนมัติเวลา assign ค่าที่มี heap data ไปเลย จะได้ไม่ต้อง invalidate
ตัวแปรต้นทาง?**

ตอบ: เพราะจะทำให้ต้นทุนด้านประสิทธิภาพ (การจัดสรร heap ใหม่ + copy ข้อมูลทั้งหมด) **ถูกซ่อนไว้โดยไม่มีสัญญาณใดๆ
ในโค้ดเลย** ผู้เขียนโค้ดจะไม่รู้เลยว่าบรรทัดไหนมีต้นทุนสูงบ้าง Rust เลือกปรัชญาที่ว่า "ต้นทุนที่มองไม่เห็นในโค้ดเป็น
เรื่องอันตราย" จึงบังคับให้การ deep copy ทุกครั้งต้องมีคำว่า `.clone()` ปรากฏชัดเจน ให้ผู้เขียนโค้ด (และผู้ review)
มองเห็นต้นทุนนั้นได้ทันทีจากการอ่านโค้ดเพียงอย่างเดียว โดยไม่ต้องรันโปรแกรมหรือ profile ก่อนถึงจะรู้

**ถาม: ส่ง `String` เข้าฟังก์ชันแล้วตัวแปรต้นทางใช้ต่อไม่ได้ ทั้งที่ฟังก์ชัน "แค่" `println!` มันออกมาเฉย ๆ ดูเหมือน
ไม่ได้ทำลายอะไรเลย ทำไมยังต้อง move?**

ตอบ: เพราะการส่งค่าเข้าพารามิเตอร์ของฟังก์ชันมีความหมายเดียวกับ `let` ทุกประการในเชิง ownership — พารามิเตอร์คือ
ตัวแปร local ตัวใหม่ของฟังก์ชันนั้น เมื่อฟังก์ชันจบและพารามิเตอร์นั้นหมด scope ค่าจะถูก drop ทันที (ตามกฎข้อ 3)
ไม่ว่าฟังก์ชันจะ "ใช้" มันทำอะไรบ้างในเนื้อฟังก์ชันหรือไม่ก็ตาม ถ้า Rust ยอมให้ตัวแปรต้นทางยังใช้ต่อได้หลังส่งเข้า
ฟังก์ชัน นั่นจะเท่ากับยอมให้เข้าถึง memory ที่ (อาจจะ) ถูกคืนไปแล้ว — ปัญหานี้แหละที่ทำให้ Part 7 ต้องมีอยู่: เพื่อให้
ฟังก์ชันที่ "แค่อยากดู" ไม่ต้องรับกรรมสิทธิ์เต็ม ๆ ตั้งแต่แรก

**ถาม: ทำไม tuple `(i32, String)` ไม่เป็น `Copy` ทั้งที่มี `i32` ซึ่งเป็น `Copy` อยู่ในนั้นด้วย?**

ตอบ: เพราะกฎของ `Copy` กำหนดว่า tuple/struct จะเป็น `Copy` ได้ก็ต่อเมื่อ**สมาชิกทุกตัวไม่มีข้อยกเว้น**เป็น `Copy`
`Copy` เป็นสมบัติของทั้งก้อน ไม่ใช่แยกเป็นส่วน ๆ — ถ้าอนุญาตให้ tuple ที่มีสมาชิกผสม (บางตัว Copy บางตัวไม่ Copy)
เป็น `Copy` ได้บางส่วน จะทำให้กฎเรื่อง "เจ้าของเดียว" ของส่วนที่เป็น `String` พังทันที เพราะจะมีสอง tuple ที่ต่างก็
คิดว่าตัวเองเป็นเจ้าของ `String` ตัวเดียวกัน

**ถาม: `Drop` implement ยังไง ใครเรียกมันบ้าง?**

ตอบ: `Drop` คือ trait ที่มี method เดียวชื่อ `fn drop(&mut self)` — คุณ (หรือ standard library สำหรับ `String`/
`Vec<T>`/`File`) เขียน logic การคืน resource ไว้ในนั้น **แต่ไม่มีใครเรียก method นี้ตรง ๆ ด้วยมือได้เลย** (จะได้
error `E0040` ถ้าลองเรียก `.drop()` ตรง ๆ) ตัว Rust compiler เท่านั้นที่แทรกโค้ดเรียก `drop()` ให้อัตโนมัติ ณ จุดที่
ค่านั้นออกจาก scope — ถ้าต้องการสั่งให้หมดอายุก่อนเวลา ต้องใช้ฟังก์ชัน `drop()` จาก prelude ซึ่งทำงานโดยรับกรรมสิทธิ์
เข้าไปเป็นพารามิเตอร์แล้วปล่อยให้จบ scope ตามธรรมชาติ ไม่ใช่การเรียก destructor ตรง ๆ

## กับดักที่พบบ่อย (Common Pitfalls)

**1. ใช้ตัวแปรต่อหลังถูก move ไปแล้ว (การเข้าใจผิดที่พบมากที่สุดสำหรับมือใหม่)**

มือใหม่ที่มาจากภาษาที่มี GC (Python, JavaScript, Java) มักคาดหวังว่า `let b = a;` จะทำให้ `a` และ `b` ใช้งานคู่กันได้
ตลอดไปเหมือนการอ้างอิง object เดียวกัน:

```rust
fn main() {
    let original = String::from("ข้อมูลต้นฉบับ");
    let copy_attempt = original;

    println!("original: {original}");        // ผิด!
    println!("copy_attempt: {copy_attempt}");
}
```

```
error[E0382]: borrow of moved value: `original`
 --> src/main.rs:5:24
  |
2 |     let original = String::from("ข้อมูลต้นฉบับ");
  |         -------- move occurs because `original` has type `String`, which does not implement the `Copy` trait
3 |     let copy_attempt = original;
  |                        -------- value moved here
...
5 |     println!("original: {original}");
  |                          ^^^^^^^^^^ value borrowed here after move
```

**วิธีแก้**: ถ้าตั้งใจให้ทั้งสองตัวใช้งานได้อิสระจากกันจริง ๆ ให้เรียก `.clone()` ตอนกำหนดค่า (`let copy_attempt =
original.clone();`) ถ้าตั้งใจให้ `original` หมดหน้าที่ไปเลยหลังจากนี้ ให้ใช้ `copy_attempt` แทนต่อไปโดยไม่ต้องอ้างถึง
`original` อีก — ทางออกที่ดีที่สุดในระยะยาว (เมื่อคุณแค่ต้องการ "อ่าน" ค่าโดยไม่ต้องเป็นเจ้าของ) คือใช้ reference
(`&original`) ที่จะเรียนใน Part 7

**2. ส่ง `String` ตัวเดิมเข้าฟังก์ชันสองครั้ง (โดยเฉพาะในโค้ดที่มีหลายขั้นตอนต่อกัน)**

```rust
fn print_report(title: String) {
    println!("รายงาน: {title}");
}

fn save_to_archive(title: String) {
    println!("บันทึกเข้าคลังเอกสาร: {title}");
}

fn main() {
    let report_title = String::from("รายงานประจำเดือน");

    print_report(report_title);       // report_title ถูก move เข้าไปตรงนี้
    save_to_archive(report_title);    // ผิด! report_title ถูก move ไปแล้วตั้งแต่บรรทัดก่อน
}
```

```
error[E0382]: use of moved value: `report_title`
 --> src/main.rs:12:21
  |
10 |     let report_title = String::from("รายงานประจำเดือน");
   |         ------------ move occurs because `report_title` has type `String`, which does not implement the `Copy` trait
11 |     print_report(report_title);
   |                  ------------ value moved here
12 |     save_to_archive(report_title);
   |                      ^^^^^^^^^^^^ value used here after move
```

นี่เป็นรูปแบบที่พบบ่อยมากในโค้ดจริง เมื่อค่าตัวเดียวต้องถูกใช้ในหลายจุด (log, print, save, validate) **วิธีแก้ที่ถูกต้อง
ที่สุดคือให้ฟังก์ชันเหล่านี้ยืมข้อมูลมาดู (`&str` หรือ `&String`) แทนการรับกรรมสิทธิ์ไปเต็ม ๆ** — จะเรียนวิธีทำใน
Part 7 การใช้ `.clone()` ก่อนแต่ละครั้งที่เรียกก็แก้ error ได้เหมือนกัน แต่ต้องแลกด้วยการจัดสรร heap ใหม่ทุกครั้ง
ซึ่งไม่มีประสิทธิภาพเท่าการยืม

**3. คิดว่าต่อ `String` สองตัวด้วย `+` ได้เหมือนภาษาอื่น โดยไม่รู้ว่ามันย้ายกรรมสิทธิ์ของตัวซ้ายไปด้วย**

```rust
fn main() {
    let s1 = String::from("Hello, ");
    let s2 = String::from("world!");
    let s3 = s1 + s2; // พยายามต่อ String สองตัวตรง ๆ

    println!("{s3}");
}
```

```
error[E0308]: mismatched types
 --> src/main.rs:4:18
  |
4 |     let s3 = s1 + s2;
  |                   ^^ expected `&str`, found `String`
  |
note: `+` cannot be used to concatenate two `String` values
  = note: string concatenation requires an owned `String` on the left
help: consider using `&s2` instead
  |
4 |     let s3 = s1 + &s2;
  |                   +
```

เหตุผลเชิงเทคนิคคือ operator `+` สำหรับ `String` implement มาแบบ `fn add(self, rhs: &str) -> String` — ฝั่งขวาต้องเป็น
`&str` เท่านั้น (ไม่ใช่ `String`) วิธีแก้คือใส่ `&` หน้าตัวขวา (`s1 + &s2`) แต่ต้องรู้ไว้ด้วยว่า **`s1` จะถูก move
เข้าไปใน `+` เสมอ** (เพราะ `self` ในนิยามของ `add` รับแบบ by-value ไม่ใช่ by-reference) — หลังบรรทัดนี้ `s1` จะใช้
ต่อไม่ได้อีกแล้ว แม้จะแก้ error ให้ compile ผ่านแล้วก็ตาม (`s2` ยังใช้ได้ต่อเพราะส่งเป็น `&s2` คือแค่ยืม ไม่ได้ move)
วิธีต่อ string ที่ทั่วไปกว่าและไม่มีปัญหาเรื่อง move คือ macro `format!("{s1}{s2}")` ซึ่งเราจะเจาะลึกใน **Part 14**

**4. ใช้ `.clone()` แบบไม่คิดหน้าคิดหลัง เพื่อ "หนี" ปัญหา move/borrow checker (anti-pattern เชิงประสิทธิภาพ)**

มือใหม่จำนวนมากพบว่าใส่ `.clone()` ตรงไหนก็ได้ที่ compiler บ่น มักทำให้โค้ด compile ผ่านเสมอ — จนกลายเป็นนิสัยใส่
`.clone()` แบบสุ่มสี่สุ่มห้าโดยไม่เข้าใจว่าทำไม:

```rust
fn print_length(text: String) -> usize {
    text.len()
}

fn main() {
    let data = String::from("ข้อมูลขนาดใหญ่มาก...");

    // ใส่ .clone() ทุกครั้งที่เรียก เพียงเพื่อให้ compile ผ่าน โดยไม่คิดว่ามีทางออกที่ดีกว่า
    let len1 = print_length(data.clone());
    let len2 = print_length(data.clone());
    let len3 = print_length(data.clone());

    println!("{len1} {len2} {len3}");
}
```

โค้ดนี้ **compile ผ่านและทำงานถูกต้อง** แต่ทุกครั้งที่เรียก `data.clone()` โปรแกรมจะจัดสรร heap ใหม่ทั้งก้อนและ copy
ข้อมูลทั้งหมด (ถ้า `data` มีขนาดใหญ่ เช่นหลายพัน/หมื่นตัวอักษร นี่คือการเสียเวลา CPU และ memory ไปโดยไม่จำเป็นเลย
ทั้ง ๆ ที่ `print_length` แค่ต้องการ "อ่าน" ความยาว ไม่ได้ต้องการเป็นเจ้าของข้อมูลจริง ๆ แม้แต่นิดเดียว) นี่คือ
anti-pattern ที่เรียกกันในวงการ Rust ว่า **"clone soup"** — วิธีแก้ที่ถูกต้องคือเปลี่ยน `print_length` ให้รับ `&str`
หรือ `&String` แทน `String` (ยืมข้อมูลมาอ่าน ไม่รับกรรมสิทธิ์) ซึ่งจะไม่มีการจัดสรร heap ใหม่เลยแม้แต่ครั้งเดียว —
นี่คือแรงจูงใจสำคัญที่สุดอีกข้อที่ทำให้ต้องเรียน **Borrowing** ใน Part 7 ต่อไปทันที

**5. พยายามส่ง `String` ตัวเดิมเข้าฟังก์ชันที่กินกรรมสิทธิ์ ซ้ำ ๆ ในลูป**

ต่างจาก pitfall ที่ 2 ที่เรียกฟังก์ชันคนละตัวสองครั้ง กรณีนี้คือเรียกฟังก์ชัน**ตัวเดียวกัน**ซ้ำ ๆ ในลูปด้วยตัวแปร
เดิม ซึ่งพบได้บ่อยเวลาพยายามวนประมวลผลข้อมูลชุดเดียวหลายรอบ (เช่น retry logic):

```rust
fn send_notification(message: String) {
    println!("ส่งข้อความแจ้งเตือน: {message}");
}

fn main() {
    let message = String::from("มีสินค้าใหม่เข้าคลัง");

    for _ in 0..3 {
        send_notification(message); // ผิด! message ถูก move ไปแล้วตั้งแต่รอบแรกของลูป
    }
}
```

```
error[E0382]: use of moved value: `message`
 --> src/main.rs:9:28
  |
6  |     let message = String::from("มีสินค้าใหม่เข้าคลัง");
   |         ------- move occurs because `message` has type `String`, which does not implement the `Copy` trait
7  |
8  |     for _ in 0..3 {
   |     -------------- inside of this loop
9  |         send_notification(message);
   |                            ^^^^^^^ value moved here, in previous iteration of loop
```

สังเกตว่าข้อความ error ระบุชัดเจนว่า **"in previous iteration of loop"** — เพราะรอบแรกของลูป (iteration แรก) ทำให้
`message` ถูก move เข้าไปในฟังก์ชันเรียบร้อยแล้ว ตอนวนมาถึงรอบที่สอง compiler จึงปฏิเสธทันทีเพราะ `message` ไม่มี
ตัวตนให้ใช้อีกต่อไป **วิธีแก้ที่ตรงไปตรงมาที่สุดในตอนนี้** (ก่อนเรียน borrowing) คือเรียก `.clone()` ในแต่ละรอบ
(`send_notification(message.clone())`) แต่วิธีที่ถูกต้องและมีประสิทธิภาพที่สุดคือเปลี่ยน `send_notification` ให้รับ
`&str` แทน ซึ่งจะทำให้เรียกซ้ำในลูปได้อย่างอิสระโดยไม่มีต้นทุนการจัดสรร heap ใหม่เลยแม้แต่ครั้งเดียว — แบบเดียวกับ
ตัวอย่าง `process_item(raw_name: &str)` ในหัวข้อ 6.11 ที่วนลูปเรียกซ้ำได้สบาย ๆ เพราะไม่ได้รับกรรมสิทธิ์ไปเต็ม ๆ

## แบบฝึกหัด (Exercises)

1. **[ง่าย]** โค้ดด้านล่างนี้ compile ไม่ผ่าน จงอธิบายว่าทำไม (อ้างอิงกฎ ownership ข้อไหน) แล้วแก้ไขให้ compile ผ่าน
   ด้วย **2 วิธีที่แตกต่างกัน**: วิธีที่ 1 ใช้ `.clone()`, วิธีที่ 2 ใช้ตัวแปรที่ได้จาก move แทนตัวแปรเดิม (ไม่ใช้
   `.clone()` เลย)

   ```rust
   fn main() {
       let city = String::from("เชียงใหม่");
       let favorite_city = city;

       println!("เมืองที่ชอบ: {favorite_city}");
       println!("เมืองต้นฉบับ: {city}");
   }
   ```

   *Hint: สังเกตว่า error จะบอกตำแหน่งบรรทัดที่ "value moved here" และ "value borrowed here after move" ตรงกับ
   ที่อธิบายในหัวข้อ 6.6 เป๊ะ*

2. **[กลาง]** เขียนฟังก์ชัน 2 ตัว: `to_uppercase_label(name: String) -> String` ที่รับชื่อสินค้าเข้ามา แปลงเป็น
   ตัวพิมพ์ใหญ่ทั้งหมดด้วย method `.to_uppercase()` (คืนค่าเป็น `String` ใหม่) แล้ว return กลับไป จากนั้นเขียน
   `add_price_tag(label: String, price: f64) -> String` ที่รับ label เข้ามา ต่อข้อความราคาเข้าไปด้วย `format!`
   (เช่น `format!("{label} - {price} บาท")`) แล้ว return กลับ ทดสอบเรียกทั้งสองฟังก์ชันต่อกันเป็น chain ใน `main`
   โดยใช้ shadowing เหมือนตัวอย่างในหัวข้อ 6.11

   *Hint: `f64` เป็น `Copy` ดังนั้น `price` ยังใช้ต่อได้แม้ส่งเข้าฟังก์ชันไปแล้ว ต่างจาก `String`*

3. **[ยาก]** จำลองระบบ "ยืมหนังสือห้องสมุด" แบบง่าย ๆ โดยเขียนฟังก์ชันต่อไปนี้ (ทั้งหมดรับ/คืนกรรมสิทธิ์ของ `String`
   ที่แทนชื่อหนังสือแบบเต็มรูปแบบ ไม่ใช้ reference เลยในข้อนี้ เพื่อฝึกความเข้าใจเรื่อง move chain):
   - `checkout_book(title: String, borrower: String) -> String` — พิมพ์ข้อความ "ยืม {title} โดย {borrower}"
     แล้ว return `title` กลับไป (สมมติว่า `borrower` ไม่ต้องใช้ต่อ ปล่อยให้ถูก drop ไปในฟังก์ชันนี้)
   - `return_book(title: String) -> String` — พิมพ์ข้อความ "คืนหนังสือ {title} เรียบร้อย" แล้ว return `title` กลับไป
   - `archive_book(title: String)` — พิมพ์ข้อความ "จัดเก็บ {title} เข้าชั้นถาวร" (ไม่ return อะไร — จบสาย)

   เขียน `main` ที่สร้างชื่อหนังสือและชื่อผู้ยืม แล้วเรียกทั้งสามฟังก์ชันต่อกันเป็นห่วงโซ่ที่ถูกต้องตามกฎ ownership
   (ห้ามใช้ `.clone()` เลยในข้อนี้ — บังคับให้ต้องออกแบบลำดับการเรียกและการรับค่าคืนให้ถูกต้อง)

   *Hint: ทบทวนตัวอย่างคลังสินค้าในหัวข้อ 6.11 — โครงสร้างเหมือนกันเป๊ะ เพียงเปลี่ยนชื่อฟังก์ชัน/ตัวแปร*

4. **[ยาก/ประยุกต์]** โค้ดด้านล่างนี้มี **บั๊กเชิง ownership 2 จุด** ที่ทำให้ compile ไม่ผ่าน จงหาทั้งสองจุด อธิบายว่า
   ทำไมแต่ละจุดถึงผิด (อ้างอิงกฎข้อไหนของ ownership) แล้วแก้ไขให้ compile ผ่านโดย**แก้แค่วิธีเรียกใช้ฟังก์ชันใน `main`
   เท่านั้น** (ห้ามเปลี่ยน signature ของฟังก์ชันทั้งสามตัว และห้ามเพิ่ม `.clone()` แม้แต่ครั้งเดียว — เป็นไปได้เสมอ
   ถ้าจัดการรับค่าที่ return กลับมาให้ถูกต้อง):

   ```rust
   fn log_transaction(item: String) -> String {
       println!("[LOG] ทำรายการ: {item}");
       item // คืนกรรมสิทธิ์กลับไปให้ผู้เรียก เพื่อให้ขั้นตอนถัดไปใช้ต่อได้
   }

   fn ship_item(item: String) -> String {
       println!("[SHIP] จัดส่งสินค้า: {item}");
       item // คืนกรรมสิทธิ์กลับไปให้ผู้เรียกเช่นกัน
   }

   fn notify_customer(item: String) {
       println!("[NOTIFY] แจ้งลูกค้าว่าสินค้า {item} จัดส่งแล้ว");
       // ฟังก์ชันนี้เป็นขั้นตอนสุดท้ายของ workflow โดยตั้งใจ — ไม่ return กรรมสิทธิ์กลับ
   }

   fn main() {
       let item = String::from("โน้ตบุ๊ก");

       ship_item(item);
       log_transaction(item);
       notify_customer(item);
   }
   ```

   จากนั้นตอบคำถามเชิงแนวคิดสั้น ๆ (3-5 บรรทัด): ทำไม Rust ถึงเลือกให้ compiler ปฏิเสธโค้ดแบบนี้ตั้งแต่ compile time
   แทนที่จะยอมให้ compile ผ่านแล้วปล่อยให้เกิดปัญหาตอน runtime แบบภาษาที่ไม่มีการตรวจสอบชนิดนี้ (เชื่อมโยงกับแนวคิด
   "zero-cost abstraction" และตารางเปรียบเทียบ 3 แนวทางจัดการ memory ในหัวข้อ 6.1)

   *Hint: จุดบั๊กแรกคือ `ship_item(item)` ไม่ได้เก็บค่าที่ return กลับมา (ค่าที่คืนมาเลยหายไปเฉย ๆ แม้ฟังก์ชันจะคืน
   กรรมสิทธิ์ให้ก็ตาม) ทำให้ `item` เดิมยังถือว่าถูก move ไปแล้วตั้งแต่บรรทัดนั้น — ต้องเก็บด้วย
   `let item = ship_item(item);` จุดบั๊กที่สองคือ `log_transaction(item)` ก็มีปัญหาเดียวกัน — มัน return `String`
   กลับมาเช่นกัน แต่ `main` ไม่ได้เก็บค่านั้นไว้ ต้องเขียน `let item = log_transaction(item);` ด้วย เมื่อแก้ทั้งสองจุด
   แล้ว `notify_customer(item)` (ซึ่งตั้งใจให้เป็นขั้นตอนสุดท้ายที่ไม่คืนกรรมสิทธิ์) จะเรียกได้ตามปกติโดยไม่ต้องแก้อะไร
   เพิ่มเลย — โครงสร้างนี้เหมือนกับตัวอย่างคลังสินค้าในหัวข้อ 6.11 ทุกประการ*

## สรุป

บทนี้คือบทที่สำคัญที่สุดในหลักสูตรทั้งหมด เพราะ Ownership คือแนวคิดที่ทำให้ Rust แตกต่างจากภาษาโปรแกรมมิ่งอื่นเกือบทุกภาษา
เราเริ่มจากปัญหาคลาสสิกที่ทุกภาษาต้องเลือก: **จัดการ memory ด้วยมือ** (เร็วแต่เสี่ยง use-after-free/double-free แบบ
C/C++) หรือ **ใช้ garbage collector** (ปลอดภัยแต่มี runtime overhead และ pause ที่คาดเดาไม่ได้) — Rust เลือกทางที่สาม
คือให้ **compiler ตรวจสอบกฎการใช้ memory ตอน compile time** ผ่านระบบ Ownership ทำให้ได้ทั้งความปลอดภัยและความเร็ว
โดยไม่ต้องแลกอะไรเลยตอน runtime

เราเข้าใจความแตกต่างระหว่าง **stack** (เร็ว, LIFO, ต้องรู้ขนาดตายตัวตอน compile time) กับ **heap** (ยืดหยุ่นกว่า
แต่ช้ากว่า, ขนาดปรับได้ระหว่างรัน) และเห็นว่า `String` คือชนิดข้อมูลแรกในหลักสูตรที่จัดสรร buffer บน heap ของตัวเอง
(ต่างจาก `&str` literal ที่ฝังอยู่ใน binary) เราท่องกฎ 3 ข้อของ ownership ได้แล้ว: **(1) ทุกค่ามีเจ้าของเดียว
(2) เจ้าของได้ครั้งละหนึ่งเดียวในเวลาใดเวลาหนึ่ง (3) เมื่อเจ้าของหมด scope ค่าจะถูก drop โดยอัตโนมัติ** และเห็นกลไก
`Drop` ที่ทำให้กฎข้อ 3 เกิดขึ้นจริงโดยไม่ต้องมี garbage collector

เราเรียนรู้ **move semantics** ผ่านตัวอย่าง `let s2 = s1;` ที่ทำให้ `s1` ใช้ต่อไม่ได้ (error `E0382`) เพื่อป้องกัน
double-free ของข้อมูลบน heap และเข้าใจว่า **`.clone()`** คือวิธีขอ deep copy อย่างชัดเจนเมื่อต้องการสองสำเนาที่เป็น
อิสระจากกันจริง ๆ (พร้อมต้นทุนที่ต้องแลก) เราเปรียบเทียบกับ **`Copy` trait** ที่ทำให้ `i32`, `bool`, `char`, `f64`
และ tuple ของชนิดเหล่านี้ copy ได้อย่างอิสระโดยไม่ต้อง move เพราะไม่มี heap resource ต้องกังวลเรื่องเจ้าของซ้ำ
สุดท้ายเราเห็นว่ากฎเดียวกันนี้ใช้กับ**การส่งค่าเข้าฟังก์ชันและการ return ค่ากลับ** ทำให้เกิด "ห่วงโซ่การโอนกรรมสิทธิ์"
(move chain) ที่เราสาธิตผ่านตัวอย่างระบบคลังสินค้า

ปัญหาที่เราเจอชัดเจนในหัวข้อ 6.10 คือ: การต้อง "รับกรรมสิทธิ์คืนกลับ" ทุกครั้งที่ต้องการแค่ "อ่าน" ค่าจากฟังก์ชัน
เป็นเรื่องยุ่งยากเกินความจำเป็นมาก — **Part 7: Borrowing และ References** จะแก้ปัญหานี้โดยตรง เราจะเรียนรู้วิธี
"ยืม" ค่ามาใช้ชั่วคราวผ่าน `&T` และ `&mut T` โดยไม่ต้องโอนกรรมสิทธิ์เลย พร้อมกฎของ **borrow checker** ที่ compiler
ใช้ตรวจสอบว่าการยืมนั้นปลอดภัยเสมอ (ไม่มีใครเขียนพร้อมกับที่อีกคนอ่าน) — นี่คือกลไกที่ทำให้ Rust เขียนโปรแกรมได้สะดวก
เทียบเท่าภาษาที่มี GC โดยยังคงความปลอดภัยและความเร็วของ ownership ไว้ครบถ้วน
