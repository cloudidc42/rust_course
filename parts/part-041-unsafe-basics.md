# Part 41: Unsafe Rust เบื้องต้น

> โมดูล: ระดับสูง (Advanced) | ระดับ: สูง | เวลาโดยประมาณ: 240 นาที

## เป้าหมายของบทเรียน

หลังจากจบบทนี้ คุณจะสามารถ:

- อธิบายได้อย่างแม่นยำว่า **ทำไม `unsafe` ต้องมีอยู่ในภาษา Rust เลย** — เข้าใจขอบเขตที่แท้จริงของ static analysis
  ของ borrow checker ว่ามันพิสูจน์ความปลอดภัยได้แค่ไหน และมีสถานการณ์จริงแบบไหนบ้างที่ **มนุษย์พิสูจน์ความปลอดภัยได้
  ด้วยตัวเอง แต่ compiler พิสูจน์ให้ไม่ได้ด้วย static analysis เพียงอย่างเดียว**
- ท่องจำและอธิบาย **ห้าสิ่งที่เขียนได้เฉพาะภายใน `unsafe` block** ได้ครบทั้งห้าข้อ พร้อมยกตัวอย่าง syntax ของแต่ละข้อ
  และเข้าใจว่านี่คือ**รายการที่ตายตัวและถูกจำกัดไว้อย่างตั้งใจ** ไม่ใช่โหมด "ปิดกฎทั้งหมด" แบบที่มือใหม่มักเข้าใจผิด
- พิสูจน์ให้ตัวเองเห็นด้วยโค้ดจริงว่า `unsafe` **ไม่ได้ปิด** borrow checker, ไม่ได้ปิด move semantics, และไม่ได้ปิด
  การตรวจสอบ type ส่วนใหญ่ของ Rust เลย — ขอบเขตของมันเล็กและเจาะจงมาก
- เขียนและอ่าน `unsafe fn` ได้อย่างถูกต้อง เข้าใจว่า **สัญญาความปลอดภัย (safety contract)** ของมันคืออะไร ทำไม
  compiler ตรวจสอบสัญญานั้นไม่ได้ และทำไมเอกสาร `# Safety` (จาก Part 34) ถึงสำคัญมากขนาดต้องมีอยู่ในทุก `unsafe fn`
  ที่เป็น public API
- อธิบายได้ว่า **undefined behavior (UB)** อันตรายกว่า compile error ทั่วไปอย่างไร — เข้าใจว่าทำไมโค้ด `unsafe`
  ที่ผิดอาจ "ดูเหมือนทำงานได้" ตอน test แล้วพังตอน production โดยไม่มีสัญญาณเตือนล่วงหน้าเลย
- ออกแบบ **safe abstraction เหนือ unsafe code** ได้ — เขียนฟังก์ชัน `unsafe` ที่เล็กและตรวจสอบได้ง่าย แล้วห่อด้วย
  safe API ที่ signature ของมันทำให้ผู้เรียกใช้ **ไม่มีทางเรียกผิดได้เลย** ไม่ว่าจะส่ง input อะไรมาก็ตาม — หลักการ
  เดียวกันที่ `Vec<T>`, `String`, `Rc<T>`, และ `Mutex<T>` ใช้อยู่ภายในตัวเองทั้งหมด
- เขียน simplified version ของ `split_at_mut` ได้ด้วยตัวเอง — เข้าใจตัวอย่างในตำนานที่สุดของวัฒนธรรม Rust ว่าทำไม
  ฟังก์ชันนี้ **เขียนด้วย safe Rust ล้วน ๆ ไม่ได้เลย** ทั้งที่การใช้งานมันปลอดภัย 100% เสมอ

## ความรู้ที่ต้องมีมาก่อน

บทนี้คือ**จุดเปลี่ยนทางปรัชญาที่ใหญ่ที่สุดของหลักสูตรทั้งหมด** เพราะทุกอย่างที่เรียนมาตั้งแต่ Part 6 ถูกออกแบบมาให้
compiler เป็นผู้พิสูจน์ความปลอดภัยให้เราโดยอัตโนมัติ แต่บทนี้จะแสดงให้เห็นว่ามีขอบเขตที่ compiler พิสูจน์ให้ไม่ได้อยู่จริง
และเมื่อถึงขอบเขตนั้น **หน้าที่การพิสูจน์จะย้ายมาอยู่ที่ตัวคุณเอง** ความรู้ที่ต้องมีมาก่อนสำคัญที่สุดคือ:

- **Part 6 (Ownership เบื้องต้น) และ Part 7 (Borrowing และ References)** — นี่คือสองบทที่สำคัญที่สุดสำหรับบทนี้
  โดยเฉพาะ **กฎเหล็กสองข้อของ borrowing** (ห้าม mutable reference กับ immutable reference อยู่พร้อมกัน, ห้าม
  dangling reference) ที่ borrow checker ตรวจสอบให้แบบอัตโนมัติมาตลอด 34 บทที่ผ่านมาโดยที่เราไม่ต้องคิดถึงมันเลย
  บทนี้จะแสดงให้เห็นว่า **กฎเดียวกันนี้ยังคงมีผลอยู่จริงแม้ในโค้ดที่มี `unsafe`** — เราไม่ได้ "ทิ้ง" กฎจาก Part 6-7
  ไปเลย เราแค่เพิ่ม**พื้นที่แคบ ๆ** ที่กฎอื่นบางข้อ (ไม่ใช่ทั้งหมด) ถูกยกให้เป็นความรับผิดชอบของมนุษย์แทน
- **Part 3 (ตัวแปร ชนิดข้อมูลพื้นฐาน และ Mutability)** — หัวข้อเรื่อง `static` ที่ทิ้งท้ายไว้สั้น ๆ ว่า `static mut`
  ต้องอยู่ใน `unsafe` block เสมอ พร้อมประโยคที่บอกตรง ๆ ว่า **"จะเจาะลึกเรื่อง `unsafe` ใน Part 41"** — บทนี้คือคำตอบ
  เต็มรูปแบบของประโยคนั้น
- **Part 34 (Documentation: rustdoc)** — หัวข้อ `# Safety` section ที่แนะนำไว้สั้น ๆ ว่าใช้กับ `unsafe fn` เพื่อ
  อธิบาย invariant ที่ผู้เรียกต้องรักษา และบอกไว้ว่า **"รายละเอียดเต็มของ `unsafe` อยู่ในบทว่าด้วย unsafe Rust
  โดยตรง"** — บทนี้จะอธิบายเหตุผลเชิงลึกแบบสมบูรณ์ว่าทำไม `# Safety` ต้องมีอยู่ และทำไมมันคือ**เอกสารที่สำคัญที่สุด**
  ในทุก public API ที่เป็น `unsafe fn`
- **Part 13-14 (Collections: `Vec<T>`, `String`)** — เราใช้ทั้งสอง type นี้มาตลอดหลักสูตรในฐานะ "safe container"
  ที่ใช้งานได้โดยไม่ต้องคิดเรื่อง memory เลย บทนี้จะเฉลยว่า **เบื้องหลัง `Vec<T>` และ `String` เต็มไปด้วย `unsafe`**
  (raw pointer, manual memory allocation) และนี่คือตัวอย่างที่สมบูรณ์แบบที่สุดของหลักการ "safe abstraction เหนือ
  unsafe code" ที่เป็นแก่นของบทนี้
- **Part 28 (Smart Pointers: `Rc<T>` และ `RefCell<T>`) และ Part 39 (Mutex, Arc)** — ทั้ง `Rc<T>` (reference
  counting แบบไม่ atomic) และ `Mutex<T>`/`Arc<T>` (locking และ atomic reference counting) ก็ใช้ `unsafe`
  ภายในเช่นกันเพื่อทำ interior mutability และ synchronization ที่ safe Rust ล้วน ๆ ทำไม่ได้
- **Part 40 (Send, Sync และความปลอดภัยของ Concurrency)** — บทที่เพิ่งปิดโมดูล 2 ไป อธิบายว่า compiler พิสูจน์ความ
  ปลอดภัยของ concurrency ได้อย่างสมบูรณ์ผ่าน auto trait `Send`/`Sync` โดยไม่ต้องมี `unsafe` เลยในโค้ดระดับผู้ใช้ทั่วไป
  — แต่คำถามที่ Part 40 ไม่ได้ตอบคือ "แล้ว `Send`/`Sync` ของ `Rc<T>`, `Arc<T>` เองถูก implement ยังไง ในเมื่อ
  compiler คำนวณ auto trait นี้แบบอัตโนมัติจาก field?" คำตอบคือ **`unsafe impl`** ซึ่งเป็นหนึ่งในห้าสิ่งที่บทนี้
  จะอธิบาย

ถ้าคุณจำได้ว่า Part 20 (บทสุดท้ายของโมดูล 1) ปิดท้ายด้วยประโยค **"Rust ทำให้โปรแกรมปลอดภัยจาก use-after-free,
double-free, dangling pointer, และ data race ได้ทั้งหมด โดยไม่ต้องมี garbage collector และไม่มี runtime cost เลย
แม้แต่นิดเดียว"** — บทนี้จะเติมส่วนที่ประโยคนั้น "ไม่ได้พูดถึง" ให้ครบ: ประโยคนั้นเป็นจริง **สำหรับ safe Rust**
เท่านั้น และคำถามที่ต้องเผชิญตอนนี้คือ — **แล้วใครพิสูจน์ความปลอดภัยให้กับส่วนที่ไม่ใช่ safe Rust?**

## เนื้อหา

### 41.1 เปิดโมดูล 3: จาก "compiler พิสูจน์ให้" สู่ "คุณต้องพิสูจน์เอง"

Part 21 ถึง Part 40 คือ **โมดูล 2: ระดับกลาง (Intermediate)** — ยี่สิบบทที่พาเราเจาะลึกสามเสาหลักจากโมดูล 1
(generics, traits, lifetimes) ให้ซับซ้อนขึ้นอีกขั้น, สอนแนวคิดฟังก์ชันนัลอย่าง closures และ iterators, เปิดเผยว่า
smart pointer อย่าง `Box`, `Rc`, `RefCell`, `Weak`, `Cow` ทำงานอย่างไร, สอน error handling และ testing และ
documentation ระดับมืออาชีพ, และปิดท้ายด้วยสามบทเรื่อง concurrency (`thread`, `mpsc`, `Mutex`/`Arc`) ที่จบลงด้วย
Part 40 ซึ่งอธิบายว่า `Send`/`Sync` ทำให้ compiler ตรวจจับบั๊ก data race ได้ **ก่อน**โปรแกรมรันด้วยซ้ำ

สังเกตสิ่งที่ **ทุกบทในยี่สิบบทนั้นมีเหมือนกัน**: ไม่ว่าเนื้อหาจะซับซ้อนแค่ไหน ทุกตัวอย่างโค้ดที่เราเขียนคือ
**safe Rust** ทั้งหมด — เราไม่เคยต้องเขียนคำว่า `unsafe` แม้แต่ครั้งเดียวเพื่อให้โค้ดทำงาน (ยกเว้นการเกริ่นสั้น ๆ
ใน Part 3 และ Part 34 ที่บอกไว้ตรง ๆ ว่า "รอไปเรียนเต็ม ๆ ใน Part 41") นี่ไม่ใช่เรื่องบังเอิญ — มันคือ**แก่นสำคัญ
ที่สุดของปรัชญาการออกแบบ Rust**: ระบบ ownership, borrowing, lifetime, และ trait ทั้งหมดที่เรียนมา ถูกออกแบบมา
อย่างตั้งใจให้ **compiler พิสูจน์ความปลอดภัยของหน่วยความจำและ concurrency ได้เองแบบ mechanical (คำนวณตามกฎที่
ตายตัว ไม่ต้องใช้วิจารณญาณของมนุษย์) ที่ compile time** โดยไม่ต้องพึ่งความไว้วางใจในตัวโปรแกรมเมอร์เลยแม้แต่นิดเดียว

**โมดูล 3: ระดับสูง (Advanced)** ที่บทนี้เป็นบทแรก คือจุดที่เราเดินออกจากพื้นที่ปลอดภัยนั้นเป็นครั้งแรกอย่างเป็น
ทางการ คำถามใหญ่ที่บทนี้ตอบคือ: **ถ้า compiler พิสูจน์ความปลอดภัยให้เราได้ดีขนาดนี้ แล้วทำไม Rust ยังต้องมีทางให้
"หนี" ออกจากการพิสูจน์นั้นด้วย?** และคำตอบคือสิ่งที่ทำให้ Rust แตกต่างจากภาษาที่มี garbage collector อย่างสิ้นเชิง:
**มีงานจริงบางอย่างที่มีค่าและจำเป็น ซึ่ง static analysis ของ borrow checker พิสูจน์ความปลอดภัยให้ไม่ได้ ทั้งที่
มนุษย์ที่มีบริบทเพียงพอสามารถพิสูจน์ความปลอดภัยของมันได้ด้วยตัวเอง** — `unsafe` คือ**ประตูที่ถูกควบคุมอย่างเข้มงวด**
ที่เปิดให้ทำงานเหล่านั้นได้ โดยที่**ภาระการพิสูจน์**ถูกโยกจาก compiler มาที่คุณ

บทนี้เปิดโมดูลใหม่ทั้งหมด และเนื้อหาของมันจะเป็นรากฐานให้กับอีกหลายบทถัดไปในโมดูล 3: **Part 42 (Raw Pointers และ
Memory Layout)** จะเจาะลึก `*const T`/`*mut T` แบบเต็มรูปแบบ, **Part 43 (FFI)** จะใช้ `unsafe fn` เพื่อเรียก
โค้ด C จริง, และอีกหลายบทเรื่อง async/atomics ในโมดูลนี้ก็จะพึ่งพาความเข้าใจเรื่อง `unsafe` จากบทนี้เป็นพื้นฐาน
เหมือนที่ Part 20 เป็นรากฐานให้กับทั้งโมดูล 2

ก่อนเข้าเนื้อหาหลัก ลองทวนภาพรวมของ "สามชั้นการพิสูจน์อัตโนมัติ" ที่ทำให้ safe Rust (Part 6-40) ปลอดภัยได้โดยไม่
ต้องมี garbage collector อีกครั้งแบบสั้น ๆ เพื่อให้เห็นภาพว่าบทนี้กำลังจะ "เจาะรู" ผ่านชั้นไหนบ้าง:

| ชั้นการพิสูจน์ | สอนใน | พิสูจน์อะไร | ยังมีผลใน `unsafe` หรือไม่ |
|---|---|---|---|
| **Ownership** | Part 6 | ทุกค่ามีเจ้าของเดียว ไม่เกิด double-free | **มีผลเสมอ** (หัวข้อ 41.5 จะพิสูจน์) |
| **Borrowing** | Part 7 | ไม่มี mutable/immutable reference ปนกันในเวลาเดียวกัน ไม่เกิด dangling reference | **มีผลเสมอ** สำหรับ reference ทั่วไป (หัวข้อ 41.5) — แต่ **ไม่ครอบคลุม raw pointer** (นี่คือช่องว่างที่ `unsafe` เข้ามาเติม) |
| **Lifetime** | Part 20, 23 | reference ที่คืนจากฟังก์ชัน/เก็บใน struct จะไม่มีวัน dangling | มีผลกับ reference ทั่วไปเหมือนเดิม — raw pointer ไม่มี lifetime ติดตามให้ (Part 42) |
| **Send/Sync** | Part 40 | โค้ด concurrency ปลอดภัยจาก data race พิสูจน์ได้ตอน compile time | คำนวณอัตโนมัติจาก field เหมือนเดิม แต่ override ได้ด้วย `unsafe impl` (หัวข้อ 41.4.4) |

สังเกตจากคอลัมน์ขวาสุด: **`unsafe` ไม่ได้ "ปิด" ชั้นการพิสูจน์เหล่านี้เลยแม้แต่ชั้นเดียว** มันแค่เปิดทางให้ทำงานกับ
**raw pointer** ซึ่งเป็น type ที่อยู่ "นอก" ระบบการพิสูจน์ของ borrowing/lifetime มาตั้งแต่ต้น (raw pointer ไม่ใช่
reference — มันไม่มี lifetime parameter ผูกอยู่เลย) และเปิดทางให้ **override** ผลลัพธ์ของ auto trait ได้ (ด้วย
`unsafe impl`) ในกรณีที่มนุษย์มีความรู้มากกว่าที่ auto trait คำนวณเองได้ — นี่คือขอบเขตที่แท้จริงและแคบมากของสิ่ง
ที่ `unsafe` เปลี่ยนแปลง

### 41.2 `unsafe` คืออะไรกันแน่ (และที่สำคัญกว่า: มันไม่ใช่อะไร)

ก่อนอธิบายอะไรเพิ่ม เราต้องกำจัดความเข้าใจผิดที่พบบ่อยที่สุดและอันตรายที่สุดเกี่ยวกับคำว่า `unsafe` ก่อน เพราะถ้า
เข้าใจผิดตั้งแต่ประโยคแรก ทุกอย่างที่เรียนต่อจากนี้จะบิดเบือนไปหมด

**ความเข้าใจผิดที่ต้องกำจัด**: "`unsafe` คือการ 'ปิดสวิตช์' Rust ให้กลายเป็นภาษาแบบ C ที่ไม่มีการตรวจสอบอะไรเลย
เขียนอะไรก็ได้ตามใจ"

**ความจริง**: `unsafe` เป็นเพียงคำสั่งที่บอก compiler ว่า **"ต่อจากนี้ ฉันต้องการทำสิ่งใดสิ่งหนึ่งในรายการห้าอย่าง
ที่กำหนดไว้แน่นอนตายตัว (ดูหัวข้อ 41.4) และฉันรับผิดชอบพิสูจน์ความปลอดภัยของสิ่งนั้นด้วยตัวเองแทนที่จะให้ compiler
พิสูจน์ให้"** — มันไม่ได้ปิดการตรวจสอบชนิดข้อมูล (type checking) ไม่ได้ปิด borrow checker ไม่ได้ปิด move
semantics ไม่ได้ปิด `Drop`, ไม่ได้ปิดการตรวจสอบ trait bound ใด ๆ เลย มันเปิดให้ทำได้แค่**ห้าอย่างที่ระบุไว้ชัดเจน
เท่านั้น** และการตรวจสอบทุกอย่างที่เหลือของภาษายังทำงานเหมือนเดิมทุกประการ เราจะพิสูจน์ประโยคนี้ให้เห็นด้วยโค้ดจริง
ในหัวข้อ 41.5

เปรียบเทียบให้เห็นภาพชัดที่สุด: การเขียน `unsafe { }` **ไม่เหมือน** การใส่ `#[allow(warnings)]` ที่ปิด lint ทั้งหมด
แบบกว้าง ๆ แต่เหมือนกับการเซ็นเอกสารทางกฎหมายที่ระบุไว้ชัดเจนว่า **"ฉันรับผิดชอบเฉพาะข้อ ก, ข, ค ที่ระบุไว้ในสัญญา
นี้เท่านั้น กฎอื่นทั้งหมดที่ไม่ได้อยู่ในสัญญานี้ยังมีผลบังคับใช้ตามเดิม"**

ประโยคที่คนในชุมชน Rust พูดกันซ้ำ ๆ จนกลายเป็นหลักการที่ควรจำไว้ตลอดคือ: **"`unsafe` does not mean incorrect"**
(`unsafe` ไม่ได้แปลว่าโค้ดผิดหรือแปลว่าคุณภาพต่ำ) — โค้ด `unsafe` ที่เขียนอย่างถูกต้อง ผ่านการพิสูจน์อย่างรอบคอบ
และห่อด้วย safe abstraction ที่ดี (ตามหัวข้อ 41.8) **ปลอดภัยไม่แพ้ safe Rust เลย** จากมุมมองของผู้ใช้ปลายทาง —
สิ่งที่ต่างออกไปมีแค่ **"ใครเป็นผู้พิสูจน์"** เท่านั้น: safe Rust ให้ compiler พิสูจน์แบบอัตโนมัติ ในขณะที่ `unsafe`
ให้มนุษย์พิสูจน์เอง (แล้วบันทึกการพิสูจน์นั้นไว้ในคอมเมนต์ `// SAFETY:` ตามหัวข้อ 41.10) — คุณภาพของโค้ดไม่ได้ขึ้น
กับว่ามันมีคำว่า `unsafe` อยู่หรือไม่ แต่ขึ้นกับว่า**การพิสูจน์นั้นถูกต้องและมีหลักฐานรองรับหรือไม่** ต่างหาก

ทำไมการเข้าใจผิดนี้อันตรายมาก? เพราะถ้าใครเชื่อว่า `unsafe` คือ "ปิดกฎทั้งหมด" พวกเขาจะ:

1. **กลัว `unsafe` เกินความจำเป็น** — คิดว่าทุกครั้งที่เห็น `unsafe` ในโค้ด (เช่นใน `Vec<T>` ที่จะเห็นในหัวข้อ 41.8)
   คือสัญญาณว่าโค้ดนั้น "อันตรายมาก ไม่ควรเชื่อถือ" ทั้งที่จริง ๆ แล้วมันอาจเป็น safe abstraction ที่ผ่านการตรวจสอบ
   อย่างละเอียดแล้ว
2. **ประมาทเกินไปเมื่อเขียน `unsafe` เอง** — คิดว่าเมื่อเข้าสู่ `unsafe { }` แล้วสามารถเขียนอะไรก็ได้ตามใจ ทำให้
   ละเลยกฎอื่น ๆ ที่ยังบังคับใช้อยู่ (เช่นคิดว่าเขียน `let s2 = s; println!("{s}");` ใน `unsafe` block ได้โดยไม่ผิด
   move semantics — ซึ่งผิด เราจะพิสูจน์ในหัวข้อ 41.5)

ข้อสรุปที่ต้องจำไว้ตลอดทั้งบทนี้และตลอดการเขียน Rust ทั้งชีวิตการทำงาน: **`unsafe` คือคำที่แปลว่า "ต้องระวังเป็น
พิเศษ" ไม่ใช่คำที่แปลว่า "อนุญาตให้ทำอะไรก็ได้"** และขอบเขตของสิ่งที่มันอนุญาตนั้น **แคบและถูกกำหนดไว้ชัดเจนเป็นราย
การตายตัว** ซึ่งเราจะดูรายการนั้นทั้งหมดในหัวข้อ 41.4

### 41.3 ทำไม `unsafe` ต้องมีอยู่จริง: ขอบเขตของสิ่งที่ Static Analysis พิสูจน์ได้

Borrow checker คือ static analyzer — มันวิเคราะห์โค้ดโดย **ไม่รันโปรแกรมจริงเลย** และตัดสินใจว่าโค้ดปลอดภัยหรือไม่
จากกฎที่ตายตัว (mechanical rules) ล้วน ๆ ข้อดีมหาศาลของวิธีนี้คือความน่าเชื่อถือ 100% (ถ้า compile ผ่าน การันตีได้
ว่าไม่มี use-after-free แน่นอน) แต่ข้อเสียที่หลีกเลี่ยงไม่ได้ของ static analyzer แบบตายตัวทุกตัวคือ: **มันต้อง
ระมัดระวังแบบ conservative (ระแวงไว้ก่อนเสมอ) เพื่อไม่พลาดปฏิเสธโค้ดที่ปลอดภัยจริง ๆ แต่ "รูปแบบ" ของมันซับซ้อนเกิน
กว่าที่กฎตายตัวจะพิสูจน์ได้**

พูดให้เป็นรูปธรรม: มี**เซตของโปรแกรมที่ปลอดภัยจริง 100%** และมี**เซตของโปรแกรมที่ borrow checker พิสูจน์ได้ว่า
ปลอดภัย** — เซตที่สองเป็น**เซตย่อย**ของเซตแรกเสมอ (borrow checker ไม่เคยยอมให้โปรแกรมที่ไม่ปลอดภัยผ่านโดยไม่มี
`unsafe`) แต่**ไม่เท่ากัน** — มีโปรแกรมที่ปลอดภัยจริงอยู่จำนวนหนึ่งที่ borrow checker ปฏิเสธ เพราะการพิสูจน์ความ
ปลอดภัยของมันต้องใช้ความรู้เกี่ยวกับ**ความหมายเชิง runtime** ของโค้ด (เช่น "index สองตัวนี้ไม่มีทางเท่ากันเพราะ
เราเช็ค `mid <= len` ไว้แล้ว") ซึ่งเกินขอบเขตของกฎ static ที่ตรวจสอบแค่ **โครงสร้างของ type และ scope** เท่านั้น

ตัวอย่างคลาสสิกที่สุดของช่องว่างนี้ (และเป็น case study หลักของบทนี้ในหัวข้อ 41.9) คือฟังก์ชัน `split_at_mut`:
มันต้องคืน **mutable reference สองตัวไปยังคนละครึ่งของ slice เดียวกัน** ในทางความหมายจริง (semantically) สองครึ่ง
นี้**ไม่มีวันซ้อนกัน** เพราะมันถูกแบ่งด้วยตำแหน่ง (index) ที่ไม่ทับกัน — มนุษย์มองแล้วรู้ทันทีว่าปลอดภัย 100%
แต่ borrow checker **มองไม่เห็นความหมายนี้** มันเห็นแค่ว่า "มีการยืม `&mut` สองตัวจาก slice ตัวเดียวกัน" ซึ่งตรงกับ
รูปแบบที่มันถูกออกแบบมาให้ปฏิเสธเสมอ (ป้องกัน aliasing ของ mutable reference) — เราจะพิสูจน์และแก้ปัญหานี้แบบเต็ม
รูปแบบในหัวข้อ 41.9

ตัวอย่างอื่น ๆ ที่ borrow checker พิสูจน์ให้ไม่ได้ (แต่มนุษย์พิสูจน์ได้จริง) ที่ควรรู้จักไว้เป็นแผนที่ความคิด แม้จะ
ยังไม่เจาะลึกทุกตัวในบทนี้:

- **การเรียกฟังก์ชันภาษา C ผ่าน FFI** (Part 43): compiler ของ Rust ไม่มีทางรู้ว่าฟังก์ชัน C ที่ compile มาจากคนละ
  ภาษา คนละ toolchain นั้น จะปฏิบัติกับ pointer ที่ส่งเข้าไปอย่างไรบ้าง — ต้องอาศัยเอกสารของ C library และความ
  เข้าใจของมนุษย์เท่านั้น
- **การเข้าถึง memory-mapped hardware register ใน embedded programming**: การอ่าน/เขียนตำแหน่ง memory ที่ผูกกับ
  ฮาร์ดแวร์จริง (ไม่ใช่ RAM ปกติ) ต้องใช้ raw pointer เสมอ เพราะ borrow checker ไม่มีแนวคิดเรื่อง "ฮาร์ดแวร์" อยู่
  ในโมเดลของมันเลย
- **การสร้าง data structure ที่มี self-referential pointer หรือ cyclic structure ที่ซับซ้อนมาก** (เช่น doubly
  linked list แบบดั้งเดิม, บาง arena allocator): รูปแบบการอ้างอิงแบบนี้ต้านทานการพิสูจน์ด้วย lifetime ตามกฎของ
  borrow checker โดยธรรมชาติ (เราเห็นแนวทางแก้แบบ safe มาแล้วบางส่วนด้วย `Rc<RefCell<T>>` ใน Part 28 แต่มัน
  แลกมาด้วย runtime cost — บางสถานการณ์ที่ต้องการ performance สูงสุดจึงเลือกใช้ raw pointer แทน)
- **การ optimize โค้ดบางจุดที่รู้ล่วงหน้าว่าตรวจสอบซ้ำไม่จำเป็น**: เช่น `String::from_utf8_unchecked` ที่ข้ามการ
  ตรวจสอบว่า byte sequence เป็น UTF-8 ที่ถูกต้อง เพราะโปรแกรมเมอร์รู้แน่นอนอยู่แล้วว่าข้อมูลนั้นถูกตรวจสอบมาก่อนแล้ว
  จากแหล่งอื่น (เช่น อ่านมาจากไฟล์ที่เพิ่ง encode เป็น UTF-8 เองสด ๆ) การข้ามการตรวจซ้ำช่วยประหยัดเวลาได้จริงในโค้ด
  ที่ performance-critical
- **การสร้าง safe abstraction ขึ้นมาใหม่ (`Vec`, `Rc`, `Mutex` และเพื่อนของมันทั้งหมด)**: สิ่งเหล่านี้**ต้องถูก
  สร้างขึ้นมาจากอะไรสักอย่าง** — และที่ก้นบึ้งสุดของทุก safe abstraction ในโลก Rust (รวมถึงใน standard library เอง)
  คือ `unsafe` เสมอ เพราะไม่มีทางสร้าง memory allocator หรือ atomic counter ขึ้นมาจาก safe Rust ล้วน ๆ ได้ — ต้อง
  มีจุดหนึ่งที่คุยกับ raw memory โดยตรง

สังเกตว่าทุกตัวอย่างข้างบนมีลักษณะร่วมกัน: **มันคือปฏิบัติการที่มีค่าจริงและจำเป็นจริงในโลกของการเขียนโปรแกรมระดับ
ระบบ (systems programming)** — Rust ไม่ได้สร้าง `unsafe` ขึ้นมาเพื่อ "โกงกฎของตัวเอง" แต่สร้างขึ้นมาเพื่อให้ Rust
ยังคงใช้งานได้ในทุกที่ที่ C/C++ ใช้งานได้ (kernel, driver, embedded, high-performance library) โดยที่**ยังคง
ควบคุมพื้นที่เสี่ยงให้เล็กที่สุดและตรวจสอบได้ง่ายที่สุดเท่าที่จะทำได้** — นี่คือความแตกต่างที่สำคัญที่สุดระหว่าง
Rust กับ C: **C ไม่มีแนวคิดเรื่อง "safe" เลยด้วยซ้ำ ทุกอย่างเป็น unsafe ตลอดเวลาโดยปริยาย** ในขณะที่ Rust **แยก
พื้นที่ปลอดภัยกับพื้นที่เสี่ยงออกจากกันอย่างชัดเจนด้วย keyword เดียว** ทำให้เวลาเกิดบั๊กด้าน memory ขึ้นจริง คุณรู้
ทันทีว่าต้องไปมองหาที่ไหนก่อน (มองหาคำว่า `unsafe` ในโค้ด) ไม่ต้องสงสัยทั้งโปรแกรมเหมือนตอนเขียน C

#### เปรียบเทียบกับภาษาอื่น: ขอบเขตของโค้ด "เสี่ยง" ในแต่ละภาษา

เพื่อให้เห็นภาพว่าการมี keyword `unsafe` แบบมีขอบเขตชัดเจนนั้นพิเศษแค่ไหน ลองเทียบมุมมองของแต่ละภาษาต่อ "โค้ดที่
เสี่ยงต่อ memory safety" ดู:

| ภาษา | มีแนวคิด "โค้ดเสี่ยง" แยกจาก "โค้ดปลอดภัย" หรือไม่ | ผลที่ตามมา |
|---|---|---|
| **C / C++** | **ไม่มี** — ทุก pointer operation คือความเสี่ยงโดยปริยายตลอดเวลา ไม่มี keyword ใดแยกมันออกจากโค้ดทั่วไป | ต้องระวังทุกบรรทัดเท่ากันหมด ไม่มีทาง "มองหา" จุดเสี่ยงได้เร็วจากโครงสร้างโค้ดเอง ต้องอาศัยเครื่องมือแยก เช่น `ThreadSanitizer`/`AddressSanitizer`/Valgrind (ดูเพิ่มในหัวข้อ 41.7) |
| **Java / Python / JavaScript** | ไม่มีในระดับโค้ดผู้ใช้ทั่วไป — garbage collector และ managed runtime ซ่อน pointer ดิบไว้ทั้งหมด | ปลอดภัยจาก memory bug ประเภทนี้โดยธรรมชาติ แต่แลกมาด้วย runtime overhead ของ GC และไม่สามารถทำงานระดับต่ำมาก ๆ (เช่นเขียน OS kernel) ได้เลย |
| **Go** | มีบางส่วน — มี package ชื่อ `unsafe` ที่ให้เข้าถึง raw pointer ได้ (ส่วนใหญ่ใช้ตอนเขียน `cgo` หรือโค้ดภายในของ standard library เอง) | คล้าย Rust ในแง่ที่แยกโค้ดเสี่ยงออกมาชัดเจนด้วยชื่อ package แต่ **ไม่มีการตรวจสอบอะไรเพิ่มเติมเลย** เมื่อ import package นั้นมาใช้ — ต่างจาก Rust ที่ยังคง borrow checker และ type checking ทำงานอยู่ครบตามหัวข้อ 41.5 |
| **Rust** | **มีอย่างชัดเจน** — จำกัดไว้เพียง 5 ปฏิบัติการตายตัว (หัวข้อ 41.4) ที่เหลือทุกกฎยังบังคับใช้เหมือนเดิม | มองหาคำว่า `unsafe` ในโค้ดได้ทันที รู้แน่ชัดว่าต้อง audit ตรงไหนเป็นพิเศษ และกฎอื่นของภาษายังช่วยจับบั๊กที่ไม่เกี่ยวกับ memory (type mismatch, move ผิด ฯลฯ) ได้เหมือนเดิมทุกจุด |

ข้อสังเกตที่สำคัญที่สุดจากตารางนี้: **Rust ไม่ได้ "ประดิษฐ์" แนวคิดเรื่องโค้ดเสี่ยงขึ้นมาใหม่** — โค้ดเสี่ยงแบบนี้มี
อยู่จริงในทุกภาษาที่ทำงานระดับต่ำได้ (C, C++, และ `unsafe` package ของ Go) สิ่งที่ Rust ทำต่างออกไปคือ **แยกมันออก
มาให้เห็นชัดด้วย syntax และยังคงบังคับใช้กฎอื่นของภาษาทั้งหมดไปพร้อมกัน** ในขณะที่ C/C++ ไม่แยกเลย (ทุกอย่างเสี่ยง
เท่ากันหมดตลอดเวลา) — นี่คือเหตุผลที่คำพูดที่ว่า **"Rust ทำให้ systems programming ปลอดภัยขึ้นโดยไม่ต้องเสีย
ความสามารถในการทำงานระดับต่ำไปเลย"** เป็นความจริงในทางเทคนิค ไม่ใช่แค่คำโฆษณา

### 41.4 ห้าสิ่งที่ `unsafe` Block ปลดล็อก — และมีแค่ห้าอย่างนี้เท่านั้น

นี่คือหัวข้อที่สำคัญที่สุดในการกำจัดความเข้าใจผิดเรื่อง "unsafe = ปิดกฎทั้งหมด" ให้สิ้นซาก: `unsafe` block (หรือ
`unsafe fn`) ปลดล็อกให้ทำได้ **เฉพาะห้าปฏิบัติการนี้เท่านั้น** ไม่มีอย่างที่หกซ่อนอยู่ นี่คือรายการที่ตายตัวที่
กำหนดไว้ใน Rust Reference:

| # | ปฏิบัติการที่ปลดล็อก | เหตุผลที่ compiler ตรวจสอบเองไม่ได้ (สรุปสั้น) |
|---|---|---|
| 1 | Dereference raw pointer (`*const T`, `*mut T`) | ไม่มีการันตีเรื่อง lifetime หรือ aliasing ติดมากับ raw pointer เลย |
| 2 | เรียก `unsafe fn` (รวมถึงฟังก์ชัน FFI) | ฟังก์ชันนั้นมี precondition ที่ต้องตรวจสอบเอง compiler ตรวจให้ไม่ได้ |
| 3 | อ่าน/เขียนตัวแปร `static mut` | ตัวแปร global ที่ mutable ได้จากทุกที่ (รวมข้ามเธรด) เสี่ยง data race |
| 4 | Implement `unsafe trait` | trait นั้นมี invariant ที่ compiler ตรวจสอบให้ไม่ได้ ต้องอาศัยผู้ implement รับรอง |
| 5 | เข้าถึง field ของ `union` | ไม่รู้ว่า field ไหนถูก initialize ไว้จริง ๆ (ต่างจาก `enum` ที่มี tag บอก) |

มาดูตัวอย่าง syntax สั้น ๆ ของแต่ละข้อ เพื่อให้เห็นว่าแต่ละอย่างมีรูปร่างหน้าตาจริงเป็นอย่างไร (รายละเอียดเชิงลึก
ของข้อ 1 อยู่ใน Part 42, ข้อ 2 ที่เป็น FFI อยู่ใน Part 43 — ที่นี่แสดงแค่พอให้เห็นว่า syntax มีอยู่จริงและทำงาน
ได้จริง)

#### 41.4.1 Dereference Raw Pointer

```rust
fn main() {
    let x = 42;
    let raw_ptr: *const i32 = &x as *const i32; // สร้าง raw pointer ได้โดยไม่ต้อง unsafe

    // แต่การ "dereference" (ใช้ * เพื่ออ่านค่าที่มันชี้ไป) ต้องอยู่ใน unsafe block
    let value = unsafe { *raw_ptr };
    println!("ค่าที่ raw_ptr ชี้ไปคือ: {value}");
}
```

สังเกตว่า **การสร้าง raw pointer เอง (`&x as *const i32`) ไม่ต้องใช้ `unsafe`** — เฉพาะตอน **dereference**
(ใช้ `*` เพื่ออ่าน/เขียนค่าที่มันชี้ไป) เท่านั้นที่ต้องอยู่ใน `unsafe` block เหตุผลคือการสร้าง raw pointer เป็นแค่
"การคำนวณเลข address" ซึ่งปลอดภัยเสมอไม่ว่า address นั้นจะถูกต้องหรือไม่ — อันตรายเกิดขึ้นเฉพาะตอนที่คุณ**ใช้
address นั้นไปอ่าน/เขียน memory จริง** ต่างหาก (รายละเอียดเต็มของ raw pointer และเหตุผลที่มันไม่มีการันตีเรื่อง
lifetime/aliasing เหมือน reference ทั่วไปจะอยู่ใน Part 42)

`*mut T` (raw pointer แบบ mutable) dereference ได้ทั้งอ่านและเขียนภายใน `unsafe` block เดียวกัน:

```rust
fn main() {
    let mut x = 10;
    let raw_mut_ptr: *mut i32 = &mut x as *mut i32; // สร้าง raw mutable pointer — ยังไม่ต้อง unsafe

    unsafe {
        *raw_mut_ptr = 99; // เขียนค่าใหม่ผ่าน raw pointer โดยตรง — ต้องอยู่ใน unsafe
    }

    println!("ค่าของ x หลังแก้ไขผ่าน raw pointer: {x}");
}
```

ผลลัพธ์:

```
ค่าของ x หลังแก้ไขผ่าน raw pointer: 99
```

สังเกตว่า `x` เปลี่ยนค่าจริงเป็น `99` แม้เราไม่ได้แก้ผ่าน `x` ตรง ๆ เลย (เราแก้ผ่าน `raw_mut_ptr` ที่ชี้ไปยัง
ตำแหน่ง memory เดียวกันกับ `x`) — นี่คือพลังของ raw pointer ที่ต่างจาก `&mut i32` ทั่วไป: **compiler ไม่ได้
ติดตาม "aliasing" ของ raw pointer เหมือนที่ติดตาม `&mut` reference** คุณสามารถมี `*mut T` หลายตัวชี้ไปยังที่
เดียวกันพร้อมกันได้โดย compiler ไม่ฟ้อง (ต่างจาก `&mut T` ที่กฎเหล็กข้อ 1 ของ Part 7 ห้ามไว้เด็ดขาด) — ภาระในการ
รับรองว่าจะไม่เกิดปัญหาจาก aliasing แบบนี้จึงตกไปอยู่ที่คุณทั้งหมด (รายละเอียดเต็มของกฎ aliasing ของ raw pointer
คือเนื้อหาหลักของ Part 42)

#### 41.4.2 เรียก `unsafe fn`

```rust
/// # Safety
///
/// ฟังก์ชันนี้ไม่มี precondition พิเศษ (เป็นตัวอย่าง syntax ล้วน ๆ)
unsafe fn dangerous_operation() -> i32 {
    99
}

fn main() {
    // การเรียก unsafe fn ต้องอยู่ใน unsafe block เสมอ — เพื่อ "ยืนยัน" ว่าผู้เรียกได้ตรวจสอบ
    // สัญญาความปลอดภัยของฟังก์ชันนั้นแล้วจริง ๆ (รายละเอียดเต็มอยู่ในหัวข้อ 41.6)
    let result = unsafe { dangerous_operation() };
    println!("ผลลัพธ์: {result}");
}
```

รายการนี้ครอบคลุมถึง**การเรียกฟังก์ชันจากภาษา C ผ่าน FFI** ด้วย เพราะทุกฟังก์ชัน FFI ถูกประกาศเป็น `unsafe fn`
โดยอัตโนมัติ (compiler ของ Rust ไม่มีทางตรวจสอบความถูกต้องของโค้ด C ที่ compile มาจากคนละ toolchain ได้เลย)
ตัวอย่างสั้น ๆ ที่เรียกฟังก์ชัน `abs` จาก C standard library ที่ระบบปฏิบัติการ Linux/macOS เชื่อมโยง (link) ให้
กับทุกโปรแกรมโดยอัตโนมัติอยู่แล้ว:

```rust
extern "C" {
    fn abs(input: i32) -> i32;
}

fn main() {
    unsafe {
        println!("ค่า absolute ของ -7 ตามฟังก์ชัน C: {}", abs(-7));
    }
}
```

Part 43 จะเจาะลึกเรื่อง FFI แบบเต็มรูปแบบ (การประกาศ `extern "C"` block, ABI, การจัดการ memory ข้ามภาษา,
`bindgen`) ที่นี่แค่ให้เห็นว่ามันคือการประยุกต์ใช้ "เรียก unsafe fn" ข้อเดียวกันนี้เอง ไม่ใช่กลไกพิเศษแยกต่างหาก

#### 41.4.3 อ่าน/เขียนตัวแปร `static mut`

```rust
static mut REQUEST_COUNTER: u32 = 0;

fn record_request() {
    unsafe {
        REQUEST_COUNTER += 1;
    }
}

fn main() {
    record_request();
    record_request();
    record_request();

    // อ่านค่าออกมาเก็บใน local variable ก่อน แล้วค่อย print — หลีกเลี่ยงการสร้าง reference
    // ไปยัง static mut โดยตรง (จะอธิบายเหตุผลเชิงลึกเรื่องนี้ในกับดักที่พบบ่อยข้อที่ 5)
    let count = unsafe { REQUEST_COUNTER };
    println!("จำนวน request ทั้งหมด: {count}");
}
```

Part 3 ทิ้งท้ายไว้แล้วว่า `static mut` ควรหลีกเลี่ยงในโค้ดจริงแทบทุกกรณี เพราะตัวแปร global ที่ mutable ได้จาก
ทุกที่ (รวมถึงจากหลายเธรดพร้อมกัน) คือสาเหตุคลาสสิกของ data race — และตอนนี้เราเห็นเหตุผลที่แท้จริงแล้วว่าทำไม
Rust ต้องบังคับให้อยู่ใน `unsafe`: **compiler ไม่มีทางรู้ว่ามีใครกำลังเข้าถึง `REQUEST_COUNTER` พร้อมกันจากเธรดอื่น
อยู่หรือไม่** (ต่างจาก `Mutex<T>` ที่เรียนใน Part 39 ที่บังคับให้ต้อง `.lock()` ก่อนเข้าถึงเสมอ ทำให้ compiler
รับประกันผ่าน type system ได้) — ในทางปฏิบัติจริง โค้ด production สมัยใหม่แทบไม่ใช้ `static mut` เลย นิยมใช้
`Mutex`/`Arc` (Part 39) หรือ `AtomicU32`/`OnceLock` (จะเรียนใน Part 51 และหลังจากนั้น) แทนเสมอ

#### 41.4.4 Implement `unsafe trait`

```rust
/// trait นี้มี "สัญญา" ที่ compiler ตรวจสอบให้ไม่ได้: ทุก type ที่ implement ต้องรับประกันว่า
/// ข้อมูลภายในไม่มี padding byte ที่ไม่ได้ initialize เมื่อแปลงเป็น byte slice ตรง ๆ
unsafe trait SafeToTransmute {}

struct SensorReading {
    temperature: f32,
    humidity: f32,
}

// ผู้ implement ต้องยืนยันด้วย "unsafe impl" ว่าได้ตรวจสอบเงื่อนไขที่ trait กำหนดไว้แล้วจริง ๆ
unsafe impl SafeToTransmute for SensorReading {}

fn main() {
    let reading = SensorReading { temperature: 25.5, humidity: 60.0 };
    println!("อุณหภูมิ: {} องศา, ความชื้น: {}%", reading.temperature, reading.humidity);
}
```

`unsafe trait` เป็นรายการที่มือใหม่มักงงที่สุด เพราะการ**ประกาศ** trait ว่าเป็น `unsafe trait` ไม่ได้ทำให้ตัว
trait นั้นมี method ที่ "อันตราย" อะไรเลย — สิ่งที่มันบอกจริง ๆ คือ **"trait นี้มี invariant ที่ code ส่วนอื่นของ
โปรแกรมจะ 'เชื่อ' โดยไม่ตรวจสอบซ้ำ ถ้ามีใคร implement trait นี้ผิด โค้ดส่วนอื่นที่เชื่อใจ invariant นี้จะพังทันที
โดยไม่มีการเตือน"** ตัวอย่างที่แท้จริงที่สุดของ `unsafe trait` ใน standard library ก็คือ `Send` และ `Sync`
ที่เรียนใน Part 40 นั่นเอง — ปกติ compiler คำนวณให้อัตโนมัติแบบ auto trait แต่ถ้าคุณต้องการ**บอกด้วยตัวเอง**ว่า
type ของคุณปลอดภัยที่จะส่งข้ามเธรด (เช่นเพราะคุณ implement การป้องกัน data race เองแล้วด้วยกลไกที่ compiler มอง
ไม่เห็น) คุณต้องเขียน `unsafe impl Send for MyType {}` — และการเขียนแบบนี้คือการที่คุณ**เอาชีวิตเข้าไปเป็นประกัน**
ว่า invariant ของ `Send` (ปลอดภัยที่จะย้ายข้ามเธรด) เป็นจริงสำหรับ type นี้จริง ๆ ไม่ใช่ compiler ตรวจให้

ตัวอย่างที่ใกล้เคียงกับสถานการณ์จริงมากขึ้น (และเป็นสิ่งที่ Part 43 เรื่อง FFI จะเจอบ่อย): struct ที่ห่อ handle
จากไลบรารี C เอาไว้ — auto trait ปกติจะไม่ implement `Send`/`Sync` ให้กับ raw pointer โดยอัตโนมัติ (เพราะ
compiler ไม่รู้ว่า C library รับประกันความปลอดภัยข้ามเธรดหรือไม่) แต่ถ้าเรา**อ่านเอกสารของ C library แล้วรู้แน่ชัด
จริง ๆ** ว่ามันปลอดภัย เราสามารถเขียน `unsafe impl` ยืนยันเองได้:

```rust
struct FfiHandle {
    raw: *mut u8,
}

// SAFETY: สมมติว่าเอกสารของ C library ที่ raw ชี้ไปยัง handle นี้ ระบุไว้อย่างชัดเจนว่า
// handle ประเภทนี้ถูกออกแบบให้เรียกใช้ข้ามเธรดได้อย่างปลอดภัย (thread-safe by design ตาม
// เอกสารต้นทาง) — ถ้าไม่มีการันตีแบบนี้จากเอกสารจริง ห้ามเขียน unsafe impl นี้เด็ดขาด
unsafe impl Send for FfiHandle {}
unsafe impl Sync for FfiHandle {}

fn main() {
    let handle = FfiHandle { raw: std::ptr::null_mut() };
    println!("สร้าง handle เรียบร้อย (raw pointer: {:p})", handle.raw);
}
```

ข้อควรระวังที่สำคัญที่สุด: **การเขียน `unsafe impl Send`/`Sync` แบบนี้ต้องมีเหตุผลรองรับจริงจากเอกสารของ library
ต้นทางเสมอ ไม่ใช่การเขียนเพื่อ "ทำให้ compiler เงียบ"** — ถ้าเอกสารไม่ได้รับประกันไว้ การเขียนแบบนี้คือการโกหก
compiler โดยตรง และจะทำให้เกิด data race จริงถ้ามีคนใช้ `FfiHandle` ข้ามเธรดจริง ๆ (ดูกับดักที่พบบ่อยข้อที่ 6
ที่จะอธิบายกรณีนี้กับ `Rc<T>` โดยตรง)

#### 41.4.5 เข้าถึง Field ของ `union`

```rust
union IntOrFloat {
    as_int: i32,
    as_float: f32,
}

fn main() {
    let value = IntOrFloat { as_int: 1_078_530_011 };

    // การอ่าน field ของ union ต้องอยู่ใน unsafe block เสมอ
    unsafe {
        println!("อ่านเป็น i32: {}", value.as_int);
        println!("อ่านเป็น f32 (ตีความ bit pattern เดียวกันใหม่): {}", value.as_float);
    }
}
```

`union` (ต่างจาก `enum` ที่เรียนใน Part 10) **ไม่มี tag ซ่อนอยู่ที่บอกว่า field ไหนถูกเขียนไว้ล่าสุด** — ทุก field
ของ `union` ใช้พื้นที่ memory เดียวกันซ้อนทับกันหมด (เหมือน `union` ใน C) ดังนั้นการอ่าน field ที่ **ไม่ตรงกับ
field ที่เขียนล่าสุด** จะเป็นการ "ตีความ bit pattern เดิมใหม่ในชนิดข้อมูลอื่น" ซึ่งอาจให้ผลลัพธ์ที่ถูกต้อง (ถ้า
เข้าใจ memory layout ดีและตั้งใจทำแบบนี้จริง เช่นเทคนิคระดับต่ำในการตีความ bit ของ float กลับเป็น int เพื่อ
ประมวลผลแบบพิเศษ) หรืออาจให้ผลลัพธ์ที่ไร้ความหมายโดยสิ้นเชิงก็ได้ — compiler ไม่มีทางรู้ได้เลยว่า field ไหน
"ถูกต้อง" ในเวลาไหน จึงต้องบังคับให้อยู่ใน `unsafe` เสมอ ในโค้ด Rust ทั่วไป `union` ถูกใช้น้อยมาก (ส่วนใหญ่ใช้
`enum` แทนเพราะปลอดภัยกว่าและมี tag ให้ compiler ตรวจสอบ) แต่มันสำคัญมากในงาน FFI ที่ต้อง interop กับ C library
ที่ใช้ `union` (Part 43 จะเจอสถานการณ์นี้จริง) และในงาน low-level bit manipulation บางประเภท

**สรุปหัวข้อนี้**: ห้าอย่างข้างบนคือ**รายการที่สมบูรณ์**ของสิ่งที่ `unsafe` ปลดล็อก ไม่มีอย่างที่หก การเขียน
`unsafe` แล้วเปลี่ยน type ผิด ๆ, ลืม `.clone()`, ทำ integer overflow (ที่ panic ใน debug mode ตามที่เรียนใน
Part 3), หรือละเมิดกฎ borrowing ธรรมดา — **ทั้งหมดนี้ยังคงถูกตรวจสอบและปฏิเสธเหมือนเดิมทุกประการ ไม่ว่าจะอยู่ใน
`unsafe` block หรือไม่ก็ตาม** เราจะพิสูจน์ประโยคนี้ให้เห็นจริงในหัวข้อถัดไป

### 41.5 พิสูจน์ให้เห็นจริง: `unsafe` ไม่ได้ปิด Borrow Checker หรือ Move Semantics

นี่คือหัวข้อที่สำคัญที่สุดในการทำให้ความเข้าใจเรื่อง "ขอบเขตแคบของ `unsafe`" เป็นรูปธรรม ไม่ใช่แค่คำพูดลอย ๆ
ลองเขียนโค้ดที่ละเมิดกฎ borrowing ธรรมดา (กฎเดียวกับที่เรียนใน Part 7) **ภายใน** `unsafe` block ดูว่าจะเกิดอะไรขึ้น:

```rust
fn main() {
    let mut v = vec![1, 2, 3];

    unsafe {
        let r1 = &v[0];      // ยืมแบบ immutable
        v.push(4);           // ❌ ลองยืมแบบ mutable ทั้งที่ r1 ยังมีชีวิตอยู่ — ข้างใน unsafe block ด้วย!
        println!("{r1}");
    }
}
```

โค้ดนี้ **compile ไม่ผ่าน** แม้จะอยู่ใน `unsafe` block ก็ตาม:

```
error[E0502]: cannot borrow `v` as mutable because it is also borrowed as immutable
 --> src/main.rs:6:9
  |
5 |         let r1 = &v[0];      // ยืมแบบ immutable
  |                   - immutable borrow occurs here
6 |         v.push(4);           // ❌ ลองยืมแบบ mutable ทั้งที่ r1 ยังมีชีวิตอยู่ — ข้างใน unsafe block ด้วย!
  |         ^^^^^^^^^ mutable borrow occurs here
7 |         println!("{r1}");
  |                    -- immutable borrow later used here
```

(compiler อาจแสดง warning `unused_unsafe` ควบคู่มาด้วย เนื่องจากในตัวอย่างนี้ไม่มีปฏิบัติการทั้งห้าตามหัวข้อ 41.4
อยู่ในบล็อกเลยจริง ๆ — เป็นคนละประเด็นกับ error หลักที่เราสนใจอยู่ ไม่ต้องสนใจ warning นั้นในตัวอย่างนี้)

สังเกตว่า error code (`E0502`) และข้อความ error **เหมือนกันเป๊ะ ๆ** กับที่จะเกิดถ้าเราลบ `unsafe { }` ทิ้งไป
เพราะ **`v.push(4)` ไม่ใช่หนึ่งในห้าปฏิบัติการที่ `unsafe` ปลดล็อกเลย** มันเป็นแค่การเรียก method ธรรมดาบน `Vec<T>`
— borrow checker วิเคราะห์โค้ดทั้ง block รวมถึงโค้ดที่อยู่ข้างใน `unsafe { }` เหมือนกับโค้ดข้างนอกทุกประการ ไม่มี
การ "ปิดตา" ให้กับส่วนที่อยู่ใน `unsafe` เลยแม้แต่นิดเดียว

มาดูอีกตัวอย่างที่พิสูจน์ว่า **move semantics** (จาก Part 6) ก็ยังมีผลอยู่ภายใน `unsafe` เช่นกัน:

```rust
fn main() {
    let s = String::from("hello");

    unsafe {
        let s2 = s;          // move ownership จาก s ไป s2 — เป็นการ move ธรรมดา ไม่เกี่ยวกับ unsafe เลย
        println!("{s}");     // ❌ ใช้ s หลังจากถูก move ไปแล้ว
        println!("{s2}");
    }
}
```

ทั้งห้าของหัวข้อ 41.4 อยู่จริง — ไม่ใช่ประเด็นที่เราสนใจในตัวอย่างนี้)

เหมือนกับตัวอย่างก่อนหน้า: **`let s2 = s;` ไม่ใช่หนึ่งในห้าปฏิบัติการของ `unsafe`** มันเป็นแค่ assignment ธรรมดา
ที่ trigger move semantics เหมือนที่เรียนมาตั้งแต่ Part 6 — `unsafe` ไม่ได้ทำให้ `String` กลายเป็น `Copy` type
ขึ้นมา ไม่ได้ทำให้เราแอบ "ยืม" ค่าที่ถูก move ไปแล้วกลับมาใช้ได้อีก

**สิ่งที่เกิดขึ้นจริงในสองตัวอย่างข้างบนคือ**: `unsafe` block เป็นแค่ **"เขตพื้นที่"** ที่ทำให้ syntax ห้าแบบ
(raw pointer dereference, unsafe fn call, static mut access, unsafe trait impl, union field access) ถูกต้อง
ตามกฎของ compiler เท่านั้น — **โค้ดทุกบรรทัดที่อยู่ในเขตพื้นที่นั้นซึ่งไม่ได้ใช้ห้าปฏิบัติการนั้น ยังต้องผ่านการ
ตรวจสอบตามปกติทุกอย่าง** ไม่ว่าจะเป็น type checking, borrow checking, หรือ move semantics — เหมือนกับการที่คุณ
ได้รับใบอนุญาตพิเศษให้ทำกิจกรรมเฉพาะอย่างในพื้นที่หนึ่ง แต่กฎจราจรทั่วไปของถนนสายนั้นก็ยังบังคับใช้อยู่เหมือนเดิม
ไม่ได้ยกเว้นไปทั้งหมด

### 41.6 `unsafe fn`: สัญญาที่ Compiler ตรวจสอบไม่ได้

ตอนนี้เรารู้แล้วว่า **การเรียก** `unsafe fn` คือหนึ่งในห้าปฏิบัติการที่ต้องมี `unsafe` block ครอบ แต่เรายังไม่ได้
อธิบายอย่างลึกว่า **ทำไม** ฟังก์ชันหนึ่งถึงถูกประกาศเป็น `unsafe fn` ตั้งแต่แรก และ**ความหมายที่แท้จริง**ของการ
ประกาศแบบนี้คืออะไร

**นิยามที่แม่นยำที่สุด**: การประกาศฟังก์ชันเป็น `unsafe fn` คือการบอกว่า **"ฟังก์ชันนี้มี precondition (เงื่อนไข
ก่อนเรียก) ที่ต้องเป็นจริงเสมอ ไม่อย่างนั้นจะเกิด undefined behavior — และ precondition นั้นเป็นสิ่งที่ type
system ของ Rust ตรวจสอบให้ไม่ได้ด้วย static analysis"** ภาระในการตรวจสอบว่า precondition เป็นจริงจึงตกไปอยู่ที่
**ผู้เรียก (caller)** ทั้งหมด — compiler ทำได้แค่บังคับให้ผู้เรียกต้องเขียน `unsafe { }` ครอบเพื่อ **"เซ็นรับรอง"**
ว่าได้ตรวจสอบ precondition แล้วจริง ๆ แต่ตัว compiler เอง **ไม่มีทางตรวจสอบเนื้อหาของ precondition ได้เลย**

นี่คือเหตุผลที่แท้จริงที่ Part 34 บอกว่า **`# Safety` doc comment สำคัญมาก** สำหรับ `unsafe fn` ทุกตัวที่เป็น
public API — เพราะ compiler พิมพ์ประโยค "ต้องมี unsafe block" ให้เราได้ แต่ compiler **เขียนไม่ได้** ว่า
precondition ที่แท้จริงคืออะไร ผู้เขียนฟังก์ชันต้องเขียนมันเองในภาษาที่มนุษย์อ่านได้ ไม่อย่างนั้นผู้เรียกจะไม่มี
ทางรู้เลยว่าต้อง "ตรวจสอบอะไร" ก่อนเซ็นรับรองด้วย `unsafe { }`

มาดูตัวอย่างที่มี precondition จริงและสำคัญมาก — ฟังก์ชันที่อ่านค่าจาก slice โดย **ไม่ตรวจสอบขอบเขต** (คล้ายกับ
`slice::get_unchecked` ของ standard library) เพื่อความเร็วสูงสุด (ข้าม bounds check ที่ปกติ Rust ทำให้อัตโนมัติ
ทุกครั้งที่ใช้ `slice[index]`):

```rust
/// อ่านค่าที่ตำแหน่ง `index` ใน `slice` โดยไม่ตรวจสอบขอบเขตเลย (เร็วกว่า `slice[index]`
/// เพราะข้าม bounds check ที่ปกติ Rust แทรกให้อัตโนมัติ)
///
/// # Safety
///
/// ผู้เรียกต้องมั่นใจว่า `index < slice.len()` เสมอ ก่อนเรียกฟังก์ชันนี้ ถ้า `index >= slice.len()`
/// จะเป็นการอ่าน memory ที่อยู่นอกขอบเขตของ slice ซึ่งเป็น **undefined behavior** ทันที — อาจได้ค่า
/// ขยะที่ดูสมเหตุสมผล, อาจ crash, หรืออาจไม่เกิดอาการอะไรที่สังเกตได้เลยในการรันครั้งนั้น (ดูเหตุผล
/// เชิงลึกในหัวข้อ 41.7)
unsafe fn read_unchecked(slice: &[i32], index: usize) -> i32 {
    // SAFETY: ฟังก์ชันนี้พึ่งพา precondition ที่ caller ต้องรับประกันตามที่ระบุใน # Safety ข้างบน
    unsafe { *slice.as_ptr().add(index) }
}

fn main() {
    let data = vec![10, 20, 30];

    // ผู้เรียกต้องตรวจสอบเองว่า index < data.len() แล้วค่อยเรียก — นี่คือ "การเซ็นรับรอง" ที่ unsafe block กำหนดไว้
    let value = unsafe { read_unchecked(&data, 1) };
    println!("ค่าที่ index 1: {value}"); // 20 — ถูกต้อง เพราะ 1 < 3
}
```

โค้ดข้างบนนี้**ถูกต้องและปลอดภัย** เพราะเราเรียกด้วย `index = 1` ซึ่ง `1 < data.len()` (คือ `3`) เป็นจริง — แต่
ลองดูว่าเกิดอะไรขึ้นถ้าเราละเมิด precondition ที่ `# Safety` ระบุไว้:

```rust
unsafe fn read_unchecked(slice: &[i32], index: usize) -> i32 {
    unsafe { *slice.as_ptr().add(index) }
}

fn main() {
    let data = vec![10, 20, 30]; // data.len() == 3

    // ⚠️ ตัวอย่างนี้จงใจละเมิด precondition (index < len) เพื่อการสอนเท่านั้น — ห้ามเขียนแบบนี้ในโค้ดจริง
    let out_of_bounds = unsafe { read_unchecked(&data, 10) };
    println!("ค่าที่อ่านได้ (ห้ามเชื่อถือ — เป็น undefined behavior): {out_of_bounds}");
}
```

โค้ดนี้ **compile ผ่านโดยไม่มี error หรือ warning ใด ๆ เลย** — นี่คือประเด็นที่สำคัญที่สุดของหัวข้อนี้: **compiler
ไม่มีทางรู้เลยว่า `10` ที่ส่งเข้าไปนั้นละเมิด precondition ของ `# Safety`** เพราะ `# Safety` เป็นแค่ข้อความในภาษา
มนุษย์ที่ compiler ไม่ได้อ่านหรือตรวจสอบเลย มันเป็น**สัญญาทางสังคม (social contract)** ระหว่างผู้เขียนฟังก์ชันกับ
ผู้เรียกใช้เท่านั้น ไม่ใช่สัญญาที่ type system บังคับใช้ — เมื่อรันโปรแกรมนี้จริง ผลลัพธ์ที่ได้**ไม่แน่นอนตามหลัก
วิชาการของ Rust** (คือ undefined behavior โดยนิยาม) แต่ในทางปฏิบัติจริงบนเครื่องส่วนใหญ่ มันมักจะ**อ่าน memory
ที่อยู่ติดกับ allocation ของ `data` ไปแล้ว** และพิมพ์ตัวเลขขยะบางอย่างออกมาโดยไม่ crash (เพราะ memory บริเวณนั้น
ยังอยู่ในหน้า memory ที่ระบบปฏิบัติการจัดสรรให้โปรแกรมแล้ว จึงไม่ใช่การเข้าถึง memory ที่ "ไม่มีอยู่จริง" ในทันที)
— นี่คือเหตุผลที่แท้จริงที่หัวข้อถัดไปจะอธิบายว่า **UB อันตรายกว่า compile error เพราะมันไม่พังทันทีเสมอไป**

**บทเรียนที่ต้องจำจากตัวอย่างนี้**: `unsafe fn` ไม่ได้ทำให้โค้ดที่เรียกมัน "ปลอดภัยโดยอัตโนมัติ" มันเป็นการโยน
ภาระการพิสูจน์ทั้งหมดไปให้ผู้เรียกแทน — ถ้าผู้เรียกพิสูจน์ผิด (หรือไม่พิสูจน์เลย) ผลลัพธ์ที่ได้คือ undefined
behavior ที่ compiler ไม่มีทางเตือนล่วงหน้าได้เลยแม้แต่นิดเดียว

#### หมายเหตุเชิงเทคนิค: `unsafe fn` และ Edition 2021 เทียบกับ Edition 2024

สังเกตว่าในตัวอย่าง `read_unchecked` ข้างบน เราเขียน `unsafe { *slice.as_ptr().add(index) }` **ไว้ข้างในตัวมัน
เองอีกชั้นหนึ่ง** ทั้งที่ตัวฟังก์ชันทั้งก้อนก็เป็น `unsafe fn` อยู่แล้ว — บางคนอาจสงสัยว่านี่ซ้ำซ้อนหรือไม่ ในความ
เป็นจริง **ใน edition 2021 (ที่หลักสูตรนี้ใช้) เนื้อโค้ดทั้งหมดภายใน `unsafe fn` ถูกถือว่าอยู่ใน `unsafe` block
โดยอัตโนมัติอยู่แล้ว** ดังนั้นการเขียน `unsafe { }` ซ้อนเข้าไปอีกชั้นในตัวอย่างของบทนี้จึงเป็นเพียง**ทางเลือกด้าน
สไตล์เพื่อความชัดเจน** ไม่ใช่ข้อบังคับทางไวยากรณ์

อย่างไรก็ตาม นี่คือจุดที่ควรรู้ไว้เพื่อความเข้าใจภาพรวมของภาษาที่ครบถ้วน: **เริ่มตั้งแต่ edition 2024 เป็นต้นไป
lint ที่ชื่อ `unsafe_op_in_unsafe_fn` เปลี่ยนจาก "ปิดโดย default" เป็น **"เปิดและเป็น error โดย default"** — ซึ่ง
หมายความว่าใน edition 2024 การเรียก unsafe operation ภายใน `unsafe fn` **จะต้องมี `unsafe { }` ครอบอย่างชัดเจน
เสมอ** เหมือนกับที่เราเขียนไว้ในตัวอย่างของบทนี้ทุกจุด เหตุผลเบื้องหลังการเปลี่ยนแปลงนี้ตรงกับหลักการที่หัวข้อ
41.10 ของบทนี้จะอธิบายเรื่อง minimizing scope: การบังคับให้เขียน `unsafe { }` ซ้อนเข้าไปชัดเจนอีกชั้น ทำให้ผู้อ่าน
เห็นทันทีว่า **จุดไหนกันแน่ในฟังก์ชันที่ใช้ปฏิบัติการทั้งห้าอย่างจากหัวข้อ 41.4 จริง ๆ** แทนที่จะต้องสันนิษฐานว่า
"ทั้งฟังก์ชันเสี่ยงหมด" เพียงเพราะมันถูกประกาศเป็น `unsafe fn` — **บทนี้เขียนโค้ดตัวอย่างทุกตัวตามสไตล์ของ edition
2024 อยู่แล้ว (ใส่ `unsafe { }` ซ้อนในทุก `unsafe fn`) เพื่อให้เป็น best practice ที่ใช้ได้ทั้งสอง edition และ
เพื่อให้อ่านง่ายที่สุดเสมอ** ไม่ว่าโปรเจกต์ของคุณจะใช้ edition ไหนก็ตาม

### 41.7 อันตรายที่แท้จริงของ Undefined Behavior: ทำไมมันไม่พังทันทีเสมอไป — และนั่นคือปัญหา

ตลอด 40 บทที่ผ่านมา เราคุ้นเคยกับรูปแบบการเรียนรู้แบบหนึ่งมาตลอด: **ถ้าเขียนโค้ดผิด compiler จะปฏิเสธทันทีตอน
`cargo check`/`cargo build`** ไม่ว่าจะเป็น type mismatch, borrow checker violation, หรือ move ผิดกฎ — เราไม่มี
ทาง "หนีรอด" ไปได้เลย และนี่คือสิ่งที่ทำให้เขียน Rust สนุกและมั่นใจ: **ถ้า compile ผ่าน มันแปลว่าไม่มีบั๊กประเภท
เหล่านี้แน่นอน 100%** ไม่ต้องกังวลว่าจะมี edge case ที่ลืมทดสอบ

**`unsafe` ทำลายความสบายใจนี้ไปเลยโดยสิ้นเชิง** และนี่คือเหตุผลที่แท้จริง: เมื่อคุณละเมิด precondition ของ
`unsafe fn` หรือทำผิดพลาดกับ raw pointer, สิ่งที่เกิดขึ้นคือ **undefined behavior (UB)** — และคำว่า "undefined"
ในที่นี้มีความหมายที่เข้มงวดกว่าที่คำแปลไทยตรง ๆ จะสื่อได้: มันไม่ได้แปลว่า "ผลลัพธ์จะสุ่มออกมาแบบไม่แน่นอนแต่ยัง
อยู่ในขอบเขตที่พอเข้าใจได้" (เช่น "อาจได้ 1 หรือ 2") แต่แปลว่า **compiler และ optimizer มีสิทธิ์ทำอะไรก็ได้กับโค้ด
ส่วนนั้น** เพราะตาม spec ของภาษา โค้ดที่มี UB **ไม่มีความหมายที่นิยามไว้เลย** — ไม่ใช่แค่ runtime ที่ทำอะไรแบบสุ่ม
แต่ตัว compiler เองในขณะที่ compile ก็มีสิทธิ์ optimize โดยสมมติว่า "UB ไม่มีทางเกิดขึ้น" (เพราะสัญญาที่คุณให้ไว้
ตอนเขียน `unsafe` คือ "รับรองว่าจะไม่มี UB") แล้วลบ, จัดเรียงใหม่, หรือแทนที่โค้ดส่วนนั้นด้วยอะไรก็ได้ที่ optimizer
เห็นว่า "สมเหตุสมผลภายใต้สมมติฐานว่าไม่มี UB"

นี่คือความแตกต่างเชิงคุณภาพที่สำคัญมากระหว่าง compile error กับ UB:

| แง่มุม | Compile Error (เช่น borrow checker violation) | Undefined Behavior (จาก `unsafe` ที่ผิด) |
|---|---|---|
| ตรวจพบเมื่อไหร่ | ทันทีตอน `cargo check`/`build` — **ก่อน** โปรแกรมรันด้วยซ้ำ | ไม่มีการแจ้งเตือนใด ๆ เลย ทั้งตอน compile และมักไม่มีตอน run ด้วย |
| ผลลัพธ์ตอนรัน (ถ้าปล่อยผ่านไปได้) | ไม่มีทางเกิดขึ้น เพราะ compile ไม่ผ่านตั้งแต่แรก | รันได้จริง อาจ "ดูเหมือนทำงานถูกต้อง" ไปหลายเดือนหรือหลายปี |
| ขึ้นกับ optimization level หรือไม่ | ไม่เกี่ยว — error เดิมเกิดเหมือนกันทั้ง debug และ release | อาจแสดงอาการต่างกันอย่างสิ้นเชิงระหว่าง debug กับ release build |
| ขึ้นกับ input/platform หรือไม่ | ไม่เกี่ยว — เป็น static property ของโค้ด ไม่ใช่ของ runtime data | อาจทำงาน "ถูกต้อง" บน input หนึ่ง แต่พังบน input อื่น หรือพังแค่บน CPU/OS บางรุ่น |
| แก้ยากแค่ไหน | ง่าย — error message ชี้ตำแหน่งชัดเจน แก้แล้ว compile ผ่านคือจบ | ยากมาก — อาการที่เห็น (เช่น crash ตรงจุดหนึ่ง) อาจไม่เกี่ยวกับต้นเหตุจริงเลย |

ตัวอย่างที่เป็นจริงและเกิดขึ้นซ้ำ ๆ ในโลกการเขียนโปรแกรมระดับระบบ (ทั้งใน C/C++ และใน `unsafe` Rust ที่เขียนผิด):
โค้ดที่มี UB อาจ **compile และรันได้ "ถูกต้องสมบูรณ์" ในโหมด debug** (เพราะ optimizer ไม่ทำอะไรมาก โค้ดจึงรันตาม
ลำดับตรงไปตรงมาแบบที่เขียนไว้ และ memory ที่ไม่ได้ initialize มักบังเอิญมีค่าที่ "ดูสมเหตุสมผล" อยู่) **แต่พังทันที
ในโหมด release** (เพราะ optimizer ที่ optimize แบบเข้มข้นกว่า อาจสมมติว่าโค้ดไม่มี UB แล้วจัดเรียงคำสั่งใหม่, ลบ
เงื่อนไขที่ดู "ซ้ำซ้อน" ทิ้ง, หรือเก็บค่าไว้ใน register ผิดตำแหน่ง) — และที่แย่กว่านั้นคือบางครั้งอาการกลับกัน:
ทำงานถูกใน release แต่พังใน debug, หรือทำงานถูกบนเครื่อง CI ทุกเครื่องตลอดหลายเดือนแต่พังทันทีบนเครื่องของลูกค้า
คนหนึ่งที่ใช้ CPU สถาปัตยกรรมต่างออกไป

**นี่คือคำตอบที่แท้จริงว่าทำไมเนื้อหาข้อกำหนดในบทของโจทย์บอกว่า "unsafe superpowers ไม่ได้แปลว่าจะเกิด UB ทันที
เสมอไป — และนั่นแหละคืออันตรายที่สุด"**: ถ้าโค้ด `unsafe` ที่ผิดพัง**ทันทีทุกครั้งแบบเดิม** มันจะไม่ต่างอะไรจาก
compile error เลย (แค่เจอช้าไปหน่อย ตอน runtime แทนตอน compile) — ปัญหาจริงคือมันสามารถ **"ดูเหมือนใช้งานได้"
ผ่านการทดสอบทุกแบบที่คุณคิดจะทดสอบ (unit test, integration test, การใช้งานจริงในโปรดักชันนานหลายเดือน)** แล้วจึง
"เลือก" จะแสดงอาการผิดพลาดในสถานการณ์ที่คุณคาดไม่ถึง (compiler เวอร์ชันใหม่กว่า, optimization flag ต่างออกไป,
ข้อมูล input ที่ไม่ได้ทดสอบมาก่อน, หรือแม้แต่แค่เปลี่ยนไปคอมไพล์บนเครื่องอื่น) — **testing ไม่สามารถพิสูจน์ความ
ไม่มี UB ได้เลย เพราะการที่โค้ดผ่าน test ครั้งหนึ่งไม่ได้แปลว่า optimizer จะปฏิบัติกับมันแบบเดิมทุกครั้งไปตลอด
กาล**

เปรียบเทียบกับสิ่งที่เราคุ้นเคยมาตลอด 40 บทที่ผ่านมาให้ชัดที่สุด: **borrow checker ให้การันตีแบบ "พิสูจน์ได้
สมบูรณ์" (sound) — ถ้า compile ผ่าน ไม่มี dangling reference แน่นอน 100% ไม่ว่าจะรันกี่ครั้ง บนเครื่องไหน ด้วย
optimization level ไหนก็ตาม** แต่การเขียน `unsafe` ที่ถูกต้อง **ไม่มี compiler คอยการันตีให้แบบนั้นเลย** ความ
ถูกต้องขึ้นอยู่กับการให้เหตุผล (reasoning) ของมนุษย์ล้วน ๆ — และนี่คือเหตุผลที่แท้จริงว่าทำไมโค้ด `unsafe` **ต้อง
การความรอบคอบมากขึ้น ไม่ใช่น้อยลง** เมื่อเทียบกับ safe Rust ทั้งที่มัน "อนุญาต" ให้ทำอะไรได้มากขึ้นก็ตาม — อำนาจ
ที่มากขึ้นมาพร้อมกับภาระการพิสูจน์ที่มากขึ้นเสมอ ไม่ใช่น้อยลง

#### เปรียบเทียบกับภาษาอื่น: เครื่องมือตรวจจับ UB ที่มีอยู่ในแต่ละ Ecosystem

ปัญหา "UB ที่ตรวจจับตอน compile time ไม่ได้" ไม่ใช่ปัญหาเฉพาะของ Rust เท่านั้น — มันคือปัญหาพื้นฐานของโค้ดระดับ
ต่ำทุกภาษาที่ทำงานกับ raw memory ได้ ลองดูว่า ecosystem ของแต่ละภาษาแก้ปัญหานี้อย่างไร:

| ภาษา / Ecosystem | เครื่องมือหลักที่ใช้ตรวจจับ UB | จุดแตกต่างจาก Miri ของ Rust |
|---|---|---|
| **C / C++** | `AddressSanitizer` (ASan), `UndefinedBehaviorSanitizer` (UBSan), `ThreadSanitizer` (TSan), Valgrind | ตรวจจับได้เฉพาะ path ที่ execute จริงเหมือน Miri แต่ทำงานที่ระดับ **native machine code** (compile ด้วย flag พิเศษแล้วรันจริงบนเครื่อง) จึงเร็วกว่า Miri มาก แต่ไม่มี "โมเดลความหมายของภาษา" ที่เข้มงวดเท่า เพราะ C/C++ เองก็ไม่มีนิยาม UB ที่เข้มงวดเท่า Rust |
| **Go** | `go build -race` (race detector สำหรับ data race โดยเฉพาะ) | ครอบคลุมแค่ data race ระหว่าง goroutine ไม่ครอบคลุม memory safety ทั่วไปเพราะ Go ปลอดภัยเรื่อง memory อยู่แล้วโดยดีฟอลต์ (มี GC) ยกเว้นเมื่อใช้ package `unsafe` |
| **Java / C# / Python** | ไม่มีความจำเป็นในโค้ดผู้ใช้ทั่วไป | UB ประเภทนี้เกิดขึ้นไม่ได้เลยในโค้ดที่ managed โดย runtime (แลกมาด้วย GC overhead ตามที่อธิบายไว้ในหัวข้อ 41.3) |
| **Rust** | **Miri** (ตีความผ่าน MIR พร้อมโมเดลความหมายของภาษาที่เข้มงวด) | ช้ากว่าการรันแบบ native มาก (เพราะเป็น interpreter ไม่ใช่ native code) แต่ตรวจจับได้ละเอียดกว่า ASan/UBSan ในหลายกรณี เพราะ Rust นิยามกฎ aliasing ของ reference ไว้เข้มงวดกว่า C/C++ มาก |

ข้อสรุปจากตารางนี้: **ไม่มีภาษาไหนในโลกที่ "แก้ปัญหา UB ได้สมบูรณ์ 100% ด้วยเครื่องมืออัตโนมัติ"** — ทุก ecosystem
ต้องพึ่งพาการ reasoning ของมนุษย์ร่วมกับเครื่องมือช่วยตรวจสอบเสมอ สิ่งที่ Rust ทำต่างออกไปคือ **ลดพื้นที่ที่ต้อง
พึ่งพาการ reasoning ของมนุษย์ให้เหลือน้อยที่สุดเท่าที่จะทำได้** (ผ่าน borrow checker ที่ครอบคลุมโค้ด 99% ของ
โปรแกรมทั่วไป) แล้วค่อยให้เครื่องมืออย่าง Miri ช่วยเสริมเฉพาะพื้นที่แคบ ๆ ที่เหลือ (คือ `unsafe` block) ซึ่งเป็น
กลยุทธ์ที่ต่างจาก C/C++ ที่ต้องพึ่งพา sanitizer ครอบคลุมทั้งโปรแกรม เพราะทั้งโปรแกรมมีความเสี่ยงเท่ากันหมด

### 41.8 หลักปรัชญาแกนกลาง: Safe Abstraction เหนือ Unsafe Code

ถ้า `unsafe` อันตรายและต้องระวังมากขนาดนี้ คำถามที่ตามมาคือ: **แล้วเราควรใช้มันยังไงในทางปฏิบัติ?** คำตอบคือ
หลักการที่เป็นแก่นกลางของวัฒนธรรมการเขียน Rust ทั้งระบบ (รวมถึง standard library เองทั้งหมด):

> **เขียน `unsafe` block ให้เล็กที่สุดและตรวจสอบได้ง่ายที่สุดเท่าที่จะทำได้ แล้วห่อมันด้วย safe function ที่
> signature ของมันทำให้ผู้เรียกใช้ "เรียกผิดไม่ได้" ไม่ว่าจะส่ง input อะไรมาก็ตาม**

นี่คือรูปแบบที่เรียกว่า **safe abstraction (การสร้างสิ่งที่ปลอดภัยครอบสิ่งที่ไม่ปลอดภัย)** และมันคือสิ่งที่ทำให้
`Vec<T>`, `String`, `Rc<T>`, และ `Mutex<T>` ที่เราใช้มาตั้งแต่ Part 13, 14, 28, และ 39 **ปลอดภัย 100% จากมุมมอง
ของผู้ใช้** ทั้งที่ **ภายในเต็มไปด้วย `unsafe`**

ลองดูให้เห็นภาพจริง — `Vec<T>` ต้องจัดการ **raw memory allocation** ด้วยตัวเอง (มันไม่สามารถใช้ `Vec<T>` ตัวอื่น
มาช่วยจัดการ memory ของตัวเองได้ เพราะนั่นจะเป็นการวนซ้ำแบบไม่มีที่สิ้นสุด — ต้องมีจุดหนึ่งที่คุยกับ memory
allocator โดยตรง) `String` ก็เช่นกัน (มันคือ wrapper รอบ `Vec<u8>` ที่การันตีว่าข้อมูลภายในเป็น UTF-8 ที่ถูกต้อง
เสมอ) `Rc<T>` ต้องเก็บตัวนับ reference ไว้ใน heap แล้วให้หลาย `Rc<T>` instance ชี้ไปที่ตัวนับเดียวกันได้ (ซึ่งคือ
การมี mutable state ที่ถูกแชร์ — สิ่งที่ borrow checker ปกติไม่ยอมให้ทำแบบ safe ตรง ๆ) และ `Mutex<T>` ต้องเรียก
primitive ของระบบปฏิบัติการเพื่อ lock/unlock ที่ต่ำกว่าระดับที่ type system ของ Rust มองเห็นได้เลย

ลองเขียนตัวอย่างที่จำลองรูปแบบเดียวกันในระดับเล็ก ๆ เพื่อให้เห็นหลักการชัดที่สุด: ฟังก์ชัน `safe_read_at` ที่
**ห่อ** การอ่านค่าผ่าน raw pointer (ซึ่งเป็น unsafe operation ตามข้อ 1 ในหัวข้อ 41.4) ด้วยการตรวจสอบขอบเขต
**ก่อน** เข้าสู่ `unsafe` เสมอ ทำให้ตัวฟังก์ชันเอง **ปลอดภัย 100% ไม่ว่าผู้เรียกจะส่ง `index` อะไรมาก็ตาม**:

```rust
/// อ่านค่าที่ตำแหน่ง `index` ใน `data` อย่างปลอดภัย 100%
///
/// ต่างจาก `read_unchecked` ในหัวข้อ 41.6 ที่ผู้เรียกต้องรับผิดชอบตรวจสอบ `index < data.len()` เอง —
/// ฟังก์ชันนี้ตรวจสอบเงื่อนไขนั้น**ให้เสร็จก่อน**เข้าสู่ unsafe ทุกครั้ง จึงไม่มี precondition ใด ๆ
/// เหลือให้ผู้เรียกต้องรับผิดชอบเลย นี่คือ signature ที่ "เรียกผิดไม่ได้" — ผู้เรียกไม่ต้องรู้จักคำว่า
/// unsafe เลยแม้แต่คำเดียวเพื่อใช้ฟังก์ชันนี้อย่างปลอดภัย
fn safe_read_at(data: &[i32], index: usize) -> Option<i32> {
    if index >= data.len() {
        return None; // ปฏิเสธ input ที่ผิดตั้งแต่ต้น — ไม่มีทางไปถึง unsafe ด้วย index ที่ผิดได้เลย
    }

    // ณ จุดนี้ compiler ไม่รู้ แต่ "เรา" รู้แน่นอน 100% ว่า index < data.len() เพราะเช็คไปแล้วข้างบน
    // นี่คือตัวอย่างของ "สิ่งที่มนุษย์พิสูจน์ได้ แต่ borrow checker พิสูจน์ไม่ได้" ตามหัวข้อ 41.3
    let ptr = data.as_ptr();
    let value = unsafe {
        // SAFETY: index < data.len() ถูกตรวจสอบไปแล้วข้างบนแบบไม่มีทางหลีกเลี่ยง (early return ถ้าไม่ผ่าน)
        // ptr มาจาก data.as_ptr() ซึ่งชี้ไปยัง allocation ที่ถูกต้องของ data เสมอ
        *ptr.add(index)
    };

    Some(value)
}

fn main() {
    let data = vec![10, 20, 30];

    println!("{:?}", safe_read_at(&data, 1));   // Some(20)
    println!("{:?}", safe_read_at(&data, 99));  // None — ไม่ crash แม้ input ผิดขนาดนี้
    println!("{:?}", safe_read_at(&data, 0));   // Some(10)
}
```

ผลลัพธ์:

```
Some(20)
None
Some(10)
```

สังเกตสิ่งสำคัญที่สุดในตัวอย่างนี้: **ผู้เรียก `safe_read_at` ไม่ต้องรู้อะไรเกี่ยวกับ `unsafe` เลยแม้แต่นิดเดียว**
พวกเขาสามารถส่ง `index` อะไรก็ได้ (รวมถึง `99` ที่เกินขอบเขตไปมาก) และได้ผลลัพธ์ที่ **นิยามไว้ชัดเจนเสมอ** (`None`)
ไม่มีทาง trigger undefined behavior ได้เลยไม่ว่าจะพยายามแค่ไหน — นี่คือความแตกต่างเชิงคุณภาพที่สำคัญที่สุดระหว่าง
`read_unchecked` ในหัวข้อ 41.6 (ที่ผู้เรียกต้องรับผิดชอบพิสูจน์ precondition เอง) กับ `safe_read_at` (ที่ตัว
ฟังก์ชันเองรับผิดชอบพิสูจน์ให้ครบก่อนใช้ `unsafe`)

**นี่คือกลไกที่แท้จริงที่ทำให้ `Vec<T>::push()`, `String::push_str()`, `Rc::clone()` ปลอดภัย 100% จากมุมมองผู้ใช้
ทั้งที่ภายในมี `unsafe`**: ทุก method เหล่านี้**ตรวจสอบเงื่อนไขที่จำเป็นทั้งหมดก่อนเข้าสู่ `unsafe` เสมอ** (เช่น
`Vec::push` ตรวจสอบว่ามี capacity เพียงพอหรือไม่ ถ้าไม่พอจะขยาย buffer ก่อนเสมอ แล้วจึงค่อยเขียนค่าลง raw pointer
ที่รู้แน่นอนว่าอยู่ในขอบเขตที่จัดสรรไว้แล้ว) ผู้ใช้ `Vec<T>` ไม่ต้องรู้เรื่อง capacity, raw pointer, หรือ memory
allocation เลยแม้แต่นิดเดียว — **นี่คือคุณค่าที่แท้จริงของคำว่า "abstraction" ในวิศวกรรมซอฟต์แวร์**: ซ่อนความ
ซับซ้อนและความเสี่ยงทั้งหมดไว้หลัง interface ที่เรียบง่ายและพิสูจน์ถูกต้องแล้วครั้งเดียว เพื่อให้โค้ดนับล้านบรรทัด
ที่เรียกใช้มันในภายหลังไม่ต้องพิสูจน์อะไรซ้ำอีกเลย

Part 28 สอนให้เราใช้ `Rc<T>` ในฐานะ "smart pointer ที่นับจำนวนเจ้าของ" โดยไม่ต้องรู้เลยว่าภายในทำงานอย่างไร —
ตอนนี้เรามีความรู้ครบพอที่จะเขียนเวอร์ชันง่าย ๆ ของมันขึ้นมาเองแล้ว เพื่อพิสูจน์ให้เห็นเป็นรูปธรรมที่สุดว่า
"safe abstraction เหนือ unsafe code" ที่อธิบายไปข้างบนไม่ใช่แค่ทฤษฎี แต่คือกลไกที่แท้จริงเบื้องหลัง `Rc<T>`
ของจริงในบรรจุ ไอเดียหลักคือ: เก็บค่าและตัวนับ reference ไว้ด้วยกันบน heap ผ่าน `Box`, แล้วดึง raw pointer ออกมา
ด้วย `Box::into_raw` เพื่อให้หลาย `MiniRc<T>` instance ชี้ไปยังก้อนความจำเดียวกันได้ (สิ่งที่ safe Rust ทำแบบ
ตรง ๆ ไม่ได้ เพราะ `Box<T>` มีเจ้าของเดียวเสมอตามกฎ ownership จาก Part 27):

```rust
use std::ops::Deref;

/// ข้อมูลที่แท้จริงบน heap: ค่าที่ต้องแชร์ พร้อมตัวนับจำนวน MiniRc ที่ชี้มาที่นี่อยู่
struct MiniRcInner<T> {
    value: T,
    count: usize,
}

/// เวอร์ชันง่ายของ Rc<T> — เก็บแค่ raw pointer ไปยัง MiniRcInner<T> บน heap
struct MiniRc<T> {
    ptr: *mut MiniRcInner<T>,
}

impl<T> MiniRc<T> {
    fn new(value: T) -> Self {
        let inner = Box::new(MiniRcInner { value, count: 1 });
        // Box::into_raw "ปลด" การจัดการ memory อัตโนมัติของ Box ออก แล้วคืน raw pointer มาให้
        // เราจัดการ deallocate เองตอน count ลงมาเป็น 0 (ดู impl Drop ข้างล่าง)
        MiniRc { ptr: Box::into_raw(inner) }
    }
}

impl<T> Clone for MiniRc<T> {
    fn clone(&self) -> Self {
        unsafe {
            // SAFETY: self.ptr ยังไม่ถูก deallocate แน่นอน ตราบใดที่ self ยังมีชีวิตอยู่
            // (เพราะการ deallocate เกิดขึ้นเฉพาะใน Drop เมื่อ count ลดลงเป็น 0 เท่านั้น)
            (*self.ptr).count += 1;
        }
        MiniRc { ptr: self.ptr }
    }
}

impl<T> Deref for MiniRc<T> {
    type Target = T;
    fn deref(&self) -> &T {
        // SAFETY: เหตุผลเดียวกับใน clone — ptr ยังไม่ถูก deallocate ตราบใดที่ self มีชีวิตอยู่
        unsafe { &(*self.ptr).value }
    }
}

impl<T> Drop for MiniRc<T> {
    fn drop(&mut self) {
        unsafe {
            (*self.ptr).count -= 1;
            if (*self.ptr).count == 0 {
                // count เป็น 0 แล้ว แปลว่านี่คือ MiniRc ตัวสุดท้ายที่ชี้มาที่นี่ — คืน memory ได้อย่างปลอดภัย
                // Box::from_raw "คืน" การจัดการ memory ให้ Box อีกครั้ง แล้ว drop ทำให้มันถูกปล่อยจริง
                drop(Box::from_raw(self.ptr));
            }
        }
    }
}

fn main() {
    let a = MiniRc::new(String::from("ข้อมูลที่แชร์กัน"));
    println!("a: {}", *a);

    let b = a.clone(); // count กลายเป็น 2 — a และ b ชี้ไปยัง MiniRcInner เดียวกัน
    println!("b: {}", *b);

    drop(a); // count ลดลงเป็น 1 — memory ยังไม่ถูกคืน เพราะ b ยังใช้งานอยู่
    println!("b ยังใช้งานได้ปกติแม้ a ถูก drop ไปแล้ว: {}", *b);

    drop(b); // count ลดลงเป็น 0 — ตรงนี้แหละที่ memory ถูกคืนจริง
}
```

ผลลัพธ์:

```
a: ข้อมูลที่แชร์กัน
b: ข้อมูลที่แชร์กัน
b ยังใช้งานได้ปกติแม้ a ถูก drop ไปแล้ว: ข้อมูลที่แชร์กัน
```

สังเกตสิ่งสำคัญที่สุด: **`main()` ไม่มีคำว่า `unsafe` เลยแม้แต่คำเดียว** — ผู้ใช้ `MiniRc<T>` เรียก `.clone()`,
ใช้ `*a`/`*b` ผ่าน `Deref`, และปล่อยให้ `drop()` ทำงานอัตโนมัติ (หรือเรียกเองตรง ๆ ก็ได้) โดยไม่ต้องรู้เลยว่า
ภายในมี raw pointer, `Box::into_raw`, หรือการนับ reference มือ ๆ อยู่เบื้องหลัง — `unsafe` ทั้งหมดถูก "ปิดผนึก"
ไว้ในสี่ method (`new`, `clone`, `deref`, `drop`) เท่านั้น ตรงกับหลักการ minimize scope จากหัวข้อ 41.10 ที่จะ
อธิบายถัดไป

ข้อสังเกตเพิ่มเติมที่เชื่อมกับ Part 40 โดยตรง: ถ้าคุณลองส่ง `MiniRc<T>` เข้า `thread::spawn` จะพบว่า **compiler
ปฏิเสธด้วย error ประเภทเดียวกับที่ Part 39-40 อธิบายไว้กับ `Rc<T>` ตัวจริง** เพราะ auto trait `Send`/`Sync`
(Part 40) มองเห็นว่า field `ptr: *mut MiniRcInner<T>` เป็น raw pointer ซึ่ง**ไม่ implement `Send`/`Sync` โดย
auto trait เสมอ** compiler จึงสรุปว่า `MiniRc<T>` ก็ไม่ `Send`/`Sync` ไปด้วยโดยอัตโนมัติ — นี่คือเหตุผลเชิงลึกอีก
ชั้นหนึ่งที่สอดคล้องกับของจริง 100%: `Rc<T>` ตัวจริงไม่ `Send` เพราะ **(1)** ตัวนับ (`count`) ไม่ใช่ atomic
(ถ้าส่งข้ามเธรดแล้วสองเธรดเพิ่ม/ลดค่าพร้อมกัน จะเกิด data race บนตัวนับเอง) และ **(2)** ยืนยันไปอีกชั้นด้วยกลไก
auto trait ที่มองเห็น raw pointer ภายในและปฏิเสธ `Send`/`Sync` ให้แบบอัตโนมัติอยู่แล้ว — สองเหตุผลนี้เสริมกัน
ไม่ได้ขัดแย้งกัน (`Arc<T>` ตัวจริงแก้ปัญหาข้อ (1) ด้วย atomic counter และแก้ปัญหาข้อ (2) ด้วยการเขียน
`unsafe impl Send`/`Sync` ให้ตัวเองอย่างตั้งใจ หลังจากพิสูจน์แล้วว่าอะตอมิกเคาน์เตอร์ทำให้ปลอดภัยจริง)

### 41.9 กรณีศึกษาสมบูรณ์: เขียน `split_at_mut` ด้วยตัวเอง

ตอนนี้เรามีความรู้ครบทุกส่วนที่จำเป็นแล้ว มาถึงตัวอย่างในตำนานที่สุดของวัฒนธรรม Rust — ฟังก์ชัน `split_at_mut`
จาก standard library ที่ทุกคนที่เขียน Rust ระดับลึกต้องเจอสักครั้งในชีวิต ลายเซ็นจริงของมันคือ:

```text
impl<T> [T] {
    pub fn split_at_mut(&mut self, mid: usize) -> (&mut [T], &mut [T])
}
```

หน้าที่ของมันตรงไปตรงมา: รับ mutable slice กับตำแหน่ง `mid` แล้วแบ่งเป็นสองครึ่ง — ครึ่งแรกคือ `[0..mid)` ครึ่ง
ที่สองคือ `[mid..len)` — และคืน **mutable reference ไปยังทั้งสองครึ่งพร้อมกัน** เพื่อให้ผู้เรียกแก้ไขทั้งสองครึ่ง
ได้อิสระในเวลาเดียวกัน (เช่นใช้ในอัลกอริทึม sort แบบ divide-and-conquer ที่ต้องเรียง sort สองครึ่งพร้อมกันแบบ
parallel — เราจะเห็นการใช้งานจริงแบบนี้เมื่อเรียนเรื่อง thread/rayon ในบทถัดไปของหลักสูตร)

#### ทำไมเขียนด้วย Safe Rust ล้วน ๆ ไม่ได้: พิสูจน์ให้เห็นจริง

ลองเขียนแบบที่ดูตรงไปตรงมาที่สุดก่อน — ใช้ slicing syntax ธรรมดาที่เรียนมาตั้งแต่ Part 8:

```rust
fn split_at_mut_attempt<T>(slice: &mut [T], mid: usize) -> (&mut [T], &mut [T]) {
    (&mut slice[..mid], &mut slice[mid..])
}

fn main() {
    let mut v = vec![1, 2, 3, 4, 5, 6];
    let (left, right) = split_at_mut_attempt(&mut v, 3);
    left[0] = 100;
    right[0] = 200;
    println!("{:?}", v);
}
```

โค้ดนี้ **compile ไม่ผ่าน**:

```
error[E0499]: cannot borrow `*slice` as mutable more than once at a time
 --> src/main.rs:2:30
  |
1 | fn split_at_mut_attempt<T>(slice: &mut [T], mid: usize) -> (&mut [T], &mut [T]) {
  |                                   - let's call the lifetime of this reference `'1`
2 |     (&mut slice[..mid], &mut slice[mid..])
  |     -------------------------^^^^^--------
  |     |     |                  |
  |     |     |                  second mutable borrow occurs here
  |     |     first mutable borrow occurs here
  |     returning this value requires that `*slice` is borrowed for `'1`
  |
  = help: use `.split_at_mut(position)` to obtain two mutable non-overlapping sub-slices
```

สังเกตบรรทัด `= help:` ที่ compiler แนะนำมาด้วยตรง ๆ — **compiler รู้จักปัญหานี้ดีจนแนะนำให้ใช้ `split_at_mut`
ที่มีอยู่แล้วใน standard library ทันที** นี่คือหลักฐานที่ชัดเจนที่สุดว่ารูปแบบนี้พบบ่อยและสำคัญพอที่ทีมพัฒนา
compiler เองจะเขียนข้อความช่วยเหลือเฉพาะสำหรับมันไว้เลย

ตรงตามที่หัวข้อ 41.3 อธิบายไว้ทุกประการ: **borrow checker มองเห็นแค่ว่า `&mut slice[..mid]` และ `&mut
slice[mid..]` เป็นการยืม `slice` แบบ mutable สองครั้งพร้อมกัน** ซึ่งตรงกับ**รูปแบบ**ที่กฎเหล็กข้อที่ 1 ของ
borrowing จาก Part 7 ห้ามไว้เสมอ (ห้ามมี mutable reference มากกว่าหนึ่งตัวไปยัง**ข้อมูลตัวเดียวกัน**ในเวลาเดียวกัน)
— **borrow checker ไม่มีทาง "มองทะลุ" เข้าไปวิเคราะห์ค่าจริงของ `mid` ได้เลยว่าสองช่วง `[..mid]` และ `[mid..]`
ไม่มีวันซ้อนทับกันในทางความหมาย (semantics)** มันเห็นแค่โครงสร้าง syntax ว่า "ยืม slice ตัวเดียวกันแบบ mutable
สองครั้ง" เท่านั้น — นี่คือตัวอย่างที่ชัดเจนที่สุดของ "โปรแกรมที่ปลอดภัยจริง 100% แต่ borrow checker พิสูจน์ให้
ไม่ได้" ตามที่อธิบายไว้ในหัวข้อ 41.3

#### เขียนใหม่ด้วย Raw Pointer: Safe Abstraction เหนือ Unsafe Code

วิธีแก้คือใช้หลักการจากหัวข้อ 41.8: เขียน `unsafe` เล็ก ๆ ที่ตรวจสอบเงื่อนไขที่จำเป็นให้ครบก่อน แล้วห่อด้วย safe
signature:

```rust
fn split_at_mut_demo<T>(slice: &mut [T], mid: usize) -> (&mut [T], &mut [T]) {
    let len = slice.len();
    let ptr = slice.as_mut_ptr();

    // ตรวจสอบเงื่อนไขที่จำเป็นก่อนเข้าสู่ unsafe เสมอ — เหมือนหลักการเดียวกับ safe_read_at ในหัวข้อ 41.8
    // ถ้า mid > len ให้ panic ทันที (ยังดีกว่าเข้าสู่ unsafe ด้วยค่าที่ไม่ถูกต้อง)
    assert!(mid <= len, "mid ({mid}) ต้องไม่เกิน len ของ slice ({len})");

    unsafe {
        // SAFETY:
        // 1. `ptr` มาจาก `slice.as_mut_ptr()` จึงชี้ไปยัง allocation ที่ถูกต้องและมีขนาดอย่างน้อย `len` element เสมอ
        // 2. `mid <= len` ถูกการันตีไปแล้วด้วย assert! ข้างบน จึงมั่นใจได้ว่า ptr.add(mid) ยังอยู่ในขอบเขตของ allocation เดิม (หรือเท่ากับ one-past-the-end ซึ่งถูกต้องตามกฎของ Rust)
        // 3. ช่วง [0, mid) และ [mid, len) ไม่มีวันทับกันเลย เพราะถูกแบ่งด้วยจุดตัดเดียวกัน (mid) พอดี
        //    — นี่คือความรู้เชิงความหมาย (semantic knowledge) ที่มนุษย์พิสูจน์ได้แต่ borrow checker พิสูจน์ไม่ได้
        // จึงปลอดภัย 100% ที่จะสร้าง mutable reference สองตัวไปยังสอง "ช่วง" ที่ไม่ทับกันนี้พร้อมกัน
        let left = slice::from_raw_parts_mut(ptr, mid);
        let right = slice::from_raw_parts_mut(ptr.add(mid), len - mid);
        (left, right)
    }
}

use std::slice;

fn main() {
    let mut v = vec![1, 2, 3, 4, 5, 6];

    let (left, right) = split_at_mut_demo(&mut v, 3);
    println!("ครึ่งแรก: {left:?}");
    println!("ครึ่งหลัง: {right:?}");

    left[0] = 100;   // แก้ไขครึ่งแรกได้อิสระ
    right[0] = 200;  // แก้ไขครึ่งหลังได้อิสระพร้อมกัน — คนละ memory location กันจริง ไม่ทับกันเลย

    println!("หลังแก้ไข: {v:?}");
}
```

ผลลัพธ์:

```
ครึ่งแรก: [1, 2, 3]
ครึ่งหลัง: [4, 5, 6]
หลังแก้ไข: [100, 2, 3, 200, 5, 6]
```

มาแยกวิเคราะห์ทีละส่วนว่าทำไมโค้ดนี้ปลอดภัยจริง ไม่ใช่แค่ "compile ผ่านแล้วจบ":

1. **`slice.as_mut_ptr()`**: ดึง raw pointer ที่ชี้ไปยัง element แรกของ slice ออกมา — การกระทำนี้เองไม่ใช่
   `unsafe` (ตามที่อธิบายไว้ในหัวข้อ 41.4.1 ว่าการ "สร้าง" raw pointer ไม่ต้องใช้ `unsafe` เฉพาะตอน dereference
   เท่านั้น)
2. **`assert!(mid <= len, ...)`**: นี่คือขั้นตอนที่**สำคัญที่สุดของทั้งฟังก์ชัน** — มันคือจุดที่เราพิสูจน์
   precondition ที่จำเป็นสำหรับความปลอดภัยของ `unsafe` block ข้างล่าง **ก่อน**ที่จะเข้าสู่มัน ถ้า `mid > len`
   โปรแกรมจะ panic ทันที (ปลอดภัยกว่าการปล่อยให้เข้าสู่ `unsafe` ด้วยค่าที่ผิดมาก) — สังเกตว่านี่คือรูปแบบเดียวกัน
   เป๊ะ ๆ กับ `if index >= data.len() { return None; }` ใน `safe_read_at` ของหัวข้อ 41.8: **ตรวจสอบเงื่อนไขที่
   จำเป็นให้เสร็จก่อนเข้าสู่ unsafe เสมอ ไม่มีข้อยกเว้น**
3. **`slice::from_raw_parts_mut(ptr, mid)`**: นี่คือฟังก์ชัน `unsafe fn` จาก standard library ที่ **สร้าง mutable
   slice ขึ้นมาจาก raw pointer และความยาวที่กำหนด** — precondition ของมัน (ตาม `# Safety` ของมันจริงในเอกสาร
   standard library) คือ pointer ต้องไม่เป็น null, ต้องชี้ไปยัง memory ที่ถูกจัดสรรไว้อย่างถูกต้องอย่างน้อย `mid`
   element, และข้อมูลต้อง initialize ไว้แล้วครบ — ทั้งหมดนี้เป็นจริงเพราะ `ptr` มาจาก slice ที่มีอยู่จริงแล้ว
4. **`slice::from_raw_parts_mut(ptr.add(mid), len - mid)`**: สร้าง slice ที่สองโดยเลื่อน pointer ไปข้างหน้า
   `mid` element ก่อน (`ptr.add(mid)` คือการคำนวณ address ใหม่ ยังไม่ dereference จึงไม่ต้อง `unsafe` แยก — แต่
   อยู่ใน `unsafe` block เดียวกันเพราะ `from_raw_parts_mut` ที่ครอบมันอยู่คือ `unsafe fn`) แล้วกำหนดความยาวเป็น
   `len - mid` (จำนวน element ที่เหลือ)

**ทำไมความปลอดภัยของทั้งสอง slice การันตีได้แน่นอน 100%**: เพราะ `left` ครอบคลุมช่วง byte offset `[0, mid)`
คูณด้วยขนาดของ `T` และ `right` ครอบคลุมช่วง `[mid, len)` คูณด้วยขนาดของ `T` — **สองช่วงนี้ไม่มีวันทับกันเลยไม่ว่า
`mid` จะเป็นค่าอะไร** (ตราบใดที่ `mid <= len` เป็นจริงตามที่ `assert!` การันตีไว้) เพราะมันถูกแบ่งด้วยจุดตัดจุด
เดียวกันพอดี ไม่มีการซ้อนทับทางคณิตศาสตร์เกิดขึ้นได้เลย — นี่คือ**ความรู้เชิงความหมาย (semantic knowledge)** ที่
มนุษย์ผู้เขียนฟังก์ชันนี้เข้าใจและพิสูจน์ได้อย่างสมบูรณ์ แต่ borrow checker ไม่มีทางมองเห็นได้เพราะมันวิเคราะห์
แค่ "รูปแบบ" ของการยืม ไม่ได้วิเคราะห์ "ค่าจริง" ของตัวแปร `mid` เลย

**และนี่คือหัวใจสำคัญที่สุดของบทนี้ทั้งบท**: ฟังก์ชัน `split_at_mut_demo` ที่เราเขียนนี้ **มี `unsafe` อยู่ข้างใน
ก็จริง แต่ signature ของมัน (`fn split_at_mut_demo<T>(slice: &mut [T], mid: usize) -> (&mut [T], &mut [T])`)
เป็น safe function ธรรมดา 100%** — ผู้เรียกใช้ฟังก์ชันนี้จากภายนอกไม่ต้องเขียนคำว่า `unsafe` เลยแม้แต่คำเดียว
(สังเกตใน `main()` ข้างบนว่าเราเรียก `split_at_mut_demo(&mut v, 3)` ตรง ๆ โดยไม่มี `unsafe` ล้อมรอบ) และไม่มีทาง
เรียกมันจนเกิด undefined behavior ได้เลย (ถ้าส่ง `mid` ที่เกิน `len` จะ panic แบบควบคุมได้ ไม่ใช่ UB) — **นี่คือ
ตัวอย่างที่สมบูรณ์แบบที่สุดในวัฒนธรรม Rust ของคำว่า "safe abstraction เหนือ unsafe code": งานที่ borrow checker
พิสูจน์ให้ไม่ได้ (แบ่ง mutable reference เป็นสองส่วนที่ไม่ทับกัน) ถูกพิสูจน์โดยมนุษย์ครั้งเดียวอย่างรอบคอบ แล้วถูก
"ปิดผนึก" ไว้หลัง signature ที่ปลอดภัยสำหรับทุกคนที่เรียกใช้ต่อจากนี้ไปตลอดกาล ไม่ต้องพิสูจน์ซ้ำอีกเลย**

#### 41.9.1 ทำไม Mutable Reference สองตัวพร้อมกันมีค่าจริง: ตัวอย่างการใช้งานในระบบคลังสินค้า

เพื่อไม่ให้ `split_at_mut` ดูเป็นแค่ "trick ทางเทคนิค" ที่ไม่มีประโยชน์ใช้งานจริง ลองดูสถานการณ์ที่มันมีค่าจริงมาก:
สมมติระบบคลังสินค้าต้องปรับราคาสินค้าในคลัง (เพิ่มราคาสินค้าทุกตัวขึ้น 10% เพื่อรองรับภาษีใหม่) แต่คลังมีสินค้า
จำนวนมาก จึงต้องการแบ่งงานประมวลผลเป็นสองเธรดพร้อมกันเพื่อความเร็ว (นำความรู้เรื่อง `thread::scope` จาก Part 37
กลับมาใช้) — โครงสร้างข้อมูลคือ `Vec<f64>` เดียวที่เก็บราคาสินค้าทุกตัวเรียงกันในหน่วยความจำเดียว และเราต้องการให้
สองเธรดแก้ไข**คนละครึ่ง**ของ `Vec` เดียวกันนี้พร้อมกันโดยตรง (ไม่ต้อง clone ข้อมูลออกมาแยกกันซึ่งจะเสีย memory
และเวลา copy โดยไม่จำเป็น):

```rust
use std::slice;
use std::thread;

fn split_at_mut_demo<T>(slice: &mut [T], mid: usize) -> (&mut [T], &mut [T]) {
    let len = slice.len();
    let ptr = slice.as_mut_ptr();
    assert!(mid <= len, "mid ({mid}) ต้องไม่เกิน len ของ slice ({len})");

    unsafe {
        (
            slice::from_raw_parts_mut(ptr, mid),
            slice::from_raw_parts_mut(ptr.add(mid), len - mid),
        )
    }
}

/// เพิ่มราคาทุกตัวใน chunk ขึ้น 10% (ใช้แทนการคำนวณภาษีใหม่)
fn apply_tax_increase(prices: &mut [f64]) {
    for price in prices.iter_mut() {
        *price *= 1.10;
    }
}

fn main() {
    let mut warehouse_prices = vec![100.0, 200.0, 300.0, 400.0, 500.0, 600.0];
    let midpoint = warehouse_prices.len() / 2;

    // แบ่ง Vec เดียวกันเป็นสองครึ่งที่ไม่ทับกันเลย แล้วส่งให้คนละเธรดแก้ไขพร้อมกัน
    let (first_half, second_half) = split_at_mut_demo(&mut warehouse_prices, midpoint);

    thread::scope(|scope| {
        scope.spawn(|| apply_tax_increase(first_half));
        scope.spawn(|| apply_tax_increase(second_half));
    });

    println!("ราคาสินค้าหลังปรับภาษี: {warehouse_prices:?}");
}
```

ผลลัพธ์:

```
ราคาสินค้าหลังปรับภาษี: [110.00000000000001, 220.00000000000003, 330.0, 440.00000000000006, 550.0, 660.0]
```

(ตัวเลขทศนิยมท้ายบรรทัดที่ดูไม่กลมพอดี เช่น `110.00000000000001` เป็นเรื่องปกติของ floating-point arithmetic
ตามที่เรียนใน Part 3 — ไม่เกี่ยวข้องกับ `unsafe` หรือ UB แต่อย่างใด)

จุดสำคัญที่สุดของตัวอย่างนี้: `thread::scope` (จาก Part 37) กำหนดให้ closure ที่ส่งให้ `scope.spawn()` ต้องมี
`'static` lifetime หรือถูกจำกัดด้วย scope ที่ปิดก่อนฟังก์ชันจบ — และการที่เราส่ง `first_half`/`second_half` (ซึ่ง
เป็น `&mut [f64]` ที่มี lifetime ผูกกับ `warehouse_prices`) เข้าไปในสองเธรดพร้อมกันได้โดย **compiler ไม่ฟ้องเรื่อง
aliasing เลย** ก็เพราะ `split_at_mut_demo` การันตีไว้แล้วว่าทั้งสอง mutable reference นี้**ไม่ทับกันในทางความหมาย
จริง** (ตามที่พิสูจน์ไว้ในหัวข้อ 41.9) — ถ้าไม่มี `split_at_mut` (หรือฟังก์ชันแบบนี้) เราจะไม่มีทางส่ง mutable
reference ไปยัง `Vec` เดียวกันให้สองเธรดพร้อมกันได้เลยด้วย safe Rust ล้วน ๆ (borrow checker จะปฏิเสธทันทีเพราะ
มันเห็นแค่ว่ามีการยืม mutable สองครั้งจากตัวแปรเดียวกัน) — **นี่คือเหตุผลเชิงปฏิบัติที่แท้จริงว่าทำไมฟังก์ชันแบบ
`split_at_mut` มีค่ามากในโค้ดที่ต้องการ parallelism ประสิทธิภาพสูง**: มันเปิดทางให้ทำงานคู่ขนานบน buffer เดียวกัน
ได้โดยไม่ต้อง copy ข้อมูล และยังปลอดภัย 100% เพราะการพิสูจน์ความไม่ทับกันถูกทำไว้ครั้งเดียวอย่างรอบคอบแล้ว

### 41.10 Best Practice: ทำ `unsafe` Block ให้เล็กที่สุดเท่าที่จะทำได้

จากตัวอย่าง `split_at_mut_demo` ในหัวข้อก่อนหน้า สังเกตว่า `unsafe { }` block ครอบ**เฉพาะสองบรรทัดที่จำเป็นต้อง
ใช้ raw pointer จริง ๆ** ไม่ได้ครอบทั้งฟังก์ชัน (การเรียก `slice.as_mut_ptr()`, `assert!`, และการคำนวณ `len`
ทั้งหมดอยู่**นอก** `unsafe` block) — นี่ไม่ใช่เรื่องบังเอิญ แต่เป็น **best practice ที่สำคัญที่สุดข้อหนึ่งในการ
เขียน `unsafe` Rust**: **ทำ `unsafe` block ให้เล็กที่สุดเท่าที่จะทำได้ ครอบเฉพาะปฏิบัติการที่จำเป็นต้องเป็น
`unsafe` จริง ๆ เท่านั้น ไม่ใช่ครอบทั้งฟังก์ชันเพราะความขี้เกียจ**

เหตุผลเชิงลึกที่หลักการนี้สำคัญมาก: เวลาที่ต้อง **audit** (ตรวจสอบทบทวน) โค้ดว่าปลอดภัยหรือไม่ — อาจเป็นตอน code
review, ตอนดีบัคบั๊กที่สงสัยว่าเป็น UB, หรือตอนที่มีคนมาแก้โค้ดในอนาคต — สิ่งที่ต้องทำคือ**อ่านเฉพาะบรรทัดที่อยู่
ใน `unsafe` block และพยายามพิสูจน์ว่า precondition ทั้งหมดที่จำเป็นเป็นจริง ณ จุดนั้น** ถ้า `unsafe` block เล็ก
และครอบเฉพาะสิ่งที่จำเป็น การ audit จะทำได้เร็วและแม่นยำ แต่ถ้า `unsafe` block ใหญ่และครอบโค้ดที่ไม่เกี่ยวข้องกับ
raw pointer เลยด้วย (เช่น `println!`, การคำนวณทั่วไป, การเรียก safe function อื่น) ผู้ตรวจสอบจะต้องเสียเวลาแยกแยะ
ว่า**ส่วนไหนของ block นี้กันแน่ที่ "อันตรายจริง"** และเสี่ยงมองข้ามจุดที่แท้จริงที่ต้องระวังไปเลย

ลองเปรียบเทียบสองแบบให้เห็นภาพชัด — ตัวอย่างฟังก์ชันที่รวมค่าใน slice โดยใช้ `get_unchecked` เพื่อความเร็ว
(ข้าม bounds check ที่ปกติเกิดขึ้นทุกครั้งที่ index ด้วย `[]`):

**แบบที่ไม่ดี — `unsafe` block กว้างเกินความจำเป็น:**

```rust
fn sum_unchecked_wide(data: &[i32]) -> i32 {
    unsafe {
        let mut total = 0;
        for i in 0..data.len() {
            total += *data.get_unchecked(i); // นี่คือบรรทัดเดียวที่ "จำเป็น" ต้อง unsafe จริง ๆ
        }
        println!("รวมได้ {total} จาก {} ตัว", data.len()); // ไม่จำเป็นต้องอยู่ใน unsafe เลย!
        total
    }
}

fn main() {
    let data = vec![1, 2, 3, 4, 5];
    println!("ผลรวม: {}", sum_unchecked_wide(&data));
}
```

**แบบที่ดี — `unsafe` block แคบ ครอบเฉพาะที่จำเป็น:**

```rust
fn sum_unchecked_tight(data: &[i32]) -> i32 {
    let mut total = 0;
    for i in 0..data.len() {
        // SAFETY: i มาจาก 0..data.len() เสมอในลูปนี้ จึงมั่นใจได้ว่า i < data.len() ทุกครั้งที่เรียก
        total += unsafe { *data.get_unchecked(i) };
    }
    println!("รวมได้ {total} จาก {} ตัว", data.len()); // อยู่นอก unsafe แล้ว — เห็นชัดว่าไม่เกี่ยวกับความเสี่ยงเลย
    total
}

fn main() {
    let data = vec![1, 2, 3, 4, 5];
    println!("ผลรวม: {}", sum_unchecked_tight(&data));
}
```

ผลลัพธ์ (เหมือนกันทั้งสองแบบ):

```
รวมได้ 15 จาก 5 ตัว
ผลรวม: 15
```

ทั้งสองฟังก์ชันทำงาน**เหมือนกันทุกประการ** และให้ผลลัพธ์เดียวกัน แต่แบบที่สองดีกว่าอย่างชัดเจนในเชิงวิศวกรรม
ซอฟต์แวร์: ผู้อ่านโค้ดเห็น `unsafe { *data.get_unchecked(i) }` แค่บรรทัดเดียวและรู้ทันทีว่า **นี่คือจุดเดียวที่
ต้องพิสูจน์ความปลอดภัย** (และคอมเมนต์ `SAFETY:` ที่อยู่เหนือมันบอกเหตุผลไว้ครบ) ในขณะที่แบบแรกทำให้ทุกบรรทัด
ภายใน block ดู "น่าสงสัยเท่ากันหมด" ทั้งที่จริง ๆ มีแค่บรรทัดเดียวที่เสี่ยงจริง — **หลักการปฏิบัติที่ควรยึดถือ**:
เขียนคอมเมนต์ `// SAFETY: ...` เหนือทุก `unsafe` block เสมอ อธิบายว่าเงื่อนไขอะไรที่ทำให้ปฏิบัติการข้างในบรรทัดนี้
ปลอดภัย และพยายามให้ `unsafe` block มีขนาดเล็กที่สุดเท่าที่ยังทำงานได้ถูกต้อง — นี่คือ convention ที่ทีมพัฒนา
standard library ของ Rust เองใช้อย่างเคร่งครัดในทุกจุดที่มี `unsafe` ในโค้ดของพวกเขา

#### 41.10.1 Lint `unused_unsafe` และ `#[allow(unused_unsafe)]`

มีอีกด้านหนึ่งของการ "จัดการขนาด `unsafe` block ให้เหมาะสม" ที่ควรรู้จัก: compiler มี lint ชื่อ `unused_unsafe`
(เปิดเป็น warning โดย default) ที่จะเตือนทันทีถ้าคุณเขียน `unsafe { }` ครอบโค้ดที่**ไม่มีปฏิบัติการใดในห้าข้อของ
หัวข้อ 41.4 อยู่เลยแม้แต่ข้อเดียว** — ลองดูตัวอย่าง:

```rust
fn redundant_unsafe_example() -> i32 {
    let x = 42;
    unsafe {
        x // ไม่มี raw pointer, ไม่มี unsafe fn, ไม่มี static mut, ไม่มี union — ไม่จำเป็นต้องมี unsafe เลย
    }
}

fn main() {
    println!("{}", redundant_unsafe_example());
}
```

โค้ดนี้ compile ผ่านแต่แสดง warning:

```
warning: unnecessary `unsafe` block
 --> src/main.rs:3:5
  |
3 |     unsafe {
  |     ^^^^^^ unnecessary `unsafe` block
  |
  = note: `#[warn(unused_unsafe)]` (part of `#[warn(unused)]`) on by default
```

lint นี้มีประโยชน์จริงในทางปฏิบัติ: มันมักจะเตือนคุณเมื่อมีการ **refactor โค้ดออกจนส่วนที่ต้อง `unsafe` จริง ๆ
ถูกลบทิ้งไปแล้ว แต่ตัว `unsafe { }` เองถูกลืมลบตามไปด้วย** — เป็นสัญญาณว่าโค้ดอาจ "เก่า" กว่าที่ควรและควรทำความ
สะอาด (สอดคล้องกับหลักการ minimize scope ของหัวข้อ 41.10 โดยตรง: ถ้า `unsafe` block ไม่มีอะไรที่ต้อง unsafe อยู่
เลย มันไม่ควรมีอยู่)

แต่มีบางสถานการณ์ (พบไม่บ่อย) ที่การมี `unsafe { }` ที่ดู "ไม่จำเป็น" นั้นตั้งใจจริง ๆ เช่นโค้ดที่ generate มาจาก
`macro_rules!` (Part 36) ที่ต้องใช้ pattern เดียวกันได้ทั้งกรณีที่เนื้อโค้ดข้างในต้อง unsafe และกรณีที่ไม่ต้อง
(macro ไม่รู้ล่วงหน้าว่าจะถูกเรียกใช้แบบไหน) ในสถานการณ์แบบนี้สามารถปิด lint นี้เฉพาะจุดได้ด้วย
`#[allow(unused_unsafe)]`:

```rust
#[allow(unused_unsafe)]
fn from_generated_macro() -> i32 {
    let x = 42;
    // สมมติว่าบรรทัดนี้ถูก generate มาจาก macro ที่ใช้ pattern เดียวกันกับกรณีอื่นที่ต้อง unsafe จริง ๆ
    unsafe { x }
}

fn main() {
    println!("{}", from_generated_macro());
}
```

**ข้อควรระวัง**: `#[allow(unused_unsafe)]` ควรใช้เฉพาะกรณีที่มีเหตุผลชัดเจนแบบนี้เท่านั้น **ไม่ใช่การปิด warning
เพื่อความสะดวกเฉย ๆ** เพราะถ้าใช้พร่ำเพรื่อจะทำให้ signal ที่มีประโยชน์ของ lint นี้ (ช่วยจับ `unsafe` block ที่
"ตกค้าง" อยู่โดยไม่จำเป็นหลัง refactor) หายไปด้วย — ตรงกันข้ามกับหลักการ minimize scope ที่ทั้งหัวข้อนี้พยายาม
สื่อสารมาตลอด

### 41.11 เครื่องมือช่วยตรวจจับ UB: Miri

จากหัวข้อ 41.7 เราเห็นแล้วว่า **การทดสอบ (testing) ไม่สามารถพิสูจน์ความไม่มี UB ได้เลย** เพราะโค้ดที่มี UB อาจ
"ดูเหมือนทำงานถูกต้อง" ผ่านทุก test case ที่คุณคิดจะเขียน แล้วพังในสถานการณ์ที่ไม่ได้ทดสอบ — คำถามที่ตามมาคือ:
**แล้วเราไว้ใจ `unsafe` code ของตัวเองได้อย่างไรเลย ถ้า testing ธรรมดาไม่ช่วยอะไร?**

คำตอบส่วนหนึ่ง (ไม่ใช่คำตอบสมบูรณ์ 100% แต่ช่วยได้มากในทางปฏิบัติ) คือเครื่องมือที่ชื่อ **Miri** — Miri คือ
**interpreter ของ Rust MIR (Mid-level Intermediate Representation ซึ่งเป็นรูปแบบภายในที่ compiler ใช้ก่อน
แปลงเป็น machine code)** ที่รันโค้ด Rust แบบ**ตีความทีละคำสั่ง (interpret)** แทนการ compile เป็น native code
ตรง ๆ และในระหว่างการตีความนั้น มันจะ**ตรวจสอบเงื่อนไขความปลอดภัยของ memory หลายประเภทไปด้วยพร้อมกัน** เช่น:

- การอ่าน/เขียน memory ที่อยู่นอกขอบเขตของ allocation (out-of-bounds access)
- การใช้ memory ที่ถูก deallocate ไปแล้ว (use-after-free)
- การสร้าง reference ที่ไม่ align ตรงตามที่ type กำหนด (misaligned reference)
- การละเมิดกฎ aliasing ของ reference ที่ Rust กำหนดไว้ (เช่นมี `&mut T` สองตัวที่ชี้ไปยังข้อมูลเดียวกันพร้อมกัน
  แม้จะสร้างผ่าน raw pointer ก็ตาม)
- การอ่าน memory ที่ยังไม่ถูก initialize (reading uninitialized memory)
- data race ระหว่างเธรดในบางกรณี

วิธีใช้งานในทางปฏิบัติ (ต้องใช้ Rust nightly toolchain เพราะ Miri ยังไม่ถูกรวมเข้า stable):

```text
rustup +nightly component add miri
cargo +nightly miri test
```

หรือถ้าต้องการรันโปรแกรมทั้งโปรแกรม (ไม่ใช่แค่ test) ผ่าน Miri เพื่อดูว่ามี UB แอบซ่อนอยู่ระหว่างการทำงานจริง
หรือไม่ ใช้คำสั่ง `cargo +nightly miri run` แทนได้เช่นกัน — ทั้งสองคำสั่งใช้หลักการเดียวกัน แค่ต่างกันที่ target
ที่ถูกตีความ (test suite เทียบกับ `fn main()`)

คำสั่งนี้จะรัน test suite ของโปรเจกต์ทั้งหมดผ่าน Miri interpreter แทนการรันแบบ native — ถ้ามี `unsafe` code
ที่ละเมิดเงื่อนไขข้างบน Miri จะรายงาน error ออกมาทันทีพร้อมชี้ตำแหน่งที่แน่นอน **แม้ว่าการรันแบบ native ปกติจะ
"ดูเหมือนทำงานได้" อย่างสมบูรณ์แบบก็ตาม** เพราะ Miri ไม่ได้แค่รันโค้ดแล้วดูว่า crash หรือไม่ — มันจำลอง**โมเดล
ความหมายที่เข้มงวดของภาษา Rust** และตรวจสอบว่าโค้ดสอดคล้องกับโมเดลนั้นในทุกขั้นตอนจริง ๆ

**ข้อควรรู้ที่สำคัญ**: Miri **ไม่ใช่การพิสูจน์ที่สมบูรณ์ (not a formal proof)** — มันตรวจสอบได้แค่ **path ของ
โค้ดที่ test case ของคุณ execute จริงเท่านั้น** (เหมือนกับข้อจำกัดของ testing ทั่วไป) ถ้า test ของคุณไม่ครอบคลุม
edge case ที่มี UB อยู่ Miri ก็จะไม่เจอมันเช่นกัน — แต่มันยังมีค่ามากในทางปฏิบัติ เพราะมันเปลี่ยนสถานการณ์จาก
"UB ที่ซ่อนเงียบและไม่มีสัญญาณเตือนเลย" (ตามที่อธิบายในหัวข้อ 41.7) ให้กลายเป็น **"UB ที่ถูกตรวจจับได้ทันทีถ้า test
case ของคุณครอบคลุม path ที่มีปัญหา"** — ทีมพัฒนา standard library ของ Rust เองใช้ Miri รัน test ของ `Vec`,
`String`, และ smart pointer ทุกตัวอย่างสม่ำเสมอ เพื่อจับ regression ด้าน UB ที่อาจแอบเข้ามาตอนแก้โค้ดในอนาคต —
บทเรียนที่ควรจำคือ: **ทุกครั้งที่เขียน `unsafe` code ที่ไม่ใช่แบบง่ายที่สุด ควรพิจารณารัน test suite ผ่าน Miri
เป็นส่วนหนึ่งของ CI pipeline เสมอ** เพื่อเพิ่มความมั่นใจ (แม้จะไม่ถึงระดับการันตี 100% แบบที่ borrow checker
ให้กับ safe Rust ก็ตาม)

## กับดักที่พบบ่อย (Common Pitfalls)

### 1. เข้าใจผิดว่า `unsafe` ปิดกฎของ Rust ทั้งหมด

นี่คือกับดักที่พบบ่อยที่สุดในหมู่มือใหม่ (และเป็นเหตุผลที่หัวข้อ 41.2 และ 41.5 ของบทนี้เน้นย้ำเรื่องนี้ซ้ำแล้วซ้ำ
อีก) มือใหม่มักคิดว่าเมื่อเจอ compile error แล้วจน "แก้ไม่ได้" การเติม `unsafe { }` ครอบทั้งฟังก์ชันจะ "แก้ปัญหา"
ได้เสมอ ลองดูตัวอย่าง:

```rust
fn main() {
    let mut v = vec![1, 2, 3];
    unsafe {
        let r = &v[0];
        v.push(4); // ยังคง error เหมือนเดิม แม้จะพยายามครอบด้วย unsafe
        println!("{r}");
    }
}
```

การครอบทั้ง `main()` ด้วย `unsafe { }` **ไม่ช่วยอะไรเลย** เพราะ `v.push(4)` ไม่ใช่หนึ่งในห้าปฏิบัติการที่ `unsafe`
ปลดล็อก (ตามหัวข้อ 41.4) — โค้ดนี้ยัง compile ไม่ผ่านด้วย error `E0502` เดียวกับที่ไม่มี `unsafe` เลยทุกประการ (ตาม
ที่พิสูจน์ไว้แล้วในหัวข้อ 41.5) วิธีแก้ที่ถูกต้องคือแก้ตามหลักการของ Part 7 ตามปกติ (จำกัด scope ของ `r` ให้จบก่อน
`push`) ไม่ใช่การเติม `unsafe`

### 2. เขียน `unsafe fn` เป็น public API โดยไม่มี `# Safety` Doc

```rust
// ไม่ดี — ไม่มีใครรู้ว่า precondition ที่ต้องรักษาคืออะไร
pub unsafe fn process_buffer(ptr: *mut u8, len: usize) {
    // ...
}
```

clippy มี lint ชื่อ `missing_safety_doc` ที่จะเตือนถ้า public `unsafe fn` ไม่มี `# Safety` section (แม้ lint
นี้ปิดโดย default เพื่อไม่ให้เข้มงวดเกินไปสำหรับโค้ดภายในที่ไม่ได้ export แต่ควรเปิดเสมอสำหรับ crate ที่เป็น
library) วิธีแก้: เขียน `# Safety` section ตามหลักการจาก Part 34 และหัวข้อ 41.6 ของบทนี้เสมอ อธิบาย precondition
ทุกข้อที่ผู้เรียกต้องรักษาให้ครบ

### 3. เขียน `unsafe` Block กว้างเกินความจำเป็น จนตรวจสอบยาก

ตามที่อธิบายในหัวข้อ 41.10 — ครอบทั้งฟังก์ชันด้วย `unsafe { }` ทั้งที่มีแค่บรรทัดเดียวที่จำเป็นต้องเป็น `unsafe`
จริง ๆ ทำให้การ code review และการ audit ทำได้ยากขึ้นมาก เพราะแยกไม่ออกว่าส่วนไหนของโค้ดคือส่วนที่ "อันตรายจริง"
วิธีแก้: ทำตามหลักการ minimize scope และเขียนคอมเมนต์ `// SAFETY:` อธิบายเหตุผลเหนือทุก `unsafe` block เสมอ

### 4. เชื่อว่า "test ผ่านหมด" แปลว่าโค้ด `unsafe` ไม่มี UB

ตามที่อธิบายในหัวข้อ 41.7 — การที่ test suite ผ่านทั้งหมด (รวมถึงการรันจริงในโปรดักชันเป็นเวลานาน) **ไม่ได้
การันตีว่าไม่มี UB** เพราะ UB อาจไม่แสดงอาการเลยจนกว่าจะเปลี่ยน optimization level, compiler เวอร์ชัน, หรือ
สถาปัตยกรรม CPU มือใหม่มักเข้าใจผิดว่า "รันได้ถูกต้องแปลว่าโค้ดถูกต้อง" ทั้งที่ในโลกของ `unsafe` ประโยคนี้ไม่เป็น
จริงเสมอไป วิธีแก้: ใช้ Miri (หัวข้อ 41.11) ร่วมกับการ reasoning อย่างรอบคอบทุกครั้งที่เขียน `unsafe` และเมื่อเป็น
ไปได้ให้เลือกใช้ safe abstraction ที่มีอยู่แล้วใน standard library (เช่น `get()` ที่คืน `Option` แทน
`get_unchecked()`) เว้นแต่มี profiling data ที่ยืนยันชัดเจนว่าจำเป็นต้องข้าม bounds check จริง ๆ เพื่อ performance

### 5. สร้าง Reference ไปยัง `static mut` โดยตรง แล้วเจอ Warning หรือ Error ที่ไม่คาดคิด

```rust
static mut COUNTER: u32 = 0;

fn bad_increment() {
    unsafe {
        COUNTER += 1;
        println!("{COUNTER}"); // การ format แบบนี้แอบสร้าง reference ไปยัง COUNTER
    }
}
```

โค้ดนี้ compile ผ่านได้ แต่ compiler จะแสดง warning `static_mut_refs` เพราะ `println!("{COUNTER}")` แอบสร้าง
`&COUNTER` (reference ไปยัง static mut) ขึ้นมาเบื้องหลังเพื่อ format ค่า — และ**การสร้าง reference ไปยัง `static
mut`** เป็นสิ่งที่อันตรายกว่าการอ่าน/เขียนค่าตรง ๆ เพราะ reference นั้นอาจถูกส่งไปให้โค้ดส่วนอื่นถือไว้นาน ๆ ในขณะ
ที่มีโค้ดอื่นมาแก้ไขค่าเดิมพร้อมกัน (เกิด aliasing ที่ compiler ควบคุมไม่ได้อีกต่อไป) วิธีแก้ที่ถูกต้อง: อ่านค่า
ออกมาเก็บใน local variable ก่อนเสมอ อย่าสร้าง reference ไปยัง `static mut` ตรง ๆ (ตามที่ตัวอย่างในหัวข้อ 41.4.3
ทำไว้ — ใช้ `let count = unsafe { REQUEST_COUNTER };` แล้วค่อย print ค่าตัวแปร local แทน)

วิธีแก้ที่ "ถูกต้องยิ่งกว่า" (และเป็นแนวทางที่แนะนำใน Rust สมัยใหม่) คือใช้ `std::ptr::addr_of!`/`addr_of_mut!`
เพื่อสร้าง raw pointer ไปยัง `static mut` **โดยไม่ผ่านการสร้าง reference เลยแม้แต่ขั้นตอนเดียว**:

```rust
static mut COUNTER: u32 = 0;

fn good_increment() {
    unsafe {
        // สร้าง raw pointer ตรงไปยัง COUNTER โดยไม่ผ่านการสร้าง &mut COUNTER เลย — ไม่ trigger
        // static_mut_refs warning เพราะไม่มี "reference" เกิดขึ้นในขั้นตอนนี้เลย มีแต่ raw pointer
        let ptr = std::ptr::addr_of_mut!(COUNTER);
        *ptr += 1;
    }
}

fn read_counter() -> u32 {
    unsafe { *std::ptr::addr_of!(COUNTER) }
}

fn main() {
    good_increment();
    good_increment();
    good_increment();
    println!("จำนวน request ทั้งหมด: {}", read_counter());
}
```

ผลลัพธ์:

```
จำนวน request ทั้งหมด: 3
```

`addr_of_mut!`/`addr_of!` (รายละเอียดเต็มของ raw pointer macro เหล่านี้อยู่ใน Part 42) คือแนวทางที่ปลอดภัยกว่า
เพราะมันแยกขั้นตอน "คำนวณ address" กับขั้นตอน "dereference" ออกจากกันอย่างชัดเจน โดยไม่มีขั้นตอนกลางที่ต้องสร้าง
`&mut` reference ไปยัง `static mut` เลย — ซึ่งคือต้นเหตุของ warning `static_mut_refs` ที่กล่าวไปข้างบน

### 6. ใช้ `unsafe` เพื่อ "หลบเลี่ยง" กฎของ Send/Sync โดยไม่เข้าใจเหตุผล

จาก Part 40 เราเรียนว่า `Rc<T>` ไม่ implement `Send` เพราะตัวนับ reference ภายในไม่ใช่ atomic — มือใหม่บางคนที่
เพิ่งรู้จัก `unsafe impl` อาจคิดจะเขียน `unsafe impl Send for MyWrapper<Rc<T>> {}` เพื่อ "บังคับ" ให้ compiler
ยอมรับโดยไม่แก้ปัญหาที่ต้นเหตุจริง ๆ — นี่คือการใช้ `unsafe` ที่**ผิดหลักการโดยสิ้นเชิง**: การเขียน `unsafe impl
Send` คือการที่คุณ "เซ็นรับรอง" ด้วยตัวเองว่า type นี้ปลอดภัยที่จะส่งข้ามเธรดจริง ๆ — ถ้าตัวนับของ `Rc<T>` ที่
ซ่อนอยู่ภายในยังไม่ใช่ atomic จริง ๆ การเซ็นรับรองแบบนี้คือการโกหก compiler และจะทำให้เกิด data race จริงตอน
รันโปรแกรมข้ามเธรด (เป็น UB ที่ร้ายแรงมาก เพราะเกิดกับตัวนับ reference ที่ถ้าค่าผิดพลาดอาจนำไปสู่ double-free
ได้) วิธีแก้ที่ถูกต้องเสมอ: เปลี่ยนไปใช้ `Arc<T>` (ที่ใช้ atomic counter จริง) ตามที่ Part 39 สอนไว้ ไม่ใช่การ
เขียน `unsafe impl` เพื่อหลบเลี่ยงการตรวจสอบของ compiler

### 7. ลืมว่าการตีความ Bit Pattern ผ่าน `union` ไม่ portable ข้าม Platform

มือใหม่ที่เริ่มใช้ `union` เพื่อตีความ bit pattern ใหม่ (ตามหัวข้อ 41.4.5) มักลืมว่า **memory layout ของ struct/
union ไม่ได้ถูกกำหนดตายตัวโดย Rust เสมอไป** (ยกเว้นเขียน `#[repr(C)]` กำกับไว้อย่างชัดเจน) และแม้จะกำหนด
`#[repr(C)]` แล้ว การตีความ byte ของตัวเลขก็ยังขึ้นอยู่กับ **endianness** ของ CPU (little-endian อย่าง x86/ARM
ส่วนใหญ่ เทียบกับ big-endian ที่พบในบางระบบฝังตัว) โค้ดที่ทดสอบผ่านบนเครื่องพัฒนา (มักเป็น little-endian) อาจให้
ผลลัพธ์ผิดไปเลยเมื่อ compile ไปรันบนสถาปัตยกรรมอื่น วิธีแก้: ถ้าต้องการตีความ bit pattern ข้าม type แบบ portable
ให้ใช้ method ที่ standard library เตรียมไว้ให้แล้วอย่าง `f32::to_bits()`/`f32::from_bits()` หรือ
`i32::to_le_bytes()`/`from_le_bytes()` ที่จัดการเรื่อง endianness ให้อย่างชัดเจนและปลอดภัย 100% (ไม่ต้องใช้
`unsafe`/`union` เลยด้วยซ้ำ) แทนการเขียน `union` เองสำหรับงานที่ standard library มีเครื่องมือรองรับอยู่แล้ว

## แบบฝึกหัด (Exercises)

1. **โจทย์ระดับง่าย**: เขียนฟังก์ชัน `unsafe fn first_byte_unchecked(bytes: &[u8]) -> u8` ที่คืน byte แรกของ
   slice โดยไม่ตรวจสอบว่า slice ว่างหรือไม่ (ใช้ raw pointer dereference ตรง ๆ) พร้อมเขียน `# Safety` doc
   comment ที่อธิบาย precondition ให้ครบถ้วน (ต้องระบุชัดว่า `bytes` ต้องไม่ว่าง) จากนั้นเขียนฟังก์ชัน safe
   wrapper ชื่อ `first_byte(bytes: &[u8]) -> Option<u8>` ที่ตรวจสอบว่า slice ว่างหรือไม่ก่อนเรียก `unsafe fn`
   ข้างในเสมอ (ใช้หลักการเดียวกับ `safe_read_at` ในหัวข้อ 41.8) ทดสอบด้วย slice ว่างและ slice ที่มีข้อมูล
   ทั้งสองกรณีใน `main()`

   (hint: `bytes.as_ptr()` ให้ raw pointer ไปยัง element แรก, เงื่อนไขที่ต้องเช็คก่อนเรียก unsafe fn คือ
   `!bytes.is_empty()`)

2. **โจทย์ระดับกลาง**: โค้ดข้างล่างนี้ compile ไม่ผ่าน จงอธิบายว่าทำไม (อ้างอิงหลักการจากหัวข้อ 41.5) และแก้ไข
   ให้ compile ผ่านโดย**ไม่เปลี่ยนพฤติกรรมของโปรแกรม** (คำใบ้: ปัญหาไม่ได้อยู่ที่ raw pointer เลยแม้แต่นิดเดียว):

   ```rust
   fn main() {
       let data = vec![1, 2, 3];
       let ptr = data.as_ptr();

       unsafe {
           let first = &data[0];
           let value_via_ptr = *ptr;
           drop(data); // ลบ data ทิ้งทั้งที่ first ยังอ้างถึงอยู่
           println!("{first} {value_via_ptr}");
       }
   }
   ```

   (hint: ลองคิดว่า error message ที่ได้จะพูดถึง `first` หรือพูดถึง `ptr`/`value_via_ptr` — สังเกตว่า `drop(data)`
   เป็นการยึด ownership ของ `data` ไปทำลายทั้งที่ `first` ยังยืมอยู่ นี่คือกฎ borrowing ธรรมดาจาก Part 7 ที่ยังมีผล
   อยู่แม้ใน `unsafe` block ตามหลักการหัวข้อ 41.5 — ทางแก้คือย้ายลำดับการใช้งาน `first` ให้จบก่อน `drop(data)`)

3. **โจทย์ระดับยาก**: เขียนฟังก์ชัน `fn split_first_mut<T>(slice: &mut [T]) -> Option<(&mut T, &mut [T])>` ที่
   คืน mutable reference ไปยัง **element แรก** พร้อมกับ mutable slice ของ **element ที่เหลือทั้งหมด** พร้อมกัน
   (คืน `None` ถ้า slice ว่าง) — ฟังก์ชันนี้คือญาติของ `split_at_mut` ในหัวข้อ 41.9 (จริง ๆ แล้ว standard library
   มีฟังก์ชันนี้อยู่แล้วในชื่อ `slice::split_first_mut` ให้ลองเขียน implementation ของมันขึ้นมาเองโดยใช้หลักการ
   เดียวกันกับหัวข้อ 41.9 คือใช้ raw pointer + `assert`/`if` ตรวจสอบก่อน + ห่อด้วย safe signature) ทดสอบด้วย
   `Vec<i32>` จริง แล้วลองแก้ไขทั้ง element แรกและ slice ที่เหลือพร้อมกันเพื่อพิสูจน์ว่ามันทำงานได้จริง

   (hint: ใช้ `slice.split_at_mut(1)` เป็นฐานความคิด (ปลอดภัยกว่าการเขียน raw pointer ใหม่หมด เพราะ standard
   library implement มันให้ปลอดภัยแล้ว) แล้วแปลงครึ่งแรกที่มี 1 element ให้เป็น `&mut T` ด้วย `.first_mut()`
   หรือ pattern `&mut half[0]`; หรือถ้าต้องการฝึกเขียน raw pointer เองทั้งหมด ให้ใช้ `slice.as_mut_ptr()` และ
   `&mut *ptr` กับ `slice::from_raw_parts_mut(ptr.add(1), len - 1)` ตามแนวทางเดียวกับหัวข้อ 41.9 เป๊ะ ๆ)

4. **โจทย์ระดับยาก/ประยุกต์ใช้งานจริง**: สมมติคุณกำลังเขียน library ที่มี struct `RingBuffer<T>` (บัฟเฟอร์วงกลม
   ขนาดคงที่ที่ใช้ raw pointer ภายในเพื่อความเร็วสูงสุด แทนการใช้ `VecDeque` ธรรมดา) — จงออกแบบ (ไม่ต้องเขียนโค้ด
   เต็มรูปแบบ แต่ให้เขียน struct definition, signature ของ method หลัก ๆ อย่างน้อย `push`, `pop`, `len`, และเขียน
   `# Safety` doc comment ให้กับทุก `unsafe fn` ที่ปรากฏ) โดยยึดหลักการจากบทนี้ทั้งหมด: (ก) เขียน `unsafe` block
   ให้เล็กที่สุดในทุกจุด (ข) ทุก public method ต้องเป็น safe function (ไม่มี `unsafe` ใน signature สาธารณะเลย)
   (ค) พิสูจน์ในคอมเมนต์ `// SAFETY:` ว่าทำไมแต่ละจุดที่ใช้ raw pointer ปลอดภัย จากนั้นตอบคำถามสั้น ๆ (5-8
   บรรทัด): ถ้าคุณต้องมั่นใจเพิ่มขึ้นว่า implementation ของคุณไม่มี UB ซ่อนอยู่ ก่อนที่จะ publish เป็น crate
   สาธารณะ คุณจะใช้เครื่องมือหรือกระบวนการอะไรเพิ่มเติมบ้าง (อ้างอิงหัวข้อ 41.11)

   (hint: field ที่จำเป็นมักมี `buffer: *mut T` หรือ `Box<[MaybeUninit<T>]>`, `capacity: usize`, `head: usize`,
   `tail: usize`, `len: usize` — จุดที่ต้องระวังที่สุดคือการคำนวณ index แบบ wrap-around ด้วย modulo ที่ต้อง
   ไม่เกิน `capacity` เสมอ และต้องไม่ `pop()` จาก buffer ที่ว่างเปล่า — คำตอบของคำถามท้ายข้อควรพูดถึง Miri อย่าง
   น้อยหนึ่งจุด)

## สรุป

บทนี้เปิด **โมดูล 3: ระดับสูง (Advanced)** ด้วยการเปลี่ยนมุมมองที่ใหญ่ที่สุดของหลักสูตรทั้งหมด: ตลอด 40 บทที่
ผ่านมา เราอยู่ในโลกที่ **compiler พิสูจน์ความปลอดภัยของหน่วยความจำและ concurrency ให้เราแบบอัตโนมัติ 100%** ผ่าน
ระบบ ownership (Part 6), borrowing (Part 7), lifetime (Part 20 และ 23), และ `Send`/`Sync` (Part 40) — บทนี้
เฉลยความจริงที่สำคัญว่า **โลกนั้นมีขอบเขต** และ `unsafe` คือประตูที่ควบคุมอย่างเข้มงวดสำหรับก้าวข้ามขอบเขตนั้น
เมื่อมีความจำเป็นจริง ๆ (การสร้าง safe abstraction อย่าง `Vec`/`Rc`/`Mutex`, FFI, การ optimize ที่ borrow
checker พิสูจน์ให้ไม่ได้)

เรามาทวนประเด็นสำคัญที่สุดของบทนี้อีกครั้ง:

- **`unsafe` ไม่ใช่การ "ปิดกฎ" ของ Rust** มันปลดล็อกได้เฉพาะ **ห้าปฏิบัติการที่ตายตัว** เท่านั้น (dereference
  raw pointer, เรียก unsafe fn, เข้าถึง static mut, implement unsafe trait, เข้าถึง union field) — borrow
  checker, move semantics, และการตรวจสอบ type ส่วนใหญ่ยังทำงานเหมือนเดิมทุกประการแม้ในโค้ดที่มี `unsafe`
- **`unsafe fn` คือสัญญาที่ compiler บังคับให้เขียนแต่ตรวจสอบเนื้อหาให้ไม่ได้** — ภาระการพิสูจน์ precondition
  ตกไปอยู่ที่ผู้เรียกทั้งหมด และ `# Safety` doc (จาก Part 34) คือเครื่องมือเดียวที่สื่อสารสัญญานั้นให้มนุษย์คนอื่น
  เข้าใจได้
- **Undefined behavior อันตรายกว่า compile error เพราะมันไม่พังทันทีเสมอไป** — มันอาจ "ดูเหมือนใช้งานได้" ผ่าน
  ทุก test ที่คิดจะเขียน แล้วพังในสถานการณ์ที่คาดไม่ถึง testing ไม่สามารถพิสูจน์ความไม่มี UB ได้ ต้องใช้การ
  reasoning อย่างรอบคอบ (และเครื่องมือเสริมอย่าง Miri) แทน
- **หลักปรัชญาแกนกลางคือ safe abstraction เหนือ unsafe code**: เขียน `unsafe` เล็ก ๆ ที่พิสูจน์ความปลอดภัยได้
  ครั้งเดียวอย่างรอบคอบ ตรวจสอบ precondition ให้ครบก่อนเข้าสู่ `unsafe` เสมอ แล้วห่อด้วย safe signature ที่ผู้
  เรียกใช้ไม่มีทางเรียกผิดได้เลย — นี่คือกลไกเดียวกันที่ทำให้ `Vec<T>`, `String`, `Rc<T>`, `Mutex<T>` ปลอดภัย
  100% จากมุมมองผู้ใช้ ทั้งที่ภายในมี `unsafe` เต็มไปหมด
- **`split_at_mut` คือตัวอย่างในตำนานที่พิสูจน์ทุกหลักการข้างบนพร้อมกัน**: มันคือฟังก์ชันที่ปลอดภัยจริง 100% ใน
  ทางความหมาย แต่เขียนด้วย safe Rust ล้วน ๆ ไม่ได้เลย เพราะ borrow checker พิสูจน์ไม่ได้ว่าสองครึ่งของ slice
  ไม่ทับกัน — ต้องใช้ raw pointer ที่ผ่านการพิสูจน์โดยมนุษย์ห่อด้วย safe API เพื่อปิดผนึกความปลอดภัยนั้นไว้ให้
  ทุกคนที่เรียกใช้ในอนาคต

**นี่คือคำตอบที่แท้จริงของคำถามใหญ่ที่บทนี้เปิดไว้ตั้งแต่ต้น**: `unsafe` มีอยู่จริงเพราะมีงานที่มีค่าจริงซึ่ง
static analysis ของ borrow checker พิสูจน์ให้ไม่ได้ แต่มนุษย์ที่มีบริบทเพียงพอพิสูจน์ได้ — Rust เลือกที่จะ**เปิด
ประตูนั้นไว้แต่ควบคุมมันให้แคบและตรวจสอบได้ที่สุดเท่าที่จะทำได้** แทนที่จะปิดประตูนั้นไปเลย (แบบภาษาที่มี garbage
collector ล้วน ๆ ซึ่งทำงานระดับ systems programming ไม่ได้เต็มรูปแบบ) หรือเปิดประตูนั้นไว้กว้างตลอดเวลาแบบ C/C++
(ที่ไม่มีแนวคิดเรื่อง "safe" แยกจาก "unsafe" เลยด้วยซ้ำ)

จาก **Part 42: Raw Pointers และ Memory Layout** เป็นต้นไป เราจะกลับไปเจาะลึกสิ่งที่บทนี้แค่ "แนะนำให้รู้จัก"
แบบเบา ๆ (`*const T`, `*mut T`, การคำนวณ pointer arithmetic ด้วย `.add()`/`.offset()`, ความแตกต่างระหว่าง raw
pointer กับ reference ในเชิง memory layout, และเหตุผลที่ raw pointer ไม่มีการันตีเรื่อง lifetime/aliasing แบบ
ที่ reference มี) ให้ครบทุกมุม — ทุกอย่างที่เรียนในบทนี้ (ห้าปฏิบัติการของ `unsafe`, หลักการ safe abstraction,
วิธีอ่าน `# Safety` doc) จะเป็น**พื้นฐานที่ขาดไม่ได้**สำหรับบทนั้น เหมือนที่ Part 20 เป็นรากฐานให้กับเรื่อง
lifetime ที่ซับซ้อนขึ้นตลอดโมดูล 2 — และตามด้วย **Part 43: FFI** ที่จะนำหลักการ "เรียก unsafe fn" จากหัวข้อ
41.4.2 ของบทนี้ไปใช้งานจริงเต็มรูปแบบกับโค้ดภาษา C
