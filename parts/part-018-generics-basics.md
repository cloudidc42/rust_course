# Part 18: Generics เบื้องต้น

> โมดูล: พื้นฐานภาษา Rust (Core Language Fundamentals) | ระดับ: พื้นฐาน | เวลาโดยประมาณ: 200 นาที

## เป้าหมายของบทเรียน

หลังจากจบบทนี้ คุณจะสามารถ:

- อธิบายได้ว่าทำไมการเขียนฟังก์ชันที่ทำงานเหมือนกันทุกประการแต่รับชนิดข้อมูลต่างกัน (เช่น `largest_i32`,
  `largest_char`) ถึงเป็นปัญหาการซ้ำโค้ด (code duplication) ที่แท้จริง และ **generics** แก้ปัญหานี้อย่างไรโดยไม่
  เสียความปลอดภัยของ type system หรือประสิทธิภาพตอน runtime แม้แต่นิดเดียว
- เขียนฟังก์ชัน generic ของตัวเองได้ (`fn largest<T>(...)`) พร้อมเข้าใจว่าทำไม compiler จึงปฏิเสธโค้ดบางแบบด้วย
  error อย่าง `E0369` และรู้จัก **trait bound** ในระดับที่เพียงพอสำหรับบทนี้ (`T: PartialOrd + Copy`) ก่อนที่จะไป
  เจาะลึกความหมายจริงของ trait ใน Part 19
- ออกแบบ struct และ enum แบบ generic ได้เอง ทั้งแบบ type parameter เดียว (`Point<T>`) และหลายตัวที่เป็นอิสระจากกัน
  (`Point<T, U>`) พร้อมเขียน `impl` block ที่ผูกกับ generic ได้อย่างถูกต้อง
- อธิบายได้ว่า `Option<T>` (จาก Part 11) และ `Result<T, E>` (จาก Part 12) ที่ใช้มาตลอดหลักสูตร **ไม่ใช่ของวิเศษ
  ที่ built-in เข้ากับภาษา** แต่เป็น enum ธรรมดาที่ประกาศด้วย syntax generic แบบเดียวกันกับที่คุณเพิ่งเรียนในบทนี้
  ทุกประการ
- เขียน method แบบ generic ที่มี type parameter ของตัวเองแยกจาก type parameter ของ struct ได้ (`fn mixup<U>(...)`
  บน `impl<T> Point<T>`) และอธิบายความแตกต่างระหว่าง type parameter สองระดับนี้ได้ชัดเจน
- อธิบายกลไก **monomorphization** ได้อย่างละเอียดว่า compiler ทำอะไรจริง ๆ กับโค้ด generic ตอน compile time
  และเชื่อมโยงกับคำสัญญา **"zero-cost abstraction"** ที่ถูกพูดถึงตั้งแต่ Part 1 ให้เป็นรูปธรรม พร้อมรู้จัก
  ข้อเสียด้าน code bloat ที่แลกมาด้วย และรู้จัก const generics เบื้องต้น (`Grid<const N: usize>`)

## ความรู้ที่ต้องมีมาก่อน

- **Part 7**: Borrowing และ slice reference (`&[T]`) — ฟังก์ชัน generic ในบทนี้ทุกตัวรับ parameter เป็น `&[T]`
  ตามหลักการที่เรียนมาจาก Part 7-8 ว่าฟังก์ชันควรรับ borrow ไม่ใช่ ownership เมื่อไม่จำเป็นต้องเป็นเจ้าของข้อมูล
- **Part 9**: Structs และ `impl` block — บทนี้ขยาย `struct`/`impl` ที่เรียนมาให้รับ type parameter ได้ ไวยากรณ์
  พื้นฐานของ field และ method ทั้งหมดเหมือนเดิมทุกประการ มีแค่ `<T>` เพิ่มเข้ามา
- **Part 10**: Enums และ pattern matching — `enum` ที่เรียนมาจะถูกขยายให้ variant เก็บ type parameter ได้ ซึ่งคือ
  สิ่งที่ `Option<T>` และ `Result<T, E>` เป็นอยู่แล้วตลอดมา
- **Part 11**: `Option<T>` — คุณใช้ `Option<T>` มาแล้วนับสิบครั้งตั้งแต่ Part 11 โดยไม่รู้ตัวว่ามันคือ generic enum
  ที่คุณเขียนแบบเดียวกันได้เองตั้งแต่บทนี้เป็นต้นไป บทนี้จะเฉลยโครงสร้างจริงของมันให้เห็นตรง ๆ
- **Part 12**: `Result<T, E>` — เช่นเดียวกับ `Option<T>` แต่มี type parameter สองตัว (`T` สำหรับค่าที่สำเร็จ, `E`
  สำหรับ error) ซึ่งเป็นตัวอย่างที่ดีที่สุดของ enum ที่มี **type parameter มากกว่าหนึ่งตัว**
- **Part 13**: `Vec<T>` — บทนี้ (13.11 ในเนื้อหาเดิม) ได้ทีเซอร์ไว้แล้วว่า `Vec<T>` เองก็เป็น generic type ที่จะ
  เรียนอย่างเป็นทางการใน Part 18 — นี่คือ Part 18 ที่ Part 13 พูดถึง และ `Vec<T>` ก็ยังเป็นตัวอย่างที่ดีที่สุดของ
  generic struct ที่ standard library เขียนไว้ให้ใช้แล้ว
- **Part 15**: `HashMap<K, V>` — เช่นเดียวกับ `Vec<T>` แต่เป็นตัวอย่างของ struct ที่มี **type parameter สองตัว**
  (`K` และ `V`) ซึ่งเป็นรูปแบบเดียวกันกับ `Point<T, U>` ที่เราจะเขียนเองในหัวข้อ 18.4

ถ้าสังเกตดี ๆ คุณจะเห็นว่าตั้งแต่ Part 11 เป็นต้นมา **ทุกบทใช้ generics มาโดยตลอดโดยไม่ได้อธิบายว่ามันคืออะไร** —
`Option<T>`, `Result<T, E>`, `Vec<T>`, `String` (ที่จริงคือ `Vec<u8>` แบบพิเศษ), `HashMap<K, V>` ล้วนเป็น generic
type ทั้งสิ้น บทนี้คือจุดที่เราหยุดแล้วถามคำถามที่ค้างมานานว่า **"เครื่องหมาย `<T>` ที่เห็นซ้ำ ๆ ตลอดมานี้ทำงาน
อย่างไร และเราเขียนของแบบนี้เองได้อย่างไร"**

## เนื้อหา

### 18.1 ปัญหาเริ่มต้น: ทำไมการเขียนฟังก์ชันซ้ำสำหรับแต่ละชนิดข้อมูลถึงเป็นปัญหาจริง

ลองจินตนาการว่าคุณกำลังเขียนโปรแกรมที่ต้องหาค่ามากที่สุดในชุดข้อมูลตัวเลข `i32` จำนวนหนึ่ง วิธีที่ตรงไปตรงมาที่สุด
คือเขียนฟังก์ชันขึ้นมาตัวหนึ่ง:

```rust
fn largest_i32(list: &[i32]) -> i32 {
    let mut largest = list[0];

    for &item in list {
        if item > largest {
            largest = item;
        }
    }

    largest
}

fn main() {
    let numbers = vec![34, 50, 25, 100, 65];
    let result = largest_i32(&numbers);
    println!("ตัวเลขที่มากที่สุดคือ {result}");
}
```

ผลลัพธ์:

```
ตัวเลขที่มากที่สุดคือ 100
```

โค้ดนี้ตรงไปตรงมามาก: รับ `&[i32]` ตามหลักการรับ slice ที่เรียนจาก Part 7-8, เริ่มด้วยสมาชิกตัวแรกเป็นค่าเริ่มต้น
ของ `largest`, แล้ววนเทียบทุกตัวว่ามากกว่าค่าที่เก็บไว้หรือไม่ ถ้ามากกว่าก็แทนที่ ทำไปจนครบทุกตัวก็จะได้ค่าที่มาก
ที่สุด — เป็น algorithm ง่าย ๆ ที่ไม่มีอะไรซับซ้อน

ตอนนี้สมมติว่าโปรแกรมเดียวกันต้องหาค่ามากที่สุดของตัวอักษร (`char`) ด้วย เช่นหาตัวอักษรที่มาหลังสุดตามลำดับ ASCII/
Unicode ในชุดข้อมูลหนึ่งชุด คุณจะเขียนฟังก์ชันใหม่ขึ้นมาอีกตัว:

```rust
fn largest_i32(list: &[i32]) -> i32 {
    let mut largest = list[0];

    for &item in list {
        if item > largest {
            largest = item;
        }
    }

    largest
}

fn largest_char(list: &[char]) -> char {
    let mut largest = list[0];

    for &item in list {
        if item > largest {
            largest = item;
        }
    }

    largest
}

fn main() {
    let numbers = vec![34, 50, 25, 100, 65];
    println!("ตัวเลขที่มากที่สุด: {}", largest_i32(&numbers));

    let chars = vec!['y', 'm', 'a', 'q'];
    println!("ตัวอักษรที่มากที่สุด: {}", largest_char(&chars));
}
```

ผลลัพธ์:

```
ตัวเลขที่มากที่สุด: 100
ตัวอักษรที่มากที่สุด: y
```

หยุดดูโค้ดทั้งสองฟังก์ชันนี้ให้ดี ๆ — **เนื้อในของ `largest_i32` และ `largest_char` เหมือนกันทุกตัวอักษร** ต่างกัน
แค่ 3 จุดเท่านั้น: ชื่อฟังก์ชัน, ชนิดข้อมูลใน parameter (`&[i32]` กับ `&[char]`), และชนิดข้อมูลของ return value
(`i32` กับ `char`) ตรรกะการทำงานข้างในเหมือนกันเป๊ะทุกบรรทัด (`let mut largest = list[0];`, วน `for &item in list`,
เทียบด้วย `>`, คืนค่า `largest`)

**นี่คือปัญหาการซ้ำโค้ด (code duplication) ที่แท้จริง** และมันไม่ใช่ปัญหาเล็ก ๆ แค่ "เขียนยาวขึ้นนิดหน่อย" แต่เป็น
ปัญหาเชิงวิศวกรรมซอฟต์แวร์ที่ร้ายแรงในระยะยาว:

1. **ถ้าต้องแก้ algorithm** (เช่น เปลี่ยนจาก "หาค่ามากที่สุด" เป็น "หาค่ามากที่สุดแบบข้าม `None`/ค่าว่าง") ต้องแก้
   **ทุกฟังก์ชันที่ copy กันมา** — ถ้าลืมแก้ตัวใดตัวหนึ่ง จะได้ bug ที่ตรวจจับยากเพราะฟังก์ชันหนึ่งทำงานถูก อีก
   ฟังก์ชันทำงานผิด ทั้ง ๆ ที่ตั้งใจให้ทำงานเหมือนกัน
2. **ยิ่งมีชนิดข้อมูลใหม่เพิ่มขึ้นเรื่อย ๆ ก็ต้อง copy โค้ดเพิ่มเรื่อย ๆ** — ถ้าต้องหาค่ามากที่สุดของ `f64`,
   `u8`, `i64`, หรือ struct ของคุณเอง ก็ต้องเขียน `largest_f64`, `largest_u8`, `largest_i64`, `largest_product`
   ฯลฯ เพิ่มไปเรื่อย ๆ ไม่มีที่สิ้นสุด
3. **compiler ไม่ได้ช่วยยืนยันว่าฟังก์ชันที่ copy กันมาทำงาน "เหมือนกันจริง"** — มันเป็นแค่ข้อความ (text) ที่คุณ
   copy-paste มาด้วยมือ ไม่มีความสัมพันธ์อะไรในสายตา compiler เลยว่าทั้งสองฟังก์ชันนี้ "ควรจะ" เหมือนกัน

สิ่งที่เราต้องการจริง ๆ คือความสามารถในการเขียน **"อัลกอริทึมเดียว ใช้ได้กับหลายชนิดข้อมูล"** โดยที่ compiler ยัง
ตรวจสอบความถูกต้องของ type ให้เต็มรูปแบบเหมือนเดิม ไม่ใช่การเสียสละความปลอดภัยของ type system เพื่อความสั้นของโค้ด
— นี่คือปัญหาที่ **generics** ถูกออกแบบมาเพื่อแก้โดยเฉพาะ

### 18.2 เขียนฟังก์ชัน generic ตัวแรก: จาก error สู่ trait bound

ลองรวมฟังก์ชันทั้งสองเข้าด้วยกันโดยใช้ **type parameter** — เขียนแทนชนิดข้อมูลที่ตายตัว (`i32`, `char`) ด้วยชื่อ
ตัวแปรชนิดข้อมูล (โดยธรรมเนียมนิยมใช้ตัวอักษรตัวเดียวตัวใหญ่ เริ่มจาก `T` ซึ่งมาจากคำว่า "Type") แล้วประกาศไว้ใน
`<...>` ทันทีหลังชื่อฟังก์ชัน:

```rust
fn largest<T>(list: &[T]) -> T {
    let mut largest = list[0];

    for &item in list {
        if item > largest {
            largest = item;
        }
    }

    largest
}

fn main() {
    let numbers = vec![34, 50, 25, 100, 65];
    let result = largest(&numbers);
    println!("ตัวเลขที่มากที่สุดคือ {result}");
}
```

ถ้าคุณลองคาดเดาว่าโค้ดนี้ควรทำงานได้เหมือนสองฟังก์ชันก่อนหน้ารวมกัน — **มันไม่ compile** ครับ compiler จะฟ้อง error
ดังนี้:

```
error[E0369]: binary operation `>` cannot be applied to type `T`
 --> src/main.rs:5:17
  |
5 |         if item > largest {
  |            ---- ^ ------- T
  |            |
  |            T
  |
help: consider restricting type parameter `T` with trait `PartialOrd`
  |
1 | fn largest<T: std::cmp::PartialOrd>(list: &[T]) -> T {
  |             ++++++++++++++++++++++
```

นี่คือจุดที่สำคัญที่สุดของทั้งบทนี้ ลองอ่าน error message ให้เข้าใจจริง ๆ ว่ามันกำลังบอกอะไร: **"การเปรียบเทียบ
ด้วย `>` ใช้กับชนิดข้อมูล `T` ไม่ได้"** ทำไมล่ะ? ในตอนที่เราเขียน `largest_i32` และ `largest_char` แยกกัน compiler
รู้อยู่แล้วว่า `i32` และ `char` **เปรียบเทียบกันด้วย `>` ได้** (เพราะมันเป็นชนิดข้อมูลพื้นฐานที่ Rust implement
ความสามารถนี้ไว้ให้) แต่พอเราเขียน `T` แบบไม่มีเงื่อนไขอะไรเลย compiler ต้องตั้งคำถามว่า **"`T` จะถูกแทนด้วยชนิด
ข้อมูลอะไรก็ได้ในโลกนี้ แล้วชนิดข้อมูลทุกตัวรองรับ `>` จริงหรือ?"** — คำตอบคือ **ไม่จริง** อย่างแน่นอน ลองนึกถึง
`struct Product { name: String, price: f64 }` — การเขียน `product_a > product_b` ควรจะหมายความว่าอะไร? ถ้าเทียบ
ชื่อ (`name`) ตามตัวอักษร? เทียบราคา (`price`)? เทียบทั้งสองอย่างรวมกัน? **ไม่มีคำตอบที่ถูกต้องเสมอไป** สำหรับทุก
struct ที่เป็นไปได้ในโลกนี้ ดังนั้น Rust จึง**ไม่ยอมให้สมมติเอาเองว่า `T` ทุกตัวเปรียบเทียบกันได้** — มันบังคับให้
คุณ**ประกาศเงื่อนไขที่ `T` ต้องมีอย่างชัดเจน**

นี่คือแนวคิดที่เรียกว่า **trait bound** — เราจะเจาะลึกว่า **trait คืออะไรจริง ๆ** ในทุกมิติอย่างเต็มรูปแบบใน
**Part 19** แต่ในบทนี้เราต้องรู้พอเพียงที่จะเขียนโค้ดต่อไปได้ก่อน สำหรับตอนนี้ให้เข้าใจแบบง่ายที่สุดว่า:

- **trait** คือ "ชุดความสามารถ" ที่ชนิดข้อมูลหนึ่ง ๆ อาจมีหรือไม่มีก็ได้ (คล้าย ๆ กับ "ใบรับรอง" ว่าชนิดข้อมูลนี้
  ทำสิ่งนี้ได้)
- **`PartialOrd`** คือ trait ที่แปลว่า **"ชนิดข้อมูลนี้เปรียบเทียบลำดับได้"** (รองรับ `<`, `>`, `<=`, `>=`) —
  ชนิดข้อมูลพื้นฐานอย่าง `i32`, `f64`, `char`, `&str` implement trait นี้ไว้ให้แล้วโดย standard library
- **`Copy`** คือ trait ที่แปลว่า **"ชนิดข้อมูลนี้คัดลอกได้แบบเร็วและถูก โดยไม่ต้องมี ownership ย้ายไปมา"** (จาก
  Part 6 — ชนิดข้อมูลอย่าง `i32`, `f64`, `char`, `bool` เป็น `Copy` แต่ `String`, `Vec<T>` ไม่เป็น เพราะการ copy
  ต้องคัดลอกข้อมูลบน heap ซึ่งไม่ถูกและไม่ควรทำแบบอัตโนมัติ)
- การเขียน **`T: PartialOrd + Copy`** แปลว่า **"`T` จะเป็นชนิดข้อมูลอะไรก็ได้ ตราบใดที่มันเปรียบเทียบลำดับได้
  (`PartialOrd`) และคัดลอกได้แบบถูก (`Copy`) เท่านั้น"** — เป็นการ**จำกัดขอบเขต**ของ `T` ให้แคบลงจาก "อะไรก็ได้
  ในโลกนี้" เป็น "อะไรก็ได้ที่ทำสิ่งที่เราต้องการได้จริง"

มาแก้ฟังก์ชันของเราด้วยความเข้าใจนี้:

```rust
fn largest<T: PartialOrd + Copy>(list: &[T]) -> T {
    let mut largest = list[0];

    for &item in list {
        if item > largest {
            largest = item;
        }
    }

    largest
}

fn main() {
    let numbers = vec![34, 50, 25, 100, 65];
    println!("ตัวเลขที่มากที่สุด: {}", largest(&numbers));

    let chars = vec!['y', 'm', 'a', 'q'];
    println!("ตัวอักษรที่มากที่สุด: {}", largest(&chars));

    let prices = vec![19.99, 5.50, 42.10, 3.25];
    println!("ราคาสูงสุด: {}", largest(&prices));
}
```

ผลลัพธ์:

```
ตัวเลขที่มากที่สุด: 100
ตัวอักษรที่มากที่สุด: y
ราคาสูงสุด: 42.1
```

ตอนนี้เราได้ฟังก์ชัน**เดียว** ที่ใช้กับ `Vec<i32>`, `Vec<char>`, และ `Vec<f64>` ได้ทั้งหมด โดยไม่ต้อง copy-paste
โค้ดแม้แต่บรรทัดเดียว — ถ้าวันหนึ่งต้องแก้ algorithm การหาค่ามากที่สุด ก็แก้ที่เดียวจบ และ compiler ยัง**ตรวจสอบ
type อย่างเข้มงวดเหมือนเดิมทุกประการ** ไม่ได้ผ่อนปรนอะไรเลย — ถ้าคุณลองเรียก `largest(&some_vec_of_products)`
โดยที่ `Product` ไม่ได้ implement `PartialOrd` และ `Copy` ไว้ compiler จะปฏิเสธทันทีตั้งแต่ compile time (เราจะ
เห็น error แบบนี้ชัด ๆ ในหัวข้อ "กับดักที่พบบ่อย") — **generics ไม่ได้ทำให้ type-checking หลวมลงแม้แต่นิดเดียว
มันแค่ทำให้เขียนโค้ดที่ผ่าน type-checking แบบเข้มงวดได้สั้นลงโดยไม่ต้องซ้ำ**

#### สังเกตอะไรบางอย่างที่คุ้นเคยอยู่แล้ว

ถ้าคุณสังเกตดี ๆ syntax `fn largest<T: PartialOrd + Copy>(list: &[T]) -> T` นี้ **ไม่ใช่เรื่องใหม่โดยสิ้นเชิง** —
คุณเคยเห็นวงเล็บมุม `<...>` แบบนี้มาแล้วนับครั้งไม่ถ้วนตลอดหลักสูตร: `Vec<i32>`, `Option<String>`,
`Result<f64, String>`, `HashMap<String, u32>` — ทั้งหมดนี้คือการ **"ใส่ค่าจริงลงใน type parameter"** ของ generic
type ที่คนอื่นเขียนไว้ให้แล้ว (standard library) สิ่งที่บทนี้สอนคือวิธี **สร้าง `<T>` ของตัวเองขึ้นมา** ไม่ใช่แค่
ใช้ของที่มีอยู่แล้ว

### 18.3 Generic struct: `Point<T>` และ `impl` block ที่ผูกกับ generic

หลักการเดียวกันกับฟังก์ชันใช้ได้กับ `struct` ด้วย ลองสร้างชนิดข้อมูลแทนพิกัดจุด (`Point`) ที่เก็บพิกัด `x` และ `y`
โดยที่ยังไม่รู้ (และไม่ต้องรู้) ว่าพิกัดจะเป็นชนิดข้อมูลอะไร — จะเป็นจำนวนเต็ม (`i32`) หรือทศนิยม (`f64`) ก็ได้:

```rust
struct Point<T> {
    x: T,
    y: T,
}

impl<T> Point<T> {
    fn new(x: T, y: T) -> Self {
        Point { x, y }
    }
}

fn main() {
    let integer_point = Point::new(5, 10);
    let float_point = Point::new(1.0, 4.0);

    println!("integer_point: ({}, {})", integer_point.x, integer_point.y);
    println!("float_point: ({}, {})", float_point.x, float_point.y);
}
```

**อธิบายโค้ดทีละส่วน:**

- **`struct Point<T> { x: T, y: T }`** — ประกาศ type parameter `T` ไว้หลังชื่อ struct ทันที (เหมือนที่ทำกับ
  ฟังก์ชัน) แล้วใช้ `T` เป็นชนิดข้อมูลของ field `x` และ `y` **ทั้งสอง field ใช้ `T` ตัวเดียวกัน** ซึ่งหมายความว่า
  **ทั้ง `x` และ `y` ต้องเป็นชนิดข้อมูลเดียวกันเสมอ** (จะเป็น `i32` ทั้งคู่ หรือ `f64` ทั้งคู่ก็ได้ แต่ผสมกันไม่ได้
  — เราจะเห็น error ของกรณีผสมกันในหัวข้อกับดัก)
- **`impl<T> Point<T> { ... }`** — สังเกตว่าต้องประกาศ `<T>` ไว้ **ทั้งหลังคำว่า `impl` และหลังคำว่า `Point`**
  ส่วนแรก (`impl<T>`) คือการประกาศว่า "ในกลุ่ม method ต่อไปนี้ เราจะใช้ตัวแปรชนิดข้อมูลชื่อ `T`" ส่วนที่สอง
  (`Point<T>`) คือการบอกว่า "กำลัง implement ให้กับ `Point` ที่ field เป็นชนิด `T` ตัวนี้แหละ" — ทั้งสองส่วนต้อง
  คู่กันเสมอ ลืมส่วนใดส่วนหนึ่งไปจะ compile ไม่ผ่าน
- **`fn new(x: T, y: T) -> Self`** — `Self` (ตัว S ใหญ่) หมายถึง "ชนิดข้อมูลที่กำลัง impl อยู่นี้" ซึ่งในที่นี้คือ
  `Point<T>` เขียน `Self` แทน `Point<T>` ซ้ำ ๆ ทำให้โค้ดสั้นลงและแก้ชื่อ struct ทีเดียวจบถ้าต้องเปลี่ยนชื่อในอนาคต
- **`Point::new(5, 10)`** — compiler **infer** ได้เองว่า `T` คือ `i32` จากค่า `5` และ `10` ที่ส่งเข้ามา ไม่ต้อง
  เขียน `Point::<i32>::new(5, 10)` แบบยาว (แนวคิด type inference เดียวกับที่เรียนมาตั้งแต่ Part 3)

ผลลัพธ์:

```
integer_point: (5, 10)
float_point: (1, 4)
```

#### `impl` block ที่ผูกกับชนิดข้อมูลจริงเจาะจง (concrete-type-specific methods)

สิ่งที่ทรงพลังของ generics คือคุณสามารถเขียน `impl` block ได้ **หลายแบบซ้อนกัน** — แบบหนึ่งใช้ได้กับ `Point<T>`
ทุกชนิด (generic ล้วน) และอีกแบบใช้ได้กับ `Point<T>` **เฉพาะเมื่อ `T` เป็นชนิดข้อมูลที่ระบุเจาะจง** เท่านั้น:

```rust
struct Point<T> {
    x: T,
    y: T,
}

impl<T> Point<T> {
    fn new(x: T, y: T) -> Self {
        Point { x, y }
    }
}

impl<T: std::fmt::Display> Point<T> {
    fn describe(&self) {
        println!("จุดอยู่ที่ ({}, {})", self.x, self.y);
    }
}

impl Point<f64> {
    fn distance_from_origin(&self) -> f64 {
        (self.x.powi(2) + self.y.powi(2)).sqrt()
    }
}

fn main() {
    let integer_point = Point::new(5, 10);
    integer_point.describe();

    let float_point = Point::new(1.0, 4.0);
    float_point.describe();
    println!("ระยะจากจุดกำเนิด: {}", float_point.distance_from_origin());
}
```

ผลลัพธ์:

```
จุดอยู่ที่ (5, 10)
จุดอยู่ที่ (1, 4)
ระยะจากจุดกำเนิด: 4.123105625617661
```

สังเกตความแตกต่างสำคัญของ `impl` block ทั้งสามแบบนี้:

1. **`impl<T> Point<T>`** — ใช้ได้กับ `Point<T>` **ทุกชนิดข้อมูลไม่มีเงื่อนไข** เหมาะกับ method พื้นฐานที่ไม่
   สนใจว่า `T` เป็นอะไร เช่น `new()`
2. **`impl<T: std::fmt::Display> Point<T>`** — ใช้ได้กับ `Point<T>` **เฉพาะเมื่อ `T` implement trait `Display`
   ได้เท่านั้น** (แปลว่า "พิมพ์ด้วย `{}` ได้") เพราะ `describe()` ต้องพิมพ์ `self.x` และ `self.y` ด้วย `{}` ถ้า
   ไม่มี bound นี้ compiler จะฟ้อง error แบบเดียวกับหัวข้อ 18.2 (แต่คราวนี้เป็นเรื่อง `Display` ไม่ใช่ `PartialOrd`)
3. **`impl Point<f64>`** — **ไม่มี `<T>` เลย** เพราะนี่คือการ implement ให้กับ `Point<f64>` **ตัวเดียวเจาะจง**
   ไม่ใช่ generic อีกต่อไป — `distance_from_origin()` ใช้ `.powi(2)` และ `.sqrt()` ซึ่งเป็น method ของ `f64`
   โดยเฉพาะ (ไม่มีใน `i32`) การเขียนแบบนี้ทำให้ `Point<i32>` **ไม่มี** method `distance_from_origin()` เลย แต่
   `Point<f64>` มี — compiler แยกแยะให้อัตโนมัติตามชนิดข้อมูลจริงที่ใช้จริง

รูปแบบที่ 3 นี้สำคัญมาก: มันแสดงให้เห็นว่า **generic ไม่ได้แปลว่า "ทุกอย่างต้องเป็น generic เท่ากันหมด"** — คุณ
สามารถเขียนโค้ดส่วนที่ใช้ได้กับทุกชนิดข้อมูลแบบ generic (`new`, `describe`) ควบคู่กับโค้ดที่ใช้ได้เฉพาะบางชนิด
ข้อมูล (`distance_from_origin` เฉพาะ `f64`) ในไฟล์เดียวกันได้อย่างกลมกลืน — นี่คือความยืดหยุ่นที่ภาษาที่ไม่มี
generics จริง ๆ (เช่นต้อง copy-paste struct ทุกครั้ง) ทำไม่ได้เลย

### 18.4 ขยายให้เป็นสอง type parameter อิสระจากกัน: `Point<T, U>`

`Point<T>` ในหัวข้อก่อนบังคับว่า `x` และ `y` ต้องเป็นชนิดข้อมูลเดียวกัน แต่ในโลกจริงบางครั้งเราต้องการโครงสร้างที่
เก็บสองค่าที่**เป็นคนละชนิดข้อมูลกันได้อย่างอิสระ** เช่น เก็บชื่อ (`String`) คู่กับอายุ (`u8`) หรือพิกัด `x` เป็น
จำนวนเต็มคู่กับ `y` เป็นทศนิยม วิธีทำคือประกาศ **type parameter สองตัว** แทนตัวเดียว:

```rust
struct Point<T, U> {
    x: T,
    y: U,
}

impl<T, U> Point<T, U> {
    fn new(x: T, y: U) -> Self {
        Point { x, y }
    }
}

fn main() {
    let both_integer = Point::new(5, 10);
    let both_float = Point::new(1.0, 4.0);
    let mixed = Point::new(5, 4.0);
    let strings_and_char = Point::new("สวัสดี", 'ก');

    println!("both_integer: ({}, {})", both_integer.x, both_integer.y);
    println!("both_float: ({}, {})", both_float.x, both_float.y);
    println!("mixed: ({}, {})", mixed.x, mixed.y);
    println!("strings_and_char: ({}, {})", strings_and_char.x, strings_and_char.y);
}
```

ผลลัพธ์:

```
both_integer: (5, 10)
both_float: (1, 4)
mixed: (5, 4)
strings_and_char: (สวัสดี, ก)
```

**อธิบายโค้ดทีละส่วน:**

- **`struct Point<T, U> { x: T, y: U }`** — ประกาศ type parameter สองตัวคั่นด้วยจุลภาค (`T, U`) — ธรรมเนียม
  นิยมทั่วไปเมื่อมีมากกว่าหนึ่งตัวคือใช้ตัวอักษรถัดไปตามลำดับ (`T`, `U`, `V`, ...) หรือชื่อที่สื่อความหมายมากขึ้น
  เช่น `K, V` สำหรับ key-value (ตามที่ `HashMap<K, V>` จาก Part 15 ใช้จริง)
- **`x: T`, `y: U`** — ตอนนี้ `x` ใช้ type parameter ตัวแรก และ `y` ใช้ตัวที่สอง **แยกจากกันโดยสิ้นเชิง** ทำให้
  `x` และ `y` เป็นชนิดข้อมูลอะไรก็ได้ ไม่จำเป็นต้องเหมือนกัน — สังเกตจากตัวแปร `mixed` ที่ `x` เป็น `i32` แต่ `y`
  เป็น `f64` และ `strings_and_char` ที่ `x` เป็น `&str` แต่ `y` เป็น `char`
- **`impl<T, U> Point<T, U>`** — ต้องประกาศ type parameter ทั้งสองตัวใน `impl<...>` ด้วยเสมอ เหมือนหลักการจาก
  หัวข้อ 18.3 แต่คราวนี้มีสองตัว

นี่คือรูปแบบเดียวกันเป๊ะกับ `HashMap<K, V>` ที่คุณใช้มาแล้วใน Part 15 — `K` (key) และ `V` (value) เป็น type
parameter สองตัวที่อิสระจากกันโดยสิ้นเชิง คุณสร้าง `HashMap<String, u32>` (key เป็นข้อความ, value เป็นตัวเลข) หรือ
`HashMap<u32, Vec<String>>` (key เป็นตัวเลข, value เป็น `Vec` ของข้อความ) ได้ตามใจ เพราะ `K` และ `V` ถูกออกแบบมา
เป็นอิสระจากกันตั้งแต่ต้น ด้วยหลักการเดียวกับ `Point<T, U>` ที่เราเพิ่งเขียนเอง

#### พิสูจน์ด้วยขนาดจริงในหน่วยความจำ: type parameter ที่ต่างกันทำให้ได้ type ที่ต่างกันจริง

ลองยืนยันด้วยตัวเลขจริงว่า `Point<i32>`, `Point<f64>`, และ `Point<T, U>` ที่ต่าง concrete type กัน ล้วนเป็นชนิด
ข้อมูลที่ **ต่างกันโดยสิ้นเชิงในสายตา compiler** (ไม่ใช่แค่ "ชื่อเดียวกันแต่พารามิเตอร์ต่างกันเฉย ๆ"):

```rust
struct Point<T> {
    x: T,
    y: T,
}

struct PointXY<T, U> {
    x: T,
    y: U,
}

fn main() {
    println!("size_of Point<i32>  = {} bytes", std::mem::size_of::<Point<i32>>());
    println!("size_of Point<f64>  = {} bytes", std::mem::size_of::<Point<f64>>());
    println!("size_of Point<i8>   = {} bytes", std::mem::size_of::<Point<i8>>());
    println!(
        "size_of PointXY<i32, f64> = {} bytes",
        std::mem::size_of::<PointXY<i32, f64>>()
    );
}
```

ผลลัพธ์บนเครื่อง 64-bit ทั่วไป:

```
size_of Point<i32>  = 8 bytes
size_of Point<f64>  = 16 bytes
size_of Point<i8>   = 2 bytes
size_of PointXY<i32, f64> = 16 bytes
```

ตัวเลขเหล่านี้ยืนยันสิ่งสำคัญที่สุดที่ต้องเข้าใจก่อนไปหัวข้อ 18.7 (monomorphization): **`Point<i32>` และ
`Point<f64>` มีขนาดต่างกันจริง (8 bytes เทียบกับ 16 bytes) เพราะ compiler มองว่ามันเป็นชนิดข้อมูลคนละตัวกันโดย
สิ้นเชิง ไม่ใช่ "แม่แบบเดียวกัน" ที่ใช้ร่วมกันตอน runtime** — `Point<i32>` เก็บ `i32` สองตัว (4 bytes × 2 = 8
bytes) ส่วน `Point<f64>` เก็บ `f64` สองตัว (8 bytes × 2 = 16 bytes) เมื่อคุณเขียน `Point<T>` เพียงครั้งเดียวใน
source code แต่ใช้กับหลายชนิดข้อมูล **compiler จะสร้างชนิดข้อมูลที่เป็นรูปธรรม (concrete type) แยกกันจริง ๆ
สำหรับแต่ละชนิดข้อมูลที่ใช้จริง** — นี่คือแนวคิดตั้งต้นของ monomorphization ที่เราจะเจาะลึกในหัวข้อ 18.7

### 18.5 Generic enum: `Option<T>` และ `Result<T, E>` ไม่ใช่ของวิเศษ

ตอนนี้เราเข้าใจ generic struct และฟังก์ชันแล้ว มาดูว่า **generic enum** ทำงานอย่างไร — และที่สำคัญกว่านั้นคือ มา
เฉลยกันว่า `Option<T>` ที่ใช้มาตั้งแต่ Part 11 และ `Result<T, E>` ที่ใช้มาตั้งแต่ Part 12 นั้น **มีนิยามจริงเป็น
enum ธรรมดาที่เขียนด้วย syntax เดียวกันกับที่คุณเพิ่งเรียนไปหมาด ๆ**

นิยามจริงของทั้งสอง type ใน standard library ของ Rust คือ:

```rust
enum Option<T> {
    Some(T),
    None,
}

enum Result<T, E> {
    Ok(T),
    Err(E),
}
```

เพียงเท่านี้จริง ๆ — ไม่มีอะไรซับซ้อนหรือเป็นเวทมนตร์ที่ built-in เข้ากับ compiler แต่อย่างใด (ยกเว้นสิทธิพิเศษเล็ก
น้อยเช่นการเขียน `None`/`Some`/`Ok`/`Err` ได้โดยไม่ต้องขึ้นต้นด้วยชื่อ enum เพราะถูก re-export ไว้ใน "prelude" —
ชุด type ที่ Rust นำเข้าให้อัตโนมัติทุกไฟล์ ซึ่งเป็นเรื่องความสะดวกในการใช้งาน ไม่ใช่เรื่อง type system) ลองดูว่า
ถ้าเราประกาศ enum ที่มีชื่อและโครงสร้างเดียวกันนี้ขึ้นมาเอง (บังตัว `Option`/`Result` ของ std ไว้ในไฟล์นี้) มันยัง
ใช้งานได้ตรรกะเดียวกันทุกประการหรือไม่:

```rust
// นิยามซ้ำของ Option<T> และ Result<T, E> เพื่อดูโครงสร้างจริงเบื้องหลัง
// (บังตัวจาก std prelude เฉพาะในไฟล์นี้เท่านั้น เพื่อจุดประสงค์ทางการศึกษา)
enum Option<T> {
    Some(T),
    None,
}

enum Result<T, E> {
    Ok(T),
    Err(E),
}

fn divide(a: f64, b: f64) -> Result<f64, String> {
    if b == 0.0 {
        Result::Err(String::from("หารด้วยศูนย์ไม่ได้"))
    } else {
        Result::Ok(a / b)
    }
}

fn find_first_even(numbers: &[i32]) -> Option<i32> {
    for &n in numbers {
        if n % 2 == 0 {
            return Option::Some(n);
        }
    }
    Option::None
}

fn main() {
    match divide(10.0, 2.0) {
        Result::Ok(value) => println!("ผลหาร: {value}"),
        Result::Err(e) => println!("เกิดข้อผิดพลาด: {e}"),
    }

    match find_first_even(&[1, 3, 5, 8, 9]) {
        Option::Some(n) => println!("เจอเลขคู่ตัวแรก: {n}"),
        Option::None => println!("ไม่มีเลขคู่เลย"),
    }
}
```

ผลลัพธ์:

```
ผลหาร: 5
เจอเลขคู่ตัวแรก: 8
```

โค้ดนี้ **ทำงานได้เหมือนกับที่คุณเขียนมาตลอด Part 11-12 ทุกประการ** เพียงแต่ต้องเขียน `Option::Some`,
`Option::None`, `Result::Ok`, `Result::Err` เต็มรูปแบบ (เพราะในไฟล์นี้เราประกาศ enum ของเราเองทับ ปิดสิทธิ์การใช้
ชื่อสั้น ๆ จาก prelude ของ std ไปในตัว) — ในโค้ดจริงที่ใช้ `Option`/`Result` จาก std ตามปกติ (ไม่ได้บังตัวแบบนี้)
คุณเขียน `Some(n)`/`None`/`Ok(value)`/`Err(e)` แบบสั้นได้เลยอย่างที่คุ้นเคย

**นี่คือประเด็นสำคัญที่สุดของหัวข้อนี้**: `Option<T>` คือ enum ที่มี **หนึ่ง type parameter** เก็บอยู่ใน variant
`Some(T)` (ส่วน `None` ไม่เก็บข้อมูลอะไรเลย ไม่เกี่ยวกับ `T`) ส่วน `Result<T, E>` คือ enum ที่มี **สอง type
parameter** — `T` เก็บอยู่ใน `Ok(T)` และ `E` เก็บอยู่ใน `Err(E)` แยกจากกันโดยสิ้นเชิง (เหมือนหลักการ
`Point<T, U>` จากหัวข้อ 18.4 เป๊ะ ๆ) — ทุกครั้งที่คุณเขียน `Option<String>`, `Option<Vec<i32>>`, `Result<u32,
std::io::Error>` คุณกำลัง "ใส่ค่าจริง" ลงใน type parameter ของ enum ธรรมดา ๆ ตัวหนึ่ง ไม่ต่างอะไรจากที่คุณเขียน
`Point::new(5, 10)` เพื่อสร้าง `Point<i32>` เลย

ทำไม Rust เลือกออกแบบให้ "การไม่มีค่า" (`Option`) และ "ความสำเร็จ/ล้มเหลว" (`Result`) เป็น enum ธรรมดาที่ผู้ใช้
เขียนเองได้ ไม่ใช่ feature พิเศษที่ built-in เข้ากับภาษา (เหมือน `null` ในภาษาอื่นที่เป็น keyword พิเศษ)? เหตุผล
เชิงลึกคือ **ความสม่ำเสมอของภาษา (language consistency)** — ถ้า `Option`/`Result` เป็น feature พิเศษที่มีกฎเกณฑ์
ของตัวเอง คุณจะต้องเรียนกฎพิเศษเพิ่มเพื่อเข้าใจมัน แต่เพราะมันเป็น enum ธรรมดาที่ใช้ generics และ pattern
matching แบบเดียวกับที่คุณเรียนไปแล้วทุกประการ **ความรู้เรื่อง enum + generics ที่คุณมีอยู่แล้วครอบคลุมมันได้
ทั้งหมดโดยไม่ต้องเรียนอะไรเพิ่มเลย** — นี่คือปรัชญาการออกแบบที่เรียกว่า **"orthogonality"**: feature พื้นฐานไม่
กี่ตัว (enum, generics, pattern matching) ผสมกันแล้วได้ผลลัพธ์ที่ทรงพลัง แทนการเพิ่ม feature พิเศษเฉพาะทางไปเรื่อย
ๆ ทีละเรื่อง

### 18.6 Generic method ที่มี type parameter ของตัวเอง แยกจาก type parameter ของ struct

หัวข้อนี้คือจุดที่ลึกที่สุดของบทนี้ — เราจะเห็นว่า **method หนึ่งตัวสามารถมี type parameter ของตัวเองเพิ่มเติมได้
โดยไม่ต้องพึ่ง type parameter ของ struct ที่มันอยู่ใน `impl`** ลองกลับไปที่ `Point<T, U>` แล้วเพิ่ม method ชื่อ
`mixup` ที่ทำหน้าที่ **"ผสมพิกัด `x` จาก `Point` ตัวหนึ่งกับพิกัด `y` จาก `Point` อีกตัวหนึ่งที่อาจเป็นคนละชนิด
ข้อมูลกันโดยสิ้นเชิง"**:

```rust
struct Point<T, U> {
    x: T,
    y: U,
}

impl<T, U> Point<T, U> {
    fn new(x: T, y: U) -> Self {
        Point { x, y }
    }

    fn mixup<V, W>(self, other: Point<V, W>) -> Point<T, W> {
        Point {
            x: self.x,
            y: other.y,
        }
    }
}

fn main() {
    let p1 = Point::new(5, 10.4);
    let p2 = Point::new("สวัสดี", 'c');

    let p3 = p1.mixup(p2);

    println!("p3.x = {}, p3.y = {}", p3.x, p3.y);
}
```

ผลลัพธ์:

```
p3.x = 5, p3.y = c
```

**อธิบายโค้ดทีละส่วนอย่างละเอียด เพราะนี่คือจุดที่สับสนบ่อยที่สุด:**

- **`impl<T, U> Point<T, U>`** — `T` และ `U` คือ type parameter ของ **struct `Point`** เอง กำหนดไว้แล้วตั้งแต่
  ตอนสร้าง `Point` ตัวนั้นขึ้นมา (เช่น `p1` มี `T = i32`, `U = f64` เพราะ `Point::new(5, 10.4)`)
- **`fn mixup<V, W>(self, other: Point<V, W>) -> Point<T, W>`** — สังเกตว่า `mixup` ประกาศ type parameter
  **เพิ่มเติมของตัวเอง** คือ `V` และ `W` ไว้หลังชื่อ method โดยตรง (`mixup<V, W>`) — `V` และ `W` นี้ **เป็นคนละ
  ตัวกับ `T` และ `U`** โดยสิ้นเชิง มันคือชนิดข้อมูลของ `other` (พารามิเตอร์ `Point` อีกตัวที่ส่งเข้ามา) ซึ่งอาจ
  เป็นชนิดข้อมูลคนละแบบไปเลยจาก `self`
- **`self` (แบบ `self` ไม่ใช่ `&self`)** — `mixup` รับ `self` ตรง ๆ ไม่ใช่ reference แปลว่า method นี้**ยึด
  ownership ของ `Point` ตัวเดิม (`self`) ไปเลย** (จาก Part 6-7 — เหมือนหลักการที่ `self` แบบไม่มี `&` มักใช้กับ
  method ที่ "แปลงร่าง" ค่าเดิมให้กลายเป็นค่าใหม่ ไม่ต้องใช้ค่าเดิมอีกต่อไป)
- **`-> Point<T, W>`** — ค่าที่คืนกลับมาเป็น `Point` ที่ `x` เป็นชนิดข้อมูลเดิมจาก `self` (`T`) แต่ `y` เป็นชนิด
  ข้อมูลจาก `other` (`W`) — **นี่คือ "การผสม" ที่ชื่อ method บอกไว้ตรง ๆ**: เอา `x` จากตัวแรก ผสมกับ `y` จากตัว
  ที่สอง แม้จะเป็นคนละชนิดข้อมูลกันโดยสิ้นเชิงก็ตาม

ในตัวอย่าง: `p1` คือ `Point<i32, f64>` (`x = 5`, `y = 10.4`) และ `p2` คือ `Point<&str, char>` (`x = "สวัสดี"`,
`y = 'c'`) เมื่อเรียก `p1.mixup(p2)` compiler จับคู่ type parameter ดังนี้: `T = i32`, `U = f64` (จาก `p1`),
`V = &str`, `W = char` (จาก `p2`) ผลลัพธ์คือ `Point<T, W>` = `Point<i32, char>` — เก็บ `x = 5` (จาก `p1.x`) และ
`y = 'c'` (จาก `p2.y`) ตรงกับผลลัพธ์ที่ print ออกมา (`p3.x = 5, p3.y = c`) เป๊ะ

**ทำไมเรื่องนี้ถึงสำคัญ**: มันแสดงให้เห็นว่า generics ใน Rust มี **สองระดับที่เป็นอิสระจากกัน** — ระดับของ
struct/enum เอง (`impl<T, U>`) และระดับของ method แต่ละตัว (`fn mixup<V, W>`) type parameter ของ method ไม่
จำเป็นต้องเกี่ยวข้องอะไรกับ type parameter ของ struct ที่มันสังกัดอยู่เลย มันแค่ "ยืม" พื้นที่ใน signature ของ
method นั้นเพื่อรับชนิดข้อมูลใหม่เข้ามาชั่วคราวสำหรับการเรียกครั้งนั้น ๆ เท่านั้น — ตัวอย่างนี้ (ปรับจากตัวอย่าง
คลาสสิกใน The Rust Programming Language โดย Steve Klabnik และ Carol Nichols) เป็นตัวอย่างที่นักเขียนโปรแกรม Rust
ทุกคนควรเข้าใจให้แน่น เพราะมันคือรากฐานของหลาย pattern ที่จะเจอในโค้ดจริงต่อไป เช่น method `.collect::<Vec<U>>()`
ของ iterator ที่จะเรียนใน Part 25-26 ก็ใช้หลักการ "type parameter ของ method แยกจาก type parameter ของ struct"
แบบเดียวกันนี้

### 18.7 Monomorphization: compiler ทำอะไรจริง ๆ กับโค้ด generic

ตอนนี้เราเขียน generic function, struct, enum, และ method ได้แล้ว มาถึงคำถามที่สำคัญที่สุดในเชิงวิศวกรรม:
**เมื่อโปรแกรม compile และรันจริง เกิดอะไรขึ้นกับโค้ด generic ที่เราเขียน?** คำตอบคือกระบวนการที่เรียกว่า
**monomorphization** (มาจากคำว่า "mono" แปลว่าหนึ่ง และ "morph" แปลว่ารูปแบบ — แปลตรง ๆ ว่า "การทำให้เหลือรูป
แบบเดียว")

#### หลักการของ monomorphization

เมื่อ compiler เจอการเรียกใช้ฟังก์ชัน generic (หรือสร้าง struct/enum generic) ด้วยชนิดข้อมูลที่เป็นรูปธรรม
(concrete type) ตัวหนึ่ง มันจะ **สร้างสำเนาของฟังก์ชัน/struct นั้นขึ้นมาใหม่ทั้งหมด โดยแทน `T` ด้วยชนิดข้อมูลจริง
ตัวนั้นทันที ตั้งแต่ตอน compile time** — พูดง่าย ๆ คือ compiler "เขียนโค้ดที่ไม่มี generics เหลืออยู่เลย" ให้คุณ
โดยอัตโนมัติ ก่อนที่จะแปลงเป็น machine code จริง

ลองกลับไปดูฟังก์ชัน `largest<T: PartialOrd + Copy>` จากหัวข้อ 18.2 ที่เราเรียกใช้กับ `Vec<i32>`, `Vec<char>`, และ
`Vec<f64>` — สิ่งที่ compiler ทำจริง ๆ เบื้องหลัง (แสดงแบบ pseudo-code เพื่อให้เห็นภาพ ไม่ใช่ syntax ที่เขียนได้
จริง) คือมันสร้างฟังก์ชันแยกกันสามตัวขึ้นมาเองโดยที่เราไม่เห็น:

```
fn largest_i32(list: &[i32]) -> i32 { /* เนื้อในเหมือนกันทุกตัวอักษร */ }
fn largest_char(list: &[char]) -> char { /* เนื้อในเหมือนกันทุกตัวอักษร */ }
fn largest_f64(list: &[f64]) -> f64 { /* เนื้อในเหมือนกันทุกตัวอักษร */ }
```

สังเกตว่านี่คือฟังก์ชันแบบเดียวกันกับที่เราเขียนด้วยมือใน **หัวข้อ 18.1** เป๊ะ ๆ! **generics ไม่ได้ทำให้ compiler
"เก่งขึ้น" จนไม่ต้องสร้างโค้ดแยกสำหรับแต่ละชนิดข้อมูล — มันแค่ย้ายงาน "เขียนโค้ดซ้ำ" จากตัวเรา (มนุษย์ที่ต้อง
copy-paste) ไปให้ compiler ทำแทนโดยอัตโนมัติ ตอน compile time** เราเขียนแค่ครั้งเดียว แต่ compiler generate โค้ด
ที่เทียบเท่าการเขียนด้วยมือหลายครั้งให้เราโดยอัตโนมัติและถูกต้องเสมอ (ไม่มีโอกาสพลาดแบบ copy-paste ด้วยมือ)

#### พิสูจน์ด้วยเครื่องมือจริง: มองเข้าไปในไฟล์ binary ที่ compile แล้ว

ข้ออ้างที่ว่า "compiler สร้างสำเนาแยกกันจริง" ไม่ใช่แค่ทฤษฎี เราพิสูจน์ได้จริงด้วยเครื่องมือ `nm` (แสดงรายชื่อ
symbol/ฟังก์ชันที่อยู่ในไฟล์ binary ที่ compile แล้ว) ลองสร้างโปรแกรมที่เรียก `largest` กับ 5 ชนิดข้อมูลต่างกัน
(`i32`, `f64`, `char`, `u8`, `i16`) แล้ว compile ด้วย `rustc` ธรรมดา (build แบบ debug ที่ไม่ inline/optimize
ฟังก์ชันทิ้ง) จากนั้นใช้คำสั่ง:

```
rustc --edition 2021 -C strip=none main.rs -o main
nm -C main | grep "::largest"
```

ผลลัพธ์จริงที่ได้ (สังเกตที่อยู่ในหน่วยความจำ — คอลัมน์ตัวเลขซ้ายสุด — ของแต่ละบรรทัด ต่างกันทั้งหมด):

```
0000000000016260 t main::largest
0000000000016300 t main::largest
00000000000163b0 t main::largest
0000000000016470 t main::largest
0000000000016510 t main::largest
```

**มี symbol ชื่อ `largest` อยู่ 5 ตัวจริง ๆ ในไฟล์ binary** — แต่ละตัวอยู่ที่ตำแหน่งหน่วยความจำต่างกัน (แปลว่าเป็น
ก้อน machine code คนละก้อนกันจริง ไม่ใช่ตัวเดียวกันที่ใช้ร่วมกัน) เทียบกับโปรแกรมที่เรียก `largest` กับ `i32`
เพียงชนิดเดียว ซึ่งจะมี symbol `largest` อยู่แค่ **1 ตัว**:

```
0000000000014700 t main::largest
```

นี่คือหลักฐานที่จับต้องได้ (ไม่ใช่แค่คำอธิบายเชิงทฤษฎี) ว่า **การเรียกฟังก์ชัน generic ตัวเดียวกันด้วยชนิดข้อมูล
ที่ต่างกัน 5 ชนิด ทำให้ได้ machine code แยกกันจริง 5 ก้อนในไฟล์ binary สุดท้าย** — เมื่อตรวจสอบขนาดของแต่ละก้อน
ด้วย `nm -S -C main | grep "::largest"` (ตัวเลือก `-S` แสดงขนาดของแต่ละ symbol) จะพบว่าแต่ละก้อนมีขนาดประมาณ
159-177 bytes ของ machine code (ตัวเลขจะแตกต่างกันเล็กน้อยระหว่างชนิดข้อมูล เพราะคำสั่งเปรียบเทียบ `>` ของ
`i32` กับ `f64` ใช้ instruction คนละชุดกันในระดับ CPU) — ตัวเลขที่แน่นอนอาจต่างกันไปตาม platform, เวอร์ชัน
`rustc`, และ optimization level แต่**หลักการที่ว่า "ยิ่งใช้กับชนิดข้อมูลหลากหลายเท่าไหร่ ยิ่งได้ก้อน machine code
แยกกันมากขึ้นเท่านั้น" เป็นจริงเสมอ** เราจะกลับมาพูดถึงผลกระทบด้านขนาด binary ของเรื่องนี้ในหัวข้อ 18.8

#### เปรียบเทียบวิธีการทำ generic กับภาษาอื่น: นี่คือที่มาของ "zero-cost abstraction"

จาก **Part 1** หลักสูตรนี้ได้กล่าวถึงคำสัญญาของ Rust เรื่อง **"zero-cost abstraction"** — แนวคิดที่ว่า feature
ระดับสูงที่ช่วยให้เขียนโค้ดสั้นและอ่านง่ายขึ้น **ไม่ควรมีต้นทุนด้านประสิทธิภาพตอน runtime เพิ่มขึ้นเลย เมื่อเทียบ
กับการเขียนโค้ดแบบ "ดิบ ๆ" ด้วยมือ** ตอนนั้นอาจฟังดูเป็นคำโฆษณาลอย ๆ แต่ตอนนี้เราพิสูจน์ได้แล้วว่ามันเป็นจริง
สำหรับ generics: **เพราะ compiler สร้างสำเนาโค้ดที่เป็นรูปธรรมสำหรับทุกชนิดข้อมูลตั้งแต่ตอน compile time
โปรแกรมที่ compile แล้วจึง "ไม่รู้ตัว" เลยว่าเคยมี generics อยู่ในนั้น** — เวลาโปรแกรมรันจริง CPU เห็นแค่ก้อน
คำสั่งที่เจาะจงสำหรับ `i32` ก้อนหนึ่ง เจาะจงสำหรับ `f64` อีกก้อนหนึ่ง **ไม่มีการตรวจสอบชนิดข้อมูลตอน runtime
ไม่มีการแปลงชนิดข้อมูล ไม่มี layer พิเศษคั่นกลางแม้แต่นิดเดียว** — เร็วเท่ากับที่คุณเขียน `largest_i32` และ
`largest_f64` แยกกันด้วยมือทุกประการ

มาเทียบกับแนวทางของภาษาอื่นที่แก้ปัญหาเดียวกัน (เขียนโค้ดที่ใช้ได้กับหลายชนิดข้อมูล) ด้วยวิธีที่ต่างกันโดย
สิ้นเชิง:

| ภาษา | กลไก "generic" | เกิดอะไรขึ้นตอน runtime | ต้นทุนด้านประสิทธิภาพ |
|---|---|---|---|
| **Rust** | Monomorphization ตอน compile time | ไม่มี generics เหลืออยู่เลย มีแต่โค้ดเจาะจงชนิดข้อมูลแยกกัน | **ไม่มีเลย** (zero-cost) |
| **Java** | Generics แบบ type erasure | ชนิดข้อมูล generic (`<T>`) ถูก "ลบ" ออกตอน compile เหลือแค่ `Object` แล้วต้อง **cast กลับเป็นชนิดจริงตอน runtime ทุกครั้งที่เข้าถึงค่า** | มีต้นทุนจริง (runtime cast + อาจ boxing ค่า primitive) |
| **Python** | Duck typing (ไม่มี generics แบบ static เลย) | ทุก operation ต้อง **ตรวจสอบชนิดข้อมูลจริงตอน runtime** ก่อนเลือกว่าจะทำอะไร (dynamic dispatch) | มีต้นทุนจริงสูงกว่า Java เพราะเช็คทุก operation ไม่ใช่แค่ตอน cast |
| **C++** | Templates (คล้าย Rust มาก) | Compiler สร้างสำเนาโค้ดแยกกันเหมือนกัน (`template instantiation`) | **ไม่มีเลย** (zero-cost เหมือน Rust — เพราะใช้กลไกคล้ายกัน) |

**อธิบายเชิงลึกของแต่ละแนวทาง:**

- **Java (type erasure)**: เมื่อคุณเขียน `List<Integer>` ใน Java, compiler จะ "ลบ" ข้อมูลชนิด `Integer` ออกไป
  ตอน compile ทำให้ bytecode ที่ได้เก็บแค่ `List` ของ `Object` ธรรมดา ๆ เมื่อคุณดึงค่าออกมาใช้ (`list.get(0)`)
  JVM ต้อง**ตรวจสอบและแปลงชนิดข้อมูล (cast) จาก `Object` กลับเป็น `Integer` ทุกครั้งตอน runtime** — เป็นการ
  ตรวจสอบที่มีต้นทุนจริง (แม้จะเล็ก แต่สะสมได้เมื่อเรียกบ่อย ๆ ในลูปขนาดใหญ่) และยังมีปัญหาเรื่อง "boxing" ค่า
  primitive อย่าง `int` ให้กลายเป็น `Integer` object บน heap เพื่อให้เก็บใน `List<T>` ได้ (เพราะ generic ของ
  Java ใช้กับ primitive type ตรง ๆ ไม่ได้เลย ต้องห่อเป็น object เสมอ)
- **Python (ไม่มี generics แบบ static เลย)**: Python ไม่ต้องประกาศชนิดข้อมูลล่วงหน้าเลย ทุก object เก็บข้อมูล
  ชนิดของตัวเองไว้ (type tag) ตอน runtime ทุกครั้งที่ทำ operation (เช่น `a + b`) Python ต้อง **เช็คชนิดข้อมูล
  จริงของ `a` และ `b` ก่อนเสมอ** แล้วค้นหา method ที่ถูกต้องมาเรียก (เรียกว่า dynamic dispatch) — นี่คือเหตุผล
  หลักที่ Python ช้ากว่า Rust/C++ อย่างมากในงานคำนวณหนัก เพราะการเช็คชนิดข้อมูลนี้เกิดขึ้น **ทุก operation
  ทุกครั้งที่รัน** ไม่ใช่แค่ตอน compile ครั้งเดียวเหมือน Rust
- **C++ (templates)**: นี่คือภาษาที่ใช้แนวทางใกล้เคียง Rust ที่สุด — `template<typename T>` ของ C++ ก็ทำ
  "template instantiation" ซึ่งเป็นแนวคิดเดียวกันกับ monomorphization ของ Rust เกือบทุกประการ (สร้างสำเนาโค้ด
  แยกกันสำหรับแต่ละชนิดข้อมูลที่ใช้จริง) ต่างกันหลัก ๆ ที่ Rust ตรวจสอบ trait bound (`T: PartialOrd + Copy`)
  **ตั้งแต่ตอนเขียนฟังก์ชัน generic เลย** (แจ้ง error ทันทีถ้า `T` ไม่รองรับ operation ที่ใช้ — อย่างที่เห็นใน
  `E0369` ที่หัวข้อ 18.2) ในขณะที่ C++ (ก่อนมี concepts ใน C++20) จะตรวจสอบ**ตอนที่มีการเรียกใช้ template จริง
  เท่านั้น** ทำให้ error message ของ C++ template มักซับซ้อนและอ่านยากกว่ามาก เพราะชี้ไปที่จุดที่เรียกใช้ ไม่ใช่
  จุดที่นิยาม template

จุดที่ต้องเน้นย้ำให้ชัดคือ **Rust ไม่ได้เป็นภาษาเดียวที่ทำ zero-cost generics ได้ (C++ ก็ทำได้)** แต่ **Rust ทำได้
โดยไม่ต้องแลกกับความปลอดภัยของ type ที่ตรวจสอบตอน compile time แบบเข้มงวด** (ผ่าน trait bound ที่ต้องประกาศไว้
ชัดเจนตั้งแต่ตอนนิยามฟังก์ชัน) — ในขณะที่ Java/Python เลือกแนวทางอื่นที่มีต้นทุน runtime แลกกับความง่ายในการ
implement compiler (type erasure ของ Java ง่ายกว่าการทำ monomorphization เต็มรูปแบบมาก) หรือความยืดหยุ่นสูงสุด
(dynamic typing ของ Python ไม่ต้องประกาศชนิดข้อมูลอะไรเลย แต่แลกมาด้วยการเช็คทุกอย่างตอน runtime)

#### เห็นภาพ "ชนิดข้อมูลที่ compiler เลือกใช้จริง" ด้วย `type_name`

เพื่อให้เห็นภาพว่า ณ จุดที่ compiler ทำ monomorphization แต่ละครั้ง มันรู้ชนิดข้อมูลที่เป็นรูปธรรมแน่นอนแล้วเสมอ
(ไม่มีความกำกวมเหลืออยู่ตอน runtime) เราใช้ `std::any::type_name::<T>()` ซึ่งเป็นฟังก์ชันช่วยเหลือสำหรับการ debug
ที่คืนชื่อชนิดข้อมูลจริงของ `T` ณ จุดนั้นออกมาเป็นข้อความ:

```rust
fn show_type<T>(_value: &T) {
    println!("T ที่ compiler เลือกใช้จริงคือ: {}", std::any::type_name::<T>());
}

fn main() {
    show_type(&5i32);
    show_type(&5.0f64);
    show_type(&"สวัสดี");
}
```

ผลลัพธ์:

```
T ที่ compiler เลือกใช้จริงคือ: i32
T ที่ compiler เลือกใช้จริงคือ: f64
T ที่ compiler เลือกใช้จริงคือ: &str
```

แม้ในซอร์สโค้ดเราจะเขียน `show_type<T>` เพียงครั้งเดียว แต่ ณ **ทุกจุดที่เรียกใช้จริง** compiler รู้อยู่แล้วว่า
`T` คือชนิดข้อมูลอะไรกันแน่ (ไม่มีทางที่ `T` จะ "ไม่รู้ว่าเป็นชนิดไหน" หลงเหลืออยู่ตอนโปรแกรมรันจริง) — นี่คือ
รากฐานที่ทำให้ monomorphization เป็นไปได้ตั้งแต่แรก: **generics ของ Rust ถูกแทนที่ด้วยชนิดข้อมูลจริงเสมอ
ตั้งแต่ compile time ไม่ใช่แนวคิดที่ "ลอยอยู่" จนถึง runtime แบบที่ Python ทำ**

### 18.8 ข้อเสียของ monomorphization: code bloat และเมื่อไหร่ที่ต้องคิดถึงมัน

ทุกการออกแบบมีข้อแลกเปลี่ยน (trade-off) เสมอ — zero-cost abstraction ของ monomorphization ก็มีต้นทุนซ่อนอยู่
เช่นกัน แม้จะไม่ใช่ต้นทุนด้าน**เวลา**ตอน runtime แต่เป็นต้นทุนด้าน**ขนาดของไฟล์ binary** ที่ compile ออกมา

ย้อนกลับไปดูตัวอย่าง `nm` ในหัวข้อ 18.7 — เมื่อเรียก `largest` กับ 5 ชนิดข้อมูล เราได้ machine code แยกกัน 5 ก้อน
แต่ละก้อนขนาดประมาณ 160-180 bytes รวมแล้วประมาณ 800 bytes เทียบกับการเรียกด้วยชนิดข้อมูลเดียวที่ได้แค่ก้อนเดียว
ขนาดประมาณ 160 bytes — **ยิ่งเรียกฟังก์ชัน generic เดียวกันด้วยชนิดข้อมูลที่หลากหลายมากเท่าไหร่ ขนาดของไฟล์
binary สุดท้ายก็ยิ่งใหญ่ขึ้นตามจำนวนชนิดข้อมูลที่ใช้จริง** (ไม่ใช่ขนาดคงที่แบบที่ฟังก์ชันธรรมดาที่ไม่ใช่ generic
เป็น) ปรากฏการณ์นี้เรียกว่า **code bloat**

ในตัวอย่างเล็ก ๆ อย่าง `largest` ที่มีเนื้อในไม่กี่บรรทัด 800 bytes เทียบกับ 160 bytes ไม่ใช่เรื่องน่ากังวลอะไรเลย
แต่ลองจินตนาการสถานการณ์ที่ขยายใหญ่ขึ้น:

1. **ฟังก์ชัน generic ที่มีเนื้อในซับซ้อนมาก** (หลายร้อยบรรทัด, เรียกฟังก์ชันอื่นซ้อนกันหลายชั้น) — ถ้าถูกเรียก
   ด้วยชนิดข้อมูล 20 ชนิดในโปรแกรมเดียว ก็จะได้สำเนาโค้ดซับซ้อนนั้น 20 ชุดฝังอยู่ใน binary ทั้งหมด
2. **generic struct ที่มี method จำนวนมาก** ถูกใช้กับ struct ของผู้ใช้เองหลายสิบชนิด (เช่น `Vec<T>` ที่มี method
   นับสิบตัว ถูกใช้เป็น `Vec<Product>`, `Vec<Order>`, `Vec<Customer>`, ... ในโปรแกรมขนาดใหญ่) — ทุก method ของ
   `Vec<T>` ที่ถูกเรียกจริงกับแต่ละชนิดข้อมูล จะถูก monomorphize แยกกันหมด
3. **Generic function ที่เรียก generic function อื่นซ้อนกันเป็นชั้น ๆ** — การ bloat อาจทวีคูณกันได้ (ฟังก์ชัน A
   เรียก B เรียก C ทั้งหมดเป็น generic ถ้า A ถูกใช้กับ 10 ชนิดข้อมูล และแต่ละครั้งเรียก B, C ต่อ ก็อาจได้สำเนา
   ของ B และ C มากถึง 10 ชุดเช่นกัน)

ผลกระทบที่เกิดขึ้นจริงจาก code bloat มีทั้งขนาดไฟล์ binary ที่ใหญ่ขึ้น (สำคัญมากในระบบ embedded ที่มีพื้นที่จัด
เก็บจำกัด หรือโปรแกรมที่ต้อง download ผ่านเครือข่ายบ่อย ๆ) และเวลา compile ที่นานขึ้น (compiler ต้อง generate
และ optimize โค้ดหลายสำเนาแยกกันจริง ๆ ไม่ใช่แค่ครั้งเดียว) รวมถึงอาจกระทบ **instruction cache** ของ CPU ในบาง
สถานการณ์ (โค้ดที่กระจัดกระจายเป็นหลายสำเนามากเกินไป อาจทำให้ CPU cache โค้ดได้ไม่มีประสิทธิภาพเท่าโค้ดก้อนเดียว
ที่ใช้ร่วมกัน — แม้ในทางปฏิบัติผลกระทบนี้มักเล็กน้อยกว่าประโยชน์ที่ได้จากการไม่มี runtime dispatch overhead
มากในกรณีส่วนใหญ่)

**ทางเลือกอื่นที่ Rust มีให้เมื่อขนาด binary สำคัญกว่าความเร็วดิบ**: Rust ไม่ได้บังคับให้ใช้ monomorphization
เสมอไป — มันมีอีกกลไกหนึ่งเรียกว่า **`dyn Trait`** (trait object) ที่ทำงานคล้าย type erasure ของ Java มากกว่า
(ใช้ตัวชี้ไปยัง vtable แทนการสร้างสำเนาโค้ด ทำให้มีโค้ดอยู่ **ก้อนเดียว** ที่ใช้ร่วมกันสำหรับทุกชนิดข้อมูล แลก
กับ**ต้นทุน runtime เล็กน้อย**จากการเรียกผ่าน pointer พิเศษ) เราจะเรียนเรื่องนี้แบบเต็มรูปแบบใน **Part 21** —
สำหรับตอนนี้ให้จำหลักการไว้ก่อนว่า **Rust ให้คุณเลือกได้ทั้งสองทาง**: `T: Trait` แบบ generic (เร็วที่สุด แต่
อาจทำให้ binary ใหญ่ขึ้นถ้าใช้กับชนิดข้อมูลหลากหลายมาก) หรือ `dyn Trait` (โค้ดกะทัดรัดกว่า แลกกับ overhead
เล็กน้อยตอน runtime) — เป็นการตัดสินใจเชิงวิศวกรรมที่ต้องเลือกให้เหมาะกับสถานการณ์จริง ไม่มีคำตอบที่ถูกเสมอไป
ทางเดียว

### 18.9 Const generics เบื้องต้น: parameter ที่เป็นค่าคงที่ ไม่ใช่ชนิดข้อมูล

ตลอดบทนี้ type parameter ที่เราเขียน (`T`, `U`, `V`) ทุกตัวแทน **"ชนิดข้อมูล"** แต่ Rust ยังมี generics อีกแบบ
หนึ่งที่ parameter แทน **"ค่าคงที่ (constant value)"** ไม่ใช่ชนิดข้อมูล เรียกว่า **const generics** — จำได้ว่า
จาก **Part 3 และ Part 13** เราเรียนว่า array (`[T; N]`) มีความยาว `N` ที่ต้องเป็นค่าคงที่ตายตัวตอน compile time
เสมอ (ต่างจาก `Vec<T>` ที่ปรับขนาดได้ตอน runtime) const generics คือความสามารถที่ทำให้คุณเขียน struct ที่ **มี
ขนาด array เป็น parameter ที่ปรับได้** โดยยังคงความปลอดภัยและประสิทธิภาพของ array ตายตัวไว้ครบทุกประการ:

```rust
struct Grid<const N: usize> {
    cells: [i32; N],
}

impl<const N: usize> Grid<N> {
    fn new() -> Self {
        Grid { cells: [0; N] }
    }

    fn sum(&self) -> i32 {
        self.cells.iter().sum()
    }

    fn len(&self) -> usize {
        N
    }
}

fn main() {
    let mut small_grid: Grid<4> = Grid::new();
    small_grid.cells[0] = 10;
    small_grid.cells[3] = 5;
    println!(
        "small_grid: len = {}, sum = {}",
        small_grid.len(),
        small_grid.sum()
    );

    let big_grid: Grid<9> = Grid::new();
    println!("big_grid: len = {}, sum = {}", big_grid.len(), big_grid.sum());
}
```

ผลลัพธ์:

```
small_grid: len = 4, sum = 15
big_grid: len = 9, sum = 0
```

**อธิบายโค้ดทีละส่วน:**

- **`struct Grid<const N: usize>`** — แทนที่จะเขียน `<T>` (type parameter) เราเขียน **`<const N: usize>`** —
  คำว่า `const` บอก compiler ว่า `N` ไม่ใช่ชนิดข้อมูล แต่เป็น **ค่าคงที่ชนิด `usize`** ที่ต้องรู้ตายตัวตอน
  compile time (เหมือนความยาว array ตามหลักการจาก Part 3)
- **`cells: [i32; N]`** — ใช้ `N` เป็นความยาวของ array ได้ตรง ๆ เหมือน `N` เป็นตัวเลขธรรมดา (ในทางเทคนิคมันคือ
  ตัวเลขธรรมดาจริง ๆ ตอน compile time เพียงแต่ยังไม่ตัดสินใจว่าเป็นค่าเท่าไหร่จนกว่าจะรู้ว่าจะสร้าง `Grid`
  ขนาดไหน)
- **`Grid<4>`, `Grid<9>`** — ตอนใช้งานจริง เราใส่ **ตัวเลข** ลงในวงเล็บมุมตรง ๆ (ไม่ใช่ชนิดข้อมูลแบบ `Grid<i32>`)
  — `Grid<4>` และ `Grid<9>` เป็นชนิดข้อมูลที่ **ต่างกันโดยสิ้นเชิงในสายตา compiler** เหมือนกับที่ `Point<i32>`
  และ `Point<f64>` เป็นชนิดข้อมูลต่างกัน (ตามหลักการ monomorphization จากหัวข้อ 18.7 — const generics ก็ผ่าน
  กระบวนการ monomorphization แบบเดียวกัน คือ compiler สร้างสำเนาโค้ดแยกกันสำหรับทุกค่า `N` ที่ใช้จริง)
- **`fn len(&self) -> usize { N }`** — `N` ใช้งานได้ตรง ๆ ในเนื้อ method เหมือนตัวแปรค่าคงที่ธรรมดา เพราะ ณ
  จุดที่ compiler ทำ monomorphization มันรู้ค่า `N` ที่แน่นอนแล้วเสมอ (เหมือนที่ `T` ถูกแทนด้วยชนิดข้อมูลจริง)

เพราะ `Grid<4>` และ `Grid<9>` เป็นชนิดข้อมูลคนละตัวกัน การพยายามส่ง `Grid<9>` เข้าไปในฟังก์ชันที่รับ `&Grid<4>`
โดยตรงจะ **compile ไม่ผ่าน**:

```rust
struct Grid<const N: usize> {
    cells: [i32; N],
}

fn total(grid: &Grid<4>) -> i32 {
    grid.cells.iter().sum()
}

fn main() {
    let grid: Grid<9> = Grid { cells: [0; 9] };
    println!("{}", total(&grid));
}
```

```

  --> src/main.rs:11:26

   |                    ----- ^^^^^ expected `4`, found `9`
   |                    |
   |                    arguments to this function are incorrect
   |
   = note: expected reference `&Grid<4>`
              found reference `&Grid<9>`
note: function defined here
 --> src/main.rs:5:4
  |
5 | fn total(grid: &Grid<4>) -> i32 {
  |    ^^^^^ --------------
```

Error message ยืนยันตรงตัวว่า **"expected `4`, found `9`"** — compiler เห็น `Grid<4>` และ `Grid<9>` เป็นชนิด
ข้อมูลที่เข้ากันไม่ได้เลย เหมือนกับที่ `i32` และ `f64` เข้ากันไม่ได้ นี่คือประโยชน์สำคัญของ const generics: **มัน
ทำให้ "ขนาด" กลายเป็นส่วนหนึ่งของการตรวจสอบ type ตอน compile time** ทำให้บั๊กประเภท "ขนาดไม่ตรงกัน" (เช่น พยายาม
เอาข้อมูลจาก grid ขนาด 9 ไปใส่ในฟังก์ชันที่ออกแบบมาสำหรับ grid ขนาด 4) ถูกจับได้ตั้งแต่ก่อนโปรแกรมรันจริงเสียอีก
ตัวอย่าง const generics ที่ใช้จริงในโลกการเขียนโปรแกรม Rust ที่คุณอาจเจอในอนาคต ได้แก่ library คำนวณเมทริกซ์/
เวกเตอร์ทางคณิตศาสตร์ที่ใช้ `Matrix<const R: usize, const C: usize>` เพื่อบังคับให้การคูณเมทริกซ์ที่ขนาดไม่ตรง
กันถูกปฏิเสธตั้งแต่ compile time โดยไม่ต้องเช็คขนาดตอน runtime เลย

const generics เป็นหัวข้อที่ลึกได้อีกมาก (เช่น การคำนวณ expression ซับซ้อนกับ `N` ใน const context, การใช้ร่วม
กับ trait bound) แต่สำหรับบทนี้ในระดับ "เบื้องต้น" ขอให้จำแค่หลักการสำคัญไว้พอ: **`<const N: usize>` คือ
generics ที่ parameter เป็นค่าคงที่ ไม่ใช่ชนิดข้อมูล และมันก็ผ่านกระบวนการ monomorphization แบบเดียวกันกับ type
parameter ทุกประการ** — เพียงพอที่จะจำ syntax นี้ได้เมื่อเจอในโค้ดจริงหรือใน error message ต่อไป

### 18.10 ตัวอย่างจริง: ระบบวิเคราะห์ข้อมูลที่ใช้ generic function/struct ตัวเดียวกันกับข้อมูลหลายประเภท

มาปิดท้ายด้วยตัวอย่างที่ผสมทุกอย่างที่เรียนมาในบทนี้เข้าด้วยกัน ในสถานการณ์ใกล้เคียงงานจริง: ระบบวิเคราะห์ข้อมูล
พื้นฐานที่ต้อง **หาค่าสูงสุด/ต่ำสุด** จากชุดข้อมูลตัวเลขหลายประเภทที่ไม่เกี่ยวข้องกันเลย — อุณหภูมิ (`f64`),
คะแนนสอบ (`i32`), ราคาสินค้าที่ดึงมาจาก `Vec<Product>` (`f64`), และค่าที่มี "ป้ายชื่อ" กำกับไว้ด้วย (generic
struct `Reading<T>`)

```rust
// ระบบวิเคราะห์ข้อมูลง่าย ๆ ที่ใช้ generic function/struct ตัวเดียวกันกับข้อมูลหลายชนิด
#[derive(Debug, Clone, Copy)]
struct Reading<T> {
    label: &'static str,
    value: T,
}

impl<T> Reading<T> {
    fn new(label: &'static str, value: T) -> Self {
        Reading { label, value }
    }
}

// ฟังก์ชัน generic คู่หนึ่งที่ใช้ได้กับข้อมูลตัวเลขชนิดใดก็ได้ที่ "เทียบกันได้" และ "คัดลอกได้เร็ว"
fn find_max<T: PartialOrd + Copy>(items: &[T]) -> Option<T> {
    let mut iter = items.iter();
    let mut max = *iter.next()?;
    for &item in iter {
        if item > max {
            max = item;
        }
    }
    Some(max)
}

fn find_min<T: PartialOrd + Copy>(items: &[T]) -> Option<T> {
    let mut iter = items.iter();
    let mut min = *iter.next()?;
    for &item in iter {
        if item < min {
            min = item;
        }
    }
    Some(min)
}

// generic function ที่ทำงานบน Reading<T> โดยตรง เทียบค่า .value ของแต่ละตัว
fn find_max_reading<T: PartialOrd + Copy>(readings: &[Reading<T>]) -> Option<Reading<T>> {
    let mut iter = readings.iter();
    let mut max = *iter.next()?;
    for &r in iter {
        if r.value > max.value {
            max = r;
        }
    }
    Some(max)
}

struct Product {
    name: String,
    price: f64,
    quantity: u32,
}

fn main() {
    // ใช้กับอุณหภูมิ (f64)
    let temperatures = vec![28.5, 31.2, 26.8, 33.9, 29.0];
    println!(
        "อุณหภูมิ: สูงสุด = {:?}, ต่ำสุด = {:?}",
        find_max(&temperatures),
        find_min(&temperatures)
    );

    // ใช้กับคะแนนสอบ (i32) — ฟังก์ชันเดียวกัน ไม่ต้องเขียนใหม่
    let scores = vec![88, 95, 72, 100, 67];
    println!(
        "คะแนนสอบ: สูงสุด = {:?}, ต่ำสุด = {:?}",
        find_max(&scores),
        find_min(&scores)
    );

    // ใช้กับราคาสินค้า (f64) จาก Vec<Product> — ต้องดึง .price ออกมาก่อนเป็น Vec<f64>
    let products = vec![
        Product { name: String::from("ปากกา"), price: 12.0, quantity: 50 },
        Product { name: String::from("สมุด"), price: 35.0, quantity: 20 },
        Product { name: String::from("ยางลบ"), price: 5.0, quantity: 100 },
    ];
    for p in &products {
        println!("สินค้า: {} ราคา {} บาท คงเหลือ {} ชิ้น", p.name, p.price, p.quantity);
    }
    let prices: Vec<f64> = products.iter().map(|p| p.price).collect();
    println!(
        "ราคาสินค้า: สูงสุด = {:?}, ต่ำสุด = {:?}",
        find_max(&prices),
        find_min(&prices)
    );

    // ใช้ Reading<T> ห่อค่าพร้อม label แล้วหา reading ที่ค่ามากที่สุด กับข้อมูล 2 ชนิดต่างกัน
    let temp_readings = vec![
        Reading::new("เช้า", 24.5),
        Reading::new("บ่าย", 33.1),
        Reading::new("เย็น", 29.7),
    ];
    if let Some(hottest) = find_max_reading(&temp_readings) {
        println!("ช่วงเวลาที่ร้อนที่สุด: {} ({} °C)", hottest.label, hottest.value);
    }

    let stock_readings = vec![
        Reading::new("ปากกา", 50u32),
        Reading::new("สมุด", 20u32),
        Reading::new("ยางลบ", 100u32),
    ];
    if let Some(most_stocked) = find_max_reading(&stock_readings) {
        println!(
            "สินค้าที่มีสต็อกมากที่สุด: {} ({} ชิ้น)",
            most_stocked.label, most_stocked.value
        );
    }
}
```

ผลลัพธ์:

```
อุณหภูมิ: สูงสุด = Some(33.9), ต่ำสุด = Some(26.8)
คะแนนสอบ: สูงสุด = Some(100), ต่ำสุด = Some(67)
สินค้า: ปากกา ราคา 12 บาท คงเหลือ 50 ชิ้น
สินค้า: สมุด ราคา 35 บาท คงเหลือ 20 ชิ้น
สินค้า: ยางลบ ราคา 5 บาท คงเหลือ 100 ชิ้น
ราคาสินค้า: สูงสุด = Some(35.0), ต่ำสุด = Some(5.0)
ช่วงเวลาที่ร้อนที่สุด: บ่าย (33.1 °C)
สินค้าที่มีสต็อกมากที่สุด: ยางลบ (100 ชิ้น)
```

**อธิบายจุดสำคัญของตัวอย่างนี้:**

- **`find_max`/`find_min` เขียนครั้งเดียว ใช้กับ 3 ชุดข้อมูลที่ไม่เกี่ยวข้องกันเลย** (`Vec<f64>` ของอุณหภูมิ,
  `Vec<i32>` ของคะแนนสอบ, `Vec<f64>` ที่ดึงมาจาก field `.price` ของ `Vec<Product>`) — นี่คือคำตอบของปัญหาที่
  เราเริ่มบทนี้ด้วยในหัวข้อ 18.1 พอดี: ไม่ต้องเขียน `find_max_temperature`, `find_max_score`, `find_max_price`
  แยกกันสามฟังก์ชันอีกต่อไป
- **`find_max` คืนค่าเป็น `Option<T>` ไม่ใช่ `T` ตรง ๆ** — สังเกตว่าเราออกแบบให้คืน `None` ถ้า slice ที่รับเข้า
  มาว่างเปล่า (ผ่าน `?` operator กับ `iter.next()` ที่คืน `Option<&T>` — เชื่อมกับหลักการจาก **Part 11-12**
  โดยตรง) ต่างจากฟังก์ชัน `largest` ในหัวข้อ 18.1-18.2 ที่ยัง panic ได้ถ้า `list` ว่างเปล่า (เพราะ `list[0]`
  ใช้ indexing ตรง ๆ) — นี่คือตัวอย่างที่ดีว่า generics กับ `Option<T>` ทำงานร่วมกันได้อย่างเป็นธรรมชาติ ไม่มี
  ความขัดแย้งอะไรเลยระหว่างสองแนวคิดนี้
- **`Reading<T>` คือ generic struct ที่ "ห่อ" ค่าตัวเลขไว้พร้อมป้ายชื่อ (`label`)** — ใช้กับ `T = f64`
  (`temp_readings`) และ `T = u32` (`stock_readings`) ในโปรแกรมเดียวกัน โดยไม่ต้องเขียน struct แยกกันสองแบบ
  (`TemperatureReading`, `StockReading`) เลย — สอดคล้องกับหลักการ generic struct จากหัวข้อ 18.3-18.4
- **`find_max_reading<T: PartialOrd + Copy>` เทียบค่าที่ field `.value` ของ `Reading<T>` ตรง ๆ** ไม่ได้ derive
  `PartialOrd` ให้ `Reading<T>` เอง (เพราะการเทียบ `Reading` ทั้งตัวโดยอัตโนมัติจะเทียบ `label` ก่อน `value`
  ตามลำดับ field ซึ่งไม่ตรงกับความหมายที่เราต้องการ คือ "reading ไหนมีค่ามากที่สุด" ไม่ใช่ "label ไหนมาก่อน
  ตามตัวอักษร") นี่คือตัวอย่างการเลือก **bound ให้ตรงกับความหมายทางธุรกิจจริง** ไม่ใช่การใส่ `derive` มัดรวมทุก
  อย่างโดยไม่คิด

ตัวอย่างนี้แสดงให้เห็นภาพรวมของบททั้งบท: **generic function** (`find_max`, `find_min`, `find_max_reading`),
**generic struct** (`Reading<T>`), **trait bound ที่เลือกให้ตรงกับความหมายที่ต้องการจริง** (`PartialOrd + Copy`),
และ **การนำ `Option<T>` จาก Part 11 มาผสมกับ generics แบบเป็นธรรมชาติ** — ทั้งหมดนี้คือสิ่งที่ทำให้ Rust เขียน
โค้ดที่ปลอดภัย นำกลับมาใช้ใหม่ได้ และยังเร็วเท่าโค้ดที่เขียนแยกด้วยมือทุกประการ (ตามหลักการ monomorphization ที่
เรียนในหัวข้อ 18.7)

### 18.11 syntax เสริม: `where` clause เมื่อรายการ trait bound ยาวเกินไป

ก่อนปิดเนื้อหา มีอีกหนึ่ง syntax ที่ควรรู้จักไว้ เพราะจะเจอบ่อยมากในโค้ด Rust จริงและใน error message ที่ compiler
แนะนำ — เมื่อฟังก์ชัน generic ต้องการ trait bound หลายตัวพร้อมกัน (เช่นต้องการทั้ง `PartialOrd`, `Copy`, และ
`Display`) การเขียน bound ทั้งหมดไว้ในวงเล็บมุมเดียวกันอย่างที่ทำมาตลอดบทนี้ (`T: PartialOrd + Copy + Display`)
จะเริ่มอ่านยากเมื่อมี type parameter หลายตัวและ bound หลายเงื่อนไข Rust จึงมี syntax อีกแบบเรียกว่า **`where`
clause** ที่ย้ายรายการ bound ทั้งหมดไปเขียนแยกไว้หลังชื่อฟังก์ชัน ทำให้ signature หลักอ่านง่ายขึ้น:

```rust
use std::fmt::Display;

fn describe_and_compare<T>(a: T, b: T) -> String
where
    T: PartialOrd + Copy + Display,
{
    if a > b {
        format!("{a} มากกว่า {b}")
    } else if a < b {
        format!("{a} น้อยกว่า {b}")
    } else {
        format!("{a} เท่ากับ {b}")
    }
}

fn main() {
    println!("{}", describe_and_compare(10, 20));
    println!("{}", describe_and_compare(3.5, 1.2));
}
```

ผลลัพธ์:

```
10 น้อยกว่า 20
3.5 มากกว่า 1.2
```

`fn describe_and_compare<T>(a: T, b: T) -> String where T: PartialOrd + Copy + Display { ... }` มีความหมาย
**เหมือนกันทุกประการ** กับการเขียน `fn describe_and_compare<T: PartialOrd + Copy + Display>(a: T, b: T) -> String
{ ... }` — ไม่มีความแตกต่างด้าน behavior หรือประสิทธิภาพเลยแม้แต่นิดเดียว (compiler มองสองแบบนี้เหมือนกันเป๊ะ
ตอนตรวจสอบ type และตอนทำ monomorphization) ต่างกันแค่**ความอ่านง่าย**เมื่อ signature ซับซ้อนขึ้น: `where` แยก
"ฟังก์ชันนี้ทำอะไร รับอะไร คืนอะไร" (บรรทัดแรก) ออกจาก "เงื่อนไขที่ type parameter ต้องมี" (บรรทัดถัดไป) ทำให้
อ่านทีละส่วนได้ชัดเจนกว่า โดยเฉพาะเมื่อมี type parameter หลายตัวที่แต่ละตัวต้องการ bound ต่างกัน — เรื่องนี้จะ
กลับมาสำคัญอีกครั้งอย่างเป็นทางการใน **Part 22 (Generics ขั้นสูง)** ที่ชื่อหัวข้อบอกตรง ๆ ว่ามี "where clauses"
เป็นส่วนหนึ่งของเนื้อหา — สำหรับบทนี้ขอให้แค่จำได้ว่าเมื่อเจอ syntax `where` ใน error message หรือโค้ดคนอื่น มัน
คือ trait bound แบบเดียวกับที่เราเขียนมาตลอดบทนี้ เพียงจัดวางตำแหน่งต่างออกไปเท่านั้น

## กับดักที่พบบ่อย (Common Pitfalls)

**1. ใช้ generic function/struct กับชนิดข้อมูลที่ไม่รองรับ operation ที่ต้องการ (ลืมว่า trait bound คือสัญญา
ที่ต้องรักษา)**

โค้ดนี้ดูเผิน ๆ เหมือนไม่มีอะไรผิด แต่จะ compile ไม่ผ่านทันทีที่ struct ของเราไม่รองรับการเปรียบเทียบด้วย `>`:

```rust
struct Temperature(f64);

fn main() {
    let morning = Temperature(24.5);
    let afternoon = Temperature(33.1);

    if afternoon > morning {
        println!("บ่ายร้อนกว่าเช้า");
    }
}
```

```

 --> src/main.rs:7:18
  |
7 |     if afternoon > morning {
  |        --------- ^ ------- Temperature
  |        |
  |        Temperature
  |
note: an implementation of `PartialOrd` might be missing for `Temperature`
 --> src/main.rs:1:1
  |
1 | struct Temperature(f64);
  | ^^^^^^^^^^^^^^^^^^ must implement `PartialOrd`
help: consider annotating `Temperature` with `#[derive(PartialEq, PartialOrd)]`
  |
1 + #[derive(PartialEq, PartialOrd)]
2 | struct Temperature(f64);
  |
```

**เหตุผลเชิงลึก**: นี่คือ error ตัวเดียวกันกับ `E0369` ที่เราเห็นในหัวข้อ 18.2 เป๊ะ — struct ของเราเอง
(`Temperature`) ไม่ได้ implement `PartialOrd` ไว้ (เพราะ compiler ไม่รู้ว่าเราต้องการให้เทียบด้วยอะไร ถ้า struct
มีหลาย field มันก็ไม่มีทางเดารูปแบบการเทียบที่ "ถูกต้อง" ให้เองได้) ปัญหานี้จะเกิดซ้ำแล้วซ้ำอีกทุกครั้งที่คุณส่ง
struct ของตัวเองเข้าไปในฟังก์ชัน generic ที่ต้องการ `PartialOrd` (เช่น `find_max` จากหัวข้อ 18.10) โดยไม่ได้
เตรียม struct ให้พร้อมก่อน

**วิธีแก้**: เติม `#[derive(PartialEq, PartialOrd)]` เหนือ struct ตามที่ compiler แนะนำ (ต้องมี `PartialEq`
ควบคู่ไปด้วยเสมอ เพราะ `PartialOrd` ต้องพึ่งพา `PartialEq`) — สำหรับ tuple struct ที่มี field เดียวแบบนี้ การ
derive จะเทียบตามค่าใน field นั้นตรง ๆ ให้อัตโนมัติ:

```rust
#[derive(PartialEq, PartialOrd)]
struct Temperature(f64);

fn main() {
    let morning = Temperature(24.5);
    let afternoon = Temperature(33.1);

    if afternoon > morning {
        println!("บ่ายร้อนกว่าเช้า");
    }
}
```

**2. ลืมว่า generic struct ที่ใช้ type parameter ตัวเดียวกันหลาย field บังคับให้ทุก field ต้องเป็นชนิดข้อมูล
เดียวกัน**

```rust
struct Box2D<T> {
    width: T,
    height: T,
}

fn main() {
    let b = Box2D { width: 10, height: 3.5 };
    println!("{} x {}", b.width, b.height);
}
```

```
error[E0308]: mismatched types
 --> src/main.rs:7:40
  |
7 |     let b = Box2D { width: 10, height: 3.5 };
  |                                        ^^^ expected integer, found floating-point number
```

**เหตุผลเชิงลึก**: `struct Box2D<T> { width: T, height: T }` ใช้ `T` **ตัวเดียวกัน** สำหรับทั้งสอง field ตาม
หลักการจากหัวข้อ 18.3 — เมื่อ compiler เห็น `width: 10` มันตัดสินใจว่า `T = i32` (ค่าเริ่มต้นของ integer literal
ที่ไม่มี suffix กำกับ) ไปแล้ว พอเจอ `height: 3.5` ที่เป็น floating-point มันจึงขัดแย้งกับ `T = i32` ที่ตัดสินไว้
ก่อนหน้าทันที นี่ไม่ใช่ข้อจำกัดที่ไม่มีเหตุผล แต่เป็นไปตามนิยามที่**เราเองเป็นคนกำหนด**ไว้ในการประกาศ struct

**วิธีแก้**: ถ้าต้องการให้ `width` และ `height` เป็นชนิดข้อมูลต่างกันได้อย่างอิสระ ต้องใช้ type parameter สองตัว
แยกกันตามหลักการจากหัวข้อ 18.4 (`struct Box2D<T, U> { width: T, height: U }`) แต่ถ้าตั้งใจให้เป็นชนิดข้อมูล
เดียวกันจริง ๆ (ซึ่งมักสมเหตุสมผลกว่าสำหรับพิกัด/ขนาดที่ควรเทียบกันได้) ก็แค่ทำให้ค่าที่ส่งเข้ามาเป็นชนิดเดียวกัน
เช่น `Box2D { width: 10.0, height: 3.5 }` หรือ `Box2D { width: 10, height: 4 }`

**3. ประกาศ type parameter ที่ไม่ได้ใช้งานจริงใน field ไหนเลยของ struct**

```rust
struct Wrapper<T> {
    label: String,
}

fn main() {
    println!("compiled");
}
```

```
error[E0392]: type parameter `T` is never used
 --> src/main.rs:1:16
  |
1 | struct Wrapper<T> {
  |                ^ unused type parameter
  |
  = help: consider removing `T`, referring to it in a field, or using a marker such as `PhantomData`
  = help: if you intended `T` to be a const parameter, use `const T: /* Type */` instead
```

**เหตุผลเชิงลึก**: นี่เป็นข้อผิดพลาดที่มักเกิดตอนกำลังออกแบบ struct แล้วยังไม่ได้ใส่ field ที่ใช้ `T` จริง ๆ
(อาจกำลังเขียนไปเรื่อย ๆ แล้วลืมกลับมาใส่ หรือตั้งใจให้ `T` เป็นแค่ "หมวดหมู่" โดยไม่มีข้อมูลจริงเก็บอยู่) Rust
ปฏิเสธ struct แบบนี้เพราะ `T` ที่ไม่ถูกใช้เลยทำให้ compiler ไม่รู้ว่าจะ monomorphize (ตามหลักการหัวข้อ 18.7)
อย่างไร — มันไม่มีข้อมูลจริงของชนิด `T` เก็บอยู่ใน struct เลยสักไบต์ จึงไม่มีความหมายทาง memory layout ให้ยึด

**วิธีแก้**: ทางที่ตรงไปตรงมาที่สุดคือเพิ่ม field ที่ใช้ `T` จริง ๆ:

```rust
struct Wrapper<T> {
    label: String,
    value: T,
}
```

ถ้าตั้งใจจริง ๆ ที่จะให้ `T` เป็นแค่ "ป้ายกำกับประเภท" โดยไม่มีข้อมูลเก็บอยู่จริง (เช่นใช้แยกแยะ `Wrapper<Meters>`
กับ `Wrapper<Feet>` เป็นคนละชนิดข้อมูลกัน ทั้งที่ข้างในเก็บแค่ตัวเลขเหมือนกัน) จะต้องใช้ `std::marker::PhantomData`
ซึ่งเป็นเทคนิคขั้นสูงกว่าที่จะเจาะลึกใน **Part 22** — สำหรับตอนนี้จำไว้แค่ว่า error นี้เกิดขึ้นเพื่อป้องกันการ
ประกาศ type parameter ที่ไม่มีความหมายอะไรเลยในทาง memory โดยไม่ตั้งใจ

**4. เรียก generic function โดยไม่มี context เพียงพอให้ compiler infer type parameter ได้**

```rust
fn make_empty<T>() -> Vec<T> {
    Vec::new()
}

fn main() {
    let v = make_empty();
    println!("{:?}", v);
}
```

```
error[E0282]: type annotations needed for `Vec<_>`
 --> src/main.rs:6:9
  |
6 |     let v = make_empty();
  |         ^   ------------ type must be known at this point
  |
help: consider giving `v` an explicit type, where the type for type parameter `T` is specified
  |
6 |     let v: Vec<T> = make_empty();
  |          ++++++++
```

**เหตุผลเชิงลึก**: ต่างจากตัวอย่าง `Point::new(5, 10)` ในหัวข้อ 18.3 ที่ compiler infer `T = i32` ได้ทันทีจาก
argument ที่ส่งเข้ามา ฟังก์ชัน `make_empty<T>()` **ไม่มี parameter เลย** — ไม่มีค่าอะไรให้ compiler ดูเพื่อเดา
ว่า `T` ควรเป็นอะไร ส่วน `println!("{:?}", v)` ก็ debug-print ได้กับทุกชนิดข้อมูลที่ implement `Debug` เหมือนกัน
จึงไม่ช่วยจำกัดขอบเขตของ `T` ให้แคบลงได้เลย compiler จึงต้อง**หยุดและถามกลับ**ว่าจริง ๆ แล้วต้องการ `T` เป็นอะไร
กันแน่ แทนที่จะเดาแบบสุ่มเสี่ยง

**วิธีแก้**: มีสองวิธีหลักที่ใช้กันทั่วไปในโค้ด Rust จริง — วิธีแรกคือกำหนด type annotation ตรง ๆ ที่ตัวแปร:

```rust
let v: Vec<i32> = make_empty();
```

วิธีที่สองคือใช้ **turbofish syntax** (`::<...>`) ระบุ type parameter ให้ฟังก์ชันตรง ๆ ตอนเรียก:

```rust
let v2 = make_empty::<String>();
```

turbofish (ชื่อเล่นของ syntax `::<>` เพราะรูปร่างคล้ายปลาพอง) เป็นวิธีที่สะดวกเมื่อไม่ต้องการประกาศ type ที่ตัวแปร
ตรง ๆ เช่นตอนเรียกฟังก์ชัน generic แบบ chain method ต่อกันหลายตัว (`"42".parse::<i32>()` ที่คุณอาจเคยเห็นมาแล้ว
ตั้งแต่ Part 12 ก็คือ turbofish แบบเดียวกันนี้เอง)

**5. ย้าย (move) ค่า generic `T` ที่ไม่ใช่ `Copy` ออกจาก slice/Vec โดยตรง**

```rust
fn first<T>(list: Vec<T>) -> T {
    list[0]
}

fn main() {
    let names = vec![String::from("Alice"), String::from("Bob")];
    let first_name = first(names);
    println!("{first_name}");
}
```

```
error[E0507]: cannot move out of index of `Vec<T>`
 --> src/main.rs:2:5
  |
2 |     list[0]
  |     ^^^^^^^ move occurs because value has type `T`, which does not implement the `Copy` trait
  |
help: if `T` implemented `Clone`, you could clone the value
 --> src/main.rs:1:10
  |
1 | fn first<T>(list: Vec<T>) -> T {
  |          ^ consider constraining this type parameter with `Clone`
2 |     list[0]
  |     ------- you could clone this value
```

**เหตุผลเชิงลึก**: `list[0]` คือการ indexing ที่พยายามดึงค่าออกมา**เป็นเจ้าของ (by value)** — จาก **Part 6** เรา
เรียนว่าการดึงค่าออกจากตำแหน่งกลาง collection แบบนี้ทำได้ก็ต่อเมื่อชนิดข้อมูลนั้นเป็น `Copy` (คัดลอกได้ทันทีโดย
ไม่ต้องยึด ownership จากที่เก็บเดิม) ถ้า `T` ไม่ใช่ `Copy` (เช่น `String` ที่ต้องดูแล heap buffer ของตัวเอง)
compiler ต้อง**ย้าย ownership** ออกมาจริง ๆ ซึ่งจะทำให้ `Vec<T>` เหลือ "ช่องว่าง" อยู่ตรงตำแหน่งนั้น — สถานะแบบนี้
เป็นสิ่งที่ Rust ไม่อนุญาตให้เกิดขึ้นได้เลย (จะทำลาย invariant ที่ว่าทุกตำแหน่งใน `Vec` ต้องมีค่าที่ถูกต้องเสมอ)
สังเกตว่าฟังก์ชัน `largest<T: PartialOrd + Copy>` ในหัวข้อ 18.2 ต้องมี bound `Copy` ก็เพราะเหตุผลเดียวกันนี้เป๊ะ
(`let mut largest = list[0];` ก็คือการดึงค่าออกมาแบบเดียวกัน)

**วิธีแก้**: ถ้าไม่ต้องการยึด ownership ของ `Vec` ทั้งก้อน ให้เปลี่ยนไปรับ `&[T]` แล้วคืน reference (`&T`) แทน
ตามหลักการ borrowing จาก Part 7 แต่ถ้าจำเป็นต้องคืนค่าเป็นเจ้าของจริง ๆ และ `T` ไม่ใช่ `Copy` ให้เพิ่ม bound
`Clone` แล้วใช้ `.clone()` แทน indexing ตรง ๆ:

```rust
fn first<T: Clone>(list: Vec<T>) -> T {
    list[0].clone()
}
```

`.clone()` ทำสำเนาข้อมูล (รวมถึงคัดลอก heap buffer ถ้าจำเป็น เช่นกรณี `String`) แทนการย้าย ownership ออกจาก
ตำแหน่งเดิม จึงไม่ทำให้ `Vec` เหลือช่องว่างที่ไม่มีค่า — แลกกับต้นทุนการคัดลอกข้อมูลจริงที่มากกว่า `Copy` (ตาม
หลักการต้นทุนของ `Clone` เทียบกับ `Copy` ที่เรียนมาจาก Part 6)

## แบบฝึกหัด (Exercises)

1. **[ง่าย]** เขียนฟังก์ชัน generic ชื่อ `fn count_matching<T: PartialEq>(list: &[T], target: &T) -> usize` ที่
   นับว่าใน `list` มีสมาชิกที่**เท่ากับ** `target` กี่ตัว (ใช้ operator `==` ซึ่งต้องการ trait `PartialEq` — trait
   ที่ให้ความสามารถ "เทียบว่าเท่ากันหรือไม่" ต่างจาก `PartialOrd` ที่ให้ความสามารถ "เทียบลำดับมาก-น้อย") จากนั้น
   ทดสอบเรียกฟังก์ชันนี้กับ `Vec<i32>` (นับจำนวนเลขที่ซ้ำกับค่าหนึ่ง) และ `Vec<&str>` (นับจำนวนคำที่ซ้ำกับคำหนึ่ง)
   ในโปรแกรมเดียวกัน
   (hint: วน `for item in list` แล้วเทียบ `item == target` เพิ่มตัวนับทีละ 1 ถ้าเท่ากัน สังเกตว่าฟังก์ชันนี้
   **ไม่ต้องการ bound `Copy`** เลย เพราะไม่มีการดึงค่าออกมาเป็นเจ้าของที่ไหนเลย มีแต่การเทียบค่าผ่าน reference)

2. **[กลาง]** ออกแบบ generic struct ชื่อ `Pair<T>` ที่เก็บค่าสองตัวชนิดเดียวกัน (`first: T`, `second: T`) พร้อม
   `impl<T: PartialOrd + Copy> Pair<T>` ที่มี method `fn larger(&self) -> T` คืนค่าที่มากกว่าระหว่าง `first` กับ
   `second` จากนั้นทดสอบสร้าง `Pair<i32>` และ `Pair<f64>` แล้วเรียก `.larger()` ทั้งคู่ พิมพ์ผลลัพธ์ให้เห็นชัดเจน
   (hint: เขียน `impl<T> Pair<T> { fn new(first: T, second: T) -> Self { ... } }` แยกไว้อีก block หนึ่งสำหรับ
   `new()` ที่ไม่ต้องมี bound อะไรเลย ตามรูปแบบที่เห็นในหัวข้อ 18.3 ที่มีหลาย `impl` block ซ้อนกันสำหรับเงื่อนไข
   ต่างกัน ส่วน method `larger` ให้เทียบด้วย `if self.first > self.second { self.first } else { self.second }`)

3. **[ยาก]** โค้ดต่อไปนี้ compile ไม่ผ่าน (ละเมิดกฎเดียวกับหัวข้อ 18.3 เรื่อง generic struct ที่ใช้ type
   parameter ตัวเดียวกันในหลาย field) ให้แก้ไขให้ compile ผ่านได้ **2 วิธีที่แตกต่างกัน** (วิธีที่ 1: เปลี่ยนเป็น
   type parameter สองตัวอิสระจากกันตามหลักการหัวข้อ 18.4, วิธีที่ 2: ทำให้ค่าที่ส่งเข้ามาเป็นชนิดข้อมูลเดียวกัน
   จริง ๆ) แล้วอธิบายด้วยคำพูดของตัวเองสัก 2-3 บรรทัดว่าทั้งสองวิธีนี้เหมาะกับสถานการณ์ที่ต่างกันอย่างไร:
   ```rust
   struct Range<T> {
       start: T,
       end: T,
   }

   fn main() {
       let r = Range { start: 0, end: 9.5 };
       println!("{} to {}", r.start, r.end);
   }
   ```
   (hint: ดูตัวอย่าง error message และวิธีแก้ทั้งสองแบบในกับดักที่พบบ่อยข้อ 2 แล้วปรับชื่อ field ให้ตรงกับโจทย์นี้
   — ลองคิดว่า "ช่วงตัวเลข" (range) ที่ `start` และ `end` เป็นชนิดข้อมูลต่างกันได้จริง ๆ สมเหตุสมผลในโลกจริง
   หรือไม่ เทียบกับ "จุดพิกัด" ที่ `x` กับ `y` ควรเป็นชนิดเดียวกันเสมอ)

4. **[ยาก/ประยุกต์]** ขยายตัวอย่างระบบวิเคราะห์ข้อมูลในหัวข้อ 18.10 โดยเพิ่มฟังก์ชัน generic ใหม่ชื่อ
   `fn average<T>(items: &[T]) -> f64` ที่คำนวณค่าเฉลี่ยของข้อมูลตัวเลขใน `items` แล้วคืนผลลัพธ์เป็น `f64` เสมอ
   (ไม่ว่า `T` จะเป็น `i32`, `u32`, หรือ `f64` ก็ตาม) จากนั้นทดสอบเรียกกับข้อมูลอุณหภูมิ คะแนนสอบ และราคาสินค้าจาก
   หัวข้อ 18.10 ทั้งสามชุด พร้อมพิมพ์ผลลัพธ์ให้ชัดเจนว่าค่าเฉลี่ยของแต่ละชุดคือเท่าไหร่
   (hint: การคำนวณค่าเฉลี่ยต้อง**บวก**สมาชิกทุกตัวเข้าด้วยกันก่อน ซึ่งต้องการ trait bound เพิ่มเติมที่ยังไม่ได้
   เรียนอย่างเป็นทางการในบทนี้ — ลองใช้ `T: Into<f64> + Copy` (trait `Into` แปลงชนิดข้อมูลหนึ่งเป็นอีกชนิดได้
   ซึ่งชนิดข้อมูลตัวเลขพื้นฐานอย่าง `i32`/`u32`/`f64` implement ไว้ให้แล้วสำหรับแปลงเป็น `f64`) แล้ววน `for &item
   in items` แปลงแต่ละตัวด้วย `item.into()` สะสมเป็น `f64` ก่อนหารด้วย `items.len() as f64` ท้ายสุด — ถ้ายังไม่
   คุ้นกับ `Into` มากนัก ไม่ต้องกังวล เราจะเจาะลึก trait จากมุมมองที่ครบถ้วนกว่านี้มากใน Part 19 ข้อนี้เป็นแค่การ
   ให้เห็นตัวอย่างว่า trait bound มากกว่าหนึ่งตัวใช้ร่วมกันได้เสมอ เขียนคั่นด้วย `+`)

## สรุป

บทนี้เริ่มจากปัญหาที่จับต้องได้จริง: การเขียนฟังก์ชัน `largest_i32` และ `largest_char` ที่มีตรรกะเหมือนกันทุก
ประการแต่ต้อง copy-paste แยกกันเพราะรับชนิดข้อมูลต่างกัน — **generics** แก้ปัญหานี้ด้วยการให้เขียน type
parameter (`<T>`) แทนชนิดข้อมูลที่ตายตัว เราเห็นว่าการเขียน `fn largest<T>` แบบไม่มีเงื่อนไขจะ compile ไม่ผ่าน
(`E0369`) เพราะไม่ใช่ทุกชนิดข้อมูลเปรียบเทียบกันได้ ซึ่งนำไปสู่ความเข้าใจเบื้องต้นเรื่อง **trait bound**
(`T: PartialOrd + Copy`) ก่อนจะไปเจาะลึกความหมายจริงของ trait อย่างเต็มรูปแบบใน Part 19

เราขยายหลักการเดียวกันไปสู่ **generic struct** (`Point<T>`, `Point<T, U>`) พร้อมเห็นว่า `impl` block เขียนได้
หลายแบบซ้อนกัน (generic ล้วน, generic ที่มี bound, หรือเจาะจงชนิดข้อมูลตายตัว) แล้วเฉลยความจริงที่ซ่อนอยู่ตลอด
หลักสูตรว่า **`Option<T>` (Part 11) และ `Result<T, E>` (Part 12) ก็เป็นแค่ enum ธรรมดาที่เขียนด้วย syntax
generics แบบเดียวกันนี้เอง** ไม่มีอะไรวิเศษซ่อนอยู่เบื้องหลังเลย จากนั้นเราเรียน **generic method ที่มี type
parameter ของตัวเอง** (`fn mixup<V, W>`) ซึ่งเป็นพื้นฐานสำคัญของ pattern ที่จะเจอซ้ำ ๆ ในโค้ด Rust ระดับสูงต่อไป

หัวใจสำคัญที่สุดของบทนี้คือ **monomorphization** — เราพิสูจน์ด้วยเครื่องมือจริง (`nm`) ว่า compiler สร้างสำเนา
โค้ดที่เป็นรูปธรรมแยกกันจริงสำหรับทุกชนิดข้อมูลที่ใช้จริง ตั้งแต่ตอน compile time ทำให้ generics ของ Rust มี
**ต้นทุนตอน runtime เท่ากับศูนย์** ต่างจาก type erasure ของ Java (ต้อง cast ตอน runtime) และ dynamic typing ของ
Python (ต้องเช็คชนิดข้อมูลทุก operation) นี่คือคำสัญญา **zero-cost abstraction** จาก Part 1 ที่กลายเป็นรูปธรรม
ให้เห็นจริงในบทนี้ พร้อมทั้งรู้จักข้อเสียที่แลกมา — **code bloat** เมื่อฟังก์ชัน generic ถูกใช้กับชนิดข้อมูล
หลากหลายมาก ๆ ซึ่งเป็นเหตุผลที่ Rust มี `dyn Trait` เป็นทางเลือกสำรองที่จะเรียนใน Part 21

ปิดท้ายด้วย **const generics** เบื้องต้น (`Grid<const N: usize>`) ที่ทำให้ "ขนาด" กลายเป็นส่วนหนึ่งของการ
ตรวจสอบ type ได้ และตัวอย่างระบบวิเคราะห์ข้อมูลจริงที่ผสม generic function (`find_max`, `find_min`), generic
struct (`Reading<T>`), trait bound ที่เลือกให้ตรงกับความหมายทางธุรกิจ, และ `Option<T>` เข้าด้วยกันอย่างเป็น
ธรรมชาติ

ใน **Part 19** เราจะย้อนกลับไปตอบคำถามที่บทนี้เปิดไว้อย่างเป็นทางการเต็มรูปแบบ: **trait คืออะไรจริง ๆ**,
`PartialOrd`/`Copy`/`Display`/`Clone` ที่เราแค่ "หยิบมาใช้" ในบทนี้มีนิยามอย่างไร, และที่สำคัญที่สุดคือ **เราจะ
สร้าง trait ของตัวเองได้อย่างไร** — ความเข้าใจเรื่อง generics ที่แน่นจากบทนี้ทั้งหมด (โดยเฉพาะ trait bound และ
`impl<T: SomeTrait>`) จะเป็นฐานสำคัญที่ทำให้ Part 19 เข้าใจง่ายขึ้นอย่างมาก เพราะ syntax ที่เห็นซ้ำ ๆ (`<T:
Trait>`) จะไม่ใช่เรื่องใหม่อีกต่อไป มีแค่ความหมายของ "Trait" ที่จะลึกซึ้งขึ้นเท่านั้น
